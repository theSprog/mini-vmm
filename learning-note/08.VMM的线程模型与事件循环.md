# 卷八：VMM 的线程模型与事件循环

<!-- learning-note/08.VMM的线程模型与事件循环.md -->

本卷讲 mini-vmm 里“谁在哪个线程上做什么”：vCPU 线程只跑 `KVM_RUN` 和处理 exit，一个 epoll I/O 线程负责所有后端 fd，两类线程通过设备模型和锁会合。对应里程碑 `event-loop`，代码在 `include/io/event_loop.h`、`src/io/event_loop.c`、`src/console.c`、`src/main.c`。停机协调（`vm_request_stop`、`immediate_exit`）见卷六第 6 节，`io_lock` 的来历见卷六第 6.5 节。

## 1. 要解决的问题

VMM 里有两类完全不同的“等待”：

- vCPU 线程等的是 guest：它阻塞在 `ioctl(KVM_RUN)` 里，guest 执行 HLT 时睡在 KVM 的 `kvm_vcpu_block`，有中断要注入时被唤醒。
- 后端等的是 host：终端有没有按键、TAP 有没有收到包、磁盘读请求有没有完成。

如果把后者放进 vCPU 线程，例如 guest 读串口 RBR 时 VMM 去 `read(stdin)`，那么 host 没有输入时这个 vCPU 就停在 `read` 里，guest 里这颗 CPU 整个卡死，连时钟中断都处理不了。正确的分工是：后端数据由别的线程准备好放进设备模型（串口 RX FIFO、网卡 RX ring），然后拉中断线；vCPU 线程访问寄存器时只读设备模型里已有的状态，永远不等 host。

对照：

| | 每个后端一个阻塞读线程（这一里程碑之前的 console 线程） | 一个 epoll I/O 线程 |
|---|---|---|
| 线程数 | 后端数 + vCPU 数 + 主线程 | 1 + vCPU 数 + 主线程 |
| 停机 | 阻塞在 `read` 里的线程唤不醒，只能 detach 后随进程一起消失 | 写一个 eventfd，I/O 线程从 `epoll_wait` 返回，`pthread_join` |
| 加新后端 | 再开一个线程，再想一遍它和其他线程的锁 | 注册一个 fd 和回调，所有回调天然串行 |
| stdin 是 `/dev/null` | `read` 立即返回 0，线程悄悄退出 | `epoll_ctl` 报 EPERM，启动时明确打印“guest 输入被关闭” |

QEMU 的 main loop（`util/main-loop.c` 加 AioContext）和 kvmtool 的 `epoll` 线程是同一个思路。mini-vmm 只取最小的那部分：一个线程、水平触发、回调表。

## 2. 结构

```text
            ┌──────────── 主线程 (comm "vmm") ────────────┐
            │ evl_init → console_start(注册 stdin)        │
            │ → evl_start → vm_run(join vCPU) → evl_stop  │
            └─────────────────────────────────────────────┘
                         │ 创建                │ 创建
                         ▼                     ▼
   ┌─────── I/O 线程 (comm "io") ──────┐   ┌── vCPU 线程 (comm "vcpuN") ──┐
   │ epoll_wait(epfd)                  │   │ ioctl(KVM_RUN)                │
   │  ├─ stop eventfd 可读 → 退出循环  │   │  └─ KVM_EXIT_IO               │
   │  └─ stdin 可读 → console_on_input │   │       lock(io_lock)           │
   │       read(stdin, 64 字节)        │   │       serial_read/write       │
   │       serial8250_push_rx          │   │         lock(serial.lock)     │
   │         lock(serial.lock)         │   │         update_irq            │
   │         update_irq → KVM_IRQ_LINE │   │           → KVM_IRQ_LINE      │
   └───────────────────────────────────┘   └───────────────────────────────┘
```

guest 停在 shell 提示符时，`tests/e2e/event-loop.sh` 从 `/proc/$pid/task/*/{comm,wchan}` 读到的正是这张图：

```text
thread vmm futex_wait_queue     主线程在 pthread_join
thread io do_epoll_wait         I/O 线程在 epoll_wait
thread vcpu0 kvm_vcpu_block     guest 空闲，vCPU 睡在 HLT
thread vcpu1 kvm_vcpu_block
```

这一里程碑之前同一位置读到的是 `vcpu0 vcpu1 vmm vmm`：多出来的那个 `vmm` 是没有命名的 console 线程，它睡在 tty 的 `read` 里。

### 2.1 数据结构

```c
struct evl_slot {
    int             fd;
    evl_handler_fn  fn;         /* NULL 表示空闲或已删除 */
    void           *opaque;
    bool            retired;    /* 本批结果处理完之前不复用 */
};

struct event_loop {
    int             epfd;
    int             stop_fd;    /* eventfd */
    pthread_t       thread;
    bool            started;
    bool            dispatching;
    struct evl_slot slots[EVL_MAX_HANDLERS];
};
```

`epoll_event.data.ptr` 存的是槽位地址，所以槽位必须在整个生命周期里不移动，这是用定长数组而不是可增长数组的原因。停机 eventfd 注册时 `data.ptr = NULL`，派发时看到 NULL 就知道是停机。

### 2.2 线程模型：处理器表只有一个写者

`evl_add`/`evl_del` 只允许在 `evl_start` 之前（主线程注册阶段）或者在回调里（I/O 线程上）调用，别的线程调用返回 `VMM_ERR_INVAL` 并打印是谁越界。这样处理器表不需要锁。以后 vCPU 线程需要 I/O 线程做事（例如 guest 往 AHCI 写了命令、需要后端开始读磁盘）时，应当写一个由 I/O 线程监听的 eventfd，让 I/O 线程在自己的回调里改表或发起 I/O。

## 3. 最反直觉的三处

### 3.1 同一批结果里的陈旧事件

`epoll_wait` 一次把多个就绪事件拷到用户态数组里（`fs/eventpoll.c` 的 `ep_send_events()` 逐个 `epoll_put_uevent`）。拷出来之后，内核那一侧再怎么变，用户态数组里的条目都不会变。于是：

```text
evs[0] = {data.ptr = &slots[0] (fd A)}   evs[1] = {data.ptr = &slots[1] (fd B)}

派发 evs[0]：A 的回调 evl_del(B)，又 evl_add(C)
  - 如果 C 立即复用 slots[1]，派发 evs[1] 时会调用 C 的回调，
    而 C 根本没有就绪，events 还是 B 的
  - 如果 slots[1] 标成 retired，C 拿到 slots[2]，evs[1] 看到
    slots[1].fn == NULL，跳过
```

删除只把 `fn` 清空，并在派发期间把槽位标 `retired`；一批处理完再统一清掉 `retired`。`tests/unit/event_loop_test.c` 的 “stale event in the batch is not dispatched to a newly added fd” 用一个永远没有数据的空管道作 C：C 的回调被调用一次就是派发错了。把 `retired` 去掉的变体在这条用例上必红（got 1, want 0）。

### 3.2 水平触发与 EOF

`ep_send_events()` 对没有 `EPOLLET` 的条目在交付后 `list_add_tail(&epi->rdllink, &ep->rdllist)` 放回就绪链表，下一次 `epoll_wait` 会重新 poll 一遍。管道写端关闭后 poll 一直报 `EPOLLHUP`（连同 `EPOLLIN`），`read` 一直返回 0。回调读到 EOF 却不 `evl_del`，I/O 线程就会空转。

e2e 用例 “stdin EOF: handler removes stdin once” 用 `true | vmm -v ...` 让 stdin 一开始就是 EOF，要求 `console: stdin EOF` 日志恰好一条。去掉 `evl_del` 的变体在一次启动里打印了七十多万条。

选水平触发而不是边沿触发的理由：回调一次只处理自己能处理的部分（终端一次读 64 字节，以后网卡一次只收 RX ring 放得下的包），剩下的数据下一轮自动再报；边沿触发要求回调读到 `EAGAIN` 为止，否则剩下的数据再也不会被通知，这又要求 fd 是非阻塞的，见 3.3。

### 3.3 stdin 不能设 O_NONBLOCK

`O_NONBLOCK` 是“打开文件描述”（`struct file`）的属性，不是 fd 的属性。在终端里启动时，shell 只打开一次 tty，再 dup 成 0、1、2，于是 stdin 和 stdout 是同一个 `struct file`。给 stdin 设 `O_NONBLOCK` 等于给串口输出用的 stdout 也设上，终端一忙 `write` 就返回 `EAGAIN`，guest 的输出被丢掉。

所以 stdin 保持阻塞模式，水平触发报可读之后只 `read` 一次。raw 模式下 `VMIN=1, VTIME=0`，有 1 字节就返回；管道上有数据时 `read` 返回已有的字节。两种情况下这一次 `read` 都不会阻塞。

## 4. 不能 poll 的 stdin

`run_case` 把被测进程的 stdin 接到 `/dev/null`。`drivers/char/mem.c` 的 `null_fops` 没有 `.poll`，`fs/eventpoll.c` 的 `do_epoll_ctl()` 在 `!file_can_poll(tf.file)` 时返回 `-EPERM`；普通文件同理。`evl_add` 把 EPERM 单独映射成 `VMM_ERR_UNSUPPORTED` 且不打日志，由调用方决定这算不算错误。对控制台来说这不是错误：打印 `console: stdin cannot be polled (regular file or /dev/null), guest input is disabled`，guest 照常运行。

注册放在切 raw 模式之前：监听不了时终端保持原样，不会留下一个 raw 模式却没人读的终端。

## 5. 加锁顺序

```text
vCPU 线程：  io_lock ──► 设备锁（serial.lock）──► KVM_IRQ_LINE
I/O 线程：  [io_lock] ──► 设备锁 ──────────────► KVM_IRQ_LINE
```

- 回调更新没有自己锁的设备（i8042、RTC，以后的 e1000、AHCI）时先拿 `io_lock`，和 vCPU 线程的 exit 分发串行，这和 QEMU main loop 回调持有 BQL 是同一回事。
- 设备有自己的锁时（串口），回调只拿那把锁。`console_on_input()` → `serial8250_push_rx()` 就是这种。
- 持有设备锁时不能再拿 `io_lock`：vCPU 线程是先 `io_lock` 后设备锁，反过来就是 ABBA 死锁。
- `KVM_IRQ_LINE` 不拿 VMM 的任何锁，KVM 内部自己串行化，在哪一层调用都不影响顺序。

这个顺序写在 `include/io/event_loop.h` 的头注释里，`vmm.h` 的 `io_lock` 注释指向它。

## 6. 生命周期

`src/main.c`：

```text
vm_create
evl_init                       epoll + 停机 eventfd
设备注册、boot_linux
  └─ console_start             evl_add(stdin)，切 raw 模式
evl_start                      创建 "io" 线程
vm_run                         创建并 join 所有 vCPU 线程
evl_stop                       写 eventfd，join "io"
console_stop                   恢复终端
evl_destroy、vm_destroy
```

`evl_stop` 放在 `vm_run` 返回之后：此时 vCPU 线程都已 join，再停掉 I/O 线程，之后就没有任何线程会碰设备状态，`vcpu_dump_state` 和 `mem_hexdump` 读到的是静止的现场。Ctrl-A x 在 I/O 线程上识别，调用 `vm_request_stop()` 踢出所有 vCPU（卷六第 6 节），主线程的 `vm_run` 随之返回，走同一条停机路径。

`evl_stop` 写 eventfd 失败时不 join：线程收不到停机事件，join 会永远等下去，宁可让它随进程退出。eventfd 只有计数器将要溢出时写才会失败，这里每次只加 1，实际上不会发生。

## 7. 验证为什么足够

| 契约 | 判据 | 能证明它会红的对照 |
|---|---|---|
| 回调在 I/O 线程上运行 | 回调里记录 `pthread_self()`，等于 `l.thread`、不等于主线程 | — |
| `evl_stop` 唤醒空闲循环 | 没有任何 fd 时 `evl_stop` 返回；唤不醒时 `alarm(30)` 终止进程 | 不写 eventfd 的变体：进程被超时杀掉 |
| 同批删除不再派发 | 两个 fd 互删，恰好一个回调运行 | — |
| 同批删除再注册不误派发 | 空管道 C 的回调调用次数为 0 | 去掉 `retired`：got 1 |
| 运行中别的线程不能改表 | 主线程 `evl_add`/`evl_del` 返回 `VMM_ERR_INVAL` | 去掉线程检查：两条都红 |
| 不可 poll 的 fd | `/dev/null` 返回 `VMM_ERR_UNSUPPORTED`，不占槽位 | — |
| EOF 后摘除 | 回调恰好调用一次、带 `EPOLLHUP` | — |
| 线程布局 | e2e：提示符处线程名恰好是 `io vcpu0 vcpu1 vmm`，`io` 睡在 epoll | 这一里程碑之前的二进制：`vcpu0 vcpu1 vmm vmm` |
| 串口输入经 I/O 线程 | e2e：guest 里 `echo EVL-$((6*7))` 输出 `EVL-42`；Ctrl-A x 退出 | 同上，整个 suite 3/3 红 |
| stdin EOF 不空转 | e2e：EOF 日志恰好一条 | 去掉 `evl_del`：七十多万条 |

前七条是 `make test unit` 里的 `event_loop_test`（ASan + UBSan），后三条是 `make test event-loop`。现有 e2e（linux-boot、smp、legacy-devices 等）的 guest shell 用例全部经由 I/O 线程送入命令，它们通过就说明串口输入路径没有退化。

`wchan` 是内核函数名：6.x 上 epoll_wait 睡在 `do_epoll_wait`（`ep_poll` 被内联），`ep_poll` 没被内联的内核上显示 `ep_poll`，用例两者都接受。换 host 内核后这条断言失败时，先看 `/proc/<pid>/task/<tid>/wchan` 实际是什么。

## 8. 限制

- 串口输出仍在 vCPU 线程里同步 `write(stdout)`。终端或管道读得慢时，写 THR 的 vCPU 会阻塞在 `write` 里。改成异步要给 THR 加发送缓冲，THRE 中断和 LSR 的 THRE/TEMT 位也要随缓冲状态变化，这一块和串口本身的语义绑在一起，没有放进这个里程碑。
- RX FIFO 256 字节满了之后 `serial8250_push_rx()` 丢字节，没有流控。有了事件循环以后可以做：FIFO 满时 `EPOLL_CTL_MOD` 暂停监听 stdin，guest 读走数据后再恢复，但“guest 读走了”这个事件发生在 vCPU 线程上，需要一个 vCPU → I/O 线程的通知 eventfd。
- 目前只有 stdin 一个后端。TAP、磁盘文件、socket 在 `emu-net`、`emu-blk` 里接入，异步块 I/O 在 `blk-io-uring`。
