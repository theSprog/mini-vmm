# 卷六：SMP 虚拟化——AP 唤醒、vCPU 线程与 CPU 拓扑

> 承接卷五（固件表与 Linux 启动协议），配套 blog 第二篇《从零理解 KVM：中断、设备与多核》的第八章与第十三章。
>
> 卷五结束时，guest 内核已经从 MADT 里读到“这台机器有 4 颗处理器，APIC ID 是 0 到 3”，并且在日志里打印了 `smpboot: Allowing 4 CPUs, 0 hotplug CPUs`。但此时真正在执行指令的只有一颗：BSP。另外三颗停在一个规范定义的等待状态里，要等 BSP 通过 LAPIC 发出一组特定的 IPI 才会开始取指。本卷讲的就是从这组 IPI 到 `smp: Brought up 1 node, 4 CPUs` 之间发生的全部事情。
>
> 这条链路横跨三层，每一层都有自己的状态机：guest 内核的 cpuhp 状态机负责决定什么时候叫醒谁、叫醒之后走哪些初始化步骤；KVM 的 `mp_state` 状态机负责把 INIT 和 SIPI 这两种 IPI 翻译成 vCPU 的架构状态变化；VMM 这一层负责线程、CPUID 与固件表。有意思的地方在于三层的分工极不均衡：AP 唤醒这件在物理机上最讲究时序的事情，到了 VMM 这里一行代码都不用写；反而是 CPUID 拓扑这种看起来只是“报几个数字”的事情，写错一位就会让 guest 的调度器、缓存拓扑和 NUMA 判断全部跑偏。本卷会逐一说明为什么。
>
> 全卷贯穿一条铁律，卷五第 9 节已经提过一次，这里给出它在 CPU 侧的完整形式：**KVM 模拟出来的 LAPIC ID、固件表里登记的 APIC ID、CPUID 指令返回的 initial APIC ID，三者必须相同**。三方中任意两方不一致，内核要么在启动时打印 `[Firmware Bug]`，要么静默地把某颗 CPU 算到错误的 socket 上，要么干脆 AP 起不来而挂在 trampoline 里。
>
> host 侧源码基于 Linux **v5.15**（KVM）。guest 侧源码基于 Linux **v6.6.91**，即 mini-vmm 实际引导的那个内核；文中 `file:line` 形式的行号都对应这两棵树。规范依据 Intel SDM Vol.3A 第 8 章（Multiple-Processor Management）、AMD64 APM Vol.2 第 16 章（Advanced Programmable Interrupt Controller）与 `Documentation/arch/x86/topology.rst`。

## 1. 从一颗到四颗：问题的全貌

### 1.1 BSP 与 AP

x86 多处理器系统上电时，所有处理器同时收到 RESET 信号，但它们不会一起跑。硬件（早期是外部逻辑，Pentium 4 之后是处理器之间的一次片上仲裁）会在其中选出一颗 **BSP**（bootstrap processor），其余的叫 **AP**（application processor）。区别体现在两处：

- BSP 的 `IA32_APIC_BASE` MSR 第 8 位（BSP flag）为 1，AP 为 0。这是唯一一处架构上可见的、能让一颗 CPU 知道“我是不是 BSP”的标志。
- BSP 从复位向量 `0xFFFFFFF0` 开始取指，正常进入固件；AP 执行完内部的 BIST 之后进入 **wait-for-SIPI** 状态，不取指、不执行，只保留对 INIT、SIPI、NMI 和 SMI 的响应能力。

也就是说，从加电到操作系统把 AP 叫醒之前，AP 一直什么都没做。整个系统从软件视角看是单处理器的：固件是单线程跑完的，bootloader 是单线程的，内核的 `startup_64`、`setup_arch()`、`start_kernel()` 前半段也都是单线程的。第一条在 AP 上执行的指令，出现在 `smp_init()` 之后。

在虚拟机里这套语义由 KVM 完整保留。`KVM_CREATE_VCPU` 创建出来的 vCPU 也分 BSP 与 AP：

```c
/* host v5.15 arch/x86/kvm/x86.c:10697，kvm_arch_vcpu_create() */
if (!irqchip_in_kernel(vcpu->kvm) || kvm_vcpu_is_reset_bsp(vcpu))
    vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
else
    vcpu->arch.mp_state = KVM_MP_STATE_UNINITIALIZED;
```

`kvm_vcpu_is_reset_bsp()` 比较的是 `vcpu_id` 与 `kvm->arch.bsp_vcpu_id`，后者默认为 0，可以用 `KVM_SET_BOOT_CPU_ID` 改（`x86.c:6036`）。mini-vmm 不改，所以 vCPU 0 是 BSP。这一行里还藏着一个容易忽略的分支：**没有内核态 irqchip 时，所有 vCPU 一律是 `RUNNABLE`**。因为 INIT/SIPI 是 LAPIC 的功能，LAPIC 不在内核里，KVM 就没法替你实现 wait-for-SIPI，整套唤醒协议必须由用户态自己模拟。mini-vmm 在 `--mode linux` 下总是先调 `KVM_CREATE_IRQCHIP` 再创建 vCPU（`src/vm.c:486`），顺序不能反——KVM 是在 `KVM_CREATE_VCPU` 的时刻才决定要不要给这个 vCPU 挂一个内核态 LAPIC 的。

### 1.2 三层状态机

| 层 | 状态机 | 状态 | 驱动它前进的事件 |
|---|---|---|---|
| guest 内核 | cpuhp（`kernel/cpu.c`） | `CPUHP_OFFLINE` … `CPUHP_BP_KICK_AP` … `CPUHP_ONLINE`，共 200 余级 | `bringup_nonboot_cpus()` 逐级调用 startup 回调 |
| guest 内核（AP 侧） | `ap_sync_state`（6.6 新增） | `KICKED` → `ALIVE` → `SHOULD_ONLINE` → `ONLINE` | AP 自己在 `cpuhp_ap_sync_alive()` 里翻牌，BSP 轮询等待 |
| KVM | `vcpu->arch.mp_state` | `UNINITIALIZED` → `INIT_RECEIVED` → `RUNNABLE`（另有 `HALTED`、`AP_RESET_HOLD`） | LAPIC 收到 `APIC_DM_INIT` / `APIC_DM_STARTUP` |
| VMM | 无 | 线程要么在 `KVM_RUN` 里，要么在处理 exit | `pthread_create`、信号、`immediate_exit` |

VMM 这一列是空的，这正是本卷的第一个结论：**AP 唤醒过程中，用户态 VMM 不需要执行任何动作**。BSP 写 ICR 会触发 VM exit 吗？不会——LAPIC 在内核态，写 ICR 只是一次 APIC MMIO 访问，由 KVM 的 `kvm_lapic_reg_write()` 就地处理完，连用户态都不会通知。AP 线程此刻正阻塞在自己的 `KVM_RUN` 里，KVM 把它唤醒、改好状态、送进 guest，全程用户态无感。

代价是这件事变得难以观察：如果 AP 没起来，`strace` 上看不到任何异常，日志里也没有痕迹，只有 guest 内核在 10 秒超时之后打印一行 `CPU#1 stuck`。第 11 节会给出可用的观察手段。

## 2. MP 初始化协议：INIT-SIPI-SIPI

### 2.1 规范怎么说

唤醒 AP 的唯一标准手段是 **通用启动算法**（universal start-up algorithm），Intel SDM Vol.3A §9.4.4.1 与 AMD64 APM Vol.2 §16.9 各自给出了一份，内容一致。BSP 依次做三件事：

1. 向目标 AP 发一个 **INIT IPI**。AP 收到后进入初始化状态：寄存器复位成架构定义的初值，然后回到 wait-for-SIPI。
2. 等待 10 ms。
3. 连发两个 **SIPI**（startup IPI，也叫 Start-Up IPI），中间隔 200 µs。SIPI 携带一个 8 位向量 *V*，AP 收到后从物理地址 `V << 12` 开始，以**实模式**执行，`CS.selector = V << 8`、`CS.base = V << 12`、`IP = 0`。

两个问题值得先回答。

**为什么发两次 SIPI？** 规范的说法是：如果第一个 SIPI 成功，AP 已经在跑了，第二个 SIPI 会被它忽略（不在 wait-for-SIPI 状态的 CPU 不响应 SIPI）；如果第一个因为某些早期芯片的时序问题丢了，第二个是补救。这是一条纯历史包袱，但今天的软件仍然照做，因为它无害。

**为什么入口必须在 1 MiB 以下？** SIPI 向量只有 8 位，`V << 12` 的最大值是 `0xFF000`，不到 1 MiB；而且 AP 醒来时在实模式，本来也寻址不到更高的地方。这条约束一路传导到 VMM：**E820 里 1 MiB 以下必须有一段可用 RAM**，否则 guest 内核分配不到 trampoline，`reserve_real_mode()` 里就会 panic。卷五第 4 节讲 E820 时提到的“低端内存必须留 RAM”，根子就在这里。

### 2.2 ICR 的位域

INIT 和 SIPI 都是通过写 LAPIC 的中断命令寄存器（ICR）发出的。xAPIC 模式下 ICR 是两个 32 位寄存器：`0x300`（低半，写它就触发发送）和 `0x310`（高半，只放目标 APIC ID）。

| 位 | 名称 | INIT 时的值 | SIPI 时的值 |
|---|---|---|---|
| 7:0 | Vector | 0 | 入口地址 >> 12 |
| 10:8 | Delivery Mode | `101b` = INIT | `110b` = Start-Up |
| 11 | Destination Mode | 0（physical） | 0（physical） |
| 12 | Delivery Status | 只读，1 表示上一次还没送出去 | 同左 |
| 14 | Level | assert 时 1，de-assert 时 0 | 1 |
| 15 | Trigger Mode | 1（level） | 0（edge） |
| 19:18 | Destination Shorthand | 00（用 ICR2 里的 ID） | 00 |
| 63:56（ICR2 的 31:24） | Destination Field | 目标 APIC ID | 目标 APIC ID |

Linux 里这些常量定义在 `arch/x86/include/asm/apicdef.h:70-95`：`APIC_DM_INIT` 是 `0x500`，`APIC_DM_STARTUP` 是 `0x600`，`APIC_INT_ASSERT` 是 `0x4000`，`APIC_INT_LEVELTRIG` 是 `0x8000`。

写 ICR 的顺序是固定的：先写 ICR2（目标），再写 ICR 低半（触发发送），中间关中断防止被抢占后目标被改掉。

```c
/* guest v6.6 arch/x86/kernel/apic/apic.c:244 */
void native_apic_icr_write(u32 low, u32 id)
{
    unsigned long flags;

    local_irq_save(flags);
    apic_write(APIC_ICR2, SET_XAPIC_DEST_FIELD(id));
    apic_write(APIC_ICR, low);
    local_irq_restore(flags);
}
```

### 2.3 Linux 的实现

`arch/x86/kernel/smpboot.c:801` 的 `send_init_sequence()` 发 INIT 的 assert 与 de-assert 两拍：

```c
/* Assert INIT on the target CPU */
apic_icr_write(APIC_INT_LEVELTRIG | APIC_INT_ASSERT | APIC_DM_INIT, phys_apicid);
safe_apic_wait_icr_idle();

udelay(init_udelay);

/* Deassert INIT on the target CPU */
apic_icr_write(APIC_INT_LEVELTRIG | APIC_DM_INIT, phys_apicid);
safe_apic_wait_icr_idle();
```

de-assert 那一拍是 82489DX 外置 APIC 时代的产物：那时候 INIT 是一根真实的电平信号线，要拉高再拉低。集成 APIC（P54C 之后）对 level-triggered 的 INIT de-assert 不做任何事，但 Linux 仍然照发。KVM 也照收不误：`__apic_accept_irq()` 里 `case APIC_DM_INIT` 的条件是 `if (!trig_mode || level)`，de-assert 那一拍 `trig_mode=1` 而 `level=0`，条件不成立，直接被丢掉（`host v5.15 arch/x86/kvm/lapic.c:1126`）。

`init_udelay` 的值由 `smp_quirk_init_udelay()`（`smpboot.c:781`）决定：Intel family 6、AMD family ≥ 0xF、**Hygon family ≥ 0x18** 一律取 0，其余取 10000（微秒）。mini-vmm 跑在海光上，guest 看到的 family 是 0x18，所以规范要求的那个 10 ms 延迟实际上是 0。这条路径也可以用 `cpu_init_udelay=` 命令行参数强制（`smpboot.c:773`）。

发 SIPI 的循环在 `wakeup_secondary_cpu_via_init()`（`smpboot.c:827`）：

```c
for (j = 1; j <= num_starts; j++) {
    ...
    apic_icr_write(APIC_DM_STARTUP | (start_eip >> 12), phys_apicid);
    if (init_udelay == 0)
        udelay(10);
    else
        udelay(300);
    send_status = safe_apic_wait_icr_idle();
    ...
}
```

`num_starts` 在集成 APIC 上是 2，于是就有了协议名里的两个 SIPI。注意 `start_eip >> 12` —— 这就是 SIPI 向量的来历。`start_eip` 来自 `real_mode_header->trampoline_start`，也就是下一节要讲的实模式跳板。

### 2.4 KVM 怎么接住这两种 IPI

BSP 写 ICR 会被 KVM 的 LAPIC 模拟截住。路径是 `kvm_lapic_reg_write()` → `kvm_apic_send_ipi()` → `kvm_irq_delivery_to_apic()` → 目标 vCPU 的 `__apic_accept_irq()`：

```c
/* host v5.15 arch/x86/kvm/lapic.c:2060，kvm_lapic_reg_write() */
case APIC_ICR:
    /* No delay here, so we always clear the pending bit */
    val &= ~(1 << 12);
    kvm_apic_send_ipi(apic, val, kvm_lapic_get_reg(apic, APIC_ICR2));
    kvm_lapic_set_reg(apic, APIC_ICR, val);
    break;
```

第一行注释值得留意：KVM 直接把 Delivery Status 位清零，因为它的“发送”是同步完成的，不存在排队。所以 guest 里 `safe_apic_wait_icr_idle()` 那个自旋等待永远一次就过，`/proc/interrupts` 里的 `RTR: APIC ICR read retries` 计数恒为 0——这是一个可以用来确认“LAPIC 在内核态被模拟”的旁证。

`kvm_apic_send_ipi()`（`lapic.c:1279`）把 ICR 的两半解成一个 `struct kvm_lapic_irq`，然后按 dest_mode 和 shorthand 找出目标 vCPU 集合。真正的动作在 `__apic_accept_irq()`：

```c
/* host v5.15 arch/x86/kvm/lapic.c:1126 */
case APIC_DM_INIT:
    if (!trig_mode || level) {
        result = 1;
        /* assumes that there are only KVM_APIC_INIT/SIPI */
        apic->pending_events = (1UL << KVM_APIC_INIT);
        kvm_make_request(KVM_REQ_EVENT, vcpu);
        kvm_vcpu_kick(vcpu);
    }
    break;

case APIC_DM_STARTUP:
    result = 1;
    apic->sipi_vector = vector;
    /* make sure sipi_vector is visible for the receiver */
    smp_wmb();
    set_bit(KVM_APIC_SIPI, &apic->pending_events);
    kvm_make_request(KVM_REQ_EVENT, vcpu);
    kvm_vcpu_kick(vcpu);
    break;
```

两件事：在目标 vCPU 的 `pending_events` 位图里置位，然后 `kvm_vcpu_kick()` 把目标线程从阻塞里唤醒。注意 INIT 用的是**赋值**而不是置位——收到 INIT 会把之前挂着的 SIPI 一并抹掉，这符合规范（INIT 让 AP 回到 wait-for-SIPI，之前的 SIPI 自然作废）。

整个过程中 `kvm_vcpu_kick()` 唤醒的是 host 上那个 vCPU 线程，而这个线程正阻塞在 `KVM_RUN` 内部——不是阻塞在用户态。所以从 mini-vmm 的角度，什么都没发生过。

## 3. 实模式跳板：从 16 位到 `secondary_startup_64`

AP 收到 SIPI 后，在实模式下从 `V << 12` 开始执行。而内核本体运行在长模式、开着四级或五级页表、代码在 `0xffffffff8xxxxxxx` 这样的高端虚拟地址上。中间这段落差由一块叫 **real mode trampoline** 的代码填补。它是内核里少数几段仍然用 `.code16` 写的代码之一。

### 3.1 它住在哪

跳板是一段独立编译、链接、然后当作二进制大块（blob）嵌进 vmlinux 的代码，源码在 `arch/x86/realmode/rm/`，链接脚本是 `realmode.lds.S`，最终以 `real_mode_blob` 符号出现在内核镜像里。启动早期它被整块复制到一片 1 MiB 以下的内存上：

```c
/* guest v6.6 arch/x86/realmode/init.c:46 */
void __init reserve_real_mode(void)
{
    phys_addr_t mem;
    size_t size = real_mode_size_needed();
    ...
    /* Has to be under 1M so we can execute real-mode AP code. */
    mem = memblock_phys_alloc_range(size, PAGE_SIZE, 0, 1<<20);
    if (!mem)
        pr_info("No sub-1M memory is available for the trampoline\n");
    else
        set_real_mode_mem(mem);

    /*
     * Unconditionally reserve the entire fisrt 1M, see comment in
     * setup_arch().
     */
    memblock_reserve(0, SZ_1M);
}
```

调用点在 `setup_arch()` 的 `x86_platform.realmode_reserve()`（`arch/x86/kernel/setup.c:1163`），紧挨在 `init_mem_mapping()` 之前。这段代码解释了卷五第 4 节那条 E820 约束的全部理由：**如果 1 MiB 以下一个 RAM 字节都没有，`memblock_phys_alloc_range()` 返回 0，`real_mode_header` 是 NULL，随后 `init_real_mode()` 里直接 `panic("Real mode trampoline was not allocated")`**。注意这个 panic 发生在 `early_initcall` 阶段，也就是说即使是单 vCPU 的 guest 也躲不过——跳板不只给 AP 用，ACPI S3 唤醒和 `reboot=bios` 也走它。

mini-vmm 的 E820 第一项正是为此存在：

```text
[    0.000000] BIOS-e820: [mem 0x0000000000000000-0x000000000009fbff] usable
[    0.000000] BIOS-e820: [mem 0x000000000009fc00-0x00000000000fffff] reserved
[    0.000000] BIOS-e820: [mem 0x0000000000100000-0x000000001fffffff] usable
```

跳板成功时一行日志都不打印，所以它是“沉默的依赖”：只有失败了才知道它存在。反过来说，`No sub-1M memory is available for the trampoline` 这一行如果出现在日志里，问题一定出在 VMM 的 E820 上，而不是内核。最后那句 `memblock_reserve(0, SZ_1M)` 还说明：不管 VMM 把低端 1 MiB 报成什么，内核最终都会把整个第一兆保留下来不给分配器用，理由是“BIOS 经常破坏低端内存，几百 KiB 不值得花力气去精确检测”。

### 3.2 复制与重定位

`setup_real_mode()`（`realmode/init.c:89`）把 blob 复制到目标地址后要做一次重定位。原因很直白：这段代码在实模式下运行，段基址由 `CS` 决定，而 `CS` 的值到运行时才知道；代码里又有 32 位的绝对地址引用（`pa_startup_32` 之类）。编译时不知道装到哪，只能编译后打补丁。

```c
    memcpy(base, real_mode_blob, size);

    phys_base = __pa(base);
    real_mode_seg = phys_base >> 4;

    rel = (u32 *) real_mode_relocs;

    /* 16-bit segment relocations. */
    count = *rel++;
    while (count--) {
        u16 *seg = (u16 *) (base + *rel++);
        *seg = real_mode_seg;
    }

    /* 32-bit linear relocations. */
    count = *rel++;
    while (count--) {
        u32 *ptr = (u32 *) (base + *rel++);
        *ptr += phys_base;
    }
```

重定位表 `real_mode_relocs` 是构建时用 `arch/x86/tools/relocs` 从跳板的 ELF 里抽出来的。这也是跳板源码开头那句警告的由来：“如果你改这个文件，用 `objdump --full-contents --reloc` 检查一下目标文件，确保没有重定位项”——意思是不能引入编译器自己生成的重定位，只能用这套手工机制。

### 3.3 `trampoline_header`：BSP 交给 AP 的五个值

重定位之后，BSP 往跳板尾部一个固定结构里填五个字段，这是两者之间唯一的数据接口：

```c
/* guest v6.6 arch/x86/include/asm/realmode.h:43 */
struct trampoline_header {
    u64 start;      /* AP 进入长模式后要跳的目标：secondary_startup_64 的虚拟地址 */
    u64 efer;       /* BSP 当前的 EFER，去掉 LMA 位 */
    u32 cr4;        /* mmu_cr4_features，BSP 当前的 CR4 去掉 PCIDE */
    u32 flags;      /* TH_FLAGS_SME_ACTIVE，内存加密用 */
    u32 lock;       /* 实模式栈的自旋锁 */
};
```

填写在 `setup_real_mode()` 的后半段：

```c
    /*
     * Some AMD processors will #GP(0) if EFER.LMA is set in WRMSR
     * so we need to mask it out.
     */
    rdmsrl(MSR_EFER, efer);
    trampoline_header->efer = efer & ~EFER_LMA;

    trampoline_header->start = (u64) secondary_startup_64;
    trampoline_cr4_features = &trampoline_header->cr4;
    *trampoline_cr4_features = mmu_cr4_features;
```

“AP 用 BSP 的 CR4 和 EFER”这件事有实际后果：BSP 在 `setup_arch()` 里探测出来的每一项 CR4 特性（PGE、SMEP、SMAP、PCIDE 之外的都在），AP 醒来时直接照抄，不再自己探测。所以**所有 vCPU 的 CPUID 必须一致**——如果 VMM 给 vCPU 1 报了一个 vCPU 0 没有的特性，或者反过来，AP 会带着一份为别人算出来的 CR4 进长模式。mini-vmm 的 `amd_init_vcpu()` 对每个 vCPU 都调同一份 `KVM_GET_SUPPORTED_CPUID` 的结果，只改拓扑字段，正是为了保证这一点。

`lock` 字段是 6.5 引入并行启动之后才加的。跳板只有一份，实模式栈也只有一份，并行启动时多个 AP 会同时跑进来，必须串行化：

```asm
/* guest v6.6 arch/x86/realmode/rm/trampoline_64.S:40 */
.macro LOCK_AND_LOAD_REALMODE_ESP lock_pa=0
.Llock_rm\@:
	.if \lock_pa
        lock btsl       $0, pa_tr_lock
	.else
        lock btsl       $0, tr_lock
	.endif
        jnc             2f
        pause
        jmp             .Llock_rm\@
2:
	# Setup stack
	movl	$rm_stack_end, %esp
.endm
```

拿不到锁就 `pause` 自旋。锁在 AP 切到自己的内核栈之后才释放，释放点在 `head_64.S` 的 `.Lsetup_cpu` 之后（见 3.5）。`lock btsl` 是一条带 `lock` 前缀的原子指令，在 KVM 下它对应一次普通的内存访问，不产生 exit——NPT/EPT 之下 guest 的原子指令由硬件直接做，VMM 完全看不到。

### 3.4 跳板代码本身

`trampoline_start`（`trampoline_64.S:59`）按页对齐，因为 SIPI 向量的粒度是 4 KiB。整段代码干的事情可以一行行数清楚：

```asm
SYM_CODE_START(trampoline_start)
	cli			# We should be safe anyway
	wbinvd

	LJMPW_RM(1f)
1:
	mov	%cs, %ax	# Code and data in the same place
	mov	%ax, %ds
	mov	%ax, %es
	mov	%ax, %ss

	LOCK_AND_LOAD_REALMODE_ESP

	call	verify_cpu		# Verify the cpu supports long mode
	testl   %eax, %eax		# Check for return code
	jnz	no_longmode

.Lswitch_to_protected:
	lidtl	tr_idt	# load idt with 0, 0
	lgdtl	tr_gdt	# load gdt with whatever is appropriate

	movw	$__KERNEL_DS, %dx	# Data segment descriptor

	# Enable protected mode
	movl	$(CR0_STATE & ~X86_CR0_PG), %eax
	movl	%eax, %cr0		# into protected mode

	# flush prefetch and jump to startup_32
	ljmpl	$__KERNEL32_CS, $pa_startup_32
```

- `wbinvd` 是给 AP 清缓存用的，规范推荐动作。它在 KVM 下会产生一次 VM exit（SVM 的 `VMEXIT_WBINVD`），由 host 内核就地处理，不到用户态。
- `verify_cpu` 是一段共享的检查程序（`arch/x86/kernel/verify_cpu.S`），确认 CPUID 可用、支持长模式、NX 可开。失败就落到 `no_longmode` 里 `hlt` 死循环——这是 AP 起不来的经典现场之一：BSP 等 10 秒超时，日志里一行 `CPU#1 stuck`，而 AP 其实已经停在这里了。
- `tr_idt` 是一个 limit=0 的 IDT，装它的意思是“此刻任何异常都应该导致三重故障立即停机”，而不是跑飞。在 VMM 里这一点非常友好：AP 出问题会以 `KVM_EXIT_SHUTDOWN` 的形式直接冒到用户态，mini-vmm 的 `vcpu_handle_exit()` 会打印 `vCPU N: SHUTDOWN (usually a triple fault)` 并 dump 寄存器。
- `tr_gdt` 是跳板自带的一份三项 GDT（`__KERNEL32_CS`、`__KERNEL_CS`、`__KERNEL_DS`），因为内核真正的 GDT 在高端虚拟地址上，实模式够不着。

进入 32 位保护模式后的 `startup_32`（`trampoline_64.S:124`）继续：开 `CR4.PAE`（从 `tr_cr4` 取）、把 `pa_trampoline_pgd` 装进 CR3、按 `tr_efer` 写 EFER（于是 `EFER.LME=1`）、开 `CR0.PG` 激活长模式，最后 `ljmpl $__KERNEL_CS, $pa_startup_64` 进 64 位。跳板里的 `startup_64` 只有一条指令：

```asm
SYM_CODE_START(startup_64)
	# Now jump into the kernel using virtual addresses
	jmpq	*tr_start(%rip)
SYM_CODE_END(startup_64)
```

`tr_start` 就是 `trampoline_header.start`，即 `secondary_startup_64` 的虚拟地址。能用虚拟地址跳，是因为 `trampoline_pgd` 里既有低端的恒等映射（`trampoline_pgd[0] = trampoline_pgd_entry.pgd`），又把内核页表 `__PAGE_OFFSET` 以上的全部 PGD 项照抄了一份（`realmode/init.c:170`）。

### 3.5 AP 侧：`secondary_startup_64` 怎么知道自己是几号

这是 6.5 引入并行启动之后变化最大的一段。BSP 和 AP 共用 `secondary_startup_64`，BSP 从 `startup_64` 走过来，AP 从跳板走过来。两者都要在这里确定“我是哪个逻辑 CPU”，因为下一步就要用 `__per_cpu_offset[cpu]` 找自己的 per-CPU 区。

老办法是 BSP 在发 SIPI 之前把 CPU 号写进全局变量 `smpboot_control`，AP 直接读——但这要求一次只能唤醒一颗。并行启动要同时唤醒所有 AP，就必须让 AP 自己查：

```asm
/* guest v6.6 arch/x86/kernel/head_64.S:242 */
	movl	smpboot_control(%rip), %ecx
	testl	$STARTUP_READ_APICID, %ecx
	jnz	.Lread_apicid
	/*
	 * No control bit set, single CPU bringup. CPU number is provided
	 * in bit 0-23. This is also the boot CPU case (CPU number 0).
	 */
	andl	$(~STARTUP_PARALLEL_MASK), %ecx
	jmp	.Lsetup_cpu

.Lread_apicid:
	/* Check whether X2APIC mode is already enabled */
	mov	$MSR_IA32_APICBASE, %ecx
	rdmsr
	testl	$X2APIC_ENABLE, %eax
	jnz	.Lread_apicid_msr
	...
.Lread_apicid_mmio:
	/* Read the APIC ID from the fix-mapped MMIO space. */
	movq	apic_mmio_base(%rip), %rcx
	addq	$APIC_ID, %rcx
	movl	(%rcx), %eax
	shr	$24, %eax
	jmp	.Llookup_AP
	...
.Llookup_AP:
	/* EAX contains the APIC ID of the current CPU */
	xorq	%rcx, %rcx
	leaq	cpuid_to_apicid(%rip), %rbx

.Lfind_cpunr:
	cmpl	(%rbx,%rcx,4), %eax
	jz	.Lsetup_cpu
	inc	%ecx
	cmpl	nr_cpu_ids(%rip), %ecx
	jb	.Lfind_cpunr

	/*  APIC ID not found in the table. Drop the trampoline lock and bail. */
	movq	trampoline_lock(%rip), %rax
	movl	$0, (%rax)

1:	cli
	hlt
	jmp	1b
```

`STARTUP_READ_APICID` 是 `0x80000000`（`arch/x86/include/asm/smp.h:193`），由 `arch_cpuhp_init_parallel_bringup()` 在并行启动可用时置上（`smpboot.c:1177`）。走到 `.Lread_apicid` 的 AP 做三件事：

1. 从 LAPIC 读自己的 APIC ID。xAPIC 模式下读的是 MMIO 的 `0xFEE00020`，取高 8 位；x2APIC 模式下读 MSR `0x802`。
2. 在 `cpuid_to_apicid[]` 数组里线性查找这个值。这个数组是 BSP 在解析 MADT 时按登记顺序建起来的（`generic_processor_info()`，卷五 8.3 节）。
3. 找到就把下标当作自己的 CPU 号，找不到就**放掉跳板锁然后 `hlt` 死循环**。

第 3 步是整卷最值得记住的一条因果链。**guest 通过 MMIO 读到的 APIC ID 由 KVM 的 LAPIC 模拟给出，而 `cpuid_to_apicid[]` 的内容来自 VMM 写的 MADT。这两者只要对不上，AP 就永远查不到自己，直接死在这里。** KVM 里 vCPU 的 LAPIC ID 默认等于 `vcpu_id`（也就是 `KVM_CREATE_VCPU` 的参数），所以 MADT 里第 *i* 条 LAPIC 条目的 `apic_id` 必须写 *i*。mini-vmm 的 `src/boot/acpi.c:242` 正是 `l->apic_id = (uint8_t)i;`，`src/boot/mptable.c:153` 同理。这条约束不能靠“差不多”蒙混：APIC ID 空间是稀疏的，真实硬件上常见 0、2、4、6 这种带洞的编号，而 KVM 不是。

查到 CPU 号之后：

```asm
.Lsetup_cpu:
	/* Get the per cpu offset for the given CPU# which is in ECX */
	movq	__per_cpu_offset(,%rcx,8), %rdx
	...
	movq	pcpu_hot + X86_current_task(%rdx), %rax
	movq	TASK_threadsp(%rax), %rsp

	/*
	 * Now that this CPU is running on its own stack, drop the realmode
	 * protection. For the boot CPU the pointer is NULL!
	 */
	movq	trampoline_lock(%rip), %rax
	testq	%rax, %rax
	jz	.Lsetup_gdt
	movl	$0, (%rax)
```

AP 用 per-CPU 偏移找到 `pcpu_hot.current_task`（BSP 在 `common_cpu_up()` 里事先填好的 idle 任务），从任务结构里取出内核栈，切过去，然后才放掉跳板锁——下一个 AP 这时才能进跳板。这段串行区非常短，只有实模式到长模式的几十条指令。

### 3.6 一个会打到 VMM 设备模型上的副作用

`do_boot_cpu()` 在发 IPI 之前还有一段：

```c
/* guest v6.6 arch/x86/kernel/smpboot.c:1004 */
	if (x86_platform.legacy.warm_reset) {
		pr_debug("Setting warm reset code and vector.\n");
		smpboot_setup_warm_reset_vector(start_ip);
		...
	}
```

`x86_platform.legacy.warm_reset` 在 `x86_early_init_platform_quirks()` 里无条件置 1（`arch/x86/kernel/platform-quirks.c:13`），`hardware_subarch` 为 0 也不例外。于是每唤醒一颗 AP，内核都会执行：

```c
	spin_lock_irqsave(&rtc_lock, flags);
	if (!smpboot_warm_reset_vector_count++) {
		CMOS_WRITE(0xa, 0xf);
		*((volatile unsigned short *)phys_to_virt(TRAMPOLINE_PHYS_HIGH)) = start_eip >> 4;
		*((volatile unsigned short *)phys_to_virt(TRAMPOLINE_PHYS_LOW)) = start_eip & 0xf;
	}
	spin_unlock_irqrestore(&rtc_lock, flags);
```

这是 286 时代的遗迹：那时从保护模式回实模式只能靠复位 CPU，固件在复位后读 CMOS 索引 `0x0F`（shutdown status byte），值为 `0x0A` 表示“跳到 `0040:0067` 存的地址去”。`TRAMPOLINE_PHYS_LOW` 和 `TRAMPOLINE_PHYS_HIGH` 就是物理地址 `0x467` 和 `0x469`（`arch/x86/include/asm/apic.h`）。

对 VMM 的要求有两条，都很低但都必须满足：

- **CMOS 索引 `0x0F` 的写必须被接受。** mini-vmm 的 RTC 模型把除状态寄存器 C、D 之外的所有索引当普通 CMOS 字节存下（`src/devices/rtc.c:93-95`），符合要求。如果 VMM 的 RTC 只实现了时间寄存器而对其他索引报错或崩溃，AP 唤醒的第一步就会翻车——而现象会表现成完全无关的样子。
- **物理地址 `0x467` 必须是可写的 RAM。** 它落在 mini-vmm E820 第一项 `[0x0, 0x9fc00) RAM` 里，没问题。

顺带一提，这段代码里的 `spin_lock_irqsave(&rtc_lock)` 意味着 AP 唤醒和 RTC 驱动会争同一把锁。在 VMM 里 CMOS 访问是 PIO exit，要走出用户态、抢 `io_lock`、再回来，比物理机慢几个数量级，但因为整个启动过程只做一次（`smpboot_warm_reset_vector_count` 从 0 变 1 时才写），影响可以忽略。

## 4. guest 内核这一侧：从 `smp_init()` 到 4 颗 CPU 全部在线

### 4.1 时机

`start_kernel()` 的最后一步是 `arch_call_rest_init()` → `rest_init()`，它创建 init 线程后者调用 `kernel_init_freeable()`，其中有一行 `smp_init()`。在此之前所有初始化都是单线程的；在此之后内核才真正是多处理器的。

```c
/* guest v6.6 kernel/smp.c:971 */
void __init smp_init(void)
{
    int num_nodes, num_cpus;

    idle_threads_init();
    cpuhp_threads_init();

    pr_info("Bringing up secondary CPUs ...\n");

    bringup_nonboot_cpus(setup_max_cpus);

    num_nodes = num_online_nodes();
    num_cpus  = num_online_cpus();
    pr_info("Brought up %d node%s, %d CPU%s\n",
        num_nodes, (num_nodes > 1 ? "s" : ""),
        num_cpus,  (num_cpus  > 1 ? "s" : ""));

    /* Any cleanup work */
    smp_cpus_done(setup_max_cpus);
}
```

这段对应 mini-vmm guest 日志里的这几行，它们把整个 SMP 启动过程夹在中间：

```text
[    0.457657] smp: Bringing up secondary CPUs ...
[    0.459283] smpboot: x86: Booting SMP configuration:
[    0.460087] .... node  #0, CPUs:      #1 #2 #3
[    0.464195] smp: Brought up 1 node, 4 CPUs
[    0.466087] smpboot: Max logical packages: 1
[    0.467083] smpboot: Total of 4 processors activated (24000.94 BogoMIPS)
```

从 `Bringing up` 到 `Brought up` 一共 6.5 毫秒，三颗 AP 全部上线。注意 `idle_threads_init()` 在前：每颗 AP 必须先有一个 idle 任务（也就是它的 `swapper/N`），AP 醒来后第一件事就是用这个任务的内核栈，第 3.5 节 `.Lsetup_cpu` 里取的就是它。

### 4.2 cpuhp：一个两百级的状态机

Linux 3.x 时代的 CPU 上线是一串 notifier 回调，顺序靠优先级维持，出错难以回滚。4.x 之后改成了显式的状态机：每个子系统在 `enum cpuhp_state`（`include/linux/cpuhotplug.h`）里占一格，每格有一对 `startup`/`teardown` 回调，上线时从低到高逐格调 startup，下线时从高到低逐格调 teardown。

这些状态分三段，段的划分决定了回调**在哪颗 CPU 上执行**：

| 段 | 范围 | 执行者 |
|---|---|---|
| `CPUHP_OFFLINE` … `CPUHP_BRINGUP_CPU` | BP 段 | 控制方 CPU（通常是 BSP） |
| `CPUHP_AP_OFFLINE` … `CPUHP_AP_ONLINE` | AP 段（早期） | 目标 AP 自己，中断关闭 |
| `CPUHP_AP_ONLINE_DYN` … `CPUHP_ONLINE` | AP 段（线程化） | 目标 AP 上的 `cpuhp/N` 内核线程 |

中间那格 `CPUHP_BRINGUP_CPU` 是分水岭：它的 startup 回调就是真正发 INIT-SIPI-SIPI 的地方。在开启 `CONFIG_HOTPLUG_SPLIT_STARTUP` 的内核里（mini-vmm 的 guest 就是），这一格被拆成了两格：

```c
/* guest v6.6 kernel/cpu.c:2150 附近，cpuhp_hp_states[] */
	[CPUHP_BP_KICK_AP] = {
		.name			= "cpu:kick_ap",
		.startup.single		= cpuhp_kick_ap_alive,
	},
	[CPUHP_BRINGUP_CPU] = {
		.name			= "cpu:bringup",
		.startup.single		= cpuhp_bringup_ap,
		.teardown.single	= finish_cpu,
		.cant_stop		= true,
	},
```

- `cpuhp_kick_ap_alive()` 只负责“踢”：`arch_cpuhp_kick_ap_alive()` → `native_kick_ap()` → `do_boot_cpu()` → 发 IPI，然后立刻返回，不等结果。
- `cpuhp_bringup_ap()` 负责“等”：`cpuhp_bp_sync_alive()` 轮询目标 CPU 的 `ap_sync_state` 变成 `SYNC_STATE_ALIVE`。

拆开的意义就是下一节的并行启动。

### 4.3 并行启动：为什么 4 颗 CPU 只花 6 毫秒

传统做法是一颗一颗来：踢一颗、等它跑完实模式跳板和长模式初始化、报到、放行、走完全部 AP 状态到 online，然后才踢下一颗。串行化的理由是跳板只有一份。6.5 给跳板加了一把锁（3.3 节的 `tr_lock`）之后，这个限制只剩下跳板里那几十条指令，于是可以改成：先把所有 AP 都踢起来，让它们在跳板上排队，然后再逐个放行做后续初始化。

```c
/* guest v6.6 kernel/cpu.c:1869 */
static bool __init cpuhp_bringup_cpus_parallel(unsigned int ncpus)
{
    const struct cpumask *mask = cpu_present_mask;

    if (__cpuhp_parallel_bringup)
        __cpuhp_parallel_bringup = arch_cpuhp_init_parallel_bringup();
    if (!__cpuhp_parallel_bringup)
        return false;

    if (cpuhp_smt_aware()) {
        ...
    }

    /* Bring the not-yet started CPUs up */
    cpuhp_bringup_mask(mask, ncpus, CPUHP_BP_KICK_AP);
    cpuhp_bringup_mask(mask, ncpus, CPUHP_ONLINE);
    return true;
}
```

两次 `cpuhp_bringup_mask()`：第一次把所有 AP 推进到 `CPUHP_BP_KICK_AP`（也就是全部发完 IPI），第二次再把它们逐个推到 `CPUHP_ONLINE`。

x86 侧的开关是 `arch_cpuhp_init_parallel_bringup()`（`arch/x86/kernel/smpboot.c:1170`），它做的事只有一件——把 `smpboot_control` 设成 `STARTUP_READ_APICID`，告诉 AP“自己去查 CPU 号”，也就是 3.5 节那段汇编走的分支。mini-vmm 的 guest `.config` 里 `CONFIG_HOTPLUG_PARALLEL=y`、`CONFIG_HOTPLUG_SPLIT_STARTUP=y`、`CONFIG_HOTPLUG_CORE_SYNC_FULL=y`，`x86_cpuinit.parallel_bringup` 默认为 `true`（`arch/x86/kernel/x86_init.c:129`），所以走的是并行路径。

这对 VMM 有一个实际后果：**三个 AP 的 vCPU 线程会在几乎同一时刻被唤醒，同时进入 guest。** 如果 VMM 的设备模型有并发问题，这是最容易暴露的时刻之一。mini-vmm 用一把 `io_lock` 把所有 PIO/MMIO exit 串行化（`src/vm.c:279`、`src/vm.c:289`），和 QEMU 的 BQL 是同一个思路，所以这里是安全的。

`cpuhp_smt_aware()` 那个分支在 mini-vmm 下不会走：它要求 `smp_num_siblings > 1`，而 mini-vmm 报的拓扑是每核一线程（第 7 节），`smp_num_siblings` 等于 1。

同步点的超时是 10 秒：

```c
/* guest v6.6 kernel/cpu.c:309 */
static bool cpuhp_wait_for_sync_state(unsigned int cpu, enum cpuhp_sync_state state,
                      enum cpuhp_sync_state next_state)
{
    atomic_t *st = per_cpu_ptr(&cpuhp_state.ap_sync_state, cpu);
    ktime_t now, end, start = ktime_get();
    int sync;

    end = start + 10ULL * NSEC_PER_SEC;
    ...
}
```

超时之后 `cpuhp_bp_sync_alive()` 打印 `CPU%u failed to report alive state` 并返回 `-EIO`。**这是 AP 没起来时唯一会出现的日志。** 如果你在 VMM 上看到它，说明 AP 的 vCPU 要么根本没收到 SIPI，要么在跳板或 `.Lfind_cpunr` 里死掉了。第 11 节给出区分这两种情况的方法。

### 4.4 AP 侧：`start_secondary()`

跳板把 AP 送进 `secondary_startup_64`，后者在设置完栈、GDT、段寄存器之后跳到 `initial_code`，也就是 `start_secondary()`（`do_boot_cpu()` 在 `smpboot.c:985` 设的）。这个函数的注释第一句就是警告：

```c
/* guest v6.6 arch/x86/kernel/smpboot.c:240 */
static void notrace start_secondary(void *unused)
{
	/*
	 * Don't put *anything* except direct CPU state initialization
	 * before cpu_init(), SMP booting is too fragile that we want to
	 * limit the things done here to the most necessary things.
	 */
	cr4_init();
	...
	cpu_init_exception_handling();
	load_ucode_ap();

	/*
	 * Synchronization point with the hotplug core. Sets this CPUs
	 * synchronization state to ALIVE and spin-waits for the control CPU to
	 * release this CPU for further bringup.
	 */
	cpuhp_ap_sync_alive();

	cpu_init();
	fpu__init_cpu();
	rcu_cpu_starting(raw_smp_processor_id());
	x86_cpuinit.early_percpu_clock_init();

	ap_starting();

	/* Check TSC synchronization with the control CPU. */
	check_tsc_sync_target();

	ap_calibrate_delay();
	...
	lock_vector_lock();
	set_cpu_online(smp_processor_id(), true);
	lapic_online();
	unlock_vector_lock();
	...
	local_irq_enable();

	x86_cpuinit.setup_percpu_clockev();

	wmb();
	cpu_startup_entry(CPUHP_AP_ONLINE_IDLE);
}
```

按顺序拆开，每一步对 VMM 意味着什么：

| 步骤 | 做什么 | VMM 侧的对应 |
|---|---|---|
| `cr4_init()` | 从 `cr4_init_shadow` 恢复 CR4 | 无 |
| `cpu_init_exception_handling()` | 装 IDT、设置 TSS 与 IST 栈 | 无。此后异常不再是三重故障 |
| `load_ucode_ap()` | 早期微码加载 | 置了 `hypervisor` 位就跳过，见卷五第 10 节 |
| `cpuhp_ap_sync_alive()` | 翻牌 `ALIVE`，自旋等 BSP 放行 | 纯内存自旋，KVM 下不产生 exit |
| `cpu_init()` | 加载 GDT/TSS、初始化 per-CPU | 无 |
| `ap_starting()` → `smp_store_cpu_info()` | **执行 CPUID，填 `cpu_data(cpu)`** | 第 7 节的全部内容都在这里生效 |
| `ap_starting()` → `set_cpu_sibling_map()` | 按拓扑建 sibling/core/llc 掩码 | CPUID 拓扑填错，这里就错 |
| `check_tsc_sync_target()` | TSC 同步检查 | 第 8 节 |
| `ap_calibrate_delay()` | 校准 `loops_per_jiffy` | BogoMIPS 那一行的来源 |
| `lapic_online()` | 把这颗 CPU 纳入中断向量分配 | 之后它才能收 IPI 和外设中断 |
| `local_irq_enable()` | **开中断** | 从这里开始 AP 会被时钟中断打断 |
| `setup_percpu_clockev()` | 启动 LAPIC timer | `/proc/interrupts` 的 `LOC` 计数从这里开始涨 |
| `cpu_startup_entry()` | 进 idle 循环，不返回 | AP 空闲时执行 `hlt`，见 6.3 节 |

最后那个 `hlt` 值得单独强调：**AP 一旦进入 idle 循环，它的 vCPU 线程绝大部分时间都阻塞在 `KVM_RUN` 里**，因为 KVM 对 guest 的 `HLT` 默认是拦截并在内核里睡眠，而不是返回用户态。mini-vmm 的 `vcpu_handle_exit()` 里 `KVM_EXIT_HLT` 分支写着“HLT, stopping”——那是 Step 1 的裸机 payload 用的语义，Linux guest 走不到这里，因为有了内核态 LAPIC 之后 HLT 由 KVM 自己处理。这个区别在 6.2 节还会再提一次。

## 5. KVM 这一侧：`mp_state` 状态机

### 5.1 五个状态

`KVM_GET_MP_STATE` / `KVM_SET_MP_STATE` 暴露出来的这个枚举（`include/uapi/linux/kvm.h`）是 KVM 对“处理器复位状态”的建模：

| 值 | 名字 | 含义 | x86 上谁会处在这里 |
|---|---|---|---|
| 0 | `KVM_MP_STATE_RUNNABLE` | 可以执行指令 | BSP 一创建就是；AP 收到 SIPI 之后 |
| 1 | `KVM_MP_STATE_UNINITIALIZED` | 从未被初始化，等 INIT | AP 刚创建时 |
| 2 | `KVM_MP_STATE_INIT_RECEIVED` | 收过 INIT，等 SIPI（即架构上的 wait-for-SIPI） | AP 收到 INIT 之后、SIPI 之前 |
| 3 | `KVM_MP_STATE_HALTED` | 执行了 `HLT`，等中断 | idle 中的任何 vCPU |
| 4 | `KVM_MP_STATE_SIPI_RECEIVED` | 历史遗留，x86 上 KVM 内部不再使用 | 只在 `KVM_SET_MP_STATE` 时被接受并折算成 `INIT_RECEIVED` |

正常的 AP 生命周期就是 `UNINITIALIZED` → `INIT_RECEIVED` → `RUNNABLE` → (`HALTED` ⇄ `RUNNABLE`) 这条链。

### 5.2 `KVM_RUN` 在 `UNINITIALIZED` 上的特殊行为

AP 线程创建出来后立刻调 `KVM_RUN`，此时它的 `mp_state` 是 `UNINITIALIZED`。KVM 的处理在 `kvm_arch_vcpu_ioctl_run()` 的最开头：

```c
/* host v5.15 arch/x86/kvm/x86.c:10007 */
	if (unlikely(vcpu->arch.mp_state == KVM_MP_STATE_UNINITIALIZED)) {
		if (kvm_run->immediate_exit) {
			r = -EINTR;
			goto out;
		}
		kvm_vcpu_block(vcpu);
		if (kvm_apic_accept_events(vcpu) < 0) {
			r = 0;
			goto out;
		}
		kvm_clear_request(KVM_REQ_UNHALT, vcpu);
		r = -EAGAIN;
		if (signal_pending(current)) {
			r = -EINTR;
			kvm_run->exit_reason = KVM_EXIT_INTR;
			++vcpu->stat.signal_exits;
		}
		goto out;
	}
```

`kvm_vcpu_block()` 把线程挂起，直到 `kvm_arch_vcpu_runnable()` 为真。BSP 发出的 INIT 在 `__apic_accept_irq()` 里置了 `pending_events` 并调 `kvm_vcpu_kick()`，线程被唤醒，`kvm_apic_accept_events()` 把状态推到 `INIT_RECEIVED`，然后——**`KVM_RUN` 返回 `-EAGAIN`，一次 guest 指令都没执行**。

这是 AP 唤醒全过程中唯一会冒到用户态的事件，也是 VMM 唯一必须写的一行代码：`EAGAIN` 不是错误，要当成“重新进 `KVM_RUN`”处理。mini-vmm 的处理在 `src/kvm_wrappers.c:129`：

```c
int kvm_run(int vcpu_fd)
{
    int r;

    /* 两种“没有 exit 可处理、重进 KVM_RUN 即可”的返回：
     *   EINTR   vm_request_stop() 用 immediate_exit + SIGUSR1 把 vCPU
     *           踢出来（Ctrl-A x、另一个 vCPU 触发了停机）
     *   EAGAIN  AP 处于 KVM_MP_STATE_UNINITIALIZED 时 KVM_RUN 阻塞到
     *           收到 INIT/SIPI，醒来后返回 -EAGAIN 而不是进 guest，
     *           见 host arch/x86/kvm/x86.c kvm_arch_vcpu_ioctl_run()
     * 两者都不写（或不保证写）exit_reason，单独返回 VMM_ERR_INTR，
     * 让 run loop 回去检查 should_stop 后重进。 */
    r = ioctl(vcpu_fd, KVM_RUN, 0);
    if (r < 0 && (errno == EINTR || errno == EAGAIN))
        return VMM_ERR_INTR;
    ...
}
```

把 `EAGAIN` 当成致命错误是新手 VMM 最常见的 SMP bug：单 vCPU 时永远遇不到，一加 `--smp 2` 就“AP 线程报错退出”，而错误信息 `Resource temporarily unavailable` 指向的方向完全是误导的。

漏掉 `exit_reason` 的处理同样危险。`-EAGAIN` 和 `immediate_exit` 路径都**不写** `kvm_run->exit_reason`，里面还留着上一次的值。如果 run loop 不加判断就去分发，会把上一次的 PIO 重放一遍。mini-vmm 在 `vcpu_run_loop()` 里对此有专门的注释和 `continue`（`src/vm.c:344-348`）。

### 5.3 第二次 `KVM_RUN`：等 SIPI

第二次进 `KVM_RUN` 时 `mp_state` 已经是 `INIT_RECEIVED`，走的是正常路径 `vcpu_run()`：

```c
/* host v5.15 arch/x86/kvm/x86.c:9825 */
	for (;;) {
		if (kvm_vcpu_running(vcpu)) {
			r = vcpu_enter_guest(vcpu);
		} else {
			r = vcpu_block(kvm, vcpu);
		}
		...
	}
```

`kvm_vcpu_running()` 要求 `mp_state == RUNNABLE`，`INIT_RECEIVED` 不满足，于是进 `vcpu_block()` 继续睡。SIPI 到达后：

```c
/* host v5.15 arch/x86/kvm/x86.c:9788，vcpu_block() */
	if (kvm_apic_accept_events(vcpu) < 0)
		return 0;
	switch(vcpu->arch.mp_state) {
	case KVM_MP_STATE_HALTED:
	case KVM_MP_STATE_AP_RESET_HOLD:
		vcpu->arch.pv.pv_unhalted = false;
		vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
		fallthrough;
	case KVM_MP_STATE_RUNNABLE:
		vcpu->arch.apf.halted = false;
		break;
	case KVM_MP_STATE_INIT_RECEIVED:
		break;
	default:
		return -EINTR;
	}
	return 1;
```

返回 1 表示循环继续；下一轮 `kvm_vcpu_running()` 为真，直接进 guest。整个第二段等待完全发生在 `KVM_RUN` 内部，用户态连一次返回都看不到。

### 5.4 `kvm_apic_accept_events()`：真正改状态的地方

```c
/* host v5.15 arch/x86/kvm/lapic.c:2880 */
int kvm_apic_accept_events(struct kvm_vcpu *vcpu)
{
	...
	pe = smp_load_acquire(&apic->pending_events);
	if (!pe)
		return 0;
	...
	/*
	 * INITs are latched while CPU is in specific states
	 * (SMM, VMX root mode, SVM with GIF=0).
	 * ...
	 */
	if (kvm_vcpu_latch_init(vcpu)) {
		WARN_ON_ONCE(vcpu->arch.mp_state == KVM_MP_STATE_INIT_RECEIVED);
		if (test_bit(KVM_APIC_SIPI, &pe))
			clear_bit(KVM_APIC_SIPI, &apic->pending_events);
		return 0;
	}

	if (test_bit(KVM_APIC_INIT, &pe)) {
		clear_bit(KVM_APIC_INIT, &apic->pending_events);
		kvm_vcpu_reset(vcpu, true);
		if (kvm_vcpu_is_bsp(apic->vcpu))
			vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
		else
			vcpu->arch.mp_state = KVM_MP_STATE_INIT_RECEIVED;
	}
	if (test_bit(KVM_APIC_SIPI, &pe)) {
		clear_bit(KVM_APIC_SIPI, &apic->pending_events);
		if (vcpu->arch.mp_state == KVM_MP_STATE_INIT_RECEIVED) {
			/* evaluate pending_events before reading the vector */
			smp_rmb();
			sipi_vector = apic->sipi_vector;
			kvm_x86_ops.vcpu_deliver_sipi_vector(vcpu, sipi_vector);
			vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
		}
	}
	return 0;
}
```

三个细节：

**INIT 会触发一次完整的 vCPU 复位。** `kvm_vcpu_reset(vcpu, true)` 把通用寄存器清零、`RIP` 置 `0xfff0`、`RFLAGS` 置 `X86_EFLAGS_FIXED`（即只有第 1 位）、`CR0` 只留 `ET`（加上从复位前继承的 `CD`/`NW`）、`CR4` 和 `EFER` 清零、`CR3` 清零，并按 SDM 的要求把 `EDX` 设成 CPUID.1:EAX 的值（家族/型号/步进）。这是架构规定的 INIT 语义，KVM 一丝不苟地实现了，连 Intel 与 AMD 手册对 `CD`/`NW` 描述不一致这种细节都在注释里写明了（`x86.c:10944`）。

**BSP 收到 INIT 不进 wait-for-SIPI。** 这符合规范：BSP 上的 INIT 等同于一次不经固件的软复位，它直接变回 `RUNNABLE` 从 `0xfff0` 重新开始。Linux 的 `reboot=triple` 之类路径依赖这一点。

**SIPI 的落地只有四行。**

```c
/* host v5.15 arch/x86/kvm/x86.c:10981 */
void kvm_vcpu_deliver_sipi_vector(struct kvm_vcpu *vcpu, u8 vector)
{
	struct kvm_segment cs;

	kvm_get_segment(vcpu, &cs, VCPU_SREG_CS);
	cs.selector = vector << 8;
	cs.base = vector << 12;
	kvm_set_segment(vcpu, &cs, VCPU_SREG_CS);
	kvm_rip_write(vcpu, 0);
}
```

`CS.base = vector << 12`，`RIP = 0`，于是下一条指令的物理地址正是 `vector << 12`。这里没有任何“进实模式”的动作——因为 INIT 复位已经把 `CR0.PE` 清掉了，vCPU 本来就在实模式。SVM 后端只是包了一层给 SEV-ES 用（`arch/x86/kvm/svm/svm.c:4494`）。

### 5.5 什么时候 VMM 才需要自己动手

前面说“VMM 什么都不用做”有一个前提：**内核态 irqchip**。把这个前提拿掉，结论完全反过来：

- 没有内核态 LAPIC，`KVM_CREATE_VCPU` 就把所有 vCPU 设成 `RUNNABLE`（`x86.c:10697`）。AP 线程一进 `KVM_RUN` 就会从 `RIP=0xfff0` 开始执行，而那里是空的。
- BSP 写 ICR 会变成一次 MMIO exit 打到用户态，VMM 必须自己解码 delivery mode，自己用 `KVM_SET_MP_STATE(KVM_MP_STATE_INIT_RECEIVED)` 和 `KVM_SET_SREGS` 模拟 INIT 与 SIPI 的语义。

这也是 `KVM_SET_MP_STATE` 这个**写**方向的 ioctl 存在的主要理由之一。另一个理由是虚拟机的保存/恢复与复位：QEMU 在 `kvm_arch_put_registers()` 里会写回 `mp_state`，否则从快照恢复出来的 AP 会带着错误的状态开跑。mini-vmm 这两件事都不做，所以从来不写 `mp_state`。

读的方向则相反：`KVM_GET_MP_STATE` 是排查 AP 不启动最直接的手段，mini-vmm 把它做成了 debug 级别的诊断（`src/kvm_wrappers.c` 的 `kvm_get_mp_state()`，调用点在 `vcpu_run_loop()`，见 11.1 节）。

需要注意的不是权限而是锁：几乎所有 vCPU ioctl 都在 `mutex_lock_killable(&vcpu->mutex)` 之后执行（`host v5.15 virt/kvm/kvm_main.c:3756`），而这把锁在整个 `KVM_RUN` 期间都被持有。所以从主线程去 `KVM_GET_MP_STATE` 一个正阻塞在 `KVM_RUN` 里的 AP，调用方会一直卡住，直到那个 vCPU 因为别的原因退出 `KVM_RUN`——而 AP 卡死的场景里它恰好永远不会退出。可行的做法只有两条：让每个 vCPU 线程在自己的 run loop 里报告状态（mini-vmm 选的这条），或者先用 `immediate_exit` + 信号把目标踢出来再查。

把三层合起来，一次 AP 唤醒的完整时序是这样的（横向是时间）：

## 6. vCPU 就是一个线程

### 6.1 模型

KVM 的 vCPU 是一个 fd，`KVM_RUN` 是一次阻塞的 ioctl，它在返回之前一直在执行 guest 代码。谁来调这个 ioctl，谁就是这颗 vCPU。所以 VMM 的 CPU 模型完全由它自己决定：

- **一线程一 vCPU**（QEMU、crosvm、Firecracker、mini-vmm 都是这个模型）。最自然，host 调度器直接看到 N 个可运行实体，SMP guest 的并行度是真实的。
- **一线程多 vCPU 轮转**。理论上可行（每个 vCPU fd 轮流 `KVM_RUN`，靠 `immediate_exit` 打断），但 guest 里任何自旋等待都会立刻死锁——vCPU 0 拿着锁自旋等 vCPU 1，而 vCPU 1 要等 vCPU 0 让出线程。没有实用价值。
- **同一个 vCPU 由不同线程先后运行**。KVM 允许，`kvm_vcpu_ioctl()` 里有一段专门处理 `vcpu->pid` 变化（`virt/kvm/kvm_main.c:3763`），但 `vcpu->mutex` 保证同一时刻只有一个线程在里面。迁移线程有额外代价（`kvm_arch_vcpu_run_pid_change()`），没有理由这么做。

mini-vmm 的实现只有 30 行：

```c
/* src/smp.c:152 */
int vm_run(struct vmm_vm *vm)
{
    struct sigaction sa;
    int i, started = 0, r = VMM_OK;

    /* 不带 SA_RESTART，保证 KVM_RUN 返回 EINTR */
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = kick_handler;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGUSR1, &sa, NULL) < 0) {
        vmm_err("sigaction(SIGUSR1) failed");
        return VMM_ERR_SYS;
    }

    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        if (pthread_create(&v->thread, NULL, vcpu_thread, v) != 0) {
            ...
        }
        __atomic_store_n(&v->thread_started, true, __ATOMIC_RELEASE);
        started++;
    }
    vmm_info("%d vCPU thread(s) running", started);

    for (i = 0; i < started; i++) {
        ...
        pthread_join(v->thread, NULL);
        ...
    }
    return r;
}
```

注意所有 vCPU 线程是**一次全部创建**的，包括 AP。AP 线程一起跑就一头扎进 `KVM_RUN`，然后阻塞在 KVM 内部等 INIT，一直等到 guest 内核跑到 `smp_init()`——在 mini-vmm 的日志时间轴上大约是 0.46 秒之后。这期间三个线程完全不消耗 CPU（`kvm_vcpu_block()` 用的是 `TASK_INTERRUPTIBLE` 的等待队列），`top` 里看到的 mini-vmm 只有一个线程在跑。

### 6.2 `KVM_RUN` 什么时候返回

理解 SMP VMM 的性能特征，关键是知道哪些事件会让 `KVM_RUN` 返回用户态，哪些不会。

| guest 行为 | 是否返回用户态 | 处理者 |
|---|---|---|
| PIO / MMIO 打到未被 KVM 接管的地址 | **是**，`KVM_EXIT_IO` / `KVM_EXIT_MMIO` | VMM 的设备模型 |
| 访问 LAPIC / IOAPIC / PIC / PIT 寄存器 | 否 | KVM 内核态 irqchip |
| 写 ICR 发 IPI（包括 INIT/SIPI） | 否 | 同上 |
| `HLT` | **取决于有没有内核态 LAPIC** | 有则 KVM 内部睡眠；无则 `KVM_EXIT_HLT` |
| `PAUSE`（自旋锁里） | 视 PLE 配置，多数情况下否 | KVM 的 `kvm_vcpu_on_spin()` |
| `CPUID`、`RDMSR`/`WRMSR` | 否（除非是 KVM 不认识的 MSR 且开了 filter） | KVM |
| 缺页（NPT/EPT violation） | 否 | KVM 的 MMU |
| 收到 `SIGUSR1` 等未屏蔽信号 | **是**，`-EINTR` | VMM |
| `kvm_run->immediate_exit == 1` | **是**，`-EINTR`，且不执行任何 guest 指令 | VMM |

`HLT` 那一行值得展开。mini-vmm 的 `vcpu_handle_exit()` 里有：

```c
    case KVM_EXIT_HLT:
        vcpu->n_exit_hlt++;
        vmm_info("vCPU %d: HLT, stopping", vcpu->id);
        return VMM_ERR_EXIT;
```

这是 Step 1 的语义：裸机 payload 执行完就 `hlt`，VMM 把它当作“跑完了”。但在 `--mode linux` 下这条分支永远走不到，因为 `KVM_CREATE_IRQCHIP` 之后 guest 的 `HLT` 由 KVM 自己处理——`kvm_emulate_halt()` → `__kvm_vcpu_halt()` 把 `mp_state` 设成 `HALTED` 然后阻塞，直到有中断可以注入。这是对的：Linux 的 idle 循环每秒执行几百次 `hlt`，每次都返回用户态的话开销无法接受。

这也解释了一个容易困惑的现象：mini-vmm 的 guest 关机时，四个 vCPU 里只有一个会走到 `KVM_EXIT_SYSTEM_EVENT`（执行 ACPI S5 写的那颗），其余三颗都还阻塞在 `HALTED` 里。让它们停下来是 6.4 节的事。

### 6.3 超卖与锁持有者被抢占

一线程一 vCPU 的直接后果是：**vCPU 的“物理 CPU 时间”由 host 调度器决定，guest 对此一无所知。** 如果 host 上跑着比物理核更多的 vCPU（超卖），或者 host 上有别的负载，一颗 vCPU 可能在任意一条指令之间被抢占几毫秒。

这在单核 guest 上只是变慢，在 SMP guest 上会引发结构性问题：

- **锁持有者被抢占**（lock holder preemption）。vCPU 0 拿着一把自旋锁，然后被 host 抢占。vCPU 1、2、3 在 guest 里自旋等这把锁，它们每一个都在真实地烧物理 CPU 时间，而且正是这些时间让 vCPU 0 更难被调度回来。
- **锁等待者被抢占**（lock waiter preemption）。排队自旋锁（queued spinlock）是有序的，队头的 vCPU 被抢占，后面所有人都得等。
- **IPI 延迟放大**。BSP 给一颗被抢占的 vCPU 发 IPI，`kvm_vcpu_kick()` 只是把它的线程置为可运行，真正执行要等 host 调度。物理机上 IPI 延迟是微秒级，超卖的虚拟机上可以是毫秒级。

业界对此有三套缓解手段，正好对应三个层次：

**硬件层：PAUSE 拦截。** guest 自旋锁里的 `PAUSE` 指令可以被拦截。AMD 叫 pause filter，Intel 叫 PLE（pause-loop exiting）。逻辑是“连续执行了 N 条 PAUSE 而没有别的进展，说明可能在自旋等一个被抢占的持有者”，于是产生一次 VM exit：

```c
/* host v5.15 arch/x86/kvm/svm/svm.c:3001 */
static int pause_interception(struct kvm_vcpu *vcpu)
{
	bool in_kernel;
	...
	if (!kvm_pause_in_guest(vcpu->kvm))
		grow_ple_window(vcpu);

	kvm_vcpu_on_spin(vcpu, in_kernel);
	return kvm_skip_emulated_instruction(vcpu);
}
```

`kvm_vcpu_on_spin()` 做的是**定向让步**（directed yield）：在同一个 VM 的其它 vCPU 里挑一个“看起来正需要 CPU”的，把自己的时间片让给它，赌的就是那个被挑中的正是锁持有者。SVM 的默认参数是 `pause_filter_count = 3000`、`pause_filter_thresh = 128`（`arch/x86/kvm/x86.h:66-72`），并且窗口会按 `grow_ple_window()` / `shrink_ple_window()` 动态调整。mini-vmm 的 `svm_dump_caps()` 会打印 `pausefilter` 特性位，海光机器上是有的。整件事完全在 host 内核里完成，用户态 VMM 既不用配置也看不到。

**半虚拟化层：PV spinlock 与 PV EOI。** guest 知道自己在虚拟机里的话，可以把“自旋等锁”换成“告诉 hypervisor 我要睡了，锁释放时叫我”（`KVM_HC_KICK_CPU` 超调用），把纯浪费的自旋变成一次让出。这需要 guest 侧 `CONFIG_PARAVIRT_SPINLOCKS`。mini-vmm 的 guest `.config` 里 `CONFIG_HYPERVISOR_GUEST` 没开，整条 PV 路径都不存在，用的是原生的 `qspinlock`。这是卷五第 10 节讨论 `hypervisor` 位时那条“开了 `CONFIG_KVM_GUEST` 的内核才会继续查 0x40000000 叶”的下游后果之一。

**部署层：不超卖。** 最简单也最有效。mini-vmm 是教学/实验 VMM，`--smp` 的值远小于 soc63 的物理核数，上面这些问题不会出现。但它们是真实生产环境里 SMP 虚拟化最主要的性能来源，值得知道其存在。

### 6.4 停机：信号与 `immediate_exit`

多 vCPU 带来的第二个用户态问题是：**怎么让所有 vCPU 线程停下来。**

单 vCPU 时不需要考虑——vCPU 自己走到 `KVM_EXIT_SYSTEM_EVENT` 就结束了。多 vCPU 时，触发关机的只有一颗，其余几颗可能在 `HLT` 里睡着，可能在跑 guest 代码，也可能刚检查完退出标志正要进 `KVM_RUN`。

最朴素的做法是设一个标志再发信号：

```c
v->should_stop = true;
pthread_kill(v->thread, SIGUSR1);
```

`KVM_RUN` 收到未屏蔽的信号会返回 `-EINTR`，run loop 看到 `should_stop` 就退出。但这有一个窗口：目标线程刚读完 `should_stop`（还是 false），还没进 `KVM_RUN`，此刻信号到达，被 handler 吃掉，什么也没发生；随后它进入 `KVM_RUN`，在 guest 的 `HLT` 里无限期睡下去，因为再也不会有人给它发信号了。

`kvm_run->immediate_exit`（`KVM_CAP_IMMEDIATE_EXIT`，4.11 引入）正是为这个窗口设计的。它是 `kvm_run` 共享页里的一个字段，`KVM_RUN` 在入口处检查它，为 1 就直接返回 `-EINTR`，一条 guest 指令都不执行（`host v5.15 arch/x86/kvm/x86.c:10056`）。

```c
/* src/smp.c:118 */
void vm_request_stop(struct vmm_vm *vm)
{
    int i;

    vm->running = false;
    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        v->should_stop = true;
        if (v->run)
            __atomic_store_n(&v->run->immediate_exit, 1, __ATOMIC_SEQ_CST);
        if (__atomic_load_n(&v->thread_started, __ATOMIC_ACQUIRE) &&
            !pthread_equal(v->thread, pthread_self()))
            pthread_kill(v->thread, SIGUSR1);
    }
}
```

**先置 `immediate_exit`，再发信号**，两个窗口就都被覆盖了：已经在 `KVM_RUN` 里的被信号踢出来，还没进去的被 `immediate_exit` 挡在门口。`__ATOMIC_SEQ_CST` 保证这个顺序不被编译器或 CPU 重排。

这里有三处容易写错的地方：

1. **信号处理函数不能带 `SA_RESTART`。** 带了的话 `KVM_RUN` 会被自动重启，`-EINTR` 根本传不到用户态。mini-vmm 用 `sigaction` 且 `sa.sa_flags` 为 0（`src/smp.c:158`）。用 `signal()` 而不是 `sigaction()` 是典型的坑，glibc 的 `signal()` 默认带 `SA_RESTART`。
2. **`immediate_exit` 置位后必须清。** mini-vmm 只在停机路径上置位，之后不会再进 guest，所以不用清。如果 VMM 把 `immediate_exit` 用作通用的“踢出”手段（比如为了同步取快照），下一次 `KVM_RUN` 之前必须清零，否则会无限返回 `-EINTR` 空转。
3. **`pthread_kill` 不能发给自己。** 触发停机的那颗 vCPU 正在 `vm_request_stop()` 里，给自己发信号没有意义还可能干扰后续逻辑，所以有 `!pthread_equal(v->thread, pthread_self())` 这个判断。

还有一个更彻底的方案：`KVM_SET_SIGNAL_MASK`。它让 KVM 在进 guest 之前替换线程的信号掩码、出来之后恢复（`kvm_sigset_activate()` / `kvm_sigset_deactivate()`，`x86.c:10003` 与 `10066`），从而彻底消除“信号在检查与进入之间丢失”的竞态。QEMU 用的是这条路。`immediate_exit` 更简单，对 mini-vmm 够用。

### 6.5 设备模型的并发

多个 vCPU 线程会同时陷出到用户态访问设备。mini-vmm 的选择是一把大锁：

```c
/* src/vm.c:275 */
    case KVM_EXIT_IO: {
        int r;

        vcpu->n_exit_io++;
        pthread_mutex_lock(&vcpu->vm->io_lock);
        r = handle_io(vcpu);
        pthread_mutex_unlock(&vcpu->vm->io_lock);
        return r;
    }
```

和 QEMU 的 BQL（big QEMU lock）是同一个思路：设备模型本身完全不做并发保护，由分发路径统一串行化。代价是设备访问不能并行，收益是所有设备实现（8250、i8042、RTC、ACPI PM1）都可以当单线程代码写。对于一个 exit 频率以千次每秒计的教学 VMM，这个取舍是明显划算的。

需要强调的是**设备表本身是只读的**：所有 `vmm_register_pio()` / `vmm_register_mmio()` 都在 guest 启动之前完成，之后只查不改，所以查表不需要加锁（加锁的只是设备回调）。如果将来要支持热插拔，这个假设就不成立了。

附带一条排查经验：多 vCPU 下如果串口输出出现交错，先判断交错发生在**行边界还是字符边界**。行边界的交错是 guest 行为，多核 `printk` 本来就允许不同 CPU 的整行穿插；字符边界的交错才说明 VMM 这一侧的串行化漏了，也就是某条设备访问路径绕过了 `io_lock`。

## 7. CPUID 拓扑：VMM 唯一真正必须写对的地方

前面六节的结论是“AP 唤醒不用 VMM 操心”。本节是它的反面：CPUID 拓扑字段必须由 VMM 逐位改写，而且 `KVM_GET_SUPPORTED_CPUID` 给出的默认值**一定是错的**。

### 7.1 问题出在哪

`KVM_GET_SUPPORTED_CPUID` 是一个 VM 级（其实是 `/dev/kvm` 级）的 ioctl，它返回“这台 host 的 CPU 能支持、且 KVM 愿意暴露的 CPUID 内容”。对于特性位，这个语义是对的；对于拓扑字段，它是有害的，因为：

- **CPUID.1:EBX[31:24] 是 initial APIC ID。** KVM 填的是执行这条 ioctl 的那颗物理 CPU 的值。把它原样 `KVM_SET_CPUID2` 给所有 vCPU，四颗 vCPU 会自报同一个 APIC ID。
- **核数、线程数、缓存共享关系描述的是 host 的物理拓扑**，而 guest 看到的是 VMM 决定的虚拟拓扑，两者毫无关系。soc63 是 32 个逻辑处理器，`--smp 4` 的 guest 只有 4 个 vCPU，直接透传的结果是 guest 以为自己有 32 个核。

后果不是“报告的数字难看”，而是功能性的：`initial_apicid` 决定 `phys_proc_id` 和 `cpu_core_id`，进而决定 `cpu_sibling_map` / `cpu_core_map` / `cpu_llc_shared_map`，进而决定调度域。所有 vCPU 自称同一个 APIC ID 时，`topology_update_package_map()` 里的 `BUG_ON` 未必会触发，但调度器会认为四颗 CPU 是同一个核的四个超线程，负载均衡行为完全错乱。

所以 mini-vmm 在 `amd_init_vcpu()` 里的顺序是固定的：取 host 的 CPUID → 按 vCPU 改写拓扑 → 置 `hypervisor` 位 → `KVM_SET_CPUID2`。

```c
/* src/arch/amd/svm.c，amd_init_vcpu() */
    r = kvm_get_supported_cpuid(vcpu->vm->kvm_fd, &cpuid);
    ...
    smp_fixup_cpuid(vcpu, cpuid);
    cpuid_mark_hypervisor(cpuid);
    r = kvm_set_cpuid2(vcpu->fd, cpuid);
```

**每个 vCPU 各调一次 `KVM_GET_SUPPORTED_CPUID`**，拿到各自独立的一份缓冲区再改，这样四份结果只有拓扑字段不同。共用一份缓冲区反复改写再 set 也能工作，但容易在下一次改动时写出“vCPU 3 的值覆盖了 vCPU 2”的 bug。

### 7.2 APIC ID 的结构

在讲具体的叶子之前要先说清 APIC ID 本身。x86 把 APIC ID 当作一个**分层编码的整数**：低位是线程号，往上是核号，再往上是 die/node 号，最高位是 socket 号。每一层占几位由 CPUID 告知。

```text
xAPIC ID（8 位）                    x2APIC ID（32 位）
┌────────┬────────┬────────┐        同样的分层，位宽更大
│ socket │  core  │ thread │
└────────┴────────┴────────┘
   高位              低位
```

mini-vmm 选择的拓扑是 **1 socket × N core × 1 thread，APIC ID 等于 vCPU 序号**。这意味着 thread 层占 0 位，core 层占 `ceil(log2(N))` 位，socket 层占剩下的。这是最简单也最不容易出错的选择：ID 连续、没有洞、和 `vcpu_id` 一一对应，和 KVM 的 LAPIC 默认 ID 一致，和 MADT 的登记顺序一致。

QEMU 支持更复杂的 `-smp sockets=,cores=,threads=`，代价是 APIC ID 变成稀疏的，MADT、CPUID、KVM 三边的换算全部要自己维护。对于 mini-vmm 这个规模，没有必要。

### 7.3 要改写的五个叶子

`smp_fixup_cpuid()`（`src/smp.c:195`）遍历所有 CPUID 条目，改其中四个叶子，再单独补一个：

```c
void smp_fixup_cpuid(const struct vmm_vcpu *vcpu, struct kvm_cpuid2 *cpuid)
{
    uint32_t id = (uint32_t)vcpu->id;
    uint32_t n  = (uint32_t)vcpu->vm->cfg.nr_vcpus;
    uint32_t i;

    for (i = 0; i < cpuid->nent; i++) {
        struct kvm_cpuid_entry2 *e = &cpuid->entries[i];

        switch (e->function) {
        case 0x1:
            e->ebx = (e->ebx & 0x0000ffffu) | (id << 24) |
                     ((n > 255 ? 255 : n) << 16);
            if (n > 1)
                e->edx |= CPUID_1_EDX_HTT;
            else
                e->edx &= ~CPUID_1_EDX_HTT;
            break;
        case 0x1f:
            e->eax = e->ebx = e->ecx = e->edx = 0;
            break;
        case 0x80000008:
            e->ecx = (e->ecx & ~0xf0ffu) | (order_base2(n) << 12) | (n - 1);
            break;
        case 0x8000001d: {
            uint32_t level = (e->eax >> 5) & 0x7;
            uint32_t share = (level >= 3) ? n - 1 : 0;

            if (e->eax & 0x1f)          /* cache type = 0 表示列表结束 */
                e->eax = (e->eax & ~(0xfffu << 14)) | (share << 14);
            break;
        }
        case 0x8000001e:
            e->eax = id;
            e->ebx = id & 0xff;
            e->ecx = 0;
            break;
        default:
            break;
        }
    }

    /* 0xB 要追加子叶，放在遍历之后做，避免边遍历边改 nent */
    cpuid_fill_topology_leaf(cpuid, id, n);
}
```

逐个说明。

#### CPUID.1:EBX 与 EDX.HTT

| 位 | 含义 | mini-vmm 填 |
|---|---|---|
| EBX[7:0] | Brand index | 保持 host 值 |
| EBX[15:8] | CLFLUSH 行大小（8 字节为单位） | 保持 host 值 |
| EBX[23:16] | 本 package 内可寻址的逻辑处理器数（HTT=1 时有效） | vCPU 总数，上限 255 |
| EBX[31:24] | **initial APIC ID** | vCPU 序号 |
| EDX[28] | HTT。AMD 语义：置位表示 EBX[23:16] 有效 | N>1 时置 1 |

`(e->ebx & 0x0000ffffu)` 保留低 16 位、重写高 16 位，正是这张表。

Linux 从这里读 `initial_apicid`：

```c
/* guest v6.6 arch/x86/kernel/cpu/common.c:1855，generic_identify() */
	if (c->cpuid_level >= 0x00000001) {
		c->initial_apicid = (cpuid_ebx(1) >> 24) & 0xFF;
		...
		c->phys_proc_id = c->initial_apicid;
	}
```

BSP 在 `identify_boot_cpu()` 里走一次，每个 AP 在 `start_secondary()` → `ap_starting()` → `smp_store_cpu_info()` → `identify_secondary_cpu()` 里各走一次。所以 **`initial_apicid` 是每颗 vCPU 自己执行 CPUID 得到的**，这就是它必须按 vCPU 改写的原因。

EBX[23:16] 这一项在 mini-vmm 的 guest 上其实没人读：Linux 读它的路径是 `detect_ht_early()`，而那个函数开头就有

```c
	if (cpu_has(c, X86_FEATURE_CMP_LEGACY))
		return -1;
```

海光/AMD 会置 `cmp_legacy`（CPUID.80000001:ECX[1]，guest `/proc/cpuinfo` 的 flags 里能看到），于是整条 `detect_ht` 路径被跳过，核数改从 `0x80000008` 取。填对它是为了自洽和面向别的 guest（比如 Intel 风格的解析），不是因为 Linux 需要。

#### CPUID.0xB 与 0x1F：扩展拓扑枚举

这两个是 Intel 定义的扩展拓扑枚举叶（0xB 是两级：SMT、Core；0x1F 是多级：加了 die、module、tile）。它们的每个子叶报告一层：

| 字段 | 含义 |
|---|---|
| EAX[4:0] | 从本层算到下一层，APIC ID 要右移几位 |
| EBX[15:0] | 本层的逻辑处理器数；为 0 表示这一层无效 |
| ECX[7:0] | 子叶号，原样回显 |
| ECX[15:8] | 层类型：0 = 无效（列表结束），1 = SMT，2 = Core，5 = Die |
| EDX | 完整的 32 位 x2APIC ID |

在 soc63 上实测 `KVM_GET_SUPPORTED_CPUID` 对这两个叶子的态度：0xB 只有一条**内容全零**的子叶 0，0x1F 一条都没有。

```text
leaf 00000000 idx 0 flags 0 : eax=0000000d ...
leaf 0000000b idx 0 flags 1 : eax=00000000 ebx=00000000 ecx=00000000 edx=00000000
```

Linux 判断“有没有这套枚举”的条件是子叶 0 的 EBX 非零且层类型为 SMT：

```c
/* guest v6.6 arch/x86/kernel/cpu/topology.c:35 */
static int check_extended_topology_leaf(int leaf)
{
	unsigned int eax, ebx, ecx, edx;

	cpuid_count(leaf, SMT_LEVEL, &eax, &ebx, &ecx, &edx);

	if (ebx == 0 || (LEAFB_SUBTYPE(ecx) != SMT_TYPE))
		return -1;

	return 0;
}
```

所以原样透传等于告诉 guest“不提供”。对 AMD/海光 guest 这没有影响——它们还有 `0x80000008` + `0x8000001E` 这条退路；但 Intel guest 只认 0x1F/0xB，退路是 `detect_ht()` 读 CPUID.1:EBX[23:16] 加 CPUID.4，更难填对。

mini-vmm 现在按 1 socket × n core × 1 thread 把 0xB 补齐（`src/smp.c:90` 的 `cpuid_fill_topology_leaf()`）。由于 KVM 只给了子叶 0，补出另外两条必须往 `kvm_cpuid2` 数组里**追加**条目，所以 `kvm_get_supported_cpuid()` 在申请缓冲区时多留了 `KVM_CPUID_SPARE` 个空位，但只向 KVM 声明较小的 `nent`：

```c
/* src/kvm_wrappers.c */
        /* 多分配 KVM_CPUID_SPARE 条但只向 KVM 声明 nent 条，
         * 于是返回后 entries[] 末尾必然还有这么多空位可供追加 */
        c = calloc(1, sizeof(*c) +
                      (nent + KVM_CPUID_SPARE) * sizeof(struct kvm_cpuid_entry2));
        if (!c)
            return VMM_ERR_NOMEM;
        c->nent = nent;
```

追加的三条子叶是：

| 子叶 | EAX（移位） | EBX（本层处理器数） | ECX（子叶号 + 类型） | EDX |
|---|---|---|---|---|
| 0 | 0 | 1 | `0 \| (1 << 8)` SMT | APIC ID |
| 1 | `order_base2(n)` | n | `1 \| (2 << 8)` Core | APIC ID |
| 2 | 0 | 0 | `2 \| (0 << 8)` 无效，终止 | APIC ID |

每条都要带 `KVM_CPUID_FLAG_SIGNIFCANT_INDEX`（子叶号有意义），否则 KVM 查表时不会区分 index。追加位置放在数组末尾即可：KVM 的 `cpuid_entry2_find()` 是线性查找，不要求排序。

把这三条代进 `detect_extended_topology()`（`topology.c:92`）算一遍，结果与 `0x8000001E` 那条路完全一致：`ht_mask_width = 0`，`pkg_mask_width = order_base2(n)`，于是 `cpu_core_id = apicid`、`phys_proc_id = apicid >> order_base2(n) = 0`、`x86_max_cores = n`、`__max_die_per_package = 1`。两条路并存不会打架——这一点很重要，因为海光的 `hygon_get_topology()` 会**先**读 0x8000001E、**再**调 `detect_extended_topology()` 去覆盖，两者必须得出同样的答案。`--smp 16` 实测确认了这一点：补齐 0xB 之后 guest 报的仍然是 `APIC-0-1-…-15`、`CORE-0-1-…-15`、`PKG-0`、`thread_siblings_list` 每颗只有自己，与补齐之前逐字相同。

0x1F 仍然整体清零。KVM 一条子叶都没给，而填一半（比如只有 SMT 层没有 Core 层）会让 `detect_extended_topology()` 算出错误的 `core_select_mask`。**宁可不提供，不要提供一半**，这是 CPUID 改写的通则。清零之后 `detect_extended_topology_leaf()` 会跳过 0x1F 转而检查 0xB，正是我们想要的顺序。

顺带一提，这台 host 的 CPUID.0:EAX 是 `0x0d`，也就是最大基本叶为 13：大于 0xB，小于 0x1F。所以 guest 根本不会去查 0x1F（`c->cpuid_level >= 0x1f` 不成立），而 0xB 会被查到。如果某台 host 的最大基本叶小于 0xB，补上的 0xB 就是白补——按 AMD 的 CPUID 语义，越界的叶子返回全零。无害，但知道这一点能省下一次困惑。

#### CPUID.0x80000008:ECX

AMD 的核数与 APIC ID 位宽：

| 位 | 名称 | 含义 | mini-vmm 填 |
|---|---|---|---|
| ECX[7:0] | NC | 本 package 内的物理核数 **减 1** | `n - 1` |
| ECX[11:8] | 保留 | | 保持 |
| ECX[15:12] | ApicIdSize | APIC ID 中用于区分核的位数；为 0 表示“自己按 NC 推算” | `ceil(log2(n))` |

Linux 的读取点：

```c
/* guest v6.6 arch/x86/kernel/cpu/hygon.c:192，early_init_hygon_mc() */
	ecx = cpuid_ecx(0x80000008);

	c->x86_max_cores = (ecx & 0xff) + 1;

	/* CPU telling us the core id bits shift? */
	bits = (ecx >> 12) & 0xF;

	/* Otherwise recompute */
	if (bits == 0) {
		while ((1 << bits) < c->x86_max_cores)
			bits++;
	}

	c->x86_coreid_bits = bits;
```

`--smp 4` 时 mini-vmm 写的是 `ecx = 0x2003`：`x86_max_cores = 4`，`x86_coreid_bits = 2`。随后 `hygon_detect_cmp()`（`hygon.c:119`）用这两个值把 APIC ID 拆开：

```c
	bits = c->x86_coreid_bits;
	/* Low order bits define the core id (index of core in socket) */
	c->cpu_core_id = c->initial_apicid & ((1 << bits)-1);
	/* Convert the initial APIC ID into the socket ID */
	c->phys_proc_id = c->initial_apicid >> bits;
	/* use socket ID also for last level cache */
	per_cpu(cpu_llc_id, cpu) = c->cpu_die_id = c->phys_proc_id;
```

APIC ID 0-3、`bits=2` ⇒ `cpu_core_id` 是 0-3，`phys_proc_id` 全是 0。这就是 guest `/proc/cpuinfo` 里 `physical id: 0`、`cpu cores: 4`、`core id: 0..3` 的来源，也是 `smpboot: Max logical packages: 1` 的来源。

**`order_base2(n)` 而不是 `n - 1` 的位数**：如果 `n` 不是 2 的幂（比如 `--smp 3`），`order_base2(3)` 是 2，`bits=2` 能容纳 APIC ID 0、1、2，正确。如果这里填 0 让内核自己推算，`while ((1 << bits) < 3) bits++` 同样得到 2。两条路一致，显式填上只是为了不依赖内核的推算逻辑。

#### CPUID.0x8000001E

AMD 的扩展 APIC ID 与核/节点编号：

| 寄存器与位 | 含义 | mini-vmm 填 |
|---|---|---|
| EAX[31:0] | Extended APIC ID | vCPU 序号 |
| EBX[7:0] | Core ID（package 内） | vCPU 序号 |
| EBX[15:8] | 每核线程数 **减 1** | 0（每核单线程） |
| ECX[7:0] | Node ID | 0 |
| ECX[10:8] | 每 package 的节点数 **减 1** | 0（单节点） |

三处读取点，全部集中在海光的拓扑代码里：

```c

{

		smp_num_siblings = ((cpuid_ebx(0x8000001e) >> 8) & 0xff) + 1;
}
```

```c
/* guest v6.6 arch/x86/kernel/cpu/hygon.c:223，bsp_init_hygon() */
	if (boot_cpu_has(X86_FEATURE_TOPOEXT)) {
		u32 ecx;

		ecx = cpuid_ecx(0x8000001e);
		__max_die_per_package = nodes_per_socket = ((ecx >> 8) & 7) + 1;
	}
```

```c
/* guest v6.6 arch/x86/kernel/cpu/hygon.c:74，hygon_get_topology() */
		cpuid(0x8000001e, &eax, &ebx, &ecx, &edx);

		c->cpu_die_id  = ecx & 0xff;
		c->cpu_core_id = ebx & 0xff;

			c->x86_max_cores /= smp_num_siblings;
```

三项分别给出 `smp_num_siblings = 1`（无 SMT）、`nodes_per_socket = 1`（单节点）、`cpu_core_id = vCPU 序号`、`cpu_die_id = 0`。`smp_num_siblings = 1` 这一项还有一个间接作用：它让 6.6 的并行启动跳过 `cpuhp_smt_aware()` 那个“先起主线程”的分支（4.3 节）。

`X86_FEATURE_TOPOEXT` 来自 CPUID.80000001:ECX[22]，host 有、透传给 guest，所以上面三条路径都会走。

#### CPUID.0x8000001D

AMD 的缓存拓扑，按子叶枚举每一级缓存：

| 位 | 含义 |
|---|---|
| EAX[4:0] | 缓存类型：0=无（枚举结束）、1=数据、2=指令、3=统一 |
| EAX[7:5] | 缓存层级（1/2/3） |
| EAX[25:14] | **共享这一级缓存的逻辑处理器数减 1** |
| EBX / ECX / EDX | 行大小、路数、组数等几何参数 |

mini-vmm 只改 `EAX[25:14]`：L1 和 L2 按每核私有（填 0），L3 按所有 vCPU 共享（填 `n-1`）。这对应“单 socket、所有核共享一个 LLC”的模型，也是 guest 里 `/sys/devices/system/cpu/cpu0/cache/index3/shared_cpu_list` 应该显示 `0-3` 的原因。

这里有一个只在 vCPU 数较多时才暴露的坑，值得单独记一笔。海光在 model < 0x5 的处理器上**不看 `0x8000001D`**，而是直接从 APIC ID 里取 LLC 域号：

```c
/* guest v6.6 arch/x86/kernel/cpu/cacheinfo.c:702 */
void cacheinfo_hygon_init_llc_id(struct cpuinfo_x86 *c, int cpu)
{
	if (!cpuid_edx(0x80000006))
		return;

	if (c->x86_model < 0x5 ||
	    (c->x86_model >= 0x10 && c->x86_model <= 0x1f)) {
		/*
		* LLC is at the core complex level.
		* Core complex ID is ApicId[3] for these processors.
		*/
		per_cpu(cpu_llc_id, cpu) = c->apicid >> 3;
	} else {
		...
	}
}
```

mini-vmm 的 guest 上 `model = 1`，走的正是第一个分支：`cpu_llc_id = apicid >> 3`。**vCPU 数不超过 8 时所有 vCPU 的 `cpu_llc_id` 都是 0，一切正常；一旦超过 8，vCPU 8 及以后的 `cpu_llc_id` 变成 1、2……，`match_llc()` 就会把它们判为不同的 LLC 域**，`cpu_llc_shared_map` 被切成几块，调度域也随之分层。

这一条是在 soc63 上实测确认的。`--smp 4` 时符合预期：

```text
[guest /]# cat /sys/devices/system/cpu/cpu0/cache/index3/shared_cpu_list
0-3
[guest /]# cat /sys/devices/system/cpu/cpu0/cache/index0/shared_cpu_list
0
```

`--smp 16` 时 LLC 在第 8 颗上被切开：

```text
cpu0 llc=0-7
cpu7 llc=0-7
cpu8 llc=8-15
cpu9 llc=8-15
cpu15 llc=8-15
```

注意此时 CPUID.0x8000001D 里 mini-vmm 报的仍然是“L3 由 16 个逻辑处理器共享”，guest 根本没看这个字段，直接按 `apicid >> 3` 判了。这不是 mini-vmm 的 bug，而是“APIC ID 等于 vCPU 序号”这个简单约定在特定 guest CPU 型号上的副作用——真实硬件上海光这一代的 APIC ID 第 3 位确实就是核簇（CCX）编号，内核的这条捷径在物理机上是对的。

要不要管它，取决于目标：如果只是让 guest 跑起来，8 核以内无所谓，超过也只是拓扑不好看；如果要拿 mini-vmm 测调度或缓存亲和性，就必须让 VMM 报告的拓扑与 guest 的解析规则自洽——最省事的办法是在 CPUID 里把 `model` 也改写成一个落进 `else` 分支的值，但那会连带影响别的 errata 判断，得慎重。这类“guest 用一条写死的规则从 APIC ID 反推拓扑”的情况在各家 CPU 上都有，是 VMM 做 CPU 模型时必须逐条排查的暗礁。

mini-vmm 现在的做法是**只提示、不改行为**：`vm_run()` 开头调一次 `smp_warn_llc_split()`（`src/smp.c:144`），host 是海光且型号落在那两个区间、且 vCPU 超过 8 个时打一行警告。

```text
[WARN] 16 vCPUs: this guest CPU model derives the LLC id from APIC ID bit 3, so the guest will split the vCPUs into 8-CPU last-level-cache domains regardless of what CPUID leaf 0x8000001D reports
```

判断条件照抄内核：海光厂商、`model < 0x5` 或 `0x10 <= model <= 0x1f`。family/model 的组合方式也和内核一致（family 为 `0xf` 时加扩展 family，family ≥ `0xf` 时拼上扩展 model），这样这行警告要么准确，要么根本不出现。

### 7.4 三家 CPU 的三条解析路径

同一件事（从 CPUID 推出拓扑），Linux 有三条并行的实现，VMM 改写 CPUID 时必须知道 guest 会走哪一条：

| 厂商 | 入口 | 优先用 | 退路 |
|---|---|---|---|
| Intel | `init_intel()` → `detect_extended_topology()` | 0x1F，其次 0xB | `detect_ht()` 读 CPUID.1:EBX[23:16] + CPUID.4:EAX[31:26] |
| AMD | `init_amd()` → `amd_get_topology()` | `TOPOEXT` 时用 0x8000001E，其中再试一次 0xB/0x1F | `amd_detect_cmp()` 用 `0x80000008` 的 `coreid_bits` 拆 APIC ID |
| 海光 | `init_hygon()` → `hygon_get_topology()` | 同 AMD，另加 `cacheinfo_hygon_init_llc_id()` | `hygon_detect_cmp()` |

三条路都要先有正确的 `initial_apicid`，所以 **CPUID.1:EBX[31:24] 是唯一一个无论 guest 是什么 CPU 都必须改对的字段**。其余字段是“按 guest 会走哪条路来填”。mini-vmm 目前只有 AMD/海光后端，所以 0x8000001E 和 0x80000008 填得细，0xB 直接清零；将来加 Intel 后端时，0xB 必须补齐，否则 Intel guest 会退到 `detect_ht()`，而那条路需要 CPUID.4 的核数字段也一并改写。

注意 `amd_get_topology()` 与 `hygon_get_topology()` 内部还会**再调一次 `detect_extended_topology()`**（`hygon.c:87`）：如果 0xB 可用，用 0xB 的结果覆盖前面从 0x8000001E 得到的值。所以“AMD 就不看 0xB”是不准确的——清零 0xB 是让它明确地走不通，而不是让它被忽略。

### 7.5 三方一致：Linux 自己会检查

本卷开头那条铁律，Linux 里有一处显式检查：

```c
/* guest v6.6 arch/x86/kernel/cpu/common.c:1889 */
static void validate_apic_and_package_id(struct cpuinfo_x86 *c)
{
#ifdef CONFIG_SMP
	unsigned int apicid, cpu = smp_processor_id();

	apicid = apic->cpu_present_to_apicid(cpu);

	if (apicid != c->apicid) {
		pr_err(FW_BUG "CPU%u: APIC id mismatch. Firmware: %x APIC: %x\n",
		       cpu, apicid, c->initial_apicid);
	}
	BUG_ON(topology_update_package_map(c->phys_proc_id, cpu));
	BUG_ON(topology_update_die_map(c->cpu_die_id, cpu));
#endif
```

`apic->cpu_present_to_apicid(cpu)` 取的是**固件表**（MADT 或 MP 表）登记的值，`c->apicid` 是 `init_hygon()` 里 `read_apic_id()` 从 **LAPIC** 读到的值。两者不等就打印 `[Firmware Bug] CPU1: APIC id mismatch`。这是 VMM 固件表与 KVM 不一致时最直接的信号，而且它出现在 AP 上线的过程中，很容易被淹没在别的日志里——排查 SMP 问题时应该主动 `dmesg | grep -i 'apic id'` 找一遍。

第三方——CPUID 报告的 `initial_apicid`——反而没有被直接比对。它的错误表现得更隐蔽：`phys_proc_id` 和 `cpu_core_id` 算错，`topology_update_package_map()` 返回非零触发 `BUG_ON`，或者悄悄地把几颗 CPU 归进同一个核。

三者的来源和 mini-vmm 的保证方式：

| 来源 | 由谁决定 | mini-vmm 怎么保证等于 vCPU 序号 |
|---|---|---|
| LAPIC 的 ID 寄存器（`read_apic_id()`） | KVM 的 LAPIC 模拟，默认 `= vcpu_id` | 不动 KVM 的默认值 |
| 固件表（`cpu_present_to_apicid()`） | VMM 写的 MADT / MP 表 | `acpi.c:242` 与 `mptable.c:153` 都是 `= i` |
| CPUID.1:EBX[31:24] | `KVM_SET_CPUID2` 的内容 | `smp.c:66` 的 `id << 24` |

三处代码分别在三个文件里，靠的是同一个约定而不是同一个常量。这正是这类 bug 难查的原因，也是第 10 节要把检查清单单独列出来的原因。

## 8. 多核之后的时间：TSC 同步

### 8.1 为什么 SMP 让时间变成问题

单核时“现在几点”只有一个答案。多核时每颗 CPU 有自己的 TSC 计数器，内核要用它们做 `sched_clock()`、`clocksource`、延迟循环，前提是**所有 CPU 的 TSC 读数一致且以同样速率前进**。物理机上这个前提经常不成立：多路系统的 TSC 由不同的时钟源驱动，深度 C 状态可能停掉 TSC，BIOS 可能在某些 CPU 上写过 `IA32_TSC_ADJUST`。所以内核必须自己验证。

验证逻辑在 `arch/x86/kernel/tsc_sync.c`，每颗 AP 在 `start_secondary()` 里调 `check_tsc_sync_target()`，与 BSP 配对做一次 warp 检测：两边反复读 TSC，如果后读到的值比先读到的小，说明不同步。失败的话打印 `Measured N cycles TSC warp between CPUs, turning off TSC clock.` 并把 TSC 标为不可用，退回 HPET 或 ACPI PM timer——在 mini-vmm 的 guest 里这两者都没有，只剩 `jiffies`，系统会变得极慢且时间精度极差。

### 8.2 mini-vmm 的 guest 为什么跳过了这项检查

实际的 guest 日志里没有任何 `TSC synchronization` 相关的行。原因在检测函数开头：

```c
/* guest v6.6 arch/x86/kernel/tsc_sync.c:431 */
void check_tsc_sync_target(void)
{
	...
	/* Also aborts if there is no TSC. */
	if (unsynchronized_tsc())
		return;

	/*
	 * Store, verify and sanitize the TSC adjust register. If
	 * successful skip the test.
	 * ...
	 */
	if (tsc_store_and_check_tsc_adjust(false) || tsc_clocksource_reliable)
		return;
```

`tsc_store_and_check_tsc_adjust()` 在 CPU 支持 `IA32_TSC_ADJUST`（`X86_FEATURE_TSC_ADJUST`，guest `/proc/cpuinfo` 的 flags 里有 `tsc_adjust`）时，会读出本 CPU 的 `TSC_ADJUST` 值，与同 socket 内已经上线的参考 CPU 比较：

```c
/* guest v6.6 arch/x86/kernel/tsc_sync.c:230 */
	if (bootval != ref->adjusted) {
		cur->adjusted = ref->adjusted;
		wrmsrl(MSR_IA32_TSC_ADJUST, ref->adjusted);
	}
	/*
	 * We have the TSCs forced to be in sync on this package. Skip sync
	 * test:
	 */
	return true;
```

一致（都是 0）就返回 `true`，warp 检测整个跳过。这是现代物理机上的常规路径，虚拟机里同样成立。

**这不是运气。** KVM 保证了所有 vCPU 的 TSC 偏移相同：

```c
/* host v5.15 arch/x86/kvm/x86.c:10805，kvm_arch_vcpu_postcreate() */
	kvm_synchronize_tsc(vcpu, 0);
```

每个 vCPU 创建完成时 KVM 都会用 `data == 0` 调一次 `kvm_synchronize_tsc()`，而这个值被专门当作“vCPU 初始化”的信号：

```c
/* host v5.15 arch/x86/kvm/x86.c:2472 */
		if (data == 0) {
			/*
			 * detection of vcpu initialization -- need to sync
			 * with other vCPUs. This particularly helps to keep
			 * kvm_clock stable after CPU hotplug
			 */
			synchronizing = true;
		}
```

`synchronizing` 为真且 host TSC 稳定时，新 vCPU 直接复用 `kvm->arch.cur_tsc_offset`——**同一个 VM 的所有 vCPU 共享同一个 TSC 偏移**。guest 里读到的 TSC 就是 `host TSC + 同一个常数`，天然同步。这也是 `kvm->arch.nr_vcpus_matched_tsc` 计数的用途：全部匹配时 KVM 才会启用 master clock 模式（`kvm_track_tsc_matching()`，`x86.c:2308`），让 kvmclock 走快速路径。

所以 VMM 这一侧要做的是**不要破坏它**：

- 不要用 `KVM_SET_MSRS` 给不同 vCPU 写不同的 `MSR_IA32_TSC`。真要设置初始 TSC，所有 vCPU 必须在很短的时间窗口内写同一个值（KVM 有一个 1 秒的容忍窗口，见 `x86.c:2481` 的 `synchronizing = data < tsc_exp + tsc_hz && ...`）。
- 不要给不同 vCPU 设不同的 `KVM_SET_TSC_KHZ`。
- 快照恢复时要成组地恢复 TSC，而不是逐个 vCPU 恢复。

mini-vmm 这三件事一件都不做，所以它落在最安全的默认路径上。

### 8.3 TSC 频率与缩放

guest 看到的 TSC 频率默认等于 host 的。`KVM_GET_TSC_KHZ` 可以查，`KVM_SET_TSC_KHZ` 可以改——改成与 host 不同的值需要硬件支持 TSC 缩放，AMD 叫 `TscRateMSR`，Intel 叫 TSC scaling。mini-vmm 的 `svm_dump_caps()` 输出里的 `tsc_scale` 就是这一位（CPUID Fn8000_000A_EDX[4]），soc63 上是有的：

```text
[INFO] SVM features: npt lbrv svm_lock nrip_save tsc_scale vmcb_clean flushbyasid decodeassists pausefilter avic v_vmsave_vmload vgif
```

它的用途是虚拟机迁移：从 3.0 GHz 的机器迁到 2.5 GHz 的机器上，guest 里的 TSC 频率必须保持不变，否则所有基于 TSC 的计时都会错。不迁移的话没有必要碰它。

**guest 怎么知道 TSC 频率？** 在没有 kvmclock 的情况下，只能自己测。mini-vmm 的 guest 用的是 PIT：

```text
[    0.000000] tsc: Fast TSC calibration using PIT
[    0.000000] tsc: Detected 3000.118 MHz processor
```

这条路径（`quick_pit_calibrate()`）在虚拟机里是有抖动的：它要求两次读 PIT 之间的时间误差外推后低于 500 ppm，只有约 24 µs 的余量，而虚拟机里每次读 PIT 都是一次 VM exit。失败时内核不打印任何提示，直接退回更慢但更稳的 `pit_calibrate_tsc()`，日志变成 `tsc: Using PIT calibration value`。两条路都正确，只是测得的精度不同。soc63 上 12 次启动里快速路径成功 8 次，这就是 `tests/step2.sh` 里那条断言必须用 `expect_any` 同时接受两种日志的原因。

如果要从根上避免这类抖动，VMM 可以用 `KVM_GET_TSC_KHZ` 取得频率，再通过内核命令行 `tsc_early_khz=<kHz>` 直接告诉 guest，绕开 PIT 校准。这条路 mini-vmm 目前没走，因为它会让 guest 的时间来源从“自己测”变成“信 VMM 说的”，对一个用来教学的 VMM 来说，保留真实的校准过程反而更有价值。

### 8.4 BogoMIPS 与 AP 的延迟校准

`start_secondary()` 里 TSC 同步检查之后紧接着的是：

```c
/* guest v6.6 arch/x86/kernel/smpboot.c:222 */
static void ap_calibrate_delay(void)
{
	/*
	 * Calibrate the delay loop and update loops_per_jiffy in cpu_data.
	 * ...
	 * As this is invoked after the TSC synchronization check,
	 * calibrate_delay_is_known() will skip the calibration routine
	 * when TSC is synchronized across sockets.
	 */
	calibrate_delay();
	cpu_data(smp_processor_id()).loops_per_jiffy = loops_per_jiffy;
}
```

TSC 已确认同步时，`calibrate_delay_is_known()` 让 AP 直接沿用 BSP 的 `loops_per_jiffy`，不再自己跑校准循环。guest 日志里因此只有 BSP 那一行：

```text
[    0.153526] Calibrating delay loop (skipped), value calculated using timer frequency.. 6000.59 BogoMIPS (lpj=3000295)
```

而最终的总数是简单相加（`impress_friends()`，`smpboot.c:751`）。16 vCPU 时 `16 × 6000.59 ≈ 96009.44`，与实测的 `smpboot: Total of 16 processors activated (96009.44 BogoMIPS)` 完全对上。**这是一个很方便的自检：BogoMIPS 总数除以 vCPU 数如果不等于单颗的值，说明某颗 AP 的 TSC 或延迟校准走了不同的路径，多半意味着 TSC 同步出了问题。**

顺带说明为什么这里的 BogoMIPS（6000.59）恰好是主频（3000.295 MHz）的两倍：跳过校准时 `lpj` 直接取 `tsc_khz`（这里是 3000295），而 BogoMIPS 的定义是 `lpj / (500000/HZ)`，guest 的 `CONFIG_HZ=1000`，除数就是 500，于是 `3000295/500 = 6000.59`——正好是频率的两倍。这个数字在现代内核里已经不代表任何真实的循环速度。

### 8.5 没有 kvmclock 的后果

KVM 提供了一个半虚拟化时钟 kvmclock：host 把一个结构体（TSC 时间戳 + 换算系数 + 系统时间）写进 guest 的一页内存，guest 读 TSC 再按系数换算，就能得到与 host 一致的、跨迁移稳定的墙钟时间。它需要 guest 侧 `CONFIG_KVM_GUEST`，而识别的第一步是看 CPUID.1:ECX[31] 的 `hypervisor` 位（卷五第 10 节）。

mini-vmm 的 guest `.config` 里 `CONFIG_HYPERVISOR_GUEST` 没开，所以即使 VMM 置了 `hypervisor` 位，kvmclock 也不会启用。guest 的时间完全靠自己的 TSC：

```text
[    0.594722] clocksource: Switched to clocksource tsc-early
[    1.714051] clocksource: Switched to clocksource tsc
[    0.762038] sched_clock: Marking stable (748015673, 13759732)->(784025844, -22250439)
```

`Switched to clocksource tsc` 是一个重要的正面信号：它意味着内核完成了 `tsc_refine_calibration_work()` 的复核，认定 TSC 稳定且同步，愿意把它当作系统时钟源。如果 SMP 环境下 TSC 有问题，这一行会变成 `Switched to clocksource jiffies` 或者出现 `Marking TSC unstable`。**排查 SMP 时间问题时，`dmesg | grep clocksource` 的最后一行是最直接的结论。**

## 9. IPI：多核运行期的主要开销

AP 起来之后，SMP 带给 VMM 的持续性负担只有一项：**处理器间中断**。本节把它的代价、观察方法和三种优化路径讲清楚。

### 9.1 guest 里的 IPI 从哪来

`/proc/interrupts` 下半部分全是 IPI 计数。mini-vmm 4 vCPU 的实测：

```text
NMI:          0          0          0          0   Non-maskable interrupts
LOC:        344        114        179        120   Local timer interrupts
SPU:          0          0          0          0   Spurious interrupts
IWI:          0          0          0          0   IRQ work interrupts
RTR:          0          0          0          0   APIC ICR read retries
RES:          0         16         15         12   Rescheduling interrupts
CAL:        173         71        139         39   Function call interrupts
TLB:          0          0          1          0   TLB shootdowns
```

| 计数 | 来源 | 触发场景 |
|---|---|---|
| `LOC` | LAPIC timer，不是 IPI | 每颗 CPU 自己的时钟中断。注意它是**由 KVM 的内核态 LAPIC 模拟产生的**，不经过 VMM |
| `RES` | `smp_send_reschedule()` | 唤醒的任务应该跑在另一颗 CPU 上，通知它重新调度 |
| `CAL` | `smp_call_function*()` | 跨 CPU 执行函数。启动阶段这个数最大，因为 MTRR 同步、CPU 特性设置、缓存初始化都要在所有 CPU 上执行 |
| `TLB` | `flush_tlb_others()` | 一颗 CPU 改了共享的页表，要通知其他 CPU 作废 TLB |
| `RTR` | `safe_apic_wait_icr_idle()` 的重试次数 | **在 KVM 下恒为 0**，见 2.4 节：KVM 的 ICR 发送是同步的，Delivery Status 位被直接清掉 |

`RTR` 恒为 0 这一点可以当作“LAPIC 确实在内核态被模拟”的旁证。如果 VMM 自己在用户态模拟 LAPIC 且没有正确处理 Delivery Status，这个计数会开始增长。

### 9.2 一次 IPI 在 KVM 里走多远

物理机上一次 IPI 是几百纳秒：写 ICR，中断通过总线送到目标 LAPIC，目标 CPU 在下一个指令边界响应。虚拟机里这条路要长得多：

```text
源 vCPU (guest)         写 ICR 0x300
     ↓ APIC MMIO 访问被 KVM 接管，不产生用户态 exit
KVM (host 内核)         kvm_lapic_reg_write()
                        kvm_apic_send_ipi()
                        kvm_irq_delivery_to_apic()      ← 遍历目标集合
                        __apic_accept_irq(APIC_DM_FIXED)
                          kvm_lapic_set_irr()           ← 置目标 vCPU 的 IRR
                          kvm_make_request(KVM_REQ_EVENT)
                          kvm_vcpu_kick()               ← 唤醒/踢出目标线程
     ↓
host 调度器             目标 vCPU 线程变成可运行，等待被调度上物理核
     ↓
目标 vCPU (host 内核)   vcpu_enter_guest()
                        inject_pending_event() → 写 VMCB 的 EVENTINJ
     ↓ VMRUN
目标 vCPU (guest)       执行中断处理程序
```

关键的开销不在 KVM 的代码路径（那部分是几百条指令），而在两处：

1. **目标 vCPU 如果正在 guest 里跑**，`kvm_vcpu_kick()` 要给它发一个物理 IPI 把它踢出 guest（`kvm_arch_vcpu_should_kick()` 判断它是否 `IN_GUEST_MODE`），这是一次真实的 VM exit + VM entry，大约 1-2 微秒。
2. **目标 vCPU 如果被 host 抢占了**，`kvm_vcpu_kick()` 只是把线程置为可运行，实际执行要等 host 调度器。这个延迟没有上界，超卖时可以到毫秒级。

第二条正是 6.3 节讲的问题在 IPI 上的体现。它也解释了为什么 `CAL` 计数在启动阶段特别高却不影响体验（启动时没有超卖），而稳态下如果 `RES` 和 `CAL` 持续高企，就值得怀疑 host 侧的调度。

**这整条路径用户态 VMM 完全看不到。** mini-vmm 的 exit 统计里（`n_exits`、`n_exit_io`、`n_exit_mmio`、`n_exit_hlt`）不会因为 IPI 增加任何一个计数，因为 IPI 从来不走到用户态。这是内核态 irqchip 的最大价值：把最高频的虚拟化事件留在内核里。

### 9.3 三种减少 IPI 代价的机制

**IPI shorthand（内核侧）。** guest 日志里有一行：

```text
[    0.755841] IPI shorthand broadcast: enabled
```

它来自 `arch/x86/kernel/apic/ipi.c:25`。含义是：给“除自己外所有 CPU”发 IPI 时，用 ICR 的 destination shorthand 字段（`APIC_DEST_ALLBUT`）一次发出，而不是对每个目标各写一次 ICR。在物理机上这省的是总线事务，在 KVM 下省的是 `kvm_lapic_reg_write()` 的调用次数——N 颗 CPU 的广播从 N-1 次变成 1 次。启用条件是“所有 present 的 CPU 都至少启动过一次”（`apic_smt_update()`，`ipi.c:43`），所以这一行出现在启动后期而不是 `smp_init()` 附近。可以用 `no_ipi_broadcast=1` 关掉做对比。

**x2APIC（架构侧）。** x2APIC 把 LAPIC 的访问从 MMIO 换成 MSR，发 IPI 变成一条 `WRMSR`，而且目标 ID 是 32 位的，支持超过 255 颗 CPU。guest 的 `.config` 里 `CONFIG_X86_X2APIC=y`，CPU 也报告支持（`/proc/cpuinfo` 的 flags 里有 `x2apic`），但日志里是：

```text
[    0.128018] APIC: Switch to symmetric I/O mode setup
[    0.129768] x2apic: IRQ remapping doesn't support X2APIC mode
```

原因在这里：

```c
/* guest v6.6 arch/x86/kernel/apic/apic.c:1869 */
	if (remap_mode != IRQ_REMAP_X2APIC_MODE) {
		u32 apic_limit = 255;

		/*
		 * Using X2APIC without IR is not architecturally supported
		 * on bare metal but may be supported in guests.
		 */
		if (!x86_init.hyper.x2apic_available()) {
			pr_info("x2apic: IRQ remapping doesn't support X2APIC mode\n");
			x2apic_disable();
			return;
		}
		...
	}
```

物理机上开 x2APIC 需要中断重映射单元（IOMMU 的 IR），mini-vmm 没有提供，guest 也没有解析 DMAR 表。注释里写明了“虚拟机里可以不要 IR”，但这条例外要靠 `x86_init.hyper.x2apic_available()` 返回真，而这个钩子的默认实现是 `bool_x86_init_noop`，恒返回 false（`arch/x86/kernel/x86_init.c:113`）；只有 `CONFIG_HYPERVISOR_GUEST` 打开、且 guest 识别出自己跑在 KVM 上时，`kvm_init_platform()` 才会把它换成真正的判断。mini-vmm 的 guest 没开这个配置，所以**即使 VMM 置了 `hypervisor` 位，x2APIC 也起不来**。

这是卷五第 10 节那条结论的又一个下游后果，也说明一件事：**`hypervisor` 位只是一张入场券，它带来的所有实际收益都在 `CONFIG_HYPERVISOR_GUEST` 那一大块代码里**。对于 mini-vmm 现在这个 guest，置位的作用仅限于跳过微码加载和 host 专属的勘误 MSR。

顺带说明，xAPIC 的 8 位 APIC ID 把 mini-vmm 的 vCPU 数上限卡在 255（实际 `VMM_MAX_VCPUS` 是 32，MP 表的空间还能放 40 条，见卷五 5.4 节）。要突破就必须上 x2APIC，而那需要 guest 侧的配合。

**AVIC（硬件侧）。** AMD 的 Advanced Virtual Interrupt Controller 把 LAPIC 的大部分寄存器访问和 IPI 投递做进硬件：源 vCPU 写 ICR 不产生 `#VMEXIT`，硬件直接查 AVIC 的物理 APIC ID 表，把中断写进目标 vCPU 的后备页并向目标所在的物理核发一个 doorbell 中断。目标 vCPU 如果正在运行，整个过程零 exit。

soc63 的 CPU 报告支持它（mini-vmm 的 `SVM features` 行里有 `avic`），但 KVM 5.15 里 AVIC 默认关闭：

```c
/* host v5.15 arch/x86/kvm/svm/svm.c:193 */
static bool avic;
module_param(avic, bool, 0444);
...
/* svm_hardware_setup()，svm.c:1034 */
	enable_apicv = avic = avic && npt_enabled && boot_cpu_has(X86_FEATURE_AVIC);
```

`avic` 没有初值即为 false，soc63 上 `cat /sys/module/kvm_amd/parameters/avic` 读出来也确实是 `N`。启不启用对 VMM 是透明的——AVIC 的所有配置都在 host 的 `kvm_amd` 模块里，用户态既不能开也不能关，只能通过 `modprobe kvm_amd avic=1` 从 host 侧调整。卷四第 9 节对 AVIC 的结构有更详细的介绍。

### 9.4 VMM 能做什么

结论很简短：**在 IPI 这件事上用户态 VMM 唯一能做的就是用内核态 irqchip**。`KVM_CREATE_IRQCHIP` 一旦调了，LAPIC、IOAPIC、PIC 全在内核里，IPI 路径就是最优的。剩下的优化（shorthand、x2APIC、AVIC）分别属于 guest 内核、guest 配置和 host 内核模块，VMM 只能创造条件，不能直接控制。

反过来，如果 VMM 选择用户态 irqchip（`KVM_IRQCHIP_SPLIT` 或完全自己模拟），每一次 IPI 都会变成一次用户态往返，SMP guest 的性能会塌掉一个数量级。这也是 mini-vmm 在 `--mode linux` 下无条件调 `irqchip_create()` 的原因（`src/vm.c:486`）。

## 10. 一致性检查清单

卷五第 9 节给出了固件表与设备模型之间的一致性约束。本节是它在 CPU 侧的对应物：把 SMP 相关的全部约束集中列出，可以当作写 VMM 时的核对表。每一条都标注了违反时的现象，因为这类 bug 的共同特点是**现象离原因很远**。

### 10.1 编号与数量

| 约束 | 三方（或多方）分别在哪 | 违反的现象 |
|---|---|---|
| APIC ID 必须三方相同 | KVM 的 LAPIC（默认 `= vcpu_id`）／MADT 的 `apic_id`（`acpi.c:242`）／CPUID.1:EBX[31:24]（`smp.c:66`） | 固件表与 LAPIC 不一致：`[Firmware Bug] CPUn: APIC id mismatch`。并行启动时 AP 在 `.Lfind_cpunr` 查不到自己，直接 `hlt`，10 秒后 `CPUn failed to report alive state` |
| vCPU 数量必须处处一致 | `KVM_CREATE_VCPU` 的次数／MADT 的 LAPIC 条目数／MP 表的 processor 条目数／CPUID 0x80000008 的 NC | 表里多报：内核为不存在的 CPU 发 IPI 然后超时。表里少报：多出来的 vCPU 线程永远阻塞在 `KVM_RUN`，VM 退不出去 |
| BSP 必须是同一颗 | KVM 的 `bsp_vcpu_id`（默认 0）／MP 表的 `CPU_BOOTPROCESSOR` 标志（`mptable.c:155`）／MADT 的第一条 LAPIC 条目 | BSP 认错：真正的 BSP 是 `RUNNABLE` 的那颗，它会照常执行；被标错的那颗收不到 INIT 就不会动。表现为 `Brought up N-1 CPUs` |
| IOAPIC ID 不能与任何 LAPIC ID 冲突 | mini-vmm 取 `nr_cpus`（`mptable.c:125`、`acpi.c:251`） | APIC ID 空间冲突，中断路由异常。`--smp` 增大时这条尤其容易被忘记——ID 必须跟着挪 |
| vCPU 数不得超过 KVM 上限 | `KVM_CHECK_EXTENSION(KVM_CAP_MAX_VCPUS)` | `KVM_CREATE_VCPU` 返回 `EINVAL`。mini-vmm 在 `vm_create()` 里提前检查并报错（`src/vm.c:442`） |
| vCPU 数不得超过 MP 表容量与 xAPIC 的 8 位 ID | `VMM_MAX_VCPUS` = 32，MP 表按 `MPTABLE_MAX_SIZE` 能放 40 条，xAPIC 上限 255 | 溢出会静默地写坏后面的表 |

### 10.2 内存与设备

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| E820 中 1 MiB 以下必须有可用 RAM | AP 的实模式跳板必须装在那里（3.1 节） | `No sub-1M memory is available for the trampoline`，随后 `panic("Real mode trampoline was not allocated")`。**单 vCPU 也会 panic** |
| 物理地址 `0x467`/`0x469` 必须是可写 RAM | warm reset vector（3.6 节） | 每次唤醒 AP 时写进黑洞；本身不致命，但如果那段地址被映射成 MMIO 会产生莫名的 exit |
| CMOS 索引 `0x0F` 的写必须被接受 | 同上 | RTC 模型如果对未知索引报错，`do_boot_cpu()` 的第一步就失败 |
| 内核态 irqchip 必须在创建 vCPU **之前**建好 | KVM 在 `KVM_CREATE_VCPU` 时才决定挂不挂内核态 LAPIC | 顺序反了：所有 vCPU 都是 `RUNNABLE`，AP 从 `0xfff0` 跑飞，表现为 `KVM_EXIT_SHUTDOWN`；同时 IPI 全部变成用户态 MMIO exit |
| 设备模型必须能承受并发访问 | 并行启动时多个 AP 几乎同时进 guest（4.3 节） | 数据竞争，现象随机。mini-vmm 用 `io_lock` 串行化（`src/vm.c:279`） |

### 10.3 CPUID

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| CPUID.1:EBX[31:24] 必须按 vCPU 改写 | 它是 `initial_apicid`（7.3 节） | 所有 vCPU 自报同一 APIC ID，`phys_proc_id` 全相同，调度域错乱；严重时 `topology_update_package_map()` 的 `BUG_ON` 触发 |
| **除拓扑字段外，所有 vCPU 的 CPUID 必须完全相同** | AP 直接沿用 BSP 探测出的 CR4 与 EFER（3.3 节） | AP 带着为别人算出的 CR4 进长模式；`verify_cpu` 可能失败；特性不一致还会让 `alternatives` 打错补丁 |
| 扩展拓扑叶（0xB/0x1F）要么填完整，要么整体清零 | Linux 用 `EBX == 0` 判断“不提供”（7.3 节） | 填一半会让 `detect_extended_topology()` 算出错误的掩码，比整体不填更糟 |
| 填 0xB 时必须与 0x8000001E / 0x80000008 得出同样的拓扑 | 海光的 `hygon_get_topology()` 先读后者、再用前者覆盖（7.3 节） | 两条路打架，`cpu_core_id` / `phys_proc_id` 随内核版本变化而不同 |
| 追加 CPUID 子叶要带 `KVM_CPUID_FLAG_SIGNIFCANT_INDEX` | 没有这个标志 KVM 查表时不区分 index | 所有子叶都命中第一条，枚举提前结束 |
| 0x80000008:ECX 的 NC 是“核数减 1”，0x8000001E:EBX[15:8] 是“每核线程数减 1” | 多处 AMD 字段都是减 1 编码 | 差一错误。`cpu cores` 少一个或多一个，`Max logical packages` 算错 |
| 拓扑改写要对每个 vCPU 各取一份 CPUID 缓冲区 | 共用缓冲区容易写出覆盖 bug（7.1 节） | 后创建的 vCPU 覆盖先创建的，表现为部分 vCPU 拓扑正确、部分不正确 |
| 注意 guest 可能从 APIC ID 直接反推拓扑 | 海光 model < 5 的 `cpu_llc_id = apicid >> 3`（7.3 节） | vCPU 超过 8 时 LLC 域被切开。**CPUID 填对了也没用**，因为 guest 根本没看 |

### 10.4 运行期

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| `KVM_RUN` 返回 `EAGAIN` 必须当作“重进” | AP 在 `UNINITIALIZED` 状态下被唤醒时返回它（5.2 节） | AP 线程报 `Resource temporarily unavailable` 退出；单 vCPU 时完全正常，一加 `--smp 2` 就坏 |
| `EINTR` / `EAGAIN` 之后不能去读 `exit_reason` | 这两条路径不保证写这个字段 | 上一次的 PIO 被重放一遍，串口输出出现重复字符 |
| 停机信号的 handler 不能带 `SA_RESTART` | 带了 `KVM_RUN` 会自动重启（6.4 节） | 停机请求丢失，VM 挂死。用 `signal()` 而不是 `sigaction()` 是常见诱因 |
| 停机要先置 `immediate_exit` 再发信号 | 覆盖“刚检查完标志还没进 `KVM_RUN`”的窗口（6.4 节） | 偶发挂死，概率随 vCPU 数增加而上升 |
| 不要给不同 vCPU 设不同的 TSC 偏移或频率 | KVM 默认让所有 vCPU 共享同一偏移（8.2 节） | guest 的 TSC 同步检查失败：`Measured N cycles TSC warp between CPUs, turning off TSC clock` |
| `--smp > 1` 只在有 irqchip 的模式下允许 | 没有 LAPIC 就没有 INIT/SIPI | mini-vmm 直接在参数校验阶段报错：`--smp > 1 requires --mode linux` |

## 11. 验证与排障

SMP 问题的共同特点是**沉默**：AP 起不来时 VMM 侧没有任何异常，guest 侧要等 10 秒才出一行日志。所以排障的第一步不是看现象，而是主动去采集状态。

### 11.1 在 host 侧观察

**线程。** 一线程一 vCPU 的模型让 `top -H` 直接可用：

```sh
top -H -p $(pgrep -x vmm)
```

mini-vmm 给每个线程都设了名字（`src/smp.c:140` 的 `pthread_setname_np`），所以看到的是 `vcpu0`…`vcpu3`。三条判断规则：

- 启动早期只有 `vcpu0` 在跑，其余为 0——正常，AP 还没收到 SIPI。
- guest 起来之后所有线程都接近 0——正常，都在 idle 的 `HLT` 里。
- guest 起来之后某个 AP 线程恒为 0 而 guest 里 `nproc` 少了一个——AP 没起来。
- 某个线程 100% 而 guest 空闲——AP 卡在自旋里，多半是跳板锁或 `.Lfind_cpunr` 的死循环（后者是 `hlt`，不占 CPU；前者的 `pause` 自旋会占）。

**`KVM_GET_MP_STATE`。** 这是判断“AP 到底走到哪一步”的决定性证据。但 5.5 节说过，它要抢 `vcpu->mutex`，而 `KVM_RUN` 期间这把锁是被持有的，从主线程直接查会卡住。正确的位置是让 vCPU 线程自己在 run loop 里报告——mini-vmm 就把它放在 `kvm_run()` 返回 `VMM_ERR_INTR` 的那个分支里，只在 debug 级别执行：

```c
/* src/vm.c，vcpu_run_loop() */
        if (r == VMM_ERR_INTR) {
            /* AP 唤醒（EAGAIN）和停机（EINTR）都走这条路，每个 vCPU 整个
             * 生命周期里只会走几次，所以在这里查一次 mp_state 的代价可以
             * 忽略，而它是判断 AP 卡在哪一步的决定性证据 */
            if (vmm_log_level >= 3) {
                uint32_t st;

                if (kvm_get_mp_state(vcpu->fd, &st) == VMM_OK)
                    vmm_dbg("vCPU %d: KVM_RUN interrupted, mp_state=%u (%s)",
                            vcpu->id, st, kvm_mp_state_str(st));
            }
            continue;
        }
```

加 `-v` 跑一次 4 vCPU 的 guest，能直接看到三颗 AP 从 INIT 醒来、以及关机时被踢出 `HLT` 的两批输出：

```text
[DBG ] vm.c:359: vCPU 1: KVM_RUN interrupted, mp_state=2 (INIT_RECEIVED)
[DBG ] vm.c:359: vCPU 2: KVM_RUN interrupted, mp_state=2 (INIT_RECEIVED)
[DBG ] vm.c:359: vCPU 3: KVM_RUN interrupted, mp_state=2 (INIT_RECEIVED)
[    0.490865] smp: Brought up 1 node, 4 CPUs
[DBG ] vm.c:359: vCPU 1: KVM_RUN interrupted, mp_state=3 (HALTED)
[DBG ] vm.c:359: vCPU 2: KVM_RUN interrupted, mp_state=3 (HALTED)
[DBG ] vm.c:359: vCPU 3: KVM_RUN interrupted, mp_state=3 (HALTED)
```

第一批就是 5.2 节那次 `-EAGAIN` 返回：三颗 AP 收到 INIT、状态推到 `INIT_RECEIVED`、`KVM_RUN` 一条 guest 指令都没执行就返回了。第二批是 6.4 节的停机协调把它们从 `HLT` 里踢出来。读到的值这样解读：

| 读到 | 含义 |
|---|---|
| `UNINITIALIZED` 且一直不变 | BSP 根本没发 INIT。检查 MADT 里这颗 CPU 有没有登记、`enabled` 位有没有置 |
| `INIT_RECEIVED` 且一直不变 | 收到了 INIT 但没收到 SIPI。检查 `do_boot_cpu()` 是不是在发 SIPI 之前就失败了（比如 CMOS 写被拒） |
| `RUNNABLE` 但 guest 里 CPU 数不对 | AP 跑起来了但死在跳板或 `.Lfind_cpunr`。看 APIC ID 一致性 |
| `HALTED` | 正常，AP 在 idle |

**host 侧的 KVM 统计。** 需要 root：

```sh
sudo ls /sys/kernel/debug/kvm/*/vcpu*/
sudo cat /sys/kernel/debug/kvm/*/vcpu1/halt_successful_poll
```

`vcpu1` 目录存在但所有计数为 0，说明这颗 vCPU 从未进过 guest。

### 11.2 在 guest 内观察

```sh
# 1. CPU 数与拓扑
nproc
grep -E '^(processor|apicid|core id|physical id|siblings|cpu cores)' /proc/cpuinfo

# 2. 每颗 CPU 的拓扑属性
for c in /sys/devices/system/cpu/cpu[0-9]*; do
    echo "$c pkg=$(cat $c/topology/physical_package_id) core=$(cat $c/topology/core_id)"

# 3. 缓存共享关系
cat /sys/devices/system/cpu/cpu0/cache/index*/shared_cpu_list

# 4. 三类关键告警

# 6. IPI 计数
cat /proc/interrupts
```

第 4 条的四个关键词分别对应四类问题：`apic id` 是三方不一致，`failed to report` 是 AP 没起来，`do_boot_cpu failed` 是 IPI 发送本身失败，`stuck` 是老内核的超时信息。

### 11.3 有用的 guest 命令行开关

| 开关 | 作用 | 用来验证什么 |
|---|---|---|
| `maxcpus=1` | 只启动 BSP，AP 保持在 `possible` 但不上线 | AP 在收到 SIPI 前确实不占 CPU；对比有无 AP 时的行为差异 |
| `nosmp` | 完全关掉 SMP | 把问题二分到“SMP 相关”还是“与 SMP 无关” |
| `possible_cpus=N` | 强制 `possible` 集合大小 | 测试固件表报的数量与内核认知不一致时的行为 |
| `cpu_init_udelay=10000` | 强制 INIT 与 SIPI 之间等 10 ms（`smpboot.c:779`） | 怀疑唤醒时序问题时拉长窗口 |
| `no_ipi_broadcast=1` | 关掉 IPI shorthand（`ipi.c:21`） | 对比广播与逐个发送的开销 |
| `nox2apic` | 强制 xAPIC | 排除 x2APIC 相关问题（mini-vmm 的 guest 本来就没开） |
| `clearcpuid=hypervisor` | 让 guest 看不到 `hypervisor` 位 | A/B 对比这一位的实际影响（卷五第 10 节用过） |
| `initcall_debug` | 打印每个 initcall 的耗时 | 定位卡在哪个初始化步骤 |

注意 `cpu_init_udelay` 的内核注释里写的是 `init_cpu_udelay=`，与 `early_param()` 注册的实际名字 `cpu_init_udelay` 不一致（`arch/x86/kernel/smpboot.c:768` 与 `:779`）。以代码为准。

### 11.4 症状对照

| 症状 | 最可能的原因 | 先查什么 |
|---|---|---|
| VMM 报 `KVM_RUN: Resource temporarily unavailable` 后 AP 线程退出 | 没处理 `EAGAIN`（5.2 节） | `kvm_run()` 包装函数 |
| guest 日志 `CPUn failed to report alive state`，10 秒一颗 | AP 死在跳板或查不到 CPU 号 | APIC ID 三方一致；1 MiB 以下有没有 RAM |
| guest 日志 `[Firmware Bug] CPUn: APIC id mismatch` | MADT/MP 表的 APIC ID 与 KVM 的 LAPIC ID 不符 | `acpi.c` 与 `mptable.c` 里填 ID 的那两行 |
| `panic: Real mode trampoline was not allocated` | E820 里 1 MiB 以下没有可用 RAM | E820 第一项 |
| 所有 vCPU 都跑，但 guest 只认 1 颗 | MADT 只登记了 1 条，或 `nr_vcpus` 没传到固件表 | `MP table @ GPA ...: N CPU(s)` 这行日志里的 N |
| `smp: Brought up 1 node, 1 CPUs` 而 `Allowing 4 CPUs` | 表登记正确但 AP 全部唤醒失败 | 同第 2 行 |
| guest 里四颗 CPU 的 `core id` 全是 0 | CPUID.1:EBX[31:24] 没按 vCPU 改写 | `smp_fixup_cpuid()` |
| `Measured N cycles TSC warp between CPUs` | VMM 给不同 vCPU 设了不同的 TSC | 有没有调 `KVM_SET_MSRS(MSR_IA32_TSC)` 或 `KVM_SET_TSC_KHZ` |
| guest 关机后 VMM 不退出 | 停机协调漏了某个阻塞在 `HLT` 的 AP | `vm_request_stop()` 的 `immediate_exit` 与信号（6.4 节） |
| VMM 退出但终端没恢复 | 与 SMP 无关，是终端 raw 模式没还原 | `console.c` 的 atexit 处理 |
| 串口输出出现重复的字符片段 | `EINTR`/`EAGAIN` 之后错误地分发了旧的 `exit_reason` | `vcpu_run_loop()` |

### 11.5 自动化：`tests/step6.sh`

mini-vmm 把上面这些检查固化成了三条用例。第一条走 panic-reset 路径，覆盖“全部 AP 起来 + 任一 vCPU 触发的停机能让所有线程退出”：

```sh
run_case "$SMP vCPU 启动到 VFS panic 并经 i8042 reset 全部退出" \
    timeout 60 "$VMM" --mode linux --smp "$SMP" --mem "$MEM" \
        --initrd "$INITRD" --append "rdinit=/nonexistent" "$VMLINUX"
expect_rc 0
expect_has "MP table @ GPA 0x9fc00: $SMP CPU(s), IOAPIC id $SMP"
expect_has "$SMP vCPU thread(s) running"
expect_has "smpboot: Allowing $SMP CPUs, 0 hotplug CPUs"
expect_has "smp: Brought up 1 node, $SMP CPUs"
expect_has "guest requested reset via i8042"
# AP 唤醒失败、APIC ID 和固件表对不上、TSC 不同步的典型报错
expect_not "failed to report alive state"
expect_not "do_boot_cpu failed"
expect_not "APIC id mismatch"
expect_not "TSC synchronization"
expect_not "stopped with error"
expect_not "SHUTDOWN"
end_case
```

四条 `expect_has` 是一条链：固件表写对了 → VMM 起了 4 个线程 → guest 认到 4 颗 → 4 颗全部上线。断在哪一环，问题就在哪一层。六条 `expect_not` 覆盖的正是 11.4 表里最常见的几种失败。

**用 `expect_not` 而不是只看退出码，是这类测试的关键。** AP 起不来时 VM 照样能跑完、照样正常退出，退出码是 0；只有日志里那一行 `failed to report alive state` 能暴露问题。`timeout 60` 则兜住“停机协调漏了某颗 AP”这种挂死。

第二条用例进 initramfs 的 shell，把拓扑的每一项都断言一遍：

```sh
CUR_OUT="$(feed_shell \
    'echo NPROC-$(nproc)' \
    'echo APIC-$(sed -n "s/^apicid.*: //p" /proc/cpuinfo | tr "\n" -)' \
    'echo CORE-$(sed -n "s/^core id.*: //p" /proc/cpuinfo | tr "\n" -)' \
    'echo PKG-$(sed -n "s/^physical id.*: //p" /proc/cpuinfo | sort -u | tr "\n" -)' \
    'echo L3-$(cat /sys/devices/system/cpu/cpu0/cache/index3/shared_cpu_list)' \
    'echo L2-$(cat /sys/devices/system/cpu/cpu1/cache/index2/shared_cpu_list)' \
    | timeout 60 "$VMM" --mode linux --smp "$SMP" --mem "$MEM" \
          --initrd "$INITRD" "$VMLINUX" 2>&1)"
...
expect_has "APIC-0-1-2-3-"
expect_has "CORE-0-1-2-3-"
expect_has "PKG-0-"
expect_has "L3-0-3"
expect_has "L2-1"
```

`echo XXX-$(...)` 这种写法是为了和终端回显区分开：guest 的 shell 会把输入的命令原样回显一遍，回显里只有 `$(...)` 字面量，只有真正执行后的输出才带着展开结果，断言不会误匹配。

第三条用例把 vCPU 数拉到 `SMP_MANY`（默认 16）再跑一遍。4 个 vCPU 压不到并行启动的关键路径——所有 AP 同时抢实模式跳板那把锁（3.3 节），vCPU 多一些才有真正的竞争：

```sh
CUR_OUT="$(FEED_WAIT=10 feed_shell \
    'echo NPROC-$(nproc)' \
    'echo PKG-$(sed -n "s/^physical id.*: //p" /proc/cpuinfo | sort -u | tr "\n" -)' \
    'echo L3A-$(cat /sys/devices/system/cpu/cpu0/cache/index3/shared_cpu_list)' \
    "echo L3B-\$(cat /sys/devices/system/cpu/cpu$(( SMP_MANY - 1 ))/cache/index3/shared_cpu_list)" \
    | timeout 120 "$VMM" --mode linux --smp "$SMP_MANY" --mem "$MEM_MANY" \
          --initrd "$INITRD" "$VMLINUX" 2>&1)"
...
expect_has "smp: Brought up 1 node, $SMP_MANY CPUs"
expect_not "failed to report alive state"
expect_not "TSC synchronization"
# LLC 域：VMM 在 CPUID 0x8000001D 里报的是所有 vCPU 共享 L3，但海光
# model < 5 的 guest 内核根本不看这个字段，而是直接
#   per_cpu(cpu_llc_id, cpu) = c->apicid >> 3   (cacheinfo_hygon_init_llc_id)
# 于是按 8 个 APIC ID 一组切开。两种结果都是已知且正确的行为，用
# expect_any 同时接受；VMM 侧对应 smp.c 的 smp_warn_llc_split()。
expect_any "L3A-0-$(( SMP_MANY - 1 ))" "L3A-0-7"
```

最后那条 `expect_any` 是本卷 7.3 节那个发现的固化：它把“LLC 域可能按 APIC ID 被切开”从一次意外变成一条写进测试的已知事实。哪天换了 guest CPU 型号、或者 VMM 改了 APIC ID 的分配方式，这条断言的两个分支都不匹配时会立刻失败，而不是悄悄变成另一种拓扑。

人工验收部分补了三条自动化测不了的：`top -H` 看四个线程是否真的并行、`Ctrl-A x` 能否停下所有 vCPU、`maxcpus=1` 时 AP 线程是否确实不占 CPU。

## 12. 本卷小结与卷七预告

**AP 唤醒。** 规范定义的 INIT-SIPI-SIPI 序列在 KVM 下完整保留，但实现全在内核里：BSP 写 ICR 不产生用户态 exit，AP 的等待与唤醒发生在 `KVM_RUN` 内部。用户态 VMM 在这条链路上只需要做一件事——把 `KVM_RUN` 返回的 `EAGAIN` 当作“重进”而不是错误。前提是内核态 irqchip，而且它必须在创建 vCPU **之前**建好。

**跳板。** SIPI 向量只有 8 位，AP 的入口必须在 1 MiB 以下，这条硬件约束一路传导到 VMM 的 E820：低端必须有可用 RAM，否则连单 vCPU 的 guest 都会 panic。跳板还会顺带写一次 CMOS 索引 `0x0F` 和物理地址 `0x467`，VMM 的 RTC 模型和低端内存都得接得住。

**并行启动。** 6.5 起 Linux 给跳板加了锁，改成“先全部踢醒、再逐个放行”。代价是所有 AP 几乎同时进 guest，对 VMM 的设备模型并发是一次集中考验；收益是 AP 自己从 LAPIC 读 APIC ID、再去 `cpuid_to_apicid[]` 查自己的编号——这让“固件表里的 APIC ID 必须等于 KVM 的 LAPIC ID”从一条建议变成了硬性要求，对不上的 AP 会直接 `hlt` 死在那里。

**`mp_state`。** `UNINITIALIZED` → `INIT_RECEIVED` → `RUNNABLE` 这三态就是架构上的 wait-for-SIPI 的建模。INIT 触发一次完整的 vCPU 复位，SIPI 只改 `CS.base = vector << 12` 和 `RIP = 0`。`KVM_GET_MP_STATE` 是排查 AP 不启动的决定性手段，但要注意它会抢 `vcpu->mutex`。

**vCPU 就是线程。** 这带来两个纯用户态的问题：停机协调（`immediate_exit` + 不带 `SA_RESTART` 的信号，两个窗口都要覆盖）和设备并发（一把大锁最省事）。运行期的性能问题——锁持有者被抢占、IPI 延迟放大——则主要由 host 调度与 PAUSE 拦截决定，VMM 能做的只是选择内核态 irqchip。

**CPUID 拓扑。** 这是本卷唯一必须逐位手写的部分。`KVM_GET_SUPPORTED_CPUID` 的拓扑字段一定是错的，因为它描述的是 host。必须改的五个叶子是 1、0xB/0x1F、0x80000008、0x8000001D、0x8000001E，其中 **CPUID.1:EBX[31:24] 的 initial APIC ID 是唯一一个无论 guest 是什么 CPU 都必须改对的字段**。扩展拓扑叶要么填完整要么整体清零，不能填一半。

**三方一致。** KVM 的 LAPIC ID、固件表的 APIC ID、CPUID 的 initial APIC ID 必须相同。Linux 自己会检查其中两方并打印 `[Firmware Bug] CPUn: APIC id mismatch`，第三方错了则表现为拓扑错乱。第 10 节的清单可以直接当作核对表。

**guest 会从 APIC ID 反推拓扑。** 这是本卷发现的、超出“把字段填对”范畴的一类问题：海光 model < 5 的内核直接用 `cpu_llc_id = apicid >> 3`，完全不看 CPUID 报的缓存共享关系。实测 `--smp 16` 时 LLC 域被切成 `0-7` 和 `8-15` 两块，而 mini-vmm 在 CPUID 里报的是 16 颗共享。各家 CPU 上都有这类写死的捷径，做 CPU 模型时必须逐条排查。

**四条来自本卷核对过程的改进，都已经实现：**

1. `--smp` 大于 8 且 host 型号落在那两个区间时打印一行提示，说明 guest 会把 LLC 域按 APIC ID 的第 3 位切开（7.3 节）。这不是错误，但会让基于 mini-vmm 做调度实验的人少走弯路。实现是 `src/smp.c:144` 的 `smp_warn_llc_split()`，由 `vm_run()` 调用一次。
2. `vcpu_run_loop()` 收到 `VMM_ERR_INTR` 时，以 debug 日志级别打印一次 `KVM_GET_MP_STATE`（11.1 节）。这条路径每个 vCPU 在整个生命周期里只会走几次，开销可以忽略，但对排查 AP 不启动非常有用——加上 `-v` 就能直接看到三颗 AP 停在 `INIT_RECEIVED` 的那一跳。新增 `kvm_get_mp_state()` 与 `kvm_mp_state_str()` 两个封装。
3. `tests/step6.sh` 新增一条 `SMP_MANY`（默认 16）的用例，覆盖并行启动下多个 AP 争跳板锁的路径，并用 `expect_any` 把 LLC 切分的行为固化成已知事实而不是意外（11.5 节）。
4. CPUID 叶 0xB 补齐（7.3 节）。原来的理由是“KVM 只给了子叶 0，追加条目要先扩容数组，留给 Intel 后端一起做”——扩容这件事本身很小：`kvm_get_supported_cpuid()` 多申请 `KVM_CPUID_SPARE` 条但只向 KVM 声明较小的 `nent`，末尾就留出了可追加的空位。补齐之后 AMD/海光 guest 的解析结果与 `0x8000001E` 那条路逐字相同（已在 soc63 与本机用 `--smp 16` 验证），而 Intel guest 将来不必再退回更难填对的 `detect_ht()` 路径。0x1F 仍然整体清零。

**卷七回到设备。** 本卷和卷五让 guest 认识了这台机器并把所有 CPU 跑了起来，但 guest 看到的“设备”一直是被当作黑盒对待的。卷七将逐寄存器追踪 Linux 驱动的探测序列：8250 的 `autoconfig()` 怎样靠一串读写认出 16550A、`quick_pit_calibrate()` 与 `pit_calibrate_tsc()` 各自读了 PIT 的哪几个字节、CMOS RTC 的 UIP 位与 BCD 编码、i8042 的自检与 AUX 判定，以及 `reboot=k` 与 ACPI S5 这两条关机/重启路径在寄存器层面分别做了什么。核心命题是：**设备要模拟到什么程度，由驱动的探测逻辑决定，而不是由芯片手册决定。**
