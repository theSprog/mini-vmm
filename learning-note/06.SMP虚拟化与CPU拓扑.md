# 卷六：SMP 虚拟化——AP 唤醒、vCPU 线程与 CPU 拓扑

> 承接卷五（固件表与 Linux 启动协议），配套 blog《从零入门虚拟化》的《多核·原理篇》《多核·实现篇》。
>
> 卷五结束时，guest 内核已经从 MADT 里读到“这台机器有 4 颗处理器，APIC ID 是 0 到 3”，并且在日志里打印了 `CPU topo: Allowing 4 present CPUs plus 0 hotplug CPUs`。但此时真正在执行指令的只有一颗：BSP。另外三颗停在一个规范定义的等待状态里，要等 BSP 通过 LAPIC 发出一组特定的 IPI 才会开始取指。本卷讲的就是从这组 IPI 到 `smp: Brought up 1 node, 4 CPUs` 之间发生的全部事情。
>
> 这条链路横跨三层，每一层都有自己的状态机：guest 内核的 cpuhp 状态机负责决定什么时候叫醒谁、叫醒之后走哪些初始化步骤；KVM 的 `mp_state` 状态机负责把 INIT 和 SIPI 这两种 IPI 翻译成 vCPU 的架构状态变化；VMM 这一层负责线程、CPUID 与固件表。有意思的地方在于三层的分工极不均衡：AP 唤醒这件在物理机上最讲究时序的事情，到了 VMM 这里一行代码都不用写；反而是 CPUID 拓扑这种看起来只是“报几个数字”的事情，写错一位就会让 guest 的调度器、缓存拓扑和 NUMA 判断全部跑偏。本卷会逐一说明为什么。
>
> 全卷贯穿一条铁律，卷五第 9 节已经提过一次，这里给出它在 CPU 侧的完整形式：**KVM 模拟出来的 LAPIC ID、固件表里登记的 APIC ID、CPUID 指令返回的 initial APIC ID，三者必须相同**。三方中任意两方不一致，内核要么在启动时打印 `[Firmware Bug]`，要么静默地把某颗 CPU 算到错误的 socket 上，要么干脆 AP 起不来而挂在 trampoline 里。
>
> host 侧源码基于 Linux **v6.6**（KVM，行号对应 v6.6.91），即开发机 WSL2 自带的 host 内核。guest 侧源码基于 Linux **v7.4-rc2**（commit `7e1392a42ea2`），即 `tools/build_guest_kernel.sh` 钉住、mini-vmm 实际引导的那个内核；文中 `file:line` 形式的行号都对应这两棵树。文中的实测输出来自 AMD Ryzen 7 5800H（Zen 3，family 0x19）上的 WSL2。规范依据 Intel SDM Vol.3A 第 8 章（Multiple-Processor Management）、AMD64 APM Vol.2 第 16 章（Advanced Programmable Interrupt Controller）与 `Documentation/arch/x86/topology.rst`。

## 1. 从一颗到四颗：问题的全貌

### 1.1 BSP 与 AP

x86 多处理器系统上电时，所有处理器同时收到 RESET 信号，但它们不会一起跑。硬件（早期是外部逻辑，Pentium 4 之后是处理器之间的一次片上仲裁）会在其中选出一颗 **BSP**（bootstrap processor），其余的叫 **AP**（application processor）。区别体现在两处：

- BSP 的 `IA32_APIC_BASE` MSR 第 8 位（BSP flag）为 1，AP 为 0。这是唯一一处架构上可见的、能让一颗 CPU 知道“我是不是 BSP”的标志。
- BSP 从复位向量 `0xFFFFFFF0` 开始取指，正常进入固件；AP 执行完内部的 BIST 之后进入 **wait-for-SIPI** 状态，不取指、不执行，只保留对 INIT、SIPI、NMI 和 SMI 的响应能力。

也就是说，从加电到操作系统把 AP 叫醒之前，AP 一直什么都没做。整个系统从软件视角看是单处理器的：固件是单线程跑完的，bootloader 是单线程的，内核的 `startup_64`、`setup_arch()`、`start_kernel()` 前半段也都是单线程的。第一条在 AP 上执行的指令，出现在 `smp_init()` 之后。

在虚拟机里这套语义由 KVM 完整保留。`KVM_CREATE_VCPU` 创建出来的 vCPU 也分 BSP 与 AP：

```c
/* host v6.6 arch/x86/kvm/x86.c:11884，kvm_arch_vcpu_create() */
if (!irqchip_in_kernel(vcpu->kvm) || kvm_vcpu_is_reset_bsp(vcpu))
    vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
else
    vcpu->arch.mp_state = KVM_MP_STATE_UNINITIALIZED;
```

`kvm_vcpu_is_reset_bsp()` 比较的是 `vcpu_id` 与 `kvm->arch.bsp_vcpu_id`，后者默认为 0，可以用 `KVM_SET_BOOT_CPU_ID` 改（`x86.c:6978`）。mini-vmm 不改，所以 vCPU 0 是 BSP。这一行里还藏着一个容易忽略的分支：**没有内核态 irqchip 时，所有 vCPU 一律是 `RUNNABLE`**。因为 INIT/SIPI 是 LAPIC 的功能，LAPIC 不在内核里，KVM 就没法替你实现 wait-for-SIPI，整套唤醒协议必须由用户态自己模拟。mini-vmm 在 `--mode linux` 下总是先建 irqchip（默认 `KVM_CREATE_IRQCHIP`，`--irqchip split` 时是 `KVM_CAP_SPLIT_IRQCHIP`，两种都把 LAPIC 留在内核）再创建 vCPU（`src/vm.c:778`），顺序不能反——KVM 是在 `KVM_CREATE_VCPU` 的时刻才决定要不要给这个 vCPU 挂一个内核态 LAPIC 的。

### 1.2 三层状态机

| 层 | 状态机 | 状态 | 驱动它前进的事件 |
|---|---|---|---|
| guest 内核 | cpuhp（`kernel/cpu.c`） | `CPUHP_OFFLINE` … `CPUHP_BP_KICK_AP` … `CPUHP_ONLINE`，共 200 余级 | `bringup_nonboot_cpus()` 逐级调用 startup 回调 |
| guest 内核（AP 侧） | `ap_sync_state` | `KICKED` → `ALIVE` → `SHOULD_ONLINE` → `ONLINE` | AP 自己在 `cpuhp_ap_sync_alive()` 里翻牌，BSP 轮询等待 |
| KVM | `vcpu->arch.mp_state` | `UNINITIALIZED` → `INIT_RECEIVED` → `RUNNABLE`（另有 `HALTED`、`AP_RESET_HOLD`） | LAPIC 收到 `APIC_DM_INIT` / `APIC_DM_STARTUP` |
| VMM | 无 | 线程要么在 `KVM_RUN` 里，要么在处理 exit | `pthread_create`、信号、`immediate_exit` |

VMM 这一列是空的，这正是本卷的第一个结论：**AP 唤醒过程中，用户态 VMM 不需要执行任何动作**。BSP 写 ICR 会退出到用户态吗？不会。写 ICR 确实会引起 VM exit，但这个 exit 只到 KVM 为止：guest 处在 x2APIC 模式，写 ICR 是一条 `WRMSR 0x830`，KVM 在 `kvm_x2apic_icr_write()` 里就地处理完（xAPIC 模式下是一次 APIC 页的 MMIO 写，走 `kvm_lapic_reg_write()`，结果一样），连用户态都不会通知。AP 线程此刻正阻塞在自己的 `KVM_RUN` 里，KVM 把它唤醒、改好状态、送进 guest，全程用户态无感。

代价是这件事变得难以观察：如果 AP 没起来，`strace` 上看不到任何异常，日志里也没有痕迹，只有 guest 内核在 10 秒超时之后打印一行 `CPU1 failed to report alive state`（`kernel/cpu.c:444`，`cpuhp_bp_sync_alive()`）。第 11 节会给出可用的观察手段。

## 2. MP 初始化协议：INIT-SIPI-SIPI

### 2.1 规范怎么说

唤醒 AP 的唯一标准手段是 **通用启动算法**（universal start-up algorithm），Intel SDM Vol.3A §9.4.4.1 与 AMD64 APM Vol.2 §16.9 各自给出了一份，内容一致。BSP 依次做三件事：

1. 向目标 AP 发一个 **INIT IPI**。AP 收到后进入初始化状态：寄存器复位成架构定义的初值，然后回到 wait-for-SIPI。
2. 等待 10 ms。
3. 连发两个 **SIPI**（startup IPI，也叫 Start-Up IPI），中间隔 200 µs。SIPI 携带一个 8 位向量 *V*，AP 收到后从物理地址 `V << 12` 开始，以**实模式**执行，`CS.selector = V << 8`、`CS.base = V << 12`、`IP = 0`。

两个问题值得先回答。

**为什么发两次 SIPI？** 规范的说法是：如果第一个 SIPI 成功，AP 已经在跑了，第二个 SIPI 会被它忽略（不在 wait-for-SIPI 状态的 CPU 不响应 SIPI）；如果第一个因为某些早期芯片的时序问题丢了，第二个是补救。这是一条纯历史包袱，但今天的软件仍然照做，因为它无害。

**为什么入口必须在 1 MiB 以下？** SIPI 向量只有 8 位，`V << 12` 的最大值是 `0xFF000`，不到 1 MiB；而且 AP 醒来时在实模式，本来也寻址不到更高的地方。这条约束一路传导到 VMM：**E820 里 1 MiB 以下必须有一段可用 RAM**，否则 guest 内核分配不到 trampoline，`reserve_real_mode()` 里就会 panic。卷五第 4 节讲 E820 时提到的“低端内存必须留 RAM”，根子就在这里。

### 2.2 ICR 的位域

INIT 和 SIPI 都是通过写 LAPIC 的中断命令寄存器（ICR）发出的。xAPIC 模式下 ICR 是两个 32 位 MMIO 寄存器：`0x300`（低半，写它就触发发送）和 `0x310`（高半，只放 8 位目标 APIC ID）。x2APIC 模式下 ICR 合成一个 64 位 MSR `0x830`，一条 `WRMSR` 同时写入目标和命令，目标字段扩成 32 位，占 63:32 位；位 12（Delivery Status）在 x2APIC 里是保留位，所以也没有“等发送完成”这回事。下表按 xAPIC 布局列出，低 32 位两种模式相同。

| 位 | 名称 | INIT 时的值 | SIPI 时的值 |
|---|---|---|---|
| 7:0 | Vector | 0 | 入口地址 >> 12 |
| 10:8 | Delivery Mode | `101b` = INIT | `110b` = Start-Up |
| 11 | Destination Mode | 0（physical） | 0（physical） |
| 12 | Delivery Status | 只读，1 表示上一次还没送出去 | 同左 |
| 14 | Level | assert 时 1，de-assert 时 0 | 1 |
| 15 | Trigger Mode | 1（level） | 0（edge） |
| 19:18 | Destination Shorthand | 00（用 ICR2 里的 ID） | 00 |
| 63:56（ICR2 的 31:24） | Destination Field | 目标 APIC ID | 目标 APIC ID |

Linux 里这些常量定义在 `arch/x86/include/asm/apicdef.h:77-100`：`APIC_DM_INIT` 是 `0x500`，`APIC_DM_STARTUP` 是 `0x600`，`APIC_INT_ASSERT` 是 `0x4000`，`APIC_INT_LEVELTRIG` 是 `0x8000`。

xAPIC 下写 ICR 的顺序是固定的：先写 ICR2（目标），再写 ICR 低半（触发发送），中间关中断防止被抢占后目标被改掉。x2APIC 下一条 `WRMSR` 就是原子的，不需要这层保护。Linux 通过 `apic->icr_write` 在两者之间切换，mini-vmm 的 guest 选中的是 `apic_x2apic_phys`，用的是第二个：

```c
/* guest v7.4-rc2 arch/x86/kernel/apic/apic.c:225（xAPIC） */
void native_apic_icr_write(u32 low, u32 id)
{
    unsigned long flags;

    local_irq_save(flags);
    apic_write(APIC_ICR2, SET_XAPIC_DEST_FIELD(id));
    apic_write(APIC_ICR, low);
    local_irq_restore(flags);
}

/* guest v7.4-rc2 arch/x86/include/asm/apic.h:227（x2APIC） */
static inline void native_x2apic_icr_write(u32 low, u32 id)
{
    wrmsrq(APIC_BASE_MSR + (APIC_ICR >> 4), ((__u64) id) << 32 | low);
}
```

### 2.3 Linux 的实现

`arch/x86/kernel/smpboot.c:845` 的 `send_init_sequence()` 发 INIT 的 assert 与 de-assert 两拍：

```c
/* Assert INIT on the target CPU */
apic_icr_write(APIC_INT_LEVELTRIG | APIC_INT_ASSERT | APIC_DM_INIT, phys_apicid);
safe_apic_wait_icr_idle();

udelay(init_udelay);

/* Deassert INIT on the target CPU */
apic_icr_write(APIC_INT_LEVELTRIG | APIC_DM_INIT, phys_apicid);
safe_apic_wait_icr_idle();
```

de-assert 那一拍是 82489DX 外置 APIC 时代的产物：那时候 INIT 是一根真实的电平信号线，要拉高再拉低。集成 APIC（P54C 之后）对 level-triggered 的 INIT de-assert 不做任何事，但 Linux 仍然照发。KVM 也照收不误：`__apic_accept_irq()` 里 `case APIC_DM_INIT` 的条件是 `if (!trig_mode || level)`，de-assert 那一拍 `trig_mode=1` 而 `level=0`，条件不成立，直接被丢掉（`host v6.6 arch/x86/kvm/lapic.c:1350`）。

`init_udelay` 的值由 `smp_set_init_udelay()`（`smpboot.c:825`）决定：Intel Pentium Pro 及以后、AMD family ≥ 0xF、Hygon family ≥ 0x18 一律取 0，其余取 10000（微秒）。guest 看到的是 host 透传的 family 0x19，所以规范要求的那个 10 ms 延迟实际上是 0。这条路径也可以用 `cpu_init_udelay=` 命令行参数强制（`smpboot.c:817`）。

发 SIPI 的循环在 `wakeup_secondary_cpu_via_init()`（`smpboot.c:871`）：

```c
for (j = 1; j <= num_starts; j++) {
    ...
    apic_icr_write(APIC_DM_STARTUP | (start_eip >> 12), phys_apicid);
    if (init_udelay == 0)
        udelay(10);
    else
        udelay(300);
    send_status = safe_apic_wait_icr_idle();
    ...
}
```

`num_starts` 在集成 APIC 上是 2，于是就有了协议名里的两个 SIPI。注意 `start_eip >> 12` —— 这就是 SIPI 向量的来历。`start_eip` 来自 `real_mode_header->trampoline_start`，也就是下一节要讲的实模式跳板。

### 2.4 KVM 怎么接住这两种 IPI

BSP 写 ICR 会被 KVM 的 LAPIC 模拟截住。x2APIC 模式下 `WRMSR 0x830` 先因 MSR 拦截退出到 KVM，经 `kvm_x2apic_msr_write()` 进入 `kvm_x2apic_icr_write()`；xAPIC 模式下是 APIC 页的 MMIO 写，进 `kvm_lapic_reg_write()` 的 `APIC_ICR` 分支。两条路随后汇合：`kvm_apic_send_ipi()` → `kvm_irq_delivery_to_apic()` → 目标 vCPU 的 `__apic_accept_irq()`：

```c
/* host v6.6 arch/x86/kvm/lapic.c:2446 */
int kvm_x2apic_icr_write(struct kvm_lapic *apic, u64 data)
{
    if (data & X2APIC_ICR_RESERVED_BITS)
        return 1;
    ...
    data &= ~APIC_ICR_BUSY;

    kvm_apic_send_ipi(apic, (u32)data, (u32)(data >> 32));
    ...
}

/* host v6.6 arch/x86/kvm/lapic.c:2310，kvm_lapic_reg_write() */
case APIC_ICR:
    WARN_ON_ONCE(apic_x2apic_mode(apic));

    /* No delay here, so we always clear the pending bit */
    val &= ~APIC_ICR_BUSY;
    kvm_apic_send_ipi(apic, val, kvm_lapic_get_reg(apic, APIC_ICR2));
    kvm_lapic_set_reg(apic, APIC_ICR, val);
    break;
```

两处都把 Delivery Status（BUSY）位清掉，因为 KVM 的“发送”是同步完成的，不存在排队。x86.c 里还有一条更短的路 `handle_fastpath_set_x2apic_icr_irqoff()`（`x86.c:2160`），在 VM exit 之后不开 host 中断就直接处理 ICR 写，但它只接 Fixed、physical、无 shorthand 的普通 IPI，INIT 和 SIPI 不满足条件，仍走上面的常规路径。guest 侧在 x2APIC 下 `apic_x2apic_phys` 根本没有 `safe_wait_icr_idle` 回调，`safe_apic_wait_icr_idle()` 直接返回 0，所以 `/proc/interrupts` 里的 `RTR: APIC ICR read retries` 恒为 0 只说明 guest 没读过 ICR，不能拿来判断 LAPIC 在哪里被模拟。

`kvm_apic_send_ipi()`（`lapic.c:1503`）把 ICR 的两半解成一个 `struct kvm_lapic_irq`，然后按 dest_mode 和 shorthand 找出目标 vCPU 集合。真正的动作在 `__apic_accept_irq()`：

```c
/* host v6.6 arch/x86/kvm/lapic.c:1350 */
case APIC_DM_INIT:
    if (!trig_mode || level) {
        result = 1;
        /* assumes that there are only KVM_APIC_INIT/SIPI */
        apic->pending_events = (1UL << KVM_APIC_INIT);
        kvm_make_request(KVM_REQ_EVENT, vcpu);
        kvm_vcpu_kick(vcpu);
    }
    break;

case APIC_DM_STARTUP:
    result = 1;
    apic->sipi_vector = vector;
    /* make sure sipi_vector is visible for the receiver */
    smp_wmb();
    set_bit(KVM_APIC_SIPI, &apic->pending_events);
    kvm_make_request(KVM_REQ_EVENT, vcpu);
    kvm_vcpu_kick(vcpu);
    break;
```

两件事：在目标 vCPU 的 `pending_events` 位图里置位，然后 `kvm_vcpu_kick()` 把目标线程从阻塞里唤醒。注意 INIT 用的是**赋值**而不是置位——收到 INIT 会把之前挂着的 SIPI 一并抹掉，这符合规范（INIT 让 AP 回到 wait-for-SIPI，之前的 SIPI 自然作废）。

整个过程中 `kvm_vcpu_kick()` 唤醒的是 host 上那个 vCPU 线程，而这个线程正阻塞在 `KVM_RUN` 内部——不是阻塞在用户态。所以从 mini-vmm 的角度，什么都没发生过。

## 3. 实模式跳板：从 16 位到 `secondary_startup_64`

AP 收到 SIPI 后，在实模式下从 `V << 12` 开始执行。而内核本体运行在长模式、开着四级或五级页表、代码在 `0xffffffff8xxxxxxx` 这样的高端虚拟地址上。中间这段落差由一块叫 **real mode trampoline** 的代码填补。它是内核里少数几段仍然用 `.code16` 写的代码之一。

### 3.1 它住在哪

跳板是一段独立编译、链接、然后当作二进制大块（blob）嵌进 vmlinux 的代码，源码在 `arch/x86/realmode/rm/`，链接脚本是 `realmode.lds.S`，最终以 `real_mode_blob` 符号出现在内核镜像里。启动早期它被整块复制到一片 1 MiB 以下的内存上：

```c
/* guest v7.4-rc2 arch/x86/realmode/init.c:47 */
void __init reserve_real_mode(void)
{
    phys_addr_t mem;
    size_t size = real_mode_size_needed();
    ...
    /* Has to be under 1M so we can execute real-mode AP code. */
    mem = memblock_phys_alloc_range(size, PAGE_SIZE, 0, 1<<20);
    if (!mem)
        pr_info("No sub-1M memory is available for the trampoline\n");
    else
        set_real_mode_mem(mem);

    /*
     * Unconditionally reserve the entire fisrt 1M, see comment in
     * setup_arch().
     */
    memblock_reserve(0, SZ_1M);
}
```

调用点在 `setup_arch()` 的 `x86_platform.realmode_reserve()`（`arch/x86/kernel/setup.c:1136`），紧挨在 `init_mem_mapping()` 之前。这段代码解释了卷五第 4 节那条 E820 约束的全部理由：**如果 1 MiB 以下一个 RAM 字节都没有，`memblock_phys_alloc_range()` 返回 0，`real_mode_header` 是 NULL，随后 `init_real_mode()` 里直接 `panic("Real mode trampoline was not allocated")`**。注意这个 panic 发生在 `early_initcall` 阶段，也就是说即使是单 vCPU 的 guest 也躲不过——跳板不只给 AP 用，ACPI S3 唤醒和 `reboot=bios` 也走它。

mini-vmm 的 E820 第一项正是为此存在：

```text
[    0.000000] BIOS-e820: [mem 0x0000000000000000-0x000000000009fbff]  System RAM
[    0.000000] BIOS-e820: [mem 0x000000000009fc00-0x00000000000fffff]  device reserved
[    0.000000] BIOS-e820: [mem 0x0000000000100000-0x000000001fffffff]  System RAM
```

跳板成功时一行日志都不打印，所以它是“沉默的依赖”：只有失败了才知道它存在。反过来说，`No sub-1M memory is available for the trampoline` 这一行如果出现在日志里，问题一定出在 VMM 的 E820 上，而不是内核。最后那句 `memblock_reserve(0, SZ_1M)` 还说明：不管 VMM 把低端 1 MiB 报成什么，内核最终都会把整个第一兆保留下来不给分配器用，理由是“BIOS 经常破坏低端内存，几百 KiB 不值得花力气去精确检测”。

### 3.2 复制与重定位

`setup_real_mode()`（`realmode/init.c:91`）把 blob 复制到目标地址后要做一次重定位。原因很直白：这段代码在实模式下运行，段基址由 `CS` 决定，而 `CS` 的值到运行时才知道；代码里又有 32 位的绝对地址引用（`pa_startup_32` 之类）。编译时不知道装到哪，只能编译后打补丁。

```c
    memcpy(base, real_mode_blob, size);

    phys_base = __pa(base);
    real_mode_seg = phys_base >> 4;

    rel = (u32 *) real_mode_relocs;

    /* 16-bit segment relocations. */
    count = *rel++;
    while (count--) {
        u16 *seg = (u16 *) (base + *rel++);
        *seg = real_mode_seg;
    }

    /* 32-bit linear relocations. */
    count = *rel++;
    while (count--) {
        u32 *ptr = (u32 *) (base + *rel++);
        *ptr += phys_base;
    }
```

重定位表 `real_mode_relocs` 是构建时用 `arch/x86/tools/relocs` 从跳板的 ELF 里抽出来的。这也是跳板源码开头那句警告的由来：“如果你改这个文件，用 `objdump --full-contents --reloc` 检查一下目标文件，确保没有重定位项”——意思是不能引入编译器自己生成的重定位，只能用这套手工机制。

### 3.3 `trampoline_header`：BSP 交给 AP 的五个值

重定位之后，BSP 往跳板尾部一个固定结构里填五个字段，这是两者之间唯一的数据接口：

```c
/* guest v7.4-rc2 arch/x86/include/asm/realmode.h:44（64 位部分） */
struct trampoline_header {
    u64 start;      /* AP 进入长模式后要跳的目标：secondary_startup_64 的虚拟地址 */
    u64 efer;       /* BSP 当前的 EFER，去掉 LMA 位 */
    u32 cr4;        /* mmu_cr4_features，BSP 当前的 CR4 去掉 PCIDE */
    u32 flags;      /* TH_FLAGS_SME_ACTIVE，内存加密用 */
    u32 lock;       /* 实模式栈的自旋锁 */
};
```

填写在 `setup_real_mode()` 的后半段：

```c
    /*
     * Some AMD processors will #GP(0) if EFER.LMA is set in WRMSR
     * so we need to mask it out.
     */
    rdmsrq(MSR_EFER, efer);
    trampoline_header->efer = efer & ~EFER_LMA;

    trampoline_header->start = (u64) secondary_startup_64;
    trampoline_cr4_features = &trampoline_header->cr4;
    *trampoline_cr4_features = mmu_cr4_features;
```

“AP 用 BSP 的 CR4 和 EFER”这件事有实际后果：BSP 在 `setup_arch()` 里探测出来的每一项 CR4 特性（PGE、SMEP、SMAP、PCIDE 之外的都在），AP 醒来时直接照抄，不再自己探测。所以**所有 vCPU 的 CPUID 必须一致**——如果 VMM 给 vCPU 1 报了一个 vCPU 0 没有的特性，或者反过来，AP 会带着一份为别人算出来的 CR4 进长模式。mini-vmm 的 `amd_init_vcpu()` 对每个 vCPU 都调同一份 `KVM_GET_SUPPORTED_CPUID` 的结果，只改拓扑字段，正是为了保证这一点。

`lock` 字段是随并行启动一起加进来的。跳板只有一份，实模式栈也只有一份，并行启动时多个 AP 会同时跑进来，必须串行化：

```asm
/* guest v7.4-rc2 arch/x86/realmode/rm/trampoline_64.S:40 */
.macro LOCK_AND_LOAD_REALMODE_ESP lock_pa=0 lock_rip=0
.Llock_rm\@:
	.if \lock_pa
        lock btsl       $0, pa_tr_lock
	.elseif \lock_rip
        lock btsl       $0, tr_lock(%rip)
	.else
        lock btsl       $0, tr_lock
	.endif
        jnc             2f
        pause
        jmp             .Llock_rm\@
2:
	# Setup stack
	movl	$rm_stack_end, %esp
.endm
```

拿不到锁就 `pause` 自旋。锁在 AP 切到自己的内核栈之后才释放，释放点在 `head_64.S` 的 `.Lsetup_cpu` 之后（见 3.5）。`lock btsl` 是一条带 `lock` 前缀的原子指令，在 KVM 下它对应一次普通的内存访问，不产生 exit——NPT/EPT 之下 guest 的原子指令由硬件直接做，VMM 完全看不到。

### 3.4 跳板代码本身

`trampoline_start`（`trampoline_64.S:61`）按页对齐，因为 SIPI 向量的粒度是 4 KiB。整段代码干的事情可以一行行数清楚：

```asm
SYM_CODE_START(trampoline_start)
	cli			# We should be safe anyway
	wbinvd

	LJMPW_RM(1f)
1:
	mov	%cs, %ax	# Code and data in the same place
	mov	%ax, %ds
	mov	%ax, %es
	mov	%ax, %ss

	LOCK_AND_LOAD_REALMODE_ESP

	call	verify_cpu		# Verify the cpu supports long mode
	testl   %eax, %eax		# Check for return code
	jnz	no_longmode

.Lswitch_to_protected:
	lidtl	tr_idt	# load idt with 0, 0
	lgdtl	tr_gdt	# load gdt with whatever is appropriate

	movw	$__KERNEL_DS, %dx	# Data segment descriptor

	# Enable protected mode
	movl	$(CR0_STATE & ~X86_CR0_PG), %eax
	movl	%eax, %cr0		# into protected mode

	# flush prefetch and jump to startup_32
	ljmpl	$__KERNEL32_CS, $pa_startup_32
```

- `wbinvd` 是给 AP 清缓存用的，规范推荐动作。它在 KVM 下会产生一次 VM exit（SVM 的 `VMEXIT_WBINVD`），由 host 内核就地处理，不到用户态。
- `verify_cpu` 是一段共享的检查程序（`arch/x86/kernel/verify_cpu.S`），确认 CPUID 可用、支持长模式、NX 可开。失败就落到 `no_longmode` 里 `hlt` 死循环——这是 AP 起不来的经典现场之一：BSP 等 10 秒超时，日志里一行 `CPU1 failed to report alive state`，而 AP 其实已经停在这里了。
- `tr_idt` 是一个 limit=0 的 IDT，装它的意思是“此刻任何异常都应该导致三重故障立即停机”，而不是跑飞。在 VMM 里这一点非常友好：AP 出问题会以 `KVM_EXIT_SHUTDOWN` 的形式直接冒到用户态，mini-vmm 的 `vcpu_handle_exit()` 会打印 `vCPU N: SHUTDOWN (usually a triple fault)` 并 dump 寄存器。
- `tr_gdt` 是跳板自带的一份三项 GDT（`__KERNEL32_CS`、`__KERNEL_CS`、`__KERNEL_DS`），因为内核真正的 GDT 在高端虚拟地址上，实模式够不着。

进入 32 位保护模式后的 `startup_32`（`trampoline_64.S:126`）继续：开 `CR4.PAE`（从 `tr_cr4` 取）、把 `pa_trampoline_pgd` 装进 CR3、按 `tr_efer` 写 EFER（于是 `EFER.LME=1`）、开 `CR0.PG` 激活长模式，最后 `ljmpl $__KERNEL_CS, $pa_startup_64` 进 64 位。跳板里的 `startup_64` 只有一条指令：

```asm
SYM_CODE_START(startup_64)
	# Now jump into the kernel using virtual addresses
	jmpq	*tr_start(%rip)
SYM_CODE_END(startup_64)
```

`tr_start` 就是 `trampoline_header.start`，即 `secondary_startup_64` 的虚拟地址。能用虚拟地址跳，是因为 `trampoline_pgd` 里既有低端的恒等映射（`trampoline_pgd[0] = trampoline_pgd_entry.pgd`），又把内核页表 `__PAGE_OFFSET` 以上的全部 PGD 项照抄了一份（`realmode/init.c:172`）。

### 3.5 AP 侧：`secondary_startup_64` 怎么知道自己是几号

这是引入并行启动之后变化最大的一段。BSP 和 AP 共用 `secondary_startup_64`，BSP 从 `startup_64` 走过来，AP 从跳板走过来。两者都要在这里确定“我是哪个逻辑 CPU”，因为下一步就要用 `__per_cpu_offset[cpu]` 找自己的 per-CPU 区。

老办法是 BSP 在发 SIPI 之前把 CPU 号写进全局变量 `smpboot_control`，AP 直接读——但这要求一次只能唤醒一颗。并行启动要同时唤醒所有 AP，就必须让 AP 自己查：

```asm
/* guest v7.4-rc2 arch/x86/kernel/head_64.S:244 */
	movl	smpboot_control(%rip), %ecx
	testl	$STARTUP_READ_APICID, %ecx
	jnz	.Lread_apicid
	/*
	 * No control bit set, single CPU bringup. CPU number is provided
	 * in bit 0-23. This is also the boot CPU case (CPU number 0).
	 */
	andl	$(~STARTUP_PARALLEL_MASK), %ecx
	jmp	.Lsetup_cpu

.Lread_apicid:
	/* Check whether X2APIC mode is already enabled */
	mov	$MSR_IA32_APICBASE, %ecx
	rdmsr
	testl	$X2APIC_ENABLE, %eax
	jnz	.Lread_apicid_msr

	/* BSP 已经切到 x2APIC：MMIO 窗口可能没映射，直接把自己也切过去 */
	cmpl	$0, x2apic_mode(%rip)
	jz	.Lread_apicid_mmio
	orl	$X2APIC_ENABLE, %eax
	wrmsr
	jmp	.Lread_apicid_msr

.Lread_apicid_mmio:
	/* Read the APIC ID from the fix-mapped MMIO space. */
	movq	apic_mmio_base(%rip), %rcx
	addq	$APIC_ID, %rcx
	movl	(%rcx), %eax
	shr	$24, %eax
	jmp	.Llookup_AP

.Lread_apicid_msr:
	mov	$APIC_X2APIC_ID_MSR, %ecx
	rdmsr

.Llookup_AP:
	/* EAX contains the APIC ID of the current CPU */
	xorl	%ecx, %ecx
	leaq	cpuid_to_apicid(%rip), %rbx

.Lfind_cpunr:
	cmpl	(%rbx,%rcx,4), %eax
	jz	.Lsetup_cpu
	inc	%ecx
	cmpl	nr_cpu_ids(%rip), %ecx
	jb	.Lfind_cpunr

	/*  APIC ID not found in the table. Drop the trampoline lock and bail. */
	movq	trampoline_lock(%rip), %rax
	movl	$0, (%rax)

1:	cli
	hlt
	jmp	1b
```

`STARTUP_READ_APICID` 是 `0x80000000`（`arch/x86/include/asm/smp.h:193`），由 `arch_cpuhp_init_parallel_bringup()` 在并行启动可用时置上（`smpboot.c:1209`）。走到 `.Lread_apicid` 的 AP 做三件事：

1. 从 LAPIC 读自己的 APIC ID。xAPIC 模式下读的是 MMIO 的 `0xFEE00020`，取高 8 位；x2APIC 模式下读 MSR `0x802`。刚从 INIT 出来的 AP 的 LAPIC 处在 xAPIC 模式，但 BSP 已经切到 x2APIC 时（`x2apic_mode` 非 0，mini-vmm 的 guest 正是这样），AP 先自己写 `IA32_APIC_BASE` 打开 x2APIC 再读 MSR，因为 MMIO 窗口可能根本没映射，而此刻发生异常是没法处理的。这次 `WRMSR` 会退出到 KVM，由 `kvm_set_apic_base()` 切换 LAPIC 模式，`RDMSR 0x802` 读到的值是 KVM 按 `vcpu_id` 算出的 x2APIC ID。
2. 在 `cpuid_to_apicid[]` 数组里线性查找这个值。这个数组是 BSP 在解析 MADT 时按登记顺序建起来的（`topo_register_apic()`，`arch/x86/kernel/cpu/topology.c:232`，卷五 8.3 节）。
3. 找到就把下标当作自己的 CPU 号，找不到就**放掉跳板锁然后 `hlt` 死循环**。

第 3 步是整卷最值得记住的一条因果链。**guest 从 LAPIC 读到的 APIC ID 由 KVM 的 LAPIC 模拟给出，而 `cpuid_to_apicid[]` 的内容来自 VMM 写的 MADT。这两者只要对不上，AP 就永远查不到自己，直接死在这里。** KVM 里 vCPU 的 LAPIC ID 默认等于 `vcpu_id`（也就是 `KVM_CREATE_VCPU` 的参数），所以 MADT 里第 *i* 条 LAPIC 条目的 `apic_id` 必须写 *i*。mini-vmm 的 `src/boot/acpi.c:511` 正是 `l->apic_id = (uint8_t)i;`，`src/boot/mptable.c:183` 同理。这条约束不能靠“差不多”蒙混：APIC ID 空间是稀疏的，真实硬件上常见 0、2、4、6 这种带洞的编号，而 KVM 不是。

查到 CPU 号之后：

```asm
.Lsetup_cpu:
	/* Get the per cpu offset for the given CPU# which is in ECX */
	movq	__per_cpu_offset(,%rcx,8), %rdx
	...
	movq	current_task(%rdx), %rax
	movq	TASK_threadsp(%rax), %rsp

	/*
	 * Now that this CPU is running on its own stack, drop the realmode
	 * protection. For the boot CPU the pointer is NULL!
	 */
	movq	trampoline_lock(%rip), %rax
	testq	%rax, %rax
	jz	.Lsetup_gdt
	movl	$0, (%rax)
```

AP 用 per-CPU 偏移找到自己的 `current_task`（BSP 在 `common_cpu_up()` 里事先填好的 idle 任务），从任务结构里取出内核栈，切过去，然后才放掉跳板锁——下一个 AP 这时才能进跳板。这段串行区非常短，只有实模式到长模式的几十条指令。

### 3.6 一个会打到 VMM 设备模型上的副作用

`do_boot_cpu()` 在发 IPI 之前还有一段：

```c
/* guest v7.4-rc2 arch/x86/kernel/smpboot.c:1045 */
	if (x86_platform.legacy.warm_reset) {
		pr_debug("Setting warm reset code and vector.\n");
		smpboot_setup_warm_reset_vector(start_ip);
		...
	}
```

`x86_platform.legacy.warm_reset` 在 `x86_early_init_platform_quirks()` 里无条件置 1（`arch/x86/kernel/platform-quirks.c:13`），`hardware_subarch` 为 0 也不例外。于是每唤醒一颗 AP，内核都会执行：

```c
	spin_lock_irqsave(&rtc_lock, flags);
	if (!smpboot_warm_reset_vector_count++) {
		CMOS_WRITE(0xa, 0xf);
		*((volatile unsigned short *)phys_to_virt(TRAMPOLINE_PHYS_HIGH)) = start_eip >> 4;
		*((volatile unsigned short *)phys_to_virt(TRAMPOLINE_PHYS_LOW)) = start_eip & 0xf;
	}
	spin_unlock_irqrestore(&rtc_lock, flags);
```

这是 286 时代的遗迹：那时从保护模式回实模式只能靠复位 CPU，固件在复位后读 CMOS 索引 `0x0F`（shutdown status byte），值为 `0x0A` 表示“跳到 `0040:0067` 存的地址去”。`TRAMPOLINE_PHYS_LOW` 和 `TRAMPOLINE_PHYS_HIGH` 就是物理地址 `0x467` 和 `0x469`（`arch/x86/include/asm/apic.h`）。

对 VMM 的要求有两条，都很低但都必须满足：

- **CMOS 索引 `0x0F` 的写必须被接受。** mini-vmm 的 RTC 模型把除状态寄存器 C、D 之外的所有索引当普通 CMOS 字节存下（`src/devices/rtc.c:93-95`），符合要求。如果 VMM 的 RTC 只实现了时间寄存器而对其他索引报错或崩溃，AP 唤醒的第一步就会翻车——而现象会表现成完全无关的样子。
- **物理地址 `0x467` 必须是可写的 RAM。** 它落在 mini-vmm E820 第一项 `[0x0, 0x9fc00) RAM` 里，没问题。

顺带一提，这段代码里的 `spin_lock_irqsave(&rtc_lock)` 意味着 AP 唤醒和 RTC 驱动会争同一把锁。在 VMM 里 CMOS 访问是 PIO exit，要走出用户态、抢 `io_lock`、再回来，比物理机慢几个数量级，但因为整个启动过程只做一次（`smpboot_warm_reset_vector_count` 从 0 变 1 时才写），影响可以忽略。

## 4. guest 内核这一侧：从 `smp_init()` 到 4 颗 CPU 全部在线

### 4.1 时机

`start_kernel()` 的最后一步是 `arch_call_rest_init()` → `rest_init()`，它创建 init 线程后者调用 `kernel_init_freeable()`，其中有一行 `smp_init()`。在此之前所有初始化都是单线程的；在此之后内核才真正是多处理器的。

```c
/* guest v7.4-rc2 kernel/smp.c:1142 */
void __init smp_init(void)
{
    int num_nodes, num_cpus;

    idle_threads_init();
    cpuhp_threads_init();

    pr_info("Bringing up secondary CPUs ...\n");

    bringup_nonboot_cpus(setup_max_cpus);

    num_nodes = num_online_nodes();
    num_cpus  = num_online_cpus();
    pr_info("Brought up %d node%s, %d CPU%s\n",
        num_nodes, (num_nodes > 1 ? "s" : ""),
        num_cpus,  (num_cpus  > 1 ? "s" : ""));

    /* Any cleanup work */
    smp_cpus_done(setup_max_cpus);
}
```

这段对应 mini-vmm guest 日志里的这几行，它们把整个 SMP 启动过程夹在中间：

```text
[    0.525675] smp: Bringing up secondary CPUs ...
[    0.525963] smpboot: x86: Booting SMP configuration:
[    0.526836] .... node  #0, CPUs:      #1 #2 #3
[    0.537211] smp: Brought up 1 node, 4 CPUs
[    0.538825] smpboot: Total of 4 processors activated (25551.31 BogoMIPS)
```

从 `Bringing up` 到 `Brought up` 一共 12 毫秒左右（`--smp 4`、512M，三次启动分别是 11.5、12.0、13.0 毫秒），三颗 AP 全部上线。注意 `idle_threads_init()` 在前：每颗 AP 必须先有一个 idle 任务（也就是它的 `swapper/N`），AP 醒来后第一件事就是用这个任务的内核栈，第 3.5 节 `.Lsetup_cpu` 里取的就是它。

### 4.2 cpuhp：一个两百级的状态机

Linux 3.x 时代的 CPU 上线是一串 notifier 回调，顺序靠优先级维持，出错难以回滚。4.x 之后改成了显式的状态机：每个子系统在 `enum cpuhp_state`（`include/linux/cpuhotplug.h`）里占一格，每格有一对 `startup`/`teardown` 回调，上线时从低到高逐格调 startup，下线时从高到低逐格调 teardown。

这些状态分三段，段的划分决定了回调**在哪颗 CPU 上执行**：

| 段 | 范围 | 执行者 |
|---|---|---|
| `CPUHP_OFFLINE` … `CPUHP_BRINGUP_CPU` | BP 段 | 控制方 CPU（通常是 BSP） |
| `CPUHP_AP_OFFLINE` … `CPUHP_AP_ONLINE` | AP 段（早期） | 目标 AP 自己，中断关闭 |
| `CPUHP_AP_ONLINE_DYN` … `CPUHP_ONLINE` | AP 段（线程化） | 目标 AP 上的 `cpuhp/N` 内核线程 |

中间那格 `CPUHP_BRINGUP_CPU` 是分水岭：它的 startup 回调就是真正发 INIT-SIPI-SIPI 的地方。在开启 `CONFIG_HOTPLUG_SPLIT_STARTUP` 的内核里（mini-vmm 的 guest 就是），这一格被拆成了两格：

```c
/* guest v7.4-rc2 kernel/cpu.c:2105 附近，cpuhp_hp_states[] */
	[CPUHP_BP_KICK_AP] = {
		.name			= "cpu:kick_ap",
		.startup.single		= cpuhp_kick_ap_alive,
	},
	[CPUHP_BRINGUP_CPU] = {
		.name			= "cpu:bringup",
		.startup.single		= cpuhp_bringup_ap,
		.teardown.single	= finish_cpu,
		.cant_stop		= true,
	},
```

- `cpuhp_kick_ap_alive()` 只负责“踢”：`arch_cpuhp_kick_ap_alive()` → `native_kick_ap()` → `do_boot_cpu()` → 发 IPI，然后立刻返回，不等结果。
- `cpuhp_bringup_ap()` 负责“等”：`cpuhp_bp_sync_alive()` 轮询目标 CPU 的 `ap_sync_state` 变成 `SYNC_STATE_ALIVE`。

拆开的意义就是下一节的并行启动。

### 4.3 并行启动：为什么 4 颗 CPU 只花十几毫秒

传统做法是一颗一颗来：踢一颗、等它跑完实模式跳板和长模式初始化、报到、放行、走完全部 AP 状态到 online，然后才踢下一颗。串行化的理由是跳板只有一份。跳板加了一把锁（3.3 节的 `tr_lock`）之后，这个限制只剩下跳板里那几十条指令，于是可以改成：先把所有 AP 都踢起来，让它们在跳板上排队，然后再逐个放行做后续初始化。

```c
/* guest v7.4-rc2 kernel/cpu.c:1831 */
static bool __init cpuhp_bringup_cpus_parallel(unsigned int ncpus)
{
    const struct cpumask *mask = cpu_present_mask;

    if (__cpuhp_parallel_bringup)
        __cpuhp_parallel_bringup = arch_cpuhp_init_parallel_bringup();
    if (!__cpuhp_parallel_bringup)
        return false;

    if (cpuhp_smt_aware()) {
        ...
    }

    /* Bring the not-yet started CPUs up */
    cpuhp_bringup_mask(mask, ncpus, CPUHP_BP_KICK_AP);
    cpuhp_bringup_mask(mask, ncpus, CPUHP_ONLINE);
    return true;
}
```

两次 `cpuhp_bringup_mask()`：第一次把所有 AP 推进到 `CPUHP_BP_KICK_AP`（也就是全部发完 IPI），第二次再把它们逐个推到 `CPUHP_ONLINE`。

x86 侧的开关是 `arch_cpuhp_init_parallel_bringup()`（`arch/x86/kernel/smpboot.c:1202`），它做的事只有一件——把 `smpboot_control` 设成 `STARTUP_READ_APICID`，告诉 AP“自己去查 CPU 号”，也就是 3.5 节那段汇编走的分支。mini-vmm 的 guest `.config` 里 `CONFIG_HOTPLUG_PARALLEL=y`、`CONFIG_HOTPLUG_SPLIT_STARTUP=y`、`CONFIG_HOTPLUG_CORE_SYNC_FULL=y`，`x86_cpuinit.parallel_bringup` 默认为 `true`（`arch/x86/kernel/x86_init.c:136`），所以走的是并行路径。只有 SEV-ES 之类加密 guest、TDX 这类 AP 不能自己读 APIC ID 的平台会把它关掉。

这对 VMM 有一个实际后果：**三个 AP 的 vCPU 线程会在几乎同一时刻被唤醒，同时进入 guest。** 如果 VMM 的设备模型有并发问题，这是最容易暴露的时刻之一。mini-vmm 用一把 `io_lock` 把所有 PIO/MMIO exit 串行化（`src/vm.c:503`、`src/vm.c:512`），和 QEMU 的 BQL 是同一个思路，所以这里是安全的。

`cpuhp_smt_aware()` 那个分支在 mini-vmm 下不会走：它要求 `smp_num_siblings > 1`，而 mini-vmm 报的拓扑是每核一线程（第 7 节），`smp_num_siblings` 等于 1。

同步点的超时是 10 秒：

```c
/* guest v7.4-rc2 kernel/cpu.c:308 */
static bool cpuhp_wait_for_sync_state(unsigned int cpu, enum cpuhp_sync_state state,
                      enum cpuhp_sync_state next_state)
{
    atomic_t *st = per_cpu_ptr(&cpuhp_state.ap_sync_state, cpu);
    ktime_t now, end, start = ktime_get();
    int sync;

    end = start + 10ULL * NSEC_PER_SEC;
    ...
}
```

超时之后 `cpuhp_bp_sync_alive()`（`kernel/cpu.c:444`）打印 `CPU%u failed to report alive state` 并返回 `-EIO`。**这是 AP 没起来时唯一会出现的日志。** 如果你在 VMM 上看到它，说明 AP 的 vCPU 要么根本没收到 SIPI，要么在跳板或 `.Lfind_cpunr` 里死掉了。第 11 节给出区分这两种情况的方法。

### 4.4 AP 侧：`start_secondary()`

跳板把 AP 送进 `secondary_startup_64`，后者在设置完栈、GDT、段寄存器之后跳到 `initial_code`，也就是 `start_secondary()`（`do_boot_cpu()` 在 `smpboot.c:1026` 设的）。这个函数的注释第一句就是警告：

```c
/* guest v7.4-rc2 arch/x86/kernel/smpboot.c:228 */
static void notrace __noendbr start_secondary(void *unused)
{
	/*
	 * Don't put *anything* except direct CPU state initialization
	 * before cpu_init(), SMP booting is too fragile that we want to
	 * limit the things done here to the most necessary things.
	 */
	cr4_init();
	...
	cpu_init_exception_handling(false);
	load_ucode_ap();

	/*
	 * Synchronization point with the hotplug core. Sets this CPUs
	 * synchronization state to ALIVE and spin-waits for the control CPU to
	 * release this CPU for further bringup.
	 */
	cpuhp_ap_sync_alive();

	cpu_init();
	fpu__init_cpu();
	rcutree_report_cpu_starting(raw_smp_processor_id());
	x86_cpuinit.early_percpu_clock_init();

	ap_starting();

	/* Check TSC synchronization with the control CPU. */
	check_tsc_sync_target();

	ap_calibrate_delay();
	...
	lock_vector_lock();
	set_cpu_online(smp_processor_id(), true);
	lapic_online();
	unlock_vector_lock();
	...
	local_irq_enable();

	x86_cpuinit.setup_percpu_clockev();

	wmb();
	cpu_startup_entry(CPUHP_AP_ONLINE_IDLE);
}
```

按顺序拆开，每一步对 VMM 意味着什么：

| 步骤 | 做什么 | VMM 侧的对应 |
|---|---|---|
| `cr4_init()` | 从 `cr4_init_shadow` 恢复 CR4 | 无 |
| `cpu_init_exception_handling()` | 装 IDT、设置 TSS 与 IST 栈 | 无。此后异常不再是三重故障 |
| `load_ucode_ap()` | 早期微码加载 | 置了 `hypervisor` 位就跳过，见卷五第 10 节 |
| `cpuhp_ap_sync_alive()` | 翻牌 `ALIVE`，自旋等 BSP 放行 | 纯内存自旋，KVM 下不产生 exit |
| `cpu_init()` | 加载 GDT/TSS、初始化 per-CPU | 无 |
| `early_percpu_clock_init()` | guest 是 KVM guest 时为 `kvm_setup_secondary_clock()`（`arch/x86/kernel/kvmclock.c:351`），给这颗 CPU 注册 kvmclock 页 | 一次 `WRMSR MSR_KVM_SYSTEM_TIME_NEW`，KVM 处理，不到用户态 |
| `ap_starting()` → `apic_ap_setup()` | 初始化本 CPU 的 LAPIC（SPIV、LVT、TPR） | x2APIC 下全是 MSR 写，KVM 处理 |
| `ap_starting()` → `identify_secondary_cpu()` | **执行 CPUID，填 `cpu_data(cpu)`** | 第 7 节的全部内容都在这里生效 |
| `ap_starting()` → `set_cpu_sibling_map()` | 按拓扑建 sibling/core/llc 掩码 | CPUID 拓扑填错，这里就错 |
| `check_tsc_sync_target()` | TSC 同步检查 | 第 8 节 |
| `ap_calibrate_delay()` | 校准 `loops_per_jiffy` | BogoMIPS 那一行的来源 |
| `lapic_online()` | 把这颗 CPU 纳入中断向量分配 | 之后它才能收 IPI 和外设中断 |
| `local_irq_enable()` | **开中断** | 从这里开始 AP 会被时钟中断打断 |
| `setup_percpu_clockev()` | 启动 LAPIC timer | `/proc/interrupts` 的 `LOC` 计数从这里开始涨 |
| `cpu_startup_entry()` | 进 idle 循环，不返回 | AP 空闲时执行 `hlt`，见 6.3 节 |

最后那个 `hlt` 值得单独强调：**AP 一旦进入 idle 循环，它的 vCPU 线程绝大部分时间都阻塞在 `KVM_RUN` 里**，因为 KVM 对 guest 的 `HLT` 默认是拦截并在内核里睡眠，而不是返回用户态。mini-vmm 的 `vcpu_handle_exit()` 里 `KVM_EXIT_HLT` 分支写着“HLT, stopping”——那是裸 payload 模式用的语义，Linux guest 走不到这里，因为有了内核态 LAPIC 之后 HLT 由 KVM 自己处理。这个区别在 6.2 节还会再提一次。

## 5. KVM 这一侧：`mp_state` 状态机

### 5.1 五个状态

`KVM_GET_MP_STATE` / `KVM_SET_MP_STATE` 暴露出来的这个枚举（`include/uapi/linux/kvm.h`）是 KVM 对“处理器复位状态”的建模：

| 值 | 名字 | 含义 | x86 上谁会处在这里 |
|---|---|---|---|
| 0 | `KVM_MP_STATE_RUNNABLE` | 可以执行指令 | BSP 一创建就是；AP 收到 SIPI 之后 |
| 1 | `KVM_MP_STATE_UNINITIALIZED` | 从未被初始化，等 INIT | AP 刚创建时 |
| 2 | `KVM_MP_STATE_INIT_RECEIVED` | 收过 INIT，等 SIPI（即架构上的 wait-for-SIPI） | AP 收到 INIT 之后、SIPI 之前 |
| 3 | `KVM_MP_STATE_HALTED` | 执行了 `HLT`，等中断 | idle 中的任何 vCPU |
| 4 | `KVM_MP_STATE_SIPI_RECEIVED` | 历史遗留，x86 上 KVM 内部不再使用 | 只在 `KVM_SET_MP_STATE` 时被接受并折算成 `INIT_RECEIVED` |

正常的 AP 生命周期就是 `UNINITIALIZED` → `INIT_RECEIVED` → `RUNNABLE` → (`HALTED` ⇄ `RUNNABLE`) 这条链。

### 5.2 `KVM_RUN` 在 `UNINITIALIZED` 上的特殊行为

AP 线程创建出来后立刻调 `KVM_RUN`，此时它的 `mp_state` 是 `UNINITIALIZED`。KVM 的处理在 `kvm_arch_vcpu_ioctl_run()` 的最开头：

```c
/* host v6.6 arch/x86/kvm/x86.c:11136 */
	if (unlikely(vcpu->arch.mp_state == KVM_MP_STATE_UNINITIALIZED)) {
		if (kvm_run->immediate_exit) {
			r = -EINTR;
			goto out;
		}
		...
		kvm_vcpu_srcu_read_unlock(vcpu);
		kvm_vcpu_block(vcpu);
		kvm_vcpu_srcu_read_lock(vcpu);

		if (kvm_apic_accept_events(vcpu) < 0) {
			r = 0;
			goto out;
		}
		r = -EAGAIN;
		if (signal_pending(current)) {
			r = -EINTR;
			kvm_run->exit_reason = KVM_EXIT_INTR;
			++vcpu->stat.signal_exits;
		}
		goto out;
	}
```

`kvm_vcpu_block()` 把线程挂起，直到 `kvm_arch_vcpu_runnable()` 为真。BSP 发出的 INIT 在 `__apic_accept_irq()` 里置了 `pending_events` 并调 `kvm_vcpu_kick()`，线程被唤醒，`kvm_apic_accept_events()` 把状态推到 `INIT_RECEIVED`（如果这时 SIPI 也已经挂着，同一次调用里接着推到 `RUNNABLE`），然后——**`KVM_RUN` 返回 `-EAGAIN`，一次 guest 指令都没执行**。

这是 AP 唤醒全过程中唯一会冒到用户态的事件，也是 VMM 唯一必须写的一行代码：`EAGAIN` 不是错误，要当成“重新进 `KVM_RUN`”处理。mini-vmm 的处理在 `src/kvm_wrappers.c:154`：

```c
int kvm_run(int vcpu_fd)
{
    int r;

    /* 两种“没有 exit 可处理、重进 KVM_RUN 即可”的返回：
     *   EINTR   vm_request_stop() 用 immediate_exit + SIGUSR1 把 vCPU
     *           踢出来（Ctrl-A x、另一个 vCPU 触发了停机）
     *   EAGAIN  AP 处于 KVM_MP_STATE_UNINITIALIZED 时 KVM_RUN 阻塞到
     *           收到 INIT/SIPI，醒来后返回 -EAGAIN 而不是进 guest，
     *           见 host arch/x86/kvm/x86.c kvm_arch_vcpu_ioctl_run()
     * 两者都不写（或不保证写）exit_reason，单独返回 VMM_ERR_INTR，
     * 让 run loop 回去检查 should_stop 后重进。 */
    r = ioctl(vcpu_fd, KVM_RUN, 0);
    if (r < 0 && (errno == EINTR || errno == EAGAIN))
        return VMM_ERR_INTR;
    ...
}
```

把 `EAGAIN` 当成致命错误是新手 VMM 最常见的 SMP bug：单 vCPU 时永远遇不到，一加 `--smp 2` 就“AP 线程报错退出”，而错误信息 `Resource temporarily unavailable` 指向的方向完全是误导的。

漏掉 `exit_reason` 的处理同样危险。`-EAGAIN` 和 `immediate_exit` 路径都**不写** `kvm_run->exit_reason`，里面还留着上一次的值。如果 run loop 不加判断就去分发，会把上一次的 PIO 重放一遍。mini-vmm 在 `vcpu_run_loop()` 里对此有专门的注释和 `continue`（`src/vm.c:596-599`）。

### 5.3 第二次 `KVM_RUN`：等 SIPI

第二次进 `KVM_RUN` 时 `mp_state` 已经不是 `UNINITIALIZED`，走的是正常路径 `vcpu_run()`。Linux 7.4 guest 在 AMD 上 INIT 之后几微秒就发 SIPI，AP 线程回到用户态再进来时 SIPI 多半已经处理完，状态直接是 `RUNNABLE`，下面这段等待根本不发生；只有 SIPI 来得晚（例如 guest 命令行加 `cpu_init_udelay=10000`），才会看到 `INIT_RECEIVED` 在这里睡一段：

```c
/* host v6.6 arch/x86/kvm/x86.c:10983，vcpu_run() */
	for (;;) {
		if (kvm_vcpu_running(vcpu)) {
			r = vcpu_enter_guest(vcpu);
		} else {
			r = vcpu_block(kvm, vcpu);
		}
		...
	}
```

`kvm_vcpu_running()` 要求 `mp_state == RUNNABLE`，`INIT_RECEIVED` 不满足，于是进 `vcpu_block()` 继续睡。SIPI 到达后：

```c
/* host v6.6 arch/x86/kvm/x86.c:10909，vcpu_block() 后半段 */
	if (kvm_apic_accept_events(vcpu) < 0)
		return 0;
	switch(vcpu->arch.mp_state) {
	case KVM_MP_STATE_HALTED:
	case KVM_MP_STATE_AP_RESET_HOLD:
		vcpu->arch.pv.pv_unhalted = false;
		vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
		fallthrough;
	case KVM_MP_STATE_RUNNABLE:
		vcpu->arch.apf.halted = false;
		break;
	case KVM_MP_STATE_INIT_RECEIVED:
		break;
	default:
		WARN_ON_ONCE(1);
		break;
	}
	return 1;
```

返回 1 表示循环继续；下一轮 `kvm_vcpu_running()` 为真，直接进 guest。整个第二段等待完全发生在 `KVM_RUN` 内部，用户态连一次返回都看不到。

### 5.4 `kvm_apic_accept_events()`：真正改状态的地方

```c
/* host v6.6 arch/x86/kvm/lapic.c:3310 */
int kvm_apic_accept_events(struct kvm_vcpu *vcpu)
{
	...
	if (!kvm_apic_has_pending_init_or_sipi(vcpu))
		return 0;
	...
	/*
	 * INITs are blocked while CPU is in specific states (SMM, VMX root
	 * mode, SVM with GIF=0), while SIPIs are dropped if the CPU isn't in
	 * wait-for-SIPI (WFS).
	 */
	if (!kvm_apic_init_sipi_allowed(vcpu)) {
		WARN_ON_ONCE(vcpu->arch.mp_state == KVM_MP_STATE_INIT_RECEIVED);
		clear_bit(KVM_APIC_SIPI, &apic->pending_events);
		return 0;
	}

	if (test_and_clear_bit(KVM_APIC_INIT, &apic->pending_events)) {
		kvm_vcpu_reset(vcpu, true);
		if (kvm_vcpu_is_bsp(apic->vcpu))
			vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
		else
			vcpu->arch.mp_state = KVM_MP_STATE_INIT_RECEIVED;
	}
	if (test_and_clear_bit(KVM_APIC_SIPI, &apic->pending_events)) {
		if (vcpu->arch.mp_state == KVM_MP_STATE_INIT_RECEIVED) {
			/* evaluate pending_events before reading the vector */
			smp_rmb();
			sipi_vector = apic->sipi_vector;
			static_call(kvm_x86_vcpu_deliver_sipi_vector)(vcpu, sipi_vector);
			vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
		}
	}
	return 0;
}
```

三个细节：

**INIT 会触发一次完整的 vCPU 复位。** `kvm_vcpu_reset(vcpu, true)` 把通用寄存器清零、`RIP` 置 `0xfff0`、`RFLAGS` 置 `X86_EFLAGS_FIXED`（即只有第 1 位）、`CR0` 只留 `ET`（加上从复位前继承的 `CD`/`NW`）、`CR4` 和 `EFER` 清零、`CR3` 清零，并按 SDM 的要求把 `EDX` 设成 CPUID.1:EAX 的值（家族/型号/步进）。这是架构规定的 INIT 语义，KVM 一丝不苟地实现了，连 Intel 与 AMD 手册对 `CD`/`NW` 描述不一致这种细节都在注释里写明了（`x86.c:12149`）。

**BSP 收到 INIT 不进 wait-for-SIPI。** 这符合规范：BSP 上的 INIT 等同于一次不经固件的软复位，它直接变回 `RUNNABLE` 从 `0xfff0` 重新开始。Linux 的 `reboot=triple` 之类路径依赖这一点。

**SIPI 的落地只有四行。**

```c
/* host v6.6 arch/x86/kvm/x86.c:12190 */
void kvm_vcpu_deliver_sipi_vector(struct kvm_vcpu *vcpu, u8 vector)
{
	struct kvm_segment cs;

	kvm_get_segment(vcpu, &cs, VCPU_SREG_CS);
	cs.selector = vector << 8;
	cs.base = vector << 12;
	kvm_set_segment(vcpu, &cs, VCPU_SREG_CS);
	kvm_rip_write(vcpu, 0);
}
```

`CS.base = vector << 12`，`RIP = 0`，于是下一条指令的物理地址正是 `vector << 12`。这里没有任何“进实模式”的动作——因为 INIT 复位已经把 `CR0.PE` 清掉了，vCPU 本来就在实模式。SVM 后端只是包了一层给 SEV-ES 用（`arch/x86/kvm/svm/svm.c:4932`）。

### 5.5 什么时候 VMM 才需要自己动手

前面说“VMM 什么都不用做”有一个前提：**内核态 irqchip**。把这个前提拿掉，结论完全反过来：

- 没有内核态 LAPIC，`KVM_CREATE_VCPU` 就把所有 vCPU 设成 `RUNNABLE`（`x86.c:11884`）。AP 线程一进 `KVM_RUN` 就会从 `RIP=0xfff0` 开始执行，而那里是空的。
- BSP 写 ICR 会变成一次 MMIO exit 打到用户态，VMM 必须自己解码 delivery mode，自己用 `KVM_SET_MP_STATE(KVM_MP_STATE_INIT_RECEIVED)` 和 `KVM_SET_SREGS` 模拟 INIT 与 SIPI 的语义。

这也是 `KVM_SET_MP_STATE` 这个**写**方向的 ioctl 存在的主要理由之一。另一个理由是虚拟机的保存/恢复与复位：QEMU 在 `kvm_arch_put_registers()` 里会写回 `mp_state`，否则从快照恢复出来的 AP 会带着错误的状态开跑。mini-vmm 这两件事都不做，所以从来不写 `mp_state`。

读的方向则相反：`KVM_GET_MP_STATE` 是排查 AP 不启动最直接的手段，mini-vmm 把它做成了 debug 级别的诊断（`src/kvm_wrappers.c` 的 `kvm_get_mp_state()`，调用点在 `vcpu_run_loop()`，见 11.1 节）。

需要注意的不是权限而是锁：几乎所有 vCPU ioctl 都在 `mutex_lock_killable(&vcpu->mutex)` 之后执行（`host v6.6 virt/kvm/kvm_main.c:4139`），而这把锁在整个 `KVM_RUN` 期间都被持有。所以从主线程去 `KVM_GET_MP_STATE` 一个正阻塞在 `KVM_RUN` 里的 AP，调用方会一直卡住，直到那个 vCPU 因为别的原因退出 `KVM_RUN`——而 AP 卡死的场景里它恰好永远不会退出。可行的做法只有两条：让每个 vCPU 线程在自己的 run loop 里报告状态（mini-vmm 选的这条），或者先用 `immediate_exit` + 信号把目标踢出来再查。

### 5.6 整条链路的时序

把三层合起来，一次 AP 唤醒的完整时序是这样的（横向是时间）：

## 6. vCPU 就是一个线程

### 6.1 模型

KVM 的 vCPU 是一个 fd，`KVM_RUN` 是一次阻塞的 ioctl，它在返回之前一直在执行 guest 代码。谁来调这个 ioctl，谁就是这颗 vCPU。所以 VMM 的 CPU 模型完全由它自己决定：

- **一线程一 vCPU**（QEMU、crosvm、Firecracker、mini-vmm 都是这个模型）。最自然，host 调度器直接看到 N 个可运行实体，SMP guest 的并行度是真实的。
- **一线程多 vCPU 轮转**。理论上可行（每个 vCPU fd 轮流 `KVM_RUN`，靠 `immediate_exit` 打断），但 guest 里任何自旋等待都会立刻死锁——vCPU 0 拿着锁自旋等 vCPU 1，而 vCPU 1 要等 vCPU 0 让出线程。没有实用价值。
- **同一个 vCPU 由不同线程先后运行**。KVM 允许，`kvm_vcpu_ioctl()` 里有一段专门处理 `vcpu->pid` 变化（`virt/kvm/kvm_main.c:4143-4152`），但 `vcpu->mutex` 保证同一时刻只有一个线程在里面。迁移线程有额外代价（`kvm_arch_vcpu_run_pid_change()`），没有理由这么做。

mini-vmm 的实现只有几十行：

```c
/* src/smp.c:366 */
int vm_run(struct vmm_vm *vm)
{
    struct sigaction sa;
    sigset_t kick;
    int i, started = 0, err, r = VMM_OK;

    /* 不带 SA_RESTART，保证 KVM_RUN 返回 EINTR */
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = kick_handler;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGUSR1, &sa, NULL) < 0) {
        vmm_err("sigaction(SIGUSR1) failed");
        return VMM_ERR_SYS;
    }
    /* 信号掩码从父进程继承，启动器可能阻塞了 SIGUSR1；vCPU 线程继承本线程
     * 的掩码，所以在创建它们之前解除阻塞 */
    sigemptyset(&kick);
    sigaddset(&kick, SIGUSR1);
    err = pthread_sigmask(SIG_UNBLOCK, &kick, NULL);
    ...

    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        if (pthread_create(&v->thread, NULL, vcpu_thread, v) != 0) {
            ...
        }
        __atomic_store_n(&v->thread_started, true, __ATOMIC_RELEASE);
        started++;
    }
    vmm_info("%d vCPU thread(s) running", started);

    for (i = 0; i < started; i++) {
        ...
        pthread_join(v->thread, NULL);
        ...
    }
    return r;
}
```

注意所有 vCPU 线程是**一次全部创建**的，包括 AP。AP 线程一起跑就一头扎进 `KVM_RUN`，然后阻塞在 KVM 内部等 INIT，一直等到 guest 内核跑到 `smp_init()`——在 mini-vmm 的日志时间轴上大约是 0.7 秒之后。这期间三个线程完全不消耗 CPU（`kvm_vcpu_block()` 用的是 `TASK_INTERRUPTIBLE` 的等待队列），`top` 里看到的 mini-vmm 只有一个线程在跑。

### 6.2 `KVM_RUN` 什么时候返回

理解 SMP VMM 的性能特征，关键是知道哪些事件会让 `KVM_RUN` 返回用户态，哪些不会。

| guest 行为 | 是否返回用户态 | 处理者 |
|---|---|---|
| PIO / MMIO 打到未被 KVM 接管的地址 | **是**，`KVM_EXIT_IO` / `KVM_EXIT_MMIO` | VMM 的设备模型 |
| 访问 LAPIC / IOAPIC / PIC / PIT 寄存器 | 否 | KVM 内核态 irqchip |
| 写 ICR 发 IPI（包括 INIT/SIPI） | 否 | 同上 |
| `HLT` | **取决于有没有内核态 LAPIC** | 有则 KVM 内部睡眠；无则 `KVM_EXIT_HLT` |
| `PAUSE`（自旋锁里） | 视 PLE 配置，多数情况下否 | KVM 的 `kvm_vcpu_on_spin()` |
| `CPUID`、`RDMSR`/`WRMSR` | 否（除非是 KVM 不认识的 MSR 且开了 filter） | KVM |
| 缺页（NPT/EPT violation） | 否 | KVM 的 MMU |
| 收到 `SIGUSR1` 等未屏蔽信号 | **是**，`-EINTR` | VMM |
| `kvm_run->immediate_exit == 1` | **是**，`-EINTR`，且不执行任何 guest 指令 | VMM |

`HLT` 那一行值得展开。mini-vmm 的 `vcpu_handle_exit()` 里有：

```c
    case KVM_EXIT_HLT:
        vmm_info("vCPU %d: HLT, stopping", vcpu->id);
        return VMM_ERR_EXIT;
```

这是裸 payload 模式的语义：payload 执行完就 `hlt`，VMM 把它当作“跑完了”。但在 `--mode linux` 下这条分支永远走不到，因为 LAPIC 在内核里（默认和 split 两种 irqchip 都是），guest 的 `HLT` 由 KVM 自己处理——`kvm_emulate_halt()` → `__kvm_vcpu_halt()` 把 `mp_state` 设成 `HALTED` 然后阻塞，直到有中断可以注入。这是对的：Linux 的 idle 循环每秒执行几百次 `hlt`，每次都返回用户态的话开销无法接受。

这也解释了一个容易困惑的现象：mini-vmm 的 guest 关机时，四个 vCPU 里只有一个会退出到用户态（执行 ACPI S5 写、即写 PM1a_CNT 端口 `0x604` 的那颗，是一次 `KVM_EXIT_IO`），其余三颗都还阻塞在 `HALTED` 里。让它们停下来是 6.4 节的事。

### 6.3 超卖与锁持有者被抢占

一线程一 vCPU 的直接后果是：**vCPU 的“物理 CPU 时间”由 host 调度器决定，guest 对此一无所知。** 如果 host 上跑着比物理核更多的 vCPU（超卖），或者 host 上有别的负载，一颗 vCPU 可能在任意一条指令之间被抢占几毫秒。

这在单核 guest 上只是变慢，在 SMP guest 上会引发结构性问题：

- **锁持有者被抢占**（lock holder preemption）。vCPU 0 拿着一把自旋锁，然后被 host 抢占。vCPU 1、2、3 在 guest 里自旋等这把锁，它们每一个都在真实地烧物理 CPU 时间，而且正是这些时间让 vCPU 0 更难被调度回来。
- **锁等待者被抢占**（lock waiter preemption）。排队自旋锁（queued spinlock）是有序的，队头的 vCPU 被抢占，后面所有人都得等。
- **IPI 延迟放大**。BSP 给一颗被抢占的 vCPU 发 IPI，`kvm_vcpu_kick()` 只是把它的线程置为可运行，真正执行要等 host 调度。物理机上 IPI 延迟是微秒级，超卖的虚拟机上可以是毫秒级。

业界对此有三套缓解手段，正好对应三个层次：

**硬件层：PAUSE 拦截。** guest 自旋锁里的 `PAUSE` 指令可以被拦截。AMD 叫 pause filter，Intel 叫 PLE（pause-loop exiting）。逻辑是“连续执行了 N 条 PAUSE 而没有别的进展，说明可能在自旋等一个被抢占的持有者”，于是产生一次 VM exit：

```c
/* host v6.6 arch/x86/kvm/svm/svm.c:3258 */
static int pause_interception(struct kvm_vcpu *vcpu)
{
	bool in_kernel;
	...
	if (!kvm_pause_in_guest(vcpu->kvm))
		grow_ple_window(vcpu);

	kvm_vcpu_on_spin(vcpu, in_kernel);
	return kvm_skip_emulated_instruction(vcpu);
}
```

`kvm_vcpu_on_spin()` 做的是**定向让步**（directed yield）：在同一个 VM 的其它 vCPU 里挑一个“看起来正需要 CPU”的，把自己的时间片让给它，赌的就是那个被挑中的正是锁持有者。SVM 的默认参数是 `pause_filter_count = 3000`、`pause_filter_thresh = 128`（`arch/x86/kvm/x86.h:52-58` 的 `KVM_SVM_DEFAULT_PLE_WINDOW` 与 `KVM_DEFAULT_PLE_GAP`，`svm.c:177-180` 引用），并且窗口会按 `grow_ple_window()` / `shrink_ple_window()` 动态调整。mini-vmm 启动时打印的 `SVM features` 行里有 `pausefilter`，开发机（WSL2 嵌套在 Hyper-V 上）的 L1 KVM 也拿得到这个特性。整件事完全在 host 内核里完成，用户态 VMM 既不用配置也看不到。

**半虚拟化层：PV spinlock 与 PV EOI。** guest 知道自己在虚拟机里的话，可以把“自旋等锁”换成“告诉 hypervisor 我要睡了，锁释放时叫我”（`KVM_HC_KICK_CPU` 超调用），把纯浪费的自旋变成一次让出。这需要 guest 侧 `CONFIG_PARAVIRT_SPINLOCKS`。mini-vmm 的 guest 配置开了 `CONFIG_KVM_GUEST` 但没开它，所以锁仍是原生的 `qspinlock`；开着的 PV 特性在启动日志里各留一行：

```text
kvm-guest: APIC: eoi() replaced with kvm_guest_apic_eoi_write()
kvm-guest: KVM setup pv remote TLB flush
kvm-guest: setup PV sched yield
kvm-guest: APIC: send_IPI_mask() replaced with kvm_send_ipi_mask()
kvm-guest: APIC: send_IPI_mask_allbutself() replaced with kvm_send_ipi_mask_allbutself()
kvm-guest: setup PV IPIs
```

PV TLB flush 和 PV sched yield 正是冲着抢占问题来的：前者让发起 TLB shootdown 的 vCPU 不必等一颗被抢占的 vCPU 回应 IPI，只在它的 steal-time 页里记一笔“下次进 guest 前刷 TLB”；后者让等 IPI 回应的 vCPU 发现目标被抢占时用 `KVM_HC_SCHED_YIELD` 把时间片让给它。它们依赖 KVM 在 CPUID `0x40000001` 里报告的 `KVM_FEATURE_*` 位，mini-vmm 把 `KVM_GET_SUPPORTED_CPUID` 的 KVM 叶原样交给 guest，所以这些特性都在。这是卷五第 10 节讨论 `hypervisor` 位时那条“开了 `CONFIG_KVM_GUEST` 的内核才会继续查 0x40000000 叶”的下游后果之一。

**部署层：不超卖。** 最简单也最有效。mini-vmm 是教学/实验 VMM，`--smp` 的值远小于开发机的 16 个逻辑 CPU，上面这些问题不会明显出现。但它们是真实生产环境里 SMP 虚拟化最主要的性能来源，值得知道其存在。

### 6.4 停机：信号与 `immediate_exit`

多 vCPU 带来的第二个用户态问题是：**怎么让所有 vCPU 线程停下来。**

单 vCPU 时不需要考虑——vCPU 自己走到 `KVM_EXIT_SYSTEM_EVENT` 就结束了。多 vCPU 时，触发关机的只有一颗，其余几颗可能在 `HLT` 里睡着，可能在跑 guest 代码，也可能刚检查完退出标志正要进 `KVM_RUN`。

最朴素的做法是设一个标志再发信号：

```c
v->should_stop = true;
pthread_kill(v->thread, SIGUSR1);
```

`KVM_RUN` 收到未屏蔽的信号会返回 `-EINTR`，run loop 看到 `should_stop` 就退出。但这有一个窗口：目标线程刚读完 `should_stop`（还是 false），还没进 `KVM_RUN`，此刻信号到达，被 handler 吃掉，什么也没发生；随后它进入 `KVM_RUN`，在 guest 的 `HLT` 里无限期睡下去，因为再也不会有人给它发信号了。

`kvm_run->immediate_exit`（`KVM_CAP_IMMEDIATE_EXIT`，4.11 引入）正是为这个窗口设计的。它是 `kvm_run` 共享页里的一个字段，`KVM_RUN` 在入口处检查它，为 1 就直接返回 `-EINTR`，一条 guest 指令都不执行（`host v6.6 arch/x86/kvm/x86.c:11215`；`UNINITIALIZED` 的 AP 在 `x86.c:11137` 另有一处同样的检查）。

mini-vmm 把“踢出 `KVM_RUN`”做成一个通用函数，停机、gdb 暂停、往 vCPU 投递工作都用它：

```c
/* src/smp.c:273 */
void vcpu_kick(struct vmm_vcpu *v)
{
    if (v->run)
        __atomic_store_n(&v->run->immediate_exit, 1, __ATOMIC_SEQ_CST);
    if (__atomic_load_n(&v->thread_started, __ATOMIC_ACQUIRE) &&
        !pthread_equal(v->thread, pthread_self()))
        pthread_kill(v->thread, SIGUSR1);
}

/* src/smp.c:285 */
void vm_request_stop(struct vmm_vm *vm)
{
    ...
    vm->running = false;
    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        __atomic_store_n(&v->should_stop, true, __ATOMIC_SEQ_CST);
        vcpu_kick(v);
    }
    ...
}
```

**先写“要做的事”（`should_stop`），再置 `immediate_exit`，再发信号**，两个窗口就都被覆盖了：已经在 `KVM_RUN` 里的被信号踢出来，还没进去的被 `immediate_exit` 挡在门口。`__ATOMIC_SEQ_CST` 保证这个顺序不被编译器或 CPU 重排。

这里有三处容易写错的地方：

这里有四处容易写错的地方：

1. **信号处理函数不能带 `SA_RESTART`。** 带了的话 `KVM_RUN` 会被自动重启，`-EINTR` 根本传不到用户态。mini-vmm 用 `sigaction` 且 `sa.sa_flags` 为 0（`src/smp.c:376`）。用 `signal()` 而不是 `sigaction()` 是典型的坑，glibc 的 `signal()` 默认带 `SA_RESTART`。
2. **信号不能被阻塞。** 信号掩码会从父进程继承，被阻塞的 `SIGUSR1` 只挂在 pending 里，不会让 `HLT` 中的 vCPU 离开 `KVM_RUN`。所以 `vm_run()` 在创建 vCPU 线程之前先 `pthread_sigmask(SIG_UNBLOCK)`。
3. **`immediate_exit` 置位后要按时清。** 只为停机置位时不用清，之后不会再进 guest；mini-vmm 把它用作通用的“踢出”手段，所以 vCPU 线程在 `-EINTR` 之后、检查要做的事之前清零（`src/vm.c:603-605`），停机期间则保持为 1，正在退出的线程不能再睡进 `KVM_RUN`。顺序反过来（先检查再清）会丢事：调用方在两步之间写好事并置位，vCPU 随后把置位清掉、又看不到事，就睡回去了。
4. **`pthread_kill` 不能发给自己。** 触发停机的那颗 vCPU 正在 `vm_request_stop()` 里，给自己发信号没有意义还可能干扰后续逻辑，所以有 `!pthread_equal(v->thread, pthread_self())` 这个判断。

还有一个更彻底的方案：`KVM_SET_SIGNAL_MASK`。它让 KVM 在进 guest 之前替换线程的信号掩码、出来之后恢复（`kvm_sigset_activate()` / `kvm_sigset_deactivate()`，`x86.c:11131` 与 `11233`），从而彻底消除“信号在检查与进入之间丢失”的竞态。QEMU 用的是这条路。`immediate_exit` 更简单，对 mini-vmm 够用。

### 6.5 设备模型的并发

多个 vCPU 线程会同时陷出到用户态访问设备。mini-vmm 的选择是一把大锁：

```c
/* src/vm.c:499 */
    case KVM_EXIT_IO: {
        int r;

        pthread_mutex_lock(&vcpu->vm->io_lock);
        r = handle_io(vcpu);
        pthread_mutex_unlock(&vcpu->vm->io_lock);
        return r;
    }
```

和 QEMU 的 BQL（big QEMU lock）是同一个思路：设备模型本身完全不做并发保护，由分发路径统一串行化。代价是设备访问不能并行，收益是所有设备实现（8250、i8042、RTC、ACPI PM1、PCI 设备）都可以当单线程代码写。I/O 线程（事件循环）上的设备代码同样先拿 `io_lock`。对于一个 exit 频率以千次每秒计的教学 VMM，这个取舍是明显划算的。

需要强调的是**设备表本身是只读的**：所有 `vmm_register_pio()` / `vmm_register_mmio()` 都在 guest 启动之前完成，之后只查不改，所以查表不需要加锁（加锁的只是设备回调）。如果将来要支持热插拔，这个假设就不成立了。

附带一条排查经验：多 vCPU 下如果串口输出出现交错，先判断交错发生在**行边界还是字符边界**。行边界的交错是 guest 行为，多核 `printk` 本来就允许不同 CPU 的整行穿插；字符边界的交错才说明 VMM 这一侧的串行化漏了，也就是某条设备访问路径绕过了 `io_lock`。

## 7. CPUID 拓扑：VMM 唯一真正必须写对的地方

前面六节的结论是“AP 唤醒不用 VMM 操心”。本节是它的反面：CPUID 拓扑字段必须由 VMM 逐位改写，而且 `KVM_GET_SUPPORTED_CPUID` 给出的默认值**一定是错的**。

### 7.1 问题出在哪

`KVM_GET_SUPPORTED_CPUID` 是一个 VM 级（其实是 `/dev/kvm` 级）的 ioctl，它返回“这台 host 的 CPU 能支持、且 KVM 愿意暴露的 CPUID 内容”。对于特性位，这个语义是对的；对于拓扑字段，它是有害的，因为：

- **CPUID.1:EBX[31:24] 是 initial APIC ID。** KVM 填的是执行这条 ioctl 的那颗物理 CPU 的值。把它原样 `KVM_SET_CPUID2` 给所有 vCPU，所有 vCPU 会自报同一个 APIC ID。
- **核数、线程数、缓存共享关系描述的是 host 的物理拓扑**，而 guest 看到的是 VMM 决定的虚拟拓扑，两者毫无关系。

这台 host（AMD Ryzen 7 5800H，16 个逻辑处理器）上 `KVM_GET_SUPPORTED_CPUID` 给出的拓扑相关叶子是这样的：

```text
leaf 00000000 idx 0 flags 0 : eax=0000000d ...
leaf 00000001 idx 0 flags 0 : eax=00a50f00 ebx=0f100800 ecx=76f83203 edx=078bfbff
leaf 0000000b idx 0 flags 1 : eax=00000000 ebx=00000000 ecx=00000000 edx=0000000f
leaf 80000000 idx 0 flags 0 : eax=80000021 ...
leaf 80000008 idx 0 flags 0 : eax=00003030 ebx=1302d005 ecx=0000400f edx=00000000
leaf 8000001d idx 3 flags 1 : eax=0003c163 ebx=03c0003f ecx=00003fff edx=00000001
leaf 8000001e idx 0 flags 0 : eax=00000000 ebx=00000000 ecx=00000000 edx=00000000
```

CPUID.1:EBX 的高 16 位 `0x0f10` 是“APIC ID 0x0f、package 内 16 个逻辑处理器”，0xB 子叶 0 只有 EDX 里的 host x2APIC ID，`0x80000008` 的 ECX `0x400f` 是“16 个线程、APIC ID 核号占 4 位”，`0x8000001D` 的 L3 共享数是 16，`0x8000001E` 全零。没有一项和 `--smp 4` 的 guest 对得上。

后果是功能性的。Linux 7.4 的拓扑解析（`arch/x86/kernel/cpu/topology_common.c`）把两类信息分开取：APIC ID 本身在 AP 上线后从 LAPIC 读（`read_apic_id()`），而“APIC ID 的哪几位是线程号、哪几位是核号、往上是 package”这些**位移**全部来自 CPUID。`topo_set_ids()` 用这些位移把 APIC ID 切成 `pkg_id`、`core_id`，`set_cpu_sibling_map()` 再据此建 `cpu_sibling_map` / `cpu_core_map` / `cpu_llc_shared_map`，调度域由这几张表决定。位移错了，几颗 vCPU 会被归进同一个核当超线程，或者被拆进不同的 package，负载均衡的行为随之错乱；CPUID 自报的 APIC ID 和 LAPIC 不一致时，内核只打一行 `[Firmware Bug]`，照常往下跑。

所以 mini-vmm 在 `amd_init_vcpu()` 里的顺序是固定的：取 host 的 CPUID → 按 vCPU 改写拓扑 → 置 `hypervisor` 位 → `KVM_SET_CPUID2`。

```c
/* src/arch/amd/svm.c，amd_init_vcpu() */
    r = kvm_get_supported_cpuid(vcpu->vm->kvm_fd, &cpuid);
    ...
    smp_fixup_cpuid(vcpu, cpuid);
    cpuid_mark_hypervisor(cpuid);
    r = kvm_set_cpuid2(vcpu->fd, cpuid);
```

**每个 vCPU 各调一次 `KVM_GET_SUPPORTED_CPUID`**，拿到各自独立的一份缓冲区再改，这样各份结果只有拓扑字段不同。共用一份缓冲区反复改写再 set 也能工作，但容易在下一次改动时写出“vCPU 3 的值覆盖了 vCPU 2”的 bug。

### 7.2 APIC ID 的结构

在讲具体的叶子之前要先说清 APIC ID 本身。x86 把 APIC ID 当作一个**分层编码的整数**：低位是线程号，往上是核号，再往上是 die/node 号，最高位是 socket 号。每一层占几位由 CPUID 告知。

```text
xAPIC ID（8 位）                    x2APIC ID（32 位）
┌────────┬────────┬────────┐        同样的分层，位宽更大
│ socket │  core  │ thread │
└────────┴────────┴────────┘
   高位              低位
```

Linux 7.4 把这套分层统一成一组“域”（`enum x86_topology_domains`：SMT、CORE、MODULE、TILE、DIE、DIEGRP、PKG），每个域记一个位移 `dom_shifts[]`：APIC ID 右移这么多位就得到上一层的编号。各厂商的解析代码最终都只是在填这张位移表（`topology_set_dom()`），填完以后的切分逻辑是公共的。

mini-vmm 选择的拓扑是 **1 socket × N core × 1 thread，APIC ID 等于 vCPU 序号**。这意味着 SMT 域位移为 0，CORE 域位移为 `order_base2(N)`，往上各域沿用 CORE 的位移。这是最简单也最不容易出错的选择：ID 连续、没有洞、和 `vcpu_id` 一一对应，和 KVM 的 LAPIC 默认 ID 一致，和 MADT 的登记顺序一致。

QEMU 支持更复杂的 `-smp sockets=,cores=,threads=`，代价是 APIC ID 变成稀疏的，MADT、CPUID、KVM 三边的换算全部要自己维护。对于 mini-vmm 这个规模，没有必要。

### 7.3 要改写的叶子

`smp_fixup_cpuid()`（`src/smp.c:200`）遍历所有 CPUID 条目，改其中五个叶子，再单独补一个：

```c
void smp_fixup_cpuid(const struct vmm_vcpu *vcpu, struct kvm_cpuid2 *cpuid)
{
    uint32_t id = (uint32_t)vcpu->id;
    uint32_t n  = (uint32_t)vcpu->vm->cfg.nr_vcpus;
    uint32_t i;

    for (i = 0; i < cpuid->nent; i++) {
        struct kvm_cpuid_entry2 *e = &cpuid->entries[i];

        switch (e->function) {
        case 0x1:
            e->ebx = (e->ebx & 0x0000ffffu) | (id << 24) |
                     ((n > 255 ? 255 : n) << 16);
            if (n > 1)
                e->edx |= CPUID_1_EDX_HTT;
            else
                e->edx &= ~CPUID_1_EDX_HTT;
            break;
        case 0x1f:
            e->eax = e->ebx = e->ecx = e->edx = 0;
            break;
        case 0x80000008:
            e->ecx = (e->ecx & ~0xf0ffu) | (order_base2(n) << 12) | (n - 1);
            break;
        case 0x8000001d: {
            uint32_t level = (e->eax >> 5) & 0x7;
            uint32_t share = (level >= 3) ? n - 1 : 0;

            if (e->eax & 0x1f)          /* cache type = 0 表示列表结束 */
                e->eax = (e->eax & ~(0xfffu << 14)) | (share << 14);
            break;
        }
        case 0x8000001e:
            e->eax = id;
            e->ebx = id & 0xff;
            e->ecx = 0;
            break;
        default:
            break;
        }
    }

    /* 0xB 要追加子叶，放在遍历之后做，避免边遍历边改 nent */
    cpuid_fill_topology_leaf(cpuid, id, n);
}
```

先看 guest 会按什么顺序读这些叶子。AMD 和海光都进 `cpu_parse_topology_amd()`（`topology_amd.c:209`），核心是 `parse_topology_amd()`：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/topology_amd.c:178 */
static void parse_topology_amd(struct topo_scan *tscan)
{
	...
	if (!cpu_parse_topology_ext(tscan) && !parse_8000_0008(tscan))
		return;

	if (parse_8000_001e(tscan))
		return;

	/* Try the NODEID MSR */
	parse_fam10h_node_id(tscan);
}
```

`cpu_parse_topology_ext()`（`topology_ext.c:134`）依次试 0x1F、0x80000026、0xB，第一个解析成功的就用；都不行才退到 `0x80000008`。之后不管前面走的哪条，`0x8000001E` 都会再读一次，用来取节点号和 LLC。下面按这个顺序逐个说明。

#### CPUID.1:EBX 与 EDX.HTT

| 位 | 含义 | mini-vmm 填 |
|---|---|---|
| EBX[7:0] | Brand index | 保持 host 值 |
| EBX[15:8] | CLFLUSH 行大小（8 字节为单位） | 保持 host 值 |
| EBX[23:16] | 本 package 内可寻址的逻辑处理器数（HTT=1 时有效） | vCPU 总数，上限 255 |
| EBX[31:24] | **initial APIC ID** | vCPU 序号 |
| EDX[28] | HTT。AMD 语义：置位表示 EBX[23:16] 有效 | N>1 时置 1 |

`(e->ebx & 0x0000ffffu)` 保留低 16 位、重写高 16 位，正是这张表。

Linux 从这里预置 `initial_apicid`：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/topology_common.c:142，parse_topology() */
	/* Preset Initial APIC ID from CPUID leaf 1 */
	cpuid_leaf_reg(1, CPUID_EBX, &ebx);
	c->topo.initial_apicid = ebx.apicid;
	...
	if (early)
		c->topo.apicid = c->topo.initial_apicid;
	else
		c->topo.apicid = read_apic_id();
	...
	tscan->ebx1_nproc_shift = get_count_order(ebx.nproc);
```

BSP 在 `early_identify_cpu()` → `cpu_init_topology()` 里走一次（`early = true`，这时 LAPIC 还没映射，APIC ID 直接取 CPUID 的值），之后每颗 CPU（包括 BSP）在 `identify_cpu()` → `cpu_parse_topology()` 里各走一次（`early = false`）。AP 的这一次发生在 `start_secondary()` → `ap_starting()` → `smp_store_cpu_info()` → `identify_secondary_cpu()` 里。所以 **`initial_apicid` 是每颗 vCPU 自己执行 CPUID 得到的**，这就是它必须按 vCPU 改写的原因。

这个预置值随后可能被覆盖：0xB 解析成功时取子叶 0 的 EDX，走 `0x8000001E` 时取它的 EAX。三处都按 vCPU 填成同一个值，谁覆盖谁结果都一样。

EBX[23:16] 在 mini-vmm 的 guest 上没人用：`ebx1_nproc_shift` 只在 `parse_legacy()` 里用，那是 Intel 没有 0xB、以及 Centaur/兆芯的退路，AMD/海光不走。填对它是为了自洽和面向别的 guest，不是因为 Linux 需要。

#### CPUID.0xB 与 0x1F：扩展拓扑枚举

这两个是 Intel 定义的扩展拓扑枚举叶（0xB 是两级：SMT、Core；0x1F 是多级：加了 module、tile、die），AMD 从 Zen 起也实现 0xB。它们的每个子叶报告一层：

| 字段 | 含义 |
|---|---|
| EAX[4:0] | 从本层算到下一层，APIC ID 要右移几位 |
| EBX[15:0] | 本层的逻辑处理器数；为 0 表示这一层无效 |
| ECX[7:0] | 子叶号，原样回显 |
| ECX[15:8] | 层类型：0 = 无效（列表结束），1 = SMT，2 = Core，5 = Die |
| EDX | 完整的 32 位 x2APIC ID |

`KVM_GET_SUPPORTED_CPUID` 对 0xB 只给一条子叶 0，内容是 host 的原值（见 7.1 节的 dump：EBX 为 0、EDX 是 host 的 x2APIC ID），0x1F 一条都没有。KVM 不改写这些值，因为它不知道 VMM 想给 guest 什么拓扑。

Linux 逐个子叶解析，判断一个子叶是否有效的条件是逻辑处理器数非零且类型非 0，子叶 0 无效就整个叶子放弃：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/topology_ext.c:74，topo_subleaf() */
	cpuid_read_subleaf(leaf, subleaf, &sl);

	if (!sl.num_processors || sl.type == INVALID_TYPE)
		return false;
	...
	if (!dom) {
		tscan->c->topo.initial_apicid = sl.x2apic_id;
	} else if (tscan->c->topo.initial_apicid != sl.x2apic_id) {
		pr_warn_once(FW_BUG "CPUID leaf 0x%x subleaf %d APIC ID mismatch %x != %x\n",
			     leaf, subleaf, tscan->c->topo.initial_apicid, sl.x2apic_id);
	}

	topology_set_dom(tscan, dom, sl.x2apic_shift, sl.num_processors);
	return true;
```

子叶 0（SMT 层）的 EDX 成为 `initial_apicid`，后面每个子叶的 EDX 都要和它相等，否则打 `FW_BUG`。至少解析出一个子叶时，`parse_topology_leaf()` 置上 `X86_FEATURE_XTOPOLOGY`，guest `/proc/cpuinfo` 的 flags 里会出现 `xtopology`。

所以原样透传等于告诉 guest“不提供”。AMD/海光 guest 还有 `0x80000008` + `0x8000001E` 这条退路；Intel guest 的退路是 `parse_legacy()` 读 CPUID.1:EBX[23:16] 加 CPUID.4，更难填对。

mini-vmm 按 1 socket × n core × 1 thread 把 0xB 补齐（`src/smp.c:95` 的 `cpuid_fill_topology_leaf()`）。由于 KVM 只给了子叶 0，补出另外两条必须往 `kvm_cpuid2` 数组里**追加**条目，所以 `kvm_get_supported_cpuid()` 在申请缓冲区时多留了 `KVM_CPUID_SPARE` 个空位，但只向 KVM 声明较小的 `nent`：

```c
/* src/kvm_wrappers.c */
        /* 多分配 KVM_CPUID_SPARE 条但只向 KVM 声明 nent 条，
         * 于是返回后 entries[] 末尾必然还有这么多空位可供追加 */
        c = calloc(1, sizeof(*c) +
                      (nent + KVM_CPUID_SPARE) * sizeof(struct kvm_cpuid_entry2));
        if (!c)
            return VMM_ERR_NOMEM;
        c->nent = nent;
```

填好的三条子叶是：

| 子叶 | EAX（移位） | EBX（本层处理器数） | ECX（子叶号 + 类型） | EDX |
|---|---|---|---|---|
| 0 | 0 | 1 | `0 \| (1 << 8)` SMT | APIC ID |
| 1 | `order_base2(n)` | n | `1 \| (2 << 8)` Core | APIC ID |
| 2 | 0 | 0 | `2 \| (0 << 8)` 无效，终止 | APIC ID |

每条都要带 `KVM_CPUID_FLAG_SIGNIFCANT_INDEX`（子叶号有意义），否则 KVM 查表时不会区分 index。追加位置放在数组末尾即可：KVM 的 `cpuid_entry2_find()` 是线性查找，不要求排序。

把这三条代进 `topo_subleaf()` 算一遍：SMT 域位移 0、1 个处理器，CORE 域位移 `order_base2(n)`、n 个处理器，往上各域沿用 CORE 的位移。于是 `pkg_id = apicid >> order_base2(n) = 0`，`core_id = apicid`。这与 `0x80000008` 那条退路算出的结果完全一致，所以两条路并存不会打架：哪天 0xB 不可用了，guest 退回 `0x80000008` 也得出同一个拓扑。

0x1F 仍然整体清零。`cpu_parse_topology_ext()` 先查 0x1F 再查 0xB，KVM 对 0x1F 同样只会给 host 原值，填一半（比如只有 SMT 层没有 Core 层）会被采信而跳过 0xB。**宁可不提供，不要提供一半**，这是 CPUID 改写的通则。

这台 host 的 CPUID.0:EAX 是 `0x0d`（最大基本叶 13），扩展叶最大到 `0x80000021`，所以 guest 不会去查 0x1F（`cpuid_level >= 0x1f` 不成立），也不会查 0x80000026，直接落到 0xB。如果某台 host 的最大基本叶小于 0xB，补上的 0xB 就是白补：guest 根本不读它，退回 `0x80000008`，结果相同。

#### CPUID.0x80000008:ECX

AMD 的核数与 APIC ID 位宽：

| 位 | 名称 | 含义 | mini-vmm 填 |
|---|---|---|---|
| ECX[7:0] | NC | 本 package 内的线程数 **减 1** | `n - 1` |
| ECX[11:8] | 保留 | | 保持 |
| ECX[15:12] | ApicIdSize | APIC ID 中用于区分核的位数；为 0 表示“自己按 NC 推算” | `order_base2(n)` |

0xB 可用时 guest 不读它；0xB 不可用时它是 CORE 域位移的来源：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/topology_amd.c:27，parse_8000_0008() */
	cpuid_leaf_reg(0x80000008, CPUID_ECX, &ecx);

	/* If the thread bits are 0, then get the shift value from ecx.cpu_nthreads */
	sft = ecx.apicid_coreid_len;
	if (!sft)
		sft = get_count_order(ecx.cpu_nthreads + 1);
	...
	topology_update_dom(tscan, TOPO_SMT_DOMAIN, 0, 1);
	topology_set_dom(tscan, TOPO_CORE_DOMAIN, sft, ecx.cpu_nthreads + 1);
```

`--smp 4` 时 mini-vmm 写的是 `ecx = 0x2003`：CORE 域位移 2、4 个处理器，和 0xB 的结果一样。

**`order_base2(n)` 而不是 `n - 1` 的位数**：如果 `n` 不是 2 的幂（比如 `--smp 3`），`order_base2(3)` 是 2，2 位能容纳 APIC ID 0、1、2，正确。这里填 0 让内核自己推算，`get_count_order(3)` 同样得到 2。两条路一致，显式填上只是为了不依赖内核的推算逻辑。

#### CPUID.0x8000001E

AMD 的扩展 APIC ID 与核/节点编号：

| 寄存器与位 | 含义 | mini-vmm 填 |
|---|---|---|
| EAX[31:0] | Extended APIC ID | vCPU 序号 |
| EBX[7:0] | Core ID（package 内） | vCPU 序号 |
| EBX[15:8] | 每核线程数 **减 1** | 0（每核单线程） |
| ECX[7:0] | Node ID | 0 |
| ECX[10:8] | 每 package 的节点数 **减 1** | 0（单节点） |

KVM 给的是全零（7.1 节的 dump），全零恰好也是“APIC ID 0、单线程、单节点”，对 vCPU 0 碰巧是对的，对其他 vCPU 只错在 APIC ID。guest 只在 `TOPOEXT`（CPUID.80000001:ECX[22]）置位时读这个叶子，这台 host 有、透传给了 guest：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/topology_amd.c:80，parse_8000_001e() */
```

0xB 已经解析成功（`XTOPOLOGY` 置位）时，EAX 和 EBX[15:8] 都被跳过，只用 ECX 的节点信息，再去算 LLC。0xB 不可用时 EAX 才成为 `initial_apicid`，EBX[15:8] 才决定 SMT 域。三个来源（CPUID.1:EBX[31:24]、0xB 的 EDX、0x8000001E 的 EAX）mini-vmm 都填 vCPU 序号，guest 走哪条路结果都一样。

#### CPUID.0x8000001D

AMD 的缓存拓扑，按子叶枚举每一级缓存：

| 位 | 含义 |
|---|---|
| EAX[4:0] | 缓存类型：0=无（枚举结束）、1=数据、2=指令、3=统一 |
| EAX[7:5] | 缓存层级（1/2/3） |
| EAX[25:14] | **共享这一级缓存的逻辑处理器数减 1** |
| EBX / ECX / EDX | 行大小、路数、组数等几何参数 |

mini-vmm 只改 `EAX[25:14]`：L1 和 L2 按每核私有（填 0），L3 按所有 vCPU 共享（填 `n-1`）。这对应“单 socket、所有核共享一个 LLC”的模型。KVM 给的是 host 的值：这台 host 的 L3 由 16 个线程共享（`eax=0003c163`，`EAX[25:14] = 0xf`），L1/L2 由 2 个线程（一个核的两个超线程）共享。

这个字段有两个读者。一是 `/sys/devices/system/cpu/cpuN/cache/indexM/shared_cpu_list`，由 cacheinfo 按它算出的 ID 分组；二是 LLC 域号 `llc_id`，它决定 `cpu_llc_shared_map` 进而决定调度域的 MC 层。AMD Zen2 及以后（family 0x17 model 0x20 起、family 0x19 等）由 `cacheinfo_amd_init_llc_id()` 从 L3 的共享线程数算 LLC 域号：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/cacheinfo.c:312 */
void cacheinfo_amd_init_llc_id(struct cpuinfo_x86 *c, u16 die_id)
{
	if (!cpuid_amd_hygon_has_l3_cache())
		return;

	if (c->x86 < 0x17) {
		/* Pre-Zen: LLC is at the node level */
		c->topo.llc_id = die_id;
	} else if (c->x86 == 0x17 && c->x86_model <= 0x1F) {
		/*
		 * Family 17h up to 1F models: LLC is at the core
		 * complex level.  Core complex ID is ApicId[3].
		 */
		c->topo.llc_id = c->topo.apicid >> 3;
	} else {
		/*
		 * Newer families: LLC ID is calculated from the number
		 * of threads sharing the L3 cache.
		 */
		u32 llc_index = find_num_cache_leaves(c) - 1;
		struct _cpuid4_info id4 = {};

		if (!amd_fill_cpuid4_info(llc_index, &id4))
			c->topo.llc_id = get_cache_id(c->topo.apicid, &id4);
	}
}
```

`get_cache_id()` 是 `apicid >> get_count_order(共享线程数)`。mini-vmm 填 `n-1`，于是 `llc_id = apicid >> order_base2(n) = 0`，所有 vCPU 在同一个 LLC 域。如果透传 host 的 15，`--smp 16` 以内也都落在域 0，超过 16 个 vCPU 才会按 16 个一组切开，这个错误在小规模测试里看不出来。

中间那个分支是一个和 0x8000001D 无关的暗礁：Zen1（family 0x17 model ≤ 0x1F）上内核**不看 0x8000001D**，直接拿 APIC ID 第 3 位往上当核簇（CCX）号。海光同理，`cacheinfo_hygon_init_llc_id()` 对所有海光型号都是 `apicid >> 3`。在这些 guest CPU 上，mini-vmm“APIC ID 等于 vCPU 序号”的约定会让 vCPU 超过 8 个时按 8 个一组切出多个 LLC 域，CPUID 里报的共享关系完全不起作用。真实硬件上这一代处理器的 APIC ID 第 3 位确实就是核簇编号，内核的这条捷径在物理机上是对的；虚拟机要让它和 0x8000001D 自洽，只能把 APIC ID 改成稀疏编号，MADT、MP 表、CPUID、KVM LAPIC 四处都得跟着换算。

mini-vmm 的做法是**只提示、不改行为**：`vm_run()` 开头调一次 `smp_warn_llc_split()`（`src/smp.c:151`），host 是海光或 Zen1、且 vCPU 超过 8 个时打一行警告。guest 看到的 family/model 就是 host 的，所以按 host 判断，条件照抄上面两个内核函数。

```text
[WARN] 16 vCPUs: Linux on this CPU model derives the LLC id from APIC ID bit 3, so the guest will split the vCPUs into 8-CPU last-level-cache domains regardless of what CPUID leaf 0x8000001D reports
```

### 7.4 各厂商的解析路径

同一件事（从 CPUID 推出拓扑），Linux 7.4 在 `parse_topology()`（`topology_common.c:162`）按厂商分派，但所有路径最终都只是在填同一张位移表：

| 厂商 | 入口 | 优先用 | 退路 |
|---|---|---|---|
| Intel | `cpu_parse_topology_ext()` | 0x1F，其次 0xB | `parse_legacy()` 读 CPUID.1:EBX[23:16] + CPUID.4:EAX[31:26] |
| AMD、海光 | `cpu_parse_topology_amd()` → `parse_topology_amd()` | `cpu_parse_topology_ext()`：0x1F、0x80000026、0xB | `parse_8000_0008()`；之后都再读 `0x8000001E` 取节点号和 LLC |
| Centaur、兆芯 | `parse_legacy()` | | |

所有路径都要先有正确的 `initial_apicid`，所以 **CPUID.1:EBX[31:24] 是唯一一个无论 guest 是什么 CPU 都必须改对的字段**。其余字段是“按 guest 会走哪条路来填”。mini-vmm 目前只有 AMD/海光后端，但 0xB 也补齐了：AMD guest 优先用它，将来加 Intel 后端时 Intel guest 也直接能用，不必去改写 CPUID.4 迁就 `parse_legacy()`。

### 7.5 三方一致：Linux 自己会检查

APIC ID 有三个来源，Linux 7.4 在每颗 CPU 解析拓扑时把它们两两比对：

```c
/* guest v7.4-rc2 arch/x86/kernel/cpu/topology_common.c:208 */
void cpu_parse_topology(struct cpuinfo_x86 *c)
{
	unsigned int dom, cpu = smp_processor_id();
	struct topo_scan tscan = { .c = c, };

	parse_topology(&tscan, false);

	if (IS_ENABLED(CONFIG_X86_LOCAL_APIC)) {
		if (c->topo.initial_apicid != c->topo.apicid) {
			pr_err(FW_BUG "CPU%4u: APIC ID mismatch. CPUID: 0x%04x APIC: 0x%04x\n",
			       cpu, c->topo.initial_apicid, c->topo.apicid);
		}

		if (c->topo.apicid != cpuid_to_apicid[cpu]) {
			pr_err(FW_BUG "CPU%4u: APIC ID mismatch. Firmware: 0x%04x APIC: 0x%04x\n",
			       cpu, cpuid_to_apicid[cpu], c->topo.apicid);
		}
	}

	for (dom = TOPO_SMT_DOMAIN; dom < TOPO_MAX_DOMAIN; dom++) {
		if (tscan.dom_shifts[dom] == x86_topo_system.dom_shifts[dom])
			continue;
		pr_err(FW_BUG "CPU%d: Topology domain %u shift %u != %u\n", cpu, dom,
		       tscan.dom_shifts[dom], x86_topo_system.dom_shifts[dom]);
	}

	topo_set_ids(&tscan, false);
}
```

第一处比 CPUID 与 LAPIC，第二处比固件表与 LAPIC（`cpuid_to_apicid[]` 是 MADT 或 MP 表登记、经 `topology_register_apic()` 分配逻辑 CPU 号时记下的），第三处比本 CPU 解析出的位移与 BSP 早期解析的全局位移：任何一颗 vCPU 的 CPUID 拓扑和 BSP 不一样，都会在这里报出来。

三处都只打印，不改变行为，拓扑 ID 一律按 LAPIC 读到的 APIC ID 和全局位移来切。它们出现在 AP 上线的过程中，很容易被淹没在别的日志里，排查 SMP 问题时应该主动 `dmesg | grep -i 'firmware bug'` 找一遍。mini-vmm 的 `smp` e2e suite 把 `APIC ID mismatch` 列为不应出现的输出。

三者的来源和 mini-vmm 的保证方式：

| 来源 | 由谁决定 | mini-vmm 怎么保证等于 vCPU 序号 |
|---|---|---|
| LAPIC 的 ID 寄存器（`read_apic_id()`） | KVM 的 LAPIC 模拟，默认 `= vcpu_id` | 不动 KVM 的默认值 |
| 固件表（`cpuid_to_apicid[]`） | VMM 写的 MADT / MP 表 | `acpi.c:511` 与 `mptable.c:182` 都是 `= i` |
| CPUID（1:EBX[31:24]、0xB:EDX、0x8000001E:EAX） | `KVM_SET_CPUID2` 的内容 | `smp_fixup_cpuid()` 与 `cpuid_fill_topology_leaf()` 都用 `vcpu->id` |

三处代码分别在三个文件里，靠的是同一个约定而不是同一个常量。这正是这类 bug 难查的原因，也是第 10 节要把检查清单单独列出来的原因。

## 8. 多核之后的时间：TSC 同步

### 8.1 为什么 SMP 让时间变成问题

单核时“现在几点”只有一个答案。多核时每颗 CPU 有自己的 TSC 计数器，内核要用它们做 `sched_clock()`、`clocksource`、延迟循环，前提是**所有 CPU 的 TSC 读数一致且以同样速率前进**。物理机上这个前提经常不成立：多路系统的 TSC 由不同的时钟源驱动，深度 C 状态可能停掉 TSC，BIOS 可能在某些 CPU 上写过 `IA32_TSC_ADJUST`。所以内核必须自己验证。

验证逻辑在 `arch/x86/kernel/tsc_sync.c`，每颗 AP 在 `start_secondary()` 里调 `check_tsc_sync_target()`，与 BSP 配对做一次 warp 检测：两边反复读 TSC，如果后读到的值比先读到的小，说明不同步。失败的话打印 `Measured N cycles TSC warp between CPUs, turning off TSC clock.` 并把 TSC 标为不可用，退回 HPET 或 ACPI PM timer——在 mini-vmm 的 guest 里这两者都没有，只剩 `jiffies`，系统会变得极慢且时间精度极差。

### 8.2 mini-vmm 的 guest 为什么跳过了这项检查

实际的 guest 日志里没有任何 `TSC synchronization` 相关的行。原因在检测函数开头：

```c
/* guest v7.4-rc2 arch/x86/kernel/tsc_sync.c:432 */
void check_tsc_sync_target(void)
{
	...
	/* Also aborts if there is no TSC. */
	if (unsynchronized_tsc())
		return;

	/*
	 * Store, verify and sanitize the TSC adjust register. If
	 * successful skip the test.
	 * ...
	 */
	if (tsc_store_and_check_tsc_adjust(false) || tsc_clocksource_reliable)
		return;
```

`tsc_store_and_check_tsc_adjust()` 在 CPU 支持 `IA32_TSC_ADJUST`（`X86_FEATURE_TSC_ADJUST`，guest `/proc/cpuinfo` 的 flags 里有 `tsc_adjust`）时，会读出本 CPU 的 `TSC_ADJUST` 值，与同 socket 内已经上线的参考 CPU 比较：

```c
/* guest v7.4-rc2 arch/x86/kernel/tsc_sync.c:231 */
	if (bootval != ref->adjusted) {
		cur->adjusted = ref->adjusted;
		wrmsrl(MSR_IA32_TSC_ADJUST, ref->adjusted);
	}
	/*
	 * We have the TSCs forced to be in sync on this package. Skip sync
	 * test:
	 */
	return true;
```

一致（都是 0）就返回 `true`，warp 检测整个跳过。这是现代物理机上的常规路径，虚拟机里同样成立。

**这不是运气。** KVM 保证了所有 vCPU 的 TSC 偏移相同：

```c
/* host v6.6 arch/x86/kvm/x86.c:11999，kvm_arch_vcpu_postcreate() */
	kvm_synchronize_tsc(vcpu, 0);
```

每个 vCPU 创建完成时 KVM 都会用 `data == 0` 调一次 `kvm_synchronize_tsc()`，而这个值被专门当作“vCPU 初始化”的信号：

```c
/* host v6.6 arch/x86/kvm/x86.c:2736，kvm_synchronize_tsc() */
		if (data == 0) {
			/*
			 * detection of vcpu initialization -- need to sync
			 * with other vCPUs. This particularly helps to keep
			 * kvm_clock stable after CPU hotplug
			 */
			synchronizing = true;
		}
```

`synchronizing` 为真且 host TSC 稳定时，新 vCPU 直接复用 `kvm->arch.cur_tsc_offset`——**同一个 VM 的所有 vCPU 共享同一个 TSC 偏移**。guest 里读到的 TSC 就是 `host TSC + 同一个常数`，天然同步。这也是 `kvm->arch.nr_vcpus_matched_tsc` 计数的用途：全部匹配时 KVM 才会启用 master clock 模式（`kvm_track_tsc_matching()`，`x86.c:2523`），让 kvmclock 走快速路径。

所以 VMM 这一侧要做的是**不要破坏它**：

- 不要用 `KVM_SET_MSRS` 给不同 vCPU 写不同的 `MSR_IA32_TSC`。真要设置初始 TSC，所有 vCPU 必须在很短的时间窗口内写同一个值（KVM 有一个 1 秒的容忍窗口，见 `x86.c:2752` 的 `synchronizing = data < tsc_exp + tsc_hz && ...`）。
- 不要给不同 vCPU 设不同的 `KVM_SET_TSC_KHZ`。
- 快照恢复时要成组地恢复 TSC，而不是逐个 vCPU 恢复。

mini-vmm 这三件事一件都不做，所以它落在最安全的默认路径上。

### 8.3 TSC 频率与缩放

guest 看到的 TSC 频率默认等于 host 的。`KVM_GET_TSC_KHZ` 可以查，`KVM_SET_TSC_KHZ` 可以改——改成与 host 不同的值需要硬件支持 TSC 缩放，AMD 叫 `TscRateMSR`，Intel 叫 TSC scaling。mini-vmm 启动时打印的 `SVM features` 行里的 `tsc_scale` 就是这一位（CPUID Fn8000_000A_EDX[4]），这台 host 上是有的：

```text
[INFO] SVM features: npt nrip_save tsc_scale vmcb_clean flushbyasid decodeassists pausefilter v_vmsave_vmload
```

它的用途是虚拟机迁移：从 3.0 GHz 的机器迁到 2.5 GHz 的机器上，guest 里的 TSC 频率必须保持不变，否则所有基于 TSC 的计时都会错。不迁移的话没有必要碰它。

**guest 怎么知道 TSC 频率？** mini-vmm 的 guest 内核开了 `CONFIG_KVM_GUEST`，识别出 KVM 后由 kvmclock 接管 TSC 校准：

```c
/* guest v7.4-rc2 arch/x86/kernel/kvmclock.c:139 */
static unsigned long kvm_get_tsc_khz(void)
{
	setup_force_cpu_cap(X86_FEATURE_TSC_KNOWN_FREQ);
	return pvclock_tsc_khz(this_cpu_pvti());
}
```

`kvmclock_init()`（`kvmclock.c:346-347`）把它装成 `x86_platform.calibrate_tsc` 和 `calibrate_cpu`。频率是从 KVM 写进 pvclock 结构的换算系数反推出来的，不需要测，同时置上 `tsc_known_freq`，告诉内核后面不必再复核。日志里只剩一行：

```text
[    0.016811] tsc: Detected 3193.914 MHz processor
```

没有 kvmclock 的 guest（不开 `CONFIG_KVM_GUEST`，或者 VMM 没有暴露 KVM 的 PV CPUID 叶）只能自己测，用的是 PIT：`quick_pit_calibrate()` 成功时打印 `tsc: Fast TSC calibration using PIT`，失败时退回 `pit_calibrate_tsc()`，打印 `tsc: Using PIT calibration value`。快速路径要求两次读 PIT 之间的时间误差外推后低于 500 ppm，只有约 24 µs 的余量，而虚拟机里每次读 PIT 都是一次 VM exit，所以它在虚拟机里时成时败。两条路都正确，只是精度不同。`tests/lib.sh` 的 `expect_tsc_calibrated` 因此三种日志都接受：mini-vmm 测试用的内核走 kvmclock，换一个不带 `CONFIG_KVM_GUEST` 的内核也不会误报。

### 8.4 BogoMIPS 与 AP 的延迟校准

`start_secondary()` 里 TSC 同步检查之后紧接着的是：

```c
/* guest v7.4-rc2 arch/x86/kernel/smpboot.c:211 */
static void ap_calibrate_delay(void)
{
	/*
	 * Calibrate the delay loop and update loops_per_jiffy in cpu_data.
	 * ...
	 * As this is invoked after the TSC synchronization check,
	 * calibrate_delay_is_known() will skip the calibration routine
	 * when TSC is synchronized across sockets.
	 */
	calibrate_delay();
	cpu_data(smp_processor_id()).loops_per_jiffy = loops_per_jiffy;
}
```

`calibrate_delay()`（`init/calibrate.c`）按顺序找现成的 `lpj`：本 CPU 已经校准过的值、`preset_lpj`、`lpj_fine`、`calibrate_delay_is_known()`，都没有才真的跑校准循环。kvmclock 在初始化时用 `kvm_get_preset_lpj()`（`kvmclock.c:145`）把 `preset_lpj` 设成 `tsc_khz * 1000 / HZ`，所以 BSP 和每颗 AP 都直接取这个值，日志里只有 BSP 打印的一行：

```text
[    0.586151] Calibrating delay loop (skipped) preset value.. 6387.82 BogoMIPS (lpj=3193914)
```

而最终的总数是各 CPU 的 `loops_per_jiffy` 简单相加（`impress_friends()`，`smpboot.c:785`）。4 vCPU 时 `4 × 3193914 / 500 = 25551.31`，与日志里的 `smpboot: Total of 4 processors activated (25551.31 BogoMIPS)` 对上。**这是一个很方便的自检：BogoMIPS 总数除以 vCPU 数如果不等于单颗的值，说明某颗 AP 的延迟校准走了不同的路径。** 没有 kvmclock 时这条路径换成 `lpj_fine`（BSP 的 TSC 校准结果）加 `calibrate_delay_is_known()`（TSC 同步时 AP 沿用同 package 里已上线 CPU 的值），结论相同。

这里的 BogoMIPS（6387.82）恰好是主频（3193.914 MHz）的两倍：`lpj` 直接取 `tsc_khz * 1000 / HZ`，而 BogoMIPS 的定义是 `lpj / (500000/HZ)`，两式相除 HZ 抵消，结果是 `tsc_khz / 500`，正好是以 MHz 计的频率的两倍。这个数字在现代内核里已经不代表任何真实的循环速度。

### 8.5 kvmclock 与最终的时钟源

KVM 提供了一个半虚拟化时钟 kvmclock：host 把一个结构体（TSC 时间戳 + 换算系数 + 系统时间）写进 guest 的一页内存，guest 读 TSC 再按系数换算，就能得到与 host 一致的、跨迁移稳定的时间。它需要 guest 侧 `CONFIG_KVM_GUEST`，识别的第一步是看 CPUID.1:ECX[31] 的 `hypervisor` 位，再读 `0x40000000` 起的 KVM 签名叶，日志里对应 `Hypervisor detected: KVM`。

mini-vmm 的 guest 两者都满足，时钟源的切换序列是：

```text
[    0.000000] kvm-clock: Using msrs 4b564d01 and 4b564d00
[    0.576037] clocksource: tsc-early: mask: 0xffffffffffffffff max_cycles: 0x2e09d51e55b, max_idle_ns: 440795321046 ns
[    1.632184] clocksource: Switched to clocksource kvm-clock
[    1.744493] clocksource: Switched to clocksource tsc
[    2.776694] sched_clock: Marking stable (2716446746, 60074416)->(2779388283, -2867121)
```

先切到 kvm-clock，最后落在 tsc：guest 看到 `constant_tsc` 和 `nonstop_tsc` 且 TSC 没被标为不稳定时，`kvmclock_init()` 把 kvm-clock 的 rating 降到 299（`kvmclock.c:365-368`），低于 tsc 的 300，于是 tsc 复核完成、注册为正式时钟源后胜出。`Switched to clocksource tsc` 意味着内核认定 TSC 稳定且同步，愿意把它当作系统时钟源。如果 SMP 环境下 TSC 有问题，最后一行会停在 kvm-clock，或者出现 `Marking TSC unstable`。**排查 SMP 时间问题时，`dmesg | grep clocksource` 的最后一行是最直接的结论。**

## 9. IPI：多核运行期的主要开销

AP 起来之后，SMP 带给 VMM 的持续性负担只有一项：**处理器间中断**。本节把它的代价、观察方法和几种优化路径讲清楚。

### 9.1 guest 里的 IPI 从哪来

`/proc/interrupts` 下半部分全是 IPI 和本地中断的计数。mini-vmm 4 vCPU、启动完成后执行一条命令时的值：

```text
            CPU0       CPU1       CPU2       CPU3
 NMI:          0          0          0          0  Non-maskable interrupts
 LOC:        102       1183       1275       1257  Local timer interrupts
 PMI:          0          0          0          0  Performance monitoring interrupts
 IWI:          7          0          2          0  IRQ work interrupts
 RES:          8         16         27         22  Rescheduling interrupts
 CAL:        173        209        299        218  Function call interrupts
 TLB:          0          1          0          1  TLB shootdowns
 ...
 HYP:          1          1          1          1  Hypervisor callback interrupts
```

| 计数 | 来源 | 触发场景 |
|---|---|---|
| `LOC` | LAPIC timer，不是 IPI | 每颗 CPU 自己的时钟中断。注意它是**由 KVM 的内核态 LAPIC 模拟产生的**，不经过 VMM |
| `RES` | `smp_send_reschedule()` | 唤醒的任务应该跑在另一颗 CPU 上，通知它重新调度 |
| `CAL` | `smp_call_function*()` | 跨 CPU 执行函数。启动阶段这个数最大，因为 MTRR 同步、CPU 特性设置、缓存初始化都要在所有 CPU 上执行 |
| `TLB` | `flush_tlb_multi()` | 一颗 CPU 改了共享的页表，要通知其他 CPU 作废 TLB。guest 启用了 KVM 的 PV TLB flush（`kvm-guest: KVM setup pv remote TLB flush`），目标 vCPU 被抢占时不发 IPI，改为置一个标志让 KVM 在它下次进入 guest 前代为刷新，所以这个数很小 |
| `HYP` | `HYPERVISOR_CALLBACK_VECTOR` | KVM 异步缺页的“页已就绪”通知，与 IPI 无关。每颗 CPU 上线时写 `MSR_KVM_ASYNC_PF_EN` 打开异步缺页，KVM 随即排队一个“唤醒所有等待者”的通知（host v6.6 `x86.c:3441`，`kvm_pv_enable_async_pf()` 调 `kvm_async_pf_wakeup_all()`），这就是每颗 CPU 上的那个 1 |

`SPU`（伪中断）和 `RTR`（ICR 读重试）在 7.4 里默认不显示，第一次计数时才出现（`arch/x86/kernel/irq.c` 的 `IDS()` 条目），这里没有它们说明从未发生。`RTR` 来自 xAPIC 模式下发 IPI 前轮询 ICR 的 Delivery Status 位；guest 工作在 x2APIC 模式，x2APIC 的 ICR 没有这一位，发 IPI 根本不轮询。

### 9.2 一次 IPI 在 KVM 里走多远

物理机上一次 IPI 是几百纳秒：写 ICR，中断通过总线送到目标 LAPIC，目标 CPU 在下一个指令边界响应。虚拟机里这条路要长得多。mini-vmm 的 guest 有两条发送路径：

```text
单个目标（RES 等）                     多个目标（CAL 等，send_IPI_mask）
源 vCPU: WRMSR 0x830 (x2APIC ICR)      源 vCPU: VMMCALL KVM_HC_SEND_IPI
     ↓ #VMEXIT（MSR 写）                    ↓ #VMEXIT（VMMCALL）
KVM: fastpath                          KVM: kvm_emulate_hypercall()
  handle_fastpath_set_x2apic_icr_irqoff()   kvm_pv_send_ipi()
  kvm_x2apic_icr_write()                     __pv_send_ipi()  ← 位图里的每个目标
  kvm_apic_send_ipi()                        kvm_apic_set_irq()
  kvm_irq_delivery_to_apic()
        ↘                                  ↙
          __apic_accept_irq(APIC_DM_FIXED)
            kvm_lapic_set_irr()           ← 置目标 vCPU 的 IRR
            kvm_make_request(KVM_REQ_EVENT)
            kvm_vcpu_kick()               ← 唤醒/踢出目标线程
     ↓
host 调度器             目标 vCPU 线程变成可运行，等待被调度上物理核
     ↓
目标 vCPU (host 内核)   vcpu_enter_guest()
                        inject_pending_event() → 写 VMCB 的 EVENTINJ
     ↓ VMRUN
目标 vCPU (guest)       执行中断处理程序
```

左边是 x2APIC 的原生路径：单目标 IPI 是一条 `WRMSR`，KVM 在 `#VMEXIT` 之后、开中断之前的快速路径里就处理完（`x86.c:2162`，只处理 Fixed 模式、物理目标的写；其他组合走普通 MSR 写路径）。右边是 KVM 的 PV IPI：guest 的 `kvm_setup_pv_ipi()`（`arch/x86/kernel/kvm.c:664`）把 `send_IPI_mask` 和 `send_IPI_mask_allbutself` 换成 `kvm_send_ipi_mask()`，一次超级调用带一个 128 位的目标位图，发给多个 CPU 也只退出一次（`kvm-guest: setup PV IPIs`）。

关键的开销不在 KVM 的代码路径（那部分是几百条指令），而在两处：

1. **目标 vCPU 如果正在 guest 里跑**，`kvm_vcpu_kick()` 要给它发一个物理 IPI 把它踢出 guest（`kvm_arch_vcpu_should_kick()` 判断它是否 `IN_GUEST_MODE`），这是一次真实的 VM exit + VM entry，大约 1-2 微秒。
2. **目标 vCPU 如果被 host 抢占了**，`kvm_vcpu_kick()` 只是把线程置为可运行，实际执行要等 host 调度器。这个延迟没有上界，超卖时可以到毫秒级。

第二条正是 6.3 节讲的问题在 IPI 上的体现。它也解释了为什么 `CAL` 计数在启动阶段特别高却不影响体验（启动时没有超卖），而稳态下如果 `RES` 和 `CAL` 持续高企，就值得怀疑 host 侧的调度。guest 启用的 PV sched yield（`kvm-guest: setup PV sched yield`）针对的正是这一条：发完 call-function IPI 后，如果目标 vCPU 被抢占了，源 vCPU 用 `KVM_HC_SCHED_YIELD` 把自己的时间片让给它。

**这整条路径用户态 VMM 完全看不到。** mini-vmm 的 exit 统计里（`n_exits`、`n_exit_io`、`n_exit_mmio`、`n_exit_hlt`）不会因为 IPI 增加任何一个计数，因为 IPI 从来不走到用户态。这是内核态 LAPIC 的最大价值：把最高频的虚拟化事件留在内核里。

### 9.3 几种减少 IPI 代价的机制

**IPI shorthand（内核侧）。** guest 日志里有一行：

```text
[    2.752132] IPI shorthand broadcast: enabled
```

它来自 `arch/x86/kernel/apic/ipi.c:26`。含义是：给“除自己外所有 CPU”发 IPI 时，用 ICR 的 destination shorthand 字段（`APIC_DEST_ALLBUT`）一次发出，而不是对每个目标各写一次 ICR。在物理机上这省的是总线事务，在 KVM 下省的是 ICR 写的次数。启用条件是“所有 present 的 CPU 都至少启动过一次”（`apic_smt_update()`，`ipi.c:32`），所以这一行出现在启动后期而不是 `smp_init()` 附近。可以用 `no_ipi_broadcast=1` 关掉做对比。

**x2APIC（架构侧）。** x2APIC 把 LAPIC 的访问从 MMIO 换成 MSR，发 IPI 变成一条 `WRMSR`，目标 ID 是 32 位的，支持超过 255 颗 CPU。物理机上开 x2APIC 需要中断重映射单元（IOMMU 的 IR），mini-vmm 没有提供，这条例外靠 hypervisor 钩子放行：

```c
/* guest v7.4-rc2 arch/x86/kernel/apic/apic.c:1838，try_to_enable_x2apic() */
	if (remap_mode != IRQ_REMAP_X2APIC_MODE) {
		u32 apic_limit = 255;

		/*
		 * Using X2APIC without IR is not architecturally supported
		 * on bare metal but may be supported in guests.
		 */
		if (!x86_init.hyper.x2apic_available()) {
			pr_info("x2apic: IRQ remapping doesn't support X2APIC mode\n");
			x2apic_disable();
			return;
		}
		...
```

`x2apic_available` 的默认实现是 `bool_x86_init_noop`，恒返回 false（`arch/x86/kernel/x86_init.c:120`）；guest 识别出 KVM 后换成 `kvm_para_available`（`arch/x86/kernel/kvm.c:1071`），于是 x2APIC 打开，没有 IR 时只能用物理目标模式：

```text
[    0.541627] x2apic enabled
[    0.544861] APIC: Switched APIC routing to: physical x2apic
```

这条路依赖 guest 开 `CONFIG_KVM_GUEST`（它带上 `CONFIG_HYPERVISOR_GUEST`）。不带它的内核即使看到 `hypervisor` 位也认不出 KVM，日志会是 `x2apic: IRQ remapping doesn't support X2APIC mode`，留在 xAPIC。**`hypervisor` 位只是一张入场券，它带来的实际收益都在 `CONFIG_HYPERVISOR_GUEST` 那一大块代码里**：kvmclock、x2APIC、PV EOI、PV IPI、PV TLB flush 都是。

顺带说明，MADT 的 Processor Local APIC 条目和 MP 表的 APIC ID 都是 8 位，mini-vmm 的 vCPU 数上限本来就卡在 255 以内（实际 `VMM_MAX_VCPUS` 是 32，MP 表的空间还能放 40 条，见卷五 5.4 节）。要突破 255 除了 x2APIC，还要改用 MADT 的 Local x2APIC 条目。

**AVIC（硬件侧）。** AMD 的 Advanced Virtual Interrupt Controller 把 LAPIC 的大部分寄存器访问和 IPI 投递做进硬件：源 vCPU 写 ICR 不产生 `#VMEXIT`，硬件直接查 AVIC 的物理 APIC ID 表，把中断写进目标 vCPU 的后备页并向目标所在的物理核发一个 doorbell 中断。目标 vCPU 如果正在运行，整个过程零 exit。

KVM 6.6 里 AVIC 默认关闭：

```c
/* host v6.6 arch/x86/kvm/svm/svm.c:229 */
static bool avic;
module_param(avic, bool, 0444);
...
/* svm_hardware_setup()，svm.c:5315 */
	enable_apicv = avic = avic && avic_hardware_setup();
```

`avic` 没有初值即为 false。这台 host 是 WSL2，KVM 本身跑在 Hyper-V 之上，Hyper-V 没有把 AVIC 暴露给它：mini-vmm 的 `SVM features` 行里没有 `avic`，`/sys/module/kvm_amd/parameters/avic` 是 `N`。启不启用对 VMM 是透明的——AVIC 的所有配置都在 host 的 `kvm_amd` 模块里，用户态既不能开也不能关，只能通过 `modprobe kvm_amd avic=1` 从 host 侧调整。卷四对 AVIC 的结构有更详细的介绍。

### 9.4 VMM 能做什么

结论很简短：**在 IPI 这件事上用户态 VMM 能做的就是把 LAPIC 留在内核里，并把 KVM 的 PV 特性透传给 guest**。`KVM_CREATE_IRQCHIP`（或 `KVM_CAP_SPLIT_IRQCHIP`，它只把 IOAPIC/PIC 搬到用户态，LAPIC 仍在内核）一旦建好，IPI 路径就是最优的；PV IPI、PV TLB flush、PV sched yield 由 `0x40000001` 叶的特性位决定，mini-vmm 原样透传 `KVM_GET_SUPPORTED_CPUID` 给的值。剩下的优化（shorthand、x2APIC、AVIC）分别属于 guest 内核、guest 配置和 host 内核模块，VMM 只能创造条件，不能直接控制。

反过来，如果 VMM 自己在用户态模拟 LAPIC（不建内核态 irqchip），每一次 IPI 都会变成一次用户态往返，SMP guest 的性能会塌掉一个数量级。这也是 mini-vmm 在 `--mode linux` 下无条件建 irqchip 的原因（`src/vm.c:778`，默认 `irqchip_create()`，`--irqchip split` 时 `split_irqchip_create()`）。

## 10. 一致性检查清单

卷五第 9 节给出了固件表与设备模型之间的一致性约束。本节是它在 CPU 侧的对应物：把 SMP 相关的全部约束集中列出，可以当作写 VMM 时的核对表。每一条都标注了违反时的现象，因为这类 bug 的共同特点是**现象离原因很远**。

### 10.1 编号与数量

| 约束 | 三方（或多方）分别在哪 | 违反的现象 |
|---|---|---|
| APIC ID 必须三方相同 | KVM 的 LAPIC（默认 `= vcpu_id`）／MADT 的 `apic_id`（`acpi.c:511`）与 MP 表（`mptable.c:182`）／CPUID 的三处 APIC ID（`smp_fixup_cpuid()`、`cpuid_fill_topology_leaf()`） | 不一致时打印 `[Firmware Bug]: CPU   n: APIC ID mismatch. Firmware: ...` 或 `CPUID: ...`。并行启动时 AP 在 `.Lfind_cpunr` 查不到自己，直接 `hlt`，10 秒后 `CPUn failed to report alive state` |
| vCPU 数量必须处处一致 | `KVM_CREATE_VCPU` 的次数／MADT 的 LAPIC 条目数／MP 表的 processor 条目数／CPUID 0x80000008 的 NC | 表里多报：内核为不存在的 CPU 发 IPI 然后超时。表里少报：多出来的 vCPU 线程永远阻塞在 `KVM_RUN`，VM 退不出去 |
| BSP 必须是同一颗 | KVM 的 `bsp_vcpu_id`（默认 0）／MP 表的 `CPU_BOOTPROCESSOR` 标志（`mptable.c:185`）／MADT 的第一条 LAPIC 条目 | BSP 认错：真正的 BSP 是 `RUNNABLE` 的那颗，它会照常执行；被标错的那颗收不到 INIT 就不会动。表现为 `Brought up N-1 CPUs` |
| IOAPIC ID 不能与任何 LAPIC ID 冲突 | mini-vmm 取 `nr_cpus`（`mptable.c:148`、`acpi.c:520`） | APIC ID 空间冲突，中断路由异常。`--smp` 增大时这条尤其容易被忘记——ID 必须跟着挪 |
| vCPU 数不得超过 KVM 上限 | `KVM_CHECK_EXTENSION(KVM_CAP_MAX_VCPUS)` | `KVM_CREATE_VCPU` 返回 `EINVAL`。mini-vmm 在 `vm_create()` 里提前检查并报错（`src/vm.c:731`） |
| vCPU 数不得超过 MP 表容量与 8 位 APIC ID | `VMM_MAX_VCPUS` = 32，MP 表按 `MPTABLE_MAX_SIZE` 能放 40 条，MADT 的 Processor Local APIC 条目和 MP 表的 APIC ID 都是 8 位 | 溢出会静默地写坏后面的表 |

### 10.2 内存与设备

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| E820 中 1 MiB 以下必须有可用 RAM | AP 的实模式跳板必须装在那里（3.1 节） | `No sub-1M memory is available for the trampoline`，随后 `panic("Real mode trampoline was not allocated")`。**单 vCPU 也会 panic** |
| 物理地址 `0x467`/`0x469` 必须是可写 RAM | warm reset vector（3.6 节） | 每次唤醒 AP 时写进黑洞；本身不致命，但如果那段地址被映射成 MMIO 会产生莫名的 exit |
| CMOS 索引 `0x0F` 的写必须被接受 | 同上 | RTC 模型如果对未知索引报错，`do_boot_cpu()` 的第一步就失败 |
| 内核态 irqchip 必须在创建 vCPU **之前**建好 | KVM 在 `KVM_CREATE_VCPU` 时才决定挂不挂内核态 LAPIC | 顺序反了：所有 vCPU 都是 `RUNNABLE`，AP 从 `0xfff0` 跑飞，表现为 `KVM_EXIT_SHUTDOWN`；同时 IPI 全部变成用户态 MMIO exit |
| 设备模型必须能承受并发访问 | 并行启动时多个 AP 几乎同时进 guest（4.3 节） | 数据竞争，现象随机。mini-vmm 用 `io_lock` 串行化（`src/vm.c:503-514`） |

### 10.3 CPUID

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| CPUID.1:EBX[31:24] 必须按 vCPU 改写 | 它是 `initial_apicid` 的初值（7.3 节） | 0xB 不可用时 0x8000001E 的 EAX 会覆盖它，0xB 可用时子叶 EDX 会覆盖它；三处只要有一处和 LAPIC 不同，就打印 `APIC ID mismatch. CPUID: ...` |
| **除拓扑字段外，所有 vCPU 的 CPUID 必须完全相同** | AP 直接沿用 BSP 探测出的 CR4 与 EFER（3.3 节） | AP 带着为别人算出的 CR4 进长模式；`verify_cpu` 可能失败；特性不一致还会让 `alternatives` 打错补丁 |
| 扩展拓扑叶（0xB/0x1F）要么填完整，要么整体清零 | Linux 用子叶 0 的 EBX 为 0 或类型为 0 判断“不提供”（7.3 节） | 填一半会被采信，`topo_subleaf()` 算出错误的域位移，比整体不填更糟 |
| 填 0xB 时必须与 0x8000001E / 0x80000008 得出同样的拓扑 | AMD/海光 guest 有 0xB 时用它，没有时退回后两者（7.3 节） | 两条路打架，拓扑随 guest 走哪条路而变，换一个最大基本叶更小的 host 就变样 |
| 追加 CPUID 子叶要带 `KVM_CPUID_FLAG_SIGNIFCANT_INDEX` | 没有这个标志 KVM 查表时不区分 index | 所有子叶都命中第一条，枚举提前结束 |
| 0x80000008:ECX 的 NC 是“线程数减 1”，0x8000001E:EBX[15:8] 是“每核线程数减 1” | 多处 AMD 字段都是减 1 编码 | 差一错误。域位移算错，`CPU topo: Num. cores per package` 和 `Max. logical packages` 跟着错 |
| 拓扑改写要对每个 vCPU 各取一份 CPUID 缓冲区 | 共用缓冲区容易写出覆盖 bug（7.1 节） | 后创建的 vCPU 覆盖先创建的，表现为部分 vCPU 拓扑正确、部分不正确 |
| 注意 guest 可能从 APIC ID 直接反推拓扑 | 海光和 AMD Zen1 上 `llc_id = apicid >> 3`（7.3 节） | vCPU 超过 8 时 LLC 域被切开。**CPUID 填对了也没用**，因为 guest 根本没看 |

### 10.4 运行期

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| `KVM_RUN` 返回 `EAGAIN` 必须当作“重进” | AP 在 `UNINITIALIZED` 状态下被唤醒时返回它（5.2 节） | AP 线程报 `Resource temporarily unavailable` 退出；单 vCPU 时完全正常，一加 `--smp 2` 就坏 |
| `EINTR` / `EAGAIN` 之后不能去读 `exit_reason` | 这两条路径不保证写这个字段 | 上一次的 PIO 被重放一遍，串口输出出现重复字符 |
| 停机信号的 handler 不能带 `SA_RESTART` | 带了 `KVM_RUN` 会自动重启（6.4 节） | 停机请求丢失，VM 挂死。用 `signal()` 而不是 `sigaction()` 是常见诱因 |
| 停机要先置 `immediate_exit` 再发信号 | 覆盖“刚检查完标志还没进 `KVM_RUN`”的窗口（6.4 节） | 偶发挂死，概率随 vCPU 数增加而上升 |
| 不要给不同 vCPU 设不同的 TSC 偏移或频率 | KVM 默认让所有 vCPU 共享同一偏移（8.2 节） | guest 的 TSC 同步检查失败：`Measured N cycles TSC warp between CPUs, turning off TSC clock` |
| `--smp > 1` 只在有 irqchip 的模式下允许 | 没有 LAPIC 就没有 INIT/SIPI | mini-vmm 直接在参数校验阶段报错：`--smp > 1 requires --mode linux` |

## 11. 验证与排障

SMP 问题的共同特点是**沉默**：AP 起不来时 VMM 侧没有任何异常，guest 侧要等 10 秒才出一行日志。所以排障的第一步不是看现象，而是主动去采集状态。

### 11.1 在 host 侧观察

**线程。** 一线程一 vCPU 的模型让 `top -H` 直接可用：

```sh
top -H -p $(pgrep -x vmm)
```

mini-vmm 给每个线程都设了名字（`src/smp.c:346` 的 `pthread_setname_np`），所以看到的是 `vcpu0`…`vcpu3`。三条判断规则：

- 启动早期只有 `vcpu0` 在跑，其余为 0——正常，AP 还没收到 SIPI。
- guest 起来之后所有线程都接近 0——正常，都在 idle 的 `HLT` 里。
- guest 起来之后某个 AP 线程恒为 0 而 guest 里 `nproc` 少了一个——AP 没起来。
- 某个线程 100% 而 guest 空闲——AP 卡在自旋里，多半是跳板锁或 `.Lfind_cpunr` 的死循环（后者是 `hlt`，不占 CPU；前者的 `pause` 自旋会占）。

**`KVM_GET_MP_STATE`。** 这是判断“AP 到底走到哪一步”的决定性证据。但 5.5 节说过，它要抢 `vcpu->mutex`，而 `KVM_RUN` 期间这把锁是被持有的，从主线程直接查会卡住。正确的位置是让 vCPU 线程自己在 run loop 里报告——mini-vmm 就把它放在 `kvm_run()` 返回 `VMM_ERR_INTR` 的那个分支里，只在 debug 级别执行：

```c
/* src/vm.c，vcpu_run_loop() */
        if (r == VMM_ERR_INTR) {
            /* AP 唤醒（EAGAIN）和停机（EINTR）都走这条路，每个 vCPU 整个
             * 生命周期里只会走几次，所以在这里查一次 mp_state 的代价可以
             * 忽略，而它是判断 AP 卡在哪一步的决定性证据 */
            if (vmm_log_level >= 3) {
                uint32_t st;

                if (kvm_get_mp_state(vcpu->fd, &st) == VMM_OK)
                    vmm_dbg("vCPU %d: KVM_RUN interrupted, mp_state=%u (%s)",
                            vcpu->id, st, kvm_mp_state_str(st));
            }
            continue;
        }
```

加 `-v` 跑一次 4 vCPU 的 guest，能直接看到三颗 AP 被唤醒、以及关机时被踢出 `HLT` 的两批输出：

```text
[    0.525963] smpboot: x86: Booting SMP configuration:
[DBG ] vm.c:618: vCPU 1: KVM_RUN interrupted, mp_state=0 (RUNNABLE)
[DBG ] vm.c:618: vCPU 2: KVM_RUN interrupted, mp_state=0 (RUNNABLE)
[DBG ] vm.c:618: vCPU 3: KVM_RUN interrupted, mp_state=0 (RUNNABLE)
[    0.526836] .... node  #0, CPUs:      #1 #2 #3
[    0.537211] smp: Brought up 1 node, 4 CPUs
[DBG ] vm.c:618: vCPU 1: KVM_RUN interrupted, mp_state=3 (HALTED)
[DBG ] vm.c:618: vCPU 2: KVM_RUN interrupted, mp_state=3 (HALTED)
[DBG ] vm.c:618: vCPU 3: KVM_RUN interrupted, mp_state=3 (HALTED)
```

第一批就是 5.2 节那次 `-EAGAIN` 返回：AP 线程被 INIT 从 `kvm_vcpu_block()` 里叫醒，`KVM_RUN` 一条 guest 指令都没执行就返回了。读到的是 `RUNNABLE` 而不是 `INIT_RECEIVED`，原因在两头：`KVM_GET_MP_STATE` 自己会先调一次 `kvm_apic_accept_events()`（`host v6.6 arch/x86/kvm/x86.c:11406`），把已经挂着的 SIPI 也处理掉；而 guest 在 AMD family ≥ 0xF 上把 `init_udelay` 设成 0（`guest v7.4-rc2 arch/x86/kernel/smpboot.c:825-840`，`smp_set_init_udelay()`），INIT 之后几微秒就发 SIPI，比 AP 线程从内核返回用户态再发起下一个 ioctl 快得多。加 `--append cpu_init_udelay=10000` 把 INIT 到 SIPI 的间隔拉到 10 毫秒，同一位置读到的就是三行 `mp_state=2 (INIT_RECEIVED)`，`Brought up` 也相应推迟到约 42 毫秒之后。第二批是 6.4 节的停机协调把它们从 `HLT` 里踢出来。读到的值这样解读：

| 读到 | 含义 |
|---|---|
| `UNINITIALIZED` 且一直不变 | BSP 根本没发 INIT。检查 MADT 里这颗 CPU 有没有登记、`enabled` 位有没有置 |
| `INIT_RECEIVED` 且一直不变 | 收到了 INIT 但没收到 SIPI。检查 `do_boot_cpu()` 是不是在发 SIPI 之前就失败了（比如 CMOS 写被拒） |
| `RUNNABLE` 但 guest 里 CPU 数不对 | AP 跑起来了但死在跳板或 `.Lfind_cpunr`。看 APIC ID 一致性 |
| `HALTED` | 正常，AP 在 idle |

### 11.3 有用的 guest 命令行开关

| 开关 | 作用 | 用来验证什么 |
|---|---|---|

### 11.4 症状对照

| 症状 | 最可能的原因 | 先查什么 |
|---|---|---|
| VMM 报 `KVM_RUN: Resource temporarily unavailable` 后 AP 线程退出 | 没处理 `EAGAIN`（5.2 节） | `kvm_run()` 包装函数 |
| guest 日志 `CPUn failed to report alive state`，10 秒一颗 | AP 死在跳板或查不到 CPU 号 | APIC ID 三方一致；1 MiB 以下有没有 RAM |
| guest 日志 `[Firmware Bug]: CPU   n: APIC ID mismatch. Firmware: ...` | MADT/MP 表的 APIC ID 与 KVM 的 LAPIC ID 不符 | `acpi.c` 与 `mptable.c` 里填 ID 的那两行 |
| guest 日志 `APIC ID mismatch. CPUID: ...` 或 `CPUID leaf 0xb subleaf N APIC ID mismatch` | CPUID 里自报的 APIC ID 没按 vCPU 改写 | `smp_fixup_cpuid()`、`cpuid_fill_topology_leaf()` |
| guest 日志 `Topology domain N shift X != Y` | 某颗 AP 的 CPUID 拓扑位移和 BSP 不一样 | 是否每个 vCPU 各取了一份 CPUID 缓冲区 |
| `panic: Real mode trampoline was not allocated` | E820 里 1 MiB 以下没有可用 RAM | E820 第一项 |
| 所有 vCPU 都跑，但 guest 只认 1 颗 | MADT 只登记了 1 条，或 `nr_vcpus` 没传到固件表 | `MP table @ GPA ...: N CPU(s)` 这行日志里的 N |
| `smp: Brought up 1 node, 1 CPUs` 而 `CPU topo: Allowing 4 present CPUs` | 表登记正确但 AP 全部唤醒失败 | 同第 2 行 |
| guest 里四颗 CPU 的 `core id` 全相同，或 `physical id` 不全是 0 | CPUID 里的拓扑位移不对（0xB 的 EAX、0x80000008 的 ApicIdSize） | `smp_fixup_cpuid()`、`cpuid_fill_topology_leaf()` |
| `Measured N cycles TSC warp between CPUs` | VMM 给不同 vCPU 设了不同的 TSC | 有没有调 `KVM_SET_MSRS(MSR_IA32_TSC)` 或 `KVM_SET_TSC_KHZ` |
| guest 关机后 VMM 不退出 | 停机协调漏了某个阻塞在 `HLT` 的 AP | `vm_request_stop()` 的 `immediate_exit` 与信号（6.4 节） |
| VMM 退出但终端没恢复 | 与 SMP 无关，是终端 raw 模式没还原 | `console.c` 的 atexit 处理 |
| 串口输出出现重复的字符片段 | `EINTR`/`EAGAIN` 之后错误地分发了旧的 `exit_reason` | `vcpu_run_loop()` |

### 11.5 自动化：`tests/e2e/smp.sh` 与 `tests/mutants/smp.py`

mini-vmm 把上面这些检查固化成了一组 e2e 用例。第一条走 panic-reset 路径，覆盖“全部 AP 起来 + 任一 vCPU 触发的停机能让所有线程退出”：

```sh
run_case "$SMP vCPU 启动到 VFS panic 并经 i8042 reset 全部退出" \
    timeout 60 "$VMM" --mode linux --no-reboot --smp "$SMP" --mem "$MEM" \
        --initrd "$INITRD" --append "rdinit=/nonexistent" "$VMLINUX"
expect_rc 0
expect_has "MP table @ GPA 0x9fc00: $SMP CPU(s), IOAPIC id $SMP"
expect_has "$SMP vCPU thread(s) running"
expect_has "CPU topo: Allowing $SMP present CPUs plus 0 hotplug CPUs"
expect_has "smp: Brought up 1 node, $SMP CPUs"
expect_has "guest requested reset via i8042"
expect_not "failed to report alive state"
expect_not "do_boot_cpu failed"
expect_not "APIC ID mismatch"
expect_not "TSC synchronization"
expect_not "stopped with error"
expect_not "SHUTDOWN"
end_case
```

四条 `expect_has` 是一条链：固件表写对了 → VMM 起了 4 个线程 → guest 认到 4 颗 → 4 颗全部上线。断在哪一环，问题就在哪一层。`expect_not` 覆盖的正是 11.4 表里最常见的几种失败；它们匹配的是 guest 内核的原话（`APIC ID mismatch` 来自 `topology.c` 的 FW_BUG 检查，`failed to report alive state` 来自 `kernel/cpu.c`），换 guest 内核版本时这些字符串必须重新到新源码里核对，原话一变，断言就永远不会失败。

**用 `expect_not` 而不是只看退出码，是这类测试的关键。** AP 起不来时 VM 照样能跑完、照样正常退出，退出码是 0；只有日志里那一行 `failed to report alive state` 能暴露问题。`timeout 60` 则兜住“停机协调漏了某颗 AP”这种挂死。

第二条用同样的命令行，但在父进程里先阻塞 `SIGUSR1` 再 exec VMM。信号掩码会被子进程继承，VMM 如果只装处理函数而不解除阻塞，踢 vCPU 的信号就一直挂在 pending 里，HLT 中的 AP 永远不醒。

第三条进 initramfs 的 shell，从两层同时看拓扑。第一层是 guest 解析后的结果：

```sh
    --cmd 'echo APIC-$(sed -n "s/^apicid.*: //p" /proc/cpuinfo | tr "\n" -)' \
    --cmd 'echo CORE-$(sed -n "s/^core id.*: //p" /proc/cpuinfo | tr "\n" -)' \
    --cmd 'echo PKG-$(sed -n "s/^physical id.*: //p" /proc/cpuinfo | sort -u | tr "\n" -)' \
    --cmd 'echo L3-$(cat /sys/devices/system/cpu/cpu0/cache/index3/shared_cpu_list)' \
    --cmd 'echo L2-$(cat /sys/devices/system/cpu/cpu1/cache/index2/shared_cpu_list)' \
    --cmd 'cpuidprobe' \
```

第二层是 `cpuidprobe`（`tools/guest/cpuidprobe.c`）：它用 `sched_setaffinity()` 依次绑到每颗在线 CPU 上执行 `cpuid`，把 VMM 交给这颗 vCPU 的原始拓扑字段打印成一行，例如 `--smp 4` 时 CPU 2 是：

```text
CPUID-2 L1=2,4 B0=0,1,256,2 B1=2,4,513,2 B2=0,0,2,2 E8=8195 E1E=2,2,0 L3=4
```

只看 `/proc/cpuinfo` 不够，是因为 guest 内核会用后读的叶子覆盖先读的：0xB 子叶的 EDX 会盖掉 CPUID.1 里的 initial APIC ID，0x8000001E 只在没有 `XTOPOLOGY` 时才设 APIC ID。CPUID.1 的 APIC ID 填成 0、而 0xB 填对时，`/proc/cpuinfo` 里四个 `apicid` 照样是 0-1-2-3，只有原始值能暴露出来。期望值由脚本里的 `expect_cpuid_topology n` 按“1 socket × n core × 1 thread、APIC ID = vCPU 序号”从规范直接算出，和 `src/smp.c` 的实现无关：

| 字段 | 期望 |
|---|---|
| `L1` | CPUID.1:EBX[31:24] = i，[23:16] = n |
| `B0`/`B1`/`B2` | 0xB 三个子叶的 EAX[4:0]、EBX[15:0]、ECX[15:0]、EDX：SMT 层移位 0、1 个处理器、类型 1；Core 层移位 ⌈log₂n⌉、n 个、类型 2；终止子叶类型 0；每个子叶 EDX = i。host 的最大基本叶小于 0xB 时 KVM 不给这个叶，期望变成 `-` |
| `E8` | 0x80000008:ECX = ApicIdSize<<12 \| (n−1) |
| `E1E` | 0x8000001E 的 EAX = i、EBX[15:0] = i（核号 i、每核 1 线程）、ECX[10:0] = 0（单节点） |
| `L3` | 0x8000001D 里 L3 的共享线程数 = n |

第四条把 vCPU 数拉到 `SMP_MANY`（默认 16）再跑一遍。4 个 vCPU 压不到并行启动的关键路径——所有 AP 同时抢实模式跳板那把锁（3.3 节），vCPU 多一些才有真正的竞争。这条用例同样跑 `cpuidprobe`，并检查 LLC 域：

```sh
if [ "$SMP_MANY" -gt 8 ] && grep -q "derives the LLC id from APIC ID bit 3" <<<"$CUR_OUT"; then
    expect_has "L3A-0-7"
    ...                                  # 最后一组 8 颗
else
    expect_has "L3A-0-$(( SMP_MANY - 1 ))"
    expect_has "L3B-0-$(( SMP_MANY - 1 ))"
fi
```

哪一种结果由 host 的 CPU 型号决定：Zen2 之后的 AMD 按 0x8000001D 的共享线程数算，所有 vCPU 在一个 LLC 域里；海光和 Zen1 上 guest 直接 `llc_id = apicid >> 3`，按 8 个一组切开，这时 VMM 的 `smp_warn_llc_split()` 会打印上面那行警告。分支以 VMM 是否警告为准，所以“警告了却没切开”和“切开了却没警告”都会失败，两者都说明 VMM 对 guest 行为的判断错了。

`tests/mutants/smp.py` 是这组断言的对照组：11 个变异体各在 `src/smp.c` 里改坏一处拓扑字段（CPUID.1 的 APIC ID 或处理器数、0xB 的 Core 移位或某个子叶的 EDX、0x80000008 的 ApicIdSize 或 NC、0x8000001E 的核号或每核线程数、0x8000001D 的 L3/L2 共享数、对所有 AMD 都发 LLC 警告），`tests/mutate.py smp` 逐个编译、跑 smp suite，11 个全部被抓到。其中好几个变异体在 `/proc/cpuinfo` 和 sysfs 上完全看不出来，只有 `cpuidprobe` 那一行失败，这正是加原始值检查的理由。有两类改动在这台 host 上是等价变异体，没有收进去：0x1F 不清零（Zen3 没有 0x1F，KVM 本来就不给）、LLC 警告永不打印（Zen3 本来就不该打印）。

`tests/guest_shell.py` 负责启动 VMM 并在 guest shell 里执行这些命令：每条 `--cmd` 等 shell 提示符出现后才发送，`--stop` 发出后等 VMM 自己退出。vCPU 越多启动越慢，按固定延迟发送会在 shell 起来之前把命令送进去，而 guest 串口驱动打开 tty 时会清空 RX 缓冲区，这些命令就丢了。`echo XXX-$(...)` 这种写法是为了和终端回显区分开：回显里只有 `$(...)` 字面量，只有真正执行后的输出才带着展开结果，断言不会误匹配。

人工验收部分补了三条自动化测不了的：`top -H` 看四个线程是否真的并行、`Ctrl-A x` 能否停下所有 vCPU、`maxcpus=1` 时 AP 线程是否确实不占 CPU。

## 12. 本卷小结与卷七预告

**AP 唤醒。** 规范定义的 INIT-SIPI-SIPI 序列在 KVM 下完整保留，但实现全在内核里：BSP 写 ICR 不产生用户态 exit，AP 的等待与唤醒发生在 `KVM_RUN` 内部。用户态 VMM 在这条链路上只需要做一件事——把 `KVM_RUN` 返回的 `EAGAIN` 当作“重进”而不是错误。前提是内核态 irqchip，而且它必须在创建 vCPU **之前**建好。

**跳板。** SIPI 向量只有 8 位，AP 的入口必须在 1 MiB 以下，这条硬件约束一路传导到 VMM 的 E820：低端必须有可用 RAM，否则连单 vCPU 的 guest 都会 panic。跳板还会顺带写一次 CMOS 索引 `0x0F` 和物理地址 `0x467`，VMM 的 RTC 模型和低端内存都得接得住。

**并行启动。** 6.5 起 Linux 给跳板加了锁，改成“先全部踢醒、再逐个放行”。代价是所有 AP 几乎同时进 guest，对 VMM 的设备模型并发是一次集中考验；收益是 AP 自己从 LAPIC 读 APIC ID、再去 `cpuid_to_apicid[]` 查自己的编号——这让“固件表里的 APIC ID 必须等于 KVM 的 LAPIC ID”从一条建议变成了硬性要求，对不上的 AP 会直接 `hlt` 死在那里。

**`mp_state`。** `UNINITIALIZED` → `INIT_RECEIVED` → `RUNNABLE` 这三态就是架构上的 wait-for-SIPI 的建模。INIT 触发一次完整的 vCPU 复位，SIPI 只改 `CS.base = vector << 12` 和 `RIP = 0`。`KVM_GET_MP_STATE` 是排查 AP 不启动的决定性手段，但要注意它会抢 `vcpu->mutex`。

**vCPU 就是线程。** 这带来两个纯用户态的问题：停机协调（`immediate_exit` + 不带 `SA_RESTART` 的信号，两个窗口都要覆盖）和设备并发（一把大锁最省事）。运行期的性能问题——锁持有者被抢占、IPI 延迟放大——则主要由 host 调度与 PAUSE 拦截决定，VMM 能做的只是选择内核态 irqchip。

**CPUID 拓扑。** 这是本卷唯一必须逐位手写的部分。`KVM_GET_SUPPORTED_CPUID` 的拓扑字段一定是错的，因为它描述的是 host。必须改的五个叶子是 1、0xB/0x1F、0x80000008、0x8000001D、0x8000001E，其中 **CPUID.1:EBX[31:24] 的 initial APIC ID 是唯一一个无论 guest 是什么 CPU 都必须改对的字段**。扩展拓扑叶要么填完整要么整体清零，不能填一半。

**三方一致。** KVM 的 LAPIC ID、固件表的 APIC ID、CPUID 里自报的 APIC ID 必须相同。Linux 7.4 在每颗 CPU 解析拓扑时把 CPUID 与 LAPIC、固件表与 LAPIC 各比一次，再把本 CPU 的拓扑位移与 BSP 比一次，不一致只打印 `[Firmware Bug]`，照常往下跑。第 10 节的清单可以直接当作核对表。

**guest 会从 APIC ID 反推拓扑。** 这是超出“把字段填对”范畴的一类问题：Linux 在海光和 AMD Zen1 上直接用 `llc_id = apicid >> 3`，完全不看 CPUID 报的缓存共享关系，`--smp 16` 时 LLC 域被切成 `0-7` 和 `8-15` 两块，而 mini-vmm 在 CPUID 里报的是 16 颗共享。Zen2 之后的 AMD 按 0x8000001D 的共享线程数算，没有这个问题。各家 CPU 上都有这类写死的捷径，做 CPU 模型时必须逐条排查。

**四条来自本卷核对过程的改进，都已经实现：**

1. `--smp` 大于 8 且 host 是海光或 AMD Zen1 时打印一行提示，说明 guest 会把 LLC 域按 APIC ID 的第 3 位切开（7.3 节）。这不是错误，但会让基于 mini-vmm 做调度实验的人少走弯路。实现是 `src/smp.c:151` 的 `smp_warn_llc_split()`，由 `vm_run()` 调用一次。
2. `vcpu_run_loop()` 收到 `VMM_ERR_INTR` 时，以 debug 日志级别打印一次 `KVM_GET_MP_STATE`（11.1 节）。这条路径每个 vCPU 在整个生命周期里只会走几次，开销可以忽略，但对排查 AP 不启动非常有用——加上 `-v` 就能直接看到三颗 AP 被 INIT 唤醒的那一跳和它们读到的状态。新增 `kvm_get_mp_state()` 与 `kvm_mp_state_str()` 两个封装。
3. `tests/e2e/smp.sh` 有一条 `SMP_MANY`（默认 16）的用例，覆盖并行启动下多个 AP 争跳板锁的路径，并按 VMM 是否发出 LLC 警告分支断言 LLC 域；guest 里的 `cpuidprobe` 逐颗核对 VMM 交出的原始 CPUID 拓扑字段，`tests/mutants/smp.py` 的 11 个变异体证明这些断言挡得住拓扑字段填错（11.5 节）。
4. CPUID 叶 0xB 补齐三个子叶（7.3 节）。KVM 只给子叶 0，追加条目需要数组有空位：`kvm_get_supported_cpuid()` 多申请 `KVM_CPUID_SPARE` 条但只向 KVM 声明较小的 `nent`，末尾就留出了可追加的空位。补齐之后 AMD/海光 guest 的解析结果与 `0x80000008` + `0x8000001E` 那条路相同，而 Intel guest 将来不必再退回更难填对的 `parse_legacy()` 路径。0x1F 仍然整体清零。

**卷七回到设备。** 本卷和卷五让 guest 认识了这台机器并把所有 CPU 跑了起来，但 guest 看到的“设备”一直是被当作黑盒对待的。卷七将逐寄存器追踪 Linux 驱动的探测序列：8250 的 `autoconfig()` 怎样靠一串读写认出 16550A、`quick_pit_calibrate()` 与 `pit_calibrate_tsc()` 各自读了 PIT 的哪几个字节、CMOS RTC 的 UIP 位与 BCD 编码、i8042 的自检与 AUX 判定，以及 `reboot=k` 与 ACPI S5 这两条关机/重启路径在寄存器层面分别做了什么。核心命题是：**设备要模拟到什么程度，由驱动的探测逻辑决定，而不是由芯片手册决定。**
