# 卷一：AMD SVM 世界切换的微架构与内核实现

## 1. SVM 的开启：三个 MSR 与一块物理黑盒

### 1.1 能力探测

SVM 的存在性通过 `CPUID Fn8000_0001_ECX[SVM]`（bit 2）报告，扩展能力通过 `CPUID Fn8000_000A` 报告。后者的四个寄存器给出了这颗 CPU 支持的具体特性集：

- `EAX` = SVM revision number
- `EBX` = **可用 ASID 数量**（这个值直接决定了单台物理机能同时跑多少个地址空间不冲突的 Guest）
- `EDX` = 特性位图，包括 `NP`（Nested Paging，bit 0）、`NRIP`（NRIP Save，bit 3）、`DecodeAssists`（bit 7）、`AVIC`（bit 13）、`V_VMSAVE_VMLOAD`（bit 15）等

KVM 在 `svm_hardware_setup()` 里读这些位来决定运行策略：

```c
/* arch/x86/kvm/svm/svm.c，节选 */
sd->max_asid = cpuid_ebx(SVM_CPUID_FUNC) - 1;   /* SVM_CPUID_FUNC = 0x8000000A */
...
if (nrips) {
    if (!boot_cpu_has(X86_FEATURE_NRIPS))
        nrips = false;
}
kvm_configure_mmu(npt_enabled, get_max_npt_level(), ...);
```

除此之外还有一个容易被忽略的开关：**`VM_CR` MSR（`0xC001_0114`）的 `SVMDIS` 位（bit 4）**。很多 OEM 主板的 BIOS 在"Virtualization = Disabled"时并不是不上报 CPUID，而是置上这一位并锁死。此时 `CPUID` 仍然报告 SVM 可用，但写 `EFER.SVME` 会产生 `#GP`。KVM 的 `is_disabled()` 就是在检查这个：

```c
static int is_disabled(void)
{
    u64 vm_cr;
    rdmsrl(MSR_VM_CR, vm_cr);
    if (vm_cr & (1 << SVM_VM_CR_SVM_DISABLE))
        return 1;
    return 0;
}
```

诊断 "kvm_amd: SVM disabled by BIOS" 这类问题时，看的就是这一位。

### 1.2 `EFER.SVME`：全局使能

真正打开硬件状态机的是 `EFER`（`0xC000_0080`）的 bit 12，`SVME`。置位之前，`VMRUN`、`VMLOAD`、`VMSAVE`、`CLGI`、`STGI`、`INVLPGA`、`VMMCALL` 这些指令一律 `#UD`。

注意这是**每颗物理核**的状态，不是每虚拟机的。KVM 在 `svm_hardware_enable()` 里对每个 online CPU 各执行一次，这个函数会在模块加载和 CPU 热插拔时被调用。

### 1.3 `MSR_VM_HSAVE_PA`：世界切换的不对称性所在

这是理解 AMD 世界切换最关键的一个点，也是绝大多数中文资料一笔带过的地方。

一次 `VMRUN` 需要处理两个方向的状态：**Guest 状态从哪来**、**Host 状态存到哪去**。前者的答案是 VMCB——`VMRUN` 的隐式操作数 `RAX` 指向 VMCB 的物理地址。但 Host 状态**不存进 VMCB**，而是存进另一块完全独立的物理内存，其地址由 MSR `0xC001_0117`（`MSR_VM_HSAVE_PA`）指定。

```c
/* svm_hardware_enable()，arch/x86/kvm/svm/svm.c:507 */
wrmsrl(MSR_EFER, efer | EFER_SVME);
wrmsrl(MSR_VM_HSAVE_PA, __sme_page_pa(sd->save_area));
```

`sd` 是 `struct svm_cpu_data`，**每物理 CPU 一份**；`sd->save_area` 是一个 4 KB 页，在 `svm_cpu_init()` 里用 `alloc_page()` 分配。

于是形成了这样一个不对称结构：

```
                每颗物理 CPU                        每个 vCPU
        ┌─────────────────────────┐        ┌─────────────────────────┐
        │  sd->save_area (4KB)    │        │   VMCB (4KB)            │
        │  ─────────────────────  │        │  ─────────────────────  │
        │  Host 状态              │        │  Control Area  (0x000)  │
        │  由 VMRUN 自动写入       │        │  Save Area     (0x400)  │
        │  由 #VMEXIT 自动读回     │        │  Guest 状态             │
        └─────────────────────────┘        └─────────────────────────┘
                 ▲                                    ▲
                 │ 地址来自                            │ 地址来自
        MSR_VM_HSAVE_PA (0xC0010117)           VMRUN 的 RAX 操作数
```

**`VMRUN` 自动保存的 Host 状态**（APM Vol.2 §15.5.1）是一个精心裁剪过的子集：`ES.sel`、`CS.sel`、`SS.sel`、`DS.sel`、`GDTR`、`IDTR`、`EFER`、`CR0`、`CR4`、`CR3`、`RFLAGS`、`RIP`、`RSP`、`RAX`。`#VMEXIT` 时硬件从同一块内存自动恢复它们。

**没有被自动保存的**是：`FS`、`GS`、`TR`、`LDTR` 的完整隐藏状态，以及 `KernelGSBase`、`STAR`/`LSTAR`/`CSTAR`/`SFMASK`、`SYSENTER_CS/ESP/EIP` 这一组 MSR。这些在 Linux 内核里全都是活跃状态——`GS` 基址就是 per-CPU 变量的锚点，`LSTAR` 是 `syscall` 入口。如果 Guest 修改了它们而 Host 没恢复，返回内核的第一条 `syscall` 就会跳飞。

AMD 给的解决方案是两条专用指令：`VMSAVE` 和 `VMLOAD`，它们以 VMCB 格式的内存页为操作数，专门搬运这个"VMRUN 不管"的子集。KVM 的用法非常精确：

```c
/* svm_prepare_guest_switch()，arch/x86/kvm/svm/svm.c:1447 */
/* 把 Host 的 FS/GS/TR/LDTR/SYSCALL MSR 存进 per-CPU 页 */
vmsave(__sme_page_pa(sd->save_area));

/* svm_vcpu_enter_exit()，arch/x86/kvm/svm/svm.c:3745 */
vmload(svm->vmcb01.pa);                    /* 装入 Guest 的这组状态 */
__svm_vcpu_run(vmcb_pa, (unsigned long *)&vcpu->arch.regs);
vmsave(svm->vmcb01.pa);                    /* 存回 Guest 的这组状态 */
vmload(__sme_page_pa(sd->save_area));      /* 恢复 Host 的这组状态 */
```

注意 `sd->save_area` 这一页承担了**双重角色**：既是 `VMRUN`/`#VMEXIT` 自动读写的 Host Save Area，又是 `VMSAVE`/`VMLOAD` 手工搬运 Host 补充状态的目标。两者写的是同一页的不同偏移区间，互不冲突——因为 Host Save Area 本身就采用 VMCB Save Area 的布局。

还要注意 `vmcb01`。在嵌套虚拟化（Guest 里再跑 Hypervisor）场景下，KVM 会在 `vmcb01`（给 L1 用）和 `vmcb02`（给 L2 用）之间来回切换。代码里刻意用**始终有效的 `vmcb01`** 作为 `VMSAVE`/`VMLOAD` 的落点，这样切换 VMCB 时不需要把这组状态在两个 VMCB 之间搬来搬去。源码里的注释写得很直白：

```c
/*
 * Use a single vmcb (vmcb01 because it's always valid) for
 * context switching guest state via VMLOAD/VMSAVE, that way
 * the state doesn't need to be copied between vmcb01 and
 * vmcb02 when switching vmcbs for nested virtualization.
 */
```

**为什么硬件要设计成这种不对称结构？** 因为 Host 状态在两次 `VMRUN` 之间是高度稳定的（同一颗物理核上的 Linux 内核，`GDTR`/`IDTR`/`CR4`/`EFER` 几乎不变），而 Guest 状态是每个 vCPU 独立的、需要被 Hypervisor 频繁读写的。把 Host 状态放进一块"软件基本不需要碰"的 per-CPU 黑盒，把 Guest 状态放进一块"软件必须随意读写"的 per-vCPU 结构体，各自优化到位。这也解释了为什么 VMCB 的格式是公开的而 Host Save Area 的格式在 APM 里只说"与 VMCB Save Area 相同布局"却不鼓励软件直接访问。

Intel 在这一点上做了相反的选择：VMCS 里同时有 **Guest-State Area** 和 **Host-State Area**，Host 状态由软件在 `VMCLEAR`/`VMPTRLD` 之后用 `VMWRITE` 显式填好，硬件在 VM-Exit 时从 VMCS 恢复。代价是每次迁移 vCPU 到新物理核都要重写一遍 Host-State Area，收益是不需要额外一个 MSR 和一块 per-CPU 内存。

## 2. VMCB 字段级拆解

`struct vmcb` 定义在 `arch/x86/include/asm/svm.h`：

```c
struct vmcb {
    struct vmcb_control_area control;   /* offset 0x000 */
    struct vmcb_save_area    save;      /* offset 0x400 */
} __packed;
```

`__packed` 不是装饰。这个结构体的每个字段偏移都由硬件规范固定，编译器插入任何填充都会导致硬件读到错误位置。同文件里还有一组编译期断言强制校验：

```c
static inline void __unused_size_checks(void)
{
    BUILD_BUG_ON(sizeof(struct vmcb_save_area)    != EXPECTED_VMCB_SAVE_AREA_SIZE);
    BUILD_BUG_ON(sizeof(struct vmcb_control_area) != EXPECTED_VMCB_CONTROL_AREA_SIZE);
}
```

### 2.1 控制区完整声明

```c
struct __attribute__ ((__packed__)) vmcb_control_area {
    u32 intercepts[MAX_INTERCEPT];      /* 0x000: 6 个 32 位拦截字 */
    u32 reserved_1[15 - MAX_INTERCEPT];
    u16 pause_filter_thresh;            /* 0x03C */
    u16 pause_filter_count;
    u64 iopm_base_pa;                   /* 0x040: I/O 权限位图物理地址 */
    u64 msrpm_base_pa;                  /* 0x048: MSR 权限位图物理地址 */
    u64 tsc_offset;                     /* 0x050: TSC 偏移，用于时间虚拟化 */
    u32 asid;                           /* 0x058: 地址空间标识符 */
    u8  tlb_ctl;                        /* 0x05C: TLB 刷新控制 */
    u8  reserved_2[3];
    u32 int_ctl;                        /* 0x060: 虚拟中断控制 */
    u32 int_vector;
    u32 int_state;
    u8  reserved_3[4];
    u32 exit_code;                      /* 0x070: ← 硬件写 */
    u32 exit_code_hi;
    u64 exit_info_1;                    /* 0x078: ← 硬件写 */
    u64 exit_info_2;                    /* 0x080: ← 硬件写 */
    u32 exit_int_info;                  /* 0x088: ← 硬件写 */
    u32 exit_int_info_err;
    u64 nested_ctl;                     /* 0x090: bit0 = NP_ENABLE */
    u64 avic_vapic_bar;
    u64 ghcb_gpa;
    u32 event_inj;                      /* 0x0A8: 事件注入 */
    u32 event_inj_err;
    u64 nested_cr3;                     /* 0x0B0: NPT 根表 HPA */
    u64 virt_ext;
    u32 clean;                          /* 0x0C0: Clean Bits */
    u32 reserved_5;
    u64 next_rip;                       /* 0x0C8: ← 硬件写（需 NRIP 特性） */
    u8  insn_len;                       /* 0x0D0: ← 硬件写（需 DecodeAssists） */
    u8  insn_bytes[15];                 /* 0x0D1: ← 硬件写（需 DecodeAssists） */
    u64 avic_backing_page;              /* 0x0E0 */
    ...
    u8  reserved_sw[32];                /* 0x3E0: 规范保留给 Hypervisor 自用 */
};
```

几个值得注意的地方：

**`next_rip` 和 `insn_bytes[15]` 是硬件解码辅助。** 这两个字段的存在，直接决定了 AMD 侧 KVM 的代码路径比 Intel 侧短得多，详见本文第 6 节。

**`reserved_sw[32]`** 是规范明确划给 Hypervisor 自用的 32 字节。硬件保证不碰它，软件可以在里面放任何私有数据。这是一个体现"硬件规范为软件留后门"的设计细节。

**`nested_ctl` bit 0 是 NPT 总开关**，`nested_cr3` 是二级页表根的 Host 物理地址。KVM 在 `svm_load_mmu_pgd()` 里写它：

```c
if (npt_enabled) {
    svm->vmcb->control.nested_cr3 = __sme_set(root_hpa);
    vmcb_mark_dirty(svm->vmcb, VMCB_NPT);
    ...
}
```

`__sme_set()` 是 AMD SME（Secure Memory Encryption）相关的宏，在开启内存加密时给物理地址补上加密位。所有写入 VMCB 的物理地址都要经过它——这是移植 AMD 平台代码时容易漏掉的一环。

### 2.2 状态保存区：偏移就是硬件契约

```c
struct vmcb_save_area {
    struct vmcb_seg es, cs, ss, ds, fs, gs;
    struct vmcb_seg gdtr, ldtr, idtr, tr;
    u8  reserved_1[43];
    u8  cpl;                    /* 0x0CB */
    u8  reserved_2[4];
    u64 efer;                   /* 0x0D0 */
    u8  reserved_3[104];
    u64 xss;
    u64 cr4;                    /* 0x148 */
    u64 cr3;
    u64 cr0;
    u64 dr7;
    u64 dr6;
    u64 rflags;                 /* 0x170 */
    u64 rip;                    /* 0x178 */
    u8  reserved_4[88];
    u64 rsp;                    /* 0x1D8 */
    u8  reserved_5[24];
    u64 rax;                    /* 0x1F8 */
    u64 star, lstar, cstar, sfmask, kernel_gs_base;
    u64 sysenter_cs, sysenter_esp, sysenter_eip;
    u64 cr2;
    ...
};
```

那些 `reserved_N[...]` 数组不是浪费——它们是为了让后面每个字段的偏移精确匹配 APM 表 B-2。`rsp` 在 0x1D8、`rax` 在 0x1F8 之间隔着 24 字节保留区，这个空洞是硬件规定的，不能压缩。

`struct vmcb_seg` 是段描述符的缓存形态：

```c
struct vmcb_seg {
    u16 selector;
    u16 attrib;      /* 属性位，注意是压缩格式 */
    u32 limit;
    u64 base;
};
```

**`attrib` 字段的编码是一个实践中的坑。** 它不是段描述符里那 16 位属性的原样拷贝，而是把 descriptor 高 32 位中的 type/S/DPL/P 和 AVL/L/D/G 两段**拼接压缩**成 12 位：低 8 位是 `type[3:0] | S<<4 | DPL<<5 | P<<7`，高 4 位是 `AVL | L | D | G`。所以 `svm.h` 里那组 `SVM_SELECTOR_*_SHIFT` 宏跟 x86 段描述符原始布局对不上：

```c
#define SVM_SELECTOR_S_SHIFT    4
#define SVM_SELECTOR_DPL_SHIFT  5
#define SVM_SELECTOR_P_SHIFT    7
#define SVM_SELECTOR_AVL_SHIFT  8
#define SVM_SELECTOR_L_SHIFT    9
#define SVM_SELECTOR_DB_SHIFT   10
#define SVM_SELECTOR_G_SHIFT    11
```

自己构造 `struct kvm_sregs` 时如果按 GDT 描述符的原始位序填，会得到一个属性错乱但不报错的段——直到 Guest 第一次跨段跳转才崩。**始终用 `KVM_GET_SREGS` 读出来再改**，是唯一安全的做法。

### 2.3 通用寄存器为什么不在里面

Save Area 里通用寄存器只有 `RAX` 一个，`RSP` 也在（因为它决定栈），其余 14 个全部缺席。SEV-ES 场景下 `struct vmcb_save_area` 尾部确实有 `rcx`/`rdx`/`rbx`/`rbp`/`rsi`/`rdi`/`r8`–`r15`，但那是给加密虚拟机用的（Guest 状态被加密后 Hypervisor 无法访问寄存器，只能靠硬件全量保存），普通路径不用。

这个取舍的量化理由：x86-64 的 16 个 GPR 全量保存/恢复是 256 字节的读 + 256 字节的写。世界切换在负载虚拟机上每秒发生数万次，把它压进硬件微码意味着每次都付这个代价，且软件无法优化。交给软件之后，Hypervisor 可以：

- 在某些快速路径上只保存实际用到的寄存器；
- 利用编译器已知的 ABI，把调用者保存寄存器留在栈上；
- 在退出后立即清零，防止 Guest 值被投机执行泄漏（见第 4 节）。

Intel 做了完全相同的选择。这不是巧合，是同一个成本模型下的同一个最优解。



## 3. 拦截配置：三层位图的物理布局

### 3.1 `intercepts[6]`：位标志

```c
enum intercept_words {
    INTERCEPT_CR = 0,       /* word 0: CR0-15 读 (bit 0-15) / 写 (bit 16-31) */
    INTERCEPT_DR,           /* word 1: DR0-15 读写 */
    INTERCEPT_EXCEPTION,    /* word 2: 32 个异常向量 */
    INTERCEPT_WORD3,        /* word 3: INTR/NMI/SMI/CPUID/IOIO/MSR/... */
    INTERCEPT_WORD4,        /* word 4: VMRUN/VMMCALL/MONITOR/XSETBV/... */
    INTERCEPT_WORD5,        /* word 5: INVLPGB/INVPCID/MCOMMIT/TLBSYNC */
    MAX_INTERCEPT,
};
```

位编号是**全局连续**的，跨越 word 边界：

```c
enum {
    /* word 0，byte offset 0x000 */
    INTERCEPT_CR0_READ  = 0,
    INTERCEPT_CR3_READ  = 3,
    INTERCEPT_CR0_WRITE = 16,
    INTERCEPT_CR3_WRITE = 16 + 3,
    /* word 2，byte offset 0x008 */
    INTERCEPT_EXCEPTION_OFFSET = 64,     /* 异常向量 N → bit 64+N */
    /* word 3，byte offset 0x00C */
    INTERCEPT_INTR = 96,
    INTERCEPT_NMI,
    INTERCEPT_SMI,
    INTERCEPT_INIT,
    INTERCEPT_VINTR,
    INTERCEPT_SELECTIVE_CR0,
    INTERCEPT_STORE_IDTR,       /* ← 注意这个 */
    INTERCEPT_STORE_GDTR,
    ...
    INTERCEPT_IOIO_PROT,
    INTERCEPT_MSR_PROT,
    ...
    /* word 4，byte offset 0x010 */
    INTERCEPT_VMRUN = 128,
    INTERCEPT_VMMCALL,
    ...
};
```

`INTERCEPT_STORE_IDTR` / `INTERCEPT_STORE_GDTR` 值得特别指出：这正是第一节提到的 Popek-Goldberg 缺陷指令 `sidt`/`sgdt`。硬件虚拟化把"这条指令要不要陷出"变成了一个可编程的位，缺陷就此消失。KVM 默认**不**拦截它们（Guest 有自己的 IDTR/GDTR 在 VMCB 里，读到的本来就是正确值，没必要陷）；只有嵌套虚拟化等特殊场景才需要。

设置接口是 `svm_set_intercept()`，它同时会清 clean bit：

```c
static inline void vmcb_set_intercept(struct vmcb_control_area *control, u32 bit)
{
    WARN_ON_ONCE(bit >= 32 * MAX_INTERCEPT);
    __set_bit(bit, (unsigned long *)&control->intercepts);
}
```

### 3.2 IOPM：12 KB 的三页布局与边界溢出

x86 有 65536 个 I/O 端口，每端口一位需要 8192 字节。但 APM 规定 `iopm_base_pa` 指向的区域必须是**连续的 3 个 4 KB 物理页，共 12 KB**：

```
   IOPM (12 KB，物理连续)
   ┌────────────────────────────────────────┐ +0x0000
   │  Page 0                                │
   │  端口 0x0000 - 0x7FFF                   │
   │  32768 个端口 × 1 bit = 4096 字节        │
   ├────────────────────────────────────────┤ +0x1000
   │  Page 1                                │
   │  端口 0x8000 - 0xFFFF                   │
   │  32768 个端口 × 1 bit = 4096 字节        │
   ├────────────────────────────────────────┤ +0x2000
   │  Page 2                                │
   │  硬件规范要求存在，KVM 全部填 1           │
   │  用于宽访问跨越 0xFFFF 边界时的越界读取   │
   └────────────────────────────────────────┘ +0x3000
```

**第三页存在的微架构原因**：I/O 指令的宽度可以是 1、2、4 字节。当 Guest 执行 `in eax, dx` 且 `DX = 0xFFFF` 时，这次访问在语义上覆盖端口 `0xFFFF`、`0x10000`、`0x10001`、`0x10002`——后三个已经超出 16 位端口空间。硬件在检查权限时必须读取位图中**连续的若干位**来判定这次访问是否全部放行。如果位图只有 8 KB，硬件在检查端口 `0xFFFF` 之后的位时会读到位图之外的物理内存——那可能是另一个进程的数据页，也可能是未映射区域。加一页填满 1 的缓冲区，硬件读到的永远是"拦截"，既不越界也语义正确。

这是一个典型的"用内存换取硬件逻辑简化"的设计：与其在微码里加边界判断，不如要求软件多分配一页。

KVM 的策略是全部拦截：

```c
/* svm_hardware_setup()，arch/x86/kvm/svm/svm.c:963 */
unsigned int order = get_order(IOPM_SIZE);       /* IOPM_SIZE = PAGE_SIZE * 3 */
iopm_pages = alloc_pages(GFP_KERNEL, order);
iopm_va = page_address(iopm_pages);
memset(iopm_va, 0xff, PAGE_SIZE * (1 << order));
iopm_base = page_to_pfn(iopm_pages) << PAGE_SHIFT;
```

注意 `get_order(12 KB)` 返回 2，即实际分配 16 KB（伙伴系统只能分配 2 的幂次）。多出的 4 KB 一并填 `0xff`，无害。

而且这块 IOPM 是**全局唯一的**——所有虚拟机、所有 vCPU 共享同一个 `iopm_base`。因为策略是"全拦"，没有任何 per-VM 差异，不需要每台虚拟机各分配一份。

### 3.3 MSRPM：8 KB，两位一个 MSR，三段不连续

MSR 编号空间是 32 位，不可能给每个都留位。APM 定义 MSRPM 只覆盖三个实际使用的区间，每个 MSR 占**两位**（bit 0 = 读拦截，bit 1 = 写拦截）：

```
   MSRPM (8 KB = 2 页)
   ┌────────────────────────────────────────┐ +0x0000
   │  Vector 0: MSR 0x0000_0000 - 0x0000_1FFF│  2048 字节
   ├────────────────────────────────────────┤ +0x0800
   │  Vector 1: MSR 0xC000_0000 - 0xC000_1FFF│  2048 字节  ← SYSCALL 相关
   ├────────────────────────────────────────┤ +0x1000
   │  Vector 2: MSR 0xC001_0000 - 0xC001_1FFF│  2048 字节  ← AMD 专有
   ├────────────────────────────────────────┤ +0x1800
   │  保留                                   │
   └────────────────────────────────────────┘ +0x2000
```

不在这三段里的 MSR 一律无条件拦截。KVM 维护了一张 `direct_access_msrs[]` 表，列出哪些 MSR 可以直通给 Guest（比如 `MSR_STAR`、`MSR_LSTAR`、`MSR_FS_BASE`、`MSR_GS_BASE`），其余全拦。直通这些 MSR 的收益很直接：Guest 内核每次 `syscall` 返回、每次线程切换写 `FS_BASE`，都不会产生 `#VMEXIT`。

`msrpm_offsets[16]` 数组缓存了这些直通 MSR 在位图里的字偏移，用于嵌套虚拟化时快速合并 L1 和 L2 的位图。

### 3.4 Clean Bits：反向语义的性能优化

```c
/* arch/x86/kvm/svm/svm.h */
enum {
    VMCB_INTERCEPTS,  /* 拦截向量、TSC offset、pause filter count */
    VMCB_PERM_MAP,    /* IOPM Base 和 MSRPM Base */
    VMCB_ASID,
    VMCB_INTR,        /* int_ctl, int_vector */
    VMCB_NPT,         /* npt_en, nCR3, gPAT */
    VMCB_CR,          /* CR0, CR3, CR4, EFER */
    VMCB_DR,
    VMCB_DT,          /* GDT, IDT */
    VMCB_SEG,         /* CS, DS, SS, ES, CPL */
    VMCB_CR2,
    VMCB_LBR,
    VMCB_AVIC,
    VMCB_SW = 31,     /* 保留给软件 */
};

#define VMCB_ALWAYS_DIRTY_MASK ((1U << VMCB_INTR) | (1U << VMCB_CR2))
```

语义是：`clean` 位掩码中某位为 **1** 表示"这类字段自上次 `VMRUN` 以来软件没有改过，硬件可以复用内部缓存"。所以软件修改任何字段后必须**清掉**对应位：

```c
static inline void vmcb_mark_dirty(struct vmcb *vmcb, int bit)
{
    vmcb->control.clean &= ~(1 << bit);
}
```

`VMCB_ALWAYS_DIRTY_MASK` 里的两项（`int_ctl`/`int_vector` 和 `CR2`）在每次 `VMRUN` 前都会被写，所以干脆永远标记为脏，省掉判断。

**这个机制有两个陷阱。**

第一，**忘记调用 `vmcb_mark_dirty()` 的后果是静默的**。你改了 `save.cr3`，但没清 `VMCB_CR` 位，硬件会用流水线里的旧 `CR3` 跑 Guest，不报任何错，只是 Guest 行为诡异。这类 bug 极难定位。

第二，**Clean Bits 的缓存是 per-物理-CPU 的**。同一个 VMCB 迁移到另一颗物理核上运行时，新核的流水线里根本没有这个 VMCB 的缓存，此时如果 `clean` 还是全 1，硬件行为未定义。KVM 在 `pre_svm_run()` 里处理了这一点：

```c
static void pre_svm_run(struct kvm_vcpu *vcpu)
{
    struct svm_cpu_data *sd = per_cpu(svm_data, vcpu->cpu);
    struct vcpu_svm *svm = to_svm(vcpu);

    /*
     * If the previous vmrun of the vmcb occurred on a different physical
     * cpu, then mark the vmcb dirty and assign a new asid.  Hardware's
     * vmcb clean bits are per logical CPU, as are KVM's asid assignments.
     */
    if (unlikely(svm->current_vmcb->cpu != vcpu->cpu)) {
        svm->current_vmcb->asid_generation = 0;
        vmcb_mark_all_dirty(svm->vmcb);
        svm->current_vmcb->cpu = vcpu->cpu;
    }
    ...
}
```

一句话：**vCPU 线程被 Linux 调度器迁移到另一颗核，整个 VMCB 就全部标脏、ASID 重新分配。** 这是虚拟化场景下 vCPU 亲和性绑定（pinning）能带来性能收益的微架构层面原因之一。



## 4. 世界切换：汇编、中断窗口与投机防御

### 4.1 `__svm_vcpu_run` 的真实形态

Linux 5.15 的 `arch/x86/kvm/svm/vmenter.S`，函数签名是 `__svm_vcpu_run(unsigned long vmcb_pa, unsigned long *regs)` 两个参数。下面是剥掉 32 位分支后的完整逻辑：

```asm
SYM_FUNC_START(__svm_vcpu_run)
    /* ARG1 = %rdi = vmcb_pa,  ARG2 = %rsi = regs */

    /* 1. 保存 Host 的被调用者保存寄存器 */
    push %rbp
    push %r15
    push %r14
    push %r13
    push %r12
    push %rbx

    push %rsi                       /* 栈上暂存 @regs */
    push %rdi                       /* 栈上暂存 @vmcb_pa */

    mov  %rsi, %rax                 /* RAX = regs 指针 */

    /* 2. 从 vcpu->arch.regs[] 装入 Guest 通用寄存器 */
    mov VCPU_RCX(%rax), %rcx
    mov VCPU_RDX(%rax), %rdx
    mov VCPU_RBX(%rax), %rbx
    mov VCPU_RBP(%rax), %rbp
    mov VCPU_RSI(%rax), %rsi
    mov VCPU_RDI(%rax), %rdi
    mov VCPU_R8 (%rax), %r8
    ...
    mov VCPU_R15(%rax), %r15

    pop %rax                        /* RAX = vmcb_pa，VMRUN 的隐式操作数 */

    /* 3. 进入 Guest */
    sti
1:  vmrun %rax
2:  cli

#ifdef CONFIG_RETPOLINE
    /* 关键：VM-Exit 后、任何 ret 之前，立刻填充返回栈缓冲区 */
    FILL_RETURN_BUFFER %rax, RSB_CLEAR_LOOPS, X86_FEATURE_RETPOLINE
#endif

    pop %rax                        /* RAX = regs 指针 */

    /* 4. 把 Guest 通用寄存器存回 vcpu->arch.regs[] */
    mov %rcx, VCPU_RCX(%rax)
    ...
    mov %r15, VCPU_R15(%rax)

    /* 5. 清零所有 GPR，防止 Guest 值被投机使用 */
    xor %ecx, %ecx
    xor %edx, %edx
    xor %ebx, %ebx
    xor %ebp, %ebp
    xor %esi, %esi
    xor %edi, %edi
    xor %r8d, %r8d
    ...
    xor %r15d, %r15d

    /* 6. 恢复 Host 寄存器 */
    pop %rbx
    pop %r12
    pop %r13
    pop %r14
    pop %r15
    pop %rbp
    ret

3:  cmpb $0, kvm_rebooting          /* VMRUN 本身出错的异常处理 */
    jne 2b
    ud2
    _ASM_EXTABLE(1b, 3b)
SYM_FUNC_END(__svm_vcpu_run)
```

有四个细节值得展开。

**`sti` / `cli` 包住 `vmrun`。** 这看起来很反直觉——刚要进 Guest 却把中断打开？原因是 `VMRUN` 的语义：进入 Guest 模式时，Host 的 `RFLAGS.IF` 值会被保存起来，Guest 用的是 VMCB 里的 `RFLAGS`。而 `INTERCEPT_INTR` 被置位意味着物理中断到达时会立刻产生 `#VMEXIT`。这里 `sti` 的作用是让 `VMRUN` 之后、`#VMEXIT` 返回之时，Host 能够立即响应那个把它踢出来的物理中断——`sti` 的效果被推迟到下一条指令之后生效，恰好覆盖 `vmrun`。而 `cli` 紧接在 `vmrun` 之后，保证退出后回到 C 代码时中断仍是关的，由 `svm_vcpu_run()` 的更外层统一管理开中断时机。

**`FILL_RETURN_BUFFER` 的位置是安全关键。** 注释写得很重："IMPORTANT: Stuff the RSB immediately after VM-Exit, before RET!" Guest 可以污染 CPU 的返回栈缓冲区（Return Stack Buffer），如果退出后 Host 直接执行 `ret`，分支预测器可能沿着 Guest 投毒的地址投机执行 Host 代码——这是 Spectre-v2 的一个变种。必须在任何 `ret` 之前把 RSB 用已知安全的地址填满。

**GPR 清零** 同理：即使这些寄存器马上要被 `pop` 覆盖，L1 缓存缺失导致的延迟窗口里，投机执行仍可能用到 Guest 留下的值。注释里说 "Zeroing XORs are dirt cheap"——用几条零成本指令换掉一整类侧信道。

**`_ASM_EXTABLE(1b, 3b)`** 给 `vmrun` 指令本身挂了异常表项。`VMRUN` 在 VMCB 物理地址非法、`EFER.SVME` 被清等情况下会 `#GP`。正常情况下这是内核 bug，直接 `ud2`；但如果系统正在 `kvm_rebooting`（紧急重启路径上 KVM 已经关闭了 SVM），就静默跳过。

### 4.2 `clgi` / `stgi` 与 `cli` 的三层级联

上面的汇编里没有 `clgi`/`stgi`——它们在 C 语言层。5.15 的实际排布是：

```c
static __no_kcsan fastpath_t svm_vcpu_run(struct kvm_vcpu *vcpu)
{
    ...
    clgi();                                 /* svm.c:3804 —— 关闭 GIF */
    kvm_load_guest_xsave_state(vcpu);
    kvm_wait_lapic_expire(vcpu);
    x86_spec_ctrl_set_guest(...);

    svm_vcpu_enter_exit(vcpu);              /* 里面才是 vmload/__svm_vcpu_run/vmsave */

    x86_spec_ctrl_restore_host(...);
    reload_tss(vcpu);

    vcpu->arch.regs[VCPU_REGS_RAX] = svm->vmcb->save.rax;
    vcpu->arch.regs[VCPU_REGS_RSP] = svm->vmcb->save.rsp;
    vcpu->arch.regs[VCPU_REGS_RIP] = svm->vmcb->save.rip;

    if (unlikely(svm->vmcb->control.exit_code == SVM_EXIT_NMI))
        kvm_before_interrupt(vcpu);

    kvm_load_host_xsave_state(vcpu);
    stgi();                                 /* svm.c:3856 —— 打开 GIF */

    /* Any pending NMI will happen here */

    if (unlikely(svm->vmcb->control.exit_code == SVM_EXIT_NMI))
        kvm_after_interrupt(vcpu);
    ...
}
```

于是形成三层中断控制的级联：

```
   时间轴 ──────────────────────────────────────────────────────────►

   vcpu_enter_guest()
     │
     ├─ local_irq_disable()          第 1 层：RFLAGS.IF = 0
     │                               屏蔽：可屏蔽中断（INTR）
     │                               不屏蔽：NMI、SMI、MCE
     │
     ├─ svm_vcpu_run()
     │    │
     │    ├─ clgi()                  第 2 层：GIF = 0
     │    │                          屏蔽：INTR + NMI + SMI + INIT
     │    │                          ← 危险窗口从这里开始被封死
     │    │
     │    ├─ vmload(vmcb01)          装入 Guest 的 FS/GS/TR/LDTR
     │    ├─ __svm_vcpu_run()
     │    │    ├─ 装入 15 个 Guest GPR   ← 此刻 CPU 寄存器已是 Guest 的
     │    │    ├─ sti                    ← 第 3 层：仅为让退出后能立即响应
     │    │    ├─ vmrun ═══════════════ Guest 执行 ═══════════════
     │    │    ├─ cli
     │    │    └─ 存回 15 个 Guest GPR，清零，恢复 Host GPR
     │    ├─ vmsave(vmcb01)
     │    ├─ vmload(sd->save_area)   恢复 Host 的 FS/GS/TR/LDTR
     │    │
     │    ├─ stgi()                  GIF = 1
     │    │                          ← 之前被推迟的 NMI 在这一刻集中到达
     │    │                          ← 但 RFLAGS.IF 仍为 0，INTR 还在等
     │    │
     │    └─ return
     │
     ├─ ... 处理退出、判断是否需要退回用户态 ...
     │
     └─ local_irq_enable()           RFLAGS.IF = 1，普通中断放行
```

**为什么 `cli` 不够、必须要 `clgi`？** 因为在 `local_irq_disable()` 之后、`vmrun` 之前的这段代码里，CPU 的通用寄存器正在被逐个替换成 Guest 的值，`FS`/`GS` 基址也已经通过 `vmload` 换成了 Guest 的。此时若发生 NMI（性能计数器溢出、看门狗、IPI-NMI 都会产生），CPU 会跳进 Host 的 NMI 处理程序，而该程序会用 `swapgs`/per-CPU 变量——但 `GS` 基址已经是 Guest 的了，per-CPU 访问会落到完全错误的地址上。`clgi` 把 NMI/SMI 一并推迟到 `stgi` 之后，彻底消除这个窗口。

Intel 没有对应指令，它靠另一套机制：VM-Exit 时硬件自动把 NMI 置于 "blocked by NMI" 状态，由软件在合适时机通过执行 `iret` 或写 VMCS 字段解除。两条路径解决同一个问题，但 AMD 的方案对软件更透明。

**`stgi()` 前后那两行 `kvm_before_interrupt` / `kvm_after_interrupt` 是精确的**：如果这次退出的原因就是 NMI（`SVM_EXIT_NMI`），那么这个 NMI 在 `stgi()` 执行的瞬间会被投递给 Host 的处理程序。这两个调用给 KVM 的 NMI 处理逻辑设了一个标记窗口，让内核知道"此刻收到的 NMI 来自刚退出的 Guest"。

## 5. `VMRUN` 的微架构语义与一致性检查

`VMRUN` 不是一条普通指令，它在微码层面完成一个多步骤的原子事务：

```
   VMRUN %rax  执行序列（APM Vol.2 §15.5）

   1. 检查 EFER.SVME == 1，否则 #UD
   2. 检查 CPL == 0，否则 #GP
   3. 检查 RAX (VMCB 物理地址) 4KB 对齐且在物理地址范围内，否则 #GP
   4. 保存 Host 状态到 MSR_VM_HSAVE_PA 指向的区域
   5. 从 VMCB.save 加载 Guest 状态（受 clean bits 影响）
   6. ★ 一致性检查（Consistency Checks）
        - CR0.CD=0 且 CR0.NW=1        → 非法
        - CR0[63:32] 非零              → 非法
        - CR3 保留位非零               → 非法
        - CR4 保留位非零               → 非法
        - EFER 保留位非零 / EFER.SVME=0 → 非法
        - EFER.LME=1 且 CR0.PG=1 且 CR4.PAE=0 → 非法
        - EFER.LME=1 且 CR0.PG=1 且 CR0.PE=0  → 非法
        - 长模式下 CS.L=1 且 CS.D=1    → 非法
        - intercept 位图未拦截 VMRUN 自身 → 非法
        - ASID == 0                    → 非法
        - ...
      任一失败 → 不进入 Guest，直接产生 #VMEXIT，
                 exit_code = VMEXIT_INVALID (-1 / 0xFFFFFFFFFFFFFFFF)
   7. 清空 Host 的 TLB 中与新 ASID 冲突的项（按 tlb_ctl 指示）
   8. 进入 Guest 模式，从 VMCB.save.rip 开始取指
```

第 6 步是实践中最常撞到的地方。这些检查全部失败时**只给一个退出码，不给任何细节**，这就是自己写 VMM 时最难调的 `KVM_EXIT_FAIL_ENTRY`。KVM 对这种情况的处理是打印整个 VMCB：

```c
/* svm.c 中的 dump_vmcb()，退出码非法时被调用 */
pr_err("VMCB Control Area:\n");
pr_err("%-20s%04x\n", "cr_read:", control->intercepts[INTERCEPT_CR] & 0xffff);
...
pr_err("%-20s%016llx\n", "iopm_base_pa:", control->iopm_base_pa);
...
```

所以自己写的 VMM 遇到 `KVM_EXIT_FAIL_ENTRY` 时，`dmesg` 里通常有一份完整的 VMCB dump，比用户态那个 `0xffffffffffffffff` 有用得多。

一个高频错误：`RFLAGS` 的 bit 1 是保留位且**必须为 1**。用户态构造 `struct kvm_regs` 时若把 `rflags` 填成 0，落到 VMCB 后一致性检查失败。这个检查在 APM 里属于"保留位必须为规定值"一类，不在上面列出的显式清单里，但硬件确实会拒绝。

## 6. 退出分发与 Decode Assists

### 6.1 分发机制

`#VMEXIT` 之后，KVM 从 `vmcb->control.exit_code` 取退出原因，查一张 1024 项的函数指针表：

```c
/* arch/x86/kvm/svm/svm.c:3060 起 */
static int (*const svm_exit_handlers[])(struct kvm_vcpu *vcpu) = {
    [SVM_EXIT_READ_CR0]     = cr_interception,
    [SVM_EXIT_WRITE_CR0]    = cr_interception,
    [SVM_EXIT_EXCP_BASE + PF_VECTOR] = pf_interception,
    [SVM_EXIT_INTR]         = intr_interception,
    [SVM_EXIT_NMI]          = nmi_interception,
    [SVM_EXIT_HLT]          = kvm_emulate_halt,
    [SVM_EXIT_IOIO]         = io_interception,
    [SVM_EXIT_MSR]          = msr_interception,
    [SVM_EXIT_VMMCALL]      = kvm_emulate_hypercall,
    [SVM_EXIT_NPF]          = npf_interception,
    [SVM_EXIT_AVIC_INCOMPLETE_IPI] = avic_incomplete_ipi_interception,
    [SVM_EXIT_VMGEXIT]      = sev_handle_vmgexit,
    ...
};
```

退出码空间的划分（`arch/x86/include/uapi/asm/svm.h`）：

```
   0x000 - 0x00F   CR0-15 读
   0x010 - 0x01F   CR0-15 写
   0x020 - 0x03F   DR 读写
   0x040 - 0x05F   异常向量 0-31（SVM_EXIT_EXCP_BASE = 0x040）
   0x060           INTR         物理中断
   0x061           NMI
   0x064           VINTR        虚拟中断窗口
   0x072           CPUID
   0x078           HLT
   0x07B           IOIO
   0x07C           MSR
   0x081           VMMCALL
   0x400           NPF          嵌套缺页
   0x401 - 0x403   AVIC 相关
   0x403           VMGEXIT      SEV-ES
   -1 (0xFFFF...)  INVALID      一致性检查失败
```

注意异常退出码的编排：`SVM_EXIT_EXCP_BASE + N` 对应异常向量 N。所以 `#PF` 是 `0x40 + 14 = 0x4E`，`#UD` 是 `0x46`。这种"基址 + 向量"的连续编码让 `svm_exit_handlers[]` 可以用同一张表覆盖异常和非异常退出。

### 6.2 Decode Assists：AMD 把解码工作做进了微码

回到 `vmcb_control_area` 里那三个字段：

```c
u64 next_rip;         /* 0x0C8 */
u8  insn_len;         /* 0x0D0 */
u8  insn_bytes[15];   /* 0x0D1 */
```

**`next_rip`（需要 `NRIP Save` 特性）**：硬件在产生 `#VMEXIT` 时直接算出被拦截指令的**下一条指令地址**并填进去。软件推进 `RIP` 只需一次赋值：

```c
/* svm_skip_emulated_instruction()，arch/x86/kvm/svm/svm.c:354 */
if (nrips && svm->vmcb->control.next_rip != 0) {
    WARN_ON_ONCE(!static_cpu_has(X86_FEATURE_NRIPS));
    svm->next_rip = svm->vmcb->control.next_rip;
}

if (!svm->next_rip) {
    /* 硬件没给，只能软件解码一遍指令算长度 */
    if (!kvm_emulate_instruction(vcpu, EMULTYPE_SKIP))
        return 0;
} else {
    kvm_rip_write(vcpu, svm->next_rip);
}
```

**`insn_bytes[15]`（需要 `DecodeAssists` 特性）**：更进一步，硬件把触发退出的那条指令的**原始机器码字节**直接搬进 VMCB。这一点在缺页处理里价值极大：

```c
/* npf_interception()，arch/x86/kvm/svm/svm.c:1901 */
static int npf_interception(struct kvm_vcpu *vcpu)
{
    struct vcpu_svm *svm = to_svm(vcpu);
    u64 fault_address = svm->vmcb->control.exit_info_2;
    u64 error_code    = svm->vmcb->control.exit_info_1;

    trace_kvm_page_fault(fault_address, error_code);
    return kvm_mmu_page_fault(vcpu, fault_address, error_code,
            static_cpu_has(X86_FEATURE_DECODEASSISTS) ?
                svm->vmcb->control.insn_bytes : NULL,
            svm->vmcb->control.insn_len);
}
```

如果没有 Decode Assists，KVM 要模拟一条 MMIO 指令必须：拿 Guest 的 `RIP` → 走一遍 Guest 页表把 GVA 翻译成 GPA → 通过 memslot 把 GPA 翻译成 HVA → `copy_from_user` 读出指令字节。**这条链路本身就可能再次触发缺页**，而且在 Guest 正在改自己页表的竞态窗口里可能读到错误的指令。有了 Decode Assists，这一整段全部省掉。

### 6.3 Intel 的对照路线

Intel VMCS 里**没有** "下一条指令地址" 这个字段，只有 `VM_EXIT_INSTRUCTION_LEN`（指令字节长度）。推进 `RIP` 必须软件做加法：

```c
/* arch/x86/kvm/vmx/vmx.c:1490 */
static int skip_emulated_instruction(struct kvm_vcpu *vcpu)
{
    union vmx_exit_reason exit_reason = to_vmx(vcpu)->exit_reason;
    unsigned long rip, orig_rip;
    u32 instr_len;

    /*
     * Using VMCS.VM_EXIT_INSTRUCTION_LEN on EPT misconfig depends on
     * undefined behavior: Intel's SDM doesn't mandate the VMCS field be
     * set when EPT misconfig occurs.  In practice, real hardware updates
     * VM_EXIT_INSTRUCTION_LEN on EPT misconfig, but other hypervisors
     * (namely Hyper-V) don't set it due to it being undefined behavior,
     * i.e. we end up advancing IP with some random value.
     */
    if (!static_cpu_has(X86_FEATURE_HYPERVISOR) ||
        exit_reason.basic != EXIT_REASON_EPT_MISCONFIG) {
        instr_len = vmcs_read32(VM_EXIT_INSTRUCTION_LEN);
        ...
        orig_rip = kvm_rip_read(vcpu);
        rip = orig_rip + instr_len;
        ...
        kvm_rip_write(vcpu, rip);
    }
    ...
}
```

这段注释本身就是一个精彩的工程案例：SDM 没有规定 EPT misconfig 时该字段必须有效（undefined behavior），真实硬件其实填了，但当 KVM 自己跑在 Hyper-V 之上作为嵌套 Guest 时，Hyper-V 严格按规范办事没有填，于是 KVM 会用一个随机值推进 `RIP`。修复方式是先检查自己是不是跑在 Hypervisor 里。

对照总结：

| 事项 | AMD SVM | Intel VMX |
|---|---|---|
| 下一条指令地址 | 硬件填 `control.next_rip` | 无，软件用 `RIP + VM_EXIT_INSTRUCTION_LEN` 计算 |
| 触发指令的机器码 | 硬件填 `control.insn_bytes[15]` | 无，软件必须走 Guest 页表读取 |
| 控制块访问 | 结构体指针，普通访存 | `VMREAD`/`VMWRITE`，数十周期 |
| Host 状态存放 | 独立的 HSAVE 区域，MSR 指定 | VMCS 内的 Host-State Area |
| 补充状态搬运 | `VMSAVE`/`VMLOAD` 显式指令 | 硬件在 VM-Exit 时按 VM-Exit Controls 自动处理 |
| 全局中断屏蔽 | `CLGI`/`STGI`（GIF） | 无对应指令，靠 VMCS 中断控制字段 |

## 7. ASID 与 TLB

### 7.1 为什么需要 ASID

TLB 缓存的是"虚拟地址 → 物理地址"的翻译结果。在虚拟化场景下，同一个虚拟地址 `0xffff8880_00000000` 在 Host 内核里和在 Guest 内核里指向完全不同的物理页。如果不加区分，每次世界切换都必须全量刷 TLB，而 TLB miss 的代价（尤其是二维漫游下）会把性能吃干净。

AMD 的方案是给每个 TLB 项打上 **ASID（Address Space Identifier）** 标签，写在 `vmcb->control.asid`。**ASID 0 保留给 Host**，Guest 必须使用非零 ASID（前面一致性检查里 `ASID == 0` 是非法的）。硬件只匹配当前 ASID 的 TLB 项，不同 Guest、Host 与 Guest 之间的翻译结果可以在 TLB 里共存。

可用 ASID 数量来自 `CPUID Fn8000_000A_EBX`，现代 EPYC 上通常是 32768 或 65536。这个数字并不总是够用——每个 vCPU 在每颗物理核上都需要一个 ASID，且 SEV 虚拟机会独占一段 ASID 空间（`sd->min_asid = max_sev_asid + 1`）。

### 7.2 分配与回绕

KVM 的分配策略是 per-物理-CPU 的单调递增 + 代数回绕：

```c
/* arch/x86/kvm/svm/svm.c:1830 */
static void new_asid(struct vcpu_svm *svm, struct svm_cpu_data *sd)
{
    if (sd->next_asid > sd->max_asid) {
        ++sd->asid_generation;
        sd->next_asid = sd->min_asid;
        svm->vmcb->control.tlb_ctl = TLB_CONTROL_FLUSH_ALL_ASID;
        vmcb_mark_dirty(svm->vmcb, VMCB_ASID);
    }

    svm->current_vmcb->asid_generation = sd->asid_generation;
    svm->asid = sd->next_asid++;
}
```

逻辑是：ASID 用完一轮就把"代数"加一，并要求硬件下次 `VMRUN` 时刷掉**所有** ASID 的 TLB 项（`TLB_CONTROL_FLUSH_ALL_ASID = 1`）。每个 VMCB 记住自己拿到 ASID 时的代数，代数不匹配就重新分配。这是一个经典的"epoch-based 复用"模式，避免了维护精确的 ASID 引用计数。

`tlb_ctl` 的取值：

```c
#define TLB_CONTROL_DO_NOTHING          0
#define TLB_CONTROL_FLUSH_ALL_ASID      1
#define TLB_CONTROL_FLUSH_ASID          3   /* 只刷当前 ASID */
#define TLB_CONTROL_FLUSH_ASID_LOCAL    7   /* 只刷当前 ASID 的非全局项 */
```

Intel 的对应机制叫 **VPID（Virtual Processor ID）**，写在 VMCS 的 `VIRTUAL_PROCESSOR_ID` 字段，配合 `INVVPID` 指令做精细失效。两者在功能上等价，但 Intel 的 VPID 与 Guest 内部的 PCID 是级联关系（TLB 项同时带 VPID 和 PCID 两个标签），AMD 的 ASID 则与 Guest 的 PCID 独立工作。

## 8. 本卷小结与卷二预告

到这里，CPU 虚拟化的硬件契约已经完整：

1. `EFER.SVME` 打开状态机，`MSR_VM_HSAVE_PA` 指定 Host 状态的落点，形成 Host/Guest 状态存放的不对称结构，`VMSAVE`/`VMLOAD` 补齐硬件不管的那部分。
2. VMCB 是一块布局固定的 4 KB 物理页，控制区上半部分是软件写给硬件的策略，下半部分是硬件写给软件的退出信息。
3. 拦截策略分三层：`intercepts[6]` 位标志、12 KB 的 IOPM（三页布局有明确的边界溢出防护语义）、8 KB 的 MSRPM（两位一 MSR，三段不连续）。Clean Bits 是反向语义的缓存优化，且缓存粒度是 per-物理-CPU。
4. 世界切换的软件部分要处理 15 个通用寄存器的搬运、RSB 填充、寄存器清零，以及 `GIF`/`RFLAGS.IF` 两层中断屏蔽的级联时序。
5. 退出分发靠 `exit_code` 查函数指针表；AMD 通过 `next_rip` 和 `insn_bytes[15]` 把相当一部分指令解码工作固化进硬件，这是它与 Intel 在软件路径长度上的核心差异。

**但整篇没有回答一个问题：Guest 访问一个地址时，硬件怎么知道这个地址是内存还是设备？**

`out 0x3f8, al` 这种端口 I/O 是特殊的——x86 有独立的 I/O 地址空间和专门的拦截位图。而现代设备（PCIe BAR、VirtIO-MMIO 窗口、APIC 页）全部映射在物理地址空间里，Guest 访问它们时执行的是普通的 `mov` 指令，硬件必须在**地址翻译阶段**就把"这是 RAM"和"这是设备"区分开。

这个区分不是靠一张设备表，而是靠 NPT 页表项里的**保留位**——KVM 会给设备地址安装一个故意构造成非法格式的 SPTE，让硬件在漫游到它时抛出带 `PFERR_RSVD` 标志的 `#NPF`。

卷二从三层地址翻译讲起，把 `memslot`、二维页表漫游、`#NPF` 的完整生命周期、TDP MMU 的 RCU 无锁建表、以及 MMIO 识别的保留位技巧全部展开。
