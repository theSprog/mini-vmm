# 卷七：Linux 眼中的 PC 传统设备——驱动探测逐寄存器追踪

> 承接卷五（固件表与 Linux 启动协议）与卷六（SMP 虚拟化与 CPU 拓扑），配套 blog《从零入门虚拟化》的《传统设备·原理篇》《传统设备·实现篇》，PIT 与 TSC 校准部分配套《时间》。
>
> 卷五让 guest 认识了这台机器，卷六让它把所有 CPU 都跑了起来。但在这两卷里，“设备”一直是被当作黑盒对待的：串口能出字、RTC 能读出时间、i8042 探测不会卡住，至于驱动究竟按什么顺序读写了哪几个寄存器、每一次读回的值分别决定了什么，都没有展开。本卷把这层黑盒拆开。
>
> 全卷只有一个命题：**设备要模拟到什么程度，由驱动的探测逻辑决定，而不是由芯片手册决定。** 16550A 的手册有几十页，Linux 的 `autoconfig()` 有四百行，而在我们这台 guest 上，真正决定“这是不是一颗 16550A”的只有 22 次端口访问。反过来，有些在手册里根本不起眼的约定——比如“不存在的端口读回 0xFF”——却是某个驱动判定“这台机器没有这个设备”的唯一依据，漏掉它就会多出一整个子系统。
>
> 方法上，本卷与前几卷不同：不再只靠读源码推断，而是**先把 guest 实际发出的每一次 PIO 访问录下来，再拿录到的序列去对源码**。为此给 mini-vmm 加了一个 `--trace-pio` 选项，它把每次陷出到用户态的端口访问写成一行，未注册端口还会附上 guest 的 RIP，拿到 `vmlinux` 上一查就知道是哪个函数在盲探。本卷引用的所有序列都出自这样一次真实启动，没有一条是照着手册推演出来的。
>
> host 侧源码基于 Linux **v6.6**（KVM，行号对应 v6.6.91），guest 侧源码基于 Linux **v7.4-rc2**（commit `7e1392a42ea2`），即 mini-vmm 实际引导的那个内核；文中 `file:line` 形式的行号都对应这两棵树。数据来自 WSL2 上的一次次启动，CPU 是 AMD Ryzen 7 5800H，KVM 本身跑在 Hyper-V 的虚拟机里（嵌套虚拟化）。设备侧规范依据 National Semiconductor PC16550D 数据手册、Intel 8254/8259A 数据手册、Motorola MC146818A 数据手册、ACPI 6.5 第 4 章（ACPI Hardware Specification）与 IBM PC/AT 技术参考。

## 1. 命题：模拟到什么程度，由驱动决定

### 1.1 三种“完整”

写设备模型时，“做完了”至少有三个互不相同的标准。

第一种是**手册完整**：把数据手册上的每个寄存器、每个位、每种工作模式都实现出来。16550A 的 FIFO 触发门限有四档、波特率分频器是 16 位、MSR 的低 4 位是变化标志位（delta bits）、LSR 有奇偶错误和帧错误位。全做出来是一件很大的工程，而且做完之后你会发现绝大部分代码从来没被执行过。

第二种是**架构完整**：凡是 guest 有办法观察到的状态都要正确。这个标准比第一种弱，但依然过强——它要求你对“guest 有没有办法观察到”做出判断，而这个判断本身就需要知道 guest 会怎么访问。

第三种是**驱动完整**：让目标 guest 的驱动走完它的探测与工作路径，并且走到你希望它走到的那个分支。这是写 VMM 时真正该用的标准。它有两个特点：一是**小**，一次 Linux 启动里串口的全部寄存器访问只涉及 8 个端口中的 7 个，i8042 的控制器命令只用到 10 条；二是**不对称**，让驱动认为设备“存在且正常”，和让驱动认为设备“不存在”，是两件难度完全不同的事，而后者往往更重要——第 5 节的 AUX 口和第 7 节的 8237 DMA 控制器都是这个类型。

这个标准也有它的代价：结论只对**这个** guest、**这个**内核配置成立。本卷会反复出现“因为 `CONFIG_XXX` 没开，所以这段探测代码根本不会执行”这样的判断，换一个 `.config` 就得重新核对。所以每一处这样的结论，文中都会同时给出配置项和实测证据。

### 1.2 方法：把驱动的每一次寄存器访问录下来

KVM 的分工决定了 VMM 能看到什么。guest 执行 `in`/`out` 时，如果目标端口由内核态设备模型接管（PIC、PIT、LAPIC、IOAPIC），KVM 就地处理，用户态完全无感；否则产生一次 `KVM_EXIT_IO`，`kvm_run->io` 里带着端口号、方向、宽度、重复次数和数据缓冲区的偏移。于是**凡是能被 VMM 看见的 PIO，都是 VMM 自己负责的设备**，反过来也成立：trace 里没有的端口，要么没人访问，要么被内核态接走了。这一点在第 3 节会变成一个很强的观察结论。

追踪的实现在 `src/vm.c` 的“I/O 追踪”一节，由 `--trace-pio FILE` 打开（MMIO 对应 `--trace-mmio FILE`，格式相同）。每次访问写一行：

```text
<单调时钟秒>.<微秒> <设备名> <端口> R|W<字节数> <值> [rip=<guest RIP>]
```

写行的函数是 `trace_line()`：

```c
static void trace_line(FILE *f, const char *name, uint64_t addr, int addr_width,
                       bool is_write, uint32_t size, const uint8_t *val,
                       uint64_t rip)
{
    unsigned long long v = 0;
    struct timespec ts;
    uint32_t i;

    clock_gettime(CLOCK_MONOTONIC, &ts);
    for (i = 0; i < size && i < sizeof(v); i++)
        v |= (unsigned long long)val[i] << (8 * i);

    fprintf(f, "%lld.%06ld %-11s %0*llx %c%u %0*llx",
            (long long)ts.tv_sec, ts.tv_nsec / 1000, name, addr_width,
            (unsigned long long)addr, is_write ? 'W' : 'R', size,
            (int)(size * 2), v);
    if (rip)
        fprintf(f, " rip=%016llx", (unsigned long long)rip);
    fputc('\n', f);
}
```

三个设计决定值得说明。

**记录时机在设备回调之后、错误判断之前。** 对写来说值在调用前后一样，但对读来说，只有设备回调返回之后缓冲区里才是 guest 真正会读到的值。`io_bus_dispatch_pio()` 的分发循环里，`trace_line()` 紧跟在回调之后、`if (r != VMM_OK) return r;` 之前：mini-vmm 用回调的返回值表示“guest 请求关机/复位”，触发退出的那一次写恰恰是整条 trace 里最值得留下的一行，放在 `return` 之后就会丢掉它，第 6 节里 ACPI S5 的最后一次 `out` 就是这样一行。

**RIP 只对未注册端口取。** 已注册端口的设备名本身已经回答了“谁在访问”，而未注册端口恰恰是需要反查调用者的那一类。取 RIP 需要一次 `KVM_GET_REGS`，是一次 vCPU ioctl，只在追踪打开且访问落在未注册端口上时才付这个代价：

```c
static uint64_t trace_rip(struct vmm_vcpu *vcpu)
{
    struct kvm_regs regs;

    memset(&regs, 0, sizeof(regs));
    if (ioctl(vcpu->fd, KVM_GET_REGS, &regs) < 0)
        return 0;
    return regs.rip;
}
```

拿到 RIP 之后，`nm -n vmlinux` 排序一遍做一次二分查找就能定位到符号。本卷里几处“这是谁在访问”的结论都是这么来的，第 7 节会给出完整的对照表。

**不加锁。** vCPU 线程处理 `KVM_EXIT_IO` 和 `KVM_EXIT_MMIO` 时全程持有 `vm->io_lock`（`src/vm.c:503-514`），多 vCPU 下 PIO 分发本来就是串行的，trace 的写入自然也串行，不需要额外的锁。这是卷六那把大锁的一个副产品。

用法：

```sh
./build/vmm --mode linux --smp 1 --mem 512M \
    --trace-pio /tmp/pio.txt \
    --initrd build/initramfs.cpio.gz guest-kernel/vmlinux
python3 tools/trace_decode.py --summary /tmp/pio.txt
```

`tools/trace_decode.py` 按端口和设备统计次数，也能按端口、设备、行号区间切片，`--syms vmlinux` 把 `rip=` 换成符号加偏移。

### 1.3 一次启动的 PIO 全景

下面这张表来自一次完整的 `--smp 1` 启动加 `poweroff -f` 关机（guest 为 Linux 7.4-rc2，默认机器带 PCI 主桥）。同样的命令再跑一次，除串口外每个端口的次数逐条相同，串口的次数随打印内容和轮询时机差几百次。这一点本身就是个有用的信号：**设备探测序列由驱动代码决定，不随运行时机变化。** 第 7.1 节那张未注册端口的表也一条不差。

| 端口 | 设备 | 访问次数 | 本卷的哪一节 |
|---|---|---|---|
| 0x3f8 | 16550A 的 THR/RBR | 20532（写 20516，读 16） | 第 2 节 |

| 0x70 / 0x71 | CMOS RTC 索引/数据 | 89 / 89 | 第 4 节 |

三个立刻能读出来的事实。

**串口占了 98.0%。** 41450 次里 40585 次是 `0x3f8` 写字符加 `0x3fd` 轮询状态这一对。每个字符两次 VM exit，一次启动打印大约两万个字符。这个数字是 VirtIO 与 ioeventfd 的全部动机：不是模拟得不对，而是每个字节都要穿一次用户态实在太贵。

**PIT 一次都没出现。** 端口 0x40–0x43 和 0x61 在整张 trace 里是空的。一层原因是这些端口被 KVM 的内核态 PIT 接管，即使 guest 访问它们也不会陷出到用户态；另一层是这个 guest 根本没用 PIT 校准 TSC：它开了 `CONFIG_KVM_GUEST`，TSC 频率直接从 kvmclock 读（启动日志是 `tsc: Detected 3193.914 MHz processor`，不是 `Using PIT calibration value`）。第 3 节专门讲这两件事。

**PIC、LAPIC 和 0x80 也不在表里。** 0x20/0x21/0xa0/0xa1 和 LAPIC 的 MMIO 页都由内核态 irqchip 处理。`outb_p` 的延时写本该落在没人接管的 0x80 上，但 KVM 向 guest 声明了 `KVM_FEATURE_NOP_IO_DELAY`，guest 于是把这类延时写整个省掉了，见第 7.2 节。

## 2. 16550A 串口：三段人生

串口是 mini-vmm 里唯一一个“既要被探测出来、又要一直高速工作”的设备，也是本卷材料最多的一个。它在一次启动里经历三段互不相同的人生：先是 `earlyprintk` 直接按端口号操作的一块裸硬件，然后是 `printk` 的正式 console，最后在 `/dev/console` 被打开之后变成一个中断驱动的 tty。三段用的是三份完全不同的代码，访问模式也完全不同。

### 2.1 寄存器与 DLAB

8 个寄存器挤在 8 个连续端口上，靠两个开关复用：

| 偏移 | DLAB=0 读 | DLAB=0 写 | DLAB=1 |
|---|---|---|---|
| 0 | RBR 接收保持 | THR 发送保持 | DLL 分频器低字节 |
| 1 | IER 中断使能 | IER | DLM 分频器高字节 |
| 2 | IIR 中断标识 | FCR FIFO 控制 | （LCR=0xBF 时为 EFR，扩展芯片才有） |
| 3 | LCR 线路控制 | LCR | — |
| 4 | MCR modem 控制 | MCR | — |
| 5 | LSR 线路状态 | （只读） | — |
| 6 | MSR modem 状态 | （只读） | — |
| 7 | SCR 便笺 | SCR | — |

DLAB 是 LCR 的 bit7。这个设计带来的直接后果是：**任何一次读写偏移 0 或 1 的行为，都必须先看 LCR 的当前值才能确定它的含义**。mini-vmm 的 `serial_read()`/`serial_write()` 每个 case 都先判 `s->lcr & UART_LCR_DLAB`（`src/devices/serial8250.c:163`、`:216`），这不是画蛇添足——第 2.3 节和第 2.6 节的 trace 里都能看到 Linux 先写 LCR=0x93 打开 DLAB、写完分频器再写 LCR=0x13 关掉，中间那两次对偏移 0/1 的写如果被当成 THR 和 IER，串口就直接乱了。

偏移 2 还有第三重身份：LCR 写成 0xBF（`UART_LCR_CONF_MODE_B`）时，一批扩展 16550 兼容芯片（ST16C650V2、TI16C752 等）会把这里变成 EFR 寄存器。Linux 的 `autoconfig()` 用这条路径区分芯片型号，第 2.4 节会看到它写了一次 EFR=0。真 16550A 没有 EFR，0xBF 对它只是一个 DLAB 置位的普通 LCR 值，偏移 2 照旧是 IIR/FCR。mini-vmm 照真硬件做，不对 `LCR == 0xBF` 做任何特殊处理。直觉上的“挡掉：读回 0、写丢弃”恰恰是错的，因为 Linux 把 LCR=0xBF 下读到 0 解释为“有 EFR”，第 2.9 节展开。

### 2.2 第一段：earlyprintk 的 9 次访问

mini-vmm 的默认命令行里有 `earlyprintk=serial,ttyS0,115200`（`src/main.c` 里的默认 cmdline，启动日志第一行会回显）。这条参数走的**不是** 8250 驱动，而是 `arch/x86/kernel/early_printk.c` 里一段几十行的裸代码，它在 `setup_arch()` 里就跑起来了，那时候连内存管理都还没初始化完。

trace 的最前面两行是一次 PCI 配置读（`setup_arch()` → `early_reserve_memory()` → `trim_snb_memory()` 问 00:02.0 是不是 Sandy Bridge 核显，它在解析命令行之前就跑了，所以排在 earlyprintk 前面），紧接着的九行就是它：

```
serial8250  03fb W1 03      LCR = 0x03，8n1
serial8250  03f9 W1 00      IER = 0，关中断
serial8250  03fa W1 00      FCR = 0，关 FIFO
serial8250  03fc W1 03      MCR = DTR|RTS
serial8250  03fb R1 03      c = LCR
serial8250  03fb W1 83      LCR = c | DLAB
serial8250  03f8 W1 01      DLL = 1
serial8250  03f9 W1 00      DLM = 0
serial8250  03fb W1 03      LCR = c & ~DLAB
```

对照 `arch/x86/kernel/early_printk.c:134` 的 `early_serial_hw_init()`，九行一一对应，顺序一字不差：

```c
static __init void early_serial_hw_init(unsigned divisor)
{
	unsigned char c;

	serial_out(early_serial_base, LCR, 0x3);	/* 8n1 */
	serial_out(early_serial_base, IER, 0);	/* no interrupt */
	serial_out(early_serial_base, FCR, 0);	/* no fifo */
	serial_out(early_serial_base, MCR, 0x3);	/* DTR + RTS */

	c = serial_in(early_serial_base, LCR);
	serial_out(early_serial_base, LCR, c | DLAB);
	serial_out(early_serial_base, DLL, divisor & 0xff);
	serial_out(early_serial_base, DLH, (divisor >> 8) & 0xff);
	serial_out(early_serial_base, LCR, c & ~DLAB);
}
```

`divisor = 115200 / baud`（`early_printk.c:193`），命令行里写的是 115200，所以 DLL=1。

这九次访问里**没有一次是探测**。early_printk 不问“这里有没有串口”，它假定 0x3f8 上有一颗 UART 并直接开始用。这就是为什么它能在启动的最早期工作，也是为什么 `earlyprintk=` 参数必须由人手动给对——猜错了端口，内核只是往一个空地址写字节，不会有任何提示。

从 VMM 的角度看，要让这一段工作起来只需要满足两个条件：写 THR 的字节要送出去，读 LSR 要能读到 `THRE|TEMT` 都置位。分频器、LCR 的位宽/校验设置、MCR 的 DTR/RTS 一概不影响结果，因为 host 那一侧是一个文件描述符，不是一根真的线。mini-vmm 把 DLL/DLM 存下来但从不使用（`serial8250.c:217`、`:226`），LSR 干脆恒定返回 `THRE|TEMT`（`serial8250.c:186`）：

```c
    case UART_LSR:
        v = UART_LSR_THRE | UART_LSR_TEMT;
        if (!rx_empty(s))
            v |= UART_LSR_DR;
        break;
```

这一行决定了 `early_serial_putc()` 里那个 `while ((serial_in(..., LSR) & XMTRDY) == 0 && --timeout)` 循环永远只转一圈。代价是每个字符两次 VM exit：一次读 LSR，一次写 THR。第 1.3 节那 40585 次访问就是这么来的。

### 2.3 第二段：printk 的 console

`console=ttyS0` 让 8250 驱动在 `console_init()` 里注册一个真正的 console。这一步在 trace 里的位置很好找——紧挨着 `printk: console [ttyS0] enabled` 这行字：

```
serial8250  03f9 W1 00      IER = 0
serial8250  03fb W1 93      LCR = 0x13 | DLAB
serial8250  03f8 W1 0c      DLL = 12
serial8250  03f9 W1 00      DLM = 0
serial8250  03fb W1 13      LCR = 0x13
serial8250  03fa W1 00      FCR = 0
serial8250  03fc W1 01      MCR = DTR
```

两个值得停一下的细节。

**分频器是 12，不是 1。** `console=ttyS0` 后面没有跟波特率，`serial8250_console_setup()` 就用默认的 9600（`8250_port.c:3616` 的 `int baud = 9600`），`115200 / 9600 = 12`。也就是说 earlyprintk 阶段把串口设成 115200，正式 console 又把它改成 9600，而**输出速度一点没变**——因为 mini-vmm 根本不看分频器。真机上这里会有一次肉眼可见的速率切换，虚拟机里没有。这是“模拟到什么程度由驱动决定”的一个正面例子：分频器必须能写能读（否则 `autoconfig` 的某些分支会误判），但它的值可以完全不起作用。

**LCR 是 0x13，不是 0x03。** 0x13 = `UART_LCR_WLEN8`(0x03) | `UART_LCR_EPAR`(0x10)。命令行里没有指定校验，按说不该出现校验相关的位。原因在 `8250_port.c:2575` 的 `serial8250_compute_lcr()`：

```c
	if (c_cflag & PARENB)
		lcr |= UART_LCR_PARITY;
	if (!(c_cflag & PARODD))
		lcr |= UART_LCR_EPAR;
```

EPAR 是**无条件**跟着“不是奇校验”走的，跟 PARENB 没关系。在真硬件上 PARENB（bit3）为 0 时 EPAR 不起作用，所以这是个无害的写法，但它会让你在读 trace 时困惑一阵。mini-vmm 的 LCR 是原样存原样读（`serial8250.c:241`），不做任何合法性检查——这一点在这里正好是对的：**设备模型不该比真硬件更挑剔**。

从这里开始到 `/dev/console` 被打开之前，所有内核日志都走 `serial8250_console_write()`，它的模式是：进函数先读一次 IER 存起来、写 IER=0 关中断，然后每个字符 `wait_for_xmitr()` 读 LSR、写 THR，最后恢复 IER。trace 里每一行日志前后那对 `03f9 R` / `03f9 W` 就是它。

### 2.4 第三段之前：`autoconfig()` 用 22 次访问认出 16550A

`serial8250_isa_init_ports()` 按 `arch/x86/include/asm/serial.h` 里的 `SERIAL_PORT_DFNS` 注册四个 ISA 口（0x3f8/0x2f8/0x3e8/0x2e8），然后 `uart_add_one_port()` → `serial8250_config_port()` → `autoconfig()` 逐个探测。下面是 ttyS0 那一轮的全部访问，右边是对应的源码位置（`8250_port.c`）：


再加上第 6 步之前那次 `03f9 R`（第 1 步）和最后驱动读回 IER 的一次，正好落在 22 次上下。整段探测里**真正起判定作用的只有三次读**：

- 第 3、5 步的 IER 回读。这是“存在性测试”：把 IER 低 4 位写成 0 要能读回 0，写成 0x0f 要能读回 0x0f。mini-vmm 的 `s->ier = v & 0x0f`（`serial8250.c:232`）刚好满足。注释里写得很清楚，选 IER 是因为它是唯一一个“写什么读什么、而且不会产生副作用”的寄存器。
- 第 13 步的 IIR 回读。写 FCR 打开 FIFO 之后，IIR 的高两位要变成 11。mini-vmm 的 `update_irq()` 在 `s->fcr & UART_FCR_ENABLE` 时给 IIR 或上 0xC0（`serial8250.c:91`），于是读回 0xC1（NO_INT | FIFO）。0xC0 对应 `UART_IIR_FIFO_ENABLED_16550A`，判定结束。

换句话说：**让 Linux 认出一颗 16550A，只需要 IER 低 4 位可读写、FCR 的 bit0 能反映到 IIR 的 bit7:6 上。** 其余十几次访问都是保存与还原现场。

### 2.5 三条没有走的路

`autoconfig()` 全文四百行，上面只用到了前六十行。剩下的都被跳过了，跳过的原因各不相同，而且每一条都值得记住——因为换一个 guest 配置它们就会活过来。

**回环测试被 `UPF_SKIP_TEST` 跳过。** `8250_port.c:1172` 那段本来要写 `MCR = LOOP|OUT2|RTS`，再读 MSR 的高 4 位，期望得到 `DCD|CTS`。但 x86 的 `SERIAL_PORT_DFNS`（`arch/x86/include/asm/serial.h`）给 COM1–COM3 都带了 `UPF_SKIP_TEST`：

```c
# define STD_COMX_FLAGS	(UPF_BOOT_AUTOCONF |	UPF_SKIP_TEST	| 0		)
# define STD_COM4_FLAGS	(UPF_BOOT_AUTOCONF |	0		| 0		)
```

理由在源码注释里：有些基于 Rockwell 芯片的内置调制解调器不实现回环，而“没有哪个板卡厂商会蠢到把设备做得和 COM1–4 冲突”。只有 COM4（0x2e8）没带这个标志——但它在第 1 步的 IER 测试就失败了（见 2.9），根本走不到这里。**结论：在这台 guest 上，mini-vmm 的回环实现（`serial8250.c:127` 的 `msr_value()`）一次都没有被执行过。** 它不是废代码，只是没有被现在这套配置触发，比如把串口挂到 0x2e8 就会触发。

**变体探测被 `CONFIG_SERIAL_8250_16550A_VARIANTS=n` 跳过。** `autoconfig_16550a()` 的第一件事（`8250_port.c:950`）是：

```c
	if (!IS_ENABLED(CONFIG_SERIAL_8250_16550A_VARIANTS) &&
	    !(up->port.flags & UPF_FULL_PROBE))
		return;
```

本卷实测所用的 guest 配置里这一项是 `# CONFIG_SERIAL_8250_16550A_VARIANTS is not set`，而 `UPF_FULL_PROBE` 在整棵树里只被 `8250_pci.c:1294` 设置过，`CONFIG_SERIAL_8250_PCI` 也没开。于是 ST16650、NS16550A、TI16750、XScale、16C950 的全部识别代码，以及那个带 `mdelay(20)` 的 `size_fifo()`，统统不执行。这是个很大的便宜：`size_fifo()` 会写 MCR=LOOP、把分频器改成 1、连写 256 个字节再读回来数个数，实现起来相当烦人，而在这套配置下它根本不会被调用。打开这一项的内核会执行全部变体探测，mini-vmm 在那条路径上的表现见 2.9 节。

**IRQ 自动探测走了，而且留下了一个后效。** 这一条和前两条相反：guest 配置里 `CONFIG_SERIAL_8250_DETECT_IRQ=y`，`SERIAL_PORT_DFNS` 因此给四个口都带上 `UPF_AUTO_IRQ`（`arch/x86/include/asm/serial.h:15-17`），`serial8250_config_port()` 在 `autoconfig()` 之后调 `autoconfig_irq()`（`8250_port.c:3177`）。`autoconfig_irq()`（`8250_port.c:1246`）靠 `probe_irq_on()` / `probe_irq_off()` 观察哪根 IRQ 线被拉起来：先写 `MCR = 0`，再写 `MCR = DTR|RTS|OUT2`（0x0b）、`IER = 0x0f`，读一遍 LSR/RX/IIR/MSR，往 THR 写一个 0xFF，`udelay(20)` 之后看哪根线来过中断，最后把 MCR 和 IER 还原。trace 里 ttyS0 这一段是：

```

serial8250  03fc W1 0b      OUT2 置位，中断门控打开
serial8250  03f9 W1 0f      IER 全开：THRI 立刻成立，IRQ 4 拉高
serial8250  03fd R1 60  ┐
serial8250  03f8 R1 00  │   serial8250_clear_interrupts()
serial8250  03fa R1 02  │   读 IIR 拿到 THRI 即应答，IRQ 4 落下
serial8250  03fe R1 b0  ┘
...                         写 THR 0xFF：THR 重新变空，IRQ 4 再次拉高
serial8250  03fc W1 01      MCR 还原，OUT2 关掉，IRQ 4 落下
serial8250  03f9 W1 00      IER 还原
```

mini-vmm 这一侧能直接看到 IRQ 线的变化：`update_irq()` 在 MCR=0x0b、IER=0x0f 时把 IRQ 4 拉高，读 IIR 后放下，写 THR 后再拉高，MCR 还原成 0x01 时放下。`probe_irq_off()` 拿到的是 4，和 `SERIAL_PORT_DFNS` 里写死的值一致，所以探测结果不改变任何东西；mini-vmm 在 MP 表和 MADT 里把串口登记在 GSI 4 上（卷五第 6 节），三处必须一致。这次探测的后效在第 2.6 节：探测期间来过的那次中断没有处理程序，内核把 IRQ 4 标成待决，等 `request_irq()` 时补发。

0x2f8/0x3e8/0x2e8 三个口在 IER 存在性测试就出局（第 2.8 节），走不到这里，所以 trace 里只有 ttyS0 一段。

### 2.6 第三段：`/dev/console` 被打开，串口变成中断驱动

`kernel_init_freeable()` 的最后一步是 `console_on_rootfs()`（`init/main.c:1737`），它 `filp_open("/dev/console", O_RDWR)`，这一下走通 tty 层，触发 `uart_port_startup()` → `serial8250_do_startup()`。在 trace 里这一段紧挨着 `Freeing unused kernel image (initmem) memory` 之前，正好对上 `kernel_init()` 里 `kernel_init_freeable()` 在 `free_initmem()`（`init/main.c:1631`）之前的顺序。

这是全卷信息量最大的一段 trace：

**第 7 步那次 IIR 读是第 2.5 节 IRQ 自动探测的后效。** 探测期间 IRQ 4 来过一次中断，那时这根线上还没有处理程序，`handle_edge_irq()` 把它记成待决（`IRQS_PENDING`）。`request_irq()` 走到 `irq_startup()` 时调 `check_irq_resend()`，看到待决标志就用 `apic_retrigger_irq()` 给自己发一个同向量的 IPI 把它补上（`kernel/irq/resend.c:144`、`:108`），这次 `serial8250_interrupt()` 有了，读 IIR 得到 NO_INT 就返回。用 gdbstub 在 `apic_retrigger_irq` 上下断点，断下时的调用栈正是 `serial8250_do_startup()` → `univ8250_setup_irq()` → `request_irq()` → `__setup_irq()` → `irq_startup()` → `check_irq_resend()`。

第 8–14 步是 **THRE bug 测试**：两次“打开 THRI 中断、读 IIR、关掉”。真 16550 在发送器空闲且中断已使能时应该**反复**重新置位 THRE 中断，坏芯片只置一次。判据在 `8250_port.c:2267-2268`：第一次读到中断而第二次读到 NO_INT，就置 `UART_BUG_THRE`，之后驱动要额外挂一个定时器去踢串口。mini-vmm 两次都报 THRI，所以不带这个 bug 标志。**这正是 `serial8250.c:228` 那段注释存在的理由**：

```c
            /* 打开 THRI 的瞬间如果 THR 是空的，要马上来一次中断。
             * Linux 的 serial8250_start_tx 就是靠这个启动发送的。 */
            if (!(s->ier & UART_IER_THRI) && (v & UART_IER_THRI))
                s->thri_pending = true;
```

写 IER 时如果 THRI 从 0 变 1 就置上待决标志——第 10 步和第 13 步都靠它。少了这一句，第二次读 IIR 会读到 NO_INT，Linux 就会给我们扣上 `UART_BUG_THRE` 的帽子，然后每 25ms 拿定时器轮询一次串口。

第 17–20 步是 **TXEN bug 测试**（`8250_port.c:2285` 的 `serial8250_iir_txen_test()`），判据是 `lsr & TEMT && iir & NO_INT`。mini-vmm 的 LSR 有 TEMT，但 IIR 报的是 THRI 而不是 NO_INT，所以不置 `UART_BUG_TXEN`，皆大欢喜。

**第 21 步那次多出来的 IIR 读，是 MCR.OUT2 门控的一次现场演示。** 注意第 8–14 步的 THRE 测试之后没有多余的 IIR 读，而第 17–20 步的 TXEN 测试之后就有；两者之间唯一发生的事，是第 16 步把 MCR 从 0x01 改成了 0x09——**OUT2 被置上了**。mini-vmm 的 `update_irq()` 只有在 OUT2 置位时才真的去拉 IRQ 线（`serial8250.c:98`）：

```c
    level = !(iir & UART_IIR_NO_INT) && (s->mcr & UART_MCR_OUT2)
            && !(s->mcr & UART_MCR_LOOP);
```

于是 THRE 测试期间 IER.THRI 虽然打开了，中断线却没动；TXEN 测试期间同样的操作就把 IRQ 4 拉了起来，等 `serial8250_interrupt()` 真正跑到时 IER 已经被第 20 步清零，它读到 IIR=0x01（NO_INT）就返回了——这就是第 21 步。

PC 上 COM 口的中断要经过 MCR.OUT2 这个门控才能到 PIC，是 IBM PC/AT 的板级接线决定的，不是 16550 芯片本身的功能；`8250_port.c:2277` 的注释 “Most PC uarts need OUT2 raised to enable interrupts” 说的就是这件事。**如果 VMM 不实现这个门控，上面这条链路就会提前一步发生**：THRE 测试期间就会有中断，虽然不至于出错，但它说明你的模型和真硬件的行为已经分叉了。

第 23–26 步是 `serial8250_set_termios()` 在收尾：IER 设成 `RLSI|RDI`（接收相关的中断），分频器设成 9600，FCR 设成 `ENABLE|R_TRIG_10`（`uart_config[PORT_16550A].fcr`，`8250_port.c:70`），MCR 补上 RTS。从这一刻起串口是中断驱动的：发送时 `serial8250_start_tx()` 打开 IER.THRI，靠 THRE 中断一批批送字节。

### 2.7 IIR 的优先级与“只报一个”

16550 的中断源有四类，IIR 的 bit3:1 只报告当前优先级最高的那一个：接收线状态（0b011）> 接收数据可用（0b010）> THR 空（0b001）> modem 状态（0b000）。bit0 反过来——**0 表示有中断，1 表示没有**。

mini-vmm 只实现中间两类（`serial8250.c:81` 的 `update_irq()`）：

```c
    uint8_t iir = UART_IIR_NO_INT;

    if ((s->ier & UART_IER_RDI) && !rx_empty(s))
        iir = UART_IIR_RDI;
    else if ((s->ier & UART_IER_THRI) && s->thri_pending)
        iir = UART_IIR_THRI;
```

两个约束在这几行里：**IIR 报告的必须是当前实际有效的中断**（所以每次寄存器访问之后都重算一遍，`serial_read()` 和 `serial_write()` 结尾都调 `update_irq()`），以及**读 IIR 拿到 THRI 即视为应答**（`serial8250.c:176`），这是 16550 的规定——THR 空中断的清除条件有两个，写 THR 或者读 IIR，少实现一个就会让中断一直挂着。

顺带说明一个容易写错的地方：`update_irq()` 里的 `level != s->irq_level` 判断不是优化，是必需的。IOAPIC 上 ISA IRQ 是边沿触发，每一次新的中断都需要一个真实的 0→1 跳变；如果每次访问都无条件调一次 `KVM_IRQ_LINE(level=1)`，KVM 侧看到的是电平没变，不会产生新的边沿，第二个字节的中断就丢了。卷四第 7 节详细讨论过这条链路。

### 2.8 ttyS1/2/3：0xFF 是怎么让探测失败的

trace 里 0x2f9、0x3e9、0x2e9 各有 6 次访问，一次不多一次不少：

```
unhandled   02f9 R1 ff rip=...io_serial_in+0x13
unhandled   02f9 W1 00 rip=...io_serial_out+0x15
unhandled   02f9 R1 ff rip=...io_serial_in+0x13
unhandled   02f9 W1 0f rip=...io_serial_out+0x15
unhandled   02f9 R1 ff rip=...io_serial_in+0x13
unhandled   02f9 W1 ff rip=...io_serial_out+0x15
```

这正是第 2.4 节第 1–6 步的 IER 存在性测试，而且**只有这 6 步**。因为 `scratch2 = 0xff & 0x0f = 0x0f ≠ 0`，`8250_port.c:1151` 的判断当场失败，`goto out`，`port->type` 保持 `PORT_UNKNOWN`，所以 `/proc/tty/driver/serial_8250` 里它们是 `uart:unknown`。

这里有个值得想一想的地方：**如果未注册端口读回 0x00 而不是 0xFF，结果也是失败**，因为 `scratch3` 会是 0 而不是 0x0f。两条路都失败，但失败的位置不同。0xFF 是对的那一个，理由不在这里——在第 7 节，8237 DMA 控制器那个例子里，0xFF 和 0x00 会得出完全相反的结论。

注意第 6 步写回去的是 `scratch`，也就是第 1 步读到的 0xFF。驱动老老实实地把“旧值”还原到了一个不存在的端口上。设备模型必须能接住这种写（丢弃即可），不能因为“这个值不合法”就报错。

### 2.9 mini-vmm 的实现边界

把前面几节的结论汇总，mini-vmm 的 16550A 模型里真正**必需**的部分只有这些：

| 行为 | 谁依赖它 | 不做的后果 |
|---|---|---|
| IER 低 4 位可读写 | `autoconfig()` 存在性测试 | 端口被判为不存在，`console=ttyS0` 无效 |
| FCR.bit0 反映到 IIR.bit7:6 | `autoconfig()` 类型判定 | 被认成 8250 或 16450，FIFO 不启用 |
| LSR 的 THRE/TEMT 恒置位 | earlyprintk、`wait_for_xmitr` | 输出卡死或极慢 |
| LSR.DR 跟随接收缓冲 | tty 收字符 | 键盘输入收不到 |
| 打开 IER.THRI 时补一次 THRI | THRE bug 测试、`start_tx` | 被扣 `UART_BUG_THRE`，改成定时器轮询 |
| 读 IIR 应答 THRI | 16550 语义 | 中断一直挂着，中断风暴 |
| MCR.OUT2 门控中断 | PC/AT 板级接线 | 探测期间出现不该有的中断 |
| MSR 常态 `DCD|DSR|CTS` | tty 的载波检测 | 终端被挂断 |
| DLAB 复用偏移 0/1 | 每一段代码都在用 | 分频器写进 THR，输出乱码 |

**不必需**的部分（在这套配置下）：回环模式、EFR、波特率真的生效、FIFO 真的有深度、LSR 的错误位、MSR 的 delta 位、SCR。mini-vmm 实现了回环和 SCR，没实现其余的。

EFR 这一条值得单独说一句，回应 2.1 节留下的问题。`autoconfig()` 第 9–11 步的 `LCR=0xBF`、`EFR=0`、`LCR=0` 里那次 EFR 写落到 FCR 上，FIFO 被关掉，紧接着第 12 步又写 `FCR=UART_FCR_ENABLE_FIFO` 重新打开，第 13 步才读 IIR。这不是侥幸：真 16550A 上这次写同样落在 FCR 上，Linux 的探测顺序本来就是按这个前提排的。

`autoconfig_16550a()` 的变体探测（`8250_port.c:958` 起，`CONFIG_SERIAL_8250_16550A_VARIANTS=y` 时执行）判断“有没有 EFR”的依据是读回值：先在 LCR=0x80 下读偏移 2，读到 0 才怀疑是 ST16C650V1，往里写 0xA8 再验证；否则换 LCR=0xBF 再读，读到 0 就判定有 EFR（`autoconfig_has_efr()`），读不到芯片 ID 时结论是 ST16650V2。真 16550A 两次读到的都是 IIR（FIFO 开着时为 0xC1），不为 0，于是探测继续往下走 NatSemi、TI16750、XScale 和 `size_fifo()`，最终仍是 16550A。往 EFR 写 0xA8 只发生在第一次读到 0 之后，16550A 走不到那一步。

所以对 16550A 来说，“这颗芯片没有 EFR”的正确表达就是什么都不做。把 `LCR == 0xBF` 时的偏移 2 改成读回 0、写丢弃，在关掉该选项的内核上测试一字不变，在打开该选项的内核上却会把端口认成 ST16650V2。这和本卷反复出现的那条是同一件事：**否定答案要用驱动认得的方式给出**，而驱动认得什么只能从驱动源码和真硬件的行为里查，不能凭“读回 0 就是不存在”的直觉。`tests/unit/serial8250_test.c` 按 `8250_port.c` 的访问顺序回放了 autoconfig 的两种配置分支，不依赖手头内核的配置。

回环模式是“实现了但默认配置下用不到”的一块。回环时 modem 输入线由 MCR 输出线直接驱动（RTS → CTS、DTR → DSR、OUT1 → RI、OUT2 → DCD），`src/devices/serial8250.c:127` 的 `msr_value()` 照此计算 MSR。用到它的有两处：`autoconfig()` 的 LOOP 测试写 `MCR = LOOP|OUT2|RTS` 后要读到 MSR 高 4 位 = `DCD|CTS` = 0x90，`size_fifo()` 靠回环数 FIFO 深度。但 x86 上 COM1–COM3 带 `UPF_SKIP_TEST`，LOOP 测试不执行；COM4 不带，可它在更早的 IER 测试就已经出局；`size_fifo()` 只在打开 `CONFIG_SERIAL_8250_16550A_VARIANTS` 时执行。所以这段代码在当前配置下从未被执行过，留着它是为了把串口挪到 0x2e8 或者 guest 打开那个选项时设备仍然对，`tests/unit/serial8250_test.c` 回放了这两种分支。

## 3. 8254 PIT：一条在 trace 里完全看不见的设备

### 3.1 一个不该被忽略的空白

第 1.3 节那张表里没有 0x40–0x43，也没有 0x61。这两组端口是 8254 PIT 和它的门控/扬声器端口，是 x86 上最古老的定时器。它们没出现有两层原因，第一层是 guest 根本没拿 PIT 校准 TSC。默认启动的日志是：

```
[    0.016811] tsc: Detected 3193.914 MHz processor
```

guest 内核开了 `CONFIG_KVM_GUEST`，检测到 KVM 后 `kvmclock_init()` 把 `x86_platform.calibrate_tsc` 和 `calibrate_cpu` 都换成 `kvm_get_tsc_khz()`（`arch/x86/kernel/kvmclock.c:346-347`），TSC 频率直接从 kvmclock 的 pvclock 参数里换算出来，PIT 校准那一整套代码一次都不跑。要看 PIT 校准，得在命令行加 `no-kvmclock`，下面 3.3 到 3.5 节的数据都来自这样的启动。

第二层原因在 `irqchip_create()`（`src/devices/irqchip.c:43-44`）：

```c
    pit.flags = KVM_PIT_SPEAKER_DUMMY;
    if (ioctl(vm->vm_fd, KVM_CREATE_PIT2, &pit) < 0) {
```

`KVM_CREATE_PIT2` 让 KVM 在内核里注册两个 PIO 设备（host `arch/x86/kvm/i8254.c:706` 与 `:714`）：

```c
	kvm_iodevice_init(&pit->dev, &pit_dev_ops);
	ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS, KVM_PIT_BASE_ADDRESS,
				      KVM_PIT_MEM_LENGTH, &pit->dev);
	...
	if (flags & KVM_PIT_SPEAKER_DUMMY) {
		kvm_iodevice_init(&pit->speaker_dev, &speaker_dev_ops);
		ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS,
					      KVM_SPEAKER_BASE_ADDRESS, 4,
					      &pit->speaker_dev);
```

`KVM_PIT_BASE_ADDRESS` = 0x40、长度 4，`KVM_SPEAKER_BASE_ADDRESS` = 0x61（`i8254.h:52`）。guest 对这些端口的 `in`/`out` 仍然会触发一次 VM exit，但 exit 在 host 内核里就被 `pit_ioport_write()` / `speaker_ioport_read()` 消化掉，`KVM_RUN` 根本不返回用户态。guest 启动时确实会编程 PIT（它是 GSI 0 上的时钟中断源，见 3.6 节），这些访问同样不出现在 trace 里。于是从 VMM 的角度看，这台机器上不存在 PIT。

这是本卷方法的一个重要边界：**`--trace-pio` 看到的是“VMM 负责的设备”，不是“guest 访问过的端口”。** 判断一个端口去了哪里，要先看 KVM 内核里注册了什么。`--kernel-irqchip split` 时情况相反，PIT 由 `src/devices/i8254.c` 在用户态模拟，0x40–0x43 和 0x61 会出现在 trace 里，`tests/e2e/legacy-devices.sh` 的 trace 用例按 irqchip 模式分别断言这一点。

### 3.2 `KVM_PIT_SPEAKER_DUMMY` 到底做了什么

这个标志的名字有误导性——它和发声毫无关系。端口 0x61 在 PC/AT 上是 NMI 状态与控制寄存器，低两位是给 PIT 通道 2 用的：

| 位 | 含义 |
|---|---|
| 0 | 通道 2 的 GATE（1 = 允许计数） |
| 1 | 扬声器数据使能（把通道 2 的 OUT 接到喇叭上） |
| 4 | refresh clock，约 15 µs 翻转一次 |
| 5 | 通道 2 当前的 OUT 电平 |

不带这个标志时，KVM 只接管 0x40–0x43，0x61 会掉到用户态。而 Linux 的两个 PIT 校准函数都要靠 0x61 干活：拉高 bit0 让通道 2 开始计数，然后轮询 bit5 等待计数结束。VMM 如果不处理 0x61，读回 0xFF 时 bit5 恒为 1，`pit_calibrate_tsc()` 里的 `while ((inb(0x61) & 0x20) == 0)` 一进去就退出，`pitcnt` 为 0，小于 `loopmin`，直接返回 `ULONG_MAX`。

KVM 的实现只有十几行（host `i8254.c:583` 的 `speaker_ioport_write()` 与 `:603` 的 `speaker_ioport_read()`）：

```c
	mutex_lock(&pit_state->lock);
	pit_state->speaker_data_on = (val >> 1) & 1;
	pit_set_gate(pit, 2, val & 1);
	mutex_unlock(&pit_state->lock);
```

```c
	/* Refresh clock toggles at about 15us. We approximate as 2^14ns. */
	refresh_clock = ((unsigned int)ktime_to_ns(ktime_get()) >> 14) & 1;

	mutex_lock(&pit_state->lock);
	ret = ((pit_state->speaker_data_on << 1) | pit_get_gate(pit, 2) |
		(pit_get_out(pit, 2) << 5) | (refresh_clock << 4));
```

写只取 bit1 和 bit0，读把 GATE、OUT 和一个用主机时钟造出来的 refresh clock 拼回去。**它做的全部事情就是把 0x61 和通道 2 的状态机接上**，喇叭那一位只是存下来给 `KVM_GET_PIT2` 用。

还有一个细节值得注意：speaker 设备注册的长度是 4，覆盖 0x61–0x64，但两个回调的第一句都是 `if (addr != KVM_SPEAKER_BASE_ADDRESS) return -EOPNOTSUPP;`。`__kvm_io_bus_write()`（host `virt/kvm/kvm_main.c:5439`）在设备返回非 0 时会继续找下一个设备，都不行就返回 `-EOPNOTSUPP`，最终退回用户态。所以 0x62/0x63/0x64 仍然归 VMM。trace 里 0x64 实实在在有访问（第 5 节的 i8042 命令端口），如果 KVM 真的把 0x64 吞掉了，键盘控制器就一次也探测不到。

mini-vmm 也正因为这样才把 i8042 拆成两个单字节设备注册（`src/devices/i8042.c:344` 起的注释）。如果按 `[0x60, 0x65)` 一整段注册，mini-vmm 自己的表不会报冲突（`vmm_register_pio()` 只检查自己的表），但 0x61 的访问永远不会到达用户态，这个设备的一部分就是死的——而且没有任何提示。

### 3.3 `quick_pit_calibrate()`：成不成功取决于读一次 PIT 有多贵

没有 kvmclock、也拿不到 CPUID 0x15 或 MSR 给出的频率时，Linux 用 PIT 校准 TSC，有快慢两条路。快路是 `quick_pit_calibrate()`（`arch/x86/kernel/tsc.c:557`），思路很漂亮：

```c
	/* Set the Gate high, disable speaker */
	outb((inb(0x61) & ~0x02) | 0x01, 0x61);
	/* Counter 2, mode 0 (one-shot), binary count */
	outb(0xb0, 0x43);
	/* Start at 0xffff */
	outb(0xff, 0x42);
	outb(0xff, 0x42);
```

把通道 2 设成模式 0（一次性、到达终止计数时 OUT 拉高）、二进制计数、初值 0xFFFF，然后反复读计数器的高字节，记下每次高字节变化时的 TSC 值。PIT 的时基是 1193182 Hz，高字节每变一次正好是 256 个 PIT tick ≈ 214.5 µs，于是两次高字节变化之间的 TSC 差就直接给出 TSC 频率。

读计数器用的是 `pit_verify_msb()`（`tsc.c:520`）：

```c
static inline int pit_verify_msb(unsigned char val)
{
	/* Ignore LSB */
	inb(0x42);
	return inb(0x42) == val;
}
```

每次两个 `inb`——PIT 的数据端口是先低后高，所以要连读两次才能拿到高字节。

关键在精度控制。`tsc.c:603-605`：

```c
			if (i == 1 &&
			    d1 + d2 >= (delta * MAX_QUICK_PIT_ITERATIONS) >> 11)
				return 0;
```

`d1`、`d2` 是两次采样各自最后一段循环的 TSC 跨度，本质上就是“读一次 PIT 要多久”。真硬件上一次 `inb` 约 1 µs，`d1+d2` 只有几微秒；`delta` 是 214.5 µs 对应的 TSC 周期数。外推一下如果误差永远降不到 500 ppm，**直接返回 0，一个字都不打印**。这个函数上面那段注释（`tsc.c:485-488`）说得很直白：它检查的是“sufficiently fast and non-virtualized hardware”。在 KVM 下每个 `inb(0x42)` 都是一次 VM exit——虽然由 host 内核就地处理、不回用户态，但依然要走 VMEXIT/VMRUN 这一整套。

本机（WSL2，KVM 本身跑在 Hyper-V 的虚拟机里，属于嵌套虚拟化）读一次 PIT 端口有多贵，可以用 guest 工具 `pitprobe` 直接量出来：它在 guest 用户态照抄慢路的轮询循环（见 3.5 节），20 轮里每次读 0x61 的最短间隔中位数是 **21824 个 TSC 周期**，按 3.19 GHz 折算约 6.8 µs，比真硬件慢六七倍。`quick_pit_calibrate()` 的 500 ppm 外推阈值在这个开销下过不去，加 `no-kvmclock` 连续启动 6 次，日志里 `Fast TSC calibration using PIT`（`tsc.c:644`）和 `Fast TSC calibration failed`（`tsc.c:625`）都没有出现——三个出口里只有 `tsc.c:605` 那条 fail-fast 是静默的，所以快路每次都是静默失败。

### 3.4 `pit_calibrate_tsc()`：慢路

快路返回 0 时 `native_calibrate_cpu()`（`tsc.c:917`）转去 `pit_hpet_ptimer_calibrate_cpu()`（`tsc.c:747`），它把慢路 `pit_calibrate_tsc()`（`tsc.c:419`）连调三次（`tsc.c:784` 的 `for (i = 0; i < 3; i++)`），每次 `CAL_MS` = 10 ms：

```c
	/* Set the Gate high, disable speaker */
	outb((inb(0x61) & ~0x02) | 0x01, 0x61);
	outb(0xb0, 0x43);
	outb(latch & 0xff, 0x42);
	outb(latch >> 8, 0x42);

	tsc = t1 = t2 = get_cycles();
	...
	while ((inb(0x61) & 0x20) == 0) {
		t2 = get_cycles();
		...
		pitcnt++;
	}
```

和快路的区别是：它不再逐次读计数器，而是**只轮询 0x61 的 bit5**（通道 2 的 OUT）等一次性计数走完，中间每转一圈记一次 TSC，用最大最小值的比例来判断这段时间有没有被 SMI 之类的东西打断。只要总时长准确，每次 I/O 慢一点也能算出正确的频率。

它依赖的 KVM 行为正好是第 3.2 节那两段代码：`outb(0xb0, 0x43)` 让 `pit_ioport_write()` 把通道 2 设成模式 0，两次 `outb(..., 0x42)` 装入初值并开始计时，`inb(0x61)` 的 bit5 由 `pit_get_out(pit, 2)` 算出来——模式 0 的公式是 `out = (d >= c->count)`（host `i8254.c:154`），`d` 是从装入初值到现在按 1193182 Hz 折算的 tick 数。也就是说 KVM 的 PIT 通道 2 根本没有“计数器”，它是用 host 的 `ktime_get()` 反推出来的，**慢路测的其实是 host 的时钟**。`pitprobe` 量到的 10 ms 窗口中位数是 31919008 个 TSC 周期，即 3191 MHz，和 kvmclock 给出的 3193.914 MHz 只差千分之一，说明通道 2 的计时本身是准的。

三轮的结果最后在 `tsc.c:850` 起取舍。mini-vmm 不提供 HPET 表，FADT 里也没有 PM timer，于是 `hpet`、`ref1`、`ref2` 全为 0：三轮里只要有一轮成功，就走 `tsc.c:873-876` 打印 `Using PIT calibration value` 并取三轮的最小值（`tsc.c:800`，任何干扰都只会让测出来的频率偏高）；三轮全部判废时走 `tsc.c:850-857`。

### 3.5 慢路在本机上总是失败

慢路判废的条件在 `tsc.c:476`：

```c
	if (pitcnt < loopmin || tscmax > 10 * tscmin)
		return ULONG_MAX;
```

`pitcnt` 是 10 ms 里转了多少圈，`loopmin` 是 1000；`tscmin` / `tscmax` 是相邻两次 `get_cycles()` 之差的最小值和最大值。两条判据在本机上都很紧：读一次 0x61 约 6.8 µs，10 ms 只够转 1000 到 1400 圈，刚好贴着下限；而 vCPU 线程只要被 host 调度一次，或者某次 exit 在嵌套的 Hyper-V 层多耽搁一会儿，某一圈的间隔就会超过最短间隔的 10 倍。`pitprobe 20` 的逐轮输出把这两件事都摆出来了：

```
round 0: reads 1386 min 18880 max 391328 window 31904697 reject
round 5: reads 1277 min 21440 max 207941 window 31933349 accept
round 9: reads 866 min 21888 max 374016 window 31827958 reject
...
pitprobe: 5/20 accepted, median min read 21824 cycles, median window 31919008 cycles = 3191 MHz
```

`pitprobe` 跑在用户态、不能关中断，guest 自己的时钟中断也会落进循环，所以 5/20 不能直接当成内核那三轮的通过率，它的用处是把判废的原因（读次数贴着下限、最长间隔是最短的十几倍）摆出来。内核的结果要看启动日志：加 `no-kvmclock` 的 6 次启动全部是三轮判废，日志都是

```
[    0.010000] tsc: Unable to calibrate against PIT
[    0.012000] tsc: Marking TSC unstable due to could not calculate TSC khz
[    0.016000] Calibrating delay loop... 82.30 BogoMIPS (lpj=41152)
```

`No reference (HPET/PMTIMER) available` 之后 `native_calibrate_cpu()` 返回 0，TSC 被标成不稳定，clocksource 最后落在 `refined-jiffies`，BogoMIPS 只有几十（6 次里 24 到 82 之间，正常值是 6387）。

对写 VMM 的人，这条有两层意义。第一，**这不是 VMM 的缺陷**：PIT 通道 2 的行为由 KVM 内核模块提供，VMM 这一侧没有任何可调的东西；真正的原因是读一次端口的开销和抖动，和卷六第 6 节讲的“vCPU 就是一个普通线程”是同一件事。这句话针对的是默认的内核 irqchip；`--kernel-irqchip split` 时通道 2 和 0x61 由 `src/devices/i8254.c` 在用户态模拟，每次读 0x61 多走一趟用户态，读次数和抖动都变了，三种结局出现的比例跟着变，见 blog 37（split irqchip P4）第六节。第二，**测试断言要按 guest 的配置选判据，并把所有合法结局一并接受**。`tests/lib.sh` 的 `expect_tsc_calibrated` 先看日志里有没有 `kvm-clock: Using msrs`：有就只要求 `tsc: Detected`；没有就接受 `Fast TSC calibration using PIT`、`Using PIT calibration value`、`Unable to calibrate against PIT` 三者之一。三种 PIT 结局分别对应读一次 PIT 很便宜、较贵、又贵又抖的 host，都不能指向 VMM 的某个具体缺陷；而 `Fast TSC calibration failed`（快路的非静默失败）如果出现，说明读 PIT 的开销分布和上面的分析完全对不上，那才值得停下来看。

### 3.6 PIT 作为中断源

除了校准，PIT 还是 GSI 0 上的时钟中断源。`irqchip_create()` 的注释提到它，卷四第 8 节讲过完整的中断路径。这里只补一条 trace 侧的观察：一次 `--smp 4` 启动后 guest 里 `/proc/interrupts` 的第 0 行是

```
   0:       2596          0          0          0  IO-APIC     0-edge      timer
```

这 2596 次中断全部由 KVM 内核态的 hrtimer 产生并注入，用户态既不知道它们发生过，也没有为它们付任何代价。对比一下第 1.3 节里串口的 41450 次用户态往返，能直观地看出“把设备放进内核”这件事的收益有多大。

`..TIMER: vector=0x30 apic1=0 pin1=0 apic2=-1 pin2=-1` 这行日志说明定时器走的是 IOAPIC 的 pin 0、向量 0x30，没有用 pin2 备份路径。卷五第 8 节讲过为什么 mini-vmm 不能照抄 QEMU 那套“IRQ0 接 pin 2 加 Interrupt Source Override”的写法——KVM 的默认 GSI 路由是恒等映射，照抄会让时钟中断丢失。

### 3.7 这一节对写 VMM 的意义

PIT 是本卷里唯一一个“**正确做法是不做**”的设备。默认的内核 irqchip 下 mini-vmm 没有一行 PIT 模拟代码，只有 `irqchip_create()` 里的一次 `KVM_CREATE_PIT2` 和一个标志位。要点有三条：

1. **`KVM_PIT_SPEAKER_DUMMY` 必须带上。** 不带的话 0x61 掉到用户态，没有 kvmclock 的 guest 校准 TSC 时慢路每轮都读不到 OUT2，症状是 `Unable to calibrate against PIT` 之后 TSC 被标成不稳定，离“端口 0x61 没人应答”这个原因非常远。
2. **`KVM_CREATE_PIT2` 要在 `KVM_CREATE_IRQCHIP` 之后。** PIT 的中断要挂到 GSI 0，没有 irqchip 就没地方挂。mini-vmm 的顺序在 `src/devices/irqchip.c:29` 和 `:44`。
3. **别去占 0x61。** 它已经被内核接管了，用户态注册的设备永远收不到访问。

## 4. CMOS RTC：UIP 协议与两个 1 秒超时

### 4.1 索引/数据端口与 NMI 位

MC146818 只占两个端口。0x70 是索引口（只写），0x71 是数据口。读一个寄存器要两次 I/O：先往 0x70 写寄存器号，再从 0x71 读值。x86 上的封装在 `arch/x86/kernel/rtc.c:80`：

```c
unsigned char rtc_cmos_read(unsigned char addr)
{
	unsigned char val;

	lock_cmos_prefix(addr);
	outb(addr, RTC_PORT(0));
	val = inb(RTC_PORT(1));
	lock_cmos_suffix(addr);
	return val;
}
```

`RTC_PORT(x)` = `0x70 + x`（`arch/x86/include/asm/mc146818rtc.h`），`lock_cmos_prefix/suffix` 在 64 位下是空的。注意这里用的是 `outb`/`inb` 而不是 `outb_p`/`inb_p`——所以 RTC 访问本来就不带第 7.2 节那种 0x80 延时写，trace 里 0x70/0x71 永远是干净的两两成对。

0x70 的 bit7 是 NMI 屏蔽位，跟寄存器选择无关：写 0x80|reg 表示“选 reg 并且屏蔽 NMI”。mini-vmm 只取低 7 位（`src/devices/rtc.c:97`）：

```c
    if (off == 0) {
        /* bit7 是 NMI 屏蔽位，和寄存器选择无关 */
        g_rtc.index = v & 0x7f;
```

寄存器布局的前 14 个字节是时钟和控制，剩下 114 字节是 CMOS RAM：

| 索引 | 内容 | mini-vmm 的值 |
|---|---|---|
| 0x00/0x02/0x04 | 秒 / 分 / 时 | 每次读现取 host UTC |
| 0x06 | 星期（1–7） | 有实现，但 Linux 不读 |
| 0x07/0x08/0x09 | 日 / 月 / 年（两位） | 现取 |
| 0x0A | 寄存器 A：UIP(bit7)、时基、周期中断分频 | 0x26，**UIP 恒为 0** |
| 0x0B | 寄存器 B：中断使能、24 小时制(bit1)、BCD/二进制(bit2) | 0x02 |
| 0x0C | 寄存器 C：中断标志（读后清零） | 0 |
| 0x0D | 寄存器 D：电池有效(bit7) | 0x80 |
| 0x32 | 世纪（由 FADT 指定的索引） | 现取 |
| 其余 | CMOS RAM | 可读可写的普通字节 |

### 4.2 UIP 协议：`mc146818_avoid_UIP()`

真硬件的 MC146818 每秒会进入一次“更新周期”，持续约 2 ms，期间时间寄存器的内容未定义。芯片在更新开始前 244 µs 把寄存器 A 的 bit7（UIP）置起来。软件要读到一致的时间，就得在 UIP 为 0 的窗口里把全部字段读完。

Linux 的实现（`drivers/rtc/rtc-mc146818-lib.c:21`）比这还要小心一层：

```c
	for (i = 0; UIP_RECHECK_LOOPS_MS(i) < timeout; i++) {
		seconds = CMOS_READ(RTC_SECONDS);

		if (CMOS_READ(RTC_FREQ_SELECT) & RTC_UIP) { ... continue; }

		/* Revalidate the above readout */
		if (seconds != CMOS_READ(RTC_SECONDS)) { ... continue; }

		if (callback)
			callback(seconds, param);

		if (CMOS_READ(RTC_FREQ_SELECT) & RTC_UIP) { ... continue; }

		if (seconds != CMOS_READ(RTC_SECONDS)) { ... continue; }
		...
		return true;
	}
	return false;
```

先存秒、再查 UIP、再复读秒确认没变；回调读完剩下的字段之后，**再查一次 UIP、再复读一次秒**。注释说得很实在：“there is also virt...”——这套双重校验就是为虚拟机这种时间会突然跳的环境准备的。

启动期第一次走这套协议的不是时钟子系统，而是 `CONFIG_PM_TRACE_RTC`：`drivers/base/power/trace.c:279` 的 `early_resume_init()`（core_initcall）调 `read_magic_time()`，用 `mc146818_get_time(&time, 1000)` 读一次时间，打印 `PM: RTC time: 09:43:34, date: 2026-11-17`。时间子系统本来会更早地经 `x86_platform.get_wallclock` 读一次 RTC（默认是 `mach_get_cmos_time()`，`arch/x86/kernel/rtc.c:56`），但这个 guest 开了 `CONFIG_KVM_GUEST`，`kvmclock_init()` 把它换成了 `kvm_get_wallclock()`（`arch/x86/kernel/kvmclock.c:348`），墙上时间从 kvmclock 的共享页读，不碰 0x70/0x71。

**星期寄存器（0x06）没有被读。** `mc146818_get_time_callback()` 的注释明说：“Even though the RTC has RTC_DAY_OF_WEEK, we ignore it, as it is only updated by the RTC when initially set to a non-zero value.” mini-vmm 实现了它（`src/devices/rtc.c:72`），属于白写。

**世纪寄存器的索引来自 FADT，不是写死的。** `lib.c:131`：

```c
	if (acpi_gbl_FADT.header.revision >= FADT2_REVISION_ID &&
	    acpi_gbl_FADT.century) {
		p->century = CMOS_READ(acpi_gbl_FADT.century);
```

mini-vmm 在 FADT 里填的是 0x32（`src/boot/acpi.c:480`），trace 里读的就是 0x32。这是卷五“固件表必须和设备模型一致”那条铁律在 RTC 上的具体形态：**这个索引由 VMM 自己决定，但填在 FADT 里的值和 RTC 模型里认的值必须是同一个。** 填 0 的话 `p->century` 为 0，`lib.c:183` 的 `if (p.century > 19)` 不成立，年份就落在 1926 或 2026 取决于 `tm_year <= 69` 那条补偿——具体到 26 会被补成 2026，看起来居然是对的，直到 2070 年之后才出错。这种错误极难在测试里发现。

**BCD 不是可选的。** `mc146818_get_time()` 的转换条件是 `if (!(p.ctrl & RTC_DM_BINARY) || RTC_ALWAYS_BCD)`，而 x86 的 `arch/x86/include/asm/mc146818rtc.h` 里 `#define RTC_ALWAYS_BCD 1`。也就是说**不管寄存器 B 的 DM 位怎么写，x86 上 Linux 一律按 BCD 解释**。mini-vmm 用 `bin2bcd()` 编码（`src/devices/rtc.c:46`）是对的；如果哪天想改成二进制模式并把寄存器 B 的 bit2 置起来，x86 guest 会读出一个荒唐的时间。

### 4.3 非原子的读为什么也安全

mini-vmm 的实现没有内部时钟，每次读时间寄存器都现取一次 host 的 UTC（`src/devices/rtc.c:66`）：

```c
    now = time(NULL);
    gmtime_r(&now, &tm);
    switch (reg) {
    case RTC_SECONDS: return bin2bcd(tm.tm_sec);
```

于是一组时间寄存器的读**不是原子的**：秒可能取自 10:09:59，分可能取自 10:10:00，拼出来就是 10:10:59，比真实时间早了将近一分钟。

救下这一点的正是上一节那套复读协议。任何一次跨越秒边界的读，必然伴随秒字段的变化；`lib.c:74` 最后那次复读秒发现值变了就整轮重来。日期、月份、年份的进位同样只发生在秒进位的时刻，所以也被这一层兜住了。

这不是说“可以不管”，而是说明**一个看起来偷懒的实现之所以能work，往往是因为驱动那边有一套为真硬件设计的防御机制恰好也覆盖了它**。反过来，如果 VMM 把 UIP 位真的做出来（比如每秒置 2 ms），反而要额外保证 UIP 为 0 的窗口里读到的值确实一致——那才需要在 VMM 里做一次快照。mini-vmm 选择让 UIP 恒为 0，等于向 guest 承诺“我永远不在更新中”，这个承诺是它能兑现的。

### 4.4 `rtc_cmos` 驱动的探测

第二段 RTC trace 有 154 次访问，属于 `rtc_cmos` 驱动的探测和注册。平台设备在更早的时候由 `arch/x86/kernel/rtc.c:134` 的 `add_rtc_cmos()` 注册，日志是 `platform rtc_cmos: registered fallback platform RTC device`（`rtc.c:143`）：DSDT 里没有 `PNP0B00` 这类 RTC 设备，PNP 枚举不出它，内核就直接注册一个平台设备，让 `rtc-cmos` 驱动去 0x70/0x71 上找。

### 4.5 不模拟 RTC 的代价：8 万次 exit、几秒启动时间

`src/devices/rtc.c` 的文件头注释给出了不模拟 RTC 的后果。借追踪能力可以把它精确量出来：在一份副本里把 `src/main.c:665` 的 `rtc_attach()` 调用摘掉重新编译，其余完全不变，各启动一次。

| | 有 RTC 模型 | 没有 RTC 模型 |
|---|---|---|
| 整次启动的 PIO exit 总数 | 42302 | 121283 |
| 0x70 写 / 0x71 读 | 89 / 89 | 40000 / 40000 |
| `Run /init as init process` 的时刻（不开 trace，各两次） | 1.355 s / 1.350 s | 5.382 s / 4.502 s |
| 相关日志 | `PM: RTC time: ...`、`rtc_cmos rtc_cmos: setting system clock to 2026-11-17T09:58:45 UTC` | `PM: Unable to read current time from RTC`、`rtc_cmos rtc_cmos: broken or not accessible` |

八万次多出来的 exit，来自两次各 1 秒的超时。`mc146818_avoid_UIP()` 的循环上界是 `UIP_RECHECK_LOOPS_MS(i) < timeout`，`UIP_RECHECK_DELAY_MS` = 10，`timeout` = 1000，所以最多转 10000 圈；每圈两次 `CMOS_READ`（秒和寄存器 A），每次 `CMOS_READ` 是一次写 0x70 加一次读 0x71。10000 × 2 × 2 = 40000 次端口访问，也就是 20000 次写 0x70 加 20000 次读 0x71。两个调用者各超时一次——`read_magic_time()`（`drivers/base/power/trace.c:123`）和 `cmos_do_probe()` 里的 `mc146818_does_rtc_work()`——正好凑出 40000 / 40000。每圈还有一次 `udelay(100)`，10000 圈就是 1 秒，两次就是 2 秒；剩下的 1–2 秒是那 8 万次 exit 本身：这台 host 是 Hyper-V 之上的嵌套 KVM，一次陷出到用户态的 PIO 往返要十几到二十几微秒，8 万次就是一两秒，而且随 host 负载浮动，所以两次启动差了将近 0.9 秒。在裸机 KVM 上一次 PIO exit 只要一两微秒，同样的实验多出来的时间就几乎只剩那 2 秒的 `udelay`。

死循环的原因只有一句话：未注册端口读回 0xFF，寄存器 A 的 bit7（UIP）恒为 1，`lib.c:43` 的判断永远成立。

这条数据是本卷命题最直白的例子。RTC 在这台虚拟机上不提供任何实际功能——没有闹钟、没有周期中断、guest 里 `/proc/interrupts` 的 IRQ 8 计数是 0——但**不实现它要付出启动慢好几秒、多 8 万次用户态往返的代价**，仅仅因为驱动为了等一个真硬件才有的 2 ms 窗口写了一个 1 秒的超时循环。

### 4.6 mini-vmm 的实现边界

| 做了 | 为什么 |
|---|---|
| 索引 + 数据两端口，索引取低 7 位 | 基本协议 |
| 时间寄存器现取 host UTC，BCD 编码 | `RTC_ALWAYS_BCD`，见 4.2 |
| 寄存器 A = 0x26，UIP 恒 0 | 让 `mc146818_avoid_UIP()` 一次通过 |
| 寄存器 B = 0x02（24 小时制） | `rtc-cmos.c:1098` 的硬性检查 |
| 寄存器 C 读回 0 | 没有挂起的中断 |
| 寄存器 D bit7 = 1 | 电池有效，CMOS 内容可信 |
| 世纪寄存器 0x32 与 FADT 一致 | 见 4.2 |
| 128 字节 CMOS RAM 可读写 | NVRAM 接口 |
| 写寄存器 C/D 被忽略 | 只读寄存器 |

| 没做 | 后果 |
|---|---|
| 内部时钟（时间不会自己走） | 无。每次读都现取 host 时间，等价于走得很准 |
| 设置时间（写时间寄存器当普通 CMOS 字节） | `hwclock -w` 写进去读不回来。guest 里没人这么干 |
| UIP 位真的翻转 | 无。恒 0 是一个更强也更容易兑现的承诺 |
| 周期中断 / 闹钟中断（IRQ 8） | `/proc/interrupts` 里 IRQ 8 恒为 0。`rtc-cmos` 仍然注册成功 |
| 星期寄存器被使用 | 无，Linux 不读 |

还有一件值得一提的事：卷六第 3.6 节说过，AP 唤醒时 `smpboot_setup_warm_reset_vector()` 会写 CMOS 索引 `0x0F`（`CMOS_WRITE(0xa, 0xf)`）。那次写落在 `rtc_write()` 的“普通 CMOS 字节”分支上，被老老实实存进 `g_rtc.cmos[0x0f]`。**如果 RTC 模型对未知索引报错或者干脆不存在，`do_boot_cpu()` 的第一步就会踩空。** 这也是为什么 `--smp 1` 和 `--smp 4` 都依赖这个设备。

## 5. i8042：把“不存在”讲清楚比把“存在”讲清楚更难

i8042 是本卷里唯一一个 mini-vmm 需要同时表达“有”和“没有”的设备：KBD 口要装成一个正常工作的 AT 键盘，AUX 口（PS/2 鼠标）要让驱动干脆利落地判定不存在。后者花的力气比前者多。

### 5.1 两个端口、三个寄存器

| 端口 | 读 | 写 |
|---|---|---|
| 0x60 | 输出缓冲（控制器应答或设备数据） | 命令参数，或转发给键盘设备的字节 |
| 0x64 | 状态寄存器 | 控制器命令 |

状态寄存器的位：

| 位 | 名字 | 含义 |
|---|---|---|
| 0 | OBF | 输出缓冲满，主机可以读 0x60 |
| 1 | IBF | 输入缓冲满，主机**不能**再写 |
| 2 | SYSFLAG | 自检通过 |
| 3 | CMDDAT | 上一次写的是 0x64（命令）而不是 0x60（数据） |
| 4 | KEYLOCK | 1 表示键盘没被锁 |
| 5 | AUXDATA | 输出缓冲里的字节来自 AUX 口 |

驱动的每一次访问都要先过这两道等待（`drivers/input/serio/i8042.c:230`、`:241`）：

```c
static int i8042_wait_read(void)
{
	int i = 0;

	while ((~i8042_read_status() & I8042_STR_OBF) && (i < I8042_CTL_TIMEOUT)) {
		udelay(50);
		i++;
	}
	return -(i == I8042_CTL_TIMEOUT);
}
```

`I8042_CTL_TIMEOUT` 是 10000（`i8042.h:34`），每圈 `udelay(50)`，**一次超时正好 0.5 秒**。这个数字很重要：i8042 的探测路径上有十几条命令，每条命令要等一次写就绪、可能还要等一次读就绪，任何一条没应答都要白等半秒。`src/devices/i8042.c` 的文件头注释写的就是这个 0.5 秒和它的出处。

mini-vmm 的状态寄存器是**算出来**的，不是存起来的（`src/devices/i8042.c:296`）：

```c
        v = STR_SYSFLAG | STR_KEYLOCK | g_kbc.status_cmd;
        if (g_kbc.count) {
            v |= STR_OBF;
            if (g_kbc.obuf[g_kbc.head].aux)
                v |= STR_AUXDATA;
        }
```

IBF 永远是 0——我们“瞬间”消化掉每一次写，所以输入缓冲从来不满，`i8042_wait_write()` 一圈都不用转。这是虚拟设备相对真硬件的一个纯赚：真 i8042 的一条命令要几十微秒。

```
21  0064 R 15     wait_read：OBF=1
22  0064 R 15     AUXDATA 检查——没有 0x20，return -1                         :316
23  0064 R 15     wait_write
24  0064 W a9     I8042_CMD_AUX_TEST                                         :835
25  0064 R 1d
26  0060 R 01     param = 0x01，非 0 且不是 0xfa/0xff ⇒ return -1            :836
27  0064 R 1c
28  0064 W 60     I8042_CMD_CTL_WCTR
29  0064 R 1c
30  0060 W 65     CTR 还原成 0x65
```

第 3–9 步那个“连读两次 CTR 直到两次相同”的循环（`i8042.c:995-1009`）容易被忽略：**CTR 必须是稳定可读的**。如果 VMM 每次读 CTR 返回不同的值（比如把某个位跟时间挂钩），这个循环最多转 10 次然后打印 `Unable to get stable CTR read` 放弃整个 i8042。

第 14 步写进去的 CTR 是 0x74，也就是在初值 0x65 的基础上置 `KBDDIS`(0x10)、清 `KBDINT`(0x01)——探测期间关掉键盘口和它的中断，改成纯轮询。这解释了一个乍看矛盾的现象：mini-vmm 明明为键盘实现了 IRQ 1，但控制器命令的应答（第 5、9、26 步）全是轮询读出来的。mini-vmm 正是照这个分工写的（`src/devices/i8042.c:115`）：

```c
static void update_irq(void)
{
    const struct obuf_ent *e = &g_kbc.obuf[g_kbc.head];

    set_irq(g_kbc.count && e->from_kbd && (g_kbc.ctr & CTR_KBDINT) &&
            !(g_kbc.ctr & CTR_KBDDIS));
}
```

只有**键盘设备**发出的字节（`from_kbd`）才打中断，控制器自己的应答不打；而且要看 CTR 里的 KBDINT/KBDDIS。

### 5.3 自检命令没有被执行

trace 里没有 0xAA（控制器自检）也没有 0xAB（键盘口测试）。原因在 `i8042.c:57`：

```c
#define I8042_RESET_DEFAULT	I8042_RESET_ON_S2RAM
static enum i8042_controller_reset_mode i8042_reset = I8042_RESET_DEFAULT;
```

`i8042_probe()`（`i8042.c:1537`）只有在 `i8042_reset == I8042_RESET_ALWAYS` 或者正在从 S2RAM 恢复时才调 `i8042_controller_selftest()`。默认两者都不成立，所以自检被跳过。mini-vmm 实现了 `CMD_SELF_TEST` 回 0x55、`CMD_KBD_TEST` 回 0x00（`src/devices/i8042.c:228`、`:231`），在这套配置下是白写的——但这两条实现起来各只有一行，而且加上 `i8042.reset=always` 内核参数就会用到，留着是合理的。

### 5.4 AUX 判定的两道关

让驱动相信“没有 PS/2 鼠标”有两种做法，难度差别很大。

**笨办法**：对 0xD3 和 0xA9 都不应答。这样 `i8042_wait_read()` 各超时一次，两次 0.5 秒，启动凭空慢 1 秒，而且日志里没有任何解释。

**正确办法**：让两道检查都以“明确的否定答案”失败，一次都不超时。`i8042_check_aux()` 的两道关是这样设计的：

第一关是**内部回环**（`i8042.c:824`）。驱动发 `I8042_CMD_AUX_LOOP`（0xD3）带参数 0x5a，期望控制器把这个字节原样放回输出缓冲**并且置上 AUXDATA**。判据藏在 `__i8042_command()` 里（`i8042.c:316`）：

```c
		if (command == I8042_CMD_AUX_LOOP &&
		    !(i8042_read_status() & I8042_STR_AUXDATA)) {
			dbg("     -- i8042 (auxerr)\n");
			return -1;
		}
```

mini-vmm 把字节放回去了，但**故意不置 AUXDATA**（`src/devices/i8042.c:271`）：

```c
    case CMD_WRITE_AUX_OBUF:
        /* 故意不置 AUXDATA：让驱动判定 AUX 回环失败，见文件头 */
        obuf_push(v, false, false);
        break;
```

于是第 21 步读到的状态是 0x15（OBF 置位、AUXDATA 清零），驱动当场返回 -1，**而且它连 0x60 都没读**——第 22 步之后直接跳到下一条命令。这个细节很关键：那个 0x5a 还留在输出缓冲里。mini-vmm 在每条新的控制器命令开头把缓冲清空（`src/devices/i8042.c:205`）：

```c
    /* 新命令会冲掉还没被读走的旧应答。否则一次失败的 AUX_LOOP 残留
     * 的字节会被下一条 AUX_TEST 当成自己的应答读走。 */
    g_kbc.count = 0;
```

没有这一句，第 26 步读到的就是 0x5a 而不是 0x01，之后每条命令的应答都错位一格。

第二关是**外部连接测试**（`i8042.c:835`）：

```c
		if (i8042_command(&param, I8042_CMD_AUX_TEST) ||
		    (param && param != 0xfa && param != 0xff))
			return -1;
```

`I8042_CMD_AUX_TEST`（0xA9）返回 0 表示“AUX 口正常”，0x01–0x03 表示时钟线/数据线卡住，0xFF 是通用错误。注意这个判断的形状：**0x00、0xFA、0xFF 都算“有 AUX 口”**，只有 0x01–0x03 这几个值才让驱动放弃。mini-vmm 回 0x01（`src/devices/i8042.c:66` 的 `AUX_TEST_CLK_STUCK`），走的正是唯一那条否定路径。

这一条特别值得记住：**“不存在”不是默认值，而是一个需要精确表达的答案。** 回 0x00 会让驱动认为 AUX 口好好的，接着去 `request_irq(12)`、`i8042_enable_aux_port()`、发 0xA5 测中断，最后在 `wait_for_completion_timeout(..., 250ms)` 那里超时（`i8042.c:902`），既慢又会在 `/proc/interrupts` 里留下一个没人用的 IRQ 12；回 0xFF 同理。

两道关走完，日志是干净的：

```
i8042: PNP: No PS/2 controller found.
i8042: Probing ports directly.
serio: i8042 KBD port at 0x60,0x64 irq 1
```

只有 KBD port，没有 AUX port，也没有任何超时警告。

### 5.5 键盘侧：中断计数是一个可验证的断言

控制器探测完之后，`serio` 总线上注册出 KBD 口，`atkbd` 驱动接上去开始和“键盘设备”对话。trace 的第二段（32 次访问）是一串整齐的命令—应答，来自 `atkbd_probe()` 和 `atkbd_reset_state()`（`drivers/input/keyboard/atkbd.c:816`、`:928`、`:936`）以及 `atkbd_activate()`（`:719`）：

```
0064 R 14 / 0060 W f2    ATKBD_CMD_GETID
0064 R 15 / 0060 R fa    ACK
0064 R 15 / 0060 R ab    ┐ 键盘 ID
0064 R 15 / 0060 R 83    ┘
0064 R 14 / 0060 W f5    ATKBD_CMD_RESET_DIS
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W ed    ATKBD_CMD_SETLEDS
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W 00    参数
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W f3    ATKBD_CMD_SETREP
```

`0xAB 0x83` 就是日志里那句 `input: AT Translated Set 2 keyboard as /devices/platform/i8042/serio0/input/input1` 的来源（`input0` 是更早注册的 ACPI 电源按钮）。

紧接着还有第三段（16 次访问），又是一遍 `ED 00` 和 `F3 00`：

```
0064 R 14 / 0060 W ed    ATKBD_CMD_SETLEDS
0064 R 15 / 0060 R fa

0064 R 15 / 0060 R fa

```

这一遍不是探测代码发的。在 `atkbd_set_leds()` 上打硬件断点，命中时的调用栈是 `worker_thread` → `process_one_work` → `atkbd_event_work()`（`atkbd.c:634`）：input 设备注册后，键盘输入处理程序把 LED 和重复率状态以 `EV_LED`、`EV_REP` 事件下发，`atkbd_event()` 把它们攒进 `event_mask` 交给工作队列，工作函数再分别调 `atkbd_set_leds()`、`atkbd_set_repeat_rate()`。它在 trace 里有没有、出现几遍，取决于 input 子系统的事件流，换内核版本时要重新数。

这里每一对 `0064 R 15` / `0060 R fa` **都是中断处理程序**在跑：`i8042_interrupt()` 先读状态再读数据。和控制器命令的轮询不同，键盘设备的应答走的是 `serio` → `libps2` → 等待中断这条路。

于是有了一个干净的、可以当作断言写进测试的数字。上面两段一共产生 13 个键盘字节：第二段 GETID 的 3 个加上另外 6 条命令各 1 个 ACK，第三段 4 个 ACK。而 guest 里：

```
  1:         13   IO-APIC   1-edge      i8042
```

**IRQ 1 的计数正好是 13。** 这同时证明了三件事：每个字节都产生了一个独立的上升沿（`set_irq()` 里先降后升的那段逻辑是对的，`src/devices/i8042.c:137` 的 `obuf_pop()` 里 `set_irq(0)` 后再 `update_irq()`）；控制器自己的应答确实没有打中断（否则计数会远大于 13）；没有多余的中断（否则计数会更大）。

如果不给这些应答打中断会怎样？`ps2_command()` 会等 `atkbd` 的超时（默认 200 ms 一条），启动慢一大截，最后 `atkbd` 报 `keyboard reset failed` 之类的错误。这是 mini-vmm 文件头注释里那句“不打中断的话 atkbd 会等到超时”的具体含义。

### 5.6 复位：i8042 为什么能重启机器

PC/AT 的 i8042 有一根输出引脚接在 CPU 的 RESET 线上，这是历史上从实模式回到实模式的标准手段，也是 `reboot=k` 的由来。两条路都能触发：

- 命令 0xFE（严格说是 0xF0–0xFF，低 4 位为 0 的那几根线被脉冲拉低，bit0 就是 RESET#）；
- 命令 0xD1（写输出端口）后往 0x60 写一个 bit0 为 0 的值。

mini-vmm 两条都接（`src/devices/i8042.c:245` 与 `:263`）：

```c
        if (cmd >= CMD_PULSE_BASE && !(cmd & OUTP_RESET_N))
            return request_reset();
```

```c
    case CMD_WRITE_OUTP:
        g_kbc.outp = v;
        if (!(v & OUTP_RESET_N))
            return request_reset();
```

`request_reset()` 返回 `VMM_ERR_EXIT`，整个 VM 停下来。第 6 节会说明 `reboot=k` 这条命令行参数是怎么走到这里的。

### 5.7 mini-vmm 的实现边界

| 做了 | 谁依赖 |
|---|---|
| 状态寄存器的 OBF/SYSFLAG/CMDDAT/KEYLOCK/AUXDATA | 每一次访问 |
| IBF 恒 0 | `i8042_wait_write()` 立刻通过 |
| CTR 的读写（0x20 / 0x60），且读回来稳定 | `i8042_controller_init()` 的两次比对 |
| AUX_LOOP 回字节但不置 AUXDATA | `__i8042_command()` 的 AUXDATA 检查 |
| AUX_TEST 回 0x01 | `i8042_check_aux()` 的“时钟线卡住”分支 |
| 新命令清空输出缓冲 | 保证应答不错位 |
| 键盘命令一律 ACK，GETID 回 0xAB 0x83 | `atkbd` 探测 |
| 键盘字节打 IRQ 1（边沿），控制器应答不打 | `libps2` 等中断；IRQ 1 计数 = 13 |
| 0xFE 脉冲与 0xD1 写输出端口触发退出 | `reboot=k` |

| 没做 | 后果 |
|---|---|
| 控制器自检 0xAA / 键盘口测试 0xAB 的真实语义 | 默认配置不调用；实现了但走不到 |
| 扫描码：没有任何按键事件 | guest 的控制台收不到键盘输入。串口是唯一输入通道 |
| A20 控制（输出端口 bit1） | 长模式下无意义 |
| AUX 设备 | 按设计不存在 |
| 0xC0（读输入端口）等其余命令 | Linux 不用 |

## 6. 关机与重启：两条完全不同的路

VMM 必须能停下来，而且要能区分“guest 要关机”和“guest 要重启”——前者应该退出，后者应该把整台机器复位后重新引导。mini-vmm 照此分开处理：S5 关机让进程退出，i8042 复位走整机复位，给了 `--no-reboot` 时才改为退出。

### 6.1 ACPI S5：从 `_S5_` 到两次端口写

卷五第 7 节讲过 DSDT 里那 14 字节 AML 的编码，这里接着往下讲它怎么变成一次 `out`。

`poweroff` 最终走到 `acpi_power_off()`（`drivers/acpi/sleep.c:1105`），它调 `acpi_enter_sleep_state(ACPI_STATE_S5)`，ACPICA 里对应 `acpi_hw_legacy_sleep()`（`drivers/acpi/acpica/hwsleep.c:30`）。`acpi_gbl_sleep_type_a` 的值来自启动时对 `\_S5_` 求值的结果——就是我们 DSDT 里那个 `Package () { 5, 5, 0, 0 }` 的第一个元素。

trace 最后那五行，一一对应源码：

```
acpi-pm1a   0600 W2 8000    清 WAKE_STATUS               hwsleep.c:48
acpi-pm1a   0600 W2 c731    acpi_hw_clear_acpi_status()  hwsleep.c:59
acpi-pm1a   0604 R2 0001    读 PM1A 控制寄存器            hwsleep.c:73
acpi-pm1a   0604 W2 1401    写 #1：只写 SLP_TYP           hwsleep.c:101
acpi-pm1a   0604 W2 3401    写 #2：SLP_TYP + SLP_EN       hwsleep.c:127
```

0xC731 不是随手凑的，它是 `ACPI_BITMASK_ALL_FIXED_STATUS`（`drivers/acpi/acpica/aclocal.h:1007`）：TIMER(0x0001) | BUS_MASTER(0x0010) | GLOBAL_LOCK(0x0020) | POWER_BUTTON(0x0100) | SLEEP_BUTTON(0x0200) | RT_CLOCK(0x0400) | PCIEXP_WAKE(0x4000) | WAKE(0x8000)。PM1 状态寄存器是“写 1 清零”语义，所以这一次写把所有固定事件的状态位一次清干净。mini-vmm 照这个语义实现（`src/devices/acpi_pm.c:93`），寄存器按字节处理，所以字访问和两次字节访问结果相同：

```c
        case ACPI_PM_OFF_STS:
        case ACPI_PM_OFF_STS + 1:
            pm->sts &= (uint16_t)~(b << sh);
            break;
```

0x1401 与 0x3401 拆开的理由写在源码注释里（`hwsleep.c:94`）：

```c
	/*
	 * We split the writes of SLP_TYP and SLP_EN to workaround
	 * poorly implemented hardware.
	 */
```

`0x1401` = SCI_EN(bit0) | SLP_TYP=5(bit12:10)，`0x3401` 再或上 SLP_EN(bit13)。**只有带 SLP_EN 的第二次写才是真正的“睡下去”**。mini-vmm 的判断因此必须同时看两个字段：`acpi_pm_write()` 在写到控制寄存器高字节时调 `sleep_request()`（`src/devices/acpi_pm.c:70-77`、`:104-107`），SLP_EN 置位才算请求，SLP_TYP 等于 5 是关机，其余类型只告警；`src/power.c` 的 `pm_write()` 据此退出：

```c
    case ACPI_PM_POWEROFF:
        vmm_info("guest requested poweroff via ACPI S5 (port 0x%llx, value 0x%x)",
                 (unsigned long long)(ACPI_PM1A_EVT_PORT + off), v);
        vm->exit_code = 0;
        return VMM_ERR_EXIT;
```

只看 SLP_TYP 的话，第一次写（0x1401）就会让 VM 退出——**早了一步**。这一步之差在真机上无所谓（反正马上就要关），但在 VMM 里意味着你把一次“准备”当成了“执行”，如果将来要支持 S3 挂起就会出错。

读回值里那个 SCI_EN（bit0）也值得一提。mini-vmm 拼寄存器读回值时无条件把它或上去（`src/devices/acpi_pm.c:46`）：

```c
    uint16_t cnt = pm->cnt | ACPI_PM1_CNT_SCI_EN;
```

真机上这一位由固件在 `acpi_enable()` 之后置起来，表示“已经从 legacy 模式切到 ACPI 模式”。我们没有 SMI、也没有 legacy 模式，所以直接承诺“永远在 ACPI 模式”。ACPICA 的 `acpi_enable()` 会读这一位来判断是否需要发 ACPI_ENABLE 命令；返回 0 的话它会去写 SMI_CMD 端口然后轮询这一位，等不到就报 `Hardware did not enter ACPI mode`。

### 6.2 启动期的 PM1a 访问

除了关机，PM1a 在启动期还有 26 次访问，都出现在 ACPI 子系统初始化阶段：

```
0602 R2 0000 / 0602 W2 0000   × 5        acpi_ev_fixed_event_initialize()
0600 W2 0020                             清 GBL_STS
0602 R2 0000 / 0602 W2 0020 / 0602 R2 0020
                                         使能 GBL_EN 并读回校验（全局锁）
0600 W2 0100                             清 PWRBTN_STS
0602 R2 0020 / 0602 W2 0120 / 0602 R2 0120
                                         使能 PWRBTN_EN（电源按钮驱动）
0600 W2 0400                             清 RTC_STS
0602 R2 0120 / 0602 W2 0520 / 0602 R2 0120
                                         试图使能 RTC_EN，读回没有 0x400
0600 W2 0400 / 0602 R2 0120 / 0602 W2 0120 / 0602 R2 0120
                                         放弃，再把它关掉
```

开头那五对“读 PM1a_EN、写 0”来自 ACPICA 逐个禁用五个固定事件（timer、global lock、power button、sleep button、RTC）。每个都是一次读—改—写，因为 `acpi_write_bit_register()` 要保留其他位。之后每使能一个事件，`acpi_enable_event()` 都会把使能位读回来校验：GBL_EN 和 PWRBTN_EN 存住了；RTC_EN 是 mini-vmm 没实现的可选位，读回 0，ACPICA 打出 `ACPI Error: Could not enable RealTimeClock event` 并把它关掉。所以这一段对 VMM 的要求是**实现了的使能位要能存住值、没实现的使能位要读回 0**，读回值就是驱动判断这个事件存不存在的依据。

### 6.3 `reboot=k`：重启走 i8042

mini-vmm 的默认命令行里有 `reboot=k`。这个参数在 `arch/x86/kernel/reboot.c:155` 被解析成 `reboot_type = BOOT_KBD`，跳过 ACPI 复位寄存器那条路。

实测一次 `reboot -f`，trace 的最后两行是：

```
i8042-cmd   0064 R1 14
i8042-cmd   0064 W1 fe
```

对应 `native_machine_emergency_restart()` 的 `BOOT_KBD` 分支（`reboot.c:613`）：

```c
		case BOOT_KBD:
			mach_reboot_fixups(); /* For board specific fixups */

			for (i = 0; i < 10; i++) {
				kb_wait();
				udelay(50);
				outb(0xfe, 0x64); /* Pulse reset low */
				udelay(50);
			}
```

`kb_wait()` 读状态等 IBF 清零，就是那次 `0064 R 14`；然后 `outb(0xfe, 0x64)` 脉冲复位线。循环本来要转 10 次，但 mini-vmm 在第一次就停下了 vCPU，所以 trace 里只有一对。带 `--no-reboot` 时 VMM 侧的输出是：

```
[    2.743654] reboot: Restarting system
[    2.745315] reboot: machine restart
[INFO] guest requested reset via i8042
[INFO] --no-reboot: stopping instead of resetting
[INFO] --- left guest (ok) ---
```

不带 `--no-reboot` 时同一次写触发整机复位：vCPU、设备和内存恢复到开机状态，guest 从头再引导一遍。

**为什么要指定 `reboot=k` 而不用默认值？** 默认的 `reboot_type` 在 x86 上是 `BOOT_ACPI`（经 DMI 检查可能被改），它会先调 `acpi_reboot()` 去写 FADT 里的 RESET_REG。mini-vmm 的 FADT 提供了 RESET_REG：指向 i8042 命令口 0x64，RESET_VALUE 为 0xFE，并置了 `ACPI_FADT_RESET_REG_SUP`，所以 `acpi_reboot()` 写出的也是同一个 0xFE，结果一样。写死 `reboot=k` 让这条路径不依赖 DMI 对 `reboot_type` 的改写，也让“VMM 收到 0xFE”成为一个可以写进测试的断言；用户用 `--cmdline` 去掉它时，默认的 `BOOT_ACPI` 同样一次成功。

`reboot.c:605` 那个 `for (;;)` 循环还有一个副作用值得知道：如果 VMM 不理会 0xFE，内核会依次尝试 EFI、BIOS（`machine_real_restart()`，回实模式跳 `0xFFFF:0x0000`）、0xCF9 端口……全部失败之后回到 `BOOT_KBD` 无限重来。症状是 guest 卡在 `reboot: Restarting system` 不动，CPU 占满——**看起来像死循环，其实是在一条条试**。

### 6.4 mini-vmm 的两条退出路径

| 触发 | 端口 | 判据 | 日志 | 结果 |
|---|---|---|---|---|
| ACPI S5 关机 | 0x604 写高字节 | SLP_EN 且 SLP_TYP == 5 | `guest requested poweroff via ACPI S5 (port 0x604, value 0x3401)` | 退出，`exit_code` 0 |
| i8042 复位 | 0x64 写 0xF0–0xFF 且 bit0 = 0；或 0xD1 + 0x60 写 bit0 = 0 | `src/devices/i8042.c:245`、`:265` | `guest requested reset via i8042` | 整机复位；`--no-reboot` 时退出，`exit_code` 0 |
| 测试用退出口 | 0xF4 写 | 写入值即退出码 | `guest requested exit, code=N` | 退出，`exit_code` 为写入值 |

三条都通过设备回调返回 `VMM_ERR_EXIT` 让 vCPU 停下；复位时 `vm_request_reset()`（`src/reset.c:243`）先置 `reset_requested`，主线程看到它就把整机恢复到开机状态再放 vCPU 继续跑，而不是退出进程。这也是第 1.2 节那个“先记录 trace 再判返回值”的顺序之所以重要的原因——这三次写恰恰是 vCPU 停下前的最后一次写。

## 7. 浮空总线：“读回 0xFF”是一条契约，不是一个默认值

一次启动里有 19 次 PIO 落在 mini-vmm 没有注册任何设备的端口上。`io_bus_dispatch_pio()` 对它们的处理只有几行（`src/vm.c:364-376`）：

```c
    if (!dev) {
        /* 未注册端口：写丢弃，读返回全 1（真机上空闲总线的行为）。
         * 不能直接报错退出——Linux 内核启动时会盲探一堆遗留端口。 */
        if (!is_write)
            memset(data, 0xFF, (size_t)size * count);
```

这一节要说明的是：这几行不是“兜底”，它们和任何一个设备模型一样，是在向 guest 表达一个明确的语义。

### 7.1 19 次访问分别是谁

有了 `--trace-pio` 记录的 RIP，`tools/trace_decode.py --syms vmlinux --dev unhandled` 把它们逐条对到符号上：

| 端口 | 次数 | 调用者 | 干什么 |
|---|---|---|---|
| 0x2f9 / 0x3e9 / 0x2e9 | 各 3 读 3 写 | `io_serial_in+0x13`、`io_serial_out+0x15` | ttyS1/2/3 的 autoconfig（第 2.8 节） |
| 0x87 | 1 读 | `i8237A_init_ops+0x4` | 判断有没有 8237 DMA 控制器 |

同样的命令再跑一次，这张表逐条相同：次数、调用者符号都对得上。

RIP 反查这件事本身值得推荐：**当你看到一次不认识的端口访问时，"谁在访问" 通常比 "访问了什么" 更有用**，而这个信息在 VMM 这一侧是现成的，只差一次 `KVM_GET_REGS`。

### 7.2 0x80：被半虚拟化省掉的延时写

表里没有 0x80，这本身就是一条值得解释的观察。guest 的 `.config` 里 `CONFIG_IO_DELAY_0X80=y`，`native_io_delay()`（`arch/x86/kernel/io_delay.c:42`）在这个配置下编译成一条往 0x80 写 AL 的指令：

```c
	case IO_DELAY_TYPE_0X80:
		asm volatile ("outb %al, $0x80");
```

历史上这个端口是 BIOS 的 POST 码显示口，往它写一个字节的耗时正好接近一个 ISA 总线周期，于是被拿来当作 `outb_p`/`inb_p` 这类“慢速 I/O”在两次访问之间的延时。

但 `_p` 系列并不直接调它，中间隔着一层判断（`arch/x86/include/asm/io.h:250-256`）：`slow_down_io()` 只有 `call_io_delay()` 为真时才调 `native_io_delay()`，而开了 `CONFIG_PARAVIRT` 时 `call_io_delay()` 就是 `pv_info.io_delay`（`arch/x86/include/asm/paravirt-base.h:32`）。KVM 在 CPUID 0x40000001 里声明了 `KVM_FEATURE_NOP_IO_DELAY`，guest 的 `paravirt_ops_setup()` 看到它就把这个开关关掉（`arch/x86/kernel/kvm.c:350-351`）：

```c
	if (kvm_para_has_feature(KVM_FEATURE_NOP_IO_DELAY))
		pv_info.io_delay = false;
```

道理很直接：延时写的唯一作用是等慢速硬件，而虚拟设备没有总线周期要等，每次延时写却都要付一次 VM exit。mini-vmm 把 `KVM_GET_SUPPORTED_CPUID` 给出的 KVM 半虚拟化叶原样交给 guest，这个特性位就随之传了过去。

把这一位在 VMM 里清掉再启动一次，0x80 立刻回到 trace 里：7 次写，值都是 0x00，RIP 全部是 `native_io_delay+0x19`，3 次紧跟在 `ACPI: Core revision` 那行日志之后，4 次紧跟在 `VFS: Finished mounting rootfs on nullfs` 之后。RIP 落在 `native_io_delay()` 自己身上，所以它只告诉我们“这是一次 `outb_p`/`inb_p` 的延时”，并不能告诉我们是**哪个** `_p` 调用产生的——要知道那个得去栈上取返回地址，`--trace-pio` 不做这件事。

这里顺带有一个和第 3 节呼应的观察：真正频繁使用 `_p` 系列的那些老设备——PIC 的 0x20/0x21/0xa0/0xa1——即使在延时写打开时也一次都不出现在 trace 里，因为它们在内核态被接走了；而 0x80 这个纯粹的副产品却会漏出来。**把设备搬进内核能省掉寄存器访问本身，省不掉它顺带产生的延时写；省掉延时写要靠 guest 知道自己跑在虚拟机里。**

对 VMM 的要求因此仍然是一条：0x80 的写必须被安静地丢弃。不声明 `KVM_FEATURE_NOP_IO_DELAY` 的 VMM、或者没开 `CONFIG_KVM_GUEST` 的 guest 都会在启动早期发出这类盲写，如果 VMM 对未知端口的写报错退出，虚拟机会死在一个和任何设备都无关的地方。

### 7.3 0x87：0xFF 与 0x00 的区别在这里变成决定性的

只有一次访问的 0x87，是本节最有说服力的例子。`arch/x86/kernel/i8237.c` 的 `i8237A_init_ops()`：

```c
	/*
	 * From SKL PCH onwards, the legacy DMA device is removed in which the
	 * I/O ports (81h-83h, 87h, 89h-8Bh, 8Fh) related to it are removed
	 * as well. All removed ports must return 0xff for a inb() request.
	 * ...
	 */
	if (dma_inb(DMA_PAGE_0) == 0xFF)
		return -ENODEV;
```

`DMA_PAGE_0` 就是 0x87。内核用一次读来判断这台机器上还有没有 8237 DMA 控制器，判据**写死**是 0xFF。读回 0xFF：驱动认为没有，`return -ENODEV`，`i8237_syscore_ops` 不注册，从此系统里不存在 8237。读回 0x00（或者任何别的值）：驱动认为有，注册 syscore ops，之后每次从挂起恢复都会去写 0x0D/0xDA/0x0A 这一串 DMA 寄存器——在 mini-vmm 上这些写会落到别的地方或者被丢弃，行为未定义。

注释里那句 “All removed ports must return 0xff for a inb() request” 说得再清楚不过：**这是硬件规范对“不存在”的规定，而 VMM 的未注册端口处理就是在实现这条规定。** 0xFF 不是随便选的默认值，它是浮空总线（floating bus）——没有设备驱动数据线时，上拉电阻把总线拉到全 1——在软件侧的契约化。

同一个道理在第 2.8 节的 ttyS1/2/3 上也成立，只是那里 0xFF 和 0x00 都会导致探测失败，区别只在失败的位置。0x87 这个例子里，两者会得出**相反**的结论。

### 7.4 PCI：锁存器测试

0xcf8–0xcff 在 mini-vmm 上是 pci-bus 里程碑实现的配置机制 #1，不再属于未注册端口，但内核判断“这台机器有没有配置机制 #1”的方式，和 0x87 一样建立在对读回值的约定上，值得放在这一节看。

整次启动里配置端口有 533 次访问，最早的几次在 `setup_arch()` 里就出现了（第 2.2 节那次 `trim_snb_memory()` 的探测，以及 `early_quirks()` 用 `read_pci_config()` 扫总线 0），这时 PCI 子系统还没初始化，内核直接假设配置机制 #1 存在。写 VMM 时要知道，**即使不打算支持 PCI，这些访问照样会来**，未注册时它们靠 0xFFFFFFFF 得出“这个槽位没有设备”的结论。

真正的存在性判断在 `pci_direct_probe()` 里，先试机制 #1（`arch/x86/pci/direct.c:223`）：

```c
	outb(0x01, 0xCFB);
	tmp = inl(0xCF8);
	outl(0x80000000, 0xCF8);
	if (inl(0xCF8) == 0x80000000 && pci_sanity_check(&pci_direct_conf1)) {
		works = 1;
	}
	outl(tmp, 0xCF8);
```

trace 里对应的是：

```
pci-conf1-addr 0cfb W1 01
pci-conf1-addr 0cf8 R4 80fefb00     tmp：上一次留下的地址
pci-conf1-addr 0cf8 W4 80000000
pci-conf1-addr 0cf8 R4 80000000     读回一致：0xCF8 是可读写的锁存器
pci-conf1-addr 0cf8 W4 80000008
pci-conf1-data 0cfe R2 0600         pci_sanity_check()：00:00.0 的 class 是 host bridge
pci-conf1-addr 0cf8 W4 80fefb00     outl(tmp, 0xCF8) 还原
```

机制 #1 的判据是：**往 0xCF8 写 0x80000000，再读回来必须一模一样**。它要求 0xCF8 是一个真正的可读写锁存器，未注册端口读回的 0xFFFFFFFF 过不了这一关。`pci_sanity_check()`（`direct.c:195`）在 DMI 报告的 BIOS 年份不早于 2001 时直接放行；mini-vmm 不提供 SMBIOS，年份取不到，于是它真的去总线 0 上找一个 host bridge 或 VGA 设备，在 00:00.0 读到 class 0x0600 就通过了。日志随后是 `PCI: Using configuration type 1 for base access`。

机制 #1 成功后机制 #2 不再尝试。它的判据恰好反过来（`direct.c:243`）：

```c
	outb(0x00, 0xCFB);
	outb(0x00, 0xCF8);
	outb(0x00, 0xCFA);
	if (inb(0xCF8) == 0x00 && inb(0xCFA) == 0x00 &&
	    pci_sanity_check(&pci_direct_conf2)) {
```

写 0 再读回必须是 0。**这里 0xFF 和 0x00 的角色互换了**——如果未注册端口读回 0x00，这个测试的前半截就会通过，接着去跑 `pci_sanity_check()`，探测会往前多走一大截。实现细节见 blog《PCI·原理篇》和《PCI·实现篇》。

### 7.5 未注册端口的四种可选行为

| 做法 | 后果 |
|---|---|
| 读回 0xFF，写丢弃（mini-vmm） | 与真硬件的浮空总线一致。`i8237A_init_ops()`、autoconfig、PCI 探测全部得出正确结论 |
| 读回 0x00，写丢弃 | 8237 被误认为存在；没有配置机制 #1 的机器上，PCI 机制 #2 的探测多走几步。其余大多数场合看不出区别 |
| 报错并退出 | 启动早期就死在一次盲探上，而且现场和任何设备都对不上号 |
| 打印警告但继续 | 可用，但每次启动都有一串和故障无关的噪音。mini-vmm 把它放在 debug 级别（`vmm_dbg`），默认不显示 |

mini-vmm 选第一种，并且在 MMIO 侧用了同样的约定（`src/vm.c:411`，未注册 MMIO 读返回全 1）。

## 8. 设备模型的并发：两把锁，各管一边

设备模拟的并发问题有两个来源，性质完全不同。

**第一个来源是多个 vCPU 线程同时陷出。** `--smp 4` 时四个线程可能同时落在 PIO 分发里。mini-vmm 的做法是一把大锁，vCPU 循环在分发每一次 `KVM_EXIT_IO` / `KVM_EXIT_MMIO` 之前拿 `vm->io_lock`（`src/vm.c:503-514`）：

```c
    case KVM_EXIT_IO: {
        int r;

        pthread_mutex_lock(&vcpu->vm->io_lock);
        r = handle_io(vcpu);
        pthread_mutex_unlock(&vcpu->vm->io_lock);
        return r;
    }
```

于是**所有设备回调都在这把锁下串行执行**。`src/devices/i8042.c` 和 `src/devices/rtc.c` 里的文件级静态结构体、`src/power.c` 里的 `g_power`（内含 `struct acpi_pm`），都没有自己的锁，靠的就是这个前提。这是 QEMU 的 BQL 同一个思路：代价是设备访问不能并行，收益是设备模型可以当单线程代码写。

在这一卷的语境下这个选择尤其划算：第 1.3 节的表说明 98% 的 PIO 是串口，而串口在任一时刻只可能被一个 CPU 用来输出（printk 有自己的锁），并行度本来就接近 1。

**第二个来源是 vCPU 之外的线程。** 有两类路径不由 guest 的 `in`/`out` 发起，它们都跑在 I/O 线程（`src/io/event_loop.c` 的 epoll 循环）上：

- host 终端的输入。串口的接收方向不由 guest 驱动，是 host 的 stdin 有数据时才往里塞。`src/console.c` 的 `console_on_input()` 是 I/O 线程上的回调，读到字节后经 `console_byte()` 处理 Ctrl-A 转义，再调 `serial8250_push_rx()`。
- monitor 命令。`system_powerdown` 的处理函数（`src/power.c:109-116`）要置 PM1_STS 的 PWRBTN_STS 并重新计算 SCI。

两条路径的处理方式不同，取决于设备有没有自己的锁。串口有：`struct serial8250` 带一把 `lock`（寄存器读写在 `src/devices/serial8250.c:160`、`:213`、`:285` 拿它），`serial8250_push_rx()` 只拿这把锁，不拿 `io_lock`。它除了改 FIFO 还要调 `update_irq()`，因为新字节到达可能需要拉起 IRQ 4：

```c
bool serial8250_push_rx(struct serial8250 *s, uint8_t c)
{
    ...
    pthread_mutex_lock(&s->lock);
    next = (s->rx_head + 1) % SERIAL_RX_BUF;
    if (next != s->rx_tail) {
        s->rx_buf[s->rx_head] = c;
        s->rx_head = next;
        ok = true;
    }
    update_irq(s);
    pthread_mutex_unlock(&s->lock);
    return ok;
}
```

PM1 没有自己的锁，所以 monitor 的处理函数先拿 `io_lock`，和 vCPU 线程的 exit 分发串行，再调 `acpi_pm_press_power_button()`。

**加锁顺序。** `include/io/event_loop.h` 把顺序定为 `vm->io_lock` → 设备自己的锁 → KVM ioctl。串口的路径上出现的是 `io_lock` → `s->lock`（vCPU 读写寄存器）和单独的 `s->lock`（I/O 线程收字符），不会出现 `s->lock` → `io_lock`，所以没有环。持有设备锁时绝不能再去拿 `io_lock`，否则和持有 `io_lock` 再拿设备锁的 vCPU 线程构成 ABBA 死锁。`update_irq()` 会在持有 `s->lock` 的情况下调 `irqchip_set_irq()`：内核 irqchip 下是一次 `ioctl(KVM_IRQ_LINE)`，KVM 的这条路径不会阻塞在 `vcpu->mutex` 上；split irqchip 下进入用户态 IOAPIC/PIC，拿的是 `src/devices/split_irqchip.c` 自己的锁，排在设备锁之后，同样不会回头拿 `io_lock`。

**一个更一般的结论。** 本卷讲的五个设备里，只有串口有“设备主动产生事件”的方向（收字符）；RTC、i8042、PM1a、PIT 在 guest 眼里都是“guest 问、设备答”，PM1a 唯一的外部入口（monitor 按电源键）频率极低，直接借 `io_lock` 就够了。**判断一个设备模型要不要自己的锁，看它有没有不由 vCPU 线程发起、又频繁到值得和 vCPU 并行的路径。** i8042 的键盘应答看起来像是设备主动发的，但它总是由一次 `out` 触发的，所以不算。

## 9. 一致性检查清单

卷五第 9 节给了固件表侧的清单，卷六第 10 节给了 CPU 侧的。这一节是设备侧的。每一条都标注了违反时的现象，因为这类 bug 的共同特点仍然是**现象离原因很远**。

### 9.1 端口归属

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 0x40–0x43、0x61 必须留给 KVM 的内核态 PIT | `KVM_CREATE_PIT2` 已经注册了它们 | 用户态注册的设备收不到任何访问，而且没有任何提示 |
| `KVM_CREATE_PIT2` 必须带 `KVM_PIT_SPEAKER_DUMMY` | 0x61 是 PIT 通道 2 的 GATE 与 OUT | TSC 校准失败，jiffies 不走；日志是 `Unable to calibrate against PIT` |
| `KVM_CREATE_PIT2` 要在 `KVM_CREATE_IRQCHIP` 之后 | PIT 的中断要挂 GSI 0 | ioctl 返回 `EFAULT`/`ENXIO` |
| 0x64 归 VMM，不受 KVM speaker 设备注册长度 4 的影响 | `speaker_ioport_*()` 对非 0x61 返回 `-EOPNOTSUPP`，总线会继续往下找 | 无——但如果误以为被吞掉而不去注册 i8042，键盘控制器探测会超时 |
| i8042 要按 0x60 和 0x64 两个单字节设备注册 | 中间隔着 0x61 | 整段注册时 0x61 的访问静默丢失 |
| 未注册端口：读回 0xFF、写丢弃 | 浮空总线的软件契约 | 读回 0x00 会让 `i8237A_init_ops()` 误判有 8237；报错退出会死在盲探上 |
| 未注册 MMIO 用同样的约定 | 同上 | 同上 |

### 9.2 16550A

| 约束 | 谁依赖 | 违反的现象 |
|---|---|---|
| IER 低 4 位写什么读什么 | `autoconfig()` 存在性测试（`8250_port.c:1144`） | 端口被判为不存在，`console=ttyS0` 完全没有输出 |
| FCR 的 bit0 要反映到 IIR 的 bit7:6 | `autoconfig()` 类型判定（`8250_port.c:1197`） | 被认成 8250/16450，FIFO 不启用，性能下降 |
| LSR 的 THRE 与 TEMT 恒置位 | earlyprintk、`wait_for_xmitr()` | 输出卡死；`serial8250_do_startup()` 的 LSR 安全检查看到 0xFF 会直接 `-ENODEV` |
| LSR 的 DR 跟随接收 FIFO | tty 收字符 | 输入收不到 |
| 打开 IER.THRI 时若 THR 空要补一次 THRI | THRE bug 测试（`serial8250_THRE_test()`，`8250_port.c:2253-2268`）、`serial8250_start_tx()` | 被扣 `UART_BUG_THRE`，改成每 25 ms 定时器轮询 |
| 读 IIR 拿到 THRI 即视为应答 | 16550 语义 | 中断一直挂着，中断风暴 |
| 中断要经 MCR.OUT2 门控 | PC/AT 板级接线（`serial8250_init_mctrl()`，`8250_port.c:2276-2279`） | 探测期间出现不该有的中断；真正的 bug 要到别处才暴露 |
| 中断线只在电平变化时才调 `KVM_IRQ_LINE` | IOAPIC 上 ISA IRQ 是边沿触发 | 第二个字节起中断丢失 |
| MSR 常态要有 DCD/DSR/CTS | tty 的载波检测 | 终端被挂断，进程收到 SIGHUP |
| DLAB 必须复用偏移 0/1 | 每一段代码都在用 | 分频器写进 THR，输出乱码 |
| LCR 原样存原样读，不做合法性检查 | Linux 会写 0x13（EPAR 无条件置位）、0xBF | 设备模型比真硬件挑剔，探测会在莫名其妙的地方失败 |
| 偏移 2 不随 LCR 变化，LCR=0xBF 时也照常是 IIR/FCR | 真 16550A 没有 EFR；Linux 在 LCR=0xBF 下读偏移 2，读到 0 就判定有 EFR | 开了 `CONFIG_SERIAL_8250_16550A_VARIANTS` 的内核把端口认成 ST16650V2 |

### 9.3 CMOS RTC

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 寄存器 A 的 UIP（bit7）必须能读到 0 | `mc146818_avoid_UIP()` 的循环条件 | 两次 1 秒超时、8 万次 PIO exit、`Unable to read current time from RTC` |
| 寄存器 B 的 bit1（24 小时制）必须为 1 | `rtc-cmos.c:1098` 的硬性检查 | `only 24-hr supported`，`rtc_cmos` 探测失败 |
| 时间寄存器必须是 BCD | x86 的 `RTC_ALWAYS_BCD` 写死 | 时间荒唐，`setting system clock to` 显示一个乱七八糟的日期 |
| 世纪寄存器的索引要与 FADT 里填的一致 | `rtc-mc146818-lib.c:132-133` 用 `acpi_gbl_FADT.century` 当索引 | 年份落到错误的世纪；FADT 填 0 时短期看不出来，2070 年后才错 |
| 索引口写入要屏蔽 bit7 | bit7 是 NMI 屏蔽位 | 选到 0x80 以上的寄存器，读回垃圾 |
| CMOS RAM 的 128 字节要真的能存 | `rtc-cmos` 导出 114 字节 NVRAM | NVRAM 读写前后不一致 |
| 索引 0x0F 的写必须被接受 | AP 唤醒的 warm reset vector（卷六 3.6 节） | `do_boot_cpu()` 第一步失败 |
| 寄存器 C 读回 0 | 没有挂起中断 | 驱动以为有未处理的 RTC 中断 |

### 9.4 i8042

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 状态寄存器的 OBF 要准确反映输出缓冲 | `i8042_wait_read()` | 每条命令白等 0.5 秒 |
| IBF 恒 0（或及时清零） | `i8042_wait_write()` | 同上 |
| CTR 读回来必须稳定 | `i8042_controller_init()` 连读两次比对 | `Unable to get stable CTR read`，整个 i8042 被放弃 |
| AUX_LOOP（0xD3）回字节但**不**置 AUXDATA | `__i8042_command()` 的 AUXDATA 检查 | 置了的话驱动认为有 AUX 口，接着去测 IRQ 12，250 ms 超时 |
| AUX_TEST（0xA9）回 0x01–0x03 | 只有这几个值表示“没有 AUX” | 回 0x00/0xFA/0xFF 都表示“有 AUX 口” |
| 新命令要清掉未读的旧应答 | 失败的 AUX_LOOP 会留下一个字节 | 之后每条命令的应答错位一格 |
| 键盘设备的应答要打 IRQ 1，控制器应答不打 | `libps2` 等中断，控制器命令是轮询 | 前者不打会让 `atkbd` 逐条超时；后者打了会多出莫名的中断 |
| IRQ 1 要受 CTR 的 KBDINT/KBDDIS 门控 | 探测期间驱动会关掉键盘口 | 探测阶段出现不该有的中断 |
| 0xFE 脉冲与 0xD1+bit0=0 都要能触发复位 | `reboot=k` 走前者，某些代码走后者 | guest 卡在 `reboot: Restarting system`，CPU 占满地逐条试其他复位方式 |

### 9.5 ACPI PM1a

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 只有 SLP_EN 与 SLP_TYP **同时**满足才算关机 | ACPICA 分两次写（`hwsleep.c:99` 的 Write #1 与 `:125` 的 Write #2） | 只看 SLP_TYP 会在第一次写时就退出，早了一步 |
| SLP_TYP 的值要与 DSDT 里 `_S5_` 的第一个元素一致 | 那个值就是 ACPICA 要写的 | 写进来的 SLP_TYP 对不上，VMM 不退出，guest 停在 `Preparing to enter system sleep state S5` |
| PM1a_CNT 读回时 SCI_EN 必须为 1 | `acpi_enable()` 用它判断是否已在 ACPI 模式 | `Hardware did not enter ACPI mode`，之后 `_S5_` 求值也会出问题 |
| PM1a_STS 是“写 1 清零” | ACPICA 用 0xC731 一次清干净 | 状态位清不掉，`acpi_hw_clear_acpi_status()` 之后仍然有挂起事件 |
| PM1a_EN 的已实现位要能存住值，未实现位读回 0 | ACPICA 的位操作是读—改—写，`acpi_enable_event()` 写完会回读校验 | 已实现位存不住时电源键事件开不起来；未实现位（如 RTC_EN）读回 1 会让 ACPICA 以为启用了一个永远不会来的事件 |
| 端口块地址与 FADT 里的 `pm1a_evt_blk` / `pm1a_cnt_blk` 一致 | 卷五的老规矩 | ACPICA 写到没人管的端口，关机无效 |

### 9.6 通用

| 约束 | 为什么 |
|---|---|
| 设备回调要能承受任意宽度的访问 | guest 可能按字节、字、双字访问同一块寄存器；mini-vmm 的 PM1 端口块（0x600 起 8 字节）按字节拆开，逐字节落到 STS、EN、CNT 上 |
| 只读寄存器的写要被忽略而不是报错 | 驱动会把读到的值原样写回去，包括从不存在端口读到的 0xFF |
| 设备状态的并发保护：看有没有非 vCPU 线程发起的路径 | 只有串口的接收方向需要自己的锁，其余靠 `io_lock` |
| 退出用的写要先记进 trace 再返回 | 否则最关键的那一行丢了 |

## 10. 验证与排障

### 10.1 三步法

设备类问题的排查顺序和中断、SMP 都不一样：这里**不需要猜**，因为 guest 的每一次寄存器访问都可以被完整记录下来。

**第一步：录一份 trace。**

```sh
./build/vmm --mode linux --mem 512M --trace-pio /tmp/pio.txt \
    --initrd build/initramfs.cpio.gz $VMLINUX
```

**第二步：看全貌。**

```sh
./tools/trace_decode.py /tmp/pio.txt --summary
```

三个问题可以立刻回答：这个端口有没有被访问过（没有 → 要么 guest 不关心它，要么它被 KVM 内核接走了）；访问了多少次（次数异常大通常意味着某个轮询循环在超时）；哪个设备占了大头。

**第三步：定位到时间点。** trace 只有时间戳和行号，而人能读懂的是内核日志。把两者对上：

```sh
./tools/trace_decode.py /tmp/pio.txt --console | less
```

输出的每一行是 `<起始行号>-<结束行号>\t<那条日志的文本>`。找到感兴趣的日志，就知道它前后的 trace 行号区间；反过来，看到一段奇怪的访问，也能查出它发生在哪条日志附近。然后：

```sh
./tools/trace_decode.py /tmp/pio.txt --from 25700 --to 25800
./tools/trace_decode.py /tmp/pio.txt --dev unhandled --syms $VMLINUX
```

`--syms` 那条是找“谁在访问一个我没实现的端口”的标准手段。第 7.1 节整张表就是这么来的。

### 10.2 症状到原因

| 症状 | 先看什么 | 常见原因 |
|---|---|---|
| 完全没有串口输出 | trace 里有没有 0x3f8 | IER 存在性测试没过（IER 低 4 位不可读写）；或者端口号/`console=` 参数对不上 |
| 有 earlyprintk 输出，`console [ttyS0] enabled` 之后就停了 | `autoconfig()` 那 20 来次访问 | IIR 的 FIFO 位没跟着 FCR 走，端口被判成 `PORT_UNKNOWN` |
| 串口输出很慢、字符间隔均匀 | `/proc/interrupts` 的 IRQ 4 | 被扣了 `UART_BUG_THRE`，改成定时器轮询；检查“打开 THRI 时补一次中断” |
| 串口输出重复一段 | `EINTR`/`EAGAIN` 之后有没有重新分发 exit | 卷六 10.4 节那条：这两条路径不保证写 `exit_reason` |
| 启动卡住约 0.5 秒的整数倍 | trace 里最后一次访问的端口 | i8042 的某条命令没应答，`i8042_wait_read()` 超时 |
| 启动慢约 2 秒，日志有 `Unable to read current time from RTC` | 0x70/0x71 的访问次数 | RTC 没实现，或者寄存器 A 的 UIP 恒为 1 |
| `rtc_cmos: broken or not accessible` | 同上 | 同上；或者 `mc146818_does_rtc_work()` 超时 |
| `rtc_cmos: only 24-hr supported` | 寄存器 B 的值 | bit1 没置 |
| 时间对但年份差 100 年 | FADT 的 `century` 字段与 RTC 模型认的索引 | 两边对不上 |
| `Unable to calibrate against PIT`，jiffies 不走 | trace 里有没有 0x61 | 忘了 `KVM_PIT_SPEAKER_DUMMY`；也可能只是 host 负载大（3.5 节） |
| `i8042: Can't read CTR` | trace 里 0x64 写 0x20 之后有没有应答 | CTR 读命令没实现 |
| 多出一个没人用的 IRQ 12 | AUX 两道检查的返回值 | AUX_LOOP 置了 AUXDATA，或 AUX_TEST 回了 0x00 |
| `poweroff` 之后 guest 停在 `Preparing to enter system sleep state S5` | trace 里 0x604 的最后两次写 | 只看 SLP_TYP 没看 SLP_EN；或者 DSDT 的 `_S5_` 值与 VMM 的判据不一致 |
| `reboot` 之后 CPU 占满且不退出 | trace 的最后几行 | 0xFE 没被处理，内核在逐条试 EFI/BIOS/0xCF9 |
| guest 认为有一个不存在的设备 | 那个设备的探测端口读回了什么 | 未注册端口读回了 0x00 而不是 0xFF |

### 10.3 `tests/e2e/legacy-devices.sh`

三条自动用例：

**设备都被正确探测，且一次超时都没有。** 断言分两类：一类是“该出现的日志”（`serial8250: ttyS0 I/O:0x3f8 (irq = 4, base_baud = 115200) is a 16550A`、`serio: i8042 KBD port at 0x60,0x64 irq 1`、`AT Translated Set 2 keyboard`、`rtc_cmos rtc_cmos: registered as rtc0`、`alarms up to one day, y3k, 114 bytes nvram`、`guest requested poweroff via ACPI S5`），另一类是“不该出现的日志”（`ttyS1 I/O:0x2f8`、`LSR safety check engaged`、`i8042 AUX port`、`Can't read CTR`、`Unable to get stable CTR read`、`No controller found`、`Unable to read current time from RTC`、`broken or not accessible`、`only 24-hr supported`、`Reading current time from RTC took around`）。**第二类比第一类更有价值**——设备探测失败时 Linux 往往还是能启动，只是慢、少了功能，正向断言容易全绿而毛病还在。反向断言的子串必须在钉住的 guest 内核源码里找得到对应的格式串，否则它永远不会命中，换内核时要逐条复核。TSC 用 `tests/lib.sh` 的 `expect_tsc_calibrated` 判定，判据见第 3.5 节。

还有几条来自 guest 自己的断言：

```sh
'echo SER-$(sed -n "s/^0: uart:\([^ ]*\).*/\1/p" /proc/tty/driver/serial_8250)'
'echo SER1-$(sed -n "s/^1: uart:\([^ ]*\).*/\1/p" /proc/tty/driver/serial_8250)'
'echo SERIRQ-$(sed -n "s/^ *4: *\([0-9]*\).*/\1/p" /proc/interrupts)-END'
'echo KBDIRQ-$(sed -n "s/^ *1: *\([0-9]*\).*/\1/p" /proc/interrupts)'
'echo RTCIRQ-$(sed -n "s/^ *8: *\([0-9]*\).*/\1/p" /proc/interrupts)'
```

期望是 `SER-16550A`、`SER1-unknown`、IRQ 4 计数非 0、`KBDIRQ-13`、`RTCIRQ-0`。`KBDIRQ-13` 是本卷最喜欢的一条断言：13 正好是读计数之前键盘设备回复的字节数——`atkbd` 初始化时的 GETID 回 3 个字节，F5、ED 00、F3 00、F4 各回一个 ACK，`atkbd_event_work()` 再发一轮 ED 00、F3 00 又是 4 个 ACK（第 5 节）。它一次同时锁住三件事——每个字节产生一次独立的边沿、控制器应答不打中断、没有多余中断。任何一处写错这个数字就变了。数字本身取决于 `atkbd` 发了哪些命令，换内核后要用 `--trace-pio` 数一遍 0x60 上的读写序列重新核对，不能直接改成新看到的数。

**trace 的结构。** 直接对 `--trace-pio` 的输出做静态检查：

```sh
expect_has "PIT-USERSPACE-0"      # 内核 irqchip：0x40-0x43 与 0x61 一条都不该落到用户态
expect_has "DMA0-R1-ff"           # 0x87 读回 0xFF
expect_has "S5-1401-3401-"        # 0x604 最后两次写：先 SLP_TYP 后 SLP_EN
```

`IRQCHIP=split` 时 PIT 在用户态，第一条反过来断言计数不为 0。这类断言的好处是它检查的是**机制**而不是**日志措辞**，换内核版本时不容易假失败。

**退出路径。** `reboot -f` 之后 trace 的最后一行必须是 `i8042-cmd 0064 W1 fe`，VMM 打印 `guest requested reset via i8042`。这同时验证了 `reboot=k` 这条命令行参数、i8042 的复位命令解码，以及“先记 trace 再判返回值”那个顺序。

### 10.4 断言该写多严

**写断言之前先问“它失败时能指向 VMM 的哪个缺陷”。** 指不出来的，要么放宽，要么换一个能指出来的断言。TSC 那条就是例子：PIT 校准的三种结局取决于 host 上读一次端口的开销和抖动，都不指向 VMM，所以一并接受；作为补偿，trace 结构的三条断言失败时能精确指到某一行代码。

### 10.5 人工验收

`tests/e2e/legacy-devices.sh -m` 打印三条人工项：用 `trace_decode.py` 逐段读一次启动的寄存器序列；确认串口确实是中断驱动（`/proc/interrupts` 的 IRQ 4 随输出增长）；以及把 `rtc_attach()` 摘掉重编，亲眼看一次 8 万次 exit 的代价。

## 11. 本卷小结与卷八预告

**方法。** 本卷和前几卷最大的不同是先测后读：mini-vmm 的 `--trace-pio` 把 guest 发出的每一次落到用户态的 PIO 原样录下来，再拿录到的序列去对源码。记录点放在设备回调**之后**、错误判断**之前**，这样触发退出的最后一次写也会留在 trace 里；未注册端口额外取一次 `KVM_GET_REGS` 记下 guest 的 RIP，`tools/trace_decode.py --syms` 把它解析成符号，就知道是谁在盲探。第 2 节的串口探测序列、第 5 节的 i8042 序列、第 7 节那张“谁在访问未注册端口”的表，都不是从手册推演出来的，而是从一次真实启动里抄下来的。**写设备模型时，能录就别猜。**

**命题。** 设备要模拟到什么程度，由驱动的探测逻辑决定。具体到这一卷：

- 让 Linux 认出一颗 16550A，只需要 IER 低 4 位可读写、FCR 的 bit0 能反映到 IIR 的 bit7:6 上。`autoconfig()` 四百行里剩下的都被 `UPF_SKIP_TEST` 和 `CONFIG_SERIAL_8250_16550A_VARIANTS=n` 挡住了。打开这个选项的内核还会跑完 EFR、NatSemi、TI16750、XScale、`size_fifo()` 一串探测，只要偏移 2 始终是 IIR/FCR、IER 高 4 位不可写，结论仍是 16550A。
- 让 Linux 相信没有 PS/2 鼠标，要精确地回两个“否”：AUX_LOOP 回字节但不置 AUXDATA，AUX_TEST 回 0x01。回 0x00 或 0xFF 都表示“有”。
- 让 Linux 相信没有 8237 DMA 控制器，只要端口 0x87 读回 0xFF。读回别的值它就认为有。
- 让 `rtc-cmos` 探测通过，寄存器 B 的 bit1 必须是 1，寄存器 A 的 UIP 必须能读到 0，时间必须是 BCD——这三条任何一条错了，代价是秒级的超时。

**不做也是一种做法。** PIT 是本卷唯一一个正确做法是完全不实现的设备：`KVM_CREATE_PIT2` 加一个 `KVM_PIT_SPEAKER_DUMMY` 标志，0x40–0x43 和 0x61 就全归内核了，用户态一次 exit 都看不到。代价是要知道这件事——不知道的话，会在用户态注册一个永远收不到访问的设备，而且没有任何提示。

**“不存在”比“存在”难表达。** 这是本卷反复出现的一条。设备不存在时驱动的行为不是“什么都不做”，而是“按某条特定路径失败”，而那条路径往往带着超时。第 4.5 节测到的 8 万次 exit、2 秒，第 5.4 节那两道 AUX 检查，第 7 节的 0x87，讲的都是同一件事：**未实现的设备要主动给出否定答案，而不是沉默。**

**guest 的配置和 host 的开销都会改变走哪条路径。** 第 3 节的 TSC 是个干净的例子：开了 kvmclock 的 guest 根本不碰 PIT；关掉 kvmclock 后，读一次 PIT 端口的开销决定快路能不能过，开销的抖动决定慢路能不能过，本机（嵌套虚拟化）上两条都过不去。第 7.2 节的 0x80 也是一样：`KVM_FEATURE_NOP_IO_DELAY` 让 guest 跳过 I/O 延迟写，隐藏这个特性后 0x80 的写就回来了。这直接说明了为什么断言要按“它失败时能指向什么缺陷”来写，而不是按“我这次看到了什么”来写。

**卷八：把 PIO exit 从热路径上拿掉。** 本卷最刺眼的一个数字是一次启动 42302 条用户态 PIO 里有 41450 条是串口，每个字符至少两次往返（写 THR、读 LSR）。这不是模拟得不对——恰恰相反，16550A 的语义就是一次一个字节。问题出在“设备接口”本身：一个为 1980 年代总线设计的寄存器协议，放到虚拟机里每次访问都要穿一遍用户态。卷八转向 VirtIO：用共享内存里的环形队列代替寄存器读写，用 ioeventfd 把“通知”变成内核里的一次 eventfd 写而不再回用户态，用 irqfd 把中断注入从 `KVM_IRQ_LINE` 这条 ioctl 上挪走。核心命题会从本卷的“模拟到什么程度”变成：**当设备可以为虚拟化重新设计时，接口应该长什么样。**
