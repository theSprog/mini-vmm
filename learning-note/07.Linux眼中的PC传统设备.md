# 卷七：Linux 眼中的 PC 传统设备——驱动探测逐寄存器追踪

> 承接卷五（固件表与 Linux 启动协议）与卷六（SMP 虚拟化与 CPU 拓扑），配套 blog 第二篇《从零理解 KVM：中断、设备与多核》的第六章与第十一章。
>
> 卷五让 guest 认识了这台机器，卷六让它把所有 CPU 都跑了起来。但在这两卷里，“设备”一直是被当作黑盒对待的：串口能出字、RTC 能读出时间、i8042 探测不会卡住，至于驱动究竟按什么顺序读写了哪几个寄存器、每一次读回的值分别决定了什么，都没有展开。本卷把这层黑盒拆开。
>
> 全卷只有一个命题：**设备要模拟到什么程度，由驱动的探测逻辑决定，而不是由芯片手册决定。** 16550A 的手册有几十页，Linux 的 `autoconfig()` 有四百行，而在我们这台 guest 上，真正决定“这是不是一颗 16550A”的只有 22 次端口访问。反过来，有些在手册里根本不起眼的约定——比如“不存在的端口读回 0xFF”——却是某个驱动判定“这台机器没有这个设备”的唯一依据，漏掉它就会多出一整个子系统。
>
> 方法上，本卷与前几卷不同：不再只靠读源码推断，而是**先把 guest 实际发出的每一次 PIO 访问录下来，再拿录到的序列去对源码**。为此给 mini-vmm 加了一个 `--trace-pio` 选项，它把每次陷出到用户态的端口访问写成一行，未注册端口还会附上 guest 的 RIP，拿到 `vmlinux` 上一查就知道是哪个函数在盲探。本卷引用的所有序列都出自这样一次真实启动，没有一条是照着手册推演出来的。
>
> host 侧源码基于 Linux **v5.15**（KVM），guest 侧源码基于 Linux **v6.6.91**，即 mini-vmm 实际引导的那个内核；文中 `file:line` 形式的行号都对应这两棵树。设备侧规范依据 National Semiconductor PC16550D 数据手册、Intel 8254/8259A 数据手册、Motorola MC146818A 数据手册、ACPI 6.4 第 4 章（ACPI Hardware Specification）与 IBM PC/AT 技术参考。

## 1. 命题：模拟到什么程度，由驱动决定

### 1.1 三种“完整”

写设备模型时，“做完了”至少有三个互不相同的标准。

第一种是**手册完整**：把数据手册上的每个寄存器、每个位、每种工作模式都实现出来。16550A 的 FIFO 触发门限有四档、波特率分频器是 16 位、MSR 的低 4 位是变化标志位（delta bits）、LSR 有奇偶错误和帧错误位。全做出来是一件很大的工程，而且做完之后你会发现绝大部分代码从来没被执行过。

第二种是**架构完整**：凡是 guest 有办法观察到的状态都要正确。这个标准比第一种弱，但依然过强——它要求你对“guest 有没有办法观察到”做出判断，而这个判断本身就需要知道 guest 会怎么访问。

第三种是**驱动完整**：让目标 guest 的驱动走完它的探测与工作路径，并且走到你希望它走到的那个分支。这是写 VMM 时真正该用的标准。它有两个特点：一是**小**，一次 Linux 启动里串口的全部寄存器访问只涉及 8 个端口中的 7 个，i8042 的控制器命令只用到 10 条；二是**不对称**，让驱动认为设备“存在且正常”，和让驱动认为设备“不存在”，是两件难度完全不同的事，而后者往往更重要——第 5 节的 AUX 口和第 7 节的 8237 DMA 控制器都是这个类型。

这个标准也有它的代价：结论只对**这个** guest、**这个**内核配置成立。本卷会反复出现“因为 `CONFIG_XXX` 没开，所以这段探测代码根本不会执行”这样的判断，换一个 `.config` 就得重新核对。所以每一处这样的结论，文中都会同时给出配置项和实测证据。

### 1.2 方法：把驱动的每一次寄存器访问录下来

KVM 的分工决定了 VMM 能看到什么。guest 执行 `in`/`out` 时，如果目标端口由内核态设备模型接管（PIC、PIT、LAPIC、IOAPIC），KVM 就地处理，用户态完全无感；否则产生一次 `KVM_EXIT_IO`，`kvm_run->io` 里带着端口号、方向、宽度、重复次数和数据缓冲区的偏移。于是**凡是能被 VMM 看见的 PIO，都是 VMM 自己负责的设备**，反过来也成立：trace 里没有的端口，要么没人访问，要么被内核态接走了。这一点在第 3 节会变成一个很强的观察结论。

追踪的实现在 `src/vm.c:178` 起的一小段，由 `--trace-pio FILE` 打开：

```c
static void pio_trace(const char *name, uint16_t port, bool is_out,
                      uint32_t size, const uint8_t *val, uint64_t rip)
{
    unsigned long long v = 0;
    struct timespec ts;
    uint32_t i;

    if (!g_pio_trace)
        return;

    clock_gettime(CLOCK_MONOTONIC, &ts);
    for (i = 0; i < size && i < sizeof(v); i++)
        v |= (unsigned long long)val[i] << (8 * i);

    fprintf(g_pio_trace, "%lld.%06ld %-11s %04x %c%u %0*llx",
            (long long)ts.tv_sec, ts.tv_nsec / 1000, name, port,
            is_out ? 'W' : 'R', size, (int)(size * 2), v);
    if (rip)
        fprintf(g_pio_trace, " rip=%016llx", (unsigned long long)rip);
    fputc('\n', g_pio_trace);
}
```

三个设计决定值得说明。

**记录时机在设备回调之后。** 对写来说值在调用前后一样，但对读来说，只有设备回调返回之后缓冲区里才是 guest 真正会读到的值。所以 `pio_trace()` 放在分发循环的末尾，而且**放在错误判断之前**（`src/vm.c:280`）——mini-vmm 用回调的返回值表示“guest 请求关机/复位”，触发退出的那一次写恰恰是整条 trace 里最值得留下的一行，放在 `return` 之后就会丢掉它。这个顺序是踩过一次才调对的：第 6 节里 ACPI S5 的最后一次 `out` 一开始就没被记下来。

**RIP 只对未注册端口取。** 已注册端口的设备名本身已经回答了“谁在访问”，而未注册端口恰恰是需要反查调用者的那一类。取 RIP 需要一次 `KVM_GET_REGS`，是一次 vCPU ioctl，只在这种情况下才付这个代价（`src/vm.c:224`）：

```c
static uint64_t pio_trace_rip(struct vmm_vcpu *vcpu)
{
    struct kvm_regs regs;

    if (!g_pio_trace)
        return 0;
    memset(&regs, 0, sizeof(regs));
    if (ioctl(vcpu->fd, KVM_GET_REGS, &regs) < 0)
        return 0;
    return regs.rip;
}
```

拿到 RIP 之后，`nm -n vmlinux` 排序一遍做一次二分查找就能定位到符号。本卷里几处“这是谁在访问”的结论都是这么来的，第 7 节会给出完整的对照表。

**不加锁。** `handle_io()` 全程持有 `vm->io_lock`（`src/vm.c:364`），多 vCPU 下 PIO 分发本来就是串行的，trace 的写入自然也串行，不需要额外的锁。这是卷六第 6.5 节那把大锁的一个副产品。

用法：

```sh
./build/vmm --mode linux --smp 1 --mem 512M \
    --trace-pio /tmp/pio.txt \
    --initrd initramfs.cpio.gz vmlinux
```

### 1.3 一次启动的 PIO 全景

下面这张表来自一次完整的 `--smp 1` 启动加 `poweroff -f` 关机，数字是本机（WSL2，HygonGenuine）上的一次实测。同一份代码在 soc63 上跑一次得到 30445 条，与本机的 30449 条相差 4 条，而这 4 条**全部**落在串口自己身上（两台机器打印出来的启动日志内容本来就略有不同，比如 CPU 型号那一行）；除串口外的每一个端口，两台机器的次数逐条相同。这一点本身就是个有用的信号：**设备探测序列由驱动代码决定，和跑在哪台 host 上无关。** 第 7.1 节那张未注册端口的表在两台机器上更是一条不差。

三个立刻能读出来的事实。

**串口占了 98.2%。** 29912 次里 29235 次是 `0x3f8` 写字符加 `0x3fd` 轮询状态这一对。每个字符两次 VM exit，一次启动打印大约 14800 个字符。这个数字是下一卷 VirtIO 与 ioeventfd 的全部动机：不是模拟得不对，而是每个字节都要穿一次用户态实在太贵。

**PIT 一次都没出现。** 端口 0x40–0x43 和 0x61 在整张 trace 里是空的。不是 Linux 不校准 TSC——启动日志里明明写着 `tsc: Using PIT calibration value`——而是这些端口被 KVM 的内核态 PIT 接管了。第 3 节专门讲这件事。

**同理，PIC 和 LAPIC 也不在表里。** 0x20/0x21/0xa0/0xa1 和 LAPIC 的 MMIO 页都由内核态 irqchip 处理。唯一漏出来的痕迹是 0x80 那 7 次写——`outb_p` 的延时写落在了一个没人接管的端口上，见第 7.2 节。

## 2. 16550A 串口：三段人生

串口是 mini-vmm 里唯一一个“既要被探测出来、又要一直高速工作”的设备，也是本卷材料最多的一个。它在一次启动里经历三段互不相同的人生：先是 `earlyprintk` 直接按端口号操作的一块裸硬件，然后是 `printk` 的正式 console，最后在 `/dev/console` 被打开之后变成一个中断驱动的 tty。三段用的是三份完全不同的代码，访问模式也完全不同。

### 2.1 寄存器与 DLAB

8 个寄存器挤在 8 个连续端口上，靠两个开关复用：

| 偏移 | DLAB=0 读 | DLAB=0 写 | DLAB=1 |
|---|---|---|---|
| 0 | RBR 接收保持 | THR 发送保持 | DLL 分频器低字节 |
| 1 | IER 中断使能 | IER | DLM 分频器高字节 |
| 2 | IIR 中断标识 | FCR FIFO 控制 | （LCR=0xBF 时为 EFR，扩展芯片才有） |
| 3 | LCR 线路控制 | LCR | — |
| 4 | MCR modem 控制 | MCR | — |
| 5 | LSR 线路状态 | （只读） | — |
| 6 | MSR modem 状态 | （只读） | — |
| 7 | SCR 便笺 | SCR | — |

DLAB 是 LCR 的 bit7。这个设计带来的直接后果是：**任何一次读写偏移 0 或 1 的行为，都必须先看 LCR 的当前值才能确定它的含义**。mini-vmm 的 `serial_read()`/`serial_write()` 每个 case 都先判 `s->lcr & UART_LCR_DLAB`（`src/devices/serial8250.c:159`、`:214`），这不是画蛇添足——第 2.3 节和第 2.6 节的 trace 里都能看到 Linux 先写 LCR=0x93 打开 DLAB、写完分频器再写 LCR=0x13 关掉，中间那两次对偏移 0/1 的写如果被当成 THR 和 IER，串口就直接乱了。

偏移 2 还有第三重身份：LCR 写成 0xBF（`UART_LCR_CONF_MODE_B`）时，一批扩展 16550 兼容芯片会把这里变成 EFR 寄存器。Linux 的 `autoconfig()` 用这条路径区分芯片型号，第 2.4 节会看到它写了一次 EFR=0。mini-vmm 不是那种芯片，于是把 `LCR == 0xBF` 时对偏移 2 的访问单独挡掉：读回 0、写丢弃（`serial8250.c:170`、`:234`）。**这一条是本卷核对过程中补上的**——原来这些访问会落到 IIR/FCR 上，恰好无害，第 2.9 节说明为什么“恰好”不够。

### 2.2 第一段：earlyprintk 的 9 次访问

mini-vmm 的默认命令行里有 `earlyprintk=serial,ttyS0,115200`（`src/main.c` 里的默认 cmdline，启动日志第一行会回显）。这条参数走的**不是** 8250 驱动，而是 `arch/x86/kernel/early_printk.c` 里一段几十行的裸代码，它在 `setup_arch()` 里就跑起来了，那时候连内存管理都还没初始化完。

trace 的最前面九行就是它：

```
serial8250  03fb W1 03      LCR = 0x03，8n1
serial8250  03f9 W1 00      IER = 0，关中断
serial8250  03fa W1 00      FCR = 0，关 FIFO
serial8250  03fc W1 03      MCR = DTR|RTS
serial8250  03fb R1 03      c = LCR
serial8250  03fb W1 83      LCR = c | DLAB
serial8250  03f8 W1 01      DLL = 1
serial8250  03f9 W1 00      DLM = 0
serial8250  03fb W1 03      LCR = c & ~DLAB
```

对照 `arch/x86/kernel/early_printk.c:130` 的 `early_serial_hw_init()`，九行一一对应，顺序一字不差：

```c
static __init void early_serial_hw_init(unsigned divisor)
{
	unsigned char c;

	serial_out(early_serial_base, LCR, 0x3);	/* 8n1 */
	serial_out(early_serial_base, IER, 0);	/* no interrupt */
	serial_out(early_serial_base, FCR, 0);	/* no fifo */
	serial_out(early_serial_base, MCR, 0x3);	/* DTR + RTS */

	c = serial_in(early_serial_base, LCR);
	serial_out(early_serial_base, LCR, c | DLAB);
	serial_out(early_serial_base, DLL, divisor & 0xff);
	serial_out(early_serial_base, DLH, (divisor >> 8) & 0xff);
	serial_out(early_serial_base, LCR, c & ~DLAB);
}
```

`divisor = 115200 / baud`（`early_printk.c:184`），命令行里写的是 115200，所以 DLL=1。

这九次访问里**没有一次是探测**。early_printk 不问“这里有没有串口”，它假定 0x3f8 上有一颗 UART 并直接开始用。这就是为什么它能在启动的最早期工作，也是为什么 `earlyprintk=` 参数必须由人手动给对——猜错了端口，内核只是往一个空地址写字节，不会有任何提示。

从 VMM 的角度看，要让这一段工作起来只需要满足两个条件：写 THR 的字节要送出去，读 LSR 要能读到 `THRE|TEMT` 都置位。分频器、LCR 的位宽/校验设置、MCR 的 DTR/RTS 一概不影响结果，因为 host 那一侧是一个文件描述符，不是一根真的线。mini-vmm 把 DLL/DLM 存下来但从不使用（`serial8250.c:215`、`:224`），LSR 干脆恒定返回 `THRE|TEMT`（`serial8250.c:184`）：

```c
    case UART_LSR:
        v = UART_LSR_THRE | UART_LSR_TEMT;
        if (!rx_empty(s))
            v |= UART_LSR_DR;
        break;
```

这一行决定了 `early_serial_putc()` 里那个 `while ((serial_in(..., LSR) & XMTRDY) == 0 && --timeout)` 循环永远只转一圈。代价是每个字符两次 VM exit：一次读 LSR，一次写 THR。第 1.3 节那 29235 次访问就是这么来的。

### 2.3 第二段：printk 的 console

`console=ttyS0` 让 8250 驱动在 `console_init()` 里注册一个真正的 console。这一步在 trace 里的位置很好找——紧挨着 `printk: console [ttyS0] enabled` 这行字：

```
serial8250  03f9 W1 00      IER = 0
serial8250  03fb W1 93      LCR = 0x13 | DLAB
serial8250  03f8 W1 0c      DLL = 12
serial8250  03f9 W1 00      DLM = 0
serial8250  03fb W1 13      LCR = 0x13
serial8250  03fa W1 00      FCR = 0
serial8250  03fc W1 01      MCR = DTR
```

两个值得停一下的细节。

**分频器是 12，不是 1。** `console=ttyS0` 后面没有跟波特率，`serial8250_console_setup()` 就用默认的 9600（`8250_core.c` 里 `baud = 9600`），`115200 / 9600 = 12`。也就是说 earlyprintk 阶段把串口设成 115200，正式 console 又把它改成 9600，而**输出速度一点没变**——因为 mini-vmm 根本不看分频器。真机上这里会有一次肉眼可见的速率切换，虚拟机里没有。这是“模拟到什么程度由驱动决定”的一个正面例子：分频器必须能写能读（否则 `autoconfig` 的某些分支会误判），但它的值可以完全不起作用。

**LCR 是 0x13，不是 0x03。** 0x13 = `UART_LCR_WLEN8`(0x03) | `UART_LCR_EPAR`(0x10)。命令行里没有指定校验，按说不该出现校验相关的位。原因在 `8250_port.c:2636` 的 `serial8250_compute_lcr()`：

```c
	if (c_cflag & PARENB)
		cval |= UART_LCR_PARITY;
	if (!(c_cflag & PARODD))
		cval |= UART_LCR_EPAR;
```

EPAR 是**无条件**跟着“不是奇校验”走的，跟 PARENB 没关系。在真硬件上 PARENB（bit3）为 0 时 EPAR 不起作用，所以这是个无害的写法，但它会让你在读 trace 时困惑一阵。mini-vmm 的 LCR 是原样存原样读（`serial8250.c:241`），不做任何合法性检查——这一点在这里正好是对的：**设备模型不该比真硬件更挑剔**。

从这里开始到 `/dev/console` 被打开之前，所有内核日志都走 `serial8250_console_write()`，它的模式是：进函数先读一次 IER 存起来、写 IER=0 关中断，然后每个字符 `wait_for_xmitr()` 读 LSR、写 THR，最后恢复 IER。trace 里每一行日志前后那对 `03f9 R` / `03f9 W` 就是它。

### 2.4 第三段之前：`autoconfig()` 用 22 次访问认出 16550A

`serial8250_isa_init_ports()` 按 `arch/x86/include/asm/serial.h` 里的 `SERIAL_PORT_DFNS` 注册四个 ISA 口（0x3f8/0x2f8/0x3e8/0x2e8），然后 `uart_add_one_port()` → `serial8250_config_port()` → `autoconfig()` 逐个探测。下面是 ttyS0 那一轮的全部访问，右边是对应的源码位置（`8250_port.c`）：


再加上第 6 步之前那次 `03f9 R`（第 1 步）和最后驱动读回 IER 的一次，正好落在 22 次上下。整段探测里**真正起判定作用的只有三次读**：

- 第 3、5 步的 IER 回读。这是“存在性测试”：把 IER 低 4 位写成 0 要能读回 0，写成 0x0f 要能读回 0x0f。mini-vmm 的 `s->ier = v & 0x0f`（`serial8250.c:230`）刚好满足。注释里写得很清楚，选 IER 是因为它是唯一一个“写什么读什么、而且不会产生副作用”的寄存器。
- 第 13 步的 IIR 回读。写 FCR 打开 FIFO 之后，IIR 的高两位要变成 11。mini-vmm 的 `update_irq()` 在 `s->fcr & UART_FCR_ENABLE` 时给 IIR 或上 0xC0（`serial8250.c:87`），于是读回 0xC1（NO_INT | FIFO）。0xC0 对应 `UART_IIR_FIFO_ENABLED_16550A`，判定结束。

### 2.5 三条没有走的路

`autoconfig()` 全文四百行，上面只用到了前六十行。剩下的都被跳过了，跳过的原因各不相同，而且每一条都值得记住——因为换一个 guest 配置它们就会活过来。

**回环测试被 `UPF_SKIP_TEST` 跳过。** `8250_port.c:1233` 那段本来要写 `MCR = LOOP|OUT2|RTS`，再读 MSR 的高 4 位，期望得到 `DCD|CTS`。但 x86 的 `SERIAL_PORT_DFNS`（`arch/x86/include/asm/serial.h`）给 COM1–COM3 都带了 `UPF_SKIP_TEST`：

```c
# define STD_COMX_FLAGS	(UPF_BOOT_AUTOCONF |	UPF_SKIP_TEST	| 0		)
# define STD_COM4_FLAGS	(UPF_BOOT_AUTOCONF |	0		| 0		)
```

理由在源码注释里：有些基于 Rockwell 芯片的内置调制解调器不实现回环，而“没有哪个板卡厂商会蠢到把设备做得和 COM1–4 冲突”。只有 COM4（0x2e8）没带这个标志——但它在第 1 步的 IER 测试就失败了（见 2.9），根本走不到这里。**结论：在这台 guest 上，mini-vmm 的回环实现（`serial8250.c:123` 的 `msr_value()`）一次都没有被执行过。** 它不是废代码，只是没有被现在这套配置触发，比如把串口挂到 0x2e8 就会触发。

**变体探测被 `CONFIG_SERIAL_8250_16550A_VARIANTS=n` 跳过。** `autoconfig_16550a()` 的第一件事（`8250_port.c:992`）是：

```c
	if (!IS_ENABLED(CONFIG_SERIAL_8250_16550A_VARIANTS) &&
	    !(up->port.flags & UPF_FULL_PROBE))
		return;
```

guest 的 `.config` 里这一项是 `# CONFIG_SERIAL_8250_16550A_VARIANTS is not set`，而 `UPF_FULL_PROBE` 在整棵树里只被 `8250_pci.c:1228` 设置过，`CONFIG_SERIAL_8250_PCI` 也没开。于是 ST16650、NS16550A、TI16750、XScale、16C950 的全部识别代码，以及那个带 `mdelay(20)` 的 `size_fifo()`，统统不执行。这是个很大的便宜：`size_fifo()` 会写 MCR=LOOP、把分频器改成 1、连写 256 个字节再读回来数个数，实现起来相当烦人，而在这套配置下它根本不会被调用。

**IRQ 自动探测被 `CONFIG_SERIAL_8250_DETECT_IRQ=n` 跳过。** `autoconfig_irq()`（`8250_port.c:1324`）靠 `probe_irq_on()` / `probe_irq_off()` 观察哪根 IRQ 线被拉起来，做法是写 `MCR = OUT1|OUT2`、写 `IER = 0x0f`、往 THR 写一个 0xFF，然后看中断落在哪。`SERIAL_PORT_DFNS` 里 COM1 的 IRQ 写死是 4，配置项没开就不带 `UPF_AUTO_IRQ`，这段也不会执行。mini-vmm 在 MP 表和 MADT 里把串口登记在 GSI 4 上（卷五第 6 节），跟这里的写死值必须一致——不一致的话中断收不到，但**探测阶段不会有任何报错**，因为根本没人去验证。

### 2.6 第三段：`/dev/console` 被打开，串口变成中断驱动

`kernel_init_freeable()` 的最后一步是 `console_on_rootfs()`（`init/main.c:1558`），它 `filp_open("/dev/console", O_RDWR)`，这一下走通 tty 层，触发 `uart_port_startup()` → `serial8250_do_startup()`。在 trace 里这一段紧挨着 `Freeing unused kernel image (initmem) memory` 之前，正好对上 `kernel_init()` 里 `kernel_init_freeable()` 在 `free_initmem()`（`init/main.c:1452`）之前的顺序。

第 7–13 步是 **THRE bug 测试**：两次“打开 THRI 中断、读 IIR、关掉”。真 16550 在发送器空闲且中断已使能时应该**反复**重新置位 THRE 中断，坏芯片只置一次。判据在 `8250_port.c:2367`：`iir1` 有中断而 `iir` 没有，就置 `UART_BUG_THRE`，之后驱动要额外挂一个定时器去踢串口。mini-vmm 两次都报 THRI，所以不带这个 bug 标志。**这正是 `serial8250.c:226` 那段注释存在的理由**：

```c
            /* 打开 THRI 的瞬间如果 THR 是空的，要马上来一次中断。
             * Linux 的 serial8250_start_tx 就是靠这个启动发送的。 */
            if (!(s->ier & UART_IER_THRI) && (v & UART_IER_THRI))
                s->thri_pending = true;
```

写 IER 时如果 THRI 从 0 变 1 就置上待决标志——第 9 步和第 12 步都靠它。少了这一句，第二次读 IIR 会读到 NO_INT，Linux 就会给我们扣上 `UART_BUG_THRE` 的帽子，然后每 25ms 拿定时器轮询一次串口。

第 16–19 步是 **TXEN bug 测试**（`8250_port.c:2411`），判据是 `lsr & TEMT && iir & NO_INT`。mini-vmm 的 LSR 有 TEMT，但 IIR 报的是 THRI 而不是 NO_INT，所以不置 `UART_BUG_TXEN`，皆大欢喜。

**第 20 步那次多出来的 IIR 读，是 MCR.OUT2 门控的一次现场演示。** 注意第 7–13 步的 THRE 测试之后没有多余的 IIR 读，而第 16–19 步的 TXEN 测试之后就有；两者之间唯一发生的事，是第 15 步把 MCR 从 0x01 改成了 0x09——**OUT2 被置上了**。mini-vmm 的 `update_irq()` 只有在 OUT2 置位时才真的去拉 IRQ 线（`serial8250.c:94`）：

```c
    level = !(iir & UART_IIR_NO_INT) && (s->mcr & UART_MCR_OUT2)
            && !(s->mcr & UART_MCR_LOOP);
```

于是 THRE 测试期间 IER.THRI 虽然打开了，中断线却没动；TXEN 测试期间同样的操作就把 IRQ 4 拉了起来，等 `serial8250_interrupt()` 真正跑到时 IER 已经被第 19 步清零，它读到 IIR=0x01（NO_INT）就返回了——这就是第 20 步。

PC 上 COM 口的中断要经过 MCR.OUT2 这个门控才能到 PIC，是 IBM PC/AT 的板级接线决定的，不是 16550 芯片本身的功能；`8250_port.c:2386` 的注释 “Most PC uarts need OUT2 raised to enable interrupts” 说的就是这件事。**如果 VMM 不实现这个门控，上面这条链路就会提前一步发生**：THRE 测试期间就会有中断，虽然不至于出错，但它说明你的模型和真硬件的行为已经分叉了。

第 22–25 步是 `serial8250_set_termios()` 在收尾：IER 设成 `RLSI|RDI`（接收相关的中断），分频器设成 9600，FCR 设成 `ENABLE|R_TRIG_10`（`uart_config[PORT_16550A].fcr`，`8250_port.c:82`），MCR 补上 RTS。从这一刻起串口是中断驱动的：发送时 `serial8250_start_tx()` 打开 IER.THRI，靠 THRE 中断一批批送字节。

`RTS|CTS|DTR|DSR|CD` 这一串来自 MCR 的 DTR/RTS 和 MSR 的 CTS/DSR/DCD。mini-vmm 把 MSR 的常态设成 `DCD|DSR|CTS`（`serial8250.c:265`），相当于“线接好了、对端在线”，于是 tty 层不会因为载波丢失去挂断终端。这是个容易漏的点：MSR 如果返回 0，`uart_handle_dcd_change()` 会认为载波掉了，正在等待的进程会收到 SIGHUP。

### 2.7 IIR 的优先级与“只报一个”

16550 的中断源有四类，IIR 的 bit3:1 只报告当前优先级最高的那一个：接收线状态（0b011）> 接收数据可用（0b010）> THR 空（0b001）> modem 状态（0b000）。bit0 反过来——**0 表示有中断，1 表示没有**。

mini-vmm 只实现中间两类（`serial8250.c:77` 的 `update_irq()`）：

```c
    uint8_t iir = UART_IIR_NO_INT;

    if ((s->ier & UART_IER_RDI) && !rx_empty(s))
        iir = UART_IIR_RDI;
    else if ((s->ier & UART_IER_THRI) && s->thri_pending)
        iir = UART_IIR_THRI;
```

两个约束在这几行里：**IIR 报告的必须是当前实际有效的中断**（所以每次寄存器访问之后都重算一遍，`serial_read()` 和 `serial_write()` 结尾都调 `update_irq()`），以及**读 IIR 拿到 THRI 即视为应答**（`serial8250.c:174`），这是 16550 的规定——THR 空中断的清除条件有两个，写 THR 或者读 IIR，少实现一个就会让中断一直挂着。

顺带说明一个容易写错的地方：`update_irq()` 里的 `level != s->irq_level` 判断不是优化，是必需的。IOAPIC 上 ISA IRQ 是边沿触发，每一次新的中断都需要一个真实的 0→1 跳变；如果每次访问都无条件调一次 `KVM_IRQ_LINE(level=1)`，KVM 侧看到的是电平没变，不会产生新的边沿，第二个字节的中断就丢了。卷四第 7 节详细讨论过这条链路。

### 2.8 ttyS1/2/3：0xFF 是怎么让探测失败的

trace 里 0x2f9、0x3e9、0x2e9 各有 6 次访问，一次不多一次不少：

```
unhandled   02f9 R1 ff rip=...io_serial_in+0x1c
unhandled   02f9 W1 00 rip=...io_serial_out+0x1e
unhandled   02f9 R1 ff rip=...io_serial_in+0x1c
unhandled   02f9 W1 0f rip=...io_serial_out+0x1e
unhandled   02f9 R1 ff rip=...io_serial_in+0x1c
unhandled   02f9 W1 ff rip=...io_serial_out+0x1e
```

这正是第 2.4 节第 1–6 步的 IER 存在性测试，而且**只有这 6 步**。因为 `scratch2 = 0xff & 0x0f = 0x0f ≠ 0`，`8250_port.c:1210` 的判断当场失败，`goto out`，`port->type` 保持 `PORT_UNKNOWN`，所以 `/proc/tty/driver/serial` 里它们是 `uart:unknown`。

这里有个值得想一想的地方：**如果未注册端口读回 0x00 而不是 0xFF，结果也是失败**，因为 `scratch3` 会是 0 而不是 0x0f。两条路都失败，但失败的位置不同。0xFF 是对的那一个，理由不在这里——在第 7 节，8237 DMA 控制器那个例子里，0xFF 和 0x00 会得出完全相反的结论。

注意第 6 步写回去的是 `scratch`，也就是第 1 步读到的 0xFF。驱动老老实实地把“旧值”还原到了一个不存在的端口上。设备模型必须能接住这种写（丢弃即可），不能因为“这个值不合法”就报错。

### 2.9 mini-vmm 的实现边界，以及两处本卷改掉的地方

把前面几节的结论汇总，mini-vmm 的 16550A 模型里真正**必需**的部分只有这些：

| 行为 | 谁依赖它 | 不做的后果 |
|---|---|---|
| IER 低 4 位可读写 | `autoconfig()` 存在性测试 | 端口被判为不存在，`console=ttyS0` 无效 |
| FCR.bit0 反映到 IIR.bit7:6 | `autoconfig()` 类型判定 | 被认成 8250 或 16450，FIFO 不启用 |
| LSR 的 THRE/TEMT 恒置位 | earlyprintk、`wait_for_xmitr` | 输出卡死或极慢 |
| LSR.DR 跟随接收缓冲 | tty 收字符 | 键盘输入收不到 |
| 打开 IER.THRI 时补一次 THRI | THRE bug 测试、`start_tx` | 被扣 `UART_BUG_THRE`，改成定时器轮询 |
| 读 IIR 应答 THRI | 16550 语义 | 中断一直挂着，中断风暴 |
| MCR.OUT2 门控中断 | PC/AT 板级接线 | 探测期间出现不该有的中断 |
| MSR 常态 `DCD|DSR|CTS` | tty 的载波检测 | 终端被挂断 |
| DLAB 复用偏移 0/1 | 每一段代码都在用 | 分频器写进 THR，输出乱码 |

**不必需**的部分（在这套配置下）：回环模式、EFR、波特率真的生效、FIFO 真的有深度、LSR 的错误位、MSR 的 delta 位、SCR。mini-vmm 实现了回环和 SCR，没实现其余的。

EFR 这一条值得单独说一句，回应 2.1 节留下的问题。改之前，`autoconfig()` 第 9–11 步的 `LCR=0xBF`、`EFR=0`、`LCR=0` 里那次 EFR 写会落到 FCR 上。**它之所以无害，是因为写的值恰好是 0，而且顺序恰好合适**——FIFO 被关掉了，紧接着第 12 步又写 `FCR=UART_FCR_ENABLE_FIFO` 重新打开，第 13 步才读 IIR。

这是运气，不是设计。`autoconfig_16550a()` 里的变体探测（`8250_port.c:1000` 起）会读 EFR、往 EFR 写 0xA8 再读回来——落到 IIR/FCR 上，读到的是 IIR 的 0xC1（不是 EFR 该有的 0），写 0xA8 则因为 bit0 为 0 而把 FIFO 使能位清掉。这套配置下这段代码不会执行（2.5 节），所以看不出问题；一旦 guest 打开 `CONFIG_SERIAL_8250_16550A_VARIANTS`，探测就会沿着一条谁也没验证过的路径走下去。

**“没实现某个寄存器”和“把它悄悄复用成另一个寄存器”是两回事**，后者只在写入值恰好无害时才安全。本卷把它改成显式的“这颗芯片没有 EFR”：`LCR == 0xBF` 时偏移 2 的读回 0、写丢弃（`serial8250.c:51` 的 `UART_LCR_CONF_B` 与 `:170`、`:234`）。改完之后四套测试的结果一字不变——这正是预期，因为当前配置下根本走不到那条路；它的价值在于**把一次侥幸变成一条明确的语义**。

核对过程中发现 `serial8250.c:130` 的注释有一处与事实不符：

```c
    /* 回环时 modem 输入线由 MCR 输出线直接驱动（16550 datasheet 规定）：
     *   RTS -> CTS, DTR -> DSR, OUT1 -> RI, OUT2 -> DCD
     * Linux autoconfig 写 MCR=LOOP|0x0A 后要读到 MSR 高 4 位 = 0x90。 */
```

前两行是对的，第三行不对：x86 上 COM1–COM3 带 `UPF_SKIP_TEST`，这段测试根本不执行；COM4 不带，但它在更早的 IER 测试就已经出局。也就是说这段回环代码在当前配置下从未被执行过。它仍然值得留着——把串口挪到 0x2e8，或者 guest 打开 `CONFIG_SERIAL_8250_16550A_VARIANTS`（`size_fifo()` 也用回环）时就会用上——但注释应当说清楚“什么时候会用上”，而不是断言“Linux autoconfig 会这么做”。第 11 节把它列为本卷的第一条改进。

## 3. 8254 PIT：一条在 trace 里完全看不见的设备

### 3.1 一个不该被忽略的空白

第 1.3 节那张表里没有 0x40–0x43，也没有 0x61。这两组端口是 8254 PIT 和它的门控/扬声器端口，是 x86 上最古老的定时器。启动日志里明明白白地写着内核用它校准了 TSC：

```
# 本机（WSL2）
[    0.012000] tsc: Using PIT calibration value
[    0.014000] tsc: Detected 2299.022 MHz processor

# soc63（裸机 KVM）
[    0.000000] tsc: Fast TSC calibration using PIT
[    0.000000] tsc: Detected 3000.045 MHz processor
```

两台机器走的还不是同一条路——这件事第 3.3 节会变成本节最有意思的一个结论。

那为什么一次访问都没录到？因为 `irqchip_create()` 里那一行：

```c
    memset(&pit, 0, sizeof(pit));
    pit.flags = KVM_PIT_SPEAKER_DUMMY;
    if (ioctl(vm->vm_fd, KVM_CREATE_PIT2, &pit) < 0) {
```

`KVM_CREATE_PIT2` 让 KVM 在内核里注册两个 PIO 设备（host `arch/x86/kvm/i8254.c:703` 与 `:710`）：

```c
	kvm_iodevice_init(&pit->dev, &pit_dev_ops);
	ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS, KVM_PIT_BASE_ADDRESS,
				      KVM_PIT_MEM_LENGTH, &pit->dev);
	...
	if (flags & KVM_PIT_SPEAKER_DUMMY) {
		kvm_iodevice_init(&pit->speaker_dev, &speaker_dev_ops);
		ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS,
					      KVM_SPEAKER_BASE_ADDRESS, 4,
					      &pit->speaker_dev);
```

`KVM_PIT_BASE_ADDRESS` = 0x40、长度 4，`KVM_SPEAKER_BASE_ADDRESS` = 0x61（`i8254.h:53`）。guest 对这些端口的 `in`/`out` 仍然会触发一次 VM exit，但 exit 在 host 内核里就被 `pit_ioport_write()` / `speaker_ioport_read()` 消化掉，`KVM_RUN` 根本不返回用户态。于是从 VMM 的角度看，这台机器上不存在 PIT。

这是本卷方法的一个重要边界：**`--trace-pio` 看到的是“VMM 负责的设备”，不是“guest 访问过的端口”。** 判断一个端口去了哪里，要先看 KVM 内核里注册了什么。

### 3.2 `KVM_PIT_SPEAKER_DUMMY` 到底做了什么

这个标志的名字有误导性——它和发声毫无关系。端口 0x61 在 PC/AT 上是 NMI 状态与控制寄存器，低两位是给 PIT 通道 2 用的：

| 位 | 含义 |
|---|---|
| 0 | 通道 2 的 GATE（1 = 允许计数） |
| 1 | 扬声器数据使能（把通道 2 的 OUT 接到喇叭上） |
| 4 | refresh clock，约 15 µs 翻转一次 |
| 5 | 通道 2 当前的 OUT 电平 |

不带这个标志时，KVM 只接管 0x40–0x43，0x61 会掉到用户态。而 Linux 的两个 TSC 校准函数都要靠 0x61 干活：拉高 bit0 让通道 2 开始计数，然后轮询 bit5 等待计数结束。VMM 如果不处理 0x61，读回 0xFF 时 bit5 恒为 1，`pit_calibrate_tsc()` 里的 `while ((inb(0x61) & 0x20) == 0)` 一进去就退出，`pitcnt` 为 0，小于 `loopmin`，直接返回 `ULONG_MAX`。

KVM 的实现只有十几行（`i8254.c:585` 与 `:602`）：

```c
	mutex_lock(&pit_state->lock);
	pit_state->speaker_data_on = (val >> 1) & 1;
	pit_set_gate(pit, 2, val & 1);
	mutex_unlock(&pit_state->lock);
```

```c
	/* Refresh clock toggles at about 15us. We approximate as 2^14ns. */
	refresh_clock = ((unsigned int)ktime_to_ns(ktime_get()) >> 14) & 1;

	mutex_lock(&pit_state->lock);
	ret = ((pit_state->speaker_data_on << 1) | pit_get_gate(pit, 2) |
		(pit_get_out(pit, 2) << 5) | (refresh_clock << 4));
```

写只取 bit1 和 bit0，读把 GATE、OUT 和一个用主机时钟造出来的 refresh clock 拼回去。**它做的全部事情就是把 0x61 和通道 2 的状态机接上**，喇叭那一位只是存下来给 `KVM_GET_PIT2` 用。

还有一个细节值得注意：speaker 设备注册的长度是 4，覆盖 0x61–0x64，但 `speaker_ioport_write()` 的第一句是 `if (addr != KVM_SPEAKER_BASE_ADDRESS) return -EOPNOTSUPP;`。`__kvm_io_bus_write()`（`virt/kvm/kvm_main.c:4888`）在设备返回非 0 时会继续找下一个设备，都不行就返回 `-EOPNOTSUPP`，最终退回用户态。所以 0x62/0x63/0x64 仍然归 VMM。这不是理论推演——trace 里 0x64 实实在在有 49 次访问（第 5 节的 i8042 命令端口），如果 KVM 真的把 0x64 吞掉了，键盘控制器就一次也探测不到。

mini-vmm 也正因为这样才把 i8042 拆成两个单字节设备注册（`src/devices/i8042.c:337`）：

```c
    /* 0x60 和 0x64 中间隔着 0x61（PIT gate，由 KVM 内核处理），
     * 所以分两个单字节设备注册，不能占 [0x60, 0x65) 整段。 */
```

如果按 `[0x60, 0x65)` 一整段注册，mini-vmm 自己的表不会报冲突（`io_register()` 只检查自己的表），但 0x61 的访问永远不会到达用户态，这个设备的一部分就是死的——而且没有任何提示。

### 3.3 `quick_pit_calibrate()`：成不成功取决于读一次 PIT 有多贵

Linux 校准 TSC 有快慢两条路。快路是 `quick_pit_calibrate()`（`arch/x86/kernel/tsc.c:563`），思路很漂亮：

```c
	/* Set the Gate high, disable speaker */
	outb((inb(0x61) & ~0x02) | 0x01, 0x61);
	/* Counter 2, mode 0 (one-shot), binary count */
	outb(0xb0, 0x43);
	/* Start at 0xffff */
	outb(0xff, 0x42);
	outb(0xff, 0x42);
```

把通道 2 设成模式 0（一次性、到达终止计数时 OUT 拉高）、二进制计数、初值 0xFFFF，然后反复读计数器的高字节，记下每次高字节变化时的 TSC 值。PIT 的时基是 1193182 Hz，高字节每变一次正好是 256 个 PIT tick ≈ 214.5 µs，于是两次高字节变化之间的 TSC 差就直接给出 TSC 频率。

读计数器用的是 `pit_verify_msb()`（`tsc.c:526`）：

```c
static inline int pit_verify_msb(unsigned char val)
{
	/* Ignore LSB */
	inb(0x42);
	return inb(0x42) == val;
}
```

每次两个 `inb`——PIT 的数据端口是先低后高，所以要连读两次才能拿到高字节。

关键在精度控制。`tsc.c:609`：

```c
			/*
			 * Extrapolate the error and fail fast if the error will
			 * never be below 500 ppm.
			 */
			if (i == 1 &&
			    d1 + d2 >= (delta * MAX_QUICK_PIT_ITERATIONS) >> 11)
				return 0;
```

`d1`、`d2` 是两次采样各自最后一段循环的 TSC 跨度，本质上就是“读一次 PIT 要多久”。真硬件上一次 `inb` 约 1 µs，`d1+d2` 只有几微秒；`delta` 是 214.5 µs 对应的 TSC 周期数。外推一下如果误差永远降不到 500 ppm，**直接返回 0，一个字都不打印**。

这个函数上面那段注释（`tsc.c:491`）说得很直白：“This reads the current MSB of the PIT counter, and checks if we are running on sufficiently fast and **non-virtualized** hardware.” 在 KVM 下每个 `inb(0x42)` 都是一次 VM exit——虽然由 host 内核就地处理、不回用户态，但依然要走 VMEXIT/VMRUN 这一整套。

按这段注释的口气，很容易得出“快路在虚拟机里必然失败”的结论。**实测不是这样，而且两台机器的结果正好相反：**

| | soc63（裸机 KVM） | 本机（WSL2，KVM 跑在 Hyper-V 的 guest 里，属于嵌套虚拟化） |
|---|---|---|
| 连跑 6 次的结果 | 6 次全是 `Fast TSC calibration using PIT` | 5 次 `Using PIT calibration value`，1 次 `Unable to calibrate against PIT` |
| 走的是哪条路 | 快路成功 | 快路静默失败，慢路接手（其中一次慢路也失败） |

也就是说，`tsc.c:609` 那个 500 ppm 的外推阈值，恰好卡在“一次 VM exit 的开销”这个量级上：裸机 KVM 的一次 PIO exit 够便宜，快路能过；再套一层虚拟化就过不去了。**同一份 guest 内核、同一份 VMM，跑在不同的 host 上会走不同的校准路径**——这对写测试的人是个直接的教训，第 3.5 节会讲它怎么变成一条 flaky 断言。

快路失败时具体走的是哪个出口，也是可以从日志反推的，不必猜。`quick_pit_calibrate()` 一共三个出口：成功打印 `Fast TSC calibration using PIT`（`tsc.c:650`），常规失败打印 `Fast TSC calibration failed`（`tsc.c:631`），只有 `tsc.c:611` 那条 fail-fast 是静默的。本机的日志里这两条消息一条都没有，却出现了 `Using PIT calibration value`——这句只在慢路 `pit_hpet_ptimer_calibrate_cpu()` 里打印（`tsc.c:881`），而慢路只在 `native_calibrate_cpu()` 发现快路返回 0 时才会被调用（`tsc.c:927`）。三条消息互斥，剩下唯一一条路就是静默的 fail-fast。

顺带排除两种替代解释：`has_legacy_pic()` 为假会让 `pit_calibrate_tsc()` 走 `udelay` 分支并打印 `Unable to calibrate against PIT`（`tsc.c:858`），那次日志里没有；`cpu_khz_from_cpuid()` 或 `cpu_khz_from_msr()` 返回非零的话 `native_calibrate_cpu()` 会提前返回，慢路根本不会跑，也就不会有 `Using PIT calibration value`。

### 3.4 `pit_calibrate_tsc()`：慢路，也是真正生效的那条

慢路在 `tsc.c:425`，被 `pit_hpet_ptimer_calibrate_cpu()` 连调三次（`tsc.c:790` 的 `for (i = 0; i < 3; i++)`），每次 `CAL_MS` = 10 ms：

```c
	/* Set the Gate high, disable speaker */
	outb((inb(0x61) & ~0x02) | 0x01, 0x61);
	outb(0xb0, 0x43);
	outb(latch & 0xff, 0x42);
	outb(latch >> 8, 0x42);

	tsc = t1 = t2 = get_cycles();
	...
	while ((inb(0x61) & 0x20) == 0) {
		t2 = get_cycles();
		...
		pitcnt++;
	}
```

和快路的区别是：它不再逐次读计数器，而是**只轮询 0x61 的 bit5**（通道 2 的 OUT）等一次性计数走完，中间每转一圈记一次 TSC，用最大最小值的比例来判断这段时间有没有被 SMI 之类的东西打断（`tsc.c:482`：`pitcnt < loopmin || tscmax > 10 * tscmin` 就作废）。这条路对每次 I/O 的延迟不敏感，只要求总时长准确，所以在虚拟机里能过。

它依赖的 KVM 行为正好是第 3.2 节那两段代码：`outb(0xb0, 0x43)` 让 `pit_ioport_write()` 把通道 2 设成模式 0，两次 `outb(..., 0x42)` 装入初值并开始计时，`inb(0x61)` 的 bit5 由 `pit_get_out(pit, 2)` 算出来——模式 0 的公式是 `out = (d >= c->count)`（`i8254.c:154`），`d` 是从装入初值到现在按 1193182 Hz 折算的 tick 数。也就是说 KVM 的 PIT 通道 2 根本没有“计数器”，它是用 host 的 `ktime_get()` 反推出来的。这就是为什么慢路能给出一个可信的值：**它测的其实是 host 的时钟。**

最后一段是三次结果的取舍（`tsc.c:853` 起）。我们的 guest 既没有 HPET（mini-vmm 不提供 HPET 表），FADT 里也没有 PM timer，于是 `hpet`、`ref1`、`ref2` 全为 0，走 `tsc.c:880`：

```c
	/* We don't have an alternative source, use the PIT calibration value */
	if (!hpet && !ref1 && !ref2) {
		pr_info("Using PIT calibration value\n");
		return tsc_pit_min;
	}
```

三次取最小值（`tsc.c:806` 的 `tsc_pit_min = min(...)`），因为任何干扰都只会让测出来的频率偏高。

### 3.5 慢路也会失败，而且这件事是个已知的 flaky 来源

慢路对每次 I/O 的延迟不敏感，但它有另一道抽查（`tsc.c:482`）：

```c
	if (pitcnt < loopmin || tscmax > 10 * tscmin)
		return ULONG_MAX;
```

`tscmin` / `tscmax` 是那 10 ms 轮询循环里相邻两次 `get_cycles()` 之差的最小值和最大值。**vCPU 线程只要在这 10 ms 里被 host 调度器抢占一次**，某一圈的间隔就会比其他圈大几个数量级，`tscmax > 10 * tscmin` 成立，整轮作废。三轮都作废就走到 `tsc.c:856`：

```
[    0.012000] tsc: Unable to calibrate against PIT
[    0.014000] tsc: No reference (HPET/PMTIMER) available
[    0.015000] tsc: Marking TSC unstable due to could not calculate TSC khz
[    0.579000] clocksource: Switched to clocksource refined-jiffies
```

在本机（WSL2，有其他负载）连跑 6 次出现了 1 次；soc63 上那 6 次连快路都没失败，自然更不会走到这里。

对写 VMM 的人，这条有两层意义。第一，**这不是 VMM 的缺陷**：PIT 通道 2 的行为由 KVM 内核模块提供，VMM 这一侧没有任何可调的东西；真正的原因是 vCPU 线程被 host 抢占，和卷六第 6 节讲的“vCPU 就是一个普通线程”是同一件事。第二，**测试断言必须把三种结局一并接受**。mini-vmm 的 `tests/step2.sh` 原来断言的是

```sh
expect_any "tsc: Fast TSC calibration using PIT" "tsc: Using PIT calibration value"
```

在 soc63 上它长期是绿的（走第一个候选），在本机上大多数时候也是绿的（走第二个候选），但每六次左右会挂一次——因为第三种结局 `Unable to calibrate against PIT` 没被列进去。它旁边那句注释“快速 PIT 校准……偶尔失败并悄悄退回慢速 PIT 校准（实测约三成）”也不准：它把“快路失败”当成了偶发，而在本机上快路是**必然**失败的，偶发的是慢路。本卷把这条断言改成三选一，并在注释里写清三种结局各自对应什么 host 环境。

这类断言的通病是**把一次观察当成了规律**。判断一条断言该写多严，标准是“它失败时能不能指向 VMM 的某个具体缺陷”——这三种结局都不能，所以它们都该被接受；而 `Fast TSC calibration failed`（快路的非静默失败）如果出现，说明读 PIT 的开销分布和我们的分析完全对不上，那才值得停下来看。

### 3.6 PIT 作为中断源

除了校准，PIT 还是 GSI 0 上的周期性中断源。`irqchip_create()` 的注释提到它，卷四第 8 节讲过完整的中断路径。这里只补一条 trace 侧的观察：guest 里 `/proc/interrupts` 的第 0 行

```
  0:        501   IO-APIC   0-edge      timer
```

这 501 次中断全部由 KVM 内核态的 hrtimer 产生并注入，用户态既不知道它们发生过，也没有为它们付任何代价。对比一下同一次启动里串口的 29912 次用户态往返，能直观地看出“把设备放进内核”这件事的收益有多大。

`..TIMER: vector=0x30 apic1=0 pin1=0 apic2=-1 pin2=-1` 这行日志说明定时器走的是 IOAPIC 的 pin 0、向量 0x30，没有用 pin2 备份路径。卷五第 8 节讲过为什么 mini-vmm 不能照抄 QEMU 那套“IRQ0 接 pin 2 加 Interrupt Source Override”的写法——KVM 的默认 GSI 路由是恒等映射，照抄会让时钟中断丢失。

### 3.7 这一节对写 VMM 的意义

PIT 是本卷里唯一一个“**正确做法是不做**”的设备。mini-vmm 没有一行 PIT 模拟代码，只有 `irqchip_create()` 里的一次 `KVM_CREATE_PIT2` 和一个标志位。要点有三条：

1. **`KVM_PIT_SPEAKER_DUMMY` 必须带上。** 不带的话 0x61 掉到用户态，TSC 校准会间歇性失败——间歇性，因为 `quick_pit_calibrate()` 本来就允许失败，真正出问题的是慢路。症状是 `Unable to calibrate against PIT` 之后 jiffies 不走，离“端口 0x61 没人应答”这个原因非常远。
2. **`KVM_CREATE_PIT2` 要在 `KVM_CREATE_IRQCHIP` 之后。** PIT 的中断要挂到 GSI 0，没有 irqchip 就没地方挂。mini-vmm 的顺序在 `irqchip.c:23` 和 `:38`。
3. **别去占 0x61。** 它已经被内核接管了，用户态注册的设备永远收不到访问。

## 4. CMOS RTC：UIP 协议与两个 1 秒超时

### 4.1 索引/数据端口与 NMI 位

MC146818 只占两个端口。0x70 是索引口（只写），0x71 是数据口。读一个寄存器要两次 I/O：先往 0x70 写寄存器号，再从 0x71 读值。x86 上的封装在 `arch/x86/kernel/rtc.c:81`：

```c
unsigned char rtc_cmos_read(unsigned char addr)
{
	unsigned char val;

	lock_cmos_prefix(addr);
	outb(addr, RTC_PORT(0));
	val = inb(RTC_PORT(1));
	lock_cmos_suffix(addr);
	return val;
}
```

`RTC_PORT(x)` = `0x70 + x`（`arch/x86/include/asm/mc146818rtc.h`），`lock_cmos_prefix/suffix` 在 64 位下是空的。注意这里用的是 `outb`/`inb` 而不是 `outb_p`/`inb_p`——所以 RTC 访问不会顺带产生第 7.2 节那种 0x80 延时写，trace 里 0x70/0x71 永远是干净的两两成对。

0x70 的 bit7 是 NMI 屏蔽位，跟寄存器选择无关：写 0x80|reg 表示“选 reg 并且屏蔽 NMI”。mini-vmm 只取低 7 位（`src/devices/rtc.c:97`）：

```c
    if (off == 0) {
        /* bit7 是 NMI 屏蔽位，和寄存器选择无关 */
        g_rtc.index = v & 0x7f;
```

寄存器布局的前 14 个字节是时钟和控制，剩下 114 字节是 CMOS RAM：

| 索引 | 内容 | mini-vmm 的值 |
|---|---|---|
| 0x00/0x02/0x04 | 秒 / 分 / 时 | 每次读现取 host UTC |
| 0x06 | 星期（1–7） | 有实现，但 Linux 不读 |
| 0x07/0x08/0x09 | 日 / 月 / 年（两位） | 现取 |
| 0x0A | 寄存器 A：UIP(bit7)、时基、周期中断分频 | 0x26，**UIP 恒为 0** |
| 0x0B | 寄存器 B：中断使能、24 小时制(bit1)、BCD/二进制(bit2) | 0x02 |
| 0x0C | 寄存器 C：中断标志（读后清零） | 0 |
| 0x0D | 寄存器 D：电池有效(bit7) | 0x80 |
| 0x32 | 世纪（由 FADT 指定的索引） | 现取 |
| 其余 | CMOS RAM | 可读可写的普通字节 |

### 4.2 UIP 协议：`mc146818_avoid_UIP()`

真硬件的 MC146818 每秒会进入一次“更新周期”，持续约 2 ms，期间时间寄存器的内容未定义。芯片在更新开始前 244 µs 把寄存器 A 的 bit7（UIP）置起来。软件要读到一致的时间，就得在 UIP 为 0 的窗口里把全部字段读完。

Linux 的实现（`drivers/rtc/rtc-mc146818-lib.c:21`）比这还要小心一层：

```c
	for (i = 0; UIP_RECHECK_LOOPS_MS(i) < timeout; i++) {
		seconds = CMOS_READ(RTC_SECONDS);

		if (CMOS_READ(RTC_FREQ_SELECT) & RTC_UIP) { ... continue; }

		/* Revalidate the above readout */
		if (seconds != CMOS_READ(RTC_SECONDS)) { ... continue; }

		if (callback)
			callback(seconds, param);

		if (CMOS_READ(RTC_FREQ_SELECT) & RTC_UIP) { ... continue; }

		if (seconds != CMOS_READ(RTC_SECONDS)) { ... continue; }
		...
		return true;
	}
	return false;
```

**星期寄存器（0x06）没有被读。** `mc146818_get_time_callback()` 的注释明说：“Even though the RTC has RTC_DAY_OF_WEEK, we ignore it, as it is only updated by the RTC when initially set to a non-zero value.” mini-vmm 实现了它（`rtc.c:72`），属于白写。

**BCD 不是可选的。** `mc146818_get_time()` 的转换条件是 `if (!(p.ctrl & RTC_DM_BINARY) || RTC_ALWAYS_BCD)`，而 x86 的 `arch/x86/include/asm/mc146818rtc.h` 里 `#define RTC_ALWAYS_BCD 1`。也就是说**不管寄存器 B 的 DM 位怎么写，x86 上 Linux 一律按 BCD 解释**。mini-vmm 用 `bin2bcd()` 编码（`rtc.c:46`）是对的；如果哪天想改成二进制模式并把寄存器 B 的 bit2 置起来，x86 guest 会读出一个荒唐的时间。

### 4.3 非原子的读为什么也安全

mini-vmm 的实现没有内部时钟，每次读时间寄存器都现取一次 host 的 UTC（`rtc.c:66`）：

```c
    now = time(NULL);
    gmtime_r(&now, &tm);
    switch (reg) {
    case RTC_SECONDS: return bin2bcd(tm.tm_sec);
```

于是一组时间寄存器的读**不是原子的**：秒可能取自 10:09:59，分可能取自 10:10:00，拼出来就是 10:10:59，比真实时间早了将近一分钟。

救下这一点的正是上一节那套复读协议。任何一次跨越秒边界的读，必然伴随秒字段的变化；`lib.c:74` 最后那次复读秒发现值变了就整轮重来。日期、月份、年份的进位同样只发生在秒进位的时刻，所以也被这一层兜住了。

这不是说“可以不管”，而是说明**一个看起来偷懒的实现之所以能work，往往是因为驱动那边有一套为真硬件设计的防御机制恰好也覆盖了它**。反过来，如果 VMM 把 UIP 位真的做出来（比如每秒置 2 ms），反而要额外保证 UIP 为 0 的窗口里读到的值确实一致——那才需要在 VMM 里做一次快照。mini-vmm 选择让 UIP 恒为 0，等于向 guest 承诺“我永远不在更新中”，这个承诺是它能兑现的。

### 4.5 不模拟 RTC 的代价：实测 8 万次 exit、2 秒

`src/devices/rtc.c` 的文件头注释给出了不模拟 RTC 的后果。借这次的追踪能力，把它精确复测一遍：把 `rtc_attach()` 从 `main.c:394` 摘掉重新编译，其余完全不变。

| | 有 RTC 模型 | 没有 RTC 模型 |
|---|---|---|
| 整次启动的 PIO exit 总数 | 30449 | 110187 |
| 0x70 写 / 0x71 读 | 89 / 89 | 40000 / 40000 |
| `Run /init as init process` 的时刻 | 0.748 s | 2.703 s |
| 相关日志 | `setting system clock to 2026-09-12T10:09:02 UTC` | `Unable to read current time from RTC`、`rtc_cmos rtc_cmos: broken or not accessible` |

八万次多出来的 exit，来自两次各 1 秒的超时。`mc146818_avoid_UIP()` 的循环上界是 `UIP_RECHECK_LOOPS_MS(i) < timeout`，`UIP_RECHECK_DELAY_MS` = 10，`timeout` = 1000，所以最多转 10000 圈；每圈两次 `CMOS_READ`（秒和寄存器 A），每次 `CMOS_READ` 是一次写 0x70 加一次读 0x71。10000 × 2 × 2 = 40000 次端口访问，也就是 20000 次写 0x70 加 20000 次读 0x71。两个调用者各超时一次——`mach_get_cmos_time()`（`arch/x86/kernel/rtc.c:70`）和 `cmos_do_probe()` 里的 `mc146818_does_rtc_work()`——正好凑出 40000 / 40000。每圈还有一次 `udelay(100)`，10000 圈就是 1 秒，两次就是 2 秒，和实测的 2.703 − 0.748 = 1.955 秒吻合。

死循环的原因只有一句话：未注册端口读回 0xFF，寄存器 A 的 bit7（UIP）恒为 1，`lib.c:43` 的判断永远成立。

这条数据是本卷命题最直白的例子。RTC 在这台虚拟机上不提供任何实际功能——没有闹钟、没有周期中断、guest 里 `/proc/interrupts` 的 IRQ 8 计数是 0——但**不实现它要付出启动慢 2 秒、多 8 万次用户态往返的代价**，仅仅因为驱动为了等一个真硬件才有的 2 ms 窗口写了一个 1 秒的超时循环。

### 4.6 mini-vmm 的实现边界

| 做了 | 为什么 |
|---|---|
| 索引 + 数据两端口，索引取低 7 位 | 基本协议 |
| 时间寄存器现取 host UTC，BCD 编码 | `RTC_ALWAYS_BCD`，见 4.2 |
| 寄存器 A = 0x26，UIP 恒 0 | 让 `mc146818_avoid_UIP()` 一次通过 |
| 寄存器 B = 0x02（24 小时制） | `rtc-cmos.c:1067` 的硬性检查 |
| 寄存器 C 读回 0 | 没有挂起的中断 |
| 寄存器 D bit7 = 1 | 电池有效，CMOS 内容可信 |
| 世纪寄存器 0x32 与 FADT 一致 | 见 4.2 |
| 128 字节 CMOS RAM 可读写 | NVRAM 接口 |
| 写寄存器 C/D 被忽略 | 只读寄存器 |

| 没做 | 后果 |
|---|---|
| 内部时钟（时间不会自己走） | 无。每次读都现取 host 时间，等价于走得很准 |
| 设置时间（写时间寄存器当普通 CMOS 字节） | `hwclock -w` 写进去读不回来。guest 里没人这么干 |
| UIP 位真的翻转 | 无。恒 0 是一个更强也更容易兑现的承诺 |
| 周期中断 / 闹钟中断（IRQ 8） | `/proc/interrupts` 里 IRQ 8 恒为 0。`rtc-cmos` 仍然注册成功 |
| 星期寄存器被使用 | 无，Linux 不读 |

还有一件值得一提的事：卷六第 3.6 节说过，AP 唤醒时 `smpboot_setup_warm_reset_vector()` 会写 CMOS 索引 `0x0F`（`CMOS_WRITE(0xa, 0xf)`）。那次写落在 `rtc_write()` 的“普通 CMOS 字节”分支上，被老老实实存进 `g_rtc.cmos[0x0f]`。**如果 RTC 模型对未知索引报错或者干脆不存在，`do_boot_cpu()` 的第一步就会踩空。** 这也是为什么 `--smp 1` 和 `--smp 4` 都依赖这个设备。

## 5. i8042：把“不存在”讲清楚比把“存在”讲清楚更难

i8042 是本卷里唯一一个 mini-vmm 需要同时表达“有”和“没有”的设备：KBD 口要装成一个正常工作的 AT 键盘，AUX 口（PS/2 鼠标）要让驱动干脆利落地判定不存在。后者花的力气比前者多。

### 5.1 两个端口、三个寄存器

| 端口 | 读 | 写 |
|---|---|---|
| 0x60 | 输出缓冲（控制器应答或设备数据） | 命令参数，或转发给键盘设备的字节 |
| 0x64 | 状态寄存器 | 控制器命令 |

状态寄存器的位：

| 位 | 名字 | 含义 |
|---|---|---|
| 0 | OBF | 输出缓冲满，主机可以读 0x60 |
| 1 | IBF | 输入缓冲满，主机**不能**再写 |
| 2 | SYSFLAG | 自检通过 |
| 3 | CMDDAT | 上一次写的是 0x64（命令）而不是 0x60（数据） |
| 4 | KEYLOCK | 1 表示键盘没被锁 |
| 5 | AUXDATA | 输出缓冲里的字节来自 AUX 口 |

驱动的每一次访问都要先过这两道等待（`drivers/input/serio/i8042.c:245`、`:256`）：

```c
static int i8042_wait_read(void)
{
	int i = 0;

	while ((~i8042_read_status() & I8042_STR_OBF) && (i < I8042_CTL_TIMEOUT)) {
		udelay(50);
		i++;
	}
	return -(i == I8042_CTL_TIMEOUT);
}
```

`I8042_CTL_TIMEOUT` 是 10000（`i8042.h:34`），每圈 `udelay(50)`，**一次超时正好 0.5 秒**。这个数字很重要：i8042 的探测路径上有十几条命令，每条命令要等一次写就绪、可能还要等一次读就绪，任何一条没应答都要白等半秒。mini-vmm 的文件头注释原来写的是“约 0.6 秒”，本卷把它订正成 0.5 秒并注明了出处（第 11 节第 4 条）。

mini-vmm 的状态寄存器是**算出来**的，不是存起来的（`src/devices/i8042.c:300`）：

```c
        v = STR_SYSFLAG | STR_KEYLOCK | g_kbc.status_cmd;
        if (g_kbc.count) {
            v |= STR_OBF;
            if (g_kbc.obuf[g_kbc.head].aux)
                v |= STR_AUXDATA;
        }
```

IBF 永远是 0——我们“瞬间”消化掉每一次写，所以输入缓冲从来不满，`i8042_wait_write()` 一圈都不用转。这是虚拟设备相对真硬件的一个纯赚：真 i8042 的一条命令要几十微秒。

### 5.2 控制器探测的 30 次访问

```c

{
```

只有**键盘设备**发出的字节（`from_kbd`）才打中断，控制器自己的应答不打；而且要看 CTR 里的 KBDINT/KBDDIS。

### 5.3 自检命令没有被执行

trace 里没有 0xAA（控制器自检）也没有 0xAB（键盘口测试）。原因在 `i8042.c:56`：

```c
#define I8042_RESET_DEFAULT	I8042_RESET_ON_S2RAM
static enum i8042_controller_reset_mode i8042_reset = I8042_RESET_DEFAULT;
```

`i8042_probe()`（`i8042.c:1185`）只有在 `i8042_reset == I8042_RESET_ALWAYS` 或者正在从 S2RAM 恢复时才调 `i8042_controller_selftest()`。默认两者都不成立，所以自检被跳过。mini-vmm 实现了 `CMD_SELF_TEST` 回 0x55、`CMD_KBD_TEST` 回 0x00（`i8042.c:232`、`:235`），在这套配置下是白写的——但这两条实现起来各只有一行，而且加上 `i8042.reset=always` 内核参数就会用到，留着是合理的。

### 5.4 AUX 判定的两道关

让驱动相信“没有 PS/2 鼠标”有两种做法，难度差别很大。

**笨办法**：对 0xD3 和 0xA9 都不应答。这样 `i8042_wait_read()` 各超时一次，两次 0.5 秒，启动凭空慢 1 秒，而且日志里没有任何解释。

**正确办法**：让两道检查都以“明确的否定答案”失败，一次都不超时。`i8042_check_aux()` 的两道关是这样设计的：

第一关是**内部回环**（`i8042.c:830`）。驱动发 `I8042_CMD_AUX_LOOP`（0xD3）带参数 0x5a，期望控制器把这个字节原样放回输出缓冲**并且置上 AUXDATA**。判据藏在 `__i8042_command()` 里（`i8042.c:337`）：

```c
		if (command == I8042_CMD_AUX_LOOP &&
		    !(i8042_read_status() & I8042_STR_AUXDATA)) {
			dbg("     -- i8042 (auxerr)\n");
			return -1;
		}
```

mini-vmm 把字节放回去了，但**故意不置 AUXDATA**（`src/devices/i8042.c:275`）：

```c
    case CMD_WRITE_AUX_OBUF:
        /* 故意不置 AUXDATA：让驱动判定 AUX 回环失败，见文件头 */
        obuf_push(v, false, false);
        break;
```

于是第 21 步读到的状态是 0x15（OBF 置位、AUXDATA 清零），驱动当场返回 -1，**而且它连 0x60 都没读**——第 22 步之后直接跳到下一条命令。这个细节很关键：那个 0x5a 还留在输出缓冲里。mini-vmm 在每条新的控制器命令开头把缓冲清空（`i8042.c:207`）：

```c
    /* 新命令会冲掉还没被读走的旧应答。否则一次失败的 AUX_LOOP 残留
     * 的字节会被下一条 AUX_TEST 当成自己的应答读走。 */
    g_kbc.count = 0;
```

没有这一句，第 26 步读到的就是 0x5a 而不是 0x01，之后每条命令的应答都错位一格。

第二关是**外部连接测试**（`i8042.c:841`）：

```c
		if (i8042_command(&param, I8042_CMD_AUX_TEST) ||
		    (param && param != 0xfa && param != 0xff))
			return -1;
```

`I8042_CMD_AUX_TEST`（0xA9）返回 0 表示“AUX 口正常”，0x01–0x03 表示时钟线/数据线卡住，0xFF 是通用错误。注意这个判断的形状：**0x00、0xFA、0xFF 都算“有 AUX 口”**，只有 0x01–0x03 这几个值才让驱动放弃。mini-vmm 回 0x01（`src/devices/i8042.c:68` 的 `AUX_TEST_CLK_STUCK`），走的正是唯一那条否定路径。

这一条特别值得记住：**“不存在”不是默认值，而是一个需要精确表达的答案。** 回 0x00 会让驱动认为 AUX 口好好的，接着去 `request_irq(12)`、`i8042_enable_aux_port()`、发 0xA5 测中断，最后在 `wait_for_completion_timeout(..., 250ms)` 那里超时（`i8042.c:911`），既慢又会在 `/proc/interrupts` 里留下一个没人用的 IRQ 12；回 0xFF 同理。

两道关走完，日志是干净的：

```
i8042: PNP: No PS/2 controller found.
i8042: Probing ports directly.
serio: i8042 KBD port at 0x60,0x64 irq 1
```

只有 KBD port，没有 AUX port，也没有任何超时警告。

### 5.5 键盘侧：中断计数是一个可验证的断言

控制器探测完之后，`serio` 总线上注册出 KBD 口，`atkbd` 驱动接上去开始和“键盘设备”对话。trace 的第二段（32 次访问）是一串整齐的命令—应答：

```
0064 R 14 / 0060 W f2    ATKBD_CMD_GETID
0064 R 15 / 0060 R fa    ACK
0064 R 15 / 0060 R ab    ┐ 键盘 ID
0064 R 15 / 0060 R 83    ┘
0064 R 14 / 0060 W f5    ATKBD_CMD_RESET_DIS
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W ed    ATKBD_CMD_SETLEDS
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W 00    参数
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W f3    ATKBD_CMD_SETREP
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W 00    参数
0064 R 15 / 0060 R fa
0064 R 14 / 0060 W f4    ATKBD_CMD_ENABLE
0064 R 15 / 0060 R fa
```

`0xAB 0x83` 就是日志里那句 `input: AT Translated Set 2 keyboard as /devices/platform/i8042/serio0/input/input0` 的来源。

这里每一对 `0064 R 15` / `0060 R fa` **都是中断处理程序**在跑：`i8042_interrupt()` 先读状态再读数据。和控制器命令的轮询不同，键盘设备的应答走的是 `serio` → `libps2` → 等待中断这条路。

于是有了一个干净的、可以当作断言写进测试的数字。上面这一段一共产生 9 个键盘字节（3 + 1 + 1 + 1 + 1 + 1 + 1），而 guest 里：

```
  1:          9   IO-APIC   1-edge      i8042
```

**IRQ 1 的计数正好是 9。** 这同时证明了三件事：每个字节都产生了一个独立的上升沿（`set_irq()` 里先降后升的那段逻辑是对的，`src/devices/i8042.c:139` 的 `obuf_pop()` 里 `set_irq(0)` 后再 `update_irq()`）；控制器自己的应答确实没有打中断（否则计数会远大于 9）；没有多余的中断（否则计数会更大）。

如果不给这些应答打中断会怎样？`ps2_command()` 会等 `atkbd` 的超时（默认 200 ms 一条），启动慢一大截，最后 `atkbd` 报 `keyboard reset failed` 之类的错误。这是 mini-vmm 文件头注释里那句“不打中断的话 atkbd 会等到超时”的具体含义。

### 5.6 复位：i8042 为什么能重启机器

PC/AT 的 i8042 有一根输出引脚接在 CPU 的 RESET 线上，这是历史上从实模式回到实模式的标准手段，也是 `reboot=k` 的由来。两条路都能触发：

- 命令 0xFE（严格说是 0xF0–0xFF，低 4 位为 0 的那几根线被脉冲拉低，bit0 就是 RESET#）；
- 命令 0xD1（写输出端口）后往 0x60 写一个 bit0 为 0 的值。

mini-vmm 两条都接（`src/devices/i8042.c:249` 与 `:268`）：

```c
        if (cmd >= CMD_PULSE_BASE && !(cmd & OUTP_RESET_N))
            return request_reset();
```

```c
    case CMD_WRITE_OUTP:
        g_kbc.outp = v;
        if (!(v & OUTP_RESET_N))
            return request_reset();
```

`request_reset()` 返回 `VMM_ERR_EXIT`，整个 VM 停下来。第 6 节会说明 `reboot=k` 这条命令行参数是怎么走到这里的。

### 5.7 mini-vmm 的实现边界

| 做了 | 谁依赖 |
|---|---|
| 状态寄存器的 OBF/SYSFLAG/CMDDAT/KEYLOCK/AUXDATA | 每一次访问 |
| IBF 恒 0 | `i8042_wait_write()` 立刻通过 |
| CTR 的读写（0x20 / 0x60），且读回来稳定 | `i8042_controller_init()` 的两次比对 |
| AUX_LOOP 回字节但不置 AUXDATA | `__i8042_command()` 的 AUXDATA 检查 |
| AUX_TEST 回 0x01 | `i8042_check_aux()` 的“时钟线卡住”分支 |
| 新命令清空输出缓冲 | 保证应答不错位 |
| 键盘命令一律 ACK，GETID 回 0xAB 0x83 | `atkbd` 探测 |
| 键盘字节打 IRQ 1（边沿），控制器应答不打 | `libps2` 等中断；IRQ 1 计数 = 9 |
| 0xFE 脉冲与 0xD1 写输出端口触发退出 | `reboot=k` |

| 没做 | 后果 |
|---|---|
| 控制器自检 0xAA / 键盘口测试 0xAB 的真实语义 | 默认配置不调用；实现了但走不到 |
| 扫描码：没有任何按键事件 | guest 的控制台收不到键盘输入。串口是唯一输入通道 |
| A20 控制（输出端口 bit1） | 长模式下无意义 |
| AUX 设备 | 按设计不存在 |
| 0xC0（读输入端口）等其余命令 | Linux 不用 |

## 6. 关机与重启：两条完全不同的路

VMM 必须能停下来，而且要能区分“guest 要关机”和“guest 要重启”——前者应该退出，后者在真实 VMM 里应该重新引导。mini-vmm 两条都接到“退出”上，但退出原因是分开报的。

### 6.1 ACPI S5：从 `_S5_` 到两次端口写

卷五第 7 节讲过 DSDT 里那 14 字节 AML 的编码，这里接着往下讲它怎么变成一次 `out`。

`poweroff` 最终走到 `acpi_power_off()`（`drivers/acpi/sleep.c`），它调 `acpi_enter_sleep_state(ACPI_STATE_S5)`，ACPICA 里对应 `acpi_hw_legacy_sleep()`（`drivers/acpi/acpica/hwsleep.c:30`）。`acpi_gbl_sleep_type_a` 的值来自启动时对 `\_S5_` 求值的结果——就是我们 DSDT 里那个 `Package () { 5, 5, 0, 0 }` 的第一个元素。

trace 最后那四行，一一对应源码：

```
acpi-pm1a   0600 W2 8000    清 WAKE_STATUS               hwsleep.c:48
acpi-pm1a   0600 W2 c731    acpi_hw_clear_acpi_status()  hwsleep.c:59
acpi-pm1a   0604 R2 0001    读 PM1A 控制寄存器            hwsleep.c:73
acpi-pm1a   0604 W2 1401    写 #1：只写 SLP_TYP           hwsleep.c:101
acpi-pm1a   0604 W2 3401    写 #2：SLP_TYP + SLP_EN       hwsleep.c:127
```

0xC731 不是随手凑的，它是 `ACPI_BITMASK_ALL_FIXED_STATUS`（`drivers/acpi/acpica/aclocal.h:1006`）：TIMER(0x0001) | BUS_MASTER(0x0010) | GLOBAL_LOCK(0x0020) | POWER_BUTTON(0x0100) | SLEEP_BUTTON(0x0200) | RT_CLOCK(0x0400) | PCIEXP_WAKE(0x4000) | WAKE(0x8000)。PM1 状态寄存器是“写 1 清零”语义，所以这一次写把所有固定事件的状态位一次清干净。mini-vmm 照这个语义实现（`src/boot/acpi.c:340`）：

```c
    case 0:
        g_pm.sts &= (uint16_t)~v;    /* 写 1 清零 */
        break;
```

0x1401 与 0x3401 拆开的理由写在源码注释里（`hwsleep.c:94`）：

```c
	/*
	 * We split the writes of SLP_TYP and SLP_EN to workaround
	 * poorly implemented hardware.
	 */
```

`0x1401` = SCI_EN(bit0) | SLP_TYP=5(bit12:10)，`0x3401` 再或上 SLP_EN(bit13)。**只有带 SLP_EN 的第二次写才是真正的“睡下去”**。mini-vmm 的判断因此必须同时看两个字段（`src/boot/acpi.c:346`）：

```c
    case 4:
        if ((v & PM1_CNT_SLP_EN) && PM1_CNT_SLP_TYP(v) == S5_SLP_TYP) {
            vmm_info("guest requested poweroff via ACPI S5");
            vm->exit_code = 0;
            return VMM_ERR_EXIT;
        }
        g_pm.cnt = v & (uint16_t)~PM1_CNT_SLP_EN;
```

只看 SLP_TYP 的话，第一次写（0x1401）就会让 VM 退出——**早了一步**。这一步之差在真机上无所谓（反正马上就要关），但在 VMM 里意味着你把一次“准备”当成了“执行”，如果将来要支持 S3 挂起就会出错。

读回值里那个 SCI_EN（bit0）也值得一提。mini-vmm 在 `pm_read()` 里无条件把它或上去（`acpi.c:318`）：

```c
    uint16_t cnt = g_pm.cnt | PM1_CNT_SCI_EN;   /* 永远处于 ACPI 模式 */
```

真机上这一位由固件在 `acpi_enable()` 之后置起来，表示“已经从 legacy 模式切到 ACPI 模式”。我们没有 SMI、也没有 legacy 模式，所以直接承诺“永远在 ACPI 模式”。ACPICA 的 `acpi_enable()` 会读这一位来判断是否需要发 ACPI_ENABLE 命令；返回 0 的话它会去写 SMI_CMD 端口然后轮询这一位，等不到就报 `Hardware did not enter ACPI mode`。

### 6.2 启动期的 PM1a 访问

除了关机，PM1a 在启动期还有 27 次访问，都出现在 ACPI 子系统初始化阶段：

```
0602 R2 0000 / 0602 W2 0000   × 5        acpi_ev_fixed_event_initialize()
0600 W2 0020                             清 GBL_STS
0602 R2 0000 / 0602 W2 0020              使能 GBL_EN
0602 R2 0020
...
0600 W2 0400 / 0602 R / 0602 W 0420      RT_CLOCK 事件的开关
0600 W2 0400 / 0602 R / 0602 W 0020      再关掉
```

开头那五对“读 PM1a_EN、写 0”来自 ACPICA 逐个禁用五个固定事件（timer、global lock、power button、sleep button、RTC）。每个都是一次读—改—写，因为 `acpi_write_bit_register()` 要保留其他位。这一段对 VMM 的唯一要求是**使能寄存器要能存住值**——mini-vmm 的 `g_pm.en` 就是为此存在的。如果读回来永远是 0，ACPICA 的位操作会反复写同样的值，行为上不会立刻出错，但 `acpi_enable_event()` 的返回值校验会失败。

### 6.3 `reboot=k`：重启走 i8042

mini-vmm 的默认命令行里有 `reboot=k`。这个参数在 `arch/x86/kernel/reboot.c:151` 被解析成 `reboot_type = BOOT_KBD`，跳过 ACPI 复位寄存器那条路。

实测一次 `reboot -f`，trace 的最后两行是：

```
i8042-cmd   0064 R1 14
i8042-cmd   0064 W1 fe
```

对应 `native_machine_emergency_restart()` 的 `BOOT_KBD` 分支（`reboot.c:660`）：

```c
		case BOOT_KBD:
			mach_reboot_fixups(); /* For board specific fixups */

			for (i = 0; i < 10; i++) {
				kb_wait();
				udelay(50);
				outb(0xfe, 0x64); /* Pulse reset low */
				udelay(50);
			}
```

`kb_wait()` 读状态等 IBF 清零，就是那次 `0064 R 14`；然后 `outb(0xfe, 0x64)` 脉冲复位线。循环本来要转 10 次，但 mini-vmm 在第一次就退出了，所以 trace 里只有一对。VMM 侧的输出是：

```
[    7.434950] reboot: Restarting system
[    7.435950] reboot: machine restart
[INFO] guest requested reset via i8042
[INFO] --- left guest (ok) ---
```

**为什么要指定 `reboot=k` 而不用默认值？** 默认的 `reboot_type` 在 x86 上是 `BOOT_ACPI`（经 DMI 检查可能被改），它会先调 `acpi_reboot()` 去写 FADT 里的 RESET_REG。mini-vmm 的 FADT 不提供 RESET_REG（`ACPI_FADT_RESET_REG_SUP` 标志没置），`acpi_reboot()` 会直接返回，然后 `reboot_type` 落到 `BOOT_KBD`——结果一样，只是多绕一圈。写死 `reboot=k` 让这条路径变得确定，也让“VMM 收到 0xFE”成为一个可以写进测试的断言。

`reboot.c:654` 那个 `for (;;)` 循环还有一个副作用值得知道：如果 VMM 不理会 0xFE，内核会依次尝试 EFI、BIOS（`machine_real_restart()`，回实模式跳 `0xFFFF:0x0000`）、0xCF9 端口……全部失败之后回到 `BOOT_KBD` 无限重来。症状是 guest 卡在 `reboot: Restarting system` 不动，CPU 占满——**看起来像死循环，其实是在一条条试**。

### 6.4 mini-vmm 的两条退出路径

| 触发 | 端口 | 判据 | 日志 | `exit_code` |
|---|---|---|---|---|
| ACPI S5 关机 | 0x604 写 | SLP_EN 且 SLP_TYP == 5 | `guest requested poweroff via ACPI S5` | 0 |
| i8042 复位 | 0x64 写 0xF0–0xFF 且 bit0 = 0；或 0xD1 + 0x60 写 bit0 = 0 | `src/devices/i8042.c:249`、`:269` | `guest requested reset via i8042` | 0 |
| 测试用退出口 | 0xF4 写 | 写入值即退出码 | `guest requested exit, code=N` | 写入值 |

三条都通过设备回调返回 `VMM_ERR_EXIT` 实现，由 `handle_io()` 一路传回 `vcpu_run_loop()`。这也是第 1.2 节那个“先记录 trace 再判返回值”的顺序之所以重要的原因——这三次写恰恰是最后一次写。

真正的 VMM 应该把复位和关机区分对待：复位要把 vCPU 状态、设备状态、内存内容恢复到初始状态再重新进入 guest，而不是退出进程。mini-vmm 选择退出，因为“重新引导”在直接内核引导的模型下等价于把 VMM 再跑一遍。

## 7. 浮空总线：“读回 0xFF”是一条契约，不是一个默认值

一次启动里有 257 次 PIO 落在 mini-vmm 没有注册任何设备的端口上。`handle_io()` 对它们的处理只有三行（`src/vm.c:249`）：

```c
    if (!dev) {
        /* 未注册端口：写丢弃，读返回全 1（真机上空闲总线的行为）。
         * 不能直接报错退出——Linux 内核启动时会盲探一堆遗留端口。 */
        if (run->io.direction == KVM_EXIT_IO_IN)
            memset(data, 0xFF, (size_t)run->io.size * run->io.count);
```

这一节要说明的是：这三行不是“兜底”，它们和任何一个设备模型一样，是在向 guest 表达一个明确的语义。

### 7.1 257 次访问分别是谁

有了 `--trace-pio` 记录的 RIP，把它们逐条对到符号上（`nm -n vmlinux` 加一次二分查找）：

| 端口 | 次数 | 调用者 | 干什么 |
|---|---|---|---|
| 0xcf8 | 78 W4 | `read_pci_config+0x36` | `early_quirks()` 扫总线 0 |
| 0xcfc | 78 R4 | `read_pci_config+0x3c` | 同上，读回 0xFFFFFFFF |
| 0xcf8 | 33 W4 | `read_pci_config_16+0x34` | 同上，读 vendor/class |
| 0xcfe / 0xcfc | 32 + 1 R2 | `read_pci_config_16+0x3e` | 同上 |
| 0xcf8 / 0xcfa / 0xcfb | 6 + 1 + 2 | `pci_direct_probe` | 配置机制 1 与 2 的探测 |
| 0x80 | 7 W1 | `native_io_delay+0x1e` | `outb_p` 的延时写 |
| 0x2f9 / 0x3e9 / 0x2e9 | 各 6 | `io_serial_in/out` | ttyS1/2/3 的 autoconfig（第 2.8 节） |
| 0x87 | 1 R1 | `i8237A_init_ops+0x9` | 判断有没有 8237 DMA 控制器 |

这张表在本机和 soc63 上**逐条相同**——257 次访问、每个端口的次数、每条的调用者符号全都对得上。设备探测不看 host，这里是又一个证据。

RIP 反查这件事本身值得推荐：**当你看到一次不认识的端口访问时，"谁在访问" 通常比 "访问了什么" 更有用**，而这个信息在 VMM 这一侧是现成的，只差一次 `KVM_GET_REGS`。

### 7.2 0x80：`outb_p` 的延时写

guest 的 `.config` 里 `CONFIG_IO_DELAY_0X80=y`，于是 `native_io_delay()`（`arch/x86/kernel/io_delay.c:38`）编译成：

```c
	case IO_DELAY_TYPE_0X80:
		asm volatile ("outb %al, $0x80");
```

写什么值取决于当时 AL 里是什么（我们这次录到的七次都是 0x00）。历史上这个端口是 BIOS 的 POST 码显示口，往它写一个字节的耗时正好接近一个 ISA 总线周期，于是被拿来当作“两次 I/O 之间的延时”。

这 7 次的 RIP 全部落在 `native_io_delay()` 自己身上，所以它只告诉我们“这是一次 `outb_p`/`inb_p` 的延时”，并不能告诉我们是**哪个** `_p` 调用产生的——要知道那个得去栈上取返回地址，`--trace-pio` 目前不做这件事。能确定的是数量：一次启动只有 7 次，全部集中在两处，一处在 `ACPI: Core revision` 与 `APIC: Switch to symmetric I/O mode setup` 之间（3 次），另一处在 `Mountpoint-cache hash table entries` 与 `smpboot: CPU0` 之间（4 次）。

这里顺带有一个和第 3 节呼应的观察：真正频繁使用 `_p` 系列的那些老设备——PIC 的 0x20/0x21/0xa0/0xa1——一次都没出现在 trace 里，因为它们在内核态被接走了；而 0x80 这个纯粹的副产品却漏了出来。**把设备搬进内核能省掉寄存器访问本身，省不掉它顺带产生的延时写。**

对 VMM 的要求只有一条：0x80 的写必须被安静地丢弃。这类盲写在启动早期就会出现，如果 VMM 对未知端口的写报错退出，虚拟机会死在一个和任何设备都无关的地方。

### 7.3 0x87：0xFF 与 0x00 的区别在这里变成决定性的

只有一次访问的 0x87，是本节最有说服力的例子。`arch/x86/kernel/i8237.c` 的 `i8237A_init_ops()`：

```c
	/*
	 * From SKL PCH onwards, the legacy DMA device is removed in which the
	 * I/O ports (81h-83h, 87h, 89h-8Bh, 8Fh) related to it are removed
	 * as well. All removed ports must return 0xff for a inb() request.
	 * ...
	 */
	if (dma_inb(DMA_PAGE_0) == 0xFF)
		return -ENODEV;
```

`DMA_PAGE_0` 就是 0x87。内核用一次读来判断这台机器上还有没有 8237 DMA 控制器，判据**写死**是 0xFF。读回 0xFF：驱动认为没有，`return -ENODEV`，`i8237_syscore_ops` 不注册，从此系统里不存在 8237。读回 0x00（或者任何别的值）：驱动认为有，注册 syscore ops，之后每次从挂起恢复都会去写 0x0D/0xDA/0x0A 这一串 DMA 寄存器——在 mini-vmm 上这些写会落到别的地方或者被丢弃，行为未定义。

注释里那句 “All removed ports must return 0xff for a inb() request” 说得再清楚不过：**这是硬件规范对“不存在”的规定，而 VMM 的未注册端口处理就是在实现这条规定。** 0xFF 不是随便选的默认值，它是浮空总线（floating bus）——没有设备驱动数据线时，上拉电阻把总线拉到全 1——在软件侧的契约化。

同一个道理在第 2.8 节的 ttyS1/2/3 上也成立，只是那里 0xFF 和 0x00 都会导致探测失败，区别只在失败的位置。0x87 这个例子里，两者会得出**相反**的结论。

### 7.4 PCI：一次完整的“这台机器没有 PCI”

0xcf8/0xcfc 那 220 多次访问分两批。

**第一批是 `early_quirks()`**，在 `setup_arch()` 里就跑了。它用 `read_pci_config()` / `read_pci_config_16()` 直接操作配置机制 1 的两个端口，扫总线 0 上的设备，找需要提前处理的芯片组 quirk。全部读回 0xFFFFFFFF，什么都没找到。这一批发生在 PCI 子系统初始化**之前**，所以它不受“系统有没有 PCI”的影响——写 VMM 时要知道，**即使你完全不打算支持 PCI，这些访问照样会来**。

**第二批是 `pci_direct_probe()`**（`arch/x86/pci/direct.c`），它依次试两种配置机制：

```c
static int __init pci_check_type1(void)
{
	...
	outb(0x01, 0xCFB);
	tmp = inl(0xCF8);
	outl(0x80000000, 0xCF8);
	if (inl(0xCF8) == 0x80000000 && pci_sanity_check(&pci_direct_conf1)) {
		works = 1;
	}
	outl(tmp, 0xCF8);
```

机制 1 的判据是：**往 0xCF8 写 0x80000000，再读回来必须一模一样**。这是个很聪明的存在性测试——它要求 0xCF8 是一个真正的可读写锁存器。mini-vmm 不注册这个端口，读回 0xFFFFFFFF，判定失败。

```c
static int __init pci_check_type2(void)
{
	...
	outb(0x00, 0xCFB);
	outb(0x00, 0xCF8);
	outb(0x00, 0xCFA);
	if (inb(0xCF8) == 0x00 && inb(0xCFA) == 0x00 &&
	    pci_sanity_check(&pci_direct_conf2)) {
```

机制 2 的判据反过来：写 0 再读回必须是 0。**注意这里 0xFF 和 0x00 的角色互换了**——如果我们的未注册端口读回 0x00，这个测试的前半截就会通过，接着去跑 `pci_sanity_check()`，那里会读若干个设备的 class/vendor 并要求出现一个 host bridge；全 0 也过不了，但探测会往前多走一大截。

两种机制都失败，于是：

```
[    0.450145] PCI: Fatal: No config space access function found
[    0.501305] PCI: System does not support PCI
```

“Fatal” 这个词吓人，但它只是说 PCI 子系统不启用，启动继续。对 mini-vmm 来说这正是想要的结果——下一卷引入 VirtIO 时会先用 MMIO 传输层，真正需要 PCI 时再来实现这两个端口。

### 7.5 未注册端口的四种可选行为

| 做法 | 后果 |
|---|---|
| 读回 0xFF，写丢弃（mini-vmm） | 与真硬件的浮空总线一致。`i8237A_init_ops()`、autoconfig、PCI 探测全部得出正确结论 |
| 读回 0x00，写丢弃 | 8237 被误认为存在；PCI 机制 2 的探测多走几步。其余大多数场合看不出区别 |
| 报错并退出 | 启动早期就死在一次盲探上，而且现场和任何设备都对不上号 |
| 打印警告但继续 | 可用，但一次启动 257 行噪音。mini-vmm 把它放在 debug 级别（`vmm_dbg`），默认不显示 |

mini-vmm 选第一种，并且在 MMIO 侧用了同样的约定（`src/vm.c:298`，未注册 MMIO 读返回全 1）。

## 8. 设备模型的并发：两把锁，各管一边

设备模拟的并发问题有两个来源，性质完全不同。

**第一个来源是多个 vCPU 线程同时陷出。** `--smp 4` 时四个线程可能同时落在 `handle_io()` 里。卷六第 6.5 节讲过，mini-vmm 的做法是一把大锁（`src/vm.c:364`）：

```c
    case KVM_EXIT_IO: {
        ...
        pthread_mutex_lock(&vcpu->vm->io_lock);
        r = handle_io(vcpu);
        pthread_mutex_unlock(&vcpu->vm->io_lock);
```

于是**所有设备回调都在这把锁下串行执行**。`src/devices/i8042.c` 里那个 `g_kbc` 全局结构体、`src/boot/acpi.c` 里的 `g_pm`、`src/devices/rtc.c` 里的 `g_rtc`，都没有自己的锁，靠的就是这个前提。这是 QEMU 的 BQL 同一个思路：代价是设备访问不能并行，收益是设备模型可以当单线程代码写。

在这一卷的语境下这个选择尤其划算：第 1.3 节的表说明 98% 的 PIO 是串口，而串口在任一时刻只可能被一个 CPU 用来输出（printk 有自己的锁），并行度本来就接近 1。

**第二个来源是 host 侧的异步输入。** 串口的接收方向不由 guest 驱动——是 host 的 stdin 有数据时才往里塞。`src/console.c:34` 起有一个独立线程干这件事：

```c
static void *console_thread(void *arg)
{
    ...
    for (;;) {
        n = read(STDIN_FILENO, &c, 1);
        ...
        serial8250_push_rx(g_serial, c);
```

这个线程**不持有 `io_lock`**，它和 vCPU 线程是真正并发的。所以 `struct serial8250` 必须有自己的锁（`src/devices/serial8250.c:156`、`:294`），而且 `serial8250_push_rx()` 里除了改 FIFO 还要调 `update_irq()`——因为新字节到达可能需要拉起 IRQ 4。

```c
bool serial8250_push_rx(struct serial8250 *s, uint8_t c)
{
    ...
    pthread_mutex_lock(&s->lock);
    next = (s->rx_head + 1) % SERIAL_RX_BUF;
    if (next != s->rx_tail) {
        s->rx_buf[s->rx_head] = c;
        s->rx_head = next;
        ok = true;
    }
    update_irq(s);
    pthread_mutex_unlock(&s->lock);
    return ok;
}
```

**加锁顺序。** 串口的路径上可能出现 `io_lock` → `s->lock`（vCPU 读寄存器）和单独的 `s->lock`（console 线程），不会出现 `s->lock` → `io_lock`，所以没有环。但要注意 `update_irq()` 会在持有 `s->lock` 的情况下调 `irqchip_set_irq()` → `ioctl(KVM_IRQ_LINE)`——一次系统调用在锁里。这是可以接受的（KVM 的这条路径不会阻塞在 `vcpu->mutex` 上），但如果将来把它换成某种会阻塞的通知机制，就得重新审视。

**一个更一般的结论。** 本卷讲的五个设备里，只有串口有“设备主动产生事件”的方向（收字符）；RTC、i8042、PM1a、PIT 都是纯粹的“guest 问、设备答”。凡是只有后一种方向的设备，都可以完全靠 `io_lock` 兜住，不需要自己的锁。**判断一个设备模型要不要自己的锁，只要看它有没有一条不由 vCPU 线程发起的路径。** i8042 的键盘应答看起来像是设备主动发的，但它总是由一次 `out` 触发的，所以不算。

## 9. 一致性检查清单

卷五第 9 节给了固件表侧的清单，卷六第 10 节给了 CPU 侧的。这一节是设备侧的。每一条都标注了违反时的现象，因为这类 bug 的共同特点仍然是**现象离原因很远**。

### 9.1 端口归属

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 0x40–0x43、0x61 必须留给 KVM 的内核态 PIT | `KVM_CREATE_PIT2` 已经注册了它们 | 用户态注册的设备收不到任何访问，而且没有任何提示 |
| `KVM_CREATE_PIT2` 必须带 `KVM_PIT_SPEAKER_DUMMY` | 0x61 是 PIT 通道 2 的 GATE 与 OUT | TSC 校准失败，jiffies 不走；日志是 `Unable to calibrate against PIT` |
| `KVM_CREATE_PIT2` 要在 `KVM_CREATE_IRQCHIP` 之后 | PIT 的中断要挂 GSI 0 | ioctl 返回 `EFAULT`/`ENXIO` |
| 0x64 归 VMM，不受 KVM speaker 设备注册长度 4 的影响 | `speaker_ioport_*()` 对非 0x61 返回 `-EOPNOTSUPP`，总线会继续往下找 | 无——但如果误以为被吞掉而不去注册 i8042，键盘控制器探测会超时 |
| i8042 要按 0x60 和 0x64 两个单字节设备注册 | 中间隔着 0x61 | 整段注册时 0x61 的访问静默丢失 |
| 未注册端口：读回 0xFF、写丢弃 | 浮空总线的软件契约 | 读回 0x00 会让 `i8237A_init_ops()` 误判有 8237；报错退出会死在盲探上 |
| 未注册 MMIO 用同样的约定 | 同上 | 同上 |

### 9.2 16550A

| 约束 | 谁依赖 | 违反的现象 |
|---|---|---|
| IER 低 4 位写什么读什么 | `autoconfig()` 存在性测试（`8250_port.c:1203`） | 端口被判为不存在，`console=ttyS0` 完全没有输出 |
| FCR 的 bit0 要反映到 IIR 的 bit7:6 | `autoconfig()` 类型判定（`8250_port.c:1260`） | 被认成 8250/16450，FIFO 不启用，性能下降 |
| LSR 的 THRE 与 TEMT 恒置位 | earlyprintk、`wait_for_xmitr()` | 输出卡死；`serial8250_do_startup()` 的 LSR 安全检查看到 0xFF 会直接 `-ENODEV` |
| LSR 的 DR 跟随接收 FIFO | tty 收字符 | 输入收不到 |
| 打开 IER.THRI 时若 THR 空要补一次 THRI | THRE bug 测试（`8250_port.c:2347`）、`serial8250_start_tx()` | 被扣 `UART_BUG_THRE`，改成每 25 ms 定时器轮询 |
| 读 IIR 拿到 THRI 即视为应答 | 16550 语义 | 中断一直挂着，中断风暴 |
| 中断要经 MCR.OUT2 门控 | PC/AT 板级接线（`8250_port.c:2386`） | 探测期间出现不该有的中断；真正的 bug 要到别处才暴露 |
| 中断线只在电平变化时才调 `KVM_IRQ_LINE` | IOAPIC 上 ISA IRQ 是边沿触发 | 第二个字节起中断丢失 |
| MSR 常态要有 DCD/DSR/CTS | tty 的载波检测 | 终端被挂断，进程收到 SIGHUP |
| DLAB 必须复用偏移 0/1 | 每一段代码都在用 | 分频器写进 THR，输出乱码 |
| LCR 原样存原样读，不做合法性检查 | Linux 会写 0x13（EPAR 无条件置位）、0xBF | 设备模型比真硬件挑剔，探测会在莫名其妙的地方失败 |
| `LCR == 0xBF` 时偏移 2 是 EFR，不实现就要显式挡掉 | 不挡的话这些访问会落到 IIR/FCR 上 | 当前配置下恰好无害；开了 `CONFIG_SERIAL_8250_16550A_VARIANTS` 之后探测走进未验证的分支 |

### 9.3 CMOS RTC

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 寄存器 A 的 UIP（bit7）必须能读到 0 | `mc146818_avoid_UIP()` 的循环条件 | 两次 1 秒超时、8 万次 PIO exit、`Unable to read current time from RTC` |
| 寄存器 B 的 bit1（24 小时制）必须为 1 | `rtc-cmos.c:1067` 的硬性检查 | `only 24-hr supported`，`rtc_cmos` 探测失败 |
| 时间寄存器必须是 BCD | x86 的 `RTC_ALWAYS_BCD` 写死 | 时间荒唐，`setting system clock to` 显示一个乱七八糟的日期 |
| 世纪寄存器的索引要与 FADT 里填的一致 | `lib.c:133` 用 `acpi_gbl_FADT.century` 当索引 | 年份落到错误的世纪；FADT 填 0 时短期看不出来，2070 年后才错 |
| 索引口写入要屏蔽 bit7 | bit7 是 NMI 屏蔽位 | 选到 0x80 以上的寄存器，读回垃圾 |
| CMOS RAM 的 128 字节要真的能存 | `rtc-cmos` 导出 114 字节 NVRAM | NVRAM 读写前后不一致 |
| 索引 0x0F 的写必须被接受 | AP 唤醒的 warm reset vector（卷六 3.6 节） | `do_boot_cpu()` 第一步失败 |
| 寄存器 C 读回 0 | 没有挂起中断 | 驱动以为有未处理的 RTC 中断 |

### 9.4 i8042

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 状态寄存器的 OBF 要准确反映输出缓冲 | `i8042_wait_read()` | 每条命令白等 0.5 秒 |
| IBF 恒 0（或及时清零） | `i8042_wait_write()` | 同上 |
| CTR 读回来必须稳定 | `i8042_controller_init()` 连读两次比对 | `Unable to get stable CTR read`，整个 i8042 被放弃 |
| AUX_LOOP（0xD3）回字节但**不**置 AUXDATA | `__i8042_command()` 的 AUXDATA 检查 | 置了的话驱动认为有 AUX 口，接着去测 IRQ 12，250 ms 超时 |
| AUX_TEST（0xA9）回 0x01–0x03 | 只有这几个值表示“没有 AUX” | 回 0x00/0xFA/0xFF 都表示“有 AUX 口” |
| 新命令要清掉未读的旧应答 | 失败的 AUX_LOOP 会留下一个字节 | 之后每条命令的应答错位一格 |
| 键盘设备的应答要打 IRQ 1，控制器应答不打 | `libps2` 等中断，控制器命令是轮询 | 前者不打会让 `atkbd` 逐条超时；后者打了会多出莫名的中断 |
| IRQ 1 要受 CTR 的 KBDINT/KBDDIS 门控 | 探测期间驱动会关掉键盘口 | 探测阶段出现不该有的中断 |
| 0xFE 脉冲与 0xD1+bit0=0 都要能触发复位 | `reboot=k` 走前者，某些代码走后者 | guest 卡在 `reboot: Restarting system`，CPU 占满地逐条试其他复位方式 |

### 9.5 ACPI PM1a

| 约束 | 为什么 | 违反的现象 |
|---|---|---|
| 只有 SLP_EN 与 SLP_TYP **同时**满足才算关机 | ACPICA 分两次写（`hwsleep.c:94` 的注释） | 只看 SLP_TYP 会在第一次写时就退出，早了一步 |
| SLP_TYP 的值要与 DSDT 里 `_S5_` 的第一个元素一致 | 那个值就是 ACPICA 要写的 | 写进来的 SLP_TYP 对不上，VMM 不退出，guest 停在 `Preparing to enter system sleep state S5` |
| PM1a_CNT 读回时 SCI_EN 必须为 1 | `acpi_enable()` 用它判断是否已在 ACPI 模式 | `Hardware did not enter ACPI mode`，之后 `_S5_` 求值也会出问题 |
| PM1a_STS 是“写 1 清零” | ACPICA 用 0xC731 一次清干净 | 状态位清不掉，`acpi_hw_clear_acpi_status()` 之后仍然有挂起事件 |
| PM1a_EN 要能存住值 | ACPICA 的位操作是读—改—写 | `acpi_enable_event()` 的回读校验失败 |
| 端口块地址与 FADT 里的 `pm1a_evt_blk` / `pm1a_cnt_blk` 一致 | 卷五的老规矩 | ACPICA 写到没人管的端口，关机无效 |

### 9.6 通用

| 约束 | 为什么 |
|---|---|
| 设备回调要能承受任意宽度的访问 | guest 可能按字节、字、双字访问同一块寄存器；mini-vmm 的 PM1a 就是当成 6 字节的小端寄存器文件处理的 |
| 只读寄存器的写要被忽略而不是报错 | 驱动会把读到的值原样写回去，包括从不存在端口读到的 0xFF |
| 设备状态的并发保护：看有没有非 vCPU 线程发起的路径 | 只有串口的接收方向需要自己的锁，其余靠 `io_lock` |
| 退出用的写要先记进 trace 再返回 | 否则最关键的那一行丢了 |

## 10. 验证与排障

### 10.1 三步法

设备类问题的排查顺序和中断、SMP 都不一样：这里**不需要猜**，因为 guest 的每一次寄存器访问都可以被完整记录下来。

**第一步：录一份 trace。**

```sh
./build/vmm --mode linux --mem 512M --trace-pio /tmp/pio.txt \
    --initrd build/initramfs.cpio.gz $VMLINUX
```

**第二步：看全貌。**

```sh
./tools/pio_decode.py /tmp/pio.txt --summary
```

三个问题可以立刻回答：这个端口有没有被访问过（没有 → 要么 guest 不关心它，要么它被 KVM 内核接走了）；访问了多少次（次数异常大通常意味着某个轮询循环在超时）；哪个设备占了大头。

**第三步：定位到时间点。** trace 只有时间戳和行号，而人能读懂的是内核日志。把两者对上：

```sh
./tools/pio_decode.py /tmp/pio.txt --console | less
```

输出的每一行是 `<起始行号>-<结束行号>\t<那条日志的文本>`。找到感兴趣的日志，就知道它前后的 trace 行号区间；反过来，看到一段奇怪的访问，也能查出它发生在哪条日志附近。然后：

```sh
./tools/pio_decode.py /tmp/pio.txt --from 25700 --to 25800
./tools/pio_decode.py /tmp/pio.txt --dev unhandled --syms $VMLINUX
```

`--syms` 那条是找“谁在访问一个我没实现的端口”的标准手段。第 7.1 节整张表就是这么来的。

### 10.2 症状到原因

| 症状 | 先看什么 | 常见原因 |
|---|---|---|
| 完全没有串口输出 | trace 里有没有 0x3f8 | IER 存在性测试没过（IER 低 4 位不可读写）；或者端口号/`console=` 参数对不上 |
| 有 earlyprintk 输出，`console [ttyS0] enabled` 之后就停了 | `autoconfig()` 那 20 来次访问 | IIR 的 FIFO 位没跟着 FCR 走，端口被判成 `PORT_UNKNOWN` |
| 串口输出很慢、字符间隔均匀 | `/proc/interrupts` 的 IRQ 4 | 被扣了 `UART_BUG_THRE`，改成定时器轮询；检查“打开 THRI 时补一次中断” |
| 串口输出重复一段 | `EINTR`/`EAGAIN` 之后有没有重新分发 exit | 卷六 10.4 节那条：这两条路径不保证写 `exit_reason` |
| 启动卡住约 0.5 秒的整数倍 | trace 里最后一次访问的端口 | i8042 的某条命令没应答，`i8042_wait_read()` 超时 |
| 启动慢约 2 秒，日志有 `Unable to read current time from RTC` | 0x70/0x71 的访问次数 | RTC 没实现，或者寄存器 A 的 UIP 恒为 1 |
| `rtc_cmos: broken or not accessible` | 同上 | 同上；或者 `mc146818_does_rtc_work()` 超时 |
| `rtc_cmos: only 24-hr supported` | 寄存器 B 的值 | bit1 没置 |
| 时间对但年份差 100 年 | FADT 的 `century` 字段与 RTC 模型认的索引 | 两边对不上 |
| `Unable to calibrate against PIT`，jiffies 不走 | trace 里有没有 0x61 | 忘了 `KVM_PIT_SPEAKER_DUMMY`；也可能只是 host 负载大（3.5 节） |
| `i8042: Can't read CTR` | trace 里 0x64 写 0x20 之后有没有应答 | CTR 读命令没实现 |
| 多出一个没人用的 IRQ 12 | AUX 两道检查的返回值 | AUX_LOOP 置了 AUXDATA，或 AUX_TEST 回了 0x00 |
| `poweroff` 之后 guest 停在 `Preparing to enter system sleep state S5` | trace 里 0x604 的最后两次写 | 只看 SLP_TYP 没看 SLP_EN；或者 DSDT 的 `_S5_` 值与 VMM 的判据不一致 |
| `reboot` 之后 CPU 占满且不退出 | trace 的最后几行 | 0xFE 没被处理，内核在逐条试 EFI/BIOS/0xCF9 |
| guest 认为有一个不存在的设备 | 那个设备的探测端口读回了什么 | 未注册端口读回了 0x00 而不是 0xFF |

### 10.3 `tests/step7.sh`

本卷新增的验收脚本，三条自动用例：

**7.1 四个设备都被正确探测，且一次超时都没有。** 断言分两类：一类是“该出现的日志”（`ttyS0 ... is a 16550A`、`serio: i8042 KBD port at 0x60,0x64 irq 1`、`rtc_cmos ... registered as rtc0`、`alarms up to one day, y3k, 114 bytes nvram`），另一类是“不该出现的日志”（`Can't read CTR`、`broken or not accessible`、`only 24-hr supported`、`LSR safety check engaged`、`Unable to get stable CTR read`）。**第二类比第一类更有价值**——设备探测失败时 Linux 往往还是能启动，只是慢、少了功能，正向断言容易全绿而毛病还在。

还有三条来自 guest 自己的断言：

```sh
'echo SER-$(sed -n "s/^0: uart:\([^ ]*\).*/\1/p" /proc/tty/driver/serial)'
'echo KBDIRQ-$(sed -n "s/^ *1: *\([0-9]*\).*/\1/p" /proc/interrupts)'
'echo RTCIRQ-$(sed -n "s/^ *8: *\([0-9]*\).*/\1/p" /proc/interrupts)'
```

其中 `KBDIRQ-9` 是本卷最喜欢的一条断言：9 正好是 `atkbd` 初始化时键盘设备回复的字节数（GETID 的 3 个加上另外 6 条命令各 1 个 ACK）。它一次同时锁住三件事——每个字节产生一次独立的边沿、控制器应答不打中断、没有多余中断。任何一处写错这个数字就变了。

**7.2 trace 的结构。** 直接对 `--trace-pio` 的输出做静态检查：

```sh
expect_has "PIT-USERSPACE-0"      # 0x40-0x43 与 0x61 一条都不该落到用户态
expect_has "DMA0-R1-ff"           # 0x87 读回 0xFF
expect_has "S5-1401-3401-"        # 0x604 最后两次写：先 SLP_TYP 后 SLP_EN
```

这类断言的好处是它检查的是**机制**而不是**日志措辞**，换内核版本时不容易假失败。

**7.3 退出路径。** `reboot -f` 之后 trace 的最后一行必须是 `i8042-cmd 0064 W1 fe`。这同时验证了 `reboot=k` 这条命令行参数、i8042 的复位命令解码，以及“先记 trace 再判返回值”那个顺序。

### 10.4 两条本卷改过的 flaky 断言

`tests/step2.sh` 里关于 TSC 校准的那条断言，本卷把它从两选一改成三选一，理由见第 3.5 节：三种结局分别对应裸机 KVM、嵌套虚拟化、host 负载大，都不是 VMM 的问题。

更一般的教训是：**写断言之前先问“它失败时能指向 VMM 的哪个缺陷”**。指不出来的，要么放宽，要么换一个能指出来的断言。本卷把 TSC 那条放宽的同时，加了 7.2 的三条 trace 结构断言作为补偿——后者失败时能精确指到某一行代码。

### 10.5 人工验收

`tests/step7.sh -m` 打印三条人工项：用 `pio_decode.py` 逐段读一次启动的寄存器序列；确认串口确实是中断驱动（`/proc/interrupts` 的 IRQ 4 随输出增长）；以及把 `rtc_attach()` 摘掉重编，亲眼看一次 8 万次 exit 的代价。

## 11. 本卷小结与卷八预告

**方法。** 本卷和前几卷最大的不同是先测后读：给 mini-vmm 加一个 `--trace-pio`，把 guest 发出的每一次 PIO 原样录下来，再拿录到的序列去对源码。这件事的成本极低（`src/vm.c` 里不到八十行），收益却贯穿全卷——第 2 节那 22 次访问、第 5 节那 30 次访问、第 7 节那张“谁在访问未注册端口”的表，都不是从手册推演出来的，而是从一次真实启动里抄下来的。**写设备模型时，能录就别猜。**

**命题。** 设备要模拟到什么程度，由驱动的探测逻辑决定。具体到这一卷：

- 让 Linux 认出一颗 16550A，只需要 IER 低 4 位可读写、FCR 的 bit0 能反映到 IIR 的 bit7:6 上。`autoconfig()` 四百行里剩下的都被 `UPF_SKIP_TEST` 和 `CONFIG_SERIAL_8250_16550A_VARIANTS=n` 挡住了。
- 让 Linux 相信没有 PS/2 鼠标，要精确地回两个“否”：AUX_LOOP 回字节但不置 AUXDATA，AUX_TEST 回 0x01。回 0x00 或 0xFF 都表示“有”。
- 让 Linux 相信没有 8237 DMA 控制器，只要端口 0x87 读回 0xFF。读回别的值它就认为有。
- 让 `rtc-cmos` 探测通过，寄存器 B 的 bit1 必须是 1，寄存器 A 的 UIP 必须能读到 0，时间必须是 BCD——这三条任何一条错了，代价是 1 到 2 秒的超时。

**不做也是一种做法。** PIT 是本卷唯一一个正确做法是完全不实现的设备：`KVM_CREATE_PIT2` 加一个 `KVM_PIT_SPEAKER_DUMMY` 标志，0x40–0x43 和 0x61 就全归内核了，用户态一次 exit 都看不到。代价是要知道这件事——不知道的话，会在用户态注册一个永远收不到访问的设备，而且没有任何提示。

**“不存在”比“存在”难表达。** 这是本卷反复出现的一条。设备不存在时驱动的行为不是“什么都不做”，而是“按某条特定路径失败”，而那条路径往往带着超时。第 4.5 节测到的 8 万次 exit、2 秒，第 5.4 节那两道 AUX 检查，第 7.3 节的 0x87，讲的都是同一件事：**未实现的设备要主动给出否定答案，而不是沉默。**

**同一份代码在不同 host 上会走不同的路径。** 第 3.3 节的 TSC 校准是个干净的例子：soc63（裸机 KVM）上快路成功，本机（WSL2 嵌套虚拟化）上快路静默失败改走慢路，host 负载大时慢路也会失败。三种结局都是正常的。这直接说明了为什么断言要按“它失败时能指向什么缺陷”来写，而不是按“我这次看到了什么”来写。

**五条改进，都已经实现：**

1. **`--trace-pio FILE`**（`src/vm.c:178`–`:234`、`src/main.c:261`）。每次陷出到用户态的 PIO 记一行；未注册端口额外取一次 `KVM_GET_REGS` 记下 guest 的 RIP，拿 `nm -n vmlinux` 一查就知道是谁在盲探。记录点放在设备回调**之后**、错误判断**之前**（`src/vm.c:280`），这样触发退出的最后一次写也会留在 trace 里。配套 `tools/pio_decode.py`，提供 `--summary`（端口/设备直方图）、`--console`（把 0x3f8 的写还原成控制台文本并标出行号区间）、`--syms`（RIP 解析成符号）、以及按端口/设备/行号区间切片。本卷的全部实测数据都出自这两个工具。
2. **`tests/step7.sh`**。三条自动用例：设备探测的结论（含 `KBDIRQ-9` 这条能一次锁住三件事的断言）、trace 的结构（PIT 不落用户态、0x87 读回 0xFF、S5 分两次写）、以及 `reboot -f` 的 0xFE 脉冲。人工项给出 `pio_decode.py` 的典型用法和“摘掉 RTC 看代价”的对照实验。
3. **`LCR == 0xBF` 时不再把 EFR 的访问落到 IIR/FCR 上**（`src/devices/serial8250.c:51`、`:170`、`:234`）。原来的行为只是恰好无害（2.9 节），现在是一条明确的语义：这颗芯片没有 EFR，读回 0、写丢弃。四套测试的结果一字不变——当前配置下走不到那条路，这条改动买的是“换一个 guest 配置时不会突然进入未验证分支”。
4. **三处注释订正。** `src/devices/serial8250.c:130` 原来断言“Linux autoconfig 会做回环测试”，实际上 x86 的 `SERIAL_PORT_DFNS` 给 COM1–COM3 带了 `UPF_SKIP_TEST`，这段代码在当前配置下从未执行；改成说明它什么时候才会被用到。`src/devices/i8042.c` 的文件头把“忙等约 0.6 秒”改成准确的 0.5 秒（`I8042_CTL_TIMEOUT` 10000 圈 × `udelay(50)`）并给出出处。`src/devices/rtc.c` 的文件头把“约 4 万次 exit、1.4 秒”换成本卷实测的数字：8 万次 PIO exit（30449 → 110187）、`Run /init` 从 0.75 s 推到 2.70 s，并说明它由两个各 1 秒的超时构成。
5. **`tests/step2.sh` 的 TSC 断言订正。** 原来是 `expect_any "Fast TSC calibration using PIT" "Using PIT calibration value"`，注释说“快路偶尔失败（实测约三成）”。实测表明这个描述不准：在裸机 KVM 上快路**必然**成功，在嵌套虚拟化下快路**必然**失败，而真正偶发的是慢路也失败（本机约 1/6）——后者没被列进候选，于是这条断言会周期性假失败。改成三选一，并在注释里写清每种结局对应什么 host 环境。

**卷八：把 PIO exit 从热路径上拿掉。** 本卷最刺眼的一个数字是 30449 次 PIO exit 里有 29912 次是串口，每个字符两次往返。这不是模拟得不对——恰恰相反，16550A 的语义就是一次一个字节。问题出在“设备接口”本身：一个为 1980 年代总线设计的寄存器协议，放到虚拟机里每次访问都要穿一遍用户态。卷八转向 VirtIO：用共享内存里的环形队列代替寄存器读写，用 ioeventfd 把“通知”变成内核里的一次 eventfd 写而不再回用户态，用 irqfd 把中断注入从 `KVM_IRQ_LINE` 这条 ioctl 上挪走。核心命题会从本卷的“模拟到什么程度”变成：**当设备可以为虚拟化重新设计时，接口应该长什么样。**
