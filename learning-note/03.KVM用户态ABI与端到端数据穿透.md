# 卷三：KVM 用户态 ABI 与一次设备访问的端到端穿透

> 承接卷一（CPU 虚拟化与世界切换）和卷二（内存虚拟化与 MMIO 识别）。
>
> 卷二结束时，Guest 的一次设备访问已经被硬件和 KVM MMU 一路押送到了 `x86_emulate_instruction()` 的门口。本卷讲清楚这道门之后发生的事：KVM 与用户态之间那份基于共享内存的 ABI 契约，两条设备访问路径（PIO 与 MMIO）的完整穿透与成本差异，以及一个最小 VMM 的实现。
>
> 源码基于 Linux **v5.15**。

---

## 1. KVM 的边界：它不模拟设备

一个必须先厘清的定位问题：**KVM 不是虚拟机监控器，它是 CPU 与内存虚拟化的驱动。**

KVM 负责的是卷一和卷二讲的全部内容：管理 VMCB/VMCS、执行世界切换、维护 NPT/EPT、处理缺页。它对"这台虚拟机有一块什么网卡"、"磁盘镜像是什么格式"、"串口输出到哪去"一无所知，也不想知道。

设备模型（Device Model）在用户态。QEMU、Firecracker、crosvm、kvmtool 都是用户态 VMM，它们通过同一套 `ioctl` 驱动 KVM。

KVM 内核里确实有少量设备实现——LAPIC、IOAPIC、PIC、PIT、以及 `kvm_io_bus` 上挂的 `ioeventfd`——但这些是**性能例外**而非常规：它们进入内核只因为把它们留在用户态的往返开销无法接受。判断标准很清晰：访问频率高到每次多一趟系统调用就会影响整机性能的，才进内核。

这个边界划分决定了整个 ABI 的形态：**内核与用户态之间需要一条低延迟、高频率、能传结构化数据的通道。**

## 2. ABI 设计：三层文件描述符与一块共享内存

### 2.1 fd 层级

```
  open("/dev/kvm", O_RDWR | O_CLOEXEC)  ──►  system fd
      │                                       作用域：整个 KVM 子系统
      │                                       · KVM_GET_API_VERSION
      │                                       · KVM_CHECK_EXTENSION
      │                                       · KVM_GET_VCPU_MMAP_SIZE
      │                                       · KVM_GET_SUPPORTED_CPUID
      │
      └─ ioctl(KVM_CREATE_VM, 0) ──────►  VM fd
             │                              作用域：一台虚拟机
             │                              · KVM_SET_USER_MEMORY_REGION
             │                              · KVM_CREATE_IRQCHIP / KVM_CREATE_PIT2
             │                              · KVM_IRQ_LINE / KVM_SET_GSI_ROUTING
             │                              · KVM_IOEVENTFD / KVM_IRQFD
             │                              · KVM_GET_DIRTY_LOG
             │
             ├─ ioctl(KVM_CREATE_VCPU, 0) ──►  vCPU fd 0
             │      │                           作用域：一个虚拟 CPU
             │      │                           · KVM_RUN
             │      │                           · KVM_GET/SET_REGS
             │      │                           · KVM_GET/SET_SREGS
             │      │                           · KVM_GET/SET_MSRS
             │      │                           · KVM_SET_CPUID2
             │      │
             │      └─ mmap(vcpu_fd, 0, mmap_size) ──►  共享通信区
             │
             ├─ ioctl(KVM_CREATE_VCPU, 1) ──►  vCPU fd 1
             │      └─ mmap(...)
             │
             └─ ioctl(KVM_CREATE_DEVICE) ──►  device fd（VFIO、vGIC 等）
```

**多核虚拟机的线程模型由这个层级直接决定**：每个 vCPU 是一个独立 fd，用户态为每个 vCPU 起一个线程，各自阻塞在自己的 `KVM_RUN` 上。Guest 里的 SMP 并行，在 Host 看来就是若干个普通线程被 CFS 调度到不同物理核。vCPU 的"抢占"就是线程被调度出去——这也是为什么 Guest 里的自旋锁在超售场景下会退化（持锁的 vCPU 被 Host 调度走了，其他 vCPU 在真实的物理核上空转），以及为什么需要 PV Spinlock 这类半虚拟化机制。

### 2.2 版本策略：`KVM_API_VERSION` 永远是 12

```c
/* include/uapi/linux/kvm.h */
#define KVM_API_VERSION 12
```

这个值从 2007 年至今没变过，未来也不会变。KVM 的 ABI 演进不靠版本号，而靠**逐特性查询**：

```c
if (ioctl(kvm_fd, KVM_CHECK_EXTENSION, KVM_CAP_USER_MEMORY) <= 0)
    fatal("KVM_CAP_USER_MEMORY not supported");

int nr_slots = ioctl(kvm_fd, KVM_CHECK_EXTENSION, KVM_CAP_NR_MEMSLOTS);
int max_vcpus = ioctl(kvm_fd, KVM_CHECK_EXTENSION, KVM_CAP_MAX_VCPUS);
```

`KVM_CHECK_EXTENSION` 对布尔型能力返回 0/1，对数值型能力直接返回数值。这套设计让新老组合可以自由搭配：老 VMM 在新内核上跑（用不到新特性），新 VMM 在老内核上跑（查询失败就降级）。

部分能力还需要显式启用（`KVM_ENABLE_CAP`），因为启用它们会改变既有 `ioctl` 的行为，默认打开会破坏老程序。

### 2.3 共享内存：为什么不用 `ioctl` 传参

`KVM_RUN` 的返回信息包含退出原因、端口号、物理地址、数据、指令长度、中断状态等，而且这个调用在负载虚拟机上每秒发生数万次。如果每次都走 `copy_to_user`，光是参数拷贝就是可观的开销。

KVM 的方案是在创建 vCPU 时分配好通信区，用户态 `mmap(vcpu_fd)` 映射进自己的地址空间。此后 `KVM_RUN` 这个 `ioctl` 不传参数、不返回数据，退化成一个纯粹的"开始/结束"信号。

映射的实现在 `virt/kvm/kvm_main.c`：

```c
static vm_fault_t kvm_vcpu_fault(struct vm_fault *vmf)
{
    struct kvm_vcpu *vcpu = vmf->vma->vm_file->private_data;
    struct page *page;

    if (vmf->pgoff == 0)
        page = virt_to_page(vcpu->run);
#ifdef CONFIG_X86
    else if (vmf->pgoff == KVM_PIO_PAGE_OFFSET)
        page = virt_to_page(vcpu->arch.pio_data);
#endif
#ifdef CONFIG_KVM_MMIO
    else if (vmf->pgoff == KVM_COALESCED_MMIO_PAGE_OFFSET)
        page = virt_to_page(vcpu->kvm->coalesced_mmio_ring);
#endif
    else if (kvm_page_in_dirty_ring(vcpu->kvm, vmf->pgoff))
        page = kvm_dirty_ring_get_page(&vcpu->dirty_ring,
                                       vmf->pgoff - KVM_DIRTY_LOG_PAGE_OFFSET);
    else
        return kvm_arch_vcpu_fault(vcpu, vmf);

    get_page(page);
    vmf->page = page;
    return 0;
}
```

这是一个**按页偏移分发的 `mmap`**：同一个 fd 的不同页映射到内核里不同的对象。布局如下：

```
   mmap(vcpu_fd, 0, ioctl(kvm_fd, KVM_GET_VCPU_MMAP_SIZE, 0), ...)

   ┌────────────────────────────────────────────┐ pgoff 0
   │  struct kvm_run                            │
   │  ┌──────────────────────────────────────┐  │
   │  │ __u8  request_interrupt_window  (in)  │  │  用户态 → 内核
   │  │ __u8  immediate_exit            (in)  │  │
   │  ├──────────────────────────────────────┤  │
   │  │ __u32 exit_reason              (out)  │  │  内核 → 用户态
   │  │ __u8  ready_for_interrupt_injection   │  │
   │  │ __u8  if_flag                         │  │
   │  ├──────────────────────────────────────┤  │
   │  │ __u64 cr8       (in/out)              │  │
   │  │ __u64 apic_base (in/out)              │  │
   │  ├──────────────────────────────────────┤  │
   │  │ union {                               │  │  按 exit_reason 解释
   │  │   struct { u8 direction; u8 size;     │  │
   │  │            u16 port; u32 count;       │  │
   │  │            u64 data_offset; } io;     │  │  ← 注意：无数据字段
   │  │   struct { u64 phys_addr;             │  │
   │  │            u8  data[8];               │  │  ← MMIO 数据内联
   │  │            u32 len; u8 is_write; } mmio;│ │
   │  │   struct { ... } hypercall;           │  │
   │  │   struct { ... } internal;            │  │
   │  │   ...                                 │  │
   │  │ }                                     │  │
   │  └──────────────────────────────────────┘  │
   ├────────────────────────────────────────────┤ pgoff 1  (KVM_PIO_PAGE_OFFSET)
   │  PIO 数据页（4 KB）                          │
   │  端口 I/O 的实际数据                         │
   ├────────────────────────────────────────────┤ pgoff 2  (可选)
   │  coalesced MMIO ring                       │
   ├────────────────────────────────────────────┤ pgoff 3+ (可选)
   │  dirty ring                                │
   └────────────────────────────────────────────┘
```

**永远不要用 `sizeof(struct kvm_run)` 作为 `mmap` 长度。** 必须调 `KVM_GET_VCPU_MMAP_SIZE`：

```c
case KVM_GET_VCPU_MMAP_SIZE:
    if (arg) goto out;
    r = PAGE_SIZE;      /* struct kvm_run */
#ifdef CONFIG_X86
    r += PAGE_SIZE;     /* pio data page */
#endif
#ifdef CONFIG_KVM_MMIO
    r += PAGE_SIZE;     /* coalesced mmio ring page */
#endif
    break;
```

实际大小随内核配置变化，至少两页。用 `sizeof` 的后果是访问 PIO 数据页时段错误——这是自己写 VMM 时最常见的第一个崩溃。

### 2.4 PIO 数据为什么单独一页，MMIO 数据为什么内联

对比 `kvm_run` 里两个 union 成员：

```c
/* KVM_EXIT_IO */
struct {
    __u8  direction;
    __u8  size;         /* bytes */
    __u16 port;
    __u32 count;
    __u64 data_offset;  /* relative to kvm_run start */
} io;

/* KVM_EXIT_MMIO */
struct {
    __u64 phys_addr;
    __u8  data[8];      /* 数据直接放这 */
    __u32 len;
    __u8  is_write;
} mmio;
```

差异的原因是**串操作**。x86 的 `rep outsb` 可以一条指令输出几千字节，`count` 字段就是重复次数。这些数据塞不进几十字节的 union，必须放在独立的页里，由 `data_offset` 指向。

MMIO 没有对应的串操作形式（`rep movsb` 到 MMIO 地址会被拆成多次单独的模拟），单次最大 8 字节，直接内联最省事。

## 3. 最小 VMM 的构造

### 3.1 完整的 `ioctl` 序列

```c
#include <fcntl.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <linux/kvm.h>

#define MEM_SIZE   (2 * 1024 * 1024)
#define CODE_GPA   0x1000

int main(void)
{
    /* ---- 1. 打开设备并握手 ---- */
    int kvm_fd = open("/dev/kvm", O_RDWR | O_CLOEXEC);
    if (ioctl(kvm_fd, KVM_GET_API_VERSION, 0) != 12)
        fatal("unexpected KVM API version");
    if (ioctl(kvm_fd, KVM_CHECK_EXTENSION, KVM_CAP_USER_MEMORY) <= 0)
        fatal("KVM_CAP_USER_MEMORY missing");

    /* ---- 2. 创建虚拟机 ---- */
    int vm_fd = ioctl(kvm_fd, KVM_CREATE_VM, 0);

    /* ---- 3. 分配 Guest 物理内存 ---- */
    void *mem = mmap(NULL, MEM_SIZE, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);
    memcpy((char *)mem + CODE_GPA, payload, sizeof(payload));

    /* ---- 4. 注册 memslot ---- */
    struct kvm_userspace_memory_region region = {
        .slot            = 0,
        .flags           = 0,
        .guest_phys_addr = 0,
        .memory_size     = MEM_SIZE,
        .userspace_addr  = (uint64_t)mem,
    };
    ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION, &region);

    /* ---- 5. 创建 vCPU 并映射通信区 ---- */
    int vcpu_fd = ioctl(vm_fd, KVM_CREATE_VCPU, 0);
    int mmap_size = ioctl(kvm_fd, KVM_GET_VCPU_MMAP_SIZE, 0);
    struct kvm_run *run = mmap(NULL, mmap_size, PROT_READ | PROT_WRITE,
                               MAP_SHARED, vcpu_fd, 0);

    /* ---- 6. 设置初始寄存器 ---- */
    struct kvm_sregs sregs;
    ioctl(vcpu_fd, KVM_GET_SREGS, &sregs);   /* 读-改-写，不要自己构造 */
    sregs.cs.base     = 0;
    sregs.cs.selector = 0;
    ioctl(vcpu_fd, KVM_SET_SREGS, &sregs);

    struct kvm_regs regs = {
        .rip    = CODE_GPA,
        .rflags = 0x2,       /* bit 1 是保留位，硬件要求恒为 1 */
    };
    ioctl(vcpu_fd, KVM_SET_REGS, &regs);

    /* ---- 7. 运行循环 ---- */
    for (;;) {
        if (ioctl(vcpu_fd, KVM_RUN, 0) < 0)
            fatal("KVM_RUN: %s", strerror(errno));

        switch (run->exit_reason) {
        case KVM_EXIT_IO:
            handle_pio(run);
            break;
        case KVM_EXIT_MMIO:
            handle_mmio(run);
            break;
        case KVM_EXIT_HLT:
            return 0;
        case KVM_EXIT_SHUTDOWN:
            fatal("guest triple faulted");
        case KVM_EXIT_FAIL_ENTRY:
            fatal("VMRUN consistency check failed: 0x%llx",
                  run->fail_entry.hardware_entry_failure_reason);
        case KVM_EXIT_INTERNAL_ERROR:
            fatal("internal error, suberror %u", run->internal.suberror);
        default:
            fatal("unhandled exit_reason %u", run->exit_reason);
        }
    }
}
```

### 3.2 为什么必须改 `CS`

`KVM_CREATE_VCPU` 返回时，vCPU 的状态是按 x86 加电复位规范初始化的：

```c
/* arch/x86/kvm/x86.c:10935，kvm_vcpu_reset() */
kvm_rip_write(vcpu, 0xfff0);

/* arch/x86/kvm/svm/svm.c，init_vmcb() */
save->cs.selector = 0xf000;
save->cs.base     = 0xffff0000;
save->cs.limit    = 0xffff;
```

实模式取指地址是 `CS.base + RIP = 0xFFFF0000 + 0xFFF0 = 0xFFFFFFF0`——真实 x86 机器的复位向量，那里应该是主板 BIOS ROM 的末尾 16 字节。

注意这个组合本身是"非法"的实模式状态：实模式下 `CS.base` 应该等于 `CS.selector << 4 = 0xF0000`，而硬件在复位时故意让它等于 `0xFFFF0000`。这是 x86 的历史设计——为了让 CPU 在还没初始化任何东西的时候就能访问 4 GB 顶端的 ROM，第一条 `far jmp` 之后 `CS.base` 才会被重新计算成正常的实模式形式。

我们的虚拟机没有 BIOS，`0xFFFFFFF0` 不在任何 memslot 里。所以必须把 `CS.base` 清零、把 `RIP` 指到我们放代码的地方。

`KVM_GET_SREGS` → 改 → `KVM_SET_SREGS` 这个读-改-写模式不是可选的。`struct kvm_sregs` 里有段属性位（卷一讲过 VMCB 的 `attrib` 是压缩格式）、`CR0`/`CR4` 的保留位、`EFER` 状态，自己从零构造几乎必然触发 `VMRUN` 的一致性检查失败。

### 3.3 实模式：AMD 与 Intel 的分歧

让 vCPU 从复位状态直接跑，意味着它在 **16 位实模式**下执行。

**AMD SVM 原生支持。** VMCB 的 Save Area 里存的就是完整的段基址/界限/属性，硬件按实模式语义执行，没有任何额外要求。

**早期 Intel VT-x 不支持。** 最初的 VMX 规范要求 Guest 必须处于保护模式且开启分页，否则 VM-Entry 的一致性检查失败。但每台虚拟机开机都要跑实模式的 BIOS 代码，所以 KVM 不得不用软件模拟 vm86 模式，并且需要用户态额外提供两块 Guest 物理内存：

```c
ioctl(vm_fd, KVM_SET_TSS_ADDR, 0xfffbd000);          /* 假 TSS 的 3 页空间 */
ioctl(vm_fd, KVM_SET_IDENTITY_MAP_ADDR, &addr);      /* 恒等映射页表 */
```

**这两个 `ioctl` 只在 Intel 平台上有意义，AMD 平台调用了也是空操作。** 后来 Intel 加入了 **unrestricted guest** 特性，硬件才原生支持实模式 Guest，这两个 `ioctl` 也就变成了历史兼容项。

写跨平台 VMM 时，这是少数几个必须做平台区分的地方之一——虽然最省事的做法是无条件调用它们。

## 4. 路径一：端口 I/O 的完整穿透

### 4.1 全链路

以 Guest 执行 `out %al, (%dx)`（`DX = 0x3f8`，`AL = 'H'`）为例：

```
┌─ Guest 模式 ─────────────────────────────────────────────────────────┐
│  RIP = 0x1005:  out %al, (%dx)                                       │
└──────────────────────┬───────────────────────────────────────────────┘
                       │ (1) 硬件查 VMCB.control.iopm_base_pa 指向的位图
                       │     端口 0x3f8 对应位 = 1（KVM 全填 0xff）→ 拦截
                       ▼
┌─ 硬件（AMD SVM）─────────────────────────────────────────────────────┐
│  · 指令未执行，Guest 状态回退到指令边界                                │
│  · Guest CS/RIP/RSP/RFLAGS/RAX → VMCB.save                           │
│  · exit_code   = 0x07B (SVM_EXIT_IOIO)                               │
│  · exit_info_1 = 端口/方向/宽度编码                                   │
│  · exit_info_2 = 下一条指令的 RIP（NRIP 特性）                        │
│  · 恢复 Host 状态，切回 Host 模式                                      │
└──────────────────────┬───────────────────────────────────────────────┘
                       │ (2)
                       ▼
┌─ Host 内核态 ────────────────────────────────────────────────────────┐
│  vmenter.S: 存回 15 个 Guest GPR，清零，恢复 Host GPR，ret            │
│  svm_vcpu_run(): vmsave/vmload，同步 RAX/RSP/RIP，stgi()             │
│  handle_exit(): exit_code = 0x7B → svm_exit_handlers[0x7B]           │
│      ▼                                                               │
│  io_interception()                                                   │
│      port = io_info >> 16;  in = io_info & 1;  size = ...            │
│      string ? kvm_emulate_instruction() : kvm_fast_pio()             │
│      ▼                                                               │
│  kvm_fast_pio_out()                                                  │
│      ★ val = kvm_rax_read(vcpu)   ← 数据直接从寄存器读，无需解码指令   │
│      ▼                                                               │
│  emulator_pio_out() → emulator_pio_in_out()                          │
│      kernel_pio(): 问 kvm_io_bus，内核里有没有设备接管这个端口？        │
│         有（PIT/PIC/ioeventfd）→ 内核处理完，返回 1，不退出用户态       │
│         没有 → 继续                                                   │
│      ▼                                                               │
│      vcpu->run->exit_reason    = KVM_EXIT_IO;                        │
│      vcpu->run->io.direction   = KVM_EXIT_IO_OUT;                    │
│      vcpu->run->io.size        = 1;                                  │
│      vcpu->run->io.port        = 0x3f8;                              │
│      vcpu->run->io.count       = 1;                                  │
│      vcpu->run->io.data_offset = KVM_PIO_PAGE_OFFSET * PAGE_SIZE;    │
│      *(u8 *)vcpu->arch.pio_data = 'H';                               │
│      return 0;                                                       │
│      ▼                                                               │
│  kvm_fast_pio() 尾部：kvm_skip_emulated_instruction()                 │
│      ★ RIP 在返回用户态之前就推进好了                                  │
│      ▼                                                               │
│  vcpu_enter_guest() 返回 0 → vcpu_run() 跳出循环                      │
└──────────────────────┬───────────────────────────────────────────────┘
                       │ (3) ioctl(KVM_RUN) 返回
                       ▼
┌─ Host 用户态 ────────────────────────────────────────────────────────┐
│  run->exit_reason == KVM_EXIT_IO                                     │
│  run->io.port == 0x3f8 → 认出这是 COM1                                │
│  char *data = (char *)run + run->io.data_offset;   /* = run + 4096 */│
│  fwrite(data, run->io.size, run->io.count, stdout);                  │
│                                                                      │
│  ioctl(vcpu_fd, KVM_RUN, 0);   /* 无需修改任何寄存器 */                │
└──────────────────────┬───────────────────────────────────────────────┘
                       │ (4)
                       ▼
              vmrun → Guest 从 RIP+2 继续
```

### 4.2 `exit_info_1` 的编码

```
   exit_info_1（SVM_EXIT_IOIO）

    31                    16 15  10 9    7 6    4  3   2   1  0
   ┌────────────────────────┬──────┬──────┬──────┬───┬───┬──┬───┐
   │      端口号（16 位）     │ 保留  │ ASIZE│ SIZE │REP│STR│ -│TYPE│
   └────────────────────────┴──────┴──────┴──────┴───┴───┴──┴───┘
     TYPE  bit 0    : 1 = IN，0 = OUT
     STR   bit 2    : 1 = 串操作（ins/outs）
     REP   bit 3    : 1 = 带 REP 前缀
     SIZE  bit 6:4  : 操作宽度 1/2/4 字节（独热编码）
     ASIZE bit 9:7  : 地址宽度 16/32/64 位（串操作用）
```

```c
/* arch/x86/kvm/svm/svm.c:2062 */
static int io_interception(struct kvm_vcpu *vcpu)
{
    struct vcpu_svm *svm = to_svm(vcpu);
    u32 io_info = svm->vmcb->control.exit_info_1;
    int size, in, string;
    unsigned port;

    ++vcpu->stat.io_exits;
    string = (io_info & SVM_IOIO_STR_MASK) != 0;
    in     = (io_info & SVM_IOIO_TYPE_MASK) != 0;
    port   = io_info >> 16;
    size   = (io_info & SVM_IOIO_SIZE_MASK) >> SVM_IOIO_SIZE_SHIFT;

    if (string) {
        if (sev_es_guest(vcpu->kvm))
            return sev_es_string_io(svm, size, port, in);
        else
            return kvm_emulate_instruction(vcpu, 0);   /* 串操作走完整模拟器 */
    }

    svm->next_rip = svm->vmcb->control.exit_info_2;
    return kvm_fast_pio(vcpu, size, port, in);         /* 简单情况走快路 */
}
```

**串操作必须回退到完整模拟器**，因为 `outsb` 要访问 Guest 内存取数据、要递增 `RSI`、`REP` 前缀还要循环并递减 `RCX`。硬件给的信息只够处理单次访问。这种"常见情况走快路，复杂情况回退通用模拟器"的分层是 KVM 里反复出现的模式。

### 4.3 RIP 由谁推进

```c
/* arch/x86/kvm/x86.c:8105 */
int kvm_fast_pio(struct kvm_vcpu *vcpu, int size, unsigned short port, int in)
{
    int ret;
    if (in)
        ret = kvm_fast_pio_in(vcpu, size, port);
    else
        ret = kvm_fast_pio_out(vcpu, size, port);
    return ret && kvm_skip_emulated_instruction(vcpu);
}
```

`kvm_skip_emulated_instruction()`（AMD 上直接用 `vmcb->control.next_rip`，见卷一第 6 节）在**返回用户态之前**就把 `RIP` 推进了。所以用户态处理完 PIO 后不需要碰任何寄存器，直接再次 `KVM_RUN` 即可。

注意 `kvm_fast_pio_out()` 里那段兼容代码：

```c
/*
 * Workaround userspace that relies on old KVM behavior of %rip being
 * incremented prior to exiting to userspace to handle "OUT 0x7e".
 */
if (port == 0x7e && kvm_check_has_quirk(vcpu->kvm, KVM_X86_QUIRK_OUT_7E_INC_RIP))
```

内核 ABI 一旦发布就不能破坏，哪怕只有一个用户依赖某个未文档化的行为。代价就是这种针对单个端口号的特殊分支。

### 4.4 `IN` 方向的差异

`IN` 比 `OUT` 多一步：内核填好 `kvm_run->io` 后退出，用户态把读到的值写进 PIO 数据页，再次 `KVM_RUN`；内核这次不进 Guest，而是先执行**续传回调**把数据搬进 Guest 的 `RAX`：

```c
static int complete_fast_pio_in(struct kvm_vcpu *vcpu)
{
    unsigned long val = ...;
    complete_emulator_pio_in(vcpu, &val);
    kvm_rax_write(vcpu, val);
    return kvm_skip_emulated_instruction(vcpu);
}
```

这个 `vcpu->arch.complete_userspace_io` 回调机制是 KVM 处理"需要用户态返回数据"的通用手段，MMIO 读也走同一套（见下节）。

## 5. 路径二：MMIO 的完整穿透

### 5.1 为什么 MMIO 比 PIO 贵得多

PIO 有两个先天优势：硬件在 `exit_info_1` 里给出了端口号和宽度；数据的位置由指令语义硬性规定（`OUT` 的源永远是 `AL`/`AX`/`EAX`）。所以 KVM 只需要读一个寄存器。

MMIO 完全不同。卷二讲过，硬件产生 `#NPF` 时只给出**故障 GPA** 和**访问类型**（读/写/取指）。它不告诉你：

- 要写入的值是多少
- 数据来自哪个寄存器（可以是任意 GPR，也可以是立即数）
- 访问宽度是多少（1/2/4/8 字节）
- 目标操作数用了什么寻址模式

因为写 MMIO 的指令可以是 `mov`、`movzx`、`add`、`or`、`xchg`、`cmpxchg`、`movs`……每一条的操作数布局都不同。硬件不可能把这些语义都编码进两个 64 位字段。

**唯一的办法是软件解码这条指令。** `arch/x86/kvm/emulate.c` 是一个完整的 x86 指令解码器和执行器，五千多行，支持实模式/保护模式/长模式、各种前缀、ModRM/SIB 寻址、段限检查。它存在的首要理由就是 MMIO 模拟。

### 5.2 全链路


### 5.3 fragment 机制存在的原因

`vcpu->mmio_fragments[]` 看起来是多余的复杂度，但它解决两个真实问题：

**跨页访问。** 一次 8 字节的 MMIO 写可能跨越页边界，两半属于不同的 GPA 页，甚至一半是 RAM 一半是 MMIO。`emulator_read_write()` 里有专门的拆分逻辑：

```c
/* Crossing a page boundary? */
if (((addr + bytes - 1) ^ addr) & PAGE_MASK) {
    now = -addr & ~PAGE_MASK;
    rc = emulator_read_write_onepage(addr, val, now, exception, vcpu, ops);
    ...
    addr += now; val += now; bytes -= now;
}
```

**部分命中。** 一次访问可能前半段被内核设备接管、后半段需要用户态处理。`handled` 返回实际处理的字节数，剩余部分才记成 fragment。

用户态 VMM 需要知道的是：**一条 Guest 指令可能对应多次 `KVM_EXIT_MMIO`**，每次处理一个 fragment，最多 8 字节。用户态不需要关心这个拆分，只要每次都老实处理 `run->mmio` 里描述的那一段就行。

### 5.4 `kvm_io_bus`：内核内设备的分发

`kvm_io_bus_write()` 是内核内设备模型的入口。KVM 维护若干条"总线"：

```c
enum kvm_bus {
    KVM_MMIO_BUS,
    KVM_PIO_BUS,
    KVM_VIRTIO_CCW_NOTIFY_BUS,   /* s390 */
    KVM_FAST_MMIO_BUS,           /* ioeventfd 的零长度写 */
    KVM_NR_BUSES
};
```

每条总线上挂着一组 `struct kvm_io_device`，按地址范围排序，查找用二分。注册在这上面的有：in-kernel LAPIC/IOAPIC/PIC/PIT、以及通过 `KVM_IOEVENTFD` 注册的地址。

**`KVM_FAST_MMIO_BUS` 值得单独提。** 它专门服务于 VirtIO 的通知路径：Guest 往 QueueNotify 寄存器写一个值，语义上 VMM 只关心"有人敲门了"，写进去的值是什么并不重要。于是可以注册一个"零长度"的 ioeventfd——KVM 在 MMU 层面识别出这次访问命中了 fast MMIO 总线，**连指令解码都跳过**，直接 `eventfd_signal()` 唤醒后端线程，然后 `vmrun` 回去。

这条优化把 VirtIO 通知的成本从"完整 NPF + 指令解码 + 退出用户态 + 系统调用往返"压缩到了"NPF + eventfd 唤醒"。

### 5.5 两条路径的成本对比

| 环节 | 端口 I/O (`KVM_EXIT_IO`) | MMIO (`KVM_EXIT_MMIO`) |
|---|---|---|
| 硬件退出原因 | `SVM_EXIT_IOIO` (0x7B) | `SVM_EXIT_NPF` (0x400) |
| 硬件提供的信息 | 端口、方向、宽度、串标志 | 故障 GPA、访问类型 |
| 是否需要软件解码指令 | **否**（数据在 `RAX`） | **是**（必须解码） |
| 首次访问是否需要建表 | 否 | 是（安装 MMIO SPTE） |
| 后续访问的 MMU 路径 | 不涉及 MMU | RSVD 快速路径 + per-vCPU 缓存 |
| 单次访问可传输字节 | 1/2/4，串操作可批量 | 最多 8，跨页要拆 fragment |
| 内核旁路手段 | `ioeventfd`（PIO 总线） | `ioeventfd` / fast MMIO（可跳过解码） |
| 典型使用者 | 传统 ISA 设备、VirtIO-PCI 传统模式 | PCIe BAR、VirtIO-MMIO、APIC |

一个初看反直觉的结论：**VirtIO-MMIO 这个"更现代"的传输层，单次陷出成本反而高于老式的端口 I/O。** 因为端口 I/O 有专门的硬件拦截通道，而 MMIO 复用的是缺页机制，必须付指令解码的代价。

这也就是为什么高性能虚拟化的答案不是换传输层，而是**根本不走这条路**：

```
   性能演进的三级台阶

   第一级：完整往返
     Guest MMIO 写 → #NPF → 解码 → KVM_EXIT_MMIO → 用户态处理 → KVM_RUN
     成本：~10 微秒量级

   第二级：ioeventfd（内核旁路用户态）
     Guest MMIO 写 → #NPF → kvm_io_bus 命中 → eventfd_signal → vmrun
     用户态的 I/O 线程被 epoll 唤醒，异步处理
     成本：~2-3 微秒量级，且不阻塞 vCPU 线程

   第三级：vhost（连用户态都不参与）
     数据面完全在内核（vhost-net / vhost-vsock）或硬件（VFIO / SR-IOV）
     Guest 的通知直达内核线程或物理设备
     成本：接近裸机
```

后续讲 VirtIO 和 vhost 时，这三级台阶是主线。

## 6. `KVM_EXIT_HLT` 与 in-kernel irqchip

自己写的最小 VMM 会频繁看到 `KVM_EXIT_HLT`，但用 QEMU 跑一台正常虚拟机几乎看不到——Guest 的 idle 循环每秒执行几千次 `hlt`，却不退出用户态。

原因在这段代码：

```c
/* arch/x86/kvm/x86.c:8521 */
static int __kvm_vcpu_halt(struct kvm_vcpu *vcpu, int state, int reason)
{
    ++vcpu->stat.halt_exits;
    if (lapic_in_kernel(vcpu)) {
        vcpu->arch.mp_state = state;      /* 内核内处理，不回用户态 */
        return 1;
    } else {
        vcpu->run->exit_reason = reason;  /* 回用户态 */
        return 0;
    }
}
```

分支条件是这台虚拟机有没有**内核内的本地 APIC**。

- QEMU 调用了 `KVM_CREATE_IRQCHIP`，中断控制器在内核里。`hlt` 的语义是"停下来等中断"，而中断也在内核里，KVM 完全有能力自己决定何时唤醒：把 vCPU 置为 `KVM_MP_STATE_HALTED`，在 `kvm_vcpu_block()` 里睡眠，中断到达时唤醒。用户态全程不知情。
- 最小 VMM 没有创建 irqchip，KVM 里没有中断源，它无法判断何时该唤醒，只能把决定权交给用户态。

所以 `KVM_EXIT_HLT` 是"简化配置下的产物"。这也说明了 `KVM_CREATE_IRQCHIP` 为什么是性能上的必选项——它把整条中断路径（`hlt` 阻塞、中断投递、EOI 处理、IPI 转发）都留在了内核里，配合 `irqfd` 可以做到设备后端直接在内核注入中断，vCPU 线程完全不被打扰。

## 7. 调试指南

### 7.1 常见故障

**`KVM_EXIT_FAIL_ENTRY`，`hardware_entry_failure_reason = 0xffffffffffffffff`**

`VMRUN` 的一致性检查失败（卷一第 5 节列了检查项）。用户态拿到的这个值毫无信息量，**但 `dmesg` 里通常有一份完整的 VMCB dump**——`svm.c` 的 `dump_vmcb()` 会把控制区和保存区的每个字段打出来。排查顺序：

1. `rflags` bit 1 是否为 1
2. `CR0`/`CR4`/`EFER` 是否自洽（比如设了 `EFER.LME` 但没开 `CR4.PAE`）
3. 段属性位是否是从 `KVM_GET_SREGS` 读出来改的
4. 长模式下 `CS.L` 和 `CS.D` 是否同时为 1（非法组合）

**`KVM_EXIT_SHUTDOWN`**

Guest 触发了 triple fault：处理异常时又产生异常，连续三次。真机上这会导致 CPU 复位。常见原因是跳到了没有代码的地址、IDT 未初始化就产生了异常、或者栈指针指向未映射区域。

**`KVM_EXIT_INTERNAL_ERROR`，`suberror = KVM_INTERNAL_ERROR_EMULATION`**

指令模拟器解不了这条指令。绝大多数情况意味着 Guest 已经跑飞，正在把随机数据当指令执行。`run->internal.data[]` 里带着出错时的指令字节和 `RIP`，拿去反汇编能看出跑到了哪。

另一种可能是模拟器真的不支持某条指令——这在模拟不常见设备访问模式时会遇到（比如用 `movnti` 写 MMIO）。

**访问 `run->io.data_offset` 时段错误**

`mmap` 长度用了 `sizeof(struct kvm_run)`。改用 `KVM_GET_VCPU_MMAP_SIZE`。

**`KVM_SET_USER_MEMORY_REGION` 返回 `EINVAL`**

`guest_phys_addr` / `userspace_addr` 未页对齐，或 `memory_size` 不是页整数倍，或与已有 slot 的 GPA 区间重叠。

### 7.2 观测

```bash
# 实时看退出原因分布，判断性能瓶颈的第一手段
perf kvm stat live

# 抓完整事件流
trace-cmd record -e kvm:kvm_exit -e kvm:kvm_entry -e kvm:kvm_mmio -e kvm:kvm_pio

# 单独看某类退出
trace-cmd record -e kvm:kvm_page_fault
```

一台健康运行的虚拟机，退出原因分布中占大头的通常是 `npf`（启动阶段）、`msr`、`io`、`vintr`。如果发现某个意外的退出原因占了绝大多数，那里就是问题所在。典型的病态案例：

- `hlt` 占比极高 → 没开 in-kernel irqchip，或者 Guest 有忙等待的 idle 驱动
- `npf` 在稳定运行期仍然很高 → 大页被拆分，或者 Host 内存压力导致反复回收再建表
- `msr` 占比高 → 某个 MSR 没有加进直通列表，Guest 在热路径上频繁读写它
- `cpuid` 占比高 → Guest 里有代码在循环里调 `cpuid`（通常是做序列化屏障用）

## 8. 全系列总结

三卷讲完了一台虚拟机在没有任何设备的情况下，从加电到执行第一条指令、再到触碰第一个设备寄存器的完整机制：

**卷一（CPU 虚拟化）**：`EFER.SVME` 打开硬件状态机，`MSR_VM_HSAVE_PA` 指向 Host 状态的落点，形成 Host/Guest 状态存放的不对称结构；VMCB 是布局固定的 4 KB 契约页，控制区上半部分是软件写给硬件的策略、下半部分是硬件写给软件的退出信息；拦截配置分三层（位标志、12 KB IOPM、8 KB MSRPM）；世界切换的软件部分要处理 15 个 GPR 的搬运、RSB 填充、寄存器清零，以及 GIF/IF 两层中断屏蔽的级联；AMD 通过 `next_rip` 和 `insn_bytes[15]` 把部分指令解码固化进硬件。

**卷二（内存虚拟化）**：三层地址与二维漫游的 24 次访存；`memslot` 定义 GPA 空间中哪些是 RAM；`#NPF` 的完整生命周期与 `mmu_notifier_seq` 乐观锁；TDP MMU 用 RCU + `cmpxchg` 实现读锁并发建表；MMIO 通过"故意非法的 SPTE"（AMD 用物理地址保留位，Intel 用非法 W/X 组合）识别，generation 编码进 SPTE 实现 O(1) 惰性失效。

**卷三（用户态闭环）**：三层文件描述符 + 一块按页偏移分发的共享内存构成 ABI；PIO 因为硬件提供了完整信息而走快速路径，MMIO 因为硬件只给 GPA 而必须软件解码指令；`kvm_io_bus` 是内核内设备的分发点，也是 `ioeventfd` 旁路用户态的锚点。

**下一层的问题在设备侧：** Guest 和 VMM 如何在一块共享内存上协商出一个高效的、无锁的、支持批量与异步的 I/O 协议？这就是 VirtIO 与 Virtqueue。而 Virtqueue 里存放的全部是 GPA——卷二讲的 memslot 换算 `HVA = slot->userspace_addr + (GPA - base_gfn * PAGE_SIZE)` 会在那里成为每一次 I/O 都要走的热路径，连带着边界校验与恶意描述符防护一起，成为下一个主题的核心。
