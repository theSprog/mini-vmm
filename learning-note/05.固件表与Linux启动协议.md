# 卷五：固件表与 Linux 启动协议——从 boot_params 到 MADT 的逐字节拆解

> 承接卷四（x86 中断控制器与 KVM 中断注入全链路），配套 blog 第二篇《从零理解 KVM：中断、设备与多核》。
>
> 物理机上电后，BIOS 或 UEFI 固件要做两件事：初始化硬件，以及把“这台机器长什么样”写成一组约定格式的数据结构交给操作系统。在 VMM 里，硬件由 KVM 和设备模型扮演，而第二件事没有人替你做：内存布局、CPU 数量、中断控制器的位置、ISA 中断怎么接、电源怎么关，全部要由 VMM 亲手写进 guest 内存。写错一个字段，轻则某个设备不工作，重则内核在打印第一行日志之前就死循环。
>
> 本卷把这些结构按偏移逐字段拆开：64 位启动协议的入口约定、`struct boot_params` 与 setup header、E820 内存图、Intel MP 规范的配置表、ACPI 的 RSDP/XSDT/FADT/DSDT/MADT。每一个字段都回答三个问题：规范怎么定义、Linux 在启动的哪个阶段由哪个函数读它、mini-vmm 填了什么以及为什么。文中的十六进制转储不是手写的，而是把 mini-vmm 的 `mptable_setup()`、`acpi_setup()`、`zeropage_setup()` 原样编译进一个 host 端小程序、在平坦缓冲区上运行后导出的，与 guest 实际看到的字节一致。
>
> host 侧源码基于 Linux **v5.15**（KVM）。guest 侧源码基于 Linux **v6.6.91**，即 mini-vmm 实际引导的那个内核的源码树与 `.config`；文中 `file:line` 形式的行号都对应这棵树。规范依据 `Documentation/arch/x86/boot.rst`、`Documentation/arch/x86/zero-page.rst`、ACPI 6.x 规范与 Intel MultiProcessor Specification 1.4。

## 1. 固件缺席之后：谁来回答内核的五个问题

### 1.1 五个问题

一个 x86 内核从入口开始执行时，对自己所处的机器一无所知。它必须依次得到五类答案，才能把启动流程走完：

| 问题 | 典型答案的载体 | 物理机上由谁提供 | mini-vmm 中由谁提供 |
|---|---|---|---|
| 我处在什么 CPU 状态、参数在哪 | 入口寄存器约定（`%rsi` 指向 boot_params） | bootloader（GRUB 等） | `boot_setup_linux64()` 直接设置 vCPU 寄存器 |
| 物理内存有哪些、哪些能用 | E820 内存图 | BIOS 的 `INT 15h, AX=E820h`，经 bootloader 转交 | `zeropage_setup()` 直接填 `boot_params.e820_table` |
| 命令行、initrd 在哪 | setup header 的 `cmd_line_ptr`、`ramdisk_image` | bootloader | `zeropage_setup()` |
| 有几颗 CPU、中断控制器在哪、ISA 中断怎么接 | MP 配置表或 ACPI MADT | BIOS 在低端内存里放好的表 | `mptable_setup()` 与 `acpi_setup()` |
| 平台有哪些固定硬件、怎么关机 | ACPI FADT 与 DSDT 中的 AML | BIOS | `acpi_setup()` 与 `acpi_pm_attach()` |

还有一些信息不走表格，而是由 CPU 或设备自己回答：CPUID 与 MSR（KVM 负责，VMM 通过 `KVM_SET_CPUID2` 决定内容）、LAPIC ID 寄存器（KVM 的 LAPIC 模拟）、IOAPIC 版本寄存器里的引脚数（KVM 的 IOAPIC 模拟）、各种 I/O 端口探测（设备模型）。这些信息和表格之间必须一致，第 9 节会把所有一致性约束集中列出来。

### 1.2 三种信息通道

从 VMM 的角度看，把信息交给 guest 内核有三种性质完全不同的通道：

**直接传递。** `struct boot_params`（历史上叫 zero page）是 bootloader 与内核之间的私有契约。VMM 把它放在任意一块 guest 内存里，然后把地址放进 `%rsi`。内核在最早期把它整块复制到自己的 `.data` 里，之后再也不看原件。这是信息量最小、约束最少的通道，任何字段写错都只影响对应的功能。

**内存中的表，靠扫描或指针找到。** MP 表和 ACPI 表都是“BIOS 事先放在内存某处，OS 自己去找”的模式。找的方式有两种：按规范在几个固定的物理地址区间里逐 16 字节扫签名（`_MP_`、`RSD PTR `），或者由 bootloader 直接给出指针（`boot_params.acpi_rsdp_addr`、EFI 配置表）。这类表的特点是有签名、有校验和、有版本号，内核会做完整性检查，而且 MP 表和 ACPI 表对校验失败的态度截然不同（见 5.5 与 6.2 节）。

**可执行的描述。** DSDT 里的内容不是数据，而是 AML 字节码，由内核里的 ACPICA 解释器执行。`\_S5` 这样的对象在需要时才被求值。VMM 在这里写的是一段程序，写错了不会在启动时报错，而是在关机的那一刻才暴露。

### 1.3 Linux 在什么时候读什么

下表按执行顺序列出 guest 内核读取固件信息的关键点。前半段都在 `setup_arch()` 里，这是一个约 450 行的函数，x86 平台的全部“认识机器”的工作几乎都集中在这里。

| 阶段 | 位置 | 读取的信息 | 对应的启动日志 |
|---|---|---|---|
| 入口 | `arch/x86/kernel/head_64.S:67` | `%rsi` → `%r15`，保存 boot_params 物理地址 | 无 |
| 复制参数 | `arch/x86/kernel/head64.c:445` `copy_bootdata()` | 整个 boot_params 与 2048 字节命令行 | 无 |
| 平台类型 | `head64.c:545` `x86_early_init_platform_quirks()` | `hdr.hardware_subarch` | 无 |
| 早期保留 | `setup.c:941` `early_reserve_memory()` | initrd 位置、setup_data、BDA 中的 EBDA 指针 | 无 |
| 内存图 | `setup.c:944` `e820__memory_setup()` | `e820_entries` 与 `e820_table[]` | `BIOS-provided physical RAM map:` |
| 扩展数据 | `setup.c:945` `parse_setup_data()` | `hdr.setup_data` 链表 | 无 |
| 命令行 | `setup.c:985` `parse_early_param()` | `boot_command_line` 中的 early_param | `Command line: ...` 在更早的 `setup.c:879` 打印 |
| DMI | `setup.c:1032` `x86_init.resources.dmi_setup()` | 0xF0000 区间的 SMBIOS 入口点 | `DMI not present or invalid.` |
| MP 表扫描 | `setup.c:1103` `find_smp_config()` | 低端内存中的 `_MP_` 签名 | `found SMP MP-table at ...` |
| initrd | `setup.c:1207` `reserve_initrd()` | `ramdisk_image/size` | `RAMDISK: [mem ...]` |
| ACPI 表定位 | `setup.c:1211` `acpi_boot_table_init()` | RSDP → XSDT → 各表头 | `ACPI: RSDP ...` 等表头行 |
| MADT 早期解析 | `setup.c:1219` `early_acpi_boot_init()` | MADT 表头中的 LAPIC 地址 | 无 |
| FADT 与 MADT | `setup.c:1261` `acpi_boot_init()` | FADT 标志、SCI、PM 定时器；MADT 全部子表 | `ACPI: LAPIC_NMI ...`、`IOAPIC[0]: ...`、`Using ACPI (MADT) ...` |
| MP 表解析 | `setup.c:1267` `get_smp_config()` | MP 配置表（仅当 ACPI 没有提供时） | 本例中无 |
| CPU 数量 | `setup.c:1275` `prefill_possible_map()` | 前面登记的处理器数 | `smpboot: Allowing 4 CPUs, 0 hotplug CPUs` |
| PCI 空洞 | `setup.c:1289` `e820__setup_pci_gap()` | E820 中 4 GiB 以下最大的空隙 | `[mem 0x20000000-0xffffffff] available for PCI devices` |
| ACPICA 就绪 | `init/main.c:1035` `acpi_early_init()` | 重新分配根表并补做校验和检查 | 无 |
| AML 装载 | `drivers/acpi/bus.c:1295` `acpi_load_tables()`，在 `acpi_bus_init()` 中 | DSDT 的 AML | `ACPI: 1 ACPI AML tables successfully acquired and loaded` |
| 睡眠状态 | `drivers/acpi/bus.c:1351` `acpi_sleep_init()` | `\_S0`–`\_S5` 对象 | `ACPI: PM: (supports S0 S5)` |

表里有两个顺序值得注意。第一，MP 表的扫描（`find_smp_config()`，第 1103 行）发生在 ACPI 表定位（第 1211 行）之前，所以即使最终用的是 ACPI，MP 表也总会被扫描到并被 memblock 保留，这就是 mini-vmm 的启动日志里 `found SMP MP-table` 出现在所有 ACPI 行之前的原因。第二，MADT 的解析被拆成两次：`early_acpi_boot_init()` 只处理表头和 LAPIC 地址，把 LAPIC 映射到 fixmap 并读出 BSP 自己的 APIC ID（8.3 节），因为此后登记任何 CPU 之前都必须先知道谁是 BSP；完整的 CPU 与 IOAPIC 登记要等到 `acpi_boot_init()`。

### 1.4 mini-vmm 的整体布局

mini-vmm 在 Linux 模式下调用这些构造函数的顺序在 `src/main.c` 中：先 `elf_load_vmlinux()` 装载内核，再依次 `mptable_setup()`、`acpi_setup()`、`zeropage_setup()`，最后建页表并设置 vCPU 寄存器。它们在 guest 物理内存低端占用的区域如下（以 512 MiB 内存、4 个 vCPU 的默认配置为例）：

| GPA 区间 | 内容 | 由谁写入 | E820 类型 |
|---|---|---|---|
| `0x0000_0000`–`0x0000_0fff` | 空 | 无 | RAM（内核会把第 0 页改成保留） |
| `0x0000_1000`–`0x0000_1fff` | GDT | `boot_build_gdt()` | RAM |
| `0x0000_2000`–`0x0000_4fff` | PML4、PDPT、PD 三张页表 | `boot_build_page_table()` | RAM |
| `0x0000_7000`–`0x0000_7fff` | `struct boot_params` | `zeropage_setup()` | RAM |
| `0x0002_0000` 起 | 内核命令行 | `zeropage_setup()` | RAM |
| `0x0009_fc00`–`0x0009_fd2b` | MP 浮动指针与配置表 | `mptable_setup()` | 保留 |
| `0x000e_0000`–`0x000e_022d` | RSDP、XSDT、FADT、DSDT、MADT | `acpi_setup()` | 保留 |
| `0x0100_0000`–`0x02a2_ffff` | vmlinux 的 4 个 PT_LOAD 段 | `elf_load_vmlinux()` | RAM |
| `0x1fe0_0000` 起 | initrd | `load_initrd()` | RAM |

这张表在本卷后面会反复出现。它体现了一个原则：**VMM 写给内核的一次性数据（GDT、页表、boot_params、命令行）放在 RAM 里，内核用完即可回收；需要长期存在、并可能被扫描的表（MP 表、ACPI 表）放在 E820 报告为保留的区域里，内核不会把它们当作空闲内存分配出去。**

## 2. 入口：64 位启动协议与 vmlinux 直接启动

### 2.1 x86 Linux 的几个入口

同一个 x86 内核可以从好几个不同的入口被启动，每个入口对 CPU 状态和参数传递的约定都不同。VMM 选哪个入口，决定了它需要替固件做多少事。

| 入口 | 进入时的 CPU 状态 | 参数传递 | 谁读 E820 | 典型使用者 |
|---|---|---|---|---|
| 16 位实模式协议 | 实模式，`CS:IP` 指向 setup 代码的 `0x200` 偏移 | setup header 在 setup 代码段内 | 内核自己的 setup 代码调用 `INT 15h` | GRUB（legacy BIOS）、kvmtool |
| 32 位协议 | 保护模式、分页关闭，`%esi` 指向 boot_params | boot_params | bootloader 预先填好 | 部分 EFI 前的 bootloader、kexec |
| 64 位协议（bzImage） | 长模式、分页开启，从“保护模式部分的装载地址 + `0x200`”进入 | `%rsi` 指向 boot_params | bootloader 预先填好 | mini-vmm、rust-vmm `linux-loader` 的 bzImage 装载器 |
| vmlinux 直接启动 | 同 64 位协议，但直接跳到未压缩内核的 `startup_64` | `%rsi` 指向 boot_params | VMM 预先填好 | mini-vmm、`linux-loader` 的 ELF 装载器 |
| PVH | 32 位保护模式、分页关闭，`%ebx` 指向 `hvm_start_info` | `hvm_start_info`，由内核转换成 boot_params | VMM 通过 memmap 表提供 | Xen PVH、QEMU 的 `-kernel vmlinux`、Cloud Hypervisor |
| EFI stub | UEFI 固件调用 PE 入口 | EFI 系统表 | EFI 内存图转换而来 | 所有 UEFI 平台 |

其中 16 位入口需要一个真的 BIOS 在后面撑着，因为内核的 setup 代码（`arch/x86/boot/`）会调用 `INT 10h` 设置显示、调用 `INT 15h, AX=E820h` 获取内存图。kvmtool 走的就是这条路：它把 bzImage 的 setup 部分装到 `0x1000:0x0000`，把 vCPU 置于实模式并从 `0x1000:0x0200` 开始执行，同时自带一个只有几个文件的迷你 BIOS（`x86/bios/` 目录下的 `int10.c`、`int15.c`、`e820.c` 等），实现内核 setup 代码会用到的少数几个中断服务。

PVH 入口由 ELF note `XEN_ELFNOTE_PHYS32_ENTRY` 声明，需要内核开启 `CONFIG_PVH`，而该选项依赖 `CONFIG_HYPERVISOR_GUEST`。本卷的 guest 内核没有开 `CONFIG_HYPERVISOR_GUEST`（卷四 3.1 节讨论 x2APIC 时已经遇到过这个配置），所以对它来说 PVH 入口不存在，`readelf -n vmlinux` 也看不到这个 note。

mini-vmm 两条路都支持，按文件头自动识别（2.5 节），本卷大部分内容以 vmlinux 直接启动为例。它不是 `boot.rst` 里单独列出的协议，而是 64 位协议作用在未压缩内核上的特例：`arch/x86/kernel/head_64.S` 中 `startup_64` 的注释明确写着“We come here either directly from a 64bit bootloader, or from arch/x86/boot/compressed/head_64.S”。换言之，bzImage 里的解压器在完成解压后，也是按同样的约定跳到这里的。

### 2.2 64 位协议的入口约定

`Documentation/arch/x86/boot.rst` 对 64 位协议的要求只有一段话，逐条拆开是：

1. CPU 处于 64 位模式，分页开启。
2. 从内核装载起始地址开始、长度为 `setup_header.init_size` 的区间，以及 zero page 和命令行缓冲区，必须恒等映射（虚拟地址等于物理地址）。
3. GDT 中必须有选择子 `__BOOT_CS`（`0x10`）和 `__BOOT_DS`（`0x18`）两个描述符，都是 4 GiB 平坦段，前者可执行可读，后者可读写。
4. `CS` 必须是 `__BOOT_CS`，`DS`、`ES`、`SS` 必须是 `__BOOT_DS`。
5. 中断关闭。
6. `%rsi` 存放 `struct boot_params` 的基址。

mini-vmm 在 `boot_setup_linux64()` 与 `setup_long_mode_common()`（`src/boot/gdt_pgtable.c`）里逐条满足：

| 要求 | mini-vmm 的做法 |
|---|---|
| 长模式、分页开启 | `KVM_SET_SREGS` 直接给出 `CR0 = PE\|MP\|ET\|NE\|WP\|AM\|PG`、`CR4 = PAE`、`EFER = LME\|LMA`、`CR3 = 0x2000` |
| 恒等映射 | 用 2 MiB 大页恒等映射 GPA `[0, 1 GiB)`，覆盖内核、zero page、命令行和 initrd |
| GDT | 在 `0x1000` 写入 `[null, null, code64, data64]` 四项，`GDTR.limit = 31` |
| 段寄存器 | `CS` 选择子 `0x10`，其余数据段选择子 `0x18`，影子缓存按描述符内容直接填好 |
| 中断关闭 | `RFLAGS = 0x2`，`IF = 0` |
| `%rsi` | `0x7000`，即 boot_params 所在 GPA |

规范之外，Linux 真正依赖哪些东西，要看 `startup_64` 前几十条指令做了什么（`arch/x86/kernel/head_64.S:46-119`）：

```asm
SYM_CODE_START_NOALIGN(startup_64)
	mov	%rsi, %r15                    /* 保存 boot_params 物理地址 */
	leaq	(__end_init_task - PTREGS_SIZE)(%rip), %rsp
	leaq	_text(%rip), %rdi
	movl	$MSR_GS_BASE, %ecx           /* 为栈保护设 GS 基址 */
	...
	wrmsr
	call	startup_64_setup_env          /* 装自己的 GDT 和 IDT */
	pushq	$__KERNEL_CS
	leaq	.Lon_kernel_cs(%rip), %rax
	pushq	%rax
	lretq                                 /* 切到内核自己的 CS */
.Lon_kernel_cs:
	call	verify_cpu
	leaq	_text(%rip), %rdi
	movq	%r15, %rsi
	call	__startup_64                  /* 修正页表中的物理地址 */
	addq	$(early_top_pgt - __START_KERNEL_map), %rax
	jmp 1f                                /* 之后装入 CR3 并跳到高地址 */
```

`startup_64_setup_env()`（`arch/x86/kernel/head64.c:624`）第一件事就是 `native_load_gdt(&startup_gdt_descr)`，把 GDTR 换成内核镜像里自带的 `startup_gdt`，然后用 `__KERNEL_DS` 重新加载 `DS`、`SS`、`ES`，接着装入内核自己的早期 IDT。在此之前，`startup_64` 只执行了 `mov`、`lea`、`wrmsr` 和一次 `call`，没有任何段寄存器的加载。所以对 v6.6 的 vmlinux 直接启动而言，VMM 写进内存的那张 GDT 实际上从未被硬件查过，起作用的只是 KVM 中已经填好的段影子缓存。mini-vmm 仍然按协议写了这张表（`gdt_pgtable.c:369` 的注释说明了理由），这是对的：协议是契约，内核实现的某个版本恰好没用到某条要求，不代表下个版本也不用。bzImage 的解压器就是一个会用到这些选择子的实现。

恒等映射的实际需求也可以这样推出来。`__startup_64()` 返回之前，CPU 一直在以物理地址执行内核代码（`RIP` 从 `0x1000000` 开始），栈（`__end_init_task` 在内核 `.data` 段内）也按物理地址访问，所以内核镜像本身必须被恒等映射。之后内核切换到自己构造的 `early_top_pgt`，跳到 `0xffffffff81000000` 起的高地址执行。`x86_64_start_kernel()` 调用 `copy_bootdata(__va(real_mode_data))`（`head64.c:526`）时，访问的是直接映射区的虚拟地址，这时直接映射区还是空的，第一次访问会触发缺页，由 `do_early_exception()` → `early_make_pgtable()`（`head64.c:400-413`）当场补建一个 2 MiB 映射。也就是说，在本卷的 guest 配置下，boot_params 和命令行并不依赖 VMM 的恒等映射；但开启 `CONFIG_AMD_MEM_ENCRYPT` 的内核会在切换页表之前通过物理地址读取 boot_params 中的 initrd 信息（`arch/x86/mm/mem_encrypt_identity.c:331`），这就是规范要求恒等映射 zero page 的原因之一。

`__startup_64()` 里还有两个不打印任何信息的死循环，写 VMM 时值得记住（`head64.c:195-206`）：

```c
	/* Is the address too large? */
	if (physaddr >> MAX_PHYSMEM_BITS)
		for (;;);

	load_delta = physaddr - (unsigned long)(_text - __START_KERNEL_map);

	/* Is the address not 2M aligned? */
	if (load_delta & ~PMD_MASK)
		for (;;);
```

`load_delta` 是实际装载地址与链接地址之差。内核的高地址映射用 2 MiB 页，所以只能整体平移 2 MiB 的整数倍。如果 VMM 把 vmlinux 装在一个没有按 2 MiB 对齐的偏移上，vCPU 会在这里原地空转，没有任何退出、没有任何日志，从 VMM 看就是“guest 启动后卡死”。mini-vmm 严格按 `p_paddr` 装载，`load_delta = 0`，不会触发这个问题。

```text
   01     .data __bug_table .vvar
   02     .data..percpu
   03     .init.text ... .smp_locks .bss .brk
```

有三点值得注意。

**入口是物理地址。** ELF 头的 `e_entry = 0x1000000`。链接脚本 `arch/x86/kernel/vmlinux.lds.S:45` 写的是 `ENTRY(phys_startup_64)`，而第 121 行定义 `phys_startup_64 = ABSOLUTE(startup_64 - LOAD_OFFSET)`，其中 `LOAD_OFFSET = __START_KERNEL_map = 0xffffffff80000000`。所以 `e_entry` 本身就是 `startup_64` 的物理地址，等于 `CONFIG_PHYSICAL_START`（`0x1000000`）。mini-vmm 的 `elf_load_vmlinux()` 同时兼容 `e_entry` 落在虚拟地址区的情形，但对上游 x86_64 内核来说这个分支不会被走到。

**必须用 `p_paddr` 而不是 `p_vaddr` 装载。** 第 3 个段 `.data..percpu` 的虚拟地址是 0。x86_64 的 per-CPU 变量用 `%gs` 相对寻址，链接时以 0 为基址，所以这个段的 `p_vaddr` 毫无意义。一个用 `p_vaddr - 0xffffffff80000000` 推算物理地址的装载器，会在这里算出一个巨大的负数；而用 `p_paddr` 的装载器把它放在 `0x24f6000`，紧挨在 `.data` 段之后，恰好是内核期望的位置。mini-vmm 的启动日志中 `PT_LOAD #2: GPA [0x24f6000, 0x2522528)` 就是这个段。

**`MemSiz > FileSiz` 的部分要清零。** 第 4 个段文件中只有 `0x238000` 字节，内存中占 `0x50d000` 字节，多出来的是 `.bss` 和 `.brk`。`elf_load_vmlinux()` 用 `memset` 把这部分清零，这是 ELF 装载语义本身的要求。内核在 `x86_64_start_kernel()` 里也会调用 `clear_bss()`（`head64.c:428`）把 `.bss` 和 `.brk` 再清一遍，但那已经是 `startup_64`、`__startup_64()` 执行完之后的事了；装载器不应该假设这之前的代码不会碰到这些区域。

### 2.4 没有解压器意味着什么：KASLR

guest 内核开启了 `CONFIG_RANDOMIZE_BASE=y` 和 `CONFIG_RANDOMIZE_MEMORY=y`，但在 mini-vmm 里两者都不生效，原因各不相同。

**物理与虚拟地址的随机化发生在解压器里。** `arch/x86/boot/compressed/kaslr.c` 的 `choose_random_location()` 在解压之前根据 E820 内存图挑选一个随机的物理装载地址和虚拟偏移，然后把内核解压到那里。vmlinux 直接启动跳过了解压器，内核就运行在链接地址上，`__startup_64()` 算出的 `load_delta = 0`。

**内存区域的随机化看的是 `loadflags`。** `arch/x86/include/asm/setup.h:81`：

```c
static inline bool kaslr_enabled(void)
{
	return IS_ENABLED(CONFIG_RANDOMIZE_MEMORY) &&
		!!(boot_params.hdr.loadflags & KASLR_FLAG);
}
```

`KASLR_FLAG` 是 `loadflags` 的 bit 1，`boot.rst` 把它标为“kernel internal”，本意是由解压器在完成随机化后置位，告诉后面的内核“KASLR 已启用”。mini-vmm 写的 `loadflags = 0x01`，只有 `LOADED_HIGH`，于是 `kaslr_enabled()` 为假，`kernel_randomize_memory()`（`setup.c:1082`，实现在 `arch/x86/mm/kaslr.c:98`）直接返回，`page_offset_base`、`vmalloc_base`、`vmemmap_base` 都取默认值。内核 panic 时打印的 `Kernel Offset: disabled`（`setup.c:811`）也来自这个判断。

启动日志里那行没有时间戳的 `Poking KASLR using RDRAND RDTSC...` 容易让人误以为 KASLR 在工作。它来自 `poking_init()`（`arch/x86/mm/init.c:834`）：这个函数为 `text_poke()` 选择一个随机的临时映射地址，只检查 `CONFIG_RANDOMIZE_BASE`，不检查 `kaslr_enabled()`。`kaslr_get_random_long()` 在内核本体中把 `debug_putstr` 定义为 `early_printk`（`arch/x86/lib/kaslr.c`），所以这行字只经过 earlyprintk 通道输出，不进 printk 的环形缓冲区，也就没有时间戳。

对一个教学用 VMM 来说，没有 KASLR 是优点：内核符号地址固定，`System.map` 可以直接用来解读 guest 的 RIP，卷一介绍的 `KVM_GET_REGS` 调试方法因此格外好用。

### 2.5 bzImage 的装载

发行版只提供 bzImage，不提供 vmlinux。按 64 位协议装载 bzImage 需要以下步骤（与 rust-vmm `linux-loader` 的 bzImage 装载器是同一个思路，那里默认把保护模式部分装在 `code32_start`）：

1. 读取文件前 `0x300` 字节。检查 `0x1FE` 处的 `boot_flag == 0xAA55`、`0x202` 处的 `header == "HdrS"`、`version >= 0x020C`，以及 `xloadflags` 的 `XLF_KERNEL_64` 位，确认存在 64 位入口。
2. 读取 `setup_sects`（为 0 时按 4 处理）。保护模式部分从文件偏移 `(setup_sects + 1) * 512` 开始。
3. 把 `[0x1F1, 0x202 + byte[0x201])` 这段 setup header 原样复制到 boot_params 的相同偏移，其余字段清零。
4. 选择装载地址：优先 `pref_address`；如果 `relocatable_kernel` 非零，也可以选任何按 `kernel_alignment` 对齐、且其后 `init_size` 字节都是空闲 RAM 的地址。
5. 填写 loader 负责的字段：`type_of_loader`、`loadflags` 中的 `LOADED_HIGH`、`cmd_line_ptr`、`ramdisk_image/size`，以及 E820、`acpi_rsdp_addr` 等 zero page 字段。
6. 恒等映射 `[装载地址, 装载地址 + init_size)`、zero page 和命令行；`RIP = 装载地址 + 0x200`，`RSI = boot_params`。

与 guest 同源构建的 bzImage，其 setup header 的实际取值如下，可以和 mini-vmm 为 vmlinux 伪造的值对照：

| 字段 | 偏移 | bzImage 中的值 | mini-vmm 伪造的值 | 说明 |
|---|---|---|---|---|
| `setup_sects` | `0x1F1` | 31 | 0 | setup 部分共 32 个扇区即 16 KiB，保护模式部分从文件偏移 `0x4000` 开始 |
| `syssize` | `0x1F4` | `0x79c40` | 0 | 以 16 字节为单位，即 `0x79c400` 字节；`0x4000 + 0x79c400` 恰好等于文件大小 |
| `version` | `0x206` | `0x020f` | `0x020f` | 协议 2.15 |
| `loadflags` | `0x211` | `0x01` | `0x01` | `LOADED_HIGH` |
| `initrd_addr_max` | `0x22C` | `0x7fffffff` | `0x37ffffff` | mini-vmm 取的是 2.02 及更早协议的默认值，偏保守 |
| `kernel_alignment` | `0x230` | `0x200000` | `0x1000000` | 真实值是 `CONFIG_PHYSICAL_ALIGN` |
| `relocatable_kernel` | `0x234` | 1 | 0 | |
| `min_alignment` | `0x235` | 21 | 0 | 最低对齐 2 MiB |
| `xloadflags` | `0x236` | `0x7b` | 0 | `KERNEL_64`、`CAN_BE_LOADED_ABOVE_4G`、`EFI_HANDOVER_64`、`EFI_KEXEC`、`5LEVEL`、`5LEVEL_ENABLED` |
| `cmdline_size` | `0x238` | 2047 | 63 | 见 3.4 节 |
| `pref_address` | `0x258` | `0x1000000` | 0 | |
| `init_size` | `0x260` | `0x1c66000` | 0 | 解压与初始化期间需要的线性内存，约 28.4 MiB |

两者的差异无一例外都不影响 vmlinux 直接启动，原因在下一节：未压缩的内核本体几乎不读 setup header 里“由内核声明、给 loader 看”的那一类字段。

mini-vmm 按这个步骤实现了 bzImage 装载（`src/boot/bzimage.c`），并由 `src/boot/kernel_loader.c` 根据文件头自动分派：以 ELF 魔数开头的走 vmlinux 路径，`0x1FE` 处为 `0xAA55` 且 `0x202` 处为 `HdrS` 的走 bzImage 路径，两者都不是则报错。两条路径共用同一套 boot_params、E820 与 ACPI 表，vCPU 的进入状态也完全相同，差别只有两处：入口地址，以及 setup header 是伪造的还是内核自带的。bzImage 路径下 `zeropage_setup()` 把内核自带的 header 原样拷进 boot_params，只填 `type_of_loader`、`cmd_line_ptr`、`ramdisk_*` 等 loader 字段，`version`、`cmdline_size`、`initrd_addr_max` 都保留内核声明的值。启动日志的开头会多出解压器自己的输出：

```text
[INFO] bzImage: protocol 2.15, setup 16384 bytes, payload 0x79c400 bytes -> GPA 0x1000000, init_size 0x1c66000, entry 0x1000200
[INFO] kernel format: bzImage
Physical KASLR using RDRAND RDTSC...
Virtual KASLR using RDRAND RDTSC...
Decompressing Linux... Parsing ELF... Performing relocations... done.
Booting the kernel (entry_offset: 0x0000000000000000).
```

这里的输出靠 `earlyprintk=serial,ttyS0,115200` 打印出来，因为解压器同样会解析这个参数。另外两行说明物理与虚拟 KASLR 都已生效，解压器随后在 `loadflags` 里置上 `KASLR_FLAG`，于是内核本体启动后又会多出一行 `Memory KASLR using RDRAND RDTSC...`，这是 2.4 节那个 `kaslr_enabled()` 判断在这条路径下的结果。从 VMM 的角度看，bzImage 路径反而更省事：不解析 ELF，不伪造 header，解压、重定位与 KASLR 都由内核自己完成。

走 bzImage 路线还有一个隐含的差别：解压器自己会读 E820（为了挑选 KASLR 地址）和命令行（为了识别 `nokaslr`、`mem=`、`memmap=`），所以这些数据在跳到 `装载地址 + 0x200` 的那一刻就必须完整可用，而不是等到内核本体的 `copy_bootdata()`。

## 3. `struct boot_params`：4 KiB 的私有契约

### 3.1 布局总览

`struct boot_params` 定义在 `arch/x86/include/uapi/asm/bootparam.h:186`，大小正好 4096 字节。它是 uapi 头文件，用户态可以直接 `#include <asm/bootparam.h>`，mini-vmm 的 `zeropage.c` 就是这么做的，没有自己抄一份定义。下表列出与 VMM 相关的字段，省略了 APM、IST、EDD、OLPC 等只有真实 BIOS 或特定平台才会填写的部分：

|---|---|---|---|---|
| `0x000` | 64 | `screen_info` | 文本模式或帧缓冲信息 | 全 0 |
| `0x070` | 8 | `acpi_rsdp_addr` | RSDP 的物理地址 | `0xe0000` |
| `0x0c0` | 4 | `ext_ramdisk_image` | `ramdisk_image` 的高 32 位 | 0 |
| `0x0c4` | 4 | `ext_ramdisk_size` | `ramdisk_size` 的高 32 位 | 0 |
| `0x0c8` | 4 | `ext_cmd_line_ptr` | `cmd_line_ptr` 的高 32 位 | 0 |
| `0x13c` | 4 | `cc_blob_address` | 机密计算（SEV-SNP）信息块地址 | 0 |
| `0x1c0` | 32 | `efi_info` | EFI 系统表、内存图的地址与签名 | 全 0 |
| `0x1e0` | 4 | `alt_mem_k` | `INT 15h, AX=E801h` 报告的内存大小（KiB） | 0 |
| `0x1e8` | 1 | `e820_entries` | `e820_table` 中的有效项数 | 3 |
| `0x1ef` | 1 | `sentinel` | 检测不守规矩的 bootloader，见 3.2 节 | 0 |
| `0x1f1` | 123 | `hdr` | setup header，见 3.3 节 | 见下 |
| `0x2d0` | 2560 | `e820_table[128]` | E820 内存图，每项 20 字节 | 3 项 |

`acpi_rsdp_addr` 的历史值得一提。它最初在 2018 年被加进 setup header，对应协议版本 2.14；很快人们意识到 setup header 应该只包含传统 BIOS 引导路径会用到的字段，于是在同年 11 月的 x86/urgent 分支里把它撤出 setup header，改放到 boot_params 的 `0x070` 偏移处，并且在 `boot.rst` 里把 2.14 标记为“BURNT BY INCORRECT COMMIT, DO NOT USE”。mini-vmm 最初在 `zeropage.c` 的注释里写的是“协议 2.14 起内核直接从这里拿 RSDP”，严格说并不准确：这个字段不属于任何协议版本，它是 boot_params 的普通字段，一个支持它的内核无论 `hdr.version` 是多少都会去读。这条注释已经随本卷的核对修正。

下面是 mini-vmm 构造的 boot_params 中非零区域的实际字节（`0x7000` 是 boot_params 所在 GPA，左列地址为 GPA）：

### 3.2 sentinel 与“先清零、再复制”规则

`boot.rst` 对 32/64 位协议的第一条要求是：boot_params 必须先整体清零，然后只把 setup header 复制进来并按需修改，其余字段按 `zero-page.rst` 填写。这条规则针对的是一类常见的 bootloader bug：把 bzImage 开头的整个扇区当成 boot_params 复制过去，结果把 setup 代码里的随机字节带进了本应为零的字段。

内核用 `sentinel` 字段（偏移 `0x1ef`）检测这种情况。bzImage 的 `arch/x86/boot/header.S` 在这个位置放了 `0xff`；遵守规则的 bootloader 只复制 `0x1f1` 之后的 setup header，`sentinel` 会保持为 0；如果它非零，说明 bootloader 把 setup header 之前的字节也一起复制了。`copy_bootdata()` 在复制完 boot_params 后立即调用 `sanitize_boot_params()`（`arch/x86/include/asm/bootparam_utils.h`），在 `sentinel` 非零时只保留一张白名单里的字段，其余全部清零。白名单包括 `screen_info`、`apm_bios_info`、`efi_info`、`e820_entries`、`e820_table`、`hdr` 等 20 项，源码注释说它来自对 kexec-tools 行为的分析。**白名单不包括 `acpi_rsdp_addr`、`ext_ramdisk_image`、`ext_ramdisk_size`、`ext_cmd_line_ptr`**：一旦 `sentinel` 非零，内核无法判断这些较新的字段是 loader 有意填写的，还是随 setup 代码一起被误复制过来的垃圾，于是一律清零。

mini-vmm 的 `zeropage_setup()` 在填写任何字段之前先 `memset(bp, 0, sizeof(*bp))`（`zeropage.c:98`），`sentinel` 为 0，不会触发清理。即使将来某个改动意外把 `sentinel` 写成了非零，mini-vmm 也有第二道保险：ACPI 表放在 `0xE0000`，恰好在 ACPICA 的传统扫描区间内（见 6.3 节），`acpi_rsdp_addr` 被清零后内核仍然能靠扫描找到 RSDP。

### 3.3 setup header：字段的方向

setup header 的每个字段在 `boot.rst` 里都标有类型，表示信息的流向：

| 类型 | 含义 | 例子 |
|---|---|---|
| read | 内核声明、loader 读取 | `version`、`initrd_addr_max`、`kernel_alignment`、`xloadflags`、`cmdline_size`、`init_size`、`pref_address` |
| write | loader 填写、内核读取 | `type_of_loader`、`cmd_line_ptr`、`ramdisk_image`、`ramdisk_size`、`setup_data`、`hardware_subarch` |
| modify | 内核给默认值、loader 可以改 | `loadflags`、`code32_start`、`vid_mode` |

bzImage 自带一份填好了 read 类字段的 setup header，loader 读完再往里写 write 类字段。vmlinux 没有 setup header，mini-vmm 只能凭空构造一份。那么内核本体究竟会读其中的哪些字段？在 guest 的源码树里搜索 `boot_params.hdr.` 的所有读取点（排除 `arch/x86/boot/` 下的解压器与实模式代码），结果如下：

| 字段 | 读取位置 | 作用 |
|---|---|---|
| `version` | `head64.c:542` | `x86_64_start_reservations()` 用它判断 boot_params 是否已经复制过：“version is always not zero if it is copied”；另外通过 `/sys/kernel/boot_params/version` 导出 |
| `type_of_loader` | `setup.c:290`、`setup.c:304`、`setup.c:905` | **为 0 时 initrd 被忽略**；导出为 `/proc/sys/kernel/bootloader_type` |
| `loadflags` | `setup.h:83` | 只看 `KASLR_FLAG`，见 2.4 节 |
| `ramdisk_image`、`ramdisk_size` | `setup.c:235`、`setup.c:246`；`cpu/microcode/core.c:213` | initrd 的位置与大小；早期微码加载器也会在 initrd 里找微码 |
| `cmd_line_ptr` | `head64.c:438` | 命令行地址，与 `ext_cmd_line_ptr` 拼成 64 位 |
| `hardware_subarch` | `head64.c:547`、`platform-quirks.c:17` | 平台类型，0 表示普通 PC |
| `setup_data` | `setup.c:390`、`setup.c:436`、`e820.c:1002`、`ksysfs.c`、`kdebugfs.c` | 扩展数据链表，见 3.5 节 |
| `root_dev`、`vid_mode`、`root_flags` | `setup.c:897`、`setup.c:904`、`setup.c:949` | 远古的根设备号、显示模式、根文件系统只读标志 |

没有出现在表里的字段，内核本体一概不读：`boot_flag`、`header`、`kernel_alignment`、`initrd_addr_max`、`cmdline_size`、`setup_sects`、`syssize`、`pref_address`、`init_size`、`xloadflags`（`CONFIG_AMD_MEM_ENCRYPT` 路径除外）。mini-vmm 写进去的 `boot_flag = 0xAA55`、`header = "HdrS"`、`kernel_alignment`、`initrd_addr_max` 对启动没有任何影响，它们的作用是让这份 boot_params 在形式上像一份合法的 boot_params，方便用 `/sys/kernel/boot_params/data` 导出后用工具检查。

表中最容易踩坑的是 `type_of_loader`。`early_reserve_initrd()` 与 `reserve_initrd()` 开头都有同样的判断（`setup.c:290-292`）：

```c
	if (!boot_params.hdr.type_of_loader ||
	    !ramdisk_image || !ramdisk_size)
		return;		/* No initrd provided by bootloader */
```

一个 VMM 如果只填了 `ramdisk_image` 和 `ramdisk_size`，却忘了 `type_of_loader`，内核不会报任何错误，只是既不保留也不使用这块 initrd；随后内核找不到根文件系统，panic 信息是 `VFS: Unable to mount root fs`，很难联想到是 boot_params 里一个字节的问题。协议规定没有注册 ID 的 loader 填 `0xFF`，mini-vmm 正是这么做的（`zeropage.c:125`）。几个常见的注册 ID：`0x7` GRUB、`0x9` Xen、`0xB` QEMU、`0xD` kexec-tools，写入时放在高 4 位，低 4 位是版本号。内核的 PVH 入口在把 `hvm_start_info` 转换成 boot_params 时，对非 Xen 的宿主写的是 `0xB0`（`arch/x86/platform/pvh/enlighten.c:95`），也就是冒用了 QEMU 的 ID。

### 3.4 命令行

内核命令行通过 `cmd_line_ptr`（低 32 位）与 `ext_cmd_line_ptr`（高 32 位）传递。`copy_bootdata()` 的处理只有两行（`head64.c:458-462`）：

```c
	cmd_line_ptr = get_cmd_line_ptr();
	if (cmd_line_ptr) {
		command_line = __va(cmd_line_ptr);
		memcpy(boot_command_line, command_line, COMMAND_LINE_SIZE);
	}
```

这里有两个值得 VMM 作者注意的细节。

**它无条件复制 `COMMAND_LINE_SIZE` 个字节。** x86 的 `COMMAND_LINE_SIZE` 是 2048（`arch/x86/include/asm/setup.h:7`）。不管命令行实际多长，内核都会从 `cmd_line_ptr` 开始读 2048 字节，所以命令行缓冲区之后至少要有 2 KiB 可读的 guest 内存。mini-vmm 把命令行放在 `0x20000`，后面是大片 RAM，没有问题；如果有人把命令行放在某个 RAM 区间的最后几十个字节，这次复制就会越界读到 MMIO 空洞或者未映射的地址。

**超过 2047 个字符的部分被静默截断。** `boot_command_line` 的大小就是 2048，`setup_arch()` 随后用 `strscpy(command_line, boot_command_line, COMMAND_LINE_SIZE)`（`setup.c:975`）复制一份供解析，`strscpy` 保证结尾有 NUL，所以有效长度最多 2047。bzImage 在 setup header 里用 `cmdline_size = 2047` 把这个上限告诉 loader，这是一个 read 类字段。mini-vmm 最初有两处和规范不一致的地方，都已随本卷的核对修正：

- `ZP_CMDLINE_MAX` 原先定义为 4096，`zeropage_setup()` 允许写入最长 4095 字节的命令行。长度在 2048 到 4095 之间的命令行能通过 VMM 的检查，但第 2047 个字符之后的内容会被 guest 静默丢弃。现在上限是 2048（`include/boot/zeropage.h`），超长时报错；bzImage 路径还会额外检查内核自己声明的 `cmdline_size`。
- `zeropage_setup()` 原先把 `cmdline_size` 写成实际长度。这个字段的方向是“内核告诉 loader 上限”，loader 写它没有意义；由于内核本体不读它，所以不会造成问题，只是会让检查 `/sys/kernel/boot_params/data` 的人困惑。现在 vmlinux 路径不再写它，bzImage 路径保留内核声明的值。

命令行的解析分两个阶段。`setup_arch()` 在第 879 行打印 `Command line: ...`，在第 985 行调用 `parse_early_param()`，处理所有用 `early_param()` 注册的参数，例如 `earlyprintk`、`acpi`、`mem`、`memmap`、`noapic`、`apic`。这一步必须早，因为这些参数会影响后面的内存与 ACPI 初始化。回到 `start_kernel()` 之后，`init/main.c:911` 的 `parse_args("Booting kernel", ...)` 处理其余的 `__setup()` 参数和内置模块参数，打印 `Kernel command line: ...`；内核不认识的参数会作为命令行参数或环境变量传给 init 进程。

mini-vmm 默认命令行 `console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1` 中的每一项都和 VMM 的设备模型有直接关系：

| 参数 | 由谁解析 | 行为 | 对 VMM 的要求 |
|---|---|---|---|
| `earlyprintk=serial,ttyS0,115200` | `arch/x86/kernel/early_printk.c` 的 `early_serial_init()` | 端口取 `0x3f8`，除数为 `115200 / 115200 = 1`；依次写 LCR、IER、FCR、MCR 与除数锁存器，之后每个字符都轮询 LSR 的 bit 5（`XMTRDY`），最多轮询 `0xffff` 次 | 串口模型的 LSR 必须报告 THRE = 1，否则每输出一个字符都要空转 65535 次 PIO 退出 |
| `console=ttyS0` | 8250 驱动注册 console 时匹配 | 串口驱动接管后 earlyprintk 的 bootconsole 被注销，日志中的 `bootconsole [earlyser0] disabled` 就是这一刻 | 8250 模型要能通过驱动的探测（卷七） |
| `reboot=k` | `kernel/reboot.c:1049` | `reboot_type = BOOT_KBD`；重启时 `native_machine_emergency_restart()` 先往 BDA 的 `0x472` 写热重启标志，然后向 `0x64` 端口写 10 次 `0xFE`，即让 8042 键盘控制器拉低 CPU 的复位线 | i8042 模型收到 `0xFE` 命令时让 VMM 退出 |
| `panic=-1` | `kernel/panic.c` | `panic_timeout` 为负值时不等待，panic 后立即调用 `emergency_restart()` | 同上，panic 最终也走 `0x64` 端口退出 |

默认情况下（不写 `reboot=`），x86 的 `reboot_type` 是 `BOOT_ACPI`（`kernel/reboot.c:48`），重启流程会先调用 `acpi_reboot()`，而它要求 FADT 版本不低于 2 且 `Flags` 中设置了 `RESET_REG_SUP`（`drivers/acpi/reboot.c` 中的 `ACPI_FADT_RESET_REGISTER` 检查）。mini-vmm 的 FADT 没有提供复位寄存器，`acpi_reboot()` 什么也不做就返回，流程随后退到 `BOOT_KBD`（`arch/x86/kernel/reboot.c:655-658`）。所以即使去掉 `reboot=k`，最终也还是走键盘控制器；显式写上它只是省掉一次无效的尝试，也让行为一目了然。

### 3.5 setup_data：可扩展的链表

`hdr.setup_data` 是一个 64 位物理地址，指向一个单向链表，每个节点的格式是：

```c
struct setup_data {
	__u64 next;      /* 下一个节点的物理地址，0 表示结束 */
	__u32 type;
	__u32 len;       /* data 的长度，不含本头部 */
	__u8  data[];
};
```

`type` 的取值定义在 `arch/x86/include/uapi/asm/bootparam.h:6-19`。内核本体在 `parse_setup_data()`（`setup.c:385`）里处理的类型有：

| 类型 | 值 | 用途 | VMM 何时需要 |
|---|---|---|---|
| `SETUP_E820_EXT` | 1 | 追加 E820 表项 | boot_params 内的 128 项放不下时 |
| `SETUP_DTB` | 2 | 设备树 blob | 用设备树描述平台时（x86 上罕见） |
| `SETUP_EFI` | 4 | kexec 传递 EFI 运行时信息 | 无 |
| `SETUP_IMA` | 8 | IMA 度量日志 | 无 |
| `SETUP_RNG_SEED` | 9 | 随机数种子，内核读取后立即把数据和长度清零 | 想让 guest 在没有 RDRAND 的 CPU 上也能早期获得熵时 |
| `SETUP_INDIRECT` | `1 << 31` | 与其他类型按位或，表示数据不紧跟在头部之后，而是由 `struct setup_indirect` 间接指向 | 数据很大时 |

链表节点所在的内存会被 `memblock_x86_reserve_range_setup_data()`（`setup.c:429`）在最早期保留，并由 `e820__reserve_setup_data()`（`setup.c:1025`）在 E820 中标为 `E820_TYPE_RESERVED_KERN`，所以 VMM 可以把它们放在任意 RAM 中，不必额外在 E820 里挖洞。

mini-vmm 目前不使用 setup_data。guest 的 CPUID 暴露了 RDRAND，启动日志里 `random: crng init done` 出现在第 0.075 秒，熵不是问题。

## 4. E820：一张由 VMM 说了算的内存图

### 4.1 来历与格式

E820 这个名字来自 BIOS 调用的功能号：在实模式下执行 `INT 15h`，`EAX = 0xE820`，`EDX = 0x534D4150`（ASCII `SMAP`），`ES:DI` 指向缓冲区，`EBX` 作为续传标记，每次调用返回一个描述符，直到 `EBX` 返回 0。每个描述符最初是 20 字节：64 位起始地址、64 位长度、32 位类型。ACPI 3.0 给它加了 4 字节的扩展属性，但 Linux 只使用前 20 字节。

在传统 BIOS 引导路径上，内核自己的实模式 setup 代码（`arch/x86/boot/memory.c`）会调用这个 BIOS 服务，把结果放进 `boot_params.e820_table`。在 VMM 直接启动的路径上没有 BIOS，也不执行 setup 代码，VMM 直接把表写进 boot_params 即可。内核中对应的结构是：

```c
struct boot_e820_entry {
	__u64 addr;
	__u64 size;
	__u32 type;
} __attribute__((packed));
```

`e820__memory_setup()` 里有一行 `BUILD_BUG_ON(sizeof(struct boot_e820_entry) != 20)`（`arch/x86/kernel/e820.c:1304`），注释写着“This is a firmware interface ABI - make sure we don't break it”。boot_params 里最多容纳 `E820_MAX_ENTRIES_ZEROPAGE = 128` 项，更多的表项要通过 setup_data 的 `SETUP_E820_EXT` 追加。

内核认识的类型定义在 `arch/x86/include/asm/e820/types.h`：

| 类型 | 值 | 日志中的名称 | 含义 |
|---|---|---|---|
| `E820_TYPE_RAM` | 1 | `usable` | 普通内存，OS 可以随意使用 |
| `E820_TYPE_RESERVED` | 2 | `reserved` | 保留，OS 不得使用 |
| `E820_TYPE_ACPI` | 3 | `ACPI data` | 存放 ACPI 表，OS 读完后可以回收 |
| `E820_TYPE_NVS` | 4 | `ACPI NVS` | 固件在睡眠唤醒时要用的内存，OS 必须保留 |
| `E820_TYPE_UNUSABLE` | 5 | `unusable` | 检测出错误的内存 |
| `E820_TYPE_PMEM` | 7 | `persistent (type 7)` | 持久内存 |
| `E820_TYPE_PRAM` | 12 | `persistent (type 12)` | 非标准的持久内存表示 |
| `E820_TYPE_RESERVED_KERN` | 128 | `usable` | 内核内部使用：被 setup_data 等占用的 RAM |
| `E820_TYPE_SOFT_RESERVED` | `0xefffffff` | `soft reserved` | 由 EFI 的 `EFI_MEMORY_SP` 属性转换而来 |

### 4.2 内核的处理流水线

E820 表从 boot_params 进入内核之后，要经过一系列修改才会变成 memblock 分配器可以使用的内存。按执行顺序：

**第一步，复制与清洗。** `e820__memory_setup()`（`e820.c:1299`）调用 `x86_init.resources.memory_setup`，默认是 `e820__memory_setup_default()`（`e820.c:1261`）。它先调用 `append_e820_table()`，这个函数的第一行就是一个陷阱（`e820.c:453-459`）：

```c
static int __init append_e820_table(struct boot_e820_entry *entries, u32 nr_entries)
{
	/* Only one memory region (or negative)? Ignore it */
	if (nr_entries < 2)
		return -1;

	return __append_e820_table(entries, nr_entries);
}
```

**只有一项的 E820 表会被整个丢弃。** 这时内核退回到更古老的 `alt_mem_k`（E801）和 `screen_info.ext_mem_k`（`INT 15h, AH=88h`）两个字段，伪造一张 `[0, 0x9f000)` 加 `[1 MiB, 1 MiB + mem_size)` 的表，日志里的来源也从 `BIOS-e820` 变成 `BIOS-e801` 或 `BIOS-88`。VMM 通常不填这两个字段，`mem_size` 为 0，内核就只剩下 636 KiB 可用内存，而内核镜像本身在 16 MiB 处，接下来 `e820_add_kernel_range()` 会报 `.text .data .bss are not marked as E820_TYPE_RAM!` 并把内核所占的范围强行补成 RAM，但可分配内存几乎为零，启动很快就会失败。一个“只报一整块 RAM”的偷懒 VMM 会一头撞上这条规则，这也是 mini-vmm 至少要报三项的原因之一。

表被接受后，`e820__update_table()`（`e820.c:322`）对它做一次清洗：把所有表项的起止点排序，逐段扫描；如果某一段同时被多个表项覆盖，**取类型值最大的那个**（`e820.c:391-393` 中的 `if (overlap_list[i]->type > current_type)`）；相邻且类型相同的段合并。“类型值大者胜”意味着 RAM（1）与保留（2）重叠时，重叠部分按保留处理，这是一个偏安全的选择。清洗后的表以 `BIOS-e820:` 为前缀打印出来，也就是启动日志里的这三行：

```text
BIOS-e820: [mem 0x0000000000000000-0x000000000009fbff] usable
BIOS-e820: [mem 0x000000000009fc00-0x00000000000fffff] reserved
BIOS-e820: [mem 0x0000000000100000-0x000000001fffffff] usable
```

同一时刻，这份表还被复制成 `e820_table_firmware` 和 `e820_table_kexec` 两份。前者之后不再修改，通过 `/sys/firmware/memmap` 导出（`CONFIG_FIRMWARE_MEMMAP=y`），是在 guest 里核对“VMM 到底传了什么”的最佳入口。

**第二步，最早期的 memblock 保留。** `early_reserve_memory()`（`setup.c:767`）在 E820 被解析之前就执行，它按物理地址直接做几件事：保留内核镜像本身；无条件保留物理地址 `[0, 64 KiB)`（`setup.c:788`，注释说有些 BIOS 会踩坏低端内存，而且第 0 页在有 L1TF 漏洞的 CPU 上可能被泄露给用户态）；保留 initrd 与 setup_data；调用 `reserve_bios_regions()`。

`reserve_bios_regions()`（`arch/x86/kernel/ebda.c`）试图从 BIOS 数据区（BDA）推算出 EBDA 的起点：`0x413` 处的字是以 KiB 为单位的基本内存大小，`0x40E` 处的字是 EBDA 的段地址。在 VMM 里这两处都是 0，函数的合理性检查会把起点修正为 `BIOS_START_MAX = 0x9f000`，然后保留 `[0x9f000, 1 MiB)`。这个行为只在 `x86_platform.legacy.reserve_bios_regions` 为真时发生，而 `x86_early_init_platform_quirks()` 只在 `hardware_subarch == X86_SUBARCH_PC` 时设置它。

**第三步，修剪低端区域。** `trim_bios_range()`（`setup.c:722`）把 E820 中第 0 页从 RAM 改为保留，再把 `[0xA0000, 1 MiB)` 范围内标为 RAM 的部分删除（有些 BIOS 会把这段错报成 RAM）。

**第四步，交给 memblock。** `e820__memblock_setup()`（`e820.c:1315`）把类型为 RAM 和 `RESERVED_KERN` 的表项加入 `memblock.memory`，其他类型一概不加；最后调用 `memblock_trim_memory(PAGE_SIZE)`，把不是整页的头尾切掉。mini-vmm 的第一项结束于 `0x9fc00`，不是 4 KiB 对齐的，于是被截到 `0x9f000`。

**第五步，实模式跳板。** `x86_platform.realmode_reserve()` 即 `reserve_real_mode()`（`arch/x86/realmode/init.c:46`）在 1 MiB 以下分配一块内存放置实模式跳板代码，然后无条件保留整个第一个 1 MiB（`realmode/init.c:67`）。这块跳板是 AP 启动时执行的第一段代码：BSP 发送的 SIPI 只能携带一个 8 位的向量，AP 从物理地址 `向量 × 4 KiB` 处以实模式开始执行，所以跳板必须在 1 MiB 以下（卷六会详细讨论这个过程）。如果 1 MiB 以下没有任何可用 RAM，这里只打印一行 `No sub-1M memory is available for the trampoline`，真正的失败在稍后的 `init_real_mode()` 中以 `panic("Real mode trampoline was not allocated")` 的形式出现（`realmode/init.c:209`）。`zeropage.c:156-158` 的注释说“完全不给低端内存的话会 panic”，指的就是这里。

把这五步合起来，就能精确解释 mini-vmm 启动日志中的内存数字：

```text
Zone ranges:
  DMA      [mem 0x0000000000001000-0x0000000000ffffff]
  DMA32    [mem 0x0000000001000000-0x000000001fffffff]
Early memory node ranges
  node   0: [mem 0x0000000000001000-0x000000000009efff]
  node   0: [mem 0x0000000000100000-0x000000001fffffff]
On node 0, zone DMA: 1 pages in unavailable ranges
On node 0, zone DMA: 97 pages in unavailable ranges
Memory: 485368K/523896K available (...)
```

- 节点的第一个区间从 `0x1000` 开始：第 0 页已被 `trim_bios_range()` 改为保留，不在 `memblock.memory` 中。
- 第一个区间结束于 `0x9efff`：`0x9fc00` 被 `memblock_trim_memory()` 截到了页边界。
- `1 pages in unavailable ranges` 是第 0 页；`97 pages` 是 `[0x9f000, 0x100000)`，恰好 `0x61000 / 0x1000 = 97` 页。
- `523896K` 是 memblock 中全部内存：`(0x9f000 - 0x1000) + (0x20000000 - 0x100000) = 0x1ff9e000` 字节，除以 1024 正好是 523896。
- `485368K available` 是扣除内核镜像、initrd、页表、第一个 1 MiB 等已保留部分后剩下的。

**第六步，发布给 PCI 与 `/proc/iomem`。** `setup_arch()` 末尾的 `e820__reserve_resources()`（`setup.c:1284`）把每个表项注册为 `iomem_resource` 下的资源，`/proc/iomem` 中的 `System RAM`、`Reserved` 就来自这里。`e820__setup_pci_gap()`（`setup.c:1289`）在 4 GiB 以下找最大的空隙，作为 PCI 设备 MMIO 窗口的候选，日志中的 `[mem 0x20000000-0xffffffff] available for PCI devices` 说明内核认为从 RAM 末端到 4 GiB 之间全都可以分配给 PCI BAR。这个区间当然包括 `0xFEC00000` 的 IOAPIC 与 `0xFEE00000` 的 LAPIC。IOAPIC 的 MMIO 区间由 `ioapic_insert_resources()` 登记到 `/proc/iomem`，但它的调用者是 PCI 的资源普查 `pcibios_resource_survey()`（`arch/x86/pci/i386.c:408`）；mini-vmm 目前没有 PCI，这一步不会发生，在 guest 里 `cat /proc/iomem` 只能看到 `System RAM`、`Reserved`、`System ROM` 和内核镜像的几段。将来加入 PCI 时，BAR 分配器依靠这些资源登记避开 IOAPIC 与 LAPIC，所以 E820 与 DSDT 中 PCI 窗口的划分都要让出这两段地址。

### 4.3 mini-vmm 的三项及其理由

有了上面的流水线，mini-vmm 这三项的每一个边界都能说出理由：

| 表项 | 范围 | 类型 | 理由 |
|---|---|---|---|
| 1 | `[0, 0x9fc00)` | RAM | 给实模式跳板留出 1 MiB 以下的 RAM；GDT、页表、boot_params、命令行也在这里，内核复制完之后可以回收 |
| 2 | `[0x9fc00, 0x100000)` | 保留 | 覆盖传统的 EBDA（最后 1 KiB 的基本内存）、VGA 显存窗口 `0xA0000`–`0xBFFFF`、选项 ROM 区和 BIOS 区；MP 表在 `0x9fc00`，ACPI 表在 `0xE0000`，都落在这一项里 |
| 3 | `[0x100000, ram_size)` | RAM | 常规内存，内核、initrd 都在这里 |

几点补充说明。

第一项结束在 `0x9fc00` 而不是 `0xa0000`，是沿用 PC 的惯例：BIOS 在基本内存的最后 1 KiB 放 EBDA，并通过 BDA 的 `0x413` 报告 639 KiB 的基本内存。mini-vmm 在这 1 KiB 里放 MP 表，而 Linux 恰好会扫描 `[639 KiB, 640 KiB)` 这个区间（见 5.2 节），两件事对上了。

ACPI 表所在区间报成了保留（类型 2），而不是 ACPI data（类型 3）。两者对 Linux 来说效果相同：类型 3 的内存也不会被加入 `memblock.memory`（第四步只加入 RAM 和 `RESERVED_KERN`），Linux 并不回收 ACPI 表占用的内存。在真实固件里，类型 3 的意义是告诉 OS“读完这些表之后这块内存就归你了”，而 Linux 在运行期间一直需要访问 ACPI 表，从来没有利用这个许可。

mini-vmm 目前拒绝大于 3 GiB 的内存（`zeropage.c:90-93`）。原因是它只有一个从 GPA 0 开始的 memslot，内存一旦超过 3 GiB，就会和 `0xFEC00000`、`0xFEE00000` 等 32 位 MMIO 地址重叠。支持大内存的标准做法是：

- memslot 拆成两块：`[0, 3 GiB)` 与 `[4 GiB, 4 GiB + (ram_size - 3 GiB))`，中间 1 GiB 留给 MMIO。
- E820 相应地报成 `[1 MiB, 3 GiB)` 与 `[4 GiB, ...)` 两段 RAM，中间的空洞不写，或者把其中确知有设备的区间标为保留。
- 空洞中放 IOAPIC、LAPIC、HPET 以及将来 PCI 的 32 位 MMIO 窗口。

这里有一条硬约束：**E820 报告为 RAM 的每一个字节，都必须有 KVM memslot 在背后支撑。** 如果 E820 说某段是 RAM，而 KVM 中没有对应的 memslot，guest 对它的每一次访问都会以 `KVM_EXIT_MMIO` 的形式退出到 VMM，内核把它当内存用时会产生海量退出，VMM 若把这类退出当作非法访问处理，guest 则会直接崩溃。反过来，memslot 覆盖了而 E820 没有报告的内存只是浪费，不会出错。

## 5. MP 配置表：Intel MultiProcessor Specification 1.4

### 5.1 为什么还要写 MP 表

Intel MultiProcessor Specification（下称 MPS）是 ACPI 普及之前描述 x86 多处理器系统的标准，最后一个版本是 1997 年的 1.4。它只描述三件事：有哪些处理器、有哪些总线和 IOAPIC、每条中断线接在哪里。ACPI 2.0 之后，这些信息由 MADT 承担，现代固件多半已经不再提供 MP 表。

mini-vmm 同时提供 MP 表和 ACPI 表，理由写在 `include/boot/acpi.h` 的注释里：开了 `CONFIG_X86_MPPARSE` 的内核能用 MP 表，开了 `CONFIG_ACPI` 的内核用 MADT，两者都开时 Linux 优先 ACPI。`include/boot/mptable.h` 的注释则说明了它最初要解决的问题：既没有 MADT 也没有 MP 表时，Linux 只能进入“virtual wire mode with no configuration”，不知道 IOAPIC 在哪、ISA 中断怎么接，PIT 中断送不到 LAPIC，定时器校准会一直等下去。MP 表的格式比 ACPI 简单一个数量级，kvmtool 和 Firecracker 都生成它。在同时提供 MADT 的今天，它仍然有两个用处：一是作为 `acpi=off` 时的后备，二是作为验证 VMM 中断拓扑的一个独立参照，见 5.6 节。

MPS 的数据分两层：一个 16 字节的**浮动指针结构**（MP Floating Pointer Structure），放在 OS 会去扫描的位置；它指向一张可变长的**配置表**（MP Configuration Table），由 44 字节的表头和若干条目组成。mini-vmm 把两者紧挨着放在 `0x9fc00` 开始的 1 KiB 里（`include/boot/mptable.h`）。

### 5.2 浮动指针结构与扫描

浮动指针结构的布局：

| 偏移 | 大小 | 字段 | 含义 | mini-vmm 的值 |
|---|---|---|---|---|
| 0 | 4 | signature | ASCII `_MP_` | `5f 4d 50 5f` |
| 4 | 4 | physptr | 配置表的物理地址；0 表示使用默认配置 | `0x0009fc10` |
| 8 | 1 | length | 本结构长度，以 16 字节为单位，固定为 1 | 1 |
| 9 | 1 | spec_rev | 规范版本，1 表示 1.1，4 表示 1.4 | 4 |
| 10 | 1 | checksum | 使 16 个字节之和模 256 为 0 | `0x8b` |
| 11 | 1 | feature1 | 0 表示存在配置表；1–7 表示使用规范定义的默认配置之一 | 0 |
| 12 | 1 | feature2 | bit 7 为 IMCRP：置 1 表示系统处于 PIC 模式并实现了 IMCR | 0 |
| 13 | 3 | feature3–5 | 保留 | 0 |

对应的实际字节：

```text
9fc00: 5f 4d 50 5f 10 fc 09 00 01 04 8b 00 00 00 00 00
       └─ "_MP_" ─┘ └ physptr ┘ len rev sum f1 f2 ...
```

MPS 规定 OS 按以下顺序在三个区间里找它：EBDA 的前 1 KiB；如果没有 EBDA，则找基本内存的最后 1 KiB；然后是 BIOS ROM 区 `0xF0000`–`0xFFFFF`。Linux 的实现是 `default_find_smp_config()`（`arch/x86/kernel/mpparse.c:590`），顺序略有不同：

```c
	if (smp_scan_config(0x0, 0x400) ||
	    smp_scan_config(639 * 0x400, 0x400) ||
	    smp_scan_config(0xF0000, 0x10000))
		return;
	...
	address = get_bios_ebda();
	if (address)
		smp_scan_config(address, 0x400);
```

它先扫物理地址 `[0, 1 KiB)`（源码注释自己也写着 FIXME），再扫 `[639 KiB, 640 KiB)`，再扫 BIOS ROM 区，最后才根据 BDA 中 `0x40E` 处的段地址去扫 EBDA。在 mini-vmm 里 BDA 全为 0，最后一步不会发生，结构在第二步就被找到。加上 `apic=verbose` 启动时，日志会把扫描过程打印出来：

```text
Scan for SMP in [mem 0x00000000-0x000003ff]
Scan for SMP in [mem 0x0009fc00-0x0009ffff]
found SMP MP-table at [mem 0x0009fc00-0x0009fc0f]
  mpc: 9fc10-9fd2c
```

`smp_scan_config()`（`mpparse.c:546`）逐 16 字节比较，接受一个候选的条件是四项同时成立：签名为 `_MP_`、`length == 1`、16 字节校验和为 0、`spec_rev` 为 1 或 4。找到之后它设置 `smp_found_config = 1`，并用 `memblock_reserve()` 保留浮动指针结构本身，以及 `physptr` 指向的整张配置表（长度从配置表头读出）。这一步发生在 `setup_arch()` 的第 1103 行，远早于 ACPI 的解析，所以无论最终是否使用 MP 表，它都会被找到并保留。

### 5.3 配置表头

配置表头 44 字节：

| 偏移 | 大小 | 字段 | 含义 | mini-vmm 的值 |
|---|---|---|---|---|
| 0 | 4 | signature | ASCII `PCMP` | `PCMP` |
| 4 | 2 | base_table_length | 表头加全部基本条目的字节数 | `0x011c`（284） |
| 6 | 1 | spec_rev | 规范版本 | 4 |
| 7 | 1 | checksum | 使 `base_table_length` 个字节之和为 0 | `0x3d` |
| 8 | 8 | oem_id | OEM 标识，空格填充 | `MINIVMM ` |
| 16 | 12 | product_id | 产品标识 | `000000000000` |
| 28 | 4 | oem_table_ptr | 可选的 OEM 表地址 | 0 |
| 32 | 2 | oem_table_size | OEM 表大小 | 0 |
| 34 | 2 | entry_count | 基本条目数 | 24 |
| 36 | 4 | lapic_address | LAPIC 的物理地址 | `0xfee00000` |
| 40 | 2 | ext_table_length | 扩展条目的总长度 | 0 |
| 42 | 1 | ext_table_checksum | 扩展条目的校验和 | 0 |
| 43 | 1 | reserved | | 0 |

```text
9fc10: 50 43 4d 50 1c 01 04 3d 4d 49 4e 49 56 4d 4d 20   "PCMP" len=0x11c rev=4 sum=0x3d "MINIVMM "
9fc20: 30 30 30 30 30 30 30 30 30 30 30 30 00 00 00 00   "000000000000" oem_ptr=0
9fc30: 00 00 18 00 00 00 e0 fe 00 00 00 00 ...           oem_size=0 count=24 lapic=0xfee00000
```

mini-vmm 的结构体（`src/boot/mptable.c` 中的 `struct mpc_table`）把最后 4 个字节合并成了一个 `uint32_t reserved`，Linux 的 `struct mpc_table`（`arch/x86/include/asm/mpspec_def.h`）也是这么做的；由于 mini-vmm 不生成扩展条目，这样合并没有问题。

Linux 用 `smp_check_mpc()`（`mpparse.c:139`）检查表头，四种失败各有一条错误信息：

| 检查 | 失败时的信息 |
|---|---|
| 签名为 `PCMP` | `MPTABLE: bad signature [xxxx]!` |
| `base_table_length` 字节的校验和为 0 | `MPTABLE: checksum error!` |
| `spec_rev` 为 1 或 4 | `MPTABLE: bad table version (%d)!!` |
| `lapic_address` 非零 | `MPTABLE: null local APIC address!` |

任何一项失败，`check_physptr()` 都会打印 `BIOS bug, MP table errors detected!...` 与 `... disabling SMP support. (tell your hw vendor)`，并把 `smp_found_config` 清零，整张表作废。检查通过后打印 OEM ID、Product ID 和 LAPIC 地址，并在 ACPI 没有提供 LAPIC 信息时用 `register_lapic_address()` 登记 LAPIC 的物理地址。

### 5.4 五种条目

基本条目紧跟在表头之后，第一个字节是类型。MPS 要求条目按类型升序排列，Linux 的解析循环 `smp_read_mpc()`（`mpparse.c:188`）按类型分派，遇到不认识的类型会调用 `smp_dump_mptable()` 打印 `Your mptable is wrong, contact your HW vendor!` 并把整张表十六进制转储出来，然后停止解析。

**处理器条目（类型 0，20 字节）**

| 偏移 | 大小 | 字段 | mini-vmm 的值 |
|---|---|---|---|
| 0 | 1 | type | 0 |
| 1 | 1 | lapic_id | vCPU 编号 0–3 |
| 2 | 1 | lapic_version | `0x14` |
| 3 | 1 | cpu_flags：bit 0 EN（可用），bit 1 BP（引导处理器） | CPU 0 为 3，其余为 1 |
| 4 | 4 | cpu_signature：CPUID.1:EAX 的步进、型号、家族 | `0x00000600` |
| 8 | 4 | feature_flags：CPUID.1:EDX | `0x00000201`，即 FPU 与 APIC |
| 12 | 8 | reserved | 0 |

```text
9fc3c: 00 00 14 03 00 06 00 00 01 02 00 00 00 00 00 00 00 00 00 00   CPU 0, EN|BP
9fc50: 00 01 14 01 00 06 00 00 01 02 00 00 00 00 00 00 00 00 00 00   CPU 1, EN
```

Linux 的 `MP_processor_info()`（`mpparse.c:49`）只看两个字段：EN 为 0 时计入 `disabled_cpus` 后返回；否则调用 `generic_processor_info(m->apicid)` 登记这颗 CPU。BP 位只用于打印 `(Bootup-CPU)`；哪颗是 BSP，Linux 是通过读取正在运行的 CPU 自己的 LAPIC ID 寄存器确定的（`register_lapic_address()` → `apic_set_fixmap()` → `apic_read_boot_cpu_id()`），`generic_processor_info()` 遇到与 `boot_cpu_physical_apicid` 相同的 ID 时直接返回逻辑 CPU 0。`lapic_version`、`cpu_signature`、`feature_flags` 在 v6.6 中完全不读，mini-vmm 在 `mptable.c:156` 的注释里说它们“Linux 只拿来打印，填个合理值”，这是对的。`lapic_version = 0x14` 与 KVM 的 LAPIC 版本寄存器低 8 位一致（卷四 3.2 节，KVM 报告 `0x50014`，日志中的 `APIC VERSION: 00050014` 可以印证）。

**总线条目（类型 1，8 字节）**

| 偏移 | 大小 | 字段 | mini-vmm 的值 |
|---|---|---|---|
| 0 | 1 | type | 1 |
| 1 | 1 | bus_id | 0 |
| 2 | 6 | bus_type：空格填充的 ASCII，如 `ISA   `、`PCI   `、`EISA  ` | `ISA   ` |

总线条目看似无关紧要，其实决定了中断条目的解读方式。中断条目里的“源总线 IRQ”字段对 ISA 总线就是 IRQ 号，对 PCI 总线则编码为 `(设备号 << 2) | INTx 引脚`；而且两种总线的“遵从总线默认”极性和触发方式不同，ISA 是高电平有效的边沿触发，PCI 是低电平有效的电平触发。Linux 的 `MP_bus_info()` 把每条总线的类型记在 `mp_bus_not_pci` 位图等数据结构里，供 IOAPIC 代码查询。

**IOAPIC 条目（类型 2，8 字节）**

| 偏移 | 大小 | 字段 | mini-vmm 的值 |
|---|---|---|---|
| 0 | 1 | type | 2 |
| 1 | 1 | ioapic_id | `nr_cpus`，4 个 vCPU 时为 4 |
| 2 | 1 | ioapic_version | `0x11` |
| 3 | 1 | flags：bit 0 EN | 1 |
| 4 | 4 | address | `0xfec00000` |

```text
9fc94: 02 04 11 01 00 00 c0 fe
```

`MP_ioapic_info()`（`mpparse.c:103`）在 EN 置位时调用 `mp_register_ioapic(m->apicid, m->apicaddr, gsi_top, &cfg)`。注意 MP 表没有“GSI 基址”字段，Linux 用全局变量 `gsi_top` 依次分配：第一颗 IOAPIC 从 GSI 0 开始，引脚数由 `mp_register_ioapic()` 读 IOAPIC 版本寄存器的“最大重定向项”字段得到。这就是日志中 `IOAPIC[0]: apic_id 4, version 17, address 0xfec00000, GSI 0-23` 的来源：版本 17 即 `0x11`，GSI 0–23 是因为 KVM 模拟的 IOAPIC 有 24 个引脚（卷四 2.4 节）。IOAPIC ID 取 `nr_cpus`，是为了避开 LAPIC ID 0 到 `nr_cpus - 1`；两者如果冲突，Linux 的 `io_apic_unique_id()` 会重新挑选一个（卷四 2.1 节）。

**I/O 中断条目（类型 3，8 字节）**

| 偏移 | 大小 | 字段 | 含义 |
|---|---|---|---|
| 0 | 1 | type | 3 |
| 1 | 1 | irq_type | 0 INT（向量中断），1 NMI，2 SMI，3 ExtINT |
| 2 | 2 | irq_flag | bit 1:0 极性 PO，bit 3:2 触发方式 EL |
| 4 | 1 | src_bus_id | 源总线 |
| 5 | 1 | src_bus_irq | 源总线上的 IRQ |
| 6 | 1 | dst_ioapic_id | 目标 IOAPIC；`0xFF` 表示全部 |
| 7 | 1 | dst_intin | 目标 IOAPIC 的输入引脚号 |

`irq_flag` 的两个 2 位字段编码相同：`00` 表示遵从总线默认，`01` 表示高电平有效或边沿触发，`10` 保留，`11` 表示低电平有效或电平触发。

mini-vmm 写了 16 条：ISA IRQ `i` 接 IOAPIC 引脚 `i`，`irq_flag = 0`。

```text
9fc9c: 03 00 00 00 00 00 04 00   INT, conforming, ISA IRQ 0 -> IOAPIC 4 pin 0
9fca4: 03 00 00 00 00 01 04 01   INT, conforming, ISA IRQ 1 -> IOAPIC 4 pin 1
...
9fd14: 03 00 00 00 00 0f 04 0f   INT, conforming, ISA IRQ 15 -> IOAPIC 4 pin 15
```

`mp_save_irq()` 把这些条目原样存进 `mp_irqs[]` 数组，之后 IOAPIC 代码查询“某个 ISA IRQ 接在哪个引脚、什么极性和触发方式”时查的就是它。IRQ 0 接引脚 0 而不是 QEMU 惯用的引脚 2，原因在卷四 2.7 节已经详细讨论过：KVM 内核态 irqchip 的默认 GSI 路由是恒等映射，PIT 的中断注入到 GSI 0，而 GSI 0 在 IOAPIC 上就是引脚 0。mini-vmm 的 `mptable.c` 文件头注释专门警告“照抄 qemu 的表会让时钟中断丢失”，启动日志中的 `..TIMER: vector=0x30 apic1=0 pin1=0` 说明内核确实在引脚 0 上找到了时钟。

**本地中断条目（类型 4，8 字节）**

格式与 I/O 中断条目完全相同，只是最后两个字节的含义变成目标 LAPIC ID（`0xFF` 表示全部）和目标 LINT 引脚号。mini-vmm 写了两条：

```text
9fd1c: 04 03 00 00 00 00 ff 00   ExtINT -> all LAPICs, LINT0
9fd24: 04 01 00 00 00 00 ff 01   NMI    -> all LAPICs, LINT1
```

这两条描述的是 PC 的标准接线：8259A 的 INTR 输出接每颗 LAPIC 的 LINT0（ExtINT 方式，即虚拟线模式），NMI 接 LINT1。Linux 的 `MP_lintsrc_info()` 只在 `apic=verbose` 时把它们打印出来，并不根据它们编程 LVT。LINT0 与 LINT1 的实际配置由 `setup_local_APIC()` 按 PC 的惯例自行决定（卷四 3.6 节），这也意味着一个 VMM 如果模拟了非标准的接线，仅靠改这两条条目是没有用的。

### 5.5 Linux 什么时候真正使用 MP 表

MP 表的扫描总会发生，但配置表的内容是否被解析，取决于 ACPI 的结果。`get_smp_config()` 最终调用 `default_get_smp_config()`（`mpparse.c:476`），开头有四个提前返回：

```c
	if (!smp_found_config)
		return;
	if (!mpf_found)
		return;
	if (acpi_lapic && early)
		return;
	/*
	 * MPS doesn't support hyperthreading, aka only have
	 * thread 0 apic id in MPS table
	 */
	if (acpi_lapic && acpi_ioapic)
		return;
```

结合 ACPI 侧的逻辑（8.7 节），可以把各种组合列成表：

| ACPI 状态 | MP 表的命运 |
|---|---|
| ACPI 启用，MADT 同时提供了 LAPIC 与 IOAPIC | 配置表不解析，只保留内存；日志 `Using ACPI (MADT) for SMP configuration information` |
| ACPI 启用，MADT 只有 LAPIC、没有 IOAPIC | 解析配置表，但跳过处理器条目（`if (!acpi_lapic)`），只取总线、IOAPIC 和中断条目 |
| ACPI 启用，但 ACPI 表中没有 MADT | **MP 表也被作废**：`acpi_process_madt()` 打印 `No APIC-table, disabling MPS` 并清零 `smp_found_config`，系统以单处理器 PIC 模式运行 |
| `acpi=off` 或内核未开 `CONFIG_ACPI` | 完整解析配置表 |

第三行是一个值得记住的陷阱。一个 VMM 如果先写了 MP 表，后来又加上 RSDP、XSDT 和 FADT（比如为了支持 ACPI 关机），却还没来得及写 MADT，guest 会从多核退化成单核，而且原因不在新写的 ACPI 代码里，而是 ACPI 的存在让 Linux 主动放弃了 MP 表。源码注释给出的建议是“Boot with "acpi=off" to use MPS on such a system”。

两类表对完整性错误的态度也截然相反。MP 表的浮动指针结构校验和错误，扫描时直接跳过，就像不存在一样；配置表校验和错误，整张表作废并关闭 SMP。ACPI 表的校验和错误只产生一条警告，表照样使用（6.2 节）。所以 MP 表的构造代码更不能容忍“差一个字节”的错误，而一旦出错，现象又特别彻底：多核变单核，或者 IOAPIC 消失导致定时器不工作。

### 5.6 用 `acpi=off` 验证 MP 表

因为默认启动时 MP 表的内容根本不被解析，mini-vmm 的 MP 表即使有错也不会在正常启动中暴露出来。验证它的办法是在命令行追加 `acpi=off apic=verbose`，强制内核走 MP 表路径。在实验机上用同一个 vmlinux 实测，关键日志如下：

## 6. ACPI 基础：表头、RSDP 与 XSDT

### 6.1 表的拓扑

ACPI 用一棵以 RSDP 为根的指针树描述平台。mini-vmm 构造的是这棵树里最小的一个可用子集：

```text
boot_params.acpi_rsdp_addr = 0xe0000
            │
            ▼
   RSDP  @0xe0000 (36 B, "RSD PTR ", rev 2)
            │ xsdt_address
            ▼
   XSDT  @0xe0030 (52 B, 2 entries)
       ├── [0] FADT "FACP" @0xe0070 (276 B, rev 6.4)
       │         └── X_DSDT ──► DSDT @0xe0190 (50 B, AML: \_S5)
       └── [1] MADT "APIC" @0xe01d0 (94 B, rev 5)
```

真实平台上 XSDT 通常还会列出 HPET、MCFG（PCIe 配置空间）、SRAT/SLIT（NUMA）、SSDT（额外的 AML）、FACS（由 FADT 引用，用于睡眠唤醒）等十几张表。每一张缺失的表都对应一个“内核自己想办法”的分支，第 10 节会按启动日志逐条对照。

表与表之间的规则可以概括为三条：

- RSDP 不是标准表，没有通用表头，只能靠扫描或者由 bootloader 给出地址找到。
- XSDT（或老式的 RSDT）列出除 DSDT 与 FACS 之外的所有顶层表。
- DSDT 与 FACS 由 FADT 中的指针引用，**不应该**出现在 XSDT 中。mini-vmm 的 `acpi.c:272` 注释写的正是这一条。

### 6.2 通用表头与校验和的政策

除 RSDP 和 FACS 外，所有 ACPI 表都以 36 字节的通用表头开始：

| 偏移 | 大小 | 字段 | 含义 | mini-vmm 的值 |
|---|---|---|---|---|
| 0 | 4 | Signature | 4 字符表签名 | `FACP`、`APIC`、`DSDT`、`XSDT` |
| 4 | 4 | Length | 整张表的字节数，含表头 | 各表不同 |
| 8 | 1 | Revision | 该表自身的版本号，与 ACPI 规范版本不是一回事 | XSDT 1、DSDT 2、MADT 5、FADT 6 |
| 9 | 1 | Checksum | 使整张表所有字节之和模 256 为 0 | 由 `acpi_checksum()` 计算 |
| 10 | 6 | OEM ID | OEM 标识 | `MINVMM` |
| 16 | 8 | OEM Table ID | OEM 为这张表取的名字 | `MINIVMM ` |
| 24 | 4 | OEM Revision | OEM 自定义的版本号 | 1 |
| 28 | 4 | Creator ID | 生成这张表的工具的厂商 ID（用 iasl 编译时是 `INTL`） | `MVMM` |
| 32 | 4 | Creator Revision | 工具版本 | 1 |

Linux 在定位表时把每张表的表头打印成一行，格式来自 ACPICA 的 `acpi_tb_print_table_header()`（`drivers/acpi/acpica/tbprint.c:93`），依次是签名、物理地址、长度、括号里的表版本、OEM ID、OEM Table ID、OEM Revision、Creator ID、Creator Revision：

```text
ACPI: RSDP 0x00000000000E0000 000024 (v02 MINVMM)
ACPI: XSDT 0x00000000000E0030 000034 (v01 MINVMM MINIVMM  00000001 MVMM 00000001)
ACPI: FACP 0x00000000000E0070 000114 (v06 MINVMM MINIVMM  00000001 MVMM 00000001)
ACPI: DSDT 0x00000000000E0190 000032 (v02 MINVMM MINIVMM  00000001 MVMM 00000001)
ACPI: APIC 0x00000000000E01D0 00005E (v05 MINVMM MINIVMM  00000001 MVMM 00000001)
```

RSDP 没有通用表头，所以它那一行只有地址、长度和 OEM ID；长度 `0x24` 即 36 字节，这是版本 2 RSDP 的长度。

`Revision` 字段的含义值得多说一句。它是**这张表自己的**格式版本：MADT 版本 5 是 ACPI 6.3 为引入 LAPIC 的“Online Capable”标志而升级的格式，FADT 版本 6 是 ACPI 6.0 增加“Hypervisor Vendor Identity”字段后的格式；一张表的版本号不代表整个平台遵循哪一版 ACPI 规范。FADT 另外有一个 `Minor Version` 字段（偏移 131），与 `Revision` 合起来才表示平台遵循的规范版本，mini-vmm 的 `Revision = 6`、`Minor Version = 4` 就是在声明 ACPI 6.4。这个版本号不只是装饰，8.3 节会看到它决定了 Linux 如何解读 MADT 里 LAPIC 条目的标志位。

**校验和的政策。** 与 MP 表的“错一个字节就作废”截然不同，Linux 对 ACPI 表的校验和非常宽容：

1. 早期阶段根本不检查。`acpi_locate_initial_tables()`（`drivers/acpi/tables.c:867`）根据 `acpi_verify_table_checksum` 决定是否校验，默认值为 `false`，于是打印 `ACPI: Early table checksum verification disabled`。源码注释给出的理由是“size limitation of the current x86 early mapping implementation”：早期映射窗口很小，不适合把整张表映射进来求和。命令行参数 `acpi_force_table_verification` 可以打开早期校验。
2. 例外是 XSDT/RSDT 本身：`acpi_tb_parse_root_table()` 总会调用 `acpi_ut_verify_checksum()` 检查根表（`tbutils.c:303`）。FADT 也在复制前被检查一次（`tbfadt.c:301`），注释说明“Ignore checksum error as we want to try to get the DSDT and FACS”。
3. ACPICA 就绪后补做校验。`acpi_early_init()` 调用 `acpi_reallocate_root_table()`，后者把 `acpi_gbl_enable_table_validation` 置为真，并对所有尚未验证的表调用 `acpi_tb_verify_temp_table()`（`tbxface.c:169-185`）。
4. 即使补做校验时发现错误，也只是警告。`acpi_ut_verify_checksum()`（`drivers/acpi/acpica/utcksum.c:35`）在校验和不符时打印 `Incorrect checksum in table [XXXX] - 0xNN, should be 0xMM`，然后只有在编译期常量 `ACPI_CHECKSUM_ABORT` 为真时才返回错误；Linux 中这个常量是 `FALSE`（`include/acpi/acconfig.h:54`），所以函数总是返回 `AE_OK`，表照常使用。

这种宽容来自现实：大量量产 BIOS 的 ACPI 表校验和是错的，如果严格执行，Linux 在这些机器上就无法启动。对 VMM 作者来说，这意味着校验和错误不会让 guest 启动失败，只会在日志里留下一行 `ACPI BIOS Warning`；反过来，检查自己的 ACPI 表时不能以“guest 能启动”为标准，要去日志里搜 `Incorrect checksum`，或者用 iasl 反汇编检查（第 11 节）。

### 6.3 RSDP：根指针

RSDP（Root System Description Pointer）的布局：

| 偏移 | 大小 | 字段 | 版本 | mini-vmm 的值 |
|---|---|---|---|---|
| 0 | 8 | Signature | 全部 | `RSD PTR `（注意末尾的空格） |
| 8 | 1 | Checksum：前 20 字节之和为 0 | 全部 | `0x0b` |
| 9 | 6 | OEM ID | 全部 | `MINVMM` |
| 15 | 1 | Revision：0 表示 ACPI 1.0，2 表示 ACPI 2.0 及以后 | 全部 | 2 |
| 16 | 4 | RsdtAddress：RSDT 的 32 位物理地址 | 全部 | 0 |
| 20 | 4 | Length：整个 RSDP 的长度 | 2+ | 36 |
| 24 | 8 | XsdtAddress：XSDT 的 64 位物理地址 | 2+ | `0xe0030` |
| 32 | 1 | Extended Checksum：全部 36 字节之和为 0 | 2+ | `0x9e` |
| 33 | 3 | Reserved | 2+ | 0 |

```text
e0000: 52 53 44 20 50 54 52 20 0b 4d 49 4e 56 4d 4d 02   "RSD PTR " sum=0x0b "MINVMM" rev=2
e0010: 00 00 00 00 24 00 00 00 30 00 0e 00 00 00 00 00   rsdt=0 len=36 xsdt=0x00000000000e0030
e0020: 9e 00 00 00                                       xsum=0x9e
```

RSDP 有两个校验和，这是 ACPI 1.0 到 2.0 演进的遗迹：1.0 的 RSDP 只有 20 字节，2.0 在后面追加了 16 字节，为了让老 OS 仍能校验前 20 字节，新增了一个覆盖全部 36 字节的扩展校验和。mini-vmm 在 `acpi.c:286-287` 先算 20 字节的校验和，再算 36 字节的扩展校验和，顺序不能反：扩展校验和的计算范围包含 `Checksum` 字段本身。

Linux 找 RSDP 的顺序在 `acpi_os_get_root_pointer()`（`drivers/acpi/osl.c`）中：

1. 命令行参数 `acpi_rsdp=`。仅在 `CONFIG_KEXEC` 打开且内核没有处于 lockdown 状态时生效，主要供 kexec 使用。
2. `acpi_arch_get_root_pointer()`，在 x86 上是 `x86_init.acpi.get_root_pointer`，默认实现 `x86_default_get_root_pointer()`（`arch/x86/kernel/acpi/boot.c:1900`）直接返回 `boot_params.acpi_rsdp_addr`。
3. 如果是 EFI 启动，从 EFI 配置表中取 ACPI 2.0 表的地址，没有的话再取 ACPI 1.0 表的地址。
4. 否则，在打开了 `CONFIG_ACPI_LEGACY_TABLES_LOOKUP` 的内核上（guest 的配置打开了），调用 ACPICA 的 `acpi_find_root_pointer()`（`drivers/acpi/acpica/tbxfroot.c`）做传统扫描。

传统扫描遵循 ACPI 规范：先从 BDA 的 `0x40E` 处读出 EBDA 的段地址，若其值落在 `(0x400, 0xA0000)` 内，就扫描 EBDA 的前 1 KiB；然后按 16 字节步长扫描 `[0xE0000, 0x100000)`（`include/acpi/acconfig.h:151-156` 中的 `ACPI_HI_RSDP_WINDOW_BASE` 与 `ACPI_HI_RSDP_WINDOW_SIZE`）。每个候选都要经过 `acpi_tb_validate_rsdp()`：签名正确、20 字节校验和为 0，版本不低于 2 时 36 字节扩展校验和也要为 0。

这里有一个不对称：**只有扫描路径会校验 RSDP**。经由 `boot_params.acpi_rsdp_addr` 得到的地址直接交给 `acpi_tb_parse_root_table()`，而这个函数只做了映射和打印，不检查 RSDP 的签名和校验和（`tbutils.c:240-265`）。所以一个 RSDP 校验和算错了的 VMM，在填写了 `acpi_rsdp_addr` 时一切正常，一旦 boot_params 的这个字段因为某种原因被清零（比如 3.2 节的 sentinel 清理），扫描路径就会拒绝这个 RSDP，guest 突然“失去”ACPI。mini-vmm 两条路径都能走通：RSDP 放在 `0xE0000` 的 16 字节边界上，两个校验和都正确。

### 6.4 XSDT 与 RSDT

RSDT 与 XSDT 的区别只在于表项宽度：RSDT 的表项是 32 位物理地址，XSDT 是 64 位。ACPICA 的选择规则在 `acpi_tb_parse_root_table()`（`tbutils.c:251-265`）：

```c
	if ((rsdp->revision > 1) &&
	    rsdp->xsdt_physical_address && !acpi_gbl_do_not_use_xsdt) {
		address = (acpi_physical_address)rsdp->xsdt_physical_address;
		table_entry_size = ACPI_XSDT_ENTRY_SIZE;
	} else {
		address = (acpi_physical_address)rsdp->rsdt_physical_address;
		table_entry_size = ACPI_RSDT_ENTRY_SIZE;
	}
```

RSDP 版本大于 1 且 XSDT 地址非零时用 XSDT，否则用 RSDT。命令行参数 `acpi=rsdt` 设置 `acpi_gbl_do_not_use_xsdt`，强制使用 RSDT。mini-vmm 只提供 XSDT，RSDP 中的 `RsdtAddress` 为 0，所以在 `acpi=rsdt` 下 ACPICA 会去映射物理地址 0 处的“RSDT”。x86 的 `__acpi_map_table()`（`arch/x86/kernel/acpi/boot.c:114`）对地址 0 直接返回 NULL，`acpi_tb_parse_root_table()` 以 `AE_NO_MEMORY` 失败，`acpi_boot_table_init()` 随即调用 `disable_acpi()` 把 ACPI 整体关闭，内核转而使用 MP 表。在实验机上实测，日志中 `ACPI: RSDP ...` 那一行之后再没有任何 ACPI 表头，也没有任何错误信息，紧接着出现的是 `Intel MultiProcessor Specification v1.4`，4 颗 CPU 照常启动。这不是 bug，只是 mini-vmm 选择了不支持 ACPI 1.0 风格的 OS；如果要兼容，可以再生成一张 RSDT，两个指针同时填写。

根表的长度必须至少能容纳一个表项，否则 ACPICA 报 `Invalid table length 0x%X in RSDT/XSDT` 并放弃（`tbutils.c:289-294`）。之后它对每个非零表项调用 `acpi_tb_install_standard_table()`，遇到 FADT 时立即调用 `acpi_tb_parse_fadt()`，从 FADT 中取出 DSDT 与 FACS 的地址一并安装。

mini-vmm 的 XSDT：

```text
e0030: 58 53 44 54 34 00 00 00 01 db 4d 49 4e 56 4d 4d   "XSDT" len=52 rev=1 sum=0xdb "MINVMM"
e0040: 4d 49 4e 49 56 4d 4d 20 01 00 00 00 4d 56 4d 4d   "MINIVMM " oem_rev=1 "MVMM"
e0050: 01 00 00 00 70 00 0e 00 00 00 00 00 d0 01 0e 00   creator_rev=1 [0]=0xe0070 (FADT)
e0060: 00 00 00 00                                       [1]=0xe01d0 (MADT)
```

注意第一个表项位于表内偏移 36 处，这个地址只是 4 字节对齐而不是 8 字节对齐。ACPICA 在 `acpi_tb_get_root_table_entry()` 里专门注明“Addresses are 32-bit aligned (not 64) in both RSDT and XSDT”，并用 `ACPI_MOVE_64_TO_64` 做非对齐读取（`tbutils.c:173-188`），所以没有问题；但如果 VMM 作者自己写代码解析 XSDT（比如在测试里校验），要注意不能直接把指针强制转换成 `uint64_t *` 访问。

表被安装后，`acpi_reserve_initial_tables()`（`drivers/acpi/tables.c:886`）用 memblock 保留根表列表中每一张表所占的内存，这就是日志中的三行：

```text
ACPI: Reserving FACP table memory at [mem 0xe0070-0xe0183]
ACPI: Reserving DSDT table memory at [mem 0xe0190-0xe01c1]
ACPI: Reserving APIC table memory at [mem 0xe01d0-0xe022d]
```

RSDP 和 XSDT 不在这个列表里，Linux 不会为它们调用 `memblock_reserve()`。它们之所以安全，完全是因为 E820 把 `[0x9fc00, 0x100000)` 报成了保留。由此得出一条 VMM 规则：**ACPI 表，尤其是 RSDP 和根表，必须放在 E820 中不属于 RAM 的区域。** 如果把它们放进一段 RAM，内核在早期保留完三张表之后可能会把 RSDP 所在的页分配出去；kexec 等需要在运行期重新找到 RSDP 的功能就会读到垃圾。

## 7. FADT 与 DSDT：固定硬件、AML 与关机

### 7.1 FADT 的角色

FADT（Fixed ACPI Description Table，签名 `FACP`）描述 ACPI 规范里的“固定硬件”：一组位置由 FADT 给出、语义由规范规定的寄存器块，包括 PM1 事件与控制寄存器、PM 定时器、GPE 块、复位寄存器等。它还携带若干平台标志，并保存 DSDT 与 FACS 的地址。ACPICA 要正常初始化，FADT 是唯一不可缺少的表。

FADT 的版本演进很长，长度从 ACPI 1.0 的 116 字节一路增长到 ACPI 6.0 之后的 276 字节。ACPICA 的处理方式是把 FADT 复制到一个按最新格式定义的全局结构 `acpi_gbl_FADT` 里：`acpi_tb_create_local_fadt()`（`drivers/acpi/acpica/tbfadt.c`）先把目标清零，再按 `min(表长, sizeof(struct acpi_table_fadt))` 复制，表比已知格式更长时截断并打印警告。之后所有代码只读 `acpi_gbl_FADT`，永远不会再访问原始的 FADT。

几个字段值得展开。

**32 位字段与 X 字段。** ACPI 2.0 为每个 32 位的寄存器块地址增加了一个 12 字节的通用地址结构（Generic Address Structure，GAS）版本，能表示 64 位地址和 I/O、内存、PCI 配置等不同地址空间。规范说 X 字段非零时优先使用。mini-vmm 只填 32 位字段，X 字段全部留 0（`acpi.c:91` 的注释：“留 0 让 ACPICA 从 32 位字段转换”）。ACPICA 的 `acpi_tb_convert_fadt()` 对此的处理是：32 位地址非零而 X 地址为零时，用 32 位地址和对应的长度字段构造一个空间类型为 System I/O 的 GAS 填进 X 字段；两者都非零且不相等时打印 `32/64X address mismatch` 警告并采用 X 字段。转换之后 ACPICA 只使用 X 字段。

**必需字段。** `acpi_tb_convert_fadt()` 把 PM1a_EVT_BLK 和 PM1a_CNT_BLK 标记为必需：只要不是硬件精简平台，这两个块的地址和长度任何一个为 0，都会打印 `Required FADT field %s has zero address and/or length`。这就是 mini-vmm 必须实现 PM1a 寄存器（`acpi_pm_attach()`）的直接原因，而 `include/boot/acpi.h` 的注释说明了更深一层的原因：不设 HW_REDUCED 标志，是因为硬件精简模式会让 Linux 认为没有 PIT 和 8259（7.4 节）。

**SMI_CMD 为 0。** 真实的 PC 固件开机时处于“传统模式”，电源事件由 SMM 中的固件代码处理；OS 要接管，得向 SMI_CMD 端口写入 ACPI_ENABLE，触发一次 SMI，由固件把 PM1_CNT 的 SCI_EN 位置 1。VMM 没有 SMM，也不需要这个过程。ACPICA 的 `acpi_hw_get_mode()`（`drivers/acpi/acpica/hwacpi.c:114`）在 SMI_CMD 为 0 时直接认为系统已处于 ACPI 模式，注释引用的是 ACPI 2.0 的澄清：“if SMI_CMD in FADT is zero, system does not support mode transition”。mini-vmm 的 PM1_CNT 读回值永远带 SCI_EN 位（`acpi.c:318`），与这个声明一致。

**PM_TMR_BLK 为 0。** ACPI PM 定时器是一个 3.579545 MHz 的自由计数器，Linux 用它作为 `acpi_pm` 时钟源，并在校准 LAPIC 定时器时拿它做参照。mini-vmm 没有提供它，于是 `acpi_parse_fadt()` 在检查 `xpm_timer_block.space_id` 时就返回了：32 位字段为 0 时 ACPICA 不做转换，X 字段保持全 0，空间类型 0 是 System Memory 而不是 System I/O（`arch/x86/kernel/acpi/boot.c:1063-1066`）。启动日志中因此没有 `ACPI: PM-Timer IO Port: 0x...` 这一行，`apic=verbose` 下 LAPIC 定时器校准打印 `... PM-Timer delta = 0`，校准改用 PIT 与 jiffies。在 KVM 下这没有损失：TSC 恒定且可靠，最终时钟源是 `tsc`；而 PM 定时器每读一次都是一次 PIO 退出，当时钟源用反而更慢。

**CENTURY 为 `0x32`。** CMOS RTC 只存两位数的年份，世纪存在哪个 CMOS 寄存器由固件决定，FADT 的 CENTURY 字段给出索引。Linux 的 `mc146818_get_time()`（`drivers/rtc/rtc-mc146818-lib.c:131-135`）在 FADT 版本不低于 3 且该字段非零时读取这个寄存器；RTC 驱动还会在初始化信息里打印 `y3k`（5.6 节的对照实验）。`0x32` 是 IBM PC/AT 的传统位置，mini-vmm 的 RTC 模型在同一个索引上提供世纪值（`acpi.c:225` 的注释指向 `rtc.c`）。

**Hypervisor Vendor Identity。** 这个 8 字节字段是 ACPI 6.0 为虚拟化平台增加的。在 guest 的 v6.6 源码树里，唯一读取它的是 arm64 上的 Hyper-V 探测代码（`arch/arm64/hyperv/mshyperv.c:37`，比较是否为 `MsHyperV`）；x86 上识别 hypervisor 走的是 CPUID，不看这个字段。mini-vmm 留 0 没有任何影响。

### 7.3 两组标志位

**IAPC_BOOT_ARCH（偏移 109，16 位）** 告诉 OS 哪些 PC 传统设备存在。定义在 `include/acpi/actbl.h:260-265`，Linux 的消费者如下：

| 位 | 名称 | 含义 | Linux 的消费者 | mini-vmm |
|---|---|---|---|---|
| 0 | LEGACY_DEVICES | 存在 LPC/ISA 总线上的设备 | `acpi_parse_fadt()`：未置位时关闭 PnPBIOS | 1 |
| 1 | 8042 | 端口 `0x60`/`0x64` 上有 8042 键盘控制器 | `acpi_parse_fadt()`：FADT 版本不低于 3 且未置位时，把 `x86_platform.legacy.i8042` 设为 `FIRMWARE_ABSENT`，i8042 驱动将不探测 | 1 |
| 2 | VGA Not Present | 探测 VGA 不安全 | `acpi_parse_fadt()` 设置 `x86_platform.legacy.no_vga` | 0 |
| 3 | MSI Not Supported | 不得启用 MSI | `drivers/pci/pci-acpi.c:1502` 调用 `pci_no_msi()` | 0 |
| 4 | PCIe ASPM Controls | 不得启用 ASPM | `drivers/pci/pci-acpi.c:1507`、`drivers/acpi/pci_root.c:606` | 0 |
| 5 | CMOS RTC Not Present | 没有 CMOS RTC | `acpi_parse_fadt()` 把 `x86_platform.legacy.rtc` 清零，不注册 `rtc_cmos` 平台设备 | 0 |

第 1 位与 mini-vmm 的 i8042 模型直接相关。i8042 驱动先通过 PnP 查找 `PNP0303` 等设备，找不到时是否退回到直接探测传统端口，取决于 `x86_platform.legacy.i8042`（`drivers/input/serio/i8042-acpipnpio.h:1583-1597`）：值为 `EXPECTED_PRESENT` 时打印 `Probing ports directly.` 并继续；值为 `FIRMWARE_ABSENT` 时直接返回 `-ENODEV`。mini-vmm 的 DSDT 里没有 PnP 设备，日志中紧挨着的两行 `i8042: PNP: No PS/2 controller found.` 与 `i8042: Probing ports directly.` 正是这个分支的写照；如果把这一位清掉，第二行就会消失，键盘控制器从此不被驱动接管（重启代码本身不看这个标志，照样会写 `0x64`）。卷七会逐寄存器追踪 i8042 驱动的探测过程。

**Flags（偏移 112，32 位）** 是平台特性的集合，定义在 `include/acpi/actbl.h:276-297`。mini-vmm 设置了第 0、4、5 位：

| 位 | 名称 | 含义 | Linux 的消费者 | mini-vmm |
|---|---|---|---|---|
| 0 | WBINVD | `WBINVD` 指令能正确回写并失效缓存 | `drivers/acpi/processor_idle.c:365`：C3 状态的支持条件之一 | 1 |
| 4 | PWR_BUTTON | 置 1 表示电源键**不是**固定硬件，而是作为控制方法设备出现在 DSDT 中（或者根本没有） | `drivers/acpi/scan.c:2564`：未置位时创建固定硬件电源键设备 `LNXPWRBN` | 1 |
| 5 | SLP_BUTTON | 同上，针对睡眠键 | `drivers/acpi/scan.c:2578` | 1 |
| 6 | FIX_RTC | RTC 唤醒状态不在固定寄存器中 | `drivers/rtc/rtc-cmos.c:877` | 0 |
| 8 | TMR_VAL_EXT | PM 定时器是 32 位（否则 24 位） | `drivers/acpi/acpica/hwtimer.c` | 0 |
| 10 | RESET_REG_SUP | 支持通过 RESET_REG 复位 | `acpi_reboot()` | 0 |
| 19 | FORCE_APIC_PHYSICAL_DESTINATION_MODE | 所有 xAPIC 必须使用物理目标模式 | `arch/x86/kernel/apic/apic_flat_64.c:131`：选择 `apic_physflat` 驱动 | 0 |
| 20 | HW_REDUCED_ACPI | 硬件精简平台 | ACPICA 设置 `acpi_gbl_reduced_hardware`，见 7.4 节 | 0 |
| 21 | LOW_POWER_S0_IDLE_CAPABLE | S0 空闲的功耗不比 S3 差 | 选择 suspend-to-idle 作为默认挂起方式 | 0 |

PWR_BUTTON 的语义是反直觉的：置 1 反而表示“没有固定硬件电源键”。mini-vmm 置 1，于是 Linux 不创建 `LNXPWRBN` 设备，也不会使能 PM1_EN 中的 PWRBTN_EN 位。

第 19 位值得 VMM 作者留意。卷四 3.7 节讲过，4 个 vCPU 的 guest 选择了逻辑 flat 目标模式（`apic_flat`）。v6.6 的 APIC 驱动选择过程中，`apic_physflat` 的 `acpi_madt_oem_check` 回调在 FADT 版本不低于 3 且第 19 位置位时返回 1，使内核改用物理目标模式。所以 VMM 可以不改 guest 内核，只通过 FADT 的一个位来决定 guest 使用哪种 APIC 目标模式；这对需要比较两种模式下 KVM 中断投递路径的实验很方便。

### 7.4 为什么不用硬件精简模式

ACPI 5.0 引入了硬件精简（Hardware-Reduced）模式，Flags 第 20 位置 1 即可声明。在这个模式下 FADT 的固定硬件寄存器块全部可以为 0，电源管理通过 `SLEEP_CONTROL_REG` 等少数几个寄存器或纯 AML 完成。它看起来对 VMM 更友好，Firecracker、Cloud Hypervisor 的 ACPI 实现都采用了它。

mini-vmm 没有采用，原因在 x86 Linux 对这个标志的处理。`early_acpi_boot_init()` 在检测到 `acpi_gbl_reduced_hardware` 时调用 `x86_init.acpi.reduced_hw_early_init`，默认实现是 `acpi_generic_reduced_hw_init()`（`arch/x86/kernel/acpi/boot.c:1484`）：

```c
void __init acpi_generic_reduced_hw_init(void)
{
	/*
	 * Override x86_init functions and bypass legacy PIC in
	 * hardware reduced ACPI mode.
	 */
	x86_init.timers.timer_init	= x86_init_noop;
	x86_init.irqs.pre_vector_init	= x86_init_noop;
	legacy_pic			= &null_legacy_pic;
}
```

`timer_init` 被置空意味着不再初始化 PIT 作为时钟事件设备，`legacy_pic` 被换成空实现意味着 8259A 被当作不存在。mini-vmm 依赖 PIT 校准 TSC（启动日志中的 `tsc: Fast TSC calibration using PIT`），并且在卷四的中断拓扑中 PIT 与 8259A 都是存在的；声明硬件精简会让内核的认识与 KVM 的实际配置不一致。硬件精简模式适合的是另一种 VMM 设计：不创建 PIT、不用 8259A、时钟完全依赖 TSC 与 LAPIC 定时器，并通过 `KVM_CREATE_IRQCHIP` 之外的方式（例如 split irqchip）组织中断。

另外，`acpi_parse_madt_ioapic_entries()` 在硬件精简平台上不为 SCI 伪造中断源覆盖（`arch/x86/kernel/acpi/boot.c` 中 `!acpi_gbl_reduced_hardware` 的判断），`acpi_sleep_state_supported()` 在硬件精简平台上要求 `SLEEP_CONTROL_REG` 与 `SLEEP_STATUS_REG` 都存在才认为支持睡眠状态（`drivers/acpi/sleep.c:93-95`）。换用硬件精简模式不是改一个位的事，关机路径也要重新实现。

### 7.5 SCI：一条目前不会响的中断线

SCI（System Control Interrupt）是 ACPI 固定硬件与 GPE 事件通知 OS 的中断。FADT 的 SCI_INT 字段给出它在 8259 模式下的 IRQ 号，mini-vmm 写的是 9，这是 PC 平台的惯例值。

Linux 对 SCI 的特殊处理在 `acpi_parse_madt_ioapic_entries()` 中：如果 MADT 里没有针对 SCI 的中断源覆盖条目，就调用 `acpi_sci_ioapic_setup(sci_interrupt, 0, 0, sci_interrupt)`“假装”有一条（`arch/x86/kernel/acpi/boot.c:548-575`），而这个函数把极性 0 和触发方式 0（遵从总线默认）解释为：

```c
	if (trigger == 0)	/* compatible SCI trigger is level */
		trigger = 3;

	if (polarity == 0)	/* compatible SCI polarity is low */
		polarity = 3;
```

即**低电平有效的电平触发**。这与 ISA 中断的默认（高电平有效的边沿触发）不同，因为 ACPI 规范规定 SCI 是可共享的电平中断。结果体现在 `/proc/interrupts` 中：IRQ 9 的类型是 `IO-APIC 9-fasteoi acpi`，而 IRQ 0、1、4、8 都是 `-edge`。随后 ACPICA 通过 `acpi_os_install_interrupt_handler()`（`drivers/acpi/osl.c`）以 `IRQF_SHARED` 申请这条中断。

mini-vmm 的 PM1 设备从不拉起 SCI：`pm_write()` 只处理 STS 的写 1 清零、EN 的保存与 CNT 的关机请求，没有任何状态会触发中断。所以 IRQ 9 在 `/proc/interrupts` 中的计数永远是 0。如果将来要实现 ACPI 电源键（让 host 请求 guest 优雅关机），需要做三件事：清除 FADT Flags 的第 4 位，让 Linux 创建固定电源键设备并使能 PM1_EN 的 PWRBTN_EN（第 8 位）；host 请求关机时把 PM1_STS 的 PWRBTN_STS（第 8 位）置 1；只要 `PM1_STS & PM1_EN` 非零，就保持 GSI 9 为有效电平，即调用 `KVM_IRQ_LINE` 把 GSI 9 置 1，guest 写 1 清除状态位后再置 0。这里有一个与卷四衔接的细节：IOAPIC 表项被 Linux 编程为低电平有效，但 KVM 的 IOAPIC 模拟忽略极性（卷四 2.2 节），`KVM_IRQ_LINE` 的 `level = 1` 就表示“中断有效”，VMM 不需要也不应该自己反转电平。

### 7.6 DSDT 与 AML：14 字节的程序

DSDT（Differentiated System Description Table）的内容是 AML（ACPI Machine Language）字节码。ACPICA 在 `acpi_bus_init()` 中调用 `acpi_load_tables()` 把它装进 ACPI 命名空间，日志中的 `ACPI: 1 ACPI AML tables successfully acquired and loaded` 就是这一步；这里的“1”指 DSDT，没有 SSDT。

mini-vmm 的 DSDT 除表头外只有 14 个字节：

```text
e0190: 44 53 44 54 32 00 00 00 02 c3 4d 49 4e 56 4d 4d   "DSDT" len=0x32 rev=2 sum=0xc3
e01a0: 4d 49 4e 49 56 4d 4d 20 01 00 00 00 4d 56 4d 4d
e01b0: 01 00 00 00 08 5f 53 35 5f 12 08 04 0a 05 0a 05   AML 从 e01b4 开始
e01c0: 00 00
```

按 ACPI 规范第 20 章的 AML 文法逐字节解码：

| 字节 | 文法成分 | 含义 |
|---|---|---|
| `08` | NameOp | 定义一个命名对象：`DefName := NameOp NameString DataRefObject` |
| `5F 53 35 5F` | NameSeg | `_S5_`；ACPI 名字固定 4 字符，不足时用 `_` 补齐，所以 `\_S5` 在 AML 中是 `_S5_` |
| `12` | PackageOp | 对象的值是一个包：`DefPackage := PackageOp PkgLength NumElements PackageElementList` |
| `08` | PkgLength | 单字节编码：bit 7:6 为 0 表示后面没有额外的长度字节，bit 5:0 为长度；长度 8 包括 PkgLength 字节本身及其后的 7 个字节 |
| `04` | NumElements | 包中有 4 个元素 |
| `0A 05` | BytePrefix + 字节 | 整数 5：PM1a_CNT 的 SLP_TYP |
| `0A 05` | BytePrefix + 字节 | 整数 5：PM1b_CNT 的 SLP_TYP |
| `00` | ZeroOp | 整数 0，保留 |
| `00` | ZeroOp | 整数 0，保留 |

对应的 ASL 源码只有一行：

```text
DefinitionBlock ("", "DSDT", 2, "MINVMM", "MINIVMM ", 1)
{
    Name (_S5, Package (0x04) { 0x05, 0x05, Zero, Zero })
}
```

几个编码细节：

- 这个 `Name` 不在任何 `Scope` 里，所以对象定义在命名空间根 `\` 下，全名 `\_S5`。这正是 ACPICA 查找睡眠状态对象时使用的路径。
- DSDT 的表头 Revision 为 2，含义是 AML 中的整数按 64 位处理；Revision 小于 2 的 DSDT 中整数是 32 位。对只有几个小整数的 `\_S5` 没有区别，但写复杂的 AML 时需要注意。
- AML 对 0、1 和全 1 有专门的单字节操作码 ZeroOp（`00`）、OneOp（`01`）、OnesOp（`FF`），其他小于 256 的常数用 BytePrefix（`0A`）加一个字节表示。

包里前两个元素为什么是 5？ACPI 规定每个睡眠状态对象 `\_Sx` 返回的包中，前两个整数是写入 PM1a_CNT 与 PM1b_CNT 的 SLP_TYP 字段（第 10–12 位）的值。这个值没有全平台统一的规定，由芯片组决定；OS 从 `\_Sx` 读出后原样写入，由硬件解释。VMM 可以自己约定，只要 DSDT 与 PM1 设备模型一致即可。mini-vmm 约定 5（`acpi.c:158` 的 `S5_SLP_TYP`），PM1 设备在 `pm_write()` 中比较的就是这个值。ACPICA 要求这个值不超过 `ACPI_SLEEP_TYPE_MAX = 7`（3 位字段的上限），否则在 `acpi_enter_sleep_state()` 中报 `Sleep values out of range`（`drivers/acpi/acpica/hwxfsleep.c:292-294`）。

ACPICA 读取 `\_Sx` 的函数 `acpi_get_sleep_type_data()`（`drivers/acpi/acpica/hwxface.c`）对包的长度有两种处理：包里只有 1 个元素时，SLP_TYPa 取它的低 8 位，SLP_TYPb 取它的第 8–15 位；有 2 个及以上元素时分别取前两个元素（`hwxface.c:398-429`）。mini-vmm 用的是规范推荐的 4 元素形式。

### 7.7 关机的完整路径

有了 FADT 与 DSDT，guest 执行 `poweroff -f` 时发生的事情可以从头追到尾。

**启动时的准备。** `acpi_bus_init()` 在解释器就绪后调用 `acpi_sleep_init()`（`drivers/acpi/sleep.c:1073`）。这个函数先无条件把 S0 标为支持，然后调用 `acpi_sleep_state_supported(ACPI_STATE_S5)`，后者求值 `\_S5`；成功后注册两个系统关机回调 `acpi_power_off_prepare()` 与 `acpi_power_off()`，优先级为 `SYS_OFF_PRIO_FIRMWARE`，最后打印支持的状态列表，即日志中的 `ACPI: PM: (supports S0 S5)`。mini-vmm 的 DSDT 没有 `\_S1` 到 `\_S4`，所以列表里只有这两项。

**关机时。** 内核关机流程先调用 prepare 回调 `acpi_power_off_prepare()`：`acpi_sleep_prepare(ACPI_STATE_S5)` 经 `acpi_enter_sleep_state_prep()` 取得 SLP_TYP，并尝试执行可选的 `\_PTS`（Prepare To Sleep）与 `\_SST`（System Status）方法，mini-vmm 没有定义它们，ACPICA 跳过；随后禁用所有 GPE。然后调用 `acpi_power_off()`：关闭本地中断，调用 `acpi_enter_sleep_state(ACPI_STATE_S5)`，最终进入 `acpi_hw_legacy_sleep()`（`drivers/acpi/acpica/hwsleep.c:30`）。

**寄存器序列。** `acpi_hw_legacy_sleep()` 对 PM1 寄存器的操作顺序如下，右列是 mini-vmm 的 `pm_write()`（`src/boot/acpi.c:331`）对每一步的处理：

| 步骤 | 访问 | 目的 | mini-vmm 的处理 |
|---|---|---|---|
| 1 | 写 PM1_STS，WAK_STS（第 15 位）为 1 | 清除唤醒状态 | 写 1 清零 |
| 2 | 写 GPE 状态与使能寄存器 | 禁用并清除所有 GPE | 没有 GPE 块，ACPICA 跳过 |
| 3 | 写 PM1_STS，全部固定事件状态位为 1 | 清除所有固定事件状态 | 写 1 清零 |
| 4 | 读 PM1_CNT | 取当前控制寄存器的值 | 返回 `cnt \| SCI_EN` |
| 5 | 写 PM1_CNT，清除 SLP_TYP 与 SLP_EN 后填入 SLP_TYP = 5 | 先设置睡眠类型 | 保存为 `cnt`，SLP_EN 未置位，不退出 |
| 6 | 写 PM1_CNT，在上一步的基础上再置 SLP_EN（第 13 位） | 进入睡眠 | SLP_EN 置位且 SLP_TYP = 5，打印 `guest requested poweroff via ACPI S5`，返回 `VMM_ERR_EXIT`，VM 退出 |

实际的输出是这样的（guest 最后两行与 VMM 的两行交替出现）：

```text
[guest /]# poweroff -f
[    9.420494] ACPI: PM: Preparing to enter system sleep state S5
[    9.422045] reboot: Power down
[INFO] guest requested poweroff via ACPI S5
[INFO] --- left guest (ok) ---
```

第一行来自 `acpi_sleep_prepare()`，第二行是内核在调用关机回调之前打印的，此后 guest 内再没有输出，因为第 6 步的写入直接让 VM 退出了。

分两次写 PM1_CNT 是规范的要求：先写睡眠类型，再单独置 SLP_EN，避免硬件在类型字段尚未稳定时就开始状态转换。mini-vmm 的实现只在第 6 步做出反应，与这个顺序完全吻合。在第 6 步之前，ACPICA 还会在 S4 以下的状态执行 `ACPI_FLUSH_CPU_CACHE()`（即 `WBINVD`），S5 不做这一步。

一个 VMM 设计上的细节：PM1 设备的 `pm_read()` 对访问宽度与偏移做了统一处理，把 `[0x600, 0x606)` 当作 6 字节的小端寄存器文件（`acpi.c:313-314` 的注释）。ACPICA 访问 PM1 寄存器的宽度由 GAS 的 `access_width` 或寄存器长度决定，PM1_STS 与 PM1_EN 各 16 位，PM1_CNT 16 位；但其他 OS 或将来的 ACPICA 版本可能按字节访问，这种“寄存器文件”式的实现对访问宽度不敏感，比按端口逐个 `switch` 更稳健。

### 7.8 一个完整的 DSDT 通常还有什么

mini-vmm 的 DSDT 是能让 Linux ACPI 子系统正常初始化的最小集合。对照启动日志，可以看出缺少的内容各自导致了什么：

| 通常存在的对象 | 作用 | mini-vmm 缺少它的后果 |
|---|---|---|
| `\_SB.PCI0`（`PNP0A03`/`PNP0A08`）及其 `_CRS`、`_PRT` | 描述 PCI 主桥、它转发的地址窗口、PCI INTx 到 GSI 的路由 | 日志 `PCI: Using host bridge windows from ACPI` 之后没有发现任何主桥；PCI 的探测在更早就因为没有配置空间访问方式而放弃（第 10 节） |
| `\_SB.PCI0.ISA` 下的 `PNP0501`（串口）、`PNP0303`（键盘）、`PNP0B00`（RTC）、`PNP0100`（PIT）等 | 让 PnP 子系统枚举 ISA 设备及其资源 | `pnp: PnP ACPI: found 0 devices`；i8042、RTC 驱动退回到硬编码的传统地址 |
| `\_SB.CPUx`（`ACPI0007` 设备或 `Processor` 对象） | 与 MADT 中 LAPIC 条目的 ACPI 处理器 UID 对应，承载 `_CST`、`_PSS` 等电源管理方法 | ACPI 处理器驱动不绑定任何设备，cpuidle 只用 `hlt`；这对 VM 恰好是合适的 |
| `\_S3`、`\_S4` | 挂起到内存、挂起到磁盘 | 只支持 S0 与 S5 |
| `\_PIC` 方法 | 让 OS 告诉固件自己使用 PIC 还是 APIC 模式 | 无影响：Linux 在 `acpi_bus_init_irq()`（`drivers/acpi/bus.c`）打印 `ACPI: Using IOAPIC for interrupt routing` 之后调用它，返回 `AE_NOT_FOUND` 时直接忽略 |

这些对象都可以以后逐步补充。它们的共同点是：每增加一个对象，就在 VMM 的设备模型与 guest 的驱动之间增加一份需要保持一致的契约。

## 8. MADT：CPU 与中断控制器的清单

### 8.1 表头与 PCAT_COMPAT

MADT（Multiple APIC Description Table，签名 `APIC`）承担了 MP 配置表的全部职责，并且扩展到了 x2APIC、ARM GIC、RISC-V 等多种中断架构。它的结构是 44 字节的固定部分加上一串变长子表：

| 偏移 | 大小 | 字段 | 含义 | mini-vmm 的值 |
|---|---|---|---|---|
| 0 | 36 | 通用表头 | `APIC`，版本 5 | 长度 94 |
| 36 | 4 | Local Interrupt Controller Address | LAPIC 的 32 位物理地址 | `0xfee00000` |
| 40 | 4 | Flags | bit 0 PCAT_COMPAT：系统同时有 8259A | 1 |
| 44 | 变长 | 子表 | 每个子表以“类型、长度”两个字节开头 | 6 个 |

完整的字节与 iasl 的解码（用 ACPICA 20241212 版的 `iasl -d` 反汇编 mini-vmm 生成的二进制表，无任何警告）：

```text

e01e0: 4d 49 4e 49 56 4d 4d 20 01 00 00 00 4d 56 4d 4d
e01f0: 01 00 00 00 00 00 e0 fe 01 00 00 00               lapic=0xfee00000 flags=PCAT_COMPAT
e01fc:                                     00 08 00 00 01 00 00 00   LAPIC uid=0 id=0 enabled
e0204: 00 08 01 01 01 00 00 00                                       LAPIC uid=1 id=1 enabled
e020c: 00 08 02 02 01 00 00 00                                       LAPIC uid=2 id=2 enabled
e0214: 00 08 03 03 01 00 00 00                                       LAPIC uid=3 id=3 enabled
e021c: 01 0c 04 00 00 00 c0 fe 00 00 00 00                           IOAPIC id=4 addr=0xfec00000 gsi_base=0
e0228: 04 06 ff 00 00 01                                             LAPIC_NMI uid=0xff flags=0 LINT1
```

```text
[024h 0036 004h]          Local Apic Address : FEE00000
[028h 0040 004h]       Flags (decoded below) : 00000001
                         PC-AT Compatibility : 1
[02Ch 0044 001h]               Subtable Type : 00 [Processor Local APIC]
[02Dh 0045 001h]                      Length : 08
[02Eh 0046 001h]                Processor ID : 00
[02Fh 0047 001h]               Local Apic ID : 00
[030h 0048 004h]       Flags (decoded below) : 00000001
                           Processor Enabled : 1
                      Runtime Online Capable : 0
...
[04Ch 0076 001h]               Subtable Type : 01 [I/O APIC]
[04Eh 0078 001h]                 I/O Apic ID : 04
[050h 0080 004h]                     Address : FEC00000
[054h 0084 004h]                   Interrupt : 00000000
```

`acpi_parse_madt()`（`arch/x86/kernel/acpi/boot.c:132`）处理表头：LAPIC 地址非零时记入 `acpi_lapic_addr`；PCAT_COMPAT 置位时调用 `legacy_pic_pcat_compat()`；再根据 FADT 版本决定是否支持 Online Capable 位（8.3 节）；最后调用 `default_acpi_madt_oem_check()`，让各个 APIC 驱动根据 OEM ID 或 FADT 标志决定是否由自己接管（7.3 节的 `apic_physflat` 就是在这里被选中的）。

PCAT_COMPAT 的作用在 v6.6 中非常具体。`legacy_pic_pcat_compat()`（`arch/x86/kernel/i8259.c:452`）只设置一个 `pcat_compat` 标志，它在 `probe_8259A()` 里起作用（`i8259.c:322`）：标志为真时直接认定 8259A 存在，跳过“写 IMR 再读回”的探测。标志为假时，内核向从片 IMR 写 `0xff`、向主片 IMR 写一个探测值再读回，不相等就打印 `Using NULL legacy PIC` 并换上空实现。卷四 1.7 节讲过，mini-vmm 用 `KVM_CREATE_IRQCHIP` 创建了内核态 8259A，探测本来就能通过；置上 PCAT_COMPAT 让结果不依赖一次端口读写，与真实 PC 的固件保持一致。

### 8.2 子表类型

MADT 的子表类型在 `include/acpi/actbl2.h:871-900` 中定义到 27，x86 平台用到的是下面这些：

| 类型 | 名称 | 长度 | 用途 | Linux 解析函数 |
|---|---|---|---|---|
| 0 | Processor Local APIC | 8 | 一颗 CPU，APIC ID 小于 255 | `acpi_parse_lapic()` |
| 1 | I/O APIC | 12 | 一颗 IOAPIC | `acpi_parse_ioapic()` |
| 2 | Interrupt Source Override | 10 | ISA IRQ 与 GSI 的非恒等映射，或极性、触发方式的改变 | `acpi_parse_int_src_ovr()` |
| 3 | NMI Source | 8 | 某个 GSI 是 NMI | `acpi_parse_nmi_src()`，只打印 |
| 4 | Local APIC NMI | 6 | NMI 接在哪个 LINT 上 | `acpi_parse_lapic_nmi()` |
| 5 | Local APIC Address Override | 12 | LAPIC 的 64 位地址 | `acpi_parse_lapic_addr_ovr()` |
| 9 | Processor Local x2APIC | 16 | 一颗 CPU，32 位 APIC ID | `acpi_parse_x2apic()` |
| 10 | Local x2APIC NMI | 12 | x2APIC 版的 LAPIC NMI | `acpi_parse_x2apic_nmi()` |
| 16 | Multiprocessor Wakeup | 16 | 用邮箱而不是 INIT/SIPI 唤醒 AP（TDX 等机密计算场景） | `acpi_parse_mp_wake()` |

子表以“类型 + 长度”自描述，所以解析器可以跳过不认识的类型；但 Linux 用 `BAD_MADT_ENTRY()` 宏检查每个认识的子表：长度字段必须不小于该类型结构体的大小，并且不能越过表尾，否则整个 MADT 解析失败，`acpi_process_madt()` 打印 `Invalid BIOS MADT, disabling ACPI` 并关闭 ACPI。mini-vmm 在 `acpi.c:128-133` 用 `_Static_assert` 固定了三种子表的大小，从源头上杜绝了长度写错的可能。

### 8.3 LAPIC 条目：处理器的登记

Processor Local APIC 子表的布局：

| 偏移 | 大小 | 字段 | 含义 |
|---|---|---|---|
| 0 | 1 | Type | 0 |
| 1 | 1 | Length | 8 |
| 2 | 1 | ACPI Processor UID | 与 DSDT 中处理器对象的 `_UID` 或 `Processor` 声明中的 ID 对应 |
| 3 | 1 | APIC ID | 这颗 CPU 的 LAPIC ID |
| 4 | 4 | Flags | bit 0 Enabled；bit 1 Online Capable（ACPI 6.3 起） |

Linux 的处理在 `acpi_parse_lapic()`（`boot.c:256`）：

1. APIC ID 为 `0xff` 的条目被忽略。这个值在 xAPIC 中是广播地址，真实固件用它表示“占位但不存在”的处理器。
2. 用 `acpi_is_processor_usable()` 判断是否登记。
3. 调用 `acpi_register_lapic(apic_id, uid, enabled)`：Enabled 位为 0 时计入 `disabled_cpus`；为 1 时调用 `generic_processor_info()` 分配一个逻辑 CPU 号，并记录 `x86_cpu_to_acpiid`。

第 2 步的判断依赖 FADT 声明的 ACPI 版本，`acpi_parse_madt()` 在 FADT 版本高于 6、或等于 6 且 Minor Version 不低于 3 时设置 `acpi_support_online_capable`：

```c
static bool __init acpi_is_processor_usable(u32 lapic_flags)
{
	if (lapic_flags & ACPI_MADT_ENABLED)
		return true;

	if (!acpi_support_online_capable ||
	    (lapic_flags & ACPI_MADT_ONLINE_CAPABLE))
		return true;

	return false;
}
```

把组合列出来：

| Enabled | Online Capable | 平台声明 ACPI 6.3 之前 | 平台声明 ACPI 6.3 及之后 |
|---|---|---|---|
| 1 | 任意 | 在线 CPU | 在线 CPU |
| 0 | 0 | 可热插拔 CPU（计入 `disabled_cpus`） | **完全忽略** |
| 0 | 1 | 可热插拔 CPU | 可热插拔 CPU |

mini-vmm 的 FADT 声明 ACPI 6.4，所以它如果将来要预留可热插拔的 vCPU，必须同时设置 Online Capable 位，只清 Enabled 位的条目会被当作不存在。启动日志中 `smpboot: Allowing 4 CPUs, 0 hotplug CPUs` 来自 `prefill_possible_map()`（`arch/x86/kernel/smpboot.c:1296`）：可能的 CPU 数等于在线数加上 `disabled_cpus`，两者都来自这里的登记。

**BSP 不由表决定。** MADT 没有“引导处理器”标志。`generic_processor_info()`（`arch/x86/kernel/apic/apic.c:2436`）开头检查 `cpuid_to_apicid[0]` 是否已经登记，没有就 panic：`Boot CPU APIC not registered yet`。BSP 的 APIC ID 是在更早的 `early_acpi_boot_init()` 阶段登记的：`early_acpi_parse_madt_lapic_addr_ovr()` 处理完地址覆盖子表后调用 `register_lapic_address()`，后者把 LAPIC 映射到 fixmap，并通过 `apic_read_boot_cpu_id()` 读取**当前正在运行的 CPU** 的 LAPIC ID 寄存器。之后遇到与这个 ID 相同的条目，`generic_processor_info()` 直接返回逻辑 CPU 0。这也说明了为什么 MADT 表头中的 LAPIC 地址必须与 KVM 的 `IA32_APIC_BASE` 一致：内核读 BSP 的 APIC ID 用的就是这个地址。

**逻辑 CPU 号由条目顺序决定。** 其余 CPU 的逻辑号由 `allocate_logical_cpuid()`（`apic.c:2390`）按遇到的顺序依次分配。mini-vmm 按 APIC ID 升序写条目，BSP 的 APIC ID 为 0，于是逻辑 CPU 号恰好等于 APIC ID 等于 vCPU 编号。这种一致性不是必然的：如果 VMM 把条目倒序写，或者 APIC ID 不连续（例如为了模拟多个 socket 而按 2 的幂对齐），逻辑 CPU 号与 vCPU 线程编号就会错开，调试时要格外小心。卷六会讨论 APIC ID 与 CPUID 拓扑叶的一致性。

**何时需要 x2APIC 条目。** 类型 0 的 APIC ID 只有 8 位，而 `0xff` 又被保留，所以它最多描述 APIC ID 为 0 到 254 的 CPU。APIC ID 不小于 255 的 CPU 必须用类型 9 的 x2APIC 子表描述，它的 APIC ID 与 UID 都是 32 位。`acpi_parse_madt_lapic_entries()` 用 `acpi_table_parse_entries_array()` 在一趟遍历中同时处理类型 0 与类型 9。mini-vmm 的 vCPU 上限是 `VMM_MAX_VCPUS = 32`（`include/vmm.h`），远在这个限制之内；另外 MP 表只占 `0x9fc00` 起的 1 KiB，按每颗 CPU 一个 20 字节条目算，最多容纳 40 颗，`mptable_setup()` 在装不下时报错（`mptable.c:134-138`）。

### 8.4 IOAPIC 条目

I/O APIC 子表的布局：

| 偏移 | 大小 | 字段 | mini-vmm 的值 |
|---|---|---|---|
| 0 | 1 | Type | 1 |
| 1 | 1 | Length | 12 |
| 2 | 1 | I/O APIC ID | `nr_cpus`，4 个 vCPU 时为 4 |
| 3 | 1 | Reserved | 0 |
| 4 | 4 | I/O APIC Address | `0xfec00000` |
| 8 | 4 | Global System Interrupt Base | 0 |

与 MP 表的 IOAPIC 条目相比，最大的区别是多了 **GSI 基址**。GSI（Global System Interrupt）是 ACPI 引入的全局中断编号：系统中每颗 IOAPIC 的每个引脚都有一个唯一的 GSI，第一颗 IOAPIC 的引脚 `n` 对应 `GSI 基址 + n`。卷四 2.7 节的 KVM GSI 路由表用的就是同一套编号。

`acpi_parse_ioapic()`（`boot.c:519`）调用 `mp_register_ioapic(id, address, gsi_base, &cfg)`；GSI 基址小于 16 的 IOAPIC 使用“legacy”类型的中断域，ISA IRQ 号与 Linux 的 IRQ 号静态对应，其余 IOAPIC 使用动态分配。引脚数由 `mp_register_ioapic()` 读 IOAPIC 版本寄存器得到，所以 MADT 中没有引脚数这个字段，日志中的 `GSI 0-23` 是 KVM 模拟的 IOAPIC 自己报告的。

### 8.5 Interrupt Source Override

Interrupt Source Override（ISO）子表 10 字节，描述“某条 ISA IRQ 没有接在与之同号的 GSI 上”或“极性、触发方式与 ISA 默认不同”：

| 偏移 | 大小 | 字段 | 含义 |
|---|---|---|---|
| 0 | 1 | Type | 2 |
| 1 | 1 | Length | 10 |
| 2 | 1 | Bus | 0，表示 ISA |
| 3 | 1 | Source | ISA IRQ 号 |
| 4 | 4 | Global System Interrupt | 实际接到的 GSI |
| 8 | 2 | Flags | 与 MP 表相同的 MPS INTI 标志：bit 1:0 极性，bit 3:2 触发方式 |

Linux 的处理分三步，都在 `acpi_parse_madt_ioapic_entries()`（`boot.c:1262`）里：

1. 逐条处理 ISO（`acpi_parse_int_src_ovr()`，`boot.c:579`）。源 IRQ 等于 FADT 中 SCI_INT 的条目交给 `acpi_sci_ioapic_setup()`；源 IRQ 为 0 的条目受两个命令行参数影响：`acpi_skip_timer_override` 让内核忽略它，`acpi_fix_pin2_polarity` 在它指向 GSI 2 时强制改为高电平有效。其余条目通过 `mp_override_legacy_irq()` 写入 `mp_irqs[]`。
2. 如果没有针对 SCI 的 ISO，调用 `acpi_sci_ioapic_setup()` 伪造一条，把 SCI 设为低电平有效的电平触发（7.5 节）。
3. `mp_config_acpi_legacy_irqs()`（`boot.c:1192`）为 ISA IRQ 0–15 中还没有映射的补上恒等映射，极性与触发方式为“遵从总线默认”。这一步会跳过两类 IRQ：源 IRQ 已经被 ISO 映射过的，以及目标引脚已经被别的 ISO 占用的。

mini-vmm 的 MADT 不含任何 ISO，于是第 3 步为 16 条 ISA IRQ 全部建立恒等映射，第 2 步把 IRQ 9 改成电平触发。`acpi.c:256-257` 的注释说明了原因：“Linux 在没有 override 时默认就是恒等，而 KVM 的默认路由也是恒等”。

作为对照，QEMU 的 PC 机型会在 MADT 中放一条 `Source = 0, GSI = 2` 的 ISO，因为它把 PIT 接在 IOAPIC 的引脚 2 上（卷四 2.7 节）。这时第 3 步会同时跳过 IRQ 0（已被映射）与 IRQ 2（引脚 2 已被占用），IRQ 2 本来就是 8259A 的级联线，不需要映射。如果 VMM 使用 KVM 的默认 GSI 路由却照抄了这条 ISO，Linux 会在引脚 2 上等时钟中断，而 KVM 把 PIT 的中断送到了引脚 0，结果与 MP 表写错的后果相同：时钟中断丢失。ISO 条目在日志中以 `pr_info` 级别打印，形如 `ACPI: INT_SRC_OVR (bus 0 bus_irq 0 global_irq 2 dfl dfl)`；mini-vmm 的日志中没有这样的行，正说明没有覆盖。

### 8.6 NMI 相关的两种子表

Local APIC NMI 子表 6 字节：类型 4、长度 6、ACPI 处理器 UID（`0xff` 表示全部处理器）、2 字节 MPS INTI 标志、LINT 编号。它在日志中打印为：

```text
ACPI: LAPIC_NMI (acpi_id[0xff] dfl dfl lint[0x1])
```

其中两个 `dfl` 分别是极性与触发方式，取值来自 `drivers/acpi/tables.c:33-34` 的两个字符串表 `{ "dfl", "high", "res", "low" }` 与 `{ "dfl", "edge", "res", "level" }`。与 MP 表的本地中断条目一样，Linux 对它只做一件事：LINT 编号不是 1 时打印 `NMI not connected to LINT 1!`（`boot.c:340-341`）。LINT1 的实际编程由 `setup_local_APIC()` 按 PC 惯例完成，只有 BSP 的 LINT1 不屏蔽（卷四 3.6 节）。

NMI Source 子表把一个 GSI 声明为 NMI 输入。v6.6 的 `acpi_parse_nmi_src()`（`boot.c:624`）只打印一行，函数体里留着一句注释 `/* TBD: Support nimsrc entries? */`。mini-vmm 没有生成这种子表。

### 8.7 解析的时序与失败模式

把 MADT 的解析过程和第 5 节的 MP 表放在一起，完整时序是：

| 阶段 | 函数 | MADT 中被处理的内容 | 结果 |
|---|---|---|---|
| `early_acpi_boot_init()` | `early_acpi_process_madt()` | 表头；类型 5 地址覆盖 | `register_lapic_address()`，登记 BSP 的 APIC ID；`acpi_lapic = 1` |
| `acpi_boot_init()` | `acpi_process_madt()` → `acpi_parse_madt_lapic_entries()` | 类型 7（SAPIC）；类型 0 与 9；类型 10 与 4 | 登记全部 CPU；`acpi_lapic = 1` |
| 同上 | `acpi_parse_madt_ioapic_entries()` | 类型 1；类型 2；SCI 伪造覆盖；ISA 恒等映射；类型 3 | 登记 IOAPIC 与 `mp_irqs[]`；`acpi_ioapic = 1` |
| 同上 | `acpi_table_parse_madt(ACPI_MADT_TYPE_MULTIPROC_WAKEUP, ...)` | 类型 16 | 仅在机密计算平台上有效 |
| `get_smp_config()` | `default_get_smp_config()` | 无 | `acpi_lapic && acpi_ioapic` 为真，MP 表内容不解析 |

几种典型的失败及其日志：

| VMM 的错误 | Linux 的反应 | 日志 |
|---|---|---|
| 没有任何 LAPIC 条目 | `acpi_parse_madt_lapic_entries()` 返回 `-ENODEV`，IOAPIC 条目也不再解析；但 `acpi_lapic` 早在 `early_acpi_process_madt()` 中就已置 1，于是 `default_get_smp_config()` 虽然会读 MP 表，却跳过其中的处理器条目，最终多半只剩 BSP 一颗 CPU | `No LAPIC entries present` |
| 某个子表的 Length 小于结构体大小 | 解析失败，关闭 ACPI | `Invalid BIOS MADT, disabling ACPI` |
| 没有 IOAPIC 条目 | 只用 MADT 的 CPU 信息，IOAPIC 与中断条目改从 MP 表取 | `No IOAPIC entries present`、`Using ACPI for processor (LAPIC) configuration information` |
| 根本没有 MADT，但有 MP 表 | MP 表也被放弃，单处理器 PIC 模式 | `No APIC-table, disabling MPS` |
| LAPIC 地址与 KVM 的 APIC 基址不一致 | BSP 的 APIC ID 从错误的地址读取；此后所有 LAPIC 访问都落到没有设备的 GPA 上 | 早期无明显错误，之后定时器与 IPI 全部失效 |
| 两个 LAPIC 条目的 APIC ID 相同 | `allocate_logical_cpuid()` 返回同一个逻辑号，第二颗 CPU 实际上不会被启动 | 可能的 CPU 数少于 vCPU 线程数 |

最后两行在 KVM 下尤其隐蔽，因为 KVM 在复位 LAPIC 时把 ID 寄存器写成 `vcpu_id`（卷四 3.2 节），MADT 中写的 APIC ID 必须与之逐一对应。VMM 创建了 4 个 vCPU 线程，MADT 却只描述了 3 颗 CPU 时，第 4 个 vCPU 线程会一直停在 KVM 的 `KVM_MP_STATE_UNINITIALIZED` 状态里，永远等不到 INIT/SIPI，从 VMM 看就是一个永远阻塞在 `KVM_RUN` 里的线程。

## 9. 一致性约束：表、KVM 与设备模型必须说同一种话

前面各节分散提到了很多“这里必须与那里一致”的要求。这些约束是 VMM 固件代码最容易出错、也最难排查的地方，因为 Linux 很少验证表中的描述与硬件实际是否相符，它相信表，然后在后面某个完全不相关的地方失败。本节把它们集中列出，并按“描述方”与“实现方”配对。

### 9.1 地址与编号

| 约束 | 描述方 | 实现方 | mini-vmm 的取值 | 不一致的后果 |
|---|---|---|---|---|
| LAPIC 物理地址 | MADT 表头、MP 配置表头 | KVM：vCPU 复位时 `IA32_APIC_BASE` 为 `0xFEE00000`（卷四 3.1 节） | `0xfee00000` | BSP 的 APIC ID 读错；所有 LAPIC 访问落空，定时器与 IPI 失效 |
| IOAPIC 物理地址 | MADT 的 IOAPIC 子表、MP 的 IOAPIC 条目 | KVM：`kvm_ioapic_init()` 把 IOAPIC 固定注册在 `IOAPIC_DEFAULT_BASE_ADDRESS = 0xfec00000`，长度 `0x100`（`arch/x86/kvm/ioapic.h:18-19`，`ioapic.c:671`、`ioapic.c:700`） | `0xfec00000` | 所有外部中断无法编程，`..TIMER` 检查失败 |
| IOAPIC 引脚数 | 无（Linux 读版本寄存器） | KVM：`IOAPIC_NUM_PINS = 24` | 24 | 不存在不一致的可能，这正是规范不在表中重复它的原因 |
| IOAPIC ID | MADT、MP 表 | KVM 的 IOAPIC ID 寄存器可由 guest 改写 | `nr_cpus` | 与某个 LAPIC ID 重复时，Linux 的 `io_apic_unique_id()` 另选一个 ID（卷四 2.1 节）；两张表之间不一致时，只有被采用的那张起作用 |
| LAPIC ID 集合 | MADT 的 LAPIC 子表、MP 的处理器条目 | KVM：LAPIC 的 ID 寄存器复位为 `vcpu_id`，vCPU 由 `KVM_CREATE_VCPU` 的参数决定 | 0 到 `nr_cpus - 1` | 表中缺少的 vCPU 永远不会被唤醒，线程阻塞在 `KVM_RUN` 中；表中多出的 CPU，Linux 发出 INIT/SIPI 后无人响应，等待超时后放弃 |
| BSP | 无（Linux 读当前 CPU 的 APIC ID） | KVM：`kvm->arch.bsp_vcpu_id`，默认 0，可用 `KVM_SET_BOOT_CPU_ID` 修改 | vCPU 0 | VMM 必须让 BSP 对应的那个 vCPU 线程先按启动协议设置寄存器，其余 vCPU 保持复位状态等待 SIPI |

### 9.2 中断拓扑

| 约束 | 描述方 | 实现方 | mini-vmm 的取值 | 不一致的后果 |
|---|---|---|---|---|
| ISA IRQ 到 GSI 的映射 | MADT 的 ISO（缺省即恒等）、MP 的 I/O 中断条目 | KVM 默认 GSI 路由：GSI 0–15 同时送 8259A 与 IOAPIC 的同号引脚；VMM 也可用 `KVM_SET_GSI_ROUTING` 自定义（卷四 2.7 节） | 恒等，无 ISO | 最典型的是照抄 QEMU 的 `IRQ0 → GSI2`，时钟中断丢失 |
| 每个设备的 IRQ 号 | 若有 PnP：DSDT 中设备的 `_CRS`；否则驱动的硬编码默认值 | 设备模型调用 `KVM_IRQ_LINE` 时使用的 GSI | 串口 4、键盘 1、RTC 8、PIT 0 | 驱动在 A 线上等中断，设备在 B 线上发中断；驱动的超时路径被触发，通常表现为“能输出不能输入”或探测失败 |
| 触发方式 | ISA 默认边沿；SCI 默认电平；ISO 可改 | 设备模型使用 `KVM_IRQ_LINE` 的方式：边沿中断发一个 1 再发 0，电平中断保持到设备状态清除 | 串口按电平跟踪 `irq_level`（卷四提到的 `update_irq()`） | 电平设备被当成边沿处理会丢中断；边沿设备被 Linux 编程成电平会导致 remote IRR 卡住、中断风暴 |
| 极性 | ISO、MP 条目的 PO 位 | KVM 的 IOAPIC 模拟忽略极性（卷四 2.2 节） | 不涉及 | 无后果：`level = 1` 永远表示有效。VMM 不应自作主张地反转电平 |
| 8259A 存在与否 | MADT 的 PCAT_COMPAT；FADT 的 HW_REDUCED | `KVM_CREATE_IRQCHIP` 是否创建了内核态 PIC | 存在，PCAT_COMPAT 置位，不设 HW_REDUCED | 声明 HW_REDUCED 会让 Linux 放弃 PIT 与 8259A（7.4 节） |
| NMI 接线 | MADT 的 LAPIC NMI、MP 的本地中断条目 | KVM 的 LAPIC 模拟：LINT1 按 guest 编程的 LVT 处理 | LINT1 | Linux 只在不是 LINT1 时警告，不会据此改变编程 |

### 9.3 固定硬件与设备

| 约束 | 描述方 | 实现方 | mini-vmm 的取值 | 不一致的后果 |
|---|---|---|---|---|
| PM1a 事件块 | FADT 的 `PM1a_EVT_BLK` 与 `PM1_EVT_LEN` | 设备模型在对应端口注册 PIO 设备 | `0x600`，长度 4 | ACPICA 读写落在未注册的端口上；mini-vmm 对未注册端口的读返回全 1（`src/vm.c:175`），状态位全部被读成“已置位” |
| PM1a 控制块 | FADT 的 `PM1a_CNT_BLK` 与 `PM1_CNT_LEN` | 同上 | `0x604`，长度 2 | 关机写入无人响应，guest 停在关机路径上 |
| S5 的 SLP_TYP | DSDT 的 `\_S5` | PM1 设备在 `pm_write()` 中比较的值 | 5 | guest 写了 SLP_EN，VMM 却认为不是关机请求 |
| SCI 中断号 | FADT 的 `SCI_INT` | PM1 设备拉起中断时使用的 GSI | 9（当前不拉起） | 事件中断送错线 |
| 世纪寄存器 | FADT 的 `CENTURY` | RTC 模型的 CMOS 索引 | `0x32`，`rtc.c` 中的 `RTC_CENTURY` | 年份解释错误，系统时间偏差 100 年的整数倍 |
| 8042 是否存在 | FADT 的 `IAPC_BOOT_ARCH` bit 1 | i8042 设备模型 | 存在 | 声明不存在则驱动不探测；声明存在而没有模型，驱动的探测结果取决于未注册端口读回什么值，通常以 `i8042: No controller found` 或命令超时告终 |
| RTC 是否存在 | FADT 的 `IAPC_BOOT_ARCH` bit 5 | RTC 设备模型 | 存在 | 同上 |

### 9.4 内存

| 约束 | 描述方 | 实现方 | mini-vmm 的取值 | 不一致的后果 |
|---|---|---|---|---|
| RAM 区间 | E820 中类型为 1 的表项 | KVM memslot | 两者一致，都在 3 GiB 以下 | E820 报 RAM 而 memslot 不覆盖：大量 MMIO 退出，guest 崩溃（4.3 节） |
| MMIO 区域 | E820 中不报 RAM | KVM 的内核态设备（LAPIC、IOAPIC）与 VMM 的 MMIO 设备 | 3 GiB 以下只有 RAM，MMIO 在 `0xFEC00000` 起 | 访问只有在 NPT 找不到 memslot 时才会退出并分派给 KVM 的内核态设备或 VMM；memslot 与设备地址重叠时，guest 直接读写这块 RAM，设备收不到访问 |
| 表所在区域 | ACPI 表、MP 表必须在非 RAM 区 | E820 类型 2 | `[0x9fc00, 0x100000)` | 内核可能把表所在页分配出去（6.4 节） |
| 1 MiB 以下的 RAM | E820 | memslot | `[0, 0x9fc00)` | 没有实模式跳板，AP 无法启动，`init_real_mode()` panic |
| 内核装载地址 | ELF 的 `p_paddr` | memslot 与 E820 的 RAM | `0x1000000` 起 | 不在 RAM 中：`e820_add_kernel_range()` 报警告并强行补成 RAM；装载地址未按 2 MiB 对齐：`__startup_64()` 静默死循环（2.2 节） |

### 9.5 两张表之间

mini-vmm 同时提供 MP 表和 ACPI 表，它们之间也存在一致性问题。Linux 只采用其中一张（5.5 节），所以两张表不一致不会在正常启动中暴露，只会在切换到另一张表时显现：比如某次调试时加了 `acpi=off`，或者换了一个没有开 `CONFIG_ACPI` 的内核。mini-vmm 的做法是让两份构造代码共享同一组常量：`MP_LAPIC_BASE`、`MP_IOAPIC_BASE` 定义在 `include/boot/mptable.h`，`acpi.c` 直接引用它们；IOAPIC ID 在两处都取 `nr_cpus`，并在 `acpi.c:251` 注释“和 MP table 保持一致”。更彻底的做法是从同一份平台描述结构生成两张表，这样“一致”就不再依赖注释。5.6 节的 `acpi=off` 实验则提供了一个低成本的回归测试：两种启动方式都应该得到 4 颗 CPU 和工作在引脚 0 上的时钟。

## 10. 读懂启动日志：固件缺席的痕迹

mini-vmm 的 guest 启动日志里有十几行看起来像警告或错误的信息。它们几乎都不是故障，而是“某项固件信息不存在，内核走了后备路径”的记录。逐行弄清它们的来源，是判断一个新出现的日志行到底是不是问题的前提。下表按日志出现的顺序排列，所有行都来自第 1 节引用的那份启动日志。

## 11. 验证与排障

### 11.1 在 host 端检查 VMM 生成的字节

固件表的构造函数是纯函数：输入内存布局和 vCPU 数，输出一段字节。这让它们可以脱离 KVM 在 host 端单独运行和检查。本卷的全部十六进制转储都是这样得到的：写一个几十行的桩文件，实现 `gpa_to_hva()`、`mem_write()`、`vmm_log()`、`vmm_register_pio()` 等接口，让它们操作一块 `calloc` 出来的平坦缓冲区；然后把 `src/boot/acpi.c`、`mptable.c`、`zeropage.c` 原样编译进来：

```sh
gcc -O0 -Wall -Iinclude -o tbldump stub.c \
    src/boot/acpi.c src/boot/mptable.c src/boot/zeropage.c
./tbldump            # 打印各表的十六进制转储，并把每张 ACPI 表写成 xxxx.dat
iasl -d apic.dat     # 反汇编为 apic.dsl
```

`iasl` 是 ACPICA 项目的 ASL 编译器兼反汇编器，从 ACPICA 的源码包执行 `make iasl` 即可得到，不需要 root 权限。它对每个字段按规范解码并标注含义，校验和、长度不对时会在输出中给出提示；本卷用 20241212 版反汇编 mini-vmm 的 XSDT、FADT、DSDT、MADT，均无任何警告，DSDT 反汇编出的正是 7.6 节那一行 `Name (_S5, Package (0x04) { 0x05, 0x05, Zero, Zero })`。这个办法值得做成 mini-vmm 的一个单元测试：表结构的任何回归都能在不启动 guest 的情况下发现。注意 `iasl -d` 把发现的问题写在生成的 `.dsl` 文件里（例如校验和错误会在该字段后注释 `Incorrect checksum, should be 48`，子表长度为 0 会写 `Invalid zero length subtable`），标准输出里看不到，自动化检查时要去 `.dsl` 中搜索。

mini-vmm 自己也提供了一个运行时手段：`--dump GPA:LEN` 选项在 VM 退出时把一段 guest 内存以十六进制打印出来。`--dump e0000:560` 可以看到 guest 实际运行结束时 ACPI 表区域的内容，用来确认 guest 没有改写它们。

### 11.2 在 guest 内检查内核看到了什么

| 接口 | 内容 | 在 mini-vmm guest 中的实际输出 |
|---|---|---|
| `/sys/firmware/acpi/tables/` | 内核装载的每张 ACPI 表的原始字节，文件名为签名 | `APIC  DSDT  FACP  data  dynamic`；`hexdump -C` 读出的 DSDT 与 7.6 节的字节完全相同 |
| `/sys/firmware/memmap/*/{start,end,type}` | `e820_table_firmware`，即 VMM 传入、未经内核修改的 E820 | `0x0 0x9fbff System RAM`、`0x9fc00 0xfffff Reserved`、`0x100000 0x1fffffff System RAM` |
| `/sys/kernel/boot_params/version`、`data` | `boot_params.hdr.version`；整个 boot_params 的 4096 字节 | `0x020f` |
| `/proc/sys/kernel/bootloader_type`、`bootloader_version` | 由 `type_of_loader` 推导 | `255`、`15` |
| `/proc/iomem` | E820 与内核镜像形成的资源树 | `00000000-00000fff : Reserved`（第 0 页已被改成保留）、`0009fc00-000fffff : Reserved` 及其下的 `000f0000-000fffff : System ROM` 等 |
| `/proc/interrupts` | 每条 IRQ 在各 CPU 上的计数与触发方式 | IRQ 9 为 `IO-APIC 9-fasteoi acpi`，计数为 0（7.5 节） |
| `dmesg` | 第 10 节的全部日志 | |

`/sys/firmware/memmap` 与 `/proc/iomem` 的第一行对比很能说明问题：前者是 VMM 传入的原样，从 0 开始就是 RAM；后者是内核处理之后的结果，第 0 页已经被 `trim_bios_range()` 改成了保留（4.2 节）。

initramfs 里通常没有 `acpidump` 和 `iasl`，但 busybox 的 `hexdump -C` 足以把 `/sys/firmware/acpi/tables/` 下的表打印到串口，再在 host 端从日志里还原成二进制文件交给 `iasl`。

### 11.3 命令行开关

以下命令行参数都在 guest v6.6 中有效，用来隔离固件表的问题：

| 参数 | 作用 | 典型用途 |
|---|---|---|
| `acpi=off` | 不解析任何 ACPI 表，也不启用解释器 | 强制走 MP 表路径（5.6 节）；判断问题是否与 ACPI 有关 |
| `acpi=noirq` | 解析 ACPI 表，但不使用 ACPI 做中断路由 | 区分“表内容”问题与“中断路由”问题 |
| `acpi=rsdt` | 使用 RSDT 而不是 XSDT | 检查 RSDT 路径；对 mini-vmm 会导致 ACPI 被关闭（6.4 节） |
| `acpi_rsdp=0x...` | 指定 RSDP 地址（需要 `CONFIG_KEXEC`） | 绕过 boot_params 与扫描 |
| `acpi_force_table_verification` | 在早期阶段就检查表的校验和 | 让校验和错误尽早暴露 |
| `apic=verbose`、`apic=debug` | 打印 APIC 与 MP 表解析的详细过程 | 5.6 节的扫描过程与每一条中断条目就是用它打出来的 |
| `noapic` | 不使用 IOAPIC | 判断问题是否出在 IOAPIC 路由 |
| `nolapic` | 完全不使用 LAPIC | 退回单处理器 8259A 模式 |
| `nr_cpus=N`、`maxcpus=N`、`possible_cpus=N` | 限制逻辑 CPU 数量或启动的 CPU 数 | 排查 MADT 中 CPU 条目的问题 |
| `mem=`、`memmap=` | 修改内核使用的内存图 | 模拟 E820 的各种形态，而不必改 VMM |
| `acpi_skip_timer_override` | 忽略 IRQ 0 的 ISO | 验证时钟中断丢失是否由 ISO 引起（8.5 节） |
| `acpi_sci=level\|edge\|high\|low` | 覆盖 SCI 的触发方式与极性 | 实现 SCI 之后排查中断问题 |
| `loglevel=8` 或 `ignore_loglevel` | 让 `KERN_DEBUG` 级别的 printk 也输出到控制台 | 看到 `e820: update [mem ...]` 这类调试信息 |
| `earlyprintk=serial,ttyS0,115200` | 从最早期开始通过轮询串口输出 | mini-vmm 默认已开 |

注意 `loglevel=8` 只能放出直接使用 `printk(KERN_DEBUG ...)` 的信息；MADT 中 LAPIC 与 IOAPIC 子表的打印用的是 `pr_debug()`，在没有开 `CONFIG_DYNAMIC_DEBUG` 的内核里会被编译掉，guest 的 `.config` 正是如此，所以这些行无论如何都看不到，只能用 `iasl` 在 host 端检查。

### 11.4 症状对照

| 症状 | 首先怀疑 | 依据 |
|---|---|---|
| vCPU 启动后没有任何输出，也没有退出 | vmlinux 装载地址未按 2 MiB 对齐；入口地址错误 | 2.2 节 `__startup_64()` 中的两个 `for (;;)` |
| 没有 `BIOS-e820` 行，而是 `BIOS-e801` 或 `BIOS-88` | E820 只有一项或为空 | 4.2 节 `append_e820_table()` |
| `Real mode trampoline was not allocated` | 1 MiB 以下没有 RAM | 4.2 节第五步 |
| initrd 被忽略，`VFS: Unable to mount root fs` | `type_of_loader` 为 0；initrd 地址或大小为 0 | 3.3 节 |
| 命令行末尾的参数不生效 | 命令行超过 2047 字节 | 3.4 节 |
| 没有任何 `ACPI:` 表头行 | RSDP 找不到：`acpi_rsdp_addr` 为 0 且 RSDP 不在扫描区间，或扫描路径下 RSDP 校验和错误 | 6.3 节 |
| `ACPI BIOS Warning (bug): Incorrect checksum in table [XXXX]` | 该表的校验和计算错误 | 6.2 节；表仍会被使用 |
| `Required FADT field Pm1aEventBlock has zero address and/or length` | 非硬件精简平台缺少 PM1a 寄存器块 | 7.2 节 |
| `No APIC-table, disabling MPS`，只有 1 颗 CPU | 有 ACPI 表而没有 MADT | 5.5 节 |
| `Invalid BIOS MADT, disabling ACPI` | 某个 MADT 子表的长度字段错误 | 8.2 节 |
| `MPTABLE: checksum error!` 或 `BIOS bug, MP table errors detected!` | MP 配置表校验和错误 | 5.3 节 |
| `smpboot: Allowing N CPUs` 中的 N 少于 vCPU 数 | MADT 或 MP 表中缺少处理器条目，或 APIC ID 重复 | 8.3 节、8.7 节 |
| 启动卡在时钟校准，或 `..TIMER` 检查失败、`IO-APIC + timer doesn't work!` | ISA IRQ 0 的映射与 KVM 的 GSI 路由不一致；IOAPIC 地址错误 | 8.5 节、9.2 节 |
| `poweroff` 后 VM 不退出 | `\_S5` 的值与 PM1 设备约定的不一致；PM1 端口与 FADT 不一致；ACPI 被关闭 | 7.7 节、5.6 节 |
| 键盘或 `reboot=k` 不工作 | FADT 的 8042 位未置；i8042 模型未注册 | 7.3 节 |
| 系统时间差了 100 年的整数倍 | FADT 的 CENTURY 与 RTC 模型不一致 | 7.2 节 |

## 12. 本卷小结与卷六预告

**入口。** mini-vmm 走的是 vmlinux 直接启动：按 `p_paddr` 装载 ELF 的每个 `PT_LOAD` 段，用 `KVM_SET_SREGS` 直接把 vCPU 置于长模式，`RSI` 指向 boot_params，`RIP` 指向 `e_entry`。v6.6 的 `startup_64` 几乎立刻换上自己的 GDT 与页表，真正依赖 VMM 的只有长模式状态、覆盖内核镜像的恒等映射和 `RSI`；但 VMM 仍应完整遵守协议。没有解压器意味着没有 KASLR，也意味着没有人替你检查 2 MiB 对齐。

**boot_params。** 内核本体只读 setup header 中的少数几个字段，最要紧的是 `type_of_loader`（为 0 时 initrd 被忽略）、`cmd_line_ptr` 与 `ramdisk_*`。先整体清零再填写，`sentinel` 就不会触发清理。命令行上限是 2047 字节，mini-vmm 允许的 4095 字节上限需要收紧。

**E820。** 至少两项，1 MiB 以下留出 RAM 给实模式跳板，放表的区域报成保留，每一个 RAM 字节背后都要有 memslot。内核随后会修剪第 0 页与 `[0x9f000, 1 MiB)`，启动日志中的每个内存数字都可以由 VMM 的 E820 精确推出。

**MP 表与 ACPI。** 两者描述同一件事，Linux 优先 ACPI；MP 表对错误零容忍，ACPI 表对校验和几乎完全宽容。FADT 的 PM1 块、SCI、CENTURY、IAPC_BOOT_ARCH 与 Flags 各自连着一个设备模型或一段内核路径；DSDT 里 14 字节的 `\_S5` 和 PM1 设备一起构成了 VM 的关机通道。MADT 登记 CPU 与 IOAPIC，BSP 由正在运行的 CPU 自己的 APIC ID 决定，逻辑 CPU 号由条目顺序决定，ISA 中断缺省恒等映射，这与 KVM 的默认 GSI 路由正好吻合。

**一致性。** 固件表不是自说自话的文档，而是 VMM 对 guest 做出的承诺。LAPIC 与 IOAPIC 的地址、APIC ID 的集合、ISA 中断的接线、PM1 的端口、`\_S5` 的取值、世纪寄存器的索引，每一项都必须与 KVM 或设备模型的实际行为逐一对应。第 9 节的表格可以作为 VMM 固件代码的检查清单。

**写给 mini-vmm 的几条改进建议**，都来自本卷的核对过程（前三条与第四条的前半已经实现，同时加入了 bzImage 装载与“Linux 模式必须提供 `--initrd`”的检查）：

1. 把 `ZP_CMDLINE_MAX` 从 4096 改为 2048，超长时报错，避免命令行尾部被 guest 静默截断（3.4 节）。
2. 不再写入 `cmdline_size`，它是内核告诉 loader 的只读字段（3.4 节）；`zeropage.c` 里关于“协议 2.14”的注释改为“boot_params 偏移 `0x070`”（3.1 节）。
3. 把 host 端的表转储与 `iasl -d` 检查做成单元测试（11.1 节）。
4. 在 CPUID.1:ECX 置上 `hypervisor` 位，让 guest 知道自己在虚拟机里（第 10 节，卷六展开）。启动日志中 `[Firmware Bug]` 那一行对应的 HWCR 第 24 位则无法由 VMM 设置：KVM 只接受用户态写 HWCR 的第 18 位（第 10 节）。

**卷六的问题在 CPU 侧。** 本卷让 Linux 知道了“有 4 颗 CPU，APIC ID 是 0 到 3”，但还没有回答它们是怎么跑起来的。卷六将从 BSP 发出的第一个 INIT IPI 开始：实模式跳板的内容与位置、INIT 与 SIPI 在 KVM 中的模拟（`KVM_MP_STATE_UNINITIALIZED` 到 `INIT_RECEIVED` 再到 `RUNNABLE`）、vCPU 线程与 `KVM_RUN` 的阻塞关系、CPUID 拓扑叶与 APIC ID 的一致性，以及 mini-vmm 的 `smp.c` 中每一处修正 CPUID 的理由。
