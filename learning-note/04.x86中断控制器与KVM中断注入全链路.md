## 1. 8259A：一颗 8080 时代的芯片为什么还要模拟

### 1.1 引脚与三个 8 位寄存器

8259A 是一颗 28 脚的可编程中断控制器（PIC），PC/AT 上用两颗级联：主片（master）的 IR2 接从片（slave）的 INT 输出，一共 15 条可用的中断线 IRQ0–IRQ15（IRQ2 被级联占用，老设备原本接 IRQ2 的在 AT 上改接 IRQ9）。

和中断处理直接相关的引脚只有四组：

| 引脚 | 方向 | 含义 |
|---|---|---|
| IR0–IR7 | 输入 | 8 条中断请求线，设备拉高表示请求 |
| INT | 输出 | 接 CPU 的 INTR 引脚（主片）或主片的 IR2（从片） |
| INTA# | 输入 | CPU 的中断应答周期，8086 模式下连续两个脉冲 |
| CAS0–CAS2 | 双向 | 级联总线，主片在 INTA 周期里用它告诉从片“轮到你送向量了” |

芯片内部的状态几乎全部集中在三个 8 位寄存器里，每一位对应一条 IR 线：

- **IRR（Interrupt Request Register）**：哪些线在请求。边沿模式下，线上出现上升沿时置位；电平模式下，线为高时置位。
- **ISR（In-Service Register）**：哪些中断正在被 CPU 服务。INTA 第一个脉冲时，把 IRR 中优先级最高的一位搬到 ISR；EOI 命令清除 ISR 的一位。
- **IMR（Interrupt Mask Register）**：哪些线被屏蔽。被屏蔽的线仍然会在 IRR 里置位，但不会参与优先级仲裁，也不会让 INT 输出变高。

一次完整的中断握手是这样的：

```
设备拉高 IRn
   │
   ▼
IRR[n] = 1 ── IMR[n] = 1 ? ──是──► 停在 IRR，不输出
   │否
   ▼
优先级仲裁：IRn 的优先级高于 ISR 中所有已置位的位？ ──否──► 等当前服务结束
   │是
   ▼
INT 输出拉高 ──► CPU 在指令边界检查 RFLAGS.IF
   │
   ▼
CPU 发出 INTA#（第一个脉冲）：IRR[n] 搬到 ISR[n]（电平模式不清 IRR）
CPU 发出 INTA#（第二个脉冲）：8259A 把向量号 = ICW2 基址 + n 放到数据总线
   │
   ▼
CPU 用这个向量号查 IDT，进入处理程序
   │
   ▼
处理程序向 0x20 写 EOI ──► ISR[n] = 0，低优先级的挂起中断可以继续
```

这里有两个常被忽略的细节。

第一，**ISR 决定的是“能不能嵌套”**。只要 ISR 里还有一位是 1，所有优先级不高于它的中断都送不出去，哪怕 CPU 的 IF 是开的。所以漏发 EOI 的症状是：这条线以及比它优先级低的所有线“全部哑火”，而比它高的线（比如 IRQ0 时钟）照常工作。这个症状在 IOAPIC/LAPIC 上同样成立，只是“优先级”换成了向量号的高 4 位。

第二，**向量号是在 INTA 周期里由 8259A 提供的**，而不是 CPU 自己算的。这就是为什么 8259A 的中断在 LAPIC 的术语里叫 **ExtINT**（External Interrupt）：LAPIC 看到 LINT0 上的请求时并不知道向量号，它必须模拟一次 INTA 周期去问外部控制器要。KVM 的实现正是如此，见 1.6 节。

### 1.2 端口与“同一个端口、不同的寄存器”

主片占端口 `0x20`/`0x21`，从片占 `0xA0`/`0xA1`。每颗芯片只有两个端口，却要承载 4 个初始化命令字（ICW1–ICW4）、3 个操作命令字（OCW1–OCW3）和 3 个可读寄存器。8259A 用了三种方式来复用：

1. **写 `0x20` 时看数据的 bit4 和 bit3。** bit4 = 1 是 ICW1，并且会把芯片复位进初始化序列；bit4 = 0 且 bit3 = 0 是 OCW2；bit4 = 0 且 bit3 = 1 是 OCW3。
2. **写 `0x21` 时看芯片当前处于初始化序列的哪一步。** ICW1 之后，接下来对 `0x21` 的写依次是 ICW2、（级联时）ICW3、（ICW1 要求时）ICW4；初始化序列结束后，对 `0x21` 的写就是 OCW1，也就是 IMR。
3. **读 `0x20` 返回 IRR 还是 ISR，取决于上一次 OCW3 的设置。** 读 `0x21` 总是返回 IMR。

这种隐式状态机是 8259A 编程最容易出错的地方：初始化序列中途多写或少写一个字节，后续对 `0x21` 的所有写入就错位了。

### 1.3 ICW1–ICW4 逐位

**ICW1**（写 `0x20`，bit4 = 1）：

| 位 | 名称 | 含义 | Linux 的取值 |
|---|---|---|---|
| 0 | IC4 | 1 = 后面会跟 ICW4 | 1 |
| 1 | SNGL | 1 = 单片模式，没有 ICW3 | 0（级联） |
| 2 | ADI | 调用地址间隔，只对 8080/8085 有意义 | 0 |
| 3 | LTIM | 1 = 所有线电平触发，0 = 边沿触发 | 0 |
| 4 | — | 固定为 1，标识这是 ICW1 | 1 |
| 7:5 | A7–A5 | 8080 模式下的向量地址，8086 模式忽略 | 0 |

所以 Linux 写的是 `0x11`。注意 LTIM 是整片的开关，不能按线设置。PC/AT 兼容机上按线设置触发方式靠的是后来 EISA/PIIX 引入的 **ELCR**（Edge/Level Control Register，端口 `0x4D0`/`0x4D1`），见 1.5 节。

**ICW2**（写 `0x21`）：向量基址。8086 模式下只有 bit7:3 有效，低 3 位由芯片填入 IR 编号。BIOS 的传统取值是主片 `0x08`、从片 `0x70`；主片的 `0x08` 恰好和 CPU 异常 `#DF` 冲突，这是历史上 IBM PC 的一个设计失误，所以所有保护模式操作系统都要重新编程 8259A。Linux x86_64 用的是 `ISA_IRQ_VECTOR(0)` = `0x30` 和 `ISA_IRQ_VECTOR(8)` = `0x38`。

**ICW3**（写 `0x21`，仅级联模式）：主片和从片的含义不同。主片上是一个位图，bit n = 1 表示 IRn 上接了从片，PC 上是 `0x04`（IR2）；从片上是自己的级联 ID，也就是它接在主片的哪根线上，PC 上是 `0x02`。

**ICW4**（写 `0x21`，仅当 ICW1.IC4 = 1）：

| 位 | 名称 | 含义 | Linux 的取值 |
|---|---|---|---|
| 0 | μPM | 1 = 8086/8088 模式，0 = 8080/8085 模式 | 1 |
| 1 | AEOI | 1 = 自动 EOI：第二个 INTA 脉冲结束时自动清 ISR | 0（默认） |
| 2 | M/S | 缓冲模式下，1 = 主片 | 0 |
| 3 | BUF | 1 = 缓冲模式 | 0 |
| 4 | SFNM | 1 = 特殊全嵌套模式 | 0 |

AEOI 模式下，处理程序不需要写 EOI，但代价是 ISR 始终为 0，同优先级和低优先级的中断可以随时嵌套进来，失去了硬件上的嵌套保护。SFNM 只对主片有意义：正常模式下，从片上一个中断在服务时，主片 IR2 在 ISR 里置位，会挡住从片上优先级更高的中断；SFNM 让主片在计算当前优先级时忽略 IR2，从片内部自己仲裁。

Linux 的初始化代码（guest 侧 `arch/x86/kernel/i8259.c:344`）把上面这些拼在一起：

```c
static void init_8259A(int auto_eoi)
{
	outb(0xff, PIC_MASTER_IMR);	/* mask all of 8259A-1 */

	outb_pic(0x11, PIC_MASTER_CMD);	/* ICW1: select 8259A-1 init */
	/* ICW2: 8259A-1 IR0-7 mapped to ISA_IRQ_VECTOR(0) */
	outb_pic(ISA_IRQ_VECTOR(0), PIC_MASTER_IMR);
	/* 8259A-1 (the master) has a slave on IR2 */
	outb_pic(1U << PIC_CASCADE_IR, PIC_MASTER_IMR);
	if (auto_eoi)	/* master does Auto EOI */
		outb_pic(MASTER_ICW4_DEFAULT | PIC_ICW4_AEOI, PIC_MASTER_IMR);
	else		/* master expects normal EOI */
		outb_pic(MASTER_ICW4_DEFAULT, PIC_MASTER_IMR);

	outb_pic(0x11, PIC_SLAVE_CMD);	/* ICW1: select 8259A-2 init */
	/* ICW2: 8259A-2 IR0-7 mapped to ISA_IRQ_VECTOR(8) */
	outb_pic(ISA_IRQ_VECTOR(8), PIC_SLAVE_IMR);
	/* 8259A-2 is a slave on master's IR2 */
	outb_pic(PIC_CASCADE_IR, PIC_SLAVE_IMR);
	outb_pic(SLAVE_ICW4_DEFAULT, PIC_SLAVE_IMR);
	...
	udelay(100);		/* wait for 8259A to initialize */

	outb(cached_master_mask, PIC_MASTER_IMR); /* restore master IRQ mask */
	outb(cached_slave_mask, PIC_SLAVE_IMR);	  /* restore slave IRQ mask */
}
```

翻译成端口写序列就是：

```
0x21 <- 0xFF     屏蔽主片全部
0x20 <- 0x11     ICW1：级联、边沿、要 ICW4
0x21 <- 0x30     ICW2：主片向量基址 0x30
0x21 <- 0x04     ICW3：IR2 上有从片
0x21 <- 0x01     ICW4：8086 模式、普通 EOI
0xA0 <- 0x11     从片 ICW1
0xA1 <- 0x38     从片 ICW2：向量基址 0x38
0xA1 <- 0x02     从片 ICW3：级联 ID = 2
0xA1 <- 0x01     从片 ICW4
0x21 <- mask     OCW1：恢复屏蔽字
0xA1 <- mask
```

`outb_pic()` 在每次写之后多做一次对 `0x80` 端口的写（`slow_down_io`），这是给老式 ISA 总线留时间的传统。在 KVM 下，如果 VMM 没有注册 `0x80`，每一次都是一次“未处理端口”的退出；blog 第十一章讲过，对未注册端口的写直接丢弃即可。

### 1.4 OCW1–OCW3 逐位

**OCW1**（初始化完成后写 `0x21`）：就是 IMR 本身，bit n = 1 屏蔽 IRn。

**OCW2**（写 `0x20`，bit4 = 0、bit3 = 0）：bit7:5 是 R（Rotate）、SL（Select Level）、EOI 三个标志，bit2:0 是目标级别 L2–L0。组合如下：

| R SL EOI | 值（bit7:5） | 含义 |
|---|---|---|
| 0 0 1 | 1 | 非特定 EOI：清除 ISR 中优先级最高的那一位 |
| 0 1 1 | 3 | 特定 EOI：清除 ISR 的第 L 位 |
| 1 0 1 | 5 | 非特定 EOI 并轮转：清除后把刚服务的线变成最低优先级 |
| 1 0 0 | 4 | 在 AEOI 模式下开启自动轮转 |
| 0 0 0 | 0 | 在 AEOI 模式下关闭自动轮转 |
| 1 1 1 | 7 | 特定 EOI 并轮转 |
| 1 1 0 | 6 | 设置优先级：让第 L 位成为最低优先级 |
| 0 1 0 | 2 | 空操作 |

Linux 在 `mask_and_ack_8259A()` 里用的是特定 EOI：`0x60 + irq`（`0x60` = `011` 左移 5 位）。从片上的中断要发两次：先给从片发特定 EOI，再给主片发 `0x60 + 2`，因为主片的 ISR 里 IR2 那一位也置着。

默认的**固定优先级**是 IR0 最高、IR7 最低；轮转会改变这个顺序。KVM 用 `priority_add` 这个字段表达“当前最高优先级是哪条线”，`get_priority()` 从 `priority_add` 开始循环扫描，这样一个整数就能描述全部 8 种轮转状态。

**OCW3**（写 `0x20`，bit4 = 0、bit3 = 1）：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | RIS | 读寄存器选择：0 = 下次读 `0x20` 返回 IRR，1 = 返回 ISR |
| 1 | RR | 1 = RIS 生效 |
| 2 | P | 1 = 轮询命令：下次读 `0x20` 相当于一次 INTA，返回最高优先级的挂起线号 |
| 5 | SMM | 特殊屏蔽模式的值 |
| 6 | ESMM | 1 = SMM 生效 |

Linux 读 ISR 用的是 `0x0B`（RR = 1、RIS = 1），读 IRR 用 `0x0A`。`i8259A_irq_real()` 判断一个中断是不是伪中断时，就是写 `0x0B` 读 ISR、再写 `0x0A` 恢复。

### 1.5 伪中断 IRQ7 与 ELCR

**伪中断。** 如果设备在 IR 线上拉高又很快撤销，8259A 可能已经把 INT 拉高、CPU 也已经开始 INTA 周期，但此时 IRR 里已经没有任何位了。8259A 这时的做法是：送出 IR7 的向量（主片是 `0x37`，从片是 `0x3F`，主片同时还要为 IR2 做级联），但**不在 ISR 里置位**。这就是著名的“spurious IRQ7”。操作系统的应对是：收到 IRQ7 时先读 ISR，第 7 位没有置位就说明是伪中断，**不能发 EOI**（发了会错误地清掉别的中断的 ISR 位）。Linux 的 `mask_and_ack_8259A()` 里 `spurious_8259A_irq` 那一段就是这套逻辑，它还会打印一次 `spurious 8259A interrupt: IRQ7.`。

**ELCR。** ICW1 的 LTIM 只能整片切换触发方式，PCI 设备需要电平触发、ISA 设备需要边沿触发，于是 EISA 芯片组引入了两个 8 位的 ELCR 寄存器：`0x4D0` 对应 IRQ0–7，`0x4D1` 对应 IRQ8–15，bit n = 1 表示这条线电平触发。其中 IRQ0（PIT）、IRQ1（键盘）、IRQ2（级联）、IRQ8（RTC）、IRQ13（FPU）在硬件上固定为边沿，不可更改，KVM 用掩码表达这一点：主片 `elcr_mask = 0xf8`（屏蔽 bit0–2），从片 `elcr_mask = 0xde`（屏蔽 bit0 和 bit5，即 IRQ8 和 IRQ13）。

### 1.6 KVM 的 8259A 模拟

KVM 的实现在 `arch/x86/kvm/i8259.c`，最初移植自 QEMU。状态结构是 `struct kvm_kpic_state`（`arch/x86/kvm/irq.h:28`），和 1.1 节讲的寄存器一一对应：

```c
struct kvm_kpic_state {
	u8 last_irr;	/* edge detection */
	u8 irr;		/* interrupt request register */
	u8 imr;		/* interrupt mask register */
	u8 isr;		/* interrupt service register */
	u8 priority_add;	/* highest irq priority */
	u8 irq_base;
	u8 read_reg_select;
	u8 poll;
	u8 special_mask;
	u8 init_state;
	u8 auto_eoi;
	u8 rotate_on_auto_eoi;
	u8 special_fully_nested_mode;
	u8 init4;		/* true if 4 byte init */
	u8 elcr;		/* PIIX edge/trigger selection */
	u8 elcr_mask;
	u8 isr_ack;	/* interrupt ack detection */
	struct kvm_pic *pics_state;
};
```

多出来的 `last_irr` 是做**边沿检测**用的。硬件上边沿检测靠的是电路里的触发器，软件模拟只能记住“上一次这条线是什么电平”。核心函数 `pic_set_irq1()`（`i8259.c:89`）：

```c
static inline int pic_set_irq1(struct kvm_kpic_state *s, int irq, int level)
{
	int mask, ret = 1;
	mask = 1 << irq;
	if (s->elcr & mask)	/* level triggered */
		if (level) {
			ret = !(s->irr & mask);
			s->irr |= mask;
			s->last_irr |= mask;
		} else {
			s->irr &= ~mask;
			s->last_irr &= ~mask;
		}
	else	/* edge triggered */
		if (level) {
			if ((s->last_irr & mask) == 0) {
				ret = !(s->irr & mask);
				s->irr |= mask;
			}
			s->last_irr |= mask;
		} else
			s->last_irr &= ~mask;

	return (s->imr & mask) ? -1 : ret;
}
```

边沿分支说明了一件对 VMM 至关重要的事：**连续两次 `level = 1` 只算一个边沿**。如果 VMM 的串口模拟在中断条件成立时调用 `KVM_IRQ_LINE(4, 1)`，下一次中断条件成立时又调用 `KVM_IRQ_LINE(4, 1)`，中间没有拉低过，第二次调用在 8259A 这里什么都不会发生。IOAPIC 的边沿逻辑也是一样的（见 2.5 节）。所以边沿中断的设备模拟必须维护“线的当前电平”，并且在中断条件消失时真正拉低，mini-vmm 串口模拟的 `update_irq()`（blog 第十一章）就是这样做的：它用 `irq_level` 记住线的当前电平，只有电平真正变化时才调用 `KVM_IRQ_LINE`。

返回值也值得注意：`-1` 表示被 IMR 屏蔽，`0` 表示“合并”（这个请求已经在 IRR 里了，没有产生新的中断），`1` 表示产生了新的请求。这个返回值会一路回传到 `KVM_IRQ_LINE_STATUS` 的 `status` 字段，PIT 的补发逻辑就是靠它判断“这个 tick 有没有被合并掉”。

**线电平的“或”。** 一条 IRQ 线上可能有多个中断源。KVM 为每条线维护一个位图 `irq_states[irq]`，每个中断源占一位，线的电平是所有位的逻辑或（`arch/x86/include/asm/kvm_host.h:1725`）：

```c
static inline int __kvm_irq_line_state(unsigned long *irq_state,
				       int irq_source_id, int level)
{
	/* Logical OR for level trig interrupt */
	if (level)
		__set_bit(irq_source_id, irq_state);
	else
		__clear_bit(irq_source_id, irq_state);

	return !!(*irq_state);
}
```

中断源 ID 是 KVM 内部分配的：`KVM_USERSPACE_IRQ_SOURCE_ID` = 0 给所有来自 `KVM_IRQ_LINE` 的请求，`KVM_IRQFD_RESAMPLE_IRQ_SOURCE_ID` = 1 给带 resample 的 irqfd，内核 PIT 在创建时再申请一个。**这意味着用户态所有设备在 KVM 眼里是同一个中断源**：如果 VMM 让两个设备共享一条 GSI，设备 A 拉高、设备 B 拉低，KVM 看到的就是这条线被拉低了，设备 A 的请求丢失。VMM 必须自己在用户态做“或”，再把结果交给 `KVM_IRQ_LINE`。mini-vmm 每个设备独占一条线，不存在这个问题。

**端口写入的状态机。** `pic_ioport_write()`（`i8259.c:305`）对照 1.2–1.4 节就能读懂：写偶数端口时，`val & 0x10` 是 ICW1，调用 `kvm_pic_reset()` 并把 `init_state` 置 1；`val & 0x08` 是 OCW3；否则按 `val >> 5` 分发 OCW2。写奇数端口时按 `init_state` 分发：0 是 OCW1（写 IMR，并触发 mask notifier），1 是 ICW2（`irq_base = val & 0xf8`），2 是 ICW3（KVM 直接忽略它的内容，因为级联关系是写死的），3 是 ICW4（只取 SFNM 和 AEOI 两位）。

有两处简化需要知道：ICW1 的 SNGL 和 LTIM 都不支持，写了只打一行 `kvm: pic: single mode not supported` 之类的限速日志。触发方式完全由 ELCR 决定，这和真实的 PIIX 芯片组行为一致。

**INT 输出与 INTA。** 8259A 的 INT 输出在 KVM 里是 `kvm_pic.output` 这个整数。`pic_update_irq()` 在任何可能改变仲裁结果的操作之后被调用：先看从片有没有要送的中断，有就在主片 IR2 上打一个脉冲（`pic_set_irq1(..., 2, 1)` 紧跟 `pic_set_irq1(..., 2, 0)`，恰好构成一个边沿）；再看主片的仲裁结果，写到 `output`。`output` 从 0 变 1 时置 `wakeup_needed`，`pic_unlock()` 在释放锁之后找到第一个“愿意接收 PIC 中断”的 vCPU，发 `KVM_REQ_EVENT` 并 kick 它。

“愿意接收 PIC 中断”的判断是 `kvm_apic_accept_pic_intr()`（`lapic.c:2512`）：

```c
int kvm_apic_accept_pic_intr(struct kvm_vcpu *vcpu)
{
	u32 lvt0 = kvm_lapic_get_reg(vcpu->arch.apic, APIC_LVT0);

	if (!kvm_apic_hw_enabled(vcpu->arch.apic))
		return 1;
	if ((lvt0 & APIC_LVT_MASKED) == 0 &&
	    GET_APIC_DELIVERY_MODE(lvt0) == APIC_MODE_EXTINT)
		return 1;
	return 0;
}
```

这两个条件对应真实硬件的两种接法：LAPIC 被全局禁用（`IA32_APIC_BASE` 的 EN 位为 0）时，8259A 的 INT 直接连到 CPU 的 INTR 引脚，这是 PC/AT 的原始接法；LAPIC 启用时，8259A 的 INT 接在 LAPIC 的 LINT0 上，只有 LVT0 未屏蔽且投递模式为 ExtINT，才会把它当作“外部中断”转交给 CPU。这就是 MP 规范里的 **virtual wire mode**（虚拟线模式）。

vCPU 真正取中断时，走的是 `kvm_cpu_get_interrupt()` → `kvm_cpu_get_extint()` → `kvm_pic_read_irq()`（`i8259.c:234`），它就是软件版的 INTA 周期：对主片做 `pic_intack()`（IRR 搬 ISR，边沿模式清 IRR，AEOI 模式立即清 ISR），如果主片选中的是 IR2 就再对从片做一次；两边都没有可送的中断时返回 IR7 的向量，也就是 1.5 节的伪中断。**注意 ExtINT 的优先级高于 LAPIC 自己的 IRR**：`kvm_cpu_get_interrupt()` 先问 PIC，PIC 没有才问 LAPIC。

### 1.7 在 IOAPIC 时代，8259A 还在做什么

mini-vmm 的 guest 工作在 symmetric I/O 模式，所有 ISA 中断都经 IOAPIC 投递，8259A 在稳态下全部被屏蔽。但它并不是没有用：

- **`probe_8259A()`。** Linux 在 `early_irq_init()` 阶段经 `arch_probe_nr_irqs()`（`arch/x86/kernel/apic/vector.c:711`）调用 `legacy_pic->probe()`，也就是 `probe_8259A()`：屏蔽从片、给主片写一个特定的 IMR 值再读回，读回的值不对就认为没有 PIC，改用 `null_legacy_pic`。如果 MADT 头部的 flags 里有 `PCAT_COMPAT`，这一步会被跳过（`legacy_pic_pcat_compat()`），直接认为 PIC 存在。mini-vmm 的 MADT 设置了这个标志。没有 PIC 的后果是 `nr_legacy_irqs()` 返回 0，ISA 中断号 0–15 不再被预留，这会让一系列假设“IRQ0 就是时钟”的代码走上不同的分支。
- **`check_timer()`。** IOAPIC 初始化时，Linux 要验证时钟中断到底接在哪里。它会依次尝试 IOAPIC 直连、经 8259A 的 virtual wire、LAPIC 的 LVT0 ExtINT 等几种接法，每种都实际等几个 tick 看中断有没有到。blog 第二章提过这段代码；这里补充的是：在其中几种尝试里，8259A 会被真正取消屏蔽 IRQ0，所以 KVM 的 8259A 必须能正确地把 PIT 的 tick 送出去，否则 `check_timer()` 会一路失败到 `panic("IO-APIC + timer doesn't work!")`。
- **`KVM_CREATE_IRQCHIP` 一次性创建了 PIC、IOAPIC 和每个 vCPU 的 LAPIC。** 默认的 GSI 路由把 GSI 0–15 同时连到 PIC 和 IOAPIC（2.6 节），所以 VMM 拉一次 `KVM_IRQ_LINE`，两颗控制器都会收到。只要 guest 把 8259A 屏蔽了，PIC 那一路就只停留在 IRR 里，没有副作用。

## 2. IOAPIC：把“线”翻译成“消息”

### 2.1 定位与寻址

IOAPIC 的原型是 Intel 82093AA，一颗 24 引脚的 I/O 中断控制器。它和 8259A 的根本区别在于：8259A 的输出是一根物理线（INT），只能接一颗 CPU；IOAPIC 的输出是 **APIC 总线（后来是系统总线）上的中断消息**，消息里写着向量号、投递模式、目标 CPU，所有 LAPIC 都能收到并判断“是不是给我的”。从这个角度看，IOAPIC 本质上是一个“把电平或边沿翻译成 MSI 消息”的设备，Linux 6.6 的 `io_apic.c` 注释里就直接这样写：*The I/OAPIC is just a device for generating MSI messages from legacy interrupt pins.*

IOAPIC 只占 MMIO 空间里很小的一块，默认基址 `0xFEC00000`，由固件表（MADT 的 IOAPIC 条目或 MP table 的 IOAPIC 条目）告诉操作系统。它只暴露两个直接可访问的 32 位寄存器，其余全部间接访问：

| 偏移 | 名称 | 含义 |
|---|---|---|
| `0x00` | IOREGSEL | 索引寄存器，低 8 位写入要访问的间接寄存器编号 |
| `0x10` | IOWIN | 数据窗口，读写 IOREGSEL 选中的那个间接寄存器 |
| `0x40` | EOI | 仅版本 ≥ `0x20` 的 IOAPIC 有：写入向量号，清除对应表项的 remote IRR |

间接寄存器：

| 索引 | 名称 | 内容 |
|---|---|---|
| `0x00` | IOAPICID | bit27:24 为 IOAPIC 自己的 APIC ID（82093AA 是 4 位） |
| `0x01` | IOAPICVER | bit7:0 为版本号，bit23:16 为“最大重定向表项的下标”，即引脚数减 1 |
| `0x02` | IOAPICARB | 仲裁 ID，APIC 串行总线时代的遗留，现代系统无意义 |
| `0x10 + 2n` | IOREDTBL[n] 低 32 位 | 第 n 个引脚的重定向表项 |
| `0x11 + 2n` | IOREDTBL[n] 高 32 位 | |

这种“索引 + 窗口”的设计意味着**访问 IOAPIC 天然不是原子的**：写一个表项要先写 IOREGSEL、再写 IOWIN，两次 MMIO；写满 64 位要四次。两颗 CPU 并发访问会互相踩掉对方的 IOREGSEL，所以 Linux 用一把全局的 `ioapic_lock` 自旋锁保护所有 IOAPIC 访问。

KVM 的实现（`arch/x86/kvm/ioapic.h`）把这些都写成了常量：

```c
#define IOAPIC_VERSION_ID 0x11	/* IOAPIC version */
#define IOAPIC_DEFAULT_BASE_ADDRESS  0xfec00000
#define IOAPIC_MEM_LENGTH            0x100
/* Direct registers. */
#define IOAPIC_REG_SELECT  0x00
#define IOAPIC_REG_WINDOW  0x10
/* Indirect registers. */
#define IOAPIC_REG_APIC_ID 0x00	/* x86 IOAPIC only */
#define IOAPIC_REG_VERSION 0x01
#define IOAPIC_REG_ARB_ID  0x02	/* x86 IOAPIC only */
```

版本号 `0x11` 就是 82093AA，**没有 EOI 寄存器**，偏移 `0x40` 的写入会落到 `ioapic_mmio_write()` 的 `default` 分支被忽略。读版本寄存器返回 `((24 - 1) << 16) | 0x11` = `0x00170011`。基址固定为 `0xFEC00000`，长度 `0x100`，在 `kvm_ioapic_init()` 里注册到 `KVM_MMIO_BUS`。

对 VMM 的直接推论有三条，blog 第十、十二章已经分别讲过，这里汇总：

1. 固件表里 IOAPIC 的地址必须写 `0xFEC00000`，引脚数（MADT 里是 GSI base = 0，由版本寄存器隐含 24 根）与 KVM 一致。
2. `0xFEC00000` 这一页不能被任何 memslot 覆盖。`KVM_MMIO_BUS` 上的设备只有在 GPA 没有 memslot（产生 `#NPF` 并被判定为 MMIO）时才会被查找；一旦 RAM 盖住了这一页，guest 对 IOAPIC 的写就写进了普通内存，KVM 的 IOAPIC 永远收不到。
3. IOAPIC ID 在 KVM 里复位为 0，guest 可以改写。MADT 里写的 IOAPIC ID 应该与 LAPIC ID 不冲突（mini-vmm 写的是 vCPU 数，也就是紧跟在最后一个 LAPIC ID 之后）；Linux 64 位的 `io_apic_unique_id()`（`io_apic.c:2570`）只检查多颗 IOAPIC 之间是否重复，发现重复会改用一个未使用的 ID 并写回 IOAPIC。

### 2.2 重定向表项逐位

每个引脚一个 64 位表项，这是 IOAPIC 编程的全部核心：

| 位 | 名称 | 读写 | 含义 |
|---|---|---|---|
| 7:0 | Vector | RW | 投递给 CPU 的向量号，合法范围 `0x10`–`0xFE` |
| 10:8 | Delivery Mode | RW | `000` Fixed；`001` Lowest Priority；`010` SMI；`100` NMI；`101` INIT；`111` ExtINT |
| 11 | Destination Mode | RW | 0 = 物理模式（目标字段是 APIC ID）；1 = 逻辑模式（目标字段与各 LAPIC 的 LDR/DFR 匹配） |
| 12 | Delivery Status | RO | 1 = 消息已经发出但目标 LAPIC 还没接受（Send Pending） |
| 13 | Interrupt Input Pin Polarity | RW | 0 = 高电平有效；1 = 低电平有效 |
| 14 | Remote IRR | RO | 仅电平触发有意义：1 = 中断已被 LAPIC 接受，正在等 EOI |
| 15 | Trigger Mode | RW | 0 = 边沿；1 = 电平 |
| 16 | Mask | RW | 1 = 屏蔽。复位值为 1 |
| 55:17 | — | | 保留（Linux 用 bit55:49 表达扩展目标 ID，见下） |
| 63:56 | Destination | RW | 物理模式下是目标 APIC ID（82093AA 只用 bit59:56 这 4 位）；逻辑模式下是 8 位的目标集合 |

KVM 的 C 表示（`ioapic.h`）用位域一比一地对应：

```c
union kvm_ioapic_redirect_entry {
	u64 bits;
	struct {
		u8 vector;
		u8 delivery_mode:3;
		u8 dest_mode:1;
		u8 delivery_status:1;
		u8 polarity:1;
		u8 remote_irr:1;
		u8 trig_mode:1;
		u8 mask:1;
		u8 reserve:7;
		u8 reserved[4];
		u8 dest_id;
	} fields;
};
```

guest 侧 Linux 6.6 的 `struct IO_APIC_route_entry`（`arch/x86/include/asm/io_apic.h:58`）则多了一个 `virt_destid_8_14` 字段，占 bit55:49。这是为超过 255 个 vCPU 设计的“扩展目标 ID”：物理硬件上这几位是保留位，但当 hypervisor 通过 CPUID 宣告 `KVM_FEATURE_MSI_EXT_DEST_ID` 时，guest 可以把 APIC ID 的 bit14:8 放在这里，从而在不启用中断重映射的情况下寻址 32768 个 CPU。mini-vmm 只有几个 vCPU，也不宣告 KVM paravirt 特性，这几位保持为 0。

有几个字段在虚拟化环境里语义被“削弱”了，写 VMM 或读 KVM 源码时要知道：

- **Delivery Status** 在 KVM 里从不置 1，因为 KVM 的投递是同步完成的，不存在“消息在总线上飞”的中间状态。
- **Polarity** 在 KVM 里完全不参与计算。`ioapic_set_irq()` 只看 `irq_level` 是 0 还是 1，**`KVM_IRQ_LINE` 的 `level` 表示逻辑上的“有效/无效”，与电气极性无关**。即使 guest 把 SCI 配置成低电平有效，VMM 要触发 SCI 时传的仍然是 `level = 1`。
- **Destination** 在物理模式下，KVM 使用完整的 8 位，而不是 82093AA 的 4 位，所以 APIC ID 可以到 254（255 是广播）。

写表项的顺序也有讲究，Linux 的注释说得很清楚（`io_apic.c:314`）：

```c
/*
 * When we write a new IO APIC routing entry, we need to write the high
 * word first! If the mask bit in the low word is clear, we will enable
 * the interrupt, and we need to make sure the entry is fully populated
 * before that happens.
 */
static void __ioapic_write_entry(int apic, int pin, struct IO_APIC_route_entry e)
{
	io_apic_write(apic, 0x11 + 2*pin, e.w2);
	io_apic_write(apic, 0x10 + 2*pin, e.w1);
}
```

启用一个表项时先写高 32 位（目标），再写低 32 位（向量、模式、mask = 0）；屏蔽时反过来，先写低 32 位把 mask 置 1，再改高 32 位。因为低 32 位一写入，表项就立即生效了。KVM 的 `ioapic_write_indirect()` 也是按 32 位为单位即时生效的，所以它忠实地保留了这个语义：如果 guest 写反了顺序，在 KVM 里同样可能在中间状态把中断投给错误的 CPU。

### 2.3 边沿、电平与 remote IRR

边沿触发与电平触发在 IOAPIC 上的区别，不只是“什么时候认为有请求”，更在于**谁负责防止重复投递**。

**边沿触发**：引脚上出现一个有效边沿，IOAPIC 发一条消息，然后就忘了这件事。消息投递到 LAPIC 后，LAPIC 的 IRR 置位；如果同一个向量在 IRR 里已经置位，第二个消息会被合并。IOAPIC 本身不跟踪“这个中断有没有被处理完”。

**电平触发**：引脚为有效电平时，IOAPIC 发一条消息，并把表项的 **remote IRR** 置 1。只要 remote IRR 为 1，即使引脚一直保持有效，IOAPIC 也不再发消息。直到 CPU 处理完中断、向 LAPIC 写 EOI，LAPIC 发现这个向量在 **TMR**（Trigger Mode Register）里是 1（表示它是电平触发的中断），就向所有 IOAPIC **广播一条 EOI 消息**，消息里带着向量号。IOAPIC 找到向量号匹配的表项，清掉 remote IRR；此时如果引脚仍然有效，立即再发一次。

```
             边沿触发                                    电平触发
  引脚 ___/‾‾‾\_____/‾‾‾\___                引脚 ___/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\___
          │         │                              │            │      │
          ▼         ▼                              ▼            ▼      ▼
       发消息     发消息                         发消息      EOI 广播  EOI 广播
                                              remote IRR=1  remote IRR=0
                                                            引脚仍有效 → 再发一次
                                                            remote IRR=1
```

电平触发的设计是为了**共享中断线**：PCI 的 INTx 允许多个设备共用一根线，线上的电平是所有设备请求的“线或”。处理程序依次询问每个设备，清掉所有请求，最后写 EOI；此时如果还有某个设备在请求，线保持有效，IOAPIC 在收到 EOI 后立即重发，不会丢失。边沿触发做不到这一点：两个设备的请求如果时间上重叠，只会产生一个边沿。

**EOI 广播的抑制。** 在很多 CPU 的系统上，每一次电平中断的 EOI 都广播给所有 IOAPIC 是一种浪费。于是 LAPIC 版本寄存器的 bit24 引入了“支持抑制 EOI 广播”（Directed EOI）能力，SVR 的 bit12 用来打开它。打开后 LAPIC 不再广播，操作系统要自己写 IOAPIC 的 EOI 寄存器（偏移 `0x40`）。这要求 IOAPIC 版本 ≥ `0x20`。

KVM 的内核 IOAPIC 是 `0x11`，没有 EOI 寄存器，因此 **KVM 在内核 IOAPIC 模式下不向 guest 宣告 Directed EOI 能力**（`lapic.c:367`）：

```c
void kvm_apic_set_version(struct kvm_vcpu *vcpu)
{
	struct kvm_lapic *apic = vcpu->arch.apic;
	u32 v = APIC_VERSION;
	...
	/*
	 * KVM emulates 82093AA datasheet (with in-kernel IOAPIC implementation)
	 * which doesn't have EOI register; Some buggy OSes (e.g. Windows with
	 * Hyper-V role) disable EOI broadcast in lapic not checking for IOAPIC
	 * version first and level-triggered interrupts never get EOIed in
	 * IOAPIC.
	 */
	if (guest_cpuid_has(vcpu, X86_FEATURE_X2APIC) &&
	    !ioapic_in_kernel(vcpu->kvm))
		v |= APIC_LVR_DIRECTED_EOI;
	kvm_lapic_set_reg(apic, APIC_LVR, v);
}
```

只有 split irqchip（IOAPIC 在用户态）并且 guest 有 x2APIC 时才宣告。

**没有 EOI 寄存器时怎么手动清 remote IRR？** Linux 有一个流传很久的技巧，出自 `__eoi_ioapic_pin()`（`io_apic.c:478`）：

```c
static void __eoi_ioapic_pin(int apic, int pin, int vector)
{
	if (mpc_ioapic_ver(apic) >= 0x20) {
		io_apic_eoi(apic, vector);
	} else {
		struct IO_APIC_route_entry entry, entry1;

		entry = entry1 = __ioapic_read_entry(apic, pin);

		/*
		 * Mask the entry and change the trigger mode to edge.
		 */
		entry1.masked = true;
		entry1.is_level = false;

		__ioapic_write_entry(apic, pin, entry1);

		/*
		 * Restore the previous level triggered entry.
		 */
		__ioapic_write_entry(apic, pin, entry);
	}
}
```

把表项临时改成“屏蔽 + 边沿”再改回来。82093AA 在表项被改为边沿触发时会清掉 remote IRR，这是一个没有写进规范、但所有操作系统都依赖的硬件行为。KVM 专门模拟了它（`ioapic.c` 的 `ioapic_write_indirect()`）：

```c
		/*
		 * Some OSes (Linux, Xen) assume that Remote IRR bit will
		 * be cleared by IOAPIC hardware when the entry is configured
		 * as edge-triggered. This behavior is used to simulate an
		 * explicit EOI on IOAPICs that don't have the EOI register.
		 */
		if (e->fields.trig_mode == IOAPIC_EDGE_TRIG)
			e->fields.remote_irr = 0;
```

Linux 什么时候需要手动清？`ioapic_ack_level()` 的长注释解释了两种情况：一是 82093AA 的一个勘误，电平中断偶尔被当作边沿中断投递，LAPIC 的 TMR 没有置位，EOI 就不会广播；二是 CPU 下线时，未处理的中断经 IPI 转发到别的 CPU，IPI 总是边沿的，同样不会触发 EOI 广播。Linux 的检测方法是在 ack 时读 LAPIC 的 TMR，发现本应是电平的向量在 TMR 里是 0，就手动对 IOAPIC 做一次 EOI。

### 2.4 KVM 的 IOAPIC 状态

```c
struct kvm_ioapic {
	u64 base_address;
	u32 ioregsel;
	u32 id;
	u32 irr;
	u32 pad;
	union kvm_ioapic_redirect_entry redirtbl[IOAPIC_NUM_PINS];
	unsigned long irq_states[IOAPIC_NUM_PINS];
	struct kvm_io_device dev;
	struct kvm *kvm;
	void (*ack_notifier)(void *opaque, int irq);
	spinlock_t lock;
	struct rtc_status rtc_status;
	struct delayed_work eoi_inject;
	u32 irq_eoi[IOAPIC_NUM_PINS];
	u32 irr_delivered;
};
```

- `irr`：24 位的引脚状态，bit n 表示第 n 根引脚当前有效（电平）或出现过尚未投递的边沿。真实的 82093AA 并没有暴露这样一个寄存器，这是 KVM 的内部状态。
- `irq_states[]`：与 8259A 一样的“多中断源线或”位图，见 1.6 节。
- `irr_delivered`：边沿中断已经投递出去的引脚。它只在 `KVM_GET_IRQCHIP` 保存状态时用，确保迁移后不会把已经投递过的边沿再投递一次（`kvm_get_ioapic()` 里 `state->irr &= ~ioapic->irr_delivered`）。
- `rtc_status`：RTC（GSI 8）的特殊 EOI 跟踪，见 2.6 节。
- `irq_eoi[]` 与 `eoi_inject`：电平中断风暴的缓解，见 2.6 节。

复位（`kvm_ioapic_reset()`）时所有 24 个表项的 mask 位为 1，其余为 0，也就是说**复位后所有引脚都是屏蔽的、向量为 0、边沿触发、物理模式、目标 APIC ID 0**。在 guest 编程 IOAPIC 之前，VMM 拉任何 GSI 都不会产生中断，只会在 `irr` 里留下记录。

### 2.5 `ioapic_set_irq()`：边沿检测与合并

这是 IOAPIC 引脚收到电平变化的入口（`ioapic.c:207`），完整代码值得逐行读：

```c
static int ioapic_set_irq(struct kvm_ioapic *ioapic, unsigned int irq,
		int irq_level, bool line_status)
{
	union kvm_ioapic_redirect_entry entry;
	u32 mask = 1 << irq;
	u32 old_irr;
	int edge, ret;

	entry = ioapic->redirtbl[irq];
	edge = (entry.fields.trig_mode == IOAPIC_EDGE_TRIG);

	if (!irq_level) {
		ioapic->irr &= ~mask;
		ret = 1;
		goto out;
	}

	/*
	 * AMD SVM AVIC accelerate EOI write iff the interrupt is edge
	 * triggered, in which case the in-kernel IOAPIC will not be able
	 * to receive the EOI.  In this case, we do a lazy update of the
	 * pending EOI when trying to set IOAPIC irq.
	 */
	if (edge && kvm_apicv_activated(ioapic->kvm))
		ioapic_lazy_update_eoi(ioapic, irq);

	/* ... RTC 特判，见 2.6 节 ... */
	if (irq == RTC_GSI && line_status &&
		rtc_irq_check_coalesced(ioapic)) {
		ret = 0;
		goto out;
	}

	old_irr = ioapic->irr;
	ioapic->irr |= mask;
	if (edge) {
		ioapic->irr_delivered &= ~mask;
		if (old_irr == ioapic->irr) {
			ret = 0;
			goto out;
		}
	}

	ret = ioapic_service(ioapic, irq, line_status);

out:
	trace_kvm_ioapic_set_irq(entry.bits, irq, ret == 0);
	return ret;
}
```

分三种情况：

1. **拉低**：清掉 `irr` 的对应位，什么都不投递。对边沿中断，这一步是“为下一个上升沿做准备”；对电平中断，这一步撤销请求，但**已经在 LAPIC IRR 里的向量不会被撤回**。
2. **边沿、拉高、之前已经是高**：`old_irr == ioapic->irr`，判定为合并，返回 0，不投递。这就是 blog 第十章讲的“边沿中断重复拉高是无操作”，VMM 必须先拉低再拉高才能产生第二个中断。
3. **电平拉高，或边沿的真正上升沿**：调用 `ioapic_service()` 尝试投递。

注意电平中断没有“合并检查”：每次 `level = 1` 都会调用 `ioapic_service()`，由它里面的 remote IRR 检查来防止重复投递。

`ioapic_service()`（`ioapic.c:413`）把表项翻译成一个 `struct kvm_lapic_irq`，交给通用的 APIC 投递函数：

```c
static int ioapic_service(struct kvm_ioapic *ioapic, int irq, bool line_status)
{
	union kvm_ioapic_redirect_entry *entry = &ioapic->redirtbl[irq];
	struct kvm_lapic_irq irqe;
	int ret;

	if (entry->fields.mask ||
	    (entry->fields.trig_mode == IOAPIC_LEVEL_TRIG &&
	    entry->fields.remote_irr))
		return -1;

	irqe.dest_id = entry->fields.dest_id;
	irqe.vector = entry->fields.vector;
	irqe.dest_mode = kvm_lapic_irq_dest_mode(!!entry->fields.dest_mode);
	irqe.trig_mode = entry->fields.trig_mode;
	irqe.delivery_mode = entry->fields.delivery_mode << 8;
	irqe.level = 1;
	irqe.shorthand = APIC_DEST_NOSHORT;
	irqe.msi_redir_hint = false;

	if (irqe.trig_mode == IOAPIC_EDGE_TRIG)
		ioapic->irr_delivered |= 1 << irq;

	/* ... RTC 分支 ... */
		ret = kvm_irq_delivery_to_apic(ioapic->kvm, NULL, &irqe, NULL);

	if (ret && irqe.trig_mode == IOAPIC_LEVEL_TRIG)
		entry->fields.remote_irr = 1;

	return ret;
}
```

几个值得注意的点：

- **被屏蔽时直接返回 -1，但 `irr` 已经置位。** 所以 guest 之后取消屏蔽时，`ioapic_write_indirect()` 里有这样一段：`if (e->fields.trig_mode == IOAPIC_LEVEL_TRIG && ioapic->irr & (1 << index)) ioapic_service(ioapic, index, false);`，也就是**电平中断在取消屏蔽时会立即补投**。边沿中断则没有这个待遇：屏蔽期间到来的边沿，在取消屏蔽时不会补投。这与真实 82093AA 的行为一致（边沿在屏蔽期间直接丢失），这也是 Linux 通用中断层默认采用“懒禁用”（lazy disable）的原因之一：`disable_irq()` 只在软件上打标记，不去碰硬件屏蔽位；如果被禁用期间中断真的来了，才在硬件上屏蔽它并记下 `IRQS_PENDING`，等 `enable_irq()` 时通过重触发把它补回来，从而不丢失边沿。
- **`delivery_mode << 8`**：IOAPIC 表项里投递模式是 bit10:8，而 LAPIC ICR 里也是 bit10:8，KVM 内部统一用 ICR 的格式（`APIC_DM_FIXED` = `0x000`、`APIC_DM_LOWEST` = `0x100`、`APIC_DM_NMI` = `0x400` 等），所以要左移 8 位。
- **remote IRR 只在投递成功时置位。** `ret` 是成功接收这个中断的 LAPIC 个数；如果目标 APIC ID 不存在，`ret` 为 0 或 -1，remote IRR 不会置位，下次再拉高还会再尝试。
- **`ret` 的含义一路回传到用户态。** `KVM_IRQ_LINE_STATUS` 的 `status` 字段：大于 0 表示有 LAPIC 接收；0 表示合并（中断已经挂起）；-1 表示被屏蔽或没有目标。PIT 的补发和 RTC 的 coalesced 统计都依赖它。

### 2.6 两处特殊处理：RTC 与中断风暴

**RTC 的 EOI 跟踪。** GSI 8（`RTC_GSI`）是边沿触发的，按理说 IOAPIC 不跟踪它的 EOI。但 Windows guest 用 RTC 周期中断计时，如果中断被合并（上一次还没处理完，下一次又来了），Windows 的时间就会慢下来。QEMU 需要知道“这次 RTC 中断到底有没有被合并”，以便补发。于是 KVM 为 GSI 8 专门维护 `rtc_status`：投递时记录发给了哪些 vCPU、什么向量（`dest_map`），每个 vCPU 写 EOI 时递减 `pending_eoi`。当 `pending_eoi > 0` 时，`ioapic_set_irq()` 直接返回 0（合并），QEMU 据此计数 coalesced 中断。

这个机制只在 `line_status = true` 时启用，也就是用户态用 `KVM_IRQ_LINE_STATUS` 拉线时。mini-vmm 用的是 `KVM_IRQ_LINE`，`line_status = false`，而且 mini-vmm 的 RTC 不产生中断，所以这段逻辑对它是透明的。另外，`kvm_ioapic_scan_entry()` 会把 RTC 的向量加入“需要拦截 EOI 的向量”集合，即使它是边沿中断，这一点在 AVIC 下有意义（第 8 节）。

**电平中断风暴。** 如果 guest 的电平中断处理程序有 bug，没有清掉设备的中断条件就写了 EOI，那么 EOI 一到，IOAPIC 发现引脚仍然有效，立即重投，guest 再进处理程序、再写 EOI……vCPU 将永远卡在这个循环里。真实硬件上，EOI 消息在总线上传递需要时间，重投也有延迟，guest 还能慢慢前进。KVM 模拟了这种“慢”（`kvm_ioapic_update_eoi_one()`，`ioapic.c:502`）：

```c
#define IOAPIC_SUCCESSIVE_IRQ_MAX_COUNT 10000
	...
	ent->fields.remote_irr = 0;
	if (!ent->fields.mask && (ioapic->irr & (1 << pin))) {
		++ioapic->irq_eoi[pin];
		if (ioapic->irq_eoi[pin] == IOAPIC_SUCCESSIVE_IRQ_MAX_COUNT) {
			/*
			 * Real hardware does not deliver the interrupt
			 * immediately during eoi broadcast, and this
			 * lets a buggy guest make slow progress
			 * even if it does not correctly handle a
			 * level-triggered interrupt.  Emulate this
			 * behavior if we detect an interrupt storm.
			 */
			schedule_delayed_work(&ioapic->eoi_inject, HZ / 100);
			ioapic->irq_eoi[pin] = 0;
			trace_kvm_ioapic_delayed_eoi_inj(ent->bits);
		} else {
			ioapic_service(ioapic, pin, false);
		}
	} else {
		ioapic->irq_eoi[pin] = 0;
	}
```

连续 10000 次“EOI 后引脚仍然有效”，就把下一次投递推迟 10 ms。对 VMM 的启示是：**电平中断的设备模拟必须在中断条件消失时及时拉低**，否则 guest 会被风暴拖慢，trace 里会出现 `kvm_ioapic_delayed_eoi_inj`。

### 2.7 GSI 路由：一张把“中断号”翻译成“芯片引脚”的表

VMM 调用 `KVM_IRQ_LINE` 时传的是 **GSI**（Global System Interrupt）号，不是 IOAPIC 引脚号。GSI 到“哪颗芯片的哪根引脚”的映射由 KVM 的**中断路由表**决定。`KVM_CREATE_IRQCHIP` 在创建 PIC 和 IOAPIC 之后，调用 `kvm_setup_default_irq_routing()` 装入一张默认表（`irq_comm.c`）：

```c
#define IOAPIC_ROUTING_ENTRY(irq) \
	{ .gsi = irq, .type = KVM_IRQ_ROUTING_IRQCHIP,	\
	  .u.irqchip = { .irqchip = KVM_IRQCHIP_IOAPIC, .pin = (irq) } }
#define ROUTING_ENTRY1(irq) IOAPIC_ROUTING_ENTRY(irq)

#define PIC_ROUTING_ENTRY(irq) \
	{ .gsi = irq, .type = KVM_IRQ_ROUTING_IRQCHIP,	\
	  .u.irqchip = { .irqchip = SELECT_PIC(irq), .pin = (irq) % 8 } }
#define ROUTING_ENTRY2(irq) \
	IOAPIC_ROUTING_ENTRY(irq), PIC_ROUTING_ENTRY(irq)

static const struct kvm_irq_routing_entry default_routing[] = {
	ROUTING_ENTRY2(0), ROUTING_ENTRY2(1),
	...
	ROUTING_ENTRY2(14), ROUTING_ENTRY2(15),
	ROUTING_ENTRY1(16), ROUTING_ENTRY1(17),
	...
	ROUTING_ENTRY1(22), ROUTING_ENTRY1(23),
};
```

即：GSI 0–15 各有两条路由，一条到 IOAPIC 的同号引脚，一条到 PIC 的对应引脚（`SELECT_PIC(irq)` 选主片或从片，引脚号取模 8）；GSI 16–23 只到 IOAPIC。一个 GSI 可以对应多条路由，`kvm_set_irq()`（`virt/kvm/irqchip.c:71`）把它们全部触发一遍：

```c
int kvm_set_irq(struct kvm *kvm, int irq_source_id, u32 irq, int level,
		bool line_status)
{
	struct kvm_kernel_irq_routing_entry irq_set[KVM_NR_IRQCHIPS];
	int ret = -1, i, idx;

	trace_kvm_set_irq(irq, level, irq_source_id);

	/* Not possible to detect if the guest uses the PIC or the
	 * IOAPIC.  So set the bit in both. The guest will ignore
	 * writes to the unused one.
	 */
	idx = srcu_read_lock(&kvm->irq_srcu);
	i = kvm_irq_map_gsi(kvm, irq_set, irq);
	srcu_read_unlock(&kvm->irq_srcu, idx);

	while (i--) {
		int r;
		r = irq_set[i].set(&irq_set[i], kvm, irq_source_id, level,
				   line_status);
		if (r < 0)
			continue;

		ret = r + ((ret < 0) ? 0 : ret);
	}

	return ret;
}
```

注释说得很直白：KVM 不知道 guest 用的是 PIC 还是 IOAPIC，所以两边都设。返回值是各路由返回值中非负部分的和，全部为负时返回 -1。

路由表是用 SRCU 保护的，读路径（每一次 `KVM_IRQ_LINE`）无锁，写路径（`KVM_SET_GSI_ROUTING`）替换整张表后等待 SRCU 宽限期。**`KVM_SET_GSI_ROUTING` 是整表替换，不是增量更新**：VMM 如果只想加一条 MSI 路由，必须把默认的 40 条（16 × 2 + 8）连同新的一起提交，否则 GSI 0–23 的路由就全没了。

**路由项类型**（`kvm_set_routing_entry()`，`irq_comm.c:267`）：

| 类型 | 用途 | 投递函数 |
|---|---|---|
| `KVM_IRQ_ROUTING_IRQCHIP` | 连到内核 PIC 主片、从片或 IOAPIC 的某根引脚 | `kvm_set_pic_irq` / `kvm_set_ioapic_irq` |
| `KVM_IRQ_ROUTING_MSI` | 直接构造一条 MSI 消息（地址 + 数据） | `kvm_set_msi` |
| `KVM_IRQ_ROUTING_HV_SINT` | Hyper-V 合成中断 | `kvm_hv_set_sint` |

split irqchip 模式下不允许 `IRQCHIP` 类型的路由（内核里没有 PIC 和 IOAPIC），只能用 MSI。

**GSI 0 的两种接法。** 真实 PC 上，PIT 的输出接 8259A 的 IR0，但在 IOAPIC 上通常接的是 **pin 2**（pin 0 接 8259A 的 INT 输出，用于 virtual wire）。所以绝大多数真实固件的 MADT 里都有一条中断源覆盖（Interrupt Source Override）：ISA IRQ 0 → GSI 2。QEMU 为了模仿真实硬件，也在 MADT 里写了这条覆盖，并用 `KVM_SET_GSI_ROUTING` 把 KVM 的 GSI 0 改路由到 IOAPIC pin 2。KVM 的默认路由则是恒等：GSI 0 → pin 0。mini-vmm 选择不改路由、固件表也不写覆盖，两边都是恒等。两种做法都对，**错的是混搭**：照抄 QEMU 的 MADT 覆盖，但保留 KVM 默认路由，结果 Linux 按覆盖把时钟中断配置在 pin 2，KVM 内核 PIT 却一直在拉 pin 0，`check_timer()` 失败。blog 第十章 10.6 节和第十五章的 `/proc/interrupts` 验证讲的就是这件事。

**MSI 路由的翻译**（`kvm_set_msi_irq()`）。MSI 消息的地址和数据格式与 IOAPIC 表项几乎一一对应，这也印证了“IOAPIC 就是个 MSI 生成器”：

| MSI 地址位 | 含义 | 对应 IOAPIC 表项 |
|---|---|---|
| 31:20 | 固定 `0xFEE` | — |
| 19:12 | Destination ID | bit63:56 |
| 3 | Redirection Hint | （与 lowest priority 配合） |
| 2 | Destination Mode | bit11 |

| MSI 数据位 | 含义 | 对应 IOAPIC 表项 |
|---|---|---|
| 7:0 | Vector | bit7:0 |
| 10:8 | Delivery Mode | bit10:8 |
| 14 | Level（Assert） | — |
| 15 | Trigger Mode | bit15 |

KVM 把两者都翻译成同一个 `struct kvm_lapic_irq`，再交给同一个 `kvm_irq_delivery_to_apic()`。从这个函数往后，“来自 IOAPIC 的中断”和“来自 MSI 的中断”在 KVM 里没有任何区别。

## 3. LAPIC：每颗 CPU 门口的守门人

### 3.1 两种访问方式与 `IA32_APIC_BASE`

LAPIC 集成在每颗 CPU 核心里，是中断到达 CPU 前的最后一站。它有两种编程接口：

- **xAPIC 模式**：寄存器映射在物理地址 `0xFEE00000` 开始的 4 KB 页里，用普通的 `mov` 访问。每颗 CPU 访问同一个物理地址，看到的却是**自己的** LAPIC，这个地址在 CPU 内部就被截获了，不会出现在系统总线上。
- **x2APIC 模式**：寄存器改为 MSR `0x800`–`0x8FF`，用 `rdmsr`/`wrmsr` 访问。MSR 编号 = `0x800 + (xAPIC 偏移 >> 4)`，比如 EOI 在 xAPIC 下是偏移 `0x0B0`，在 x2APIC 下是 MSR `0x80B`。APIC ID 从 8 位扩展到 32 位，ICR 合并成一个 64 位 MSR，写一次就发送。

两种模式由 **`IA32_APIC_BASE`**（MSR `0x1B`）控制：

| 位 | 名称 | 含义 |
|---|---|---|
| 8 | BSP | 只读，1 = 这颗 CPU 是启动处理器 |
| 10 | EXTD | 1 = x2APIC 模式（要求 EN 也为 1） |
| 11 | EN | LAPIC 全局使能（硬件使能）。清零后 LAPIC 完全关闭，CPU 退回 PC/AT 的 INTR 引脚接法 |
| 51:12 | Base | xAPIC 寄存器页的物理基址，默认 `0xFEE00` |

KVM 在 vCPU 复位时设置这个 MSR（`kvm_lapic_reset()`，`lapic.c:2321`）：

```c
	if (!init_event) {
		msr_val = APIC_DEFAULT_PHYS_BASE | MSR_IA32_APICBASE_ENABLE;
		if (kvm_vcpu_is_reset_bsp(vcpu))
			msr_val |= MSR_IA32_APICBASE_BSP;
		kvm_lapic_set_base(vcpu, msr_val);
	}
```

即 `0xFEE00000 | EN`，vCPU 0 再加上 BSP 位。`kvm_vcpu_is_reset_bsp()` 比较的是 `kvm->arch.bsp_vcpu_id`（默认 0，可用 `KVM_SET_BOOT_CPU_ID` 修改）。这就是 blog 第十三章说“BSP 身份由 KVM 决定，VMM 不用管”的依据。

`kvm_lapic_set_base()` 最后有一句 `pr_warn_once("APIC base relocation is unsupported by KVM")`：guest 如果把基址改到别处，KVM 只打一行警告，不会真的搬家。

**mini-vmm 的 guest 实际工作在 xAPIC 模式。** 虽然 VMM 在 CPUID 里暴露了 x2APIC 特性位（blog 第十五章的 `/proc/cpuinfo` flags 里有 `x2apic`），但启动日志里有这样一行：

```
x2apic: IRQ remapping doesn't support X2APIC mode
```

它来自 Linux 6.6 的 `try_to_enable_x2apic()`（`apic.c:1864`）：在没有中断重映射（IOMMU）的情况下，只有 `x86_init.hyper.x2apic_available()` 返回真，Linux 才会启用 x2APIC；这个钩子由 KVM/Hyper-V 等 paravirt 探测代码提供，而 guest 内核没有开 `CONFIG_HYPERVISOR_GUEST`，钩子是默认的 `bool_x86_init_noop`，返回假。于是 Linux 调用 `x2apic_disable()`，所有 LAPIC 访问都走 MMIO。这对性能有直接影响：没有 AVIC 时，每一次 EOI、每一次发 IPI 都是一次 `#NPF` 退出加一次指令模拟，比 x2APIC 的 MSR 退出更贵（卷三第 5 节讲过 MMIO 为什么比 PIO 和 MSR 贵）。

**KVM 里 LAPIC 的 MMIO 分发。** IOAPIC 挂在 `KVM_MMIO_BUS` 上，全 VM 共享一份；LAPIC 却是每个 vCPU 一份，同一个地址在不同 vCPU 上要落到不同的对象。所以 LAPIC 不在总线上，而是在 `vcpu_mmio_write()`（`x86.c:6276`）里被**优先**检查：

```c
static int vcpu_mmio_write(struct kvm_vcpu *vcpu, gpa_t addr, int len,
			   const void *v)
{
	...
	do {
		n = min(len, 8);
		if (!(lapic_in_kernel(vcpu) &&
		      !kvm_iodevice_write(vcpu, &vcpu->arch.apic->dev, addr, n, v))
		    && kvm_io_bus_write(vcpu, KVM_MMIO_BUS, addr, n, v))
			break;
		...
	} while (len);
	...
}
```

先问当前 vCPU 自己的 LAPIC（`apic_mmio_write()` 检查地址是否落在 `base_address` 开始的 4 KB 内），不是再查 MMIO 总线，还不是才退出到用户态。与 IOAPIC 一样，**`0xFEE00000` 这一页不能被 memslot 覆盖**，否则 guest 的 LAPIC 访问会写进内存。启用 AVIC 时，KVM 会自己在这里放一个私有 memslot（`APIC_ACCESS_PAGE_PRIVATE_MEMSLOT`），那是另一回事，见第 8 节。

### 3.2 寄存器地图

xAPIC 页里每个寄存器 32 位宽，但按 16 字节对齐。Intel SDM 规定访问必须是 32 位对齐访问，KVM 的 `apic_mmio_write()` 对不满足 `len == 4 && (offset & 0xf) == 0` 的写直接忽略。

| 偏移 | 寄存器 | 读写 | 说明（KVM 行为） |
|---|---|---|---|
| `0x020` | ID | RW | bit31:24 为 xAPIC ID。KVM 复位时写入 `vcpu_id` |
| `0x030` | Version | RO | KVM 返回 `0x00050014`：版本 `0x14`，bit23:16 = 5 表示 6 个 LVT（最大下标 5） |
| `0x080` | TPR | RW | 任务优先级，见 3.4 节 |
| `0x090` | APR | RO | 仲裁优先级，KVM 返回 0 |
| `0x0A0` | PPR | RO | 处理器优先级，读时现算 |
| `0x0B0` | EOI | WO | 写任意值表示当前中断处理结束 |
| `0x0C0` | RRD | RO | 远程读，已废弃 |
| `0x0D0` | LDR | RW | 逻辑目标寄存器，bit31:24 为逻辑 ID |
| `0x0E0` | DFR | RW | 目标格式寄存器，bit31:28：`1111` = flat，`0000` = cluster |
| `0x0F0` | SVR | RW | 伪中断向量寄存器，见 3.5 节 |
| `0x100`–`0x170` | ISR | RO | 256 位在服务寄存器，分 8 个 32 位寄存器 |
| `0x180`–`0x1F0` | TMR | RO | 256 位触发模式寄存器，1 = 电平 |
| `0x200`–`0x270` | IRR | RO | 256 位中断请求寄存器 |
| `0x280` | ESR | RW | 错误状态 |
| `0x2F0` | LVT CMCI | RW | KVM 不实现（`KVM_APIC_LVT_NUM` = 6，不含 CMCI） |
| `0x300` | ICR 低 32 位 | RW | 写入即发送 IPI，见 3.7 节 |
| `0x310` | ICR 高 32 位 | RW | bit31:24 为目标 |
| `0x320` | LVT Timer | RW | |
| `0x330` | LVT Thermal | RW | |
| `0x340` | LVT PerfMon | RW | |
| `0x350` | LVT LINT0 | RW | |
| `0x360` | LVT LINT1 | RW | |
| `0x370` | LVT Error | RW | |
| `0x380` | Timer Initial Count | RW | |
| `0x390` | Timer Current Count | RO | 读时由 hrtimer 剩余时间反算 |
| `0x3E0` | Timer Divide Config | RW | |
| `0x3F0` | Self IPI | WO | 仅 x2APIC 模式 |

KVM 把这一整页存成一个 4 KB 的数组 `apic->regs`，布局与硬件完全相同，`kvm_lapic_get_reg(apic, APIC_TASKPRI)` 就是读 `regs + 0x80`。`KVM_GET_LAPIC`/`KVM_SET_LAPIC` 传递的 `struct kvm_lapic_state` 是这一页的前 `KVM_APIC_REG_SIZE` = `0x400` 字节，恰好覆盖 `0x000`–`0x3F0` 的全部寄存器，偏移与硬件一致。这让 VMM 可以直接按偏移读出 guest 的 LAPIC 状态做调试：比如在 vCPU 卡死时读出 IRR 和 ISR，看有没有中断挂着没被处理。

### 3.3 IRR、ISR、TMR：256 位的位图

三个 256 位寄存器各对应 256 个向量，每 32 个向量占一个寄存器，寄存器间隔 16 字节。向量 v 在第 `v / 32` 个寄存器的第 `v % 32` 位，KVM 用 `REG_POS(v)` 和 `VEC_POS(v)` 两个宏计算：

```c
#define VEC_POS(v) ((v) & (32 - 1))
#define REG_POS(v) (((v) >> 5) << 4)
```

- **IRR**：已被 LAPIC 接受、尚未交给 CPU 的中断。
- **ISR**：已交给 CPU、尚未 EOI 的中断。允许多位同时为 1，表示中断嵌套。
- **TMR**：接受中断时记录它是边沿（0）还是电平（1），EOI 时据此决定要不要向 IOAPIC 广播 EOI（2.3 节）。

向量 0–15 是非法的，LAPIC 收到这些向量会在 ESR 里记“收到非法向量”并丢弃；向量 16–31 虽然合法，但与 CPU 异常重叠，操作系统不会使用。Linux 通过把 TPR 设为 `0x10` 来确保 16–31 永远不会被投递（见下一节）。

找最高优先级的中断就是找最高置位的位。KVM 的 `find_highest_vector()`（`lapic.c:396`）从最高的寄存器往下扫，找到第一个非零寄存器后用 `__fls` 取最高位：

```c
static int find_highest_vector(void *bitmap)
{
	int vec;
	u32 *reg;

	for (vec = MAX_APIC_VECTOR - APIC_VECTORS_PER_REG;
	     vec >= 0; vec -= APIC_VECTORS_PER_REG) {
		reg = bitmap + REG_POS(vec);
		if (*reg)
			return __fls(*reg) + vec;
	}

	return -1;
}
```

每次都扫 8 个寄存器太慢，所以 KVM 做了两个缓存：`irr_pending` 表示 IRR 是否可能非空，`isr_count` 和 `highest_isr_cache` 记录 ISR 的位数和最高位。`apic_set_isr()` 里有一段很好的推理注释：注入的总是 IRR 里最高的中断，所以“最后置位的 ISR 位”必然就是 ISR 里最高的那一位，缓存它是安全的。启用 APICv/AVIC 后硬件会直接改 ISR，这些缓存就失效了，代码里到处可见 `if (vcpu->arch.apicv_active)` 的分支。

### 3.4 TPR、PPR 与优先级类

LAPIC 的优先级按**优先级类**（priority class）计算：向量号的高 4 位，`vector >> 4`，所以 256 个向量分成 16 类，每类 16 个向量。类号越大优先级越高。

- **TPR**（Task Priority Register）：操作系统写入，表示“当前任务不想被优先级低于或等于这个类的中断打扰”。bit7:4 是类，bit3:0 是子类。64 位模式下 `CR8` 就是 TPR 的 bit7:4 的别名，`mov cr8, rax` 比写 MMIO 快得多。
- **PPR**（Processor Priority Register）：只读，由 LAPIC 根据 TPR 和 ISR 算出：

```c
static bool __apic_update_ppr(struct kvm_lapic *apic, u32 *new_ppr)
{
	u32 tpr, isrv, ppr, old_ppr;
	int isr;

	old_ppr = kvm_lapic_get_reg(apic, APIC_PROCPRI);
	tpr = kvm_lapic_get_reg(apic, APIC_TASKPRI);
	isr = apic_find_highest_isr(apic);
	isrv = (isr != -1) ? isr : 0;

	if ((tpr & 0xf0) >= (isrv & 0xf0))
		ppr = tpr & 0xff;
	else
		ppr = isrv & 0xf0;
	...
}
```

即 PPR = max(TPR 的类, ISR 最高位的类)。一个 IRR 中的中断能被交给 CPU，当且仅当它的类**严格大于** PPR 的类（`apic_has_interrupt_for_ppr()`）：

```c
	if (highest_irr == -1 || (highest_irr & 0xF0) <= ppr)
		return -1;
	return highest_irr;
```

举一个具体的例子。Linux 设置 TPR = `0x10`。假设 CPU 正在处理向量 `0x31` 的某个设备中断，ISR 里 `0x31` 置位：PPR = max(`0x10`, `0x30`) = `0x30`。这时另一个设备的向量 `0x35` 到达 IRR，它的类 `0x30` 不大于 PPR 的类 `0x30`，不能投递，要等 `0x31` 处理完。但如果此时来了一个 `0xEC`（LAPIC 定时器）或 `0xFB`（调用函数 IPI），类比 `0x30` 高，立即投递，嵌套进来。**同一类里的中断不能互相嵌套**，这是 LAPIC 与 8259A 在语义上的一个差别：8259A 按线号严格排序，LAPIC 按 16 个一组排序。

**EOI 为什么会“放出”新的中断。** 写 EOI 清掉 ISR 最高位，PPR 随之下降，原先被挡住的 IRR 中断可能就满足条件了。所以 `apic_set_eoi()` 在清 ISR 后调用 `apic_update_ppr()`，后者在 PPR 下降并且有可投递的中断时发出 `KVM_REQ_EVENT`，让 vCPU 在下一次进入 guest 前重新评估注入。TPR 被写低时同理。这就是 KVM 里 `KVM_REQ_EVENT` 的核心语义：**“中断相关的状态变了，下次 VMRUN 之前重新算一遍该注入什么”**。

`CR8` 与 TPR 的同步：SVM 的 VMCB 控制区有一个 `V_TPR` 字段，guest 读写 `CR8` 实际上读写的是它，不必退出。KVM 只在一种情况下拦截 `CR8` 写（`svm_update_cr8_intercept()`，`svm.c:3406`）：IRR 里有中断、但被当前 TPR 挡住（`tpr >= irr`）。这时 guest 一旦降低 TPR，KVM 需要立即知道，以便投递那个被挡住的中断；其余时候拦截是关闭的，KVM 在每次退出后把 `V_TPR` 同步回虚拟 LAPIC 的 TPR（`sync_cr8_to_lapic()`）。注意这只对 `CR8` 有效：mini-vmm 的 guest 在 xAPIC 模式下写偏移 `0x080` 的 TPR 寄存器，走的仍然是 MMIO 退出。第 5 节讲中断窗口时还会遇到 `V_TPR`。

### 3.5 SVR：软件使能与伪中断

SVR（Spurious-Interrupt Vector Register，偏移 `0x0F0`）：

| 位 | 含义 |
|---|---|
| 7:0 | 伪中断向量。Linux 用 `SPURIOUS_APIC_VECTOR` = `0xFF` |
| 8 | APIC 软件使能。0 = 软件禁用 |
| 9 | 焦点处理器检查（仅老式 lowest priority 仲裁，64 位 Linux 不用） |
| 12 | EOI 广播抑制（需要 Version 的 bit24 支持，见 2.3 节） |

LAPIC 有**两层使能**：`IA32_APIC_BASE.EN` 是硬件使能，SVR bit8 是软件使能。KVM 的判断是 `apic_enabled()` = `kvm_apic_sw_enabled() && kvm_apic_hw_enabled()`。复位后 SVR = `0xFF`，**bit8 为 0，也就是软件禁用的**。软件禁用状态下：

- 所有 LVT 的 mask 位被强制置 1，写 LVT 时 KVM 也会自动加上 mask（`kvm_lapic_reg_write()` 里 `if (!kvm_apic_sw_enabled(apic)) val |= APIC_LVT_MASKED;`）。
- Fixed 和 Lowest Priority 模式的中断会被丢弃（`__apic_accept_irq()` 里 `if (unlikely(!apic_enabled(apic))) break;`）。
- **INIT、SIPI、NMI 仍然会被接受。** 这一点对 SMP 启动至关重要：AP 在被唤醒之前，它的 LAPIC 处于软件禁用状态，只有这样 INIT-SIPI 才能起作用。

写 SVR 把 bit8 清零时，KVM 会把所有 LVT 都加上 mask，这是规范要求的行为。

**伪中断**的产生与 8259A 类似：LAPIC 已经决定投递某个中断，但在 CPU 响应之前，这个中断因为 TPR 提高而不再满足条件。这时 LAPIC 投递 SVR 里的伪中断向量，并且**不在 ISR 里置位**，处理程序不能写 EOI。KVM 的注入是原子地在 VMRUN 之前完成的，不会出现这种竞态，所以 KVM 从不产生 LAPIC 伪中断。

Linux 在 `setup_local_APIC()` 里完成软件使能的顺序（guest 侧 `apic.c`）：先 `init_apic_ldr()`，再把 TPR 设为 `0x10`（注释写得很明白：*accept all except vectors 0-31*），然后 `apic_pending_intr_clear()` 清掉残留的 ISR/IRR，最后才写 SVR = `APIC_SPIV_APIC_ENABLED | 0xFF`。

### 3.6 LVT：本地中断源

LVT（Local Vector Table）描述 LAPIC 自己的中断源该怎么投递。每个 LVT 寄存器格式相同，但不是每个字段都存在：

| 位 | 字段 | Timer | LINT0/1 | Error | Thermal/PerfMon |
|---|---|---|---|---|---|
| 7:0 | Vector | ✓ | ✓ | ✓ | ✓ |
| 10:8 | Delivery Mode | — | ✓ | — | ✓ |
| 12 | Delivery Status | ✓ | ✓ | ✓ | ✓ |
| 13 | Polarity | — | ✓ | — | — |
| 14 | Remote IRR | — | ✓ | — | — |
| 15 | Trigger Mode | — | ✓ | — | — |
| 16 | Mask | ✓ | ✓ | ✓ | ✓ |
| 18:17 | Timer Mode | ✓ | — | — | — |

投递模式：`000` Fixed、`010` SMI、`100` NMI、`101` INIT（仅 LINT）、`111` ExtINT（仅 LINT0 有意义）。定时器模式：`00` one-shot、`01` periodic、`10` TSC-deadline（需要 CPUID.1:ECX bit24）。

KVM 用 `apic_lvt_mask[]`（`lapic.c:388`）在写入时截掉不存在的位，比如 Timer 和 Error 不能设投递模式：

```c
static const unsigned int apic_lvt_mask[KVM_APIC_LVT_NUM] = {
	LVT_MASK ,      /* part LVTT mask, timer mode mask added at runtime */
	LVT_MASK | APIC_MODE_MASK,	/* LVTTHMR */
	LVT_MASK | APIC_MODE_MASK,	/* LVTPC */
	LINT_MASK, LINT_MASK,	/* LVT0-1 */
	LVT_MASK		/* LVTERR */
};
```

Timer 的“模式掩码”是运行时加上的：只有 guest CPUID.1:ECX 里有 TSC-deadline 位（bit24），`timer_mode_mask` 才包含 bit18（`cpuid.c:160` 附近的 `kvm_update_cpuid_runtime` 路径）。**VMM 在 `KVM_SET_CPUID2` 里要不要打开这一位，决定了 guest 能不能用 TSC-deadline 模式。** 这一位比较特殊：`KVM_GET_SUPPORTED_CPUID` 不会报告它，KVM 通过单独的 `KVM_CAP_TSC_DEADLINE_TIMER` 宣告支持，由 VMM 自己决定是否在 CPUID 里置位（QEMU 默认会置位）。mini-vmm 直接透传 `KVM_GET_SUPPORTED_CPUID` 的结果、没有额外置位，blog 第十五章 `/proc/cpuinfo` 的 flags 里也没有 `tsc_deadline_timer`，所以 guest 用的是 one-shot 模式：每次编程下一个 tick 都要写一次 TMICT，也就是一次 MMIO 退出。

**复位值与 LINT0 的特殊处理。** 复位时所有 LVT 都是 `APIC_LVT_MASKED`。但 KVM 为 BSP 做了一个例外（`kvm_lapic_reset()`）：

```c
	if (kvm_vcpu_is_reset_bsp(vcpu) &&
	    kvm_check_has_quirk(vcpu->kvm, KVM_X86_QUIRK_LINT0_REENABLED))
		kvm_lapic_set_reg(apic, APIC_LVT0,
			     SET_APIC_DELIVERY_MODE(0, APIC_MODE_EXTINT));
```

BSP 的 LVT0 复位为“ExtINT、未屏蔽”，模拟 BIOS 把系统留在 virtual wire 模式的状态。这个 quirk 默认开启，VMM 可以用 `KVM_CAP_DISABLE_QUIRKS` 关掉。它的作用是让 8259A 的中断在 guest 初始化 LAPIC 之前也能送达 BSP，结合 1.6 节的 `kvm_apic_accept_pic_intr()` 就能理解。

Linux 在 `setup_local_APIC()` 里重新设置 LINT0 和 LINT1：

```c
	value = apic_read(APIC_LVT0) & APIC_LVT_MASKED;
	if (!cpu && (pic_mode || !value || ioapic_is_disabled)) {
		value = APIC_DM_EXTINT;
		apic_printk(APIC_VERBOSE, "enabled ExtINT on CPU#%d\n", cpu);
	} else {
		value = APIC_DM_EXTINT | APIC_LVT_MASKED;
		apic_printk(APIC_VERBOSE, "masked ExtINT on CPU#%d\n", cpu);
	}
	apic_write(APIC_LVT0, value);

	if ((!cpu && apic_extnmi != APIC_EXTNMI_NONE) ||
	    apic_extnmi == APIC_EXTNMI_ALL)
		value = APIC_DM_NMI;
	else
		value = APIC_DM_NMI | APIC_LVT_MASKED;
	...
	apic_write(APIC_LVT1, value);
```

BSP 上 LINT0 保持 ExtINT（因为 KVM 复位时它是未屏蔽的，`!value` 成立），AP 上屏蔽；LINT1 在 BSP 上配置为 NMI。MADT 的 Local APIC NMI 条目（blog 第十五章日志里的 `ACPI: LAPIC_NMI (acpi_id[0xff] dfl dfl lint[0x1])`）告诉 Linux“所有 CPU 的 LINT1 接的是 NMI”，与这里的配置吻合。后续 `check_timer()` 和 symmetric I/O 的设置还会再改 LVT0，那部分在 1.7 节提过。

### 3.7 目标寻址：物理、逻辑 flat、逻辑 cluster

一条中断消息（来自 IOAPIC、MSI 或 IPI）带着一个目标字段和目标模式，每个 LAPIC 独立判断“是不是给我的”。KVM 的判断函数是 `kvm_apic_match_dest()`（`lapic.c:842`），它先看简写（shorthand），没有简写时再按模式分派：

```c
	switch (shorthand) {
	case APIC_DEST_NOSHORT:
		if (dest_mode == APIC_DEST_PHYSICAL)
			return kvm_apic_match_physical_addr(target, mda);
		else
			return kvm_apic_match_logical_addr(target, mda);
	case APIC_DEST_SELF:
		return target == source;
	case APIC_DEST_ALLINC:
		return true;
	case APIC_DEST_ALLBUT:
		return target != source;
	...
	}
```

**物理模式**：目标字段直接等于 APIC ID。xAPIC 下 `0xFF` 是广播，x2APIC 下 `0xFFFFFFFF` 是广播。

**逻辑模式**：目标字段是一个位集合（MDA，Message Destination Address），与每个 LAPIC 的 LDR 比较。比较方式由 DFR 决定（`kvm_apic_match_logical_addr()`）：

```c
	logical_id = GET_APIC_LOGICAL_ID(logical_id);

	switch (kvm_lapic_get_reg(apic, APIC_DFR)) {
	case APIC_DFR_FLAT:
		return (logical_id & mda) != 0;
	case APIC_DFR_CLUSTER:
		return ((logical_id >> 4) == (mda >> 4))
		       && (logical_id & mda & 0xf) != 0;
	...
	}
```

- **flat**：LDR 的 8 位逻辑 ID 与 MDA 按位与，非零即匹配。每颗 CPU 占一位，最多 8 颗 CPU，一条消息可以同时发给任意子集。
- **cluster**：高 4 位是簇号，必须相等；低 4 位是簇内的位集合。最多 15 个簇 × 4 颗 CPU。
- **x2APIC 逻辑模式**：LDR 由硬件根据 x2APIC ID 自动生成，不可写。bit31:16 是簇号（`id >> 4`），bit15:0 是簇内位（`1 << (id & 0xf)`）。

**mini-vmm 的 guest 用的是 logical flat。** Linux 6.6 的 64 位 APIC 驱动有两个：`apic_physflat` 和 `apic_flat`（`apic_flat_64.c`）。`physflat_probe()` 只在 `num_possible_cpus() > 8` 时返回真，4 个 vCPU 的 guest 选中的是 `apic_flat`，它的 `dest_mode_logical = true`，`init_apic_ldr` 是：

```c
void default_init_apic_ldr(void)
{
	unsigned long val;

	apic_write(APIC_DFR, APIC_DFR_FLAT);
	val = apic_read(APIC_LDR) & ~APIC_LDR_MASK;
	val |= SET_APIC_LOGICAL_ID(1UL << smp_processor_id());
	apic_write(APIC_LDR, val);
}
```

CPU n 的逻辑 ID 是 `1 << n`，目标计算函数 `apic_flat_calc_apicid()` 就是 `return 1U << cpu;`。所以 guest 编程 IOAPIC 表项时，目标模式位是 1（逻辑），目标字段是 `1 << cpu`。blog 第十五章 `/proc/interrupts` 里 i8042 的中断落在 CPU2 上，对应的 IOAPIC 表项目标字段就是 `0x04`。如果把 vCPU 数改成 9 个或更多，guest 会自动切换到 physflat，表项的目标字段就变成 APIC ID 本身。**这对 VMM 没有要求，但对调试有意义**：dump IOAPIC 状态（`KVM_GET_IRQCHIP`）时要先看目标模式位，才能正确解读目标字段。

**KVM 的快速路径：`kvm_apic_map`。** 每次投递都遍历所有 vCPU 调用 `kvm_apic_match_dest()` 是 O(n) 的。KVM 维护了一张按 APIC ID 和逻辑 ID 索引的查找表 `struct kvm_apic_map`，由 `kvm_recalculate_apic_map()` 在 APIC ID、LDR、DFR 或使能状态变化时重建，用 RCU 发布。`kvm_irq_delivery_to_apic_fast()`（`lapic.c:984`）先查这张表，查不到（比如各 vCPU 的 DFR 不一致，或者 guest 用了 x2APIC 与 xAPIC 混合模式）才回退到 `irq_comm.c` 里的逐个遍历。这也是为什么 `kvm_lapic_reg_write()` 末尾无条件调用 `kvm_recalculate_apic_map()`，它内部会检查 `apic_map_dirty` 标志，没变化时立即返回。

**Lowest Priority 模式。** 投递模式 `001` 的语义是“在目标集合中选优先级最低的那颗 CPU”。硬件实现依赖 APR（仲裁优先级）和总线仲裁，KVM 没有真的去比较 TPR，而是提供了两种近似：默认的 `vector_hashing`（`x86.c` 的模块参数，默认开启）按向量号对目标集合取模，保证同一个向量总是落到同一颗 CPU；关闭时用 `apic_arb_prio` 做轮转。Linux 6.6 的 64 位 APIC 驱动已经统一使用 Fixed 模式，所以这条路径对现代 Linux guest 基本不会触发。

### 3.8 ICR：发送 IPI

ICR（Interrupt Command Register）是 LAPIC 唯一的“输出”寄存器，操作系统用它向其他 CPU 发送 IPI。xAPIC 下是两个 32 位寄存器：

| 位 | 字段 | 含义 |
|---|---|---|
| 7:0 | Vector | 向量号；对 SIPI 是启动页号 |
| 10:8 | Delivery Mode | `000` Fixed、`001` Lowest、`010` SMI、`100` NMI、`101` INIT、`110` Start-Up |
| 11 | Destination Mode | 0 = 物理，1 = 逻辑 |
| 12 | Delivery Status | 只读，1 = 正在发送 |
| 14 | Level | 0 = De-assert，1 = Assert；只对 INIT 有意义 |
| 15 | Trigger Mode | 0 = 边沿，1 = 电平；只对 INIT 有意义 |
| 19:18 | Destination Shorthand | `00` 无，`01` 自己，`10` 所有（含自己），`11` 所有（不含自己） |
| 63:56 | Destination | xAPIC 目标（在高 32 位寄存器 `0x310` 的 bit31:24） |

**写低 32 位（`0x300`）的动作触发发送**，所以必须先写高 32 位。Linux 6.6 的 xAPIC IPI 代码（`arch/x86/kernel/apic/ipi.c`）就是这个顺序，发送前还要轮询 bit12 等上一次发送完成（`apic_mem_wait_icr_idle()`）。

KVM 的处理（`kvm_lapic_reg_write()`）：

```c
	case APIC_ICR:
		/* No delay here, so we always clear the pending bit */
		val &= ~(1 << 12);
		kvm_apic_send_ipi(apic, val, kvm_lapic_get_reg(apic, APIC_ICR2));
		kvm_lapic_set_reg(apic, APIC_ICR, val);
		break;
```

KVM 的投递是同步的，写 ICR 返回时 IPI 已经放进目标 LAPIC 的 IRR 了，所以 Delivery Status 永远是 0，guest 的轮询循环一次就能通过。`kvm_apic_send_ipi()`（`lapic.c:1279`）把 ICR 拆成 `struct kvm_lapic_irq`，交给 `kvm_irq_delivery_to_apic()`，和 IOAPIC、MSI 走的是**同一个投递函数**。唯一的区别是 `src` 参数不为空，用于处理 shorthand 里“自己”和“除了自己”的判断。

x2APIC 下 ICR 是一个 64 位 MSR（`0x830`），`kvm_x2apic_msr_write()` 先写 ICR2 再写 ICR，保证了同样的语义。x2APIC 模式下访问 `0x831`（ICR2）直接返回错误。

INIT 与 SIPI 这两种投递模式在 `__apic_accept_irq()` 里不是立即生效的，而是设置 `apic->pending_events` 的对应位，由目标 vCPU 在 `kvm_apic_accept_events()` 里处理，驱动 `mp_state` 状态机。这是卷六的主题，这里只需要知道：**IPI 的发送和接收，在 KVM 里是投递路径的一种特例，而不是单独的机制。**

### 3.9 LAPIC 定时器

LAPIC 定时器有三个寄存器和一个 LVT：

- **TDCR**（Divide Configuration，`0x3E0`）：分频系数。编码是 bit3 和 bit1:0 拼起来的 3 位值：`000` = 2、`001` = 4、`010` = 8、`011` = 16、`100` = 32、`101` = 64、`110` = 128、`111` = 1。
- **TMICT**（Initial Count，`0x380`）：写入即启动定时器。
- **TMCCT**（Current Count，`0x390`）：只读，按“总线时钟 / 分频”递减。

KVM 的分频计算（`update_divide_count()`）把上面的编码转换为 `divide_count`：

```c
	tmp1 = tdcr & 0xf;
	tmp2 = ((tmp1 & 0x3) | ((tmp1 & 0x8) >> 1)) + 1;
	apic->divide_count = 0x1 << (tmp2 & 0x7);
```

而“总线时钟”是 KVM 规定的：`#define APIC_BUS_CYCLE_NS 1`（`lapic.h:19`），即 **guest 看到的 LAPIC 总线频率是 1 GHz**。计数到时间的换算是 `tmict * APIC_BUS_CYCLE_NS * divide_count` 纳秒。Linux 的 `calibrate_APIC_clock()` 会用 PIT 或 TSC 测量它，所以 guest 算出来的值应该接近 1 GHz / 分频（Linux 用 16 分频，约 62.5 MHz）。

KVM 用 host 的 hrtimer 实现定时器，到期时调用 `apic_timer_expired()`，通过 `kvm_apic_local_deliver(apic, APIC_LVTT)` 投递 LVT Timer 里的向量，走的仍然是 `__apic_accept_irq()`。SVM 没有 VMX 那样的 preemption timer，所以 AMD 平台上 KVM 总是用软件 hrtimer，TSC-deadline 模式也是由 hrtimer 模拟。定时器的完整细节（周期模式的频率下限、`lapic_timer_advance_ns` 的提前量补偿）属于卷七的时间主题，这里略过。

下面按四个阶段拆开讲。

### 4.2 阶段一：ioctl 入口与路由

```c
int kvm_vm_ioctl_irq_line(struct kvm *kvm, struct kvm_irq_level *irq_event,
			bool line_status)
{
	if (!irqchip_in_kernel(kvm))
		return -ENXIO;

	irq_event->status = kvm_set_irq(kvm, KVM_USERSPACE_IRQ_SOURCE_ID,
					irq_event->irq, irq_event->level,
					line_status);
	return 0;
}
```

这里有两点对 VMM 很重要。

第一，**`KVM_IRQ_LINE` 只要求 `irqchip_in_kernel()`**，也就是创建过 `KVM_CREATE_IRQCHIP`（full irqchip）或启用了 split irqchip。没创建就返回 `-ENXIO`。在 split 模式下，GSI 路由表里只能有 MSI 类型的项，所以 `KVM_IRQ_LINE` 能拉的 GSI 必须事先被 VMM 映射成 MSI。

第二，**ioctl 本身总是返回 0**，结果放在 `status` 字段里。但 `status` 只有在用 `KVM_IRQ_LINE_STATUS`（ioctl 号不同，是 `_IOWR`）调用时才会被拷回用户态；`KVM_IRQ_LINE` 是 `_IOW`，`status` 不回写。VMM 如果需要知道“这个中断是被投递了、被合并了，还是被屏蔽了”，必须用前者。mini-vmm 用的是后者，因为 ISA 设备的模拟不需要这些信息。

`kvm_set_irq()` 在 2.7 节已经读过。它在 SRCU 读锁保护下把 GSI 映射成最多 `KVM_NR_IRQCHIPS`（3）个路由项，然后逐一调用每个路由项的 `set` 回调。对 GSI 4 来说是 PIC 和 IOAPIC 两个。

**这一段在哪个线程里执行？** 在调用 ioctl 的那个线程里。mini-vmm 的串口中断有两个来源：vCPU 线程在模拟 guest 对串口寄存器的访问时（比如 guest 写 THR，THRE 中断条件成立），以及 console 线程收到键盘输入时。前者是“vCPU 自己给自己或别的 vCPU 发中断”，后者是“外部线程给 vCPU 发中断”。KVM 对两者一视同仁，所有需要的锁（`ioapic->lock`、`pic->lock`）都在内部获取。

### 4.3 阶段二：芯片内部与投递

IOAPIC 内部的边沿检测和 `ioapic_service()` 在 2.5 节讲过。它产出一个 `struct kvm_lapic_irq`，这是 KVM 内部“一条中断消息”的统一表示：

```c
struct kvm_lapic_irq {
	u32 vector;
	u16 delivery_mode;
	u16 dest_mode;
	bool level;
	u16 trig_mode;
	u32 shorthand;
	u32 dest_id;
	bool msi_redir_hint;
};
```

IOAPIC 表项、MSI 消息、ICR 写入，三种来源都被翻译成这个结构，然后进入 `kvm_irq_delivery_to_apic()`。它先尝试快速路径 `kvm_irq_delivery_to_apic_fast()`：用 `kvm_apic_map` 按目标 ID 直接查出目标 LAPIC 数组，对每个目标调用 `kvm_apic_set_irq()`。快速路径失败时（比如 guest 各 CPU 的 DFR 不一致，map 被标记为“混合模式”），回退到慢速路径，遍历所有 vCPU 调用 `kvm_apic_match_dest()`。

**`__apic_accept_irq()`：LAPIC 接受中断。** 这个函数（`lapic.c:1063`）是所有投递模式的汇合点，Fixed 模式的分支是：

```c
	case APIC_DM_LOWEST:
		vcpu->arch.apic_arb_prio++;
		fallthrough;
	case APIC_DM_FIXED:
		if (unlikely(trig_mode && !level))
			break;

		/* FIXME add logic for vcpu on reset */
		if (unlikely(!apic_enabled(apic)))
			break;

		result = 1;

		if (dest_map) {
			__set_bit(vcpu->vcpu_id, dest_map->map);
			dest_map->vectors[vcpu->vcpu_id] = vector;
		}

		if (apic_test_vector(vector, apic->regs + APIC_TMR) != !!trig_mode) {
			if (trig_mode)
				kvm_lapic_set_vector(vector,
						     apic->regs + APIC_TMR);
			else
				kvm_lapic_clear_vector(vector,
						       apic->regs + APIC_TMR);
		}

		if (static_call(kvm_x86_deliver_posted_interrupt)(vcpu, vector)) {
			kvm_lapic_set_irr(vector, apic);
			kvm_make_request(KVM_REQ_EVENT, vcpu);
			kvm_vcpu_kick(vcpu);
		}
		break;
```

逐行对照硬件语义：

- `trig_mode && !level`：电平触发的 De-assert 消息，LAPIC 忽略。只有 INIT 的 De-assert（INIT Level De-assert）有意义，在 INIT 分支里单独处理。
- `!apic_enabled(apic)`：LAPIC 软件或硬件禁用时丢弃（3.5 节）。注意这里 `result` 仍是 0，IOAPIC 的 remote IRR 不会置位，这条电平中断下次还会再尝试投递。
- **TMR 在接受时设置**，记录这个向量是边沿还是电平，EOI 时要用（第 6 节）。
- `deliver_posted_interrupt`：在 SVM 上是 `svm_deliver_avic_intr()`。没有启用 AVIC 时它开头就 `return -1`，于是走 `if` 里面的“传统路径”：置 IRR，发 `KVM_REQ_EVENT`，kick。启用 AVIC 时它自己置 IRR 并按门铃，返回 0，不需要 `KVM_REQ_EVENT`（第 8 节）。

`kvm_lapic_set_irr()` 设置 IRR 位并把 `irr_pending` 置真。**到这里，中断已经“到达”了目标 vCPU，但还没有“注入”**：IRR 只是一个内存里的位图，guest 看不到它。要让 guest 响应这个中断，目标 vCPU 必须回到 `vcpu_enter_guest()`，在下一次 VMRUN 之前把它写进 VMCB。

### 4.4 阶段三：kick 与 `vcpu->mode`

`kvm_make_request(KVM_REQ_EVENT, vcpu)` 在 `vcpu->requests` 位图里置一位；`kvm_vcpu_kick()` 负责让目标 vCPU 尽快去看这个位图：

```c
void kvm_vcpu_kick(struct kvm_vcpu *vcpu)
{
	int me, cpu;

	if (kvm_vcpu_wake_up(vcpu))
		return;

	me = get_cpu();
	if (kvm_arch_vcpu_should_kick(vcpu)) {
		cpu = READ_ONCE(vcpu->cpu);
		if (cpu != me && (unsigned)cpu < nr_cpu_ids && cpu_online(cpu))
			smp_send_reschedule(cpu);
	}
	put_cpu();
}
```

目标 vCPU 可能处于三种状态，kick 分别这样处理：

| 目标 vCPU 的状态 | kick 的动作 | 结果 |
|---|---|---|
| 在 `kvm_vcpu_block()` 里睡眠（guest 执行了 HLT） | `kvm_vcpu_wake_up()` 唤醒等待队列 | 线程被调度，`vcpu_block()` 返回，`mp_state` 变回 RUNNABLE，下一轮进入 `vcpu_enter_guest()` |
| 正在物理 CPU 上运行 guest（`IN_GUEST_MODE`） | `kvm_arch_vcpu_should_kick()` 用 `cmpxchg` 把 mode 改为 `EXITING_GUEST_MODE`，成功则向那颗物理 CPU 发一个 reschedule IPI | 物理中断导致 `#VMEXIT(INTR)`，vCPU 退回 KVM，处理完退出后在下一轮 `vcpu_enter_guest()` 里看到请求 |
| 在 KVM 的 host 代码里（`OUTSIDE_GUEST_MODE`），比如正在处理上一次退出 | 什么都不做 | 它在下一次 VMRUN 之前一定会检查 `vcpu->requests` |

第三种情况“什么都不做”是否安全，取决于 `vcpu_enter_guest()` 里一段精心排列的顺序：

```c
	local_irq_disable();
	vcpu->mode = IN_GUEST_MODE;

	srcu_read_unlock(&vcpu->kvm->srcu, vcpu->srcu_idx);

	/*
	 * 1) We should set ->mode before checking ->requests.  Please see
	 * the comment in kvm_vcpu_exiting_guest_mode().
	 ...
	 */
	smp_mb__after_srcu_read_unlock();
	...
	if (kvm_vcpu_exit_request(vcpu)) {
		vcpu->mode = OUTSIDE_GUEST_MODE;
		smp_wmb();
		local_irq_enable();
		preempt_enable();
		vcpu->srcu_idx = srcu_read_lock(&vcpu->kvm->srcu);
		r = 1;
		goto cancel_injection;
	}
```

这是一个经典的“先写标志、再检查条件”的无锁协议，与发送方的“先写请求、再检查 mode”配对：

```
  发送方（任意线程）                       目标 vCPU 线程
  ─────────────────                       ────────────────
  set_bit(KVM_REQ_EVENT, requests)        mode = IN_GUEST_MODE
  smp_mb()                                smp_mb()
  读 mode                                  读 requests
    == IN_GUEST_MODE → 发 IPI               非空 → 放弃这次 VMRUN，重来
    == OUTSIDE       → 不发                 为空 → VMRUN
```

两边都是“写自己的变量、全屏障、读对方的变量”，所以不可能两边都读到旧值：要么发送方看到 `IN_GUEST_MODE` 从而发 IPI，要么目标看到请求从而取消进入。加上 `local_irq_disable()` 在设置 mode 之前执行，即使 IPI 在“检查 requests 之后、VMRUN 之前”到达，它也会被挂起在物理 CPU 上，VMRUN 一开中断（SVM 在 VMRUN 时恢复 GIF 并按 guest 的中断设置处理物理中断）就立即触发 `#VMEXIT`。卷一第 4.2 节讲过 `clgi`/`stgi` 与这个过程的配合。

**这个协议对 VMM 的停止协议是一个参照。** blog 第十三章的 `immediate_exit` + 信号方案，本质上是在用户态重建同样的“标志 + 唤醒”配对：VMM 置 `should_stop` 相当于置请求位，发信号相当于 kick，`immediate_exit` 相当于“进入前检查请求”。

### 4.5 阶段四：注入

目标 vCPU 回到 `vcpu_enter_guest()` 后：

```c
	if (kvm_check_request(KVM_REQ_EVENT, vcpu) || req_int_win ||
	    kvm_xen_has_interrupt(vcpu)) {
		++vcpu->stat.req_event;
		r = kvm_apic_accept_events(vcpu);
		...
		if (vcpu->arch.mp_state == KVM_MP_STATE_INIT_RECEIVED) {
			r = 1;
			goto out;
		}

		r = inject_pending_event(vcpu, &req_immediate_exit);
		...
		if (req_int_win)
			static_call(kvm_x86_enable_irq_window)(vcpu);

		if (kvm_lapic_enabled(vcpu)) {
			update_cr8_intercept(vcpu);
			kvm_lapic_sync_to_vapic(vcpu);
		}
	}
```

`kvm_apic_accept_events()` 先处理 INIT/SIPI（卷六），然后是 `inject_pending_event()`（`x86.c:8863`）。它的结构体现了 x86 事件的优先级：

1. **重新注入上一次没注入成功的事件。** `exception.injected`、`nmi_injected`、`interrupt.injected` 这三个标志表示“上次 VMRUN 时已经写进 EVENTINJ，但因为某种原因（见 5.3 节）没有真正交付给 guest”。它们必须原样再注入一次，并且 `can_inject = false`，本轮不再注入新事件。**EVENTINJ 一次只能放一个事件**，这是整个函数围绕 `can_inject` 组织的原因。
2. **注入新的异常。** 异常（`exception.pending`）优先于 NMI 和中断，因为挂起的 fault 类异常意味着上一条指令还没“完成”。
3. **SMI、NMI。**
4. **外部中断**：

```c
	if (kvm_cpu_has_injectable_intr(vcpu)) {
		r = can_inject ? static_call(kvm_x86_interrupt_allowed)(vcpu, true) : -EBUSY;
		if (r < 0)
			goto out;
		if (r) {
			kvm_queue_interrupt(vcpu, kvm_cpu_get_interrupt(vcpu), false);
			static_call(kvm_x86_set_irq)(vcpu);
			WARN_ON(static_call(kvm_x86_interrupt_allowed)(vcpu, true) < 0);
		}
		if (kvm_cpu_has_injectable_intr(vcpu))
			static_call(kvm_x86_enable_irq_window)(vcpu);
	}
```

`kvm_cpu_has_injectable_intr()` 先问 PIC（ExtINT），再问 LAPIC：`kvm_apic_has_interrupt()` 计算 PPR，看 IRR 最高位的类是否大于 PPR（3.4 节）。有中断可注入时，`svm_interrupt_allowed()` 检查 guest 当前能不能接受中断：

```c
bool svm_interrupt_blocked(struct kvm_vcpu *vcpu)
{
	struct vcpu_svm *svm = to_svm(vcpu);
	struct vmcb *vmcb = svm->vmcb;

	if (!gif_set(svm))
		return true;
	...
	} else {
		if (!(kvm_get_rflags(vcpu) & X86_EFLAGS_IF))
			return true;
	}

	return (vmcb->control.int_state & SVM_INTERRUPT_SHADOW_MASK);
}
```

三个条件：GIF（全局中断标志，嵌套虚拟化时 L1 可能清掉它）、guest 的 `RFLAGS.IF`、**中断影子**（VMCB 的 `int_state` bit0，表示 guest 刚执行了 `sti` 或 `mov ss`，下一条指令执行完之前不能响应中断）。

允许时：

- `kvm_cpu_get_interrupt()` → `kvm_get_apic_interrupt()`：**这是软件版的 INTA 周期**。它把向量从 IRR 移到 ISR（`apic_clear_irr()` + `apic_set_isr()`），更新 PPR。从这一刻起，这个中断在虚拟 LAPIC 看来已经“交给 CPU 了”。
- `kvm_queue_interrupt()`：记录 `interrupt.injected = true`、`interrupt.nr = vector`。
- `svm_set_irq()`：写 VMCB。

```c
static void svm_set_irq(struct kvm_vcpu *vcpu)
{
	struct vcpu_svm *svm = to_svm(vcpu);

	BUG_ON(!(gif_set(svm)));

	trace_kvm_inj_virq(vcpu->arch.interrupt.nr);
	++vcpu->stat.irq_injections;

	svm->vmcb->control.event_inj = vcpu->arch.interrupt.nr |
		SVM_EVTINJ_VALID | SVM_EVTINJ_TYPE_INTR;
}
```

不允许时，调用 `svm_enable_irq_window()` 请求“中断窗口”，这是第 5 节的内容。

注入完之后还有一句 `if (kvm_cpu_has_injectable_intr(vcpu)) enable_irq_window`：如果 IRR 里还有别的中断（比如同时来了两个），本轮只能注入一个，剩下的要借助中断窗口在 guest 能再次接受中断时尽快退出，再注入下一个。

### 4.6 EVENTINJ 字段

VMCB 控制区偏移 `0xA8` 的 `EVENTINJ` 是 64 位字段，格式由 AMD APM 第 2 卷 15.20 节定义，KVM 的宏在 `arch/x86/include/asm/svm.h:365` 起：

| 位 | 名称 | 含义 |
|---|---|---|
| 7:0 | VECTOR | 向量号 |
| 10:8 | TYPE | 0 = 外部中断（INTR）；2 = NMI；3 = 异常；4 = 软件中断（`INT n`） |
| 11 | EV | 1 = 异常带错误码，错误码在 bit63:32 |
| 30:12 | — | 保留，必须为 0 |
| 31 | V | 1 = 本字段有效 |
| 63:32 | ERRORCODE | 错误码 |

```c
#define SVM_EVTINJ_VEC_MASK 0xff
#define SVM_EVTINJ_TYPE_SHIFT 8
#define SVM_EVTINJ_TYPE_INTR (0 << SVM_EVTINJ_TYPE_SHIFT)
#define SVM_EVTINJ_TYPE_NMI (2 << SVM_EVTINJ_TYPE_SHIFT)
#define SVM_EVTINJ_TYPE_EXEPT (3 << SVM_EVTINJ_TYPE_SHIFT)
#define SVM_EVTINJ_TYPE_SOFT (4 << SVM_EVTINJ_TYPE_SHIFT)
#define SVM_EVTINJ_VALID (1 << 31)
#define SVM_EVTINJ_VALID_ERR (1 << 11)
```

CPU 处理 `EVENTINJ` 的时机是：VMRUN 加载完 guest 状态之后、执行第一条 guest 指令之前。**注入时硬件不检查 `RFLAGS.IF`、不检查中断影子**，这正是 KVM 必须在软件里先调用 `svm_interrupt_allowed()` 的原因：如果 KVM 在 guest `IF = 0` 时注入 INTR 类型的事件，guest 会在关中断的临界区里被中断打断，这是严重的正确性错误。事件交付后由硬件清掉 `V` 位（KVM 在正常路径上从不手动清 `event_inj`，唯一的 `control->event_inj = 0` 在 `svm_cancel_injection()` 里）。如果交付过程本身被打断（比如 guest 的 IDT 或内核栈所在页触发 `#NPF`），事件会被记录到 `EXITINTINFO`，见 5.3 节。

同一个格式也用于 `EXITINTINFO`（偏移 `0x88`），这是 AMD 设计上的一个优雅之处：退出时读出来的“未完成事件”可以不经任何转换直接写回 `EVENTINJ` 重新注入。`svm_cancel_injection()` 就是这么做的：`control->exit_int_info = control->event_inj;` 然后调用通用的完成函数。

### 4.7 guest 看到了什么

对 guest 来说，被注入的中断与真实硬件中断没有任何区别：CPU 在指令边界上检测到外部中断，以 `vector` 为下标查 IDT，压栈 `SS:RSP`、`RFLAGS`、`CS:RIP`，清 `IF`，跳进处理程序。Linux 6.6 的 IDT 里，设备中断向量都指向 `common_interrupt` 入口，它读出向量号，查每 CPU 的 `vector_irq[]` 表得到 `irq_desc`，调用 `handle_edge_irq()` 或 `handle_fasteoi_irq()`，最终调用驱动注册的处理函数（对串口是 `serial8250_interrupt()`）。

对 IOAPIC 来的中断，EOI 的时机取决于流控类型：边沿中断走 `handle_edge_irq()`，在调用驱动**之前**就通过 `irq_ack` 回调（`ioapic_chip` 里是 `irq_chip_ack_parent`，逐层上交到向量域的 `apic_ack_edge()`）写 EOI；电平中断走 `handle_fasteoi_irq()`，在驱动**之后**通过 `irq_eoi` 回调 `ioapic_ack_level()` 写 EOI。两者最终都调用 `apic_eoi()`，向 LAPIC 的 EOI 寄存器写 0。电平中断之所以要在处理之后才 EOI，是因为 EOI 会让 IOAPIC 重新采样引脚，此时设备的中断条件必须已经被驱动清掉（2.3 节）。这一写就把我们带进了反向链路。

## 5. 注入的边角：中断窗口、重新注入与 HLT

4.5 节留下了三个问题：guest 当前不能接受中断时怎么办；写进 `EVENTINJ` 的事件没有被交付怎么办；guest 在 HLT 里睡着时中断怎么把它叫醒。这一节逐一回答。

### 5.1 中断窗口：让硬件告诉 KVM“现在可以了”

`svm_interrupt_allowed()` 返回假，最常见的原因是 guest 的 `RFLAGS.IF = 0`：它正在关中断的临界区里（`spin_lock_irqsave()`、中断处理程序本身、`cli` 到 `sti` 之间）。KVM 不能注入，只能等。问题是等到什么时候：guest 执行 `sti` 或 `popf` 恢复 `IF` 是不会退出的，KVM 无从得知。

SVM 提供的解决办法是**虚拟中断**（`V_IRQ`）。VMCB 控制区偏移 `0x60` 的 `int_ctl` 字段里有一组“虚拟中断控制位”（`arch/x86/include/asm/svm.h:173` 起）：

| 位 | 名称 | 含义 |
|---|---|---|
| 3:0 | `V_TPR` | 虚拟 TPR，guest 的 `CR8` 读写落在这里（3.4 节） |
| 8 | `V_IRQ` | 1 = 有一个虚拟中断挂起 |
| 19:16 | `V_INTR_PRIO` | 这个虚拟中断的优先级类，与 `V_TPR` 比较 |
| 20 | `V_IGN_TPR` | 1 = 忽略 `V_TPR` 比较 |
| 24 | `V_INTR_MASKING` | 1 = guest 的 `RFLAGS.IF` 只控制虚拟中断，host 的物理中断不受 guest `IF` 影响 |
| 31 | `AVIC_ENABLE` | 启用 AVIC（第 8 节） |

`V_IRQ` 的硬件语义是：当 `V_IRQ = 1`，并且 guest 的 `IF = 1`、没有中断影子、`V_INTR_PRIO > V_TPR`（或 `V_IGN_TPR = 1`）时，CPU 认为“虚拟中断可以被接受了”。此时如果 VMCB 拦截了 `VINTR`，CPU 在 guest 取这个虚拟中断之前产生 `#VMEXIT(VINTR)`；如果没有拦截，CPU 就像接受一个真实中断一样用 `int_vector` 字段里的向量进入 guest 的 IDT。

KVM 只用前一种方式，把 `V_IRQ` 当作一个“闹钟”（`svm_set_vintr()`，`svm.c:1532`）：

```c
static void svm_set_vintr(struct vcpu_svm *svm)
{
	struct vmcb_control_area *control;

	/*
	 * The following fields are ignored when AVIC is enabled
	 */
	WARN_ON(kvm_apicv_activated(svm->vcpu.kvm));

	svm_set_intercept(svm, INTERCEPT_VINTR);

	/*
	 * This is just a dummy VINTR to actually cause a vmexit to happen.
	 * Actual injection of virtual interrupts happens through EVENTINJ.
	 */
	control = &svm->vmcb->control;
	control->int_vector = 0x0;
	control->int_ctl &= ~V_INTR_PRIO_MASK;
	control->int_ctl |= V_IRQ_MASK |
		((/*control->int_vector >> 4*/ 0xf) << V_INTR_PRIO_SHIFT);
	vmcb_mark_dirty(svm->vmcb, VMCB_INTR);
}
```

注释说得很直白：*This is just a dummy VINTR to actually cause a vmexit to happen.* 向量设为 0（不会被真正使用），优先级设为最高的 `0xf` 以确保不被 `V_TPR` 挡住，打开 `VINTR` 拦截。guest 一旦 `sti`，下一条指令边界上 CPU 就产生 `#VMEXIT(VINTR)`，处理函数 `interrupt_window_interception()`（`svm.c:2985`）清掉这个假中断，发出 `KVM_REQ_EVENT`：

```c
static int interrupt_window_interception(struct kvm_vcpu *vcpu)
{
	kvm_make_request(KVM_REQ_EVENT, vcpu);
	svm_clear_vintr(to_svm(vcpu));
	...
	++vcpu->stat.irq_window_exits;
	return 1;
}
```

返回 1 表示不回用户态，直接回到 `vcpu_enter_guest()`。这一次 `inject_pending_event()` 发现 `IF = 1`，正常通过 `EVENTINJ` 注入。

```
guest: cli ... (IF=0) ........... sti   next_insn
                                    │
KVM:   有中断挂起但 IF=0             │
       svm_set_vintr()：V_IRQ=1     │
       拦截 VINTR                   │
       VMRUN ───────────────────────┘
                                    ▼
                         #VMEXIT(VINTR)（sti 的中断影子过后）
       interrupt_window_interception()
       KVM_REQ_EVENT
       inject_pending_event()：IF=1，EVENTINJ = vector
       VMRUN ─► guest 在 next_insn 之前进入中断处理程序
```

**为什么不直接用 `V_IRQ` 注入？** 从硬件能力上说，把真实向量写进 `int_vector`、不拦截 `VINTR`，CPU 就会在 guest 开中断的第一时间自己投递，省掉一次退出。KVM 不这么做，是因为用 `V_IRQ` 投递的中断，其交付时机由硬件决定，KVM 无法在交付的那一刻完成“IRR 移到 ISR、更新 PPR”这些虚拟 LAPIC 的簿记，也无法与异常、NMI 的优先级正确排序。`EVENTINJ` 则是在 KVM 完全掌控的时刻、以确定的顺序注入。代价是每个“关中断期间到来的中断”都多一次 `VINTR` 退出。`perf kvm stat` 里 `vintr` 占比较高就是这个原因，卷三第 7.2 节提过健康虚拟机的退出分布里常见 `vintr`。

**中断影子。** `sti` 和 `mov ss` 会让下一条指令执行完之前不响应中断，这叫中断影子（interrupt shadow）。Linux 的 idle 循环正是依赖它：`sti; hlt` 两条指令之间不会被中断打断，保证“开中断”和“睡眠”是原子的，不会出现“刚开中断中断就来了，处理完再去 HLT 就再也醒不来”的竞态。VMCB 的 `int_state` bit0 记录 guest 当前是否处于影子中，`svm_interrupt_blocked()` 检查它；KVM 模拟一条指令后（比如 `kvm_skip_emulated_instruction()`）会通过 `svm_set_interrupt_shadow()` 维护它。`V_IRQ` 的硬件判断同样尊重影子，所以 `sti` 之后的 `VINTR` 退出会发生在影子结束的那条指令边界上。

**NMI 窗口。** NMI 不受 `IF` 控制，但受“NMI 正在处理中”这个隐藏状态控制：从 NMI 处理程序入口到执行 `iret` 之前，新的 NMI 被阻塞。SVM 没有等价于 `V_IRQ` 的 NMI 窗口机制，KVM 的办法是注入 NMI 时打开 `IRET` 拦截（`svm_inject_nmi()` 里的 `svm_set_intercept(svm, INTERCEPT_IRET)`），guest 执行 `iret` 时退出，KVM 就知道 NMI 处理结束了。`svm_complete_interrupts()` 开头那段 `HF_IRET_MASK` 的判断，是在确认 `iret` 已经真正执行完毕（RIP 前进了）之后才清除 NMI 阻塞标志。

### 5.2 一次只能注入一个

`EVENTINJ` 只有一个槽位，而 guest 可能同时有多个待处理事件：一个异常、一个 NMI、IRR 里的若干个中断。`inject_pending_event()` 的 `can_inject` 变量就是在管理这个槽位：一旦本轮已经注入了某个事件，后面的事件只能等下一轮。

对于等待的中断，KVM 在注入完成后打开中断窗口（4.5 节的最后一句 `if (kvm_cpu_has_injectable_intr(vcpu)) enable_irq_window`）。这很巧妙：刚注入的中断会让 guest 进入处理程序，CPU 在进入中断门时自动清 `IF`，于是 `V_IRQ` 的条件不满足；处理程序执行完 `iret` 恢复 `IF` 的那一刻，`VINTR` 退出，KVM 注入下一个。如果 guest 处理程序内部提前开了中断（Linux 不会这么做），窗口会更早打开，嵌套中断也能被及时注入。

对于必须立即处理但无法注入的情况（比如嵌套虚拟化中 L2 的中断需要变成到 L1 的退出），`kvm_x86_*_allowed()` 返回 `-EBUSY`，`inject_pending_event()` 设置 `req_immediate_exit`，`vcpu_enter_guest()` 会调用 `request_immediate_exit` 让 guest 进去执行零条或一条指令就马上退出，再来一轮。

### 5.3 `EXITINTINFO`：注入到一半被打断

KVM 把事件写进 `EVENTINJ` 并执行 VMRUN 后，CPU 开始交付这个事件：读 guest 的 IDT，读 GDT 中的代码段描述符，往 guest 内核栈上压 5 到 6 个 8 字节。这些都是 guest 内存访问，都要经过 NPT 翻译。如果其中任何一次访问触发 `#NPF`（比如 guest 的中断栈所在的页还没有被 KVM 建立映射），CPU 就会在事件交付完成之前产生 `#VMEXIT(NPF)`。

这时，被打断的事件记录在 VMCB 的 `EXITINTINFO`（偏移 `0x88`）里，格式与 `EVENTINJ` 相同。KVM 在每次退出后的 `svm_complete_interrupts()`（`svm.c:3636`）里检查它：

```c
	vcpu->arch.nmi_injected = false;
	kvm_clear_exception_queue(vcpu);
	kvm_clear_interrupt_queue(vcpu);

	if (!(exitintinfo & SVM_EXITINTINFO_VALID))
		return;

	kvm_make_request(KVM_REQ_EVENT, vcpu);

	vector = exitintinfo & SVM_EXITINTINFO_VEC_MASK;
	type = exitintinfo & SVM_EXITINTINFO_TYPE_MASK;

	switch (type) {
	case SVM_EXITINTINFO_TYPE_NMI:
		vcpu->arch.nmi_injected = true;
		break;
	case SVM_EXITINTINFO_TYPE_EXEPT:
		...
		if (exitintinfo & SVM_EXITINTINFO_VALID_ERR) {
			u32 err = svm->vmcb->control.exit_int_info_err;
			kvm_requeue_exception_e(vcpu, vector, err);
		} else
			kvm_requeue_exception(vcpu, vector);
		break;
	case SVM_EXITINTINFO_TYPE_INTR:
		kvm_queue_interrupt(vcpu, vector, false);
		break;
	default:
		break;
	}
```

逻辑是：先把所有“已注入”标志清掉（默认认为上次注入的事件已经成功交付）；如果 `EXITINTINFO` 有效，再根据类型把对应的“已注入”标志重新置上。下一轮 `inject_pending_event()` 的第一步“重新注入上一次没注入成功的事件”就会把它原样写回 `EVENTINJ`。

注意这里对外部中断用的是 `kvm_queue_interrupt()`，**不会**再走一遍 `kvm_get_apic_interrupt()`：这个向量在第一次注入时已经从 IRR 移到了 ISR，虚拟 LAPIC 的状态是“CPU 已经在处理它了”，重新注入只是让交付这个动作重做一遍，不能再动 LAPIC 的簿记。这也是 `interrupt.injected`（已过 INTA、需要重做交付）与 IRR 中的“挂起”（还没过 INTA）必须严格区分的原因，`irq.c` 里 `kvm_cpu_has_extint()` 那段 FIXME 注释讲的就是这两者在嵌套虚拟化中被混淆带来的问题。

`svm_cancel_injection()` 处理的是另一种“没交付”：KVM 已经写好了 `EVENTINJ`，但在 VMRUN 之前发现有新请求（4.4 节的 `kvm_vcpu_exit_request()`），决定放弃这次进入。它把 `EVENTINJ` 拷到 `EXITINTINFO`，清空 `EVENTINJ`，然后调用同一个 `svm_complete_interrupts()`，就好像这次注入被硬件打断了一样。一个函数处理了两种情况，这得益于两个字段格式相同。

**对 VMM 的意义。** 这一整套机制都在 KVM 内部，VMM 看不到。但它解释了一个调试时可能遇到的现象：`KVM_GET_VCPU_EVENTS` 读出来的 `interrupt.injected` 可能为 1，表示有一个中断“注入了一半”。VMM 做快照或迁移时必须用 `KVM_GET_VCPU_EVENTS`/`KVM_SET_VCPU_EVENTS` 保存恢复它，否则这个中断就丢了。

### 5.4 HLT：睡在 KVM 里

guest 空闲时执行 `hlt`。SVM 默认拦截 `HLT`，KVM 的处理是 `kvm_emulate_halt()` → `__kvm_vcpu_halt()`（`x86.c:8521`）：

```c
static int __kvm_vcpu_halt(struct kvm_vcpu *vcpu, int state, int reason)
{
	++vcpu->stat.halt_exits;
	if (lapic_in_kernel(vcpu)) {
		vcpu->arch.mp_state = state;
		return 1;
	} else {
		vcpu->run->exit_reason = reason;
		return 0;
	}
}
```

有内核 LAPIC 时，只把 `mp_state` 设为 `KVM_MP_STATE_HALTED`，返回 1（不回用户态）。`vcpu_run()` 的循环发现 `kvm_vcpu_running()` 为假，调用 `vcpu_block()` → `kvm_vcpu_block()`（`kvm_main.c`）：

1. **轮询阶段（halt polling）。** 如果 `vcpu->halt_poll_ns` 非零，先在 CPU 上忙等最多这么长时间，反复调用 `kvm_vcpu_check_block()` 检查有没有事件。`halt_poll_ns` 模块参数的默认值是 `KVM_HALT_POLL_NS_DEFAULT` = 200000，即 200 µs，每个 vCPU 的实际轮询时长会根据历史命中情况在 0 到这个上限之间自适应伸缩。这是用 CPU 时间换延迟：如果中断在几十微秒内就会到来，忙等比“睡眠 + 调度器唤醒”快得多。
2. **睡眠阶段。** 轮询超时后，`set_current_state(TASK_INTERRUPTIBLE)` 并 `schedule()`，线程让出物理 CPU，直到被 `kvm_vcpu_wake_up()` 唤醒或者收到信号。

`kvm_vcpu_check_block()` 判断“该醒了”的条件：

```c
static int kvm_vcpu_check_block(struct kvm_vcpu *vcpu)
{
	int ret = -EINTR;
	int idx = srcu_read_lock(&vcpu->kvm->srcu);

	if (kvm_arch_vcpu_runnable(vcpu)) {
		kvm_make_request(KVM_REQ_UNHALT, vcpu);
		goto out;
	}
	if (kvm_cpu_has_pending_timer(vcpu))
		goto out;
	if (signal_pending(current))
		goto out;
	if (kvm_check_request(KVM_REQ_UNBLOCK, vcpu))
		goto out;

	ret = 0;
out:
	srcu_read_unlock(&vcpu->kvm->srcu, idx);
	return ret;
}
```

其中 `kvm_arch_vcpu_runnable()` → `kvm_vcpu_has_events()` 对中断的判断是：

```c
	if (kvm_arch_interrupt_allowed(vcpu) &&
	    (kvm_cpu_has_interrupt(vcpu) ||
	    kvm_guest_apic_has_interrupt(vcpu)))
		return true;
```

**要求 `kvm_arch_interrupt_allowed()`，也就是 guest 的 `IF = 1`。** 这就是 `cli; hlt` 能让一颗 CPU 永久停下的原因：`IF = 0` 时任何外部中断都唤不醒它，只有 NMI、INIT、SMI 可以。Linux 在 panic 和关机时让其他 CPU 执行的 `stop_this_cpu()` 就是这么做的。blog 第十三章讲 `poweroff` 流程时，AP 在 `stop_this_cpu()` 里永远 HLT，vCPU 线程停在 `kvm_vcpu_block()` 里，VMM 必须用信号 + `immediate_exit` 把它们叫出来，道理就在这里。

**信号为什么能唤醒。** `signal_pending(current)` 是 `kvm_vcpu_check_block()` 的条件之一。VMM 向 vCPU 线程发信号，线程从 `schedule()` 返回（`TASK_INTERRUPTIBLE` 状态可被信号打断），检查到 `signal_pending`，`kvm_vcpu_block()` 返回，`vcpu_block()` 发现 `KVM_REQ_UNHALT` 没有置位，返回 1；`vcpu_run()` 循环在 `xfer_to_guest_mode_handle_work()` 里处理信号，返回 `-EINTR`，`KVM_RUN` 以 `EINTR` 失败返回用户态。整条路径不需要 guest 配合。

**对 VMM 的一个推论。** 创建了内核 irqchip 之后，VMM 永远不会看到 `KVM_EXIT_HLT`，只有不创建 irqchip 的模式才会看到它。mini-vmm 的退出处理里保留了 `KVM_EXIT_HLT` 分支，服务的是裸 payload 模式：那个模式不创建 irqchip（`vm_create()` 里只有 Linux 模式才调用 `irqchip_create()`），payload 执行 `hlt` 就表示运行结束。卷三第 6 节从性能角度讲过同一件事。

### 5.5 没有内核 irqchip 时：用户态注入接口

作为对照，看看不创建 `KVM_CREATE_IRQCHIP` 时 VMM 要怎么注入中断。mini-vmm 的裸 payload 模式就处在“没有 irqchip”的状态，只是它从不注入中断。看清这条路径，能帮助理解内核 irqchip 替 VMM 做了多少事。

没有内核 LAPIC，就没有 IRR、PPR，也没有中断窗口的自动处理。VMM 必须自己模拟 PIC/APIC，并用以下接口与 KVM 配合：

- **`KVM_INTERRUPT`（vCPU ioctl）**：把一个向量放进 vCPU 的“待注入”槽位。`kvm_vcpu_ioctl_interrupt()`（`x86.c:4384`）在没有内核 irqchip 时直接 `kvm_queue_interrupt(vcpu, irq->irq, false)`，下一次进入 guest 时注入。它不检查 `IF`，所以 VMM 必须自己保证调用时机正确。
- **`kvm_run->request_interrupt_window`**：VMM 置 1 表示“我有中断要注入，guest 能接受时请退出告诉我”。KVM 在 `vcpu_run()` 循环里检查（`dm_request_for_irq_injection()`），条件满足时以 `KVM_EXIT_IRQ_WINDOW_OPEN` 退出。
- **`kvm_run->ready_for_interrupt_injection`**：每次退出时 KVM 填写，1 表示此刻可以用 `KVM_INTERRUPT` 注入（`IF = 1`、没有影子、没有待重新注入的事件）。
- **`kvm_run->if_flag`**：guest 的 `RFLAGS.IF`，内核注释说它 *obsolete and useless*，应该用上一个字段。

在有内核 LAPIC 但 PIC 在用户态的 split irqchip 模式下，`KVM_INTERRUPT` 的语义变成“注入一个 ExtINT”：向量放进 `pending_external_vector`，由 `kvm_cpu_get_extint()` 取走，这就是 1.6 节 `irq.c` 代码里 `irqchip_split()` 分支的来源。在完整的内核 irqchip 模式下，`KVM_INTERRUPT` 直接返回 `-ENXIO`。

三种模式的对比：

| | 无 irqchip | split irqchip | full irqchip（mini-vmm） |
|---|---|---|---|
| 创建方式 | 不创建 | `KVM_ENABLE_CAP(KVM_CAP_SPLIT_IRQCHIP)` | `KVM_CREATE_IRQCHIP` |
| LAPIC | 用户态 | 内核 | 内核 |
| IOAPIC / PIC | 用户态 | 用户态 | 内核 |
| 设备中断入口 | `KVM_INTERRUPT` | `KVM_SIGNAL_MSI` 或 MSI 路由 + `KVM_IRQ_LINE`/irqfd | `KVM_IRQ_LINE`、irqfd |
| 中断窗口 | 用户态管理（`request_interrupt_window`） | 内核管理 | 内核管理 |
| HLT | `KVM_EXIT_HLT` 回用户态 | 内核阻塞 | 内核阻塞 |
| 电平中断 EOI | 用户态模拟 | `KVM_EXIT_IOAPIC_EOI` 回用户态 | 内核内闭环 |
| 典型用户 | 教学用的最小 VMM | QEMU（`-machine kernel-irqchip=split`）等 | QEMU 的 `kernel-irqchip=on`、Firecracker、mini-vmm |

split 模式把 IOAPIC 放回用户态，是为了安全（缩小内核攻击面）和灵活性（支持中断重映射的 IOMMU 模拟、超过 24 根引脚的 IOAPIC）。代价是电平中断的 EOI 要回用户态：`kvm_ioapic_send_eoi()` 在 split 模式下设置 `pending_ioapic_eoi` 并发出 `KVM_REQ_IOAPIC_EOI_EXIT`，vCPU 以 `KVM_EXIT_IOAPIC_EOI` 退出，由 VMM 的 IOAPIC 模拟清 remote IRR。

## 6. 反向链路：EOI 从 guest 回到 IOAPIC

### 6.1 全景

```
 guest 中断处理程序结束
 apic_eoi()：mov dword [0xFEE000B0], 0            （xAPIC 模式）
   │
   ▼ #VMEXIT(NPF)：GPA 0xFEE000B0 没有 memslot
   │
   ▼ npf_interception() → kvm_mmu_page_fault() → 判定为 MMIO → x86_emulate_instruction()
   │
   ▼ emulator_write_emulated() → vcpu_mmio_write()                    x86.c:6276
   │     先问本 vCPU 的 LAPIC：apic_mmio_write()                      lapic.c:2147
   │
   ▼ kvm_lapic_reg_write(apic, APIC_EOI, 0)                           lapic.c:2002
   │
   ▼ apic_set_eoi()                                                   lapic.c:1239
   │     vector = apic_find_highest_isr()；trace: kvm_eoi
   │     apic_clear_isr(vector)；apic_update_ppr()
   │
   ▼ kvm_ioapic_send_eoi(apic, vector)                                lapic.c:1216
   │     向量不在 ioapic_handled_vectors 里 → 结束（绝大多数边沿中断）
   │     TMR[vector] ? LEVEL : EDGE
   │
   ▼ kvm_ioapic_update_eoi(vcpu, vector, trigger_mode)                ioapic.c
   │     遍历 24 个表项，找 vector 相同的
   │
   ▼ kvm_ioapic_update_eoi_one()                                      ioapic.c:502
         kvm_notify_acked_irq() → ack notifier（PIT 补发、irqfd resample）
         电平：remote_irr = 0；引脚仍有效 → ioapic_service() 重投
```

### 6.2 LAPIC 侧：`apic_set_eoi()`

```c
static int apic_set_eoi(struct kvm_lapic *apic)
{
	int vector = apic_find_highest_isr(apic);

	trace_kvm_eoi(apic, vector);

	/*
	 * Not every write EOI will has corresponding ISR,
	 * one example is when Kernel check timer on setup_IO_APIC
	 */
	if (vector == -1)
		return vector;

	apic_clear_isr(vector, apic);
	apic_update_ppr(apic);
	...
	kvm_ioapic_send_eoi(apic, vector);
	kvm_make_request(KVM_REQ_EVENT, apic->vcpu);
	return vector;
}
```

几个值得注意的点：

- **EOI 写入的值被忽略**，LAPIC 总是清除 ISR 里**最高**的那一位。这就是为什么中断必须严格按嵌套顺序 EOI：处理程序 A 被 B 嵌套打断，B 必须先 EOI。Linux 的中断处理框架天然满足这一点。
- **ISR 为空时的 EOI 是合法的**，注释里举的例子正是 `check_timer()`：Linux 在测试时钟接法时会做一些“多余”的 EOI，KVM 必须容忍，不能报错。
- **`KVM_REQ_EVENT`**：EOI 让 PPR 下降，可能“放出”被挡住的中断（3.4 节），所以无条件请求重新评估。

### 6.3 什么时候 EOI 会通知 IOAPIC

`kvm_ioapic_send_eoi()`（`lapic.c:1216`）有一个过滤条件：

```c
static void kvm_ioapic_send_eoi(struct kvm_lapic *apic, int vector)
{
	int trigger_mode;

	/* Eoi the ioapic only if the ioapic doesn't own the vector. */
	if (!kvm_ioapic_handles_vector(apic, vector))
		return;

	/* Request a KVM exit to inform the userspace IOAPIC. */
	if (irqchip_split(apic->vcpu->kvm)) {
		apic->vcpu->arch.pending_ioapic_eoi = vector;
		kvm_make_request(KVM_REQ_IOAPIC_EOI_EXIT, apic->vcpu);
		return;
	}

	if (apic_test_vector(vector, apic->regs + APIC_TMR))
		trigger_mode = IOAPIC_LEVEL_TRIG;
	else
		trigger_mode = IOAPIC_EDGE_TRIG;

	kvm_ioapic_update_eoi(apic->vcpu, vector, trigger_mode);
}
```

`ioapic_handled_vectors` 是每个 vCPU 一份的 256 位位图，表示“哪些向量的 EOI 需要通知 IOAPIC”。它由 `vcpu_scan_ioapic()`（`x86.c:9357` 附近，响应 `KVM_REQ_SCAN_IOAPIC`）调用 `kvm_ioapic_scan_entry()`（2.6 节贴过）重建，包含三类表项的向量：

1. 电平触发的表项。它们需要 EOI 来清 remote IRR，这是规范要求。
2. 注册了 ack notifier 的引脚。即使是边沿中断，也有内核组件想知道“guest 什么时候处理完了”，PIT 就是这样（第 7 节）。
3. RTC（GSI 8），为了 2.6 节的 coalesced 统计。

只有目标是本 vCPU（或者本 vCPU 的 ISR 里正挂着这个向量）的表项才计入。什么时候重建？guest 每次写 IOAPIC 表项（`ioapic_write_indirect()` 末尾的 `kvm_make_scan_ioapic_request_mask()`）、注册或注销 ack notifier、路由表变化时。

**这个过滤对性能意义重大。** 对 mini-vmm 的 guest 来说，串口、键盘这些边沿中断的 EOI 在 `kvm_ioapic_handles_vector()` 处直接返回，完全不碰 IOAPIC 的锁；只有 PIT（有 ack notifier）和 SCI（电平）的 EOI 会走到 IOAPIC。在启用 AVIC 时，这张位图还有更直接的用途：它决定了哪些向量的 EOI 必须陷出，哪些可以由硬件直接完成（第 8 节）。

### 6.4 IOAPIC 侧：清 remote IRR 与重投

`kvm_ioapic_update_eoi()` 遍历所有 24 个表项，对向量匹配的每一个调用 `kvm_ioapic_update_eoi_one()`（2.6 节已贴出完整代码）。它做三件事：

1. **释放锁后调用 `kvm_notify_acked_irq()`**。释放锁是因为 ack notifier 的回调可能反过来调用 IOAPIC（比如设备直通的 resample irqfd 会重新拉线），不释放会死锁。注释解释了这样做的安全性：remote IRR 要在回调之后才清，所以回调期间到来的同向量中断只会进 `irr`，不会被重复投递。
2. **边沿中断到此为止。** `if (trigger_mode != IOAPIC_LEVEL_TRIG || ... APIC_SPIV_DIRECTED_EOI) return;`。另外如果 guest 在 SVR 里启用了 Directed EOI（只有 split irqchip 下 KVM 才宣告这个能力，见 2.3 节），广播的 EOI 也不清 remote IRR，要等 guest 写 IOAPIC 的 EOI 寄存器。
3. **电平中断：清 remote IRR，引脚仍有效就重投**，并带着 2.6 节的风暴检测。

用一个完整的时间线把电平中断的一生串起来（以 SCI 为例，假设 guest 已把 GSI 9 配置为电平、低有效、向量 `0x41`、目标 CPU0）：

| 步骤 | 事件 | IOAPIC 表项 9 | IOAPIC irr bit9 | CPU0 LAPIC |
|---|---|---|---|---|
| 1 | VMM：`KVM_IRQ_LINE(9, 1)` | remote IRR: 0 → 1 | 1 | IRR[0x41] = 1，TMR[0x41] = 1 |
| 2 | 注入 | 1 | 1 | IRR → ISR |
| 3 | guest ACPI 驱动读 PM1 状态寄存器、写 1 清除 | 1 | 1 | ISR[0x41] = 1 |
| 4 | VMM 的 PM1 模拟发现事件已清：`KVM_IRQ_LINE(9, 0)` | 1 | 0 | 不变 |
| 5 | guest 写 EOI | remote IRR: 1 → 0；irr = 0，不重投 | 0 | ISR[0x41] = 0 |

如果第 4 步漏掉了（VMM 忘了在事件清除后拉低线），第 5 步清掉 remote IRR 后发现 irr 仍为 1，立即重投，guest 再次进入 SCI 处理程序，发现没有事件，写 EOI，再重投……这就是 2.6 节的风暴。mini-vmm 从不拉 SCI，所以 `/proc/interrupts` 里 `acpi` 计数为 0，这个路径没有被实际走过，但它是将来实现 ACPI 电源按钮等事件时必须遵守的协议。

## 7. PIT 与 ack notifier：一个需要“知道 guest 处理完了”的设备

### 7.1 为什么时钟中断不能丢

PIT（8254）的通道 0 以固定频率产生时钟中断，老式操作系统用“收到了多少个 tick”来推进时间：每个 tick 让 `jiffies` 加一。在物理机上，只要中断处理及时，tick 不会丢。在虚拟机里情况不同：vCPU 线程可能被 host 调度走几十毫秒，这期间 KVM 的 hrtimer 照样按时到期，但 guest 根本没在运行，无法处理中断。如果 KVM 每次到期都简单地拉一次 GSI 0，那么 guest 回来时 IRR 里只有一个挂起的 tick（边沿中断会合并），丢掉的那些 tick 对应的时间就永远丢失了，guest 的时钟会变慢。

现代 Linux 不再依赖 tick 计数（它用 TSC 或 kvmclock 作为时钟源，tick 只用于驱动调度），但 Windows 和一些老内核仍然依赖。KVM 的 PIT 因此默认工作在**补发模式**（reinject）：记住错过了多少个 tick，guest 每处理完一个，再补发下一个。

### 7.2 实现：pending 计数 + ack notifier

补发的核心是三个函数（`arch/x86/kvm/i8254.c`）和两个原子变量：`pending`（错过、待补发的 tick 数）和 `irq_ack`（上一个 tick 是否已被 guest 处理完）。

hrtimer 到期（`pit_timer_fn()`），在 hrtimer 的中断上下文里执行：

```c
static enum hrtimer_restart pit_timer_fn(struct hrtimer *data)
{
	struct kvm_kpit_state *ps = container_of(data, struct kvm_kpit_state, timer);
	struct kvm_pit *pt = pit_state_to_pit(ps);

	if (atomic_read(&ps->reinject))
		atomic_inc(&ps->pending);

	kthread_queue_work(pt->worker, &pt->expired);

	if (ps->is_periodic) {
		hrtimer_add_expires_ns(&ps->timer, ps->period);
		return HRTIMER_RESTART;
	} else
		return HRTIMER_NORESTART;
}
```

只做计数和排队，真正拉线的工作交给一个名为 `kvm-pit/<pid>` 的内核线程（`pit_do_work()`）：

```c
static void pit_do_work(struct kthread_work *work)
{
	...
	if (atomic_read(&ps->reinject) && !atomic_xchg(&ps->irq_ack, 0))
		return;

	kvm_set_irq(kvm, pit->irq_source_id, 0, 1, false);
	kvm_set_irq(kvm, pit->irq_source_id, 0, 0, false);
	...
}
```

补发模式下，只有上一个 tick 已被确认（`irq_ack` 为 1）才拉线，并把 `irq_ack` 清零。拉线是一个完整的脉冲（先 1 后 0），正好构成一个边沿，也不会影响用户态中断源（PIT 有自己的 `irq_source_id`，1.6 节讲过线或位图）。

guest 处理完时钟中断、写 EOI 时，反向链路（第 6 节）走到 `kvm_notify_acked_irq(kvm, KVM_IRQCHIP_IOAPIC, pin)`（`virt/kvm/eventfd.c:482`），它把 (芯片, 引脚) 反查成 GSI，调用所有注册在这个 GSI 上的 ack notifier。PIT 在创建时注册了 GSI 0 上的 notifier，回调是 `kvm_pit_ack_irq()`：

```c
static void kvm_pit_ack_irq(struct kvm_irq_ack_notifier *kian)
{
	...
	atomic_set(&ps->irq_ack, 1);
	/* irq_ack should be set before pending is read.  Order accesses with
	 * inc(pending) in pit_timer_fn and xchg(irq_ack, 0) in pit_do_work.
	 */
	smp_mb();
	if (atomic_dec_if_positive(&ps->pending) > 0)
		kthread_queue_work(pit->worker, &pit->expired);
}
```

置 `irq_ack`，然后如果还有待补发的 tick，立即排队下一次 `pit_do_work()`。于是，vCPU 被调度走期间积累的 N 个 tick，会在它回来之后以“处理完一个、补发一个”的节奏依次送达，时间不会丢。

```
 hrtimer:  T1   T2   T3   T4            (vCPU 被调度走)        T5
 pending:  1    2    3    4                                   5 ...
 do_work:  拉线  ×    ×    ×   （irq_ack=0，等待）
 guest:                               回来，处理 T1，EOI
 ack:                                 irq_ack=1，pending 4→3，排队 do_work
 do_work:                             拉线（补 T2）
 guest:                                  处理，EOI → 补 T3 → ... 追上
```

PIT 的时钟中断是边沿触发的，为什么它的 EOI 能到达 IOAPIC？这正是 6.3 节 `ioapic_handled_vectors` 的第二类：注册了 ack notifier 的引脚，即使是边沿中断，它的向量也会被加入位图。经 8259A 投递时，`pic_clear_isr()` 在 EOI 命令里同样调用 `kvm_notify_acked_irq()`，所以两条路径都能补发。

**mask notifier。** 如果 guest 屏蔽了 IRQ0，积累的 pending 会越来越多，取消屏蔽时一下子补发几千个 tick 显然不合理。PIT 还注册了一个 mask notifier（`pit_mask_notifer()`，函数名里的拼写错误是源码原样），guest 取消屏蔽 GSI 0 时调用 `kvm_pit_reset_reinject()`，把 `pending` 清零、`irq_ack` 置 1。IOAPIC 的 `ioapic_write_indirect()` 和 8259A 的 OCW1 处理里都有 `kvm_fire_mask_notifiers()` 调用，1.6 节和 2.4 节贴的代码里能看到。

**关闭补发。** VMM 可以用 `KVM_REINJECT_CONTROL` 关闭补发模式（QEMU 的 `-global kvm-pit.lost_tick_policy=discard`）。关闭后 `pit_do_work()` 每次都拉线，丢了就丢了，也不再需要 ack notifier。mini-vmm 没有调用它，PIT 处于默认的补发模式。

### 7.3 补发模式与 AVIC 的冲突

`kvm_pit_set_reinject()` 里有一段注释解释了一个跨子系统的约束：

```c
	/*
	 * AMD SVM AVIC accelerates EOI write and does not trap.
	 * This cause in-kernel PIT re-inject mode to fail
	 * since it checks ps->irq_ack before kvm_set_irq()
	 * and relies on the ack notifier to timely queue
	 * the pt->worker work iterm and reinject the missed tick.
	 * So, deactivate APICv when PIT is in reinject mode.
	 */
	if (reinject) {
		kvm_request_apicv_update(kvm, false,
					 APICV_INHIBIT_REASON_PIT_REINJ);
		...
```

AVIC 下，边沿中断的 EOI 由硬件直接完成、不产生退出（第 8 节），KVM 收不到 EOI，PIT 的 ack notifier 就不会被调用，补发模式会卡在“等待确认”上。所以只要 PIT 处于补发模式，KVM 就以 `APICV_INHIBIT_REASON_PIT_REINJ` 为理由禁用 AVIC。**这意味着一个 VMM 即使在 `kvm_amd avic=1` 的 host 上运行，只要创建了内核 PIT 又不关闭补发，AVIC 就不会生效。** 这是第 8 节“AVIC 的抑制条件”的第一个例子。

### 7.4 `KVM_PIT_SPEAKER_DUMMY` 再看一眼

blog 第十章复盘过 `KVM_PIT_SPEAKER_DUMMY` 这个坑，这里从源码补一个细节。`kvm_create_pit()` 里：

```c
	if (flags & KVM_PIT_SPEAKER_DUMMY) {
		kvm_iodevice_init(&pit->speaker_dev, &speaker_dev_ops);
		ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS,
					      KVM_SPEAKER_BASE_ADDRESS, 4,
					      &pit->speaker_dev);
		...
	}
```

`KVM_SPEAKER_BASE_ADDRESS` 是 `0x61`，注册长度 4，所以端口 `0x61`–`0x64` 的访问都会先被 KVM 的 speaker 设备看到。`speaker_ioport_read()`/`speaker_ioport_write()` 内部只处理 `0x61`，对其余地址返回 `-EOPNOTSUPP`，访问继续向下分发，所以不会吞掉 i8042 的 `0x64` 端口。另外值得一提的是 `kvm_create_pit()` 在创建时就调用了 `kvm_pit_set_reinject(pit, true)`：补发模式、ack notifier 注册、AVIC 抑制，都是在 `KVM_CREATE_PIT2` 这一刻发生的。

## 8. AVIC：让硬件接管虚拟 LAPIC

### 8.1 要解决的问题

回顾第 4、6 节，没有硬件辅助时，一次设备中断在 KVM 里的开销包括：目标 vCPU 被 kick 出 guest（一次物理 IPI 加一次 `#VMEXIT`）、注入时可能遇到的 `VINTR` 退出、guest 写 EOI 的 `#NPF` 退出加指令模拟。IPI 更贵：发送方写 ICR 是一次 MMIO 退出，接收方再被 kick 一次。对于网络、存储这类每秒几十万次中断的负载，或者调度器频繁发送“重新调度 IPI”的多核负载，这些退出是主要的性能瓶颈。

Intel 的方案是 APICv（包含 virtual-APIC page、virtual interrupt delivery、posted interrupt 三部分），AMD 的方案是 **AVIC**（Advanced Virtual Interrupt Controller）。两者目标相同：**让 guest 对 LAPIC 的常见访问、以及中断的投递，不再需要 VMM 介入。**

### 8.2 四个数据结构

AVIC 的硬件接口是四个由 KVM 准备、由 CPU 直接读写的内存结构，在 VMCB 控制区里用物理地址指向它们：

| VMCB 字段 | 偏移 | 指向 | 粒度 |
|---|---|---|---|
| `avic_vapic_bar` | `0x98` | guest 眼中 LAPIC 的 GPA（`0xFEE00000`） | 每 VM |
| `avic_backing_page` | `0xE0` | **vAPIC backing page**：一个 4 KB 页，布局与 LAPIC 寄存器页完全相同 | 每 vCPU |
| `avic_logical_id` | `0xF0` | **逻辑 APIC ID 表**：逻辑 ID → 物理 APIC ID | 每 VM |
| `avic_physical_id` | `0xF8` | **物理 APIC ID 表**：APIC ID → backing page 地址 + 所在物理 CPU + 是否在运行 | 每 VM |

`int_ctl` 的 bit31（`AVIC_ENABLE`）打开这个模式。

**vAPIC backing page** 就是 KVM 早已有的 `apic->regs`（3.2 节）。开启 AVIC 后，guest 对 `0xFEE00000` 页的读写被硬件重定向到这一页：大部分读直接从这一页返回，不退出；TPR 的写直接更新这一页并影响硬件的中断判断；EOI 的写对边沿中断由硬件完成；IRR 由硬件在投递时直接置位。KVM 在 `avic_init_backing_page()` 里把它和 KVM 私有的 `APIC_ACCESS_PAGE_PRIVATE_MEMSLOT`（覆盖 `0xFEE00000` 的一个特殊 memslot）配合起来，这就是 3.1 节提到的“启用 AVIC 时 KVM 自己放的 memslot”。

**物理 APIC ID 表**每项 64 位（`svm.h:500` 起的掩码）：

| 位 | 字段 | 含义 |
|---|---|---|
| 7:0 | Host Physical APIC ID | 这个 vCPU 当前运行在哪颗物理 CPU 上（物理 CPU 的 APIC ID） |
| 51:12 | Backing Page Pointer | 这个 vCPU 的 backing page 的 host 物理地址 |
| 62 | IsRunning | 1 = 这个 vCPU 此刻正在物理 CPU 上运行 guest |
| 63 | Valid | 本项有效 |

表按 guest APIC ID 索引，5.15 的 AVIC 最多 255 项（`AVIC_MAX_PHYSICAL_ID_COUNT`），这也是它只支持 xAPIC、不支持 x2APIC 的原因之一。`avic_vcpu_load()` 在 vCPU 被调度到某颗物理 CPU 时更新 Host Physical APIC ID 并置 IsRunning，`avic_vcpu_put()` 在调度走时清 IsRunning。

**逻辑 APIC ID 表**把 flat 或 cluster 模式下的逻辑目标映射到物理 APIC ID，供硬件处理逻辑模式 IPI 时查找。guest 写 LDR 和 DFR 时（这两个寄存器的写会陷出，见下），KVM 维护这张表。

### 8.3 中断怎么投递

**设备中断（来自 KVM 的 IOAPIC 或 MSI）。** 4.3 节的 `__apic_accept_irq()` 调用 `deliver_posted_interrupt`，在 AVIC 活跃时就是 `svm_deliver_avic_intr()`：

```c
int svm_deliver_avic_intr(struct kvm_vcpu *vcpu, int vec)
{
	if (!vcpu->arch.apicv_active)
		return -1;

	kvm_lapic_set_irr(vec, vcpu->arch.apic);
	smp_mb__after_atomic();

	if (avic_vcpu_is_running(vcpu)) {
		int cpuid = vcpu->cpu;

		if (cpuid != get_cpu())
			wrmsrl(SVM_AVIC_DOORBELL, kvm_cpu_get_apicid(cpuid));
		put_cpu();
	} else
		kvm_vcpu_wake_up(vcpu);

	return 0;
}
```

置 backing page 里的 IRR 位，然后：

- 目标正在运行：向它所在的物理 CPU 写 **doorbell** MSR（`0xC001011B`），值是那颗物理 CPU 的 APIC ID。doorbell 是一种特殊的物理 IPI，目标 CPU 收到后**不退出 guest**，而是让硬件重新扫描 backing page 的 IRR，按 PPR 规则直接把中断交给 guest。
- 目标不在运行（在 host 里或在 HLT 中睡眠）：唤醒它。它下次 VMRUN 时，硬件会检查 backing page 的 IRR，自动投递。

对比传统路径：没有 `KVM_REQ_EVENT`，没有 `inject_pending_event()`，没有 `EVENTINJ`，目标 vCPU 如果正在运行，甚至不会退出。

**IPI（guest 写 ICR）。** 硬件直接处理 Fixed 模式、边沿触发的 IPI：按目标（物理或逻辑，查两张表）找到目标 vCPU 的 backing page，置 IRR；目标 IsRunning 就发 doorbell，否则产生 `#VMEXIT(AVIC_INCOMPLETE_IPI)` 让 KVM 去唤醒它。`avic_incomplete_ipi_interception()`（`avic.c:309`）按 `exit_info_2` 里的失败原因分派：

| 原因 | 含义 | KVM 的处理 |
|---|---|---|
| `INVALID_INT_TYPE` | 不是 Fixed + 边沿（比如 INIT、SIPI、NMI） | 用软件路径模拟整个 ICR 写 |
| `TARGET_NOT_RUNNING` | 目标 vCPU 不在运行，硬件已经置了 IRR | `avic_kick_target_vcpus()`，唤醒目标 |
| `INVALID_TARGET` | 目标 ID 在表里无效 | 打警告 |
| `INVALID_BACKING_PAGE` | backing page 指针无效 | 打警告 |

所以 INIT-SIPI-SIPI 这类 IPI 在 AVIC 下仍然走 KVM 软件路径，这对 SMP 启动的正确性没有影响。

**其他 LAPIC 访问。** 硬件无法完成的访问会产生 `#VMEXIT(AVIC_NOACCEL)`，分两类（`is_avic_unaccelerated_access_trap()`，`avic.c:505`）：

- **trap 类**：写已经完成（值已写入 backing page），退出只是通知 KVM 处理副作用。包括 ID、EOI（电平中断时）、LDR、DFR、SVR、ESR、ICR（软件路径的 IPI）、所有 LVT、TMICT、TDCR。KVM 的 `avic_unaccel_trap_write()` 读出 backing page 里的新值，调用 `kvm_lapic_reg_write()` 走一遍常规逻辑。
- **fault 类**：访问没有完成（比如读 TMCCT，当前计数必须由软件计算），KVM 用指令模拟器完成它。

### 8.4 EOI：AVIC 的“盲区”

AVIC 下，**边沿中断的 EOI 由硬件完成，不退出**；只有 TMR 对应位为 1（电平中断）的 EOI 才以 trap 的形式退出。SVM 没有 Intel 那样的“EOI exit bitmap”可以指定哪些向量的 EOI 必须退出，`svm_load_eoi_exitmap()` 是空函数（`avic.c:664`）。

这对 KVM 的几个依赖“边沿中断 EOI 通知”的机制造成了影响，源码里能看到三处应对：

1. **PIT 补发模式**依赖边沿 EOI 触发 ack notifier，于是在补发模式下抑制 AVIC（7.3 节）。
2. **RTC 的 coalesced 跟踪**依赖 EOI 递减 `pending_eoi`，于是在 `ioapic_set_irq()` 里做“懒更新”：下一次拉线时检查每个目标 LAPIC 的 ISR 里是否还挂着这个向量（`ioapic_lazy_update_eoi()`，2.5 节代码的开头部分）。
3. **ExtINT**（8259A 的中断）不能通过 backing page 投递，因为它的向量要在 INTA 周期里向 PIC 要。需要注入 ExtINT 时，`svm_enable_irq_window()` 以 `APICV_INHIBIT_REASON_IRQWIN` 临时关闭 AVIC，走传统的 `V_IRQ` 中断窗口；窗口打开后 `interrupt_window_interception()` 再恢复 AVIC（5.1 节贴的代码里能看到这两处 `kvm_request_apicv_update()`）。

### 8.5 抑制条件与 mini-vmm 的现状

AVIC 是“按 VM 整体开关”的，KVM 用一个位图 `kvm->arch.apicv_inhibit_reasons` 记录所有要求关闭它的理由，只要有一位为 1，AVIC 就不活跃。5.15 的 SVM 支持的理由（`svm_check_apicv_inhibit_reasons()`，`avic.c:900`）：

| 理由 | 何时设置 |
|---|---|
| `DISABLE` | 模块参数 `avic` 为假（`kvm_amd` 在 5.15 中默认 `avic = false`）或硬件不支持 |
| `HYPERV` | guest 启用了 Hyper-V 的某些 enlightenment |
| `NESTED` | `nested = 1` 且 guest CPUID 里有 SVM 位 |
| `IRQWIN` | 需要为 ExtINT 打开中断窗口，临时设置 |
| `PIT_REINJ` | 内核 PIT 处于补发模式 |
| `X2APIC` | guest CPUID 里有 x2APIC 位（5.15 的 AVIC 不支持 x2APIC，x2AVIC 在更新的内核和 Zen 4 硬件上才出现） |

对照 mini-vmm 当前的配置：

- host 上 `kvm_amd` 的 `avic` 参数为 N（blog 第四章讲过，CPU 支持 AVIC，但模块参数没有打开），`DISABLE` 成立。
- 创建了内核 PIT 且没有关闭补发，`PIT_REINJ` 成立。
- 透传的 CPUID 里有 `x2apic`，`X2APIC` 成立。
- 透传的 CPUID 里有 `svm`（blog 第十五章 `/proc/cpuinfo` 的 flags 里能看到），如果 host 开了嵌套虚拟化，`NESTED` 也成立。

也就是说，即使只把 `avic` 参数打开，AVIC 在 mini-vmm 的 VM 上也不会生效。想要真正用上 AVIC，VMM 至少需要：用 `KVM_REINJECT_CONTROL` 关闭 PIT 补发（不能简单地不创建内核 PIT，Linux 的 TSC 校准依赖它，见 blog 第五章）；在 CPUID 里清掉 x2APIC 位；在 CPUID 里清掉 SVM 位。这是下一阶段做性能优化时的一个现成课题。读 `/sys/module/kvm_amd/parameters/avic` 可以确认模块参数，`trace-cmd record -e kvm:kvm_apicv_update_request` 可以看到每一次抑制理由的设置与清除。

### 8.6 与 Intel APICv 的对照

| | AMD AVIC（5.15 时代） | Intel APICv |
|---|---|---|
| 虚拟 LAPIC 页 | vAPIC backing page | virtual-APIC page |
| 设备中断投递 | 置 IRR + doorbell MSR | Posted Interrupt：置 PIR（posted interrupt request）+ 发 notification vector IPI |
| 目标不在运行 | 硬件无法投递，KVM 唤醒 | 同左，PIR 在下次进入时同步到 vIRR |
| guest 发 IPI | 硬件完成 Fixed/边沿；目标不在运行时退出 | 2022 年后的 IPI virtualization（Sapphire Rapids）才硬件完成，之前 ICR 写总是退出 |
| EOI | 边沿不退出、电平 trap；无 EOI exit bitmap | 可按向量配置 EOI exit bitmap |
| x2APIC | 不支持（x2AVIC 另说） | 支持 |
| 设备直通 | 与 AMD IOMMU 的 GA 模式配合，设备中断直接写 backing page | 与 VT-d posted interrupt 配合 |

KVM 在通用代码里用“apicv”这个名字统称两者，`vcpu->arch.apicv_active`、`kvm_request_apicv_update()`、`APICV_INHIBIT_REASON_*` 都是厂商无关的抽象。读 `lapic.c` 时看到 `apicv_active` 的分支，在 AMD 平台上指的就是 AVIC。

## 9. 观测与排障

### 9.1 中断相关的 tracepoint

全部在 `kvm` 子系统下，通用部分定义在 `include/trace/events/kvm.h`，x86 部分定义在 `arch/x86/kvm/trace.h`。按链路顺序排列：

| tracepoint | 触发位置 | 关键字段 | 回答的问题 |
|---|---|---|---|
| `kvm_set_irq` | `kvm_set_irq()` | gsi、level、irq_source_id | VMM 或内核设备有没有拉线 |
| `kvm_msi_set_irq` | `kvm_set_msi_irq()` | address、data | MSI 路由有没有被触发 |
| `kvm_pic_set_irq` | `kvm_pic_set_irq()` | chip、pin、elcr、imr、coalesced | 8259A 这一路是否被屏蔽或合并 |
| `kvm_ioapic_set_irq` | `ioapic_set_irq()` | 表项内容（解码为向量、模式、目标）、pin、coalesced | IOAPIC 表项是怎么配置的，是否合并 |
| `kvm_ioapic_delayed_eoi_inj` | `kvm_ioapic_update_eoi_one()` | 表项内容 | 是否发生了电平中断风暴 |
| `kvm_apic_ipi` | `kvm_apic_send_ipi()` | icr_low、dest_id | guest 发了什么 IPI |
| `kvm_apic_accept_irq` | `__apic_accept_irq()` | apicid、dm、tm、vec | 哪个 vCPU 的 LAPIC 接受了哪个向量 |
| `kvm_inj_virq` | `svm_set_irq()` | irq（向量） | 向量是否真的写进了 `EVENTINJ` |
| `kvm_eoi` | `apic_set_eoi()` | apicid、vector | guest 有没有 EOI |
| `kvm_ack_irq` | `kvm_notify_acked_irq()` | irqchip、pin | ack notifier 有没有被调用（PIT 补发） |
| `kvm_apic` | `kvm_lapic_reg_read/write()` | rw、reg、val | guest 对 LAPIC 寄存器的每一次访问 |
| `kvm_apicv_update_request` | `kvm_request_apicv_update()` | activate、bit | AVIC 为什么被开关 |
| `kvm_vcpu_wakeup` | `kvm_vcpu_block()` 结尾 | ns、waited、valid | vCPU 在 HLT 里睡了多久，是轮询命中还是真的睡了 |
| `kvm_halt_poll_ns` | halt polling 自适应 | vcpu、new、old | 轮询时长的调整 |

`kvm_apic` 在 xAPIC 模式的 guest 上非常“吵”（每次 EOI、每次 TMICT 写都有一条），但它是确认“guest 到底有没有写 EOI、写 ICR 时写了什么”的最直接证据。blog 第十六章 16.6 节用其中六个把一次按键串了起来，这里的表可以作为它的完整版。

**用法示例：确认一个中断“卡”在哪一层。** 假设 guest 里某设备没有中断计数：

```
kvm_set_irq 没有      → VMM 设备模拟没有拉线（或者拉线用错了 GSI）
kvm_set_irq 有，kvm_ioapic_set_irq 显示 coalesced=1
                      → 边沿中断没有先拉低；或者电平中断的 remote IRR 没清
kvm_ioapic_set_irq 有，表项 masked
                      → guest 没有启用这个中断（驱动没加载、探测失败）
kvm_apic_accept_irq 没有
                      → 目标不匹配：表项目标字段与各 LAPIC 的 ID/LDR 对不上
kvm_apic_accept_irq 有，kvm_inj_virq 没有
                      → guest 一直关中断，或者 PPR 挡住了（ISR 里有更高优先级的中断没 EOI）
kvm_inj_virq 有       → 问题在 guest 的中断处理本身
```

### 9.2 读取芯片状态

`kvm_vcpu_block()` 睡着的 vCPU 不会产生 trace，这时需要直接读状态。KVM 提供：

- **`KVM_GET_IRQCHIP`**（VM ioctl）：`chip_id` 为 `KVM_IRQCHIP_PIC_MASTER`（0）、`KVM_IRQCHIP_PIC_SLAVE`（1）、`KVM_IRQCHIP_IOAPIC`（2）。IOAPIC 返回 `struct kvm_ioapic_state`，包括 `irr` 和全部 24 个重定向表项，可以直接按 2.2 节的位定义解码。PIC 返回 `struct kvm_pic_state`，字段与 1.6 节的 `kvm_kpic_state` 对应。
- **`KVM_GET_LAPIC`**（vCPU ioctl）：`struct kvm_lapic_state` 是 LAPIC 寄存器页的前 `0x400` 字节。IRR 在 `0x200`，ISR 在 `0x100`，TMR 在 `0x180`，TPR 在 `0x080`。
- **`KVM_GET_VCPU_EVENTS`**（vCPU ioctl）：`interrupt.injected`、`interrupt.nr`、`nmi.pending`、`exception` 等，对应 5.3 节“注入了一半”的状态。

一个实用的调试手段是在 VMM 的“Ctrl-A x 退出”或卡死诊断里加上这些 dump。以 LAPIC 为例，判断“有没有中断被卡住”只需要三个值：IRR 的最高位、ISR 的最高位、TPR。如果 IRR 的最高位所在的类不大于 max(TPR 类, ISR 最高位的类)，说明它被挡住了；再看 ISR 里那个“挡路”的向量是谁，通常就是漏了 EOI 的那个中断。

### 9.3 症状与原因

| 症状 | 首先怀疑 | 依据 |
|---|---|---|
| 设备的第一个中断正常，之后再也没有 | 边沿中断没有拉低就再次拉高 | 1.6、2.5 节：连续 `level = 1` 被判为合并 |
| 某个中断之后，所有同类或更低类的中断都不来了 | guest 或 VMM 模拟的设备导致漏 EOI | 3.4 节：ISR 挡住 PPR |
| 中断风暴，guest 卡在某个处理程序里，trace 有 `kvm_ioapic_delayed_eoi_inj` | 电平中断的设备在条件清除后没有拉低线 | 2.6、6.4 节 |
| `KVM_IRQ_LINE` 返回 `ENXIO` | 没有创建 irqchip，或在 split 模式下路由表里没有这个 GSI | 4.2 节 |
| `KVM_CREATE_IRQCHIP` 返回 `EINVAL` | 已经创建过 vCPU | blog 第十章 |
| guest 访问 IOAPIC 或 LAPIC 没有效果 | memslot 覆盖了 `0xFEC00000` 或 `0xFEE00000` | 2.1、3.1 节 |
| guest 时钟中断配置在 pin 2，但 PIT 在拉 pin 0 | 固件表写了 IRQ0 → GSI2 的覆盖，但保留了 KVM 默认路由 | 2.7 节 |
| 两个设备共用一条 GSI，其中一个的中断丢失 | 用户态中断源在 KVM 里只有一个 `irq_source_id`，后拉低的覆盖了先拉高的 | 1.6 节 |
| `cli; hlt` 的 vCPU 无法被外部中断唤醒 | 这是正确行为 | 5.4 节 |
| 打开了 `kvm_amd avic=1`，但性能没有变化 | AVIC 被其他理由抑制 | 8.5 节 |

### 9.4 VMM 侧的中断清单

把本卷散落在各节的“VMM 必须做到”汇总成一张表，与 blog 第十四章的全局清单互为补充：

| 项目 | 必须是什么 | 出处 |
|---|---|---|
| irqchip 创建时机 | `KVM_CREATE_IRQCHIP` 在任何 `KVM_CREATE_VCPU` 之前 | blog 第十章 |
| IOAPIC 基址 | 固件表写 `0xFEC00000`，与 KVM 固定值一致 | 2.1 节 |
| LAPIC 基址 | 固件表写 `0xFEE00000`，KVM 不支持重定位 | 3.1 节 |
| memslot 布局 | 不覆盖 `0xFEC00000` 和 `0xFEE00000` 所在的页 | 2.1、3.1 节 |
| GSI 映射 | 固件表的 ISA 中断映射与 KVM 路由表一致（同为恒等，或同为 IRQ0 → pin 2） | 2.7 节 |
| `KVM_SET_GSI_ROUTING` | 若使用，必须提交完整的表（整表替换） | 2.7 节 |
| 边沿设备 | 维护线的当前电平；中断条件消失时拉低，再次成立时拉高 | 1.6、2.5 节 |
| 电平设备 | 中断条件被 guest 清除后立即拉低 | 2.6、6.4 节 |
| 共享 GSI | 在用户态做线或，再调用 `KVM_IRQ_LINE` | 1.6 节 |
| `level` 语义 | 1 = 有效，与 guest 配置的极性无关 | 2.2 节 |
| 需要合并信息时 | 用 `KVM_IRQ_LINE_STATUS` 而不是 `KVM_IRQ_LINE` | 4.2 节 |
| 快照、迁移 | 保存 `KVM_GET_IRQCHIP`（3 个芯片）、每个 vCPU 的 `KVM_GET_LAPIC` 和 `KVM_GET_VCPU_EVENTS` | 5.3、9.2 节 |
| 停止 vCPU | 信号 + `immediate_exit`，因为 HLT 中的 vCPU 睡在 KVM 里 | 4.4、5.4 节 |

## 10. 本卷小结与卷五预告

**三代控制器。** 8259A 用 IRR/ISR/IMR 三个 8 位寄存器和一个隐式的初始化状态机管理 15 条线，向量号在 INTA 周期里由芯片提供，这使它的中断在 LAPIC 看来是“外部中断”（ExtINT）。IOAPIC 把引脚翻译成带目标的中断消息，本质上是一个 MSI 生成器；它的电平触发语义靠 remote IRR 和 EOI 广播实现，KVM 模拟的 82093AA（版本 `0x11`）没有 EOI 寄存器，Linux 用“临时切换到边沿”的技巧清 remote IRR，KVM 专门模拟了这个未写入规范的行为。LAPIC 用 256 位的 IRR/ISR/TMR 和 TPR/PPR 的优先级类机制决定何时把中断交给 CPU，用 ICR 发送 IPI；在 mini-vmm 的 guest 里，它因为缺少 paravirt 钩子而运行在 xAPIC 模式，每次访问都是 MMIO 退出，并且因为只有 4 颗 CPU 而使用 logical flat 寻址。

**KVM 的复刻。** KVM 用 `kvm_kpic_state`、`kvm_ioapic`、`kvm_lapic` 三个结构逐寄存器复刻了三颗芯片，用每条线一个的中断源位图实现线或，用 `last_irr` 和 `irr` 的比较实现边沿检测。三种中断来源（IOAPIC 表项、MSI、ICR）被统一成 `struct kvm_lapic_irq`，汇入同一个 `kvm_irq_delivery_to_apic()` 和 `__apic_accept_irq()`。

**正向链路。** `KVM_IRQ_LINE` → 路由表 → 芯片 → `__apic_accept_irq()` 置 IRR、发 `KVM_REQ_EVENT`、kick → 目标 vCPU 在 `vcpu_enter_guest()` 里经 `inject_pending_event()` 做软件 INTA（IRR 移到 ISR）→ `svm_set_irq()` 写 `EVENTINJ` → VMRUN 时硬件交付。kick 与 `vcpu->mode` 的无锁协议保证请求不会在“检查之后、进入之前”丢失。

**边角。** guest 关中断时用 `V_IRQ` + `VINTR` 拦截做闹钟，等 guest 开中断时退出再注入；`EVENTINJ` 只有一个槽位，多个事件依次注入；交付被打断时事件落在格式相同的 `EXITINTINFO` 里，原样重新注入且不再触碰 LAPIC 簿记；HLT 让 vCPU 睡在 `kvm_vcpu_block()` 里，先轮询 200 µs 再睡眠，只有 `IF = 1` 时的中断、NMI/INIT、信号能唤醒它。

**反向链路。** guest 写 EOI → MMIO 退出 → `apic_set_eoi()` 清 ISR 最高位、降 PPR → 只有在 `ioapic_handled_vectors` 里的向量才通知 IOAPIC → ack notifier（PIT 补发）→ 电平中断清 remote IRR 并按需重投，连续 10000 次重投触发风暴缓解。

**AVIC。** backing page、物理与逻辑 APIC ID 表、doorbell 让设备中断和 Fixed IPI 可以不经 KVM 直接交付，边沿中断的 EOI 也不再退出。代价是 KVM 失去了边沿 EOI 的可见性，于是 PIT 补发、ExtINT、x2APIC、嵌套虚拟化都会抑制它。mini-vmm 当前的配置同时触发了多个抑制理由，这是一个现成的优化课题。

**下一卷的问题在固件侧。** 本卷反复出现“固件表必须与 KVM 一致”：IOAPIC 的地址和 ID、LAPIC 的地址、ISA 中断到 GSI 的映射、LINT1 接 NMI。这些信息是通过 MADT 或 MP table 告诉 guest 的，而 guest 在找到它们之前，还要先通过 boot_params 和 E820 知道内存布局、通过 RSDP 找到 ACPI 表。卷五将按偏移逐字段拆解这些结构：E820 的类型、boot_params 与 setup header、MP table 的全部条目、ACPI RSDP/XSDT/FADT/MADT/DSDT，以及 Linux 在启动的哪个阶段、由哪个函数解析它们。
