## 一、多核虚拟化（SMP）

### 1.1 SMP 复习：一样的 CPU，不一样的角色

**SMP（Symmetric Multi-Processing，对称多处理）** 的“对称”指的是：所有 CPU 地位平等，共享同一份物理内存，都能执行内核代码，都能处理中断。操作系统课讲过的自旋锁、内存屏障、per-CPU 变量、负载均衡，都是为 SMP 服务的。

但在**启动**这个阶段，x86 上的 CPU 并不对称。上电时硬件从所有 CPU 中选出一颗作为 **BSP（Bootstrap Processor，引导处理器）**，它从复位向量开始执行固件代码、加载操作系统；其余的 CPU 叫 **AP（Application Processor，应用处理器）**，上电后什么都不执行，停在一个特殊的等待状态里，直到 BSP 把它们叫醒。哪颗是 BSP，记录在它的 `IA32_APIC_BASE` MSR 第 8 位上。

所以“多核启动”在 x86 上是一个**接力**的过程：BSP 独自完成大部分初始化，然后逐个唤醒 AP，每个 AP 醒来后自己完成一小段初始化，报告“我上线了”，加入调度。

每颗 CPU 靠 **APIC ID** 来标识，这是 IPI 的“收件地址”。《中断·原理篇》第三章说过，APIC ID 可以通过 LAPIC 的 ID 寄存器、CPUID 指令、固件表三条途径获得，真实硬件上三者天然一致。

### 1.2 真实 x86 上 AP 是怎么醒来的

#### 1.2.1 INIT-SIPI-SIPI

Intel 在 MP 规范里定义了唤醒 AP 的标准协议，它完全依靠《中断·原理篇》第三章讲过的 LAPIC 的 ICR（中断命令寄存器）来实现。BSP 对每一个 AP 执行：

```
   BSP                                                     AP（APIC ID = n）
    │                                                       │  上电后处于
    │                                                       │  wait-for-SIPI 状态
    │  写 ICR：目的 = n，投递模式 = INIT                       │
    │ ─────────────────────── INIT IPI ───────────────────► │  复位：寄存器回到
    │                                                       │  上电初值，继续等待
    │  等待（规范要求 10ms，现代 Linux 在新 CPU 上缩短）         │
    │                                                       │
    │  写 ICR：目的 = n，投递模式 = Start-up，向量 = VV         │
    │ ─────────────────────── SIPI ───────────────────────► │  从实模式地址
    │                                                       │  VV00:0000 开始执行
    │  等待 200µs，再发一次 SIPI（为兼容老硬件）                 │  即物理地址 0xVV000
    │ ─────────────────────── SIPI ───────────────────────► │  （已在运行则忽略）
    │                                                       ▼
    │  等待 AP 报告“我已上线”                               执行 trampoline 代码
```

**INIT IPI** 让目标 CPU 复位到一个干净的状态。**SIPI（Startup IPI）** 是一种特殊的 IPI，它的 8 位“向量号”不是用来查 IDT 的，而是一个**页号**：AP 收到 SIPI 后，以实模式从 `CS = VV << 8`、`IP = 0` 开始执行，也就是物理地址 `VV × 0x1000`。8 位的页号意味着这个地址只能在 1MB 以下，并且必须 4KB 对齐。

这就是《固件与启动协议·原理篇》第一章说“低端 640KB 必须报告成 RAM”的原因：AP 的第一条指令必须位于 1MB 以下的某个页面上，Linux 需要在那里放一段代码。

发两次 SIPI 是历史遗留：早期的某些 CPU 可能错过第一个 SIPI。现代 Linux 仍然按规范发两次，AP 如果已经在第一次 SIPI 后开始运行，会忽略第二次。

#### 1.2.2 Linux 的 trampoline：从实模式一路爬到长模式

AP 醒来时处于实模式，16 位、没有分页，和 1981 年的 8086 一样。而内核是运行在 64 位长模式、高端虚拟地址上的。所以 Linux 在低端内存里放了一段叫 **trampoline（蹦床）** 的代码（`arch/x86/realmode/rm/trampoline_64.S`），它的作用就是带着 AP 走完 BSP 在启动时走过的那条路：

```
   实模式（16 位）      ← SIPI 把 AP 放在这里，CS:IP = VV00:0000
        │  加载临时 GDT，置 CR0.PE
        ▼
   保护模式（32 位）
        │  加载临时页表（trampoline_pgd），置 CR4.PAE、EFER.LME、CR0.PG
        ▼
   长模式（64 位）
        │  跳到内核的 secondary_startup_64
        ▼
   内核代码：切到内核页表，查出自己是几号 CPU，设置 per-CPU 数据和栈
        │
        ▼
   start_secondary()：初始化本 CPU 的 LAPIC、定时器，报告上线，进入 idle 循环
```

这里有一个对 VMM 来说至关重要的细节。Linux 6.6 默认启用了**并行 AP 启动**：BSP 几乎同时唤醒所有 AP，所有 AP 并行地走 trampoline，而不是一个接一个。并行启动时，AP 在进入内核之后怎么知道自己是“几号 CPU”？看 `arch/x86/kernel/head_64.S`：

```asm
.Lread_apicid_mmio:
    /* Read the APIC ID from the fix-mapped MMIO space. */
    movq    apic_mmio_base(%rip), %rcx
    addq    $APIC_ID, %rcx
    movl    (%rcx), %eax
    shr     $24, %eax              /* EAX = 本 CPU 的 LAPIC ID */
    ...
.Llookup_AP:
    /* EAX contains the APIC ID of the current CPU */
    xorq    %rcx, %rcx
    leaq    cpuid_to_apicid(%rip), %rbx

.Lfind_cpunr:
    cmpl    (%rbx,%rcx,4), %eax    /* 在 cpuid_to_apicid[] 表里找 */
    jz      .Lsetup_cpu
    inc     %ecx
    cmpl    nr_cpu_ids(%rip), %ecx
    jb      .Lfind_cpunr

    /*  APIC ID not found in the table. Drop the trampoline lock and bail. */
    ...
1:  cli
    hlt
    jmp     1b
```

AP 读自己 LAPIC 的 ID 寄存器，拿着这个 ID 去 `cpuid_to_apicid[]` 表里查找自己的逻辑 CPU 编号。而 `cpuid_to_apicid[]` 是 BSP 早先根据**固件表（MADT 或 MP table）** 里的 APIC ID 填出来的。如果 LAPIC 报告的 ID 在固件表里找不到，AP 就关中断、`hlt`，永远停在那里。BSP 那边等不到这个 AP 上线，最终超时，日志里出现 `failed to report alive state` 之类的错误。

这就是这一组文章反复强调的“三方一致”在硬件层面的体现。下面讲到虚拟化时还会遇到另外两方。

真实日志里 AP 启动的过程只有几行，从开始唤醒到 4 颗 CPU 全部上线大约 5 毫秒：

```
[    0.457657] smp: Bringing up secondary CPUs ...
[    0.459283] smpboot: x86: Booting SMP configuration:
[    0.460087] .... node  #0, CPUs:      #1 #2 #3
[    0.464195] smp: Brought up 1 node, 4 CPUs
```

### 1.3 虚拟化后：vCPU 就是一个线程

《一次 out 指令的完整旅程》讲过 KVM 的文件描述符层级：每个 vCPU 是一个 fd，VMM 为每个 vCPU 创建一个线程，线程在自己的 fd 上反复调用 `KVM_RUN`。现在把这个模型放到多核的场景下看：

```
   Guest 视角                        Host 视角
  ┌─────────────────────────┐      ┌──────────────────────────────────────────┐
  │  CPU 0  CPU 1  CPU 2  CPU 3│    │ VMM 进程                                   │
  │   │      │      │      │   │    │  ├─ 主线程（初始化后等待 join）              │
  │   ▼      ▼      ▼      ▼   │    │  ├─ vcpu0 线程 ── ioctl(fd0, KVM_RUN) 循环  │
  │  共享的“物理内存”           │    │  ├─ vcpu1 线程 ── ioctl(fd1, KVM_RUN) 循环   │
  │                           │    │  ├─ vcpu2 线程 ── ioctl(fd2, KVM_RUN) 循环   │
  └─────────────────────────┘      │  ├─ vcpu3 线程 ── ioctl(fd3, KVM_RUN) 循环   │
                                    │  └─ console 线程（读 stdin 喂给串口）         │
                                    │                                            │
                                    │ 同一块 mmap 出来的匿名内存 = guest 物理内存  │
                                    └──────────────────────────────────────────┘
                                                      │
                                           host 调度器决定每个线程
                                           此刻在哪颗物理 CPU 上跑
```

这个模型有几个直接的推论：

**guest 的“并行”就是 host 线程的并行。** 4 个 vCPU 线程可以被 host 调度到 4 颗不同的物理核上同时运行，guest 获得真正的并行。在 host 上用 `top -H` 能看到 `vcpu0` 到 `vcpu3` 四个线程，guest 满载时每个都接近 100% CPU。

**guest 的内存一致性由硬件保证。** vCPU 在 guest 模式下原生执行指令，guest 的内存访问就是真实的内存访问，x86 的 TSO 内存模型、缓存一致性协议、`lock` 前缀的原子操作全部原样生效。guest 内核的自旋锁、RCU、内存屏障不需要 hypervisor 做任何事情就能正确工作。

**guest 的“CPU”可能被抢走。** 这是虚拟化特有的问题。host 调度器可以在任何时刻把一个 vCPU 线程换下去，而 guest 对此一无所知。如果被换下去的 vCPU 恰好持有一把自旋锁，其他 vCPU 就会空转等待一个“不在运行”的锁持有者，这叫**锁持有者抢占（lock-holder preemption）**。硬件为此提供了 **PAUSE 拦截**：自旋等待循环里通常有 `pause` 指令，硬件检测到一个 vCPU 在短时间内执行了大量 `pause`，就产生一次陷出（我们 host 的特性列表里的 `pausefilter` 就是这个功能），KVM 借机让出物理 CPU 给其他 vCPU，希望锁持有者能被调度上来。

**vCPU 数量可以超过物理 CPU 数量（超卖）**，代价是上面这类问题更严重。生产环境里对延迟敏感的虚拟机通常会把 vCPU 线程**绑定（pin）** 到固定的物理核上，避免它们被随意迁移和抢占。

### 1.4 KVM 如何模拟 INIT/SIPI

真实 AP 在收到 SIPI 之前处于 wait-for-SIPI 状态，什么都不执行。虚拟机里，这个状态由 KVM 为每个 vCPU 维护的 **`mp_state`** 字段表达：

| `mp_state` | 含义 |
|---|---|
| `KVM_MP_STATE_RUNNABLE` | 可以运行 |
| `KVM_MP_STATE_UNINITIALIZED` | 刚创建的 AP，等待 INIT |
| `KVM_MP_STATE_INIT_RECEIVED` | 收到了 INIT，等待 SIPI |
| `KVM_MP_STATE_HALTED` | 执行了 HLT，等待中断 |

vCPU 创建时的初始状态在 `kvm_arch_vcpu_create()` 里决定：

```c
    if (!irqchip_in_kernel(vcpu->kvm) || kvm_vcpu_is_reset_bsp(vcpu))
        vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
    else
        vcpu->arch.mp_state = KVM_MP_STATE_UNINITIALIZED;
```

有内核态 irqchip 时，BSP（默认是 0 号 vCPU）创建出来就是 RUNNABLE，其他 vCPU 是 UNINITIALIZED。**没有内核态 irqchip 时，所有 vCPU 一创建就是 RUNNABLE**，因为此时 KVM 没有 LAPIC，也就没法接收 INIT/SIPI，只能让用户态自己决定每个 vCPU 从哪里开始跑。这就是为什么 mini-vmm 规定多核只能配合 Linux 启动模式：《一次 out 指令的完整旅程》的裸机模式没有创建 irqchip，4 个 vCPU 会同时从同一个入口地址开跑，而那段 payload 根本不知道有多个 CPU。

一次完整的虚拟 AP 唤醒流程：

```
  AP 线程                                  BSP（guest 里）
  ioctl(KVM_RUN)
  │ mp_state == UNINITIALIZED
  │ → kvm_vcpu_block()：在内核里睡眠          │
  │   （不占 CPU）                           │ guest 写 LAPIC 的 ICR（INIT）
  │                                         │ → #VMEXIT → KVM 模拟 ICR 写入
  │                                         │ → kvm_apic_send_ipi()
  │                                         │ → 目标 LAPIC 的 __apic_accept_irq()
  │                                         │     pending_events |= INIT
  │ ◄───────── kvm_vcpu_kick() 唤醒 ─────────│     kvm_vcpu_kick()
  │ kvm_apic_accept_events()：               │
  │   INIT → 复位 vCPU，mp_state = INIT_RECEIVED
  │ 返回 -EAGAIN 给用户态                     │
  │                                         │
  ioctl(KVM_RUN)（用户态看到 EAGAIN 后重进）   │ guest 写 ICR（SIPI，向量 VV）
  │ ...                                     │ → pending_events |= SIPI，sipi_vector = VV
  │ kvm_apic_accept_events()：               │
  │   SIPI → kvm_vcpu_deliver_sipi_vector()  │
  │          CS.selector = VV << 8           │
  │          CS.base     = VV << 12          │
  │          RIP         = 0                 │
  │          mp_state = RUNNABLE             │
  ▼                                         │
  VMRUN → AP 在 guest 里从 0xVV000 开始执行 trampoline
```

`kvm_vcpu_deliver_sipi_vector()` 的实现只有几行，和硬件规范一一对应：

```c
void kvm_vcpu_deliver_sipi_vector(struct kvm_vcpu *vcpu, u8 vector)
{
    struct kvm_segment cs;

    kvm_get_segment(vcpu, &cs, VCPU_SREG_CS);
    cs.selector = vector << 8;
    cs.base = vector << 12;
    kvm_set_segment(vcpu, &cs, VCPU_SREG_CS);
    kvm_rip_write(vcpu, 0);
}
```

流程图中间有一个用户态必须注意的细节：**AP 的线程在等待 INIT/SIPI 时，`KVM_RUN` 会以 `-EAGAIN` 返回**，而不是进入 guest。看 5.15 的 `kvm_arch_vcpu_ioctl_run()`：

```c
    if (unlikely(vcpu->arch.mp_state == KVM_MP_STATE_UNINITIALIZED)) {
        if (kvm_run->immediate_exit) {
            r = -EINTR;
            goto out;
        }
        kvm_vcpu_block(vcpu);                   /* 睡到有事件 */
        if (kvm_apic_accept_events(vcpu) < 0) {
            r = 0;
            goto out;
        }
        kvm_clear_request(KVM_REQ_UNHALT, vcpu);
        r = -EAGAIN;                            /* 醒了，但不进 guest */
        if (signal_pending(current)) {
            r = -EINTR;
            kvm_run->exit_reason = KVM_EXIT_INTR;
            ++vcpu->stat.signal_exits;
        }
        goto out;
    }
```

`-EAGAIN` 的意思是“状态变了，请再调用一次”。用户态如果把它当成错误，AP 一醒来整台虚拟机就退出了。正确的处理是把它和 `-EINTR` 一样看待：不是错误，重新进入 `KVM_RUN` 即可。

从这张流程图还能看出一件事：**VMM 在整个 AP 唤醒过程中什么都不用做**。它只需要为每个 vCPU 创建一个线程，让它们都进入 `KVM_RUN`。AP 线程在 KVM 里安静地睡着，不占 CPU，直到 guest 里的 BSP 通过虚拟 LAPIC 把它叫醒。VMM 的全部职责是：线程、CPUID、固件表。

### 1.5 IPI 的代价

AP 全部上线后，多核 guest 的 CPU 之间会频繁地互发 IPI：

- **重调度 IPI**：CPU 0 唤醒了一个应该在 CPU 2 上运行的线程，要通知 CPU 2 “该调度了”。
- **函数调用 IPI**：让另一颗 CPU 执行某个函数，比如修改内核代码后让所有 CPU 同步指令缓存。
- **TLB shootdown**：一颗 CPU 修改了页表，要让其他正在使用这张页表的 CPU 刷掉 TLB 中的旧条目。

真实日志里 `/proc/interrupts` 的最后几行就是这些 IPI 的计数：

```
           CPU0       CPU1       CPU2       CPU3
LOC:        344        114        179        120   Local timer interrupts
RES:          0         16         15         12   Rescheduling interrupts
CAL:        173         71        139         39   Function call interrupts
TLB:          0          0          1          0   TLB shootdowns
```

在虚拟机里，一次 IPI 的成本比裸机高得多：发送方写 ICR 导致一次 `#VMEXIT`，KVM 模拟 ICR、找到目标 vCPU、置请求位、踢它；如果目标 vCPU 正在 guest 里运行，还要给它所在的物理 CPU 发一个真实的 IPI，导致目标也 `#VMEXIT` 一次，然后注入中断。一次 guest IPI 至少对应两次世界切换。这是 AVIC/APICv 这类硬件加速最能发挥作用的地方：发送方写 ICR 时硬件直接把中断投递到目标 vCPU 的虚拟 APIC 页，目标在运行时无需陷出。

### 1.6 CPU 拓扑：guest 要知道 CPU 之间的“远近”

guest 知道了有 4 颗 CPU 之后，还想知道它们之间的关系：哪些是同一个物理核上的超线程？哪些共享 L2 缓存、哪些共享 L3？在不在同一个 socket、同一个 NUMA 节点上？这些信息叫 **CPU 拓扑**，Linux 的调度器用它来构建**调度域（scheduling domain）**：同核的超线程之间迁移任务几乎没有代价，同 L3 的核之间代价小，跨 socket 的代价大。

guest 从哪里得知拓扑？主要是 **CPUID 指令**。与拓扑相关的 CPUID leaf 有好几个，而且 Intel 和 AMD 各有一套：

| Leaf | 厂商 | 内容 |
|---|---|---|
| `0x1` | 通用 | EBX[31:24] 本 CPU 的初始 APIC ID；EBX[23:16] 本 package 的逻辑处理器数；EDX 第 28 位 HTT 表示后者有效 |
| `0x4` | Intel | 每级缓存的参数与共享情况 |
| `0xB` / `0x1F` | Intel（AMD 新型号也支持） | 扩展拓扑枚举：按层级（SMT、Core、Die……）给出每层的 APIC ID 位宽 |
| `0x80000008` | AMD | ECX[7:0] 核数减一，ECX[15:12] APIC ID 中核编号所占的位数 |
| `0x8000001D` | AMD | 每级缓存的参数，EAX[25:14] 表示共享这级缓存的逻辑处理器数减一 |
| `0x8000001E` | AMD | EAX 扩展 APIC ID，EBX[7:0] 核 ID、EBX[15:8] 每核线程数减一，ECX[7:0] 节点 ID |

问题在于：VMM 给 guest 设置 CPUID 的常规做法是调用 `KVM_GET_SUPPORTED_CPUID` 拿到“host 支持、KVM 允许的全部 CPUID 信息”，然后用 `KVM_SET_CPUID2` 设给每个 vCPU。而 `KVM_GET_SUPPORTED_CPUID` 返回的拓扑字段是**host 的原始值**。比如 leaf 1 的 EBX[31:24]，是执行这个 ioctl 时所在的那颗**物理** CPU 的 APIC ID；leaf `0x80000008` 里的核数，是物理 CPU 的核数。

如果原样设给所有 vCPU，guest 会看到：4 颗 CPU 的初始 APIC ID 全都一样（比如都是 17），而每颗 CPU 都声称自己所在的 package 里有 32 个核。Linux 会被搞糊涂：日志里出现 APIC ID 不匹配的警告，拓扑被算错，调度域建得乱七八糟。

所以 **VMM 必须按 vCPU 改写拓扑相关的 CPUID 字段**，让每个 vCPU 报告的 APIC ID 等于它自己的 ID，并声称一个与虚拟机配置一致的拓扑。mini-vmm 的拓扑是最简单的“1 个 socket × N 个核 × 每核 1 个线程”。我们的 guest 是海光 CPU，Linux 对海光的拓扑解析走 AMD 风格的 `0x8000001E` 路径（`hygon_get_topology()`，要求 CPU 有 TOPOEXT 特性），所以改写的重点在 AMD 的那几个 leaf。《多核·实现篇》会逐字段展开。

### 1.7 三方一致原则

现在可以把这条贯穿全章的原则完整地写出来了。在一台虚拟机里，“CPU n 的 APIC ID 是多少”这个问题，有三个信息来源：

```
                   ┌─────────────────────────────────┐
                   │  KVM 模拟的 LAPIC 的 ID 寄存器    │  由 KVM 设置：
                   │  （guest 读 0xFEE00020）          │  APIC ID = vcpu_id
                   └────────────────┬────────────────┘
                                    │  必须相等
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
  ┌─────┴──────────────┐   ┌────────┴─────────┐    ┌────────────┴────────────┐
  │ 固件表               │   │ CPUID            │    │ 其他：IOAPIC ID 不能与    │
  │ MADT 的 LAPIC 条目   │   │ leaf 1 EBX[31:24]│    │ 任何 LAPIC ID 冲突        │
  │ MP table 的处理器条目 │   │ leaf 0x8000001E  │    │                          │
  │ 由 VMM 生成          │   │ 由 VMM 改写       │    │                          │
  └────────────────────┘   └──────────────────┘    └──────────────────────────┘
```

KVM 在复位 LAPIC 时把 APIC ID 设成 vCPU 的 ID（`kvm_lapic_reset()` 里的 `kvm_apic_set_xapic_id(apic, vcpu->vcpu_id)`），这一方由 KVM 决定，VMM 能控制的是创建 vCPU 时传入的 ID。另外两方——固件表和 CPUID——完全由 VMM 生成，必须与第一方一致。

任何一方不一致都会出问题，但症状各不相同：

- **固件表与 LAPIC 不一致**：1.2.2 节讲过，Linux 6.6 并行启动时 AP 读 LAPIC ID 去查固件表建出的数组，查不到就永远停机，BSP 等待超时。
- **CPUID 与 LAPIC 不一致**：Linux 检测到后会打印警告，并以 LAPIC/固件表为准；拓扑信息算错，调度域不正确。
- **IOAPIC ID 与某个 LAPIC ID 冲突**：Linux 会重新分配 IOAPIC ID 或者打印警告。mini-vmm 用“IOAPIC ID = CPU 个数”来避开 0 到 N-1。

真实硬件上这三方由同一块芯片保证一致，所以操作系统不会为不一致的情况准备太多容错。在虚拟机里，这三方由 KVM 和 VMM 的不同代码分别生成，一致性完全靠 VMM 作者自己保证。

### 1.8 停下所有 vCPU：一个多线程程序的老问题

单核时，VMM 停机很简单：唯一的 vCPU 线程从 `KVM_RUN` 返回一个“关机”退出，循环结束。多核时出现了一个新问题：**任何一个 vCPU 触发了关机（比如 guest 执行 `poweroff` 时写 PM1a_CNT 的那颗 CPU），其他 vCPU 线程可能正睡在 `KVM_RUN` 里**（比如在 guest 的 HLT 里等中断）。怎么把它们叫出来？

一个阻塞在系统调用里的线程，能被外部打断的通用手段只有**信号**：给目标线程发一个信号，只要信号处理函数安装时没有带 `SA_RESTART` 标志，`KVM_RUN` 就会以 `-EINTR` 返回。

但只发信号有一个经典的竞态：目标线程刚检查完“是否该停止”的标志（结果为否），还没进入 `KVM_RUN`，此时信号到达，被信号处理函数“消费”掉了；然后线程进入 `KVM_RUN`，在 guest 的 HLT 里睡下去，再也没有信号来叫醒它。

KVM 为此专门提供了一个机制：`kvm_run` 共享页里的 **`immediate_exit`** 字段（`KVM_CAP_IMMEDIATE_EXIT`）。它为 1 时，`KVM_RUN` 在入口处直接返回 `-EINTR`，根本不进入 guest。正确的停机顺序是：**先把目标 vCPU 的 `immediate_exit` 置 1，再给它发信号**。已经在 `KVM_RUN` 里的线程被信号踢出来，还没进去的线程被 `immediate_exit` 挡在门外，两个窗口都被覆盖了。

还有一个副作用需要注意：`immediate_exit` 生效时，KVM **不会写 `kvm_run->exit_reason`**，里面还是上一次退出时的旧值。如果 VMM 在 `-EINTR` 之后仍然去读 `exit_reason` 并分发处理，就会把上一次的 I/O 再执行一遍。

### 1.9 小结

- x86 多核启动是接力：BSP 初始化后用 INIT-SIPI-SIPI 唤醒 AP，SIPI 向量乘以 `0x1000` 就是 AP 的实模式入口，必须位于 1MB 以下。
- Linux 在低端内存放 trampoline，带 AP 从实模式爬到长模式；6.6 并行启动时 AP 读 LAPIC ID 去查固件表建出的数组，确定自己的编号。
- vCPU 是 host 线程，guest 的并行就是线程的并行，内存一致性由硬件原生保证；锁持有者抢占、IPI 开销是虚拟化特有的代价。
- KVM 用 `mp_state` 模拟 AP 的等待状态，INIT/SIPI 全部在内核态 LAPIC 里完成，VMM 只需让每个 vCPU 线程进入 `KVM_RUN`；AP 醒来时 `KVM_RUN` 返回 `-EAGAIN`，要重进而不是报错。
- 没有内核态 irqchip 时所有 vCPU 都是 RUNNABLE，无法按真实协议启动 AP。
- `KVM_GET_SUPPORTED_CPUID` 给的拓扑是 host 的，VMM 必须按 vCPU 改写。
- 三方一致：KVM 的 LAPIC ID（= vcpu_id）、固件表里的 APIC ID、CPUID 里的 APIC ID 必须相同。
- 停下所有 vCPU 要用 `immediate_exit` + 信号，缺一不可；被打断时 `exit_reason` 是旧值，不能分发。
