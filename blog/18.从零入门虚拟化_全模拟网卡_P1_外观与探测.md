《PCI·实现篇》挂上的 pci-test 只有几个自己发明的寄存器，guest 里也只能拿 devmem 去戳它。这一组文章换成一块真实存在的网卡：Intel 82540EM，也就是 QEMU 里的 `-device e1000`。guest 用 Linux 自带的 e1000 驱动，完全不知道自己在虚拟机里，VMM 要做的是让这块“网卡”在驱动看来和真硬件没有区别。

网卡涉及的机制多，按机制分成几 P，每 P 先讲这一块的原理，再讲 mini-vmm 怎么实现：

| P | 内容 |
|---|---|
| P1（本篇） | 设备的外观：PCI 身份、寄存器窗口、EEPROM、PHY，驱动探测成功并报告链路 up |
| P2 | 前端与后端：`--netdev`/`--device`，TAP，收包为什么在 I/O 线程上，后端怎样暂停和恢复收包 |
| P3 | 中断：中断原因寄存器、INTx 电平、为什么中断数约等于 ICR 读次数 |
| P4 | 发送：描述符环、DMA、上下文描述符与校验和 offload |
| P5 | TSO：硬件替驱动切包，以及“哈希对了也可能是错的” |
| P6 | 接收：地址过滤、描述符写回的顺序、什么时候算环满，端到端验证 |

## 一、全模拟设备是什么

### 1.1 驱动决定模拟到什么程度

虚拟机里的网卡有两种做法。一种是半虚拟化（以后的 virtio-net）：guest 知道自己在虚拟机里，装一个专门的驱动，和 VMM 约定一套为虚拟化设计的共享内存协议。另一种是全模拟：VMM 照着某块真实芯片的手册，逐个寄存器地模拟它，guest 装的是那块芯片的原厂驱动。

全模拟的难点不在“把手册上每个寄存器都做出来”，82540EM 的手册有 410 页，寄存器几百个，真要全做是做不完的。真正的标准是：**原厂驱动实际会走到的路径，行为必须和真硬件一致；驱动不走的路径，可以不做。** 所以做全模拟设备时有两份资料要对照着读：芯片手册告诉你某个寄存器“应该”怎样，驱动源码告诉你哪些寄存器真的会被访问、以什么顺序访问、读回什么值才算通过。

拿一个具体的例子：手册里 EEPROM 可以经 EECD 寄存器逐位读，也可以经 EERD 寄存器一次读一个字。Linux 的 e1000 驱动只用前一种（第五章会看到 EECD 被写了 5000 多次），EERD 一次都没碰过。模拟器如果只做了 EERD，驱动 probe 会失败；只做了 EECD，Linux 能工作，但以后换一个用 EERD 的驱动就会失败。mini-vmm 两条都做了，因为 EERD 本身只有十几行，但哪一条是 Linux 的必经之路，要靠 trace 确认，而不是猜。

### 1.2 为什么选 82540EM

- Linux 自带驱动（`drivers/net/ethernet/intel/e1000/`），手册公开（`ref/8254x_GBe_SDM.pdf`）。
- 它是 QEMU 最常用的模拟网卡之一，同一个 guest 可以放到 QEMU 里对照。
- 它有一块“真硬件”该有的全部部件：寄存器窗口、描述符环、DMA、中断原因寄存器、外挂的 EEPROM 和 PHY 芯片。这些部件正是以后 virtio-net 要简化掉的东西，两者放在一起对比，才看得出半虚拟化到底省掉了什么。

### 1.3 驱动的探测顺序

在讲每个部件之前，先看驱动的 `e1000_probe()`（`e1000_main.c`）按什么顺序和设备打交道。每一步失败，probe 都会中止，eth0 就不会出现：

```text
e1000_probe
  ├─ pci_enable_device、pci_set_master          PCI 层：打开 decode 和总线主控
  ├─ e1000_is_need_ioport → 申请 MEM + IO BAR   82540EM 必须有 IO BAR
  ├─ pci_ioremap_bar(BAR0)                      映射寄存器窗口
  ├─ e1000_init_hw_struct
  │    ├─ e1000_set_mac_type                    按 device ID 认出 82540
  │    └─ e1000_get_bus_info                    读 STATUS，得出 "PCI:33MHz:32-bit"
  ├─ e1000_init_eeprom_params                   读 EECD，确定 EEPROM 类型和大小
  ├─ e1000_reset_hw                             经 IO BAR 写 CTRL.RST
  ├─ e1000_validate_eeprom_checksum             读全部 64 个字，和必须是 0xBABA
  ├─ e1000_read_mac_addr                        EEPROM 前 3 个字是 MAC
  └─ register_netdev                            eth0 出现
e1000_open（ip link set eth0 up）
  └─ … e1000_watchdog → e1000_check_for_link    读 STATUS.LU 和 PHY 寄存器，打印 "Link is Up"
```

下面四章按这个顺序走：PCI 外观（第二章）、寄存器窗口（第三章）、EEPROM（第四、五章）、PHY 与链路（第六章）。

## 二、PCI 外观

### 2.1 原理：驱动靠 ID 认设备

guest 枚举 PCI 时读到的 vendor ID / device ID，决定了哪个驱动来接管它。e1000 驱动的 `e1000_pci_tbl` 里列着它支持的全部 ID，`8086:100E` 是 82540EM。class code `020000` 表示“网络控制器 / 以太网”，这是给 lspci 之类的工具看的，驱动匹配只看 ID。

手册第 4.1 节给出了 82540EM 的配置空间：

| 项目 | 值 | 说明 |
|---|---|---|
| Vendor / Device | 8086 / 100E | |
| Subsystem Vendor / ID | 8086 / 1008 | 真卡从 EEPROM 加载，没有 EEPROM 时是这个默认值 |
| Class | 020000 | 以太网控制器 |
| BAR0 | 32 位 MEM，128 KiB | 全部寄存器 |
| BAR1 | 可选的外挂 flash | 驱动不用 |
| BAR2 | IO，8 字节 | IOADDR / IODATA 两个端口，间接访问同一组寄存器 |
| Interrupt Pin | INTA | |

两种 BAR 的意义在《PCI·原理篇》第三章讲过：MEM BAR 映射到物理地址空间，guest 用普通的 mov 指令访问；IO BAR 映射到 I/O 端口空间，用 in/out 访问。

### 2.2 原理：为什么还要一个 IO BAR

既然 BAR0 已经覆盖了全部寄存器，IO BAR 看起来多余。原因在 `e1000_reset_hw()`：

```c
switch (hw->mac_type) {
case e1000_82544:
case e1000_82540:
case e1000_82545:
case e1000_82546:
case e1000_82541:
case e1000_82541_rev_2:
    /* These controllers can't ack the 64-bit write when issuing the
     * reset, so use IO-mapping as a workaround to issue the reset
     */
    E1000_WRITE_REG_IO(hw, CTRL, (ctrl | E1000_CTRL_RST));
    break;
```

这一代芯片在复位的瞬间来不及应答 MMIO 写，所以驱动改用 IO 端口发复位命令。驱动在 probe 一开始就用 `e1000_is_need_ioport()` 按 device ID 决定要不要申请 IO BAR，82540EM 在名单里。模拟的设备不存在“来不及应答”的问题，但 IO BAR 必须有：没有它，`pci_request_selected_regions()` 申请不到 IO 资源，probe 直接失败。

这就是 1.1 节说的“驱动决定模拟到什么程度”的一个例子：IO BAR 存在的原因是一个只有真硬件才有的时序缺陷，但驱动已经把这条绕路写死了，模拟器就得跟着提供。

### 2.3 实现：e1000_attach

设备注册在 `src/devices/e1000.c` 的 `e1000_attach()`。PCI 核心（《PCI·实现篇》）已经负责了配置空间、BAR 分配和路由，设备只需要填自己的身份和 BAR 回调：

```c
p->name             = "e1000";
p->vendor_id        = E1000_VENDOR_ID;          /* 0x8086 */
p->device_id        = E1000_DEVICE_ID_82540EM;  /* 0x100E */
p->class_code       = 0x020000;
p->subsys_vendor_id = E1000_VENDOR_ID;
p->subsys_id        = E1000_SUBSYS_ID;          /* 0x1008 */
p->intx_pin         = 1;                        /* INTA */
p->bus_master       = true;                     /* 网卡要做 DMA */
p->bars[0] = (struct pci_bar){ .type = PCI_BAR_MEM32, .size = E1000_MMIO_SIZE,
                               .opaque = s, .read = mmio_read, .write = mmio_write };
p->bars[2] = (struct pci_bar){ .type = PCI_BAR_IO, .size = E1000_IO_SIZE,
                               .opaque = s, .read = io_read, .write = io_write };
```

和 pci-test 相比多了两个字段。`subsys_vendor_id`/`subsys_id` 是为 e1000 新加进 PCI 核心的，之前它们固定为 0。`bus_master = true` 让 COMMAND 寄存器的 Bus Master 位可写（P4 会用到：驱动不打开这一位，设备就不许做 DMA）。BAR1 留空，PCI 核心对空 BAR 读回 0，guest 就认为这个 BAR 不存在，所以 IO BAR 出现在 BAR2，guest 日志里是 `reg 0x18`：

```text
pci 0000:00:01.0: [8086:100e] type 00 class 0x020000
pci 0000:00:01.0: reg 0x10: [mem 0xc0000000-0xc001ffff]
pci 0000:00:01.0: reg 0x18: [io  0x1000-0x1007]
```

## 三、寄存器窗口

### 3.1 原理：32 位寄存器，有的有副作用

手册第 13 章列出全部寄存器，偏移从 0x00000 到 0x1FFFF，每个 32 位。按行为可以分成三类：

- **存储型**：写什么读回什么，只是某些位只读。例如 TDBAL（发送环基址低 32 位）低 4 位恒为 0，因为环必须 16 字节对齐。
- **有副作用的**：读写会触发动作。CTRL 写 RST 位让芯片复位；ICR 读一次就清零（P3）；TDT 写入新值让芯片开始发包（P4）。
- **只读的状态**：STATUS 反映链路、速率、双工，写入无效。

第 13.2 节还规定了窄访问：比 32 位窄的写被忽略，窄读返回整个寄存器里对应的字节。

### 3.2 实现：一个数组，一张表，一个 switch

`struct e1000`（`include/devices/e1000.h`）用一个数组装下整个 128 KiB 窗口：

```c
uint32_t regs[E1000_NREGS];      /* E1000_MMIO_SIZE / 4 = 32768 个 */
```

32768 个 dword 只有 128 KiB，直接按偏移索引，比为每个寄存器单独起一个字段简单得多。三类寄存器分开处理：

**存储型**放进一张表，每项记着偏移、连续个数（MTA、RA、VFTA 这类数组寄存器一项覆盖一段）和可写掩码：

```c
static const struct reg_desc plain_regs[] = {
    { E1000_TDBAL,    1, 0xFFFFFFF0 },      /* 低 4 位恒 0：16 字节对齐 */
    { E1000_TDLEN,    1, 0x000FFF80 },      /* 128 字节的倍数 */
    { E1000_RDH,      1, 0x0000FFFF },
    ...
    { E1000_MTA,      E1000_MTA_N,      0xFFFFFFFF },
    { E1000_RA,       E1000_RA_N * 2,   0xFFFFFFFF },
};
```

写入时只保留掩码里的位，这和《PCI·实现篇》2.2 节配置空间的 `wmask` 是同一个思路：可写掩码本身就是“哪些位只读”的规格，不需要为每个寄存器写一段判断。

**有副作用的**在 `e1000_reg_read()`/`e1000_reg_write()` 的 switch 里逐个处理，例如：

```c
case E1000_CTRL:
    if (val & E1000_CTRL_RST) {
        e1000_reset(s);                  /* RST 自清零 */
        return;
    }
    ...
case E1000_TDT:
    *reg(s, E1000_TDT) = val & 0xFFFF;
    tx_process(s);
    return;
```

**都不在的**就是没实现的寄存器：读 0、写丢弃，每个偏移第一次被访问时记一条 warn：

```text
e1000: write 0x<值> to unimplemented register 0x<偏移> ignored
e1000: read of unimplemented register 0x<偏移> returns 0
```

这条 warn 是做全模拟设备的指南针。驱动碰了一个模型不认识的寄存器，日志里立刻有一行，告诉你下一步该去读手册的哪一节。e2e 测试里也有一条断言要求整个启动加收发过程中**没有**这条 warn（第七章）。

### 3.3 实现：两种 BAR，一套寄存器

BAR0 的回调 `mmio_read`/`mmio_write` 按 3.1 节的窄访问规则把访问交给 `e1000_reg_read`/`e1000_reg_write`。BAR2 的 8 字节是两个 32 位端口：偏移 0 是 IOADDR，写入寄存器偏移；偏移 4 是 IODATA，读写 IOADDR 选中的那个寄存器（手册第 13.3 节）。

```c
static int io_write(void *opaque, uint64_t off, uint32_t size, const void *data)
{
    ...
    if (off == 0)
        s->ioaddr = v & 0x1FFFC;
    else if (off == 4 && s->ioaddr < E1000_MMIO_SIZE)
        e1000_reg_write(s, s->ioaddr, v);
    return VMM_OK;
}
```

两条路最后汇到同一个 `e1000_reg_write()`，所以经 IO BAR 写 CTRL.RST 和经 MMIO 写效果完全相同。一次启动里 `e1000.bar2` 只有 6 次访问，PIO trace 里是三对：

```text
e1000.bar2  1000 W4 00000000    IOADDR = 0，选中 CTRL
e1000.bar2  1004 W4 04000a09    IODATA：CTRL 的值，bit 26 是 RST
```

IO BAR 除了发复位命令，驱动再也不用。

## 四、EEPROM：原理

### 4.1 网卡为什么有一块 EEPROM

每块网卡出厂时要带上一些“这块卡自己的”信息：MAC 地址、subsystem ID、上电时某些寄存器的初值。这些信息不能写死在芯片里（同一型号芯片要卖给很多板卡厂），所以放在板子上一颗单独的小 EEPROM 里。82540EM 配的是 93C46 这类 64 个 16 位字（1 Kbit）的串行 EEPROM，内容由手册第 5.6 节规定：

| 字 | 内容 |
|---|---|
| 0x00–0x02 | MAC 地址，每个字低字节在前 |
| 0x0A | Initialization Control 1 |
| 0x0B / 0x0C | Subsystem ID / Subsystem Vendor ID |
| 0x0D / 0x0E | Device ID / Vendor ID |
| 0x0F | Initialization Control 2 |
| 0x3F | 校验字：让 0x00–0x3F 的和等于 0xBABA |

驱动 probe 时把 64 个字全部读一遍求和（`e1000_validate_eeprom_checksum()`），和不是 0xBABA 就报 "The EEPROM Checksum Is Not Valid" 并放弃。这是驱动在判断“这块卡的出厂数据有没有坏”，对模拟器来说意味着：EEPROM 镜像不能随便填，必须算出正确的校验字。

### 4.2 Microwire：用寄存器里的四个位模拟一根串行线

93C46 是一颗串行芯片，只有四根信号线：

| 信号 | 方向 | 作用 |
|---|---|---|
| CS | 主控 → EEPROM | 片选，拉高开始一次事务，拉低结束 |
| SK | 主控 → EEPROM | 时钟，EEPROM 在上升沿采样 DI |
| DI | 主控 → EEPROM | 主控发出的数据位 |
| DO | EEPROM → 主控 | EEPROM 送出的数据位 |

82540EM 把这四根线直接映射成 EECD 寄存器（偏移 0x10）的四个位：SK 是 bit 0、CS 是 bit 1、DI 是 bit 2、DO 是 bit 3。驱动要读 EEPROM，就得像操纵 GPIO 一样，一次写一个位地“搓”出时序，这种做法叫 bit-banging。

一次读操作的时序（93C46 数据手册 DS21749H 第 3 节，x16 组织）：

```text
CS  ___/‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\___
SK  ______/‾\_/‾\_/‾\_/‾\_/‾\_ … _/‾\_/‾\_/‾\_/‾\_ … _/‾\_____
DI  ______| 1 | 1 | 0 |A5 |A4 | … |A0 |
DO  _______________________________| 0 |D15|D14| … |D0 |
          起始位  操作码   6 位地址     哑 0   16 位数据，高位在前
                 READ=10
```

CS 拉高后，第一个 DI=1 的上升沿是起始位，接着 2 位操作码（READ 是 `10`）、6 位地址。地址最后一位被采样后，DO 先输出一个固定的 0（哑位），之后每个上升沿输出一位数据。CS 一直保持高电平就会顺序读出下一个字。

Linux 把“起始位 + 操作码”合起来当作 3 位的 opcode `110b` 发出去（`e1000_init_eeprom_params()` 里 `opcode_bits = 3`），每一次拉高、拉低 SK 之后都调用 `E1000_WRITE_FLUSH()` 并 `udelay(50)`：

```c
static void e1000_raise_ee_clk(struct e1000_hw *hw, u32 *eecd)
{
    *eecd = *eecd | E1000_EECD_SK;
    ew32(EECD, *eecd);
    E1000_WRITE_FLUSH();               /* 即 er32(STATUS) */
    udelay(hw->eeprom.delay_usec);     /* 50 */
}
```

`E1000_WRITE_FLUSH()` 是读一次 STATUS。在真硬件上，PCI 的写是“发出去就不管”的（posted write），读一次同一设备的寄存器，可以保证前面的写已经到达芯片，之后的 udelay 才真正是“时钟保持高电平 50 µs”。这个细节在第五章的 trace 里会变成一个很显眼的数字。

### 4.3 两条读路：EECD 和 EERD

手册还提供了 EERD 寄存器（偏移 0x14）：写入地址和 START 位，硬件自己完成整个 Microwire 事务，置 DONE 后数据出现在高 16 位。这条路省掉了驱动的位操作，82540 上就有，但 Linux 的 e1000 驱动从来不用它，整个 8254x 家族一律走 EECD 位操作；用 EERD 的是更新芯片的 e1000e 驱动。

## 五、EEPROM：实现

### 5.1 生成镜像

镜像在 `eeprom_build()` 里按 `mac=` 生成，每次启动重算：

```c
for (i = 0; i < 3; i++)                  /* MAC，每个字低字节在前 */
    w[i] = (uint16_t)(s->mac[2 * i] | s->mac[2 * i + 1] << 8);
w[0x0A] = 0x4408;                        /* Initialization Control 1 */
w[0x0B] = E1000_SUBSYS_ID;
w[0x0C] = E1000_VENDOR_ID;
w[0x0D] = E1000_DEVICE_ID_82540EM;
w[0x0E] = E1000_VENDOR_ID;
...
for (i = 0; i < E1000_EEPROM_WORDS - 1; i++)
    sum = (uint16_t)(sum + w[i]);
w[E1000_EEPROM_WORDS - 1] = (uint16_t)(E1000_EEPROM_CHECKSUM - sum);
```

最后一个字取 `0xBABA - (前 63 个字的和)`，于是 64 个字加起来恰好是 0xBABA。没列出的字是厂商保留或板级配置，取 0。

### 5.2 Microwire 状态机

EECD 的写入在 `eecd_write()` 里检测 SK 的上升沿，每个上升沿推动一次状态机 `ee_clock()`：

```text
            CS 拉低（任何状态）
   ┌────────────────────────────────────────┐
   ▼                                        │
 IDLE ──DI=1 的上升沿（起始位）──▶ CMD ──收满 2+6 位──┬─ 操作码 READ ──▶ READ
                                                   └─ 其他 ──▶ IGNORE
```

```c
case EE_CMD:
    s->ee.bits = s->ee.bits << 1 | di;
    if (++s->ee.nbits < 2 + 6)
        break;
    if ((s->ee.bits >> 6) == E1000_EE_OPCODE_READ) {
        s->ee.state = EE_READ;
        s->ee.addr = (uint8_t)(s->ee.bits & 0x3F);
        s->ee.bitpos = 16;
        s->ee.dout = false;               /* 哑 0 */
    } else {
        ...
        s->ee.state = EE_IGNORE;
    }
    break;
case EE_READ:
    if (s->ee.bitpos == 0) {             /* 一个字读完，CS 仍高：顺序读下一个字 */
        s->ee.addr = (uint8_t)((s->ee.addr + 1) % E1000_EEPROM_WORDS);
        s->ee.bitpos = 16;
    }
    s->ee.bitpos--;
    s->ee.dout = (s->eeprom[s->ee.addr] >> s->ee.bitpos) & 1;
    break;
```

读 EECD 时 `eecd_read()` 把 `dout` 放进 DO 位。写、擦除这些命令进入 IGNORE：镜像每次启动都按 `mac=` 重新生成，写进去也留不到下一次，与其假装写成功，不如让 guest 自己的校验读回旧值，同时记一条 warn。

EECD 里还有一对 REQ/GNT 位，是驱动和芯片内部的 EEPROM 自动加载逻辑之间的仲裁：驱动置 REQ，等硬件回 GNT 才能开始位操作。这里没有别的主控，`eecd_read()` 看到 REQ 就立即给 GNT。

### 5.3 最反直觉的一位：哑 0

时序图里，地址最后一位采样后 DO 先给出一个哑 0。读 Linux 的 `e1000_shift_in_ee_bits()` 会发现它并不读这一位：它每次先拉高 SK、再读 DO，16 次循环读到的依次是 D15…D0。原因是哑 0 是在地址最后一位的那个上升沿上出现的，等驱动开始“拉高 SK、读 DO”的循环时，第一个上升沿已经把 D15 推出来了。

所以模型必须在收满地址的那个沿上输出哑 0（`dout = false`，`bitpos = 16`），而不是直接输出 D15。如果偷懒直接从 D15 开始：

```c
/* 错误的写法 */
s->ee.bitpos = 15;
s->ee.dout = (s->eeprom[s->ee.addr] >> 15) & 1;
```

驱动第一次采样拿到的就是 D14，每个字整体左移一位，校验和不对，probe 失败。单元测试里这个错误实现（`ee_no_dummy`）会变红。

这正是 1.1 节那条原则的反面：只读手册的时序图，很容易把“哑 0”理解成“驱动要跳过的一位”，从而要么多输出一位、要么少输出一位；要靠驱动源码确认它在哪个沿采样，两份资料对上才算数。

### 5.4 EERD

`eerd_write()` 收到 START 就从镜像里取数，立即置 DONE。Linux 不走这条路，单元测试里用它和 Microwire 读出的值互相印证：两条路对同一个字必须读出相同的数。

### 5.5 trace 里的 EEPROM

用 `--trace-mmio` 录下一次启动（详见《数清每一次exit》），把 EECD 的写入序列按 CS 和 SK 的边沿解码回 Microwire 事务，得到：

- 71 次 READ，地址覆盖 0x00–0x3F 全部 64 个字：校验和要读 64 次，其余 7 次是对个别字的重读；
- 没有任何写命令，EERD 一次都没被访问；
- EECD 写 5112 次、读 1634 次；同一时间窗口里 STATUS 读 5005 次，正是每次搓时钟后的 `E1000_WRITE_FLUSH()`；
- probe 里的这段位操作持续约 0.4 s，几乎就是 probe 的全部耗时：dmesg 里从驱动横幅 `e1000: Intel(R) PRO/1000 Network Driver` 到 eth0 出现正好是 0.41 s。

trace 开头几行就是 4.2 节的仲裁和起始位：

```text
15 e1000.bar0 c0000010 R4 00000110    EECD：PRES | FWE=01
16 e1000.bar0 c0000010 W4 00000150    置 REQ
17 e1000.bar0 c0000010 R4 000001d0    读回 GNT
19 e1000.bar0 c0000010 W4 000001d2    CS 拉高
21 e1000.bar0 c0000010 W4 000001d6    DI=1（起始位）
22 e1000.bar0 c0000008 R4 00000083    WRITE_FLUSH：读 STATUS
23 e1000.bar0 c0000010 W4 000001d7    SK 拉高：起始位被采样
24 e1000.bar0 c0000008 R4 00000083    WRITE_FLUSH
```

这 0.4 s 里有多少是虚拟化的代价？每次 `WRITE_FLUSH` 后面跟着一次 `udelay(50)`，约 5000 次合计 0.25 s，真硬件上也一样要等；剩下的部分是一万多次 MMIO exit。一个只为读 128 字节出厂数据的协议，在虚拟机里变成了一万次陷出，这是全模拟设备代价的第一个具体例子，P6 还会在数据面上看到更大的数字。

## 六、PHY 与链路

### 6.1 原理：MAC 和 PHY

一块以太网卡在电路上分两部分。**MAC**（介质访问控制）处理以太网帧：组帧、地址过滤、校验，和主机打交道，82540EM 的寄存器窗口就是 MAC 的。**PHY**（物理层）处理网线上的电信号：编码、和对端协商速率与双工（自协商），并报告链路是否连通。82540EM 内置了一颗兼容 Marvell 88E1011 的 PHY。

MAC 和 PHY 之间用一条叫 MDIO 的管理总线通信，PHY 有自己的一组 16 位寄存器（IEEE 802.3 第 22 条定义了前 16 个的含义）：

| PHY 寄存器 | 含义 |
|---|---|
| 0 CTRL | 复位、自协商使能、重启自协商、速率和双工 |
| 1 STATUS | 能力位、自协商完成、link up |
| 2 / 3 ID | PHY 厂商和型号，驱动据此选择初始化脚本 |
| 5 LP_ABILITY | 对端通告的能力 |
| 10 1000T_STATUS | 千兆的本端与对端状态 |
| 17 SPEC_STATUS | Marvell 扩展：解析出的速率、双工、实时链路 |

驱动经 MAC 的 MDIC 寄存器（偏移 0x20）访问 PHY：把操作码（读/写）、PHY 地址、寄存器号、数据一起写进 MDIC，等 READY 位置起，读操作的结果在低 16 位（手册第 13.4.7 节）。

链路状态在 MAC 这边也有一份：STATUS 寄存器的 LU（link up）、FD（全双工）、SPEED 位。驱动的 watchdog 周期性读 STATUS.LU，发现从 0 变 1 就打印 "NIC Link is Up"，再从 PHY 读出速率和双工。

### 6.2 实现：链路永远是 1000 Mb/s 全双工

模拟的网卡没有网线，“链路”是 VMM 和 TAP 之间的一个文件描述符，不存在协商失败或者拔线。所以 PHY 被固定成“自协商已完成、1000BASE-T 全双工、链路 up”的状态，寄存器值在 `phy_reset()` 里一次给齐：

```c
s->phy[PHY_CTRL]         = 0x1140;  /* 自协商使能、全双工、1000 */
s->phy[PHY_STATUS]       = 0x796D;  /* 能力位 + 自协商完成 + link up */
s->phy[PHY_ID1]          = 0x0141;
s->phy[PHY_ID2]          = 0x0C20;  /* 88E1011，revision 0 */
s->phy[PHY_LP_ABILITY]   = 0x41E1;
s->phy[PHY_1000T_STATUS] = 0x3C00;
s->phy[PHY_SPEC_STATUS]  = 0xAC00;  /* 1000 Mb/s、全双工、已解析、实时 link up */
```

驱动写 CTRL 的“重启自协商”位时，模型直接清掉这一位，表示协商瞬间完成；写 RESET 位时回到上面的初值。STATUS、ID 这些只读寄存器写入被忽略。

MDIC 的一次写就完成整个 MDIO 事务，READY 立即置位：

```c
static void mdic_write(struct e1000 *s, uint32_t val)
{
    uint32_t phy = (val >> E1000_MDIC_PHY_SHIFT) & 0x1F;
    ...
    if (phy != E1000_PHY_ADDR) {
        out |= E1000_MDIC_ERROR;
    } else if (op == E1000_MDIC_OP_READ) {
        out = (out & ~E1000_MDIC_DATA_MASK) | s->phy[r];
    } else if (op == E1000_MDIC_OP_WRITE) {
        phy_write(s, r, (uint16_t)(val & E1000_MDIC_DATA_MASK));
    }
    *reg(s, E1000_MDIC) = out | E1000_MDIC_READY;
    ...
}
```

只有 PHY 地址 1 上有设备，访问别的地址置 ERROR，驱动据此报错，而不是读到一个假的 PHY。

MAC 侧的 STATUS 在 `e1000_reg_read()` 里固定返回：

```c
case E1000_STATUS:
    return E1000_STATUS_FD | E1000_STATUS_LU | E1000_STATUS_SPD_1000;   /* 0x83 */
```

这个值同时回答了 probe 早期 `e1000_get_bus_info()` 的问题：PCIX_MODE 位为 0 表示传统 PCI，PCI66 位为 0 表示 33 MHz，BUS64 位为 0 表示 32 位总线，于是驱动打印出 `(PCI:33MHz:32-bit)`。对虚拟设备来说这几个数字没有物理意义，取的是传统 PCI 插槽最基本的组合。

## 七、验证

### 7.1 guest 里看到的现象

`make test emu-net` 在一个新建的 user + net namespace 里启动 guest（P2 会讲为什么不需要 root），以 `mac=52:54:00:ab:cd:ef` 挂上 e1000。probe 和链路相关的断言：

```text
e1000 0000:00:01.0 eth0: (PCI:33MHz:32-bit) 52:54:00:ab:cd:ef
e1000 0000:00:01.0 eth0: Intel(R) PRO/1000 Network Connection
e1000: eth0 NIC Link is Up 1000 Mbps Full Duplex, Flow Control: RX
```

第一行的 MAC 是驱动从 EEPROM 前 3 个字读出来的，和命令行上的 `mac=` 一致，说明 Microwire 状态机、镜像布局和校验和都对。测试特意不用默认 MAC：默认值和 QEMU 一样是 `52:54:00:12:34:56`，用它的话，即使 `mac=` 没有生效，断言也会碰巧通过。

另外两条断言：`ip link set eth0 up` 后 `/sys/class/net/eth0/carrier` 变成 1（按这个状态本身等，最多 10 秒，不是固定 sleep）；整个启动加收发过程中没有一条 "unimplemented register" warn。

### 7.2 单元测试

`tests/unit/e1000_test.c` 不启动 guest，直接调 `e1000_reg_read`/`e1000_reg_write`。EEPROM 的用例按 Linux 驱动的函数（`e1000_acquire_eeprom`、`e1000_shift_out_ee_bits`、`e1000_shift_in_ee_bits`、`e1000_standby_eeprom`）逐位复刻了位操作序列，读出全部 64 个字后检查：

- 和为 0xBABA，前 3 个字是 MAC，0x0D 字是 device ID；
- EERD 读出的值和 Microwire 读出的一致；
- CS 一直保持高电平时顺序读到下一个字；
- WRITE 命令被忽略，之后再读 0 号字仍是原值。

PHY 用例检查 ID 是 0x01410C20、link up 和自协商完成位、只读寄存器写不进去、重启自协商位自清零、访问错误的 PHY 地址置 ERROR。

“少输出哑 0”的错误实现会让第一组检查变红。这样的错误实现在 P1 到 P6 里一共有十几个，每一个都对应一个容易写错的细节，测试要能把它们一一抓出来，才说明测试本身是有效的。
