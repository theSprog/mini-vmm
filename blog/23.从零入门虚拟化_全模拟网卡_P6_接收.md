# 从零入门虚拟化：全模拟网卡 P6：接收

P4 和 P5 讲的是 guest 往外发。这一 P 反过来：一帧从 TAP 进来，网卡先判断它是不是发给自己的，再把它写进 guest 预先准备好的缓冲，最后告诉驱动“这里有一帧”。发送由 guest 写 TDT 触发，在 vCPU 线程上同步做完；接收由外界触发，在 I/O 线程上做，guest 的驱动可能正同时在另一个 CPU 上读同一个环。所以接收这边多出两个发送没有的问题：描述符各个字段按什么顺序写回，以及怎样判断环里还有没有空位。最后一章把整个系列的验证放在一起：端到端测试怎样搭、它挡得住哪些错误、挡不住哪些。

| P | 内容 |
|---|---|
| P1 | 设备的外观：PCI 身份、寄存器窗口、EEPROM、PHY，驱动探测成功并报告链路 up |
| P2 | 前端与后端：`--netdev`/`--device`，TAP，收包为什么在 I/O 线程上，后端怎样暂停和恢复收包 |
| P3 | 中断：中断原因寄存器、INTx 电平、为什么中断数约等于 ICR 读次数 |
| P4 | 发送：描述符环、DMA、上下文描述符与校验和 offload |
| P5 | TSO：硬件替驱动切包，以及“哈希对了也可能是错的” |
| P6（本篇） | 接收：地址过滤、描述符写回的顺序、什么时候算环满，端到端验证 |

## 一、一帧进来要经过什么

TAP 交给后端一帧，后端在 I/O 线程上调用前端注册的回调 `e1000_receive()`（P2 第五章）。从这里开始，一帧依次经过下面几步，任何一步不通过，这一帧就到此为止：

```text
TAP ──► e1000_receive()                       I/O 线程，持 io_lock
          │ RCTL.EN=0？                       ── 丢弃
          │ 目的地址过滤（第二章）            ── 丢弃
          │ 超长？VLAN 过滤？                 ── 丢弃
          │ 补齐到 60 字节，追加 FCS，剥 VLAN tag（第三章）
          ▼
        rx_ring_put()
          │ 空闲缓冲装不下整帧？（第五章）    ── 返回 FULL，后端暂停
          │ 写数据 → 写其余字段 → 写 status（第四章）
          │ RDH 前进
          ▼
        置 ICR.RXT0（必要时 RXDMT0）→ INTx（P3）
```

被丢弃的帧不会让后端暂停，后端接着读下一帧；只有“装不下”才让后端停下来等 guest 补缓冲。这两类“不收”的区别是 P2 第 6.2 节讲过的：前者是这帧本来就不该收，后者是现在没地方放。

## 二、地址过滤

### 2.1 网卡为什么要替驱动挑帧

以太网是广播介质的后代。在一台交换机后面，网卡仍然会看到发给别人的帧（交换机还没学到地址时会泛洪），也会看到大量组播和广播。如果网卡把看到的每一帧都 DMA 进内存、再打一次中断，CPU 要为不属于自己的流量付钱。所以网卡在入口按目的 MAC 地址筛一遍，只把“可能和自己有关”的帧交给驱动。

驱动通过几个寄存器告诉网卡“和自己有关”是什么意思。82540EM 支持五种规则（手册第 3.2.1 节），任一条通过就收下：

| 规则 | 配置 | 匹配什么 |
|---|---|---|
| 精确匹配 | 16 组 RAL/RAH（`RA` 起始于 0x5400） | 目的地址等于其中一组，且这组的 AV（Address Valid）位为 1 |
| 单播混杂 | RCTL.UPE | 所有单播 |
| 组播哈希 | 128 个 MTA 寄存器，共 4096 位；RCTL.MO 选哪 12 位 | 目的地址的 12 位做下标，MTA 里对应位为 1 |
| 组播混杂 | RCTL.MPE | 所有组播 |
| 广播 | RCTL.BAM | ff:ff:ff:ff:ff:ff |

单播和组播靠目的地址第 0 个字节的最低位区分（I/G 位），1 是组播，广播是组播的特例。

### 2.2 Linux 怎样填这些寄存器

`e1000_set_rx_mode()` 在接口 up、地址列表变化、混杂模式切换时被调用。它做三件事：

1. 按接口标志设 RCTL：`IFF_PROMISC` 时置 UPE 和 MPE；`IFF_ALLMULTI` 时置 MPE。
2. RA[0] 是网卡自己的 MAC（复位时从 EEPROM 装入，P1 第五章），其余 15 组从 RA[1] 开始，先放额外的单播地址，再放组播地址。
3. 精确匹配放不下的组播地址才进 MTA 哈希表；然后把 128 个 MTA 寄存器全部写一遍。

第 2 步有一个容易忽略的后果：只要组播地址不超过 15 个，**Linux 根本不用 MTA**。哈希表是精确匹配的溢出区，不是组播的默认去处。trace 里能看到 guest 起来之后 RA[1..3] 的内容（RAL 低字节在前，RAH 的低 16 位是地址的最后两个字节，bit 31 是 AV）：

| 寄存器 | RAL | RAH | 地址 | 是什么 |
|---|---|---|---|---|
| RA[0] | 0x12005452 | 0x80005634 | 52:54:00:12:34:56 | 网卡自己的 MAC |
| RA[1] | 0x00003333 | 0x80000100 | 33:33:00:00:00:01 | IPv6 所有节点组播 |
| RA[2] | 0x005e0001 | 0x80000100 | 01:00:5e:00:00:01 | IPv4 224.0.0.1 |
| RA[3] | 0x12ff3333 | 0x80005634 | 33:33:ff:12:34:56 | 链路本地地址 fe80::5054:ff:fe12:3456 的 solicited-node 组播 |

在这份 trace 覆盖的整次运行里（启动、ping、下载、关机），128 个 MTA 寄存器每个被写了 6 次，写的值全是 0。`ip link set eth0 promisc on` 之后，RCTL 从 0x8002（BAM | EN）变成 0x801a（再加上 UPE | MPE）。

RCTL 的其余位也在这次 trace 里：BSIZE=0、BSEX=0，缓冲 2048 字节；RDMTS=0，阈值是环的一半；SECRC=0，网卡把 FCS 留在缓冲里；LPE=0，最长 1522 字节。这几位在后面几章都会用到。

### 2.3 实现

`rx_filter()` 把五条规则按手册的顺序翻译过来：

```c
static bool rx_filter(struct e1000 *s, const uint8_t *dst)
{
    uint32_t rctl = *reg(s, E1000_RCTL);
    bool mcast = dst[0] & 1;
    uint32_t hash;
    int i;

    if (mcast && (rctl & E1000_RCTL_BAM) &&
        !memcmp(dst, "\xff\xff\xff\xff\xff\xff", ETH_ALEN))
        return true;
    if (!mcast && (rctl & E1000_RCTL_UPE))
        return true;
    if (mcast && (rctl & E1000_RCTL_MPE))
        return true;
    for (i = 0; i < E1000_RA_N; i++) {
        uint32_t lo = *reg(s, E1000_RA + 8 * i), hi = *reg(s, E1000_RA + 8 * i + 4);
        uint8_t a[ETH_ALEN] = { (uint8_t)lo, (uint8_t)(lo >> 8), (uint8_t)(lo >> 16),
                                (uint8_t)(lo >> 24), (uint8_t)hi, (uint8_t)(hi >> 8) };

        /* AS（17:16）非 0 是按源地址匹配，不参与目的地址过滤 */
        if ((hi & E1000_RAH_AV) && !(hi & 0x30000) && !memcmp(a, dst, ETH_ALEN))
            return true;
    }
    if (!mcast)
        return false;
    /* MO 选取目的地址里的哪 12 位做哈希（第 13.4.22 节） */
    switch ((rctl >> E1000_RCTL_MO_SHIFT) & 3) {
    case 0:  hash = dst[4] >> 4 | (uint32_t)dst[5] << 4; break;
    case 1:  hash = dst[4] >> 3 | (uint32_t)dst[5] << 5; break;
    case 2:  hash = dst[4] >> 2 | (uint32_t)dst[5] << 6; break;
    default: hash = dst[4]      | (uint32_t)dst[5] << 8; break;
    }
    hash &= 0xFFF;
    return (*reg(s, E1000_MTA + 4 * (hash >> 5)) >> (hash & 31)) & 1;
}
```

有两处需要对照手册才看得懂：

- **哈希取的是地址的哪几位。** 手册说 MO=0 取地址的 [47:36] 位。这里的位号按网卡内部的存储方式编，也就是 RAL/RAH 里的排法：地址的第 0 个字节是 [7:0]，第 5 个字节是 [47:40]。[47:36] 就是第 5 个字节的全部 8 位，加上第 4 个字节的高 4 位，也就是代码里的 `dst[4] >> 4 | dst[5] << 4`。12 位里高 7 位选 128 个寄存器之一，低 5 位选寄存器里的一位。
- **RAH 的 AS 字段。** RAH 的 17:16 位（Address Select）为 0 时按目的地址匹配，非 0 是按源地址匹配，用于别的功能，过滤时跳过。

### 2.4 实测：每类 100 帧

在测试用的 namespace 里，host 用 packet socket 往 `tap0` 注入以太网帧，EtherType 0x88B5（IEEE 留给本地实验的值），每类 100 帧，注入前后读 guest 的 `rx_packets`。表里“网卡丢弃”一列来自临时加了计数的 VMM 构建，只数 0x88B5 的帧：

| 目的地址 | 规则 | 网卡收下 | 网卡丢弃 | guest `rx_packets` 增加 |
|---|---|---|---|---|
| 52:54:00:12:34:56（自己） | 精确匹配 RA[0] | 100 | 0 | 100 |
| 02:00:00:00:00:99（别人的单播） | 无 | 0 | 100 | 0 |
| ff:ff:ff:ff:ff:ff | BAM | 100 | 0 | 100 |
| 33:33:00:00:00:01（已加入的组播） | 精确匹配 RA[1] | 100 | 0 | 100 |
| 01:00:5e:7f:00:01（没加入的组播） | MTA 对应位为 0 | 0 | 100 | 0 |
| 打开 promisc 后：别人的单播 | UPE | 100 | 0 | 100 |
| 打开 promisc 后：没加入的组播 | MPE | 100 | 0 | 101 |

最后一行多出来的 1 帧不是注入的，是同一时间段里 host 发出的其他流量。注意 promisc 之后“别人的单播”也计入了 `rx_packets`：驱动只管把网卡交上来的帧数清楚，至于协议栈发现目的地址不是自己、把它当成 `PACKET_OTHERHOST` 丢掉，那是驱动之后的事。

## 三、接收描述符与缓冲

### 3.1 描述符的布局

接收描述符同样是 16 字节，但和发送不同，接收只有一种格式（手册第 3.2.3 节）：

```text
 0               8      10     12     13     14     16
 ├───────────────┼──────┼──────┼──────┼──────┼──────┤
 │ buffer address│length│ csum │status│errors│special│
 └───────────────┴──────┴──────┴──────┴──────┴──────┘
   驱动写           以下都由网卡写回
```

驱动只填前 8 字节的缓冲地址，其余 8 字节由网卡在放好数据后写回：

- **length**：这个缓冲里放了多少字节。
- **status**：DD（bit 0，描述符已处理完）、EOP（bit 1，这是一帧的最后一个缓冲）、IXSM（bit 2，忽略校验和指示）、VP（bit 3，帧带 802.1Q tag 且已被剥掉），以及 TCPCS、IPCS 等校验和结果位。
- **errors**：CRC 错误、符号错误、校验和错误等。
- **special**：剥掉的 VLAN tag 的 TCI。

### 3.2 一帧放在一个缓冲里

缓冲大小由 RCTL 的 BSIZE 和 BSEX 选，256 字节到 16 KiB 共七档（第 13.4.22 节）。帧比一个缓冲长时，网卡接着用下一个描述符，只有最后一个置 EOP，status 和 errors 只在 EOP 那个描述符里有意义。

Linux 的 e1000 在 MTU 不超过 1500 时选 2048 字节缓冲（`e1000_setup_rctl()`），收包函数是 `e1000_clean_rx_irq()`，它不接受跨缓冲的帧：

```c
if (unlikely(!(status & E1000_RXD_STAT_EOP)))
    adapter->discarding = true;

if (adapter->discarding) {
    /* All receives must fit into a single buffer */
    netdev_dbg(netdev, "Receive packet consumed multiple buffers\n");
    dev_kfree_skb(skb);
    if (status & E1000_RXD_STAT_EOP)
        adapter->discarding = false;
    goto next_desc;
}
```

所以在这个配置下，每一帧都恰好占一个描述符。实测下载 64 MiB 的 46564 帧和 20 万个 UDP 小包，都是一帧一个描述符。网卡仍然要按手册支持多描述符，因为 MTU 改大之后 Linux 会换成 `e1000_clean_jumbo_rx_irq()`，那一套按页拼帧。

### 3.3 缓冲里的帧长什么样

TAP 交上来的是不带 FCS 的以太网帧，可能短于 60 字节（ARP 请求只有 42 字节）。真网卡从线上收到的帧至少 64 字节（含 4 字节 FCS），短帧由发送方补齐。`e1000_receive()` 在写进环之前把帧改成“从线上收到的样子”：

```c
    total = (uint32_t)len;
    memcpy(s->rx_frame, frame, len);
    if (total < ETH_ZLEN) {
        memset(s->rx_frame + total, 0, ETH_ZLEN - total);
        total = ETH_ZLEN;
    }
    if (!(rctl & E1000_RCTL_SECRC)) {
        uint32_t fcs = eth_crc32(s->rx_frame, total);

        memcpy(s->rx_frame + total, &fcs, ETH_FCS_LEN);   /* x86 小端 */
        total += ETH_FCS_LEN;
    }
    /* VME 时剥掉 tag，TCI 放进描述符的 special 字段 */
    if (tagged && (*reg(s, E1000_CTRL) & E1000_CTRL_VME)) {
        special = get_be16(s->rx_frame + 14);
        status |= E1000_RXD_STAT_VP;
        memmove(s->rx_frame + 12, s->rx_frame + 16, total - 16);
        total -= VLAN_HLEN;
    }
```

FCS 这 4 字节必须加。RCTL.SECRC=0 的意思是“FCS 留在缓冲里，length 也算上它”，而 Linux 从不置 SECRC，它在 `e1000_clean_rx_irq()` 里无条件地减掉 4 字节：

```c
if (likely(!(netdev->features & NETIF_F_RXFCS)))
    /* adjust length to remove Ethernet CRC, this must be
     * done after the TBI_ACCEPT workaround above
     */
    length -= 4;
```

模型如果只交出 TAP 给的那些字节，每一帧的最后 4 个字节都会被驱动当成 FCS 剪掉。第六章有这个反例的实测。FCS 按 IEEE 802.3 的 CRC-32 真算出来，而不是填 4 个 0：用户用 ethtool 打开 `rx-fcs` 时，看到的是一个能校验通过的 FCS。

VLAN tag 的剥离由 CTRL.VME 控制。Linux 默认打开 `NETIF_F_HW_VLAN_CTAG_RX`，`e1000_vlan_mode()` 因此置 VME，trace 里 CTRL 的写入值是 0x48000249，bit 30 就是 VME。

### 3.4 校验和：始终置 IXSM

82540EM 能在接收时替驱动验证 TCP/UDP 校验和，结果放在 status 的 TCPCS 和 errors 的 TCPE。mini-vmm 没有实现这一项，而是在每个描述符里置 IXSM（“忽略校验和指示”）。Linux 的 `e1000_rx_checksum()` 看到 IXSM 就直接返回，skb 保持 `CHECKSUM_NONE`，由协议栈用软件验证：

```c
/* Ignore Checksum bit is set */
if (unlikely(status & E1000_RXD_STAT_IXSM))
    return;
```

驱动其实打开了接收校验和 offload：trace 里 RXCSUM 寄存器唯一的一次写入是 0x200，即 TUOFL（TCP/UDP Checksum Offload Enable）。打开了却拿到 IXSM，驱动的处理和没打开一样。这样做的代价只是 guest 多算一遍校验和，换来的是 TAP 交来的帧哪怕校验和是错的，也会被 guest 协议栈发现，而不会被一个写错的“已验证”标志放过去。

## 四、写回的顺序

### 4.1 驱动靠 DD 判断一帧到了

驱动从不读 RDH。下载 64 MiB 的整个过程里，RDH 的读次数是 0。它判断哪些描述符已经有数据，靠的是内存里 status 字节的 DD 位，这是手册第 3.2.6 节推荐的做法：

```c
while (rx_desc->status & E1000_RXD_STAT_DD) {
    ...
    dma_rmb(); /* read descriptor and rx_buffer_info after status DD */

    status = rx_desc->status;
    length = le16_to_cpu(rx_desc->length);
    ...
next_desc:
    rx_desc->status = 0;
```

看到 DD 之后才去读 length 和缓冲里的数据，用完把 status 清零，留给下一圈。`dma_rmb()` 保证 CPU 不会把对 length 的读提前到对 status 的读之前。在 x86 上它展开成 `barrier()`，只是不让编译器重排，因为 x86 的读和读之间本来就不会被 CPU 重排。

### 4.2 和发送不同：这里真的并发

P4 第 4.1 节也讲过 DD 要最后写，但发送那边的顺序其实没有人能观察到：TX 在写 TDT 的那个 vCPU 线程上同步做完，guest 的这个 CPU 在 MMIO exit 里停着，等 VMM 把整串描述符处理完才继续执行。

接收不是这样。帧在 I/O 线程上写进环，而 guest 的 NAPI poll 运行在某个 vCPU 线程上，这两个线程在 host 上同时跑。驱动在 poll 里一边处理一边看下一个描述符的 DD，I/O 线程可能正好在写这个描述符。UDP 洪泛实验里，两次 RDT 写入之间网卡最多连续写了 226 帧，这些帧都是在驱动处理前面的帧的同时写进去的。

于是顺序成了正确性问题：只要 DD 比 length 或数据先变得可见，驱动就可能读到旧的 length，或者把上一圈留在缓冲里的旧数据交给协议栈。

### 4.3 实现

`rx_ring_put()` 的写入部分：

```c
    for (i = 0; i < need; i++) {
        uint64_t gpa = base + (uint64_t)head * E1000_DESC_SIZE;
        uint64_t buf;
        uint32_t chunk = 0;
        uint8_t wb[8] = { 0 }, st;

        if (pci_dma_read(&s->pci, gpa, d, 8) != VMM_OK)
            return false;
        buf = get64(d);
        st = E1000_RXD_STAT_DD;
        if (buf) {
            chunk = len - off < bsize ? len - off : bsize;
            if (pci_dma_write(&s->pci, buf, s->rx_frame + off, chunk) != VMM_OK)
                warn_once(s, W_RX_DMA, "e1000: RX buffer gpa=0x%llx len=%u (descriptor %u) not writable",
                          (unsigned long long)buf, chunk, head);
            off += chunk;
            if (off == len)
                st |= status | E1000_RXD_STAT_EOP;
            /* 描述符的 length、csum、errors、special 先写，status 最后写：
             * 驱动看到 DD 才去读其余字段（e1000_clean_rx_irq 里 dma_rmb 之后），
             * 一次 memcpy 写 16 字节不保证 status 最后落地。x86 上存储之间不
             * 重排，函数调用边界也阻止编译器把两次写交换 */
            wb[0] = (uint8_t)chunk;
            wb[1] = (uint8_t)(chunk >> 8);
            if (st & E1000_RXD_STAT_EOP) {
                wb[6] = (uint8_t)special;
                wb[7] = (uint8_t)(special >> 8);
            }
            pci_dma_write(&s->pci, gpa + 8, wb, 4);
            pci_dma_write(&s->pci, gpa + 13, wb + 5, 3);
        }
        pci_dma_write(&s->pci, gpa + 12, &st, 1);
        head = (head + 1) % n;
    }
    *reg(s, E1000_RDH) = head;
```

每个描述符分三次写：先写缓冲里的数据；再写 status 两边的字段（偏移 8–11 的 length 和 csum，偏移 13–15 的 errors 和 special）；最后单独写 status 这一个字节。不能把 16 字节拼好一次 `memcpy` 写下去：`memcpy` 不承诺按地址顺序写，可能先写到 status 那个字节。

为什么在 VMM 里不需要显式的屏障？guest 的内存就是 VMM 进程里 mmap 出来的一块普通内存，I/O 线程往里写，guest 在另一个 CPU 上读，它们之间的可见顺序遵守 host 的内存模型。x86 是 TSO（Total Store Order），一个 CPU 的存储按程序顺序被其他 CPU 看到，所以只要编译器不把两次写交换，CPU 不会打乱它们。`pci_dma_write()` 定义在另一个编译单元里，编译器看不到它的实现，就不能把对它的两次调用交换顺序。这个推理只对 x86 成立；mini-vmm 目前只支持 x86 host（AMD 和海光），如果移植到弱内存序的架构，这里要加 release 语义的存储。

描述符地址和缓冲地址都来自 guest，`pci_dma_read()` / `pci_dma_write()` 先检查 Bus Master，再经 `mem_read()` / `mem_write()` 做 GPA 范围检查（P4 第 4.3 节）。缓冲不可写时只记一条 warn，描述符照样写回，避免环停在一个坏缓冲上。

### 4.4 null 缓冲

缓冲地址为 0 的描述符，网卡不往里放数据，只写回 DD（手册第 3.2.5.2 节）。这是给驱动用来把写回凑满一个 cache line 的手段。上面的代码里 `buf == 0` 时跳过数据和 length，只写 status；容量检查（第五章）里这种描述符不计入可用空间。Linux 的 e1000 不使用这个机制，它只由单元测试覆盖。

## 五、什么时候算环满

### 5.1 头尾指针的约定

接收环的规则和发送环一样（手册第 3.2.6 节）：硬件拥有从 RDH 到 RDT 之前的描述符，即 [RDH, RDT)；RDH 等于 RDT 时硬件手里一个空缓冲都没有。驱动补充缓冲后把 RDT 写成“最后一个有效描述符的下一个”。

按这个约定，一个 n 项的环里硬件最多能拿到 n − 1 个描述符：如果拿到 n 个，RDH 就会追上 RDT，和“一个都没有”无法区分。

### 5.2 Linux 实际交出去多少

`e1000_alloc_rx_buffers()` 填完缓冲后这样写 RDT：

```c
if (likely(rx_ring->next_to_use != i)) {
    rx_ring->next_to_use = i;
    if (unlikely(i-- == 0))
        i = (rx_ring->count - 1);
    ...
    dma_wmb();
    writel(i, hw->hw_addr + rx_ring->rdt);
}
```

`i` 原本是“下一个要填的位置”，写进 RDT 之前先减了 1，RDT 指向的是**最后一个填好的描述符本身**，而不是它的下一个。按 5.1 节的约定，RDT 指向的那个描述符不归硬件，于是它填好了缓冲，却要等下一次补充、RDT 再往前走，才会被硬件用上。

trace 里驱动对 RDT 的前几次写入是：

```text
0x00  0xfe  0xff  0x00  0x01  0x02  0x0f  0x1f  0x2f  0x39 ...
```

第一个 0 来自 `e1000_configure_rx()` 初始化；第二个 0xfe 来自打开接口时第一次填缓冲：`E1000_DESC_UNUSED()` 本身留出一个空位，所以 256 项的环填了 255 个（下标 0–254），RDT 写成 254。这时 RDH=0，硬件可用的是 [0, 254)，共 254 个。所以在 mini-vmm 里，接收环最多有 254 个空闲描述符，不是 255 个。

之后驱动并不是每处理一帧就写一次 RDT。`e1000_clean_rx_irq()` 每回收 16 个（`E1000_RX_BUFFER_WRITE`）补一次，poll 结束时再把剩下的补上。下载 64 MiB 时网卡收了 46564 帧，RDT 只写了 3306 次，平均 14 帧一次。

这两点对设备模型的影响是：空闲描述符的数量只能按 (RDT − RDH) mod n 计算，不能假设驱动会把整个环交出来，也不能假设每帧之后都会有一次 RDT 写入。

### 5.3 设备侧：装得下才动手

`rx_ring_put()` 开头先走一遍，只读不写，确认 [RDH, RDT) 里的空缓冲能装下整帧：

```c
    if (n == 0 || head >= n || tail >= n) {
        if (n)
            warn_once(s, W_RX_RING_INDEX, "e1000: RX ring index out of range (RDH=%u RDT=%u, %u descriptors)",
                      head, tail, n);
        return false;
    }
    /* 第一遍只读描述符，确认容量够装下整帧，避免写了一半才发现不够 */
    for (i = head; i != tail && cap < len; i = (i + 1) % n, need++) {
        if (pci_dma_read(&s->pci, base + (uint64_t)i * E1000_DESC_SIZE, d, 8) != VMM_OK) {
            warn_once(s, W_RX_DMA, "e1000: RX descriptor %u unreadable", i);
            return false;
        }
        if (get64(d))
            cap += bsize;
    }
    if (cap < len) {
        if ((uint64_t)(n - 1) * bsize < len)
            warn_once(s, W_RX_RING_SMALL, "e1000: a %u-byte frame cannot fit the whole RX ring (%u x %u bytes)",
                      len, n - 1, bsize);
        return false;
    }
```

为什么要先数一遍再写，而不是边写边看？假设一帧要 2 个缓冲，环里只剩 1 个。边写边看的做法会先把前一半写进去、置 DD 但不置 EOP，然后发现没地方了：

- 这一帧已经不可能完整交付了，后端如果保留它、等 guest 补缓冲后重试，重试时会从头再写一遍，guest 收到的是一个没有 EOP 的半帧加一个完整帧。Linux 遇到没有 EOP 的描述符会进入 `discarding` 状态，一直丢到下一个 EOP，于是把重试的那个完整帧也丢了。
- 后端如果不保留，就是丢了一帧，而且是在环“还有空间”的时候丢的。

先数一遍，让结果只有两种：整帧写进去，或者一个字节都不写、返回 `NETDEV_RX_FULL`。后者让后端保留这一帧、停止读 TAP，等 guest 写 RDT 时由 `netdev_rx_resume()` 恢复（P2 第六章）。“环满”在这个模型里的准确定义就是：**[RDH, RDT) 里非 null 缓冲的总容量小于这一帧的长度**。

最后那条 warn 处理一种永远装不下的情况：整个环（n − 1 个缓冲）加起来都比这一帧小。这种帧每次重试都会失败，后端会一直停着，所以要留下一条日志说明为什么收包停了。用 Linux 的配置（2048 字节缓冲、最长 1522 字节）不会走到这里。

RDH 和 RDT 的越界检查也在这一步：两者都是 guest 能随便写的寄存器，越界时不收，记一条带三个值的 warn。

### 5.4 RXDMT0：快用完时提醒一声

写完之后，`rx_ring_put()` 计算剩余的空闲描述符，降到阈值以下时除了 RXT0 再置 RXDMT0：

```c
    /* 剩余空闲描述符降到 RDMTS 选定的 1/2、1/4、1/8 以下时提醒驱动补充 */
    avail = (tail + n - head) % n;
    thr = n >> (1 + ((*reg(s, E1000_RCTL) >> E1000_RCTL_RDMTS_SHIFT) & 3));
    raise_icr(s, E1000_ICR_RXT0 | (avail <= thr ? E1000_ICR_RXDMT0 : 0));
```

RDMTS 选阈值占环的几分之一，Linux 用 1/2，256 项的环阈值就是 128。用一个临时加了计数的构建，记录每次写入后剩余的空闲描述符：

| 负载 | 收下的帧 | 写后剩余 0 | 1–128 | 129 以上 | RXDMT0 | 环满（FULL） |
|---|---|---|---|---|---|---|
| 下载 64 MiB（TCP） | 46564 | 0 | 0 | 46564 | 0 | 0 |
| 20 万个 UDP 小包 | 200001 | 5 | 914 | 199082 | 919 | 10 |

TCP 下载时环从没低于一半：TCP 有拥塞控制和接收窗口，发送方不会比接收方快太多。UDP 洪泛没有这种反馈，host 0.9 秒发完 20 万个包，guest 来不及处理，环 10 次被用完，后端 10 次暂停又恢复。guest 的 `rx_packets` 是 200001（20 万个 UDP 加一个 ARP），`rx_dropped` 是 0，一帧没丢。

RXDMT0 在 Linux 里没有专门的处理：`e1000_intr()` 不区分原因，只要 ICR 非 0 就调度 NAPI（P3 第二章）。由于 RXT0 每帧都会置位，RXDMT0 并不会带来额外的中断。

### 5.5 收一帧要几次 exit

P1 第五章算过，驱动为读 128 字节的 EEPROM 触发了一万多次 MMIO exit。数据面的绝对数更大：20 万个 UDP 小包的洪泛期间，e1000 的寄存器访问一共 43497 次。但摊到每一帧上，这个数小得出乎意料。从上面两次运行的 MMIO trace 里截出收包的那一段，按寄存器统计：

| 负载 | 收下的帧 | 寄存器访问 | 每帧 | RDT 写 | ICR 读 | IMC 写 | IMS 写 | STATUS 读 | ITR 写 |
|---|---|---|---|---|---|---|---|---|---|
| 下载 64 MiB | 46564 | 13477 | 0.29 | 3303 | 1497 | 1499 | 1497 | 3379 | 931 |
| UDP 洪泛 | 200001 | 43497 | 0.22 | 14598 | 5565 | 5567 | 5565 | 11515 | 0 |

每一帧不到一次 exit，原因有三：

1. **数据和描述符都不经过 exit。** 网卡往 guest 内存里写数据和写回描述符，是 VMM 的 I/O 线程直接写那块内存；驱动读描述符的 DD、读缓冲里的帧，也只是读自己的内存。这一部分 KVM 完全不参与。
2. **一次中断处理一批帧。** 每次中断，驱动在 `e1000_intr()` 里读 ICR、写 IMC 关中断（后面跟一次 STATUS 读把写刷出去），NAPI poll 处理完再写 IMS 开中断（又跟一次 STATUS 读），需要调整节流时再写一次 ITR。这是每次中断 5 到 6 次 exit，表里 ICR、IMC、IMS 三列几乎相等，STATUS 约是它们的两倍，就是这个原因。下载时平均一次中断处理 31 帧，洪泛时 36 帧。
3. **缓冲按批补充。** 5.2 节说过，驱动每回收 16 个缓冲才写一次 RDT。

对照 P4 第 4.6 节的发送：发送每个包都要写一次 TDT，而写 TDT 的那次 exit 里还要同步做完 DMA 和发送。同样是 exit，接收这边省掉的是“每帧通知一次”：数据到了，网卡靠写内存加一次中断告诉驱动，驱动靠写一次 RDT 交还一批缓冲。这里数的只是落到 VMM 的 MMIO exit；中断注入、guest 写 LAPIC EOI 这些在 KVM 内核里处理的 exit 不在 trace 里，要看它们用 `--exit-stats`（《数清每一次exit》）。

### 6.3 反例

每个反例都是对实现的一处小改动，其余不动，然后看单元测试、端到端测试、以及真实 guest 里的现象。端到端一列里，guest 的命令序列因为前面的步骤卡住而超时时，“驱动探测”那条也会因为拿不到 guest 的退出码而跟着红。

| 改法 | 单元测试 | 端到端（12 条） | 真实 guest 里的现象 | 详见 |
|---|---|---|---|---|
| 读 ICR 不清零 | 3 条红 | 红 | 中断风暴，133 万多次中断，传输失败 | P3 第 4.4 节 |
| TSO 每段不补 TCP 长度 | 4 条红 | 1 条红（`InCsumErrors`） | 哈希一致，上传从 0.69 秒变成 89.5 秒 | P5 第 5.2 节 |
| 发送不写 DD | 2 条红 | 6 条红 | ping 全丢，Tx Unit Hang，看门狗复位 | 本节 |
| 普通校验和 offload 不插 TXSM | 1 条红 | 5 条红（ping 通过） | ping 正常，UDP 和 TCP 全被 host 丢弃 | 本节 |
| 接收不追加 FCS | 2 条红 | 4 条红 | ARP 正常，ping 全丢 | 本节 |
| RDH 不回绕 | 3 条红 | 5 条红（ping 通过） | 收过一圈之后不再收包 | 本节 |
| 不做容量检查 | 1 条红 | **全绿** | 正常流量没有区别，洪泛时悄悄丢帧 | 本节 |

**发送不写 DD。** 把 `tx_process()` 里写回 DD 的那一行删掉，启动 guest 后 `ping -c 5 10.0.2.1`：

```text
5 packets transmitted, 0 packets received, 100% packet loss
[    6.106975] e1000 0000:00:01.0 eth0: Detected Tx Unit Hang
[    6.106975]   TDH                  <1>
[    6.106975]   TDT                  <1>
[    6.106975]   next_to_use          <1>
[    6.106975]   next_to_clean        <0>
[    6.106975] buffer_info[next_to_clean]
[    6.106975]   next_to_watch        <0>
[    6.106975]   next_to_watch.status <0>
[    8.538776] NETDEV WATCHDOG: eth0 (e1000): transmit queue 0 timed out 5696 ms
```

在 host 侧抓包能看到 guest 发出的第一帧（ARP 请求），host 的 ARP 应答也回去了，但 ICMP 请求一个都没出来。dmesg 里 TDH=1、TDT=1，说明网卡确实处理了那个描述符，而驱动的 `next_to_clean` 还停在 0，`status` 是 0。网卡做完了，驱动不知道。

连第二帧都发不出来，原因不在 e1000 驱动，在协议栈的 BQL（Byte Queue Limits，guest 内核开了 `CONFIG_BQL`）。驱动每交出一个包就调用 `netdev_sent_queue()` 记下在途字节数，只有回收时才调用 `netdev_completed_queue()` 减掉。BQL 的初始上限是 0（`dql_reset()` 把 `dql->limit` 清成 0），第一个包交出后可用额度就是负的，`netdev_tx_sent_queue()` 把队列标成 `__QUEUE_STATE_STACK_XOFF`。正常情况下第一次回收会把上限调上来；DD 永远不来，回收就永远不发生，队列也就永远停着。

接下来是两层看门狗：

1. e1000 的 watchdog 每 2 秒设一次 `detect_tx_hung`。下一次 `e1000_clean_tx_irq()` 发现最早未回收的包已经等了超过 `tx_timeout_factor × HZ`（千兆链路下为 1 秒），而 STATUS 又没有报 TXOFF，就打印 “Detected Tx Unit Hang” 并 dump 上面那组指针。
2. 协议栈的 `dev_watchdog` 发现队列停了 5 秒以上（`watchdog_timeo = 5 * HZ`），打印 “transmit queue 0 timed out”，调用 `e1000_tx_timeout()` 调度复位。复位清空发送环，也调用 `netdev_reset_queue()` 重置 BQL，于是又能放出一帧，接着又卡住。抓包里看到的正是这样：之后每隔几秒，guest 发出一个 IPv6 组播侦听报告，也只发出这一个。

DD 是驱动判断“发完”的唯一依据。少了它，帧确实发到了 host，但从 guest 的角度看，网卡卡死了。

**普通校验和 offload 不插 TXSM。** 在 `tx_finish_plain()` 里删掉 TXSM 那一支，TSO 路径不受影响。依次跑 ping、3 个小 UDP 报文、一次 20 秒超时的下载：

| | 正常 | 不插 TXSM |
|---|---|---|
| `ping -c 2` | 0% 丢包 | 0% 丢包 |
| host 收到的 UDP 报文 | 3 | 0 |
| host `Udp: InCsumErrors` | 0 | 3 |
| 下载 64 MiB | 1.35 s，哈希一致 | 20 s 超时，收到 0 字节 |
| host `Tcp: InCsumErrors` | 0 | 9 |
| guest `Tcp: OutSegs / RetransSegs` | 1284 / 0 | 1 / 8 |

ping 不受影响，因为 ICMP 走 legacy 描述符，校验和由软件算好。UDP 小报文是 `CHECKSUM_PARTIAL`，字段里只有伪首部的和，host 校验失败，丢弃并计入 `InCsumErrors`。TCP 连建立都建立不了：SYN 也是 `CHECKSUM_PARTIAL`，被 host 当成坏包丢掉。guest 按超时重传 SYN，Linux 6.6 默认先按固定间隔重传 4 次（`tcp_syn_linear_timeouts = 4`），再指数退避，20 秒里一共发了 1 个 SYN 加 8 次重传，host 侧正好记下 9 个校验和错误。

这个反例和 P5 的 TSO 反例正好相反：这里错的帧让一切停住，一眼就能看出来；P5 那里错的段被 TCP 重传悄悄修好，只有 `InCsumErrors` 能揭穿。

**接收不追加 FCS。** 把第 3.3 节追加 FCS 的那一段去掉：

```text
ARPING 10.0.2.1 from 10.0.2.15 eth0
Unicast reply from 10.0.2.1 [ea:c4:1b:76:ea:04] 0.009ms
Unicast reply from 10.0.2.1 [ea:c4:1b:76:ea:04] 0.015ms
Received 2 response(s) (0 request(s), 0 broadcast(s))
PING 10.0.2.1 (10.0.2.1): 56 data bytes
3 packets transmitted, 0 packets received, 100% packet loss
```

ARP 通，ping 不通。驱动给每一帧减掉 4 字节，减掉的是真正的数据：

- ARP 应答只有 42 字节，模型先补到 60，减掉 4 字节后还剩 56，剪掉的是补齐用的 0，ARP 的 28 字节一个没少。
- ICMP 应答 98 字节（14 字节以太网头 + 84 字节 IP 包），减掉 4 字节后 IP 包只剩 80 字节，比 IP 头里写的总长度 84 短。`ip_rcv_core()` 发现 `skb->len < len`，计入 `InTruncatedPkts` 后丢弃。

guest 里 `Ip: InReceives` 是 3，`InDelivers` 是 0，`IpExt: InTruncatedPkts` 是 3，三个 ICMP 应答都死在这里。端到端测试里 ping、下载、上传、中断四条全红；下载那条 guest 算出的哈希是 `e3b0c442...`，正是空输入的 SHA-256，一个字节都没收到。

**RDH 不回绕。** 把写入循环里的 `head = (head + 1) % n` 改成 `head + 1`（第一遍容量检查里的回绕不动）。ping 只交换几帧，两个方向都通过；开始下载 64 MiB 后，网卡用到环的最后一个描述符，RDH 被写成 256，VMM 的日志里出现：

```text
[WARN] e1000: RX ring index out of range (RDH=256 RDT=249, 256 descriptors)
```

之后每一帧都在 5.3 节的越界检查处返回 FULL，后端停下来等；guest 写 RDT 唤醒后端，重试又是 FULL。下载停在那里直到超时，后面的上传、中断检查也跟着失败，端到端测试 5 条红。越界检查在这里挡住的是：没有它，第一遍循环会从下标 256 开始，读环外面紧跟着的 16 字节当描述符，第二遍再往那里写回，改写的是 guest 里不属于这个环的内存。那条带三个值的 warn 则直接说明了收包为什么停下。

**不做容量检查。** 去掉 5.3 节的 `if (cap < len) ... return false`。这时环满了也不返回 FULL：第二遍循环写 0 个描述符，然后照常返回“收下了”，这一帧就没了。

端到端测试 12 条全绿，因为它只有 TCP 流量，而 5.4 节已经量过，TCP 下载时环从来没满过。换成 UDP 洪泛：

| | 正常 | 不做容量检查 |
|---|---|---|
| host 发出 | 200000 | 200000 |
| guest `rx_packets` | 200001 | 198689 |
| guest `rx_dropped` | 0 | 0 |

1312 帧不见了，guest 里没有任何计数记下这件事，因为在 guest 看来网卡从没收到过它们。这种错误只有单元测试挡得住（“环满与回绕”里的“环满不写”）。

### 6.4 这些验证合起来证明了什么

单元测试按手册逐条检查寄存器和描述符的语义，每条都有能让它变红的改法；端到端测试用未修改的 Linux 驱动和 host 协议栈当裁判，检查的是结果：探测成功、数据逐字节一致、校验和没有错、中断次数对得上。

两者覆盖的东西不同。上面的表里，“TSO 每段不补 TCP 长度”只靠哈希挡不住，要加 `InCsumErrors` 判据；“不做容量检查”端到端完全挡不住，只有单元测试能发现。反过来，单元测试的预期是对手册的理解，理解错了它也会跟着错；端到端测试不依赖这份理解，它只问真驱动和真协议栈满不满意。

## 七、限制

- **接收校验和 offload 没有实现。** 每个描述符置 IXSM，guest 用软件验证（3.4 节）。
- **中断延迟不模拟。** RDTR、RADV、ITR 写入后能读回，但每收一帧都立即置 RXT0（P3 第 3.3 节）。
- **没有片内 FIFO 和接收统计。** 环满时帧留在 TAP 队列里（P2 第六章），所以不会出现 RXO，MPC、RNBC 等统计寄存器读出来都是 0。
- **RXDMT0 按电平而不是按跨越触发。** 手册说空闲描述符数“变得等于”阈值时产生事件；这里每次写入后只要低于阈值就置位。由于每帧都会置 RXT0，这不会多出中断。
- **描述符不预取，也不打包写回。** 手册第 3.2.4 节的片内描述符缓存、第 3.2.5.1 节的 WTHRESH 打包写回都没有模拟，每帧处理完立即写回。
- **VLAN 过滤和剥离只有单元测试。** 端到端测试没有 VLAN 流量。
- **接收在 I/O 线程上逐帧加锁。** 每一帧都要拿一次 `io_lock`，和 vCPU 线程上的寄存器访问互斥（P2 第 5.2 节）。
