到上一篇为止，想知道一台正在运行的 mini-vmm 里发生了什么，只有三种办法：看启动日志；加 `--exit-stats`，等 guest 关机以后读报告；挂上 gdb，但 gdb 一停就是整台机器停下。都回答不了“它现在怎么样”：Arch guest 启动到一半不动了，是 vCPU 在 HLT 里睡着，还是在某个 exit 的处理里转圈？两个 vCPU 各自停在哪个地址？exit 计数还在涨吗？这一篇给 VMM 加一个 monitor：一个 unix socket，guest 照常跑着，从外面连上去敲一行命令，拿回一段文本。

它也是后面几个里程碑的入口：热插拔要有人告诉 VMM “插一块盘”，迁移要有人说“开始”，ACPI 电源按钮要有人去按。这些都会作为新命令挂到 monitor 上，所以这一篇除了几条查询命令，还要把“怎么加命令”定下来。

## 一、协议：沿用 HMP 的命令，补上结束标记

### 1.1 命令名照搬 QEMU

QEMU 有两套 monitor：给人用的 HMP（`info status`、`info cpus`、`info registers`）和给程序用的 QMP（JSON）。mini-vmm 的范围之外写明了不做 JSON 管理 API，理由是它属于生产化，不涉及新的虚拟化机制。剩下的就是一套文本协议，命令名直接用 HMP 的：

```text
help [command]       list commands, or show one command's usage
info [subcommand]    show information about the VM (bare 'info' lists them)
cpu <index>          set the current CPU for info registers
quit                 stop the guest and exit the VMM
info status          VM run state, vCPUs, memory, uptime, resets
info cpus            per-vCPU thread, state and exit counts
info registers [-a]  show the current CPU's registers (-a: all CPUs)
info exit-stats      VM exit counts so far, same report as --exit-stats
```

用过 QEMU 的人不用重新记；`cpu N` 加 `info registers` 这种“先选当前 CPU 再看”的用法也和 HMP 一样，当前 CPU 是每个连接自己的。

### 1.2 HMP 的回复没有边界

HMP 的回复是一段自由文本，后面跟一个 `(qemu) ` 提示符。人看提示符知道输出完了；程序只能去匹配提示符，而提示符可能出现在输出里，错误也只是一行普通文本，分不出成功失败。HMP 在 socket 上还开着行编辑，每敲一个字符都回显一串终端控制码，脚本拿到的是一堆转义序列。

mini-vmm 的 monitor 要同时给人和测试脚本用，所以在 HMP 的命令上加两条规则（`include/monitor.h`）：

- 请求：一行一条命令，按空格和制表符切分，行尾的 `\r` 忽略，空行没有回复。
- 回复：若干正文行，每行以两个空格开头；最后一行是 `OK` 或 `ERR <原因>`，行首没有空格。

读回复的程序只要一直读到第一行“不以空格开头”的行，就知道回复结束了，还同时拿到了成功与否。正文里就算有一行恰好是 `OK`，它也被缩进成 `  OK`，不会被当成结束标记。这一条由单元测试直接检查：一个故意输出 `OK` 和 `ERR ...` 行的测试命令，回复里这两行都必须带缩进。

```text
mon> info cpus
  * CPU #0: thread_id=3357746 state=guest host=S exits=34095 last=IO
    CPU #1: thread_id=3357747 state=guest host=R exits=5338 last=IO
OK
mon> cpu 9
ERR no such CPU 9 (this VM has 2)
```

不做行编辑，人用的时候交给客户端：`socat READLINE UNIX-CONNECT:/tmp/mon.sock` 有历史和光标移动，VMM 这边只收完整的行。

### 1.3 错误只影响那一行、那一个连接

验收要求“未知命令和参数错误返回明确的错误信息，不影响 guest 运行”。错误的种类和处理：

| 输入 | 回复 |
|---|---|
| 未知命令 | `ERR unknown command 'frob' (try 'help')` |
| 未知 info 子命令 | `ERR unknown info command 'frob' (try 'info')` |
| 参数多了或少了 | `ERR info cpus: too many arguments (usage: info cpus)`，用法从注册表生成 |
| 超过 16 个词、行里有 NUL | 各一行 ERR |
| 超过 1024 字节的行 | 整行丢弃到换行为止，只回一次 `ERR line too long (max 1024 bytes)` |
| 客户端不读回复，积压超过 1 MiB | 断开这个连接 |
| 第 5 个连接 | 回一行 `ERR too many monitor clients (max 4)` 后关闭 |

行长上限是为了让一个只发字节不发换行的客户端不能让 VMM 无限制地缓存。超长行最容易写错的是边界和分段：1024 字节的行要照常解析，1025 字节的要丢；超长的行分好几段到达时，前几段只是进入“丢弃到换行”的状态，到换行那一刻才回一次 ERR，紧跟着的下一行照常执行。这几种情形单元测试都逐字节喂了一遍。

## 二、线程模型：命令跑在 I/O 线程上

### 2.1 没有锁的注册表

monitor 不新开线程。监听 socket 和每个客户端连接都注册到第 14 篇的 event loop 上，命令处理函数在 I/O 线程里执行：

```text
                      I/O 线程（event loop）
  ┌──────────────────────────────────────────────────────┐
  │ listen fd ── accept ──> conns[4]                     │
  │ conn fd  ── read ──> 拼行 ──> 查表 ──> 处理函数 ──> out 缓冲 ── send │
  │ wake eventfd ── 异步请求完成 ──> finish ──> out 缓冲 │
  └──────────────────────────────────────────────────────┘
```

命令表在 `evl_start` 之前由主线程填好（`monitor_register()`），之后只有 I/O 线程读，所以不需要锁。命令分两张表：顶层命令，以及 `info` 下的子命令，和 HMP 一样两张表是独立的命名空间。`help` 和 `info` 本身由协议核心注册，列表从表里生成，后面的里程碑在自己的模块里调 `monitor_register()` 加命令，不用改 `monitor.c`。

socket 都是非阻塞的。I/O 线程同时负责串口输出、网卡收包、磁盘完成，它在任何一个 monitor 客户端上阻塞，guest 的串口就跟着停住。所以写回复时只写 socket 缓冲区收得下的部分，剩下的留在 `out` 里，登记 `EPOLLOUT` 等下一次可写。

### 2.2 读别人线程上的数据

处理函数在 I/O 线程上，要读的数据大多由 vCPU 线程在写。逐项看读法：

- **exit 计数**（`vcpu->exits[]`）：只有本 vCPU 线程写。以前它只在 VM 停下、线程 join 之后才读，现在 monitor 随时读。一个 64 位的值在 x86-64 上对齐访问本来就不会撕裂，但 C 标准里两个线程无同步地读写同一变量是数据竞争，编译器有权假设它不会发生（比如把计数留在寄存器里，循环结束才写回）。所以读写都改成 relaxed 原子操作。写的一侧只有一个写者，不需要原子的读改写：`__atomic_load_n` 加一再 `__atomic_store_n`，在 x86 上编译出来就是普通的 load 和 store，不带 `lock` 前缀，exit 路径不因此变慢。代价是各格之间不是同一时刻的快照，运行中拿到的报告里分项之和可能和 total 差几次 exit。
- **vCPU 状态**（guest / vmm / paused / stopped）和最近一次 exit 原因：同样是单写者的 relaxed 原子量，进出 `KVM_RUN`、gdbstub 暂停时更新。
- **设备计数**（第 15 篇的按设备统计）：exit 分发路径持 `io_lock` 更新，报告生成时也持 `io_lock`，加锁顺序和 event loop 的约定一致。
- **寄存器**：不能直接读，见第三节。
- **KVM 自己的计数器**：读法没变，打开的时机变了，见第四节。

`info cpus` 的 `host=` 列取自 `/proc/self/task/<tid>/stat` 的第 3 个字段，是 host 调度器眼里这个线程的状态。guest 执行 HLT 时，vCPU 线程在 KVM 内部睡眠，显示 `S`；guest 里有进程在空转，对应的 vCPU 线程一直可运行，显示 `R`。上面那段输出就是 guest 把一个空转循环绑到 CPU 1 之后拍下的：CPU 0 空闲是 `S`，CPU 1 是 `R`。`state=guest` 只说明线程在 `KVM_RUN` 里，分不出它是在执行 guest 指令还是在 KVM 里睡 HLT，两列合起来才完整。

## 三、`info registers`：让 vCPU 自己去读

### 3.1 为什么不能在 I/O 线程上直接调 `KVM_GET_REGS`

读寄存器就是对 vCPU fd 调 `KVM_GET_REGS` 和 `KVM_GET_SREGS`。问题在 KVM 的 vCPU ioctl 入口 `kvm_vcpu_ioctl()`（`virt/kvm/kvm_main.c`）：除了极少数异步 ioctl，进来第一件事就是 `mutex_lock_killable(&vcpu->mutex)`。`KVM_RUN` 也是一个 vCPU ioctl，它在 guest 运行的整个期间都占着这把锁，guest 执行 HLT、vCPU 在 KVM 内部睡眠时也不放。I/O 线程去调 `KVM_GET_REGS`，就要等到这个 vCPU 下一次回到用户态；一个空闲的 vCPU 可能在 HLT 里睡上好几秒。等待期间 I/O 线程什么都干不了。

gdbstub 没有这个问题，因为它读寄存器之前先让所有 vCPU 停在 `park_locked()` 里，那时没有人在 `KVM_RUN` 中。monitor 的要求相反：只看一眼，不能让整台机器停下。

### 3.2 run_on_cpu：把读寄存器这件事交给 vCPU 线程

QEMU 的做法叫 `run_on_cpu`：把一个函数交给目标 vCPU 的线程执行。mini-vmm 在 `include/smp.h` 里加了同样的机制：

```c
struct vcpu_work {
    void (*fn)(struct vmm_vcpu *v, struct vcpu_work *w);
    struct vcpu_work *next;
};
int  vcpu_queue_work(struct vmm_vcpu *v, struct vcpu_work *w);
```

`vcpu_queue_work()` 把工作挂进这个 vCPU 的队列，然后“踢”它一下。踢的方法和停机完全一样：先把 `kvm_run->immediate_exit` 置 1，再发 SIGUSR1。已经在 `KVM_RUN` 里的 vCPU 被信号打断，`KVM_RUN` 返回 `EINTR`；还没进去的，进去时看到 `immediate_exit` 就立刻返回 `EINTR`。vCPU 线程在 `EINTR` 之后执行队列里的工作，然后回到 guest。

这里有两个问题要想清楚。

**寄存器此刻一致吗？** vCPU 可能刚因为一次 PIO 退出到用户态，处理完正要回 guest，这时被踢。`kvm_arch_vcpu_ioctl_run()`（`arch/x86/kvm/x86.c`）的顺序是先调 `complete_userspace_io` 把上一次 PIO/MMIO 的结果写回（`in` 指令的目的寄存器、推进 rip），然后才检查 `immediate_exit`。所以 `EINTR` 返回时指令已经完整执行完，读到的是一个干净的指令边界。被踢出 HLT 的 vCPU 回到 `KVM_RUN` 后继续 HLT，guest 察觉不到。

**会不会踢了也没用？** vCPU 被踢出来以后要把 `immediate_exit` 清掉，否则它再也进不了 guest。清零和看队列的先后决定了会不会丢一次踢：

```text
错误的顺序：先看队列，再清 immediate_exit

  vCPU 线程                          I/O 线程
  KVM_RUN 返回 EINTR
  看队列：空的
                                     挂上工作
                                     immediate_exit = 1
                                     pthread_kill（vCPU 在用户态，handler 空转）
  immediate_exit = 0   <── 把刚才那次踢抹掉了
  KVM_RUN：进 guest，HLT 里睡下      工作没人做，客户端等到下一个中断
```

`vm.c` 的运行循环是先清零、再看队列，两边都用 seq_cst 原子操作。踢的一方是“先挂工作、再置 1”，所以 vCPU 的清零要么早于对方置 1（置位留下来，下一次 `KVM_RUN` 立刻返回），要么晚于它（那么清零之后再看队列，一定看得到工作）。这条推导写在 `src/smp.c` 的 `vcpu_kick()` 旁。停机时 `immediate_exit` 不能清，正在退出的线程不能再睡回 `KVM_RUN`，所以只在 `should_stop` 为假时清。

### 3.3 异步回复

工作在 vCPU 线程上执行，回复却要由 I/O 线程写回 socket。所以命令处理函数可以返回 `MON_PENDING`，表示“回复稍后给”：

```text
I/O 线程                         vCPU 0 线程           vCPU 1 线程
info registers -a
  job.remaining = 2 + 1
  queue_work(vCPU 0) ──kick──>  EINTR
  queue_work(vCPU 1) ──kick────────────────────────>   EINTR
  put(job)  remaining=2         print_state 到 part0
  return MON_PENDING            put(job) remaining=1
                                                       print_state 到 part1
                                                       put(job) remaining=0
                                                       mon_req_post(req)
                                                         └─ 挂 done 链表，写 wake eventfd
wake eventfd 可读
  finish：按 vCPU 顺序拼 part0、part1，写进 out
  继续处理这个连接缓存着的下一行
```

`remaining` 的初值比目标 vCPU 数多 1，多出的那一份属于处理函数自己：处理函数还在一个个排队的时候，前面的工作可能已经执行完了，没有这一份，计数会在排完之前就归零，post 出去的请求被 finish 释放，处理函数接着访问的就是已释放的内存。

同一个连接在异步命令完成之前不再执行后面的命令：monitor 不再登记这个 fd 的 `EPOLLIN`，新请求留在内核的 socket 缓冲里。回复顺序因此总是和请求顺序一致，VMM 这边缓存的输入也有上限。连接在等待期间断开时，请求被标记为孤儿，完成后照样调 finish 释放资源，回复丢弃。

**队列的保证是“被接受的工作恰好执行一次”。** vCPU 线程退出（poweroff、复位、出错）时，先关队列，再把剩下的工作执行完；关了之后 `vcpu_queue_work()` 返回错误，命令回 `ERR CPU 1 is not running`。反过来先执行再关，中间排进来的工作就永远没人执行，那个客户端永远等不到回复。被 gdb 暂停的 vCPU 不在 `KVM_RUN` 里，也不看队列，工作等到 gdb 放行或 VM 结束时执行。

## 四、`info exit-stats`：KVM 统计 fd 要提前打开

第 15 篇的报告有一段是 KVM 自己的计数器，来自 `KVM_GET_STATS_FD` 返回的 fd。原来的代码在 VM 停下之后才打开这个 fd，读完关掉。monitor 要在运行中生成同一份报告，直接照搬就会撞上 3.1 节的锁：`KVM_GET_STATS_FD` 也是一个 vCPU ioctl，要拿 `vcpu->mutex`。

把这个 fd 拿到之后，读它走的是 `kvm_vcpu_stats_read()`，它不拿 `vcpu->mutex`，计数器本身是各自更新的 `u64`。所以只要换个时机：在创建 vCPU 时、vCPU 线程启动之前打开，一直开到 `vm_destroy`。之后任何时候读都不会阻塞。只有用了 `--exit-stats` 或 `--monitor` 时才打开，host 内核早于 5.14 时打不开，报告里写明原因。

这个推导有一个直接的对照：把“查询时才打开”放回去（`tests/mutants/monitor.py` 的 `stats-fd-opened-while-running`），e2e 里的客户端 10 秒等不到 `info exit-stats` 的回复；之后连 guest 的 shell 提示符都不再出现。卡住的是 I/O 线程，它在 ioctl 里等一个睡在 HLT 里的 vCPU 放锁，串口输出也是它负责的。

## 五、`quit` 和复位撞在一起

`quit` 做两件事：置 `vm->quit_requested`，然后 `vm_request_stop()`。vCPU 线程全部退出，`vm_run()` 返回，main 走正常的退出路径：停 I/O 线程、关 monitor（删除 socket 文件）、退出码 0。被 `quit` 停下时不打印 vCPU 现场，那是给出错停机用的。

麻烦在第 31 篇的复位循环。guest 请求复位时，main 的循环是“`vm_run` 返回，看到 `reset_requested`，调 `vm_reset`，再 `vm_run`”，而 `vm_reset` 会把每个 vCPU 的 `should_stop` 清回 false。如果 `quit` 恰好落在 guest 重启的那一刻，它设的 `should_stop` 会被这次清零抹掉，VMM 复位后接着跑，`quit` 等于没发。所以 `quit` 另外记一个永不清零的 `quit_requested`，复位循环在复位前、复位后各看一次。

## 六、socket 文件

- 路径上已经有一个 socket 文件时，删掉重建，它是上一次没有正常退出留下的；有一个普通文件时拒绝启动，不删用户的文件。
- 超过 `sun_path` 的 107 字节上限时启动前报错。
- `bind` 前把 umask 临时设成 0077，socket 只对当前用户可读写：monitor 能读 guest 寄存器、能让 VMM 退出。umask 是进程级的，这时还在单线程的启动阶段，临时改动影响不到别的线程。
- `printf 'info status\n' | nc -U` 这种写完就关写端的用法：monitor 看到 EOF 后不马上关连接，已收到的命令执行完、回复发完再关。

## 七、验证

**单元测试** `monitor_test` 不建 socket，直接往连接层喂字节、读输出缓冲，53 个检查覆盖第一节的协议规则：缩进与结束标记、拆包与 CRLF、各类错误、超长行的边界、help 由注册表生成、异步命令期间后续请求等待、连接断开后的孤儿请求、每个连接各自的当前 CPU、回复积压上限。

**e2e** `make test monitor`，5 条用例：

| 用例 | 判据 |
|---|---|
| 路径上是普通文件 | 退出码 1，报 `exists and is not a socket`，文件还在 |
| 路径过长 | 退出码 1，报 `max 107 bytes` |
| 上次留下的 socket | 照常启动，退出后 socket 文件被删除 |
| 2 vCPU guest 运行中查询 | 见下 |
| `quit` | 客户端看到连接被关闭，VMM 退出码 0，没有 vCPU 现场，socket 文件删除 |

第四条在 BusyBox guest 的 shell 提示符处，由 `tests/monitor_client.py` 从 host 连进去：

- `info cpus` 的每个 `thread_id` 在 `/proc/<pid>/task/<tid>/comm` 里必须是对应的 `vcpuN`（vCPU 线程的名字），不是只看格式；空闲时有 vCPU 显示 `host=S`。
- `info registers -a` 里每个 vCPU 的 rip 必须落在 vmlinux 的 `_stext` 到 `_etext` 之间，CR0.PG 和 EFER.LMA 置位。停在提示符时所有 vCPU 都在内核的 idle 循环里，这说明读到的是 64 位内核运行中的真实状态，而不是上电复位值。连读 200 次全部 `OK`。
- guest 打印一行前后各取一次 `info exit-stats`，总数必须增长：读的是运行中的实时计数。
- guest 把空转进程绑到 CPU 1 后，vCPU 1 显示 `host=R`；这时再连读 100 次寄存器，每次都把一个在 guest 里全速运行的 vCPU 踢出来再放回去，全部 `OK`。
- 各种错误输入、5000 字节的行、只发半行就断开、第 5 个连接被拒之后，guest 还能回显 `still-alive-42`，最后正常关机。

**对照** `tests/mutate.py monitor` 有 13 个错误实现，全部让测试变红。协议的 7 个由单元测试挡住（不缩进正文、行长差一、超长行丢弃不结束、不等异步命令、断开时不标孤儿、保留 `\r`、错误原因里的换行不压平）；6 个只有真实 vCPU 线程才看得出来，由 e2e 挡住：被踢出后不执行工作、不清 `immediate_exit`、thread_id 写成 pid、host 状态写死、查询时才打开统计 fd、`quit` 不停机。

## 八、限制

- **3.2 节和 3.3 节的两处顺序要求没有测试能挡住。** 先清零再看队列、先关队列再执行剩余工作，错了的后果都要求一个请求恰好落进几条指令宽的窗口，e2e 无法稳定制造。它们的正确性来自推导，写在 `src/smp.c` 对应的函数旁。`quit` 撞上复位同理。
- **运行中的 exit 计数不是同一时刻的快照。** 见 2.2 节。
- **只有查询和退出。** 暂停、继续、热插拔、迁移这些命令由后面的里程碑各自加。暂停（HMP 的 `stop`/`cont`）需要和 gdbstub 的暂停协调，两者都想控制 vCPU 是否运行，到时要先定谁说了算。

## 附录 B：延伸阅读

- QEMU 的 QMP（`docs/interop/qmp-spec.rst`）：同样是 socket 上的命令，它用 JSON 解决了本篇 1.2 节的回复边界问题，还多了异步事件（guest 关机、设备弹出时主动推送给客户端）。热插拔、迁移这类“命令发出去，结果过一会儿才有”的操作，在 mini-vmm 里也会遇到同样的需求。
- QEMU 的 `async_run_on_cpu` 与 `run_on_cpu`：前者不等结果，后者在调用线程上等，等待期间放开 BQL。mini-vmm 的 I/O 线程不能等，所以只有异步一种，结果经 eventfd 回到 I/O 线程。
