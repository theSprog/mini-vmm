文中的“阶段 N”指《中断·实现篇》第一章的开机十阶段表。

## 一、阶段 4 与阶段 9：多个 vCPU

《多核·原理篇》第一章讲过：AP 的唤醒完全由 KVM 的内核态 LAPIC 完成，VMM 的职责只有三件事——**线程、CPUID、固件表**。固件表在《固件与启动协议·实现篇》讲完了，本文讲前两件，外加一个多线程程序绕不开的问题：怎么让所有线程可靠地停下来。

所有代码集中在 `src/smp.c`（不到 200 行）和 `vm.c` 的 run loop 里。文件头的注释就是这一章的提纲：

```c
/* src/smp.c — 多 vCPU 线程、CPUID 拓扑、停机协调
 *
 * AP 启动流程里 VMM 不需要做任何事情：
 *   - 内核态 irqchip 存在时，KVM 在 KVM_CREATE_VCPU 里把 vcpu 0 设为
 *     RUNNABLE（BSP），其余 vCPU 设为 KVM_MP_STATE_UNINITIALIZED；
 *   - AP 线程调用 KVM_RUN 后阻塞在 KVM 内部，直到 BSP 通过 LAPIC ICR
 *     发出 INIT + SIPI。KVM 收到 SIPI 后把 AP 置成实模式、
 *     CS:IP = (vector << 8):0，AP 从 Linux 放在低 1MiB 的 trampoline 起跑。
 * 所以 VMM 的职责只有线程、CPUID 和固件表（MADT/MP table）三件事。
 */
```

### 1.1 阶段 4：创建 N 个 vCPU

`--smp N` 选项把核数写进 `cfg.nr_vcpus`，取值 1 到 32（`VMM_MAX_VCPUS`）。`vm_create()` 检查它不超过 `KVM_CAP_MAX_VCPUS`（我们的 host 是 1024），然后在阶段 3 之后循环创建：

```c
    for (i = 0; i < cfg->nr_vcpus; i++) {
        r = vm_create_vcpu(vm, i);
        ...
    }
```

每个 vCPU 的创建过程与《一次 out 指令的完整旅程》相同：`KVM_CREATE_VCPU` 拿到 fd，`mmap` 它的 `kvm_run` 页，然后调用厂商后端的 `init_vcpu`（设置 CPUID）。`KVM_CREATE_VCPU` 的参数就是 vCPU 的 ID，KVM 用它作为 LAPIC 的 APIC ID，也用它判断谁是 BSP（`vcpu_id == 0`）。所以 **vCPU 的 ID 必须从 0 开始连续编号**，与固件表里的 APIC ID 一一对应。

参数检查里有一条规则值得注意：

```c
    /* 裸 payload 不会去唤醒 AP，而且没有内核态 irqchip 时
     * 所有 vCPU 一创建就是 RUNNABLE，会从同一个入口同时跑起来 */
    if (cfg->mode != VMM_BOOT_LINUX && cfg->nr_vcpus > 1) {
        vmm_err("--smp > 1 requires --mode linux");
        return VMM_ERR_INVAL;
    }
```

这就是《多核·原理篇》1.4 节那段 `kvm_arch_vcpu_create()` 源码在用户态的体现。

#### 1.1.1 一个初始化顺序的陷阱

`vm_create_vcpu()` 的末尾有一行：

```c
    if (id + 1 > vm->nr_vcpus)
        vm->nr_vcpus = id + 1;
```

`vm->nr_vcpus` 是随着 vCPU 逐个创建而递增的，而 `init_vcpu` 是在这一行**之前**被调用的。所以在创建 0 号 vCPU、设置它的 CPUID 时，`vm->nr_vcpus` 还是 0；创建 1 号时是 1……如果 CPUID 改写代码用 `vm->nr_vcpus` 作为“总核数”，每个 vCPU 看到的核数都不一样，而且都是错的。

正确的做法是用配置里的最终值 `vm->cfg.nr_vcpus`。这类“某个字段在初始化过程中还不是最终值”的陷阱在任何分阶段初始化的系统里都很常见，读代码时要留意每个变量在每个时刻的含义。

### 1.2 CPUID：只改拓扑，其余透传

AMD/海光后端的 `init_vcpu` 很简单：取 host 支持的 CPUID，改写拓扑，设进去：

```c
static int amd_init_vcpu(struct vmm_vcpu *vcpu)
{
    struct kvm_cpuid2 *cpuid = NULL;
    int r;

    r = kvm_get_supported_cpuid(vcpu->vm->kvm_fd, &cpuid);
    ...
    smp_fixup_cpuid(vcpu, cpuid);
    r = kvm_set_cpuid2(vcpu->fd, cpuid);
    free(cpuid);
    ...
}
```

`KVM_GET_SUPPORTED_CPUID` 需要调用者预先分配一个足够大的数组，太小会返回 `E2BIG`。mini-vmm 从 128 项开始，每次失败翻倍重试。

为什么要透传 host 的 CPUID，而不是自己构造一份？因为 guest 内核启动的第一件事就是执行 `CPUID`，检查长模式、SSE、APIC、NX 等一大堆特性。自己构造一份完整的 CPUID 工作量很大，而且容易漏掉某个关键位导致 guest 拒绝启动。透传 KVM 认可的 host 特性是 kvmtool、Firecracker 的共同做法，代价是 guest 看到的 CPU 型号与 host 相同（真实日志里 guest 的 `/proc/cpuinfo` 显示 `vendor_id: HygonGenuine`）。

但透传的拓扑字段是 host 的原始值，必须改写。`smp_fixup_cpuid()` 按《多核·原理篇》1.6 节的表逐个 leaf 处理，拓扑固定为“1 个 socket × N 个核 × 每核 1 个线程”，APIC ID 等于 vCPU ID：

```c
void smp_fixup_cpuid(const struct vmm_vcpu *vcpu, struct kvm_cpuid2 *cpuid)
{
    uint32_t id = (uint32_t)vcpu->id;
    uint32_t n  = (uint32_t)vcpu->vm->cfg.nr_vcpus;   /* 注意：cfg 里的最终值 */
    ...
        switch (e->function) {
        case 0x1:
            e->ebx = (e->ebx & 0x0000ffffu) | (id << 24) |
                     ((n > 255 ? 255 : n) << 16);
            if (n > 1)
                e->edx |= CPUID_1_EDX_HTT;
            else
                e->edx &= ~CPUID_1_EDX_HTT;
            break;
        case 0xb:
        case 0x1f:
            e->eax = e->ebx = e->ecx = e->edx = 0;
            break;
        case 0x80000008:
            e->ecx = (e->ecx & ~0xf0ffu) | (order_base2(n) << 12) | (n - 1);
            break;
        case 0x8000001d: {
            uint32_t level = (e->eax >> 5) & 0x7;
            uint32_t share = (level >= 3) ? n - 1 : 0;

            if (e->eax & 0x1f)          /* cache type = 0 表示列表结束 */
                e->eax = (e->eax & ~(0xfffu << 14)) | (share << 14);
            break;
        }
        case 0x8000001e:
            e->eax = id;
            e->ebx = id & 0xff;
            e->ecx = 0;
            break;
        }
    ...
}
```

逐个 leaf 说明改了什么、为什么：

| Leaf | 改写 | 为什么 |
|---|---|---|
| `0x1` EBX[31:24] | = vCPU ID | “初始 APIC ID”，三方一致的 CPUID 一方 |
| `0x1` EBX[23:16] | = N | 本 package 的逻辑处理器数 |
| `0x1` EDX[28] HTT | N > 1 时置 1 | 表示上面的逻辑处理器数字段有效。这一位的名字叫“超线程”，但语义其实是“一个 package 里有多个逻辑处理器” |
| `0xB` / `0x1F` | 全部清零 | Intel 风格的扩展拓扑。KVM 在这台 host 上只返回了 subleaf 0，要正确描述需要补全多个 subleaf、扩容数组；清零表示“不提供”，guest 退回 AMD 风格的路径 |
| `0x80000008` ECX[7:0] | = N − 1 | AMD 的“核数减一” |
| `0x80000008` ECX[15:12] | = ⌈log₂N⌉ | APIC ID 里核编号占几位，guest 用它从 APIC ID 里切出核 ID |
| `0x8000001D` EAX[25:14] | L1/L2 为 0，L3 为 N − 1 | 每级缓存的共享者数量减一：L1/L2 每核私有，L3 所有核共享 |
| `0x8000001E` EAX | = vCPU ID | 扩展 APIC ID |
| `0x8000001E` EBX[7:0] | = vCPU ID | 核 ID。EBX[15:8]（每核线程数减一）清为 0，即每核 1 个线程 |
| `0x8000001E` ECX | = 0 | 节点 ID 为 0，单节点 |

`0x8000001D` 的循环里有一个细节：这个 leaf 有多个 subleaf，每个描述一级缓存，最后一个的缓存类型字段（EAX[4:0]）为 0 表示列表结束，不能改写它。

为什么重点在 AMD 的 leaf？因为我们的 guest 是海光 CPU。Linux 对海光 CPU 的拓扑解析在 `arch/x86/kernel/cpu/hygon.c`：

```c
static void hygon_get_topology(struct cpuinfo_x86 *c)
{
    int cpu = smp_processor_id();

    /* get information required for multi-node processors */
    if (boot_cpu_has(X86_FEATURE_TOPOEXT)) {
        ...
        cpuid(0x8000001e, &eax, &ebx, &ecx, &edx);

        c->cpu_die_id  = ecx & 0xff;
        c->cpu_core_id = ebx & 0xff;
        ...
        /*
         * In case leaf B is available, use it to derive
         * topology information.
         */
        err = detect_extended_topology(c);
        ...
```

有 TOPOEXT 特性时，核 ID 取自 `0x8000001E` 的 EBX[7:0]，节点 ID 取自 ECX[7:0]；如果 `0xB` 可用，还会进一步用它推导拓扑。把 `0xB` 清零，就是让这一步失败，只用 `0x8000001E` 的结果。

改写的效果可以在 guest 里验证。真实日志中 guest 的 `/proc/cpuinfo` 和 sysfs：

```
processor   : 0
physical id : 0
siblings    : 4
core id     : 0
cpu cores   : 4
apicid      : 0
initial apicid  : 0
...
[guest /]# cat /sys/devices/system/cpu/cpu2/topology/core_id /sys/devices/system/cpu/cpu2/topology/physical_package_id
2
0
```

4 个逻辑处理器（`siblings`）、4 个核（`cpu cores`）、每核 1 个线程；2 号 CPU 的核 ID 是 2、package ID 是 0。mini-vmm 的测试脚本还在 guest 里检查了每颗 CPU 的 APIC ID、核 ID、L2 和 L3 的共享 CPU 列表，断言 L2 每核私有（`L2-1`）、L3 由 0 到 3 号 CPU 共享（`L3-0-3`）。

### 1.3 阶段 9：每个 vCPU 一个线程

`vm_run()` 是阶段 9 的全部：

```c
int vm_run(struct vmm_vm *vm)
{
    struct sigaction sa;
    int i, started = 0, r = VMM_OK;

    /* 不带 SA_RESTART，保证 KVM_RUN 返回 EINTR */
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = kick_handler;          /* 空函数 */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);

    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        if (pthread_create(&v->thread, NULL, vcpu_thread, v) != 0) {
            r = VMM_ERR_SYS;
            vm_request_stop(vm);
            break;
        }
        __atomic_store_n(&v->thread_started, true, __ATOMIC_RELEASE);
        started++;
    }

    for (i = 0; i < started; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        pthread_join(v->thread, NULL);
        __atomic_store_n(&v->thread_started, false, __ATOMIC_RELEASE);
        if (r == VMM_OK && v->result != VMM_OK)
            r = v->result;
    }
    return r;
}
```

主线程为每个 vCPU 创建一个线程，然后等所有线程结束，返回第一个出错的 vCPU 的错误码。每个 vCPU 线程做的事情非常简单：

```c
static void *vcpu_thread(void *arg)
{
    struct vmm_vcpu *v = arg;
    char name[16];

    snprintf(name, sizeof(name), "vcpu%d", v->id);
    pthread_setname_np(pthread_self(), name);    /* host 上 top -H 能看到 vcpu0..3 */

    v->result = vcpu_run_loop(v);
    ...
    /* 任何一个 vCPU 退出（poweroff、reset、出错）都意味着整机停下 */
    vm_request_stop(v->vm);
    return NULL;
}
```

给线程命名是一个小但很有用的细节：在 host 上用 `top -H -p <vmm 的 pid>` 就能直接看到每个 vCPU 的 CPU 占用，判断 guest 里的负载是否真的分散到了多个核上，也能看出哪个 vCPU 卡住了。实测 guest 里跑 4 个死循环时，host 上 `vcpu0` 到 `vcpu3` 各占接近 100%；用 `--append maxcpus=1` 启动时，AP 线程的 CPU 时间是 0，证明它们确实一直睡在 KVM 里等待一个永远不来的 SIPI。

注意所有 vCPU 线程是**同时**启动的，包括 AP。AP 线程启动后立刻进入 `KVM_RUN`，因为 `mp_state` 是 UNINITIALIZED 而在 KVM 里阻塞，不占 CPU。VMM 不需要知道 guest 什么时候会唤醒 AP。

### 1.4 run loop 的两处修改

多核之后，`vcpu_run_loop()` 必须正确处理两种“没有退出事件、只需要重进 `KVM_RUN`”的返回：

```c
int kvm_run(int vcpu_fd)
{
    int r;

    /* 两种“没有 exit 可处理、重进 KVM_RUN 即可”的返回：
     *   EINTR   vm_request_stop() 用 immediate_exit + SIGUSR1 把 vCPU
     *           踢出来（Ctrl-A x、另一个 vCPU 触发了停机）
     *   EAGAIN  AP 处于 KVM_MP_STATE_UNINITIALIZED 时 KVM_RUN 阻塞到
     *           收到 INIT/SIPI，醒来后返回 -EAGAIN 而不是进 guest，
     *           见 host arch/x86/kvm/x86.c kvm_arch_vcpu_ioctl_run()
     * 两者都不写（或不保证写）exit_reason，单独返回 VMM_ERR_INTR，
     * 让 run loop 回去检查 should_stop 后重进。 */
    r = ioctl(vcpu_fd, KVM_RUN, 0);
    if (r < 0 && (errno == EINTR || errno == EAGAIN))
        return VMM_ERR_INTR;
    ...
}

int vcpu_run_loop(struct vmm_vcpu *vcpu)
{
    int r;

    while (!vcpu->should_stop) {
        r = kvm_run(vcpu->fd);
        /* 被打断时 kvm_run 页里的 exit_reason 不一定有效（immediate_exit
         * 路径下 KVM 不会改写它，还是上一次的值），不能交给
         * vcpu_handle_exit，否则会把上一次的 IO 再执行一遍 */
        if (r == VMM_ERR_INTR)
            continue;
        if (r != VMM_OK)
            return r;

        r = vcpu_handle_exit(vcpu);
        if (r == VMM_ERR_EXIT)
            return VMM_OK;      /* 正常停机 */
        if (r != VMM_OK)
            return r;
    }
    return VMM_OK;
}
```

**`EAGAIN`**：AP 收到 INIT 后 `KVM_RUN` 以 `-EAGAIN` 返回（《多核·原理篇》1.4 节）。单核时代的 run loop 把所有负返回值都当错误，于是 AP 一醒来，它的线程就报错退出，并触发整机停机。这个问题是在读 host 源码时预先发现的：在写 SMP 代码之前，先把 `kvm_arch_vcpu_ioctl_run()` 读了一遍，看到了 `r = -EAGAIN` 这一行。

**不分发 `exit_reason`**：`EINTR` 和 `EAGAIN` 返回时，`kvm_run->exit_reason` 不保证被更新。原来的代码在 `EINTR` 时也会调用 `vcpu_handle_exit()`，而 `exit_reason` 里还是上一次的 `KVM_EXIT_IO`，于是上一次的 I/O 被重复执行了一遍：串口多输出一个字符，或者更糟，某个有副作用的寄存器写入被执行两次。所以被打断时直接 `continue`，回到循环顶部检查 `should_stop`。

### 1.5 停机：`immediate_exit` + 信号

《多核·原理篇》1.8 节讲了停机的竞态。mini-vmm 的实现是 `vm_request_stop()`，它可以在任何线程里调用，而且可以重复调用：

```c
void vm_request_stop(struct vmm_vm *vm)
{
    int i;

    vm->running = false;
    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        v->should_stop = true;
        if (v->run)
            __atomic_store_n(&v->run->immediate_exit, 1, __ATOMIC_SEQ_CST);
        if (__atomic_load_n(&v->thread_started, __ATOMIC_ACQUIRE) &&
            !pthread_equal(v->thread, pthread_self()))
            pthread_kill(v->thread, SIGUSR1);
    }
}
```

对每个 vCPU 做三件事，顺序很重要：

1. **置 `should_stop`**：run loop 在循环顶部检查它。
2. **置 `immediate_exit = 1`**：它在 `kvm_run` 共享页里，KVM 在 `KVM_RUN` 的入口检查它。线程如果刚检查完 `should_stop`、还没进入 `KVM_RUN`，进去之后会立刻以 `-EINTR` 返回。
3. **发 SIGUSR1**：线程如果已经在 `KVM_RUN` 里（比如睡在 guest 的 HLT 里），信号让它以 `-EINTR` 返回。

三者覆盖了线程可能处在的全部位置：

```
   vCPU 线程可能在的位置                 被哪一步挡住
   ─────────────────────────────────────────────────────────────
   run loop 顶部，还没检查 should_stop    ① should_stop
   检查完 should_stop，还没进 KVM_RUN     ② immediate_exit（进去立刻 -EINTR）
   在 KVM_RUN 里（guest 运行或 HLT 睡眠） ③ SIGUSR1（KVM 检测到信号挂起，退出）
   在 vcpu_handle_exit 里处理设备         处理完回到顶部，被 ① 挡住
```

只用信号不用 `immediate_exit`，第二个窗口就没人管：信号被空的处理函数“吃掉”，线程随后进入 `KVM_RUN`，guest 如果正在 idle，这个线程就永远睡下去，`pthread_join()` 永远等不到它，VMM 挂住。反过来，只用 `immediate_exit` 不用信号，第三个位置就没人管。

几个实现细节：

- **信号处理函数不能带 `SA_RESTART`**。带了这个标志，内核会在处理完信号后自动重启被打断的系统调用，`KVM_RUN` 就不会返回。
- **处理函数是空的**。它的全部作用就是“让一个信号被投递”，从而让 `KVM_RUN` 返回。不能用 `SIG_IGN`：被忽略的信号根本不会打断系统调用。
- **不给自己发信号**。触发停机的 vCPU 线程（比如写 PM1a_CNT 的那个）自己已经在返回的路上了，`pthread_equal` 检查跳过它。
- **`thread_started` 用 acquire/release 原子操作**。`vm_request_stop()` 可能在主线程还在创建线程的过程中被调用（比如某个 vCPU 线程一启动就出错），此时后面的 `v->thread` 还没有被赋值，不能对它调用 `pthread_kill()`。
- **依赖 `KVM_CAP_IMMEDIATE_EXIT`**（Linux 4.11 引入），所以在阶段 1 就检查它。

有三类事件会调用 `vm_request_stop()`：任何一个 vCPU 线程退出（guest 关机、guest 重启、出错）；I/O 线程收到 Ctrl-A x；vCPU 线程创建失败。测试脚本覆盖了前两类：4 核 guest panic 后经 i8042 复位退出，此时 panic 发生在哪个 vCPU 上是不确定的，其余三个必须被可靠地踢出来，否则 VMM 挂住直到超时；guest 执行 `poweroff` 时同理。

Ctrl-A x 退出时，VMM 会打印所有 vCPU 的寄存器状态。guest 卡住时，这是唯一能看到“每颗 CPU 停在哪条指令上”的线索：

```c
    /* Ctrl-A x 打断的现场一定要看：guest 卡住时这是唯一的线索 */
    if (r == VMM_OK && (vmm_log_level >= 3 || vm.user_stop)) {
        for (i = 0; i < vm.nr_vcpus; i++)
            vcpu_dump_state(&vm.vcpus[i]);
    }
```

### 1.6 小结：阶段 4 和阶段 9 的准备清单

- vCPU ID 从 0 连续编号，0 号是 BSP；多核只允许配合内核态 irqchip（Linux 模式）。
- 初始化过程中用 `cfg.nr_vcpus` 而不是递增中的 `vm->nr_vcpus`。
- CPUID 透传 host 特性，按 vCPU 改写 leaf `0x1`、`0xB`/`0x1F`、`0x80000008`、`0x8000001D`、`0x8000001E`，在第一次 `KVM_RUN` 之前设置。
- 每个 vCPU 一个线程，给线程命名，全部同时启动，AP 自己在 KVM 里等待 SIPI。
- `KVM_RUN` 返回 `EINTR` 或 `EAGAIN` 时不是错误，也不能分发 `exit_reason`，直接重进。
- 停机：`should_stop` + `immediate_exit` + 不带 `SA_RESTART` 的 SIGUSR1，缺一不可；任何 vCPU 退出都触发整机停机。

## 二、检查清单：vCPU 与线程

### 2.1 vCPU 与 CPUID

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| vCPU ID | 从 0 连续编号 | ID 即 APIC ID，0 号是 BSP | AP 起不来或 APIC ID 与固件表不符 |
| 多核的前提 | 有内核态 irqchip | 否则所有 vCPU 创建即 RUNNABLE | 多个 vCPU 从同一入口同时开跑 |
| CPUID 来源 | `KVM_GET_SUPPORTED_CPUID`，`E2BIG` 时扩容重试 | 透传 KVM 认可的 host 特性 | 不设 CPUID 时 guest 看到全 0，认为没有长模式，直接停住 |
| CPUID 设置时机 | 第一次 `KVM_RUN` 之前 | guest 启动即读取并缓存；5.16 起运行后禁止修改 | 修改不生效或 ioctl 失败 |
| leaf 1 EBX[31:24] | = vCPU ID | 初始 APIC ID | 所有 CPU 报同一个 APIC ID |
| leaf 1 EBX[23:16] 与 EDX.HTT | = N，N>1 时 HTT=1 | 逻辑处理器数 | 拓扑错误 |
| leaf `0xB`/`0x1F` | 清零，或完整正确地填写所有 subleaf | 半截的扩展拓扑会被 guest 采信 | 拓扑错误 |
| leaf `0x80000008` ECX | NC = N−1，ApicIdSize = ⌈log₂N⌉ | AMD 核数 | 核 ID 算错 |
| leaf `0x8000001D` | L1/L2 共享数 0，L3 共享数 N−1；保留结束项 | 缓存共享 | 调度域错误 |
| leaf `0x8000001E` | EAX = ID，EBX[7:0] = ID，ECX = 0 | 海光/AMD 的核 ID、节点 ID | 拓扑错误 |
| 总核数取值 | `cfg.nr_vcpus` | `vm->nr_vcpus` 在创建过程中递增 | 每个 vCPU 看到的核数不同 |

### 2.2 线程与停机

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| vCPU 线程 | 每 vCPU 一个，全部同时启动 | AP 在 KVM 里自己等 | — |
| `KVM_RUN` 返回 `EAGAIN` | 重进 | AP 收到 INIT 后返回 | AP 一醒整机退出 |
| `KVM_RUN` 返回 `EINTR` | 重进 | 信号或 immediate_exit | 被当成错误 |
| 被打断时的 `exit_reason` | 不分发 | 是上一次的旧值 | 上一次的 I/O 重复执行 |
| 停机顺序 | `should_stop` → `immediate_exit=1` → 信号 | 覆盖全部窗口 | 某个 vCPU 永远睡在 HLT 里，VMM 挂住 |
| 信号处理函数 | 空函数，不带 `SA_RESTART`，不能是 `SIG_IGN` | 让 `KVM_RUN` 返回 `EINTR` | `KVM_RUN` 被自动重启 |
| 任一 vCPU 退出 | 触发整机停机 | 关机、重启、错误都是全局事件 | 其余 vCPU 继续跑 |
| 控制台 | raw 模式并在退出时恢复；不在前台进程组时不碰终端 | SIGTTOU/SIGTTIN | 终端乱掉；VMM 被挂起 |
