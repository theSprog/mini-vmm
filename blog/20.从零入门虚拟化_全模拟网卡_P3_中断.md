P2 把帧接到了 host 上：guest 写 TDT，帧从 vCPU 线程写进 TAP；TAP 里来了帧，I/O 线程把它 DMA 进 guest 的接收缓冲。但还差一步：帧放进 guest 内存之后，guest 驱动怎么知道？发出去的帧，驱动又怎么知道它已经发完、缓冲可以回收？答案是中断。这一 P 从网卡的中断原因寄存器讲起，一直讲到电平怎样经过 PCI、KVM 的 IOAPIC 送进 guest，最后解释 e2e 测试里那条“中断数约等于 ICR 读次数”的断言为什么成立。

| P | 内容 |
|---|---|
| P1 | 设备的外观：PCI 身份、寄存器窗口、EEPROM、PHY，驱动探测成功并报告链路 up |
| P2 | 前端与后端：`--netdev`/`--device`，TAP，收包为什么在 I/O 线程上，后端怎样暂停和恢复收包 |
| P3（本篇） | 中断：中断原因寄存器、INTx 电平、为什么中断数约等于 ICR 读次数 |
| P4 | 发送：描述符环、DMA、上下文描述符与校验和 offload |
| P5 | TSO：硬件替驱动切包，以及“哈希对了也可能是错的” |
| P6 | 接收：地址过滤、描述符写回的顺序、什么时候算环满，端到端验证 |

## 一、一根线，很多原因

### 1.1 中断原因寄存器

82540EM 只有一根中断线（PCI 的 INTA），但想通知驱动的事情有很多种：发送描述符写回了、收到帧了、链路状态变了、接收缓冲快用完了、PHY 的读写完成了……驱动被中断时，第一件事是弄清楚“为什么”。

所以网卡用一个寄存器记下所有原因，每种原因占一位，这就是 ICR（Interrupt Cause Read，手册第 13.4.17 节）。本文会碰到的几位：

| 位 | 名字 | 什么时候置位 |
|---|---|---|
| 0 | TXDW | 处理完一个带 RS（Report Status）标志的发送描述符，把状态写回了 |
| 1 | TXQE | 发送队列空了：TDH 追上了 TDT |
| 2 | LSC | 链路状态变化 |
| 4 | RXDMT0 | 空闲的接收描述符降到阈值以下，提醒驱动补充 |
| 6 | RXO | 接收溢出（P2 第 6.1 节，mini-vmm 不会置这一位） |
| 7 | RXT0 | 收到帧并写回了接收描述符 |
| 9 | MDAC | MDIC 发起的 PHY 读写完成 |

### 1.2 四个寄存器管一组位

围绕 ICR，手册定义了四个寄存器（第 13.4.17–13.4.21 节）：

| 寄存器 | 偏移 | 读 | 写 |
|---|---|---|---|
| ICR | 0xC0 | 返回所有原因位，**同时全部清零** | 写 1 的位清零，写 0 的位不变 |
| ICS | 0xC8 | — | 写 1 的位在 ICR 里置位，相当于软件“假装”发生了这件事 |
| IMS | 0xD0 | 返回当前的屏蔽位（1 = 允许） | 写 1 的位允许，写 0 的位不变 |
| IMC | 0xD8 | — | 写 1 的位禁止，写 0 的位不变 |

INTx 线的电平只由一个式子决定：

```
INTx 电平 = (ICR & IMS) != 0
```

有一个原因位置位、而且它被允许，线就是高的；否则是低的。原因位和屏蔽位是分开存的：一个被禁止的原因照样会记进 ICR，只是不拉线。等它被重新允许的那一刻，线马上拉高。2.3 节会在 trace 里看到这种情况。

### 1.3 为什么屏蔽要分成两个寄存器

IMS 写 0 没有效果，要禁止一个原因必须去写 IMC。这比一个普通的读写寄存器麻烦，但它避免了一个竞态。

假设 IMS 是普通寄存器，驱动想关掉 RXT0、保留其他位，只能“读出来、清一位、写回去”：

```
  普通读写寄存器（假设）                       set/clear 分开（82540EM）

  CPU0: v = IMS          v = 0x9d            CPU0: IMC = 0x80
  CPU1: IMS = v | 0x04   （打开 LSC）          CPU1: IMS = 0x04
  CPU0: IMS = v & ~0x80  = 0x1d
  结果：CPU1 打开的 LSC 被 CPU0 写回的旧值覆盖了   两次写互不影响，没有中间状态
```

每个写操作只说“这几位要变成什么”，不需要先知道其他位现在是什么，所以不需要锁。ICR 写 1 清零也是同样的道理。

## 二、Linux 驱动怎样用它们

### 2.1 中断处理函数只做三件事

`e1000_intr()`（`drivers/net/ethernet/intel/e1000/e1000_main.c`）：

```c
static irqreturn_t e1000_intr(int irq, void *data)
{
	...
	u32 icr = er32(ICR);

	if (unlikely((!icr)))
		return IRQ_NONE;  /* Not our interrupt */
	...
	if (unlikely(icr & (E1000_ICR_RXSEQ | E1000_ICR_LSC))) {
		hw->get_link_status = 1;
		...
		schedule_delayed_work(&adapter->watchdog_task, 1);
	}

	/* disable interrupts, without the synchronize_irq bit */
	ew32(IMC, ~0);
	E1000_WRITE_FLUSH();

	if (likely(napi_schedule_prep(&adapter->napi))) {
		...
		__napi_schedule(&adapter->napi);
	}
	...
	return IRQ_HANDLED;
}
```

1. **读 ICR。** 拿到原因，同时把它们清掉，这一读就是对网卡的应答。读出 0 说明不是自己的中断（同一根线上可能有别的设备），返回 `IRQ_NONE`。
2. **写 IMC 全 1。** 关掉网卡的全部中断。接下来不靠中断，而是靠轮询。
3. **调度 NAPI。** 真正的收发处理在软中断里的 `e1000_clean()` 进行。

`e1000_clean()` 回收发送描述符、处理接收到的帧，一批处理完、环里没有剩余工作时，调 `e1000_irq_enable()` 写 IMS，重新打开中断：

```c
#define IMS_ENABLE_MASK ( \
    E1000_IMS_RXT0   |    \
    E1000_IMS_TXDW   |    \
    E1000_IMS_RXDMT0 |    \
    E1000_IMS_RXSEQ  |    \
    E1000_IMS_LSC)        /* = 0x9d */
```

这就是 NAPI 的思路：来一个中断就关掉中断、一口气处理掉所有积压的工作，处理完再开中断。流量大时，一次中断能带走几十帧。

`E1000_WRITE_FLUSH()` 是读一次 STATUS。PCI 的写是“发出去就不管”的（posted write），读一次同一设备的寄存器，可以确保前面的写已经到达网卡。所以 trace 里每次写 IMC、IMS 之后都紧跟着一次 STATUS 读。

### 2.2 trace 里的一次完整中断

`ip link set eth0 up` 时，驱动的 `e1000_open()` 在最后写 ICS：

```c
	/* fire a link status change interrupt to start the watchdog */
	ew32(ICS, E1000_ICS_LSC);
```

驱动用软件中断给自己发一个“链路变了”的信号，好让中断处理函数去启动看门狗。这一次中断的完整过程，在 `--trace-mmio` 里是这样（时间是相对 ICS 写的微秒数）：

```text
   +0  ICS    W4 00000004     驱动置 LSC；IMS 已经允许 LSC，INTx 拉高
  +19  ICR    R4 00000004     19 µs 后中断处理函数开始执行，读到 LSC，线随之撤销
  +35  IMC    W4 ffffffff     关掉全部中断
  +49  STATUS R4 00000083     flush
  +86  ITR    W4 000003d0     NAPI 结束前调整中断节流（第 3.3 节）
 +100  IMS    W4 0000009d     重新打开中断
 +114  STATUS R4 00000083     flush
```

和 2.1 节的代码一一对应。这 19 µs 里发生了很多事：ICS 写产生一次 `KVM_EXIT_MMIO`，e1000 置位 ICR、算出电平变高，PCI 核心调 `KVM_IRQ_LINE` 把 GSI 17 拉高，KVM 的 IOAPIC 把中断投递给 vCPU；vCPU 线程回到 `KVM_RUN` 时，KVM 把中断注入 guest，guest 跳进中断处理函数，执行到 `er32(ICR)`，又是一次 MMIO exit。

### 2.3 被禁止期间记下的原因

`ping` 期间的一段 trace（相对第一次 TDT 写）：

```text
   +0  TDT    W4 00000001     发一帧
 +115  ICR    R4 00000083     中断：TXDW | TXQE | RXT0
 +145  IMC    W4 ffffffff     关中断，进入 NAPI
 +270  RDT    W4 000000ff     补充接收缓冲
 +830  TDT    W4 00000002     NAPI 处理过程中又发一帧
 +962  IMS    W4 0000009d     NAPI 结束，开中断
 +989  ICR    R4 00000083     27 µs 后又一次中断
```

第二次中断是怎么来的？+830 写 TDT 时，IMS 是 0（+145 关掉了），e1000 照样把 TXDW、TXQE 记进 ICR，只是不拉线；这段时间里新到的帧也把 RXT0 记了进去。+962 驱动写 IMS 重新允许，`(ICR & IMS)` 立刻不为 0，线马上拉高，中断随即到来。

这正是 1.2 节说的“原因和屏蔽分开存”。如果模型在被屏蔽时干脆不记原因，这次中断就不会发生，驱动要等到下一个事件（或者看门狗的兜底，2.4 节）才会发现第二帧已经发完、新帧已经到了。

### 2.4 ICR 的值都有哪些

把 64 MiB 下载加三次 ping 的整个过程里所有 ICR 读按值分组：

| 读到的值 | 含义 | 次数 |
|---|---|---|
| `0x80` | RXT0：只有收包 | 907 |
| `0x03` | TXDW + TXQE：只有发送完成 | 404 |
| `0x83` | 收发都有 | 362 |
| `0x00` | 没有原因 | 3 |
| `0x04` | LSC，`e1000_open()` 的 ICS | 1 |
| `0x12` | RXDMT0 + TXQE | 1 |
| `0x10` | RXDMT0 | 1 |

最后两行来自驱动的看门狗，它每 2 秒写一次 ICS（`e1000_watchdog()`）：

```c
	/* Cause software interrupt to ensure rx ring is cleaned */
	ew32(ICS, E1000_ICS_RXDMT0);
```

驱动不信任“网卡一定会为每个收到的帧发中断”，每 2 秒自己补一个中断，兜底清理接收环。

读到 0 的三次都紧跟在一次 `IMC = ffffffff` 后面，那是 `e1000_reset_hw()` 在复位后“清掉残留的中断事件”：

```c
	/* Clear interrupt mask to stop board from generating interrupts */
	ew32(IMC, 0xffffffff);

	/* Clear any pending interrupt events. */
	er32(ICR);
```

P1 里说过一次启动会经 IO BAR 复位三次，正好对应这三次读。

## 三、实现

### 3.1 一个函数算电平

`src/devices/e1000.c` 里，所有中断逻辑收敛到两个函数：

```c
/* INTx 电平 = 有没有一个没被屏蔽的原因位（SDM 第 13.4.17-13.4.21 节）。
 * 每次 ICR 或 IMS 变化都重新算一遍，PCI 核心只在电平变化时打 KVM。 */
static void update_irq(struct e1000 *s)
{
    pci_set_irq(&s->pci, (*reg(s, E1000_ICR) & *reg(s, E1000_IMS)) != 0);
}

static void raise_icr(struct e1000 *s, uint32_t bits)
{
    *reg(s, E1000_ICR) |= bits & E1000_ICR_MASK;
    update_irq(s);
}
```

规则只有一条：**ICR 或 IMS 的任何变化之后都调 `update_irq()`。** 设备不记“上次拉没拉线”，每次都按 1.2 节的式子从头算，算出来的电平交给 PCI 核心，由它判断有没有变化（第四章）。这样就不可能出现“原因清掉了，线却忘了放下”的状态不一致。

四个寄存器的处理：

```c
    /* 读 */
    case E1000_ICR:
        /* 读清零（第 13.4.17 节），随之撤销 INTx */
        v = *reg(s, E1000_ICR);
        *reg(s, E1000_ICR) = 0;
        update_irq(s);
        return v;
    case E1000_ICS:
    case E1000_IMC:
        return 0;                            /* 只写 */

    /* 写 */
    case E1000_ICR:
        *reg(s, E1000_ICR) &= ~val;          /* 写 1 清零 */
        update_irq(s);
        return;
    case E1000_ICS:
        raise_icr(s, val);
        return;
    case E1000_IMS:
        *reg(s, E1000_IMS) |= val & E1000_ICR_MASK;
        update_irq(s);
        return;
    case E1000_IMC:
        *reg(s, E1000_IMS) &= ~val;
        update_irq(s);
        return;
```

IMS 读走的是普通路径，返回 `*reg(s, E1000_IMS)`，和手册“Reading this register returns bits that have an interrupt mask set”一致。复位（CTRL.RST）把 ICR、IMS 一起清零后也调一次 `update_irq()`，撤销可能还挂着的中断。

### 3.2 谁在置原因位

| 原因 | 置位的地方 | 线程 |
|---|---|---|
| TXDW、TXQE | `tx_process()`：写回了带 RS 的描述符置 TXDW，处理到 TDH == TDT 置 TXQE，一次处理结束统一 `raise_icr()` | 写 TDT 的 vCPU 线程 |
| RXT0、RXDMT0 | `rx_ring_put()`：一帧写进接收环后置 RXT0；剩余空闲描述符不多于 RCTL.RDMTS 选定的 1/2、1/4 或 1/8 时同时置 RXDMT0 | I/O 线程 |
| MDAC | MDIC 写完成 | vCPU 线程 |
| 任意 | ICS 写 | vCPU 线程 |

发送那一行有一个后果：guest 写 TDT 的那次 exit 里，帧已经发完、TXDW 已经置位、线已经拉高。vCPU 线程一回到 guest，中断就到了，2.3 节 trace 里 TDT 写和下一次 ICR 读之间只隔一百多微秒就是这个原因。真网卡发送需要时间，中断要等帧真正上线之后。

两个线程都会调 `raise_icr()`，所有调用都在 `io_lock` 下（P2 第 5.2 节），ICR 的读改写不会交错。

### 3.3 不模拟的部分：中断节流

手册里还有一组寄存器专门推迟中断：ITR（第 13.4.18 节）规定两次中断之间的最小间隔，单位 256 ns；RDTR/RADV 推迟收包中断，TIDV/TADV 推迟发送中断。Linux 驱动默认用动态节流（`InterruptThrottleRate` 默认 3），NAPI 每次结束前按刚处理的流量重新算 ITR（`e1000_set_itr()`）。上面那次下载里，驱动写了 1032 次 ITR，值集中在 976（250 µs，每秒 4000 次）和 195（约 50 µs，每秒 20000 次）附近。

mini-vmm 把这些寄存器当普通存储，写进去能读回来，但不起作用：事件一发生就立刻置 ICR。头文件里写着理由：这些定时器只是把多次中断合并，驱动不依赖它们何时到期。

不节流会不会让中断多到失控？实测这次下载收了 46540 帧，中断只有 1676 次，平均一次中断带走约 28 帧。NAPI 在中断关闭期间轮询，已经把中断合并掉了，实际中断率远低于驱动设的上限。QEMU 的 e1000 实现了 ITR/RADV/TADV 的定时器（`hw/net/e1000.c` 的 `set_interrupt_cause()` 和 `mit_update_delay()`），想看节流效果的可以去那里对照。

## 四、从设备到 guest：INTx 电平

### 4.1 PCI 核心：设备输出与线电平

`update_irq()` 交出去的是“设备想要的电平”。从这个电平到 KVM 中间还有两层，都在 `src/pci/pci.c`：

```c
/* 设备实际驱动到 INTx 线上的电平（PCI 3.0 第 6.2.2 节 Interrupt Disable、
 * 第 6.2.3 节 Interrupt Status） */
static bool intx_output(const struct pci_device *d)
{
    return d->intx_pin && d->intx_level &&
           !(cfg_get(d, PCI_COMMAND, 2) & PCI_COMMAND_INTX_DISABLE);
}

void pci_set_irq(struct pci_device *d, bool level)
{
    ...
    if (level == d->intx_level)
        return;
    d->intx_level = level;
    st = (uint16_t)cfg_get(d, PCI_STATUS, 2);
    st = level ? st | PCI_STATUS_INTERRUPT : st & ~PCI_STATUS_INTERRUPT;
    cfg_set16(d, PCI_STATUS, st);
    intx_line_update(d->bus, d);
}
```

- **COMMAND.Interrupt Disable。** 驱动置了这一位，设备的请求就不上线。但 STATUS 的 Interrupt 位仍然反映设备的请求，驱动可以靠它查询有没有挂起的中断（Linux 的 `pci_check_and_mask_intx()` 就这样用）。COMMAND 写入后也会重新计算线电平：中断挂着时清掉 Interrupt Disable，线要立刻拉高。
- **共线。** 四根 INTx 线被所有 slot 共用（《PCI·实现篇》第六章的 `pci_intx_gsi()`），一根线上可能接着好几个设备。线电平是所有设备输出的“或”：

```c
static void intx_line_update(struct pci_bus *bus, const struct pci_device *d)
{
    int gsi = pci_intx_gsi(d->slot, d->intx_pin);
    ...
    for (s = 0; s < PCI_MAX_SLOTS && !level; s++) {
        const struct pci_device *o = bus->devs[s];

        if (o && o->intx_pin && pci_intx_gsi(s, o->intx_pin) == gsi)
            level = intx_output(o);
    }
    if (level == bus->intx_line[line])
        return;
    bus->intx_line[line] = level;
    irqchip_set_irq(bus->vm, gsi, level);
}
```

如果每个设备直接把自己的电平交给 KVM，共线时就会出错：设备 A、B 都在请求中断，A 被处理完撤销，直接 `KVM_IRQ_LINE(gsi, 0)` 会把 B 的请求一起抹掉，B 的中断就丢了。按“或”计算，A 撤销后线仍然是高的。

最后一行只在电平真正变化时才调 KVM。e1000 每读一次 ICR、每写一次 IMS 都会调 `update_irq()`，绝大多数调用电平没变，这样省掉了一次 ioctl。

### 4.2 KVM_IRQ_LINE 的 1 就是“有效”

`irqchip_set_irq()` 最终调 `KVM_IRQ_LINE`，参数是 GSI 和 level。

PCI 的 INTx 在真硬件上是低电平有效（active-low），MP table 和 ACPI 也是这样描述给 guest 的（《PCI·实现篇》第六、七章），guest 会把 IOAPIC 对应引脚的极性设成“低有效”。那 VMM 撤销中断时应该传 1 吗？

不用。KVM 文档（`Documentation/virt/kvm/api.rst` 第 4.25 节）规定：`level` 字段与引脚的电气极性无关，1 总是表示“有效”（asserted），0 表示“无效”。KVM 的 IOAPIC 在处理电平时不看极性位（`arch/x86/kvm/ioapic.c` 的 `ioapic_set_irq()`）。这个约定由 `KVM_CAP_X86_IOAPIC_POLARITY_IGNORED` 表明，文档也要求用户态只在这个 capability 存在时才把中断描述成低有效。

所以 VMM 里的“电平”始终是逻辑上的“有没有请求”，不用关心 guest 怎么设置极性。

### 4.3 电平触发：处理完必须放下

IOAPIC 的引脚有两种触发方式。边沿触发只在电平变化的那一刻送一次中断；电平触发则只要线是高的，就一直在要求服务。PCI INTx 是电平触发。KVM 的 IOAPIC 对电平触发引脚的处理（`ioapic.c`）：

```
  线拉高 → IOAPIC 投递中断，置这个引脚的 Remote IRR
           （Remote IRR 置位期间不再投递）
  guest 处理完，向 LAPIC 写 EOI
       → KVM 清 Remote IRR（kvm_ioapic_update_eoi_one）
       → 如果这时线仍然是高的：立刻再投递一次
```

所以电平触发的正确时序是：设备在 guest 写 EOI **之前**把线放下。e1000 正好满足这一点：中断处理函数第一件事就是读 ICR，读 ICR 清零原因、`update_irq()` 算出电平为 0、`KVM_IRQ_LINE(17, 0)`，之后驱动才返回、内核才写 EOI。

```
  guest                     e1000 / PCI / KVM
  中断到来
  er32(ICR)  ────────────▶  ICR 清零 → 电平 0 → KVM_IRQ_LINE(17, 0)
  ew32(IMC, ~0)
  return IRQ_HANDLED
  写 EOI     ────────────▶  清 Remote IRR；线是低的，不再投递
```

电平触发的好处是不会丢中断：处理期间如果又有新原因、线又被拉高，EOI 之后 KVM 会马上再投递一次，guest 不会错过。代价是设备必须正确撤销，否则就是中断风暴。

### 4.4 反例：读 ICR 不清零

把 ICR 读改成“只返回、不清零”，再跑一遍 e2e 测试：guest 的 `/proc/interrupts` 里 eth0 的计数到了 1335211，数据传输失败。

过程是这样：中断处理函数读 ICR，原因还在，线还是高的；写 IMC 关中断，`(ICR & IMS)` 变成 0，线放下了。NAPI 处理完写 IMS 重新开中断，原因还在 ICR 里，线立刻又拉高，于是又一次中断、又读到同样的原因、又进 NAPI……guest 的 CPU 全耗在这个循环里，正常的收发反而得不到处理。

注意这个循环并不是 4.3 节那种“EOI 时线还高着”的风暴：驱动在返回、写 EOI 之前已经写了 IMC，线在 EOI 时是低的。每一轮都要经过一次 NAPI，所以 guest 还能缓慢前进，测试脚本最后仍然能读出 `/proc/interrupts`。真正的 EOI 风暴（设备连屏蔽都不理会、线一直是高的）KVM 另有保护：同一个电平触发引脚连续 10000 次在 EOI 时发现线仍然是高的，就把下一次投递推迟 10 毫秒（`ioapic.c` 的 `IOAPIC_SUCCESSIVE_IRQ_MAX_COUNT`），源码注释说这是在模仿真硬件，让有 bug 的 guest 还能缓慢前进。

## 五、为什么中断数约等于 ICR 读次数

### 5.1 一一对应的来源

`e1000_intr()` 每被调用一次，开头就读一次 ICR。eth0 的那根线上只有 e1000 一个设备，所以“guest 收到的中断数”应该等于“中断处理函数读 ICR 的次数”。除此之外，驱动还会在复位路径上主动读 ICR（2.4 节的三次 0）。

实测（64 MiB 下载加三次 ping，从启动到关机）：

| 观测点 | 数值 |
|---|---|
| guest `/proc/interrupts` 里 eth0（GSI 17）的计数 | 1676 |
| trace 里 ICR 读的总次数 | 1679 |
| 其中读到 0 的次数（复位路径） | 3 |
| guest 收到的帧数（`rx_packets`） | 46540 |

1679 − 3 = 1676，严格相等。

### 5.2 这个等式检查了什么

`tests/e2e/emu-net.sh` 在跑完双向传输之后检查：

```
0 < 中断数 <= ICR 读次数 <= 中断数 + 16，并且 中断数 <= 收发包数
```

每一部分挡住一类错误：

- **中断数大于 0**：整条路径是通的。原因位、屏蔽位、PCI 线电平、GSI 编号、MP table/ACPI 里的路由、KVM 的 IOAPIC，任何一处断了，计数都是 0。
- **ICR 读次数不少于中断数**：每一个送到 guest 的中断都进了 e1000 的处理函数。中断送错了 GSI、被别的处理函数领走时，这一条就不成立。
- **ICR 读次数不超过中断数 + 16**：多出来的只能是复位这类路径上的主动读。允许的余量是 16 而不是严格等于 3，因为复位次数取决于驱动的路径（例如链路变化时的重新初始化），测试只要求它不随流量增长。
- **中断数不超过包数**：没有中断风暴。4.4 节的错误实现会让中断数远远超过包数。

e2e 测试中的一次运行：中断 8062 次，ICR 读 8065 次，收发包 65241 个。

## 六、验证

### 6.1 单元测试

`tests/unit/e1000_test.c` 的 `case_irq()` 不启动 guest，直接读写寄存器，用一个记录 `pci_set_irq()` 调用的桩函数观察电平：

- 被屏蔽的原因（ICS 写入、IMS 里没有这一位）不拉线；
- 写 IMS 允许一个挂起的原因，线立刻拉高（2.3 节的情形）；
- IMS 能读回、IMC 能重新屏蔽、ICR 写 1 清零；
- ICR 读返回所有原因并全部清零，线随之撤销；
- `case_reset_and_access()`：CTRL.RST 撤销挂着的中断，IMS 回到 0。

`tests/unit/pci_bus_test.c` 检查 PCI 核心这一层，同样用桩函数把每次 `KVM_IRQ_LINE` 记成 `"17=1 17=0"` 这样的字符串：

- 重复设置同一电平不重发；
- 共线时一个设备撤销不会放下另一个设备还在请求的线；
- Interrupt Disable 置位时撤销挂着的中断、STATUS.Interrupt 仍然反映设备请求，清掉后重新拉线；被屏蔽的设备不影响共线设备；按字节写 COMMAND 高字节也生效。

“ICR 读不清零”是 `e1000_test` 用来检验自身的九个错误实现之一，单元测试和 e2e 都会变红。

### 6.2 端到端

e2e 里和中断直接相关的两条断言：`/proc/interrupts` 里出现 ` 17: ... IO-APIC 17-fasteoi eth0`（中断经 IOAPIC 以电平触发方式送达，`fasteoi` 是 Linux 对电平触发 IOAPIC 引脚用的处理流程），以及第五章的计数关系。计数中的 ICR 读次数来自 `--trace-mmio`，用 `tools/trace_decode.py --addr` 过滤出 BAR0 + 0xC0 的读。

## 七、限制

- 中断节流寄存器不起作用（3.3 节）。驱动写的 ITR 被忽略，事件立即触发中断。
- 只有 INTx。82540EM 的 Linux 驱动用 INTx，MSI/MSI-X 在后面的 pci-msi、pci-msix 里程碑里用其他设备演示。
- 发送完成在 TDT 写的同一次 exit 里就置位，比真网卡早（3.2 节），对“发送完成中断要过一段时间才来”有隐含依赖的驱动行为在这里观察不到。
- mini-vmm 没有在启动时检查 `KVM_CAP_X86_IOAPIC_POLARITY_IGNORED`。这个 capability 在现代内核里一直存在，但按 4.2 节引用的文档，严格来说应该检查。
