P2 讲了每条命令都要走的那条路：驱动在命令表里放一个 FIS，写 PxCI 按门铃，HBA 执行完后把结果写回 FIS 接收区，并清掉 PxCI 里对应的位。这一篇看路上跑的第一条命令 IDENTIFY DEVICE：盘在这 512 字节里怎样描述自己，Linux 从中读出什么、据此决定什么；再看它为什么不以 D2H Register FIS 结束，而以 PIO Setup FIS 结束；最后看紧随其后的 SET FEATURES。

| P | 内容 |
|---|---|
| P1 | 外观与端口枚举：PCI 身份、ABAR、全局寄存器、端口的启动、COMRESET 与设备签名 |
| P2 | 命令的生命周期与中断：命令列表、命令表、FIS 接收区，从写 PxCI 到收到 D2H FIS，三级中断，出错停端口与恢复 |
| P3（本篇） | IDENTIFY 与 PIO：驱动眼里的盘长什么样，PIO Setup FIS，SET FEATURES |
| P4 | 后端与 DMA 读写：`--drive` 与 raw 镜像，PRDT 的逐项检查，写缓存与 FLUSH，端到端验证 |
| P5 | NCQ：PxSACT、FPDMA 命令与 SDB FIS，出错之后经日志 10h 恢复 |

## 一、探测时盘收到的命令

### 1.1 链路建立之后的四条命令

P1 结尾，Linux 从 PxSIG 读到 0x00000101，知道端口上接的是一块 ATA 盘。在这之后，到第一次读分区表为止，盘一共收到四条命令。下面的记录来自一个在 `exec_slot` 里把命令头和命令 FIS 打印出来的插桩版本，盘是 64 MiB 的 ext2 镜像，每行后半段是命令 FIS 的前 16 个字节：

```text
slot 0 dw0=0x00010005 cfis=27 80 ec 00 | 00 00 00 a0 | 00 00 00 00 | 00 00 00 08   IDENTIFY DEVICE
slot 0 dw0=0x00000005 cfis=27 80 ef 03 | 00 00 00 a0 | 00 00 00 00 | 46 00 00 08   SET FEATURES 03h，Count 46h
slot 0 dw0=0x00010005 cfis=27 80 ec 00 | 00 00 00 a0 | 00 00 00 00 | 00 00 00 08   IDENTIFY DEVICE
slot 4 dw0=0x00010005 cfis=27 80 60 08 | 00 00 00 40 | 00 00 00 00 | 20 00 00 08   READ FPDMA QUEUED
```

FIS 的布局 P2 第二章讲过：字节 0 的 27h 是 Register Host to Device FIS，字节 1 的 80h 是 C 位（这是一条命令），字节 2 是命令码，字节 3 是 Features，字节 12 是 Count。命令头 dw0 的低 5 位是 FIS 长度 5 个双字，高 16 位是 PRDT 的项数：IDENTIFY 有一项，因为它要把 512 字节数据交给驱动；SET FEATURES 是 0，它不带数据。

四条命令各有来由：

1. IDENTIFY DEVICE（ECh）：`ata_dev_read_id` 发出，读回盘的 512 字节自我描述，后面所有配置都从这里来。
2. SET FEATURES（EFh）子命令 03h：设置传输模式。`ata_dev_set_mode` 根据 IDENTIFY 里报的能力和控制器的能力选出 UDMA 6，Count 46h 就是 UDMA 6 的编码（第五章）。
3. 又一次 IDENTIFY DEVICE：`ata_dev_set_mode` 在设置模式之后调用 `ata_dev_revalidate` 重读一遍，确认盘还是那块盘（`ata_dev_same_device` 比较型号和序列号）、容量没有变（比较 `n_sectors`），并取得设置后的状态，例如字 88 里“当前选中的 UDMA 模式”那一位。
4. READ FPDMA QUEUED（60h）：sd 驱动读分区表。这是 NCQ 命令，留给 P5。

关机时还有两条：FLUSH CACHE（E7h）和 STANDBY IMMEDIATE（E0h），分别由 sd 的 SYNCHRONIZE CACHE 和 START STOP UNIT 翻译而来。前者是 P4 的内容；后者对模拟盘没有可做的事，直接以成功完成。这里的 FLUSH CACHE 是 28 位版本 E7h，不是 EAh：`ata_dev_config_lba` 只在容量不小于 2^28 个扇区时才设 `ATA_DFLAG_FLUSH_EXT`，64 MiB 的盘用不着。

### 1.2 dmesg 里的四行

驱动把 IDENTIFY 的结果打印成这几行：

```text
ata1.00: ATA-8: MINIVMM AHCI DISK, 1.0, max UDMA/133
ata1.00: 131072 sectors, multi 0: LBA48 NCQ (depth 32)
ata1.00: configured for UDMA/133
scsi 0:0:0:0: Direct-Access     ATA      MINIVMM AHCI DIS 1.0  PQ: 0 ANSI: 5
```

第一行出自 `ata_dev_configure`：标准版本号、型号、固件版本、能力范围内最快的传输模式。第二行出自 `ata_dev_config_lba`：容量、READ/WRITE MULTIPLE 的块大小、寻址方式、NCQ 队列深度。第三行出自 `ata_dev_set_mode`，是 SET FEATURES 之后实际采用的模式。第四行已经是 SCSI 层：libata 把 ATA 盘包装成 SCSI 盘交给 sd，INQUIRY 命令由 `ata_scsiop_inq_std` 在主机侧模拟，厂商字段固定写 `ATA     `，产品字段只有 16 个字符宽，所以型号被截成 `MINIVMM AHCI DIS`。

接下来两章把这几行拆回 512 字节里的具体位置。

## 二、512 字节里 Linux 看哪些字

### 2.1 数据的形状

IDENTIFY DEVICE 返回一个扇区，ATA8-ACS 第 7.16 节的表 22 把它定义成 256 个 16 位字。字按小端传输，所以内存里字 N 的低字节在偏移 2N、高字节在 2N+1。guest 里 `/sys/class/ata_device/dev1.0/id` 把驱动保存的这 256 个字按十六进制打出来，下面截取前几行和最后一行：

```text
0000 0000 0000 0000 0000 0000 0000 0000      字 0-7
0000 0000 6430 2020 2020 2020 2020 2020      字 8-15：字 10 起是序列号
2020 2020 2020 2020 0000 0000 0000 312e      字 16-23：字 23 起是固件版本
3020 2020 2020 4d49 4e49 564d 4d20 4148      字 24-31：字 27 起是型号
...
0000 0000 0000 0000 0000 0000 0000 1da5      字 248-255：完整性字
```

字符串字段有一个容易弄错的地方：每个字装两个字符，前一个字符在高字节。序列号 `d0` 在字 10 里是 0x6430，0x64 是 `d`、0x30 是 `0`。按小端字节序直接把内存当字符串读，得到的是 `0d`。ATA8-ACS 第 7.16.7.9 节规定了这个顺序，Linux 的 `ata_id_string` 按同样的顺序取字符；本实现的 `id_string` 照这个顺序填，长度不够的部分补空格。

型号是 `MINIVMM AHCI DISK`，固件版本是 `1.0`，序列号取 `--drive` 的 id。序列号不是随便填的：上一节说过，`ata_dev_revalidate` 会比较前后两次 IDENTIFY 的型号和序列号，对不上就认为盘被换了。所以序列号只能来自同一块盘上不变的东西，drive id 正好满足。

最后一个字是完整性字（第 7.16.7.82 节）：低字节是签名 A5h，高字节是校验和，使 512 个字节加起来模 256 为 0。上面的 1DA5 就是这样算出来的。

### 2.3 三个规律

这张表里有三个规律，理解了它们，填 IDENTIFY 就不需要逐字背表。

**“字有效”位。** 字 83、84、87、106 的 bit 15:14 规定写 01b，表示“这个字里的内容有效”。早期的盘在这些位置可能是 0000h 或 FFFFh，驱动没法分辨“不支持”和“这个字没定义”，于是加了这两位。Linux 的 `ata_id_has_lba48`、`ata_id_has_flush`、`ata_id_has_wcache` 第一步都是检查字 83 的高两位是不是 01b；字 82 自己没有有效位，由字 83 的有效位担保（源码注释原话是 “word 83 valid bits cover word 82 data”）。所以字 83 一旦漏掉 0x4000，48 位地址、FLUSH CACHE、写缓存会同时消失，而且没有任何报错。

**“支持”和“已启用”分开报。** 字 82-84 是盘支持什么，字 85-87 是当前打开了什么。写缓存可以关掉，所以字 82 bit 5 恒为 1，字 85 bit 5 跟着 SET FEATURES 变化（第五章）。传输模式也是这样：字 63、88 的低字节是支持的模式，高字节是当前选中的模式。一个字段跟着运行状态变化，就说明 IDENTIFY 不能在 attach 时生成一次存起来，每次命令到来时都要现算。本实现的 `ahci_identify` 根据当前的写缓存开关和传输模式现填。

**少报比多报安全。** 报了的能力 Linux 会去用。字 80 报 ATA8-ACS（bit 8）而不是更新的版本，是因为 Linux 对高版本有额外期待：读源码可知，版本号不小于 10（ACS-3）时，日志目录里缺 IDENTIFY DEVICE 数据日志会让 `ata_identify_page_supported` 打警告；版本号 11、12 分别会触发对并发定位范围日志、CDL 日志的读取。同理，字 82 bit 10 不报 HPA，Linux 就不会发 READ NATIVE MAX ADDRESS；字 77、78 为 0，Linux 就不读 NCQ 优先级、NCQ 管理相关的日志页。每少报一项，就少一条需要实现、否则只能中止的命令。

## 三、改一个字会怎样

表里写着 Linux 读哪个字，可读源码得到的结论毕竟是推断。下面四个实验各改 `ahci_identify` 里的一个字，其余不动，用同一个 guest 内核启动。

### 3.1 字 0 bit 15 置 1：不再是 ATA 设备

```text
ata1: SATA link up 6.0 Gbps (SStatus 133 SControl 300)
ata1.00: failed to IDENTIFY (device reports invalid type, err_mask=0x0)
ata1: limiting SATA link speed to 3.0 Gbps
ata1: SATA link up 3.0 Gbps (SStatus 123 SControl 320)
ata1.00: failed to IDENTIFY (device reports invalid type, err_mask=0x0)
ata1: SATA link up 3.0 Gbps (SStatus 123 SControl 320)
```

`ata_dev_read_id` 拿到数据之后先做“类型对不对”的检查：签名说这是 ATA 盘（P1），IDENTIFY 却说自己不是 ATA 设备，两者矛盾。err_mask 为 0，说明命令本身没有出错，是数据被驱动拒绝了。错误处理把这当成链路不可靠，先降速到 3 Gbps 再复位重试，两次 IDENTIFY 都被拒，第三次复位之后不再发 IDENTIFY。最后没有 sda，内核在 12.7 秒才跑到 init，正常启动是 1.8 秒。

这个实验说明了一件事：数据填错时，命令照样“成功”完成，报错来自驱动的检查。设备模型自己的单元测试必须直接检查数据内容，不能只看命令是否完成。

### 3.2 字 93 不为 0：被当成桥后面的并口盘

把字 93 填成 0x4000（并口盘常见的值）：

```text
ata1.00: ATA-8: MINIVMM AHCI DISK, 1.0, max UDMA/133
ata1.00: 131072 sectors, multi 0: LBA48 NCQ (depth 32)
ata1.00: applying bridge limits
ata1.00: configured for UDMA/100
```

SET FEATURES 的 Count 从 46h 变成了 45h（UDMA 5），guest 里 `queue/max_hw_sectors_kb` 从 32767 变成了 128。原因在 `ata_dev_knobble`：控制器是 SATA 的，盘却不像 SATA 盘（`ata_id_is_sata` 为假），Linux 认定中间隔着一个 SATA 转并口的桥，于是把 UDMA 限制在 5，单条命令限制在 `ATA_MAX_SECTORS` 即 256 个扇区。源码在这里的注释写的是 “200 sectors”，和常量的实际值 256 对不上，以常量为准，128 KiB 也印证了这一点。

盘照常工作，没有任何报错，只是每条命令最多传 128 KiB，而正常情况下可以传 32 MiB。这类错误只能靠比对配置结果发现。

### 3.3 字 64 为 0：SET FEATURES 消失了

把字 64 填成 0，即只报 PIO 0-2：

```text
slot 0 ... cfis=27 80 ec 00 ...    IDENTIFY DEVICE
slot 0 ... cfis=27 80 ec 00 ...    IDENTIFY DEVICE
slot 4 ... cfis=27 80 60 08 ...    READ FPDMA QUEUED
```

dmesg 依然是 `configured for UDMA/133`，但 SET FEATURES 根本没有发。这个结果乍看和 PIO 毫无关系，追下去是这样一条链：`ata_dev_set_xfermode` 只在两种情况下发命令。一是 `ata_pio_need_iordy` 为真，此时 Count 填要设的模式；二是盘支持 IORDY（字 49 bit 11），此时 Count 填 01h，表示关掉 IORDY。两者都不满足时直接返回 0，源码的注释是 “In the ancient relic department - skip all of this”。而 `ata_pio_need_iordy` 的判断条件之一是 PIO 模式高于 2：字 64 报了 PIO 3、4 时选中的是 PIO 4，需要 IORDY，于是发命令；只有 PIO 0-2 时不需要，本实现的字 49 也没报 IORDY，于是不发。

命令没发，盘上的“当前模式”停在复位默认值 UDMA 6，Linux 记下的也是 UDMA 6，两边碰巧一致，revalidate 也就看不出问题。换一个默认模式不同的盘，两边就会不一致。

### 3.4 字 83 去掉 bit 10：退回 28 位地址

```text
ata1.00: 131072 sectors, multi 0: LBA NCQ (depth 32)
```

`LBA48` 变成了 `LBA`，`max_hw_sectors_kb` 也变成了 128。`ata_dev_configure` 先把 `max_sectors` 设为 `ATA_MAX_SECTORS`（256），只有 LBA48 时才放宽到 `ATA_MAX_SECTORS_LBA48`（65535，“避免 Count 为 0000h”）。28 位命令的 Count 只有 8 位，0 表示 256 个扇区，所以上限是 256。正常配置下的 32767 KiB 就是 65535 × 512 字节向下取整。NCQ 还在，因为 FPDMA 命令本身总是带 48 位地址，和这一位无关。

### 3.5 小结：这些实验说明了什么

四个实验没有一个让命令失败：IDENTIFY 每次都正常完成，数据也完整送到了驱动手里。变的是驱动根据数据做出的决定：认不认这块盘、用多快的模式、单次传多少、发不发某条命令。全模拟设备的“行为”有很大一部分体现在这类数据上，而不是体现在寄存器的读写上。

## 四、PIO Setup FIS：IDENTIFY 怎样结束

### 4.1 为什么不是 D2H Register FIS

P2 讲的命令都以 D2H Register FIS 结束：设备把状态寄存器和错误寄存器的新值放进这个 FIS 发给主机，HBA 收到后更新 PxTFD、清 PxCI。IDENTIFY 不一样，它属于 PIO data-in 协议。ATA 的 PIO 协议来自并口时代：设备把数据放进数据寄存器，主机一个字一个字地读走，每个数据块之前设备都要先告诉主机“数据准备好了”。SATA 把这一步做成了 PIO Setup FIS（SATA 3.0 第 10.3.10 节），设备在每个 Data FIS 之前发一个。

PIO Setup FIS 是 5 个双字，和本篇相关的字段：

| 字节 | 字段 | IDENTIFY 时的值 | 含义 |
|---|---|---|---|
| 0 | FIS Type | 5Fh | |
| 1 | bit 5 D，bit 6 I | 60h | D=1：数据从设备到主机；I=1：完成后要求中断 |
| 2 | Status | 58h（DRDY、DRQ） | 数据传输开始时的状态：DRQ=1 表示有数据要传 |
| 3 | Error | 0 | |
| 15 | E_Status | 40h（DRDY） | 这一块数据传完之后的状态 |
| 16-17 | Transfer Count | 512 | 随后那个 Data FIS 的字节数 |

关键在于一个 FIS 里同时有“开始时的状态”和“结束时的状态”。并口上，主机读完最后一个字的 400 ns 内，状态寄存器要从“DRQ=1”变成新值；SATA 要求 HBA 在本地模拟这个时序，所以设备提前把结束状态 E_Status 交给 HBA，由 HBA 在数据传完时自己换上。IDENTIFY 只有一个数据块，传完后命令就结束了，设备不会再发 D2H Register FIS，最终状态就是这个 E_Status。

### 4.2 HBA 在这期间做什么

AHCI 第 5.3.9 节的 PIO Setup 接收状态机描述了 HBA 的动作：

1. **PIO:Entry**：把 FIS 复制到 FIS 接收区偏移 0x20（PSFIS），用 Status 字段更新 PxTFD.STS，记下 E_Status、Error、I 位和 Transfer Count。
2. 接收随后的 Data FIS，数据按 PRDT 写进内存（PRDT 的细节在 P4）。
3. **PIO:Update**：用记下的 E_Status 更新 PxTFD。如果其中 ERR 为 1，进入 ERR:FatalTaskfile，也就是 P2 第四章的 TFES 错误路径；如果 BSY 和 DRQ 都为 0，进入 PIO:ClearCI。
4. **PIO:ClearCI**：按第 5.4.1 节的规则把实际传输的字节数写进命令头的 PRDBC，清掉 PxCI 里对应的位。
5. I 位为 1 时置 PxIS.PSS（PIO Setup FIS Interrupt）。

所以 IDENTIFY 完成时，PxIS 里亮的是 PSS 而不是 DHRS。P2 的 trace 里第一条命令完成后读到 `P0IS = 0x2`，就是这一位。Linux 的 `DEF_PORT_IRQ` 同时打开了两者，所以不管命令以哪种 FIS 结束都能收到中断。

### 4.3 驱动从哪里取结果

Linux 的 `ahci_qc_fill_rtf` 负责把一条命令的结果状态填进 `qc->result_tf`，对 PIO data-in 单独处理：

```c
if (qc->tf.protocol == ATA_PROT_PIO && qc->dma_dir == DMA_FROM_DEVICE &&
    !(qc->flags & ATA_QCFLAG_EH)) {
	ata_tf_from_fis(rx_fis + RX_FIS_PIO_SETUP, &qc->result_tf);
	qc->result_tf.status = (rx_fis + RX_FIS_PIO_SETUP)[15];
	...
}
```

它从 PSFIS 区读整个 FIS，再把字节 15 的 E_Status 当作状态。源码注释说得很直白：PIO data-in 成功之后，设备不会发 D2H Register FIS，主机应该从前面那个 PIO Setup FIS 里取。如果设备模型对 IDENTIFY 也发一个 D2H FIS 而不发 PIO Setup FIS，Linux 读到的就是 PSFIS 区里上一次留下的内容（第一次是全 0），状态里连 DRDY 都没有。

### 4.4 E_Status 填错了，Linux 看得出来吗

做两个实验：只改 PIO Setup FIS 的 E_Status，一次加上 ERR（41h），一次加上 DRQ（48h），PxTFD 照旧写 40h。两次启动都完全正常，dmesg 和正常情况逐字相同。

原因在 4.2 的状态机：真实硬件里，E_Status 的 ERR 会经 PIO:Update 变成 TFES 错误，驱动通过 PxIS.TFES 知道出错；驱动并不会对着 PSFIS 里的 E_Status 再判断一次。读源码可知，`result_tf.status` 只在两个地方被检查：一是命令已经因为 TFES 之类进入错误处理时（`ata_exec_internal` 里的 `if (qc->flags & ATA_QCFLAG_EH)` 分支）；二是用户态经 SG_IO 发 ATA passthrough 命令、要求返回状态时，`ata_gen_passthru_sense` 根据它生成 sense 数据。启动路径上两者都不会碰到。

在本实现里，“设备”和“HBA”是同一段代码：`pio_in` 既负责填 FIS 里的 E_Status，也负责把它写进 PxTFD。规范要求两者一致，PxTFD 里的值来自 E_Status。实验说明这种不一致不会在 guest 启动时暴露，只能由单元测试直接检查两处的值是否都是 40h（第六章）。

### 4.5 本实现

```c
static void cmd_identify(struct ahci *s, struct ahci_port *p, int slot,
                         uint64_t hdr_gpa, uint32_t prdtl, uint64_t ctba)
{
    uint16_t id[ATA_ID_WORDS];
    uint8_t data[ATA_SECTOR_SIZE];
    int i;

    ahci_identify(s, id);
    for (i = 0; i < ATA_ID_WORDS; i++) {        /* 数据按小端的 16 位字传 */
        data[2 * i] = (uint8_t)id[i];
        data[2 * i + 1] = (uint8_t)(id[i] >> 8);
    }
    pio_in(s, p, slot, hdr_gpa, prdtl, ctba, data, sizeof(data));
}
```

`ahci_identify` 每次现算 256 个字，再按小端展开成字节，交给 `pio_in`。`pio_in` 是 PIO data-in 的通用部分，做的事和 4.2 的状态机一一对应，只是没有真实的链路，所以 Data FIS 的“接收”就是直接把数据拷进 PRDT 描述的内存：

```c
    r = prdt_map(s, p, slot, ctba, prdtl, len, &iov, &n, &dps);   /* 每一项单独检查，P4 */
    ...
    for (i = 0; i < n; i++) {                                     /* 数据进 guest 内存 */
        memcpy(iov[i].iov_base, data + off, iov[i].iov_len);
        off += iov[i].iov_len;
    }
    free(iov);
    if (set_prdbc(s, p, slot, hdr_gpa, len) != VMM_OK)             /* PIO:ClearCI 的 PRDBC */
        return;

    fis[0]  = SATA_FIS_PIO_SETUP;
    fis[1]  = SATA_FIS_PIO_D | SATA_FIS_I;
    fis[2]  = ATA_STS_DRDY | ATA_STS_DRQ;        /* 传输开始时的状态 */
    fis[15] = ATA_STS_DRDY;                      /* E_Status：传完之后 */
    fis[16] = (uint8_t)ATA_SECTOR_SIZE;          /* Transfer Count */
    fis[17] = (uint8_t)(ATA_SECTOR_SIZE >> 8);
    if (post_fis(s, p, AHCI_RFIS_PSFIS, fis, sizeof(fis)) != VMM_OK) {
        host_bus_fatal(s, p, slot);
        return;
    }
    p->tfd = ATA_STS_DRDY;                       /* PIO:Update：E_Status 进 PxTFD */
    p->is |= AHCI_PxIS_PSS | (dps ? AHCI_PxIS_DPS : 0);
    p->ci &= ~(1u << slot);                      /* PIO:ClearCI */
    update_irq(s);
```

顺序上有两点要注意。

第一，数据和 PRDBC 必须在清 PxCI 之前写好。P2 第二章讲过，驱动判断完成的唯一依据是 PxCI 的位被清掉；一旦清掉，驱动可能立刻读数据。本实现是在 vCPU 线程上同步执行的，清 PxCI 和驱动读数据之间隔着一次 VM entry，实际上不会交错，但代码顺序仍按规范的顺序写，换成异步执行时不需要调整。

第二，PIO Setup FIS 要写进 PSFIS 区，而不是 D2H 用的 RFIS 区。`post_fis` 只在 PxCMD.FRE 打开时才写，写失败按主机总线错误停下端口，这一点和 D2H FIS 相同（P2 第四章）。

PIO data-out 方向也有一个 `pio_out`，给 WRITE LOG EXT 用（P5）。它的区别是 D=0、I=0，E_Status 是 BSY|DRDY：主机把数据交给设备之后，设备还要处理，最终状态由随后的一个 D2H Register FIS 给出（AHCI 第 5.3.8 节的 RegFIS:ClearCI）。

## 五、SET FEATURES

### 5.1 子命令

SET FEATURES（EFh，ATA8-ACS 第 7.48 节）是一条“改设备设置”的总命令，子命令放在 Features 字段（命令 FIS 字节 3），参数放在 Count（字节 12）。Linux 对这块盘会用到三个子命令：

| 子命令 | 含义 | 什么时候发 |
|---|---|---|
| 03h | 设置传输模式，模式在 Count 里 | 探测时（1.1），条件见 3.3 |
| 02h | 打开写缓存 | 用户经 sd 的 MODE SELECT 改缓存设置时，例如 `echo "write back" > /sys/block/sda/device/scsi_disk/*/cache_type` |
| 82h | 关闭写缓存 | 同上，`write through` |

其余子命令一律中止，第一次遇到时记下子命令号。

### 5.2 传输模式的编码

Count 的高 5 位是模式类别，低 3 位是类别里的编号（表 40）：

| Count | 含义 |
|---|---|
| 00h | PIO 默认模式 |
| 01h | PIO 默认模式，关闭 IORDY |
| 08h + n | PIO 流控模式 n |
| 20h + n | 多字 DMA（MWDMA）模式 n |
| 40h + n | Ultra DMA（UDMA）模式 n |

所以 46h 是 UDMA 6，即 dmesg 里的 UDMA/133；45h 是 UDMA 5（UDMA/100）。对 SATA 来说这些都是历史遗留：链路速率由 PxSSTS 决定（P1），和这里的“模式”无关。ATA8-ACS 仍然要求 SATA 盘接受这条命令并如实在 IDENTIFY 里反映结果。

本实现检查 Count 是否落在 IDENTIFY 报告的能力范围内，在范围内就接受，否则中止：

```c
    case ATA_SF_XFER_MODE:
        switch (val & 0xF8) {
        case 0:               ok = mode == 0; break;  /* 取消 IORDY（1）不支持：字 49 bit 10 为 0 */
        case ATA_XFER_PIO:    ok = mode <= 4; break;
        case ATA_XFER_MWDMA:  ok = mode <= 2; break;
        case ATA_XFER_UDMA:   ok = mode <= 6; break;
        default:              ok = false; break;
        }
        if (ok && (val & 0xF8) >= ATA_XFER_MWDMA)
            s->dma_mode = val;
        break;
```

被接受的 DMA 模式记在 `dma_mode` 里，下一次 IDENTIFY 时体现为字 63 或字 88 高字节里的一位。MWDMA 和 UDMA 互斥（第 7.48.5 节），因为只记一个 `dma_mode`，选了一种就自然取消了另一种；PIO 模式不影响 DMA 模式。

模式对模拟的速度没有任何影响，数据总是直接拷贝。之所以还要记下来，是为了让 revalidate 读到的 IDENTIFY 和驱动刚设置的一致：驱动设了 UDMA 6，重读时字 88 的 bit 14 就应该亮着。

### 5.3 写缓存开关

```c
    case ATA_SF_WCACHE_ON:
        s->wcache = true;
        ok = true;
        break;
    case ATA_SF_WCACHE_OFF:
        ok = blk_flush(s->blk) == VMM_OK;
        if (ok)
            s->wcache = false;
        break;
```

打开只改一个标志。关闭时先把后端 flush 一次：第 7.48.4 节规定关闭写缓存后设备不再缓存写入，那么关掉之前已经接受、尚未落盘的写也要先落盘，否则驱动以为“缓存已关，之前的写都安全了”，实际上并没有。缓存关着时每条写命令完成前都要 flush，这一点放在 P4 和写命令一起讲。

`wcache` 反映到 IDENTIFY 字 85 bit 5。sd 驱动的 `Write cache: enabled` 来自 libata 模拟的 MODE SENSE 缓存页，它读的就是这一位。

### 5.4 复位之后回到默认值

ATA8-ACS 第 7.48.2 节说 SET FEATURES 设置的值在复位之后由设备自定，可以保持，也可以回到默认值。本实现选择回到默认值：COMRESET 时 `link_up` 调用 `disk_reset`，写缓存打开、模式回到 UDMA 6。这和断电重启后的状态一致，也符合 Linux 的预期：错误处理复位端口之后，libata 会重新走一遍 IDENTIFY、SET FEATURES，不依赖设备记得之前的设置。

## 六、验证

### 6.1 单元测试

`tests/unit/ahci_test.c` 里和本篇有关的三个用例：

- `case_identify_data` 直接调用 `ahci_identify`，逐项检查第二章表里的字：完整性字的签名和校验和、三个字符串的内容和字节顺序、字 0 bit 15、字 83/84/87 的有效位、`ata_id_is_sata` 的条件（字 93 为 0 且字 80 不小于 0x20）、两个容量字段（包括 129 GiB 的盘上 28 位容量饱和成 0x0FFFFFFF、48 位容量精确），以及不该报的能力（HPA、READ/WRITE MULTIPLE、字 77/78）。这些检查对应的正是第三章那类“命令成功、数据被驱动拒绝或曲解”的错误。
- `case_identify_cmd` 把 IDENTIFY 作为一条命令执行，PRDT 故意拆成 100 字节和 412 字节两段放在不相邻的内存里。检查数据按顺序落进两段、第一段没有写越界、PRDBC 为 512、PxCI 被清、PxTFD 为 40h、PSFIS 区的 FIS 字节 0、1、15、16-17、PxIS 只有 PSS 而没有 DHRS 和 TFES、D2H 区没有被写、中断已触发。
- `case_features` 检查写缓存开关和字 85 的联动、关闭时先 flush；传输模式的接受范围（UDMA 7 被中止，PxTFD 为 0441h），MWDMA 与 UDMA 的互斥，PIO 模式不影响 DMA 模式，不支持的子命令被中止，COMRESET 之后回到默认值。

这些测试会不会漏掉错误，由故意写错的实现来检验：E_Status 带上 DRQ、IDENTIFY 之后 PxTFD 带上 DRQ、关写缓存后写入不落盘，都会被上面的用例抓住。第一种正是 4.4 节说的启动时看不出来的错误。

### 6.2 端到端

`tests/e2e/emu-blk.sh` 启动一个接着两块盘的 guest，检查 dmesg 里的 `ATA-8: MINIVMM AHCI DISK, 1.0, max UDMA/133`、`131072 sectors, multi 0: LBA48 NCQ (depth 32)`、`configured for UDMA/133`、`[sda] Write cache: enabled`，并检查整个探测过程没有出现 `not supported, aborted`。最后一条保证 Linux 没有发出本实现不认识的命令：如果 IDENTIFY 多报了什么能力，Linux 多半会接着发一条相应的命令，它会在这里被发现。

## 七、限制

- 不支持 READ/WRITE MULTIPLE 和 READ/WRITE SECTORS 这类 PIO 读写命令，字 47 低字节为 0。Linux 对能做 DMA 的盘只用 DMA 和 NCQ 命令。
- 不支持 CHS 寻址（字 1、3、6 和字 54-58 为 0）；ATA8-ACS 起 LBA 是必须支持的，Linux 只在字 49 bit 9 为 0 时才走 CHS。
- 没有 HPA、安全功能集、SMART、电源管理的 IDLE 与 SLEEP、设备内统计日志、IDENTIFY DEVICE 数据日志；对应的能力位都不报，用户态工具发来的相应命令一律中止。
- 序列号就是 `--drive` 的 id。序列号字段只有 20 个字符，而 id 最长 31 个字符，超出的部分被截掉；两块盘的 id 只在第 20 个字符之后不同时，序列号会相同。
- 传输模式只做记录，不影响速度。
