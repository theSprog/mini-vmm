# 从零理解 KVM：一次 `out` 指令的完整旅程

> 本文面向刚学完操作系统课程的读者。你需要知道进程、线程、系统调用、页表、特权级这些概念，但不需要任何虚拟化经验。文中出现的 VMCB、VMEXIT、memslot、Virtqueue 之类的术语，第一次出现时都会展开解释。
>
> 全文分两部分：**原理篇**讲清楚"硬件和内核为什么要这样设计"，不贴真实代码；**实现篇**对照 Linux 5.15 的 KVM 源码与一个约 200 行的最小 VMM，讲清楚"这些原理具体落到了哪几行"。

# 原理篇

## 一、虚拟化究竟在虚拟什么

操作系统课程的主线，其实是**一套幻觉的构造术**。

CPU 只有几个核，但每个进程都以为自己独占一颗 CPU——这是时间片调度给的幻觉。物理内存只有几十 GB，但每个进程都以为自己拥有连续的 128 TB 地址空间——这是页表给的幻觉。磁盘上只有一堆扇区，但进程看到的是文件和目录——这是文件系统给的幻觉。

操作系统给进程提供的抽象，叫做**进程抽象**。而虚拟化要做的事情，是把这套把戏再往下推一层：给一整个操作系统提供**机器抽象**。

```
        进程抽象                              机器抽象
  ┌───────────────────┐              ┌───────────────────┐
  │      进程 A       │              │   Guest OS + 应用  │
  ├───────────────────┤              ├───────────────────┤
  │ 看到的"机器"：     │              │ 看到的"机器"：     │
  │  - 虚拟地址空间    │              │  - 物理地址空间    │
  │  - read/write     │              │  - 磁盘控制器      │
  │  - socket         │              │  - 网卡寄存器      │
  │  - 信号           │              │  - 中断控制器      │
  │  - 独占的 CPU     │              │  - 独占的多颗 CPU  │
  ├───────────────────┤              ├───────────────────┤
  │   由 OS 内核提供   │              │  由 Hypervisor 提供│
  └───────────────────┘              └───────────────────┘
```

两者有一个至关重要的差别：

**进程是知情的合作者。** 一个用户态程序知道自己跑在操作系统上。它想读文件，不会去操作磁盘控制器的寄存器，而是老老实实执行 `syscall` 指令，主动把控制权交给内核。这是一份契约，进程自愿遵守。

**Guest OS 是不知情的。** 一个未经改造的 Linux 内核，从加电那一刻起就认为自己是这台机器唯一的主人。它会去写 `CR3` 装载页表，会执行 `cli`/`sti` 关中断，会往端口 `0x3f8` 里写字节以为自己在驱动一块 16550 串口芯片，会执行 `hlt` 让"物理 CPU"停下来等中断。它绝不会主动通知任何人。

于是虚拟化的核心问题变成了一句话：

> **如何在一个不合作、甚至不知情的软件执行到"危险动作"时，把控制权抢回来？**

答案是**陷入与模拟**（Trap-and-Emulate）：让 Guest 大部分指令直接在物理 CPU 上全速跑（毕竟 `add`、`mov`、`jmp` 这些指令无论谁执行，语义都一样，没必要管），但当它执行到会影响到"机器全局状态"的指令时，硬件强制产生一次陷入，把控制权交给 Hypervisor。Hypervisor 看一眼 Guest 想干什么，用软件把这个动作的**效果**伪造出来，然后让 Guest 继续跑。Guest 全程无感。

这与系统调用的机制在形式上是同构的：`syscall` 是软件主动发起的陷入，而虚拟化的陷入是硬件在 Guest 毫不知情的情况下强制发起的。

## 二、Popek-Goldberg 定理与 x86 的原罪

1974 年，Popek 和 Goldberg 发表了一篇论文，给"一个体系结构能否被高效虚拟化"下了严格的判据。他们把指令分成两类：

- **特权指令（Privileged Instruction）**：在非特权级（用户态）执行时会触发异常的指令。比如 `lgdt`、`mov cr3, rax`。
- **敏感指令（Sensitive Instruction）**：会读取或修改机器全局配置、或者行为依赖于当前特权级的指令。比如读中断标志、读段描述符表基址。

定理的结论是：**当且仅当所有敏感指令都是特权指令时，该体系结构可以用陷入-模拟的方式高效虚拟化。**

这个条件的直觉很清楚：如果每一条"危险"的指令都会在降权执行时抛异常，那么 Hypervisor 只要把 Guest OS 从 ring 0 降到 ring 1 或 ring 3 去跑（这叫**Ring 压缩**），所有危险动作就都会自动落到 Hypervisor 手里。

而 x86 在 2005 年之前，**恰恰不满足这个条件**。经典的研究里数出了 17 条"敏感但不特权"的指令。举三个最典型的：

**`popf`**：这条指令从栈上弹出一个值写入 `RFLAGS`，其中包含中断使能位 `IF`。当 Guest OS 想关中断时，它会执行 `cli` 或 `popf`。问题在于，`popf` 在用户态执行时**不会报错**——它只是**静默地忽略**对 `IF` 位的修改。于是 Guest OS 以为自己关了中断，进入了临界区，实际上中断从未被关闭。这类 bug 无声无息，无法被拦截，也就无法被模拟。

**`sgdt` / `sidt` / `smsw`**：这几条指令读取全局描述符表寄存器、中断描述符表寄存器和机器状态字。它们在**任何特权级下都能执行且不报错**，读到的是**物理机器上真实的值**。Guest OS 装载了自己的 IDT 之后，如果 Hypervisor 在切换时把物理 IDTR 换成了自己的，Guest 用 `sidt` 一读就会发现值对不上——幻觉当场破碎。

**`push cs`**：把代码段选择子压栈。选择子的低 2 位是当前特权级 CPL。Guest OS 以为自己在 ring 0，压栈一看低 2 位是 1 或 3，立刻就知道自己被降权了。

面对这个先天缺陷，2005 年之前有三条工程路线：

| 路线 | 代表 | 做法 | 代价 |
|---|---|---|---|
| 二进制翻译 | VMware Workstation | 运行前扫描 Guest 代码，把有问题的指令替换成安全的桩代码 | 需要一个动态翻译器和代码缓存，工程量巨大，且难以处理自修改代码 |
| 半虚拟化 | Xen | 修改 Guest 内核源码，把特权操作全部换成显式的 hypercall | Guest 必须被移植，跑不了闭源系统 |
| 硬件辅助 | Intel VT-x / AMD-V | 改 CPU | 需要换硬件 |

历史选择了第三条。理由很简单：前两条路线本质上都是在软件层面弥补硬件的设计缺陷，而缺陷本身应该由硬件修复。

## 三、硬件辅助虚拟化：给 CPU 加一个正交的维度

很多人对硬件虚拟化的第一印象是"加了一个 ring -1"。这个说法直观但不准确，容易造成后续理解上的困难。

准确的说法是：AMD-V 和 Intel VT-x 给 CPU 状态**加了一个与特权级正交的新维度**。

原来的 CPU 只有一个维度：CPL（ring 0 到 ring 3）。现在有两个维度：

```
                    │  ring 0  │  ring 1  │  ring 2  │  ring 3
    ────────────────┼──────────┼──────────┼──────────┼──────────
     Host 模式       │ Host 内核 │          │          │ Host 用户态
    （Guest 之外）   │  + KVM   │          │          │  + VMM 进程
    ────────────────┼──────────┼──────────┼──────────┼──────────
     Guest 模式      │ Guest 内核│          │          │ Guest 用户态
    （Guest 之中）   │          │          │          │
```

关键点在于：**Guest 模式下的 ring 0 是一个完整的、货真价实的 ring 0**。Guest 内核不需要被降权，它可以正常执行 `lgdt`、写 `CR3`、执行 `cli`——这些指令在 Guest 模式的 ring 0 下**合法执行、行为正常**。Popek-Goldberg 的困境就此消解：不再需要靠"降权 + 异常"来拦截，而是靠一张**可编程的拦截位图**来精确指定"哪些动作要陷出去"。

两家厂商的术语不同：

| | AMD SVM | Intel VMX |
|---|---|---|
| 扩展名称 | Secure Virtual Machine | Virtual Machine Extension |
| 全局开关 | `EFER.SVME` 位 | `CR4.VMXE` + `VMXON` 指令 |
| 两种模式 | Host 模式 / Guest 模式 | VMX Root / VMX Non-root |
| 进入 Guest | `VMRUN` | `VMLAUNCH`（首次）/ `VMRESUME`（后续） |
| 离开 Guest | `#VMEXIT` | VM-Exit |
| 控制结构 | VMCB | VMCS |

从 Guest 模式回到 Host 模式的这次强制切换，AMD 称之为 `#VMEXIT`。虽然名字带 `#`（x86 里 `#` 前缀通常表示异常，比如 `#PF`、`#GP`），但它并不是一次普通异常——它不走 IDT，不查中断门，而是**硬件直接把 CPU 的整套状态换回 Host 的那一套**，然后从 `VMRUN` 指令的下一条继续执行。

这次切换习惯上被称为**世界切换（World Switch）**，因为它换掉的不是几个寄存器，而是整个执行环境：所有段寄存器（含它们不可见的隐藏部分）、控制寄存器、页表基址、中断状态，全部换掉。

## 四、VMCB：Host 与硬件之间的契约

既然要切换整个世界，就必须有个地方存放"另一个世界的完整状态"。在 AMD 上这块内存叫 **VMCB（Virtual Machine Control Block，虚拟机控制块）**。

VMCB 是一个 4 KB 对齐的物理内存页，分成两半：

```
  VMCB（4 KB 物理页）
  ┌──────────────────────────────────────────────┐ 0x000
  │           Control Area  控制区                │
  │  ─────────────────────────────────────────   │
  │  intercepts[]      拦截位图（我要拦哪些动作）  │
  │  iopm_base_pa      I/O 端口权限位图的物理地址  │
  │  msrpm_base_pa     MSR 权限位图的物理地址      │
  │  asid              地址空间标识符（TLB 用）    │
  │  int_ctl / int_vector  中断注入控制            │
  │  nested_cr3        二级页表根（NPT）           │
  │  clean             状态缓存位掩码              │
  │  ─────────────────────────────────────────   │
  │  exit_code         ← 硬件写：为什么退出        │
  │  exit_info_1       ← 硬件写：附加信息 1        │
  │  exit_info_2       ← 硬件写：附加信息 2        │
  │  exit_int_info     ← 硬件写：退出时挂起的中断  │
  └──────────────────────────────────────────────┘ 0x3FF
  ┌──────────────────────────────────────────────┐ 0x400
  │        State Save Area  状态保存区             │
  │  ─────────────────────────────────────────   │
  │  es/cs/ss/ds/fs/gs  段选择子 + 基址 + 界限 + 属性│
  │  gdtr / idtr / ldtr / tr                      │
  │  cr0 / cr2 / cr3 / cr4 / efer                 │
  │  rip / rsp / rflags / rax                     │
  │  cpl                当前特权级                 │
  │  dr6 / dr7          调试寄存器                 │
  └──────────────────────────────────────────────┘ 0xFFF
```

有三点值得单独强调。

**第一，控制区是双向的。** 上半部分（拦截位图、位图基址、ASID）是**软件写给硬件看的**：Hypervisor 在这里声明"我要拦截哪些事件"。下半部分（`exit_code`、`exit_info_1/2`）是**硬件写给软件看的**：陷出时硬件在这里留下退出原因。整个 VMCB 就是 Hypervisor 与 CPU 之间的一份共享内存协议。

**第二，通用寄存器不在 VMCB 里。** 仔细看状态保存区：段寄存器、控制寄存器、`RIP`、`RSP`、`RFLAGS` 都在，唯独通用寄存器只有 `RAX` 一个，`RBX`、`RCX`、`RDX`、`RSI`、`RDI`、`R8`–`R15` 全都不在。

这不是疏漏，而是刻意的性能取舍。x86-64 有 16 个 64 位通用寄存器，如果每次进出 Guest 硬件都强制把它们全部读写内存，每次世界切换要额外产生 256 字节的访存。而世界切换是**极高频**的操作——一个跑满负载的虚拟机每秒可能陷出几万次。厂商的选择是：**硬件只负责那些"没有它就无法正确恢复执行流"的状态**（`RIP` 决定从哪继续，`RSP` 决定栈在哪，段寄存器的隐藏部分软件根本没法直接读写），通用寄存器交给 Hypervisor 自己决定怎么保存——它可以压栈，可以存进自己的结构体，也可以在某些快速路径上干脆不保存。Intel 在这一点上做了完全相同的选择。

代价是，Hypervisor 必须自己写一段汇编来搬运这 15 个寄存器。Linux 里这段汇编在 `arch/x86/kvm/svm/vmenter.S`，它是整个 KVM 中唯一一段"横跨两个世界"的代码：函数的前半段跑在 Host，`vmrun` 那一行进入 Guest，等它返回时，中间已经过了不知道多少个 Guest 时钟周期。

**第三，Intel 的 VMCS 不长这样。** VMCS 同样是一个 4 KB 页，但**格式对软件不透明**：你不能定义一个 C 结构体去 cast 它，因为字段的物理布局由具体 CPU 型号决定，可能是压缩的、乱序的、部分缓存在 CPU 内部的。软件必须用 `VMREAD` / `VMWRITE` 两条指令、通过 32 位编码的"字段号"去访问。

这个差异对写代码的人影响很大：AMD 侧读一个字段就是 `svm->vmcb->control.exit_code`，一次普通内存访问；Intel 侧是 `vmcs_read32(VM_EXIT_REASON)`，展开后是一条 `VMREAD` 指令，开销在数十个周期量级。这也是为什么 Intel 侧的 KVM 代码里到处是"缓存 VMCS 字段"的逻辑，而 AMD 侧相对干净。

反过来，AMD 的平坦结构也有代价：硬件无法知道软件到底改了哪些字段，每次 `VMRUN` 都得重新解析整个 VMCB。AMD 的补丁是 **VMCB Clean Bits**——控制区里有个 `clean` 位掩码，软件用它告诉硬件"从上次退出到现在，第 N 类字段我没动过，你可以直接用流水线里缓存的版本"。这个机制的危险之处在于它是**反向语义**的：改了字段之后忘记清对应的 clean 位，硬件就会用旧值，而且不报任何错。

## 五、拦截位图：把"拦什么"变成可编程的

前面说过，硬件虚拟化不再靠"降权 + 异常"来发现危险动作，而是靠拦截位图。这块设计值得单独看，因为它直接决定了虚拟机的性能上限。

VMCB 控制区里的拦截配置有三种粒度：

**位标志**：`intercepts[]` 数组里，每一位对应一类动作。比如"拦截 `CPUID`"、"拦截 `HLT`"、"拦截 `VMRUN`"、"拦截物理中断"。这类动作数量有限，一位一个就够了。

**I/O 端口权限位图（IOPM）**：x86 有 65536 个 I/O 端口。如果用一个位标志"拦截所有 I/O"，那么 Guest 访问任何端口都要陷出，粒度太粗。AMD 的做法是让 `iopm_base_pa` 指向一块位图，每个端口一位：置 1 表示拦截，置 0 表示放行。65536 位正好是 8 KB，AMD 规定这块区域占 12 KB（多出的部分是为了让跨越端口边界的宽访问能安全地多读几位）。

**MSR 权限位图（MSRPM）**：MSR（Model Specific Register，型号特定寄存器）是 x86 上一大类配置寄存器，用 `rdmsr`/`wrmsr` 访问，编号空间很大。MSRPM 给每个受关注的 MSR 分配**两位**——读一位、写一位，因为很多场景下允许 Guest 读但必须拦截写。

有了细粒度位图，Hypervisor 就能做**选择性直通**：把 Guest 频繁访问、又不影响隔离性的资源放行，只拦真正需要模拟的。这是虚拟化性能优化的主战场之一。

而 KVM 在 I/O 端口上的策略是**全部拦截**——初始化时把整块 IOPM 填成 `0xff`。原因是 x86 的 I/O 端口是全局资源，任何一个端口的直通都可能让 Guest 摸到真实硬件。代价是 Guest 每一条 `in`/`out` 都要陷出一次，这也正是后面 VirtIO 要用 `ioeventfd` 优化的东西。

## 六、一次世界切换的完整时序

把上面的零件拼起来，一次进出 Guest 的完整流程是这样的：

```
  Host 内核态（KVM）                       硬件                    Guest
  ─────────────────────────────────────────────────────────────────────
  1. 填好 VMCB 控制区
     （拦截位图、ASID、NPT 根）
  2. 把 Guest 的段/CR/RIP 写入
     VMCB 状态保存区
  3. clgi          ────────────────►  关闭全局中断标志 GIF
                                      （连 NMI/SMI 都屏蔽）
  4. 用软件把 15 个通用寄存器
     从 KVM 的结构体装进物理寄存器
  5. vmrun %rax    ────────────────►  · 把 Host 的完整状态存进
                                        Host Save Area
                                      · 把 VMCB 状态保存区里的
                                        Guest 状态装进 CPU
                                      · 切到 Guest 模式    ────────► 开始执行
                                                                     Guest 指令
                                                                     ...
                                                                     ...
                                      ◄──────────────────────────── 执行到被
                                      · 检查拦截位图，命中             拦截的动作
                                      · 把 Guest 状态存回 VMCB
                                        状态保存区
                                      · 填 exit_code / exit_info_1/2
                                      · 恢复 Host 状态
                                      · 切回 Host 模式
  6. 从 vmrun 的下一条指令继续 ◄─────
  7. 用软件把 15 个通用寄存器
     存回 KVM 的结构体
  8. stgi          ────────────────►  重新打开 GIF
  9. 读 vmcb->control.exit_code，
     查函数指针表，分发处理
```

第 3 步和第 8 步的 `clgi` / `stgi` 值得解释。**GIF（Global Interrupt Flag，全局中断标志）** 是 AMD 特有的一个硬件标志位，它比 `RFLAGS.IF` 更强：`IF` 只能屏蔽可屏蔽中断，而 GIF 为 0 时连 NMI 和 SMI 都会被推迟。

为什么需要它？因为第 4 步到第 5 步之间存在一个危险窗口：此时 CPU 的通用寄存器里装的已经是 **Guest 的值**，但 CPU 还处于 **Host 模式**。如果这时来一个时钟中断，Host 内核的中断处理程序会在一个寄存器内容完全错乱的上下文里运行，后果是不可预测的。`clgi` 把这个窗口封死。Intel 没有对应的指令，它通过 VMCS 里的中断控制字段以另一套方式解决同样的问题。

**这次切换有多贵？** 数量级上，一次 `VMEXIT` + `VMRUN` 的往返在现代 CPU 上大约是 1000～2000 个时钟周期，如果 Hypervisor 还要做复杂处理（比如软件解码一条指令），实际开销会到几千甚至上万周期。作为对比，一次普通函数调用是几个周期，一次系统调用大约是几百个周期。

**记住这个数量级。**后面所有的虚拟化性能优化——`ioeventfd`、`irqfd`、vhost、SR-IOV——本质上都在做同一件事：**减少陷出次数，或者缩短每次陷出的处理路径。**

## 七、内存虚拟化与三层地址

Step 1 只用到了内存虚拟化的最表层，但背景必须先建立起来，否则后面的 `memslot` 会显得莫名其妙。

在没有虚拟化的机器上，地址只有两层：虚拟地址（VA）经过页表翻译成物理地址（PA）。有了虚拟机之后，变成三层：

```
   Guest 用户程序的指针
         │  GVA (Guest Virtual Address)
         │
         │  ← 由 Guest 自己的页表翻译（Guest CR3 指向它）
         ▼
   Guest 眼中的"物理地址"
         │  GPA (Guest Physical Address)
         │
         │  ← 由 Hypervisor 控制的第二层页表翻译
         ▼
   真实的物理内存地址
            HPA (Host Physical Address)
```

关键在于中间那一层：**GPA 是假的**。Guest 内核以为 `0x100000` 是一个真实的物理内存单元，实际上它只是 Hypervisor 划出来的一段编号。Guest 完全无法察觉——它拿不到 HPA，也没有任何指令能让它看到真实物理地址。

早期的实现（影子页表，Shadow Page Table）用软件维护一张"GVA 直接到 HPA"的合成页表，每当 Guest 修改自己的页表就要同步，代价极高。现代 CPU 直接用硬件做两级翻译：AMD 叫 **NPT（Nested Page Tables，嵌套页表）**，Intel 叫 **EPT（Extended Page Tables，扩展页表）**。开启后，`CR3` 仍然由 Guest 自由使用，第二层页表的根放在 VMCB 的 `nested_cr3` 字段里，MMU 自己走两遍页表。

代价是访存次数的乘法效应：四级页表下，Guest 页表的每一级查找本身都需要一次 GPA→HPA 翻译，最坏情况下一次地址翻译要 24 次物理访存。这就是为什么虚拟化场景里大页（2 MB / 1 GB）比裸机更重要。

**但是——对于写 VMM 的人来说，这一整套复杂性大部分是透明的。** 从用户态 VMM 的视角看，事情简单得多：

```
  VMM 进程的虚拟地址空间                   Guest 眼中的物理地址空间
  ┌────────────────────────┐              ┌────────────────────────┐
  │                        │              │                        │
  │  ...                   │              │                        │
  │                        │              │                        │
  │  ┌──────────────────┐  │   memslot    │  ┌──────────────────┐  │
  │  │                  │  │◄────────────►│  │                  │  │
  │  │  mmap() 出来的    │  │   注册映射    │  │   GPA 0x000000   │  │
  │  │  一大块匿名内存    │  │              │  │      ...         │  │
  │  │  (HVA)           │  │              │  │   GPA 0x200000   │  │
  │  │                  │  │              │  │                  │  │
  │  └──────────────────┘  │              │  └──────────────────┘  │
  │                        │              │                        │
  │  ...                   │              │   0xd0000000 ─────────►│ 没有 memslot
  │                        │              │   （留给 MMIO 设备）    │ → 访问会陷出
  └────────────────────────┘              └────────────────────────┘
```

VMM 用 `mmap` 申请一块普通匿名内存，然后告诉 KVM："**GPA 的 [0, 2 MB) 这段，对应我进程里 HVA 从 `addr` 开始的这段。**"这条注册记录就叫一个 **memslot（内存槽）**。

从此以后：

- Guest 访问这段 GPA 时，KVM 会（在第一次访问触发缺页时惰性地）建立 NPT 映射，让硬件直接翻译，全速运行，**不产生任何陷出**。
- VMM 想看 Guest 内存里有什么，直接解引用自己的指针就行——同一份物理内存，两个虚拟地址视图。这一点在后面实现 VirtIO 时至关重要：Virtqueue 里放的全是 GPA，VMM 要做的就是 `HVA = slot_base_hva + (GPA - slot_base_gpa)`。
- **没有被任何 memslot 覆盖的 GPA**，硬件走 NPT 时会失败，产生嵌套缺页 `#NPF`，KVM 发现这地址不属于任何内存槽，就判定它是 MMIO 访问，交给 VMM 去模拟设备。**"哪块地址是内存，哪块地址是设备"这件事，就是靠 memslot 的有无来划分的。**

## 八、KVM 的定位：把硬件能力包装成文件描述符

现在轮到 KVM 本身。有一个常见误解需要先澄清：

> **KVM 不是一个完整的虚拟机监控器。**

KVM（Kernel-based Virtual Machine）是 Linux 内核里的一个驱动模块，它只做两件事：**CPU 虚拟化**（管理 VMCB、执行 `VMRUN`、处理陷出）和**内存虚拟化**（管理 memslot、维护 NPT）。至于"这台虚拟机有一块什么型号的网卡"、"磁盘镜像是 qcow2 还是 raw"、"串口输出到哪里"——KVM 一概不管。这些属于**设备模型（Device Model）**，全部由用户态程序负责。

那个用户态程序才是真正的 VMM。QEMU 是其中最全能的一个，Firecracker、crosvm、kvmtool 是更轻量的实现。它们的共同点是：都通过同一套 `ioctl` 接口驱动 KVM。

Linux 把这套能力组织成了**三层文件描述符**，层次关系清晰得像一棵树：

```
  open("/dev/kvm")  ──►  system fd  ────── 全局能力
      │                                    · KVM_GET_API_VERSION
      │                                    · KVM_CHECK_EXTENSION（查特性）
      │                                    · KVM_GET_VCPU_MMAP_SIZE
      │
      └─ ioctl(KVM_CREATE_VM) ──► VM fd  ── 一台虚拟机
             │                             · KVM_SET_USER_MEMORY_REGION
             │                             · KVM_CREATE_IRQCHIP
             │                             · KVM_IOEVENTFD / KVM_IRQFD
             │
             ├─ ioctl(KVM_CREATE_VCPU, 0) ──► vCPU fd 0 ── 一个虚拟 CPU
             │      │                        · KVM_GET/SET_REGS
             │      │                        · KVM_GET/SET_SREGS
             │      │                        · KVM_RUN     ← 核心
             │      │
             │      └─ mmap(vcpu_fd) ──► 与内核共享的通信页
             │
             └─ ioctl(KVM_CREATE_VCPU, 1) ──► vCPU fd 1
                    └─ mmap(vcpu_fd) ──► ...
```

这个设计非常"Unix"：资源即文件，层级即父子，权限即文件权限（这也是为什么把用户加进 `kvm` 组就能不用 root 跑虚拟机）。多核虚拟机的实现也因此变得自然——**每个 vCPU 是一个 fd，VMM 为每个 vCPU 起一个线程，各自阻塞在自己的 `KVM_RUN` 上**。Guest 里的"多核并行"，在 Host 看来就是几个普通线程被调度器分配到不同物理核上。

## 九、`kvm_run`：为什么用共享内存而不是 ioctl 参数

上面那棵树里有一个东西看起来很突兀：为什么 vCPU fd 要 `mmap`？

因为 `KVM_RUN` 这个 `ioctl` 的返回信息量太大、频率太高。

`ioctl` 的传统用法是通过第三个参数传一个结构体指针，内核用 `copy_to_user` 把结果拷回来。但 vCPU 陷出时要传递的信息可能包括：退出原因、端口号、数据、物理地址、指令长度、中断状态……而且这个动作每秒会发生上万次。每次都做一遍参数拷贝，是纯粹的浪费。

KVM 的做法是：在创建 vCPU 时内核分配好一块内存，VMM 用 `mmap(vcpu_fd)` 把它映射到自己的地址空间。此后**内核和用户态直接读写同一块物理内存**，`KVM_RUN` 这个 `ioctl` 退化成一个纯粹的"信号"——它不传参数，也不返回数据，只表示"去跑吧"和"我回来了"。

这块共享区域的布局是（x86 上）：

```
   mmap(vcpu_fd, KVM_GET_VCPU_MMAP_SIZE 返回的大小)
   ┌──────────────────────────────────────────┐  offset 0
   │  第 0 页：struct kvm_run                  │
   │  ┌────────────────────────────────────┐  │
   │  │ request_interrupt_window  (in)     │  │  ← 用户态写，内核读
   │  │ immediate_exit            (in)     │  │
   │  ├────────────────────────────────────┤  │
   │  │ exit_reason               (out)    │  │  ← 内核写，用户态读
   │  │ ready_for_interrupt_injection      │  │
   │  │ if_flag                            │  │
   │  ├────────────────────────────────────┤  │
   │  │ union {                            │  │  ← 按 exit_reason 解释
   │  │   struct { ... } io;               │  │     的联合体
   │  │   struct { ... } mmio;             │  │
   │  │   struct { ... } hypercall;        │  │
   │  │   ...                              │  │
   │  │ }                                  │  │
   │  └────────────────────────────────────┘  │
   ├──────────────────────────────────────────┤  offset 4096
   │  第 1 页：PIO 数据页                       │
   │  （端口 I/O 的实际数据放这里）              │
   ├──────────────────────────────────────────┤  offset 8192
   │  可选：coalesced MMIO ring                │
   │  可选：dirty ring                         │
   └──────────────────────────────────────────┘
```

注意第 1 页的存在。`struct kvm_run` 里的 `io` 成员**不包含数据本身**，只有一个 `data_offset` 字段，指向数据在这块 mmap 区域里的偏移。为什么要绕这一道？因为一条 `rep outsb` 指令可以一次输出几千字节，塞不进 `struct kvm_run` 那个几十字节的联合体，所以数据必须放在独立的页里。

**这也是为什么绝不能用 `sizeof(struct kvm_run)` 作为 `mmap` 的长度**，必须老老实实调 `KVM_GET_VCPU_MMAP_SIZE`——真实大小至少是两页，而且随内核配置变化。这是新手最常犯的错误之一，症状是访问 PIO 数据时段错误。

## 十、VMM 的本质：一个 while 循环

所有的铺垫结束了。一个 VMM 的主体逻辑，无论是 200 行的玩具还是 QEMU，都可以概括成这个循环：

```
  准备阶段：
      打开 /dev/kvm
      创建 VM
      申请内存，注册 memslot
      把 Guest 代码/内核镜像拷进那块内存
      创建 vCPU，mmap 共享页
      设置 vCPU 的初始寄存器状态

  运行阶段：
      while (true) {
          ioctl(vcpu_fd, KVM_RUN);        // 阻塞：进入 Guest，直到陷出

          switch (run->exit_reason) {
              case KVM_EXIT_IO:            // Guest 执行了 in/out
                  模拟设备的端口读写;
                  break;
              case KVM_EXIT_MMIO:          // Guest 访问了设备内存
                  模拟设备的寄存器读写;
                  break;
              case KVM_EXIT_HLT:           // Guest 执行了 hlt
                  return;                  // 或者等待中断
              case KVM_EXIT_SHUTDOWN:      // Guest 崩了（triple fault）
                  报错退出;
              default:
                  处理其他情况;
          }
      }
```

值得停下来体会一下这个循环的形态：**它和一个事件驱动的网络服务器几乎一模一样。** `KVM_RUN` 相当于 `epoll_wait`，`exit_reason` 相当于事件类型，各个 `case` 分支相当于事件处理函数。整台虚拟机的运行，在 Host 看来就是一个线程反复阻塞在一个系统调用上，醒来处理事件，再睡回去。

理解了这一点，后面所有复杂特性的位置就都清楚了：VirtIO 是 `KVM_EXIT_MMIO` 分支里的一套协议，`ioeventfd` 是把某个 MMIO 地址的陷出提前在内核里转成 eventfd 信号从而**跳过这个循环**，vhost 是把整个设备后端搬进内核从而**连用户态都不用回**。

# 实现篇

原理篇讲的是"为什么"。这一部分对照 Linux 5.15 的真实源码，讲清楚一个最小 VMM 的每一步在内核里对应什么，以及一次 `out` 指令是如何完整穿透四个层次的。

本节的目标程序是一个约 200 行的 C 程序：它创建一台虚拟机，放进去一段 16 位实模式汇编，让这段汇编往串口端口写几个字符，然后停机。功能上等价于 `kvm-hello-world`，但我们要把每一行背后的机制讲透。

## 十一、最小 VMM 的骨架

### 11.1 打开设备与版本握手

```c
int kvm_fd = open("/dev/kvm", O_RDWR | O_CLOEXEC);
int version = ioctl(kvm_fd, KVM_GET_API_VERSION, 0);
if (version != 12)
    fatal("unexpected KVM API version");
```

`KVM_API_VERSION` 在 5.15 的 `include/uapi/linux/kvm.h` 里是 12，而且从 2007 年至今就没变过，未来也不会变。KVM 的 ABI 演进方式不是升版本号，而是**通过 `KVM_CHECK_EXTENSION` 逐个特性查询**：

```c
if (ioctl(kvm_fd, KVM_CHECK_EXTENSION, KVM_CAP_USER_MEMORY) <= 0)
    fatal("required capability missing");
```

这个设计的好处是新老 VMM 和新老内核可以任意组合：老 VMM 在新内核上跑，只是用不到新特性；新 VMM 在老内核上跑，能力查询失败就降级。这是内核 ABI 兼容性的标准做法，值得在自己的项目里借鉴。

`O_CLOEXEC` 不是可选项。VMM 通常要 `fork`/`exec` 辅助进程（比如网络配置脚本），把 `/dev/kvm` 的 fd 泄漏给子进程是一个真实的安全问题。

### 11.2 创建虚拟机

```c
int vm_fd = ioctl(kvm_fd, KVM_CREATE_VM, 0);
```

这一行在内核里做的事情不多，但值得知道它做了什么：分配一个 `struct kvm` 对象，初始化它的 memslot 数组（此时全空）、vCPU 数组（此时全空）、以及一把保护这些结构的锁；给它分配一个新的地址空间标识。

此刻这台虚拟机**没有内存、没有 CPU、没有任何设备**。它只是一个空壳。

### 11.3 申请 Guest 内存

```c
void *mem = mmap(NULL, MEM_SIZE,
                 PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE,
                 -1, 0);
```

有几个决策点：

**为什么用 `mmap` 而不是 `malloc`？** 三个原因。一是需要页对齐——`KVM_SET_USER_MEMORY_REGION` 要求 `userspace_addr` 页对齐，`malloc` 不保证。二是需要控制标志位，比如后续要用大页时需要 `MADV_HUGEPAGE`，要支持内存气球时需要 `MADV_DONTNEED`。三是 `malloc` 对于几个 GB 的分配本来也是转发给 `mmap` 的，中间那层 glibc 分配器只会添乱。

**`MAP_NORESERVE` 的意义。** 匿名映射是惰性的：`mmap` 只是在进程的地址空间里划出一段区间，并不真的分配物理页。物理页要等到**第一次访问触发缺页**时才分配。这意味着一台配置了 4 GB 内存、实际只用了 200 MB 的虚拟机，在 Host 上真的只占 200 MB。这是虚拟化超售（overcommit）的物理基础。

**这块内存在 Guest 眼里就是"物理内存条"。** Guest 内核启动时探测到的可用物理内存、它的 `page_alloc` 分配的每一个页帧、它的页表本身——全都落在这块 `mmap` 区域里。你在 VMM 里 `memcpy` 到 `mem + 0x1000`，Guest 就会在物理地址 `0x1000` 处看到这些字节。

### 11.4 注册内存槽

```c
struct kvm_userspace_memory_region region = {
    .slot            = 0,
    .flags           = 0,
    .guest_phys_addr = 0,              /* GPA 起点，必须页对齐 */
    .memory_size     = MEM_SIZE,       /* 必须是页的整数倍 */
    .userspace_addr  = (uint64_t)mem,  /* HVA 起点 */
};
ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION, &region);
```

这就是原理篇第七节说的那条注册记录。结构体只有五个字段，但语义相当丰富：

- **`slot` 是槽位编号，不是地址。** 一台虚拟机可以注册多个槽，用来拼出带空洞的物理地址布局。真实的 x86 虚拟机通常至少有两个槽：低端 640 KB 以下一个，1 MB 以上一个，中间那段是历史遗留的 VGA/BIOS 空洞。
- **不同槽的 GPA 区间不能重叠**，否则 `ioctl` 返回 `EINVAL`。
- **把 `memory_size` 设成 0 表示删除这个槽。** 这是热插拔内存和 MMIO 区域动态重映射的机制。
- **`flags` 里的 `KVM_MEM_LOG_DIRTY_PAGES`** 会让 KVM 记录哪些 GPA 被写过。这是热迁移和快照的基础设施——迁移时先全量拷贝，然后反复拷贝脏页直到收敛。Step 1 用不到，但它就在这里等着。
- **注册不等于建立映射。** 这条 `ioctl` 只是往内核的 memslot 数组里插了一条记录，**不会**立刻建立 NPT 页表项。Guest 第一次访问某个 GPA 时硬件产生 `#NPF`，KVM 查 memslot 表，算出对应的 HVA，走一遍 Host 的缺页流程拿到物理页，才建立映射。**两层惰性分配就这样串起来了。**

### 11.5 创建 vCPU 与共享页

```c
int vcpu_fd = ioctl(vm_fd, KVM_CREATE_VCPU, 0);   /* 0 是 vCPU 索引 */

int mmap_size = ioctl(kvm_fd, KVM_GET_VCPU_MMAP_SIZE, 0);
struct kvm_run *run = mmap(NULL, mmap_size,
                           PROT_READ | PROT_WRITE, MAP_SHARED,
                           vcpu_fd, 0);
```

内核在 `KVM_CREATE_VCPU` 里分配了 `struct kvm_vcpu`，而对 AMD 平台来说，`svm_vcpu_create()` 会在这里做几件关键的事：分配那个 4 KB 的 VMCB 物理页、分配 8 KB 的 MSR 权限位图、把 VMCB 控制区按默认策略填好。

`init_vmcb()` 里那一长串拦截设置，就是原理篇第五节说的位图。摘录 5.15 的实际代码：

```c
/* 摘自 arch/x86/kvm/svm/svm.c: init_vmcb() */
svm_set_intercept(svm, INTERCEPT_CPUID);
svm_set_intercept(svm, INTERCEPT_IOIO_PROT);     /* I/O 端口访问 */
svm_set_intercept(svm, INTERCEPT_MSR_PROT);      /* MSR 访问 */
svm_set_intercept(svm, INTERCEPT_VMRUN);         /* 嵌套虚拟化 */
svm_set_intercept(svm, INTERCEPT_SHUTDOWN);      /* triple fault */
...
if (!kvm_hlt_in_guest(vcpu->kvm))
    svm_set_intercept(svm, INTERCEPT_HLT);       /* hlt 指令 */

control->iopm_base_pa  = __sme_set(iopm_base);   /* 全 1 的 I/O 位图 */
control->msrpm_base_pa = __sme_set(__pa(svm->msrpm));
```

其中 `iopm_base` 指向的那块 12 KB 内存，在模块初始化时被填成了 `memset(iopm_va, 0xff, ...)`——**所有 65536 个端口全部拦截**。这决定了下一节 `out` 指令的命运。

### 11.6 设置初始寄存器：为什么必须改 CS

vCPU 被创建出来时，KVM 已经按照 x86 的**加电复位规范**初始化了它的状态。5.15 的 `kvm_vcpu_reset()` 里写得明明白白：

```c
kvm_rip_write(vcpu, 0xfff0);
/* 而 init_vmcb() 里：*/
save->cs.selector = 0xf000;
save->cs.base     = 0xffff0000;
```

实模式下取指的物理地址是 `CS.base + RIP`，所以复位后 vCPU 会从 **`0xFFFFFFF0`** 开始取指。这就是每一台真实 x86 机器加电后的第一条指令地址——那里应该是主板 BIOS ROM 的最后 16 个字节，通常放着一条跳转指令。

我们的虚拟机没有 BIOS，那个地址上什么都没有（也不在任何 memslot 里）。所以必须改：

```c
struct kvm_sregs sregs;
ioctl(vcpu_fd, KVM_GET_SREGS, &sregs);

sregs.cs.base     = 0;      /* 段基址清零 */
sregs.cs.selector = 0;
ioctl(vcpu_fd, KVM_SET_SREGS, &sregs);

struct kvm_regs regs = {
    .rip    = 0x1000,       /* 我们把代码拷到 GPA 0x1000 */
    .rflags = 0x2,          /* ← 注意这个值 */
};
ioctl(vcpu_fd, KVM_SET_REGS, &regs);
```

**`rflags = 0x2` 是一个必须记住的细节。** `RFLAGS` 的 bit 1 是保留位，x86 规定它**恒为 1**。如果你把 `rflags` 初始化成 0，`VMRUN` 会在硬件的状态合法性检查阶段直接失败，你会看到 `KVM_RUN` 返回后 `exit_reason` 是 `KVM_EXIT_FAIL_ENTRY`，`hardware_entry_failure_reason` 是 `0xffffffffffffffff`（`SVM_EXIT_ERR`）。这个报错没有任何有用信息，是新手最容易卡住的地方之一。

另外注意 `KVM_GET_SREGS` / `KVM_SET_SREGS` 是"读-改-写"模式：先读出内核给的完整合法状态，只改需要改的字段，再写回去。绝不要自己从零构造一个 `struct kvm_sregs`——里面有大量段属性位、`CR0` 的保留位、`EFER` 的状态，构造错了同样是 `KVM_EXIT_FAIL_ENTRY`。

### 11.7 为什么可以直接跑 16 位实模式代码

这是一个容易被忽略但很有意思的点。

我们让 vCPU 从复位状态直接开跑，意味着它跑在 **16 位实模式**下——没有分页、没有保护模式、段寄存器还是"基址 = 选择子 × 16"的古老语义。

**在 AMD SVM 上，这是天然支持的。** SVM 的 Guest 模式对实模式没有任何特殊要求，VMCB 里存的就是完整的段基址/界限/属性，硬件直接按实模式语义执行。

**在早期 Intel VT-x 上则不行。** 最初的 VMX 规范要求 Guest 必须处于保护模式且开启分页，否则 `VMENTRY` 失败。为了跑实模式代码（每台虚拟机开机都要跑 BIOS，都是实模式），KVM 不得不用软件模拟 vm86 模式，还需要用户态提供一块专门的内存给假的 TSS 和恒等映射页表——这就是 `KVM_SET_TSS_ADDR` 和 `KVM_SET_IDENTITY_MAP_ADDR` 这两个 `ioctl` 存在的原因。它们**只在 Intel 平台上需要**，AMD 平台调用了也是空操作。后来 Intel 加入了 **unrestricted guest** 特性，硬件才原生支持实模式 Guest。

写跨平台 VMM 时，这是必须记住的少数几个真实差异之一。

### 11.8 载荷：一段 16 位汇编

```asm
    ; 这段代码被拷贝到 GPA 0x1000
    mov  al, 'H'
    out  0x3f8, al      ; 往 COM1 的数据端口写一个字节
    mov  al, 'i'
    out  0x3f8, al
    mov  al, 0x0a
    out  0x3f8, al
    hlt                 ; 停机
```

端口 `0x3f8` 是 x86 上 COM1 串口的基地址，其中偏移 0 是数据寄存器。真实硬件上，往这个端口写一个字节，16550 UART 芯片就会把它串行发送出去。我们的 VMM 会拦截这次写，然后把字节打到 Host 的标准输出上——**这就是"模拟一个设备"的最小形态**。

Guest 物理内存的布局是这样的：

```
   GPA
   0x000000  ┌────────────────────────────┐
             │   （未使用）                │
   0x001000  ├────────────────────────────┤  ← RIP 从这里开始
             │   16 位机器码               │
             │   b0 48        mov al,0x48 │
             │   e6 f8        out 0xf8,al │
             │   b0 69        mov al,0x69 │
             │   e6 f8        out 0xf8,al │
             │   f4           hlt         │
   0x001010  ├────────────────────────────┤
             │                            │
             │   （未使用）                │
             │                            │
   0x200000  └────────────────────────────┘  ← memslot 边界，2 MB
                                              超过这里就没有映射了
```

补充一个编码细节：`out 0x3f8, al` 因为端口号超过 255，不能用 8 位立即数编码（`E6 imm8`），实际要写成 `mov dx, 0x3f8` + `out dx, al`（`EE`）。上图为了简洁用了 `0xf8` 端口示意。这类细节在手写机器码时必须查手册确认。

### 11.9 运行循环

```c
for (;;) {
    if (ioctl(vcpu_fd, KVM_RUN, 0) < 0)
        fatal("KVM_RUN failed: %s", strerror(errno));

    switch (run->exit_reason) {
    case KVM_EXIT_IO:
        if (run->io.direction == KVM_EXIT_IO_OUT &&
            run->io.port == 0x3f8) {
            /* 数据不在 run 结构体里，在 run + data_offset 处 */
            char *data = (char *)run + run->io.data_offset;
            fwrite(data, run->io.size, run->io.count, stdout);
        }
        break;

    case KVM_EXIT_HLT:
        printf("guest halted\n");
        return 0;

    case KVM_EXIT_SHUTDOWN:
        fatal("guest triple faulted");

    case KVM_EXIT_FAIL_ENTRY:
        fatal("VMRUN failed, reason 0x%llx",
              run->fail_entry.hardware_entry_failure_reason);

    default:
        fatal("unhandled exit reason %d", run->exit_reason);
    }
}
```

注意 `char *data = (char *)run + run->io.data_offset;` 这一行——指针基准是 `run`，也就是那块 mmap 区域的起点，`data_offset` 是相对它的偏移。这就是前面说的第 1 页。

至此，一个能跑的 VMM 就完整了。下面进入本文最核心的部分。

## 十二、一次 `out` 的完整穿透

Guest 执行 `out dx, al` 这一条单字节指令时，究竟发生了什么？完整链路如下：

```
┌─ Guest 模式 ─────────────────────────────────────────────────────────┐
│                                                                      │
│  RIP=0x1005:  out %al, (%dx)      ; DX=0x3f8, AL='H'                │
│                     │                                                │
└─────────────────────┼────────────────────────────────────────────────┘
                      │ (1) CPU 查 VMCB 的 IOPM 位图，
                      │     端口 0x3f8 对应的位 = 1 → 拦截
                      ▼
┌─ 硬件（AMD SVM）─────────────────────────────────────────────────────┐
│                                                                      │
│  · 指令不执行，Guest 状态回退到指令边界                                │
│  · Guest 的 CS/RIP/RSP/RFLAGS/RAX 等存回 VMCB.save                    │
│  · exit_code   = 0x07b  (SVM_EXIT_IOIO)                             │
│  · exit_info_1 = 端口/方向/宽度编码（见下）                            │
│  · exit_info_2 = 下一条指令的 RIP                                     │
│  · 恢复 Host 状态，切回 Host 模式                                      │
│  · 从 vmrun 的下一条指令继续执行                                       │
│                     │                                                │
└─────────────────────┼────────────────────────────────────────────────┘
                      │ (2)
                      ▼
┌─ Host 内核态（Linux 5.15 KVM）───────────────────────────────────────┐
│                                                                      │
│  vmenter.S: 把 15 个 GPR 存回 vcpu->arch.regs，恢复 Host GPR，ret    │
│      │                                                               │
│  svm_vcpu_run()  → stgi()  重新打开全局中断                           │
│      │                                                               │
│  handle_exit()   → 读 vmcb->control.exit_code = 0x07b                │
│      │             → 查函数指针表 svm_exit_handlers[0x07b]            │
│      ▼                                                               │
│  io_interception()                                                   │
│      │  从 exit_info_1 解出：port=0x3f8, in=0, size=1, string=0      │
│      ▼                                                               │
│  kvm_fast_pio()  → kvm_fast_pio_out()                               │
│      │  ★ 数据直接从 vcpu 的 RAX 寄存器读出，无需解码指令              │
│      ▼                                                               │
│  emulator_pio_out() → kernel_pio()                                  │
│      │  先问：这个端口有没有内核内的模拟设备接管？                      │
│      │  （in-kernel PIT / PIC / 串口重定向等）                        │

│      ▼                                                               │
│  填 kvm_run：                                                        │
│      run->exit_reason    = KVM_EXIT_IO                              │
│      run->io.direction   = KVM_EXIT_IO_OUT                          │
│      run->io.size        = 1                                        │
│      run->io.port        = 0x3f8                                    │
│      run->io.count       = 1                                        │
│      run->io.data_offset = 4096      ← 数据放在第 1 页               │
│      *(char *)(pio_data) = 'H'                                      │
│      │                                                               │
│  kvm_skip_emulated_instruction()  ← ★ RIP 在返回用户态前就推进好了     │
│      │                                                               │
│  vcpu_enter_guest() 返回 0 → 跳出内层循环                             │
│      │                                                               │
└──────┼───────────────────────────────────────────────────────────────┘
       │ (3) ioctl(KVM_RUN) 返回 0
       ▼
┌─ Host 用户态（VMM 进程）──────────────────────────────────────────────┐
│                                                                      │
│  从 ioctl 返回，读 run->exit_reason == KVM_EXIT_IO                    │
│  读 run->io.port == 0x3f8   → 认出这是串口                            │

│      │                                                               │
└──────┼───────────────────────────────────────────────────────────────┘
       │ (4)
       ▼
   回到 KVM → vmrun → Guest 从 RIP+2 继续执行下一条指令
```

这条链路上有五个点值得展开。

### 12.1 `exit_info_1` 的编码

硬件通过一个 32 位字段把 I/O 访问的全部属性打包传出来：

```
   exit_info_1  位布局
   ┌───────────────────────────┬──┬───┬───┬─┬─┬─┐
   │  31            16         │15│ 9-7│6-4│3│2│0│
   ├───────────────────────────┼──┼───┼───┼─┼─┼─┤
   │      端口号 (16 位)        │  │ASZ│SZ │R│S│T│
   └───────────────────────────┴──┴───┴───┴─┴─┴─┘
     T   bit 0     = 1 表示 IN，= 0 表示 OUT
     S   bit 2     = 1 表示串操作（ins/outs）
     R   bit 3     = 1 表示带 REP 前缀
     SZ  bit 6-4   操作宽度：1/2/4 字节
     ASZ bit 9-7   地址宽度（串操作用）
```

对应 5.15 的解码代码：

```c
/* 摘自 arch/x86/kvm/svm/svm.c: io_interception() */
u32 io_info = svm->vmcb->control.exit_info_1;

string = (io_info & SVM_IOIO_STR_MASK) != 0;
in     = (io_info & SVM_IOIO_TYPE_MASK) != 0;
port   = io_info >> 16;
size   = (io_info & SVM_IOIO_SIZE_MASK) >> SVM_IOIO_SIZE_SHIFT;

if (string)
    return kvm_emulate_instruction(vcpu, 0);   /* 串操作走完整模拟器 */

svm->next_rip = svm->vmcb->control.exit_info_2;
return kvm_fast_pio(vcpu, size, port, in);     /* 简单情况走快速路径 */
```

注意 `string` 那个分支：`outsb` 这类串操作要访问 Guest 内存、要递增 `RSI`、可能带 `REP` 循环几千次，硬件给的信息不够，必须调用 KVM 内部的完整 x86 指令模拟器。而普通的 `out` 走 `kvm_fast_pio` 这条几十行的快速路径。**这种"常见情况走快路，复杂情况回退到通用模拟器"的分层结构，在 KVM 里随处可见。**

### 12.2 为什么端口 I/O 不需要软件解码指令，而 MMIO 需要

这是理解 KVM 设备模拟的一个关键分水岭。

对于 `out` 指令，硬件在 `exit_info_1` 里给出了端口号和宽度，而**要写的数据永远在 `RAX` 里**（这是 `out` 指令的语义强制规定的）。所以 KVM 直接 `kvm_rax_read(vcpu)` 就拿到了数据，一次寄存器读取，成本几乎为零。

对于 MMIO（比如 `mov %eax, (%rdi)` 写一个设备寄存器），情况完全不同。硬件产生 `#NPF` 时只告诉 KVM"某个 GPA 发生了写违规"，**它不告诉你写的是什么值，也不告诉你数据来自哪个寄存器**——因为写操作的源可以是任意寄存器、任意立即数、任意寻址模式。KVM 别无选择，只能：

1. 根据 Guest 的 `RIP` 反向读取 Guest 内存里的指令字节；
2. 调用 `x86_emulate_instruction()` 完整解码这条 x86 指令；
3. 从解码结果里找出源操作数，再从 `vcpu->arch.regs[]` 里取出实际数值。

一个完整的 x86 指令解码器，是 KVM 里最复杂的组件之一（`arch/x86/kvm/emulate.c` 有五千多行）。所以从性能角度说，**端口 I/O 的陷出比 MMIO 的陷出便宜得多**。

这也解释了一个初看反直觉的现象：VirtIO 的 MMIO 传输层看起来比 PCI 端口 I/O 更"现代"，但单次访问的陷出成本反而更高。真正的性能解药不是换传输层，而是 `ioeventfd`——把特定 MMIO 地址的写操作在内核里直接转成一次 eventfd 通知，**根本不进指令模拟器，也不回用户态**。

### 12.3 RIP 由谁推进

这是一个必须明确的责任边界问题：陷出之后，Guest 的 `RIP` 还停在 `out` 这条指令上（硬件把状态回退到了指令边界）。如果没人推进它，恢复执行后会再次执行同一条 `out`，无限循环。

答案是：**内核负责，用户态不用管。** 看 `kvm_fast_pio` 的实现：

```c
int kvm_fast_pio(struct kvm_vcpu *vcpu, int size, unsigned short port, int in)
{
    int ret;
    if (in)
        ret = kvm_fast_pio_in(vcpu, size, port);
    else
        ret = kvm_fast_pio_out(vcpu, size, port);
    return ret && kvm_skip_emulated_instruction(vcpu);
}
```

`kvm_skip_emulated_instruction()` 把 `RIP` 推进到 `exit_info_2` 给出的下一条指令地址。这发生在**返回用户态之前**。所以用户态 VMM 只需要处理数据，不需要碰寄存器。

顺带一提，5.15 的 `kvm_fast_pio_out()` 里有一段有趣的注释：

```c
/*
 * Workaround userspace that relies on old KVM behavior of %rip being
 * incremented prior to exiting to userspace to handle "OUT 0x7e".
 */
if (port == 0x7e && kvm_check_has_quirk(vcpu->kvm, KVM_X86_QUIRK_OUT_7E_INC_RIP))
```

这是为了兼容某个依赖旧行为的用户态程序而保留的特殊逻辑。内核 ABI 一旦发布就不能破坏，哪怕只有一个用户——这条规则的代价就是这种针对单个端口号的兼容分支。

### 12.4 `KVM_EXIT_HLT` 为什么会出现

Guest 执行 `hlt` 时，我们的 VMM 收到 `KVM_EXIT_HLT`。但如果你用 QEMU 跑一台正常的 Linux 虚拟机，会发现几乎看不到这个退出——Guest 的 idle 循环里 `hlt` 每秒执行几千次，却不会陷到用户态。

原因在 5.15 的这段代码里：

```c
static int __kvm_vcpu_halt(struct kvm_vcpu *vcpu, int state, int reason)
{
    ++vcpu->stat.halt_exits;
    if (lapic_in_kernel(vcpu)) {
        vcpu->arch.mp_state = state;    /* 内核内部处理，不回用户态 */
        return 1;
    } else {
        vcpu->run->exit_reason = reason;  /* 回用户态 */
        return 0;
    }
}
```

分支的条件是 **`lapic_in_kernel(vcpu)`**：这台虚拟机有没有内核内的本地 APIC（中断控制器）。

- QEMU 会调用 `KVM_CREATE_IRQCHIP`，让 KVM 在内核里模拟 LAPIC/IOAPIC/PIC。此时 `hlt` 的语义是"停下来等中断"，而中断也在内核里，KVM 完全有能力自己处理：把 vCPU 置为 HALTED 状态，在内核里睡眠，等中断来了再唤醒。**用户态全程不知情**，省掉一次往返。
- 我们的最小 VMM 没有创建 irqchip，KVM 里没有中断控制器，它无法判断什么时候该唤醒这个 vCPU，只能把决定权交给用户态。

所以 `KVM_EXIT_HLT` 更像是一个"简化配置下的产物"。理解这一点，也就理解了为什么后面实现中断时，`KVM_CREATE_IRQCHIP` 是一个性能上的必选项——它把整个中断处理路径都留在了内核里。

### 12.5 责任边界总结

把这一节的内容压缩成一张表：

| 职责 | 硬件 | KVM（内核） | VMM（用户态） |
|---|---|---|---|
| 判断是否需要陷出 | ✔ 查拦截位图 | 配置位图 | — |
| 保存/恢复 Guest 状态 | ✔ 段/CR/RIP/RSP/RAX | ✔ 15 个通用寄存器 | — |
| 给出退出原因 | ✔ exit_code | 翻译成 KVM_EXIT_* | 读取分发 |
| 解码指令（MMIO 时） | — | ✔ x86 模拟器 | — |
| 推进 RIP | — | ✔ | — |
| 地址翻译 GVA→GPA→HPA | ✔ 二维页表漫游 | 维护 NPT | 注册 memslot |
| **模拟设备行为** | — | 少数几个（PIC/PIT/LAPIC） | ✔ **绝大部分** |
| 决定 Guest 内存布局 | — | — | ✔ |

最后一行是重点：**VMM 存在的意义，就是那张"绝大部分设备"的表。** CPU 和内存的虚拟化，硬件和 KVM 已经替你做完了；从这里往后的所有工作——串口、块设备、网卡、中断路由、VirtIO 协议、快照——都是在这个 `while (KVM_RUN)` 循环的各个 `case` 分支里填内容。

## 十三、调试清单

写第一个 VMM 时会撞上的坑，按出现频率排序：

**`KVM_RUN` 返回 `KVM_EXIT_FAIL_ENTRY`，`hardware_entry_failure_reason = 0xffffffffffffffff`。**
硬件的状态合法性检查失败。按顺序检查：`rflags` 的 bit 1 是不是 1；段寄存器的属性位是不是从 `KVM_GET_SREGS` 读出来再改的；如果开了保护模式，`CR0.PE`、`CR4`、`EFER.LME/LMA` 和实际的段属性是否自洽。这个错误不给任何细节，只能逐项排除。此时可以打开内核的 `kvm` tracepoint 或者看 `dmesg`，SVM 在某些情况下会打印完整的 VMCB dump。

**`KVM_EXIT_SHUTDOWN`。**
Guest 触发了 triple fault——异常处理时又产生异常，连续三次。在真机上这会导致 CPU 复位。最常见的原因是 Guest 跳到了没有代码的地址，或者 IDT 没设好就产生了异常。检查代码是否真的被拷进了 memslot 覆盖的 GPA、`RIP` 和 `CS.base` 是否匹配。

**访问 `run->io.data_offset` 时段错误。**
`mmap` 的长度用了 `sizeof(struct kvm_run)`。必须用 `KVM_GET_VCPU_MMAP_SIZE`。

**`KVM_SET_USER_MEMORY_REGION` 返回 `EINVAL`。**
`guest_phys_addr` 或 `userspace_addr` 没有页对齐，或者 `memory_size` 不是页的整数倍，或者与已有槽重叠。

**`KVM_EXIT_INTERNAL_ERROR` 且 `suberror = KVM_INTERNAL_ERROR_EMULATION`。**
KVM 的指令模拟器遇到了它解不了的指令。通常意味着 Guest 已经跑飞了，正在把随机数据当指令执行。`run->internal.data[]` 里会带上出错时的指令字节，可以拿去反汇编看看跑到哪了。

**观测工具。**
`perf kvm stat live` 可以实时看退出原因的分布，这是判断性能瓶颈的第一手段。更细的可以用 `trace-cmd record -e kvm:kvm_exit -e kvm:kvm_entry` 抓完整事件流。一台正常运行的虚拟机，退出原因分布中占大头的通常是 `#NPF`、`msr`、`io`；如果发现某个奇怪的退出原因占了 90%，那里就是问题所在。

## 十四、小结

回顾一下这条从 Popek-Goldberg 定理到一行 `fwrite` 的链路：

1. 虚拟化的本质是给操作系统提供机器抽象，难点在于 Guest 不知情、不合作。
2. x86 因为存在"敏感但不特权"的指令，无法用经典的陷入-模拟方法虚拟化。
3. 硬件辅助虚拟化引入了与特权级正交的 Host/Guest 模式，Guest 内核得以在真正的 ring 0 运行，"拦什么"由可编程的位图精确控制。
4. VMCB 是 Hypervisor 与硬件之间的共享内存契约，通用寄存器刻意交给软件管理以换取切换速度。
5. KVM 只做 CPU 和内存的虚拟化，把设备模型留给用户态，接口是三层文件描述符 + 一块共享内存页。
6. 于是一个 VMM 的骨架就是一个 `while (ioctl(KVM_RUN))` 循环，所有的功能都长在 `exit_reason` 的分支上。

从这里出发，往后每一步都是在这个骨架上加东西：让 Guest 进入 64 位长模式并加载真正的 Linux 内核（需要构造 GDT、页表和启动协议）；实现 VirtIO 让 Guest 用上块设备和网卡（需要理解 Virtqueue 这套共享内存环形队列协议）；引入 `ioeventfd` 和 `irqfd` 把热路径上的陷出压到最少；再往后是设备直通、多核和快照。

但无论加到多复杂，那个循环的形状不会变。
