# 从零入门虚拟化：全模拟网卡 P5：TSO

P4 里 guest 每发一帧，驱动就要准备一组描述符、写一次 TDT。以太网一帧最多带 1500 字节的 IP 包，上传 16 MiB 就是一万两千多帧。TSO（TCP Segmentation Offload）把“切成一帧一帧”这件事交给网卡：驱动一次交出一个最大 64 KiB 的 TCP 包，外加切分参数，网卡按 MSS 切成多帧，每帧的头由网卡改好、校验和由网卡算好。这一 P 先看驱动交给网卡的到底是什么，再看网卡对每一段改了哪些字段，然后看 mini-vmm 怎样在一个固定大小的缓冲里边读边切，最后用一个反例说明：TCP 上传的哈希对了，并不代表 TSO 做对了。

| P | 内容 |
|---|---|
| P1 | 设备的外观：PCI 身份、寄存器窗口、EEPROM、PHY，驱动探测成功并报告链路 up |
| P2 | 前端与后端：`--netdev`/`--device`，TAP，收包为什么在 I/O 线程上，后端怎样暂停和恢复收包 |
| P3 | 中断：中断原因寄存器、INTx 电平、为什么中断数约等于 ICR 读次数 |
| P4 | 发送：描述符环、DMA、上下文描述符与校验和 offload |
| P5（本篇） | TSO：硬件替驱动切包，以及“哈希对了也可能是错的” |
| P6 | 接收：地址过滤、描述符写回的顺序、什么时候算环满，端到端验证 |

## 一、TSO 要解决什么问题

### 1.1 没有 TSO 时谁来切

TCP 是字节流，应用一次 `write()` 8 KiB，TCP 要把它切成不超过 MSS（Maximum Segment Size）的段，每段配一套 IP 头和 TCP 头再发出去。MSS 由路径 MTU 决定：MTU 1500 减去 20 字节 IP 头、20 字节 TCP 头，再减去 12 字节时间戳选项，就是这次连接协商出的 1448。

Linux 在网卡不支持 TSO 时也不是一段一段地在 TCP 里构造包。TCP 照样先攒出一个大 skb，到了交给驱动之前，`validate_xmit_skb()` 发现设备不支持这种分段（`netif_needs_gso()`），调用 `skb_gso_segment()` 在软件里切开，再把切好的一串小 skb 逐个交给驱动。这叫 GSO（Generic Segmentation Offload），本质是把分段推迟到最后一刻。切分总要有人做，区别只在于在哪里做：

```
没有 TSO：TCP 大 skb → 软件 GSO 切成 N 个小 skb → 驱动 N 次 xmit → N 组描述符
有 TSO：  TCP 大 skb → 驱动 1 次 xmit → 1 个上下文描述符 + 几个数据描述符 → 网卡切成 N 帧
```

### 1.2 有 TSO 时驱动交出去的是一个大包

SDM 第 3.5.3 节列了 TSO 省掉的东西：协议栈不用切分，每个大包只算一次头；驱动每个大包只交互一次，而不是每帧一次；中断可以降到每个大包一次；命令硬件的 I/O 访问更少。

最后一条在虚拟机里分量特别重。对全模拟网卡来说，“命令硬件的 I/O 访问”就是 MMIO exit。guest 上传 16 MiB 时（P4 第 4.6 节的同一组插桩数据）：

| 量 | 数值 |
|---|---|
| guest 写 TDT 的次数（带描述符的） | 2092 |
| 其中 TSO 包 | 2048 |
| 网卡发出的帧 | 12295 |

2092 次 TDT 写换来一万两千多帧，平均一次 exit 发出 6 帧。如果没有 TSO，这些数据帧会由 GSO 切成单帧逐个交给驱动；按 P4 测到的“一个包一次 TDT 写”推算，TDT 写会涨到一万两千次以上，每次都是一次 MMIO exit。这是推算，不是测量：guest 里的 busybox 没有 `ethtool`，关不掉 TSO 做对照。

### 1.3 在 mini-vmm 里，“硬件”是 VMM 自己

真网卡上，切分由芯片里的 DMA 引擎和头部处理逻辑完成，主机 CPU 不参与。在 mini-vmm 里，网卡就是 VMM 进程里的一段 C 代码，切分、改头、算校验和都由写 TDT 的那个 vCPU 线程在 MMIO exit 里完成（P4 第 4.6 节测过，一个 8 KiB 的 TSO 包平均要 102 µs）。所以 TSO 在全模拟网卡上省的不是 CPU 总量，而是 exit 次数和 guest 驱动的工作量：guest 里少走 5 次协议栈和驱动，host 上少进出 5 次 KVM。

## 二、驱动交给网卡什么

### 2.1 一个 TSE=1 的上下文描述符

P4 第 2.2 节讲过上下文描述符的布局。TSO 用的是同一种描述符，只是 TUCMD 里的 TSE 位置 1，网卡就把它存进“分段上下文”，不去覆盖普通校验和用的那一份（P4 第 2.3 节）。

Linux 在 `e1000_tso()` 里填这个描述符。下面是 guest 发一个 5000 字节的 TCP 包时，mini-vmm 从环上读到的值（插桩构建在第一次见到 TSO 包时打印）：

| 字段 | 值 | 含义 | Linux 怎么算 |
|---|---|---|---|
| IPCSS | 14 | IP 头起点 | `skb_network_offset()` |
| IPCSO | 24 | IP 校验和字段位置 | `&ip_hdr(skb)->check` 的偏移 |
| IPCSE | 33 | IP 校验和覆盖到哪里（含） | `skb_transport_offset() - 1` |
| TUCSS | 34 | TCP 头起点 | `skb_transport_offset()` |
| TUCSO | 50 | TCP 校验和字段位置 | `&tcp_hdr(skb)->check` 的偏移 |
| TUCSE | 0 | 0 表示一直覆盖到帧尾 | 固定 0 |
| PAYLEN | 5000 | 要切的载荷总长，不含头 | `skb->len - hdr_len` |
| TUCMD | 0x27 | DEXT \| TSE \| IP \| TCP | IPv4 时置 IP 位 |
| HDRLEN | 66 | 原型头长度：以太网 14 + IP 20 + TCP 32 | `skb_tcp_all_headers()` |
| MSS | 1448 | 每段载荷上限 | `gso_size` |

紧跟着的第一个数据描述符里 POPTS 是 0x03，即 IXSM | TXSM：每一段都要重算 IP 校验和和 TCP 校验和。

### 2.2 原型头：驱动先把头改成“模板”

TSO 的头不单独传。数据流里最前面的 HDRLEN 字节就是头，网卡把它当作所有段共用的“原型头”（prototype header），每切一段就复制一份再按段修改。因为要被当作模板，驱动交出去之前要先改几个字段（SDM 第 3.5.5 节）：

- IPv4 总长度置 0，IP 头校验和置 0：这两个每段都不同，由网卡填；
- IP Identification 和 TCP 序号保持为第一段该有的值；
- PSH、FIN 按“最后一段”的需要设置，网卡会在前面的段里清掉它们；
- TCP 校验和字段放“不含长度的伪首部和”。

`e1000_tso()` 里对应的代码：

```c
struct iphdr *iph = ip_hdr(skb);
iph->tot_len = 0;
iph->check = 0;
tcp_hdr(skb)->check = ~csum_tcpudp_magic(iph->saddr, iph->daddr, 0, IPPROTO_TCP, 0);
```

上面那次 5000 字节的发送，mini-vmm 读到的原型头是：

```
IP  tot_len=0x0000  id=0x8456  check=0x0000
TCP seq=3986511381  flags=0x18 (PSH|ACK)  check=0x1816
```

### 2.3 为什么伪首部和里不带长度

TCP 校验和覆盖一个 12 字节的伪首部：源地址、目的地址、协议号、TCP 长度（TCP 头加载荷）。前三项对所有段都一样，TCP 长度每段不同：满的段是 32 + 1448 = 1480，最后一段可能只有 32 + 656 = 688。

驱动只能把对所有段都相同的部分先算好。按 RFC 1071 的拆分性（P4 第 3.1 节），伪首部和可以拆成“地址加协议”和“长度”两部分分别相加。手算一遍 0x1816：

```
源地址 10.0.2.15  → 0x0a00 + 0x020f
目的地址 10.0.2.1 → 0x0a00 + 0x0201
协议号 6          → 0x0006
                    ------
                    0x1816
```

`csum_tcpudp_magic()` 返回的是折叠并取反后的和，外面再取一次反，留在字段里的就是这个未取反的部分和 0x1816，和插桩读到的值一致。

网卡这一侧，SDM 第 3.5.8 节规定校验和的计算范围“包括校验和字段本身”。字段里放的是 0x1816，于是网卡从 TUCSS 一路加到帧尾时，伪首部里地址和协议这部分就自动进了和。网卡只需要再补上这一段的 TCP 长度（SDM 第 3.5.7 节：TCP Length = Payload + HDRLEN − TUCSS），取反写回即可。驱动和网卡就这样分摊了伪首部：不变的部分驱动算，随段变化的部分网卡算。

### 2.4 数据描述符怎么排

上传 16 MiB 时，2048 个 TSO 包里有 2044 个用了 4 个数据描述符（P4 第 1.4 节的统计）。加上前面的上下文描述符，一个 TSO 包占 5 个描述符。4 个数据描述符来自 `e1000_tx_map()` 的规则：

- 头在 skb 的线性区，单独一个描述符，66 字节；
- 载荷在页片段里，每个描述符最多 `max_per_txd` 字节。`e1000_xmit_frame()` 里有 TSO 时取 `min(mss << 2, 4096)`，注释说网卡在发起每个缓冲的 DMA 之前按 ceil(缓冲长度 / MSS) = 4 估算需要的 FIFO 空间，缓冲比 4 个 MSS 长就会让 FIFO 溢出。MSS 1448 时上限是 4096，8 KiB 载荷需要 2 个；
- 最后一个片段再拆出 4 字节，单独一个描述符。驱动注释称之为“4-byte sentinel desc”，用来绕开 TSO 模式下描述符过早写回的硬件勘误。

所以是 1 + 2 + 1 = 4。对模型来说，描述符怎么切都一样：它按顺序把每个描述符的数据追加进去，切段只看累积的字节数，不看描述符边界（4.2 节）。SDM 第 3.5.6 节唯一的限制是：如果头部跨多个描述符，每个描述符必须包含完整的头，不能把一个头劈成两半。Linux 的头总是在一个描述符里。

### 2.5 PAYLEN 和 EOP，以哪个为准

上下文描述符里的 PAYLEN 告诉网卡一共要切多少载荷。SDM 第 3.5.9.2 节说网卡用“PAYLEN − 已发段数 × MSS”算剩余字节；同时 DCMD 的 EOP 说明里又要求 EOP 描述符的长度“应当与 PAYLEN 剩下的部分一致”，不一致时分段上下文异常结束，计入 TSCTFC 统计寄存器。

也就是说，两者本应一致，不一致是驱动的错。mini-vmm 以 EOP 为准：读到 EOP 时缓冲里剩多少就切多少，作为最后一段发出。PAYLEN 保存在上下文里，但不参与切分。这样不需要额外的状态去对账，正常驱动下两种做法结果相同。

## 三、网卡对每一段改什么

### 3.1 按段修改的字段

SDM 第 3.5.9 节分第一段、中间段、最后一段列出了网卡改写的字段。合起来是：

| 字段 | 第一段 | 中间段 | 最后一段 |
|---|---|---|---|
| IPv4 总长度 | MSS + HDRLEN − IPCSS | 同左 | 实际载荷 + HDRLEN − IPCSS |
| IP Identification | 原型头的值 | 上一段加 1（回绕） | 上一段加 1 |
| IP 校验和 | 重算 | 重算 | 重算 |
| TCP 序号 | 原型头的值 | 加上之前各段的载荷字节数 | 同左 |
| FIN、PSH | 清掉 | 清掉 | 保留原型头里的值 |
| TCP 校验和 | 重算 | 重算 | 重算 |
| UDP 长度（UDP 分段时） | MSS + HDRLEN − TUCSS | 同左 | 实际载荷 + HDRLEN − TUCSS |

其余字段（地址、端口、ACK 号、窗口、选项）原样复制。

### 3.2 抓包看一个 5000 字节的包

在 host 侧对 tap0 抓包，同一次 5000 字节的发送在线上是这样的（序号是 tshark 换算的相对值）：

| 方向 | IP ID | IP 总长度 | TCP 序号 | 载荷 | 标志 |
|---|---|---|---|---|---|
| guest → host | 0x8456 | 1500 | 1 | 1448 | ACK |
| guest → host | 0x8457 | 1500 | 1449 | 1448 | ACK |
| guest → host | 0x8458 | 1500 | 2897 | 1448 | ACK |
| guest → host | 0x8459 | 708 | 4345 | 656 | ACK, PSH |

对照 3.1 节的表，每一列都能对上：

- IP ID 从原型头的 0x8456 开始逐段加 1；
- 总长度 1500 = 1448 + 66 − 14，最后一段 708 = 656 + 66 − 14；
- 序号每段加 1448，1448 × 3 + 656 = 5000，正好是 PAYLEN；
- 原型头里的 PSH 只出现在最后一段。

这个包里没有 FIN：busybox `nc` 读完输入后关闭连接，FIN 是在随后一个单独的空包里发的，没有走 TSO。四段的 IP 校验和 tshark 都验证通过；TCP 校验和因为抓包只截了前 128 字节没法在 tshark 里验证，但 host 的 `Tcp: InCsumErrors` 是 0，说明全部被接受了。

插桩构建同时统计了这次运行的切分结果：1 个 TSO 包、4 段，MSS 1448，HDRLEN 66，和抓包一致。

### 3.3 IPv6

SDM 给 IPv6 的公式是“Payload Length = MSS + HDRLEN − IPCSS”，和 IPv4 总长度的公式一字不差。但 IPv6 的 Payload Length 不包含 40 字节的固定头，按这个公式填会多出 40；而且最后一段那一节的 IPv6 公式里仍然写的是 MSS，没有换成实际载荷。照这样的描述实现不出一个正确的 IPv6 分段。

Linux 的 e1000 驱动对 82540EM 只声明 `NETIF_F_TSO`，不声明 `NETIF_F_TSO6`，IPv6 的大包会在 GSO 里用软件切好再交给驱动，不会走到网卡的 TSO。所以 mini-vmm 遇到 TUCMD 里 IP 位为 0 的分段上下文时丢包并打一次警告，不去猜手册的意思（4.4 节）。

## 四、实现

### 4.1 状态

TSO 相关的状态都在 `struct e1000_tx` 里（`include/devices/e1000.h`）：

```c
struct e1000_tx {
    struct e1000_tx_ctx ctx;       /* 普通校验和上下文（TSE=0 的上下文描述符） */
    struct e1000_tx_ctx tso;       /* 分段上下文（TSE=1），两者互不覆盖 */
    ...
    bool     tse;                  /* 当前包是 TSO 包 */
    uint32_t len;                  /* buf 里的字节数 */
    uint8_t  proto[256];           /* TSO 原型头（HDRLEN 最大 255） */
    bool     have_proto;
    uint32_t seg;                  /* 已发出的段数 */
    uint32_t sent;                 /* 已发出的 TCP/UDP 载荷字节 */
    uint8_t  buf[E1000_TX_BUF];    /* 64 KiB */
};
```

`tx_context_desc()` 按 TSE 位决定写进 `ctx` 还是 `tso`。`tx_desc()` 处理一个包的第一个数据描述符时，从它的 DCMD 里取 TSE 记进 `t->tse`，从 POPTS 里取 IXSM/TXSM；之后的描述符只往缓冲里追加数据。`seg` 和 `sent` 在每个包结束时（`tx_end_packet()`）清零。

`proto` 是 256 字节，因为 HDRLEN 是 8 位字段，最大 255。SDM 说头最多 240 字节，模型按字段宽度留够，不额外检查 240。

### 4.2 边读边切：缓冲里只放原型头加一段

最直接的做法是把整个 TSO 包（最大 64 KiB）攒齐再切。mini-vmm 不这样做，而是在 `tx_append()` 里每追加一块数据就检查一次，攒够“原型头 + 一个 MSS，而且还有多余”就切出一段：

```c
if (!t->have_proto && t->len >= t->tso.hdrlen) {
    memcpy(t->proto, t->buf, t->tso.hdrlen);
    t->have_proto = true;
}
while (t->have_proto && t->len > (uint32_t)t->tso.hdrlen + t->tso.mss) {
    uint32_t seg = t->tso.hdrlen + t->tso.mss;

    tso_segment(s, seg, false);
    memmove(t->buf + t->tso.hdrlen, t->buf + seg, t->len - seg);
    t->len -= t->tso.mss;
}
```

切完一段，把多出来的那部分载荷挪到头后面，缓冲里又是“头 + 不足一段的载荷”。缓冲长度因此有上界：头加一个 MSS，再加一个描述符的数据（Linux 每个描述符不超过 4096 字节）。

这和真硬件的做法一致。SDM 第 3.5.9 节说原型头在每个分段上下文开始时取一次，存进片上 240 字节的头缓冲，之后每段的头更新“和数据读取同时进行”。硬件也没有攒齐 64 KiB 的片上内存。

循环条件是严格大于。假设载荷恰好是 MSS 的整数倍，最后一个描述符读完时缓冲里正好是“头 + 一个 MSS”，用大于等于就会在这里把它当作中间段切出去，FIN/PSH 被清掉；而 EOP 处理时缓冲里只剩头，什么也不发。用严格大于，这一段留到 EOP 时由 `tx_desc()` 以 `last = true` 切出：

```c
if (t->tse) {
    if (t->have_proto && t->len > t->tso.hdrlen)
        tso_segment(s, t->len, true);
}
```

`memmove` 每段挪动的字节数不超过一个描述符的数据量，对 1448 字节的段来说是一次几 KiB 以内的内存复制，和 P4 第 4.3 节那次从 guest 内存复制进缓冲是同一个量级。

### 4.3 tso_segment：把 3.1 节的表翻译成代码

```c
static void tso_segment(struct e1000 *s, uint32_t len, bool last)
{
    struct e1000_tx *t = &s->tx;
    const struct e1000_tx_ctx *c = &t->tso;
    uint8_t *p = t->buf;
    uint32_t hdr = c->hdrlen, payload = len - hdr;
    uint32_t l4len = len - c->tucss;

    memcpy(p, t->proto, hdr);
    if (c->tucmd & E1000_TUCMD_IP) {
        put_be16(p + c->ipcss + 2, (uint16_t)(len - c->ipcss));
        put_be16(p + c->ipcss + 4, (uint16_t)(get_be16(t->proto + c->ipcss + 4) + t->seg));
    }
    if (c->tucmd & E1000_TUCMD_TCP) {
        put_be32(p + c->tucss + 4, get_be32(t->proto + c->tucss + 4) + t->sent);
        if (!last)
            p[c->tucss + 13] &= (uint8_t)~0x09;     /* FIN 0x01、PSH 0x08 */
    } else {
        put_be16(p + c->tucss + 4, (uint16_t)l4len);
    }
    if (t->popts & E1000_TXD_POPTS_IXSM)
        csum_insert(s, p, len, c->ipcss, c->ipcse, c->ipcso, 0, false);
    if (t->popts & E1000_TXD_POPTS_TXSM)
        csum_insert(s, p, len, c->tucss, c->tucse, c->tucso, l4len, true);

    tx_emit(s, p, len);
    t->seg++;
    t->sent += payload;
}
```

逐行对照 3.1 节：

- 每段先用 `proto` 覆盖缓冲开头的 HDRLEN 字节。缓冲开头原本是上一段的头（已经被改过），必须从未修改的原型头重新开始，否则 ID 和序号会被累加两次。
- `len - ipcss` 就是 IPv4 总长度；中间段时 `len` 是 HDRLEN + MSS，最后一段是实际长度，一个式子覆盖两种情况。
- IP ID 和 TCP 序号都从原型头的值加偏移，不在上一段的结果上递增，这样即使某一段因为校验和范围非法没插入校验和（`csum_insert()` 会告警并跳过），后面各段的字段也不受影响。16 位的 ID 用 `uint16_t` 截断实现回绕，32 位序号的回绕由无符号加法自然完成。
- TCP 标志在第 13 字节（TCP 头偏移 13），0x09 是 FIN | PSH。
- 非 TCP（UDP）时改的是 UDP 长度字段。
- `csum_insert()` 就是 P4 第 4.4 节的那个函数。IP 校验和的 `extra` 是 0；TCP 校验和的 `extra` 是 `l4len`，也就是 2.3 节里网卡要补进去的那个 TCP 长度。原型头里的 IP 校验和是 0，TCP 校验和字段里是部分伪首部和，两者都在求和范围内，正好是 2.3 节说的分工。

### 4.4 先检查上下文，再开始一个 TSO 包

分段上下文的每个字段都来自 guest 写的描述符，`tso_start()` 在包的第一个数据描述符处检查它们，不合格就把整个包标成 `drop`，后面的描述符只消费不发送：

```c
if (!(c->tucmd & E1000_TUCMD_IP)) {
    warn_once(s, W_TSO_IPV6, "e1000: TSO without the IPv4 bit is not supported, packet dropped");
    return false;
}
if (c->mss == 0 || c->hdrlen == 0 ||
    (uint32_t)c->hdrlen + c->mss >= E1000_TX_BUF ||
    c->tucss + 18u > c->hdrlen || c->ipcss + 20u > c->hdrlen) {
    warn_once(s, W_TSO_CTX, "e1000: bad TSO context hdrlen=%u mss=%u ipcss=%u tucss=%u, packet dropped", ...);
    return false;
}
```

每一条都对应一种后果：

- `mss == 0`：4.2 节的循环每次只减 0 字节，永远退不出来，vCPU 线程卡死；
- `hdrlen + mss` 不小于缓冲大小：缓冲放不下一整段，切段条件永远不成立，数据会一直攒到缓冲溢出被丢；
- `tucss + 18 > hdrlen`：`tso_segment()` 要读写 TCP 头的序号（偏移 4）、标志（偏移 13）和校验和，这些位置必须落在原型头里，否则会把载荷字节当成头字段改掉。18 是覆盖到 TCP 校验和字段（偏移 16、17）所需的长度；
- `ipcss + 20 > hdrlen`：同理，IPv4 头的总长度、ID、校验和字段都在前 20 字节。

这些检查不是为了配合某个驱动，Linux 永远不会填出这样的上下文。它们挡的是恶意或有 bug 的 guest：上下文里的每个偏移都会变成 VMM 进程里对 `buf` 和 `proto` 的下标，P4 第 4.3 节对 DMA 地址的要求同样适用于这些偏移。

### 4.5 实测

guest 上传 16 MiB（`dd if=/dev/urandom | nc`），插桩构建的统计：

| 量 | 数值 |
|---|---|
| TSO 包 | 2048 |
| 切出的段 | 12265 |
| 每包段数 | 6 段：2025 个；5 段：23 个 |
| PAYLEN | 4097–8192 字节：2046 个；8193–16384：2 个 |
| MSS / HDRLEN | 1448 / 66，全程不变 |
| 带 PSH 的原型头 | 2048 |

16 MiB 正好是 2048 个 8 KiB，几乎每个 TSO 包就是一次 8 KiB 的写。8192 = 1448 × 5 + 952，所以大多数包切 6 段。TSO 包的大小取决于 TCP 每次攒了多少数据（`tcp_xmit_size_goal()` 按窗口和 `gso_max_size` 定上限），离 64 KiB 的上限还很远，这次的瓶颈在发送端每次交给 TCP 的数据量，不在网卡。

两端的计数对得上：guest 的 `Tcp: OutSegs` 是 12292，host 的 `InSegs` 也是 12292，多出来的 27 段是握手、FIN 和不走 TSO 的小包；两端 `RetransSegs` 和 `InCsumErrors` 都是 0。用未插桩的构建做同样的上传，guest 计时 0.69 秒。

## 五、验证

### 5.1 单元测试

`tests/unit/e1000_test.c` 的 `case_tso` 有两部分：

- 3000 字节载荷、MSS 1000，切成 3 段。数据描述符故意按 700 字节切，让描述符边界和段边界错开，验证 4.2 节的切分只看字节数。逐段检查帧长、IP 总长度、IP ID、TCP 序号、FIN|PSH 只在最后一段、IP 校验和、TCP 校验和、载荷内容。原型头按 `e1000_tso()` 的方式准备：总长度和 IP 校验和清零，TCP 校验和放不含长度的伪首部和。
- 2500 字节载荷，最后一段不足 MSS，检查它的长度和校验和；紧跟一个 legacy 包，检查它不受分段上下文影响。

和 P4 一样，校验和由测试自己的 `sum16()`/`fold()` 判定。三个针对 TSO 的变体都被抓住：

| 变体 | 失败的检查 |
|---|---|
| 不清前面各段的 FIN/PSH | 2 项（第 1、2 段的标志） |
| 序号不加偏移 | 2 项（第 2、3 段的序号） |
| 伪首部不补 TCP 长度 | 4 项（两部分里所有段的 TCP 校验和） |

### 5.2 反例：哈希对了也可能是错的

最后一个变体在单元测试里很显眼，但放到真 guest 里，它几乎看不出来。把这个变体编成完整的 VMM，跑和 4.5 节同样的 16 MiB 上传：

| | 正确实现 | 伪首部不补 TCP 长度 |
|---|---|---|
| host 收到的 sha256 与 guest 一致 | 是 | 是 |
| 上传耗时（guest 计时） | 0.69 s | 89.5 s |
| guest `RetransSegs` | 0 | 2594 |
| host `InCsumErrors` | 0 | 2594 |
| host 侧抓到的 guest 数据帧 | — | 14183，TCP 校验和错 2594 |

guest 里没有任何报错，`nc` 正常退出，数据一个字节不差。发生了什么：

1. 这个变体只破坏 TSO 切出来的段，每一段的 TCP 校验和都差一个长度。不走 TSO 的单段包用的是普通校验和上下文（P4 第 4.4 节），完全正确。
2. host 的 TCP 收到校验和错的段，只把 `InCsumErrors` 加一然后丢掉，不回任何东西。对 guest 来说这些段就是丢了。
3. guest 的 TCP 等到重传超时（最小 200 ms，`TCP_RTO_MIN = HZ/5`）后重传。抓包里 guest 的数据帧之间有 418 次超过 0.15 秒的停顿，按 0.1 秒取整全是 0.2 秒，加起来 85 秒，占了整个上传时间。
4. 超时后拥塞窗口很小，重传和随后的发送里有一部分是单段的包，不走 TSO，校验和正确，被 host 收下；多段的仍然走 TSO，再次被丢。2594 次重传里有 834 次又是坏的。数据就这样一点一点挤过去，最终全部送达。

TCP 是可靠协议，它的职责就是在丢包时把数据补齐。拿 TCP 传完一个文件再比哈希，测到的是“TCP 的重传能不能弥补网卡的错误”，而不是“网卡有没有错”。只要错误不是 100% 的，TCP 迟早能补齐。

所以 `tests/e2e/emu-net.sh` 除了比较哈希，还检查 host 和 guest 两边的 `Tcp: InCsumErrors` 都是 0。用这个变体跑完整的 e2e，结果是 11 项通过、1 项失败，失败的正是这一项（`host InCsumErrors: "2660" != "0"`），上传哈希那一项是通过的。如果没有这条判据，这个变体能通过全部测试，唯一的症状是上传慢了一百多倍。在 guest 和 host 都闲着的测试机上，慢一百倍也只是一个跑得久一点的测试。

P6 的验证部分还会看两个同类的反例：发送不写 DD、普通校验和 offload 不插入校验和。

## 六、限制

- **IPv6 分段不支持。** 原因见 3.3 节，82540EM 的 Linux 驱动不会用到。
- **PAYLEN 不核对，TSCTC/TSCTFC 恒为 0。** 以 EOP 为准切最后一段，两者不一致时不像真硬件那样计入 TSCTFC。
- **UDP 分段没有测试。** `tso_segment()` 按手册改写了 UDP 长度，但 Linux 的 e1000 驱动只对 TCP 用 TSO，单元测试也只覆盖 TCP，这条路径没有被验证过。
- **HDRLEN 不按 240 字节限制。** 只按字段宽度和缓冲大小检查（4.4 节）。
- **切分在 vCPU 线程上同步完成。** 和 P4 一样，一个 TSO 包的全部段都在一次 MMIO exit 里切完发出，期间持有 `io_lock`。
