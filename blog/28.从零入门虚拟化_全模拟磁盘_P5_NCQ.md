P4 讲完了一条普通读写命令从 PRDT 到 host 文件的全过程。不过 Linux 默认并不用这些命令读写数据：只要 HBA 和盘都声明了 NCQ（Native Command Queuing），libata 就改用 READ/WRITE FPDMA QUEUED。这一篇讲 NCQ 在 AHCI 上多出来的东西：命令为什么要分“接受”和“完成”两步，PxSACT 和 PxCI 怎样分工，完成通知为什么换成了 Set Device Bits FIS，以及出错之后设备为什么要停下来，等主机读完一页日志才肯继续干活。

| P | 内容 |
|---|---|
| P1 | 外观与端口枚举：PCI 身份、ABAR、全局寄存器、端口的启动、COMRESET 与设备签名 |
| P2 | 命令的生命周期与中断：命令列表、命令表、FIS 接收区，从写 PxCI 到收到 D2H FIS，三级中断，出错停端口与恢复 |
| P3 | IDENTIFY 与 PIO：驱动眼里的盘长什么样，PIO Setup FIS，SET FEATURES |
| P4 | 后端与 DMA 读写：`--drive` 与 raw 镜像，PRDT 的逐项检查，写缓存与 FLUSH，端到端验证 |
| P5（本篇） | NCQ：PxSACT、FPDMA 命令与 SDB FIS，出错之后经日志 10h 恢复 |

PRDT 的逐项检查、后端读写、写缓存这些在 P4 讲过的规则，对 NCQ 命令完全一样，这一篇不再重复，只讲 NCQ 自己多出来的协议。

## 一、为什么要有 NCQ

### 1.1 一次只能有一条命令

回顾 P2 的命令生命周期：软件写 PxCI 的一位，设备执行，执行完回一个 D2H Register FIS，HBA 清掉 PxCI 的这一位，置 DHRS 发中断。设备在这条命令完成之前一直处于 BSY 状态，这期间 shadow 寄存器块不能写，主机也就不能再发下一条命令（SATA 3.0 第 13.6.1.1 节）。命令列表虽然有 32 个槽位，但对普通命令来说，同一时刻真正在设备里的只有一条。

对机械盘来说这是很大的浪费。盘一次只知道一条命令，就只能按主机给的顺序去寻道；要是能同时知道后面还有哪些命令，盘可以按磁头当前的位置重新排序，少转几圈。NCQ 做的就是这件事：主机一次最多交给设备 32 条命令，每条带一个 0 到 31 的 tag，设备按自己认为合适的顺序执行，完成一条报告一条。

### 1.2 把“接受”和“完成”拆开

要让多条命令同时在设备里，一条命令的生命周期就得拆成两步。

- **接受。** 设备收到命令后检查参数，没问题就回一个 BSY=0、I=0 的 D2H Register FIS，意思是“这条命令我收下了，你可以发下一条”（SATA 3.0 第 13.6.1.1 节）。I=0，所以这一步不产生中断。
- **完成。** 设备执行完某几条命令，回一个 Set Device Bits FIS（SDB FIS），里面 32 位的 ACT 字段按 tag 标出哪几条完成了（第 13.6.1.3 节）。I=1，产生中断。

AHCI 用两个寄存器跟踪这两步：

| 寄存器 | 谁置位 | 谁清零 | 表示 |
|---|---|---|---|
| PxCI（0x38） | 软件 | HBA，收到清掉 BSY、DRQ、ERR 的 FIS 时 | 这个槽位的命令还没被设备接受 |
| PxSACT（0x34） | 软件，在写 PxCI 之前 | HBA，按 SDB FIS 的 ACT 字段 | 这个 tag 的命令还没完成 |

一条 NCQ 命令被接受之后，它的位就只留在 PxSACT 里了。AHCI 第 3.3.13 节还规定了两个容易忽略的细节：PxSACT 的第 n 位同时对应 tag n 和槽位 n，所以 Linux 发 NCQ 命令时 tag 就是槽位号；PxSACT 在软件把 PxCMD.ST 从 1 写成 0 时清零，COMRESET 却不清它。第四章会看到，“ST 1→0 清 PxSACT”这一条在出错恢复里起了作用。

### 1.3 Linux 默认就用它

HBA 在 CAP 里置 SNCQ（bit 30），盘在 IDENTIFY 字 76 bit 8 声明支持 NCQ，字 75 给出队列深度减 1。mini-vmm 两个都声明了，深度 32（`id[75] = 31`）。Linux 启动时会打印出来：

```
ahci 0000:00:01.0: flags: 64bit ncq clo only pio
ata1.00: 131072 sectors, multi 0: LBA48 NCQ (depth 32)
```

第一行的 `ncq` 来自 CAP.SNCQ，第二行的 `NCQ (depth 32)` 来自 IDENTIFY。之后文件系统的读写全部走 FPDMA 命令；只有探测阶段的 IDENTIFY、SET FEATURES，以及 FLUSH、STANDBY 这类命令还是普通命令。内核参数 `libata.force=noncq` 会让 libata 不用 NCQ，这时第二行变成 `NCQ (not used)`，P4 的大部分实验就是这样做的。

## 二、发出一条 FPDMA 命令

### 2.1 字段挪了位置

READ FPDMA QUEUED（60h）和 WRITE FPDMA QUEUED（61h）的 Register H2D FIS 和 P4 的 READ DMA EXT 长得很像，但有三个字段挪了地方（ATA8-ACS 第 7.28、7.67 节）：

| 内容 | READ DMA EXT（25h） | READ FPDMA QUEUED（60h） |
|---|---|---|
| 扇区数 | Count，字节 12-13 | Features，字节 3 和 11 |
| tag | 无 | Count 字节 12 的 bit 7:3 |
| FUA | 无（有单独的 WRITE DMA FUA EXT） | Device 字节 7 的 bit 7 |
| LBA | 字节 4-6、8-10，48 位 | 同左 |

Count 字段被 tag 占了，扇区数只好搬进 Features。下面是 mini-vmm 加了诊断输出后记下的两条真实命令（前 16 字节）：

```
slot 4: 27 80 60 08 | 00 00 00 40 | 00 00 00 00 | 20 00 00 08    读 8 个扇区，LBA 0
slot 5: 27 80 60 00 | 00 00 00 40 | 00 00 00 08 | 28 00 00 08    读 2048 个扇区，LBA 0
```

第一条是启动时读分区表：字节 3 是 08，读 8 个扇区；字节 12 是 0x20，右移 3 位得到 tag 4，正好等于槽位号。第二条是 guest 里 `dd bs=1M iflag=direct` 发出的 1 MiB 读：字节 3 是 00，字节 11 是 08，合起来 0x0800 = 2048 个扇区；tag 是 0x28 >> 3 = 5。Device 字节都是 0x40，即 LBA 模式，FUA 位为 0。

Linux 打印出错命令时用的也是这个布局。`cmd 60/08:48:00:80:01/00:00:00:00:00/40 tag 9` 依次是命令码 60、Features 08（8 个扇区）、Count 0x48（tag 9 左移 3 位）、LBA 低三字节 00 80 01（LBA 0x018000），斜杠后面是高位字节和 Device。

mini-vmm 的 `cmd_fpdma` 按这个布局取字段：

```c
lba = (uint64_t)cfis[4] | (uint64_t)cfis[5] << 8 | (uint64_t)cfis[6] << 16 |
      (uint64_t)cfis[8] << 24 | (uint64_t)cfis[9] << 32 | (uint64_t)cfis[10] << 40;
count = (uint64_t)cfis[3] | (uint64_t)cfis[11] << 8;
if (!count)
    count = 65536;
```

扇区数 0 表示 65536，和 48 位的 READ DMA EXT 一样。

FUA 是“这次写要落到持久介质上才算完成”。实现会遵守它：带 FUA 的写，或者写缓存关着的时候，写完再 `blk_flush` 一次。不过在当前配置下 Linux 不会发 FUA。Linux 6.6 的 `libata_fua` 默认是 0，`ata_dev_config_fua` 一开始就跳过；就算打开这个参数，它还要求 IDENTIFY 字 84 bit 6（WRITE DMA FUA EXT），而 mini-vmm 没有声明这一位。

### 2.2 先写 PxSACT，再写 PxCI

Linux 的 `ahci_qc_issue`（drivers/ata/libahci.c）：

```c
if (ata_is_ncq(qc->tf.protocol))
        writel(1 << qc->hw_tag, port_mmio + PORT_SCR_ACT);
...
writel(1 << qc->hw_tag, port_mmio + PORT_CMD_ISSUE);
```

顺序是 AHCI 第 3.3.13 节规定的：软件在写 PxCI[TAG] 之前先置 PxSACT[TAG]。这样，HBA 一旦看到 PxCI 的这一位，PxSACT 里已经有它了，设备回的任何 FIS 都不会落在“PxCI 已清、PxSACT 还没置”的空档里。

和 PxCI 一样，PxSACT 也是 RW1 寄存器：写 1 置位，写 0 没有作用，所以软件只写自己那一位，不需要读改写。

### 2.3 接受

`cmd_fpdma` 先检查参数，通过以后回一个 I=0 的 D2H FIS，清掉 PxCI 的这一位：

```c
/* 接受：I=0 的 D2H FIS，BSY=0 */
fis[0] = SATA_FIS_REG_D2H;
fis[2] = ATA_STS_DRDY;
if (post_fis(s, p, AHCI_RFIS_RFIS, fis, sizeof(fis)) != VMM_OK) {
    host_bus_fatal(s, p, slot);
    return;
}
p->tfd = ATA_STS_DRDY;
p->ci &= ~(1u << slot);
```

注意这里没有置 DHRS。P2 的普通命令在 `complete_cmd` 里清 PxCI 的同时置 DHRS，因为那个 D2H FIS 带 I=1；NCQ 的接受 FIS 带 I=0，按 AHCI 的 D2H 接收状态（第 5.3.8 节）只更新 PxTFD、清 PxCI，不置中断位。真实的 HBA 在这里还有一步：设备在每段数据传输之前发 DMA Setup FIS，告诉 HBA 用哪个 tag 的缓冲区（SATA 3.0 第 13.6.1.2 节）。mini-vmm 里设备和 HBA 是同一段代码，执行时直接拿这个槽位的 PRDT，所以不生成 DMA Setup FIS，接收区 0x00 处的 DSFIS 一直是 0，Linux 也不读它。

参数检查不过时，设备在接受阶段就拒绝这条命令：回 ERR+ABRT 的 Register FIS（ATA8-ACS 第 7.28.6 节，地址越界也报 ABRT）。这种情况 PxCI 的位不清，端口停下。第四章再讲它。

## 三、完成：Set Device Bits FIS

### 3.1 SDB FIS 的布局

SDB FIS 只有 8 字节（SATA 3.0 第 10.3.6 节）：

```
字节 0   FIS 类型 A1h
字节 1   bit 6 = I（中断），bit 7 = N（通知）
字节 2   Status：bit 6:4 和 bit 2:0（BSY 和 DRQ 不在里面）
字节 3   Error
字节 4-7 ACT[31:0]（NCQ 用，第 13.6 节称它为 SActive 字段）
```

它没有 LBA，也没有 Count：SDB FIS 只用来改 Status 和 Error，外加 ACT 这一组完成位。这个 FIS 不改 BSY 和 DRQ（第 10.3.6.1 节），因为 NCQ 的完成和“设备忙不忙”是两回事：设备可能一边接受新命令，一边报告旧命令完成。

ACT 是一个位图，设备可以把几条命令的完成合在一个 SDB FIS 里报告。只有成功完成的命令才在 ACT 里置位（第 13.6.1.3 节）；失败的命令走另一条路，第四章讲。

### 3.2 HBA 收到 SDB FIS 时做什么

AHCI 第 5.3.13 节的 SDB:Entry 状态规定了 HBA 的动作，mini-vmm 的 `sdb_fis` 一步一步照着做：

```c
static void sdb_fis(struct ahci *s, struct ahci_port *p, int slot, uint32_t act,
                    uint8_t status, uint8_t error, bool irq)
{
    uint8_t fis[SATA_FIS_SDB_LEN] = { 0 };

    fis[0] = SATA_FIS_SDB;
    fis[1] = irq ? SATA_FIS_I : 0;
    fis[2] = status & 0x77;
    fis[3] = error;
    memcpy(&fis[4], &act, sizeof(act));          /* x86 小端，与 FIS 字节序一致 */
    if (post_fis(s, p, AHCI_RFIS_SDBFIS, fis, sizeof(fis)) != VMM_OK) {
        host_bus_fatal(s, p, slot);
        return;
    }
    p->tfd = ((uint32_t)error << 8) | (p->tfd & (ATA_STS_BSY | ATA_STS_DRQ)) | (status & 0x77);
    p->sact &= ~act;
    if (irq)
        p->is |= AHCI_PxIS_SDBS;
    if (status & ATA_STS_ERR) {
        p->is |= AHCI_PxIS_TFES;
        p->halted = true;
        p->ccs = (uint8_t)slot;
    }
    update_irq(s);
}
```

- FIS 写进接收区偏移 0x58。
- PxTFD 的 Status 用 FIS 的值，但保留原来的 BSY、DRQ（掩码 0x77 去掉了 bit 7 和 bit 3）。
- PxSACT 清掉 ACT 里为 1 的位。
- I=1 时置 PxIS.SDBS（bit 3）。
- Status 带 ERR 时置 TFES 并停下端口，和 P2 讲的普通命令出错一样。

一条成功的 NCQ 读在 `cmd_fpdma` 的最后只有一行：

```c
sdb_fis(s, p, slot, 1u << tag, ATA_STS_DRDY, 0, true);
```

PRDBC 不写：AHCI 第 5.4.1 节说 NCQ 命令的 PRDBC 不必有效，P4 也说过 Linux 从来不读它。

### 3.3 Linux 怎样认领完成

中断处理和 P2 一样走到 `ahci_handle_port_interrupt`，最后调 `ahci_qc_complete`。它要决定读哪个寄存器来判断“哪些命令还没完成”：

```c
/* pp->active_link is valid iff any command is in flight */
if (ap->qc_active && pp->active_link->sactive)
        qc_active = readl(port_mmio + PORT_SCR_ACT);
else
        qc_active = readl(port_mmio + PORT_CMD_ISSUE);

rc = ata_qc_complete_multiple(ap, qc_active);
```

有 NCQ 命令在途时读 PxSACT，否则读 PxCI。`ata_qc_complete_multiple` 把它和自己记的在途位图做异或，得到 `done_mask`，逐个完成。P2 讲过它的另一半：如果某一位在硬件里是 1、在软件记录里却是 0，就是 `illegal qc_active transition`，端口被冻结并复位。

完成命令的结果从哪来？普通命令从接收区的 D2H 区读（P2），PIO data-in 从 PIO Setup 区读（P3）。NCQ 命令两个都不对：接受时的那个 D2H FIS 早就被后来的命令覆盖了。`ahci_qc_ncq_fill_rtf` 读的是 SDB 区（`RX_FIS_SDB`，0x58）的 Status 和 Error，并对这一批 `done_mask` 里的所有命令填同一个值。源码里的注释写得很直白：SDB FIS 不带 LBA，所以不能用通用的 `ata_tf_from_fis`。

### 3.4 一条 NCQ 命令的 MMIO 足迹

下面是 MMIO trace 里一条 1 MiB NCQ 读（tag 8）的全部访问，寄存器名由偏移换算而来：

```
P0SACT  W4 00000100     ahci_qc_issue：先置 PxSACT
P0CI    W4 00000100                    再置 PxCI，命令在这次 exit 里执行完
IS      R4 00000001     中断处理：哪个端口
P0IS    R4 00000008     SDBS
P0IS    W4 00000008     写 1 清
P0SACT  R4 00000000     ahci_qc_complete：tag 8 已经不在了 → 完成
IS      W4 00000001
```

一共 7 次 MMIO exit，比 P2 的普通命令多一次，多的就是开头那次 PxSACT 写；完成时读的是 PxSACT 而不是 PxCI，次数不变。用 P4 第六章的负载（`dd bs=4k iflag=direct`，4096 次）分别在两种模式下数一遍整次运行的总量（含启动）：NCQ 下 ahci 的 BAR5 一共有 13089 次读、17093 次写，`libata.force=noncq` 下是 12897 次读、12676 次写。读的次数几乎一样，写多出 4417 次，基本就是每条命令多一次 PxSACT 写。dd 的耗时分别是 0.493 s 和 0.472 s，各只跑了一次，这点差别在噪声范围里。

### 3.5 队列深度 32，实际只有 1

前面说 NCQ 的价值是让设备手里同时有多条命令。可是在 mini-vmm 里，命令是在写 PxCI 的那次 MMIO exit 里同步执行完的（P2 第五章）：`ahci_qc_issue` 的 `writel` 返回时，这条命令已经接受、读完、发了 SDB FIS。下一条命令写 PxSACT 时，上一条早就不在设备里了。

trace 里能直接看到这一点。整次运行（启动、几次 dd、一次出错恢复）里一共 7 次 PxSACT 读，6 次是 0，唯一一次非零（0x200）是下一章那条出错的命令。Linux 侧的 tag 在 4、5、6、7、8、9、11 之间轮换，`/sys/block/sda/device/queue_depth` 也是 32，但设备里同时最多只有一条。

所以在 mini-vmm 现在的形态下，NCQ 带不来任何性能收益，反而多一次 exit。实现它有两个原因：

1. Linux 默认用 NCQ。不实现，Linux 只会看到一块“不支持 NCQ”的盘，日常读写走的是另一条代码路径，P2 到 P4 讲的那些东西就和真实系统的常态对不上。
2. 协议本身与执行方式无关。PxSACT 和 PxCI 的分工、SDB FIS、出错后的停机与日志，这些在同步执行下和真实盘一模一样，测试也能逐条验证。等 blk-io-uring 里程碑把后端改成异步，命令在 exit 返回之后才完成，队列才会真正被填满，那时这一套协议不需要改。

## 四、出错：设备停下，等主机读日志

### 4.1 两种出错时机

NCQ 命令可能在两个时刻出错（SATA 3.0 第 13.6.3.3 节）：

| 时机 | 设备回什么 | PxCI | PxSACT | 实测 irq_stat |
|---|---|---|---|---|
| 接受时（参数不对、只读盘写入） | Register FIS，ERR=1，Error=ABRT，I=1 | 不清 | 不清 | 0x40000001（TFES、DHRS） |
| 执行时（读写失败） | SDB FIS，ERR=1，Error=错误码，ACT=0，I=1 | 已在接受时清掉 | 不清 | 0x40000008（TFES、SDBS） |

两种情况下，状态里都只有 Status 和 Error，没有 tag。执行时出错尤其麻烦：此刻设备里可能有十几条命令在途，SDB FIS 的 ACT 里不置任何一位（失败的和还没完成的都不置），主机只知道“出错了”，不知道是哪一条。

`cmd_fpdma` 里执行失败的分支：

```c
if (rc != VMM_OK) {
    err = write ? ATA_ERR_ABRT : ATA_ERR_UNC;
    ncq_record_error(s, cfis, ATA_STS_DRDY | ATA_STS_ERR, err);
    sdb_fis(s, p, slot, 0, ATA_STS_DRDY | ATA_STS_ERR, err, true);
    return;
}
```

ACT 传的是 0，不是 `1u << tag`。第 4.7 节会看到，把这里写成 `1u << tag` 会出什么事。

### 4.2 为什么要停下

SATA 3.0 第 13.7.3 节解释了这套设计：Status 和 Error 寄存器太小，装不下“出了什么错”再加上“哪个 tag 出的错”，所以规范另加了一页日志（Queued Error Log，日志地址 10h）。设备报告错误之后就停止处理任何命令，直到主机读这页日志。停下还有一个好处：在途命令之间可能有数据依赖（例如先写后读同一块），出错后继续执行会让状态更难收拾。

这个“停下”在第 11.14 节的设备状态机里是 DFPDMAQ13: WaitforClear。在这个状态下，设备只认两样东西：读日志 10h 的 READ LOG EXT（转到 DFPDMAQ14），或者软复位。收到其他任何命令，都转到 DFPDMAQ12: BrokenHost_ClearBusy，回一个 ERR=1、Error=04h（ABRT）的 Register FIS。

mini-vmm 用一个标志 `s->ncq_err` 表示“出过 NCQ 错误，日志还没被读”，`exec_ata` 在分发命令之前先查它：

```c
if (s->ncq_err && !(cmd == ATA_CMD_READ_LOG_EXT && cfis[4] == ATA_LOG_NCQ_ERR)) {
    vmm_dbg("ahci: port %d slot %d: cmd 0x%02x aborted, NCQ error log not read yet",
            port_no(s, p), slot, cmd);
    abort_cmd(s, p, slot);
    return;
}
```

READ LOG EXT 读别的日志也不放行：单元测试里有一条检查就是 “even reading another log is aborted”。

### 4.3 日志 10h

日志 10h 只有一页 512 字节，布局在 SATA 3.0 图 221：

| 字节 | 内容 |
|---|---|
| 0 | bit 7 NQ（出错的不是 NCQ 命令），bit 6 UNL，bit 4:0 TAG |
| 2、3 | Status、Error |
| 4-6、8-10 | LBA |
| 7 | Device |
| 12、13 | Count |
| 511 | 校验和：整页 512 字节相加为 0 |

`ncq_record_error` 在出错时把这条命令的 FIS 抄进日志：

```c
memset(l, 0, ATA_SECTOR_SIZE);
l[0] = cfis[12] >> 3;                        /* TAG */
l[2] = status;
l[3] = error;
memcpy(&l[4], &cfis[4], 3);                  /* LBA 7:0 .. 23:16 */
l[7] = cfis[7];
memcpy(&l[8], &cfis[8], 3);                  /* LBA 31:24 .. 47:40 */
l[12] = cfis[12];
l[13] = cfis[13];
log_checksum(l);
s->ncq_err = true;
```

LBA 填的是命令的起始 LBA，不是第一个出错的扇区：P4 第四章说过，后端一次读写整段，不知道是哪一个扇区失败。

Linux 读日志的函数是 `ata_eh_read_log_10h`（drivers/ata/libata-sata.c）。它先算校验和，不为 0 就打印一行警告但照常往下走；NQ 位为 1 就放弃；否则取 TAG，把字节 2 到 13 填进一个 taskfile。日志是 Linux 拿到出错命令 LBA 的唯一来源，因为 SDB FIS 里没有 LBA。

### 4.4 读日志：清空队列的 SDB FIS

主机读日志 10h 时，设备先丢掉队列里所有在途命令，再发一个 ACT 全 1 的 SDB FIS，告诉主机“所有在途命令都作废了”（SATA 3.0 第 13.6.2 节）。ACT 全 1 会让 HBA 清掉 PxSACT 的所有位，Linux 认为这些命令失败，按需重发。第 13.6.3.4 节解释了这样做的用意：避免主机把失败的命令当成成功完成。

这个 SDB FIS 的 I 位，规范两处说法不一样。第 13.6.3.4 节图 208 下面写的是 “The interrupt bit shall be set to one”；第 11.14 节状态机里 DFPDMAQ14: SendQueue_CleanACK 写的是 “Interrupt bit cleared to zero”。mini-vmm 按状态机发 I=0。理由是这个 SDB FIS 后面紧跟着 READ LOG EXT 自己的 PIO 数据传输，那一步以 PIO Setup FIS 结束并置 PSS（P3），中断由它产生，不需要两次。下一节的 trace 里，READ LOG EXT 完成时 PxIS 读出来正好只有 0x2（PSS），没有 SDBS。

`cmd_log` 里的对应分支：

```c
} else if (log == ATA_LOG_NCQ_ERR) {
    if (s->ncq_err) {
        s->ncq_err = false;
        sdb_fis(s, p, slot, 0xFFFFFFFFu, ATA_STS_DRDY, 0, false);
        if (p->halted)
            return;
    }
    memcpy(buf, s->ncq_log, ATA_SECTOR_SIZE);
}
```

只有在出过错的时候才发这个 SDB FIS。第 13.6.3.4 节允许设备在“不是因为出错而读日志、又没有在途命令”时不发。日志内容在下一次 NCQ 出错之前一直保留，第二次读出来的还是第一次的错误（第 13.7.3 节）。

### 4.5 一次真实的恢复

e2e 的 `ncq_error_tests` 用一个办法让读真正失败：guest 运行中，host 把 64 MiB 的镜像 `truncate` 到 32 MiB，然后 guest 直读第 48 MiB 处的 4 KiB。后端 `preadv` 读到文件尾，按 P4 的规则报 EIO。

VMM 一侧（带诊断输出）：

```
P2DBG slot 9 ... cfis=27 80 60 08 | 00 80 01 40 | 00 00 00 00 | 48 00 00 08
[ERR ] drive e0: read 4096 bytes at offset 0x3000000: Input/output error
P5SDB slot 9 act=0x00000000 status 0x41 error 0x40 I=1 sact=0x00000200 ci=0x00000000
P2DBG slot 0 ... cfis=27 80 2f 00 | 10 00 00 a0 | 00 00 00 00 | 01 00 00 08
P5SDB slot 0 act=0xffffffff status 0x40 error 0x00 I=0 sact=0x00000000 ci=0x00000001
```

第一条 SDB FIS 是出错报告：ERR（0x41）、UNC（0x40），ACT 为 0，tag 9 留在 PxSACT 里。第二条命令是 READ LOG EXT（2Fh）：LBA 低字节 0x10 是日志地址，Count 1 页，走的是槽位 0。紧接着是清空队列的 SDB FIS，ACT 全 1、I=0。这时 PxSACT 已经是 0，原因见下面的 MMIO trace。

同一段时间的 MMIO trace：

```

591 P0IS   W4 40000008

594 P0SERR W4 00000000
595 IS     W4 00000001

596 P0CMD  R4 00004917     ahci_error_handler：停引擎

598 P0CMD  R4 00004016     CR 已清

622 P0CI   W4 00000001     IDENTIFY
628 P0SACT W4 00000800     恢复后下一次读，tag 11，正常完成
```

对着 Linux 源码看每一步：

1. **先认领成功的，再处理错误。** `ahci_handle_port_interrupt` 在 PxIS 带错误位时，先调一次 `ahci_qc_complete`，再调 `ahci_error_intr`。源码注释的解释是：报告错误之前，设备可能已经用 SDB FIS 报告过别的命令成功完成。第 592 行读到 PxSACT 是 0x200，tag 9 还在，所以它不算完成。
2. **标记错误，交给 EH。** `ahci_error_intr` 看到 TFES，给当前链路记上 `AC_ERR_DEV`，然后中止端口上所有在途命令，交给错误处理线程（EH）。
3. **重启引擎。** EH 里 `ahci_error_handler` 先停引擎再启动（第 596 到 601 行）。停引擎时 ST 从 1 变 0，PxSACT 随之清零。所以设备后面发的 ACT 全 1 的 SDB FIS 已经清不到什么，PxSACT 早就是 0 了。
4. **读日志，找出元凶。** `ata_eh_analyze_ncq_error` 只在“链路上有 NCQ 命令在途、错误类型是设备错误”时动手。它用一条内部命令读日志 10h：内部命令的 `hw_tag` 固定为 0，所以走槽位 0，而且是普通的 PIO data-in 命令，不是 NCQ 命令。日志里的 tag 是 9，正好是在途的那一条。它把日志里的 taskfile 抄进这条命令的结果，再加上 `AC_ERR_NCQ`。
5. **决定动作。** I/O 命令出错，EH 的默认动作是重新确认设备（REVALIDATE）：第 610 到 622 行的 IDENTIFY、SET FEATURES、IDENTIFY 就是它。UNC 会给命令加上 `AC_ERR_MEDIA`，而 `ata_eh_worth_retry` 对介质错误不重试（源码注释：盘自己内部大概已经重试过 10 到 30 秒了），这条读直接以失败告终。

guest 的 dmesg：


### 4.6 接受阶段出错，以及 “NCQ disabled”

P4 第 4.2 节做过一个实验：把只读的盘挂成可写，ext2 写超级块时，WRITE FPDMA QUEUED 在接受阶段就被拒绝。

```
ata1.00: irq_stat 0x40000001
ata1.00: failed command: WRITE FPDMA QUEUED
ata1.00: cmd 61/02:48:02:00:00/00:00:00:00:00/40 tag 9 ncq dma 1024 out
         res 41/04:48:02:00:00/00:00:00:00:00/40 Emask 0x401 (device error) <F>
```

irq_stat 是 TFES 加 DHRS：拒绝用的是 Register FIS。这里同样有 `<F>`，说明接受阶段的错误也记进了日志 10h，EH 读日志找到了 tag 9。`cmd_fpdma` 在接受阶段失败时也调 `ncq_record_error`，因为规范对两种时机的要求一样：报告错误后都进入 WaitforClear，都要读日志才能恢复。

这条写 Linux 重试了三次，第四次出错时打印 `NCQ disabled due to excessive errors`，之后改用普通的 WRITE DMA。规则在 `ata_eh_speed_down_verdict` 里：过去 10 分钟内，超时或违反协议（`TOUT_HSM`）的错误加上“原因不明的设备错误”（`UNK_DEV`）超过 3 次，就关掉 NCQ。`ata_eh_categorize_error` 把一个 I/O 命令的错误归为 `UNK_DEV` 的条件是：错误掩码里只有 `AC_ERR_DEV`，没有 `AC_ERR_MEDIA` 和 `AC_ERR_INVALID`。ABRT 正好是这样；上一节的 UNC 带了 `AC_ERR_MEDIA`，不计入。换句话说，Linux 认为“盘反复拒绝 NCQ 命令、又说不出具体原因”，多半是这块盘的 NCQ 实现有问题。

### 4.7 反例：把失败的命令报成完成

如果实现在执行出错时，把出错命令的 tag 也放进 SDB FIS 的 ACT 里（`1u << tag` 而不是 0），会怎样？在真实 guest 里用同样的场景跑一遍：

```
P5SDB slot 13 act=0x00002000 status 0x41 error 0x40 I=1 sact=0x00000000 ci=0x00000000
RC-0
ahci: port 0 slot 14: cmd 0x60 aborted, NCQ error log not read yet
ata1: log page 10h reported inactive tag 13
ata1.00: irq_stat 0x40000001
ata1.00: failed command: READ FPDMA QUEUED
ata1.00: cmd 60/08:70:00:00:00/00:00:00:00:00/40 tag 14 ncq dma 4096 in
         res 41/40:00:00:00:00/00:00:00:00:00/00 Emask 0x9 (media error)
I/O error, dev sda, sector 0 op 0x0:(READ) flags 0x800 phys_seg 1 prio class 2
OK-0
```

出错的读被报告成了成功，而下一条完全正常的读反倒失败了，错误还安在了一个无关的扇区上。一步步看：

1. **失败被当成成功。** SDB FIS 清掉了 PxSACT 的 tag 13。`ahci_handle_port_interrupt` 先调 `ahci_qc_complete`，读到 PxSACT 为 0，tag 13 就作为成功命令完成了，这发生在 `ahci_error_intr` 之前。随后 EH 看到链路上没有 NCQ 命令在途，`ata_eh_analyze_ncq_error` 第一个条件就不满足，不读日志，什么也没发现。于是读失败的那条 `dd` 返回 0（`RC-0`），缓冲区里根本没有读到数据。
2. **无辜的命令被拒。** 设备仍处于“日志没读”的状态，下一条 NCQ 命令（tag 14，读 LBA 0）在接受阶段被拒（irq_stat 0x40000001）。
3. **日志对不上号。** 这次 EH 读了日志，日志说出错的是 tag 13，可 tag 13 早就“成功完成”了，于是打印 `log page 10h reported inactive tag 13` 后放弃归因。这一行就是 e2e 用 `expect_not "log page 10h"` 盯着的东西。
4. **错误码张冠李戴。** tag 14 实际被拒的原因是 ABRT，可报出来的却是 UNC（`res 41/40`），而且没有 `<F>`。按源码推断，原因是：失败的命令在 `ata_qc_complete` 里就由 `fill_result_tf` 填结果，NCQ 命令读的是接收区的 SDB 区，那里还留着 tag 13 那次出错的 41/40；之后 EH 没能用日志覆盖它。结果是扇区 0 的读报介质错误（`OK-0`）。

规范为什么规定“失败的命令不在 ACT 里置位”（SATA 3.0 第 13.6.3.3.1.2 节），这个反例就是答案：ACT 置位的唯一含义是“成功完成”，主机据此把数据交给上层，没有第二次确认的机会。

同一场景下还试了另外三种错误实现，guest 都看不出来：

| 错误实现 | guest 的表现 | 为什么看不出来 |
|---|---|---|
| 读日志时不发 ACT 全 1 的 SDB FIS | 恢复正常 | Linux 在读日志之前已经停过引擎，PxSACT 已经清零 |
| 日志 10h 不算校验和 | 多一行 `invalid checksum 0x93 on log page 10h`，恢复正常 | Linux 只警告，不放弃 |
| 出错后不拦其他命令 | 恢复正常 | Linux 出错后的第一条命令就是读日志 |

这三种在 Linux 下都“能用”，但换一个按规范行事的驱动就未必。例如驱动不停引擎、直接读日志，就要靠 ACT 全 1 的 SDB FIS 清 PxSACT；出错后先发一条别的命令，就要靠设备把它拒掉。所以它们由单元测试逐条检查（第七章）。

## 五、GPL：为日志 10h 带上的东西

读日志 10h 用的 READ LOG EXT 属于 GPL（General Purpose Logging）特性集。ATA8-ACS 第 4.15.1 节要求支持 NCQ 的盘必须支持 GPL，IDENTIFY 里体现为字 84/87 的 bit 5。GPL 又要求一整套东西（第 4.10 节）：日志目录（00h，列出每个日志有几页）、WRITE LOG EXT，以及全部 Host Vendor Specific 日志（80h 到 9Fh，主机可以随意读写）。mini-vmm 把这些都实现了：每个主机日志 16 页，只存在内存里，不写进镜像：raw 镜像只装扇区数据，没有地方放它们。

`cmd_log` 对参数的检查：日志不存在、Count 为 0、页号加页数超出日志大小、写只读日志（00h 和 10h）都中止。

页号放在 FIS 的哪里，有一个坑。ref/ 里的 ATA8-ACS r4a 草案把页号写在 LBA 31:16；Linux 的 `ata_read_log_page` 放在 LBA 15:8 和 LBA 39:32，也就是 FIS 的字节 5 和 9，这是后来 ACS 标准的布局（ref/ 里没有 ACS-2 原文）。guest 是 Linux，实现按它的布局取：

```c
unsigned page = cfis[5] | (unsigned)cfis[9] << 8;
```

在这次启动的 trace 里，Linux 在第一条 READ FPDMA 之前只发了 IDENTIFY、SET FEATURES、IDENTIFY，没有读日志目录，也没有碰主机日志。全程唯一的 READ LOG EXT 就是出错恢复时读日志 10h 的那一条。GPL 的其余部分只由单元测试验证。

## 六、复位也是一条恢复路径

规范给了两条走出 WaitforClear 的路：读日志 10h，或者复位。日志 10h 的内容在软复位或 COMRESET 之后“不确定”（SATA 3.0 第 13.7.3 节）。mini-vmm 在 `disk_reset` 里把它填成 NQ=1，并清掉出错标志：

```c
s->ncq_err = false;
memset(s->ncq_log, 0, sizeof(s->ncq_log));
s->ncq_log[0] = ATA_LOG_NCQ_NQ;
log_checksum(s->ncq_log);
```

NQ=1 的意思是“最近出错的不是 NCQ 命令”。复位之后有软件来读日志，`ata_eh_read_log_10h` 看到 NQ 就返回 `-ENOENT`，不会把一份过期的记录当成某个 tag 的错误。不清出错标志的话，COMRESET 之后盘会一直拒绝所有命令，Linux 就只能一次次复位，最后放弃这块盘。

## 七、验证

### 7.1 单元测试

`tests/unit/ahci_test.c` 里和 NCQ 有关的是三个用例：

- `case_ncq`：先置 PxSACT，接受时 I=0 的 D2H FIS 清 PxCI 且不置 DHRS，完成时 SDB FIS 的 ACT 是这个 tag，清 PxSACT、置 SDBS，PRDBC 不写；数据按 48 位 LBA 写入（LBA 位 24 在字节 8）并能读回；写缓存打开时带 FUA 的写 flush 一次，普通写不 flush；扇区数 0 按 65536 算，因而越界被中止。

### 7.2 端到端

`tests/e2e/emu-blk.sh` 里和 NCQ 有关的几条：

- **NCQ 打开（默认）。** dmesg 里有 `LBA48 NCQ (depth 32)`，`queue_depth` 是 32；两个控制器端口 0 的 PxSACT 在 MMIO trace 里都被写过，说明文件系统的读写确实走了 FPDMA。P4 列出的读写校验（sha256 与 host 一致、debugfs 取回的文件一致、e2fsck 无错）都是在这个模式下做的。
- **`libata.force=noncq`。** dmesg 是 `NCQ (not used)`，READ/WRITE DMA 读写的数据单独校验一遍。
- **NCQ 出错与恢复。** 就是第 4.5 节的场景：截短镜像后读后半段。判据是：dmesg 有 `READ FPDMA QUEUED`、`{ DRDY ERR }`、`{ UNC }`、`EH complete`；读失败的 `dd` 返回 1；之后的读成功；后端统计 `1 errors`；dmesg 里不能出现 `log page 10h`、`invalid checksum`、`inactive tag`。第 4.7 节的两个错误实现在同一场景下分别打印了 `inactive tag` 和 `invalid checksum`，`dd` 的返回值也从 1 变成了 0，按这些判据会被挡住。

用第 3 步（还没有 NCQ）的二进制跑同一个 suite，NCQ 相关的 6 条全部失败。

## 八、限制

- **队列深度实际为 1。** 命令同步执行（3.5 节），NCQ 只有协议没有收益，要等 blk-io-uring 里程碑的异步后端。到那时 SDB FIS 合并多个 ACT 位、出错时还有别的命令在途需要作废，这些情况才会真正出现。现在的测试只能构造出它们的一部分。
- **不支持 NCQ 期间混发普通命令的出错路径。** 规范规定 NCQ 命令在途时收到普通命令，设备要按 BrokenHost 报错（SATA 3.0 第 13.6.2 节）。同步执行下设备里从来没有在途的 NCQ 命令，这条路径走不到，所以没有实现。
- **日志 10h 的 LBA 是命令的起始 LBA**，不是第一个出错的扇区，原因同 P4。
- **只能用 READ LOG EXT 读日志 10h。** IDENTIFY 字 76 bit 15 不声明 READ LOG DMA EXT，Linux 于是用 PIO 的 READ LOG EXT。
- **没有 NCQ 优先级、NCQ QUEUE MANAGEMENT、自动激活。** 字 77、78 为 0，Linux 也就不去读这些特性对应的日志。
- **不生成 DMA Setup FIS。** 设备和 HBA 在同一段代码里，用不着它来选择缓冲区（2.3 节）。
- **主机日志不持久。** 80h 到 9Fh 只存在内存里，VM 重启后清零。
