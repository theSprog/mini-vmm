前面的篇目里，VMM 的线程只有两类：主线程负责创建虚拟机、最后等所有 vCPU 结束，每个 vCPU 一个线程反复 `KVM_RUN`。唯一的例外是 host 终端的输入，它需要有人一直等着读。下一组里程碑要接入网卡和磁盘，需要“一直等着”的东西会越来越多：TAP 上随时可能来包，磁盘请求随时可能完成。这一章讲 mini-vmm 怎样用一个 epoll 线程统一处理这些等待，以及这样做时容易踩的几个坑。

## 一、VMM 里有两种等待

### 1.1 vCPU 等 guest，后端等 host

vCPU 线程大部分时间阻塞在 `ioctl(KVM_RUN)` 里。guest 执行 `HLT` 时，它睡在 KVM 内核里，有中断要送给这颗 CPU 时被唤醒。它等的是 **guest**。

设备的后端等的是 **host**：终端有没有按键、TAP 有没有收到包、磁盘读请求有没有完成。

两种等待不能放在同一个线程里。用串口举例，guest 的 8250 驱动读 RBR 寄存器（`0x3F8`）拿一个输入字节：

```
  在 vCPU 线程里读 host 终端                     由别的线程提前把数据放进设备模型

  guest: inb 0x3f8                              guest: inb 0x3f8
    → KVM_EXIT_IO                                 → KVM_EXIT_IO
    → serial_read()                               → serial_read()
    → read(stdin)  ← 用户没按键，阻塞               → 从 RX FIFO 取一个字节，立即返回
                                                  → KVM_RUN 继续
  这颗 vCPU 停在 read 里：
  guest 的这颗 CPU 什么都做不了，                  FIFO 空时返回“没数据”，
  连时钟中断都处理不了                              guest 驱动按 LSR 的语义处理
```

所以正确的分工是：后端的数据由别的线程准备好，放进设备模型（串口的 RX FIFO，以后网卡的接收描述符环），然后拉中断线通知 guest；vCPU 线程访问寄存器时只读设备模型里已有的状态，**永远不等 host**。

### 1.2 一个后端一个线程，还是一个线程管所有后端

“别的线程”有两种做法：

| | 每个后端一个阻塞读线程 | 一个 epoll 线程管所有后端 |
|---|---|---|
| 线程数 | 后端数 + vCPU 数 + 主线程 | 1 + vCPU 数 + 主线程 |
| 停机 | 阻塞在 `read` 里的线程没法叫醒，只能不管它，等进程退出时一起消失 | 往一个 eventfd 写一下，线程从 `epoll_wait` 返回，`pthread_join` 干净地收尾 |
| 加一个新后端 | 再开一个线程，再想一遍它和所有其他线程之间怎么加锁 | 注册一个 fd 和一个回调，所有回调在同一个线程里依次执行，彼此天然不会并发 |
| stdin 是 `/dev/null` | `read` 立即返回 0，线程悄悄退出，没人知道输入被关掉了 | 注册时 `epoll_ctl` 就报错，启动时明确打印“guest 输入被关闭”（3.4 节） |

第二种就是**事件循环**。QEMU 的 main loop（`util/main-loop.c` 加 AioContext）、kvmtool 的 epoll 线程都是这个思路。mini-vmm 只取其中最小的部分：一个线程、一张回调表。

## 二、事件循环的结构

### 2.1 epoll 的三个调用

epoll 是 Linux 上“同时等很多个 fd”的机制，用起来只有三步：

```c
int epfd = epoll_create1(0);                      /* 1. 建一个 epoll 实例 */

struct epoll_event ev = { .events = EPOLLIN, .data.ptr = something };
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);          /* 2. 告诉它要关注哪个 fd 的什么事件 */

struct epoll_event out[16];
int n = epoll_wait(epfd, out, 16, -1);            /* 3. 阻塞，直到有 fd 就绪 */
for (i = 0; i < n; i++)
    handle(out[i].data.ptr, out[i].events);       /*    注册时给的 data 原样带回来 */
```

`data` 是注册时随便塞的一个值，`epoll_wait` 把它原样还回来。事件循环用它找到“这个 fd 该调用哪个回调”。

### 2.2 mini-vmm 的回调表

```c
/* include/io/event_loop.h */
struct evl_slot {
    int             fd;
    evl_handler_fn  fn;         /* NULL 表示空闲或已删除 */
    void           *opaque;
    bool            retired;    /* 3.1 节 */
};

struct event_loop {
    int             epfd;
    int             stop_fd;    /* eventfd，evl_stop 写它把 I/O 线程唤醒 */
    pthread_t       thread;
    bool            started;
    bool            dispatching;
    struct evl_slot slots[EVL_MAX_HANDLERS];   /* 32 个 */
};
```

注册时，`epoll_event.data.ptr` 存的是槽位的地址。所以槽位在整个生命周期里不能移动，这就是回调表用定长数组、而不是用可以 `realloc` 扩容的数组的原因：数组一扩容，内核里存着的那些指针就全指到旧内存上去了。

I/O 线程的主体只有十几行：

```c
/* src/io/event_loop.c */
static void *io_thread(void *arg)
{
    ...
    pthread_setname_np(pthread_self(), "io");

    while (!stop) {
        n = epoll_wait(l->epfd, evs, EVL_BATCH, -1);
        ...
        l->dispatching = true;
        for (i = 0; i < n; i++) {
            struct evl_slot *s = evs[i].data.ptr;

            if (!s) {               /* 停机 eventfd 注册时 data.ptr = NULL */
                stop = true;
                continue;
            }
            if (s->fn)              /* 可能已经被同一批里前面的回调删掉了 */
                s->fn(s->opaque, s->fd, evs[i].events);
        }
        l->dispatching = false;
        for (i = 0; i < EVL_MAX_HANDLERS; i++)
            l->slots[i].retired = false;
    }
    return NULL;
}
```

停机靠一个 eventfd：`evl_init()` 把它注册进 epoll，`data.ptr` 设成 `NULL`，槽位地址不可能是 `NULL`，所以看到 `NULL` 就知道是停机。`evl_stop()` 往 eventfd 写一个 1，I/O 线程就从 `epoll_wait` 返回、退出循环，主线程 `pthread_join` 等它结束。这个等待依赖的是一个明确的唤醒信号，不靠睡一会儿再检查标志。

### 2.3 回调表只有一个写者

谁可以往回调表里加、删条目？如果随便哪个线程都能改，表就需要锁，而 I/O 线程在派发回调的过程中也要读这张表，加锁的范围很难划清楚。mini-vmm 的规定是：

- `evl_start()` 之前，主线程在注册阶段可以随意 `evl_add()`；
- `evl_start()` 之后，只有 I/O 线程自己（也就是在回调里）可以调用 `evl_add()`/`evl_del()`。

其他线程调用会返回 `VMM_ERR_INVAL`，并打印是哪个线程越界了。这样回调表在任何时刻都只有一个写者，不需要锁。

以后 vCPU 线程需要 I/O 线程做事时（比如 guest 刚往磁盘控制器写了一条命令，需要后端开始读文件），它不直接去改表，而是写一个由 I/O 线程监听的 eventfd，让 I/O 线程在自己的回调里处理。

### 2.4 第一个后端：host 终端

host 终端是目前唯一的后端。`console_start()` 在 guest 启动前把 stdin 注册进事件循环：

```c
/* src/console.c */
    r = evl_add(loop, STDIN_FILENO, EPOLLIN, console_on_input, loop);
```

用户按下一个键，数据一路走到 guest 里的 shell：

```
  host 终端                I/O 线程 "io"                          vCPU 线程
  ─────────                ─────────────                          ─────────
  按下 'l'
    │
    └──► stdin 可读
         epoll_wait 返回
         console_on_input()
           read(stdin) 得到 'l'
           console_byte()：不是 Ctrl-A
           serial8250_push_rx()
             lock(serial.lock)
             'l' 放进 RX FIFO
             update_irq()
               → KVM_IRQ_LINE(4, 1) ──────────► KVM 给 guest 注入串口中断
             unlock                              guest 的 8250 中断处理函数：
                                                  inb 0x3fa (IIR)、inb 0x3fd (LSR)
                                                    → 各一次 KVM_EXIT_IO，看到“有数据”
                                                  inb 0x3f8 (RBR)
                                                    → KVM_EXIT_IO → 从 FIFO 取出 'l'
```

左边的 I/O 线程负责“等”和“放”，右边的 vCPU 线程只负责“取”，任何一步都不会让 vCPU 阻塞在 host 上。Ctrl-A 转义（Ctrl-A x 退出 VMM）也在 `console_byte()` 里识别，所以退出请求是从 I/O 线程发出的：它调用 `vm_request_stop()` 把所有 vCPU 踢出 `KVM_RUN`，这条停机路径在《多核·实现篇》1.5 节讲过。

## 三、四个容易踩的坑

### 3.1 同一批结果里的过期事件

`epoll_wait` 一次可以返回好几个就绪事件，它们被拷贝到用户态数组 `evs[]` 里。拷出来之后，前面的回调对回调表做了什么，数组里的内容都不会跟着变。看这样一个场景：

```
  evs[0] 指向 slots[0]（fd A）       evs[1] 指向 slots[1]（fd B）

  派发 evs[0]：A 的回调删掉了 B，又注册了新的 C

  如果 C 立刻复用 slots[1]：                 如果 slots[1] 先标成 retired：
    派发 evs[1] 时找到 slots[1]，              C 分到 slots[2]
    调用的是 C 的回调，                          派发 evs[1] 时 slots[1].fn == NULL，跳过
    而 C 根本没有就绪，带的还是 B 的事件
```

所以 `evl_del()` 在派发期间删除槽位时，只清空回调并标上 `retired`，这一批事件处理完之前不复用；一批处理完，再统一清掉 `retired` 标记。

目前只有 stdin 一个后端，这种情况实际不会发生。但等到网卡、磁盘接进来，一个后端出错时关掉自己再重新打开，就正好是这个场景，而它的症状是“某个回调偶尔被莫名其妙地调用”，事后很难查。单元测试专门构造了这种情况：C 是一个永远没有数据的空管道，它的回调被调用一次就算失败。把 `retired` 去掉之后，这条用例立刻失败。

### 3.2 读到 EOF 必须把自己删掉

epoll 有两种触发方式：

- **水平触发**（默认）：只要 fd 还处于可读状态，每次 `epoll_wait` 都会报它。
- **边沿触发**（`EPOLLET`）：只在“从不可读变成可读”的那一刻报一次。

mini-vmm 用水平触发，因为回调可以只处理一部分数据：终端一次读 64 字节，以后网卡一次只收接收环放得下的包，剩下的下一轮会再报。边沿触发要求回调一次把数据读干净，否则剩下的数据再也不会被通知，这又要求 fd 是非阻塞的，而 3.3 节会说明 stdin 不能设成非阻塞。

水平触发在内核里是这样实现的：`fs/eventpoll.c` 的 `ep_send_events()` 把一个事件交给用户态之后，对没有 `EPOLLET` 的条目会 `list_add_tail(&epi->rdllink, &ep->rdllist)`，把它放回就绪链表，下一次 `epoll_wait` 重新 poll 一遍这个 fd，还就绪就再报。

代价是：fd 一旦到了 EOF，它就**永远**可读。管道写端关闭后，poll 一直报 `EPOLLHUP`（连同 `EPOLLIN`），每次 `read` 都立刻返回 0。回调读到 EOF 却不把自己删掉，I/O 线程就会空转，把一颗 host CPU 吃满。

```c
/* src/console.c: console_on_input() */
    n = read(fd, buf, sizeof(buf));
    ...
    if (n <= 0) {           /* EOF：不再有输入，guest 继续跑 */
        evl_del(loop, fd);
        return;
    }
```

用 `true | ./build/vmm ...` 启动，stdin 一开始就是 EOF。去掉这行 `evl_del()` 的话，`console: stdin EOF` 这条日志在一次启动里会打印七十多万次；有它时恰好一次。

### 3.3 stdin 不能设成非阻塞

写事件循环时的常见习惯是把 fd 全设成 `O_NONBLOCK`。在 VMM 里对 stdin 这么做会出问题。

`O_NONBLOCK` 是“打开的文件”的属性，不是 fd 的属性。在终端里启动程序时，shell 只打开一次终端设备，再把它复制成 fd 0、1、2：

```
  fd 0 (stdin)  ─┐
  fd 1 (stdout) ─┼──► 同一个“打开的文件”：/dev/pts/3，标志位只有一份
  fd 2 (stderr) ─┘
```

给 stdin 设 `O_NONBLOCK`，stdout 也就一起变成了非阻塞。guest 的串口输出是写到 stdout 的，终端一忙，`write` 就返回 `EAGAIN`，guest 打印的内容被直接丢掉。

所以 stdin 保持阻塞模式，epoll 报可读之后只 `read` 一次。终端处在 raw 模式时（`cfmakeraw()` 设成 `VMIN=1, VTIME=0`），有 1 个字节就返回；stdin 是管道时，返回管道里已有的数据。两种情况下这一次 `read` 都不会阻塞。

### 3.4 `/dev/null` 不能被 epoll

自动化测试常把被测程序的 stdin 接到 `/dev/null`。普通文件和 `/dev/null` 都不支持 poll：`drivers/char/mem.c` 里 `/dev/null` 的 `null_fops` 没有 `.poll`，`fs/eventpoll.c` 的 `do_epoll_ctl()` 遇到 `!file_can_poll(file)` 就返回 `-EPERM`。事件循环把这种情况单独报成 `VMM_ERR_UNSUPPORTED`，由调用方决定算不算错。对控制台来说这不算错，guest 照常运行，只是没有输入：

```
[INFO] console: stdin cannot be polled (regular file or /dev/null), guest input is disabled
```

注册放在把终端切到 raw 模式之前。注册失败时终端保持原样，不会留下一个“已经切成 raw 模式却没人读”的终端。

## 四、两类线程怎么不打架

I/O 线程和 vCPU 线程会碰同一个设备：串口的 RX FIFO，I/O 线程往里放，vCPU 线程往外取。《传统设备·实现篇》1.8 节已经讲过 `io_lock` 和串口自己的锁，以及它们的顺序。有了事件循环，这个顺序变成所有回调都要遵守的规则：

```
  vCPU 线程：   io_lock ──► 设备锁 ──► KVM_IRQ_LINE
  I/O 线程：   [io_lock] ──► 设备锁 ──► KVM_IRQ_LINE
```

- 回调要更新一个**没有自己的锁**的设备时（比如 i8042、RTC 这类只靠 `io_lock` 保护的设备），先拿 `io_lock`，和 vCPU 线程的 exit 处理排队。
- 设备**有自己的锁**时（串口），回调只拿那把锁。
- 持有设备锁时，绝不能再去拿 `io_lock`。vCPU 线程是先 `io_lock` 后设备锁，反过来拿就可能出现两个线程各拿一把、互相等对方的死锁。

这几条写在 `include/io/event_loop.h` 的头注释里，以后接网卡、磁盘时照着做。

## 五、启动和停机的顺序

```
  vm_create
  evl_init                 epoll 实例 + 停机 eventfd
  设备注册、装载内核
    └─ console_start       evl_add(stdin)，终端切 raw 模式
  evl_start                创建 "io" 线程
  vm_run                   创建所有 vCPU 线程，等它们全部结束
  evl_stop                 写 eventfd，等 "io" 线程结束
  console_stop             恢复终端
  evl_destroy、vm_destroy
```

两个顺序是有意安排的：

- **所有后端在 `evl_start` 之前注册。** 这时只有主线程，符合 2.3 节“只有一个写者”的规定。
- **`evl_stop` 在 `vm_run` 返回之后。** 先等 vCPU 全部结束，再停 I/O 线程，之后就没有任何线程会碰设备状态。出错时打印寄存器和内存现场，读到的是静止的状态，不会一边打印一边被改。

Ctrl-A x 不需要单独的停机路径：I/O 线程识别到它之后调用 `vm_request_stop()`，所有 vCPU 退出，主线程的 `vm_run` 返回，接下来和 guest 自己关机走的是同一串步骤。

`evl_stop` 写 eventfd 失败时不去 `pthread_join`：I/O 线程收不到停机事件，join 会永远等下去，宁可让它随进程一起退出。eventfd 只在计数器将要溢出时写失败，这里每次只加 1，实际上不会发生，但这条路径要有确定的行为。

## 六、怎么确认它真的在工作

### 6.1 看线程

guest 停在 shell 提示符时，从 host 上看 VMM 进程的每个线程叫什么名字、睡在内核的什么地方：

```bash
for t in /proc/$(pidof vmm)/task/*; do
    echo "$(cat $t/comm) $(cat $t/wchan)"
done
```

`--smp 2` 的 guest 得到：

```
vmm   futex_wait_queue     主线程在 pthread_join，等 vCPU 结束
io    do_epoll_wait        I/O 线程在 epoll_wait
vcpu0 kvm_vcpu_block       guest 空闲，vCPU 睡在 HLT
vcpu1 kvm_vcpu_block
```

这就是第二章那张结构图的实物。如果终端输入是由一个没命名的阻塞读线程处理的，这里会多出一个 `vmm`，睡在终端的 `read` 里。

`wchan` 显示的是内核函数名，会随内核版本变。6.x 内核上 `ep_poll` 被内联进了 `do_epoll_wait`，所以显示后者；`ep_poll` 没被内联的内核上显示 `ep_poll`。测试两者都接受。换 host 内核后这条断言失败时，先看 `/proc/<pid>/task/<tid>/wchan` 实际是什么。

### 6.2 自动化测试

`make test event-loop` 跑 `tests/e2e/event-loop.sh`，三条用例：

| 用例 | 判据 |
|---|---|
| 线程布局与终端输入 | 线程名恰好是 `io vcpu0 vcpu1 vmm`，`io` 睡在 epoll 里；在 guest 里执行 `echo EVL-$((6*7))`，输出 `EVL-42`；Ctrl-A x 能退出 |
| stdin 是 `/dev/null` | 打印“guest input is disabled”，guest 照常启动，最后经 i8042 复位退出 |
| stdin 一开始就是 EOF | `console: stdin EOF` 恰好出现一次，停机时 I/O 线程正常结束 |

第一条里用 `$((6*7))` 而不是直接 `echo EVL-42`，是因为终端会回显输入的命令行；只有 guest 真的执行了命令，输出里才会出现 `42`，回显里只有 `6*7`。

事件循环本身的规则由单元测试 `tests/unit/event_loop_test.c` 覆盖（在 ASan 和 UBSan 下运行，`alarm(30)` 防止测试挂死）。一条判据有没有用，要看它在实现写错时会不会失败，所以有几条专门拿故意写错的版本对照过：

| 规则 | 判据 | 写错的版本上会怎样 |
|---|---|---|
| 回调在 I/O 线程上运行 | 回调里记下 `pthread_self()`，等于 I/O 线程、不等于主线程 | — |
| `evl_stop` 能唤醒空闲的循环 | 没有任何 fd 时 `evl_stop` 也能返回 | 不写 eventfd：卡住，被 `alarm` 杀掉 |
| 同一批里被删的 fd 不再派发 | 两个 fd 的回调互删，恰好一个回调运行 | — |
| 删了再注册不误派发（3.1 节） | 空管道 C 的回调调用次数为 0 | 去掉 `retired`：调用了 1 次 |
| 运行中别的线程不能改表 | 主线程调用 `evl_add`/`evl_del` 返回 `VMM_ERR_INVAL` | 去掉线程检查：两条都失败 |
| 不能 poll 的 fd | `/dev/null` 返回 `VMM_ERR_UNSUPPORTED`，不占槽位 | — |
| EOF 后摘除（3.2 节） | 回调恰好调用一次，带 `EPOLLHUP` | e2e 里去掉 `evl_del`：EOF 日志七十多万条 |

上面 e2e 的三条用例，放在终端输入由一个阻塞读线程处理的 VMM 上跑会全部失败：线程名是 `vcpu0 vcpu1 vmm vmm`，没有 `io`。

另外，其他 e2e 用例里所有在 guest shell 里执行的命令，都是经由 I/O 线程送进去的。它们全部通过，就说明串口输入这条路径没有被改坏。

## 七、限制

- **串口输出仍在 vCPU 线程里同步写 stdout。** 终端或管道读得慢时，写 THR 的 vCPU 会阻塞在 `write` 里。改成异步要给 THR 加发送缓冲，THRE 中断和 LSR 的 THRE/TEMT 位也要跟着缓冲状态变，这和串口本身的语义绑在一起。
- **RX FIFO 满了丢字节，没有流控。** 有了事件循环之后可以做：FIFO 满时用 `EPOLL_CTL_MOD` 暂停监听 stdin，guest 读走数据后再恢复。但“guest 读走了”发生在 vCPU 线程上，需要一个从 vCPU 通知 I/O 线程的 eventfd（2.3 节）。
- **目前只有 stdin 一个后端。** TAP、磁盘文件、socket 在 `emu-net`、`emu-blk` 里接入，异步块 I/O 在 `blk-io-uring`。
