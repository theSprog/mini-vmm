文中的“阶段 N”指《中断·实现篇》第一章的开机十阶段表。

## 一、阶段 2：内存与物理布局

### 1.1 阶段 2：内存

内存部分与《一次 out 指令的完整旅程》相比没有本质变化：`mmap` 一块匿名内存，用 `KVM_SET_USER_MEMORY_REGION` 注册成 0 号 memslot，GPA 从 0 开始。有两处值得一提的改进：

```c
    p = mmap(NULL, ram_size, PROT_READ | PROT_WRITE,
             MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);
    ...
    /* 尽量让 host 用 2MiB 透明大页承载 guest RAM，减少 NPT 的层级和
     * TLB miss。失败不致命（比如 THP 被关掉了）。 */
    if (madvise(p, ram_size, MADV_HUGEPAGE) < 0)
        ...
```

一是 `MADV_HUGEPAGE`：让 host 尽量用 2MB 透明大页来承载 guest 内存，减少 NPT 的页表层级和 TLB 缺失。

二是内存超过 3GB 时的切分：`[3GB, 4GB)` 要留给 IOAPIC、LAPIC 和以后的 PCI BAR，所以 RAM 被拆成两个 memslot，低段 `[0, 3GB)`，超出的部分放到 4GB 以上。下面的布局图以 512MB guest 为例，只用到低段；切分本身和 E820 怎么跟着变，见《内存基础》第一章和第三章。

**IOAPIC（`0xFEC00000`）和 LAPIC（`0xFEE00000`）不需要任何 memslot。** guest 访问这两个地址时，NPT 里没有映射，产生 `#NPF`，KVM 发现这个 GPA 不属于任何 memslot，就当作 MMIO 处理：先在内核的 MMIO 总线上找有没有设备认领，内核态的 IOAPIC 和 LAPIC 就挂在那条总线上，于是访问在内核里就被处理掉了，根本不会回到用户态。

### 1.2 guest 物理内存布局

阶段 6 往 guest 内存里写了很多东西。它们各自放在哪、为什么放在那里，是 VMM 最容易出错的地方之一：两个结构重叠了，后写的会覆盖先写的，症状千奇百怪。下图是 512MB guest 的完整布局：

```
   GPA                    内容                         谁决定的地址
   ─────────────────────────────────────────────────────────────────────────────
   0x0000_0000 ┌──────────────────────────┐
               │ （空闲，实模式 IVT 位置）   │
   0x0000_1000 ├──────────────────────────┤
               │ GDT（4 项，32 字节）       │  VMM 自选，要避开下面所有结构
   0x0000_2000 ├──────────────────────────┤
               │ PML4                     │  VMM 自选；CR3 指向这里
   0x0000_3000 ├──────────────────────────┤
               │ PDPT                     │
   0x0000_4000 ├──────────────────────────┤
               │ PD（512 项 × 2MB = 1GB）  │
   0x0000_5000 ├──────────────────────────┤
               │ （空闲）                  │
   0x0000_7000 ├──────────────────────────┤
               │ boot_params（4KB）        │  VMM 自选；RSI 指向这里
   0x0000_8000 ├──────────────────────────┤
               │ （空闲，Linux 可能在低端    │  Linux 自己在低端 RAM 里挑地方
               │   内存里放 AP trampoline） │  放 trampoline
   0x0002_0000 ├──────────────────────────┤
               │ 内核命令行（≤ 4KB）         │  VMM 自选；boot_params 里记录
   0x0002_1000 ├──────────────────────────┤
               │ （空闲，E820 报告为 RAM）   │
   0x0009_FC00 ├──────────────────────────┤  ← E820：RAM 到此为止
               │ MP table（≤ 1KB）         │  MPS 规范：Linux 扫描 639K–640K
   0x000A_0000 ├──────────────────────────┤  ← E820：保留区
               │ （VGA 窗口，未使用）        │
   0x000E_0000 ├──────────────────────────┤
               │ACPI：RSDP/XSDT/FADT/DSDT/│  ACPI 规范：RSDP 在 0xE0000–0xFFFFF
               │       MADT               │
   0x0010_0000 ├──────────────────────────┤  ← 1MB，E820：RAM
               │ （空闲）                  │
   0x0100_0000 ├──────────────────────────┤  ← 16MB
               │ vmlinux 各 PT_LOAD 段     │  vmlinux 的 ELF 头（p_paddr）决定
   0x02A3_0000 ├──────────────────────────┤  ← 内核镜像结束（含 bss）
               │ （空闲，内核运行时的内存）   │
   0x1FE0_0000 ├──────────────────────────┤
               │ initrd（约 1MB）          │  VMM 自选：RAM 顶端向下 2MB 对齐
   0x2000_0000 └──────────────────────────┘  ← 512MB，RAM 结束
                            ...
   0xFEC0_0000   IOAPIC 寄存器                 KVM 内核态模拟，不在任何 memslot 里
   0xFEE0_0000   LAPIC 寄存器                  KVM 内核态模拟，不在任何 memslot 里
```

这张图里的地址分三类：

- **规范规定的**：MP table 要在 639K–640K（或另外两个扫描区），RSDP 要在 `0xE0000`–`0xFFFFF`，LAPIC 和 IOAPIC 的默认地址。放错了 guest 找不到。
- **镜像决定的**：vmlinux 的加载地址由它自己的 ELF 程序头决定，VMM 只能照办。
- **VMM 自选的**：GDT、页表、boot_params、cmdline、initrd。选择的原则是互不重叠、都在 RAM 里、都在页表的恒等映射范围内（启动协议要求）、并且避开内核镜像。

mini-vmm 在代码里用几个宏固定了这些地址：

```c
/* include/boot/gdt_pgtable.h */
#define BOOT_GDT_GPA     0x1000ULL
#define BOOT_PML4_GPA    0x2000ULL
#define BOOT_PDPT_GPA    0x3000ULL
#define BOOT_PD_GPA      0x4000ULL

/* include/boot/zeropage.h */
#define ZP_BOOT_PARAMS_GPA  0x7000ULL
#define ZP_CMDLINE_GPA      0x20000ULL

/* include/boot/mptable.h */
#define MPTABLE_GPA        0x9fc00ULL

/* include/boot/acpi.h */
#define ACPI_TABLES_GPA   0xE0000ULL
```

有一个细节要注意：`0x9FC00` 到 `0x100000` 这一段在 E820 里报告为“保留”，但它**仍然在 memslot 覆盖的 RAM 里**。这两件事并不矛盾：memslot 决定“这段 GPA 背后有没有真实内存”（MP table 和 ACPI 表必须写在真实内存里，guest 才读得到），E820 决定“guest 内核能不能把这段内存拿去分配”（不能，否则固件表会被覆盖）。

## 二、阶段 6 与阶段 7：固件表、启动协议与 BSP 寄存器

这一章是本文细节最密集的部分。阶段 6 往 guest 内存里写七样东西，阶段 7 设置 BSP 的寄存器。每一样都有一组“必须是这个值”的字段，按 `boot_linux()` 里的执行顺序依次讲。

```c
static int boot_linux(struct vmm_vm *vm, struct vmm_vcpu *vcpu,
                      const struct vmm_config *cfg, struct serial8250 *com1)
{
    ...
    r = elf_load_vmlinux(vm, cfg->payload_path, &elf);        /* 12.1 内核镜像 */
    r = mptable_setup(vm, vm->nr_vcpus);                      /* 12.5 MP table */
    r = acpi_setup(vm, vm->nr_vcpus, &rsdp);                  /* 12.4 ACPI */
    zc.acpi_rsdp   = rsdp;
    zc.cmdline     = cfg->cmdline;
    zc.initrd_path = cfg->initrd_path;
    zc.kernel_end  = elf.hi_gpa;
    r = zeropage_setup(vm, &zc);                              /* 12.2/12.3 boot_params、E820、cmdline、initrd */
    boot_layout_default(&layout);
    r = boot_build_page_table(vm, &layout);                   /* 12.6 页表 */
    r = boot_setup_linux64(vcpu, &layout, elf.entry_gpa,
                           ZP_BOOT_PARAMS_GPA);               /* 12.6/12.7 GDT 与 BSP 寄存器 */
    return console_start(vm, com1);
}
```

顺序上有两个依赖：ACPI 表要在 boot_params 之前生成，因为 boot_params 里要填 RSDP 的地址；内核镜像要在 initrd 之前载入，因为 initrd 的位置要避开内核的末尾。

### 2.1 内核镜像：按物理地址摆放 vmlinux / bzImage

bzImage 是一个“自解压”格式：前面是 16 位的 setup 代码和 setup header，后面是压缩过的内核加上一段解压代码。加载 bzImage 需要解析 setup header、按协议摆放、从 32 位或 64 位入口进入解压代码，解压代码再把真正的内核解压到目标地址。

vmlinux 的每个 `PT_LOAD` 段同时有两个地址：`p_vaddr` 是内核虚拟地址（如 `0xffffffff81000000`），`p_paddr` 是物理地址（如 `0x1000000`）。VMM 此时还没有进入 guest，只能按物理地址摆放：

```c
    for (i = 0; i < eh->e_phnum; i++) {
        const Elf64_Phdr *p = &ph[i];
        uint8_t *dst;

        if (p->p_type != PT_LOAD || p->p_memsz == 0)
            continue;
        ...
        gpa_to_hva(vm, p->p_paddr, p->p_memsz, (void **)&dst);   /* 按 p_paddr 摆放 */
        memcpy(dst, img + p->p_offset, p->p_filesz);
        memset(dst + p->p_filesz, 0, p->p_memsz - p->p_filesz);   /* bss 清零 */
        ...
    }
```

要做对的三件事：

1. **用 `p_paddr` 而不是 `p_vaddr`**。用虚拟地址会直接越界。
2. **`p_memsz` 大于 `p_filesz` 的部分要清零**，那是 bss 段。真实日志里最后一个段 `file 0x238000 mem 0x50d000`，有将近 3MB 的 bss。依赖 `mmap` 出来的匿名内存本来就是零也可以，但显式清零更稳妥（比如以后支持重启时复用内存）。
3. **入口地址 `e_entry` 要换算成物理地址**。x86_64 vmlinux 的链接脚本写的是 `ENTRY(phys_startup_64)`，已经是物理地址（真实日志里是 `0x1000000`）；但为了兼容别的构建方式，代码里检查了一下：如果 `e_entry` 落在某个段的虚拟地址范围里，就用该段的 `p_vaddr - p_paddr` 换算回物理地址。

内核被加载在 16MB（`0x1000000`）处，这是 x86_64 内核默认的 `CONFIG_PHYSICAL_START`。VMM 还要检查内核镜像不低于 1MB，否则会压到低端的 GDT、页表、boot_params。载入完成后记下镜像的最高地址（`hi_gpa`，含 bss），给 2.3 节摆放 initrd 用。

> 之所以加载在 16M，是因为传统的 ISA 总线设备以及部分陈旧外设仅支持 24 位寻址，这意味着它们的 DMA 只能访问物理内存的前 16MB，Linux 内核据此划分出了 `ZONE_DMA`（0~16MB）。

### 2.2 boot_params：VMM 交给内核的“交接单”

`struct boot_params` 固定 4KB，mini-vmm 把它放在 GPA `0x7000`，并在阶段 7 把 `RSI` 设为这个地址。结构体的定义直接用内核导出给用户态的 `<asm/bootparam.h>`，不自己抄一份，避免偏移写错。

先整体清零，然后只填内核真正会读的字段：

| 字段 | 偏移 | mini-vmm 填的值 | 含义与必要性 |
|---|---|---|---|
| `hdr.boot_flag` | `0x1FE` | `0xAA55` | setup header 的魔数，沿用引导扇区的签名 |
| `hdr.header` | `0x202` | `0x53726448`（`"HdrS"`） | setup header 的魔数 |
| `hdr.version` | `0x206` | `0x020F` | 声明遵循启动协议 2.15；下面的 `acpi_rsdp_addr` 是 2.14 引入的字段 |
| `hdr.type_of_loader` | `0x210` | `0xFF` | bootloader 类型，`0xFF` 表示“未注册的 bootloader” |
| `hdr.loadflags` | `0x211` | `0x01`（`LOADED_HIGH`） | 内核被加载在 1MB 以上 |
| `hdr.kernel_alignment` | `0x230` | `0x1000000` | 内核的物理对齐要求 |
| `hdr.cmd_line_ptr` | `0x228` | `0x20000` | 内核命令行的物理地址（低 32 位） |
| `hdr.cmdline_size` | `0x238` | 命令行长度 | |
| `ext_cmd_line_ptr` | `0x0C8` | 0 | 命令行地址的高 32 位 |
| `hdr.ramdisk_image` | `0x218` | initrd 的物理地址（低 32 位） | 没有 initrd 时为 0 |
| `hdr.ramdisk_size` | `0x21C` | initrd 的字节数（低 32 位） | |
| `ext_ramdisk_image` / `ext_ramdisk_size` | `0x0C0` / `0x0C4` | 高 32 位 | 支持 4GB 以上的 initrd |
| `hdr.initrd_addr_max` | `0x22C` | `0x37FFFFFF` | initrd 的最高地址；vmlinux 没有 setup header，填内核默认值 |
| `acpi_rsdp_addr` | `0x070` | `0xE0000` | 协议 2.14 起，直接告诉内核 RSDP 在哪，不必扫描 |
| `e820_entries` | `0x1E8` | 3 | E820 表的项数 |
| `e820_table[]` | `0x2D0` | 见 2.3 节 | 每项 20 字节：8 字节地址、8 字节长度、4 字节类型 |

有两点说明。

第一，关于魔数和版本号。直接从 64 位入口启动 vmlinux 时，内核并不会严格校验 `boot_flag`、`header` 这些魔数（这些检查在 bzImage 的 16 位 setup 代码里）。但它们是启动协议的一部分，填上是约定，部分工具和内核路径也会参考 `version` 字段。

第二，关于先清零。`boot_params` 里有很多字段是“非零表示某个功能”，比如 `hdr.hardware_subarch` 非零时内核会走 Intel MID 这类特殊平台的初始化，`sentinel` 字段非零时内核会认为 bootloader 没有正确清零、主动把一大片字段清掉。先 `memset` 为 0 再填，是避免这类意外的最简单办法。

内核在 `startup_64` 之后很早就会调用 `copy_bootdata()`，把这 4KB 拷贝到内核自己的 `boot_params` 变量里，并按 `cmd_line_ptr` 把命令行拷走。之后原来的 `0x7000` 页面和命令行页面就不再被使用，会作为普通内存释放。所以 boot_params 放在低端内存里不会与后续的 trampoline 等用途产生长期冲突。

### 2.3 E820、命令行与 initrd

#### 2.3.1 E820

E820 表只有三项，《固件与启动协议·原理篇》1.2 节讲了每一项的来历：

```c
    e820_add(bp, 0,                 ZP_EBDA_START,                     E820_TYPE_RAM);
    e820_add(bp, ZP_EBDA_START,     ZP_HIGH_MEM_START - ZP_EBDA_START, E820_TYPE_RESERVED);
    e820_add(bp, ZP_HIGH_MEM_START, ram - ZP_HIGH_MEM_START,           E820_TYPE_RAM);
```

| 区间 | 类型 | 为什么 |
|---|---|---|
| `[0, 0x9FC00)` | RAM | 低端内存必须给，Linux 要在这里放 AP 的 trampoline |
| `[0x9FC00, 0x100000)` | 保留 | EBDA、VGA、BIOS 区。MP table（`0x9FC00`）和 ACPI 表（`0xE0000`）就放在这里面，报保留才不会被内核当成空闲内存覆盖 |
| `[0x100000, ram)` | RAM | 内核、initrd、所有运行时内存 |

注意 GDT、页表、boot_params、命令行都在第一个区间里，而这个区间报告的是“可用 RAM”。这没有问题：这些结构只在启动最初的一小段时间里有用，内核拷走需要的内容、换上自己的页表和 GDT 之后，它们就可以被回收。真实 BIOS 交给 bootloader 的内存图也是这样。

#### 2.3.2 命令行

默认命令行是：

```
console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1
```

| 参数 | 作用 | 不加会怎样 |
|---|---|---|
| `console=ttyS0` | 内核日志和 `/dev/console` 走第一个串口 | 日志输出到不存在的 VGA，串口上什么都看不到 |
| `earlyprintk=serial,ttyS0,115200` | 在 8250 驱动加载之前，就用最简单的轮询方式往串口写日志 | 内核在驱动加载之前崩溃时一行日志都没有；真实日志里 `printk: bootconsole [earlyser0] enabled` 就是它 |
| `reboot=k` | 重启时写 i8042 的 `0xFE` 命令 | 内核会尝试 ACPI reset、PCI reset 等方式，VMM 可能收不到重启信号 |
| `panic=-1` | panic 后立即重启 | panic 后内核挂住，VMM 永远不退出 |

后两个参数把 guest 的“重启”和“panic”都变成了一次 i8042 复位，也就是 VMM 退出的信号。测试脚本依赖这一点：不给 initrd 时内核会以 `VFS: Unable to mount root fs` panic，然后重启，VMM 应该干净地退出。

命令行写在 GPA `0x20000`，以 `\0` 结尾，长度不超过 4096 字节。`--append` 选项可以在默认命令行后面追加参数，比如调试时加 `maxcpus=1`（只启动 BSP）或 `acpi=off`（下面 2.5 节会用到）。

#### 2.3.3 initrd

initrd 放在哪里，启动协议没有规定，只要求在 `initrd_addr_max` 以下、不与内核重叠、在页表的映射范围内。mini-vmm 的选择是 **RAM 顶端向下按 2MB 对齐**：

```c
    top = vm->mem.ram_size;
    if (top > ZP_INITRD_ADDR_MAX + 1)
        top = ZP_INITRD_ADDR_MAX + 1;
    ...
    gpa = ALIGN_DOWN(top - (uint64_t)st.st_size, 2ULL << 20);
    if (gpa < zc->kernel_end) {
        vmm_err("initrd [0x%llx, +0x%llx) overlaps the kernel image ...");
        return VMM_ERR_INVAL;
    }
```

放在顶端的理由是：内核启动时从低地址往上分配内存（早期页表、直接映射的页表、各种早期数据结构），initrd 在顶上最不容易被踩到。512MB 的 guest 上，1MB 左右的 initramfs 被放在 `0x1FE00000`。日志印证了这个位置，而且内核直接在原地使用它，没有搬移：

```
[    0.007782] RAMDISK: [mem 0x1fe00000-0x1ff09fff]
```

initrd 的内容是一个 cpio 归档（可以 gzip 压缩），内核在启动后期把它解开成根文件系统，然后执行其中的 `/init`。mini-vmm 用 `tools/build_initramfs.sh` 生成一个只含静态链接 busybox 的 initramfs，它的 `/init` 挂载 `/proc`、`/sys`、`/dev`，然后启动 shell，shell 退出后执行 `poweroff -f`。busybox 必须是**静态链接**的：initramfs 里没有动态链接器，动态链接的 busybox 会报 `No such file or directory`（找不到的其实是 `ld.so`）。

### 2.4 ACPI 表：主角

《固件与启动协议·原理篇》第一章讲了 ACPI 的结构，这一节讲 mini-vmm 具体生成了什么。全部表放在从 `0xE0000` 开始的 64KB 内，每张表 16 字节对齐：

```
   GPA        表      长度    内容
   0xE0000    RSDP    36     → XSDT
   0xE0030    XSDT    52     → FADT, MADT
   0xE0070    FADT    276    → DSDT；PM1a 在 0x600/0x604；SCI = 9
   0xE0190    DSDT    50     AML: Name(_S5, Package(){5,5,0,0})
   0xE01D0    MADT    94     4×LAPIC + IOAPIC + LAPIC_NMI
```

这些地址与真实日志里 `ACPI: RSDP 0x00000000000E0000 000024` 等几行完全对应。

#### 2.4.1 通用规则：表头与校验和

除 RSDP 外，每张表以 36 字节的通用表头开始：

```c
struct acpi_header {
    char     signature[4];      /* "XSDT"、"FACP"、"DSDT"、"APIC" */
    uint32_t length;            /* 整张表的长度，含表头 */
    uint8_t  revision;
    uint8_t  checksum;          /* 整张表所有字节之和 mod 256 == 0 */
    char     oem_id[6];
    char     oem_table_id[8];
    uint32_t oem_revision;
    char     creator_id[4];
    uint32_t creator_revision;
} __attribute__((packed));
```

两条必须遵守的规则：

1. **所有结构体都要 `packed`**，并且用 `_Static_assert` 在编译期检查大小。ACPI 表的字段大量是非对齐的（比如 FADT 里 `uint32_t flags` 紧跟在一个 `uint8_t` 后面），不加 `packed` 编译器会插入填充，所有偏移都会错。mini-vmm 对每个结构体都有断言，比如 `_Static_assert(sizeof(struct acpi_fadt) == 276, "fadt size");`。
2. **校验和最后算**。先把表的所有字段（包括 `length`）填好，把 `checksum` 置 0，计算全部字节之和，取负数写回 `checksum`。任何在算完校验和之后的修改都会让校验和失效。

```c
static uint8_t acpi_checksum(const void *p, size_t len)
{
    const uint8_t *b = p;
    uint8_t sum = 0;

    while (len--)
        sum += *b++;
    return (uint8_t)(-sum);
}
```

Linux 默认不严格校验表的校验和（日志里 `ACPI: Early table checksum verification disabled`），但 RSDP 的校验和是一定会检查的，而且其他操作系统和工具（比如 `acpidump`）会校验，所以必须算对。

#### 2.4.2 RSDP

```c
    memcpy(rsdp->signature, "RSD PTR ", 8);   /* 注意末尾的空格，共 8 字节 */
    memcpy(rsdp->oem_id, ACPI_OEM_ID, 6);
    rsdp->revision     = 2;                    /* ACPI 2.0+：使用 XSDT */
    rsdp->length       = sizeof(*rsdp);        /* 36 */
    rsdp->xsdt_address = ACPI_TABLES_GPA + xsdt_off;
    rsdp->checksum     = acpi_checksum(rsdp, 20);            /* 只算前 20 字节 */
    rsdp->ext_checksum = acpi_checksum(rsdp, sizeof(*rsdp)); /* 算全部 36 字节 */
```

两个校验和的顺序不能反：`ext_checksum` 覆盖了 `checksum` 所在的字节，所以必须先算 `checksum` 再算 `ext_checksum`。`rsdt_address` 保持 0：`revision = 2` 时操作系统使用 XSDT，不需要提供 32 位的 RSDT。

RSDP 放在 `0xE0000`，16 字节对齐，位于 ACPI 规范规定的扫描区 `[0xE0000, 0xFFFFF]` 内。同时它的地址也填进了 `boot_params.acpi_rsdp_addr`，两条路都能找到。

#### 2.4.3 XSDT

XSDT 是表头加一个 64 位地址数组。mini-vmm 只列两项：FADT 和 MADT。**DSDT 不列在 XSDT 里**，它由 FADT 的 `DSDT`/`X_DSDT` 字段引用，这是 ACPI 规范的规定：XSDT 只列“顶层”的表，DSDT 通过 FADT 间接找到。

#### 2.4.4 FADT

FADT（签名 `"FACP"`，注意不是 `"FADT"`）是 276 字节的大结构，mini-vmm 只填其中十来个字段，其余为 0：

| 字段 | 值 | 为什么 |
|---|---|---|
| `DSDT` / `X_DSDT` | `0xE0190` | 两个都填。ACPICA 优先用 64 位的 `X_DSDT` |
| `SCI_INT` | 9 | ACPI SCI 的传统中断号 |
| `SMI_CMD` | 0 | 已经在 ACPI 模式，不需要切换 |
| `PM1a_EVT_BLK` | `0x600` | 与 `acpi_pm_attach()` 注册的端口一致 |
| `PM1a_CNT_BLK` | `0x604` | 同上，关机写这里 |
| `PM1_EVT_LEN` | 4 | 事件块长度：STS 2 字节 + EN 2 字节 |
| `PM1_CNT_LEN` | 2 | 控制块长度 |
| `CENTURY` | `0x32` | 与 RTC 模拟里的世纪寄存器一致 |
| `IAPC_BOOT_ARCH` | `LEGACY_DEVICES \| 8042` | 声明有传统设备和 8042 键盘控制器 |
| `Flags` | `WBINVD \| PWR_BUTTON \| SLP_BUTTON` | 第 4、5 位置 1 表示“没有固定功能电源键/睡眠键”；**第 20 位 HW_REDUCED_ACPI 保持 0** |
| 表头 `revision` | 6 | 配合 276 字节的长度 |
| `minor_version` | 4 | FADT 次版本号 |
| `X_PM1a_EVT_BLK` 等扩展地址字段 | 全 0 | ACPICA 会从 32 位字段自动转换出扩展格式 |

两个关键点再强调一次：`Flags` 第 20 位必须为 0（《固件与启动协议·原理篇》1.4.3 节，否则 Linux 放弃 PIT 和 8259A）；PM1 相关的端口必须与 VMM 实际注册的设备一致（否则关机写到了没人响应的端口）。`SMI_CMD = 0` 与 PM1a 设备读回 `SCI_EN = 1` 是一对配合的设置。

`PWR_BUTTON` 和 `SLP_BUTTON` 这两位的语义是反的：置 1 表示“**没有**固定功能按钮”（如果有，按钮会作为控制方法设备出现在 DSDT 里）。它们置 1，Linux 就不会去 PM1 事件寄存器里等按钮事件。

#### 2.4.5 DSDT：14 字节的 AML

DSDT 是表头加 AML 字节码。mini-vmm 的全部 AML 只有 14 个字节：

```c
static const uint8_t dsdt_aml[] = {
    0x08, '_', 'S', '5', '_', 0x12, 0x08, 0x04,
    0x0a, 0x05, 0x0a, 0x05, 0x00, 0x00,
};
```

逐字节拆开：

| 字节 | 含义 |
|---|---|
| `08` | `NameOp`：定义一个命名对象 |
| `5F 53 35 5F` | 名字 `"_S5_"`。ACPI 名字固定 4 字节，ASL 里写的 `_S5` 在编码时补齐下划线 |
| `12` | `PackageOp`：对象的值是一个包 |
| `08` | `PkgLength`：包的长度，从这个字节本身开始算，共 8 字节 |
| `04` | `NumElements`：包里有 4 个元素 |
| `0A 05` | `BytePrefix` + 5：第 1 个元素，PM1a_CNT 的 SLP_TYP |
| `0A 05` | `BytePrefix` + 5：第 2 个元素，PM1b_CNT 的 SLP_TYP |
| `00` | `ZeroOp`：第 3 个元素，保留 |
| `00` | `ZeroOp`：第 4 个元素，保留 |

`PkgLength` 是 AML 里最容易算错的字段：它包含自身占用的字节数，但不包含 `PackageOp`。这里自身 1 字节加上 `NumElements` 的 1 字节加上 6 字节元素，一共 8。如果包的总长度超过 63，`PkgLength` 就要用多字节编码，这时手写 AML 就不现实了，应该用 `iasl` 编译器从 ASL 生成。

SLP_TYP 的值 5 本身没有特殊含义，它只需要与 PM1a 设备里判断关机的值一致。真实硬件上这个值由芯片组决定，不同主板不同。

#### 2.4.6 MADT

```c
    madt->lapic_addr = MP_LAPIC_BASE;          /* 0xFEE00000 */
    madt->flags      = MADT_PCAT_COMPAT;       /* 同时存在 8259A */

    for (i = 0; i < nr_cpus; i++) {            /* 类型 0：每个 vCPU 一项 */
        l->type         = 0;
        l->length       = 8;
        l->processor_id = (uint8_t)i;          /* ACPI 处理器 ID */
        l->apic_id      = (uint8_t)i;          /* 必须等于 KVM 的 LAPIC ID = vcpu_id */
        l->flags        = 1;                   /* 已启用 */
    }
    /* 类型 1：IOAPIC */
    io->ioapic_id = (uint8_t)nr_cpus;          /* 与 MP table 一致，避开 LAPIC ID */
    io->address   = MP_IOAPIC_BASE;            /* 0xFEC00000 */
    io->gsi_base  = 0;
    /* 类型 4：所有 CPU 的 LINT1 接 NMI */
    n->processor_id = 0xff;
    n->lint         = 1;
```

逐项的要求：

- `lapic_addr` 必须是 `0xFEE00000`，这是 KVM LAPIC 的地址。
- `PCAT_COMPAT` 置 1，告诉 Linux 有 8259A，需要先屏蔽它再切换到 APIC 模式。KVM 确实模拟了 8259A，所以这一位是如实描述。
- 每个 LAPIC 条目的 `apic_id` 必须等于对应 vCPU 的 ID，这是三方一致原则里“固件表”那一方。`flags` 第 0 位必须置 1，否则 Linux 认为这颗 CPU 被禁用了，`smpboot: Allowing N CPUs` 里的数字会变小。
- IOAPIC 的 `address` 必须是 `0xFEC00000`，`gsi_base` 为 0。ID 选 `nr_cpus`，这样 4 核时 LAPIC ID 是 0 到 3、IOAPIC ID 是 4，互不冲突。
- 不写任何类型 2（中断源覆盖）条目。
- 类型 4 条目声明 LINT1 接 NMI，`processor_id = 0xFF` 表示所有处理器。这是 PC 平台的标准接法，也与 KVM LAPIC 的行为一致。

### 2.5 MP table：acpi=off 时的退路

《固件与启动协议·原理篇》1.5 节讲过，guest 能用 ACPI 时 MP table 会被忽略。但在 `acpi=off` 时（或者 guest 内核没编译 ACPI），它是唯一的中断拓扑描述。可以用 `--append acpi=off` 验证这条路径。

MP table 放在 `0x9FC00`，这是 Linux `default_find_smp_config()` 扫描的第二个区间（常规内存最后 1KB，639K 到 640K）。整张表不超过 1KB：

```
   0x9FC00  MP 浮动指针（16 字节）
            signature  = "_MP_"
            physptr    = 0x9FC10      → 紧随其后的配置表
            length     = 1            （以 16 字节为单位）
            specification = 4         （MPS 1.4）
            checksum   = 使 16 字节之和为 0
            feature1   = 0            （0 = 后面有真正的配置表，不用默认配置）
   0x9FC10  MP 配置表头（44 字节）
            signature  = "PCMP"
            length     = 表头 + 所有条目
            spec       = 4
            oem / productid
            oemcount   = 条目个数
            lapic      = 0xFEE00000
            checksum   = 使整张配置表之和为 0
            ── 条目 ──
            processor × N  （每项 20 字节）apicid = i，cpuflag = ENABLED | (i==0 ? BP : 0)
            bus × 1        （8 字节）   busid = 0，bustype = "ISA   "
            ioapic × 1     （8 字节）   apicid = N，flags = USABLE，apicaddr = 0xFEC00000
            intsrc × 16    （每项 8 字节）ISA IRQ i → IOAPIC pin i
            lintsrc × 2    （每项 8 字节）LINT0 = ExtINT，LINT1 = NMI，dstapic = 0xFF
```

每个字段的要求：

- **浮动指针和配置表各有一个校验和**，都是“所有字节之和为 0”。浮动指针的校验和覆盖 16 字节，配置表的覆盖 `length` 字节。
- **`feature1` 必须为 0**。非零表示“使用 MPS 规范定义的某种默认配置”，此时 Linux 会忽略配置表，按一个固定的双 CPU 配置来处理。
- **处理器条目的 `cpuflag`**：第 0 位 `ENABLED`，第 1 位 `BP`（是 BSP）。只有 0 号 CPU 置 BP 位，与 KVM 的 BSP（`vcpu_id == 0`）一致。`cpufeature` 和 `featureflag` 字段 Linux 只用来打印，填一个合理的值即可。
- **总线条目**：`bustype` 是 6 个字符，`"ISA"` 后面补 3 个空格。I/O 中断条目通过 `srcbus = 0` 引用它，表明这些是 ISA 中断。
- **IOAPIC 条目**：`apicid` 必须与 MADT 里的一致（都是 N），`flags` 第 0 位 `USABLE` 必须为 1。
- **I/O 中断条目**：16 条，`irqflag = 0`（按总线默认：ISA 是边沿、高有效），`srcbusirq = i`，`dstirq = i`，恒等映射。
- **本地中断条目**：LINT0 接 ExtINT（8259A 的 INT 输出），LINT1 接 NMI，`dstapic = 0xFF` 表示所有 LAPIC。这让 Linux 在切换到 symmetric I/O 之前能正确地使用 virtual wire 模式。

条目个数 `oemcount` 和表长度 `length` 都要在填完所有条目后计算，然后才算校验和。

真实日志里，VMM 生成 MP table 时的输出：

```
[INFO] MP table @ GPA 0x9fc00: 4 CPU(s), IOAPIC id 4 @ 0xfec00000, 24 entries
```

24 = 4 个处理器 + 1 条总线 + 1 个 IOAPIC + 16 条 I/O 中断 + 2 条本地中断。

**两份表的一致性检查清单**，改动任何一份时都要对照：

| 信息 | MP table | ACPI MADT | 必须等于 |
|---|---|---|---|
| CPU 个数 | processor 条目数 | 类型 0 条目数 | `cfg.nr_vcpus` |
| 每颗 CPU 的 APIC ID | `apicid` | `apic_id` | `vcpu_id` |
| BSP | `cpuflag` 的 BP 位 | （MADT 不标 BSP，Linux 用当前 CPU） | vCPU 0 |
| LAPIC 地址 | 表头 `lapic` | 表头 `lapic_addr` | `0xFEE00000` |
| IOAPIC ID | ioapic `apicid` | 类型 1 `ioapic_id` | `nr_cpus` |
| IOAPIC 地址 | ioapic `apicaddr` | 类型 1 `address` | `0xFEC00000` |
| ISA IRQ → GSI | 16 条恒等 intsrc | 无覆盖条目（默认恒等） | KVM 默认路由 |
| LINT1 | lintsrc NMI | 类型 4 | NMI |

mini-vmm 用同一个 `nr_cpus` 参数、同一组宏（`MP_LAPIC_BASE`、`MP_IOAPIC_BASE`）生成两份表，从代码结构上保证一致。

### 2.6 页表与 GDT

启动协议要求进入 `startup_64` 时已经在长模式、分页已开启，而且页表恒等映射覆盖了内核、boot_params、命令行和 initrd。《一次 out 指令的完整旅程》已经详细讲过怎么构建长模式页表和 GDT，这里只列出 Linux 启动的具体参数。

**页表**：PML4 在 `0x2000`，PDPT 在 `0x3000`，PD 在 `0x4000`。PD 的 512 项每项映射 2MB 大页（PS 位置 1），一共恒等映射 1GB，覆盖了所有需要被映射的东西（内核在 16MB 附近，initrd 不超过 `initrd_addr_max` 即约 896MB，其他结构都在 1MB 以下）。三张表只占 12KB。

```c
        for (i = 0; i < nr_2m; i++)
            pd[i] = ((i << 21) & PTE_ADDR_MASK)
                    | PTE_P | PTE_RW | PTE_PS;
```

内核进入 `startup_64` 之后很快就会建立自己的页表（`early_top_pgt`），把内核映射到 `0xffffffff80000000` 开始的高端虚拟地址，这张恒等映射表只在最开始的几十条指令里有用。

**GDT**：Linux 64 位启动协议要求代码段选择子是 `0x10`（`__BOOT_CS`）、数据段选择子是 `0x18`（`__BOOT_DS`），这与《一次 out 指令的完整旅程》裸机模式用的 `0x08`/`0x10` 不同。所以 Linux 模式单独写了一张四项的 GDT：

```c
    uint64_t gdt[4] = {
        GDT_DESC_NULL,        /* 0x00 */
        GDT_DESC_NULL,        /* 0x08 占位 */
        GDT_DESC_CODE64,      /* 0x10 = __BOOT_CS */
        GDT_DESC_DATA64,      /* 0x18 = __BOOT_DS */
    };
```

两个描述符的值拆开来看：

```
   GDT_DESC_CODE64 = 0x00AF9B000000FFFF
     type=0xB（执行/可读/已访问） S=1 DPL=0 P=1  L=1（64 位代码） D=0  G=1
   GDT_DESC_DATA64 = 0x00CF93000000FFFF
     type=0x3（读写/已访问）      S=1 DPL=0 P=1  L=0              D=1  G=1
```

64 位模式下段的基址和界限基本被硬件忽略，但 `L`、`D`、`P`、`S`、`DPL`、`type` 这几位仍然有效，必须自洽：代码段 `L=1` 时 `D` 必须为 0（`L=1, D=1` 是保留组合，加载时会 `#GP`）。

**sregs 里的段寄存器必须与内存里的 GDT 一致。** 通过 `KVM_SET_SREGS` 设置段寄存器时，我们直接给出了段寄存器的“隐藏部分”（基址、界限、属性），硬件不会去查 GDT。但 guest 一旦重新加载任何段寄存器（Linux 在 `startup_64` 里很快就会做），硬件就会真的去读 GDT。如果两边不一致，guest 会在重载段寄存器的那一刻崩溃，而那个位置离真正的错误原因很远，非常难查。mini-vmm 的做法是只写一份描述符常量，sregs 里的值用 `seg_from_desc()` 从描述符反解出来。这个函数里有一个 KVM 特有的坑：

```c
    /* kvm_segment.limit 存的是已按 G 位缩放后的有效界限，
     * 不是描述符里那个 20 位原始字段。 */
    s->limit = s->g ? ((limit_raw << 12) | 0xFFF) : limit_raw;
```

`struct kvm_segment` 的 `limit` 字段是字节粒度的有效界限。G=1 时描述符里的 `0xFFFFF` 对应的是 `0xFFFFFFFF`，直接把 `0xFFFFF` 填进去，KVM 会认为这是一个只有 1MB 的段。

### 2.7 阶段 7：BSP 的初始寄存器

最后一步，把 0 号 vCPU 摆成启动协议要求的状态。按“先 `KVM_GET_SREGS` 读出 KVM 给的合法初值，只改需要改的字段，再写回”的模式（《一次 out 指令的完整旅程》讲过为什么不能从零构造）：

| 寄存器 | 值 | 为什么 |
|---|---|---|
| `CR0` | `PE \| MP \| ET \| NE \| WP \| AM \| PG` | 保护模式 + 分页。`NE` 让 x87 错误走异常，`WP` 让内核遵守只读页 |
| `CR3` | `0x2000` | PML4 的物理地址 |
| `CR4` | `PAE` | 长模式要求 PAE |
| `EFER` | `LME \| LMA` | 长模式使能且已激活 |
| `CS` | 选择子 `0x10`，从 `GDT_DESC_CODE64` 反解 | 启动协议规定 |
| `DS`/`ES`/`FS`/`GS`/`SS` | 选择子 `0x18`，从 `GDT_DESC_DATA64` 反解 | 启动协议规定 |
| `GDTR` | base = `0x1000`，limit = 31 | 指向内存里那张四项 GDT |
| `IDTR` | base = 0，limit = 0 | 不提供 IDT。启动协议要求中断关闭，内核很快会装自己的 IDT；在那之前如果发生异常，会变成 triple fault，以 `KVM_EXIT_SHUTDOWN` 暴露出来 |
| `RIP` | `0x1000000` | vmlinux 的物理入口 `phys_startup_64` |
| `RSI` | `0x7000` | `boot_params` 的物理地址 |
| `RFLAGS` | `0x2` | bit 1 是保留位恒为 1；**`IF = 0`**，启动协议要求关中断 |
| `RSP` | `0x200000` | 内核会立刻设置自己的栈，这个值不重要，但要落在已映射的 RAM 里 |

有一处容易想当然的地方：`EFER.LMA` 在真实硬件上是由 CPU 在开启分页时自动置位的，软件不能直接写。但通过 `KVM_SET_SREGS` 设置时，我们是在 vCPU 停止时直接给出它的架构状态，不经过硬件的状态转换，所以 `LMA` 要一起给上。KVM 的 `kvm_is_valid_sregs()` 会检查这组值是否自洽：`EFER.LME` 和 `CR0.PG` 同时为 1 时，必须同时有 `CR4.PAE`、`EFER.LMA` 和 `CR0.PE`，缺一个 `KVM_SET_SREGS` 就返回 `EINVAL`。

`EFER.NXE` 没有置位：Linux 启动后会自己检查 CPUID 并打开它（日志里的 `NX (Execute Disable) protection: active`）。

**AP 不需要设置任何寄存器。** 1 到 N-1 号 vCPU 创建后保持 KVM 给的复位状态，它们的 `CS:IP` 会在收到 SIPI 时由 KVM 设置（《多核·原理篇》1.4 节的 `kvm_vcpu_deliver_sipi_vector()`），之后由 guest 的 trampoline 带它们进入长模式。如果 VMM 画蛇添足地给 AP 也设置了长模式寄存器，INIT 会把它们复位掉，白做；如果在没有 irqchip 的情况下这样做，AP 会直接从内核入口开跑，结果不可预测。

### 2.8 小结：阶段 6 和阶段 7 的准备清单

- **内核**：vmlinux 按 `p_paddr` 摆放，bss 清零，入口换算成物理地址，镜像不低于 1MB，记下末尾地址。
- **boot_params**：先清零；魔数 `0xAA55`/`"HdrS"`、版本、`type_of_loader = 0xFF`、`LOADED_HIGH`；命令行指针和长度；initrd 地址和长度（含高 32 位）；`acpi_rsdp_addr`；E820 表。
- **E820**：低 640KB RAM、640KB–1MB 保留（固件表在里面）、1MB 以上 RAM。
- **命令行**：`console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1`。
- **initrd**：RAM 顶端向下 2MB 对齐，不低于内核末尾，不高于 `initrd_addr_max`；busybox 必须静态链接。
- **ACPI**：RSDP（revision 2，两个校验和，先 20 字节后 36 字节）→ XSDT（只列 FADT 和 MADT）→ FADT（PM1a 端口与设备一致，`SMI_CMD=0`，不设 HW_REDUCED）→ DSDT（`_S5_` 的 SLP_TYP 与设备一致）；MADT（每 vCPU 一条 LAPIC，IOAPIC ID = N，无覆盖，LINT1 NMI）。所有结构 `packed` 并断言大小，校验和最后算。
- **MP table**：`0x9FC00`，浮动指针和配置表各一个校验和，`feature1 = 0`，与 MADT 描述同一台机器。
- **页表**：1GB 恒等映射，2MB 大页，三张表 12KB。
- **GDT**：`0x10` 代码段、`0x18` 数据段，sregs 从同一份描述符反解，`limit` 按 G 位缩放。
- **BSP 寄存器**：长模式四件套（CR0/CR3/CR4/EFER 含 LMA）、段寄存器、GDTR、IDTR 为空、`RIP` = 入口、`RSI` = boot_params、`RFLAGS = 0x2`。
- **AP 寄存器**：不设置，交给 INIT/SIPI。

## 三、检查清单：固件表、启动协议与寄存器

### 3.1 固件表与启动协议

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| vmlinux 摆放 | 按 `p_paddr`，bss 清零 | 物理地址 | 越界或内核数据错乱 |
| 入口 | 物理地址（`e_entry` 或换算） | 分页只有恒等映射 | 立即 triple fault |
| boot_params | 先整体清零 | 很多字段非零即启用某功能 | 走进奇怪的平台初始化 |
| `hdr.boot_flag` / `hdr.header` | `0xAA55` / `"HdrS"` | 协议约定 | — |
| `hdr.type_of_loader` | `0xFF` | 未注册 bootloader | — |
| `hdr.loadflags` | `LOADED_HIGH` | 内核在 1MB 以上 | — |
| `cmd_line_ptr` | 命令行物理地址，`\0` 结尾 | 内核拷走命令行 | 命令行为空，没有串口输出 |
| `ramdisk_image` / `ramdisk_size` | initrd 位置与大小（含 `ext_` 高 32 位） | 找到 initramfs | `VFS: Unable to mount root fs` |
| `acpi_rsdp_addr` | RSDP 物理地址 | 不必扫描 | 仍可扫描到，但多一重保险 |
| E820 低端 | `[0, 0x9FC00)` 为 RAM | AP trampoline 需要低端 RAM | panic 或 AP 起不来 |
| E820 保留区 | `[0x9FC00, 0x100000)` | 固件表在里面 | 固件表被内核覆盖 |
| `[3GB, 4GB)` | 没有 memslot，也没有 E820 条目（《内存基础》1.2 节） | 32 位 MMIO 空洞，Linux 从这里给 PCI 分配地址 | 有 memslot：IOAPIC/LAPIC 被 RAM 遮住；标成保留：PCI 找不到地址 |
| 命令行 | `console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1` | 输出、早期输出、重启与 panic 退出 | 没输出；VMM 不退出 |
| initrd 位置 | 低段 RAM 顶端向下 2MB 对齐，≥ 内核末尾，≤ `initrd_addr_max` | 避开内核和早期分配 | initrd 被踩坏 |
| initramfs 里的 busybox | 静态链接 | 没有动态链接器 | `/init` 执行失败 |
| ACPI 结构体 | `packed`，编译期断言大小 | 非对齐字段 | 所有偏移错位 |
| ACPI 校验和 | 最后计算；RSDP 先 20 字节再 36 字节 | 覆盖关系 | 表被拒绝 |
| RSDP 位置 | `[0xE0000, 0xFFFFF]` 内 16 字节对齐 | 扫描区 | 找不到 ACPI |
| RSDP revision | 2，使用 XSDT | 64 位地址 | — |
| XSDT 内容 | FADT、MADT；不列 DSDT | DSDT 由 FADT 引用 | — |
| FADT 签名 | `"FACP"` | 规范 | 找不到 FADT |
| FADT Flags bit 20 | 0（不是 HW-reduced） | 否则 Linux 放弃 PIT 和 8259A | TSC、LAPIC 定时器无法校准 |
| FADT PM1a | 端口与 PM1a 设备一致 | 关机写这里 | `poweroff` 无效 |
| FADT `SMI_CMD` | 0 | 已在 ACPI 模式 | — |
| FADT `CENTURY` | 与 RTC 世纪寄存器一致（`0x32`） | 读年份 | 年份错误 |
| DSDT | `_S5_` 包，SLP_TYP 与 PM1a 设备一致 | 关机 | `ACPI: PM: (supports S0)`，无 S5 |
| MADT LAPIC 地址 | `0xFEE00000` | KVM LAPIC | — |
| MADT flags | `PCAT_COMPAT` | 确实有 8259A | — |
| MADT LAPIC 条目 | 每 vCPU 一条，`apic_id` = vCPU ID，flags bit0 = 1 | 三方一致 | AP 停在 `hlt`，`failed to report alive state`；CPU 数变少 |
| MADT IOAPIC 条目 | ID = N，地址 `0xFEC00000`，GSI 基址 0 | 与 KVM 和 MP table 一致 | 中断不通 |
| MADT 中断源覆盖 | 不写 | KVM 默认路由恒等 | 时钟中断丢失，`check_timer()` 失败 |
| MP table 位置 | `0x9FC00`（或另两个扫描区），16 字节对齐 | 扫描区 | `acpi=off` 时退回单核 |
| MP 浮动指针 | `"_MP_"`，`feature1 = 0`，自身校验和 | 否则用默认配置 | 配置表被忽略 |
| MP 配置表 | `"PCMP"`，`oemcount`、`length` 填完再算校验和 | 规范 | 表被忽略 |
| MP 与 MADT | 描述同一台机器 | `acpi=off` 前后一致 | 两种启动方式行为不同 |
| guest 内核配置 | `CONFIG_ACPI` 或 `CONFIG_X86_MPPARSE` 至少一个可用 | 否则没有中断拓扑 | virtual wire，单核 |

### 3.2 页表、GDT 与寄存器

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| 恒等映射范围 | 覆盖内核、boot_params、命令行、initrd | 启动协议 | 内核访问这些数据时缺页 → triple fault |
| GDT 选择子 | 代码 `0x10`，数据 `0x18` | Linux 64 位启动协议 | 段重载时 `#GP` |
| 代码段描述符 | L=1、D=0 | L=1,D=1 是保留组合 | 加载时 `#GP` |
| sregs 段寄存器 | 从同一份描述符反解 | 与内存中 GDT 一致 | guest 重载段寄存器时崩溃 |
| `kvm_segment.limit` | G=1 时为 `(raw << 12) \| 0xFFF` | 字节粒度 | 段界限只有 1MB |
| sregs 读改写 | 先 `KVM_GET_SREGS` 再改 | 保留 KVM 给的合法初值 | `KVM_EXIT_FAIL_ENTRY` |
| CR0 | PE、PG 等 | 保护模式 + 分页 | — |
| CR4 | PAE | 长模式要求 | `KVM_SET_SREGS` 返回 `EINVAL` |
| EFER | LME **和** LMA | SET_SREGS 不经过硬件状态转换 | `KVM_SET_SREGS` 返回 `EINVAL` |
| IDTR | limit 0 可以 | 内核很快装自己的 IDT | 早期异常 → `KVM_EXIT_SHUTDOWN`（这是好事：失败立即可见） |
| RIP | 内核物理入口 | — | — |
| RSI | boot_params 物理地址 | 启动协议 | 内核读到全 0 的参数 |
| RFLAGS | `0x2`（IF=0） | bit 1 保留为 1；协议要求关中断 | `KVM_EXIT_FAIL_ENTRY` |
| AP 寄存器 | 不设置 | INIT/SIPI 由 KVM 处理 | 白做或行为不可预测 |
