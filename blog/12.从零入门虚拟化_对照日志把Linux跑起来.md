这一篇是中断、时间、设备、固件、多核这一组文章的收尾。前面各篇分别讲了一块机制，这里把它们放回一次完整的启动里对照着看，最后讲 guest 起不来时怎么查，以及怎样把这些行为固定成自动化测试。

## 一、把裸 OS 跑起来：对照真实日志逐段解读

前面讲的所有东西，最终都会体现在一次启动的日志里。这一章拿一次真实的启动，从 VMM 的第一行输出读到 guest 关机，每一段都对应回前面各篇的某个机制。读完这一章，日志里的每一行都应该能说出“它是谁打印的、说明了什么”。

启动命令：

```bash
./build/vmm --mode linux --smp 4 --mem 512M \
            --initrd build/initramfs.cpio.gz guest-kernel/vmlinux
```

内核是 `tools/build_guest_kernel.sh` 构建的测试内核（Linux 7.4-rc2），host 是一台 AMD Ryzen 7 5800H。这个内核开了 `CONFIG_KVM_GUEST`，知道自己跑在 KVM 上，所以时间来自 kvmclock，中断控制器也用上了几项半虚拟化优化。VMM 是当前版本，带着后面各篇才讲到的 PCI 主桥、电源按钮和整机复位，这些行在日志里只占几行，遇到时简单指一下出处。

guest 起来后依次执行了 `cat /proc/interrupts`、`head -30 /proc/cpuinfo`、查看时钟源，最后 `poweroff -f`。日志里 `[INFO]` 开头的是 VMM 自己的输出，`[    x.xxxxxx]` 开头的是 guest 内核通过串口打印的日志。

### 1.1 第一段：VMM 的准备工作（阶段 1–9）

```
[INFO] KVM API v12, kvm_run size 12288 bytes, max vCPUs 1024
[INFO] CPU vendor: AuthenticAMD (AMD)
[INFO] SVM rev=1, ASIDs=32768
[INFO] SVM features: npt nrip_save tsc_scale vmcb_clean flushbyasid decodeassists pausefilter v_vmsave_vmload
```

阶段 1。API 版本 12，`kvm_run` 三页，KVM 最多允许 1024 个 vCPU。厂商是 AMD，走 SVM 后端。SVM 特性里 `npt` 保证了二维页表，`tsc_scale` 是《时间》第四章说的 TSC ratio，`pausefilter` 是《多核·原理篇》第一章说的 PAUSE 拦截。这台 host 的特性里没有 `avic`，也就是没有《中断·原理篇》第四章说的硬件 APIC 虚拟化，中断全部走软件注入。

```
[INFO] memslot 0: GPA [0x0, 0x20000000) -> HVA 0x7ec35fc00000 (512 MiB)
[INFO] in-kernel irqchip: PIC + IOAPIC + LAPIC, PIT on GSI 0 (reinject on)
[INFO] serial8250 @ PIO 0x3f8, IRQ 4
[INFO] pci 00:00.0 host-bridge [1234:0001] class 060000, no INTx
```

阶段 2 注册了一个覆盖 512MB 的 memslot；阶段 3 创建了内核态中断控制器和 PIT（在创建 vCPU 之前），PIT 丢失的 tick 会补发；阶段 5 注册了串口，挂在 GSI 4。最后一行是《PCI·实现篇》加入的 PCI 主桥，它在 00:00.0，不用中断。

```
[INFO] vmlinux PT_LOAD #0: GPA [0x1000000, 0x2dece30) file 0x1dece30 mem 0x1dece30
[INFO] vmlinux PT_LOAD #1: GPA [0x2e00000, 0x3981000) file 0xab9000 mem 0xb81000
[INFO] vmlinux loaded: GPA [0x1000000, 0x3981000), entry 0x35e14e0
[INFO] kernel format: vmlinux (ELF)
```

阶段 6 的第一步，《固件与启动协议·实现篇》2.1 节。vmlinux 有 2 个 `PT_LOAD` 段，从 16MB 开始，一共约 41MB。第一段 `file` 与 `mem` 相等；第二段 `mem` 比 `file` 大了 `0xc8000`（800KB），那是 bss，VMM 负责清零。入口 `0x35e14e0` 不在第一个段的开头，而在第二个段里：`startup_64` 放在 `.init.text` 节，启动完成后这段内存会被内核释放。VMM 只认 ELF 头里的 `e_entry`，不假设入口在哪里。

```
[INFO] MP table @ GPA 0x9fc00: 4 CPU(s), IOAPIC id 4 @ 0xfec00000, 25 entries
[INFO] ACPI @ GPA 0xe0000: RSDP XSDT@0xe0030 FADT@0xe0070 DSDT@0xe0190 MADT@0xe0880 FACS@0xe0900
```

《固件与启动协议·实现篇》2.4 和 2.5 节。MP table 在 `0x9FC00`，4 颗 CPU，IOAPIC ID 为 4，共 25 个条目：4 个 CPU、PCI 和 ISA 两条总线、1 个 IOAPIC、16 个 ISA 中断、2 个本地中断。ACPI 表从 `0xE0000` 开始，顺序和链接关系与《固件与启动协议·实现篇》2.4 节的布局图一致；DSDT 后来装进了 PCI 主桥的描述（地址窗口和中断路由表），长到 1769 字节，MADT 因此顺延到 `0xE0880`；最后的 FACS 是《ACPI 事件·实现篇》加的。

```
[INFO] cmdline @ GPA 0x20000: "console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1"
[INFO]   e820: [0x000000000000, 0x00000009fc00) RAM
[INFO]   e820: [0x00000009fc00, 0x000000100000) reserved
[INFO]   e820: [0x000000100000, 0x000020000000) RAM
[INFO] loaded build/initramfs.cpio.gz: 2272049 bytes -> GPA 0x1fc00000
[INFO] initrd @ GPA 0x1fc00000, 2272049 bytes
```

《固件与启动协议·实现篇》2.2 和 2.3 节。命令行、E820 三项、initrd 放在 RAM 顶端减去文件大小、再向下 2MB 对齐的位置：`0x20000000 − 2272049 = 0x1FDD54CF`，向下对齐到 `0x1FC00000`。

```
[INFO] page tables @ PML4=0x2000 PDPT=0x3000 PD=0x4000: identity map 1024 MiB via 512 2MiB pages
[INFO] vCPU 0: 64-bit long mode, CR3=0x2000 RIP=0x35e14e0
[INFO] vCPU 0: Linux boot protocol, CS=0x10 DS=0x18 RSI=0x7000
[INFO] reset: saved power-on state of 4 vCPU(s), 106 MSRs each, XSAVE 4096 bytes
[INFO] --- entering guest ---
[INFO] 4 vCPU thread(s) running
```

《固件与启动协议·实现篇》2.6 和 2.7 节。1GB 恒等映射；BSP 摆成长模式，`RIP` 是上面的入口，`CS=0x10`、`DS=0x18`、`RSI` 指向 boot_params。`reset:` 那一行是《整机复位》加的：进入 guest 之前把每个 vCPU 的上电状态存一份，guest 重启时用它恢复。阶段 9 启动了 4 个 vCPU 线程。从这一行开始，guest 接管。

### 1.2 第二段：内核认识这台机器

```
[    0.000000] Linux version 7.4.0-rc2-g7e1392a42ea2 (...) #1 SMP PREEMPT_DYNAMIC ...
[    0.000000] Command line: console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1
```

内核的第一行输出。能看到这一行，说明：长模式寄存器、页表、GDT 全都对了（否则早就 triple fault）；`RSI` 指向的 boot_params 被正确读取，命令行从 `cmd_line_ptr` 拷贝成功；串口的最基本输出通路（THR 写入 → VMM `write()`）是通的。此时串口驱动还没加载，这是 `earlyprintk` 用轮询方式在写。

```
[    0.000000] [Firmware Bug]: TSC doesn't count with P0 frequency!
```

AMD/海光平台的检查：内核要求 `HWCR` MSR（`0xC0010015`）的第 24 位为 1，表示 TSC 按 P0 频率计数。KVM 模拟的 `HWCR` 初值是 0，mini-vmm 创建 vCPU 时会把这一位置 1，所以一般看不到这一行；只有 host 上的 KVM 较老、不接受用户态写这一位时才会出现，这时 VMM 自己也会打印一条 `HWCR.TscFreqSel` 告警。无害。

```
[    0.000000] BIOS-provided physical RAM map:
[    0.000000] BIOS-e820: [mem 0x0000000000000000-0x000000000009fbff]  System RAM
[    0.000000] BIOS-e820: [mem 0x000000000009fc00-0x00000000000fffff]  device reserved
[    0.000000] BIOS-e820: [mem 0x0000000000100000-0x000000001fffffff]  System RAM
[    0.000000] printk: legacy bootconsole [earlyser0] enabled
```

内核原样打印了 VMM 在 boot_params 里给的 E820 表（type 1 打印成 `System RAM`，type 2 打印成 `device reserved`）。它说“BIOS-provided”，但这里的“BIOS”就是 VMM。

```
[    0.000000] Hypervisor detected: KVM
[    0.000000] kvm-clock: Using msrs 4b564d01 and 4b564d00
[    0.001287] clocksource: kvm-clock: mask: 0xffffffffffffffff max_cycles: 0x1cd42e4dffb, max_idle_ns: 881590591483 ns
[    0.005251] tsc: Detected 3193.914 MHz processor
```

《时间》第五章的核心。guest 从 CPUID 的 hypervisor 位和 `0x40000000` 叶认出了 KVM，往 kvmclock 的两个 MSR 里登记了每颗 CPU 的时间结构。TSC 频率 3193.914 MHz 是 KVM 在 kvmclock 结构里直接告诉 guest 的，没有经过 PIT 测量；没开 `CONFIG_KVM_GUEST` 的内核在这里会打印 `tsc: Fast TSC calibration using PIT`，走《时间》第二章的 PIT 校准。

```
[    0.010663] found SMP MP-table at [mem 0x0009fc00-0x0009fc0f]
```

`mpparse_find_mptable()` 在 639K–640K 扫描到了 MP 浮动指针（16 字节）。guest 内核开了 `CONFIG_X86_MPPARSE` 才会有这一行。

```
[    0.013614] RAMDISK: [mem 0x1fc00000-0x1fe2afff]
```

内核从 boot_params 读到了 initrd 的位置和大小，把这段内存（按页取整）保留下来。

```
[    0.016757] ACPI: RSDP 0x00000000000E0000 000024 (v02 MINVMM)
[    0.018681] ACPI: XSDT 0x00000000000E0030 000034 (v01 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.021150] ACPI: FACP 0x00000000000E0070 000114 (v06 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.023797] ACPI: DSDT 0x00000000000E0190 0006E9 (v02 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.026388] ACPI: FACS 0x00000000000E0900 000040
[    0.027884] ACPI: FACS 0x00000000000E0900 000040
[    0.029328] ACPI: APIC 0x00000000000E0880 00005E (v05 MINVMM MINIVMM  00000001 MVMM 00000001)
```

ACPI 表树被完整找到：RSDP 版本 2，长度 `0x24`（36）；XSDT 长 `0x34`（52 = 36 字节表头 + 2 个 8 字节地址）；FADT 长 `0x114`（276）；DSDT 长 `0x6E9`（1769）；MADT 长 `0x5E`（94 = 36 + 8 字节固定字段 + 4×8 字节 LAPIC + 12 字节 IOAPIC + 6 字节 LAPIC NMI）。FACS 打印两次，因为 FADT 里 32 位的 `FIRMWARE_CTRL` 和 64 位的 `X_FIRMWARE_CTRL` 都填了同一个地址，ACPICA 两个都登记。每一个数字都能与《固件与启动协议·实现篇》第二章的结构体大小对上。

```
[    0.048028] ACPI: LAPIC_NMI (acpi_id[0xff] dfl dfl lint[0x1])
[    0.050694] IOAPIC[0]: apic_id 4, version 17, address 0xfec00000, GSI 0-23
[    0.053456] ACPI: Using ACPI (MADT) for SMP configuration information
[    0.056229] CPU topo: Max. logical packages:   1
...
[    0.068174] CPU topo: Num. cores per package:     4
[    0.069461] CPU topo: Num. threads per package:   4
[    0.070792] CPU topo: Allowing 4 present CPUs plus 0 hotplug CPUs
```

MADT 被解析：LAPIC NMI 条目（所有 CPU 的 LINT1）；IOAPIC 的 ID 4、地址、版本 17（`0x11`，从 KVM 模拟的版本寄存器读出）、24 根引脚。然后是《固件与启动协议·原理篇》1.5 节讲的优先级：**ACPI MADT 可用，就用它，MP table 虽然找到了但不采用**。`CPU topo:` 几行是《多核·实现篇》改写 CPUID 拓扑的结果：4 颗 CPU 是同一个 package 里的 4 个核，每核 1 个线程，没有可热插拔的 CPU。

如果用 `--append acpi=off` 启动，这几行会变成 MP table 的解析结果，CPU 数和 IOAPIC 信息相同，但不会有 ACPI 表相关的行；关机时内核找不到 S5，打印 `reboot: Power off not available: System halted instead` 后停在那里。

```
[    0.072629] kvm-guest: APIC: eoi() replaced with kvm_guest_apic_eoi_write()
[    0.074892] kvm-guest: KVM setup pv remote TLB flush
[    0.076428] kvm-guest: setup PV sched yield
[    0.082405] [gap 0x20000000-0xffffffff] available for PCI devices
```

前三行是 KVM guest 的半虚拟化优化：PV EOI 让 guest 在多数情况下不必为 EOI 写 LAPIC 寄存器、因而少一次 exit；TLB flush 和 sched yield 改用 hypercall。最后一行是内核在 E820 里找到的最大空洞，留给 PCI 设备的 BAR，它的作用要到《PCI·原理篇》才会用上。

### 1.3 第三段：中断与时钟就位

```
[    0.211754] APIC: Switch to symmetric I/O mode setup
[    0.216022] x2apic enabled
[    0.218946] APIC: Switched APIC routing to: physical x2apic
[    0.221575] kvm-guest: APIC: send_IPI_mask() replaced with kvm_send_ipi_mask()
[    0.224467] kvm-guest: APIC: send_IPI_mask_allbutself() replaced with kvm_send_ipi_mask_allbutself()
[    0.227609] kvm-guest: setup PV IPIs
[    0.232108] ..TIMER: vector=0x30 apic1=0 pin1=0 apic2=-1 pin2=-1
```

《中断·原理篇》第三章的“两代共存”：Linux 从 virtual wire 模式切换到 symmetric I/O 模式，此后设备中断走 IOAPIC。

接下来两行说明 LAPIC 进了 x2APIC 模式。《中断·原理篇》3.6 节讲过，x2APIC 在裸机上要求中断重映射，这台机器没有 IOMMU，也就没有重映射；`try_to_enable_x2apic()` 在这种情况下还会问一句 hypervisor，KVM 回答可以，内核就开 x2APIC，但把 APIC ID 上限压在 255 以内，并固定用 physical 目的模式，因为没有重映射时 IOAPIC 和 MSI 只能按 8 位 physical ID 寻址。没开 `CONFIG_KVM_GUEST` 的内核在这里打印 `x2apic: IRQ remapping doesn't support X2APIC mode`，留在 xAPIC。

PV IPI 那几行把 IPI 换成了 hypercall：一次 `KVM_HC_SEND_IPI` 可以带一个目标位图，发给多颗 CPU 的 IPI 只需要一次 exit。

最后一行是 `check_timer()` 的结论：时钟中断用向量 `0x30`（`ISA_IRQ_VECTOR(0)`），走第 0 个 IOAPIC 的第 0 根引脚——恒等映射生效（《中断·实现篇》2.4 节）。这一行之后没有出现 “timer doesn't work”，说明时钟中断确实送到了。

```
[    0.234172] clocksource: tsc-early: mask: 0xffffffffffffffff max_cycles: 0x2e09d51e55b, max_idle_ns: 440795321046 ns
[    0.238588] Calibrating delay loop (skipped) preset value.. 6387.82 BogoMIPS (lpj=3193914)
```

基于 TSC 的早期时钟源可用；`udelay()` 用的 `loops_per_jiffy` 也不用测，kvmclock 按 TSC 频率直接给出预设值（`lpj = 3193914`，即每个 jiffy 的 TSC 周期数，HZ=1000）。

### 1.4 第四段：唤醒 AP

```
[    0.555688] smpboot: CPU0: AMD 19/50 (family: 0x19, model: 0x50, stepping: 0x0)
...
[    0.577889] smp: Bringing up secondary CPUs ...
[    0.578665] smpboot: x86: Booting SMP configuration:
[    0.579561] .... node  #0, CPUs:      #1 #2 #3
[    0.588896] smp: Brought up 1 node, 4 CPUs
[    0.590539] smpboot: Total of 4 processors activated (25551.31 BogoMIPS)
```

《多核·原理篇》第一章和《多核·实现篇》第一章在这里汇合。BSP 的 CPUID 显示是 AMD family `0x19` model `0x50`（Zen 3），这是透传的 host 特性。从 `Bringing up secondary CPUs` 到 `Brought up 1 node, 4 CPUs` 用了约 11 毫秒，在这期间：

1. BSP 往每个 AP 的 LAPIC 发 INIT 和 SIPI（x2APIC 下是写 ICR 对应的 MSR → `#VMEXIT` → KVM 模拟 ICR）；
2. KVM 唤醒睡在 `KVM_RUN` 里的 AP 线程，AP 的 `KVM_RUN` 返回 `-EAGAIN`，VMM 的 run loop 把它当成“重进”；
3. KVM 把 AP 的 `CS:IP` 设为 SIPI 向量指定的 trampoline 地址，AP 进入 guest，从实模式爬到长模式；
4. 每个 AP 读自己 LAPIC 的 ID（等于 vCPU ID），在 MADT 建出的 APIC ID 表里查到自己的编号，然后上线。

`Total of 4 processors activated` 的 25551.31 正好是 4 × 6387.82，每颗 AP 都用了 kvmclock 给的同一个预设 `lpj`。日志里没有出现 `APIC ID mismatch`、`failed to report alive state`、`TSC synchronization` 这类警告，mini-vmm 的测试脚本专门断言了这一点。

### 1.5 第五段：ACPI 解释器与设备驱动

```
[    0.621876] ACPI: 1 ACPI AML tables successfully acquired and loaded
[    0.622616] ACPI: Interpreter enabled
[    0.622749] ACPI: PM: (supports S0 S5)
[    0.622751] ACPI: Using IOAPIC for interrupt routing
```

ACPICA 解释器加载了 DSDT 里的 AML，在命名空间里找到了 `_S5_`，所以支持 S5（软关机）。

```
[    0.613577] PCI: Using configuration type 1 for base access
...
[    0.622962] ACPI: PCI Root Bridge [PCI0] (domain 0000 [bus 00-ff])
[    0.623588] pci 0000:00:00.0: [1234:0001] type 00 class 0x060000 conventional PCI endpoint
```

这几行属于后面的 PCI 两篇：内核通过 `0xCF8`/`0xCFC` 访问配置空间，从 DSDT 的 `PCI0` 对象得到根总线，枚举出 00:00.0 的主桥。这一组文章所讲的机器还没有这些，那时内核找不到配置空间访问方法，打印 `PCI: Fatal: No config space access function found` 并放弃 PCI，对只用传统设备的 guest 没有影响。

```
[    0.629042] clocksource: Switched to clocksource kvm-clock
...
[    0.650111] clocksource: tsc: mask: 0xffffffffffffffff max_cycles: 0x2e09d51e55b, max_idle_ns: 440795321046 ns
[    0.659950] clocksource: Switched to clocksource tsc
```

《时间》5.3 节讲过这两次切换：先切到 kvmclock，正式的 `tsc` 时钟源注册后（rating 更高）再切到 TSC。TSC 频率是 KVM 告诉的，内核不再花一秒去精修它。

```
[    0.694139] input: Power Button as /devices/platform/LNXPWRBN:00/input/input0
[    0.694226] ACPI: button: Power Button [PWRF]
```

《ACPI 事件》两篇加的电源按钮：FADT 声明了固定功能的电源按钮，内核为它建了一个输入设备。

```
[    0.695222] Serial: 8250/16550 driver, 4 ports, IRQ sharing enabled
[    0.953187] serial8250: ttyS0 I/O:0x3f8 (irq = 4, base_baud = 115200) is a 16550A
```

《传统设备·原理篇》第一章和《传统设备·实现篇》第一章的串口：`autoconfig()` 的 IER 测试、回环测试、FIFO 测试全部通过，端口被识别为 16550A。之后控制台从 earlyprintk 切换到正式的 8250 驱动，输出改为中断驱动。

两行之间隔了约 0.26 秒，这段时间花在中断号自动探测上。测试内核开了 `CONFIG_SERIAL_8250_DETECT_IRQ`，四个传统串口带着 `UPF_AUTO_IRQ` 标志，识别成功的 ttyS0 会再跑一遍 `autoconfig_irq()`：先 `probe_irq_on()` 打开所有空闲的 ISA 中断，然后把 MCR 的 OUT2 置位、IER 写成全开、往 THR 写一个字节，让串口产生一次 THRE 中断，最后 `probe_irq_off()` 看哪根线响了。`probe_irq_on()` 里有 `msleep(20)` 和 `msleep(100)` 两次睡眠，等不相干的中断平息，函数里调用了两次，合起来约 0.24 秒，真硬件上一样要等。VMM 的 `--trace-pio` 能看到这段时间里只有零星几次串口访问，中间是 127 毫秒的空白。探测结果是 `irq = 4`，这也顺带验证了 VMM 串口的中断接线：如果 THRE 中断没有送到 GSI 4，这里会是 `irq = 0`，驱动退回轮询。

```
[    0.961458] i8042: PNP: No PS/2 controller found.
[    0.961459] i8042: Probing ports directly.
[    0.962041] serio: i8042 KBD port at 0x60,0x64 irq 1
[    0.963957] input: AT Translated Set 2 keyboard as /devices/platform/i8042/serio0/input/input1
```

i8042：ACPI 的即插即用信息里没有描述 PS/2 控制器（我们的 DSDT 里没有这类设备对象），驱动改为直接探测端口。控制器命令逐条得到应答；只有 KBD 口，没有 AUX 口，说明 AUX 口被当场判定为不存在；键盘设备的命令应答通过 IRQ1 送达，atkbd 驱动注册成功。从 `Probing ports directly` 到键盘注册只用了 2.5 毫秒，没有任何超时。

RTC：UIP 为 0，时间以 BCD 格式返回，读出的正是 host 当时的 UTC 时间，被用来设置 guest 的系统时间。`y3k` 表示驱动找到了世纪寄存器，这来自 FADT 的 `CENTURY` 字段。中间的 `ACPI Error` 来自 RTC 驱动想打开 ACPI 的 RTC 唤醒事件，而 VMM 的 PM1 寄存器没有实现这一位（规范里它是可选的），ACPICA 写进去读回来还是 0；RTC 本身不受影响，《ACPI 事件·实现篇》讲了取舍。

```
            CPU0       CPU1       CPU2       CPU3
   0:        332          0          0          0  IO-APIC     0-edge      timer
   1:          0          0         13          0  IO-APIC     1-edge      i8042
   4:         34          0          0          0  IO-APIC     4-edge      ttyS0
   8:          0          0          0          0  IO-APIC     8-edge      rtc0
   9:          0          0          0          0  IO-APIC     9-fasteoi   acpi

 LOC:        309        206        295        195  Local timer interrupts
 PMI:          0          0          0          0  Performance monitoring interrupts
 IWI:          3          0          0          3  IRQ work interrupts
 RES:          2         20          9         19  Rescheduling interrupts
 CAL:        201        158        215        258  Function call interrupts
 TLB:          0          2          0          0  TLB shootdowns
 ...
 MCP:          1          1          1          1  Machine check polls
 HYP:          1          1          1          1  Hypervisor callback interrupts
```

这张表是前面各篇所有中断机制的“体检报告”：

| 行 | 来源 | 说明了什么 |
|---|---|---|
| `0: timer` | KVM 模拟的 PIT，GSI 0 | IOAPIC 引脚 0，边沿触发，恒等映射；只在 CPU0 上有计数，LAPIC 定时器接管后 PIT 不再使用 |
| `1: i8042` | VMM 的 i8042，`KVM_IRQ_LINE` GSI 1 | 键盘初始化时每条命令应答一次中断，共 13 次，被 IOAPIC 路由到了 CPU2 |
| `4: ttyS0` | VMM 的串口，`KVM_IRQ_LINE` GSI 4 | 34 次，包括 THRE 和接收中断；边沿触发的上升沿逻辑是对的，否则键盘输入进不来 |
| `8: rtc0` | 驱动注册了 IRQ8 | 计数为 0，VMM 没有实现 RTC 中断 |
| `9: acpi` | SCI | `fasteoi` 即电平触发；没按电源按钮就不会响 |
| `LOC` | KVM 模拟的 LAPIC 定时器 | 每颗 CPU 都有，说明 LAPIC 定时器在所有 vCPU 上工作；它的频率是以 TSC 为尺子校准的（《时间》第三章） |
| `RES`/`CAL`/`TLB` | guest 内的 IPI | 经 PV IPI hypercall 或 x2APIC 的 ICR MSR 投递，说明 vCPU 之间的 IPI 通路正常 |
| `HYP` | KVM 的半虚拟化通知向量 | 每颗 CPU 1 次，是 guest 打开异步缺页功能时 KVM 发来的一次“全部唤醒”通知 |

伪中断（`SPU`）和 APIC 错误（`ERR`）这里没有出现：新内核对这类计数为 0 的行不打印，也就说明中断控制器的模拟没有出过这两类异常。

### 1.8 最后一段：关机

```
[guest ~]# poweroff -f
[    1.186880] ACPI: PM: Preparing to enter system sleep state S5
[    1.188583] reboot: Power down
[INFO] guest requested poweroff via ACPI S5 (port 0x604, value 0x3401)
[INFO] --- left guest (ok) ---
```

guest 的 `poweroff` 让内核通过 ACPICA 查到 `\_S5_` 的 SLP_TYP（5），往 FADT 声明的 `PM1a_CNT_BLK`（端口 `0x604`）写入 `0x3401`：`5 << 10` 是 SLP_TYP，`0x2000` 是 SLP_EN，最低位是 ACPICA 读出来又原样写回的 SCI_EN。这次写入以 `KVM_EXIT_IO` 回到执行它的那个 vCPU 线程，PM1a 设备回调返回 `VMM_ERR_EXIT`，这个线程的 run loop 结束，调用 `vm_request_stop()`；其余三个 vCPU（大概率睡在 guest 的 HLT 里）被 `immediate_exit` 和 SIGUSR1 踢出 `KVM_RUN`；主线程 join 全部线程，打印 `left guest (ok)`，退出码 0。

从第一行 `[INFO]` 到最后一行，前面各篇的四大块——中断、时间、设备、多核——以及把它们描述给 guest 的固件表，全部参与了这次启动。

## 二、调试方法与测试

### 2.1 guest 起不来时先看什么

guest 起不来的故障，按“死在哪里”可以分成几类，每一类有不同的首选证据：

| 现象 | 最可能的原因 | 首先看什么 |
|---|---|---|
| `KVM_EXIT_FAIL_ENTRY` | 寄存器状态不合法（RFLAGS bit 1、段属性、CR0/CR4/EFER 不自洽） | VMM 打印的 vCPU 状态 dump |
| `KVM_EXIT_SHUTDOWN`，没有任何内核日志 | 入口地址不对、页表没覆盖入口、GDT 与 sregs 不一致 | vCPU dump 里的 `RIP`、`CR3`、段寄存器；用 VMM 的页表遍历工具查入口地址的翻译 |
| 有少量日志，然后 `KVM_EXIT_SHUTDOWN` | 早期异常（IDT 还没装）；boot_params 字段错误 | 最后一行日志；vCPU dump 里的 `RIP` 对照 `System.map` |
| 日志停在某行，VMM CPU 100% | guest 在忙等某个设备：PIT、RTC、i8042 | 打开 VMM 的调试日志，看未处理端口的访问 |
| 日志停在某行，VMM CPU 0% | guest 在 HLT 里等一个永远不来的中断 | Ctrl-A x 看各 vCPU 停在哪；检查中断路由和固件表 |
| 能启动，但只有 1 颗 CPU | 固件表不可用（MPPARSE 没开、ACPI 表错误）；CPUID 与固件表不一致 | `CPU topo: Allowing N present CPUs`、`APIC:` 开头的日志 |
| 能启动，但慢了好几秒 | 某个设备探测超时 | 日志时间戳的跳变；对应时刻的端口访问 |
| 能启动，键盘输入没反应 | 串口中断没有新的上升沿；console 线程没起来 | `/proc/interrupts` 里 ttyS0 的计数 |
| `poweroff` 后 VMM 不退出 | PM1a 端口与 FADT 不一致；`_S5_` 缺失；停机协议有漏洞 | `ACPI: PM: (supports ...)`；Ctrl-A x 看哪个 vCPU 还在 |

这张表的核心思想是前面各篇原理篇反复强调的：**guest 的很多故障是“安静”的**。它不报错，只是选择一条退化路径，或者停在某个等待循环里。这时候必须主动去收集证据，而不是盯着日志猜。

### 2.2 VMM 自带的观测手段

mini-vmm 在代码里预留了几个低成本但很有用的观测点：

**vCPU 状态 dump。** 任何异常退出（SHUTDOWN、FAIL_ENTRY、INTERNAL_ERROR、未知退出原因）都会打印该 vCPU 的通用寄存器、控制寄存器、EFER、段寄存器、GDTR/IDTR，以及 exit 统计。Ctrl-A x 退出时则打印**所有** vCPU 的状态，这是 guest 卡住时唯一能看到“每颗 CPU 停在哪条指令”的方法。拿到 `RIP` 之后，对照 vmlinux 的 `System.map` 或者用 `addr2line`，就能知道 guest 卡在哪个函数里（注意 `RIP` 是内核虚拟地址）。

**exit 统计。** 每个 vCPU 记录总 exit 数和 IO、MMIO、HLT 各类的次数。像 RTC 那个“多出 4 万次 exit”的问题，在这个数字上一眼就能看出来：一次启动的 IO exit 数量远超预期，再打开调试日志一看，全是端口 `0x71` 的读。

**未处理端口日志。** `-vv` 打开调试级别后，每一次访问未注册端口都会打印端口号、方向、宽度。PIT speaker 的问题（端口 `0x61`）、RTC 的问题（`0x70`/`0x71`）这类“某个设备没人模拟”的故障，都会在这里露面。

**页表遍历。** `--walk GVA` 在启动前按 VMM 构建的页表把一个地址的四级翻译过程打印出来，用来确认“入口地址到底有没有被映射到”。

### 2.3 host 侧的观测手段

**`top -H`。** vCPU 线程都有名字，`top -H -p $(pgrep -x vmm)` 能直接看到每个 vCPU 的 CPU 占用。100% 说明在 guest 里忙（或者在忙等），0% 说明在 KVM 里睡（HLT 或者等 SIPI）。多核问题首先看这里：某个 AP 线程一直是 0%，说明它从来没被唤醒。

**`perf kvm stat`。** 《一次 out 指令的完整旅程》介绍过，它按退出原因统计 exit 的分布和耗时，是找性能问题的第一手段。在 host 上执行 `perf kvm stat live`，然后在 guest 里做一些操作，就能看到哪类退出最多。

**KVM tracepoint。** `trace-cmd record -e kvm:kvm_exit -e kvm:kvm_entry -e kvm:kvm_inj_virq -e kvm:kvm_apic_ipi` 能抓到每一次退出、每一次中断注入、每一次 IPI。排查“中断到底有没有被注入”这类问题时，`kvm_inj_virq` 是决定性的证据：看到对应向量被注入，说明问题在 guest 侧；没看到，说明问题在路由或设备侧。

### 2.4 测试：自动化的三个坑

mini-vmm 的每个阶段都有自动化测试（`tests/e2e/kvm-basics.sh`、`linux-boot.sh`、`smp.sh`），思路是运行 VMM、抓取全部输出、断言其中包含或不包含某些字符串。相关的用例包括：4 核启动到 VFS panic 然后经 i8042 复位退出；4 核启动 initramfs、在 guest 里检查核数和拓扑、然后 poweroff。写这些测试时遇到了三个值得记录的坑，它们都与 VMM 本身无关，而与“怎么驱动一个交互式程序”有关。

**坑一：`timeout` 导致 VMM 被挂起。** 《传统设备·实现篇》1.7 节讲过：`timeout` 把子进程放进后台进程组，VMM 碰终端就会被 SIGTTOU/SIGTTIN 停住。在 ssh 这类没有终端的环境里跑测试，stdin 不是终端，碰不到这个问题；换到交互式终端里跑，测试就挂住了。修复有两层：VMM 自己检测前台进程组，不在前台时不碰终端；测试脚本把 VMM 的 stdin 接到 `/dev/null`。人工运行时则用 `timeout --foreground`。

**坑二：只在无终端环境里测试是不够的。** 上面这个坑的教训是，测试环境要尽量接近真实使用环境。在非交互环境里要复现“有终端”的情况，可以用 Python 的 `pty` 模块创建一个伪终端：

```bash
python3 -c 'import pty; pty.spawn(["/bin/sh","-c","./tests/e2e/smp.sh -a"])'
```

这里用 `/bin/sh` 而不是 `bash -c`，是因为 `bash` 会读用户的配置文件，可能被切换到别的 shell。用 `script` 命令配合管道的做法实测会挂住，不建议使用。

**坑三：给 guest 喂命令要等提示符，断言要防回显。** 测试需要在 guest 的 shell 里执行命令，做法是把命令通过管道写进 VMM 的 stdin，console 线程再把它们送进串口的 RX FIFO。有两个问题：

- 发早了会丢。guest 的串口驱动在 tty 打开时清空 RX FIFO，shell 起来之前送进去的字节全部丢失；VMM 这一侧的接收缓冲最多存 255 字节，guest 读走之前满了也会丢。所以 `tests/guest_shell.py` 每条命令都等 shell 打印出提示符 `[guest ...]# ` 之后才发，并拒绝超过 254 字节的命令。按固定延迟发送行不通：启动耗时随内核配置、vCPU 数和 host 负载变化，延迟猜短了，命令丢在 shell 起来之前，用例以超时失败，看起来和 VMM 卡死一模一样。
- guest 的 shell 会回显输入的命令。如果执行 `nproc` 然后断言输出里有 `4`，回显的命令行本身就可能让断言误判。正确的写法是让 guest **计算**出标记：执行 `echo NPROC-$(nproc)`，断言 `NPROC-4`。回显里只有 `$(nproc)`，只有真正执行后的输出里才有 `NPROC-4`。拓扑检查也是同样的写法，比如 `echo APIC-$(sed -n "s/^apicid.*: //p" /proc/cpuinfo | tr "\n" -)` 断言 `APIC-0-1-2-3-`。

### 2.5 负向断言

最后一个测试技巧：除了断言“应该出现什么”，还要断言“不应该出现什么”。4 核启动的用例里有一组负向断言：

```bash
expect_not "failed to report alive state"   # AP 没有上线
expect_not "do_boot_cpu failed"             # AP 唤醒失败
expect_not "APIC ID mismatch"               # CPUID 与固件表不一致
expect_not "TSC synchronization"            # vCPU 之间 TSC 不同步
expect_not "stopped with error"             # 某个 vCPU 线程出错退出
expect_not "SHUTDOWN"                       # triple fault
```

原因还是那句话：guest 的很多故障是安静的。4 颗 CPU 最终都上线了，不代表过程中没有出过问题；Linux 在很多情况下会打印一行警告然后继续。这些警告就是早期发现“三方不一致”这类问题的最好证据。

### 2.6 用 tracepoint 串起一次按键的旅程

最后给一个把全文串起来的练习。在 host 上执行：

```bash
sudo trace-cmd record -e kvm:kvm_set_irq -e kvm:kvm_ioapic_set_irq \
     -e kvm:kvm_apic_accept_irq -e kvm:kvm_inj_virq -e kvm:kvm_pio -e kvm:kvm_eoi
```

然后在 guest 的 shell 里按一个键，停止记录，用 `trace-cmd report` 查看。按照前面各篇讲过的机制，应该能依次看到：

1. `kvm_set_irq`：console 线程收到按键，串口模拟代码把 GSI 4 拉高，这是 `KVM_IRQ_LINE` 进入 KVM 的第一站（第十、十一章）。
2. `kvm_ioapic_set_irq`：KVM 按默认路由把 GSI 4 送到 IOAPIC 第 4 根引脚，读重定向表得到向量和目的 CPU（第三、四章）。
3. `kvm_apic_accept_irq`：目标 vCPU 的虚拟 LAPIC 在 IRR 里挂起这个向量，随后被 kick（《中断·原理篇》第四章）。
4. `kvm_inj_virq`：目标 vCPU 重新进入 guest 前，`kvm_check_and_inject_events()` 把向量写进 EVENTINJ（《中断·原理篇》第四章）。
5. 若干条 `kvm_pio`：guest 的串口中断处理程序读 IIR、LSR、RBR，每次都是一次端口 I/O 陷出，回到 VMM 的串口模拟代码（第六、十一章）。读空 FIFO 后中断条件消失，串口把 GSI 4 拉低，又是一次 `kvm_set_irq`。
6. `kvm_eoi`：guest 的处理程序结束，KVM 清掉虚拟 ISR 里的这一位（第二、四章）。x2APIC 下 EOI 是一次 WRMSR 陷出；PV EOI 生效时 guest 只清掉共享内存里的一个标志，不陷出，KVM 在这个 vCPU 下一次退出时补做 EOI，`kvm_eoi` 也在那时出现。

一次按键，六类事件，覆盖了中断从设备到 CPU 再回到中断控制器的完整闭环。如果某一步没有出现，问题就在它和上一步之间，这就是“证据驱动”的排障方式。
