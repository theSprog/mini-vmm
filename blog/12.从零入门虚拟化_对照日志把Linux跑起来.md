这一篇是中断、时间、设备、固件、多核这一组文章的收尾。前面各篇分别讲了一块机制，这里把它们放回一次完整的启动里对照着看，最后讲 guest 起不来时怎么查，以及怎样把这些行为固定成自动化测试。

## 一、把裸 OS 跑起来：对照真实日志逐段解读

前面讲的所有东西，最终都会体现在一次启动的日志里。这一章拿一次真实的启动，从 VMM 的第一行输出读到 guest 关机，每一段都对应回前面各篇的某个机制。读完这一章，日志里的每一行都应该能说出“它是谁打印的、说明了什么”。

启动命令：

```bash
./build/vmm --mode linux --smp 4 --mem 512M \
            --initrd build/initramfs.cpio.gz ~/china_os/linux-6.6/vmlinux
```

这个内核没有开 `CONFIG_KVM_GUEST`，把自己当成跑在裸机上，TSC 频率靠 PIT 校准。`tools/build_guest_kernel.sh` 构建的测试内核开了它，时间相关的几行会不同，见《时间》5.3 节。

guest 起来后依次执行了 `cat /proc/interrupts`、`head -30 /proc/cpuinfo`、查看拓扑和时钟源等命令，最后 `poweroff -f`。日志里 `[INFO]` 开头的是 VMM 自己的输出，`[    x.xxxxxx]` 开头的是 guest 内核通过串口打印的日志。

### 1.1 第一段：VMM 的准备工作（阶段 1–9）

```

[INFO] SVM rev=1, ASIDs=32768
[INFO] SVM features: npt lbrv svm_lock nrip_save tsc_scale vmcb_clean flushbyasid decodeassists pausefilter avic v_vmsave_vmload vgif

阶段 1。API 版本 12，`kvm_run` 三页，KVM 最多允许 1024 个 vCPU。厂商是海光，走 AMD SVM 后端。SVM 特性里 `npt` 保证了二维页表，`tsc_scale` 是《时间》第四章说的 TSC ratio，`pausefilter` 是《多核·原理篇》第一章说的 PAUSE 拦截，`avic` 是《中断·原理篇》第四章说的硬件 APIC 虚拟化（本机 kvm_amd 没有启用它）。

[INFO] ACPI @ GPA 0xe0000: RSDP XSDT@0xe0030 FADT@0xe0070 DSDT@0xe0190 MADT@0xe01d0

[INFO] page tables @ PML4=0x2000 PDPT=0x3000 PD=0x4000: identity map 1024 MiB via 512 2MiB pages
[INFO] vCPU 0: 64-bit long mode, CR3=0x2000 RIP=0x1000000

### 1.2 第二段：内核认识这台机器

```
[    0.000000] Linux version 6.6.91+ (...) #13 SMP PREEMPT_DYNAMIC ...
[    0.000000] Command line: console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1
```

内核的第一行输出。能看到这一行，说明：长模式寄存器、页表、GDT 全都对了（否则早就 triple fault）；`RSI` 指向的 boot_params 被正确读取，命令行从 `cmd_line_ptr` 拷贝成功；串口的最基本输出通路（THR 写入 → VMM `write()`）是通的。此时串口驱动还没加载，这是 `earlyprintk` 用轮询方式在写。

```
[    0.000000] [Firmware Bug]: TSC doesn't count with P0 frequency!
```

《时间》5.5 节讲过：海光/AMD 平台的检查，KVM 模拟的 `HWCR` MSR 第 24 位为 0。无害。

```
[    0.000000] BIOS-provided physical RAM map:
[    0.000000] BIOS-e820: [mem 0x0000000000000000-0x000000000009fbff] usable
[    0.000000] BIOS-e820: [mem 0x000000000009fc00-0x00000000000fffff] reserved
[    0.000000] BIOS-e820: [mem 0x0000000000100000-0x000000001fffffff] usable
[    0.000000] printk: bootconsole [earlyser0] enabled
```

内核原样打印了 VMM 在 boot_params 里给的 E820 表。它说“BIOS-provided”，但这里的“BIOS”就是 VMM。

```
[    0.000000] tsc: Fast TSC calibration using PIT
[    0.000000] tsc: Detected 3000.118 MHz processor
```

《时间》第二章的核心。`quick_pit_calibrate()` 通过端口 `0x61` 打开 PIT 通道 2 的门控，用 PIT 测出 TSC 频率 3000.118 MHz。能看到这两行，说明 `KVM_PIT_SPEAKER_DUMMY` 生效了。

```
[    0.004700] found SMP MP-table at [mem 0x0009fc00-0x0009fc0f]
```

`find_smp_config()` 在 639K–640K 扫描到了 MP 浮动指针（16 字节）。guest 内核开了 `CONFIG_X86_MPPARSE` 才会有这一行。

```
[    0.007782] RAMDISK: [mem 0x1fe00000-0x1ff09fff]
```

内核从 boot_params 读到了 initrd 的位置和大小，把这段内存保留下来。

```
[    0.010742] ACPI: RSDP 0x00000000000E0000 000024 (v02 MINVMM)
[    0.012395] ACPI: XSDT 0x00000000000E0030 000034 (v01 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.014814] ACPI: FACP 0x00000000000E0070 000114 (v06 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.017196] ACPI: DSDT 0x00000000000E0190 000032 (v02 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.019567] ACPI: APIC 0x00000000000E01D0 00005E (v05 MINVMM MINIVMM  00000001 MVMM 00000001)
```

ACPI 表树被完整找到：RSDP 版本 2，长度 `0x24`（36）；XSDT 长 `0x34`（52 = 36 字节表头 + 2 个 8 字节地址）；FADT 长 `0x114`（276）；DSDT 长 `0x32`（50 = 36 + 14 字节 AML）；MADT 长 `0x5E`（94 = 36 + 8 字节固定字段 + 4×8 字节 LAPIC + 12 字节 IOAPIC + 6 字节 LAPIC NMI）。每一个数字都能与《固件与启动协议·实现篇》第二章的结构体大小对上。

```
[    0.054315] ACPI: LAPIC_NMI (acpi_id[0xff] dfl dfl lint[0x1])
[    0.057571] IOAPIC[0]: apic_id 4, version 17, address 0xfec00000, GSI 0-23
[    0.059482] ACPI: Using ACPI (MADT) for SMP configuration information
[    0.061236] smpboot: Allowing 4 CPUs, 0 hotplug CPUs
```

MADT 被解析：LAPIC NMI 条目（所有 CPU 的 LINT1）；IOAPIC 的 ID 4、地址、版本 17（`0x11`，从 KVM 模拟的版本寄存器读出）、24 根引脚。然后是《固件与启动协议·原理篇》1.5 节讲的优先级：**ACPI MADT 可用，就用它，MP table 虽然找到了但不采用**。4 颗 CPU，没有可热插拔的 CPU。

如果用 `--append acpi=off` 启动，这几行会变成 MP table 的解析结果，CPU 数和 IOAPIC 信息相同，但不会有 ACPI 表相关的行，关机也无法走 S5。

### 1.3 第三段：中断与时钟就位

```
[    0.128018] APIC: Switch to symmetric I/O mode setup
[    0.129768] x2apic: IRQ remapping doesn't support X2APIC mode
[    0.133006] ..TIMER: vector=0x30 apic1=0 pin1=0 apic2=-1 pin2=-1
```

《中断·原理篇》第三章的“两代共存”：Linux 从 virtual wire 模式切换到 symmetric I/O 模式，此后设备中断走 IOAPIC。第二行说明没有中断重映射，所以不启用 x2APIC 模式（《中断·原理篇》3.6 节）。第三行是 `check_timer()` 的结论：时钟中断用向量 `0x30`（`ISA_IRQ_VECTOR(0)`），走第 0 个 IOAPIC 的第 0 根引脚——恒等映射生效（《中断·实现篇》2.4 节）。这一行之后没有出现 “timer doesn't work”，说明时钟中断确实送到了。

```
[    0.139007] clocksource: tsc-early: mask: 0xffffffffffffffff max_cycles: 0x2b3eb502405, max_idle_ns: 440795257978 ns
[    0.144081] Calibrating delay loop (skipped), value calculated using timer frequency.. 6000.23 BogoMIPS (lpj=3000118)
```

基于早期校准的 TSC 时钟源可用；`udelay()` 的参数直接由 TSC 频率算出（《时间》第二章）。

### 1.4 第四段：唤醒 AP

```
[    0.437306] smpboot: CPU0: Hygon 18/01 (family: 0x18, model: 0x1, stepping: 0x1)
...
[    0.457657] smp: Bringing up secondary CPUs ...
[    0.459283] smpboot: x86: Booting SMP configuration:
[    0.460087] .... node  #0, CPUs:      #1 #2 #3
[    0.464195] smp: Brought up 1 node, 4 CPUs
[    0.466087] smpboot: Max logical packages: 1
[    0.467083] smpboot: Total of 4 processors activated (24000.94 BogoMIPS)
```

《多核·原理篇》第一章和《多核·实现篇》第一章在这里汇合。BSP 的 CPUID 显示是海光 family `0x18`，这是透传的 host 特性。从 `Bringing up secondary CPUs` 到 `Brought up 1 node, 4 CPUs` 只用了约 7 毫秒，在这期间：

1. BSP 往每个 AP 的 LAPIC 发 INIT 和 SIPI（写 ICR → `#VMEXIT` → KVM 模拟 ICR）；
2. KVM 唤醒睡在 `KVM_RUN` 里的 AP 线程，AP 的 `KVM_RUN` 返回 `-EAGAIN`，VMM 的 run loop 把它当成“重进”；
3. KVM 把 AP 的 `CS:IP` 设为 SIPI 向量指定的 trampoline 地址，AP 进入 guest，从实模式爬到长模式；
4. 每个 AP 读自己 LAPIC 的 ID（等于 vCPU ID），在 MADT 建出的 `cpuid_to_apicid[]` 里查到自己的编号，然后上线。

`Max logical packages: 1` 说明 CPUID 拓扑改写成功：4 颗 CPU 被识别为同一个 package。日志里没有出现 `APIC id mismatch`、`failed to report alive state`、`TSC synchronization` 这类警告，mini-vmm 的测试脚本专门断言了这一点。

### 1.5 第五段：ACPI 解释器与设备驱动

```
[    0.499166] ACPI: 1 ACPI AML tables successfully acquired and loaded
[    0.505090] ACPI: Interpreter enabled
[    0.506102] ACPI: PM: (supports S0 S5)
[    0.508083] ACPI: Using IOAPIC for interrupt routing
```

ACPICA 解释器加载了 DSDT 里的 14 字节 AML，在命名空间里找到了 `_S5_`，所以支持 S5（软关机）。

```
[    0.480297] PCI: Fatal: No config space access function found
...
[    0.525084] PCI: System does not support PCI
```

这份日志对应的是这一组文章所讲的机器：还没有 PCI 总线（没有模拟 PCI 配置空间端口 `0xCF8`/`0xCFC`），Linux 探测后放弃了 PCI。这行 “Fatal” 看起来吓人，但对这里的 guest 没有影响。mini-vmm 加入 PCI 总线之后，这里变成 `PCI: Using configuration type 1 for base access` 和根总线的枚举日志，DSDT 也不再只有 `_S5_`，见《PCI·原理篇》第三章和第七章。

[    0.588585] Serial: 8250/16550 driver, 4 ports, IRQ sharing enabled
[    0.590811] serial8250: ttyS0 at I/O 0x3f8 (irq = 4, base_baud = 115200) is a 16550A
```

《传统设备·原理篇》第一章和《传统设备·实现篇》第一章的串口：`autoconfig()` 的 IER 测试、回环测试、FIFO 测试全部通过，端口被识别为 16550A。之后控制台从 earlyprintk 切换到正式的 8250 驱动，输出改为中断驱动。

[    0.605291] i8042: PNP: No PS/2 controller found.
[    0.606665] i8042: Probing ports directly.

i8042：ACPI 的即插即用信息里没有描述 PS/2 控制器（我们的 DSDT 里没有这类设备对象），驱动改为直接探测端口。控制器命令逐条得到应答；只有 KBD 口，没有 AUX 口，说明 AUX 口被当场判定为不存在；键盘设备的命令应答通过 IRQ1 送达，atkbd 驱动注册成功。从 `Probing ports directly` 到键盘注册只用了 7 毫秒，没有任何超时。

  0:        304          0          0          0   IO-APIC   0-edge      timer
  1:          0          0          9          0   IO-APIC   1-edge      i8042
  4:         28          0          0          0   IO-APIC   4-edge      ttyS0

这张表是前面各篇所有中断机制的“体检报告”：

| 行 | 来源 | 说明了什么 |
|---|---|---|
| `0: timer` | KVM 模拟的 PIT，GSI 0 | IOAPIC 引脚 0，边沿触发，恒等映射；只在 CPU0 上有计数，LAPIC 定时器接管后 PIT 不再使用 |
| `1: i8042` | VMM 的 i8042，`KVM_IRQ_LINE` GSI 1 | 键盘命令应答的 9 次中断，被 IOAPIC 路由到了 CPU2 |

| `9: acpi` | SCI | `fasteoi` 即电平触发；VMM 从不拉这根线 |

| `RES`/`CAL`/`TLB` | guest 内的 IPI | 经 KVM 模拟的 ICR 投递，说明 vCPU 之间的 IPI 通路正常 |
| `SPU`、`ERR` | 伪中断、APIC 错误 | 全 0，中断控制器的模拟没有异常 |

### 1.8 最后一段：关机

```
[guest /]# poweroff -f
[   15.901146] ACPI: PM: Preparing to enter system sleep state S5
[   15.903697] reboot: Power down
[INFO] guest requested poweroff via ACPI S5
[INFO] --- left guest (ok) ---
```

guest 的 `poweroff` 让内核通过 ACPICA 查到 `\_S5_` 的 SLP_TYP（5），往 FADT 声明的 `PM1a_CNT_BLK`（端口 `0x604`）写入 `5 << 10 | SLP_EN`。这次写入以 `KVM_EXIT_IO` 回到执行它的那个 vCPU 线程，PM1a 设备回调返回 `VMM_ERR_EXIT`，这个线程的 run loop 结束，调用 `vm_request_stop()`；其余三个 vCPU（大概率睡在 guest 的 HLT 里）被 `immediate_exit` 和 SIGUSR1 踢出 `KVM_RUN`；主线程 join 全部线程，打印 `left guest (ok)`，退出码 0。

从第一行 `[INFO]` 到最后一行，前面各篇的四大块——中断、时间、设备、多核——以及把它们描述给 guest 的固件表，全部参与了这次启动。

## 二、调试方法与测试

### 2.1 guest 起不来时先看什么

guest 起不来的故障，按“死在哪里”可以分成几类，每一类有不同的首选证据：

| 现象 | 最可能的原因 | 首先看什么 |
|---|---|---|
| `KVM_EXIT_FAIL_ENTRY` | 寄存器状态不合法（RFLAGS bit 1、段属性、CR0/CR4/EFER 不自洽） | VMM 打印的 vCPU 状态 dump |
| `KVM_EXIT_SHUTDOWN`，没有任何内核日志 | 入口地址不对、页表没覆盖入口、GDT 与 sregs 不一致 | vCPU dump 里的 `RIP`、`CR3`、段寄存器；用 VMM 的页表遍历工具查入口地址的翻译 |
| 有少量日志，然后 `KVM_EXIT_SHUTDOWN` | 早期异常（IDT 还没装）；boot_params 字段错误 | 最后一行日志；vCPU dump 里的 `RIP` 对照 `System.map` |
| 日志停在某行，VMM CPU 100% | guest 在忙等某个设备：PIT、RTC、i8042 | 打开 VMM 的调试日志，看未处理端口的访问 |
| 日志停在某行，VMM CPU 0% | guest 在 HLT 里等一个永远不来的中断 | Ctrl-A x 看各 vCPU 停在哪；检查中断路由和固件表 |
| 能启动，但只有 1 颗 CPU | 固件表不可用（MPPARSE 没开、ACPI 表错误）；CPUID 与固件表不一致 | `smpboot: Allowing N CPUs`、`APIC:` 开头的日志 |
| 能启动，但慢了好几秒 | 某个设备探测超时 | 日志时间戳的跳变；对应时刻的端口访问 |
| 能启动，键盘输入没反应 | 串口中断没有新的上升沿；console 线程没起来 | `/proc/interrupts` 里 ttyS0 的计数 |
| `poweroff` 后 VMM 不退出 | PM1a 端口与 FADT 不一致；`_S5_` 缺失；停机协议有漏洞 | `ACPI: PM: (supports ...)`；Ctrl-A x 看哪个 vCPU 还在 |

这张表的核心思想是前面各篇原理篇反复强调的：**guest 的很多故障是“安静”的**。它不报错，只是选择一条退化路径，或者停在某个等待循环里。这时候必须主动去收集证据，而不是盯着日志猜。

### 2.2 VMM 自带的观测手段

mini-vmm 在代码里预留了几个低成本但很有用的观测点：

**vCPU 状态 dump。** 任何异常退出（SHUTDOWN、FAIL_ENTRY、INTERNAL_ERROR、未知退出原因）都会打印该 vCPU 的通用寄存器、控制寄存器、EFER、段寄存器、GDTR/IDTR，以及 exit 统计。Ctrl-A x 退出时则打印**所有** vCPU 的状态，这是 guest 卡住时唯一能看到“每颗 CPU 停在哪条指令”的方法。拿到 `RIP` 之后，对照 vmlinux 的 `System.map` 或者用 `addr2line`，就能知道 guest 卡在哪个函数里（注意 `RIP` 是内核虚拟地址）。

**exit 统计。** 每个 vCPU 记录总 exit 数和 IO、MMIO、HLT 各类的次数。像 RTC 那个“多出 4 万次 exit”的问题，在这个数字上一眼就能看出来：一次启动的 IO exit 数量远超预期，再打开调试日志一看，全是端口 `0x71` 的读。

**未处理端口日志。** `-vv` 打开调试级别后，每一次访问未注册端口都会打印端口号、方向、宽度。PIT speaker 的问题（端口 `0x61`）、RTC 的问题（`0x70`/`0x71`）这类“某个设备没人模拟”的故障，都会在这里露面。

**页表遍历。** `--walk GVA` 在启动前按 VMM 构建的页表把一个地址的四级翻译过程打印出来，用来确认“入口地址到底有没有被映射到”。

### 2.3 host 侧的观测手段

**`top -H`。** vCPU 线程都有名字，`top -H -p $(pgrep -x vmm)` 能直接看到每个 vCPU 的 CPU 占用。100% 说明在 guest 里忙（或者在忙等），0% 说明在 KVM 里睡（HLT 或者等 SIPI）。多核问题首先看这里：某个 AP 线程一直是 0%，说明它从来没被唤醒。

**`perf kvm stat`。** 《一次 out 指令的完整旅程》介绍过，它按退出原因统计 exit 的分布和耗时，是找性能问题的第一手段。在 host 上执行 `perf kvm stat live`，然后在 guest 里做一些操作，就能看到哪类退出最多。

**KVM tracepoint。** `trace-cmd record -e kvm:kvm_exit -e kvm:kvm_entry -e kvm:kvm_inj_virq -e kvm:kvm_apic_ipi` 能抓到每一次退出、每一次中断注入、每一次 IPI。排查“中断到底有没有被注入”这类问题时，`kvm_inj_virq` 是决定性的证据：看到对应向量被注入，说明问题在 guest 侧；没看到，说明问题在路由或设备侧。

### 2.4 测试：自动化的三个坑

mini-vmm 的每个阶段都有自动化测试（`tests/e2e/kvm-basics.sh`、`linux-boot.sh`、`smp.sh`），思路是运行 VMM、抓取全部输出、断言其中包含或不包含某些字符串。相关的用例包括：4 核启动到 VFS panic 然后经 i8042 复位退出；4 核启动 initramfs、在 guest 里检查核数和拓扑、然后 poweroff。写这些测试时遇到了三个值得记录的坑，它们都与 VMM 本身无关，而与“怎么驱动一个交互式程序”有关。

**坑一：`timeout` 导致 VMM 被挂起。** 《传统设备·实现篇》1.7 节讲过：`timeout` 把子进程放进后台进程组，VMM 碰终端就会被 SIGTTOU/SIGTTIN 停住。在 ssh 这类没有终端的环境里跑测试，stdin 不是终端，碰不到这个问题；换到交互式终端里跑，测试就挂住了。修复有两层：VMM 自己检测前台进程组，不在前台时不碰终端；测试脚本把 VMM 的 stdin 接到 `/dev/null`。人工运行时则用 `timeout --foreground`。

**坑二：只在无终端环境里测试是不够的。** 上面这个坑的教训是，测试环境要尽量接近真实使用环境。在非交互环境里要复现“有终端”的情况，可以用 Python 的 `pty` 模块创建一个伪终端：

```bash
python3 -c 'import pty; pty.spawn(["/bin/sh","-c","./tests/e2e/smp.sh -a"])'
```

这里用 `/bin/sh` 而不是 `bash -c`，是因为 `bash` 会读用户的配置文件，可能被切换到别的 shell。用 `script` 命令配合管道的做法实测会挂住，不建议使用。

**坑三：给 guest 喂命令要留间隔，断言要防回显。** 测试需要在 guest 的 shell 里执行命令，做法是把命令通过管道写进 VMM 的 stdin，console 线程再把它们送进串口的 RX FIFO。有两个问题：

- 串口 RX FIFO 只有 256 字节，一次灌入太多字符，FIFO 满了之后的字符会被丢掉。测试脚本先等 6 秒让 shell 起来，之后每条命令间隔 1 秒。
- guest 的 shell 会回显输入的命令。如果执行 `nproc` 然后断言输出里有 `4`，回显的命令行本身就可能让断言误判。正确的写法是让 guest **计算**出标记：执行 `echo NPROC-$(nproc)`，断言 `NPROC-4`。回显里只有 `$(nproc)`，只有真正执行后的输出里才有 `NPROC-4`。拓扑检查也是同样的写法，比如 `echo APIC-$(sed -n "s/^apicid.*: //p" /proc/cpuinfo | tr "\n" -)` 断言 `APIC-0-1-2-3-`。

### 2.5 负向断言

最后一个测试技巧：除了断言“应该出现什么”，还要断言“不应该出现什么”。4 核启动的用例里有一组负向断言：

```bash
expect_not "failed to report alive state"   # AP 没有上线
expect_not "do_boot_cpu failed"             # AP 唤醒失败
expect_not "APIC id mismatch"               # CPUID 与固件表不一致
expect_not "TSC synchronization"            # vCPU 之间 TSC 不同步
expect_not "stopped with error"             # 某个 vCPU 线程出错退出
expect_not "SHUTDOWN"                       # triple fault
```

原因还是那句话：guest 的很多故障是安静的。4 颗 CPU 最终都上线了，不代表过程中没有出过问题；Linux 在很多情况下会打印一行警告然后继续。这些警告就是早期发现“三方不一致”这类问题的最好证据。

### 2.6 用 tracepoint 串起一次按键的旅程

最后给一个把全文串起来的练习。在 host 上执行：

```bash
sudo trace-cmd record -e kvm:kvm_set_irq -e kvm:kvm_ioapic_set_irq \
     -e kvm:kvm_apic_accept_irq -e kvm:kvm_inj_virq -e kvm:kvm_pio -e kvm:kvm_eoi
```

然后在 guest 的 shell 里按一个键，停止记录，用 `trace-cmd report` 查看。按照前面各篇讲过的机制，应该能依次看到：

1. `kvm_set_irq`：console 线程收到按键，串口模拟代码把 GSI 4 拉高，这是 `KVM_IRQ_LINE` 进入 KVM 的第一站（第十、十一章）。
2. `kvm_ioapic_set_irq`：KVM 按默认路由把 GSI 4 送到 IOAPIC 第 4 根引脚，读重定向表得到向量和目的 CPU（第三、四章）。
3. `kvm_apic_accept_irq`：目标 vCPU 的虚拟 LAPIC 在 IRR 里挂起这个向量，随后被 kick（《中断·原理篇》第四章）。
4. `kvm_inj_virq`：目标 vCPU 重新进入 guest 前，`inject_pending_event()` 把向量写进 EVENTINJ（《中断·原理篇》第四章）。
5. 若干条 `kvm_pio`：guest 的串口中断处理程序读 IIR、LSR、RBR，每次都是一次端口 I/O 陷出，回到 VMM 的串口模拟代码（第六、十一章）。读空 FIFO 后中断条件消失，串口把 GSI 4 拉低，又是一次 `kvm_set_irq`。
6. `kvm_eoi`：guest 的处理程序结束，写 LAPIC 的 EOI 寄存器，KVM 清掉虚拟 ISR 里的这一位（第二、四章）。

一次按键，六类事件，覆盖了中断从设备到 CPU 再回到中断控制器的完整闭环。如果某一步没有出现，问题就在它和上一步之间，这就是“证据驱动”的排障方式。
