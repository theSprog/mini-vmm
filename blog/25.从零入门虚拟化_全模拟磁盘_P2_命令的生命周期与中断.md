P1 讲到端口启动、链路建立、驱动从 PxSIG 认出“这里接着一块 ATA 盘”。这一篇看驱动怎样把一条命令交给控制器，控制器怎样告诉驱动“做完了”或者“出错了”。

| P | 内容 |
|---|---|
| P1 | 外观与端口枚举：PCI 身份、ABAR、全局寄存器、端口的启动、COMRESET 与设备签名 |
| P2（本篇） | 命令的生命周期与中断：命令列表、命令表、FIS 接收区，从写 PxCI 到收到 D2H FIS，三级中断，出错停端口与恢复 |
| P3 | IDENTIFY 与 PIO：驱动眼里的盘长什么样，PIO Setup FIS，SET FEATURES |
| P4 | 后端与 DMA 读写：`--drive` 与 raw 镜像，PRDT 的逐项检查，写缓存与 FLUSH，端到端验证 |
| P5 | NCQ：PxSACT、FPDMA 命令与 SDB FIS，出错之后经日志 10h 恢复 |

这一篇只讲“任何一条命令都要走的那条路”。命令本身做什么（IDENTIFY 返回什么数据、读写怎么搬数据）留给 P3、P4，NCQ 命令的那条岔路留给 P5。

## 一、命令放在哪：三块 guest 内存

### 1.1 寄存器只按门铃，命令在内存里

《全模拟网卡 P4：发送》里，e1000 的驱动把描述符写进内存里的环，再写一次 TDT 寄存器告诉网卡“环里有新东西了”。AHCI 是同一个思路：命令的全部内容都在 guest 内存里，寄存器只负责“按门铃”。区别在于组织方式：e1000 是一个首尾相接的环，用头尾两个下标表示哪些描述符待处理；AHCI 是 32 个固定的命令槽（slot），用一个 32 位的位图 PxCI 表示哪些槽里有待执行的命令。

每个端口有三块内存，地址都由驱动分配、写进端口寄存器：

| 结构 | 谁指向它 | 大小与对齐 | 内容 |
|---|---|---|---|
| 命令列表（Command List） | PxCLB/PxCLBU | 32 个命令头 × 32 字节 = 1 KiB，1 KiB 对齐 | 每个槽一个命令头 |
| 命令表（Command Table） | 命令头的 CTBA | 0x80 字节的头部加 PRDT，128 字节对齐 | 要发给设备的 FIS、数据的 scatter-gather 表 |
| FIS 接收区（Received FIS） | PxFB/PxFBU | 256 字节，256 字节对齐 | 设备发回来的各类 FIS 的副本 |

方向很清楚：命令列表和命令表是驱动写、HBA 读；FIS 接收区是 HBA 写、驱动读。

### 1.2 Linux 怎么分配这三块内存

`ahci_port_start()` 为每个端口申请一整块 DMA 内存，依次切成三段（`drivers/ata/ahci.h` 里的常量）：

```text
偏移        大小                         内容
0x0000      AHCI_CMD_SLOT_SZ  = 32 × 32  命令列表（32 个命令头）
0x0400      AHCI_RX_FIS_SZ    = 256      FIS 接收区
0x0500      32 × AHCI_CMD_TBL_SZ         32 个命令表，每个 0x80 + 168 × 16 = 2816 字节
```

每个命令表 2816 字节，是因为 Linux 给每条命令留了 `AHCI_MAX_SG = 168` 个 PRD 项（注释写着硬件最多能有 64K 项）。

trace 里驱动写进端口 0 的地址正好对上这个布局：

```text
  88 P0CLBU  W4 00000000
  89 P0CLB   W4 042c0000      命令列表
  90 P0FBU   W4 00000000
  91 P0FB    W4 042c0400      = CLB + 0x400，FIS 接收区
```

槽 n 的命令表在 `0x042c0500 + n × 2816`。下面 1.4 节从 mini-vmm 读到的命令头里，槽 4、5、6 的 CTBA 分别是 0x042c3100、0x042c3c00、0x042c4700，都与这个公式一致。

### 1.3 命令头

命令列表里每个命令头 32 字节，有效内容在前 4 个 dword（AHCI 1.3.1 第 4.2.2 节）：

```text
DW0   31          16 15  12 11 10  9  8  7  6  5  4      0
      +--------------+------+--+--+--+--+--+--+--+--------+
      |    PRDTL     | PMP  |  | C| B| R| P| W| A|  CFL   |
      +--------------+------+--+--+--+--+--+--+--+--------+
DW1   PRDBC：实际传输的字节数，HBA 写回
DW2   CTBA：命令表地址低 32 位（bit 6:0 保留，即 128 字节对齐）
DW3   CTBAU：命令表地址高 32 位
DW4-7 保留
```

- **CFL**：命令表里那个 FIS 的长度，单位 dword。规范规定 0 和 1 非法，最大 16。
- **W**：数据方向，1 表示写（主机到设备）。
- **PRDTL**：PRDT 有多少项，0 表示这条命令不传数据。
- **PRDBC**：HBA 在命令完成时写回实际传了多少字节（P4）。
- **C、R、B、A、P**：分别和软件复位、BIST、ATAPI、预取有关，Linux 的 ahci 驱动在普通命令里都填 0（`ahci_qc_prep()` 只在 ATAPI 命令时置 A 和 P）。

驱动填命令头的代码只有几行（`ahci_qc_prep()` 和 `ahci_fill_cmd_slot()`）：

```c
opts = cmd_fis_len | n_elem << 16 | (qc->dev->link->pmp << 12);   /* CFL=5, PRDTL, PMP */
if (qc->tf.flags & ATA_TFLAG_WRITE)
        opts |= AHCI_CMD_WRITE;
...
pp->cmd_slot[tag].opts = cpu_to_le32(opts);
pp->cmd_slot[tag].status = 0;                                        /* PRDBC 清零 */
pp->cmd_slot[tag].tbl_addr = cpu_to_le32(cmd_tbl_dma & 0xffffffff);
pp->cmd_slot[tag].tbl_addr_hi = cpu_to_le32((cmd_tbl_dma >> 16) >> 16);
```

`cmd_fis_len` 固定是 5：Linux 发的命令 FIS 都是 20 字节的 Register H2D FIS。

### 1.4 用 mini-vmm 看几条真实的命令

规范里的图不如真实数据直观。我在 scratchpad 里给 mini-vmm 的 `exec_slot()` 临时加了一行日志，打印每条命令的命令头和命令 FIS 的前 20 字节，然后启动 guest，用 `hdparm -S 10 /dev/sda`（设置待机定时器）发一条 mini-vmm 不支持的命令，再用 `dd ... iflag=direct` 读一次盘。部分输出：

```text
slot 0 hdr_gpa=0x42c0000 dw0=0x00010005 dw1=0 dw2=0x042c0500 dw3=0
       cfis=27 80 ec 00 | 00 00 00 a0 | 00 00 00 00 | 00 00 00 08 | 00 00 00 00
slot 0 hdr_gpa=0x42c0000 dw0=0x00000005 dw1=0 dw2=0x042c0500 dw3=0
       cfis=27 80 ef 03 | 00 00 00 a0 | 00 00 00 00 | 46 00 00 08 | 00 00 00 00
slot 4 hdr_gpa=0x42c0080 dw0=0x00010005 dw1=0 dw2=0x042c3100 dw3=0
       cfis=27 80 60 08 | 00 00 00 40 | 00 00 00 00 | 20 00 00 08 | 00 00 00 00
slot 5 hdr_gpa=0x42c00a0 dw0=0x00000005 dw1=0 dw2=0x042c3c00 dw3=0
       cfis=27 80 e3 00 | 00 00 00 00 | 00 00 00 00 | 0a 00 00 08 | 00 00 00 00
```

先看命令头。第一条 `dw0=0x00010005`：CFL=5，PRDTL=1（一项 PRD，IDENTIFY 要传 512 字节数据），W=0。第二条 `dw0=0x00000005`：PRDTL=0，不传数据。槽 n 的命令头在 `CLB + n × 32`，槽 5 正是 0x42c00a0。

再看命令 FIS，它是 SATA 3.0 第 10.3.4 节的 Register Host to Device FIS，20 字节：

| 字节 | 字段 | 第一条（IDENTIFY） | 第四条（hdparm -S 10） |
|---|---|---|---|
| 0 | FIS 类型 | 0x27（Register H2D） | 0x27 |
| 1 | bit 7 = C，bit 3:0 = PM 端口 | 0x80：C=1，这是一条命令 | 0x80 |
| 2 | Command | 0xEC IDENTIFY DEVICE | 0xE3 IDLE |
| 3 | Features 7:0 | 0 | 0 |
| 4–6 | LBA 23:0 | 0 | 0 |
| 7 | Device | 0xA0 | 0 |
| 8–10 | LBA 47:24 | 0 | 0 |
| 11 | Features 15:8 | 0 | 0 |
| 12–13 | Count | 0 | 0x0A：待机时间 10 × 5 秒 |
| 15 | Control | 0x08 | 0x08 |

FIS 的字段就是老式 ATA“任务文件”（taskfile）寄存器的一份拷贝：在并口 IDE 时代，驱动是一个个 `outb` 写进这些寄存器的；SATA 把它们打包成一个 FIS 一次发过去。C 位区分两种用法：C=1 表示写的是 Command 寄存器，即发一条命令；C=0 表示写的是 Device Control 寄存器，用来做软件复位。

另外两条留给后面：第二条是 SET FEATURES（0xEF），子命令 03 设置传输模式，Count 0x46 表示 UDMA 6（P3）；第三条是 READ FPDMA QUEUED（0x60），NCQ 命令把扇区数放在 Features，把 tag 放在 Count 的 bit 7:3，0x20 >> 3 = 4，正好是槽 4（P5）。

还有一个规律：探测阶段的命令（IDENTIFY、SET FEATURES）都用槽 0。这些是 libata 的“内部命令”，`ata_exec_internal()` 给它们的 tag 是 `ATA_TAG_INTERNAL`、`hw_tag` 是 0（`libata-core.c`）。普通 I/O 的 tag 由块层分配，所以 hdparm 和 dd 用的是槽 5、6。

### 1.5 命令表与 FIS 接收区

命令表的布局（第 4.2.3 节）：

```text
0x00  CFIS   命令 FIS，最多 64 字节（Linux 只用 20 字节）
0x40  ACMD   ATAPI 命令（SCSI CDB），16 字节，只有 A=1 时有意义
0x50  保留
0x80  PRDT   PRDTL 个 PRD，每个 16 字节：数据地址、字节数、完成时是否中断（P4）
```

FIS 接收区的布局（第 4.2.1 节）：

```text
0x00  DSFIS   DMA Setup FIS        （NCQ 的第一方 DMA 用，mini-vmm 不发）
0x20  PSFIS   PIO Setup FIS        （P3）
0x40  RFIS    D2H Register FIS     本篇的主角
0x58  SDBFIS  Set Device Bits FIS  （P5）
0x60  UFIS    未知类型的 FIS
0xA0  保留，到 0xFF
```

设备每发来一个 FIS，HBA 就把它复制到对应的位置，旧的内容被覆盖。所以 RFIS 那 20 字节永远是“最近一次收到的 D2H Register FIS”。

## 二、一条命令的一生

### 2.1 驱动这一侧：准备、按门铃

驱动发一条命令分两步。`ahci_qc_prep()` 在内存里准备好命令表（FIS 和 PRDT）和命令头，`ahci_qc_issue()` 按门铃：

```c
if (ata_is_ncq(qc->tf.protocol))
        writel(1 << qc->hw_tag, port_mmio + PORT_SCR_ACT);   /* NCQ 才写 PxSACT（P5） */
...
writel(1 << qc->hw_tag, port_mmio + PORT_CMD_ISSUE);         /* PxCI 置这一槽的位 */
```

PxCI 是“写 1 置位”（RW1）：写 `1 << 5` 只把槽 5 置上，不影响其他槽。驱动不需要先读出 PxCI 再或上新位，多个 CPU 同时发命令也不会互相覆盖。

### 2.2 HBA 这一侧：取命令、发出去、等回信

规范第 5 章用一大张状态机描述 HBA 的行为，对一条非 NCQ 命令而言，主线是这样（第 5.3 节）：

```text
PxCI 有槽置位且 ST=1
  └─ 读这一槽的命令头（PxCLB + slot × 32）
  └─ 按 CTBA 读命令表里的 CFIS，发给设备；有数据的话按 PRDT 搬
  └─ 设备回一个 D2H Register FIS（或 PIO Setup FIS，P3）
       ├─ 复制到 FIS 接收区的 RFIS
       ├─ 用其中的 Status、Error 更新 PxTFD
       ├─ FIS 的 I 位为 1：置 PxIS.DHRS
       └─ Status 里 BSY、DRQ、ERR 都是 0：清掉 PxCI 里这一槽的位
```

最后一条是 PxCI 的定义（第 3.3.14 节）：“HBA 收到清掉这条命令的 BSY、DRQ 和 ERR 的 FIS 时，清掉 PxCI 里对应的位”。这句话里有个容易漏掉的推论：Status 带 ERR 时，这一位**不清**。出错的命令会一直留在 PxCI 里，这是第四章的起点。

### 2.3 驱动怎么知道命令完成了：看 PxCI 少了哪一位

一个直觉的想法是：中断来了，看 PxIS 里有 DHRS，就知道“命令完成了”。但 PxIS 只说明“收到过一个 D2H FIS”，不说是哪一槽的。驱动判断哪些命令完成的唯一依据是 PxCI（NCQ 是 PxSACT）：

```c
/* ahci_qc_complete() */
if (ap->qc_active && pp->active_link->sactive)
        qc_active = readl(port_mmio + PORT_SCR_ACT);
else
        qc_active = readl(port_mmio + PORT_CMD_ISSUE);
rc = ata_qc_complete_multiple(ap, qc_active);
```

```c
/* ata_qc_complete_multiple()，libata-sata.c */
done_mask = ap_qc_active ^ qc_active;          /* 驱动认为在跑的 vs 硬件说还在跑的 */
if (unlikely(done_mask & qc_active)) {
        ata_port_err(ap, "illegal qc_active transition (%08llx->%08llx)\n", ...);
        return -EINVAL;
}
```

`ap->qc_active` 是驱动自己记的“发出去、还没完成”的位图，`qc_active` 是从硬件读到的。两者异或得到变化了的位，正常情况下这些位只能是“驱动记着、硬件已经清了”，也就是完成了的命令。如果硬件里多出一位驱动没发过的命令，`done_mask & qc_active` 非零，驱动判定硬件状态错乱，返回 -EINVAL，调用者冻结端口、走复位。第四章的反例就撞上了这一条。

### 2.4 命令的结果从内存读，不读寄存器

命令完成后，libata 往往要知道设备最后的 Status 和 Error（出错时要据此判断原因，`hdparm` 这类直通命令要把它们原样交给用户态）。它们并不从 PxTFD 寄存器读，而是从 FIS 接收区读（`ahci_qc_fill_rtf()`）：

```c
/* PIO data-in 命令成功时，设备不发 D2H FIS，结果在 PIO Setup FIS 里（P3） */
if (qc->tf.protocol == ATA_PROT_PIO && qc->dma_dir == DMA_FROM_DEVICE && ...) {
        ata_tf_from_fis(rx_fis + RX_FIS_PIO_SETUP, &qc->result_tf);
        ...
}
/* NCQ 命令看 SDB FIS（P5） */
...
ata_tf_from_fis(rx_fis + RX_FIS_D2H_REG, &qc->result_tf);   /* 其余：RFIS，偏移 0x40 */
```

这意味着设备模型除了更新 PxTFD，还必须把 D2H FIS 真的写进 guest 内存的 FIS 接收区，出错时也一样。只更新寄存器的话，驱动读到的是上一条命令留下的旧 FIS，可能把一条失败的命令当成成功。

### 2.5 在 trace 里看一条命令

用 `--trace-mmio` 记下 ABAR 的每一次访问，再把偏移翻译成寄存器名，这是 guest 启动后驱动发出的第一条命令（IDENTIFY，槽 0）：

```text
 488 16000.383053 P0CI   W4 00000001     按门铃：槽 0
 489 16000.383074 IS     R4 00000001     中断处理：哪个端口
 490 16000.383098 P0IS   R4 00000002     端口 0 的原因：PSS（PIO Setup FIS，IDENTIFY 的结束方式，P3）
 491 16000.383110 P0IS   W4 00000002     清 PxIS
 492 16000.383122 P0CI   R4 00000000     槽 0 的位清了：命令完成
 493 16000.383136 IS     W4 00000001     清 IS
```

随后的 SET FEATURES（第 544 行起）是同样的 6 次访问，只是 PxIS 读到的是 0x1（DHRS）。一条非 NCQ 命令在 VMM 里就是 6 次 MMIO exit：1 次按门铃，5 次在中断处理函数里。按门铃（488）到中断处理函数第一次读 IS（489）只隔 21 µs，原因在第五章。

## 三、中断：三级开关

### 3.1 结构

AHCI 的中断分两层状态（第 10.7.1 节称为 tier），再加一个总开关：

```text
端口 0:  PxIS ──AND── PxIE ──→ 虚拟线 0 ──┐
端口 1:  PxIS ──AND── PxIE ──→ 虚拟线 1 ──┤  线为 1 时置位
  ...                                     ├──────────→ IS（每端口一位，粘滞）
端口 5:  PxIS ──AND── PxIE ──→ 虚拟线 5 ──┘                │
                                                         任一位为 1
                                                            │
                                         GHC.IE ──AND───────┘
                                                   │
                                                 INTx
```

- **PxIS**（第二层）：端口里发生了什么，每种事件一位，写 1 清除。
- **PxIE**：每种事件是否产生中断。事件在 PxIE 关着时照样记进 PxIS，只是不往上传。
- **IS**（第一层）：哪个端口有待处理的中断，每端口一位。它由“虚拟线”的电平置位，软件写 1 清除。
- **GHC.IE**：整个 HBA 的总开关。它只屏蔽输出到 INTx 的那根线，不影响 IS 和 PxIS 的置位（第 10.7.1.1 节）。

### 3.2 为什么清的顺序是先 PxIS 后 IS

第 10.7.2.1 节规定了软件清中断的顺序：

> In order to clear an interrupt, software must first clear the event from the PxIS register, then clear the interrupt event from the IS register. If software clears IS register only, leaving the level of the virtual wire from the PxIS register set, the resulting level of '1' shall cause the IS register bit to be re-set.

IS 的位由虚拟线的**电平**维持。如果先清 IS，PxIS 还没清，线还是 1，IS 的位会立刻重新置上，INTx 一直有效，中断处理函数返回后马上又被叫进来。

Linux 的 `ahci_single_level_irq_intr()` 就是按这个顺序写的，源码注释说得很直白：

```c
irq_stat = readl(mmio + HOST_IRQ_STAT);              /* IS */
...
rc = ahci_handle_port_intr(host, irq_masked);        /* 每个端口：读 PxIS、写回清除、处理 */
/* HOST_IRQ_STAT behaves as level triggered latch meaning that
 * it should be cleared after all the port events are cleared;
 * otherwise, it will raise a spurious interrupt after each
 * valid one. ... */
writel(irq_stat, mmio + HOST_IRQ_STAT);              /* 最后清 IS */
```

2.5 节 trace 的 489–493 行正是这个顺序：读 IS，读 PxIS，写 PxIS，读 PxCI，写 IS。

### 3.3 驱动打开了哪些中断

端口启动后驱动写 PxIE（P1 第五章的 trace 第 480 行）：

```text
 480 P0IE  W4 7840007f
```

`ahci_port_start()` 把 `pp->intr_mask` 初始化成 `DEF_PORT_IRQ`（`drivers/ata/ahci.h`，0x78C0007F）。没有端口倍增器时 `ahci_pmp_detach()` 再去掉 BAD_PMP（bit 23），剩下的就是写进去的 0x7840007F。按位拆开：

| 位 | 名字 | 含义 | 本模型会置吗 |
|---|---|---|---|
| 0 | DHRS | 收到 D2H Register FIS | 是 |
| 1 | PSS | 收到 PIO Setup FIS | 是（P3） |
| 2 | DSS | 收到 DMA Setup FIS | 否 |
| 3 | SDBS | 收到 Set Device Bits FIS | 是（P5） |
| 4 | UFS | 收到未知 FIS | 否 |
| 5 | DPS | 一个 I=1 的 PRD 处理完 | 是（P4） |
| 6 | PCS | 端口连接状态变化 | 是，COMRESET 后 |
| 22 | PRCS | PhyRdy 变化 | 是，COMRESET 后 |
| 27 | IFS | 接口致命错误 | 否 |
| 28 | HBDS | 主机总线数据错误 | 否 |
| 29 | HBFS | 主机总线致命错误 | 是，DMA 访问失败时 |
| 30 | TFES | 任务文件错误：设备报告 ERR | 是 |

注意 OFS（bit 24，命令列表溢出）不在里面，P4 会讲这个选择的后果。

### 3.4 实现

mini-vmm 用 `update_irq()` 把三层的关系算一遍，任何可能改变某一层状态的地方都调用它：

```c
static void update_irq(struct ahci *s)
{
    int i;

    for (i = 0; i < AHCI_NR_PORTS; i++)
        if (port_is(&s->port[i]) & s->port[i].ie)
            s->is |= 1u << i;
    pci_set_irq(&s->pci, (s->ghc & AHCI_GHC_IE) && s->is);
}
```

几个细节：

- IS 只在这里被**置位**，只在软件写 IS 时被**清除**。这样“粘滞、写 1 清”和“线还是 1 就立刻重新置上”两条规则都自然成立：软件清了 IS，下一次 `update_irq()` 时线若还是 1 就又置上；而 ahci_reg_write 处理 IS 的写入时，清完紧接着就调用了一次 `update_irq()`。
- PxIS 的读值是 `port_is()`：存下的可清位，加上两个由 PxSERR 派生的只读位（PCS 镜像 PxSERR.DIAG.X，PRCS 镜像 PxSERR.DIAG.N）。规范规定这两位不能直接写 PxIS 清除，要清 PxSERR 里对应的位，所以 PxSERR 的写入也要调用 `update_irq()`。
- 每次都扫所有端口，不只扫“刚变化的那个端口”。端口只有 6 个，这样做的好处是不可能漏掉：哪怕某条路径改了状态却忘了说是哪个端口，结果也是对的。
- 最后一行交给 PCI 核心的 `pci_set_irq()`，它负责 COMMAND.INTx Disable 和同一根线上多个设备的“线或”（《PCI·实现篇》），只在电平真正变化时才调 `KVM_IRQ_LINE`。

## 四、出错：停下端口，等软件来救

### 4.1 规范怎么规定

设备回的 FIS 里 Status 带 ERR（第 6.1.4 节），或者 HBA 访问 guest 内存失败（第 6.1.1 节），都属于致命错误。第 6.2.2 节规定 HBA 进入 ERR:Fatal 状态：

> Fatal errors (signified by the setting of PxIS.HBFS, PxIS.HBDS, PxIS.IFS, or PxIS.TFES) will cause the HBA to enter the ERR:Fatal state, and clear PxCMD.CR. In this state, the HBA shall not issue any new commands ... To recover, the port must be restarted; the port is restarted by clearing PxCMD.ST to '0' and then setting PxCMD.ST to '1'.

于是一个出错的端口处于这样的状态：

- PxIS.TFES（或 HBFS）为 1，打开了中断的话 INTx 有效；
- 出错那一槽还留在 PxCI 里（2.2 节：带 ERR 的 FIS 不清 PxCI）；
- PxCMD.CCS 指着出错的槽；
- PxCMD.CR = 0 而 ST 仍为 1：引擎停了，软件写 PxCI 也不会再执行新命令。

第 6.2.2.1 节给了非 NCQ 的恢复步骤：读 PxCI 看哪些命令没完成，读 CCS 看是哪一槽出的错，清 ST（PxCI 随之清零）并等 CR 变 0，清 PxSERR 和 PxIS，如果 PxTFD 的 BSY 或 DRQ 还是 1 就发 COMRESET，最后重新置 ST。

### 4.2 在真实 guest 里触发一次

mini-vmm 的 ATA 设备不支持 IDLE（0xE3）命令，按 ATA8-ACS 第 4.1 节对不支持命令的规定中止：回 Status = DRDY|ERR（0x41），Error = ABRT（0x04）。在 guest 里执行 `hdparm -S 10 /dev/sda` 就会发出这条命令。VMM 的日志和 guest 的输出：

```text

[WARN] ahci: port 0: ATA command 0xe3 not supported, aborted (logged once per command)
```

### 4.3 Linux 这边走了哪条路

把 trace 和 libahci 的代码对照起来：

```text
INTx → ahci_single_level_irq_intr()              564 读 IS
  └─ ahci_port_intr()                            565 读 PxIS = 0x40000001，566 写回清除
       └─ ahci_handle_port_interrupt()
            status & PORT_IRQ_ERROR（含 TF_ERR）为真：
            ├─ ahci_qc_complete()                567 读 PxCI = 0x20：没有命令完成
            └─ ahci_error_intr()
                 ├─ 读写 SError                   568、569
                 ├─ active_qc->err_mask |= AC_ERR_DEV
                 └─ ata_port_abort()             交给 EH
  ...                                            570 写 IS
EH 线程 → ahci_error_handler()
  ├─ ahci_stop_engine()                          571–573：清 ST，等 CR=0
  └─ ahci_start_engine()                         574–576：置 ST
```

几点观察：

- 这次恢复没有 PxIS 的额外清除，也没有 COMRESET：中断处理函数已经把 PxIS 清了，PxTFD 的 BSY 和 DRQ 都是 0，按第 6.2.2.1 节不需要 COMRESET。设备回了一个干净的“我中止了这条命令”，状态是稳定的。
- EH 没有在 dmesg 里打印任何东西。hdparm 的命令经 SG_IO 走 ATA 直通，`ata_scsi_pass_thru()` 给它置了 `ATA_QCFLAG_QUIET`，EH 对这类命令只把错误交回给调用者。hdparm 拿到的 I/O error 就是这么来的；它读到的 Status 和 Error 来自 FIS 接收区的 RFIS（2.4 节）。
- P1 提到驱动用 CAP.SCLO 判断能不能做 CLO（Command List Override）。CLO 让 HBA 强行清掉 PxTFD 的 BSY 和 DRQ，用在设备卡在 BSY 状态、端口又必须重启的时候（`ahci_kick_engine()` 只在 BSY 或 DRQ 为 1 时才做 CLO）。mini-vmm 的设备结束每条命令时 BSY、DRQ 都是 0，所以这条路在 trace 里从未出现。mini-vmm 仍然实现了它：写 PxCMD.CLO 时清掉 PxTFD 的这两位。

### 4.4 实现

设备完成一条命令走 `complete_cmd()`：

```c
static void complete_cmd(struct ahci *s, struct ahci_port *p, int slot,
                         uint8_t status, uint8_t error)
{
    uint8_t fis[SATA_FIS_REG_LEN] = { 0 };

    fis[0] = SATA_FIS_REG_D2H;
    fis[1] = SATA_FIS_I;
    fis[2] = status;
    fis[3] = error;
    p->tfd = ((uint32_t)error << 8) | status;
    if (post_fis(s, p, AHCI_RFIS_RFIS, fis, sizeof(fis)) != VMM_OK) {
        host_bus_fatal(s, p, slot);
        return;
    }
    p->is |= AHCI_PxIS_DHRS;
    if (status & ATA_STS_ERR) {
        p->is |= AHCI_PxIS_TFES;
        p->halted = true;
        p->ccs = (uint8_t)slot;
    } else {
        p->ci &= ~(1u << slot);
    }
    update_irq(s);
}
```

顺序和 2.2 节的主线一一对应：FIS 写进接收区，更新 PxTFD，置 DHRS；出错时置 TFES、停端口、CCS 指向这一槽，不清 PxCI；正常时清 PxCI 的这一位；最后重算中断。

`post_fis()` 只在 PxCMD.FRE=1 时写内存（第 3.3.7 节：FRE=0 时 HBA 不往 FIS 接收区写）。写内存本身失败，比如驱动把 PxFB 指到了 RAM 之外，按主机总线致命错误处理：`host_bus_fatal()` 置 PxSERR.ERR.E 和 PxIS.HBFS，同样停下端口。读命令头、读命令 FIS 失败也走这里。

端口“停下”用一个 `halted` 标志表示，它体现在两处：

```c
/* port_read()：CR 由 ST 和 halted 推出来 */
if ((p->cmd & AHCI_PxCMD_ST) && !p->halted)
    v |= AHCI_PxCMD_CR;

/* port_run()：halted 时不取新命令 */
while (pending && (p->cmd & AHCI_PxCMD_ST) && !p->halted) { ... }
```

软件恢复时写 PxCMD，`write_cmd()` 处理 ST 的变化：

```c
if ((old & AHCI_PxCMD_ST) && !(val & AHCI_PxCMD_ST)) {
    /* 第 3.3.7 节：ST 1→0 时 HBA 清 PxCI、PxSACT、CCS，回到空闲 */
    p->ci = 0;
    p->sact = 0;
    p->ccs = 0;
    p->halted = false;
} else if (!(old & AHCI_PxCMD_ST) && (val & AHCI_PxCMD_ST)) {
    p->ccs = 0;
    p->halted = false;
}
```

### 4.5 反例：ST 1→0 时不清 PxCI

`p->ci = 0` 这一行看起来无关紧要：端口都停了，PxCI 里留着一位又怎样？去掉它，重新跑 4.2 节的实验：

```text

[guest ~]# dd if=/dev/sda of=/dev/null bs=4k count=1 iflag=direct
slot 5 ... cfis=27 80 e3 00 ...                         ← 槽 5 的 IDLE 又被执行了一次
d2h slot 5 status 0x41 error 0x04 ci=0x00000060
[    2.050007] ata1: illegal qc_active transition (100000000->00000060)
[    2.054400] ata1.00: exception Emask 0x1 SAct 0x40 SErr 0x0 action 0x6 frozen
[    2.056983] ata1.00: failed command: READ FPDMA QUEUED
[    2.062391] ata1: hard resetting link
[    2.376582] ata1: illegal qc_active transition (100000000->00000060)
[    2.378024] ata1.00: failed to IDENTIFY (I/O error, err_mask=0x40)
[    7.455613] ata1: hard resetting link

[    7.771089] ata1: limiting SATA link speed to 3.0 Gbps
[   13.087521] ata1: hard resetting link
[   13.400455] ata1: illegal qc_active transition (100000000->00000060)
[   13.404958] ata1.00: disable device
[   13.723936] I/O error, dev sda, sector 0 op 0x0:(READ) flags 0x800 phys_seg 1 prio class 2

```

过程是这样的：

1. EH 清 ST 时槽 5 没有被清掉，PxCI 一直是 0x20。
2. dd 的读命令是 NCQ 命令，用槽 6，驱动写 PxCI = 0x40。PxCI 是写 1 置位，结果是 0x60。`port_run()` 从低号开始，先执行了残留的槽 5，又中止一次，端口又停了，槽 6 根本没轮到。
3. NCQ 命令出错后，EH 要先用一条内部命令读 NCQ 错误日志（P5），内部命令占硬件槽 0。EH 重启引擎时槽 5 依旧没清，于是这次 `port_run()` 执行了槽 0 的读日志，接着又执行了槽 5。中断处理函数读 PxCI 得到 0x60，而驱动记着的在跑的命令只有那条内部命令（`100000000` 是 bit 32，即 `ATA_TAG_INTERNAL`），硬件里多出了驱动没发过的位，2.3 节那条检查触发：`illegal qc_active transition`。
4. 驱动冻结端口、硬复位链路、重新 IDENTIFY。`ahci_do_hardreset()` 在 COMRESET 之前也会先清 ST，而 ST 1→0 正是这里被弄坏的地方，槽 5 永远在那里。之后每一条命令都带着它一起执行，每一次都触发同样的检查。
5. 重试三次、降速一次之后，libata 放弃，`disable device`，盘没了。

一行状态没清，从一条无害的 IDLE 命令出错开始，13 秒后整块盘被驱动禁用。这个变体在单元测试里也是红的（`case_cmd_abort` 断言“ST 1->0 clears PxCI”）。

## 五、mini-vmm 的执行模型：命令在按门铃的那次 exit 里做完

### 5.1 同步执行

真实的 HBA 收到门铃后，在自己的时钟域里异步地取命令、发 FIS、等设备回应。mini-vmm 没有另起线程，命令在写 PxCI 的那次 MMIO exit 里同步做完：

```text
vCPU 线程：KVM_RUN 返回 KVM_EXIT_MMIO（写 ABAR + 0x138，PxCI）
  └─ 取 io_lock
     └─ ahci_reg_write → port_write(PxCI)
        └─ p->ci |= val; port_run()
           └─ exec_slot()：读命令头、读 CFIS
              └─ exec_ata()：执行命令（读写磁盘镜像也在这里，P4）
                 └─ complete_cmd()：写 FIS、更新 PxTFD/PxIS/PxCI
                    └─ update_irq() → pci_set_irq() → KVM_IRQ_LINE（INTx 置为有效）
  └─ 放 io_lock
  └─ 回到 KVM_RUN
```

回到 guest 时，中断已经挂在 IOAPIC 上了。驱动写 PxCI 的那条 `writel` 一返回，只要中断开着，下一条指令之前 guest 就会被中断打断，进中断处理函数。这就是 2.5 节 trace 里按门铃到读 IS 只隔 21 µs 的原因，也是 P1 第 4.2 节说的“驱动的每一次等待都是第一次读就满足”。

这个模型简单，代价是磁盘 I/O 在 vCPU 线程上执行，并且持着 io_lock：一条耗时的读写会让这个 vCPU 停在 exit 里，其他线程上要拿 io_lock 的设备也要等它。路线图上的 blk-io-uring 里程碑会把 I/O 挪出去，到时候命令真正变成异步的，门铃和完成之间就有了时间差，这里的很多“立即满足”都会变成真正的等待。先做同步版本的价值就在于留下对照。

### 5.2 port_run 只扫一遍快照

```c
static void port_run(struct ahci *s, struct ahci_port *p)
{
    uint32_t pending = p->ci;
    int slot;

    while (pending && (p->cmd & AHCI_PxCMD_ST) && !p->halted) {
        slot = __builtin_ctz(pending);
        pending &= pending - 1;
        exec_slot(s, p, slot);
    }
}
```

更自然的写法是 `while (p->ci) { ... }`：只要 PxCI 还有位就继续执行。这个写法要求每一条执行路径最终都清掉这一槽的 CI 位或者停下端口，哪条路径漏了，循环就永远不结束；而循环跑在 vCPU 线程的 MMIO exit 里，结果是这个 vCPU 卡死、guest 挂起。这不是假设：单元测试里“出错不停端口”的那个错误实现，在早先的循环写法下就让测试挂住了。快照写法保证每次写 PxCI 每一槽最多执行一次，任何遗漏最坏也只是让那条命令看起来没完成，驱动会超时并走 EH，而不会让 VMM 卡住。

槽按从低到高的顺序执行。非 NCQ 的 Linux 驱动一次只发一条命令，顺序无关紧要；NCQ 的多条命令之间本来就没有顺序要求（P5）。

### 5.3 exec_slot 的检查

`exec_slot()` 读命令头和命令 FIS，读之前和读之后各做一组检查：

| 检查 | 不满足时 | 依据 |
|---|---|---|
| 命令头能从 guest RAM 读出 | HBFS，停端口 | 第 6.1.1 节 |
| CFL 在 2..16 之间 | HBFS，停端口 | 第 4.2.2 节：0、1 非法，最大 16 |
| 命令 FIS 能从 CTBA 读出（CTBA 的 bit 6:0 忽略） | HBFS，停端口 | 第 4.2.2 节：CTBA 128 字节对齐 |
| 端口上有盘 | 中止 | 第 10.3.1 节：没有设备时软件不该发命令 |
| FIS 类型是 Register H2D | 中止 | |
| C=1（命令，而不是软件复位） | 中止，警告一次 | Linux 在 COMRESET 后不走软件复位 |

所有对 guest 内存的访问都经 `pci_dma_read()`/`pci_dma_write()`：先检查 PCI COMMAND 的 Bus Master 位（《PCI·实现篇》），再经 `gpa_to_hva()` 检查整个范围在 guest RAM 里（《内存基础》）。驱动给的每一个地址都要过这一关，命令头、命令表、FIS 接收区一样，P4 的 PRDT 也一样。

“端口上没盘”那一行值得一提：真实的 HBA 会一直等设备回应，命令卡在那里直到驱动超时。mini-vmm 直接以中止结束，让 guest 不必等超时。正常的 Linux 驱动不会在链路没建立的端口上发命令，这条路径只防错误的软件。

## 六、验证

**端到端**（`tests/e2e/emu-blk.sh`）：本篇的机制在每一条命令上都被用到，guest 能 IDENTIFY、能读写、能从盘启动（P1、P3、P4 的用例），就说明命令列表、命令表、FIS 接收区的地址解析、PxCI 的置位清除和三级中断都是对的：其中任何一环出错，驱动看到的是命令超时或者 `illegal qc_active transition`，到不了 shell。`/proc/interrupts` 上 ahci 的中断计数大于 0 这一条用例直接确认中断走的是 INTx。

**单元测试**（`tests/unit/ahci_test.c`）在一块假的 guest 内存上直接操作寄存器，覆盖端到端测试难以触发的路径：

- `case_irq`：用 PRCS 作中断源，验证 PxIS & PxIE → IS → GHC.IE → INTx 每一层；PxIS 不清时清 IS，IS 立刻重新置上，线保持有效；PxIE 关着时状态照样记、不产生中断，打开 PxIE 时已挂着的原因立即生效；GHC.IE 只屏蔽线、不屏蔽 IS。
- `case_cmd_abort`：命令中止后 PxTFD = 0x0441、TFES、出错的槽留在 PxCI、CR=0、CCS 指向它；停着的端口不执行新发的槽；按第 6.2.2.1 节恢复后 PxCI、CR、CCS 清零，中断撤销，下一条命令能到达设备；ST=0 时写 PxCI 被忽略；C=0 的软件复位 FIS 被中止。
- `case_cmd_bus_errors`：命令列表在 RAM 外、CFL 非法、命令表在 RAM 外，三种情况都是 HBFS + PxSERR.ERR.E + 槽留在 PxCI + 停端口 + 中断。

每条断言都由一个故意写错的实现证明它能报警：

| 错误实现 | 失败的检查数 |
|---|---|
| PxIS 不粘滞（下一次更新就消失） | 2 |
| TFES 不停端口 | 2 |
| ST 1→0 不清 PxCI（即 4.5 节的反例） | 1 |
| 忽略 GHC.IE | 1 |
| ST=0 时写 PxCI 也执行命令 | 1 |
| FRE=0 时仍把 FIS 写进内存 | 1 |

## 七、限制

- 命令在 vCPU 线程上同步执行，持着 io_lock（第五章）。
- 只实现了软件实际会发的那部分状态机：没有 DMA Setup FIS、没有未知 FIS 的接收（UFIS），也没有端口倍增器（PMP 字段被忽略）和 FIS-based switching。
- 软件复位（C=0 的 FIS、命令头 R 位）不支持，直接中止。
- 没有命令完成合并（CCC）：每条命令完成都立即更新中断。
- OFS、INFS、IFS、HBDS 这几种错误里，只有 OFS 会产生（P4），其余三种是链路和总线层面的错误，模拟的链路不会出现。

## 附录 B：深入阅读

- 《全模拟网卡 P3：中断》：e1000 的 ICR/IMS 是一层中断状态，AHCI 是两层，可以对照着看“粘滞”和“写 1 清”在两种设备上各自怎么用
- 《全模拟网卡 P4：发送》：环形描述符和 AHCI 的命令槽位图是两种不同的“驱动与设备共享工作队列”的做法
- 《中断·原理篇》：INTx 是电平触发的，这一点决定了第三章里“线还是 1 就重新置位”的语义为什么正确
- Linux `drivers/ata/libata-eh.c`：EH 的完整流程，本文只看到了 `ahci_error_handler()` 这一小段
