P1 把 split 模式和 KVM 的接口讲完了，这一篇讲第一颗芯片：IOAPIC。《中断·原理篇》3.2.1 节已经画过重定向表的位图，讲过 IOREGSEL/IOWIN 的间接寻址，这里不再重复，重点放在把它真正实现出来时数据手册里要抠的细节：哪些位能写、level 中断的 Remote IRR 什么时候置位什么时候清、极性位为什么不能用、RTE 怎么翻译成 KVM 认识的 MSI 消息。

| P | 内容 |

模拟的对象是 Intel 82093AA，数据手册是 `ref/82093AA_IOAPIC_290566.pdf`（290566-001），下文的“第 x 节”都指它。选它是因为它是 IOAPIC 的原型，后来的芯片组把 IOAPIC 集成进南桥，寄存器布局沿用它；KVM 内核 IOAPIC 报告的版本号 `0x11` 也是它。

## 一、寄存器：两个窗口，四类间接寄存器

### 1.1 MMIO 只有两个地址

82093AA 在 CPU 地址空间里只占两个寄存器（第 3.0 节表 1）：

| 偏移 | 名字 | 作用 |
|---|---|---|
| `00h` | IOREGSEL | 写入要访问的间接寄存器编号（bit 7:0） |
| `10h` | IOWIN | 读写 IOREGSEL 选中的那个寄存器，32 位 |

所以 mini-vmm 登记的 MMIO 窗口只有 `0x20` 字节（`IOAPIC_MMIO_SIZE`），而不是一整页：页内其余地址本来就没有寄存器，按未注册的 MMIO 处理，会进 exit-stats 的 `unhandled` 一行，这样 guest 乱访问能被看到。

访问宽度数据手册给了两条：IOREGSEL 可以字节写（“a byte memory write ... loads the IOREGSEL Register”），IOWIN 必须按 DWORD 访问（“The IOWIN Register must be accessed as a Dword quantity”）。实现上 IOREGSEL 任何宽度都只取低 8 位；IOWIN 的非 DWORD 访问读回 0、写入丢弃，并打一条带偏移和宽度的 warning。合规的驱动不会这样访问，出现了就是值得看的事。

### 1.2 间接寄存器

| 编号 | 名字 | 复位值 | 说明 |
|---|---|---|---|
| `00h` | IOAPICID | `00h` | bit 27:24，4 位 ID |
| `01h` | IOAPICVER | `00170011h` | bit 23:16 最大表项号 `17h`（24 条），bit 7:0 版本 `11h` |
| `02h` | IOAPICARB | 同 ID | 仲裁 ID，只读 |
| `10h`–`3Fh` | IOREDTBL0–23 | mask=1，其余未定义 | 每条 64 位，占两个编号：`10h+2n` 低 32 位，`11h+2n` 高 32 位 |

两个值得说的地方：

**ID 复位成 0，不是 MADT 里写的值。** mini-vmm 在 MADT 里给 IOAPIC 登记的 ID 是 vCPU 个数（《中断·原理篇》3.2.1 节），寄存器却按数据手册复位成 `00h`。64 位 Linux 只用 MADT 里的 ID，只有多个 IOAPIC 的 MADT ID 冲突时才去读寄存器（`io_apic.c` 的 `io_apic_unique_id`），这里只有一个 IOAPIC，所以照手册来就行。

**版本 `11h` 意味着没有 EOI 寄存器。** 后来的 IOAPIC（版本 `20h` 起）多了一个偏移 `40h` 的 EOI 寄存器，软件可以直接对某个向量做 EOI。Linux 在 `__eoi_ioapic_pin` 里按版本分两条路：

```c
/* arch/x86/kernel/apic/io_apic.c */
static void __eoi_ioapic_pin(int apic, int pin, int vector)
{
    if (mpc_ioapic_ver(apic) >= 0x20) {
        io_apic_eoi(apic, vector);
    } else {
        struct IO_APIC_route_entry entry, entry1;

        entry = entry1 = __ioapic_read_entry(apic, pin);
        /* Mask the entry and change the trigger mode to edge. */
        entry1.masked = true;
        entry1.is_level = false;
        __ioapic_write_entry(apic, pin, entry1);
        /* Restore the previous level triggered entry. */
        __ioapic_write_entry(apic, pin, entry);
    }
}
```

版本 `11h` 的芯片上，软件清 Remote IRR 的唯一办法是把 RTE 写成 edge 再写回 level。这个依赖决定了 3.4 节的一条实现规则。

## 二、RTE 的可写位

重定向表项的布局见《中断·原理篇》3.2.1 节的图。写 RTE 时哪些位真的会变（第 3.2.4 节）：

```c
#define RTE_RW_LO  (0xFFFull | IOAPIC_RTE_INTPOL | IOAPIC_RTE_LEVEL | \
                    IOAPIC_RTE_MASK)
#define RTE_RW_HI  (0xFFull << 56)
```

- 低 32 位：vector（7:0）、投递模式（10:8）、目标模式（11）、极性（13）、触发模式（15）、mask（16）可写。
- Delivery Status（12）和 Remote IRR（14）只读，guest 写什么都不影响它们。Remote IRR 尤其不能让 guest 写：它是芯片和 LAPIC 之间的握手状态，变异体 `ioapic-remote-irr-writable` 就是把它放进可写位，单元测试 `test_rte_bits` 挡下。
- 55:17 保留，读回 0；63:56 目标。

复位值第 3.2.4 节写作“xxx1 xxxx xxxx xxxxh”，只有 mask 位有定义。未定义的位取 0，于是每条 RTE 复位成 `0x10000`：屏蔽、edge、向量 0。

## 三、投递：边沿是事件，电平是状态

### 3.1 边沿

边沿 RTE 只在引脚出现 0→1 时发送一次消息：

```c
if (level && !was && !(rte & IOAPIC_RTE_MASK))
    send(io, pin);
```

屏蔽期间的边沿直接丢弃，不挂起（第 3.2.4 节 bit 16：“masked ... edge-sensitive interrupts signaled on a masked interrupt pin are ignored (i.e., not delivered or held pending)”），所以解除屏蔽时不补发。电平记录 `io->line` 照常更新，否则解除屏蔽后下一个真实的上升沿会被当成“一直是高”而认不出来。

变异体 `ioapic-masked-edge-held`（屏蔽期间的边沿留到解除屏蔽时发）和 `ioapic-edge-every-assert`（引脚已经是高、再断言一次也发）分别被 `test_edge` 的两条断言挡下。mini-vmm 现有的设备都只在电平变化时才调 `irqchip_set_irq`（例如 i8042 的 `set_irq` 先和记下的电平比较），但芯片模型不依赖调用方的这个习惯：边沿的定义就是电平从 0 变 1，重复的 1 不是边沿。

### 3.2 电平

level RTE 的发送条件是一个状态，而不是一个事件：

```c
/* level 表项的发送条件：未屏蔽、引脚被断言、上一次投递已经 EOI */
static void service_level(struct ioapic *io, int pin)
{
    uint64_t rte = io->redtbl[pin];

    if (!ioapic_rte_is_level(rte) || (rte & IOAPIC_RTE_MASK) ||
        (rte & IOAPIC_RTE_REMOTE_IRR) || !(io->line & (1u << pin)))
        return;
    send(io, pin);
}
```

任何可能让这四个条件同时成立的时刻都要重新评估：引脚断言（`ioapic_set_irq`）、解除屏蔽（`write_rte`）、EOI（`ioapic_eoi`）。漏掉任何一个，中断就会卡住，直到下一个无关的事件碰巧触发评估。对应的变异体：

| 变异体 | 漏掉的是 | 挡下它的 |
|---|---|---|
| `ioapic-unmask-no-service` | 解除屏蔽时不评估 | `test_level`：断言中的引脚解除屏蔽后立即投递 |
| `ioapic-eoi-no-resend` | EOI 后引脚仍断言却不重发 | `test_level`：EOI 后第二次投递 |
| `ioapic-eoi-keeps-remote-irr` | EOI 不清 Remote IRR | `test_level` |
| `ioapic-remote-irr-ignored` | 发送时不看 Remote IRR | `test_level`：EOI 前不重复投递 |

### 3.3 Remote IRR 只在“有人收下”时置位

第 3.2.4 节 bit 14：“This bit is set to 1 when local APIC(s) accept the level interrupt sent by the IOAPIC.” 关键词是 accept。

```c
n = io->ops->deliver(io->opaque, addr, data);
if (n <= 0) {
    io->lost[pin]++;
    return;
}
io->delivered[pin]++;
if (ioapic_rte_is_level(rte))
    io->redtbl[pin] |= IOAPIC_RTE_REMOTE_IRR;
```

`deliver` 回调返回 `KVM_SIGNAL_MSI` 的结果，也就是收下这条消息的 LAPIC 个数。返回 0 的情况真实存在：guest 把 RTE 的目标写成一个不存在的 APIC ID，或者目标 LAPIC 被软件禁用。这时要是也置 Remote IRR，没有 LAPIC 会对它 EOI，这根引脚就永远发不出中断了，哪怕 guest 随后把目标改对。变异体 `ioapic-remote-irr-without-accept` 被 `test_level` 里“没人收时 Remote IRR 保持为 0，不经 EOI 也能再次尝试投递”的用例挡下。

`delivered[]` 和 `lost[]` 两组计数是为排查中断丢失准备的：先看是没发出来（两个都不涨）还是发出来没人收（`lost` 涨）。monitor 的 `info irqchip` 会打印 `delivered`。

### 3.4 切成边沿时清 Remote IRR

数据手册对边沿 RTE 的 Remote IRR 只说“undefined”。但 1.2 节已经看到，版本 `11h` 上 Linux 清 Remote IRR 靠的就是“写成 edge 再写回 level”。Linux 在启动时对每根引脚调 `clear_IO_APIC_pin`，发现 Remote IRR 卡着时走这条路，之后还会检查：

```c
    ioapic_mask_entry(apic, pin);
    entry = ioapic_read_entry(apic, pin);
    if (entry.irr)
        pr_err("Unable to reset IRR for apic: %d, pin :%d\n",
               mpc_ioapic_id(apic), pin);
```

真实芯片在切 edge 时会清掉 Remote IRR，软件依赖它。所以 `write_rte` 里：

```c
if (!(rte & IOAPIC_RTE_LEVEL))
    rte &= ~IOAPIC_RTE_REMOTE_IRR;
```

这是一条从软件行为反推出来的硬件规则，数据手册里没有。变异体 `ioapic-edge-switch-keeps-remote-irr` 被 `test_edge_switch` 挡下。

### 3.5 只有 Fixed 和 Lowest Priority 看触发模式

第 3.2.4 节投递模式表里，SMI、NMI、INIT、ExtINT 四种都注明“the trigger mode ... is always edge”，不管 bit 15 怎么编。所以“这条 RTE 是不是 level”不能只看 bit 15：

```c
static inline bool ioapic_rte_is_level(uint64_t rte)
{
    uint32_t dm = IOAPIC_RTE_DELMOD(rte);

    return (rte & IOAPIC_RTE_LEVEL) &&
           (dm == IOAPIC_DELMOD_FIXED || dm == IOAPIC_DELMOD_LOWEST);
}
```

发送、Remote IRR、EOI 和 P1 讲的路由镜像都用这一个函数判断，保证四处对“level”的理解一致。

### 3.6 极性位只记录，不参与判断

RTE 的 bit 13（INTPOL）选引脚高有效还是低有效。直觉是“低有效时把电平取反”，但这样做会出错。

mini-vmm 的设备调 `irqchip_set_irq(gsi, 1)` 时，传的意思是“我在请求中断”（断言），不是“线上是高电压”。线上电压是什么，取决于设备和主板怎么接，而 guest 编 INTPOL 的依据是固件表：ISA 设备在 MADT 里没有 ISO，默认高有效；PCI INTx 由 ACPI `_PRT` 描述，Linux 默认把它编成低有效。也就是说，guest 编的极性描述的是“线上电压和断言的关系”，而 mini-vmm 的连线本来传的就是断言，极性已经在连线两端抵消了。

如果按 INTPOL 取反，PCI 设备拉高（断言）的时候 IOAPIC 会看成撤销，e1000 和 AHCI 的中断全部反过来。KVM 6.6 的内核 IOAPIC 也是同样的处理，`kvm_ioapic_set_irq` 不看 RTE 的极性。

## 四、EOI：按向量，广播

LAPIC 收到 guest 对 level 中断的 EOI 后，向 IOAPIC 广播这个向量（P1 2.3 节，split 模式下以 `KVM_EXIT_IOAPIC_EOI` 的形式出现）。IOAPIC 找出所有向量相同、处于 level、Remote IRR 置位的 RTE，清掉 Remote IRR，然后重新评估：

```c
void ioapic_eoi(struct ioapic *io, uint8_t vector)
{
    for (int pin = 0; pin < IOAPIC_NUM_PINS; pin++) {
        uint64_t rte = io->redtbl[pin];

        if (IOAPIC_RTE_VECTOR(rte) != vector || !ioapic_rte_is_level(rte) ||
            !(rte & IOAPIC_RTE_REMOTE_IRR))
            continue;
        io->redtbl[pin] = rte & ~IOAPIC_RTE_REMOTE_IRR;
        service_level(io, pin);
    }
}
```

“按向量匹配”是 APIC 体系的固有限制：EOI 消息里只有向量，没有引脚号。两根 level 引脚共用一个向量时，一次 EOI 会把两根都清掉。Linux 不会这样分配向量，所以这只是一个要知道的性质。

LAPIC 有一个 EOI-Broadcast Suppression 开关（SPIV bit 12）：打开后 LAPIC 不再广播 level 中断的 EOI，由软件直接写 IOAPIC 的 EOI 寄存器，也就是常说的 directed EOI。split 模式下 guest 有 x2APIC 时，KVM 会在 LAPIC 版本寄存器里宣告支持它（`lapic.c` 的 `APIC_LVR_DIRECTED_EOI`，条件是 IOAPIC 不在内核里），但 Linux（7.4-rc2）从不置 SPIV 的那一位，广播一直开着。而且版本 `11h` 本来就没有 EOI 寄存器，开了也没处写。

## 五、RTE → MSI：给 KVM 的翻译

82093AA 通过 APIC 总线发消息，KVM 只收 MSI 格式。好在 MSI 的地址和数据格式本来就是从 APIC 消息演化来的，字段能一一对应（Intel SDM Vol.3 第 13.11.1、13.11.2 节，《MSI》3.1 节有图）：

| MSI | 来自 RTE |
|---|---|
| 地址 bit 31:20 | 固定 `0xFEE` |
| 地址 bit 19:12 目标 ID | bit 63:56 |
| 地址 bit 2 目标模式 | bit 11 |
| 数据 bit 7:0 向量 | bit 7:0 |
| 数据 bit 10:8 投递模式 | bit 10:8 |
| 数据 bit 14 断言 | 固定 1 |
| 数据 bit 15 触发模式 | `ioapic_rte_is_level(rte)` |

```c
static inline void ioapic_rte_msi(uint64_t rte, uint64_t *addr, uint32_t *data)
{
    *addr = 0xFEE00000ull |
            ((uint64_t)IOAPIC_RTE_DEST(rte) << 12) |
            ((rte & IOAPIC_RTE_DESTMOD) ? (1ull << 2) : 0);
    *data = IOAPIC_RTE_VECTOR(rte) |
            (IOAPIC_RTE_DELMOD(rte) << 8) |
            (ioapic_rte_is_level(rte) ? (1u << 15) : 0) |
            (1u << 14);
}
```

接收端是 KVM 的 `kvm_set_msi_irq`（`arch/x86/kvm/irq_comm.c`），按上表的位置取字段。三个细节：

**目标取满 8 位。** 82093AA 的物理模式只定义了 bit 59:56（APIC ID 0–15），因为当年的 APIC 总线最多 16 个节点。mini-vmm 支持 32 个 vCPU，Linux 会把完整的 8 位 APIC ID 写进 63:56（`io_apic.c` 里的 `entry.destid_0_7`），只取 4 位的话 APIC ID 16 以上的 CPU 收不到 IOAPIC 中断。

**触发模式位决定 guest 的 LAPIC TMR。** KVM 收到消息时，按 bit 15 设置目标 LAPIC 的 TMR（Trigger Mode Register）。Linux 的 `ioapic_ack_level` 在 EOI 之后读 TMR，发现一个 level 中断在 TMR 里显示为 edge，会认为碰上了 82093AA 的一个已知勘误，手动走 `eoi_ioapic_pin` 的“切 edge 再切回”，并累加 `irq_mis_count`（`/proc/interrupts` 的 `MIS` 行）。所以 level 消息必须带 bit 15，否则 guest 每个 level 中断都要多写两次 RTE。

**路由镜像用同一个函数。** P1 讲过 KVM 靠 GSI 路由里的 trigger 位决定哪些向量的 EOI 要退出。路由条目也由 `ioapic_rte_msi` 生成，保证登记的向量、目标和触发模式就是实际投递的那条消息，两边不可能不一致。`test_msi_encoding` 逐字段检查这张表。

## 六、最难或最反直觉的地方

**极性位。** 照着数据手册写，很自然会按 INTPOL 取反。这样 ISA 设备全部正常（高有效），PCI 设备却会反过来，因为 Linux 按 `_PRT` 把它们编成了低有效。该不该取反不取决于 IOAPIC，取决于“设备调用 `set_irq(1)` 表示什么”这个接口约定：它表示断言，不表示电压。

**数据手册没写、软件却依赖的行为。** 切 edge 清 Remote IRR 就是一例。判断依据不是“手册说了什么”，而是“真实的 guest 内核怎么用它”，所以实现的注释里写的是 Linux 的函数名，以后有人想删这两行，能看到删了会坏在哪里。

**`accept` 这个词。** Remote IRR 在消息“被收下”时置位，而不是“发出”时。在真实硬件上两者几乎没有区别，在虚拟机里 guest 可以把目标写成任何值，区别就出来了。

## 八、限制

- 版本 `11h`，没有 EOI 寄存器，也就没有 directed EOI。
- 没有中断重映射。重映射要在 RTE 和 MSI 之间插一层 IOMMU 的翻译表，是 vIOMMU 的事。
- Delivery Status 位恒为 0。真实芯片在消息发出、尚未被 LAPIC 接受时置 1；这里投递是同步的 ioctl，不存在“在途”状态。
- 只有一个 IOAPIC，24 根引脚。
