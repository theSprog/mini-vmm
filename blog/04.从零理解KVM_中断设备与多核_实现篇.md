原理篇讲的是“为什么”。实现篇回答另一个问题：**一个 VMM 在按下“开机”之前，到底要准备好哪些东西？每一样放在哪里、按什么顺序准备、填什么值？**

本篇的主线是 mini-vmm 的真实代码（C 语言，约 4000 行，其中本章新增的中断、设备、固件、SMP 部分约 2000 行）。代码片段都是从仓库里摘出来的，只删掉了日志和部分错误处理。每一节都会回答三个问题：这一步准备了什么；为什么必须在这个位置；漏掉或者做错时症状是什么。

## 九、全景：开机前的十个阶段

### 9.1 阶段总表

mini-vmm 以 Linux 模式启动的命令行是：

```bash
./build/vmm --mode linux --smp 4 --mem 512M --initrd build/initramfs.cpio.gz vmlinux
```

从 `main()` 开始到 guest 执行第一条指令，VMM 依次经过十个阶段。下表是整篇实现篇的地图，后面每一章都是在展开其中的一行或几行：

| 阶段 | 做什么 | 关键 ioctl / 函数 | 顺序约束 | 做错的症状 |
|---|---|---|---|---|
| 0 配置 | 解析命令行：模式、内存、核数、initrd、cmdline | `vmm_config_parse_args()` | 最先 | — |
| 1 探测 | 打开 `/dev/kvm`，检查 API 版本和必需的 capability，探测 CPU 厂商 | `KVM_GET_API_VERSION`、`KVM_CHECK_EXTENSION` | 在创建 VM 之前 | 运行到一半才发现内核缺功能 |
| 2 VM 与内存 | 创建 VM，`mmap` 一块匿名内存作为 guest RAM，注册 memslot | `KVM_CREATE_VM`、`KVM_SET_USER_MEMORY_REGION` | 在往 guest 内存写任何东西之前 | — |
| 3 中断控制器 | 创建内核态 PIC + IOAPIC，创建 PIT | `KVM_CREATE_IRQCHIP`、`KVM_CREATE_PIT2` | **必须在创建 vCPU 之前** | 顺序反了 ioctl 返回 `EINVAL`；漏了 `SPEAKER_DUMMY` TSC 校准失败 |
| 4 vCPU | 创建 N 个 vCPU，映射各自的 `kvm_run`，按 vCPU 改写并设置 CPUID | `KVM_CREATE_VCPU`、`mmap`、`KVM_SET_CPUID2` | 在阶段 3 之后；CPUID 在第一次 `KVM_RUN` 之前 | 拓扑错乱、AP 起不来 |
| 5 设备 | 在 PIO 总线上注册串口、i8042、RTC、ACPI PM1 等设备 | `vmm_register_pio()` | 在 guest 运行之前 | 设备探测超时、启动变慢、无法关机 |
| 6 guest 内存内容 | 载入 vmlinux；写 MP table、ACPI 表、boot_params（含 E820 和 cmdline）；载入 initrd；建页表和 GDT | `elf_load_vmlinux()`、`mptable_setup()`、`acpi_setup()`、`zeropage_setup()`、`boot_build_page_table()` | 在阶段 2 之后；各结构的地址不能重叠 | 内核一启动就 triple fault，或者单核、无中断 |
| 7 BSP 寄存器 | 把 0 号 vCPU 摆成“已在 64 位长模式、RSI 指向 boot_params” | `KVM_SET_SREGS`、`KVM_SET_REGS` | 在阶段 6 之后（要知道入口地址） | `KVM_EXIT_FAIL_ENTRY`、`KVM_EXIT_SHUTDOWN` |
| 8 控制台 | 把 host 终端切到 raw 模式，启动 stdin 读线程 | `console_start()` | 在 vCPU 运行之前 | 键盘输入不进 guest，或 VMM 被 SIGTTOU 挂起 |
| 9 运行 | 安装 SIGUSR1 处理函数，为每个 vCPU 起一个线程进入 `KVM_RUN`，主线程 join | `vm_run()` | 最后 | AP 醒来时 VM 退出；停机时有线程挂住 |

对应到代码，阶段 1 到 4 在 `vm_create()` 里，阶段 5 到 8 在 `main()` 和 `boot_linux()` 里，阶段 9 在 `smp.c` 的 `vm_run()` 里。

### 9.2 为什么顺序很重要

表里有两条硬约束值得先单独拎出来，它们都来自 KVM 的实现，而不是 x86 的规范：

**阶段 3 必须在阶段 4 之前。** 原理篇第 4.5 节讲过：LAPIC 是在 `KVM_CREATE_VCPU` 里创建的，KVM 在那一刻检查“这台 VM 有没有内核态 irqchip”。先创建 vCPU 再创建 irqchip，`KVM_CREATE_IRQCHIP` 直接返回 `-EINVAL`。更隐蔽的是，vCPU 的初始 `mp_state` 也是在创建时决定的（原理篇 8.4 节）：没有 irqchip 时所有 vCPU 都是 RUNNABLE。

**CPUID 必须在第一次 `KVM_RUN` 之前设置。** KVM 允许在 vCPU 运行之后再改 CPUID，但 guest 内核启动的第一件事就是执行 `CPUID` 检查长模式、检查 APIC、读拓扑，拿到的信息会被缓存下来，之后再改就晚了。从 5.16 开始，KVM 甚至会拒绝在 vCPU 运行过之后修改 CPUID（后来的版本放宽为“只允许设置完全相同的内容”）。

其余的顺序约束来自数据依赖：往 guest 内存写东西要先有内存（阶段 2 → 6）；设置 BSP 的 `RIP` 要先知道内核入口在哪（阶段 6 → 7）；启动 vCPU 线程之前一切都要准备好（→ 9）。

### 9.3 guest 物理内存布局

阶段 6 往 guest 内存里写了很多东西。它们各自放在哪、为什么放在那里，是 VMM 最容易出错的地方之一：两个结构重叠了，后写的会覆盖先写的，症状千奇百怪。下图是 512MB guest 的完整布局：

```
   GPA                    内容                         谁决定的地址
   ─────────────────────────────────────────────────────────────────────────────
   0x0000_0000 ┌──────────────────────────┐
               │ （空闲，实模式 IVT 位置）   │
   0x0000_1000 ├──────────────────────────┤
               │ GDT（4 项，32 字节）       │  VMM 自选，要避开下面所有结构
   0x0000_2000 ├──────────────────────────┤
               │ PML4                     │  VMM 自选；CR3 指向这里
   0x0000_3000 ├──────────────────────────┤
               │ PDPT                     │
   0x0000_4000 ├──────────────────────────┤
               │ PD（512 项 × 2MB = 1GB）  │
   0x0000_5000 ├──────────────────────────┤
               │ （空闲）                  │
   0x0000_7000 ├──────────────────────────┤
               │ boot_params（4KB）        │  VMM 自选；RSI 指向这里
   0x0000_8000 ├──────────────────────────┤
               │ （空闲，Linux 可能在低端    │  Linux 自己在低端 RAM 里挑地方
               │   内存里放 AP trampoline） │  放 trampoline
   0x0002_0000 ├──────────────────────────┤
               │ 内核命令行（≤ 4KB）         │  VMM 自选；boot_params 里记录
   0x0002_1000 ├──────────────────────────┤
               │ （空闲，E820 报告为 RAM）   │
   0x0009_FC00 ├──────────────────────────┤  ← E820：RAM 到此为止
               │ MP table（≤ 1KB）         │  MPS 规范：Linux 扫描 639K–640K
   0x000A_0000 ├──────────────────────────┤  ← E820：保留区
               │ （VGA 窗口，未使用）        │
   0x000E_0000 ├──────────────────────────┤
               │ACPI：RSDP/XSDT/FADT/DSDT/│  ACPI 规范：RSDP 在 0xE0000–0xFFFFF
               │       MADT               │
   0x0010_0000 ├──────────────────────────┤  ← 1MB，E820：RAM
               │ （空闲）                  │
   0x0100_0000 ├──────────────────────────┤  ← 16MB
               │ vmlinux 各 PT_LOAD 段     │  vmlinux 的 ELF 头（p_paddr）决定
   0x02A3_0000 ├──────────────────────────┤  ← 内核镜像结束（含 bss）
               │ （空闲，内核运行时的内存）   │
   0x1FE0_0000 ├──────────────────────────┤
               │ initrd（约 1MB）          │  VMM 自选：RAM 顶端向下 2MB 对齐
   0x2000_0000 └──────────────────────────┘  ← 512MB，RAM 结束
                            ...
   0xFEC0_0000   IOAPIC 寄存器                 KVM 内核态模拟，不在任何 memslot 里
   0xFEE0_0000   LAPIC 寄存器                  KVM 内核态模拟，不在任何 memslot 里
```

这张图里的地址分三类：

- **规范规定的**：MP table 要在 639K–640K（或另外两个扫描区），RSDP 要在 `0xE0000`–`0xFFFFF`，LAPIC 和 IOAPIC 的默认地址。放错了 guest 找不到。
- **镜像决定的**：vmlinux 的加载地址由它自己的 ELF 程序头决定，VMM 只能照办。
- **VMM 自选的**：GDT、页表、boot_params、cmdline、initrd。选择的原则是互不重叠、都在 RAM 里、都在页表的恒等映射范围内（启动协议要求）、并且避开内核镜像。

mini-vmm 在代码里用几个宏固定了这些地址：

```c
/* include/boot/gdt_pgtable.h */
#define BOOT_GDT_GPA     0x1000ULL
#define BOOT_PML4_GPA    0x2000ULL
#define BOOT_PDPT_GPA    0x3000ULL
#define BOOT_PD_GPA      0x4000ULL

/* include/boot/zeropage.h */
#define ZP_BOOT_PARAMS_GPA  0x7000ULL
#define ZP_CMDLINE_GPA      0x20000ULL

/* include/boot/mptable.h */
#define MPTABLE_GPA        0x9fc00ULL

/* include/boot/acpi.h */
#define ACPI_TABLES_GPA   0xE0000ULL
```

有一个细节要注意：`0x9FC00` 到 `0x100000` 这一段在 E820 里报告为“保留”，但它**仍然在 memslot 覆盖的 RAM 里**。这两件事并不矛盾：memslot 决定“这段 GPA 背后有没有真实内存”（MP table 和 ACPI 表必须写在真实内存里，guest 才读得到），E820 决定“guest 内核能不能把这段内存拿去分配”（不能，否则固件表会被覆盖）。

## 十、阶段 1–3：探测、内存与中断通路

### 10.1 阶段 1：开工前先确认环境

第一篇的最小 VMM 只检查了 API 版本和 `KVM_CAP_USER_MEMORY`。要跑一个多核 Linux，需要确认的东西多了几项。mini-vmm 的 `vm_create()` 在创建 VM 之前依次检查：

| 检查项 | 为什么需要 | 缺失时 |
|---|---|---|
| `KVM_GET_API_VERSION == 12` | ABI 基线，从 2007 年起就没变过 | 环境根本不对，立刻退出 |
| `KVM_CAP_USER_MEMORY` | 用 `KVM_SET_USER_MEMORY_REGION` 注册内存 | 立刻退出 |
| `KVM_GET_VCPU_MMAP_SIZE ≥ sizeof(struct kvm_run)` | 编译时的 `linux/kvm.h` 可能比运行中的内核新 | 立刻退出，并提示头文件版本问题 |
| `KVM_CAP_MAX_VCPUS` | 请求的 vCPU 数不能超过 KVM 的上限 | 报告 `N vCPUs requested, KVM allows at most M` |
| `KVM_CAP_IMMEDIATE_EXIT` | 多核停机协议依赖它（第十三章） | 报告需要 4.11 以上内核 |
| `KVM_CAP_IRQCHIP` | 内核态中断控制器 | 在阶段 3 报告 |
| CPU 厂商与 SVM/NPT 特性 | 选择 AMD 或 Intel 后端；没有 NPT 时警告 | 未知厂商时退出 |

原则很简单：**所有依赖的 capability 都在开工前检查完。** 运行到一半才发现某个 ioctl 不被支持，现场会很难收拾，报错也难以理解。另外 `KVM_CHECK_EXTENSION` 必须在运行时调用，不能只看头文件里有没有定义某个 `KVM_CAP_*` 宏：发行版的 `linux-libc-dev` 头文件常常比正在运行的内核新。

真实日志里阶段 1 的输出：

```
[INFO] KVM API v12, kvm_run size 12288 bytes, max vCPUs 1024
[INFO] CPU vendor: HygonGenuine (Hygon)
[INFO] SVM rev=1, ASIDs=32768
[INFO] SVM features: npt lbrv svm_lock nrip_save tsc_scale vmcb_clean flushbyasid decodeassists pausefilter avic v_vmsave_vmload vgif
```

`kvm_run size 12288` 是三页：第 0 页是 `struct kvm_run`，第 1 页是 PIO 数据页，第 2 页是 coalesced MMIO 环。这再次说明 mmap 的长度必须用 `KVM_GET_VCPU_MMAP_SIZE` 的返回值。

### 10.2 阶段 2：内存

内存部分与第一篇相比没有本质变化：`mmap` 一块匿名内存，用 `KVM_SET_USER_MEMORY_REGION` 注册成 0 号 memslot，GPA 从 0 开始。有两处值得一提的改进：

```c
    p = mmap(NULL, ram_size, PROT_READ | PROT_WRITE,
             MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);
    ...
    /* 尽量让 host 用 2MiB 透明大页承载 guest RAM，减少 NPT 的层级和
     * TLB miss。失败不致命（比如 THP 被关掉了）。 */
    if (madvise(p, ram_size, MADV_HUGEPAGE) < 0)
        ...
```

一是 `MADV_HUGEPAGE`：让 host 尽量用 2MB 透明大页来承载 guest 内存，减少 NPT 的页表层级和 TLB 缺失。

二是内存大小的上限：因为只有一个从 0 开始的 memslot，guest 内存超过 3GB 就会压到 `0xC0000000` 以上的 MMIO 区域，IOAPIC 和 LAPIC 的地址会落进 RAM 里。

mini-vmm 目前直接拒绝超过 3GB 的配置，在 `zeropage_setup()` 里报 `guest RAM above 3GiB is not supported yet (no MMIO hole)`。

**IOAPIC（`0xFEC00000`）和 LAPIC（`0xFEE00000`）不需要任何 memslot。** guest 访问这两个地址时，NPT 里没有映射，产生 `#NPF`，KVM 发现这个 GPA 不属于任何 memslot，就当作 MMIO 处理：先在内核的 MMIO 总线上找有没有设备认领，内核态的 IOAPIC 和 LAPIC 就挂在那条总线上，于是访问在内核里就被处理掉了，根本不会回到用户态。

### 10.3 阶段 3：创建中断控制器和 PIT

阶段 3 只有两个 ioctl，全部代码在 `src/devices/irqchip.c` 里：

```c
int irqchip_create(struct vmm_vm *vm)
{
    struct kvm_pit_config pit;

    if (!kvm_check_extension(vm->kvm_fd, KVM_CAP_IRQCHIP)) {
        vmm_err("kernel does not support KVM_CAP_IRQCHIP");
        return VMM_ERR_UNSUPPORTED;
    }

    /* 一次性创建 2 片 8259 PIC + 1 个 IOAPIC，并让之后创建的每个
     * vCPU 都带一个内核态 LAPIC。GSI 0-15 默认同时路由到 PIC 和
     * IOAPIC，guest 用哪个都行。 */
    if (ioctl(vm->vm_fd, KVM_CREATE_IRQCHIP, 0) < 0) { ... }

    memset(&pit, 0, sizeof(pit));
    pit.flags = KVM_PIT_SPEAKER_DUMMY;
    if (ioctl(vm->vm_fd, KVM_CREATE_PIT2, &pit) < 0) { ... }

    vm->has_irqchip = true;
    return VMM_OK;
}
```

它在 `vm_create()` 里的位置是关键：

```c
    /* 6. 分配并注册 guest 物理内存 */
    r = mem_init(vm, cfg->ram_size);
    ...
    /* 7. Linux 需要中断控制器和 PIT，且必须在创建 vCPU 之前建好：
     *    KVM 在 KVM_CREATE_VCPU 时才决定是否给 vCPU 挂内核态 LAPIC。 */
    if (cfg->mode == VMM_BOOT_LINUX) {
        r = irqchip_create(vm);
        ...
    }

    /* 8. 创建 vCPU */
    for (i = 0; i < cfg->nr_vcpus; i++) {
        r = vm_create_vcpu(vm, i);
        ...
    }
```



#### 10.3.1 这两个 ioctl 之后，KVM 里多了什么

| 组件 | 位置 | 由谁访问 | VMM 还要做什么 |
|---|---|---|---|
| 8259A 主片 | PIO `0x20`–`0x21` | guest 早期启动、virtual wire 阶段 | 无 |
| 8259A 从片 | PIO `0xA0`–`0xA1` | 同上 | 无 |
| ELCR（边沿/电平控制） | PIO `0x4D0`–`0x4D1` | guest 设置 ISA 线的触发方式 | 无 |
| IOAPIC | MMIO `0xFEC00000` | guest 在 symmetric I/O 阶段 | 在 MP table / MADT 里如实描述它 |
| LAPIC ×N | MMIO `0xFEE00000`（每个 vCPU 各自的） | guest 全程 | 在 MP table / MADT 里如实描述每一个 |
| PIT | PIO `0x40`–`0x43` | guest 校准 TSC、早期时钟 | 无 |
| 端口 B | PIO `0x61` | guest 校准 TSC | 无（前提是带了 `SPEAKER_DUMMY`） |
| GSI 路由表 | 内核 | `KVM_IRQ_LINE` | 固件表必须与默认恒等映射一致 |

右边一列说明了一件事：**中断控制器交给 KVM 之后，VMM 的工作并没有消失，而是转移到了“描述”上**。KVM 模拟出来的 IOAPIC 在哪、有几个 LAPIC、它们的 ID 是多少、GSI 怎么路由，VMM 必须在固件表里一字不差地告诉 guest。



### 10.4 复盘：为什么要设置 pit.flags 为 `KVM_PIT_SPEAKER_DUMMY`

原理篇第五章从原理上讲了端口 `0x61` 为什么重要。这里复盘一下它在实际开发中是怎么暴露出来的，因为这类“名字看起来无关紧要”的 flag 在 KVM 里并不少见。

**症状。** 最初 `irqchip_create()` 调用 `KVM_CREATE_PIT2` 时，`flags` 是 0。guest 启动时**间歇性**卡住：日志停在 `skipped IO-APIC setup` 之后，时间戳停在 `0.001000` 不再前进，VMM 的 CPU 占用是 100%。有时候又能正常启动。

**证据。** 打开 VMM 的未处理端口调试日志，就能看到对端口 `0x61` 的读写落到了用户态，VMM 按浮空总线约定处理：写丢弃、读返回 `0xFF`。

**分析。** 读 guest 的 `quick_pit_calibrate()`：它先往 `0x61` 写“GATE=1、喇叭关”，再编程 PIT 通道 2 开始倒数，然后读通道 2 的计数器，观察它随 TSC 的变化。写 `0x61` 被 VMM 丢弃，KVM 模拟的通道 2 的 GATE 一直是 0，计数器根本不走。快速校准失败后，Linux 会退到 `pit_calibrate_tsc()` 等其他校准方法，这些方法读 `0x61` 的第 5 位（通道 2 的 OUT）来判断计数是否结束，而 VMM 返回的 `0xFF` 让 OUT 永远是 1。校准得到的是一个没有意义的值，后续依赖时间的等待循环于是表现得时好时坏。

**根因。** 读 host 的 `kvm_create_pit()`（`arch/x86/kvm/i8254.c`）：

```c
    if (flags & KVM_PIT_SPEAKER_DUMMY) {
        kvm_iodevice_init(&pit->speaker_dev, &speaker_dev_ops);
        ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS,
                                      KVM_SPEAKER_BASE_ADDRESS, 4,
                                      &pit->speaker_dev);
        ...
    }
```

只有带了这个 flag，KVM 才会在内核的 PIO 总线上为端口 `0x61` 注册处理函数，把 GATE 位转发给通道 2。所谓的“dummy speaker”指的是“没有真的喇叭，但端口的行为是真的”。

**修复。** 一行：`pit.flags = KVM_PIT_SPEAKER_DUMMY;`。QEMU、Firecracker、kvmtool 在创建 PIT 时都带了这个 flag。

这个坑的教训是：**用 KVM 的内核态设备时，要把每个 flag 的实现读一遍，不能只看名字。**

### 10.5 设备怎么“拉线”

阶段 3 建好了中断控制器，用户态的设备通过一个很薄的封装来拉线：

```c
int irqchip_set_irq(struct vmm_vm *vm, int gsi, int level)
{
    struct kvm_irq_level il;

    if (!vm->has_irqchip || gsi < 0)
        return VMM_OK;

    il.irq   = (uint32_t)gsi;
    il.level = level;
    if (ioctl(vm->vm_fd, KVM_IRQ_LINE, &il) < 0) { ... }
    return VMM_OK;
}
```

`il.irq` 是 GSI 号。按 KVM 的默认路由，GSI 4 就是串口的 IRQ4，同时连着 PIC 主片的第 4 根线和 IOAPIC 的第 4 根引脚。

真正需要花心思的是**什么时候调用它**。原理篇 4.6 节从 KVM 源码里看到：边沿触发的线上，连续两次 `level=1` 的第二次是空操作。所以设备模拟必须自己维护“中断线当前电平”，只在电平变化时调用 `KVM_IRQ_LINE`，而且每个新事件都要先让线回到 0。

串口的做法是在每次寄存器访问之后重新计算中断条件（`update_irq()`，第十一章展开），并与上次的电平比较：

```c
    level = !(iir & UART_IIR_NO_INT) && (s->mcr & UART_MCR_OUT2) && !(s->mcr & UART_MCR_LOOP);

    if (level != s->irq_level) {
        s->irq_level = level;
        if (s->irq_set)
            s->irq_set(s->irq_opaque, s->irq, level);
    }
```

驱动每读走一个字节，如果 FIFO 空了，条件变假，线被拉低；console 线程放入下一个字节，条件变真，线被拉高，形成新的上升沿。

i8042 的做法更显式。它的输出缓冲里每个字节都需要一次独立的中断（atkbd 驱动每次中断只读一个字节），所以每次从缓冲区取走一个字节时，先无条件拉低，再根据剩余内容决定是否拉高：

```c
static uint8_t obuf_pop(void)
{
    ...
    g_kbc.head = (g_kbc.head + 1) % OBUF_SIZE;
    g_kbc.count--;
    set_irq(0);        /* 先拉低：制造下降沿 */
    update_irq();      /* 缓冲里还有键盘字节就再拉高：新的上升沿 */
    return v;
}
```

这两段代码是原理篇 2.5 节“边沿触发要求每个事件一个新的上升沿”在工程上的两种写法。

### 10.6 路由与固件表：恒等映射

原理篇第三章和第四章两次提到过这个陷阱，这里给出 mini-vmm 的最终做法：**固件表里的 ISA 中断映射一律写成恒等，与 KVM 的默认路由保持一致，不写任何中断源覆盖。**

MP table 部分（`src/boot/mptable.c`），16 个 ISA IRQ 各有一条 I/O 中断分配条目，IRQ i 接 IOAPIC 引脚 i：

```c
    for (i = 0; i < 16; i++) {
        struct mpc_intsrc *s = (struct mpc_intsrc *)p;

        s->type      = MP_INTSRC;
        s->irqtype   = MP_IRQTYPE_INT;
        s->srcbus    = 0;              /* 0 号总线：ISA */
        s->srcbusirq = (uint8_t)i;     /* ISA IRQ i */
        s->dstapic   = ioapic_id;
        s->dstirq    = (uint8_t)i;     /* → IOAPIC 引脚 i */
        ...
    }
```

`irqflag` 字段保持 0，意思是“极性和触发方式遵循总线的默认约定”，ISA 总线的默认约定是边沿触发、高电平有效，与 KVM IOAPIC 的行为一致。

ACPI MADT 部分（`src/boot/acpi.c`）更简单：什么都不写。

```c
    /* ISA IRQ 0-15 与 GSI 恒等映射，不需要 Interrupt Source Override：
     * Linux 在没有 override 时默认就是恒等，而 KVM 的默认路由也是恒等。 */
```

验证方式是 guest 里的 `/proc/interrupts`。真实日志中每个 ISA 中断都挂在 `IO-APIC` 上，引脚号与 IRQ 号相同，触发方式是 `edge`：

```
           CPU0       CPU1       CPU2       CPU3
  0:        304          0          0          0   IO-APIC   0-edge      timer
  1:          0          0          9          0   IO-APIC   1-edge      i8042
  4:         28          0          0          0   IO-APIC   4-edge      ttyS0
  8:          0          0          0          0   IO-APIC   8-edge      rtc0
  9:          0          0          0          0   IO-APIC   9-fasteoi   acpi
```

几点值得注意：`0-edge timer` 说明 PIT 的时钟中断走的是 IOAPIC 第 0 根引脚，恒等映射生效；`timer` 只在 CPU0 上有计数（304 次），因为 Linux 在 LAPIC 定时器接管之后就不再使用 PIT 了；`i8042` 的 9 次中断发生在 CPU2 上，这是 IOAPIC 把中断路由到了别的 CPU，symmetric I/O 模式在工作；`acpi` 的 SCI 是 `fasteoi`，即电平触发，这是 ACPI 规范对 SCI 的要求（Linux 默认按电平、低有效配置 SCI），mini-vmm 从不拉这根线，所以计数为 0。

启动日志里还有一行可以验证时钟中断的路由：

```
[    0.133006] ..TIMER: vector=0x30 apic1=0 pin1=0 apic2=-1 pin2=-1
```

意思是：时钟中断使用向量 `0x30`，接在第 0 个 IOAPIC 的第 0 根引脚上，没有备用路径。如果固件表错误地声明了“IRQ0 → GSI 2”，这里会显示 `pin1=2`，然后 `check_timer()` 发现时钟中断不来，开始尝试各种退路。

### 10.7 小结：阶段 1–3 的准备清单

- 开工前检查全部依赖：API 版本、`USER_MEMORY`、mmap 大小、`MAX_VCPUS`、`IMMEDIATE_EXIT`、`IRQCHIP`、CPU 厂商和 NPT。
- 一个从 GPA 0 开始的 memslot 覆盖全部 RAM，建议 `MADV_HUGEPAGE`；IOAPIC 和 LAPIC 的地址不要落进任何 memslot（因此 RAM 暂时不超过 3GB）。
- `KVM_CREATE_IRQCHIP` 和 `KVM_CREATE_PIT2` 必须在创建 vCPU 之前，PIT 必须带 `KVM_PIT_SPEAKER_DUMMY`。
- 设备用 `KVM_IRQ_LINE` 拉 GSI，自己维护电平，只在变化时调用；边沿触发的线每个事件要一个新的上升沿。
- 固件表写恒等映射，不写中断源覆盖；用 `/proc/interrupts` 和 `..TIMER:` 那行日志验证。

## 十一、阶段 5 与阶段 8：设备模型与控制台

### 11.1 设备总线：一张表加一个分发函数

阶段 5 的基础设施是一条“总线”。mini-vmm 用同一个结构体描述 PIO 设备和 MMIO 设备：

```c
struct vmm_io_dev {
    const char *name;
    uint64_t    base;
    uint64_t    len;
    void       *opaque;            /* 指向具体设备实例 */

    int (*read)(void *opaque, uint64_t offset, uint32_t size, void *data);
    int (*write)(void *opaque, uint64_t offset, uint32_t size,
                 const void *data);
};
```

回调里传的是**相对于 base 的偏移**，而不是绝对地址。这样设备实现不需要知道自己被挂在哪里，同一种设备挂多个实例时（比如以后的多个 virtio-mmio 设备）可以复用同一份代码。

注册时做重叠检查，两个设备的地址区间相交就拒绝，并报出冲突双方的名字。地址区间要按设备真实占用的端口来注册：比如 i8042 不能图省事注册成 `[0x60, 0x65)` 一整段，因为中间的 `0x61` 属于 PIT 的门控（由 KVM 在内核里处理），所以要注册成 `0x60` 和 `0x64` 两个单端口设备。

分发逻辑在 `vcpu_handle_exit()` 里。PIO 路径的核心是 `handle_io()`：

```c
static int handle_io(struct vmm_vcpu *vcpu)
{
    struct kvm_run *run = vcpu->run;
    const struct vmm_io_dev *dev;
    uint8_t *data;
    uint32_t i;

    /* 数据缓冲区在 kvm_run 页内，偏移由内核填在 io.data_offset。 */
    data = (uint8_t *)run + run->io.data_offset;
    dev  = vmm_lookup_pio(vm, run->io.port);

    if (!dev) {
        /* 未注册端口：写丢弃，读返回全 1（真机上空闲总线的行为）。
         * 不能直接报错退出——Linux 内核启动时会盲探一堆遗留端口。 */
        if (run->io.direction == KVM_EXIT_IO_IN)
            memset(data, 0xFF, (size_t)run->io.size * run->io.count);
        return VMM_OK;
    }

    /* count > 1 出现在 ins/outs 串操作指令上。逐次调设备回调，
     * 每次前进 size 字节。 */
    for (i = 0; i < run->io.count; i++) {
        uint8_t *p = data + (size_t)i * run->io.size;
        uint64_t off = run->io.port - dev->base;
        ...  /* 按方向调 dev->write 或 dev->read */
    }
    return VMM_OK;
}
```

这里有三个必须做对的细节：

1. **数据地址是 `run + io.data_offset`**，不能假设它紧跟在 `struct kvm_run` 后面。
2. **`io.count` 可能大于 1**。guest 用 `rep outsb` 这类串操作指令时，KVM 会把多次访问合并成一次退出，数据连续放在数据页里。只处理第一个字节会丢数据。
3. **未注册的端口读返回 `0xFF`、写丢弃**，不能报错退出（原理篇 6.3 节）。Linux 启动过程中会探测不少没有设备的端口，打开 VMM 的调试日志就能看到它们。

### 11.2 阶段 5 要注册哪些设备

`main()` 和 `boot_linux()` 在阶段 5 注册的全部设备：

| 设备 | 端口 | 中断 | 注册函数 | 最少要做到什么 |
|---|---|---|---|---|
| 16550A 串口 | `0x3F8`–`0x3FF` | GSI 4 | `serial8250_attach()` | 通过 autoconfig 被认成 16550A；THR 输出到 stdout；RX FIFO 接 console 线程；中断语义正确 |
| i8042 | `0x60`、`0x64` | GSI 1 | `i8042_attach()` | 控制器命令全部应答；AUX 口当场判定不存在；键盘命令应答走 IRQ1；`0xFE` 等复位命令触发 VMM 退出 |
| CMOS RTC | `0x70`–`0x71` | 不产生 | `rtc_attach()` | UIP=0；BCD 时间取自 host；寄存器 C/D 语义正确 |
| ACPI PM1a | `0x600`–`0x605` | 不产生 | `acpi_pm_attach()` | `PM1_CNT` 读回 `SCI_EN=1`；写 `SLP_TYP=5 + SLP_EN` 触发 VMM 退出 |
| 调试端口 | `0x10` | — | 直接注册 | 第一篇遗留，Linux 不用 |
| 退出端口 | `0xF4` | — | 直接注册 | 第一篇遗留，写入值作为退出码 |

注意串口是在 `main()` 里无条件注册的（所有模式都要），其余三个只在 Linux 模式下由 `boot_linux()` 注册。设备的 `irq_set` 回调也是在 `boot_linux()` 里才接到 `irqchip_irq_cb` 上，裸机模式下串口的中断回调为空，纯粹轮询输出。

下面逐个看它们的实现要点。原理篇第六章已经讲了每个设备的寄存器语义，这里只讲“做成什么样才够”，以及实现时容易漏掉的地方。

### 11.3 串口

串口的状态是一个结构体，只保留 Linux 驱动真正会碰到的寄存器：

```c
struct serial8250 {
    uint8_t ier, iir, fcr, lcr, mcr, lsr, msr, scr, dll, dlm;

    uint8_t  rx_buf[SERIAL_RX_BUF];     /* 256 字节接收 FIFO */
    uint32_t rx_head, rx_tail;

    bool thri_pending;                  /* THRE 中断挂起 */
    int  irq_level;                     /* 中断线当前电平 */

    int out_fd;                         /* guest 输出去哪 */
    void (*irq_set)(void *opaque, int irq, int level);
    void *irq_opaque;
    int   irq;

    pthread_mutex_t lock;               /* vCPU 线程与 console 线程共用 */
};
```

整个设备的中断逻辑集中在一个函数里：每次寄存器读写、每次 console 线程放入字节之后都调用它，重新计算 IIR 和中断线电平：

```c
static void update_irq(struct serial8250 *s)
{
    uint8_t iir = UART_IIR_NO_INT;
    int level;

    if ((s->ier & UART_IER_RDI) && !rx_empty(s))
        iir = UART_IIR_RDI;                 /* 优先级高：有数据可读 */
    else if ((s->ier & UART_IER_THRI) && s->thri_pending)
        iir = UART_IIR_THRI;                /* 优先级低：发送保持寄存器空 */

    if (s->fcr & UART_FCR_ENABLE)
        iir |= UART_IIR_FIFO;               /* 高两位 11：16550A */
    s->iir = iir;

    /* PC 上 COM 口的中断要经过 MCR.OUT2 这个门控才会到 PIC。
     * 回环模式下中断不往外送。 */
    level = !(iir & UART_IIR_NO_INT) && (s->mcr & UART_MCR_OUT2)
            && !(s->mcr & UART_MCR_LOOP);

    if (level != s->irq_level) {
        s->irq_level = level;
        if (s->irq_set)
            s->irq_set(s->irq_opaque, s->irq, level);
    }
}
```

“每次都从状态重算”的写法比“在各处分别设置和清除中断”稳妥得多：中断条件只有一个定义，不会出现某条路径忘了清中断的情况。

几个必须模拟到位的语义，每一个都对应原理篇 6.4 节的一段，也都对应一个实际出现过或者很容易出现的故障：

| 语义 | 实现位置 | 漏掉的症状 |
|---|---|---|
| DLAB=1 时偏移 0/1 是除数寄存器 | `serial_read/write` 的 `UART_RX`、`UART_IER` 分支 | 设置波特率时输出一个乱码字符 |
| 打开 IER.THRI 时 THR 为空就立刻产生中断 | 写 IER 时 `if (!(s->ier & UART_IER_THRI) && (v & UART_IER_THRI)) s->thri_pending = true;` | printk 在控制台注册后输出停止 |
| 读 IIR 读到 THRI 即应答 | 读 IIR 分支清 `thri_pending` | 中断风暴 |
| 回环：MCR 的 RTS/DTR/OUT1/OUT2 映射到 MSR 的 CTS/DSR/RI/DCD | `msr_value()` | autoconfig 判定端口不存在，没有 ttyS0 |
| 回环：写 THR 回到自己的 RX FIFO，不输出 | `tx_byte()` | 启动时终端上出现探测用的垃圾字符 |
| IER 只保留低 4 位 | 写 IER 时 `v & 0x0f` | autoconfig 的 IER 测试失败 |
| 写 FCR 的“清 RX FIFO”位 | 写 FCR 分支 | 残留的输入字符 |
| 边沿触发：电平变化才调 `KVM_IRQ_LINE` | `update_irq()` | 后续输入字符的中断丢失，shell 收不到键盘输入 |

LSR 永远报告 THRE 和 TEMT（发送器空闲），因为“发送”就是一次 `write(out_fd)`，瞬间完成。输出没有做任何缓冲，每个字节一次 `write` 系统调用。对于日志量不大的启动过程这完全够用；以后如果需要高吞吐的控制台，应该换成 virtio-console。

### 11.4 RTC

RTC 的全部实现不到 120 行。关键是三件事：

```c
#define RTC_REG_A_DEFAULT 0x26   /* 32.768kHz 时基，1024Hz 周期，UIP=0 */
#define RTC_REG_B_24H     0x02   /* 24 小时制，BCD 编码，无中断 */
#define RTC_REG_D_VRT     0x80   /* 电池正常，CMOS 内容有效 */
```

寄存器 A 的 UIP 位永远为 0，guest 不用等；寄存器 B 声明 24 小时制和 BCD 编码（第 2 位 DM 为 0 表示 BCD），与读时间时的返回格式一致；寄存器 D 的 VRT 位为 1，否则 Linux 认为 CMOS 电池没电、时间不可信。

读时间寄存器时，现取 host 的 UTC 时间转成 BCD：

```c
    now = time(NULL);
    gmtime_r(&now, &tm);
    switch (reg) {
    case RTC_SECONDS: return bin2bcd(tm.tm_sec);
    case RTC_MINUTES: return bin2bcd(tm.tm_min);
    case RTC_HOURS:   return bin2bcd(tm.tm_hour);
    case RTC_WDAY:    return bin2bcd(tm.tm_wday + 1);   /* RTC 里星期日是 1 */
    case RTC_MDAY:    return bin2bcd(tm.tm_mday);
    case RTC_MONTH:   return bin2bcd(tm.tm_mon + 1);    /* struct tm 的月份从 0 开始 */
    case RTC_YEAR:    return bin2bcd(tm.tm_year % 100);
    default:          return bin2bcd((tm.tm_year + 1900) / 100);  /* 世纪，寄存器 0x32 */
    }
```

两处 `+1` 是 C 库的 `struct tm` 与 RTC 约定之间的差异，都是容易写错的地方。世纪寄存器的编号 `0x32` 同时写在 ACPI FADT 的 `century` 字段里，两边要一致。

写端口 `0x70` 时要屏蔽第 7 位（NMI 屏蔽位，与寄存器选择无关），否则 guest 用 `0x80 | reg` 选择寄存器时会越界。

这个设备不产生中断（没有实现 IRQ8 的周期中断和闹钟中断），也不维护内部时钟，guest 写时间寄存器只是改了 CMOS 里的字节，下次读时间仍然返回 host 时间。对启动来说这就够了。

### 11.5 i8042

i8042 是这几个设备里状态最复杂的。它的核心是一个带“来源标记”的输出缓冲队列：

```c
struct obuf_ent {
    uint8_t val;
    bool    aux;       /* 置 STR_AUXDATA：这个字节“来自鼠标” */
    bool    from_kbd;  /* 键盘设备发出的字节，需要打 IRQ 1 */
};
```

每个字节都记住自己是谁发出的，因为三类字节的行为不同：控制器对命令的应答（不打中断，驱动轮询读）、键盘设备的应答（要打 IRQ1）、“来自鼠标”的字节（要置 AUXDATA 位）。

阶段 5 要做对的几件事：

**控制器命令逐条应答。** 读 CTR（`0x20`）返回配置字节；自检（`0xAA`）返回 `0x55`；键盘口测试（`0xAB`）返回 `0x00`；读输出端口（`0xD0`）返回输出端口值。有参数的命令（`0x60` 写 CTR、`0xD1` 写输出端口、`0xD2`/`0xD3`/`0xD4`）记下待处理命令，下一次写 `0x60` 时作为参数处理。

**新命令冲掉旧应答。** 这是一个调试时才发现的细节：

```c
static int kbc_command(uint8_t cmd)
{
    /* 新命令会冲掉还没被读走的旧应答。否则一次失败的 AUX_LOOP 残留
     * 的字节会被下一条 AUX_TEST 当成自己的应答读走。 */
    g_kbc.count = 0;
    set_irq(0);
    ...
```

**AUX 口当场判定不存在。** `0xD3`（写 AUX 输出缓冲，即回环测试）的数据放回输出缓冲，但**故意不置 `aux` 标记**；`0xA9`（AUX 口测试）返回 `0x01`（时钟线卡死）。驱动两步都判定失败，放弃 AUX 口，全程没有超时。

**键盘应答走 IRQ1。** 驱动发给键盘设备的命令（复位 `0xFF`、读 ID `0xF2`、设置 LED `0xED` 等）由一个极简的“键盘”应答：复位回 `0xFA 0xAA`，读 ID 回 `0xFA 0xAB 0x83`，其他一律回 `0xFA`（ACK）。这些字节标记 `from_kbd`，在 CTR 允许键盘中断时拉 IRQ1。

**复位是退出信号。** 两条路径：命令 `0xF0`–`0xFF` 中低 4 位的第 0 位为 0 的（包括最常用的 `0xFE`），表示“脉冲拉低 reset 线”；或者用 `0xD1` 写输出端口时第 0 位为 0。两者都让 VMM 退出：

```c
static int request_reset(void)
{
    vmm_info("guest requested reset via i8042");
    g_kbc.vm->exit_code = 0;
    return VMM_ERR_EXIT;       /* 沿着分发路径一路返回，vCPU 循环结束 */
}
```

设备回调返回 `VMM_ERR_EXIT` 的约定贯穿整个设备模型：它一路从 `handle_io()` 返回到 `vcpu_run_loop()`，被当作“正常停机”处理，然后触发第十三章的停机协议。

**BIOS 交接时的初值。** 没有 BIOS，但 Linux 期望接手时控制器已经处于 BIOS 初始化后的状态：

```c
    /* BIOS 交接时的典型值：键盘中断开、扫描码翻译开、AUX 关 */
    g_kbc.ctr  = CTR_KBDINT | CTR_SYSFLAG | CTR_AUXDIS | CTR_XLATE;
    g_kbc.outp = OUTP_RESET_N | OUTP_A20;
```

`CTR_SYSFLAG` 表示“自检已通过”；输出端口的 reset 位为 1（不复位）、A20 为 1（已打开）。如果输出端口初值是 0，guest 第一次读-改-写输出端口时就会“复位”机器。

### 11.6 ACPI PM1a

PM1a 寄存器块是 6 个字节：`PM1_STS`（2 字节，写 1 清零）、`PM1_EN`（2 字节）、`PM1_CNT`（2 字节）。端口地址 `0x600` 是 mini-vmm 自己选的，只要与 FADT 里声明的 `PM1a_EVT_BLK = 0x600`、`PM1a_CNT_BLK = 0x604` 一致即可。

两处要做对：

```c
static int pm_read(void *opaque, uint64_t off, uint32_t size, void *data)
{
    uint8_t regs[6];
    uint16_t cnt = g_pm.cnt | PM1_CNT_SCI_EN;   /* 永远处于 ACPI 模式 */
    ...
}
```

读 `PM1_CNT` 时第 0 位 `SCI_EN` 必须为 1。FADT 的 `SMI_CMD` 填了 0，告诉 Linux “不需要切换就已经在 ACPI 模式”，Linux 会通过读 `SCI_EN` 来确认这一点。两者矛盾时 Linux 会尝试切换模式并失败。

```c
    case 4:   /* PM1_CNT */
        if ((v & PM1_CNT_SLP_EN) && PM1_CNT_SLP_TYP(v) == S5_SLP_TYP) {
            vmm_info("guest requested poweroff via ACPI S5");
            vm->exit_code = 0;
            return VMM_ERR_EXIT;
        }
        g_pm.cnt = v & (uint16_t)~PM1_CNT_SLP_EN;
        break;
```

写 `PM1_CNT` 时检查 `SLP_EN` 和 `SLP_TYP`。值 5 来自 DSDT 里的 `_S5_` 对象，两处必须一致。guest 可能按字节也可能按字访问这些寄存器，实现里把 6 个字节当成一个小端寄存器文件统一处理。

### 11.7 阶段 8：控制台

串口的另一半在 host 侧：把 host 终端的输入送进串口的 RX FIFO。mini-vmm 用一个独立线程读 stdin：

```c
static void *console_thread(void *arg)
{
    bool esc = false;
    uint8_t c;
    ...
    for (;;) {
        n = read(STDIN_FILENO, &c, 1);
        ...
        if (esc) {
            esc = false;
            if (c == 'x' || c == 'X') {        /* Ctrl-A x：退出 VMM */
                g_vm->user_stop = true;
                vm_request_stop(g_vm);
                break;
            }
            if (c != CTRL_A)
                serial8250_push_rx(g_serial, CTRL_A);
        } else if (c == CTRL_A) {
            esc = true;
            continue;
        }
        serial8250_push_rx(g_serial, c);
    }
    return NULL;
}
```

阶段 8 要准备三件事：

1. **终端切到 raw 模式**（`cfmakeraw()`）。否则 host 的终端驱动会在行尾之前缓冲输入、自己处理退格，而且 Ctrl-C 会变成 SIGINT 杀掉 VMM，而不是作为字符 `0x03` 送给 guest 的 shell。raw 模式下要保留输出处理（`OPOST | ONLCR`），因为 VMM 自己的日志只有 `\n`。退出时必须恢复终端设置，mini-vmm 用 `atexit()` 注册了恢复函数。
2. **提供一个退出热键。** raw 模式下 Ctrl-C 送进了 guest，VMM 自己需要另一个退出方式。mini-vmm 沿用 QEMU 的约定：Ctrl-A 然后 x。连按两次 Ctrl-A 发送一个真正的 Ctrl-A。
3. **处理后台进程组的情况。** 这是一个测试时才发现的坑：用 `timeout 60 ./vmm ...` 运行时，`timeout` 会把子进程放进一个单独的进程组，此时 VMM 不是终端的前台进程组。一个后台进程调用 `tcsetattr()` 会收到 SIGTTOU，调用 `read(stdin)` 会收到 SIGTTIN，两个信号的默认动作都是**停止进程**。表现是 VMM 静止不动，连 Ctrl-C 都没用。修复是启动时检查：

```c
    if (isatty(STDIN_FILENO) && tcgetpgrp(STDIN_FILENO) != getpgrp()) {
        vmm_warn("console: stdin is a terminal but vmm is not in the "
                 "foreground process group, guest input is disabled");
        vmm_warn("  (running under timeout? use 'timeout --foreground')");
        return VMM_OK;
    }
```

console 线程往串口放字节时会拿串口的锁，然后调用 `update_irq()`，可能进一步调用 `KVM_IRQ_LINE`。所以 `KVM_IRQ_LINE` 会从两类线程发起：vCPU 线程（guest 读写串口寄存器时）和 console 线程（有新输入时）。这个 ioctl 本身是线程安全的，KVM 内部有自己的锁。

另一个与输入有关的限制：RX FIFO 只有 256 字节，满了之后 `serial8250_push_rx()` 返回失败，字节被丢弃。人手打字不可能填满它，但测试脚本一次性往 stdin 灌大量命令时会丢字符。第十六章讲测试时会再遇到这个问题。

### 11.8 并发：两把锁和一个顺序

多个 vCPU 线程可能同时陷出、同时访问设备。mini-vmm 的并发策略是原理篇 6.9 节的“大锁”：

```c
    case KVM_EXIT_IO: {
        int r;

        vcpu->n_exit_io++;
        pthread_mutex_lock(&vcpu->vm->io_lock);
        r = handle_io(vcpu);
        pthread_mutex_unlock(&vcpu->vm->io_lock);
        return r;
    }
```

MMIO 分支完全相同。结构体里的注释写明了这把锁的约定：

```c
    /* 多个 vCPU 线程会同时陷出到用户态访问设备。设备模型本身不做
     * 并发保护，统一由 exit 分发路径持有这把大锁串行化（和 QEMU 的
     * BQL 同一个思路）。设备表在 guest 启动前注册完毕，之后只读。 */
    pthread_mutex_t   io_lock;
```

最后一句是一个重要的前提：设备表在阶段 5 注册完之后就不再修改，所以查找设备不需要额外的同步。

串口还有自己的锁，因为 console 线程也要访问它，而 console 线程不经过分发路径、不拿 `io_lock`。于是有了两把锁，必须规定顺序以避免死锁：

```
   vCPU 线程：  io_lock ──► 串口 lock ──► （可能）KVM_IRQ_LINE
   console 线程：            串口 lock ──► （可能）KVM_IRQ_LINE
```

只要所有线程都按“先 `io_lock` 后串口锁”的顺序（console 线程只拿后一把），就不会出现环形等待。i8042、RTC、PM1a 只被 vCPU 线程访问，`io_lock` 已经保护了它们，不需要自己的锁。

### 11.9 小结：阶段 5 和阶段 8 的准备清单

- 一条设备总线：地址区间到设备回调的表，注册时查重叠，回调传偏移。
- PIO 分发：数据在 `run + data_offset`，处理 `count > 1`，未注册端口读 `0xFF`、写丢弃。
- 串口：只模拟驱动会碰的寄存器，中断条件集中在 `update_irq()` 里从状态重算，只在电平变化时拉线。
- RTC：UIP=0、BCD、VRT=1，时间现取 host，注意 `tm_mon + 1` 和 `tm_wday + 1`。
- i8042：控制器命令逐条应答，新命令冲掉旧应答，AUX 口两步当场失败，键盘应答走 IRQ1，复位命令返回退出，初值模拟 BIOS 交接状态。
- PM1a：`SCI_EN` 恒为 1，`SLP_TYP=5 + SLP_EN` 返回退出，端口与 FADT 一致。
- 控制台：raw 模式并在退出时恢复，Ctrl-A x 退出，不在前台进程组时不碰终端。
- 并发：设备分发套一把大锁，串口单独一把锁，固定加锁顺序。

## 十二、阶段 6 与阶段 7：固件表、启动协议与 BSP 寄存器

这一章是全文细节最密集的部分。阶段 6 往 guest 内存里写七样东西，阶段 7 设置 BSP 的寄存器。每一样都有一组“必须是这个值”的字段，按 `boot_linux()` 里的执行顺序依次讲。

```c
static int boot_linux(struct vmm_vm *vm, struct vmm_vcpu *vcpu,
                      const struct vmm_config *cfg, struct serial8250 *com1)
{
    ...
    r = elf_load_vmlinux(vm, cfg->payload_path, &elf);        /* 12.1 内核镜像 */
    r = mptable_setup(vm, vm->nr_vcpus);                      /* 12.5 MP table */
    r = acpi_setup(vm, vm->nr_vcpus, &rsdp);                  /* 12.4 ACPI */
    zc.acpi_rsdp   = rsdp;
    zc.cmdline     = cfg->cmdline;
    zc.initrd_path = cfg->initrd_path;
    zc.kernel_end  = elf.hi_gpa;
    r = zeropage_setup(vm, &zc);                              /* 12.2/12.3 boot_params、E820、cmdline、initrd */
    boot_layout_default(&layout);
    r = boot_build_page_table(vm, &layout);                   /* 12.6 页表 */
    r = boot_setup_linux64(vcpu, &layout, elf.entry_gpa,
                           ZP_BOOT_PARAMS_GPA);               /* 12.6/12.7 GDT 与 BSP 寄存器 */
    return console_start(vm, com1);
}
```

顺序上有两个依赖：ACPI 表要在 boot_params 之前生成，因为 boot_params 里要填 RSDP 的地址；内核镜像要在 initrd 之前载入，因为 initrd 的位置要避开内核的末尾。

### 12.1 内核镜像：按物理地址摆放 vmlinux / bzImage

bzImage 是一个“自解压”格式：前面是 16 位的 setup 代码和 setup header，后面是压缩过的内核加上一段解压代码。加载 bzImage 需要解析 setup header、按协议摆放、从 32 位或 64 位入口进入解压代码，解压代码再把真正的内核解压到目标地址。

vmlinux 的每个 `PT_LOAD` 段同时有两个地址：`p_vaddr` 是内核虚拟地址（如 `0xffffffff81000000`），`p_paddr` 是物理地址（如 `0x1000000`）。VMM 此时还没有进入 guest，只能按物理地址摆放：

```c
    for (i = 0; i < eh->e_phnum; i++) {
        const Elf64_Phdr *p = &ph[i];
        uint8_t *dst;

        if (p->p_type != PT_LOAD || p->p_memsz == 0)
            continue;
        ...
        dst = gpa_to_hva(vm, p->p_paddr, p->p_memsz);   /* 按 p_paddr 摆放 */
        memcpy(dst, img + p->p_offset, p->p_filesz);
        memset(dst + p->p_filesz, 0, p->p_memsz - p->p_filesz);   /* bss 清零 */
        ...
    }
```

要做对的三件事：

1. **用 `p_paddr` 而不是 `p_vaddr`**。用虚拟地址会直接越界。
2. **`p_memsz` 大于 `p_filesz` 的部分要清零**，那是 bss 段。真实日志里最后一个段 `file 0x238000 mem 0x50d000`，有将近 3MB 的 bss。依赖 `mmap` 出来的匿名内存本来就是零也可以，但显式清零更稳妥（比如以后支持重启时复用内存）。
3. **入口地址 `e_entry` 要换算成物理地址**。x86_64 vmlinux 的链接脚本写的是 `ENTRY(phys_startup_64)`，已经是物理地址（真实日志里是 `0x1000000`）；但为了兼容别的构建方式，代码里检查了一下：如果 `e_entry` 落在某个段的虚拟地址范围里，就用该段的 `p_vaddr - p_paddr` 换算回物理地址。

内核被加载在 16MB（`0x1000000`）处，这是 x86_64 内核默认的 `CONFIG_PHYSICAL_START`。VMM 还要检查内核镜像不低于 1MB，否则会压到低端的 GDT、页表、boot_params。载入完成后记下镜像的最高地址（`hi_gpa`，含 bss），给 12.3 节摆放 initrd 用。

> 之所以加载在 16M，是因为传统的 ISA 总线设备以及部分陈旧外设仅支持 24 位寻址，这意味着它们的 DMA 只能访问物理内存的前 16MB，Linux 内核据此划分出了 `ZONE_DMA`（0~16MB）。

### 12.2 boot_params：VMM 交给内核的“交接单”

`struct boot_params` 固定 4KB，mini-vmm 把它放在 GPA `0x7000`，并在阶段 7 把 `RSI` 设为这个地址。结构体的定义直接用内核导出给用户态的 `<asm/bootparam.h>`，不自己抄一份，避免偏移写错。

先整体清零，然后只填内核真正会读的字段：

| 字段 | 偏移 | mini-vmm 填的值 | 含义与必要性 |
|---|---|---|---|
| `hdr.boot_flag` | `0x1FE` | `0xAA55` | setup header 的魔数，沿用引导扇区的签名 |
| `hdr.header` | `0x202` | `0x53726448`（`"HdrS"`） | setup header 的魔数 |
| `hdr.version` | `0x206` | `0x020F` | 声明遵循启动协议 2.15；下面的 `acpi_rsdp_addr` 是 2.14 引入的字段 |
| `hdr.type_of_loader` | `0x210` | `0xFF` | bootloader 类型，`0xFF` 表示“未注册的 bootloader” |
| `hdr.loadflags` | `0x211` | `0x01`（`LOADED_HIGH`） | 内核被加载在 1MB 以上 |
| `hdr.kernel_alignment` | `0x230` | `0x1000000` | 内核的物理对齐要求 |
| `hdr.cmd_line_ptr` | `0x228` | `0x20000` | 内核命令行的物理地址（低 32 位） |
| `hdr.cmdline_size` | `0x238` | 命令行长度 | |
| `ext_cmd_line_ptr` | `0x0C8` | 0 | 命令行地址的高 32 位 |
| `hdr.ramdisk_image` | `0x218` | initrd 的物理地址（低 32 位） | 没有 initrd 时为 0 |
| `hdr.ramdisk_size` | `0x21C` | initrd 的字节数（低 32 位） | |
| `ext_ramdisk_image` / `ext_ramdisk_size` | `0x0C0` / `0x0C4` | 高 32 位 | 支持 4GB 以上的 initrd |
| `hdr.initrd_addr_max` | `0x22C` | `0x37FFFFFF` | initrd 的最高地址；vmlinux 没有 setup header，填内核默认值 |
| `acpi_rsdp_addr` | `0x070` | `0xE0000` | 协议 2.14 起，直接告诉内核 RSDP 在哪，不必扫描 |
| `e820_entries` | `0x1E8` | 3 | E820 表的项数 |
| `e820_table[]` | `0x2D0` | 见 12.3 节 | 每项 20 字节：8 字节地址、8 字节长度、4 字节类型 |

有两点说明。

第一，关于魔数和版本号。直接从 64 位入口启动 vmlinux 时，内核并不会严格校验 `boot_flag`、`header` 这些魔数（这些检查在 bzImage 的 16 位 setup 代码里）。但它们是启动协议的一部分，填上是约定，部分工具和内核路径也会参考 `version` 字段。

第二，关于先清零。`boot_params` 里有很多字段是“非零表示某个功能”，比如 `hdr.hardware_subarch` 非零时内核会走 Intel MID 这类特殊平台的初始化，`sentinel` 字段非零时内核会认为 bootloader 没有正确清零、主动把一大片字段清掉。先 `memset` 为 0 再填，是避免这类意外的最简单办法。

内核在 `startup_64` 之后很早就会调用 `copy_bootdata()`，把这 4KB 拷贝到内核自己的 `boot_params` 变量里，并按 `cmd_line_ptr` 把命令行拷走。之后原来的 `0x7000` 页面和命令行页面就不再被使用，会作为普通内存释放。所以 boot_params 放在低端内存里不会与后续的 trampoline 等用途产生长期冲突。

### 12.3 E820、命令行与 initrd

#### 12.3.1 E820

E820 表只有三项，原理篇 7.2 节讲了每一项的来历：

```c
    e820_add(bp, 0,                 ZP_EBDA_START,                     E820_TYPE_RAM);
    e820_add(bp, ZP_EBDA_START,     ZP_HIGH_MEM_START - ZP_EBDA_START, E820_TYPE_RESERVED);
    e820_add(bp, ZP_HIGH_MEM_START, ram - ZP_HIGH_MEM_START,           E820_TYPE_RAM);
```

| 区间 | 类型 | 为什么 |
|---|---|---|
| `[0, 0x9FC00)` | RAM | 低端内存必须给，Linux 要在这里放 AP 的 trampoline |
| `[0x9FC00, 0x100000)` | 保留 | EBDA、VGA、BIOS 区。MP table（`0x9FC00`）和 ACPI 表（`0xE0000`）就放在这里面，报保留才不会被内核当成空闲内存覆盖 |
| `[0x100000, ram)` | RAM | 内核、initrd、所有运行时内存 |

注意 GDT、页表、boot_params、命令行都在第一个区间里，而这个区间报告的是“可用 RAM”。这没有问题：这些结构只在启动最初的一小段时间里有用，内核拷走需要的内容、换上自己的页表和 GDT 之后，它们就可以被回收。真实 BIOS 交给 bootloader 的内存图也是这样。

#### 12.3.2 命令行

默认命令行是：

```
console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1
```

| 参数 | 作用 | 不加会怎样 |
|---|---|---|
| `console=ttyS0` | 内核日志和 `/dev/console` 走第一个串口 | 日志输出到不存在的 VGA，串口上什么都看不到 |
| `earlyprintk=serial,ttyS0,115200` | 在 8250 驱动加载之前，就用最简单的轮询方式往串口写日志 | 内核在驱动加载之前崩溃时一行日志都没有；真实日志里 `printk: bootconsole [earlyser0] enabled` 就是它 |
| `reboot=k` | 重启时写 i8042 的 `0xFE` 命令 | 内核会尝试 ACPI reset、PCI reset 等方式，VMM 可能收不到重启信号 |
| `panic=-1` | panic 后立即重启 | panic 后内核挂住，VMM 永远不退出 |

后两个参数把 guest 的“重启”和“panic”都变成了一次 i8042 复位，也就是 VMM 退出的信号。测试脚本依赖这一点：不给 initrd 时内核会以 `VFS: Unable to mount root fs` panic，然后重启，VMM 应该干净地退出。

命令行写在 GPA `0x20000`，以 `\0` 结尾，长度不超过 4096 字节。`--append` 选项可以在默认命令行后面追加参数，比如调试时加 `maxcpus=1`（只启动 BSP）或 `acpi=off`（下面 12.5 节会用到）。

#### 12.3.3 initrd

initrd 放在哪里，启动协议没有规定，只要求在 `initrd_addr_max` 以下、不与内核重叠、在页表的映射范围内。mini-vmm 的选择是 **RAM 顶端向下按 2MB 对齐**：

```c
    top = vm->mem.ram_size;
    if (top > ZP_INITRD_ADDR_MAX + 1)
        top = ZP_INITRD_ADDR_MAX + 1;
    ...
    gpa = ALIGN_DOWN(top - (uint64_t)st.st_size, 2ULL << 20);
    if (gpa < zc->kernel_end) {
        vmm_err("initrd [0x%llx, +0x%llx) overlaps the kernel image ...");
        return VMM_ERR_INVAL;
    }
```

放在顶端的理由是：内核启动时从低地址往上分配内存（早期页表、直接映射的页表、各种早期数据结构），initrd 在顶上最不容易被踩到。512MB 的 guest 上，1MB 左右的 initramfs 被放在 `0x1FE00000`。日志印证了这个位置，而且内核直接在原地使用它，没有搬移：

```
[    0.007782] RAMDISK: [mem 0x1fe00000-0x1ff09fff]
```

initrd 的内容是一个 cpio 归档（可以 gzip 压缩），内核在启动后期把它解开成根文件系统，然后执行其中的 `/init`。mini-vmm 用 `tools/build_initramfs.sh` 生成一个只含静态链接 busybox 的 initramfs，它的 `/init` 挂载 `/proc`、`/sys`、`/dev`，然后启动 shell，shell 退出后执行 `poweroff -f`。busybox 必须是**静态链接**的：initramfs 里没有动态链接器，动态链接的 busybox 会报 `No such file or directory`（找不到的其实是 `ld.so`）。

### 12.4 ACPI 表：主角

原理篇第七章讲了 ACPI 的结构，这一节讲 mini-vmm 具体生成了什么。全部表放在从 `0xE0000` 开始的 64KB 内，每张表 16 字节对齐：

```
   GPA        表      长度    内容
   0xE0000    RSDP    36     → XSDT
   0xE0030    XSDT    52     → FADT, MADT
   0xE0070    FADT    276    → DSDT；PM1a 在 0x600/0x604；SCI = 9
   0xE0190    DSDT    50     AML: Name(_S5, Package(){5,5,0,0})
   0xE01D0    MADT    94     4×LAPIC + IOAPIC + LAPIC_NMI
```

这些地址与真实日志里 `ACPI: RSDP 0x00000000000E0000 000024` 等几行完全对应。

#### 12.4.1 通用规则：表头与校验和

除 RSDP 外，每张表以 36 字节的通用表头开始：

```c
struct acpi_header {
    char     signature[4];      /* "XSDT"、"FACP"、"DSDT"、"APIC" */
    uint32_t length;            /* 整张表的长度，含表头 */
    uint8_t  revision;
    uint8_t  checksum;          /* 整张表所有字节之和 mod 256 == 0 */
    char     oem_id[6];
    char     oem_table_id[8];
    uint32_t oem_revision;
    char     creator_id[4];
    uint32_t creator_revision;
} __attribute__((packed));
```

两条必须遵守的规则：

1. **所有结构体都要 `packed`**，并且用 `_Static_assert` 在编译期检查大小。ACPI 表的字段大量是非对齐的（比如 FADT 里 `uint32_t flags` 紧跟在一个 `uint8_t` 后面），不加 `packed` 编译器会插入填充，所有偏移都会错。mini-vmm 对每个结构体都有断言，比如 `_Static_assert(sizeof(struct acpi_fadt) == 276, "fadt size");`。
2. **校验和最后算**。先把表的所有字段（包括 `length`）填好，把 `checksum` 置 0，计算全部字节之和，取负数写回 `checksum`。任何在算完校验和之后的修改都会让校验和失效。

```c
static uint8_t acpi_checksum(const void *p, size_t len)
{
    const uint8_t *b = p;
    uint8_t sum = 0;

    while (len--)
        sum += *b++;
    return (uint8_t)(-sum);
}
```

Linux 默认不严格校验表的校验和（日志里 `ACPI: Early table checksum verification disabled`），但 RSDP 的校验和是一定会检查的，而且其他操作系统和工具（比如 `acpidump`）会校验，所以必须算对。

#### 12.4.2 RSDP

```c
    memcpy(rsdp->signature, "RSD PTR ", 8);   /* 注意末尾的空格，共 8 字节 */
    memcpy(rsdp->oem_id, ACPI_OEM_ID, 6);
    rsdp->revision     = 2;                    /* ACPI 2.0+：使用 XSDT */
    rsdp->length       = sizeof(*rsdp);        /* 36 */
    rsdp->xsdt_address = ACPI_TABLES_GPA + xsdt_off;
    rsdp->checksum     = acpi_checksum(rsdp, 20);            /* 只算前 20 字节 */
    rsdp->ext_checksum = acpi_checksum(rsdp, sizeof(*rsdp)); /* 算全部 36 字节 */
```

两个校验和的顺序不能反：`ext_checksum` 覆盖了 `checksum` 所在的字节，所以必须先算 `checksum` 再算 `ext_checksum`。`rsdt_address` 保持 0：`revision = 2` 时操作系统使用 XSDT，不需要提供 32 位的 RSDT。

RSDP 放在 `0xE0000`，16 字节对齐，位于 ACPI 规范规定的扫描区 `[0xE0000, 0xFFFFF]` 内。同时它的地址也填进了 `boot_params.acpi_rsdp_addr`，两条路都能找到。

#### 12.4.3 XSDT

XSDT 是表头加一个 64 位地址数组。mini-vmm 只列两项：FADT 和 MADT。**DSDT 不列在 XSDT 里**，它由 FADT 的 `DSDT`/`X_DSDT` 字段引用，这是 ACPI 规范的规定：XSDT 只列“顶层”的表，DSDT 通过 FADT 间接找到。

#### 12.4.4 FADT

FADT（签名 `"FACP"`，注意不是 `"FADT"`）是 276 字节的大结构，mini-vmm 只填其中十来个字段，其余为 0：

| 字段 | 值 | 为什么 |
|---|---|---|
| `DSDT` / `X_DSDT` | `0xE0190` | 两个都填。ACPICA 优先用 64 位的 `X_DSDT` |
| `SCI_INT` | 9 | ACPI SCI 的传统中断号 |
| `SMI_CMD` | 0 | 已经在 ACPI 模式，不需要切换 |
| `PM1a_EVT_BLK` | `0x600` | 与 `acpi_pm_attach()` 注册的端口一致 |
| `PM1a_CNT_BLK` | `0x604` | 同上，关机写这里 |
| `PM1_EVT_LEN` | 4 | 事件块长度：STS 2 字节 + EN 2 字节 |
| `PM1_CNT_LEN` | 2 | 控制块长度 |
| `CENTURY` | `0x32` | 与 RTC 模拟里的世纪寄存器一致 |
| `IAPC_BOOT_ARCH` | `LEGACY_DEVICES \| 8042` | 声明有传统设备和 8042 键盘控制器 |
| `Flags` | `WBINVD \| PWR_BUTTON \| SLP_BUTTON` | 第 4、5 位置 1 表示“没有固定功能电源键/睡眠键”；**第 20 位 HW_REDUCED_ACPI 保持 0** |
| 表头 `revision` | 6 | 配合 276 字节的长度 |
| `minor_version` | 4 | FADT 次版本号 |
| `X_PM1a_EVT_BLK` 等扩展地址字段 | 全 0 | ACPICA 会从 32 位字段自动转换出扩展格式 |

两个关键点再强调一次：`Flags` 第 20 位必须为 0（原理篇 7.4.3 节，否则 Linux 放弃 PIT 和 8259A）；PM1 相关的端口必须与 VMM 实际注册的设备一致（否则关机写到了没人响应的端口）。`SMI_CMD = 0` 与 PM1a 设备读回 `SCI_EN = 1` 是一对配合的设置。

`PWR_BUTTON` 和 `SLP_BUTTON` 这两位的语义是反的：置 1 表示“**没有**固定功能按钮”（如果有，按钮会作为控制方法设备出现在 DSDT 里）。它们置 1，Linux 就不会去 PM1 事件寄存器里等按钮事件。

#### 12.4.5 DSDT：14 字节的 AML

DSDT 是表头加 AML 字节码。mini-vmm 的全部 AML 只有 14 个字节：

```c
static const uint8_t dsdt_aml[] = {
    0x08, '_', 'S', '5', '_', 0x12, 0x08, 0x04,
    0x0a, 0x05, 0x0a, 0x05, 0x00, 0x00,
};
```

逐字节拆开：

| 字节 | 含义 |
|---|---|
| `08` | `NameOp`：定义一个命名对象 |
| `5F 53 35 5F` | 名字 `"_S5_"`。ACPI 名字固定 4 字节，ASL 里写的 `_S5` 在编码时补齐下划线 |
| `12` | `PackageOp`：对象的值是一个包 |
| `08` | `PkgLength`：包的长度，从这个字节本身开始算，共 8 字节 |
| `04` | `NumElements`：包里有 4 个元素 |
| `0A 05` | `BytePrefix` + 5：第 1 个元素，PM1a_CNT 的 SLP_TYP |
| `0A 05` | `BytePrefix` + 5：第 2 个元素，PM1b_CNT 的 SLP_TYP |
| `00` | `ZeroOp`：第 3 个元素，保留 |
| `00` | `ZeroOp`：第 4 个元素，保留 |

`PkgLength` 是 AML 里最容易算错的字段：它包含自身占用的字节数，但不包含 `PackageOp`。这里自身 1 字节加上 `NumElements` 的 1 字节加上 6 字节元素，一共 8。如果包的总长度超过 63，`PkgLength` 就要用多字节编码，这时手写 AML 就不现实了，应该用 `iasl` 编译器从 ASL 生成。

SLP_TYP 的值 5 本身没有特殊含义，它只需要与 PM1a 设备里判断关机的值一致。真实硬件上这个值由芯片组决定，不同主板不同。

#### 12.4.6 MADT

```c
    madt->lapic_addr = MP_LAPIC_BASE;          /* 0xFEE00000 */
    madt->flags      = MADT_PCAT_COMPAT;       /* 同时存在 8259A */

    for (i = 0; i < nr_cpus; i++) {            /* 类型 0：每个 vCPU 一项 */
        l->type         = 0;
        l->length       = 8;
        l->processor_id = (uint8_t)i;          /* ACPI 处理器 ID */
        l->apic_id      = (uint8_t)i;          /* 必须等于 KVM 的 LAPIC ID = vcpu_id */
        l->flags        = 1;                   /* 已启用 */
    }
    /* 类型 1：IOAPIC */
    io->ioapic_id = (uint8_t)nr_cpus;          /* 与 MP table 一致，避开 LAPIC ID */
    io->address   = MP_IOAPIC_BASE;            /* 0xFEC00000 */
    io->gsi_base  = 0;
    /* 类型 4：所有 CPU 的 LINT1 接 NMI */
    n->processor_id = 0xff;
    n->lint         = 1;
```

逐项的要求：

- `lapic_addr` 必须是 `0xFEE00000`，这是 KVM LAPIC 的地址。
- `PCAT_COMPAT` 置 1，告诉 Linux 有 8259A，需要先屏蔽它再切换到 APIC 模式。KVM 确实模拟了 8259A，所以这一位是如实描述。
- 每个 LAPIC 条目的 `apic_id` 必须等于对应 vCPU 的 ID，这是三方一致原则里“固件表”那一方。`flags` 第 0 位必须置 1，否则 Linux 认为这颗 CPU 被禁用了，`smpboot: Allowing N CPUs` 里的数字会变小。
- IOAPIC 的 `address` 必须是 `0xFEC00000`，`gsi_base` 为 0。ID 选 `nr_cpus`，这样 4 核时 LAPIC ID 是 0 到 3、IOAPIC ID 是 4，互不冲突。
- 不写任何类型 2（中断源覆盖）条目。
- 类型 4 条目声明 LINT1 接 NMI，`processor_id = 0xFF` 表示所有处理器。这是 PC 平台的标准接法，也与 KVM LAPIC 的行为一致。

### 12.5 MP table：acpi=off 时的退路

原理篇 7.5 节讲过，guest 能用 ACPI 时 MP table 会被忽略。但在 `acpi=off` 时（或者 guest 内核没编译 ACPI），它是唯一的中断拓扑描述。可以用 `--append acpi=off` 验证这条路径。

MP table 放在 `0x9FC00`，这是 Linux `default_find_smp_config()` 扫描的第二个区间（常规内存最后 1KB，639K 到 640K）。整张表不超过 1KB：

```
   0x9FC00  MP 浮动指针（16 字节）
            signature  = "_MP_"
            physptr    = 0x9FC10      → 紧随其后的配置表
            length     = 1            （以 16 字节为单位）
            specification = 4         （MPS 1.4）
            checksum   = 使 16 字节之和为 0
            feature1   = 0            （0 = 后面有真正的配置表，不用默认配置）
   0x9FC10  MP 配置表头（44 字节）
            signature  = "PCMP"
            length     = 表头 + 所有条目
            spec       = 4
            oem / productid
            oemcount   = 条目个数
            lapic      = 0xFEE00000
            checksum   = 使整张配置表之和为 0
            ── 条目 ──
            processor × N  （每项 20 字节）apicid = i，cpuflag = ENABLED | (i==0 ? BP : 0)
            bus × 1        （8 字节）   busid = 0，bustype = "ISA   "
            ioapic × 1     （8 字节）   apicid = N，flags = USABLE，apicaddr = 0xFEC00000
            intsrc × 16    （每项 8 字节）ISA IRQ i → IOAPIC pin i
            lintsrc × 2    （每项 8 字节）LINT0 = ExtINT，LINT1 = NMI，dstapic = 0xFF
```

每个字段的要求：

- **浮动指针和配置表各有一个校验和**，都是“所有字节之和为 0”。浮动指针的校验和覆盖 16 字节，配置表的覆盖 `length` 字节。
- **`feature1` 必须为 0**。非零表示“使用 MPS 规范定义的某种默认配置”，此时 Linux 会忽略配置表，按一个固定的双 CPU 配置来处理。
- **处理器条目的 `cpuflag`**：第 0 位 `ENABLED`，第 1 位 `BP`（是 BSP）。只有 0 号 CPU 置 BP 位，与 KVM 的 BSP（`vcpu_id == 0`）一致。`cpufeature` 和 `featureflag` 字段 Linux 只用来打印，填一个合理的值即可。
- **总线条目**：`bustype` 是 6 个字符，`"ISA"` 后面补 3 个空格。I/O 中断条目通过 `srcbus = 0` 引用它，表明这些是 ISA 中断。
- **IOAPIC 条目**：`apicid` 必须与 MADT 里的一致（都是 N），`flags` 第 0 位 `USABLE` 必须为 1。
- **I/O 中断条目**：16 条，`irqflag = 0`（按总线默认：ISA 是边沿、高有效），`srcbusirq = i`，`dstirq = i`，恒等映射。
- **本地中断条目**：LINT0 接 ExtINT（8259A 的 INT 输出），LINT1 接 NMI，`dstapic = 0xFF` 表示所有 LAPIC。这让 Linux 在切换到 symmetric I/O 之前能正确地使用 virtual wire 模式。

条目个数 `oemcount` 和表长度 `length` 都要在填完所有条目后计算，然后才算校验和。

真实日志里，VMM 生成 MP table 时的输出：

```
[INFO] MP table @ GPA 0x9fc00: 4 CPU(s), IOAPIC id 4 @ 0xfec00000, 24 entries
```

24 = 4 个处理器 + 1 条总线 + 1 个 IOAPIC + 16 条 I/O 中断 + 2 条本地中断。

**两份表的一致性检查清单**，改动任何一份时都要对照：

| 信息 | MP table | ACPI MADT | 必须等于 |
|---|---|---|---|
| CPU 个数 | processor 条目数 | 类型 0 条目数 | `cfg.nr_vcpus` |
| 每颗 CPU 的 APIC ID | `apicid` | `apic_id` | `vcpu_id` |
| BSP | `cpuflag` 的 BP 位 | （MADT 不标 BSP，Linux 用当前 CPU） | vCPU 0 |
| LAPIC 地址 | 表头 `lapic` | 表头 `lapic_addr` | `0xFEE00000` |
| IOAPIC ID | ioapic `apicid` | 类型 1 `ioapic_id` | `nr_cpus` |
| IOAPIC 地址 | ioapic `apicaddr` | 类型 1 `address` | `0xFEC00000` |
| ISA IRQ → GSI | 16 条恒等 intsrc | 无覆盖条目（默认恒等） | KVM 默认路由 |
| LINT1 | lintsrc NMI | 类型 4 | NMI |

mini-vmm 用同一个 `nr_cpus` 参数、同一组宏（`MP_LAPIC_BASE`、`MP_IOAPIC_BASE`）生成两份表，从代码结构上保证一致。

### 12.6 页表与 GDT

启动协议要求进入 `startup_64` 时已经在长模式、分页已开启，而且页表恒等映射覆盖了内核、boot_params、命令行和 initrd。第一篇已经详细讲过怎么构建长模式页表和 GDT，这里只列出 Linux 启动的具体参数。

**页表**：PML4 在 `0x2000`，PDPT 在 `0x3000`，PD 在 `0x4000`。PD 的 512 项每项映射 2MB 大页（PS 位置 1），一共恒等映射 1GB，覆盖了所有需要被映射的东西（内核在 16MB 附近，initrd 不超过 `initrd_addr_max` 即约 896MB，其他结构都在 1MB 以下）。三张表只占 12KB。

```c
        for (i = 0; i < nr_2m; i++)
            pd[i] = ((i << 21) & PTE_ADDR_MASK)
                    | PTE_P | PTE_RW | PTE_PS;
```

内核进入 `startup_64` 之后很快就会建立自己的页表（`early_top_pgt`），把内核映射到 `0xffffffff80000000` 开始的高端虚拟地址，这张恒等映射表只在最开始的几十条指令里有用。

**GDT**：Linux 64 位启动协议要求代码段选择子是 `0x10`（`__BOOT_CS`）、数据段选择子是 `0x18`（`__BOOT_DS`），这与第一篇裸机模式用的 `0x08`/`0x10` 不同。所以 Linux 模式单独写了一张四项的 GDT：

```c
    uint64_t gdt[4] = {
        GDT_DESC_NULL,        /* 0x00 */
        GDT_DESC_NULL,        /* 0x08 占位 */
        GDT_DESC_CODE64,      /* 0x10 = __BOOT_CS */
        GDT_DESC_DATA64,      /* 0x18 = __BOOT_DS */
    };
```

两个描述符的值拆开来看：

```
   GDT_DESC_CODE64 = 0x00AF9B000000FFFF
     type=0xB（执行/可读/已访问） S=1 DPL=0 P=1  L=1（64 位代码） D=0  G=1
   GDT_DESC_DATA64 = 0x00CF93000000FFFF
     type=0x3（读写/已访问）      S=1 DPL=0 P=1  L=0              D=1  G=1
```

64 位模式下段的基址和界限基本被硬件忽略，但 `L`、`D`、`P`、`S`、`DPL`、`type` 这几位仍然有效，必须自洽：代码段 `L=1` 时 `D` 必须为 0（`L=1, D=1` 是保留组合，加载时会 `#GP`）。

**sregs 里的段寄存器必须与内存里的 GDT 一致。** 通过 `KVM_SET_SREGS` 设置段寄存器时，我们直接给出了段寄存器的“隐藏部分”（基址、界限、属性），硬件不会去查 GDT。但 guest 一旦重新加载任何段寄存器（Linux 在 `startup_64` 里很快就会做），硬件就会真的去读 GDT。如果两边不一致，guest 会在重载段寄存器的那一刻崩溃，而那个位置离真正的错误原因很远，非常难查。mini-vmm 的做法是只写一份描述符常量，sregs 里的值用 `seg_from_desc()` 从描述符反解出来。这个函数里有一个 KVM 特有的坑：

```c
    /* kvm_segment.limit 存的是已按 G 位缩放后的有效界限，
     * 不是描述符里那个 20 位原始字段。 */
    s->limit = s->g ? ((limit_raw << 12) | 0xFFF) : limit_raw;
```

`struct kvm_segment` 的 `limit` 字段是字节粒度的有效界限。G=1 时描述符里的 `0xFFFFF` 对应的是 `0xFFFFFFFF`，直接把 `0xFFFFF` 填进去，KVM 会认为这是一个只有 1MB 的段。

### 12.7 阶段 7：BSP 的初始寄存器

最后一步，把 0 号 vCPU 摆成启动协议要求的状态。按“先 `KVM_GET_SREGS` 读出 KVM 给的合法初值，只改需要改的字段，再写回”的模式（第一篇讲过为什么不能从零构造）：

| 寄存器 | 值 | 为什么 |
|---|---|---|
| `CR0` | `PE \| MP \| ET \| NE \| WP \| AM \| PG` | 保护模式 + 分页。`NE` 让 x87 错误走异常，`WP` 让内核遵守只读页 |
| `CR3` | `0x2000` | PML4 的物理地址 |
| `CR4` | `PAE` | 长模式要求 PAE |
| `EFER` | `LME \| LMA` | 长模式使能且已激活 |
| `CS` | 选择子 `0x10`，从 `GDT_DESC_CODE64` 反解 | 启动协议规定 |
| `DS`/`ES`/`FS`/`GS`/`SS` | 选择子 `0x18`，从 `GDT_DESC_DATA64` 反解 | 启动协议规定 |
| `GDTR` | base = `0x1000`，limit = 31 | 指向内存里那张四项 GDT |
| `IDTR` | base = 0，limit = 0 | 不提供 IDT。启动协议要求中断关闭，内核很快会装自己的 IDT；在那之前如果发生异常，会变成 triple fault，以 `KVM_EXIT_SHUTDOWN` 暴露出来 |
| `RIP` | `0x1000000` | vmlinux 的物理入口 `phys_startup_64` |
| `RSI` | `0x7000` | `boot_params` 的物理地址 |
| `RFLAGS` | `0x2` | bit 1 是保留位恒为 1；**`IF = 0`**，启动协议要求关中断 |
| `RSP` | `0x200000` | 内核会立刻设置自己的栈，这个值不重要，但要落在已映射的 RAM 里 |

有一处容易想当然的地方：`EFER.LMA` 在真实硬件上是由 CPU 在开启分页时自动置位的，软件不能直接写。但通过 `KVM_SET_SREGS` 设置时，我们是在 vCPU 停止时直接给出它的架构状态，不经过硬件的状态转换，所以 `LMA` 要一起给上。KVM 的 `kvm_is_valid_sregs()` 会检查这组值是否自洽：`EFER.LME` 和 `CR0.PG` 同时为 1 时，必须同时有 `CR4.PAE`、`EFER.LMA` 和 `CR0.PE`，缺一个 `KVM_SET_SREGS` 就返回 `EINVAL`。

`EFER.NXE` 没有置位：Linux 启动后会自己检查 CPUID 并打开它（日志里的 `NX (Execute Disable) protection: active`）。

**AP 不需要设置任何寄存器。** 1 到 N-1 号 vCPU 创建后保持 KVM 给的复位状态，它们的 `CS:IP` 会在收到 SIPI 时由 KVM 设置（原理篇 8.4 节的 `kvm_vcpu_deliver_sipi_vector()`），之后由 guest 的 trampoline 带它们进入长模式。如果 VMM 画蛇添足地给 AP 也设置了长模式寄存器，INIT 会把它们复位掉，白做；如果在没有 irqchip 的情况下这样做，AP 会直接从内核入口开跑，结果不可预测。

### 12.8 小结：阶段 6 和阶段 7 的准备清单

- **内核**：vmlinux 按 `p_paddr` 摆放，bss 清零，入口换算成物理地址，镜像不低于 1MB，记下末尾地址。
- **boot_params**：先清零；魔数 `0xAA55`/`"HdrS"`、版本、`type_of_loader = 0xFF`、`LOADED_HIGH`；命令行指针和长度；initrd 地址和长度（含高 32 位）；`acpi_rsdp_addr`；E820 表。
- **E820**：低 640KB RAM、640KB–1MB 保留（固件表在里面）、1MB 以上 RAM。
- **命令行**：`console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1`。
- **initrd**：RAM 顶端向下 2MB 对齐，不低于内核末尾，不高于 `initrd_addr_max`；busybox 必须静态链接。
- **ACPI**：RSDP（revision 2，两个校验和，先 20 字节后 36 字节）→ XSDT（只列 FADT 和 MADT）→ FADT（PM1a 端口与设备一致，`SMI_CMD=0`，不设 HW_REDUCED）→ DSDT（`_S5_` 的 SLP_TYP 与设备一致）；MADT（每 vCPU 一条 LAPIC，IOAPIC ID = N，无覆盖，LINT1 NMI）。所有结构 `packed` 并断言大小，校验和最后算。
- **MP table**：`0x9FC00`，浮动指针和配置表各一个校验和，`feature1 = 0`，与 MADT 描述同一台机器。
- **页表**：1GB 恒等映射，2MB 大页，三张表 12KB。
- **GDT**：`0x10` 代码段、`0x18` 数据段，sregs 从同一份描述符反解，`limit` 按 G 位缩放。
- **BSP 寄存器**：长模式四件套（CR0/CR3/CR4/EFER 含 LMA）、段寄存器、GDTR、IDTR 为空、`RIP` = 入口、`RSI` = boot_params、`RFLAGS = 0x2`。
- **AP 寄存器**：不设置，交给 INIT/SIPI。

## 十三、阶段 4 与阶段 9：多个 vCPU

原理篇第八章讲过：AP 的唤醒完全由 KVM 的内核态 LAPIC 完成，VMM 的职责只有三件事——**线程、CPUID、固件表**。固件表在上一章讲完了，这一章讲前两件，外加一个多线程程序绕不开的问题：怎么让所有线程可靠地停下来。

所有代码集中在 `src/smp.c`（不到 200 行）和 `vm.c` 的 run loop 里。文件头的注释就是这一章的提纲：

```c
/* src/smp.c — 多 vCPU 线程、CPUID 拓扑、停机协调
 *
 * AP 启动流程里 VMM 不需要做任何事情：
 *   - 内核态 irqchip 存在时，KVM 在 KVM_CREATE_VCPU 里把 vcpu 0 设为
 *     RUNNABLE（BSP），其余 vCPU 设为 KVM_MP_STATE_UNINITIALIZED；
 *   - AP 线程调用 KVM_RUN 后阻塞在 KVM 内部，直到 BSP 通过 LAPIC ICR
 *     发出 INIT + SIPI。KVM 收到 SIPI 后把 AP 置成实模式、
 *     CS:IP = (vector << 8):0，AP 从 Linux 放在低 1MiB 的 trampoline 起跑。
 * 所以 VMM 的职责只有线程、CPUID 和固件表（MADT/MP table）三件事。
 */
```

### 13.1 阶段 4：创建 N 个 vCPU

`--smp N` 选项把核数写进 `cfg.nr_vcpus`，取值 1 到 32（`VMM_MAX_VCPUS`）。`vm_create()` 检查它不超过 `KVM_CAP_MAX_VCPUS`（我们的 host 是 1024），然后在阶段 3 之后循环创建：

```c
    for (i = 0; i < cfg->nr_vcpus; i++) {
        r = vm_create_vcpu(vm, i);
        ...
    }
```

每个 vCPU 的创建过程与第一篇相同：`KVM_CREATE_VCPU` 拿到 fd，`mmap` 它的 `kvm_run` 页，然后调用厂商后端的 `init_vcpu`（设置 CPUID）。`KVM_CREATE_VCPU` 的参数就是 vCPU 的 ID，KVM 用它作为 LAPIC 的 APIC ID，也用它判断谁是 BSP（`vcpu_id == 0`）。所以 **vCPU 的 ID 必须从 0 开始连续编号**，与固件表里的 APIC ID 一一对应。

参数检查里有一条规则值得注意：

```c
    /* Step 1 的裸 payload 不会去唤醒 AP，而且没有内核态 irqchip 时
     * 所有 vCPU 一创建就是 RUNNABLE，会从同一个入口同时跑起来 */
    if (cfg->mode != VMM_BOOT_LINUX && cfg->nr_vcpus > 1) {
        vmm_err("--smp > 1 requires --mode linux");
        return VMM_ERR_INVAL;
    }
```

这就是原理篇 8.4 节那段 `kvm_arch_vcpu_create()` 源码在用户态的体现。

#### 13.1.1 一个初始化顺序的陷阱

`vm_create_vcpu()` 的末尾有一行：

```c
    if (id + 1 > vm->nr_vcpus)
        vm->nr_vcpus = id + 1;
```

`vm->nr_vcpus` 是随着 vCPU 逐个创建而递增的，而 `init_vcpu` 是在这一行**之前**被调用的。所以在创建 0 号 vCPU、设置它的 CPUID 时，`vm->nr_vcpus` 还是 0；创建 1 号时是 1……如果 CPUID 改写代码用 `vm->nr_vcpus` 作为“总核数”，每个 vCPU 看到的核数都不一样，而且都是错的。

正确的做法是用配置里的最终值 `vm->cfg.nr_vcpus`。这类“某个字段在初始化过程中还不是最终值”的陷阱在任何分阶段初始化的系统里都很常见，读代码时要留意每个变量在每个时刻的含义。

### 13.2 CPUID：只改拓扑，其余透传

AMD/海光后端的 `init_vcpu` 很简单：取 host 支持的 CPUID，改写拓扑，设进去：

```c
static int amd_init_vcpu(struct vmm_vcpu *vcpu)
{
    struct kvm_cpuid2 *cpuid = NULL;
    int r;

    r = kvm_get_supported_cpuid(vcpu->vm->kvm_fd, &cpuid);
    ...
    smp_fixup_cpuid(vcpu, cpuid);
    r = kvm_set_cpuid2(vcpu->fd, cpuid);
    free(cpuid);
    ...
}
```

`KVM_GET_SUPPORTED_CPUID` 需要调用者预先分配一个足够大的数组，太小会返回 `E2BIG`。mini-vmm 从 128 项开始，每次失败翻倍重试。

为什么要透传 host 的 CPUID，而不是自己构造一份？因为 guest 内核启动的第一件事就是执行 `CPUID`，检查长模式、SSE、APIC、NX 等一大堆特性。自己构造一份完整的 CPUID 工作量很大，而且容易漏掉某个关键位导致 guest 拒绝启动。透传 KVM 认可的 host 特性是 kvmtool、Firecracker 的共同做法，代价是 guest 看到的 CPU 型号与 host 相同（真实日志里 guest 的 `/proc/cpuinfo` 显示 `vendor_id: HygonGenuine`）。

但透传的拓扑字段是 host 的原始值，必须改写。`smp_fixup_cpuid()` 按原理篇 8.6 节的表逐个 leaf 处理，拓扑固定为“1 个 socket × N 个核 × 每核 1 个线程”，APIC ID 等于 vCPU ID：

```c
void smp_fixup_cpuid(const struct vmm_vcpu *vcpu, struct kvm_cpuid2 *cpuid)
{
    uint32_t id = (uint32_t)vcpu->id;
    uint32_t n  = (uint32_t)vcpu->vm->cfg.nr_vcpus;   /* 注意：cfg 里的最终值 */
    ...
        switch (e->function) {
        case 0x1:
            e->ebx = (e->ebx & 0x0000ffffu) | (id << 24) |
                     ((n > 255 ? 255 : n) << 16);
            if (n > 1)
                e->edx |= CPUID_1_EDX_HTT;
            else
                e->edx &= ~CPUID_1_EDX_HTT;
            break;
        case 0xb:
        case 0x1f:
            e->eax = e->ebx = e->ecx = e->edx = 0;
            break;
        case 0x80000008:
            e->ecx = (e->ecx & ~0xf0ffu) | (order_base2(n) << 12) | (n - 1);
            break;
        case 0x8000001d: {
            uint32_t level = (e->eax >> 5) & 0x7;
            uint32_t share = (level >= 3) ? n - 1 : 0;

            if (e->eax & 0x1f)          /* cache type = 0 表示列表结束 */
                e->eax = (e->eax & ~(0xfffu << 14)) | (share << 14);
            break;
        }
        case 0x8000001e:
            e->eax = id;
            e->ebx = id & 0xff;
            e->ecx = 0;
            break;
        }
    ...
}
```

逐个 leaf 说明改了什么、为什么：

| Leaf | 改写 | 为什么 |
|---|---|---|
| `0x1` EBX[31:24] | = vCPU ID | “初始 APIC ID”，三方一致的 CPUID 一方 |
| `0x1` EBX[23:16] | = N | 本 package 的逻辑处理器数 |
| `0x1` EDX[28] HTT | N > 1 时置 1 | 表示上面的逻辑处理器数字段有效。这一位的名字叫“超线程”，但语义其实是“一个 package 里有多个逻辑处理器” |
| `0xB` / `0x1F` | 全部清零 | Intel 风格的扩展拓扑。KVM 在这台 host 上只返回了 subleaf 0，要正确描述需要补全多个 subleaf、扩容数组；清零表示“不提供”，guest 退回 AMD 风格的路径 |
| `0x80000008` ECX[7:0] | = N − 1 | AMD 的“核数减一” |
| `0x80000008` ECX[15:12] | = ⌈log₂N⌉ | APIC ID 里核编号占几位，guest 用它从 APIC ID 里切出核 ID |
| `0x8000001D` EAX[25:14] | L1/L2 为 0，L3 为 N − 1 | 每级缓存的共享者数量减一：L1/L2 每核私有，L3 所有核共享 |
| `0x8000001E` EAX | = vCPU ID | 扩展 APIC ID |
| `0x8000001E` EBX[7:0] | = vCPU ID | 核 ID。EBX[15:8]（每核线程数减一）清为 0，即每核 1 个线程 |
| `0x8000001E` ECX | = 0 | 节点 ID 为 0，单节点 |

`0x8000001D` 的循环里有一个细节：这个 leaf 有多个 subleaf，每个描述一级缓存，最后一个的缓存类型字段（EAX[4:0]）为 0 表示列表结束，不能改写它。

为什么重点在 AMD 的 leaf？因为我们的 guest 是海光 CPU。Linux 对海光 CPU 的拓扑解析在 `arch/x86/kernel/cpu/hygon.c`：

```c
static void hygon_get_topology(struct cpuinfo_x86 *c)
{
    int cpu = smp_processor_id();

    /* get information required for multi-node processors */
    if (boot_cpu_has(X86_FEATURE_TOPOEXT)) {
        ...
        cpuid(0x8000001e, &eax, &ebx, &ecx, &edx);

        c->cpu_die_id  = ecx & 0xff;
        c->cpu_core_id = ebx & 0xff;
        ...
        /*
         * In case leaf B is available, use it to derive
         * topology information.
         */
        err = detect_extended_topology(c);
        ...
```

有 TOPOEXT 特性时，核 ID 取自 `0x8000001E` 的 EBX[7:0]，节点 ID 取自 ECX[7:0]；如果 `0xB` 可用，还会进一步用它推导拓扑。把 `0xB` 清零，就是让这一步失败，只用 `0x8000001E` 的结果。

改写的效果可以在 guest 里验证。真实日志中 guest 的 `/proc/cpuinfo` 和 sysfs：

```
processor   : 0
physical id : 0
siblings    : 4
core id     : 0
cpu cores   : 4
apicid      : 0
initial apicid  : 0
...
[guest /]# cat /sys/devices/system/cpu/cpu2/topology/core_id /sys/devices/system/cpu/cpu2/topology/physical_package_id
2

```

4 个逻辑处理器（`siblings`）、4 个核（`cpu cores`）、每核 1 个线程；2 号 CPU 的核 ID 是 2、package ID 是 0。mini-vmm 的测试脚本还在 guest 里检查了每颗 CPU 的 APIC ID、核 ID、L2 和 L3 的共享 CPU 列表，断言 L2 每核私有（`L2-1`）、L3 由 0 到 3 号 CPU 共享（`L3-0-3`）。

### 13.3 阶段 9：每个 vCPU 一个线程

`vm_run()` 是阶段 9 的全部：

```c
int vm_run(struct vmm_vm *vm)
{
    struct sigaction sa;
    int i, started = 0, r = VMM_OK;

    /* 不带 SA_RESTART，保证 KVM_RUN 返回 EINTR */
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = kick_handler;          /* 空函数 */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGUSR1, &sa, NULL);

    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        if (pthread_create(&v->thread, NULL, vcpu_thread, v) != 0) {
            r = VMM_ERR_SYS;
            vm_request_stop(vm);
            break;
        }
        __atomic_store_n(&v->thread_started, true, __ATOMIC_RELEASE);
        started++;
    }

    for (i = 0; i < started; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        pthread_join(v->thread, NULL);
        __atomic_store_n(&v->thread_started, false, __ATOMIC_RELEASE);
        if (r == VMM_OK && v->result != VMM_OK)
            r = v->result;
    }
    return r;
}
```

主线程为每个 vCPU 创建一个线程，然后等所有线程结束，返回第一个出错的 vCPU 的错误码。每个 vCPU 线程做的事情非常简单：

```c
static void *vcpu_thread(void *arg)
{
    struct vmm_vcpu *v = arg;
    char name[16];

    snprintf(name, sizeof(name), "vcpu%d", v->id);
    pthread_setname_np(pthread_self(), name);    /* host 上 top -H 能看到 vcpu0..3 */

    v->result = vcpu_run_loop(v);
    ...
    /* 任何一个 vCPU 退出（poweroff、reset、出错）都意味着整机停下 */
    vm_request_stop(v->vm);
    return NULL;
}
```

给线程命名是一个小但很有用的细节：在 host 上用 `top -H -p <vmm 的 pid>` 就能直接看到每个 vCPU 的 CPU 占用，判断 guest 里的负载是否真的分散到了多个核上，也能看出哪个 vCPU 卡住了。实测 guest 里跑 4 个死循环时，host 上 `vcpu0` 到 `vcpu3` 各占接近 100%；用 `--append maxcpus=1` 启动时，AP 线程的 CPU 时间是 0，证明它们确实一直睡在 KVM 里等待一个永远不来的 SIPI。

注意所有 vCPU 线程是**同时**启动的，包括 AP。AP 线程启动后立刻进入 `KVM_RUN`，因为 `mp_state` 是 UNINITIALIZED 而在 KVM 里阻塞，不占 CPU。VMM 不需要知道 guest 什么时候会唤醒 AP。

### 13.4 run loop 的两处修改

多核之后，`vcpu_run_loop()` 必须正确处理两种“没有退出事件、只需要重进 `KVM_RUN`”的返回：

```c
int kvm_run(int vcpu_fd)
{
    int r;

    /* 两种“没有 exit 可处理、重进 KVM_RUN 即可”的返回：
     *   EINTR   vm_request_stop() 用 immediate_exit + SIGUSR1 把 vCPU
     *           踢出来（Ctrl-A x、另一个 vCPU 触发了停机）
     *   EAGAIN  AP 处于 KVM_MP_STATE_UNINITIALIZED 时 KVM_RUN 阻塞到
     *           收到 INIT/SIPI，醒来后返回 -EAGAIN 而不是进 guest，
     *           见 host arch/x86/kvm/x86.c kvm_arch_vcpu_ioctl_run()
     * 两者都不写（或不保证写）exit_reason，单独返回 VMM_ERR_INTR，
     * 让 run loop 回去检查 should_stop 后重进。 */
    r = ioctl(vcpu_fd, KVM_RUN, 0);
    if (r < 0 && (errno == EINTR || errno == EAGAIN))
        return VMM_ERR_INTR;
    ...
}

int vcpu_run_loop(struct vmm_vcpu *vcpu)
{
    int r;

    while (!vcpu->should_stop) {
        r = kvm_run(vcpu->fd);
        /* 被打断时 kvm_run 页里的 exit_reason 不一定有效（immediate_exit
         * 路径下 KVM 不会改写它，还是上一次的值），不能交给
         * vcpu_handle_exit，否则会把上一次的 IO 再执行一遍 */
        if (r == VMM_ERR_INTR)
            continue;
        if (r != VMM_OK)
            return r;

        r = vcpu_handle_exit(vcpu);
        if (r == VMM_ERR_EXIT)
            return VMM_OK;      /* 正常停机 */
        if (r != VMM_OK)
            return r;
    }
    return VMM_OK;
}
```

**`EAGAIN`**：AP 收到 INIT 后 `KVM_RUN` 以 `-EAGAIN` 返回（原理篇 8.4 节）。单核时代的 run loop 把所有负返回值都当错误，于是 AP 一醒来，它的线程就报错退出，并触发整机停机。这个问题是在读 host 源码时预先发现的：在写 SMP 代码之前，先把 `kvm_arch_vcpu_ioctl_run()` 读了一遍，看到了 `r = -EAGAIN` 这一行。

**不分发 `exit_reason`**：`EINTR` 和 `EAGAIN` 返回时，`kvm_run->exit_reason` 不保证被更新。原来的代码在 `EINTR` 时也会调用 `vcpu_handle_exit()`，而 `exit_reason` 里还是上一次的 `KVM_EXIT_IO`，于是上一次的 I/O 被重复执行了一遍：串口多输出一个字符，或者更糟，某个有副作用的寄存器写入被执行两次。所以被打断时直接 `continue`，回到循环顶部检查 `should_stop`。

### 13.5 停机：`immediate_exit` + 信号

原理篇 8.8 节讲了停机的竞态。mini-vmm 的实现是 `vm_request_stop()`，它可以在任何线程里调用，而且可以重复调用：

```c
void vm_request_stop(struct vmm_vm *vm)
{
    int i;

    vm->running = false;
    for (i = 0; i < vm->nr_vcpus; i++) {
        struct vmm_vcpu *v = &vm->vcpus[i];

        v->should_stop = true;
        if (v->run)
            __atomic_store_n(&v->run->immediate_exit, 1, __ATOMIC_SEQ_CST);
        if (__atomic_load_n(&v->thread_started, __ATOMIC_ACQUIRE) &&
            !pthread_equal(v->thread, pthread_self()))
            pthread_kill(v->thread, SIGUSR1);
    }
}
```

对每个 vCPU 做三件事，顺序很重要：

1. **置 `should_stop`**：run loop 在循环顶部检查它。
2. **置 `immediate_exit = 1`**：它在 `kvm_run` 共享页里，KVM 在 `KVM_RUN` 的入口检查它。线程如果刚检查完 `should_stop`、还没进入 `KVM_RUN`，进去之后会立刻以 `-EINTR` 返回。
3. **发 SIGUSR1**：线程如果已经在 `KVM_RUN` 里（比如睡在 guest 的 HLT 里），信号让它以 `-EINTR` 返回。

三者覆盖了线程可能处在的全部位置：

```
   vCPU 线程可能在的位置                 被哪一步挡住
   ─────────────────────────────────────────────────────────────
   run loop 顶部，还没检查 should_stop    ① should_stop
   检查完 should_stop，还没进 KVM_RUN     ② immediate_exit（进去立刻 -EINTR）
   在 KVM_RUN 里（guest 运行或 HLT 睡眠） ③ SIGUSR1（KVM 检测到信号挂起，退出）
   在 vcpu_handle_exit 里处理设备         处理完回到顶部，被 ① 挡住
```

只用信号不用 `immediate_exit`，第二个窗口就没人管：信号被空的处理函数“吃掉”，线程随后进入 `KVM_RUN`，guest 如果正在 idle，这个线程就永远睡下去，`pthread_join()` 永远等不到它，VMM 挂住。反过来，只用 `immediate_exit` 不用信号，第三个位置就没人管。

几个实现细节：

- **信号处理函数不能带 `SA_RESTART`**。带了这个标志，内核会在处理完信号后自动重启被打断的系统调用，`KVM_RUN` 就不会返回。
- **处理函数是空的**。它的全部作用就是“让一个信号被投递”，从而让 `KVM_RUN` 返回。不能用 `SIG_IGN`：被忽略的信号根本不会打断系统调用。
- **不给自己发信号**。触发停机的 vCPU 线程（比如写 PM1a_CNT 的那个）自己已经在返回的路上了，`pthread_equal` 检查跳过它。
- **`thread_started` 用 acquire/release 原子操作**。`vm_request_stop()` 可能在主线程还在创建线程的过程中被调用（比如某个 vCPU 线程一启动就出错），此时后面的 `v->thread` 还没有被赋值，不能对它调用 `pthread_kill()`。
- **依赖 `KVM_CAP_IMMEDIATE_EXIT`**（Linux 4.11 引入），所以在阶段 1 就检查它。

有三类事件会调用 `vm_request_stop()`：任何一个 vCPU 线程退出（guest 关机、guest 重启、出错）；console 线程收到 Ctrl-A x；vCPU 线程创建失败。测试脚本覆盖了前两类：4 核 guest panic 后经 i8042 复位退出，此时 panic 发生在哪个 vCPU 上是不确定的，其余三个必须被可靠地踢出来，否则 VMM 挂住直到超时；guest 执行 `poweroff` 时同理。

Ctrl-A x 退出时，VMM 会打印所有 vCPU 的寄存器状态。guest 卡住时，这是唯一能看到“每颗 CPU 停在哪条指令上”的线索：

```c
    /* Ctrl-A x 打断的现场一定要看：guest 卡住时这是唯一的线索 */
    if (r == VMM_OK && (vmm_log_level >= 3 || vm.user_stop)) {
        for (i = 0; i < vm.nr_vcpus; i++)
            vcpu_dump_state(&vm.vcpus[i]);
    }
```

### 13.6 小结：阶段 4 和阶段 9 的准备清单

- vCPU ID 从 0 连续编号，0 号是 BSP；多核只允许配合内核态 irqchip（Linux 模式）。
- 初始化过程中用 `cfg.nr_vcpus` 而不是递增中的 `vm->nr_vcpus`。
- CPUID 透传 host 特性，按 vCPU 改写 leaf `0x1`、`0xB`/`0x1F`、`0x80000008`、`0x8000001D`、`0x8000001E`，在第一次 `KVM_RUN` 之前设置。
- 每个 vCPU 一个线程，给线程命名，全部同时启动，AP 自己在 KVM 里等待 SIPI。
- `KVM_RUN` 返回 `EINTR` 或 `EAGAIN` 时不是错误，也不能分发 `exit_reason`，直接重进。
- 停机：`should_stop` + `immediate_exit` + 不带 `SA_RESTART` 的 SIGUSR1，缺一不可；任何 vCPU 退出都触发整机停机。

## 十四、写 VMM 的检查清单

前面五章按阶段讲完了 mini-vmm 的实现。这一章把其中所有“错一点 OS 就跑不起来”的细节汇总成一张清单，按阶段排列。以后自己写 VMM、或者 guest 起不来需要排查时，可以逐行对照。

每一行的格式是：**项目 → 必须是什么 → 为什么 → 错了会看到什么**。

### 14.1 KVM 与 VM

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| `/dev/kvm` 打开标志 | `O_RDWR \| O_CLOEXEC` | 避免 fd 泄漏给子进程 | 安全问题 |
| API 版本 | 等于 12 | ABI 基线 | — |
| capability 检查 | 运行时 `KVM_CHECK_EXTENSION`，不看头文件宏 | libc 头文件可能比内核新 | 运行到一半 ioctl 失败 |
| `kvm_run` mmap 长度 | `KVM_GET_VCPU_MMAP_SIZE` 的返回值 | 至少三页，随内核变化 | 访问 PIO 数据页时段错误 |
| `KVM_CREATE_IRQCHIP` 时机 | 创建任何 vCPU 之前 | LAPIC 在 `KVM_CREATE_VCPU` 时创建 | ioctl 返回 `EINVAL`；vCPU 没有 LAPIC |
| `KVM_CREATE_PIT2` 的 flags | `KVM_PIT_SPEAKER_DUMMY` | 端口 `0x61` 由 KVM 接管 | TSC 校准间歇失败，启动卡在 `skipped IO-APIC setup`，时间戳停在 `0.001000` |
| `KVM_CAP_IMMEDIATE_EXIT` | 必须支持 | 停机协议 | 多核停机时 VMM 挂住 |
| RAM memslot | GPA 从 0 开始，页对齐，不覆盖 `0xFEC00000`/`0xFEE00000` | 那两个地址是 IOAPIC/LAPIC | 中断控制器寄存器被 RAM 遮住 |

### 14.2 vCPU 与 CPUID

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| vCPU ID | 从 0 连续编号 | ID 即 APIC ID，0 号是 BSP | AP 起不来或 APIC ID 与固件表不符 |
| 多核的前提 | 有内核态 irqchip | 否则所有 vCPU 创建即 RUNNABLE | 多个 vCPU 从同一入口同时开跑 |
| CPUID 来源 | `KVM_GET_SUPPORTED_CPUID`，`E2BIG` 时扩容重试 | 透传 KVM 认可的 host 特性 | 不设 CPUID 时 guest 看到全 0，认为没有长模式，直接停住 |
| CPUID 设置时机 | 第一次 `KVM_RUN` 之前 | guest 启动即读取并缓存；5.16 起运行后禁止修改 | 修改不生效或 ioctl 失败 |
| leaf 1 EBX[31:24] | = vCPU ID | 初始 APIC ID | 所有 CPU 报同一个 APIC ID |
| leaf 1 EBX[23:16] 与 EDX.HTT | = N，N>1 时 HTT=1 | 逻辑处理器数 | 拓扑错误 |
| leaf `0xB`/`0x1F` | 清零，或完整正确地填写所有 subleaf | 半截的扩展拓扑会被 guest 采信 | 拓扑错误 |
| leaf `0x80000008` ECX | NC = N−1，ApicIdSize = ⌈log₂N⌉ | AMD 核数 | 核 ID 算错 |
| leaf `0x8000001D` | L1/L2 共享数 0，L3 共享数 N−1；保留结束项 | 缓存共享 | 调度域错误 |
| leaf `0x8000001E` | EAX = ID，EBX[7:0] = ID，ECX = 0 | 海光/AMD 的核 ID、节点 ID | 拓扑错误 |
| 总核数取值 | `cfg.nr_vcpus` | `vm->nr_vcpus` 在创建过程中递增 | 每个 vCPU 看到的核数不同 |

### 14.3 设备

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| PIO 数据位置 | `(u8 *)run + run->io.data_offset` | 数据页位置由内核决定 | 读写到错误位置 |
| `io.count` | 循环处理全部 | `rep ins/outs` 合并退出 | 丢数据 |
| 未注册端口 | 读 `0xFF`，写丢弃 | 浮空总线，Linux 依赖它判断设备不存在 | 报错退出则无法启动 |
| 设备注册区间 | 按真实占用注册 | 例如 i8042 是 `0x60` 和 `0x64` 两个端口 | 与别的设备冲突 |
| 串口 DLAB | LCR[7]=1 时偏移 0/1 是除数寄存器 | 驱动设置波特率 | 输出乱码字符 |
| 串口 IER | 只保留低 4 位 | autoconfig IER 测试 | 找不到 ttyS0 |
| 串口回环 | RTS→CTS、DTR→DSR、OUT1→RI、OUT2→DCD；回环数据不输出 | autoconfig 回环测试期望 MSR 高 4 位 = `0x90` | 找不到 ttyS0；终端出现垃圾字符 |
| 串口 IIR | FIFO 启用时高 2 位 = `11` | 被识别为 16550A | 被识别成 8250/16450，无 FIFO |
| 串口打开 THRI | THR 空时立即产生中断 | `serial8250_start_tx()` 靠它启动发送 | 控制台输出停止 |
| 串口 OUT2 | MCR.OUT2=0 时不拉线 | PC 平台的中断门控 | IRQ 探测误判 |
| 边沿中断 | 自己维护电平，变化时才 `KVM_IRQ_LINE`，每事件一个上升沿 | KVM 对同电平重复调用是空操作 | 第二个及以后的中断丢失 |
| RTC 寄存器 A | UIP=0 | Linux 等 UIP 清零 | 多出约 4 万次 exit、1.4 秒，`Unable to read current time from RTC` |
| RTC 编码 | 寄存器 B 声明 BCD，返回 BCD | 两者一致 | 系统时间是奇怪的日期 |
| RTC 寄存器 D | VRT=1 | CMOS 有效 | 时间被认为不可信 |
| RTC 月份与星期 | `tm_mon+1`、`tm_wday+1` | C 库与 RTC 约定不同 | 日期差一 |
| i8042 控制器命令 | 全部应答 | 驱动轮询等应答 | 忙等约 0.6 秒，`Can't read CTR` |
| i8042 AUX | 回环数据不置 AUXDATA；AUX_TEST 回 `0x01` | 让 AUX 口当场失败 | 探测超时 |
| i8042 新命令 | 清掉未读的旧应答 | 旧应答会被下一条命令误读 | AUX 判定错乱 |
| i8042 键盘应答 | 走 IRQ1 | PS/2 设备数据是中断驱动的 | atkbd 探测超时 |
| i8042 初值 | CTR = KBDINT\|SYSFLAG\|AUXDIS\|XLATE，输出端口 = RESET_N\|A20 | 模拟 BIOS 交接状态 | guest 读改写输出端口时“复位” |
| i8042 复位 | `0xF0`–`0xFF` 中 bit0=0 的命令、或写输出端口 bit0=0 | `reboot=k` 与 panic 重启 | VMM 收不到重启信号 |
| PM1_CNT 读 | SCI_EN=1 | 与 FADT `SMI_CMD=0` 配合 | Linux 尝试切换 ACPI 模式失败 |
| PM1_CNT 写 | SLP_EN 且 SLP_TYP=`_S5_` 的值 → 退出 | 关机 | `poweroff` 后 VMM 不退出 |
| 设备并发 | 分发路径持大锁；与非 vCPU 线程共享的设备另加锁，固定加锁顺序 | 多 vCPU 同时陷出 | 数据结构损坏、死锁 |

### 14.4 固件表与启动协议

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| vmlinux 摆放 | 按 `p_paddr`，bss 清零 | 物理地址 | 越界或内核数据错乱 |
| 入口 | 物理地址（`e_entry` 或换算） | 分页只有恒等映射 | 立即 triple fault |
| boot_params | 先整体清零 | 很多字段非零即启用某功能 | 走进奇怪的平台初始化 |
| `hdr.boot_flag` / `hdr.header` | `0xAA55` / `"HdrS"` | 协议约定 | — |
| `hdr.type_of_loader` | `0xFF` | 未注册 bootloader | — |
| `hdr.loadflags` | `LOADED_HIGH` | 内核在 1MB 以上 | — |
| `cmd_line_ptr` | 命令行物理地址，`\0` 结尾 | 内核拷走命令行 | 命令行为空，没有串口输出 |
| `ramdisk_image` / `ramdisk_size` | initrd 位置与大小（含 `ext_` 高 32 位） | 找到 initramfs | `VFS: Unable to mount root fs` |
| `acpi_rsdp_addr` | RSDP 物理地址 | 不必扫描 | 仍可扫描到，但多一重保险 |
| E820 低端 | `[0, 0x9FC00)` 为 RAM | AP trampoline 需要低端 RAM | panic 或 AP 起不来 |
| E820 保留区 | `[0x9FC00, 0x100000)` | 固件表在里面 | 固件表被内核覆盖 |
| RAM 上限 | ≤ 3GB（单 memslot 时） | 32 位 MMIO 空洞 | IOAPIC/LAPIC 被 RAM 遮住 |
| 命令行 | `console=ttyS0 earlyprintk=serial,ttyS0,115200 reboot=k panic=-1` | 输出、早期输出、重启与 panic 退出 | 没输出；VMM 不退出 |
| initrd 位置 | RAM 顶端向下 2MB 对齐，≥ 内核末尾，≤ `initrd_addr_max` | 避开内核和早期分配 | initrd 被踩坏 |
| initramfs 里的 busybox | 静态链接 | 没有动态链接器 | `/init` 执行失败 |
| ACPI 结构体 | `packed`，编译期断言大小 | 非对齐字段 | 所有偏移错位 |
| ACPI 校验和 | 最后计算；RSDP 先 20 字节再 36 字节 | 覆盖关系 | 表被拒绝 |
| RSDP 位置 | `[0xE0000, 0xFFFFF]` 内 16 字节对齐 | 扫描区 | 找不到 ACPI |
| RSDP revision | 2，使用 XSDT | 64 位地址 | — |
| XSDT 内容 | FADT、MADT；不列 DSDT | DSDT 由 FADT 引用 | — |
| FADT 签名 | `"FACP"` | 规范 | 找不到 FADT |
| FADT Flags bit 20 | 0（不是 HW-reduced） | 否则 Linux 放弃 PIT 和 8259A | TSC、LAPIC 定时器无法校准 |
| FADT PM1a | 端口与 PM1a 设备一致 | 关机写这里 | `poweroff` 无效 |
| FADT `SMI_CMD` | 0 | 已在 ACPI 模式 | — |
| FADT `CENTURY` | 与 RTC 世纪寄存器一致（`0x32`） | 读年份 | 年份错误 |
| DSDT | `_S5_` 包，SLP_TYP 与 PM1a 设备一致 | 关机 | `ACPI: PM: (supports S0)`，无 S5 |
| MADT LAPIC 地址 | `0xFEE00000` | KVM LAPIC | — |
| MADT flags | `PCAT_COMPAT` | 确实有 8259A | — |
| MADT LAPIC 条目 | 每 vCPU 一条，`apic_id` = vCPU ID，flags bit0 = 1 | 三方一致 | AP 停在 `hlt`，`failed to report alive state`；CPU 数变少 |
| MADT IOAPIC 条目 | ID = N，地址 `0xFEC00000`，GSI 基址 0 | 与 KVM 和 MP table 一致 | 中断不通 |
| MADT 中断源覆盖 | 不写 | KVM 默认路由恒等 | 时钟中断丢失，`check_timer()` 失败 |
| MP table 位置 | `0x9FC00`（或另两个扫描区），16 字节对齐 | 扫描区 | `acpi=off` 时退回单核 |
| MP 浮动指针 | `"_MP_"`，`feature1 = 0`，自身校验和 | 否则用默认配置 | 配置表被忽略 |
| MP 配置表 | `"PCMP"`，`oemcount`、`length` 填完再算校验和 | 规范 | 表被忽略 |
| MP 与 MADT | 描述同一台机器 | `acpi=off` 前后一致 | 两种启动方式行为不同 |
| guest 内核配置 | `CONFIG_ACPI` 或 `CONFIG_X86_MPPARSE` 至少一个可用 | 否则没有中断拓扑 | virtual wire，单核 |

### 14.5 页表、GDT 与寄存器

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| 恒等映射范围 | 覆盖内核、boot_params、命令行、initrd | 启动协议 | 内核访问这些数据时缺页 → triple fault |
| GDT 选择子 | 代码 `0x10`，数据 `0x18` | Linux 64 位启动协议 | 段重载时 `#GP` |
| 代码段描述符 | L=1、D=0 | L=1,D=1 是保留组合 | 加载时 `#GP` |
| sregs 段寄存器 | 从同一份描述符反解 | 与内存中 GDT 一致 | guest 重载段寄存器时崩溃 |
| `kvm_segment.limit` | G=1 时为 `(raw << 12) \| 0xFFF` | 字节粒度 | 段界限只有 1MB |
| sregs 读改写 | 先 `KVM_GET_SREGS` 再改 | 保留 KVM 给的合法初值 | `KVM_EXIT_FAIL_ENTRY` |
| CR0 | PE、PG 等 | 保护模式 + 分页 | — |
| CR4 | PAE | 长模式要求 | `KVM_SET_SREGS` 返回 `EINVAL` |
| EFER | LME **和** LMA | SET_SREGS 不经过硬件状态转换 | `KVM_SET_SREGS` 返回 `EINVAL` |
| IDTR | limit 0 可以 | 内核很快装自己的 IDT | 早期异常 → `KVM_EXIT_SHUTDOWN`（这是好事：失败立即可见） |
| RIP | 内核物理入口 | — | — |
| RSI | boot_params 物理地址 | 启动协议 | 内核读到全 0 的参数 |
| RFLAGS | `0x2`（IF=0） | bit 1 保留为 1；协议要求关中断 | `KVM_EXIT_FAIL_ENTRY` |
| AP 寄存器 | 不设置 | INIT/SIPI 由 KVM 处理 | 白做或行为不可预测 |

### 14.6 线程与停机

| 项目 | 必须 | 为什么 | 错了的症状 |
|---|---|---|---|
| vCPU 线程 | 每 vCPU 一个，全部同时启动 | AP 在 KVM 里自己等 | — |
| `KVM_RUN` 返回 `EAGAIN` | 重进 | AP 收到 INIT 后返回 | AP 一醒整机退出 |
| `KVM_RUN` 返回 `EINTR` | 重进 | 信号或 immediate_exit | 被当成错误 |
| 被打断时的 `exit_reason` | 不分发 | 是上一次的旧值 | 上一次的 I/O 重复执行 |
| 停机顺序 | `should_stop` → `immediate_exit=1` → 信号 | 覆盖全部窗口 | 某个 vCPU 永远睡在 HLT 里，VMM 挂住 |
| 信号处理函数 | 空函数，不带 `SA_RESTART`，不能是 `SIG_IGN` | 让 `KVM_RUN` 返回 `EINTR` | `KVM_RUN` 被自动重启 |
| 任一 vCPU 退出 | 触发整机停机 | 关机、重启、错误都是全局事件 | 其余 vCPU 继续跑 |
| 控制台 | raw 模式并在退出时恢复；不在前台进程组时不碰终端 | SIGTTOU/SIGTTIN | 终端乱掉；VMM 被挂起 |

## 十五、把裸 OS 跑起来：对照真实日志逐段解读

```
[   15.903697] reboot: Power down

```

guest 的 `poweroff` 让内核通过 ACPICA 查到 `\_S5_` 的 SLP_TYP（5），往 FADT 声明的 `PM1a_CNT_BLK`（端口 `0x604`）写入 `5 << 10 | SLP_EN`。这次写入以 `KVM_EXIT_IO` 回到执行它的那个 vCPU 线程，PM1a 设备回调返回 `VMM_ERR_EXIT`，这个线程的 run loop 结束，调用 `vm_request_stop()`；其余三个 vCPU（大概率睡在 guest 的 HLT 里）被 `immediate_exit` 和 SIGUSR1 踢出 `KVM_RUN`；主线程 join 全部线程，打印 `left guest (ok)`，退出码 0。

从第一行 `[INFO]` 到最后一行，本章的四大块——中断、时间、设备、多核——以及把它们描述给 guest 的固件表，全部参与了这次启动。

## 十六、调试方法与测试

### 16.1 guest 起不来时先看什么

guest 起不来的故障，按“死在哪里”可以分成几类，每一类有不同的首选证据：

| 现象 | 最可能的原因 | 首先看什么 |
|---|---|---|
| `KVM_EXIT_FAIL_ENTRY` | 寄存器状态不合法（RFLAGS bit 1、段属性、CR0/CR4/EFER 不自洽） | VMM 打印的 vCPU 状态 dump |
| `KVM_EXIT_SHUTDOWN`，没有任何内核日志 | 入口地址不对、页表没覆盖入口、GDT 与 sregs 不一致 | vCPU dump 里的 `RIP`、`CR3`、段寄存器；用 VMM 的页表遍历工具查入口地址的翻译 |
| 有少量日志，然后 `KVM_EXIT_SHUTDOWN` | 早期异常（IDT 还没装）；boot_params 字段错误 | 最后一行日志；vCPU dump 里的 `RIP` 对照 `System.map` |
| 日志停在某行，VMM CPU 100% | guest 在忙等某个设备：PIT、RTC、i8042 | 打开 VMM 的调试日志，看未处理端口的访问 |
| 日志停在某行，VMM CPU 0% | guest 在 HLT 里等一个永远不来的中断 | Ctrl-A x 看各 vCPU 停在哪；检查中断路由和固件表 |
| 能启动，但只有 1 颗 CPU | 固件表不可用（MPPARSE 没开、ACPI 表错误）；CPUID 与固件表不一致 | `smpboot: Allowing N CPUs`、`APIC:` 开头的日志 |
| 能启动，但慢了好几秒 | 某个设备探测超时 | 日志时间戳的跳变；对应时刻的端口访问 |
| 能启动，键盘输入没反应 | 串口中断没有新的上升沿；console 线程没起来 | `/proc/interrupts` 里 ttyS0 的计数 |
| `poweroff` 后 VMM 不退出 | PM1a 端口与 FADT 不一致；`_S5_` 缺失；停机协议有漏洞 | `ACPI: PM: (supports ...)`；Ctrl-A x 看哪个 vCPU 还在 |

这张表的核心思想是原理篇反复强调的：**guest 的很多故障是“安静”的**。它不报错，只是选择一条退化路径，或者停在某个等待循环里。这时候必须主动去收集证据，而不是盯着日志猜。

### 16.2 VMM 自带的观测手段

mini-vmm 在代码里预留了几个低成本但很有用的观测点：

**vCPU 状态 dump。** 任何异常退出（SHUTDOWN、FAIL_ENTRY、INTERNAL_ERROR、未知退出原因）都会打印该 vCPU 的通用寄存器、控制寄存器、EFER、段寄存器、GDTR/IDTR，以及 exit 统计。Ctrl-A x 退出时则打印**所有** vCPU 的状态，这是 guest 卡住时唯一能看到“每颗 CPU 停在哪条指令”的方法。拿到 `RIP` 之后，对照 vmlinux 的 `System.map` 或者用 `addr2line`，就能知道 guest 卡在哪个函数里（注意 `RIP` 是内核虚拟地址）。

**exit 统计。** 每个 vCPU 记录总 exit 数和 IO、MMIO、HLT 各类的次数。像 RTC 那个“多出 4 万次 exit”的问题，在这个数字上一眼就能看出来：一次启动的 IO exit 数量远超预期，再打开调试日志一看，全是端口 `0x71` 的读。

**未处理端口日志。** `-vv` 打开调试级别后，每一次访问未注册端口都会打印端口号、方向、宽度。PIT speaker 的问题（端口 `0x61`）、RTC 的问题（`0x70`/`0x71`）这类“某个设备没人模拟”的故障，都会在这里露面。

**页表遍历。** `--walk GVA` 在启动前按 VMM 构建的页表把一个地址的四级翻译过程打印出来，用来确认“入口地址到底有没有被映射到”。

### 16.3 host 侧的观测手段

**`top -H`。** vCPU 线程都有名字，`top -H -p $(pgrep -x vmm)` 能直接看到每个 vCPU 的 CPU 占用。100% 说明在 guest 里忙（或者在忙等），0% 说明在 KVM 里睡（HLT 或者等 SIPI）。多核问题首先看这里：某个 AP 线程一直是 0%，说明它从来没被唤醒。

**`perf kvm stat`。** 第一篇介绍过，它按退出原因统计 exit 的分布和耗时，是找性能问题的第一手段。在 host 上执行 `perf kvm stat live`，然后在 guest 里做一些操作，就能看到哪类退出最多。

**KVM tracepoint。** `trace-cmd record -e kvm:kvm_exit -e kvm:kvm_entry -e kvm:kvm_inj_virq -e kvm:kvm_apic_ipi` 能抓到每一次退出、每一次中断注入、每一次 IPI。排查“中断到底有没有被注入”这类问题时，`kvm_inj_virq` 是决定性的证据：看到对应向量被注入，说明问题在 guest 侧；没看到，说明问题在路由或设备侧。

### 16.4 测试：自动化的三个坑

mini-vmm 的每个阶段都有自动化测试（`tests/step1.sh`、`step2.sh`、`step6.sh`），思路是运行 VMM、抓取全部输出、断言其中包含或不包含某些字符串。本章相关的用例包括：4 核启动到 VFS panic 然后经 i8042 复位退出；4 核启动 initramfs、在 guest 里检查核数和拓扑、然后 poweroff。写这些测试时遇到了三个值得记录的坑，它们都与 VMM 本身无关，而与“怎么驱动一个交互式程序”有关。

**坑一：`timeout` 导致 VMM 被挂起。** 11.7 节讲过：`timeout` 把子进程放进后台进程组，VMM 碰终端就会被 SIGTTOU/SIGTTIN 停住。在 ssh 这类没有终端的环境里跑测试，stdin 不是终端，碰不到这个问题；换到交互式终端里跑，测试就挂住了。修复有两层：VMM 自己检测前台进程组，不在前台时不碰终端；测试脚本把 VMM 的 stdin 接到 `/dev/null`。人工运行时则用 `timeout --foreground`。

**坑二：只在无终端环境里测试是不够的。** 上面这个坑的教训是，测试环境要尽量接近真实使用环境。在非交互环境里要复现“有终端”的情况，可以用 Python 的 `pty` 模块创建一个伪终端：

```bash
python3 -c 'import pty; pty.spawn(["/bin/sh","-c","./tests/step6.sh -a"])'
```

这里用 `/bin/sh` 而不是 `bash -c`，是因为 `bash` 会读用户的配置文件，可能被切换到别的 shell。用 `script` 命令配合管道的做法实测会挂住，不建议使用。

**坑三：给 guest 喂命令要留间隔，断言要防回显。** 测试需要在 guest 的 shell 里执行命令，做法是把命令通过管道写进 VMM 的 stdin，console 线程再把它们送进串口的 RX FIFO。有两个问题：

- 串口 RX FIFO 只有 256 字节，一次灌入太多字符，FIFO 满了之后的字符会被丢掉。测试脚本先等 6 秒让 shell 起来，之后每条命令间隔 1 秒。
- guest 的 shell 会回显输入的命令。如果执行 `nproc` 然后断言输出里有 `4`，回显的命令行本身就可能让断言误判。正确的写法是让 guest **计算**出标记：执行 `echo NPROC-$(nproc)`，断言 `NPROC-4`。回显里只有 `$(nproc)`，只有真正执行后的输出里才有 `NPROC-4`。拓扑检查也是同样的写法，比如 `echo APIC-$(sed -n "s/^apicid.*: //p" /proc/cpuinfo | tr "\n" -)` 断言 `APIC-0-1-2-3-`。

### 16.5 负向断言

最后一个测试技巧：除了断言“应该出现什么”，还要断言“不应该出现什么”。4 核启动的用例里有一组负向断言：

```bash
expect_not "failed to report alive state"   # AP 没有上线
expect_not "do_boot_cpu failed"             # AP 唤醒失败
expect_not "APIC id mismatch"               # CPUID 与固件表不一致
expect_not "TSC synchronization"            # vCPU 之间 TSC 不同步
expect_not "stopped with error"             # 某个 vCPU 线程出错退出
expect_not "SHUTDOWN"                       # triple fault
```

原因还是那句话：guest 的很多故障是安静的。4 颗 CPU 最终都上线了，不代表过程中没有出过问题；Linux 在很多情况下会打印一行警告然后继续。这些警告就是早期发现“三方不一致”这类问题的最好证据。

### 16.6 用 tracepoint 串起一次按键的旅程

最后给一个把全文串起来的练习。在 host 上执行：

```bash
sudo trace-cmd record -e kvm:kvm_set_irq -e kvm:kvm_ioapic_set_irq \
     -e kvm:kvm_apic_accept_irq -e kvm:kvm_inj_virq -e kvm:kvm_pio -e kvm:kvm_eoi
```

然后在 guest 的 shell 里按一个键，停止记录，用 `trace-cmd report` 查看。按照本文讲过的机制，应该能依次看到：

1. `kvm_set_irq`：console 线程收到按键，串口模拟代码把 GSI 4 拉高，这是 `KVM_IRQ_LINE` 进入 KVM 的第一站（第十、十一章）。
2. `kvm_ioapic_set_irq`：KVM 按默认路由把 GSI 4 送到 IOAPIC 第 4 根引脚，读重定向表得到向量和目的 CPU（第三、四章）。
3. `kvm_apic_accept_irq`：目标 vCPU 的虚拟 LAPIC 在 IRR 里挂起这个向量，随后被 kick（第四章）。
4. `kvm_inj_virq`：目标 vCPU 重新进入 guest 前，`inject_pending_event()` 把向量写进 EVENTINJ（第四章）。
5. 若干条 `kvm_pio`：guest 的串口中断处理程序读 IIR、LSR、RBR，每次都是一次端口 I/O 陷出，回到 VMM 的串口模拟代码（第六、十一章）。读空 FIFO 后中断条件消失，串口把 GSI 4 拉低，又是一次 `kvm_set_irq`。
6. `kvm_eoi`：guest 的处理程序结束，写 LAPIC 的 EOI 寄存器，KVM 清掉虚拟 ISR 里的这一位（第二、四章）。

一次按键，六类事件，覆盖了中断从设备到 CPU 再回到中断控制器的完整闭环。如果某一步没有出现，问题就在它和上一步之间，这就是“证据驱动”的排障方式。

## 十七、小结与下一章

### 17.1 这一章新增了什么

第一篇结束时，VMM 的骨架是一个 `while (ioctl(KVM_RUN))` 循环。这一章没有改变这个骨架，而是在它的周围补上了一个操作系统对“机器”的全部期待：

**中断。** 真实硬件上，中断从设备出发，经过中断控制器仲裁，在指令边界被 CPU 接收，查 IDT 进入处理程序，最后以 EOI 收尾。虚拟化时，中断控制器的模拟因为访问太频繁而被放进 KVM；注入由硬件的 EVENTINJ 完成；guest 暂时不能接收时，用中断窗口等待；vCPU 在运行或睡眠时，用 kick 把它叫回来。VMM 要做的是在 vCPU 之前创建 irqchip，用 `KVM_IRQ_LINE` 拉线，并尊重边沿触发的语义。

**时间。** PIT 是校准一切的标准尺，TSC 靠它测频率，LAPIC 定时器靠它的时钟中断测频率。端口 `0x61` 这个“蜂鸣器端口”因此决定了系统能不能启动。TSC 原生执行，由硬件提供偏移和缩放，由 KVM 保证多 vCPU 同步。

**设备。** 一批 1980 年代的芯片：串口、RTC、键盘控制器，加上 ACPI 的电源管理寄存器。设备模拟的规格不在芯片手册里，而在驱动的探测逻辑里；未认领的端口遵循浮空总线约定。

**多核。** vCPU 就是线程，guest 的并行就是线程的并行。AP 的唤醒由 KVM 的 LAPIC 完成，VMM 只需让线程进入 `KVM_RUN` 并正确处理 `-EAGAIN`；CPUID 拓扑要按 vCPU 改写；停下所有 vCPU 要用 `immediate_exit` 加信号。

**固件。** 把以上一切告诉 guest：E820 描述内存，ACPI（以及作为退路的 MP table）描述 CPU、中断控制器和电源管理，启动协议交接 CPU 状态、命令行和 initrd。

贯穿全部五块的，是一条原则：

> **固件的描述、CPUID 的自报、KVM 实际模拟的硬件，三者必须完全一致。**

真实硬件由同一块主板保证这种一致性；虚拟机里，一致性完全由 VMM 作者保证。本章遇到的大部分坑——时钟中断丢失、SMP 被关闭、AP 起不来、拓扑错乱——本质上都是某两方之间的不一致。

### 17.3 这一章留下的问题

本章的实现能跑，但离一台“好用”的虚拟机还很远。几个明显的局限：

- **所有 I/O 都走 PIO exit，一个字节一次陷出。** 串口每输出一个字符就要一次 `#VMEXIT` + 回到用户态 + `write()` 系统调用。启动日志只有几十 KB，这不是问题；但如果要跑一块磁盘或者一块网卡，这种方式的吞吐量会低得无法接受。
- **中断注入要经过一次 ioctl。** 设备每次拉线都是一次 `KVM_IRQ_LINE` 系统调用。
- **没有 PCI。** 日志里的 `PCI: System does not support PCI` 意味着现代设备根本无法接入。
- **内存不超过 3GB。** 还没有 MMIO 空洞和第二个 memslot。
- **只支持 vmlinux。** 不能直接启动发行版的 bzImage。

### 17.4 下一章

下一章进入 **VirtIO**，也就是原理篇 6.1 节表格里的第二条路线：半虚拟化。VirtIO 设计了一种“为虚拟化而生”的设备接口，guest 和 VMM 通过共享内存里的环形队列（virtqueue）批量交换数据，一次通知可以传输成百上千个请求。配合 KVM 的两个机制——`ioeventfd`（把 guest 对某个地址的写在内核里直接转成一个 eventfd 信号，不回用户态）和 `irqfd`（把一个 eventfd 绑定到一个 GSI，写 eventfd 就注入中断，不用 ioctl）——本章讲的 PIO exit 和 `KVM_IRQ_LINE` 将从 I/O 的热路径上被移走。

但无论加到多复杂，本章建立的这些东西都不会消失：VirtIO 设备的中断仍然要经过 IOAPIC 或 MSI 到达 LAPIC，仍然要被注入；VirtIO-MMIO 设备的地址仍然要写进固件表；多个 vCPU 线程仍然会并发地访问设备模型。
