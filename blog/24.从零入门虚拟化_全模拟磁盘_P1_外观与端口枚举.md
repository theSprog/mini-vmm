全模拟网卡那一组文章让 guest 用原厂驱动驱动了一块 82540EM。这一组换成磁盘：mini-vmm 模拟一个 AHCI SATA 控制器，后面挂一块 ATA 磁盘，guest 用 Linux 自带的 ahci 驱动，能 `mkfs`、能挂载，也能把它当根文件系统启动。到后面 arch-distro 里程碑，一个完整的发行版就装在这块盘上。

磁盘这一路要讲的东西和网卡一样多，按机制分成几 P，每 P 先讲原理，再讲 mini-vmm 的实现：

| P | 内容 |
|---|---|
| P1（本篇） | 外观与端口枚举：PCI 身份、ABAR、全局寄存器、端口的启动、COMRESET 与设备签名 |
| P2 | 命令的生命周期与中断：命令列表、命令表、FIS 接收区，从写 PxCI 到收到 D2H FIS，三级中断，出错停端口与恢复 |
| P3 | IDENTIFY 与 PIO：驱动眼里的盘长什么样，PIO Setup FIS，SET FEATURES |
| P4 | 后端与 DMA 读写：`--drive` 与 raw 镜像，PRDT 的逐项检查，写缓存与 FLUSH，端到端验证 |
| P5 | NCQ：PxSACT、FPDMA 命令与 SDB FIS，出错之后经日志 10h 恢复 |

## 一、磁盘控制器在哪一层

### 1.1 三份规范，各管一段

在 guest 里执行 `cat /mnt/blob`，数据从磁盘一路上来，经过的层次是：

```text
guest 用户态     cat
guest 内核       VFS → ext2 → 块层 → sd（SCSI 磁盘）→ libata（把 SCSI 命令翻译成 ATA 命令）
                 → ahci 驱动
------------------------------------------------------------- MMIO / DMA / 中断
HBA（控制器）    AHCI：寄存器、命令列表、FIS 接收区、PRDT          ← mini-vmm 模拟
SATA 链路        SATA：FIS（帧）、链路建立、签名                  ← mini-vmm 模拟
设备（磁盘）     ATA：IDENTIFY、READ/WRITE DMA、FLUSH CACHE ...   ← mini-vmm 模拟
------------------------------------------------------------- preadv / pwritev / fdatasync
host             raw 镜像文件
```

虚线之间的三层原本是三块东西：主板上的控制器芯片（HBA，Host Bus Adapter）、一根 SATA 线、一块硬盘。它们各有一份规范，都放在 `ref/` 里：

- **AHCI 1.3.1**（`ref/serial-ata-ahci-spec-rev1-3-1.pdf`）：HBA 的寄存器和它在内存里使用的数据结构。驱动只和这一层打交道。
- **SATA 3.0**（`ref/SerialATA_Revision_3_0_Gold.pdf`）：HBA 和设备之间传的帧，叫 FIS（Frame Information Structure），以及链路怎么建立、设备复位后报告什么签名。
- **ATA8-ACS**（`ref/ATA8-ACS_d1699r4a.pdf`）：设备认识的命令，比如 IDENTIFY DEVICE、READ DMA EXT。命令本身装在 FIS 里传给设备。

mini-vmm 把三层都模拟了，但三层之间的“物理”部分（线上的电信号、链路的速率协商）没有任何可观察的效果，所以被压缩成了瞬间完成的状态切换，第五章会细讲。

### 1.2 为什么选 AHCI

- Linux 的 ahci 驱动按 PCI 类代码绑定，不认厂商。只要类代码对，任何厂商的 AHCI 控制器都用同一个驱动，mini-vmm 不需要冒充哪一款真实芯片（第二章）。
- 它的内存结构有三层：命令列表 → 命令表 → PRDT（物理区域描述符表）。和 e1000 的描述符环、以后 virtio-blk 的 virtqueue 放在一起，正好看出“设备怎样从 guest 内存里取命令”的三种不同设计。
- SATA 盘是最普通的启动盘。arch-distro 里程碑要求发行版从 AHCI 盘启动，用的就是这里的设备。
- QEMU 有同样的设备（`-device ahci` 加 `ide-hd`），同一个 guest 可以拿去对照。

### 1.3 驱动的探测顺序

在讲每个部件之前，先看 Linux 从发现 PCI 设备到认出磁盘走过的路（`drivers/ata/ahci.c`、`libahci.c`、`libata-sata.c`）：

```text
ahci_init_one                                   ahci.c
  ├─ pcim_iomap_regions_request_all(BAR5)       映射 ABAR
  ├─ ahci_pci_save_initial_config               读 CAP、VS、CAP2、PI、每个端口的 PxCMD
  ├─ ahci_pci_reset_controller                  GHC.HR 复位整个 HBA，写回 CAP/PI
  ├─ ahci_pci_init_controller                   每个端口：确认空闲、清 SERR/IS；最后 GHC.IE=1
  ├─ pci_set_master
  └─ ata_host_activate
       ├─ ahci_port_start（每个端口）           分配命令列表和 FIS 接收区，FRE=1，ST=1
       └─ 错误处理线程（每个端口各一个，并行）
            └─ ahci_hardreset                   COMRESET，等链路稳定，读 PxTFD 和 PxSIG
                 → 有盘：IDENTIFY DEVICE、SET FEATURES ...（P3）
                 → 没盘：打印 "SATA link down"
```

把 `--trace-mmio` 打开跑一次（一个控制器，端口 0 挂一块 64 MiB 的盘），从启动到关机，ABAR 上一共只有 605 次访问（读 408、写 197）。其中 164 次是读 PxSSTS（链路状态），185 次是读写 PxCMD（端口命令与状态），真正发命令的 PxCI 写只有 7 次。和 e1000 的探测动辄几千次 EEPROM 位操作相比，AHCI 的寄存器接口干净得多：控制器的大部分工作都通过内存里的数据结构完成，寄存器只用来启动和收尾。

dmesg 里对应的几行是：

```text
[1.348] ahci 0000:00:01.0: AHCI 0001.0301 32 slots 6 ports 6 Gbps 0x3f impl SATA mode
[1.352] ahci 0000:00:01.0: flags: 64bit ncq clo only pio
[1.375] ata1: SATA max UDMA/133 abar m8192@0xc0000000 port 0xc0000100 irq 17
...
[1.714] ata2: SATA link down (SStatus 0 SControl 300)
[1.720] ata1: SATA link up 6.0 Gbps (SStatus 133 SControl 300)
...
[1.731] ata1.00: ATA-8: MINIVMM AHCI DISK, 1.0, max UDMA/133
```

从驱动加载（1.346 秒）到链路报告（1.714 秒）花了将近 0.4 秒，而 mini-vmm 里的链路是瞬间建立的。这段时间花在哪里，是第五章的一个小问题。

## 二、PCI 外观

### 2.1 按类代码绑定

PCI 设备靠 vendor/device ID 和类代码让驱动认出来。ahci 驱动的匹配表 `ahci_pci_tbl`（`ahci.c`）前面几百行是具体芯片，最后有一条通配：

```c
/* Generic, PCI class code for AHCI */
{ PCI_ANY_ID, PCI_ANY_ID, PCI_ANY_ID, PCI_ANY_ID,
  PCI_CLASS_STORAGE_SATA_AHCI, 0xffffff, board_ahci },
```

`PCI_CLASS_STORAGE_SATA_AHCI` 是 0x010601：基类 01（大容量存储）、子类 06（SATA）、编程接口 01（AHCI 1.0）。mini-vmm 的控制器就用这个类代码，vendor 用本项目的 0x1234，device 0x0003：

```text
[INFO] pci 00:01.0 ahci BAR5 [mem 0xc0000000-0xc0001fff]
[INFO] pci 00:01.0 ahci [1234:0003] class 010601
[INFO] pci 00:01.0 ahci INTA -> GSI 17
```

为什么不干脆冒充一款 Intel ICH9，像 QEMU 那样？因为匹配到 Intel 的表项之后，驱动在复位控制器时会多走一段 `ahci_intel_pcs_quirk()`：

```c
if (!id || id->vendor != PCI_VENDOR_ID_INTEL)
        return;
...
pci_read_config_word(pdev, PCS_6, &tmp16);          /* 配置空间 0x92 */
if ((tmp16 & hpriv->port_map) != hpriv->port_map) {
        tmp16 |= hpriv->port_map;
        pci_write_config_word(pdev, PCS_6, tmp16);
}
```

0x92 是 ICH 芯片组私有的端口使能寄存器，AHCI 规范里没有它。冒充 Intel 就要连带模拟这个寄存器，以及驱动针对各代 Intel 芯片的其他 quirk。用自己的 vendor ID 走通配表项，驱动里没有任何厂商相关的分支，模拟的对象就只是 AHCI 规范本身。

这也顺带改正了 `include/pci/pci.h` 里一句旧注释：它原来说 vendor 0x1234 的设备“guest 不会给它们绑定任何驱动”。按 vendor/device 匹配的驱动确实不会绑上来，但按类代码匹配的驱动不看 vendor，AHCI 正是这样绑定的。

### 2.2 ABAR：为什么在 BAR5、为什么是 8 KiB

AHCI 控制器的寄存器窗口叫 ABAR（AHCI Base Address），规范第 2.1.11 节把它定在 PCI 配置空间的 0x24，也就是 BAR5。BAR0 到 BAR4 留给兼容老式 IDE 的 I/O 端口，纯 AHCI 控制器不用它们。Linux 里对应的常量是 `AHCI_PCI_BAR_STANDARD = 5`。

窗口的布局是：

```text
ABAR + 0x000 .. 0x02B   全局寄存器（CAP、GHC、IS、PI、VS ...）
ABAR + 0x0A0 .. 0x0FF   厂商自定义
ABAR + 0x100 + i*0x80   端口 i 的寄存器，每个端口 0x80 字节，i = 0..31
```

32 个端口时最后一个端口结束在 0x10FF，向上取 2 的幂就是 8 KiB。规范给 ABAR 的定义是“bit 31:13 可写”，也就是 8 KiB 对齐、8 KiB 大小，正好容纳 32 个端口；端口少的控制器可以把更多位做成可写、窗口更小。mini-vmm 只有 6 个端口，用 1 KiB 就够，但仍然给满 8 KiB：以后端口数变了不用动 BAR，驱动也不在乎窗口里多出来的空间。

驱动给每个端口打印的 `abar m8192@0xc0000000 port 0xc0000100` 就是这个布局：ABAR 在 0xC0000000，大小 8192，端口 0 在 +0x100。

## 三、全局寄存器

### 3.1 CAP：控制器的能力清单

驱动最先读的寄存器是 CAP（第 3.1.1 节）。mini-vmm 读回 0xC1349F05，逐个字段拆开：

| 位 | 字段 | 值 | 含义 |
|---|---|---|---|
| 31 | S64A | 1 | 支持 64 位地址，命令列表、FIS 接收区、数据缓冲区可以在 4 GiB 以上 |
| 30 | SNCQ | 1 | 支持 NCQ（P5） |
| 24 | SCLO | 1 | 支持 PxCMD.CLO（命令列表覆盖，P2 的错误恢复用到） |
| 23:20 | ISS | 3 | 接口最高速率 Gen3，6 Gbps |
| 18 | SAM | 1 | 只支持 AHCI 模式，没有老式 IDE 兼容模式 |
| 15 | PMD | 1 | PIO 传输可以跨多个 DRQ 块 |
| 12:8 | NCS | 31 | 32 个命令槽（字段值是“槽数减一”） |
| 4:0 | NP | 5 | 6 个端口（同样是“减一”） |

Linux 打印的 `flags: 64bit ncq clo only pio` 就是从 CAP 里翻译出来的：`64bit` 是 S64A，`ncq` 是 SNCQ，`clo` 是 SCLO，`only` 是 SAM，`pio` 是 PMD。

CAP 里为 0 的位同样重要。端口倍增器（SPM）、链路省电（SALP、SSC）、交错上电（SSS）、命令完成合并（CCC）、机箱管理（EMS）在 mini-vmm 里都是 0。对全模拟设备来说，能力位是一份承诺：声明了 SPM，驱动就会在硬复位之后再发软复位去探测倍增器；声明了 SALP，驱动就会去写链路省电相关的寄存器。不声明，驱动就根本不走这些流程，模型也就不用实现它们。这和 e1000 里“驱动不走的路径可以不做”是同一个道理，只是这里由设备自己通过能力位决定驱动走哪些路径。

### 3.2 PI、VS、CAP2

- **PI**（Ports Implemented，第 3.1.4 节）= 0x3F：端口 0 到 5 都存在。CAP.NP 只说有几个端口，PI 说是哪几个，真实芯片可能跳着编号。dmesg 里的 `0x3f impl` 就是它。
- **VS**（第 3.1.5 节）= 0x00010301：规范版本 1.3.1，dmesg 打印成 `AHCI 0001.0301`。
- **CAP2**（扩展能力）= 0：BIOS/OS 交接、设备休眠、自动链路状态切换都不支持。驱动只在 VS ≥ 1.2 时才读 CAP2（`ahci_save_initial_config`），mini-vmm 报 1.3.1，所以 trace 里能看到这一次读。

### 3.3 GHC 与 HBA 复位

GHC（Global HBA Control，第 3.1.2 节）里有三个位：

- **AE**（bit 31，AHCI Enable）：1 表示控制器工作在 AHCI 模式。CAP.SAM=1 的控制器没有别的模式，AE 只读为 1。
- **HR**（bit 0，HBA Reset）：写 1 复位整个控制器，复位完成后硬件把它清 0。
- **IE**（bit 1，Interrupt Enable）：全局中断开关，P2 细讲。

驱动复位控制器的过程在 trace 里是这样的（行号是 trace 文件里的序号）：

```text
 14  GHC   R 80000000      ahci_reset_controller：ahci_enable_ahci 先确认 AE=1
 15  GHC   R 80000000
 16  GHC   W 80000001      置 HR
 17  GHC   R 80000000      读回 HR 已经是 0：复位完成
 20  CAP   W c1349f05      ahci_restore_initial_config：把复位前读到的值写回去
 21  PI    W 0000003f
 23  P0CMD W 00000000      ...每个端口的 PxCMD 也写回“初始值”
 29  P0CMD R 00000006      读回来仍然是 6
```

两个细节：

**驱动把 CAP、PI 写回去。** 规范里 CAP、PI 是 HwInit 类型，由 BIOS 在上电时设好，对 OS 来说只读；但有些芯片复位后会把它们清掉，所以驱动在复位前保存一份、复位后写回。对 mini-vmm 来说这些值是常量，写入直接忽略就对了。

**写 PxCMD = 0 之后读回 6。** 驱动写回的是复位前 PxCMD 里“能力位”（`PORT_CMD_CAP`：热插拔、机械开关、冷插拔检测、外置端口、FBS）的值，mini-vmm 这些位全为 0，所以写的是 0。读回的 6 是 bit 1 SUD（Spin-Up Device）和 bit 2 POD（Power On Device）。按第 3.3.7 节，控制器不支持交错上电（CAP.SSS=0）时 SUD 只读为 1，不支持冷插拔检测（PxCMD.CPD=0）时 POD 只读为 1。也就是说，这两个位在 mini-vmm 里是“设备永远通着电、转着盘”的意思，写不掉。

mini-vmm 的 HR 是同步完成的：写 HR 的那次 MMIO exit 里就把整个控制器复位完了，下一次读 GHC 时 HR 已经是 0。驱动的 `ata_wait_register()` 本来要按 10 ms 一次轮询，最多等 1 秒，这里一次都不用等。

## 四、端口寄存器与端口的启动

### 4.1 端口寄存器一览

每个端口 0x80 字节，下面是 mini-vmm 实现的那些（第 3.3 节）：

| 偏移 | 寄存器 | 作用 | 详见 |
|---|---|---|---|
| 0x00/0x04 | PxCLB/PxCLBU | 命令列表在 guest 内存里的地址，1 KiB 对齐 | P2 |
| 0x08/0x0C | PxFB/PxFBU | FIS 接收区的地址，256 字节对齐 | P2 |
| 0x10 | PxIS | 端口中断状态，写 1 清除 | P2 |
| 0x14 | PxIE | 端口中断使能 | P2 |
| 0x18 | PxCMD | 端口的命令位和状态位 | 本章 |
| 0x20 | PxTFD | 设备最近报告的状态和错误寄存器 | 第五章、P2 |
| 0x24 | PxSIG | 设备复位后报告的签名 | 第五章 |
| 0x28 | PxSSTS | 链路状态（SATA 的 SStatus） | 第五章 |
| 0x2C | PxSCTL | 链路控制（SControl），COMRESET 从这里发 | 第五章 |
| 0x30 | PxSERR | 链路错误和诊断位，写 1 清除 | 第五章 |
| 0x34 | PxSACT | NCQ 命令的活动位 | P5 |
| 0x38 | PxCI | 命令发出位，每个命令槽一位 | P2 |

通知、FIS 交换、设备休眠（0x3C 之后）对应的能力都没声明，读回 0、写入忽略。

### 4.2 PxCMD：成对的“命令位”和“状态位”

PxCMD 里有两对位值得单独讲，它们是理解 AHCI 端口状态机的钥匙：

| 软件写的位 | 硬件报告的位 | 含义 |
|---|---|---|
| FRE（bit 4，FIS Receive Enable） | FR（bit 14，FIS Receive Running） | 允许 HBA 把收到的 FIS 写进 FIS 接收区 |
| ST（bit 0，Start） | CR（bit 15，Command List Running） | 允许 HBA 处理命令列表 |

软件写的是“请求”，硬件报告的是“现状”。真实控制器里两者之间有延迟：清掉 ST 之后，HBA 可能正在处理一条命令，要等它停在一个安全点，CR 才会变 0。规范第 10.1.2 节、第 10.3 节因此规定了严格的顺序：

1. 改 PxCLB/PxFB 之前，端口必须空闲：ST、CR、FRE、FR 全为 0。
2. 设好 PxFB 之后才能置 FRE，等 FR 变 1。
3. FRE=1、CR=0、设备就绪之后才能置 ST。
4. 停端口时先清 ST，等 CR 变 0（最多 500 ms），再清 FRE，等 FR 变 0。

trace 里 `ahci_port_start()` 启动端口 0 的过程正好是这个顺序：

```text
 86  P0CMD  R 00000006
 87  P0CMD  W 10000006     ahci_power_up：ICC=1（链路进入 active）
 88  P0CLBU W 00000000     ahci_start_fis_rx：命令列表在 0x042c0000
 89  P0CLB  W 042c0000
 90  P0FBU  W 00000000                        FIS 接收区在 0x042c0400
 91  P0FB   W 042c0400
 93  P0CMD  W 00000016     置 FRE
 94  P0CMD  R 00004016     FR 已经是 1
 96  P0CMD  W 00004017     ahci_start_engine：置 ST
 97  P0CMD  R 0000c017     CR 已经是 1
100  P0IE   W 00000000     端口先“冻结”，中断全关，等错误处理线程来复位链路
```

驱动给每个端口分配的一块内存里，前 1 KiB 是命令列表（32 个槽 × 32 字节），紧跟着的 256 字节是 FIS 接收区，所以 PxFB 正好比 PxCLB 大 0x400。

mini-vmm 里状态位不单独存储，而是读的时候从命令位算出来（`port_read()`）：

```c
case AHCI_PxCMD:
    /* POD、SUD 在不支持冷插拔检测、交错上电时只读为 1 */
    v = p->cmd | AHCI_PxCMD_POD | AHCI_PxCMD_SUD;
    if (p->cmd & AHCI_PxCMD_FRE)
        v |= AHCI_PxCMD_FR;
    if ((p->cmd & AHCI_PxCMD_ST) && !p->halted)
        v |= AHCI_PxCMD_CR;
    ...
```

因为命令在写 PxCI 的那次 exit 里就同步执行完了（P2），HBA 永远不会“正在处理一条命令”，所以 FR 跟着 FRE、CR 跟着 ST 立刻变化，驱动的每一次等待都是第一次读就满足。唯一的例外是 `halted`：命令出错后端口停下，CR 变 0 而 ST 还是 1，这是 P2 错误恢复的内容。

ICC（bit 31:28，Interface Communication Control）是另一种“请求”：软件写 1 表示让链路回到 active，硬件完成后读回 0。mini-vmm 的链路永远是 active，所以 ICC 不在可写的掩码 `PxCMD_RW_MASK` 里，写进去立刻就是 0。

## 五、链路：COMRESET、签名与“没插盘”

### 5.1 链路是怎么建立的

真实的 SATA 线上，HBA 和设备之间要先经过一段带外信号（OOB）握手，链路才可用：

```text
HBA                              设备
 │── COMRESET ──────────────────▶│   HBA：复位设备
 │◀────────────────── COMINIT ───│   设备：我在，已复位
 │── COMWAKE ───────────────────▶│
 │◀────────────────── COMWAKE ───│
 │◀═══════ 速率协商、对齐 ═══════▶│
 │          PhyRdy                │   链路就绪
 │◀── D2H Register FIS（签名）───│   设备报告自己是什么
```

软件看到的是这个过程的结果，都在端口的几个 SATA 寄存器里（第 3.3.10–3.3.12 节）：

- **PxSSTS**（SStatus），三个字段：DET（bit 3:0）是设备检测状态，0 = 没有设备、1 = 有设备但链路没建立、3 = 有设备且链路已建立、4 = 链路被关掉；SPD（bit 7:4）是协商出的速率，1/2/3 对应 1.5/3/6 Gbps；IPM（bit 11:8）是链路电源状态，1 = active。mini-vmm 有盘的端口报 0x133：active、Gen3、链路已建立。
- **PxSCTL**（SControl）：DET 字段写 1 就是发 COMRESET，写回 0 结束复位、开始建链，写 4 关掉链路；SPD 字段限制最高速率（0 = 不限）；IPM 字段禁止链路进入省电状态，Linux 写 3 表示两种省电状态都禁止。
- **PxSERR**（SError）：链路错误和诊断位。和这里有关的是 DIAG.X（bit 26，收到了 COMINIT，即设备换过或复位过）和 DIAG.N（bit 16，PhyRdy 变过）。

链路建立之后，设备发来第一个 D2H Register FIS，里面的寄存器值就是**签名**：Count = 01h，LBA = 000001h 表示普通的 ATA 设备（ATA8-ACS 表 92），LBA 的中间两个字节取别的值时表示 ATAPI 设备（光驱）、端口倍增器等其他类型。HBA 把这四个字节拼进 PxSIG（第 3.3.9 节），同时用 FIS 里的状态更新 PxTFD。驱动读 PxSIG 决定这个端口上是什么（`ahci_dev_classify()`）：

```c
tmp = readl(port_mmio + PORT_SIG);
tf.lbah  = (tmp >> 24) & 0xff;
tf.lbam  = (tmp >> 16) & 0xff;
tf.lbal  = (tmp >> 8)  & 0xff;
tf.nsect = (tmp)       & 0xff;
return ata_port_classify(ap, &tf);
```

所以 ATA 磁盘的 PxSIG 是 0x00000101：最低字节是 Count（01），往上依次是 LBA Low（01）、Mid（00）、High（00）。字节顺序弄反（0x01010000）时 Linux 会把它当成未知设备，单元测试里专门有这样一个错误实现（第七章）。

### 5.2 驱动怎么复位一个端口

端口启动之后，libata 的错误处理线程对每个端口做一次硬复位，入口是 `ahci_do_hardreset()`（`libahci.c`）：

```c
hpriv->stop_engine(ap);                      /* 清 ST，等 CR 变 0 */

/* clear D2H reception area to properly wait for D2H FIS */
ata_tf_init(link->device, &tf);
tf.status = ATA_BUSY;
ata_tf_to_fis(&tf, 0, 0, d2h_fis);           /* 在内存里预先写一个 BSY 的假 FIS */

ahci_port_clear_pending_irq(ap);             /* 清 PxSERR、PxIS、IS 里这个端口的位 */

rc = sata_link_hardreset(link, timing, deadline, online, ahci_check_ready);

hpriv->start_engine(ap);                     /* 重新置 ST */

if (*online)
        *class = ahci_dev_classify(ap);      /* 读 PxSIG */
```

`sata_link_hardreset()`（`libata-sata.c`）再往下：

```c
scontrol = (scontrol & 0x0f0) | 0x301;       /* IPM=3，DET=1：发 COMRESET */
sata_scr_write_flush(link, SCR_CONTROL, scontrol);
ata_msleep(link->ap, 1);                     /* AHCI 第 10.4.2 节：至少 1 ms */
sata_link_resume(link, timing, deadline);    /* 写 0x300，等链路稳定 */
...
ata_wait_ready(link, deadline, check_ready); /* 轮询 PxTFD，等 BSY=0 */
```

trace 里端口 0 对应的几行：

```text
184  P0CMD  W 0000c016   停引擎：清 ST
185  P0CMD  R 00004016   CR 立刻是 0
186  P0SERR R 00000000   清 SERR、PxIS、IS
...
192  P0SCTL W 00000301   COMRESET
231  P0SCTL W 00000300   1.2 ms 之后结束复位
266  P0SCTL R 00000300   ...203 ms 之后才第一次读链路状态
267  P0SSTS R 00000133
         （每 5 ms 读一次 PxSSTS，持续约 100 ms）
437  P0TFD  R 00000140   ahci_check_ready：BSY=0，设备就绪
439  P0CMD  W 00004017   重新置 ST
441  P0SIG  R 00000101   ATA 磁盘
```

这就回答了第一章留下的问题：mini-vmm 写完 0x300 链路就已经建好了，可驱动还是等了 0.3 秒，原因全在 `sata_link_resume()` 里：

- 写完 SControl 先睡 200 ms，源码注释是“有些 PHY 在恢复后马上被频繁读 SStatus 会出问题”。
- 然后 `sata_link_debounce()` 按 `sata_deb_timing_normal = { 5, 100, 2000 }` 每 5 ms 读一次 SStatus，DET 连续 100 ms 不变才算链路稳定。端口 0 的 PxSSTS 在这段时间里被读了 27 次。

六个端口的错误处理线程是并行的，所以总共也只等了这一个 0.3 秒，而不是六倍。dmesg 里各端口的 link up/down 打印顺序乱序（ata2 比 ata1 先），就是并行的痕迹。这段等待是为真实 PHY 设计的，对虚拟设备没有意义，但它是 Linux 的固定行为，VMM 改不了，mini-vmm 磁盘探测的时间大头就在这里。

还有一个细节值得注意：驱动在发 COMRESET 之前，在 FIS 接收区的 D2H 位置预先写了一个 BSY=1 的假 FIS，注释说是为了“正确地等待 D2H FIS”。但 `ahci_check_ready()` 判断设备就绪时读的是 PxTFD 寄存器，并不读内存里的 FIS，trace 里也只有这一次 PxTFD 读。libahci 里读 FIS 接收区 D2H 位置的是 `ahci_qc_fill_rtf()`（取命令的结果寄存器，P2）。预写 BSY 的作用应当是让这类读取拿不到复位前留下的旧值，这是从代码推断的，源码注释没有展开。

### 5.3 mini-vmm 的实现

链路相关的状态切换都在 `src/devices/ahci.c` 的几个小函数里。写 PxSCTL 时按 DET 字段的变化分三种情况：

```c
static void write_sctl(struct ahci *s, struct ahci_port *p, uint32_t val)
{
    uint32_t old_det = p->sctl & AHCI_SCTL_DET_MASK;
    uint32_t det = val & AHCI_SCTL_DET_MASK;

    p->sctl = val & PxSCTL_MASK;
    if (det == AHCI_SCTL_DET_COMRESET)
        link_down(p, AHCI_SSTS_DET_NONE);         /* 1：发 COMRESET，链路断开 */
    else if (det == AHCI_SCTL_DET_OFFLINE)
        link_down(p, AHCI_SSTS_DET_OFFLINE);      /* 4：关掉链路 */
    else if (det == 0 && old_det != 0)
        link_up(s, p);                            /* 从非 0 回到 0：复位结束，建链 */
    update_irq(s);
}
```

`link_down()` 按第 10.4.2 节把 PxTFD.STS 置成 7Fh、PxSSTS.DET 置成指定值；链路原来是通的话，置 PxSERR.DIAG.N 表示 PhyRdy 变过。`link_up()` 是整个 OOB 握手加签名 FIS 的“瞬间版”：

```c
static void link_up(struct ahci *s, struct ahci_port *p)
{
    uint32_t limit = (p->sctl >> AHCI_SCTL_SPD_SHIFT) & 0xF;
    uint32_t spd = AHCI_SPEED_GEN3;
    uint8_t fis[SATA_FIS_REG_LEN] = { 0 };

    if (!p->has_disk) {
        p->ssts = AHCI_SSTS_DET_NONE;             /* 没有设备回 COMINIT */
        return;
    }
    if (limit && limit < spd)
        spd = limit;                              /* PxSCTL.SPD 限速 */
    p->ssts = AHCI_SSTS_DET_PHY | (spd << 4) | (AHCI_SSTS_IPM_ACTIVE << 8);
    p->serr |= AHCI_SERR_DIAG_X | AHCI_SERR_DIAG_N;

    disk_reset(s);                                /* 设备侧也复位：写缓存、传输模式回默认 */
    p->sig = ATA_SIG_DISK;                        /* 0x00000101 */
    p->tfd = (ATA_DIAG_PASSED << 8) | ATA_STS_DRDY;
    fis[0]  = SATA_FIS_REG_D2H;
    fis[2]  = ATA_STS_DRDY;
    fis[3]  = ATA_DIAG_PASSED;
    fis[4]  = (uint8_t)(ATA_SIG_DISK >> 8);       /* LBA Low */
    fis[12] = (uint8_t)ATA_SIG_DISK;              /* Count */
    if (post_fis(s, p, AHCI_RFIS_RFIS, fis, sizeof(fis)) != VMM_OK)
        host_bus_fatal(s, p, -1);
}
```

几个值得解释的地方：

- **PxTFD = 0x0140。** 低字节是状态寄存器 0x40（DRDY=1，BSY=0），高字节是错误寄存器 0x01。复位之后的错误寄存器是“诊断结果”，01h 表示设备自检通过。驱动读到 BSY=0 就认为设备就绪。
- **签名 FIS 的 I 位是 0。** SATA 3.0 第 11.3 节只规定了签名 FIS 里各寄存器的值，没有要求它触发中断，所以收到它不置 PxIS.DHRS。驱动也确实不靠中断，而是靠轮询 PxTFD 等它。
- **FIS 只在 FRE=1 时写进内存。** `post_fis()` 在 FRE=0 时什么也不写。上电和 HBA 复位时 FRE 都是 0，这时签名照样更新进 PxSIG 和 PxTFD：第 10.3.2 节规定“含签名的 D2H Register FIS 无论如何都要被 HBA 接受并更新签名字段”。真实 HBA 在 FRE=0 时会把收到的 FIS 存在内部 FIFO 里，等 FRE 置 1 再写出去；mini-vmm 直接丢弃，这一点算作限制。Linux 的复位流程里 FRE 一直是 1，不受影响。
- **PxSERR 的 X 和 N 位。** trace 第 33 行驱动第一次读端口 0 的 PxSERR，读到 0x04010000，就是上电建链时置上的 DIAG.X 和 DIAG.N。驱动在初始化时把它清掉，每次硬复位前后也都清一遍（第 10.4.2 节要求复位后软件写全 1 清 PxSERR）。
- **`disk_reset()`。** COMRESET 复位的是设备本身。写缓存、传输模式这类 SET FEATURES 设置在复位后取什么值，ATA8-ACS 第 7.48.2 节说由厂商决定，mini-vmm 选择回到默认值（写缓存开、UDMA6）；NCQ 的错误状态也随复位清除（P3、P5）。

HBA 复位（GHC.HR）调 `hba_reset()`，对每个端口执行 `port_reset()`：除 PxCLB/PxCLBU/PxFB/PxFBU 以外的端口寄存器回到复位值（第 10.4.3 节），然后对每个端口做一次 COMRESET，也就是直接调 `link_up()`。保留命令列表和 FIS 接收区的地址，是规范的明确要求：软件不必在每次 HBA 复位后重新设置它们。

### 5.4 空端口

端口 1 到 5 没有盘。它们收到 COMRESET 之后收不到 COMINIT，`link_up()` 在第一行就返回，PxSSTS.DET 停在 0。驱动的 `sata_link_resume()` 照样等完 200 ms 和 100 ms 的去抖，然后 `ata_phys_link_offline()` 判断 DET 不是 3，打印：

```text
ata2: SATA link down (SStatus 0 SControl 300)
```

这几个空端口不是摆设：它们让“端口枚举”这件事真正发生，驱动必须逐个端口复位、逐个判断有没有设备，而不是假定端口 0 一定有盘。一个控制器只挂一块盘时，这条路径照样被完整走了五遍。

## 六、寄存器访问的宽度

AHCI 规范第 3 节规定寄存器访问可以是 8/16/32/64 位，只要不跨 8 字节边界。Linux 只用 32 位的 `readl`/`writel`，但其他软件不一定。mini-vmm 的 `abar_read()`/`abar_write()` 这样处理：

- 64 位访问拆成两次 32 位，分别落到相邻的两个寄存器上；
- 小于 32 位的读，返回寄存器里对应的那几个字节；
- 小于 32 位的写忽略，并记一次警告。AHCI 寄存器的位域经常跨字节（比如 PxCMD 的 ICC 和 CCS），部分写入会触发半个状态变化，规范也没有说明这时的语义，直接忽略比猜一个行为更安全。

### 7.1 端到端

`tests/e2e/emu-blk.sh` 里和本篇有关的用例启动一个只挂空盘的 guest，检查 VMM 日志里的 `pci 00:01.0 ahci [1234:0003] class 010601`（PCI 外观），以及 guest 的 dmesg：

`tests/unit/ahci_test.c` 不启动 guest，直接调 `ahci_reg_read`/`ahci_reg_write`，外部依赖换成桩：PCI 的 DMA 落在一块假的 guest 内存上，INTx 电平被记录下来。和本篇有关的用例：

## 八、限制

- 链路瞬间建立，没有 OOB 过程，也没有速率协商失败、链路抖动这类情况。
- FRE=0 时收到的 FIS 直接丢弃，不进 FIFO。
- 不支持交错上电、冷插拔检测、热插拔、端口倍增器、链路省电、命令完成合并、机箱管理（对应的能力位都是 0）。
- 端口数固定为 6，一个控制器只在端口 0 挂一块盘；要多块盘就挂多个控制器（`--device ahci` 写多次）。
- 不支持 BIOS/OS 交接（CAP2.BOH=0）：mini-vmm 直接启动 Linux，没有固件在 OS 之前用过这个控制器。
