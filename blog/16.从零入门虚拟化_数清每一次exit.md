路线图后半段几乎每个里程碑都是“同一件事换一种做法，看它便宜了多少”：e1000 对 virtio-net，`KVM_EXIT_MMIO` 对 ioeventfd，用户态后端对 vhost。要比较，第一个要数的量就是 exit：做一次 I/O，guest 停下来几次；停下来之后，是在 KVM 内核里就地处理掉，还是一路回到 VMM 的用户态。这一章讲 mini-vmm 的 `--exit-stats` 怎样把这两部分都数出来，以及怎样读这份报告。

## 一、两半 exit

《一次 out 指令的完整旅程·原理篇》讲过一次 `out` 指令的完整路径：guest 执行 `out`，CPU 产生 `#VMEXIT`，KVM 处理，需要的话 `KVM_RUN` 返回用户态。关键在“需要的话”：

```
 guest 执行 out / in / hlt / 访问 MMIO / 碰到没映射的页 / 来了外部中断
        │  #VMEXIT
        ▼
 KVM: svm_handle_exit()
        │
        ├─ 内核能处理 ───────────────────────────► 直接回到 guest
        │    · 内核里模拟的 PIC/PIT 端口                VMM 完全不知道
        │    · 有内核 LAPIC 时的 HLT
        │    · NPT 缺页（第一次访问某页）
        │    · 外部中断、中断窗口
        │
        ▼ 需要用户态
 KVM_RUN 返回，kvm_run->exit_reason = KVM_EXIT_IO / MMIO / HLT ...
        ▼
 VMM: vcpu_handle_exit() → io_bus_dispatch_pio() → 设备回调
```

VMM 只看得到下面那一半。上面那一半有多少，只有 KVM 知道。所以报告分成两半：

- **用户态这一半**由 VMM 自己数，按 exit 类型和按设备分开；
- **内核这一半**读 KVM 自己的计数器，接口是 `KVM_GET_STATS_FD`。

两半并排放，才能回答“这次 exit 付出了哪一段开销”。

## 二、用户态这一半：VMM 自己数

### 2.1 按 exit 类型：每个 vCPU 一张表

```c
/* include/vmm.h */
#define VMM_EXIT_REASON_SLOTS 64

struct vmm_vcpu {
    ...
    uint64_t        exits[VMM_EXIT_REASON_SLOTS];
};

/* src/vm.c */
int vcpu_handle_exit(struct vmm_vcpu *vcpu)
{
    struct kvm_run *run = vcpu->run;

    vcpu->exits[run->exit_reason < VMM_EXIT_REASON_SLOTS - 1
                ? run->exit_reason : VMM_EXIT_REASON_SLOTS - 1]++;
    ...
```

下标直接是 `KVM_EXIT_*` 的值。`<linux/kvm.h>` 里的 exit reason 目前不到 50 个，表有 64 格。`exit_reason` 是内核写进 `kvm_run` 的，VMM 不能假设它一定小于 64，所以先钳位：超出范围的都记进最后一格，报告里叫 `out-of-range`。不钳位的话，一个新内核加了第 70 号 exit reason，这行代码就会写到数组外面去。

这张表只有本 vCPU 自己的线程写。报告在所有 vCPU 线程都 `pthread_join` 之后才读，`pthread_join` 本身就保证了写入对读者可见，所以不需要锁，也不需要原子操作。

`KVM_RUN` 被信号打断、返回 `EINTR` 时不计数。这时 `kvm_run->exit_reason` 不是这一次的值（停机路径用 `immediate_exit` 让 `KVM_RUN` 立即返回，KVM 不改写这个字段），`vcpu_run_loop()` 在交给 `vcpu_handle_exit()` 之前就把它挡掉了。

### 2.2 按设备：和设备表平行的数组

```c
/* include/vmm.h */
struct vmm_io_stats {
    uint64_t reads;
    uint64_t writes;
};

struct vmm_vm {
    ...
    struct vmm_io_dev   pio_devs[VMM_MAX_PIO_DEVS];
    ...
    struct vmm_io_stats pio_stats[VMM_MAX_PIO_DEVS];   /* 和 pio_devs 同下标 */
    struct vmm_io_stats mmio_stats[VMM_MAX_MMIO_DEVS];
    struct vmm_io_stats pio_unhandled;                 /* 落在没注册的地址上 */
    struct vmm_io_stats mmio_unhandled;
};

/* src/vm.c: io_bus_dispatch_pio()，调用时持有 io_lock */
    dev = vmm_lookup_pio(vm, port);
    io_stats_count(dev ? &vm->pio_stats[dev - vm->pio_devs]
                       : &vm->pio_unhandled, is_write);
```

计数为什么不直接放进设备结构里？设备表在 guest 启动前注册完之后就只读了，`vmm_lookup_pio()` 返回 `const` 指针，查找不需要加锁。计数要在 guest 运行期间不断更新，放进设备表就破坏了“只读”。单独放一个同下标的数组，它在分发路径上更新，而分发路径本来就持着 `io_lock`。

这里数的是 **exit 次数**，不是访问次数。差别在字符串 I/O 上：

```
  guest: rep outsb，一次写 16 个字节到 0x3f8

  KVM_EXIT_IO 一次，count = 16
    → 设备回调被调用 16 次
    → 统计只加 1
```

要回答的问题是“exit 的开销花在了哪个设备上”，开销是按 exit 付的：一次世界切换加一次用户态往返，不管里面带了几个字节。

### 2.3 一直在数，选项只决定输出

计数代码没有开关。在已经持锁的路径上做一次自增，和一次 exit 本身（几微秒的世界切换加一次用户态往返）相比可以忽略。加开关反而要在每个计数点多一个分支，还要额外证明“打开和关闭统计时行为一致”。`--exit-stats FILE` 只决定 VM 停下后要不要输出报告、输出到哪里，`-` 表示 stderr。

两个时机上的细节：

- **统计文件在启动时就打开。** 路径写错时，在 guest 运行之前就报错退出，不会跑完一整次才发现结果没地方写。
- **VM 出错停下时也照样输出。** exit 落在哪里，正是排错的线索。

## 三、内核这一半：`KVM_GET_STATS_FD`

### 3.1 一个自描述的二进制文件

KVM 在内核里给每个 VM、每个 vCPU 维护了几十个计数器：总 exit 数、I/O exit 数、HLT exit 数、缺页次数……`ioctl(fd, KVM_GET_STATS_FD)` 对 vm fd 或 vcpu fd 调用，返回一个只读 fd，从里面能读出这些计数器。它的格式在 `Documentation/virt/kvm/api.rst` 4.133 节，是一个自描述的二进制文件：

```
offset 0        struct kvm_stats_header { flags, name_size, num_desc,
                                          id_offset, desc_offset, data_offset }
id_offset       id 字符串（name_size 字节），如 "kvm-12345/vcpu-0"
desc_offset     num_desc 个描述符，每个是 struct kvm_stats_desc（16 字节）+ name[name_size]
data_offset     数据块：第 i 项的值在 data_offset + desc[i].offset，共 desc[i].size 个 u64
```

```c
/* include/uapi/linux/kvm.h */
struct kvm_stats_desc {
	__u32 flags;        /* 低 4 位类型，4-7 位单位，8-11 位 exponent 的底 */
	__s16 exponent;
	__u16 size;         /* 这一项有几个 u64 */
	__u32 offset;       /* 在数据块里的偏移 */
	__u32 bucket_size;
	char  name[];       /* name_size 字节 */
};
```

“自描述”的意思是：VMM 不需要事先知道有哪些计数器，读描述符就知道每一项叫什么、在哪、有多大。内核加一个新计数器，VMM 不用改代码就能看到。

类型有累计值（CUMULATIVE）、瞬时值（INSTANT）、峰值（PEAK）和两种直方图。mini-vmm 只取 `size == 1` 的单值项。直方图（比如 halt-polling 时长分布）要按 bucket 解释才有意义，exit 计数用不上，解析时跳过并计数。

### 3.2 三个坑

**第一，别按“紧挨着”去读。** 真实内核给出的文件里，header、id、描述符、数据块恰好是依次紧挨着的。但 api.rst 明确写了不保证相邻，也不保证按这个顺序：

```
  按位置猜                                    按 header 里的 offset

  desc 从 sizeof(header) + name_size 开始      pread(fd, ..., h.desc_offset)
  data 紧跟在最后一个 desc 后面                 pread(fd, ..., h.data_offset)

  今天的内核：结果正确                          今天的内核：结果正确
  某个内核在块之间留了空隙：                     任何合法布局：结果正确
    读出错位的值，而且不报错
```

`kvm_stats_read()` 一律用 header 里的 offset 加 `pread` 定位。

**第二，对齐。** 描述符的步长是 `16 + name_size`。内核的 `name_size` 是 48，步长 64，恰好 8 字节对齐。但规范没有承诺 `name_size` 是 8 的倍数，直接把缓冲区里的指针强转成 `struct kvm_stats_desc *`，在步长不对齐时是未定义行为。实现先用 `memcpy` 把定长部分拷出来再用。

**第三，防御损坏的文件。** `name` 必须在 `name_size` 字节之内以 `'\0'` 结尾。`desc.offset` 是 u32，不设上限的话，一个损坏的值能让解析器先 `malloc` 4 GiB，再发现文件根本没那么长。所以数据块限制在 1 MiB，x86 vCPU 的实际数据块不到 4 KiB。

### 3.3 什么时候读

vcpu fd 上的 ioctl 进入 `kvm_vcpu_ioctl()`（`virt/kvm/kvm_main.c`）时，先要拿 `vcpu->mutex`，而 `KVM_RUN` 期间这把锁一直被 vCPU 线程持有。guest 运行时从别的线程去调 `KVM_GET_STATS_FD`，会一直卡到 vCPU 退出为止。

所以报告在 `vm_run()` 返回之后（所有 vCPU 线程已经结束，锁没人持有）、`vm_destroy()` 关掉 fd 之前读，这两个条件要同时满足。guest 运行期间的实时观察要靠以后的 `monitor` 里程碑。

## 四、读报告

### 4.1 最小的例子：实模式 payload

`tools/payload/real_mode_stub.S` 往调试端口 `0x10` 写一次、读一次、再把读到的值写回去，然后 `hlt`：

```bash
./build/vmm --mode real16 --exit-stats - build/payload16.bin
```

```
user-space exits by reason (KVM_RUN returned to the VMM)
  reason                            total        vcpu0
  IO                                    3            3
  HLT                                   1            1
  total                                 4            4

user-space exits by device (string I/O counts once per exit)
  device                     space         reads       writes
  dbg-port                   PIO               1            2
  exit-port                  PIO               0            0
  serial8250                 PIO               0            0
  unhandled                  PIO               0            0
  unhandled                  MMIO              0            0

KVM vCPU stats (KVM_GET_STATS_FD, nonzero single values; includes exits handled inside KVM)
  name                              total        vcpu0
  pf_taken                              1            1
  pf_fixed                              1            1
  exits                                 5            5
  io_exits                              3            3
  halt_exits                            1            1
  ...
```

报告分四段：用户态按类型、用户态按设备、KVM 的 vCPU 计数、KVM 的 VM 计数。设备表即使是 0 也打印，因为“注册了却一次都没被访问”本身就是信息；KVM 计数只打印非零项。

逐个数：用户态 3 次 IO 全在 `dbg-port` 上（1 读 2 写），加 1 次 HLT，共 4 次。KVM 的 `exits` 是 5，多出的 1 次正好是 `pf_taken` 的 1：guest 第一次访问代码所在的页，NPT 里还没有映射，KVM 建好映射就直接回到 guest，VMM 完全不知道。

### 4.2 串口 payload：每个数都能从源码数出来

`tools/payload/serial_stub.S` 用 8250 串口打印一行 31 个字符。每个字符先读一次 LSR 看发送寄存器空不空，再写一次 THR。mini-vmm 的 LSR.THRE 恒为 1，所以每个字符正好一读一写。之后 SCR 写读各一次、MCR 写两次、MSR 读一次，最后写一次 `dbg-port` 再 `hlt`。

```bash
./build/vmm --mode long64 --exit-stats - build/serial64.bin
```

```
  IO                                   68           68
  HLT                                   1            1
  ...
  dbg-port                   PIO               0            1
  serial8250                 PIO              33           34
  ...
  pf_taken                              4            4
  exits                                73           73
  io_exits                             68           68
  halt_exits                            1            1
```

| 数字 | 从源码怎么数出来 |
|---|---|
| serial 读 33 | 31 次 LSR + 1 次 SCR + 1 次 MSR |
| serial 写 34 | 31 次 THR + 1 次 SCR + 2 次 MCR |
| IO 68 | 33 + 34 + `dbg-port` 1 |
| KVM `io_exits` 68 | 和用户态相等：这个模式下没有创建内核 irqchip，所有端口都回到用户态 |
| KVM `exits` 73 | 用户态 69（68 + HLT 1）+ `pf_taken` 4：页表、GDT、代码、数据各一页的第一次访问 |

每个数都能对上，说明两半的计数都没有漏、也没有多。

| 量 | 用户态 | KVM | 差在哪 |
|---|---|---|---|
| IO | 54849 | `io_exits` 55012 | 163 次落在内核模拟的端口上。mini-vmm 用 `KVM_CREATE_IRQCHIP`、`KVM_CREATE_PIT2` 把 PIC、PIT 放进了内核，`emulator_pio_in_out()` 经 `kvm_io_bus_read(KVM_PIO_BUS)` 就地处理 |

| 总数 | 54849 | `exits` 66675 | 其余是外部中断（`irq_exits` 4209）、中断窗口（`irq_window_exits` 927）、缺页、指令模拟 |

按设备看，**串口占了用户态 exit 的 98%**。要看是哪几个寄存器，用 `--trace-pio` 录下同一次启动，再用 `tools/pio_decode.py --summary` 按端口拆开：THR（`0x3f8` 写）26751 次，LSR（`0x3fd` 读）26006 次，几乎一比一。控制台输出是逐字节先查 LSR.THRE 再写 THR，每个字节两次 exit。这就是以后 `virtio-console` 要对照的基线：同样的输出，换成共享内存里的环形队列，exit 能少多少。

`unhandled PIO` 里最多的是 `0xcf8` 写、`0xcfc`/`0xcfe` 读，这是 Linux 用 PCI 配置机制 #1 探测总线。`pci-bus` 里程碑实现它之后，这部分 exit 会从 `unhandled` 移到新设备的那一行。其余是 `0x2e`/`0x4e` 这类 Super I/O 端口的盲探。

## 五、怎么确认数得对

计数器最怕的不是崩溃，而是“数错了但看起来很合理”。所以测试的思路是：先构造出答案已知的场景，再要求报告逐项相等；并且用故意写错的实现确认这些判据真的能抓到错误。

**解析 KVM 统计文件**：`tests/unit/kvm_stats_test.c` 用 memfd 造出规范允许、但真实内核不会给出的布局：块的顺序倒过来、块之间留空、`name_size` 不是 8 的倍数，另外还有七种损坏的文件。四种错误实现各自至少会让一条用例失败：

| 错误实现 | 被哪条抓到 |
|---|---|
| 按位置猜描述符块 | 块顺序倒置的布局 |
| 按位置猜数据块 | 块之间留空的布局 |
| 强转不对齐的指针 | `name_size` 是奇数的布局，由 UBSan 报出 |
| 不限制数据块长度 | 测试把单次分配上限压到 64 MiB，返回值从 INVAL 变成 NOMEM |

**用户态计数**：`tests/unit/io_bus_test.c` 的 `case_stats` 经 `vcpu_handle_exit()` 构造一串 exit，逐项核对计数。按回调次数计数（而不是按 exit）、不分读写方向、把未注册的 MMIO 记进 PIO 那格、`exit_reason` 不钳位，这四种错误实现都会让它失败。

**端到端**：`make test exit-stats` 跑 `tests/e2e/exit-stats.sh`：

- 两个裸 payload 的报告，每一个数都要和 4.1、4.2 节从源码数出的值逐项相等，KVM 的 `io_exits` 和用户态 IO 相等、`exits` 不小于用户态总数；
- 打开和关闭统计时，guest 的输出逐字节相同；
- `-` 把报告写到 stderr，stdout 里没有报告；
- 路径写错时在 guest 启动前就失败；
- Linux guest 的数字每次都不一样，没法逐项比较，改用内部一致性校验：各设备行的读写之和等于 IO、MMIO 两行的总数。

不认识 `--exit-stats` 的 VMM 上，这些用例全部失败。

## 六、限制

- **没有按端口或寄存器的细分。** 按设备已经能回答“哪个设备贵”，要看单个寄存器用 `--trace-pio`（4.3 节就是这么做的）。
- **没有每次 exit 的耗时。** 时间开销要靠 host 侧的 `perf kvm stat`，或者 `exit-cost` 里程碑在 guest 里测。
- **KVM 统计只在 VM 停下之后读一次。** 运行中的观察属于 `monitor` 里程碑（3.3 节说明了为什么运行中不能直接读 vCPU 的统计）。
