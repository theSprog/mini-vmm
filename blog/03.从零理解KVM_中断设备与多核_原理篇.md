## 一、从“能跑指令”到“能跑操作系统”：还差什么

### 1.1 第一篇的 guest 是一个“哑巴”

回忆一下上一篇的 guest：一段十几字节的机器码，从固定地址开始执行，往 `0x3f8` 写几个字节，然后 `hlt`。它有 CPU，有内存，有一个“串口”。按照计算机组成课的定义，这已经是一台图灵完备的机器了。

但如果你把一个 Linux 内核放进这台“机器”，它连第一行日志都打不出来。不是因为指令不对（CPU 是真的，Linux 的每条指令都能在 guest 模式下原生执行），而是因为 Linux 对“机器”的期待，远远超出“能执行指令”这个层面。

先做一个思想实验：假设你是 Linux 内核，刚刚被 bootloader 跳到了入口点。你对这台机器一无所知。在开始调度第一个用户进程之前，你至少需要知道或者得到下面这些东西：

- **有多少内存，哪些地址能用。** 物理地址空间里有 RAM、有 ROM、有设备寄存器、还有空洞。你不能把页帧分配到一个其实是网卡寄存器的地址上。
- **有几颗 CPU，它们叫什么。** 调度器要知道能把线程放到哪些 CPU 上，要知道哪些 CPU 共享缓存；唤醒其他 CPU 时，要知道它们的“地址”。
- **时间怎么流逝。** 调度器需要一个周期性的“滴答”来抢占长时间运行的进程；`sleep(1)` 需要知道一秒是多长；日志的时间戳需要一个单调递增的计数器。
- **设备怎么通知我。** 键盘按下、网卡收到包、磁盘读完一个块——内核不可能一直轮询，它需要硬件主动打断它。
- **怎么关机和重启。** `poweroff` 最终要让某个硬件把电断掉，`reboot` 要让某个硬件把 CPU 复位。

第一篇的 VMM 一样都没提供。它没有告诉 guest 内存布局，没有中断控制器，没有定时器，只有一颗 CPU，guest 想关机也只能 `hlt`。

### 1.2 OS 跑在“平台”上，而不只是跑在 CPU 上

操作系统课本通常把硬件抽象成“CPU + 内存 + 若干设备”，这在讲原理时足够了。但一个真实的 x86 操作系统面对的是一个更具体的东西，叫做**平台（Platform）**。

平台是一整套约定俗成的规矩：中断控制器在哪个地址、定时器是哪一种芯片、键盘控制器挂在哪两个端口、固件用什么格式描述硬件、内核被加载时 CPU 处于什么状态、寄存器里放着什么。x86 的这套规矩叫做 **PC 兼容平台**，它的源头是 1981 年的 IBM PC。

这就导致了一个对写 VMM 的人来说非常重要的事实：

> **即使在 2026 年，一个现代 Linux 内核启动时，仍然会去碰 1980 年代的芯片。**

它会用 1981 年 IBM PC 上的 8253 定时器来测量 CPU 的时钟频率；会去问一个 1984 年 IBM PC/AT 上的键盘控制器“你还活着吗”；会读一块 1984 年的 CMOS 时钟芯片来设置系统时间；会通过一个 1987 年的 16550 串口芯片打印日志。如果 VMM 不在这些“古董”的端口上给出正确的反应，Linux 要么卡住，要么浪费几秒钟，要么干脆拒绝使用某些功能。

所以本章的一个核心任务是：**搞清楚 Linux 启动过程中到底会碰哪些平台设施，每一个最少需要模拟到什么程度。**

前四块是“硬件”，最后一块是“对硬件的描述”。两者必须严丝合缝：固件说有 4 颗 CPU，就必须真有 4 颗 CPU 能被唤醒；固件说中断控制器在 `0xFEC00000`，那个地址上就必须真有一个中断控制器在响应。**描述与实物不一致**，是本章所有坑里最隐蔽的一类，因为 guest 内核往往不会报错，只会默默地选择一条退化的路径——比如退回单核，或者退回一种不需要中断控制器的“兼容模式”。

### 1.4 这些东西由谁来提供

上一篇说过，KVM 只负责 CPU 和内存的虚拟化，设备模型全在用户态。但这句话在中断和时钟这里要打个折扣：KVM 在内核里模拟了少数几个设备——中断控制器（PIC、IOAPIC、LAPIC）和定时器（PIT）。原因是它们的访问频率太高了，高到每次访问都回一趟用户态会让整台虚拟机慢得不可用。

## 二、中断：操作系统的心跳

### 2.1 为什么需要中断：轮询的代价

操作系统课讲 I/O 时一般会对比两种方式：**轮询（polling）** 和 **中断（interrupt）**。

轮询就是 CPU 反复去读设备的状态寄存器：“数据来了吗？来了吗？来了吗？”这很简单，也很可靠，但有两个致命问题。第一，CPU 在轮询时什么正事都干不了，设备越慢浪费越大——一个 115200 波特的串口每秒只能收 11520 个字节，CPU 在两个字节之间可以执行几十万条指令。第二，也是更根本的：**如果 CPU 正在执行一个死循环的用户程序，没有任何机制能把它拉回来。** 轮询要求 CPU 主动去看，而一个不合作的程序永远不会让 CPU 去看。

中断把主动权反转了：设备在需要服务时主动“拍 CPU 的肩膀”，CPU 在当前指令执行完后暂停手头的工作，跳去执行一段预先登记好的处理程序，处理完再回来接着干。

这里面有一种中断的地位格外特殊：**时钟中断**。一个定时器芯片每隔固定时间（比如 1 毫秒或 4 毫秒）产生一次中断，内核在时钟中断处理程序里更新时间、检查当前进程的时间片是否用完、必要时触发调度。OS 课上讲的“抢占式调度”，其物理基础就是这个周期性的中断。**没有时钟中断，就没有抢占，也就没有分时操作系统。** 这就是为什么说时钟中断是操作系统的心跳。

对写 VMM 的人来说，这句话有一个非常直接的推论：guest 内核启动早期最先要确认的事情之一就是“时钟中断能不能到达”。Linux 甚至专门有一段代码检查这件事（`check_timer()`），检查失败会尝试各种退路，全部失败就直接 panic，打印那句著名的 “IO-APIC + timer doesn't work!”。时钟中断送不进 guest，是本章所有问题里最常见、症状也最“安静”的一种：内核卡在某行日志之后不动了，没有任何报错。

### 2.2 一次中断在 x86 上的完整路径

以“串口收到一个字节”为例，一次中断在真实 x86 机器上的完整路径如下：

```
  ① 设备                ② 中断控制器             ③ CPU                   ④ 内核
 ┌──────────┐         ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
 │ 16550 UART│  IRQ4  │  记下“4 号线   │ 向量号 │ 当前指令执行完 │ 查 IDT  │ 串口中断处理   │
 │ 收到字节   │──────► │  有请求”，按优 │──────► │ 检查 IF=1？   │──────► │ 程序：读数据   │
 │ 拉高中断线 │        │  先级仲裁，把  │        │ 保存 RIP/CS/  │        │ 寄存器，塞进   │
 └──────────┘         │  向量号交给CPU │        │ RFLAGS 到栈   │        │ tty 缓冲区    │
                      └──────────────┘        │ 跳到 handler  │        └──────┬───────┘
                             ▲                 └──────────────┘               │
                             │                                                 │
                             │           ⑤ EOI：“这次中断处理完了”              │
                             └─────────────────────────────────────────────────┘
```

这条路径上有五个角色，每一个在虚拟化时都要被模拟或者被处理：

1. **设备**决定“什么时候要中断”。串口在收到数据、发送缓冲空了等事件时，拉高自己的中断输出线。
2. **中断控制器**把几十根来自不同设备的线汇总起来，按优先级仲裁，决定此刻该让 CPU 处理哪一个，并把对应的**向量号**交给 CPU。
3. **CPU** 在每条指令的边界检查“有没有待处理的中断、我现在能不能接收”，能接收就把当前的执行现场（`RIP`、`CS`、`RFLAGS`，特权级切换时还有 `RSP`、`SS`）压到栈上，然后用向量号去查 **IDT（Interrupt Descriptor Table，中断描述符表）**，跳到对应的处理程序。
4. **内核的中断处理程序**完成实际工作：读设备寄存器、搬数据、唤醒等待的进程。
5. 处理完毕后，内核向中断控制器写一个 **EOI（End Of Interrupt）**，告诉它“这一次处理完了，你可以把同级或更低级的中断再交给我了”。

第 5 步是 OS 课上最容易被忽略的一步，但它在虚拟化里非常关键，后面会反复出现。

### 2.3 向量号、IDT 与三类“打断”

x86 的 IDT 有 256 项，下标就是**向量号（vector）**，范围 0 到 255。这 256 个向量被分成几段：

| 向量范围 | 用途 |
|---|---|
| 0–31 | CPU 异常，由 Intel 保留：0 是除零 `#DE`，6 是非法指令 `#UD`，8 是双重错误 `#DF`，13 是一般保护 `#GP`，14 是缺页 `#PF` |
| 32–255 | 外部中断和软件中断，由操作系统自由分配 |

Linux 在 x86_64 上的分配（见 `arch/x86/include/asm/irq_vectors.h`）是：外部中断从 `0x20` 开始，其中 `0x30` 到 `0x3F` 固定给 16 个传统 ISA 中断（`IRQ0` 对应 `0x30`，这个数字在后面的真实启动日志里会看到），其余向量动态分配给各种设备；`0x80` 是历史遗留的 `int 0x80` 系统调用入口；最高的一段（LAPIC 定时器往上直到 `0xFF`）留给系统向量，比如 `0xFD` 是重调度 IPI，`0xFC` 是函数调用 IPI，`0xFE` 是 APIC 错误，`0xFF` 是伪中断（spurious）。

“打断 CPU 正常执行流”的事件有三类：

- **异常（Exception）**：由当前正在执行的指令引起，比如除零、缺页、执行了非法指令。它是**同步**的：同一条指令在同样的状态下每次都会引起同样的异常。异常不受 `IF` 标志控制，不能被屏蔽。
- **外部中断（Interrupt）**：由 CPU 之外的设备引起，与当前执行的指令无关，是**异步**的。它受 `RFLAGS.IF` 控制：`IF=0` 时 CPU 不接收可屏蔽中断。
- **NMI（Non-Maskable Interrupt，不可屏蔽中断）**：同样来自外部，但不受 `IF` 控制，**固定使用向量 2**。它用于“无论如何都必须立刻处理”的情况，比如硬件故障、看门狗。

这个区分在虚拟化中直接对应到“怎么注入”：VMCB 的事件注入字段里有一个“类型”域，要明确告诉硬件这次注入的是外部中断、NMI 还是异常，因为三者在 guest 里的投递规则不同。

### 2.4 `IF` 标志与中断影子：“什么时候能打断”

`RFLAGS` 的第 9 位是 **IF（Interrupt Flag）**。内核用 `cli` 清零它、用 `sti` 置位它，从而开关可屏蔽中断。内核里所有的“关中断临界区”，本质都是在操作这一位。

`IF` 有一个 OS 课一般不讲、但在虚拟化里至关重要的细节：**中断影子（interrupt shadow）**。x86 规定，`sti` 指令执行后，**紧跟着的下一条指令执行完之前**，CPU 仍然不接收中断。`mov ss, xxx` 和 `pop ss` 也有同样的效果。

为什么要设计这么一个奇怪的规则？看 Linux idle 循环里最经典的一对指令：

```asm
    sti          ; 开中断
    hlt          ; 停机，等待中断唤醒
```

如果没有中断影子，中断可能恰好在 `sti` 和 `hlt` 之间到达：CPU 开了中断，立刻去处理中断，处理完回来执行 `hlt`——然后 CPU 就睡着了，而唤醒它的那个中断已经被处理掉了。如果接下来很长时间没有别的中断，CPU 会睡过头。中断影子保证 `sti; hlt` 是一个“原子”的序列：中断要么在 `sti` 之前到达（此时 `IF=0`，被挂起），要么在 `hlt` 执行时到达（把 CPU 从 HLT 中唤醒），不会落在两者之间。

`mov ss` 的影子是同一个道理：切换栈要先改 `SS` 再改 `RSP`，如果中断落在两条指令之间，CPU 会把现场压到一个 `SS` 和 `RSP` 不匹配的“栈”上。

写 VMM 为什么要关心这个？因为 hypervisor 在注入中断之前，必须判断 guest 此刻**能不能**接收中断，而判断条件不只是 `IF=1`，还要求 guest 不处在中断影子里。如果 hypervisor 忽略了影子，强行在 `sti` 之后立刻注入，就破坏了 guest 依赖的原子性。硬件为此在 VMCB 里专门提供了一个 `int_state` 字段，告诉 hypervisor“guest 当前是否处在中断影子中”。第四章会把这些条件汇总起来。

### 2.5 边沿触发与电平触发

设备通过一根线向中断控制器发出请求。“这根线上发生了什么才算一次请求”，有两种约定：

```
  边沿触发（Edge-triggered）：只有 0→1 的跳变算一次请求

  中断线   ─────┐     ┌─────────────┐     ┌──────
               │     │             │     │
               └─────┘             └─────┘
                     ↑                   ↑
                  一次请求             一次请求
            （高电平持续多久都不会产生新请求）


  电平触发（Level-triggered）：只要线是高电平，请求就一直存在

  中断线   ─────┐     ┌─────────────────────────┐
               │     │ ← 高电平期间请求一直有效    │
               └─────┘                         └──────
                     ↑                         ↑
               请求开始                     设备被服务后撤销
                          （EOI 时若线仍为高，控制器会再次投递）
```

**边沿触发**的语义是“发生了一件事”。它的优点是简单，缺点有两个：一是**会合并**，如果两次上升沿之间中断控制器还没来得及处理第一次，第二次就丢了（或者说被合并成了一次），所以驱动程序在处理中断时通常要循环读状态寄存器，直到设备说“没有更多事件了”；二是**线不能共享**，两个设备共用一根边沿触发的线时，一个设备保持高电平会让另一个设备的上升沿消失。

**电平触发**的语义是“有事情待处理”。设备在有待处理事件时一直拉高电平，直到驱动程序把事件处理完，设备才撤销电平。它天然支持线共享（多个设备“线或”到一根线上，只要有一个在拉高，请求就在），也不会丢事件。代价是中断控制器必须知道“处理完了没有”，否则它会在处理程序还没来得及清除设备状态时反复投递同一个中断，形成中断风暴。这就是 EOI 在电平触发中的关键作用：控制器投递了一次电平中断后，会**暂停**这根线的再次投递，直到收到 EOI；收到 EOI 时如果线还是高电平，说明设备仍有待处理的事件，就再投递一次。

历史上 ISA 总线的设备（串口、键盘控制器、PIT）都是边沿触发的，PCI 设备的 INTx 中断是电平触发的。

**这对写 VMM 的影响非常具体**：VMM 模拟设备时，是通过一个 ioctl 告诉 KVM “把某根中断线拉高/拉低”。对于边沿触发的线，如果设备连续产生两个事件，VMM 必须先把线拉低再拉高，制造一个新的上升沿；只是“保持高电平”是不会产生第二次中断的。mini-vmm 的串口实现就踩过这个坑，实现篇会回到这个问题。

### 2.6 EOI：中断处理的“回执”

EOI 已经出现了好几次，这里把它的作用归纳一下：

1. **解除优先级屏蔽。** 中断控制器在把一个中断交给 CPU 后，会记住“CPU 正在服务某个优先级的中断”（记在一个叫 ISR，In-Service Register 的寄存器里），在此期间同级和更低级的中断不会被投递。EOI 清除这个记录。
2. **重新评估电平中断。** 对电平触发的线，EOI 让控制器重新检查线的状态，决定是否再投递。
3. **作为“中断已被处理”的信号被别人观察。** 这一点在虚拟化里特别重要：hypervisor 模拟的定时器需要知道 guest 有没有处理完上一次时钟中断，才能决定要不要补发丢失的中断（第五章讲 PIT 的“reinject”时会看到）。

在 x86 上，EOI 的具体形式取决于中断控制器：对 8259A PIC，是往端口 `0x20` 写一个特定的命令字节；对 LAPIC，是往它的 EOI 寄存器（MMIO 地址 `0xFEE000B0`）写 0。**每一次中断处理都至少伴随一次 EOI 写入**，这个频率意味着：如果 EOI 寄存器的每次访问都要陷出到 hypervisor，开销会非常可观。这是第四章要算的第一笔账。

### 2.7 小结：写 VMM 需要记住的中断事实

把本章压缩成几句话：

- 中断的路径是“设备 → 中断控制器 → CPU（查 IDT）→ 处理程序 → EOI”，虚拟化要把这条路径上的每一环都接上。
- CPU 能否接收一个外部中断，取决于 `IF`、中断影子，以及（在 AMD 上）全局中断标志 GIF，hypervisor 注入前必须检查同样的条件。
- 异常、外部中断、NMI 是三种不同的事件，注入时要区分。
- 边沿触发的线只认上升沿，模拟设备时每个事件都要制造一个新的上升沿；电平触发的线依赖 EOI 来重新评估。
- EOI 频率很高，这决定了中断控制器必须在内核里模拟。
- 时钟中断是 OS 的心跳，它送不进 guest 是最常见、最“安静”的故障。

## 三、x86 中断控制器的三代演化

上一章把“中断控制器”当成一个黑盒。这一章打开它。x86 平台上的中断控制器经历了三代，而且——这是 PC 平台的老规矩——**三代同时存在于今天的每一台机器上**，包括我们要模拟的这台虚拟机。Linux 启动时会先在第一代上跑一小会儿，再切换到第二代；第三代则在有 PCI 设备时登场。

### 3.1 第一代：8259A PIC

#### 3.1.1 一颗芯片，八根线

1981 年的 IBM PC 用了一颗 Intel 8259A **PIC（Programmable Interrupt Controller，可编程中断控制器）**。它有 8 个输入引脚 IR0 到 IR7，一个输出引脚 INT 接到 CPU 的 INTR 引脚上。

8 根线显然不够用。1984 年的 PC/AT 用了两颗 8259A 级联：一颗做**主片（master）**，一颗做**从片（slave）**，从片的 INT 输出接到主片的 IR2 上。这样一共有 15 根可用的中断线（主片的 IR2 被级联占掉了），编号 IRQ0 到 IRQ15：

```
                    ┌────────────────────┐
   IRQ0  PIT ──────►│IR0                 │
   IRQ1  键盘 ─────► │IR1                 │
             ┌─────►│IR2   主片 8259A     │ INT ────────► CPU INTR 引脚
             │      │IR3   端口 0x20/0x21 │
   IRQ4  COM1 ─────►│IR4                 │
             │      │...                 │
             │      └────────────────────┘
             │      ┌────────────────────┐
             │      │IR0 (IRQ8)  RTC      │
             │      │IR1 (IRQ9)  ACPI SCI │
             └──────┤INT   从片 8259A     │
                    │... 端口 0xA0/0xA1   │
                    │IR4 (IRQ12) PS/2 鼠标│
                    │IR6 (IRQ14) IDE      │
                    └────────────────────┘
```

这张表里的 IRQ 分配——IRQ0 是 PIT 定时器、IRQ1 是键盘、IRQ4 是 COM1、IRQ8 是 RTC、IRQ12 是 PS/2 鼠标、IRQ14 是 IDE 硬盘——四十年来从没变过。今天的 Linux 内核里，这些数字仍然是硬编码的。我们的串口挂 IRQ4、键盘控制器挂 IRQ1、RTC 挂 IRQ8、ACPI 的 SCI 挂 IRQ9，全都是在遵守这张表。

#### 3.1.2 三个寄存器

8259A 内部有三个 8 位寄存器，每一位对应一根输入线：

- **IRR（Interrupt Request Register，中断请求寄存器）**：记录“哪些线上有请求在等”。
- **ISR（In-Service Register，在服务寄存器）**：记录“哪些中断已经交给 CPU、CPU 正在处理还没 EOI”。
- **IMR（Interrupt Mask Register，中断屏蔽寄存器）**：记录“哪些线被屏蔽了”。软件写 IMR 可以单独关掉某一根线。

一次中断的内部流程是这样的：线 N 出现请求 → IRR 第 N 位置 1 → 如果 IMR 第 N 位为 0，并且没有更高优先级的中断正在服务（ISR 里没有比 N 更高优先级的位），就拉高 INT 通知 CPU → CPU 响应后，8259A 把 IRR 第 N 位转移到 ISR 第 N 位，并把向量号交给 CPU → CPU 执行处理程序 → 处理程序写 EOI → 8259A 清除 ISR 第 N 位。

默认优先级是 IR0 最高、IR7 最低，这就是为什么时钟接在 IRQ0 上：时钟中断的优先级最高。

#### 3.1.3 INTA 周期：向量号是怎么交给 CPU 的

8259A 只有一根 INT 线接到 CPU，那 CPU 怎么知道是哪个中断？答案是一个专门的总线周期：CPU 发现 INTR 被拉高后，会连续发出两个 **INTA（Interrupt Acknowledge）** 总线周期；8259A 在第二个周期里把一个 8 位的向量号放到数据总线上，CPU 从数据总线读到它，再去查 IDT。

这个“CPU 主动去问中断控制器要向量号”的握手方式，在 LAPIC 时代被称为 **ExtINT** 投递模式——下一节会看到，LAPIC 为了兼容 8259A，保留了一种“向量号不由我决定，请去问外面那颗 8259A”的模式。

#### 3.1.4 必须重新编程：向量号冲突

8259A 的向量号不是固定的，而是由软件编程的：初始化时通过一串 **ICW（Initialization Command Word）** 告诉它“IR0 对应向量号几”，IR1 到 IR7 依次递增。

IBM PC 的 BIOS 把主片编程为向量 `0x08` 到 `0x0F`。在 1981 年的 8086 上这没问题，但 Intel 早就把向量 0 到 31 保留给了 CPU 异常，到了 80286 以后的保护模式里，向量 8 是双重错误 `#DF`，向量 13 是一般保护错误 `#GP`，向量 14 是缺页 `#PF`。如果不改，时钟中断（IRQ0，向量 8）和双重错误会共用一个处理程序，内核根本分不清到底发生了什么。

所以每一个保护模式操作系统在初始化时都会**重新编程 8259A**，把向量号挪到 32 以上。Linux 把主片映射到 `0x30` 到 `0x37`、从片映射到 `0x38` 到 `0x3F`，这就是上一章说的“`0x30` 到 `0x3F` 给 16 个 ISA 中断”。

这个细节对 VMM 的意义是：**KVM 模拟的 8259A 必须完整实现 ICW/OCW 编程协议**，因为 guest 会重新编程它，而且 guest 看到的向量号完全取决于它自己的编程。VMM 不能假设“IRQ4 就是向量多少”。

#### 3.1.5 EOI 与两颗芯片

8259A 的 EOI 是往命令端口写 `0x20`（非特定 EOI，清除 ISR 中优先级最高的那一位）。从片上的中断要写两次 EOI：先给从片（端口 `0xA0`），再给主片（端口 `0x20`），因为从片的请求在主片上表现为 IR2 的请求。

8259A 的局限在多处理器时代变得致命：它只有一个输出，只能接到**一颗** CPU 上。其他 CPU 收不到任何外部中断，也没法互相通信。于是有了第二代。

### 3.2 第二代：APIC 体系

1990 年代初，Intel 为多处理器系统设计了 **APIC（Advanced Programmable Interrupt Controller，高级可编程中断控制器）** 体系。它把中断控制器拆成两部分：

```
      ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
      │  CPU 0  │    │  CPU 1  │    │  CPU 2  │    │  CPU 3  │
      │ ┌─────┐ │    │ ┌─────┐ │    │ ┌─────┐ │    │ ┌─────┐ │
      │ │LAPIC│ │    │ │LAPIC│ │    │ │LAPIC│ │    │ │LAPIC│ │
      │ │ ID 0│ │    │ │ ID 1│ │    │ │ ID 2│ │    │ │ ID 3│ │
      │ └──┬──┘ │    │ └──┬──┘ │    │ └──┬──┘ │    │ └──┬──┘ │
      └────┼────┘    └────┼────┘    └────┼────┘    └────┼────┘
           │              │              │              │
  ═════════╧══════════════╧══════════════╧══════════════╧════════  系统总线
                         ▲    （中断以“消息”形式在总线上传递）
                         │
                ┌────────┴────────┐
                │     IOAPIC       │   MMIO 基址 0xFEC00000
                │  24 个输入引脚    │
                │  重定向表 ×24     │
                └─▲──▲──▲──▲──▲───┘
                  │  │  │  │  │
                PIT 键盘 串口 RTC ...   （设备的中断线）
```

- **LAPIC（Local APIC，本地 APIC）**：每颗 CPU 内部集成一个，负责“接收发给我的中断，决定何时交给我的 CPU 核”，外加一个本地定时器，以及向其他 CPU 发送中断的能力。
- **IOAPIC（I/O APIC）**：位于芯片组中，负责“把设备的中断线翻译成发给某个 LAPIC 的消息”。

两者之间不再是一根 INT 线，而是通过总线传递的**中断消息**：消息里写着目的 LAPIC 的 ID、向量号、投递模式。这个设计把“中断从哪来”和“中断到哪去”解耦了，任何设备的中断都可以被路由到任何一颗 CPU。

#### 3.2.1 IOAPIC：一张重定向表

IOAPIC 的核心是一张**重定向表（Redirection Table）**，每个输入引脚一项，每项 64 位。KVM 模拟的 IOAPIC 有 24 个引脚。每一项告诉 IOAPIC：“这根引脚上来了请求，应该怎么发出去”：

```
   重定向表项（64 位）
   63        56 55                    17  16   15   14   13   12   11  10  8 7        0
  ┌───────────┬────────────────────────┬────┬────┬────┬────┬────┬────┬─────┬──────────┐
  │ 目的 APIC  │        保留            │屏蔽 │触发 │远程 │极性│投递 │目的│投递  │  向量号   │
  │    ID     │                        │    │方式 │IRR │    │状态 │模式│模式  │          │
  └───────────┴────────────────────────┴────┴────┴────┴────┴────┴────┴─────┴──────────┘
                                        1=屏蔽 0=边沿      0=高有效 0=物理  000=Fixed
                                              1=电平              1=逻辑  001=最低优先级
                                                                         100=NMI
                                                                         111=ExtINT
```

几个字段值得解释：

- **向量号**：投递到 CPU 时用哪个 IDT 向量。和 8259A 一样，由 guest 软件决定。
- **投递模式**：`Fixed` 是普通中断，投递给目的字段指定的 CPU；`Lowest Priority` 是投给目的集合中当前优先级最低的那颗 CPU（用于负载均衡）；`NMI` 就是作为 NMI 投递；`ExtINT` 表示“这是一个 8259A 风格的中断，向量号去问 8259A”。
- **触发方式与极性**：边沿还是电平，高有效还是低有效。这两位必须与设备的真实行为一致。ISA 设备是边沿、高有效；PCI INTx 是电平、低有效。
- **远程 IRR（Remote IRR）**：只对电平触发有意义。IOAPIC 把一个电平中断发出去之后置 1，收到 LAPIC 转发回来的 EOI 后清 0；置 1 期间这根引脚不会再次发送。这就是 2.5 节说的“电平中断依赖 EOI 重新评估”在 IOAPIC 上的具体实现。
- **屏蔽位**：1 表示这根引脚不发送。Linux 在把一根引脚真正交给驱动之前，一直保持它是屏蔽的。

IOAPIC 本身通过两个 MMIO 寄存器间接访问：往 `IOREGSEL`（基址 +0x00）写要访问的寄存器编号，再从 `IOWIN`（基址 +0x10）读写数据。重定向表第 N 项占寄存器编号 `0x10 + 2N`（低 32 位）和 `0x11 + 2N`（高 32 位）。寄存器 0 是 IOAPIC 的 ID，寄存器 1 是版本号（低 8 位是版本，16–23 位是“最大重定向项编号”，也就是引脚数减一）。

**IOAPIC 有自己的 ID**，和 LAPIC 的 ID 在同一个编号空间里。这个 ID 会出现在固件表里，Linux 会检查固件表里的 IOAPIC ID 是否与它读到的寄存器一致、是否与某个 LAPIC ID 冲突。mini-vmm 把 IOAPIC ID 设为 CPU 个数（4 核时就是 4），正好排在 LAPIC ID 0–3 之后。

#### 3.2.2 LAPIC：每颗 CPU 的“中断秘书”

LAPIC 是一组映射在物理地址 `0xFEE00000` 开始的 4KB MMIO 寄存器。一个有趣的设计是：**每颗 CPU 访问 `0xFEE00000` 时，访问的都是自己的 LAPIC**。同一个物理地址，在不同 CPU 上对应不同的硬件。这对虚拟化是个挑战（同一个 GPA 要按“是哪个 vCPU 在访问”来分发），好在这件事由 KVM 在内核里处理。

LAPIC 最重要的寄存器：

| 偏移 | 名称 | 作用 |
|---|---|---|
| `0x020` | ID | 本 LAPIC 的 APIC ID，高 8 位 |
| `0x030` | Version | 版本号与 LVT 项数 |
| `0x080` | TPR | 任务优先级，软件设置“低于这个优先级的中断别来烦我” |
| `0x0A0` | PPR | 处理器优先级，只读，由 TPR 和正在服务的最高中断共同决定 |
| `0x0B0` | EOI | 写 0 表示当前中断处理完毕 |
| `0x0F0` | SVR | 伪中断向量寄存器，第 8 位是 LAPIC 的软件使能开关 |
| `0x100`–`0x170` | ISR | 在服务寄存器，256 位，每个向量一位 |
| `0x180`–`0x1F0` | TMR | 触发模式寄存器，256 位，标记哪些向量是电平触发 |
| `0x200`–`0x270` | IRR | 中断请求寄存器，256 位 |
| `0x300` / `0x310` | ICR | 中断命令寄存器，用来**向其他 CPU 发送中断** |
| `0x320` | LVT Timer | 本地定时器的向量与模式 |
| `0x350` / `0x360` | LVT LINT0 / LINT1 | 两根本地中断引脚的配置 |
| `0x380` / `0x390` / `0x3E0` | 定时器初值 / 当前值 / 分频 | 本地定时器 |

和 8259A 相比，LAPIC 的 IRR/ISR 从 8 位扩展到了 256 位，每个向量一位；优先级不再由引脚编号决定，而是由**向量号**决定：向量号的高 4 位是“优先级类”，`0x30` 的优先级类是 3，`0xFD` 的是 15。LAPIC 只把优先级类高于 PPR 的中断交给 CPU。

**LVT（Local Vector Table，本地向量表）** 描述 LAPIC 自己的中断源：本地定时器、LINT0、LINT1、性能计数器溢出、温度传感器、错误。其中 LINT0 和 LINT1 是两根物理引脚，历史上 LINT0 接 8259A 的 INT 输出，LINT1 接 NMI。第 7 章讲固件表时会看到，MP table 和 ACPI MADT 都有专门的表项来描述这两根线接的是什么。

**ICR（Interrupt Command Register）** 是 LAPIC 最重要的“发送”接口：CPU 往 ICR 写一个值，就会向目的 CPU 发出一个 **IPI（Inter-Processor Interrupt，处理器间中断）**。ICR 里指定目的 APIC ID、向量号、投递模式。投递模式除了普通的 `Fixed`，还有两个多核启动专用的模式：`INIT`（让目的 CPU 复位）和 `Start-up`（让目的 CPU 从某个地址开始执行）。第八章讲 AP 唤醒时这两个模式是主角。

#### 3.2.3 LAPIC 的开关与 APIC ID 从哪来

LAPIC 有两级开关。一级是 MSR `IA32_APIC_BASE`（编号 `0x1B`）：第 11 位是全局使能，第 8 位标记“这是 BSP（引导处理器）”，第 12 位往上是 LAPIC 的物理基址（默认 `0xFEE00000`）。另一级是 SVR 的第 8 位，由软件在初始化时置位。

APIC ID 是硬件在上电时分配的，通常由 CPU 在封装中的物理位置决定（socket、核、超线程），**不保证从 0 开始连续编号**。操作系统通过三种途径得知 APIC ID：读 LAPIC 的 ID 寄存器、执行 `CPUID` 指令（leaf 1 的 EBX 高 8 位是“初始 APIC ID”）、读固件表。**这三条途径必须给出一致的答案**——真实硬件天然一致，虚拟机则需要 VMM 刻意保证，这是第八章的核心话题之一。

### 3.3 两代共存：virtual wire 与 symmetric I/O

APIC 出现之后，8259A 并没有消失。原因是兼容性：一台机器上电时，BIOS 和早期的操作系统代码（包括 DOS）只认识 8259A。所以 Intel 的多处理器规范定义了几种过渡模式：

- **PIC 模式**：完全绕过 APIC，8259A 的 INT 直接接 CPU。
- **Virtual Wire 模式**：8259A 的 INT 输出接到 BSP 的 LAPIC 的 LINT0 引脚上，LINT0 配置为 ExtINT 模式。效果上 LAPIC 就像一根“虚拟的导线”，把 8259A 的中断透传给 CPU。这是机器上电后的默认状态。
- **Symmetric I/O 模式**：8259A 被屏蔽，所有设备中断走 IOAPIC，由 IOAPIC 按重定向表发送给任意 CPU。这是多核操作系统的正常工作模式。

Linux 启动时的轨迹是：先在 virtual wire 模式下用 8259A 跑一小会儿，等到固件表解析完、IOAPIC 初始化好之后，切换到 symmetric I/O 模式。真实启动日志里的这一行就是切换的时刻：

```
[    0.128018] APIC: Switch to symmetric I/O mode setup
```

**如果 Linux 找不到任何描述 IOAPIC 的固件表**，它就无法切换到 symmetric I/O 模式，只能留在 virtual wire 模式，而且会直接关闭 SMP，因为只有一颗 CPU 能收到中断。对应的日志是 `APIC: ACPI MADT or MP tables are not detected`。这是“固件描述缺失导致功能退化”的典型例子，第七章会展开。

KVM 的 `KVM_CREATE_IRQCHIP` 一次性创建了两颗 8259A 和一个 IOAPIC，并为每个 vCPU 创建一个 LAPIC，正是为了让 guest 能完整地走完这条“先 PIC 后 APIC”的轨迹。

### 3.4 GSI：统一的中断编号

有了两套控制器，就有了编号混乱的问题：一个设备在 8259A 上叫 IRQ4，在 IOAPIC 上接在第几根引脚？如果机器有多个 IOAPIC，第二个 IOAPIC 的第 0 根引脚又叫什么？

ACPI 规范为此引入了 **GSI（Global System Interrupt，全局系统中断号）**：把系统中所有 IOAPIC 的所有引脚排成一个统一的编号空间。第一个 IOAPIC 的引脚 0–23 就是 GSI 0–23，第二个 IOAPIC 从固件表声明的 GSI 基址开始编号。

ISA 的 IRQ 号和 GSI 之间，**默认是恒等映射**：IRQ N 对应 GSI N，也就是 IOAPIC 的第 N 根引脚。但真实主板经常不这么接，最常见的例外是 PIT：在很多主板上，PIT 的 IRQ0 接在 IOAPIC 的第 2 根引脚上（因为第 0 根引脚接了 8259A 的级联输出）。这种“例外”通过固件表里的 **Interrupt Source Override（中断源覆盖）** 表项来声明，意思是“ISA IRQ 0 实际接在 GSI 2 上”。

这个细节在虚拟化里会直接咬人。QEMU 模拟的主板遵循了“IRQ0 接 GSI 2”的真实主板惯例，它的固件表里有这条覆盖，同时 QEMU 会在 KVM 里安装一张相应的中断路由表。而 KVM 在不做任何配置时的**默认路由是恒等映射**，PIT 的中断从 GSI 0 进入 IOAPIC 的第 0 根引脚。如果一个 VMM 照抄了 QEMU 的固件表（声明“IRQ0 接 GSI 2”），却没有像 QEMU 那样修改 KVM 的路由，那么 guest 会去配置 IOAPIC 第 2 根引脚来接收时钟中断，而时钟中断实际到达的是第 0 根引脚，于是时钟中断永远到不了。mini-vmm 的做法是固件表也写恒等映射，与 KVM 的默认路由保持一致。第四章会讲 KVM 的路由表具体长什么样。

### 3.5 第三代：MSI——中断就是一次内存写

8259A 和 IOAPIC 都基于“中断线”。PCI 设备越来越多之后，中断线成了稀缺资源：线要共享，共享就要电平触发，电平触发就要每个驱动在中断处理程序里去问“是不是我的”。

PCI 2.2 引入了 **MSI（Message Signaled Interrupts，消息信号中断）**，彻底抛弃了中断线：设备想中断时，**往一个特定的内存地址写一个特定的值**。这个地址落在 `0xFEE00000` 开始的区域里，地址中编码了目的 LAPIC 的 ID，写入的数据中编码了向量号。芯片组识别出这是一次“中断写”，直接把它变成一个发给目的 LAPIC 的中断消息，完全不经过 IOAPIC。

```
   传统中断：  设备 ──中断线──► IOAPIC ──消息──► LAPIC
   MSI：      设备 ──────── 内存写 0xFEExxxxx ──────► LAPIC
```

MSI 的好处是每个设备（MSI-X 甚至每个队列）都能有自己独占的向量，不用共享，不用猜，而且写操作天然和设备之前的 DMA 写操作保序。

本章的 guest 没有 PCI 设备，所以用不到 MSI。但它是后续章节的主角：VirtIO-PCI 设备和 VFIO 直通设备都用 MSI-X，KVM 的 `irqfd` 机制在路由表里注入的也是 MSI 类型的路由项。这里先建立一个概念：**在 x86 上，中断的本质可以是一次内存写**，理解这一点对后面理解“为什么中断可以绕过 hypervisor 直接投递”非常关键。

### 3.6 x2APIC：把 MMIO 换成 MSR

最后简单提一下 **x2APIC**。xAPIC（就是 3.2 节讲的 LAPIC）有两个问题：APIC ID 只有 8 位，最多 255 颗 CPU；寄存器通过 MMIO 访问，在虚拟化环境里每次访问都要走缺页或 MMIO 模拟路径，代价高。

x2APIC 把 APIC ID 扩展到 32 位，并把寄存器访问从 MMIO 改成 MSR（`rdmsr`/`wrmsr`，编号 `0x800` 开始），ICR 也从两个 32 位寄存器合并成一个 64 位 MSR，一次写入完成 IPI 发送。MSR 访问在虚拟化里可以通过 MSR 位图精确地拦截或放行，比 MMIO 好处理得多。

KVM 总是向 guest 宣称支持 x2APIC（在我们 guest 的 `/proc/cpuinfo` 里能看到 `x2apic` 标志）。但 Linux 只在一定条件下才会真正启用 x2APIC 模式，比如有中断重映射（IOMMU）支持，或者识别出自己运行在某些 hypervisor 上。我们的 guest 两个条件都不满足，所以日志里有这一行，之后它一直工作在 xAPIC 模式：

```
[    0.129768] x2apic: IRQ remapping doesn't support X2APIC mode
```

### 3.7 小结：一张“中断控制器全家福”

把三代放在一起，就是我们要模拟的这台虚拟机里中断的全部通路：

```
                                       ┌──────────────────────────────┐
  PIT (IRQ0) ──┬──────────────────────►│ IOAPIC pin 0                 │
               │                       │ IOAPIC pin 1  ◄── i8042      │  中断消息
               │   ┌─────────┐         │ IOAPIC pin 4  ◄── 串口        │─────────┐
               └──►│ 8259A    │        │ IOAPIC pin 8  ◄── RTC        │         │
  i8042 (IRQ1) ───►│ 主 + 从  │         │ IOAPIC pin 9  ◄── ACPI SCI   │         ▼
  串口  (IRQ4) ───►│          │         └──────────────────────────────┘  ┌─────────────┐
  ...           ──►│          │── INT ── (virtual wire: 接 BSP LINT0) ──►│ LAPIC 0..3  │
                   └─────────┘                                           │ IRR/ISR/TPR │
                                                                          │ 本地定时器   │
                        （PCI 设备的 MSI 直接写 0xFEExxxxx，本章不涉及）  ───►│ ICR → IPI   │
                                                                          └──────┬──────┘
                                                                                 ▼
                                                                          vCPU 0..3 的 IDT
```

每个 ISA 中断源同时连着 8259A 和 IOAPIC，guest 在不同启动阶段用不同的那一个；LAPIC 是所有中断的终点，也是 IPI 的起点。下一章讲虚拟化时，这张图上的每一个方框都会变成 KVM 内核里的一个数据结构，每一个箭头都会变成一次函数调用。

## 四、中断虚拟化：KVM 怎么做

### 4.1 把问题拆开

有了前两章的背景，现在可以精确地说出“中断虚拟化”到底要解决什么。回到 2.2 节那条五段式路径，在虚拟机里，每一段都要换一种实现：

| 真实硬件上的一环 | 虚拟机里由谁、怎样实现 |
|---|---|
| 设备拉高中断线 | 模拟设备的代码（在 VMM 或 KVM 里）调用一个“拉线”接口 |
| 中断控制器仲裁、选出向量号 | 一段**模拟中断控制器**的软件，维护虚拟的 IRR/ISR/重定向表 |
| CPU 在指令边界接收中断、查 IDT | **注入**：hypervisor 在 VMRUN 之前告诉硬件“进入 guest 后，立刻让它收到向量 N” |
| 处理程序运行 | guest 自己的代码，原生执行，不需要任何干预 |
| 写 EOI | guest 写虚拟中断控制器的 EOI 寄存器，**被拦截**，由模拟软件更新虚拟状态 |

于是中断虚拟化可以拆成三个子问题：

1. **模拟**：把 8259A、IOAPIC、LAPIC 这些芯片的寄存器语义用软件实现出来。guest 会读写它们的寄存器，模拟必须和真实芯片行为一致。
2. **注入**：模拟出来的中断控制器决定“该给 vCPU 一个向量 N 了”之后，要有办法让 guest 真的“收到”这个中断：像真实硬件一样打断当前执行、压栈、查 IDT。而且要在**guest 能接收的时候**才能这么做。
3. **性能**：中断是高频事件，每一次中断都伴随若干次中断控制器寄存器访问。如果每次都陷出、都回用户态，开销会压垮虚拟机。

第一个问题是纯粹的软件工程，按芯片手册写就行（learning-note 卷四会逐寄存器讲 KVM 的实现）。这一章重点讲后两个问题，因为它们需要硬件和软件的配合，也是理解 KVM 设计的钥匙。

### 4.2 注入：让硬件替 guest“走一遍 IDT”

#### 4.2.1 最朴素的想法为什么不行

假设 hypervisor 决定给 guest 一个时钟中断，向量号 `0x30`。能不能用软件模拟整个过程：在 VMRUN 之前，把 guest 的 `RIP`、`CS`、`RFLAGS` 压到 guest 的栈上，清 guest 的 `IF`，然后把 guest 的 `RIP` 改成 IDT 第 `0x30` 项指向的地址？

原理上可以，但实际上非常麻烦：hypervisor 要解析 guest 的 IDT（在 guest 的虚拟地址空间里，要走 guest 页表）、处理特权级切换（guest 在用户态时要切换到 TSS 里指定的内核栈）、处理 64 位模式下的 IST 栈、处理压栈时发生缺页怎么办……这些都是 CPU 在处理真实中断时用微码做的事情，用软件重做一遍既慢又容易出错。

#### 4.2.2 硬件方案：EVENTINJ

AMD SVM 的方案是在 VMCB 控制区里提供一个 64 位的 **EVENTINJ（事件注入）** 字段：

```
   VMCB.control.event_inj（64 位）
   63                   32 31  30        12 11  10    8 7         0
  ┌───────────────────────┬───┬────────────┬───┬───────┬───────────┐
  │     错误码（可选）      │ V │    保留     │ EV│ 类型   │  向量号    │
  └───────────────────────┴───┴────────────┴───┴───────┴───────────┘
                           │                  │    │
                           │                  │    └─ 0 = 外部中断 INTR
                           │                  │       2 = NMI
                           │                  │       3 = 异常
                           │                  │       4 = 软件中断 INTn
                           │                  └─ 1 = 压入错误码（部分异常需要）
                           └─ 1 = 本字段有效
```

hypervisor 在 VMRUN 之前把这个字段填好，硬件在进入 guest 模式之后、执行 guest 的第一条指令之前，**按照 guest 当前的 IDT、GDT、TSS、页表，完整地执行一次中断投递**：压栈、切栈、查门描述符、跳转——和 guest 真的收到了一个硬件中断一模一样。投递完成后硬件自动清掉 V 位。

KVM 5.15 里对应的代码只有一行（`arch/x86/kvm/svm/svm.c`）：

```c
static void svm_set_irq(struct kvm_vcpu *vcpu)
{
    struct vcpu_svm *svm = to_svm(vcpu);

    BUG_ON(!(gif_set(svm)));
    ...
    svm->vmcb->control.event_inj = vcpu->arch.interrupt.nr |
        SVM_EVTINJ_VALID | SVM_EVTINJ_TYPE_INTR;
}
```

Intel VMX 有完全对应的机制，叫 VM-entry interruption-information field，在 VMCS 里，格式几乎一样。这是两家硬件在中断虚拟化上的第一个、也是最基本的共同设计：**hypervisor 只负责决定“投递哪个向量”，“怎么投递”交给硬件**。

2.3 节强调要区分异常、中断、NMI，原因就在这里：类型字段决定了硬件用哪套规则投递。比如异常要看是否压错误码，NMI 投递后要屏蔽后续 NMI 直到 `iret`，软件中断要检查门描述符的 DPL。类型填错，guest 看到的就不是它期望的事件。

#### 4.2.3 注入失败怎么办：exit_int_info

有一种微妙的情况：硬件在投递注入的事件时，自己也可能出事。比如压栈时 guest 的栈页恰好不在 NPT 里，触发了一次 `#NPF` 陷出。此时事件投递到了一半，hypervisor 必须知道“有一个事件还没投递完”，处理完缺页后重新注入它，否则这个中断就丢了。

硬件的做法是在 VMCB 的 **EXITINTINFO** 字段（格式与 EVENTINJ 相同）里记录“陷出时正在投递的事件”。KVM 每次陷出后都会检查这个字段（`svm_complete_interrupts()`），如果有值，就把这个事件重新排进队列，下次 VMRUN 时再注入一次。

> 事件投递不是 guest 的一条指令，因此 VMEXIT 后不存在一个可由 VMM 恢复的“投递中间 RIP”；如果 VMM 只是修好 NPT 后重新 `VMRUN`，原本正在投递的事件可能就会丢失。

### 4.3 时机：guest 什么时候能接收中断

注入不是随时都能做的。2.4 节说过，真实 CPU 只在满足条件时才接收外部中断。hypervisor 注入时必须检查同样的条件，否则就会在 guest 的 `cli` 临界区里硬塞进一个中断，破坏 guest 的正确性。

对于外部中断，在 AMD 上“guest 此刻能接收”需要同时满足：

| 条件 | 含义 | 从哪里读 |
|---|---|---|
| GIF = 1 | 全局中断标志打开（上一篇讲过，嵌套虚拟化时 guest 自己也可能执行 `clgi`） | KVM 自己记录 |
| guest 的 `RFLAGS.IF` = 1 | guest 没有关中断 | VMCB 状态保存区 |
| 不在中断影子里 | guest 刚执行完的不是 `sti` 或 `mov ss` | VMCB 的 `int_state` 字段第 0 位 |
| 没有待投递的更高优先级事件 | 比如一个还没注入完的异常 | KVM 自己记录 |

KVM 把这些条件封装在 `svm_interrupt_blocked()` 里。条件不满足时，中断就只能先挂着。

#### 4.3.1 中断窗口：请硬件在“能接收时”通知我

条件不满足时，hypervisor 面临一个问题：guest 什么时候会打开中断？可能是下一条指令（`sti`），也可能是很久以后。hypervisor 不能忙等，也不能每隔一会儿就强行陷出来检查一次。

硬件提供的解决方案叫**中断窗口（interrupt window）**：hypervisor 告诉硬件“请在 guest 能够接收中断的那一刻让我陷出”。在 AMD 上，这是用一个巧妙的“假中断”实现的：

1. hypervisor 在 VMCB 的 `int_ctl` 字段里置位 **V_IRQ**，表示“有一个虚拟中断在等待”。
2. 同时打开 **VINTR 拦截**，表示“当硬件准备把这个虚拟中断交给 guest 时，不要真的交，而是陷出”。
3. 硬件在 guest 执行过程中持续检查：一旦 guest 的 `IF=1` 且不在中断影子里，就会“接收”这个虚拟中断——但因为 VINTR 被拦截，它产生一次 `#VMEXIT(VINTR)`。
4. KVM 收到这次陷出，此时 guest 必定处于能接收中断的状态，于是清掉 V_IRQ，用 EVENTINJ 注入真正的中断，再 VMRUN。

KVM 5.15 的注释把这个技巧说得很直白：

```c
static void svm_set_vintr(struct vcpu_svm *svm)
{
    ...
    svm_set_intercept(svm, INTERCEPT_VINTR);

    /*
     * This is just a dummy VINTR to actually cause a vmexit to happen.
     * Actual injection of virtual interrupts happens through EVENTINJ.
     */
    control = &svm->vmcb->control;
    control->int_vector = 0x0;
    control->int_ctl &= ~V_INTR_PRIO_MASK;
    control->int_ctl |= V_IRQ_MASK |
        ((/*control->int_vector >> 4*/ 0xf) << V_INTR_PRIO_SHIFT);
    vmcb_mark_dirty(svm->vmcb, VMCB_INTR);
}
```

注意最后一行 `vmcb_mark_dirty`，这就是上一篇讲过的 VMCB Clean Bits：改了中断控制相关字段，必须告诉硬件这部分缓存失效了。

Intel 上对应的机制叫 interrupt-window exiting，是 VMCS 执行控制里的一个开关位，语义相同，实现更直接。

#### 4.3.2 把注入逻辑串起来

KVM 每次准备进入 guest 时（`vcpu_enter_guest()`），如果发现有待处理的事件，会调用 `inject_pending_event()`。去掉细节后，它的逻辑是：

```
  inject_pending_event():
      1. 如果上次有注入了一半的事件（来自 exit_int_info）→ 原样再注入一次，结束
      2. 如果有待投递的异常 → 注入异常，结束
      3. 如果有待投递的 NMI：
             guest 能接收 NMI → 注入 NMI
             否则 → 打开 NMI 窗口
      4. 如果中断控制器里有可投递的中断（kvm_cpu_has_injectable_intr）：
             guest 能接收中断 → 从中断控制器取出最高优先级向量（kvm_cpu_get_interrupt）
                                  → 写 EVENTINJ
             如果还有更多待投递的中断 → 打开中断窗口
```

优先级顺序是“未完成事件 > 异常 > NMI > 外部中断”，这与真实 CPU 在指令边界识别事件的优先级一致。第 4 步里的“从中断控制器取出向量”，对 LAPIC 来说意味着：在虚拟 IRR 里找到最高的那一位，把它移到虚拟 ISR 里——和真实 LAPIC 在 CPU 接收中断时做的事完全一样。

### 4.4 唤醒：guest 在跑，或者在睡

上面讨论的是“vCPU 即将进入 guest 时，发现有中断要注入”。但中断是异步的，它到达的时刻，目标 vCPU 可能处于三种状态之一：

```
   中断到达时 vCPU 的状态           KVM 要做什么
  ─────────────────────────────────────────────────────────────────────
   A. 正在 host 里（刚陷出，       什么都不用做：它回到 vcpu_enter_guest 时
      还没重新进入 guest）          自然会检查到挂起的中断
   B. 正在 guest 里全速运行        必须把它“踢”出来：给它所在的物理 CPU
                                  发一个 IPI，导致 #VMEXIT，然后在重新进入
                                  前注入
   C. guest 执行了 HLT，vCPU       必须把它“叫醒”：vCPU 线程正在内核里睡眠，
      线程在 host 里睡觉             唤醒它，让它重新进入 guest 并注入
```

KVM 用一个统一的函数处理后两种情况：`kvm_vcpu_kick()`。

```c
void kvm_vcpu_kick(struct kvm_vcpu *vcpu)
{
    int me, cpu;

    if (kvm_vcpu_wake_up(vcpu))          /* 情况 C：在睡觉就唤醒，完事 */
        return;

    me = get_cpu();
    if (kvm_arch_vcpu_should_kick(vcpu)) {      /* 情况 B：正在 guest 里 */
        cpu = READ_ONCE(vcpu->cpu);
        if (cpu != me && (unsigned)cpu < nr_cpu_ids && cpu_online(cpu))
            smp_send_reschedule(cpu);   /* 给那颗物理 CPU 发一个 IPI */
    }
    put_cpu();
}
```

情况 B 里的 IPI 是一个真实的物理中断。KVM 在初始化 VMCB 时打开了**物理中断拦截**（INTERCEPT_INTR），所以 guest 运行期间到达的任何物理中断都会导致 `#VMEXIT`。这个 IPI 本身的内容无关紧要（它借用的是重调度 IPI），它的唯一作用就是**让目标 vCPU 离开 guest 模式**。离开之后，vCPU 回到 `vcpu_enter_guest()` 的循环顶部，看到有 `KVM_REQ_EVENT` 请求，就会走 4.3.2 节的注入流程。

这就是 KVM 里无数“请求（request）+ 踢（kick）”组合的原型：**要让某个 vCPU 做一件事，就在它的请求位图里置一位，然后踢它一下**。它回到 host 后会检查请求位图并处理。LAPIC 接收中断的代码就是这个模式的教科书示例（`__apic_accept_irq()`，Fixed 模式分支）：

```c
    kvm_lapic_set_irr(vector, apic);           /* 1. 在虚拟 IRR 里置位 */
    kvm_make_request(KVM_REQ_EVENT, vcpu);     /* 2. 置请求：有事件要处理 */
    kvm_vcpu_kick(vcpu);                       /* 3. 踢它 */
```

#### 4.4.1 HLT 为什么不再回到用户态

上一篇结尾提到过：有了内核态的 LAPIC 之后，guest 执行 `HLT` 不再以 `KVM_EXIT_HLT` 返回用户态。现在可以完整地解释这件事了。

`HLT` 的语义是“停下来，直到有中断”。判断“有没有中断”需要看中断控制器的状态，而中断控制器在内核里。所以 KVM 可以完全在内核里处理 HLT：把 vCPU 的 `mp_state` 设为 `KVM_MP_STATE_HALTED`，让 vCPU 线程在内核里睡眠；某个中断经 `kvm_vcpu_kick()` 唤醒它时，检查确实有可投递的中断，就把状态改回 RUNNABLE，重新进入 guest 并注入。用户态的 VMM 全程不知情。

一个空闲的 Linux guest 每秒会执行成百上千次 HLT（每次 idle 都是 `sti; hlt`），如果每次都要回到用户态，再由用户态判断何时重新进入，开销会非常大。这是 KVM 把中断控制器放进内核的直接收益之一。

这里还有一个值得知道的优化：**halt polling**。vCPU 执行 HLT 后，KVM 不会立刻让线程睡眠，而是先忙等一小段时间（我们的 host 上是 `halt_poll_ns=200000`，即 200 微秒），看看中断会不会马上到来。原因是“睡眠-唤醒”本身要经过调度器，延迟在几十微秒量级；如果中断很快就会到来（比如网络包频繁到达时），忙等反而延迟更低。这是一个典型的用 CPU 时间换延迟的权衡。

### 4.5 性能：为什么中断控制器必须在内核里

现在算一笔账。一个跑着普通负载的 Linux guest，每秒会发生多少次中断控制器访问？

- **时钟**：现代 Linux 在忙碌时每个 CPU 每秒有 250 到 1000 次时钟中断（取决于 `CONFIG_HZ`），无论是否 tickless，每次重新编程 LAPIC 定时器都要写一次寄存器。
- **EOI**：每一次中断处理完都要写一次 EOI。
- **IPI**：多核 guest 里，调度器唤醒其他 CPU 上的线程、TLB shootdown、跨 CPU 函数调用都要发 IPI，每次 IPI 要写 ICR。
- **TPR**：某些操作系统（尤其是 32 位 Windows）会频繁读写 TPR 来提升或降低中断优先级。

一台 4 vCPU 的 guest，每秒几万次中断控制器访问是常态。每一次访问都是一次 `#VMEXIT`。关键在于陷出之后去哪里处理：

```
   方案一：中断控制器在用户态（VMM）
   guest 写 EOI ─► #VMEXIT ─► KVM 解码 MMIO 指令 ─► 返回用户态 ─► VMM 更新虚拟
   LAPIC 状态 ─► 可能要调 ioctl 注入下一个中断 ─► 再次 KVM_RUN ─► VMRUN
                  ↑ 两次特权级切换 + 至少一次额外系统调用，数微秒到十几微秒

   方案二：中断控制器在内核（KVM）
   guest 写 EOI ─► #VMEXIT ─► KVM 解码 MMIO 指令 ─► KVM 内部更新虚拟 LAPIC
   状态 ─► 直接 VMRUN
                  ↑ 没有特权级切换，一两微秒
```

上一篇说过，一次 `#VMEXIT` + `VMRUN` 往返本身大约 1000 到 2000 个时钟周期，回用户态再回来要多出几倍。乘以每秒几万次，差距就是“虚拟机能不能用”的差距。

所以 KVM 早在 2007 年就把中断控制器搬进了内核。这是 KVM 里“设备模拟应该在用户态”这条原则最重要的例外。`KVM_CREATE_IRQCHIP` 这个 ioctl 一次性创建了：

- 两颗 8259A PIC（主片 + 从片），挂在内核的 PIO 总线上，端口 `0x20`/`0x21`、`0xA0`/`0xA1`；
- 一个 24 引脚的 IOAPIC，挂在内核的 MMIO 总线上，地址 `0xFEC00000`；
- 并且让**之后创建的每一个 vCPU** 都带一个 LAPIC，地址 `0xFEE00000`。

最后一点带来了一个硬性的顺序约束：`KVM_CREATE_IRQCHIP` **必须在创建任何 vCPU 之前调用**。因为 LAPIC 是在 `KVM_CREATE_VCPU` 里创建的，KVM 在那一刻检查“这台虚拟机有没有内核态 irqchip”，决定要不要给这个 vCPU 挂一个 LAPIC。如果先建了 vCPU 再建 irqchip，KVM 会直接拒绝（5.15 源码里 `if (kvm->created_vcpus) goto create_irqchip_unlock;`，返回 `-EINVAL`）。

同理，**定时器 PIT 也在内核里**（`KVM_CREATE_PIT2`），原因相同：Linux 启动早期用 PIT 做时钟源和频率校准，每秒上千次端口访问。第五章专门讲它。

#### 4.5.1 折中方案：split irqchip

把整个中断控制器放进内核也有代价：攻击面变大（内核代码的 bug 可以被恶意 guest 利用），而且灵活性差（想实现一个与 KVM 不同的 IOAPIC 变种，比如配合虚拟 IOMMU 做中断重映射，就只能改内核）。

所以 KVM 后来又提供了一种折中：**split irqchip**（`KVM_CAP_SPLIT_IRQCHIP`）。只有访问频率最高的 LAPIC 留在内核里，访问频率低的 IOAPIC 和 8259A 回到用户态由 VMM 模拟。IOAPIC 的寄存器访问只在设备驱动初始化、中断亲和性调整时发生，频率很低；而电平中断的 EOI 虽然频繁，但可以由内核 LAPIC 通过一个专门的退出原因（`KVM_EXIT_IOAPIC_EOI`）转告用户态。

不同 VMM 的选择：QEMU 两种模式都支持，需要虚拟 IOMMU 中断重映射时必须用 split 模式；Cloud Hypervisor 使用 split 模式并在用户态实现 IOAPIC；Firecracker 和 kvmtool 使用完整的内核态 irqchip。mini-vmm 选择完整的内核态 irqchip，因为它最简单：VMM 只需要调用两个 ioctl，然后在设备需要中断时“拉线”。

### 4.6 从“拉线”到“注入”：KVM 的中断路由

用户态的设备模型（比如串口）怎么告诉 KVM“我要中断了”？答案是一个 VM 级的 ioctl：

```c
struct kvm_irq_level irq = { .irq = 4, .level = 1 };   /* 把 GSI 4 拉高 */
ioctl(vm_fd, KVM_IRQ_LINE, &irq);
```

注意参数里的 `irq` 是 **GSI 号**，不是 IOAPIC 引脚号，也不是向量号。从 GSI 到“哪个中断控制器的哪根引脚”，KVM 内部有一张**中断路由表**。在 VMM 没有自定义路由时，`KVM_CREATE_IRQCHIP` 会安装一张默认表（`arch/x86/kvm/irq_comm.c`）：

```c
static const struct kvm_irq_routing_entry default_routing[] = {
    ROUTING_ENTRY2(0), ROUTING_ENTRY2(1),    /* GSI 0-15：同时路由到     */
    ...                                      /*   PIC 的第 (n%8) 根引脚  */
    ROUTING_ENTRY2(14), ROUTING_ENTRY2(15),  /*   和 IOAPIC 的第 n 根引脚 */
    ROUTING_ENTRY1(16), ROUTING_ENTRY1(17),  /* GSI 16-23：只路由到 IOAPIC */
    ...
    ROUTING_ENTRY1(22), ROUTING_ENTRY1(23),
};
```

这张表揭示了两件事。第一，**GSI 0–15 同时连着 PIC 和 IOAPIC**，这正是 3.3 节说的“两代共存”：guest 在 virtual wire 阶段用 PIC、在 symmetric I/O 阶段用 IOAPIC，同一根“线”两边都要接上。第二，**默认路由是恒等的**：GSI N 就是 IOAPIC 第 N 根引脚。这就是 3.4 节那个陷阱的根源：固件表必须说“ISA IRQ N 接 GSI N”，不能照抄 QEMU 的“IRQ0 接 GSI 2”。

一次 `KVM_IRQ_LINE` 在 KVM 内部的完整旅程是这样的：

```
  VMM: ioctl(vm_fd, KVM_IRQ_LINE, {irq=4, level=1})
        │
        ▼
  kvm_vm_ioctl_irq_line() → kvm_set_irq(kvm, 用户态源, gsi=4, level=1)
        │  查路由表：GSI 4 → { PIC 主片 pin 4, IOAPIC pin 4 }
        ├──────────────────────────────┐
        ▼                              ▼
  kvm_pic_set_irq()              kvm_ioapic_set_irq()
  （guest 已切到 IOAPIC 模式，     │  读重定向表第 4 项：边沿触发？屏蔽？向量？目的？
    PIC 的这根线被屏蔽，无事发生）   │  边沿触发：只有 0→1 跳变才继续（同电平直接返回）
                                  ▼
                            ioapic_service() → kvm_irq_delivery_to_apic()
                                  │  按目的 APIC ID 找到目标 vCPU 的 LAPIC
                                  ▼
                            __apic_accept_irq()
                                  │  虚拟 IRR 置位 → KVM_REQ_EVENT → kvm_vcpu_kick()
                                  ▼
                            目标 vCPU 被踢出 guest / 被唤醒
                                  ▼
                            vcpu_enter_guest() → inject_pending_event()
                                  │  guest 能接收？能 → EVENTINJ；不能 → 打开中断窗口
                                  ▼
                            VMRUN → guest 的 IDT[vector] 处理程序开始执行
```

图中“边沿触发：只有 0→1 跳变才继续”对应的是 `ioapic_set_irq()` 里的这几行：

```c
    old_irr = ioapic->irr;
    ioapic->irr |= mask;
    if (edge) {
        ioapic->irr_delivered &= ~mask;
        if (old_irr == ioapic->irr) {   /* 这根线本来就是高电平 */
            ret = 0;                    /* 不产生新中断 */
            goto out;
        }
    }
```

也就是说，如果 VMM 对一根边沿触发的线连续两次调用 `level=1`，第二次调用在 KVM 里是**空操作**。这就是 2.5 节说的“模拟设备时每个事件都要制造一个新的上升沿”的源码依据。

还有一个细节：路由表的每一根线，可能有多个“源”在驱动它。比如 GSI 0 既可能被内核里的 PIT 驱动，也可能被用户态驱动。KVM 给每个源分配一个 `irq_source_id`，一根线的最终电平是所有源电平的“或”。用户态的 `KVM_IRQ_LINE` 固定使用 `KVM_USERSPACE_IRQ_SOURCE_ID`。

VMM 也可以用 `KVM_SET_GSI_ROUTING` 安装自己的路由表，路由项的类型除了“接到 PIC/IOAPIC 的某根引脚”，还可以是“发一个 MSI”。后续章节的 `irqfd` 就是把一个 eventfd 绑定到某个 GSI 上，eventfd 被写时 KVM 直接在内核里调用 `kvm_set_irq()`，连这次 ioctl 都省掉了。

### 4.7 硬件加速：让 guest 自己处理中断控制器

即使中断控制器在内核里，每一次 EOI、每一次 ICR 写入、每一次注入仍然需要一次 `#VMEXIT`。为了进一步消除这些陷出，两家厂商都在硬件里加入了 APIC 虚拟化：AMD 叫 **AVIC（Advanced Virtual Interrupt Controller）**，Intel 叫 **APICv**（包括 APIC-register virtualization、virtual-interrupt delivery 和 posted interrupts）。

它们的共同思路是：

1. **给每个 vCPU 一个“虚拟 APIC 页”**：一块 4KB 内存，布局与真实 LAPIC 的寄存器页相同。guest 读 TPR、ISR 这些寄存器时，硬件直接读这块内存，不陷出。
2. **EOI 由硬件处理**：guest 写 EOI 时，硬件自己更新虚拟 ISR、选出下一个待投递的中断，只在必要时（比如电平中断需要通知 IOAPIC）才陷出。
3. **中断直接投递给正在运行的 vCPU**：hypervisor（或者另一个 vCPU 发 IPI 时的硬件）把中断写进目标 vCPU 的虚拟 APIC 页的 IRR 里，再给目标物理 CPU 发一个特殊的“门铃”中断。目标 CPU 如果正在运行这个 vCPU，**不陷出**，直接在 guest 里投递这个中断；如果没有在运行，才退回到“踢一下”的软件路径。Intel 把这叫 **posted interrupt**。

有了这些，guest 在处理中断时可以几乎完全不陷出。代价是实现复杂，并且与某些功能不兼容（比如 AVIC 不能投递 ExtINT，guest 使用 8259A 时 KVM 必须临时关掉 AVIC，前面 `svm_enable_irq_window()` 的注释里就提到了这件事）。

我们的 host CPU 支持 AVIC（第一篇里 VMM 打印的 SVM 特性列表中有 `avic`），但 5.15 的 `kvm_amd` 模块默认不启用它（`/sys/module/kvm_amd/parameters/avic` 是 `N`）。所以本文的所有中断都走的是 4.2 到 4.6 节描述的纯软件模拟加 EVENTINJ 注入路径。这对学习来说反而是好事：每一次注入都能在 KVM 源码里找到对应的代码行。

### 4.8 小结

- 中断虚拟化 = 模拟中断控制器 + 注入 + 性能优化。
- 注入靠硬件：hypervisor 填 EVENTINJ，硬件替 guest 走一遍 IDT；投递到一半被打断时，EXITINTINFO 负责保存现场。
- 注入要看时机：guest 关着中断或处在中断影子里时，用 V_IRQ + VINTR 拦截向硬件“订阅”一个中断窗口。
- 中断到达时 vCPU 可能在运行或在睡眠，KVM 用“置请求位 + kick”统一处理：运行中的用物理 IPI 踢出来，睡眠中的直接唤醒。
- 中断控制器访问太频繁，必须放在内核里，所以有了 `KVM_CREATE_IRQCHIP`，而且它必须在创建 vCPU 之前调用。
- 用户态通过 `KVM_IRQ_LINE` 拉 GSI，默认路由恒等映射到 IOAPIC 引脚；边沿触发的线上重复的高电平是空操作。
- AVIC/APICv 进一步把中断处理搬进硬件，本机支持但默认未开启。

## 五、时间的虚拟化

中断解决了“设备怎么通知 CPU”，但 2.1 节说过，最重要的中断是时钟中断。这一章讲时间：OS 需要哪几种时间设施，它们在虚拟机里怎么实现，以及为什么一个“蜂鸣器端口”会决定 Linux 能不能启动。

### 5.1 OS 需要两种“时间”

操作系统对时间的需求可以分成两类，对应两种不同的硬件：

**定时器（timer / clock event）**：“请在 N 毫秒之后打断我一次”，或者“请每隔 N 毫秒打断我一次”。它产生中断，是调度器抢占、`sleep()` 超时、网络重传定时器的基础。x86 上能扮演这个角色的有：8254 PIT、LAPIC 定时器、HPET。

**时钟源（clocksource）**：“现在是什么时刻”。它不产生中断，只是一个可以随时读取的、单调递增的计数器。`gettimeofday()`、调度器的运行时间统计、日志时间戳都靠它。x86 上最好的时钟源是 **TSC（Time Stamp Counter）**：一个每个时钟周期加一的 64 位计数器，用 `rdtsc` 指令读取，只要几十个周期。

两者经常配合使用：定时器负责“按时叫醒”，时钟源负责“精确计量”。Linux 的时间子系统把它们抽象成 `clock_event_device` 和 `clocksource` 两个接口，启动时从可用的硬件里挑最好的。

### 5.2 8254 PIT：最古老也最可靠的定时器

**PIT（Programmable Interval Timer，可编程间隔定时器）** 是 1981 年 IBM PC 上的 Intel 8253（后来是 8254）。它的输入时钟频率是一个非常奇怪的数：**1.193182 MHz**。这个数字来自原始 IBM PC 的 14.31818 MHz 晶振（NTSC 电视彩色副载波频率的 4 倍，这样可以复用电视机的晶振，降低成本）除以 12。四十多年后，Linux 源码里仍然定义着 `PIT_TICK_RATE 1193182`。

PIT 有三个独立的 16 位倒计数通道，端口是 `0x40`、`0x41`、`0x42`（三个通道的计数器），外加 `0x43`（模式/命令寄存器）：

| 通道 | 历史用途 | 今天在做什么 |
|---|---|---|
| 通道 0 | 系统时钟，输出接 IRQ0 | Linux 启动早期的时钟中断来源，校准其他定时器的参照 |
| 通道 1 | 刷新 DRAM | 已经没用了 |
| 通道 2 | 驱动 PC 喇叭发声 | **被 Linux 用来测量 CPU 频率** |

每个通道有一个 GATE 输入（门控，高电平时计数器才计数）和一个 OUT 输出。通道 0 和 1 的 GATE 永远接高电平。通道 2 的 GATE 和 OUT 比较特殊：它们通过另一个端口 **`0x61`**（历史上叫“系统控制端口 B”，属于 8255 PPI 芯片）暴露给软件：

```
   端口 0x61 的位
   bit 0  （写）PIT 通道 2 的 GATE        1 = 允许计数
   bit 1  （写）喇叭数据使能               1 = 通道 2 的输出送到喇叭
   bit 4  （读）刷新时钟翻转位             大约每 15 微秒翻转一次
   bit 5  （读）PIT 通道 2 的 OUT 输出     计数到 0 时变化
```

软件往 bit 0 写 1、bit 1 写 0，就能让通道 2 “静音计数”；读 bit 5，就能知道计数器有没有数完。这个组合被 Linux 当成了一块高精度的秒表。

### 5.3 频率校准：为什么“蜂鸣器端口”决定能否启动

TSC 虽然好用，但它有一个根本问题：**TSC 每秒加多少，操作系统一开始并不知道。** TSC 的频率等于 CPU 的某个标称频率，不同型号不同。有些 Intel CPU 能通过 CPUID leaf `0x15`/`0x16` 直接报告这个频率，但 AMD 和海光的 CPU 不提供这个信息。

Linux 的办法是**用一个已知频率的时钟去测量 TSC**：让 PIT 通道 2 从 `0xFFFF` 开始倒数，同时读 TSC；PIT 以 1.193182 MHz 的已知频率计数，数了多少个 PIT 周期、TSC 同时走了多少，一除就得到 TSC 的频率。这就是真实启动日志开头这两行的来历：

```
[    0.000000] tsc: Fast TSC calibration using PIT
[    0.000000] tsc: Detected 3000.118 MHz processor
```

`quick_pit_calibrate()` 函数的第一件事就是操作端口 `0x61`：

```c
    /* Set the Gate high, disable speaker */
    outb((inb(0x61) & ~0x02) | 0x01, 0x61);

    /* Counter 2, mode 0 (one-shot), binary count */
    outb(0xb0, 0x43);

    /* Start at 0xffff */
    outb(0xff, 0x42);
    outb(0xff, 0x42);
```

TSC 频率一旦测错或者测不出来，后面的一切都会乱：`udelay()` 的循环次数、LAPIC 定时器的校准（它又是以 PIT 为参照测出来的）、时间戳、调度器时钟……轻则时间跑得快慢不对，重则某个等待循环永远等不到预期的时间，内核卡死。

**这就是“蜂鸣器端口决定能否启动”的因果链**：端口 `0x61` 的 GATE 位 → PIT 通道 2 能否计数 → TSC 频率能否测准 → 所有依赖时间的代码能否正常工作。

在虚拟机里，PIT 本身由 KVM 在内核里模拟（`KVM_CREATE_PIT2`），端口 `0x40`–`0x43` 由 KVM 处理。但端口 `0x61` 是另一块芯片（8255 PPI）的一部分，它**默认不归 KVM 管**，guest 对 `0x61` 的访问会以 `KVM_EXIT_IO` 回到用户态。如果用户态 VMM 不处理它，GATE 位就永远写不进 KVM 模拟的 PIT，通道 2 的 GATE 保持复位值 0（KVM 在 `kvm_pit_reset()` 里把通道 2 的 gate 初始化为 0），计数器根本不动。

KVM 为此提供了一个 flag：创建 PIT 时带上 `KVM_PIT_SPEAKER_DUMMY`，KVM 就会在内核里额外注册端口 `0x61` 的处理函数，把 GATE 位转发给通道 2，读的时候返回真实的 OUT 位和刷新翻转位（`speaker_ioport_read()`）：

```c
    /* Refresh clock toggles at about 15us. We approximate as 2^14ns. */
    refresh_clock = ((unsigned int)ktime_to_ns(ktime_get()) >> 14) & 1;
    ...
    ret = ((pit_state->speaker_data_on << 1) | pit_get_gate(pit, 2) |
           (pit_get_out(pit, 2) << 5) | (refresh_clock << 4));
```

这个 flag 的名字非常有误导性，“SPEAKER_DUMMY”听起来像是“一个假的喇叭，可有可无”。如果 vmm 没带它，结果是 TSC 校准间歇性失败：启动卡在 `skipped IO-APIC setup` 之后，日志时间戳停在 `0.001000` 不再前进。

### 5.4 PIT 在 KVM 里的实现与“补发”

KVM 用一个 host 上的高精度定时器（hrtimer）来模拟 PIT 通道 0：guest 把通道 0 编程为每隔 N 个 PIT 周期产生一次中断，KVM 就启动一个周期为 `N / 1193182` 秒的 hrtimer，每次到期时通过 4.6 节讲的路由表拉一下 GSI 0。

这里有一个虚拟化特有的问题：**guest 不一定总在运行**。vCPU 只是 host 上的一个线程，它可能被 host 调度器换下去几毫秒。在这期间 hrtimer 照样到期，但 guest 没有机会处理中断。等 vCPU 重新运行时，可能已经“欠”了好几个时钟中断。

有些操作系统（老版本的 Windows、老的 Linux）靠数时钟中断的次数来计时，丢一个中断时间就慢一个 tick。所以 KVM 的 PIT 默认工作在**补发（reinject）模式**：它记录欠了多少个中断，并注册一个 **ack notifier**，guest 每对上一次 PIT 中断写一次 EOI，KVM 就补发一个欠下的中断，直到还清为止。这是 2.6 节说的“EOI 作为被别人观察的信号”的具体用例。

现代 Linux 不靠数 tick 计时（它用 TSC 这样的时钟源），补发反而可能造成短时间内时钟中断扎堆。但 Linux 在启动早期很快就会切换到 LAPIC 定时器，PIT 只是过渡，所以这个问题在实践中影响不大。

### 5.5 LAPIC 定时器：每颗 CPU 自己的闹钟

PIT 只有一个，而多核系统需要每颗 CPU 都能独立地设置定时器。所以 Linux 在启动后期会把时钟事件切换到 **LAPIC 定时器**：每个 LAPIC 里都有一个 32 位倒计数器，通过 LVT Timer 寄存器（偏移 `0x320`）配置向量号和模式（单次、周期、TSC deadline）。

LAPIC 定时器的频率同样是未知的（它通常等于总线频率，不同机器不同），所以也要校准。Linux 的 `calibrate_APIC_clock()` 用已经在工作的全局时钟事件（也就是 PIT 的 IRQ0）当参照：在若干个 PIT 时钟中断的时间内，看 LAPIC 计数器走了多少。**PIT 不工作，LAPIC 定时器也校准不了**，这又把一切绑回到了 5.3 节的端口 `0x61` 上。

在 KVM 里，LAPIC 定时器同样用 hrtimer 模拟：guest 写初始计数寄存器时，KVM 根据分频设置算出到期时间，启动一个 hrtimer；到期时在对应 vCPU 的虚拟 LAPIC 里挂起 LVT Timer 指定的向量，然后走 4.4 节的 kick 流程。在 TSC deadline 模式下，guest 写的是 MSR `IA32_TSC_DEADLINE`（`0x6E0`），KVM 同样把它转换成 hrtimer。Intel 平台上 KVM 还可以用硬件的 VMX preemption timer 来实现 TSC deadline，省掉 hrtimer 的开销；AMD 上没有对应的硬件，只能用 hrtimer。

### 5.6 TSC 的虚拟化

TSC 是本章里唯一一个**不需要陷出**就能工作的时间设施。`rdtsc` 指令默认不被拦截，guest 执行它时直接读物理 CPU 的 TSC。但直接读有两个问题需要硬件帮忙：

**问题一：偏移。** 物理 TSC 从 host 开机就开始计数，可能已经是一个很大的值。guest 期望的是“从我开机开始计数”。SVM 在 VMCB 控制区里提供了一个 **TSC_OFFSET** 字段：guest 读到的 TSC = 物理 TSC + TSC_OFFSET。KVM 为每个 vCPU 设置这个偏移，让 guest 的 TSC 从接近 0 开始。

**问题二：频率。** 热迁移时，虚拟机可能从一台 3.0 GHz 的机器迁到一台 2.5 GHz 的机器，guest 已经校准好的 TSC 频率就不对了。SVM 提供了 **TSC ratio**（我们 host 的特性列表里的 `tsc_scale`）：guest 读到的 TSC = 物理 TSC × ratio + offset，KVM 可以让 guest 看到的 TSC 频率保持不变。

**多核的额外问题：同步。** 在多核 guest 里，Linux 要求所有 CPU 的 TSC 是同步的，否则一个线程从 CPU 0 迁到 CPU 1 上读时间，可能读到一个比刚才更早的值，时间倒流了。真实硬件上，现代 CPU 的 TSC 在所有核之间是同步的（`/proc/cpuinfo` 里的 `constant_tsc`、`nonstop_tsc` 标志）。虚拟机里，每个 vCPU 的 TSC_OFFSET 是在不同时刻设置的，如果不加处理，各 vCPU 的 TSC 就会有细微差别。KVM 在 `kvm_synchronize_tsc()` 里做了专门处理：如果多个 vCPU 在很短时间内被写入了“相同”的 TSC 值，KVM 就认为 VMM 的意图是让它们同步，给它们设置完全相同的偏移。Linux guest 在启动每个 AP 时也会检查 TSC 同步（`check_tsc_sync_source()`），发现不同步会打印 `TSC synchronization` 相关的警告并放弃使用 TSC。mini-vmm 的测试里专门断言了日志中没有这类警告。

### 5.7 半虚拟化时钟：我们没有用到的 kvmclock

最后提一下我们的 guest 没有用到的东西。在 QEMU 里启动一个发行版内核，它的时钟源通常是 **kvmclock**，而不是 TSC。kvmclock 是一种**半虚拟化**时钟：hypervisor 和 guest 共享一块内存，hypervisor 在里面写入“TSC 频率、某个时刻的 TSC 值和对应的纳秒时间”，guest 根据这些参数把 TSC 换算成时间。它的好处是 guest 不需要自己校准 TSC，而且热迁移、vCPU 被长时间挂起之后都能保持正确。

kvmclock 需要 guest 内核打开 `CONFIG_KVM_GUEST`（它依赖 `CONFIG_HYPERVISOR_GUEST`），并且 guest 要能识别出自己运行在 KVM 上（通过 CPUID 的 hypervisor leaf `0x40000000`）。我们的 guest 内核没有打开 `CONFIG_HYPERVISOR_GUEST`，所以它完全把自己当成在裸机上运行：用 PIT 校准 TSC，用 TSC 做时钟源，用 LAPIC 定时器做时钟事件。真实日志印证了这一点：

```
[    0.139007] clocksource: tsc-early: mask: 0xffffffffffffffff max_cycles: 0x2b3eb502405, ...
[    0.144081] Calibrating delay loop (skipped), value calculated using timer frequency.. 6000.23 BogoMIPS
...
[    1.576391] clocksource: Switched to clocksource tsc
```

`tsc-early` 是基于早期快速校准结果的 TSC 时钟源；大约一秒之后，Linux 用更长时间的测量精修了频率（`tsc_refine_calibration_work()`），切换到正式的 `tsc` 时钟源。`Calibrating delay loop (skipped)` 说明 Linux 直接用 TSC 频率算出了 `udelay()` 所需的 loops_per_jiffy，不需要再跑那个古老的“BogoMIPS”忙等测量。

这也说明了一个对 VMM 作者很友好的事实：**只要平台设施模拟得足够像真的，一个完全不知道自己被虚拟化的内核也能正常工作。** 半虚拟化是性能和功能上的优化，不是必需品。

顺带解释日志开头那句看起来很吓人的警告：

```
[    0.000000] [Firmware Bug]: TSC doesn't count with P0 frequency!
```

这是 AMD/海光平台特有的检查：内核读 MSR `HWCR`（`0xC0010015`）的第 24 位，确认 TSC 以最高性能状态 P0 的频率计数。KVM 模拟的 `HWCR` 没有置这一位，于是内核打印了这条警告。它不影响任何功能，因为 TSC 频率是实测出来的，不依赖这一位。

### 5.8 小结

- OS 需要定时器（产生中断）和时钟源（可读计数器）两种时间设施。
- PIT 频率已知（1.193182 MHz），被 Linux 当作校准一切的“标准尺”：TSC 频率靠 PIT 通道 2 测，LAPIC 定时器频率靠 PIT 的 IRQ0 测。
- PIT 通道 2 的 GATE 在端口 `0x61` 上，必须用 `KVM_PIT_SPEAKER_DUMMY` 让 KVM 接管这个端口，否则 TSC 校准失败。
- KVM 用 hrtimer 模拟 PIT 和 LAPIC 定时器，PIT 带补发语义，依赖 guest 的 EOI 来驱动补发。
- TSC 原生执行不陷出，硬件提供 offset 和 ratio，KVM 负责多 vCPU 之间的同步。
- 我们的 guest 没有 kvmclock，完全靠“模拟得像真的”来获得正确的时间。

## 六、设备虚拟化：本章涉及的那一部分

### 6.1 三条路线

“让 guest 用上设备”这件事，业界有三条成熟的路线：

| 路线 | 做法 | guest 需要知道自己被虚拟化吗 | 性能 | 代表 |
|---|---|---|---|---|
| **全模拟**（Full Emulation） | 用软件精确模仿一块真实存在的硬件芯片的寄存器行为 | 不需要，guest 用该芯片的原生驱动 | 差：每次寄存器访问都陷出 | QEMU 的 e1000 网卡、IDE 硬盘、本章的全部设备 |
| **半虚拟化**（Paravirtualization） | 设计一种“为虚拟化而生”的虚拟设备，接口专门优化，减少陷出 | 需要，guest 要装专门的驱动 | 好：批量传输，陷出很少 | VirtIO（下一章的主角） |
| **直通**（Passthrough） | 把一块真实物理设备直接交给 guest，guest 的驱动直接操作硬件 | 不需要 | 接近裸机 | VFIO、SR-IOV |

本章只涉及第一条路线，而且只涉及其中最“古老”的一批设备：串口、RTC、键盘控制器、电源管理寄存器。选择它们不是因为它们重要（对一台现代服务器来说，它们几乎都没用），而是因为**Linux 启动时一定会碰它们**，不处理好就启动不起来或者启动很慢。

### 6.2 设备模拟的本质：一台寄存器状态机

从 guest 的角度看，一个设备就是一组寄存器：往某个地址写一个值，设备会“做点什么”；从某个地址读，会得到反映设备当前状态的值；设备有事情时，会拉一根中断线。

所以用软件模拟一个设备，本质上是写一个**状态机**：

```
                      ┌────────────────────────────────┐
   guest 写寄存器 ────►│                                │────► 副作用（输出一个字节、
   (KVM_EXIT_IO/MMIO) │     设备内部状态                │       开始一次传输……）
                      │  （寄存器值、FIFO、模式位……）     │
   guest 读寄存器 ◄────│                                │────► 中断线电平
                      │                                │       （KVM_IRQ_LINE）
   外部事件   ────────►│                                │
   （host 输入等）     └────────────────────────────────┘
```

状态机的三个输入是 guest 写寄存器、guest 读寄存器（注意：**读也可能改变状态**，比如读串口的数据寄存器会把 FIFO 里的字节取走）、外部事件；三个输出是读的返回值、副作用、中断线电平。

写设备模拟时，最容易犯的错误是按芯片手册“完整地”实现所有功能。一块 16550 UART 的手册有几十页，包括波特率发生器、奇偶校验、断线检测、modem 控制线……在虚拟机里，这些大部分毫无意义（没有真实的线缆，波特率设多少都一样）。

真正有用的问题是：

> **guest 的驱动实际会读写哪些寄存器？它期望读到什么值？读不到期望的值时它会怎么做？**

驱动的探测逻辑，才是设备模拟的真正规格说明书。一个设备只需要模拟到“驱动认为它工作正常”的程度。多一分是浪费，少一分是 bug。这是本章最核心的方法论，下面每一个设备都会用这个视角去看。

### 6.3 端口分发与“浮空总线”约定

回忆上一篇：guest 执行 `in`/`out` 时，如果端口不归 KVM 内部的设备（PIC、PIT、以及带 `SPEAKER_DUMMY` 时的 `0x61`）管，就会以 `KVM_EXIT_IO` 回到用户态，`kvm_run->io` 里给出端口号、方向、宽度、次数。VMM 要做的第一件事是**分发**：根据端口号找到对应的设备模拟代码。

一个 VMM 通常会维护一张“地址区间 → 设备”的表，PIO 和 MMIO 各一张。MMIO 的分发逻辑完全相同，只是退出原因换成 `KVM_EXIT_MMIO`、地址换成物理地址。

那**没有任何设备认领的端口**呢？Linux 启动时会盲目地探测一大堆传统端口：第二个串口 `0x2f8`、并口 `0x378`、软驱控制器、游戏杆……如果 VMM 对未知端口报错退出，Linux 根本启动不起来。

正确的做法是模仿真实硬件的行为：在真实的 ISA 总线上，读一个没有设备响应的端口，数据线处于“浮空”状态，由上拉电阻拉成全 1，读回 `0xFF`；写一个没有设备的端口，数据就丢了。所以 VMM 对未知端口的约定是：**读返回全 1，写直接丢弃。** Linux 的很多探测代码正是依赖这个约定来判断“这里没有设备”的，比如串口驱动写一个值再读回来，读到 `0xFF` 就知道这里没有 UART。

### 6.4 16550A 串口：guest 的主要输出通道

串口是本章最重要的设备，因为它是 guest 唯一的“显示器”和“键盘”：内核日志通过它输出，shell 通过它交互。

#### 6.4.1 寄存器布局

16550A 占 8 个连续端口（COM1 是 `0x3f8`–`0x3ff`），但寄存器不止 8 个，有几个端口“一址多用”：

| 偏移 | 读 | 写 | DLAB=1 时 |
|---|---|---|---|
| 0 | RBR：接收到的字节 | THR：要发送的字节 | DLL：波特率除数低字节 |
| 1 | IER：中断使能 | IER | DLM：波特率除数高字节 |
| 2 | IIR：中断标识 | FCR：FIFO 控制 | |
| 3 | LCR：线路控制（第 7 位是 DLAB） | LCR | |
| 4 | MCR：modem 控制 | MCR | |
| 5 | LSR：线路状态 | — | |
| 6 | MSR：modem 状态 | — | |
| 7 | SCR：暂存寄存器 | SCR | |

**DLAB（Divisor Latch Access Bit）** 是 LCR 的第 7 位。它为 1 时，偏移 0 和 1 变成波特率除数寄存器。驱动设置波特率的流程是：置 DLAB → 写除数 → 清 DLAB。模拟时必须根据 DLAB 区分这两组寄存器，否则驱动设置波特率时写的除数会被当成要发送的字符打印出来——一个串口没模拟好时常见的症状，就是开头输出一个奇怪的乱码字符。

#### 6.4.2 输出：LSR 与 THRE 中断

发送一个字节的最简流程：驱动读 LSR，等第 5 位 **THRE（Transmitter Holding Register Empty，发送保持寄存器空）** 为 1，然后把字节写进 THR。

在虚拟机里，“发送”就是把字节写到 host 的标准输出，瞬间完成。所以 LSR 可以永远报告 THRE=1、TEMT=1（发送器完全空闲），驱动永远不需要等待。

但 Linux 的串口驱动在正常工作时并不轮询 LSR，而是用**中断驱动发送**：它打开 IER 的 THRI 位（“发送保持寄存器空时给我中断”），然后在中断处理程序里一次往 THR 塞一批字节。这里有一个关键的语义：**打开 THRI 的那一刻，如果 THR 已经是空的，16550 会立即产生一次中断。** Linux 的 `serial8250_start_tx()` 就是靠这个“一打开就来中断”的行为来启动发送的。如果模拟时漏掉了这个语义，驱动会一直等一个永远不来的中断，表现为 printk 在控制台注册后输出突然停止。

THRE 中断的清除也有讲究：驱动读 IIR 读到“THRE 中断”时，这个中断就被视为已应答；或者驱动再往 THR 写数据，也会清除它。

#### 6.4.3 输入：FIFO、RDA 中断与边沿触发

host 终端上敲的字符，由 VMM 的一个输入线程放进串口的接收 FIFO，同时置位 LSR 的 DR（Data Ready）位。如果 IER 打开了 RDI（接收数据中断），就拉高中断线。guest 驱动在中断处理程序里循环读 LSR 和 RBR，直到 DR 为 0。

IRQ4 是 ISA 中断，**边沿触发**。所以串口模拟每次需要产生新中断时，都必须保证中断线经历一次“低 → 高”的跳变。一种可靠的做法是：每次寄存器访问后都重新计算“当前是否有待处理的中断”，把结果和上一次的线电平比较，只在变化时调用 `KVM_IRQ_LINE`。驱动读空 FIFO 时条件变假、线被拉低；新字节到来时条件变真、线被拉高，这就形成了一个新的上升沿。

#### 6.4.4 IIR 与中断优先级

16550 同时可能有多个中断条件（有数据可读、发送保持寄存器空、线路状态错误、modem 状态变化），但 IIR 一次只报告优先级最高的一个。优先级从高到低是：线路状态 > 接收数据 > 发送保持寄存器空 > modem 状态。IIR 的低 4 位编码中断类型（`0x01` 表示无中断，`0x04` 表示接收数据，`0x02` 表示 THRE），高 2 位在 FIFO 启用时为 `11`。

#### 6.4.5 探测：Linux 怎么认出“这是一块 16550A”

Linux 的 8250 驱动在注册端口前会运行一个叫 `autoconfig()` 的探测函数。它是“驱动定义了模拟规格”的最好例子，以下三步都会碰到：

1. **IER 读写测试**：往 IER 写 0，读回来应该是 0；写 `0x0F`，读回来低 4 位应该是 `0x0F`。读不对，驱动认为这个地址上没有 UART。
2. **回环测试**：把 MCR 设成“回环模式 + OUT2 + RTS”，然后读 MSR。在回环模式下，16550 内部把 MCR 的输出线直接接到 MSR 的输入线上：RTS 接 CTS、DTR 接 DSR、OUT1 接 RI、OUT2 接 DCD。所以驱动期望读到 MSR 的高 4 位恰好是 DCD 和 CTS（`0x90`）。读不对，驱动同样判定没有 UART。
3. **FIFO 测试**：往 FCR 写“启用 FIFO”，然后读 IIR 的高 2 位：`00` 表示老式的 8250/16450，`10` 表示有缺陷的 16550，`11` 表示 16550A。

只有三步都通过，日志里才会出现这一行：

```
[    0.590811] serial8250: ttyS0 at I/O 0x3f8 (irq = 4, base_baud = 115200) is a 16550A
```

回环模式还有一个副作用需要模拟：回环时写入 THR 的字节不应该出现在 host 的输出上，而是回到自己的接收 FIFO 里，并且此时中断线不往外送。

#### 6.4.6 OUT2：PC 上的中断门控

最后一个 PC 特有的细节：在 IBM PC 的主板设计中，串口芯片的中断输出线**经过 MCR 的 OUT2 位控制的一个三态门**才连到中断控制器。OUT2 为 0 时，无论 UART 内部有没有中断，中断线都不会到达 8259A/IOAPIC。Linux 在打开串口时会置位 OUT2。模拟时要照这个规矩来：OUT2 为 0 时不拉线。这个细节会影响驱动的 IRQ 自动探测逻辑。

### 6.5 CMOS RTC：用 host 的时间回答“现在几点”

**RTC（Real-Time Clock，实时时钟）** 是一块由主板纽扣电池供电的时钟芯片（原型是 Motorola MC146818），关机后也在走，Linux 启动时从它读取当前日期时间来初始化系统时间。它还附带 64 或 128 字节的 **CMOS RAM**，BIOS 用来保存设置。

RTC 通过一对端口访问：往 `0x70` 写寄存器编号（第 7 位是历史遗留的“NMI 屏蔽”位，与寄存器选择无关），再从 `0x71` 读写数据。重要的寄存器：

| 编号 | 内容 |
|---|---|
| `0x00` / `0x02` / `0x04` | 秒 / 分 / 时 |
| `0x06` / `0x07` / `0x08` / `0x09` | 星期 / 日 / 月 / 年（两位） |
| `0x0A` | 寄存器 A，第 7 位是 **UIP（Update In Progress）** |
| `0x0B` | 寄存器 B，控制 24 小时制、BCD/二进制编码、中断使能 |
| `0x0C` | 寄存器 C，中断标志，读后清零 |
| `0x0D` | 寄存器 D，第 7 位是 VRT（电池有效） |
| `0x32` | 世纪（事实标准，由 ACPI FADT 的 `century` 字段声明） |

RTC 芯片每秒要更新一次时间寄存器，更新期间（大约 2 毫秒）读出来的值可能不一致。所以协议规定：**读时间之前，要等寄存器 A 的 UIP 位为 0**。Linux 的 `mc146818_get_time()` 就是这样做的：循环读寄存器 A，等 UIP 清零。

如果 VMM 不模拟 RTC，端口 `0x71` 按浮空总线约定读回 `0xFF`，UIP 位永远是 1，Linux 就会一直等下去——每次读寄存器 A 都是一次 `KVM_EXIT_IO`。当然 Linux 不会真的死等，它有超时，但在超时之前已经产生了大量陷出。mini-vmm 实测：不模拟 RTC 时启动过程多出约 4 万次 exit、多花约 1.4 秒，最后打印 `Unable to read current time from RTC` 放弃。

模拟 RTC 很简单：寄存器 A 返回一个 UIP=0 的固定值，寄存器 B 声明“24 小时制、BCD 编码”，读时间寄存器时现取 host 的时间转换成 BCD 返回。真实日志里的这一行说明模拟成功了：

```
[    0.617835] rtc_cmos rtc_cmos: setting system clock to 2026-09-11T06:48:34 UTC (1789109314)
```

**BCD（Binary-Coded Decimal）** 编码的意思是用 4 位表示一个十进制数字：45 秒存成 `0x45` 而不是 `0x2D`。这是 1980 年代为了让数字直接在七段数码管上显示而做的设计。忘记 BCD 转换是 RTC 模拟最常见的 bug，症状是 guest 的系统时间是一个奇怪的日期。

### 6.6 i8042 键盘控制器：为什么键盘控制器能重启机器

**i8042** 是 IBM PC/AT 上的键盘控制器，本身是一颗可编程的 8 位微控制器。它通过两个端口与 CPU 通信：

- `0x60`：数据端口。读是控制器的输出缓冲（键盘扫描码或命令应答），写是命令参数或发给键盘的字节。
- `0x64`：读是状态寄存器，写是控制器命令。

状态寄存器最重要的两位是 **OBF**（第 0 位，输出缓冲满，也就是“有数据可以从 `0x60` 读”）和 **IBF**（第 1 位，输入缓冲满，也就是“我还没处理完你上次写的东西，先别写”）。所有交互都遵循“写之前等 IBF=0，读之前等 OBF=1”的握手协议。

#### 6.6.1 A20 与 reset：键盘控制器的“副业”

i8042 除了管键盘，还有两个与键盘毫无关系的副业，都源于 IBM PC/AT 的历史：

**A20 门。** 8086 只有 20 根地址线，地址超过 1MB 会回绕到 0。有些 DOS 程序依赖这个回绕。80286 有 24 根地址线，不再回绕，为了兼容，IBM 在第 20 根地址线（A20）上加了一个“与门”，由……键盘控制器的一个空闲输出引脚控制。于是 i8042 的**输出端口**第 1 位成了 A20 开关。

**CPU 复位。** 80286 从保护模式回到实模式的唯一办法是复位 CPU。IBM 同样把 CPU 的 RESET 线接到了键盘控制器的一个输出引脚上——输出端口的第 0 位，低电平有效。于是“往 `0x64` 写命令 `0xFE`”（让控制器把输出端口第 0 位拉低一个脉冲）就成了 PC 上最经典的重启方法。

这就是为什么 Linux 的 `reboot=k` 参数（`k` 代表 keyboard）会让内核在重启时往 `0x64` 写 `0xFE`。mini-vmm 的默认 cmdline 就带了 `reboot=k`，VMM 看到这个写入就退出，这是“guest 请求重启 → VMM 退出”的通路。另一条通路是 `panic=-1`：内核 panic 后立即重启，同样走到这里。

#### 6.6.2 探测：让驱动快速通过

Linux 的 i8042 驱动探测时会发一串控制器命令：读控制器配置字节（CTR，命令 `0x20`）、控制器自检（命令 `0xAA`，期望应答 `0x55`）、键盘口测试（命令 `0xAB`，期望应答 `0x00`）、AUX（PS/2 鼠标）口测试等。每一条命令都期望在 `0x60` 上读到应答。

如果 VMM 只实现了一个空壳（比如只处理 `0xFE` 重启），驱动发出“读 CTR”后等不到 OBF，就会忙等到超时（大约 0.6 秒），然后打印 `Can't read CTR while initializing i8042`。功能上没问题，但每次启动白白浪费 0.6 秒。所以控制器命令需要逐条应答。

AUX 口的处理更有技巧：我们不想模拟鼠标，希望驱动“当场”判定 AUX 口不存在，而不是等超时。驱动判断 AUX 口是否存在的方法之一是回环测试：用命令 `0xD3` 让控制器把一个字节“假装从鼠标收到”放回输出缓冲，然后检查状态寄存器的 AUXDATA 位（第 5 位，“这个字节来自鼠标”）。真实硬件上有 AUX 口时这一位会置 1。所以模拟时**故意不置这一位**，驱动就立刻判定回环失败；接下来的 AUX 口测试命令（`0xA9`）回应 `0x01`（“时钟线卡在低电平”），驱动就放弃 AUX 口。整个过程没有一次超时。

键盘本身也要应答：atkbd 驱动会发“复位键盘”（期望 `0xFA` ACK 和 `0xAA` 自检通过）、“读 ID”（期望 `0xFA 0xAB 0x83`）等命令，而且键盘的应答要通过 **IRQ1** 送达，因为 PS/2 设备的数据路径是中断驱动的。控制器自身对命令的应答则不打中断，驱动在关中断的状态下轮询读取。真实日志里探测成功的样子：

```
[    0.606665] i8042: Probing ports directly.
[    0.610182] serio: i8042 KBD port at 0x60,0x64 irq 1
[    0.613705] input: AT Translated Set 2 keyboard as /devices/platform/i8042/serio0/input/input0
```

注意日志里只有 KBD 口没有 AUX 口，说明 AUX 口被当场判定不存在了。

一个布局上的小坑：i8042 的两个端口是 `0x60` 和 `0x64`，中间夹着 `0x61`，而 `0x61` 由 KVM 在内核里处理（第五章的 PIT 通道 2 门控）。所以 VMM 注册 i8042 时不能占用 `[0x60, 0x65)` 整段，要分成两个单端口设备分别注册。

### 6.7 ACPI PM1 寄存器块：让 `poweroff` 真的关机

重启有键盘控制器，关机呢？在 ACPI 时代，关机的标准方式是写 ACPI 定义的**电源管理寄存器**。

ACPI 规定每台机器有一组 **PM1 寄存器块**：PM1 事件块（状态寄存器 `PM1_STS` 和使能寄存器 `PM1_EN`）和 PM1 控制块（`PM1_CNT`）。它们在哪个端口，由固件表（FADT，第七章讲）声明。`PM1_CNT` 的几个关键位：

```
   PM1_CNT（16 位）
   bit 0        SCI_EN    1 = 系统处于 ACPI 模式
   bit 10–12    SLP_TYP   要进入的睡眠状态类型
   bit 13       SLP_EN    写 1 = 立即进入 SLP_TYP 指定的状态
```

ACPI 定义了 S0（正常工作）到 S5（软关机）几种系统状态。`poweroff` 的最后一步是：内核从固件的 AML 代码里查出“S5 对应的 SLP_TYP 值”，然后往 `PM1_CNT` 写入 `SLP_TYP << 10 | SLP_EN`。真实硬件上电源就断了；VMM 看到这个写入就退出。

“S5 对应的 SLP_TYP 值”这个信息存放在固件的 DSDT 表里的一个叫 `_S5_` 的对象中，第七章会把它逐字节拆开。真实日志里关机的样子：

```
[   15.901146] ACPI: PM: Preparing to enter system sleep state S5
[   15.903697] reboot: Power down
[INFO] guest requested poweroff via ACPI S5
```

最后一行是 VMM 自己的输出：它在端口 `0x604` 上收到了 `SLP_TYP=5, SLP_EN=1` 的写入。

### 6.8 设备放在哪里：一张总表

至此，本章涉及的所有设备都出场了。按“谁来模拟”分组：

| 设备 | 端口 / 地址 | 中断 | 模拟者 | 为什么在那里 |
|---|---|---|---|---|
| 8259A PIC ×2 | `0x20-0x21`、`0xA0-0xA1` | — | KVM | 中断控制器，高频 |
| IOAPIC | `0xFEC00000` | — | KVM | 中断控制器，高频 |
| LAPIC ×N | `0xFEE00000` | — | KVM | 中断控制器，最高频 |
| 8254 PIT | `0x40-0x43` | GSI 0 | KVM | 时钟，高频 |
| 端口 B（PIT 门控） | `0x61` | — | KVM（需 `SPEAKER_DUMMY`） | 与 PIT 状态紧耦合 |
| i8042 | `0x60`、`0x64` | GSI 1 | VMM | 低频 |
| 16550A COM1 | `0x3f8-0x3ff` | GSI 4 | VMM | 与 host 终端交互，必须在用户态 |
| CMOS RTC | `0x70-0x71` | GSI 8（未实现） | VMM | 低频 |
| ACPI PM1a | `0x600-0x605` | GSI 9（SCI，未使用） | VMM | 低频，关机要通知 VMM |
| 其他所有端口 | — | — | VMM 兜底 | 读 `0xFF`，写丢弃 |

规律很清楚：**高频的、与 CPU 紧密交互的放内核；低频的、需要与 host 世界交互的放用户态。**

### 6.9 设备模型的并发

最后一个问题在单核时不存在，多核时立刻出现：**多个 vCPU 线程可能同时陷出，同时访问同一个设备。**

比如 vCPU 0 正在往串口写日志，vCPU 2 同时也在写。两个线程同时进入串口模拟代码，同时修改 FIFO 指针、同时计算中断线电平，数据结构就乱了。更隐蔽的是设备与 host 输入线程之间的竞争：输入线程往接收 FIFO 里放字节，vCPU 线程同时从里面取。

设备模型的并发保护有两种思路：每个设备自己加锁（细粒度），或者所有设备访问共用一把大锁（粗粒度）。QEMU 历史上用的是后者，这把锁叫 **BQL（Big QEMU Lock）**，vCPU 线程陷出到用户态处理设备访问时要先拿 BQL。这样设备模型的代码可以完全不考虑并发，代价是所有 vCPU 的设备访问被串行化。对于本章这些低频设备，串行化的代价完全可以接受。

mini-vmm 采用了同样的思路：一把大锁 `io_lock` 包住整个 PIO/MMIO 分发过程。串口另外有一把自己的锁，用来和 host 输入线程同步。两把锁之间有固定的加锁顺序（先大锁、后串口锁），输入线程只拿串口锁，从而避免死锁。实现篇会展开。

### 6.10 小结

- 本章只涉及全模拟路线里最古老的一批设备，它们重要是因为 Linux 启动一定会碰它们。
- 设备模拟是一台寄存器状态机，模拟到什么程度由驱动的探测和使用逻辑决定。
- 未认领的端口读 `0xFF`、写丢弃，这是 Linux 探测逻辑依赖的“浮空总线”约定。
- 串口要处理 DLAB、THRE 中断的“一打开就触发”语义、回环自检、IIR 的 FIFO 位、OUT2 门控，以及边沿触发下每个事件一个新上升沿。
- RTC 要让 UIP=0，并用 BCD 返回 host 时间。
- i8042 要逐条应答控制器命令，用 AUXDATA 位和 AUX_TEST 应答让 AUX 口被当场判定为不存在；命令 `0xFE` 是重启通路。
- ACPI PM1_CNT 的 SLP_TYP/SLP_EN 写入是关机通路。
- 多 vCPU 并发访问设备，用一把大锁串行化是最简单可靠的方案。

## 七、固件：操作系统如何认识这台机器

### 7.1 发现问题：有些硬件是“问不出来”的

操作系统课讲设备驱动时，常常默认“内核知道有哪些设备”。但内核是怎么知道的？

一部分硬件可以**枚举（enumerate）**：PCI 总线规定每个设备的配置空间里有厂商 ID 和设备 ID，内核扫一遍总线就能知道挂了什么；USB 也一样，设备插上后会主动报告自己的描述符。

但还有大量硬件**无法枚举**：

- 内存有多大、哪些物理地址是 RAM、哪些是 ROM、哪些是设备寄存器、哪些是空洞？没有任何指令能问出来。往一个地址写再读，读回来一样也不能证明它是 RAM（可能是设备寄存器），读回来不一样也不能证明它不是（可能是被别人改了）。
- 有几颗 CPU？它们的 APIC ID 是多少？在所有 AP 被唤醒之前，BSP 看不到它们。
- IOAPIC 在哪个物理地址？有几个？每个管多少根线？
- 哪个 ISA 设备的中断线接在 IOAPIC 的哪根引脚上？是边沿还是电平触发？
- 关机要写哪个端口？写什么值？

这些问题的答案由**主板的设计**决定，只有做主板的厂商知道。所以 PC 平台的约定是：主板厂商把这些信息写进**固件**（BIOS 或 UEFI），固件在启动时把它们整理成一组规定格式的数据结构放在内存里，操作系统启动后去读。

**在直接启动内核的 VMM 里，没有 BIOS，VMM 自己就是固件。** 这些数据结构全部要由 VMM 在启动 guest 之前写进 guest 的物理内存。这一章讲它们分别是什么、为什么长成这样。实现篇会逐字段讲每一项该填什么值。

### 7.2 E820：内存地图

最基本的问题是“哪些物理地址是能用的 RAM”。PC 平台上回答这个问题的是 **E820 内存图**，名字来自 BIOS 的一个中断调用：`int 0x15`，`AX=0xE820`。每调用一次，BIOS 返回一个“地址区间 + 类型”的条目。类型 1 是可用 RAM，类型 2 是保留（不能用），还有 ACPI 可回收、ACPI NVS 等其他类型。

直接启动时 VMM 不走 BIOS 调用，而是把 E820 表直接写进启动参数结构（第十二章的 `boot_params`）里。一台 512MB 内存的 guest，mini-vmm 给出的 E820 表只有三项，Linux 启动时原样打印出来：

```
[    0.000000] BIOS-e820: [mem 0x0000000000000000-0x000000000009fbff] usable
[    0.000000] BIOS-e820: [mem 0x000000000009fc00-0x00000000000fffff] reserved
[    0.000000] BIOS-e820: [mem 0x0000000000100000-0x000000001fffffff] usable
```

这三项背后是 PC 平台四十年的历史：

```
   物理地址
   0x00000000 ┌──────────────────────┐
              │ 常规内存（640KB）      │  实模式 DOS 能用的全部内存
              │  ├ 0x0000 实模式中断向量表 │
              │  ├ ...                 │
   0x0009FC00 ├──────────────────────┤
              │ EBDA（扩展 BIOS 数据区）│  BIOS 放杂项数据的地方，1KB
   0x000A0000 ├──────────────────────┤
              │ VGA 显存窗口           │  历史上映射显卡
   0x000C0000 ├──────────────────────┤
              │ 扩展卡 ROM / BIOS ROM  │  0xF0000–0xFFFFF 是主板 BIOS
   0x00100000 ├──────────────────────┤  ← 1MB
              │ 扩展内存               │  内核加载在这里以上
              │ ...                    │
              │                        │
   0xC0000000 ├──────────────────────┤  ← 3GB（在真实机器上附近）
              │ 32 位 MMIO 空洞        │  PCI 设备 BAR、IOAPIC(0xFEC00000)、
              │                        │  LAPIC(0xFEE00000)、BIOS ROM 映像
   0x100000000├──────────────────────┤  ← 4GB
              │ 高端内存（>4GB 部分）   │
              └──────────────────────┘
```

1MB 以下被切成了好几段，640KB 以上到 1MB 是传统的“上位内存区”，历史上被显卡和各种 ROM 占用。现代机器在这个区域未必真有什么，但 Linux 仍然默认它不能用，VMM 要把它报告成保留。

有两个细节对 VMM 特别重要：

**第一，低端 640KB 必须报告成 RAM。** 很容易想到“内核在 1MB 以上，低端内存不给也行”，但这是错的。Linux 需要在 1MB 以下分配一小块内存放 **real-mode trampoline**：唤醒其他 CPU 时，AP 从实模式开始执行，实模式只能访问 1MB 以下的地址，所以 AP 的第一段代码必须放在低端内存里（第八章细讲）。Linux 找不到低端 RAM 放 trampoline 会直接 panic。

**第二，3GB 到 4GB 之间要留出 MMIO 空洞。** IOAPIC 在 `0xFEC00000`、LAPIC 在 `0xFEE00000`，这些地址是硬件寄存器，不能同时是 RAM。真实机器在这附近留出大约 1GB 的空洞给 PCI 设备和各种芯片，超出 3GB 的内存被重新映射到 4GB 以上。mini-vmm 目前只有一个从 0 开始的内存槽，所以限制 guest 内存不超过 3GB，等到后续章节有了 PCI 再处理这个空洞。

### 7.3 MP table：最简单的多处理器描述

E820 只解决了内存问题。CPU 有几颗、中断控制器在哪、中断线怎么接，需要另外的表。历史上有两套格式，按出现顺序：Intel 的 **MP table** 和业界联合制定的 **ACPI**。

**MP table** 来自 1997 年的 Intel MultiProcessor Specification 1.4（简称 MPS）。它的设计非常简单，由两部分组成：

- **MP 浮动指针结构（MP Floating Pointer Structure）**：16 字节，以签名 `"_MP_"` 开头，里面有一个指向配置表的物理地址。操作系统通过**扫描内存**找它：规范规定它必须位于 EBDA 的前 1KB、或者常规内存的最后 1KB（639KB 到 640KB）、或者 BIOS ROM 区（`0xF0000`–`0xFFFFF`）中，并且 16 字节对齐。Linux 的 `default_find_smp_config()` 就是依次扫描这几个区间。
- **MP 配置表（MP Configuration Table）**：以签名 `"PCMP"` 开头的表头，后面跟着一串条目。条目类型只有五种：处理器（每颗 CPU 一项，包括 APIC ID 和“是否是 BSP”标志）、总线（比如“0 号总线是 ISA”）、IOAPIC（ID 和物理地址）、I/O 中断分配（“某总线的某个 IRQ 接在某个 IOAPIC 的某根引脚上”）、本地中断分配（LAPIC 的 LINT0/LINT1 接的是什么）。

两部分都带**校验和**：表中所有字节相加，结果的低 8 位必须为 0。VMM 生成表时要最后计算校验和并填入。校验和错了，Linux 会直接忽略这张表。

MP table 的优点是简单，一个小时就能写出来；kvmtool 和 Firecracker 一直用它。它的缺点是只能描述中断拓扑，描述不了电源管理、设备的即插即用信息，也无法表达超线程（MPS 1.4 早于超线程的出现）。

Linux 解析 MP table 的代码受 `CONFIG_X86_MPPARSE` 控制。**如果 guest 内核没开这个选项，MP table 写得再正确也会被完全忽略。** 这是 mini-vmm 实际踩过的坑：最初的 guest 内核没开 `CONFIG_X86_MPPARSE`，VMM 只提供了 MP table，结果 Linux 认为既没有 MP table 也没有 ACPI MADT，退回 virtual wire 模式，并且关闭了 SMP。后来 VMM 补上了 ACPI 表，guest 内核也打开了 `CONFIG_X86_MPPARSE`，两份表都能被找到。

### 7.4 ACPI：现代 PC 的“机器说明书”

**ACPI（Advanced Configuration and Power Interface，高级配置与电源接口）** 始于 1996 年，由 Intel、Microsoft、Toshiba 等公司联合制定，最初的目标是统一电源管理，后来发展成了描述整台机器的通用框架。今天所有的 x86 服务器和 PC 都靠 ACPI 描述硬件，ARM 服务器也在用。

ACPI 的内容分成两类性质完全不同的东西：

**静态的表（Tables）**：固定格式的二进制结构，就像 MP table 那样，操作系统直接按偏移解析字段。比如“有几颗 CPU、APIC ID 是多少”“电源管理寄存器在哪个端口”。

**AML 字节码（ACPI Machine Language）**：一种由固件提供、由操作系统内置的**解释器**执行的程序代码。它用来描述那些“需要逻辑”的东西：比如“关机要往哪个寄存器写什么值”“这个设备的中断现在配置成了什么”“进入睡眠前要做哪些准备”。AML 由 ASL（ACPI Source Language）编译而来。Linux 内置了 Intel 维护的 ACPICA 解释器来执行 AML，启动日志里的 `ACPI: Core revision 20230628` 就是 ACPICA 的版本号。

把逻辑交给固件、由操作系统解释执行，这是 ACPI 最有争议也最有力的设计：主板厂商不需要为每种操作系统写驱动，只要写一份 AML；代价是操作系统必须在内核里运行一段来自固件的代码。

#### 7.4.1 表格体系：从 RSDP 出发的一棵树

ACPI 的表组织成一棵以 **RSDP** 为根的树：

```
   RSDP（Root System Description Pointer）
   签名 "RSD PTR "，36 字节
   │  操作系统通过扫描内存（0xE0000–0xFFFFF）或启动参数找到它
   │
   └──► XSDT（Extended System Description Table）
        签名 "XSDT"，内容是一串 64 位物理地址，指向其他所有顶层表
        │
        ├──► FADT（Fixed ACPI Description Table），签名 "FACP"
        │    描述固定的硬件：电源管理寄存器块在哪、SCI 中断号、
        │    是否有 8042 键盘控制器、RTC 世纪寄存器的位置……
        │    │
        │    └──► DSDT（Differentiated System Description Table）
        │         签名 "DSDT"，内容是 AML 字节码：整台机器的设备树和方法
        │
        ├──► MADT（Multiple APIC Description Table），签名 "APIC"
        │    描述中断控制器：每颗 CPU 的 LAPIC、每个 IOAPIC、
        │    中断源覆盖、NMI 连接……
        │
        └──► （真实机器上还有很多：HPET、MCFG、SRAT、SLIT、DMAR……）
```

所有的表（RSDP 除外）都以一个统一的 36 字节表头开始：4 字节签名、4 字节表长度、1 字节版本、1 字节校验和、6 字节 OEM ID、8 字节 OEM 表 ID、OEM 版本、创建者 ID、创建者版本。校验和规则和 MP table 一样：整张表所有字节相加低 8 位为 0。

RSDP 有两个校验和：前 20 字节（ACPI 1.0 的部分）一个，全部 36 字节一个。版本号为 2 表示 ACPI 2.0 以上，此时使用 XSDT（64 位地址）；版本号为 0 表示 ACPI 1.0，使用 RSDT（32 位地址）。

真实启动日志里这棵树被完整地打印了出来：

```
[    0.010742] ACPI: RSDP 0x00000000000E0000 000024 (v02 MINVMM)
[    0.012395] ACPI: XSDT 0x00000000000E0030 000034 (v01 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.014814] ACPI: FACP 0x00000000000E0070 000114 (v06 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.017196] ACPI: DSDT 0x00000000000E0190 000032 (v02 MINVMM MINIVMM  00000001 MVMM 00000001)
[    0.019567] ACPI: APIC 0x00000000000E01D0 00005E (v05 MINVMM MINIVMM  00000001 MVMM 00000001)
```

每一行依次是表签名、物理地址、表长度（十六进制）、版本号和 OEM 信息。可以看到 FADT 长 `0x114`（276 字节，ACPI 6.x 的完整长度），DSDT 只有 `0x32`（50 字节，其中 36 字节是表头，AML 只有 14 字节），MADT 长 `0x5E`（94 字节）。

操作系统怎么找到 RSDP？传统方法是在 `0xE0000`–`0xFFFFF` 这段 BIOS 区里按 16 字节对齐扫描签名 `"RSD PTR "`；UEFI 系统通过 UEFI 配置表传递；Linux 启动协议 2.14 版以后，bootloader 还可以直接把 RSDP 的物理地址填进启动参数的 `acpi_rsdp_addr` 字段。mini-vmm 两条路都走了：表放在 `0xE0000`（扫描能找到），同时在启动参数里填了地址。

#### 7.4.2 FADT：固定硬件的说明书

FADT 描述的是 ACPI 所说的“固定硬件（fixed hardware）”：每台 ACPI 机器都必须有、位置由 FADT 声明的一组寄存器。本章关心的字段是：

- **`DSDT` / `X_DSDT`**：DSDT 的物理地址（32 位和 64 位版本各一个字段）。
- **`SCI_INT`**：SCI（System Control Interrupt）使用的中断号，传统上是 9。ACPI 事件（比如按下电源键）通过它通知操作系统。
- **`PM1a_EVT_BLK` / `PM1a_CNT_BLK`**：PM1 事件块和控制块的端口地址，以及它们的长度 `PM1_EVT_LEN` / `PM1_CNT_LEN`。第六章讲的关机就是写这里声明的 `PM1a_CNT`。
- **`SMI_CMD`**：系统从“传统模式”切换到 ACPI 模式要写的端口。填 0 表示“系统已经在 ACPI 模式了，不需要切换”，对 VMM 来说这是最省事的选择。
- **`CENTURY`**：RTC 的 CMOS 里世纪寄存器的编号。
- **`IAPC_BOOT_ARCH`**：一组标志，其中第 0 位“有传统设备（LEGACY_DEVICES）”、第 1 位“有 8042 键盘控制器”。Linux 的 i8042 驱动会参考第 1 位。
- **`Flags`**：一组特性标志。其中第 20 位 **HW_REDUCED_ACPI** 至关重要，下一小节单独讲。

#### 7.4.3 HW-reduced ACPI：一个会让时钟消失的标志位

ACPI 5.0 引入了 **硬件精简（Hardware-Reduced）ACPI** 模式，本意是为平板、ARM 这类没有传统 PC 硬件的平台服务：FADT 的 `Flags` 第 20 位置 1，就表示“这台机器没有 ACPI 固定硬件，也没有传统 PC 设备”。

听起来对虚拟机很合适——虚拟机本来就想越精简越好。Firecracker 近年就改用了 HW-reduced ACPI。但对于一个依赖传统设备的 VMM，这一位是个陷阱。看 Linux 6.6 看到这一位时做了什么（`arch/x86/kernel/acpi/boot.c`）：

```c
void __init acpi_generic_reduced_hw_init(void)
{
    /*
     * Override x86_init functions and bypass legacy PIC in
     * hardware reduced ACPI mode.
     */
    x86_init.timers.timer_init   = x86_init_noop;
    x86_init.irqs.pre_vector_init = x86_init_noop;
    legacy_pic                    = &null_legacy_pic;
}
```

两件事：**不初始化传统定时器**（PIT 被当作不存在），**不使用 8259A PIC**。而第五章说过，我们的 guest 靠 PIT 校准 TSC、靠 PIT 的时钟中断校准 LAPIC 定时器（`quick_pit_calibrate()` 的第一行就是 `if (!has_legacy_pic()) return 0;`）。所以 mini-vmm 的 FADT **故意不设这一位**。代价是必须提供 PM1 寄存器块，因为非精简模式下 ACPI 要求固定硬件存在。

这个例子再次说明了本章的核心原则：固件描述必须与实际模拟的硬件一致。说“没有 PIT”却其实有 PIT，guest 就不会去用它；说“有 PM1 寄存器”却其实没有，guest 写关机寄存器时就没人响应。

#### 7.4.4 MADT：中断控制器的清单

MADT 在表头之后有两个固定字段：**LAPIC 的物理地址**（`0xFEE00000`）和一个标志字（第 0 位 **PCAT_COMPAT** 表示“除了 APIC，机器上还有兼容的 8259A”，Linux 看到后会先正确屏蔽 8259A 再切换到 APIC 模式）。然后是一串变长的条目，每条以“类型、长度”两个字节开始：

| 类型 | 名称 | 内容 |
|---|---|---|
| 0 | Processor Local APIC | ACPI 处理器 ID、APIC ID、标志（第 0 位：已启用） |
| 1 | I/O APIC | IOAPIC ID、物理地址、GSI 基址 |
| 2 | Interrupt Source Override | “ISA IRQ x 实际接在 GSI y 上，触发方式/极性为……” |
| 3 | NMI Source | 某个 GSI 是 NMI |
| 4 | Local APIC NMI | 某颗（或所有）CPU 的 LINT0/LINT1 接的是 NMI |
| 9 | Processor Local x2APIC | 32 位 APIC ID 的 CPU |

例如它里面可能描述为：

```
CPU0 → Local APIC ID 0
CPU1 → Local APIC ID 2
CPU2 → Local APIC ID 4

IOAPIC0:
    address = 0xfec00000
    GSI base = 0

IOAPIC1:
    address = 0xfec01000
    GSI base = 24
```

mini-vmm 的 MADT 包含：每颗 vCPU 一个类型 0 条目、一个类型 1 的 IOAPIC 条目（GSI 基址 0，覆盖 GSI 0–23）、一个类型 4 条目（所有 CPU 的 LINT1 接 NMI）。**没有任何类型 2 的覆盖条目**，因为没有覆盖时 Linux 默认 ISA IRQ N 就是 GSI N，正好与 KVM 的默认路由一致

Linux 解析 MADT 后的日志：

```
[    0.054315] ACPI: LAPIC_NMI (acpi_id[0xff] dfl dfl lint[0x1])
[    0.057571] IOAPIC[0]: apic_id 4, version 17, address 0xfec00000, GSI 0-23
[    0.059482] ACPI: Using ACPI (MADT) for SMP configuration information
[    0.061236] smpboot: Allowing 4 CPUs, 0 hotplug CPUs
```

`version 17` 即 `0x11`，是 Linux 从 KVM 模拟的 IOAPIC 版本寄存器里读出来的；`GSI 0-23` 是它从版本寄存器的“最大重定向项”字段算出的引脚数，与 MADT 声明的 GSI 基址拼在一起。

#### 7.4.5 DSDT 与 AML：把“关机”翻译成一次端口写

最后看 DSDT。真实机器的 DSDT 有几万到几十万字节的 AML，描述了整棵设备树。mini-vmm 的 DSDT 只有一个对象，14 字节，用 ASL 写出来是一行：

```
Name (_S5, Package () { 5, 5, 0, 0 })
```

意思是：定义一个名叫 `_S5_` 的对象（ACPI 名字固定 4 个字符，不足的用下划线补齐），它是一个包含 4 个元素的包，前两个元素分别是 PM1a 和 PM1b 控制寄存器在进入 S5 状态时要写入的 SLP_TYP 值。

Linux 执行关机时，ACPICA 解释器在 AML 命名空间里查找 `\_S5_`，取出第一个元素 5，然后写 `PM1a_CNT = (5 << 10) | SLP_EN`。这就是第六章那次端口写入的来历。启动日志里 `ACPI: PM: (supports S0 S5)` 说明 ACPICA 找到了 `_S5_` 对象；如果 DSDT 里没有它，Linux 会认为这台机器不支持软关机。

这 14 个字节是怎么编码的、每个字节是什么意思，实现篇第十二章会逐字节拆解。

### 7.5 两份表的关系，以及没有 ACPI 时的退路

同一份中断拓扑信息，mini-vmm 用 MP table 和 ACPI MADT 两种格式各描述了一遍。Linux 会怎么选？

Linux 6.6 的启动流程（`setup_arch()`）大致是：先 `find_smp_config()` 扫描 MP table，再 `acpi_boot_table_init()` 找到 ACPI 表，再 `acpi_boot_init()` 解析 MADT，最后 `get_smp_config()` 读取 MP table 的内容。而 `get_smp_config()` 里有这样一个判断：

```c
    /*
     * MPS doesn't support hyperthreading, aka only have
     * thread 0 apic id in MPS table
     */
    if (acpi_lapic && acpi_ioapic)
        return;
```

也就是说，**只要 ACPI MADT 里有 LAPIC 和 IOAPIC 信息，MP table 就被忽略**。日志里的 `ACPI: Using ACPI (MADT) for SMP configuration information` 正说明了这一点。同时日志里也有 `found SMP MP-table at [mem 0x0009fc00-0x0009fc0f]`，说明 MP table 确实被找到了，只是没被采用。

那为什么还要保留 MP table？因为存在**没有 ACPI 的情况**：

- guest 内核没有编译 ACPI 支持（`CONFIG_ACPI=n`），某些极简内核会这么做；
- 内核命令行带了 **`acpi=off`**，这在调试时很常见，也是 mini-vmm 在还没有 ACPI 表时期的实际状态。

`acpi=off` 时，Linux 完全不解析 ACPI 表，此时唯一的中断拓扑来源就是 MP table。把各种组合的结果列出来：

| guest 看到的固件表 | Linux 的行为 | 结果 |
|---|---|---|
| ACPI MADT 可用 | 用 MADT，忽略 MP table | 正常：symmetric I/O 模式，多核，ACPI 关机 |
| 无 ACPI（`acpi=off` 或未编译），有 MP table，开了 `CONFIG_X86_MPPARSE` | 用 MP table | 多核和 IOAPIC 正常；但 FADT 也没了，**不能 ACPI 关机**，`poweroff` 之后 VMM 收不到 S5 写入，只能靠别的途径退出（比如 `reboot=k` 的 i8042 复位） |
| 无 ACPI，有 MP table，没开 `CONFIG_X86_MPPARSE` | 两份都用不上 | 打印 `APIC: ACPI MADT or MP tables are not detected`，退回 virtual wire 模式，**关闭 SMP**，只剩一颗 CPU |
| 两份都没有 | 同上 | 同上 |

第三行正是 mini-vmm 早期的状态。它的症状非常“安静”：没有报错，系统能启动，只是 `nproc` 永远是 1，`/proc/interrupts` 里的中断全挂在 `XT-PIC` 上而不是 `IO-APIC` 上。

所以 MP table 在这里扮演的是**退路**的角色：成本很低（两百多行代码），在 ACPI 不可用时还能保住多核和 IOAPIC。代价是必须保证两份表描述的是同一台机器：CPU 数量、APIC ID、IOAPIC 的 ID 和地址、ISA IRQ 到 GSI 的映射，两边必须完全一致。否则 guest 在带 `acpi=off` 和不带时会看到两台不同的机器，这种 bug 极难排查。

### 7.6 启动协议：固件与内核的最后一次握手

固件表描述了“机器是什么样”，但还有一类信息需要在内核入口处直接交接：内核命令行在哪、initrd 在哪、E820 表、RSDP 地址……以及 CPU 在跳进内核的那一刻处于什么状态。这些由 **Linux x86 启动协议（boot protocol）** 规定（内核源码 `Documentation/arch/x86/boot.rst`）。

启动协议的核心是一个 4KB 的结构体 `struct boot_params`，因为历史上它放在内存第 0 页，也常被称为 **zero page**。它包含一个 **setup header**（原本位于内核镜像的固定偏移，bootloader 读出、填好、再交给内核），以及 E820 表、ACPI RSDP 地址、initrd 位置等字段。

64 位启动协议规定了进入内核 64 位入口 `startup_64` 时的 CPU 状态：已处于长模式、分页开启、页表恒等映射覆盖了内核、`boot_params`、命令行和 initrd；中断关闭；`CS` 必须是一个 64 位代码段、选择子为 `0x10`，`DS`/`ES`/`SS` 是数据段、选择子为 `0x18`；`RSI` 寄存器里放着 `boot_params` 的物理地址。

这些要求每一条都有具体的来历，错一条内核就起不来。这里只强调一点：**启动协议是 VMM 与 guest 内核之间的“ABI”**，它比 ACPI 更底层——内核在还没有能力解析任何表的时候，就要依赖启动协议给出的信息。

### 7.7 小结

- 无法枚举的硬件信息由固件描述，直接启动时 VMM 就是固件。
- E820 描述内存：低 640KB 必须是 RAM（AP trampoline 需要），640KB–1MB 报保留，3GB–4GB 留 MMIO 空洞。
- MP table 简单，只描述 CPU 和中断拓扑，要求 guest 开 `CONFIG_X86_MPPARSE`。
- ACPI 是现代标准：RSDP → XSDT → FADT（→ DSDT）/ MADT。表是静态结构，AML 是固件提供、内核解释执行的代码。
- FADT 声明 PM1 寄存器块、SCI 中断号等固定硬件；不能设 HW_REDUCED_ACPI 位，否则 Linux 会放弃 PIT 和 8259A。
- MADT 列出每颗 CPU 的 APIC ID 和 IOAPIC；不写中断源覆盖，保持与 KVM 默认路由一致的恒等映射。
- DSDT 里的 `_S5_` 对象把关机翻译成一次 PM1a_CNT 写入。
- Linux 优先用 ACPI；`acpi=off` 时 MP table 是保住多核的退路，两份表必须描述同一台机器。
- 启动协议（`boot_params` + 64 位入口状态）是 VMM 与内核之间最底层的约定。

## 八、多核虚拟化（SMP）

### 8.1 SMP 复习：一样的 CPU，不一样的角色

**SMP（Symmetric Multi-Processing，对称多处理）** 的“对称”指的是：所有 CPU 地位平等，共享同一份物理内存，都能执行内核代码，都能处理中断。操作系统课讲过的自旋锁、内存屏障、per-CPU 变量、负载均衡，都是为 SMP 服务的。

但在**启动**这个阶段，x86 上的 CPU 并不对称。上电时硬件从所有 CPU 中选出一颗作为 **BSP（Bootstrap Processor，引导处理器）**，它从复位向量开始执行固件代码、加载操作系统；其余的 CPU 叫 **AP（Application Processor，应用处理器）**，上电后什么都不执行，停在一个特殊的等待状态里，直到 BSP 把它们叫醒。哪颗是 BSP，记录在它的 `IA32_APIC_BASE` MSR 第 8 位上。

所以“多核启动”在 x86 上是一个**接力**的过程：BSP 独自完成大部分初始化，然后逐个唤醒 AP，每个 AP 醒来后自己完成一小段初始化，报告“我上线了”，加入调度。

每颗 CPU 靠 **APIC ID** 来标识，这是 IPI 的“收件地址”。第三章说过，APIC ID 可以通过 LAPIC 的 ID 寄存器、CPUID 指令、固件表三条途径获得，真实硬件上三者天然一致。

### 8.2 真实 x86 上 AP 是怎么醒来的

#### 8.2.1 INIT-SIPI-SIPI

Intel 在 MP 规范里定义了唤醒 AP 的标准协议，它完全依靠第三章讲过的 LAPIC 的 ICR（中断命令寄存器）来实现。BSP 对每一个 AP 执行：

```
   BSP                                                     AP（APIC ID = n）
    │                                                       │  上电后处于
    │                                                       │  wait-for-SIPI 状态
    │  写 ICR：目的 = n，投递模式 = INIT                       │
    │ ─────────────────────── INIT IPI ───────────────────► │  复位：寄存器回到
    │                                                       │  上电初值，继续等待
    │  等待（规范要求 10ms，现代 Linux 在新 CPU 上缩短）         │
    │                                                       │
    │  写 ICR：目的 = n，投递模式 = Start-up，向量 = VV         │
    │ ─────────────────────── SIPI ───────────────────────► │  从实模式地址
    │                                                       │  VV00:0000 开始执行
    │  等待 200µs，再发一次 SIPI（为兼容老硬件）                 │  即物理地址 0xVV000
    │ ─────────────────────── SIPI ───────────────────────► │  （已在运行则忽略）
    │                                                       ▼
    │  等待 AP 报告“我已上线”                               执行 trampoline 代码
```

**INIT IPI** 让目标 CPU 复位到一个干净的状态。**SIPI（Startup IPI）** 是一种特殊的 IPI，它的 8 位“向量号”不是用来查 IDT 的，而是一个**页号**：AP 收到 SIPI 后，以实模式从 `CS = VV << 8`、`IP = 0` 开始执行，也就是物理地址 `VV × 0x1000`。8 位的页号意味着这个地址只能在 1MB 以下，并且必须 4KB 对齐。

这就是第七章说“低端 640KB 必须报告成 RAM”的原因：AP 的第一条指令必须位于 1MB 以下的某个页面上，Linux 需要在那里放一段代码。

发两次 SIPI 是历史遗留：早期的某些 CPU 可能错过第一个 SIPI。现代 Linux 仍然按规范发两次，AP 如果已经在第一次 SIPI 后开始运行，会忽略第二次。

#### 8.2.2 Linux 的 trampoline：从实模式一路爬到长模式

AP 醒来时处于实模式，16 位、没有分页，和 1981 年的 8086 一样。而内核是运行在 64 位长模式、高端虚拟地址上的。所以 Linux 在低端内存里放了一段叫 **trampoline（蹦床）** 的代码（`arch/x86/realmode/rm/trampoline_64.S`），它的作用就是带着 AP 走完 BSP 在启动时走过的那条路：

```
   实模式（16 位）      ← SIPI 把 AP 放在这里，CS:IP = VV00:0000
        │  加载临时 GDT，置 CR0.PE
        ▼
   保护模式（32 位）
        │  加载临时页表（trampoline_pgd），置 CR4.PAE、EFER.LME、CR0.PG
        ▼
   长模式（64 位）
        │  跳到内核的 secondary_startup_64
        ▼
   内核代码：切到内核页表，查出自己是几号 CPU，设置 per-CPU 数据和栈
        │
        ▼
   start_secondary()：初始化本 CPU 的 LAPIC、定时器，报告上线，进入 idle 循环
```

这里有一个对 VMM 来说至关重要的细节。Linux 6.6 默认启用了**并行 AP 启动**：BSP 几乎同时唤醒所有 AP，所有 AP 并行地走 trampoline，而不是一个接一个。并行启动时，AP 在进入内核之后怎么知道自己是“几号 CPU”？看 `arch/x86/kernel/head_64.S`：

```asm
.Lread_apicid_mmio:
    /* Read the APIC ID from the fix-mapped MMIO space. */
    movq    apic_mmio_base(%rip), %rcx
    addq    $APIC_ID, %rcx
    movl    (%rcx), %eax
    shr     $24, %eax              /* EAX = 本 CPU 的 LAPIC ID */
    ...
.Llookup_AP:
    /* EAX contains the APIC ID of the current CPU */
    xorq    %rcx, %rcx
    leaq    cpuid_to_apicid(%rip), %rbx

.Lfind_cpunr:
    cmpl    (%rbx,%rcx,4), %eax    /* 在 cpuid_to_apicid[] 表里找 */
    jz      .Lsetup_cpu
    inc     %ecx
    cmpl    nr_cpu_ids(%rip), %ecx
    jb      .Lfind_cpunr

    /*  APIC ID not found in the table. Drop the trampoline lock and bail. */
    ...
1:  cli
    hlt
    jmp     1b
```

AP 读自己 LAPIC 的 ID 寄存器，拿着这个 ID 去 `cpuid_to_apicid[]` 表里查找自己的逻辑 CPU 编号。而 `cpuid_to_apicid[]` 是 BSP 早先根据**固件表（MADT 或 MP table）** 里的 APIC ID 填出来的。如果 LAPIC 报告的 ID 在固件表里找不到，AP 就关中断、`hlt`，永远停在那里。BSP 那边等不到这个 AP 上线，最终超时，日志里出现 `failed to report alive state` 之类的错误。

这就是本章要反复强调的“三方一致”在硬件层面的体现。下面讲到虚拟化时还会遇到另外两方。

真实日志里 AP 启动的过程只有几行，从开始唤醒到 4 颗 CPU 全部上线大约 5 毫秒：

```
[    0.457657] smp: Bringing up secondary CPUs ...
[    0.459283] smpboot: x86: Booting SMP configuration:
[    0.460087] .... node  #0, CPUs:      #1 #2 #3
[    0.464195] smp: Brought up 1 node, 4 CPUs
```

### 8.3 虚拟化后：vCPU 就是一个线程

上一篇讲过 KVM 的文件描述符层级：每个 vCPU 是一个 fd，VMM 为每个 vCPU 创建一个线程，线程在自己的 fd 上反复调用 `KVM_RUN`。现在把这个模型放到多核的场景下看：

```
   Guest 视角                        Host 视角
  ┌─────────────────────────┐      ┌──────────────────────────────────────────┐
  │  CPU 0  CPU 1  CPU 2  CPU 3│    │ VMM 进程                                   │
  │   │      │      │      │   │    │  ├─ 主线程（初始化后等待 join）              │
  │   ▼      ▼      ▼      ▼   │    │  ├─ vcpu0 线程 ── ioctl(fd0, KVM_RUN) 循环  │
  │  共享的“物理内存”           │    │  ├─ vcpu1 线程 ── ioctl(fd1, KVM_RUN) 循环   │
  │                           │    │  ├─ vcpu2 线程 ── ioctl(fd2, KVM_RUN) 循环   │
  └─────────────────────────┘      │  ├─ vcpu3 线程 ── ioctl(fd3, KVM_RUN) 循环   │
                                    │  └─ console 线程（读 stdin 喂给串口）         │
                                    │                                            │
                                    │ 同一块 mmap 出来的匿名内存 = guest 物理内存  │
                                    └──────────────────────────────────────────┘
                                                      │
                                           host 调度器决定每个线程
                                           此刻在哪颗物理 CPU 上跑
```

这个模型有几个直接的推论：

**guest 的“并行”就是 host 线程的并行。** 4 个 vCPU 线程可以被 host 调度到 4 颗不同的物理核上同时运行，guest 获得真正的并行。在 host 上用 `top -H` 能看到 `vcpu0` 到 `vcpu3` 四个线程，guest 满载时每个都接近 100% CPU。

**guest 的内存一致性由硬件保证。** vCPU 在 guest 模式下原生执行指令，guest 的内存访问就是真实的内存访问，x86 的 TSO 内存模型、缓存一致性协议、`lock` 前缀的原子操作全部原样生效。guest 内核的自旋锁、RCU、内存屏障不需要 hypervisor 做任何事情就能正确工作。

**guest 的“CPU”可能被抢走。** 这是虚拟化特有的问题。host 调度器可以在任何时刻把一个 vCPU 线程换下去，而 guest 对此一无所知。如果被换下去的 vCPU 恰好持有一把自旋锁，其他 vCPU 就会空转等待一个“不在运行”的锁持有者，这叫**锁持有者抢占（lock-holder preemption）**。硬件为此提供了 **PAUSE 拦截**：自旋等待循环里通常有 `pause` 指令，硬件检测到一个 vCPU 在短时间内执行了大量 `pause`，就产生一次陷出（我们 host 的特性列表里的 `pausefilter` 就是这个功能），KVM 借机让出物理 CPU 给其他 vCPU，希望锁持有者能被调度上来。

**vCPU 数量可以超过物理 CPU 数量（超卖）**，代价是上面这类问题更严重。生产环境里对延迟敏感的虚拟机通常会把 vCPU 线程**绑定（pin）** 到固定的物理核上，避免它们被随意迁移和抢占。

### 8.4 KVM 如何模拟 INIT/SIPI

真实 AP 在收到 SIPI 之前处于 wait-for-SIPI 状态，什么都不执行。虚拟机里，这个状态由 KVM 为每个 vCPU 维护的 **`mp_state`** 字段表达：

| `mp_state` | 含义 |
|---|---|
| `KVM_MP_STATE_RUNNABLE` | 可以运行 |
| `KVM_MP_STATE_UNINITIALIZED` | 刚创建的 AP，等待 INIT |
| `KVM_MP_STATE_INIT_RECEIVED` | 收到了 INIT，等待 SIPI |
| `KVM_MP_STATE_HALTED` | 执行了 HLT，等待中断 |

vCPU 创建时的初始状态在 `kvm_arch_vcpu_create()` 里决定：

```c
    if (!irqchip_in_kernel(vcpu->kvm) || kvm_vcpu_is_reset_bsp(vcpu))
        vcpu->arch.mp_state = KVM_MP_STATE_RUNNABLE;
    else
        vcpu->arch.mp_state = KVM_MP_STATE_UNINITIALIZED;
```

有内核态 irqchip 时，BSP（默认是 0 号 vCPU）创建出来就是 RUNNABLE，其他 vCPU 是 UNINITIALIZED。**没有内核态 irqchip 时，所有 vCPU 一创建就是 RUNNABLE**，因为此时 KVM 没有 LAPIC，也就没法接收 INIT/SIPI，只能让用户态自己决定每个 vCPU 从哪里开始跑。这就是为什么 mini-vmm 规定多核只能配合 Linux 启动模式：第一篇的裸机模式没有创建 irqchip，4 个 vCPU 会同时从同一个入口地址开跑，而那段 payload 根本不知道有多个 CPU。

一次完整的虚拟 AP 唤醒流程：

```
  AP 线程                                  BSP（guest 里）
  ioctl(KVM_RUN)
  │ mp_state == UNINITIALIZED
  │ → kvm_vcpu_block()：在内核里睡眠          │
  │   （不占 CPU）                           │ guest 写 LAPIC 的 ICR（INIT）
  │                                         │ → #VMEXIT → KVM 模拟 ICR 写入
  │                                         │ → kvm_apic_send_ipi()
  │                                         │ → 目标 LAPIC 的 __apic_accept_irq()
  │                                         │     pending_events |= INIT
  │ ◄───────── kvm_vcpu_kick() 唤醒 ─────────│     kvm_vcpu_kick()
  │ kvm_apic_accept_events()：               │
  │   INIT → 复位 vCPU，mp_state = INIT_RECEIVED
  │ 返回 -EAGAIN 给用户态                     │
  │                                         │
  ioctl(KVM_RUN)（用户态看到 EAGAIN 后重进）   │ guest 写 ICR（SIPI，向量 VV）
  │ ...                                     │ → pending_events |= SIPI，sipi_vector = VV
  │ kvm_apic_accept_events()：               │
  │   SIPI → kvm_vcpu_deliver_sipi_vector()  │
  │          CS.selector = VV << 8           │
  │          CS.base     = VV << 12          │
  │          RIP         = 0                 │
  │          mp_state = RUNNABLE             │
  ▼                                         │
  VMRUN → AP 在 guest 里从 0xVV000 开始执行 trampoline
```

`kvm_vcpu_deliver_sipi_vector()` 的实现只有几行，和硬件规范一一对应：

```c
void kvm_vcpu_deliver_sipi_vector(struct kvm_vcpu *vcpu, u8 vector)
{
    struct kvm_segment cs;

    kvm_get_segment(vcpu, &cs, VCPU_SREG_CS);
    cs.selector = vector << 8;
    cs.base = vector << 12;
    kvm_set_segment(vcpu, &cs, VCPU_SREG_CS);
    kvm_rip_write(vcpu, 0);
}
```

流程图中间有一个用户态必须注意的细节：**AP 的线程在等待 INIT/SIPI 时，`KVM_RUN` 会以 `-EAGAIN` 返回**，而不是进入 guest。看 5.15 的 `kvm_arch_vcpu_ioctl_run()`：

```c
    if (unlikely(vcpu->arch.mp_state == KVM_MP_STATE_UNINITIALIZED)) {
        if (kvm_run->immediate_exit) {
            r = -EINTR;
            goto out;
        }
        kvm_vcpu_block(vcpu);                   /* 睡到有事件 */
        if (kvm_apic_accept_events(vcpu) < 0) {
            r = 0;
            goto out;
        }
        kvm_clear_request(KVM_REQ_UNHALT, vcpu);
        r = -EAGAIN;                            /* 醒了，但不进 guest */
        if (signal_pending(current)) {
            r = -EINTR;
            kvm_run->exit_reason = KVM_EXIT_INTR;
            ++vcpu->stat.signal_exits;
        }
        goto out;
    }
```

`-EAGAIN` 的意思是“状态变了，请再调用一次”。用户态如果把它当成错误，AP 一醒来整台虚拟机就退出了。正确的处理是把它和 `-EINTR` 一样看待：不是错误，重新进入 `KVM_RUN` 即可。

从这张流程图还能看出一件事：**VMM 在整个 AP 唤醒过程中什么都不用做**。它只需要为每个 vCPU 创建一个线程，让它们都进入 `KVM_RUN`。AP 线程在 KVM 里安静地睡着，不占 CPU，直到 guest 里的 BSP 通过虚拟 LAPIC 把它叫醒。VMM 的全部职责是：线程、CPUID、固件表。

### 8.5 IPI 的代价

AP 全部上线后，多核 guest 的 CPU 之间会频繁地互发 IPI：

- **重调度 IPI**：CPU 0 唤醒了一个应该在 CPU 2 上运行的线程，要通知 CPU 2 “该调度了”。
- **函数调用 IPI**：让另一颗 CPU 执行某个函数，比如修改内核代码后让所有 CPU 同步指令缓存。
- **TLB shootdown**：一颗 CPU 修改了页表，要让其他正在使用这张页表的 CPU 刷掉 TLB 中的旧条目。

真实日志里 `/proc/interrupts` 的最后几行就是这些 IPI 的计数：

```
           CPU0       CPU1       CPU2       CPU3
LOC:        344        114        179        120   Local timer interrupts
RES:          0         16         15         12   Rescheduling interrupts
CAL:        173         71        139         39   Function call interrupts
TLB:          0          0          1          0   TLB shootdowns
```

在虚拟机里，一次 IPI 的成本比裸机高得多：发送方写 ICR 导致一次 `#VMEXIT`，KVM 模拟 ICR、找到目标 vCPU、置请求位、踢它；如果目标 vCPU 正在 guest 里运行，还要给它所在的物理 CPU 发一个真实的 IPI，导致目标也 `#VMEXIT` 一次，然后注入中断。一次 guest IPI 至少对应两次世界切换。这是 AVIC/APICv 这类硬件加速最能发挥作用的地方：发送方写 ICR 时硬件直接把中断投递到目标 vCPU 的虚拟 APIC 页，目标在运行时无需陷出。

### 8.6 CPU 拓扑：guest 要知道 CPU 之间的“远近”

guest 知道了有 4 颗 CPU 之后，还想知道它们之间的关系：哪些是同一个物理核上的超线程？哪些共享 L2 缓存、哪些共享 L3？在不在同一个 socket、同一个 NUMA 节点上？这些信息叫 **CPU 拓扑**，Linux 的调度器用它来构建**调度域（scheduling domain）**：同核的超线程之间迁移任务几乎没有代价，同 L3 的核之间代价小，跨 socket 的代价大。

guest 从哪里得知拓扑？主要是 **CPUID 指令**。与拓扑相关的 CPUID leaf 有好几个，而且 Intel 和 AMD 各有一套：

| Leaf | 厂商 | 内容 |
|---|---|---|
| `0x1` | 通用 | EBX[31:24] 本 CPU 的初始 APIC ID；EBX[23:16] 本 package 的逻辑处理器数；EDX 第 28 位 HTT 表示后者有效 |
| `0x4` | Intel | 每级缓存的参数与共享情况 |
| `0xB` / `0x1F` | Intel（AMD 新型号也支持） | 扩展拓扑枚举：按层级（SMT、Core、Die……）给出每层的 APIC ID 位宽 |
| `0x80000008` | AMD | ECX[7:0] 核数减一，ECX[15:12] APIC ID 中核编号所占的位数 |
| `0x8000001D` | AMD | 每级缓存的参数，EAX[25:14] 表示共享这级缓存的逻辑处理器数减一 |
| `0x8000001E` | AMD | EAX 扩展 APIC ID，EBX[7:0] 核 ID、EBX[15:8] 每核线程数减一，ECX[7:0] 节点 ID |

问题在于：VMM 给 guest 设置 CPUID 的常规做法是调用 `KVM_GET_SUPPORTED_CPUID` 拿到“host 支持、KVM 允许的全部 CPUID 信息”，然后用 `KVM_SET_CPUID2` 设给每个 vCPU。而 `KVM_GET_SUPPORTED_CPUID` 返回的拓扑字段是**host 的原始值**。比如 leaf 1 的 EBX[31:24]，是执行这个 ioctl 时所在的那颗**物理** CPU 的 APIC ID；leaf `0x80000008` 里的核数，是物理 CPU 的核数。

如果原样设给所有 vCPU，guest 会看到：4 颗 CPU 的初始 APIC ID 全都一样（比如都是 17），而每颗 CPU 都声称自己所在的 package 里有 32 个核。Linux 会被搞糊涂：日志里出现 APIC ID 不匹配的警告，拓扑被算错，调度域建得乱七八糟。

所以 **VMM 必须按 vCPU 改写拓扑相关的 CPUID 字段**，让每个 vCPU 报告的 APIC ID 等于它自己的 ID，并声称一个与虚拟机配置一致的拓扑。mini-vmm 的拓扑是最简单的“1 个 socket × N 个核 × 每核 1 个线程”。我们的 guest 是海光 CPU，Linux 对海光的拓扑解析走 AMD 风格的 `0x8000001E` 路径（`hygon_get_topology()`，要求 CPU 有 TOPOEXT 特性），所以改写的重点在 AMD 的那几个 leaf。实现篇会逐字段展开。

### 8.7 三方一致原则

现在可以把这条贯穿全章的原则完整地写出来了。在一台虚拟机里，“CPU n 的 APIC ID 是多少”这个问题，有三个信息来源：

```
                   ┌─────────────────────────────────┐
                   │  KVM 模拟的 LAPIC 的 ID 寄存器    │  由 KVM 设置：
                   │  （guest 读 0xFEE00020）          │  APIC ID = vcpu_id
                   └────────────────┬────────────────┘
                                    │  必须相等
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
  ┌─────┴──────────────┐   ┌────────┴─────────┐    ┌────────────┴────────────┐
  │ 固件表               │   │ CPUID            │    │ 其他：IOAPIC ID 不能与    │
  │ MADT 的 LAPIC 条目   │   │ leaf 1 EBX[31:24]│    │ 任何 LAPIC ID 冲突        │
  │ MP table 的处理器条目 │   │ leaf 0x8000001E  │    │                          │
  │ 由 VMM 生成          │   │ 由 VMM 改写       │    │                          │
  └────────────────────┘   └──────────────────┘    └──────────────────────────┘
```

KVM 在复位 LAPIC 时把 APIC ID 设成 vCPU 的 ID（`kvm_lapic_reset()` 里的 `kvm_apic_set_xapic_id(apic, vcpu->vcpu_id)`），这一方由 KVM 决定，VMM 能控制的是创建 vCPU 时传入的 ID。另外两方——固件表和 CPUID——完全由 VMM 生成，必须与第一方一致。

任何一方不一致都会出问题，但症状各不相同：

- **固件表与 LAPIC 不一致**：8.2.2 节讲过，Linux 6.6 并行启动时 AP 读 LAPIC ID 去查固件表建出的数组，查不到就永远停机，BSP 等待超时。
- **CPUID 与 LAPIC 不一致**：Linux 检测到后会打印警告，并以 LAPIC/固件表为准；拓扑信息算错，调度域不正确。
- **IOAPIC ID 与某个 LAPIC ID 冲突**：Linux 会重新分配 IOAPIC ID 或者打印警告。mini-vmm 用“IOAPIC ID = CPU 个数”来避开 0 到 N-1。

真实硬件上这三方由同一块芯片保证一致，所以操作系统不会为不一致的情况准备太多容错。在虚拟机里，这三方由 KVM 和 VMM 的不同代码分别生成，一致性完全靠 VMM 作者自己保证。

### 8.8 停下所有 vCPU：一个多线程程序的老问题

单核时，VMM 停机很简单：唯一的 vCPU 线程从 `KVM_RUN` 返回一个“关机”退出，循环结束。多核时出现了一个新问题：**任何一个 vCPU 触发了关机（比如 guest 执行 `poweroff` 时写 PM1a_CNT 的那颗 CPU），其他 vCPU 线程可能正睡在 `KVM_RUN` 里**（比如在 guest 的 HLT 里等中断）。怎么把它们叫出来？

一个阻塞在系统调用里的线程，能被外部打断的通用手段只有**信号**：给目标线程发一个信号，只要信号处理函数安装时没有带 `SA_RESTART` 标志，`KVM_RUN` 就会以 `-EINTR` 返回。

但只发信号有一个经典的竞态：目标线程刚检查完“是否该停止”的标志（结果为否），还没进入 `KVM_RUN`，此时信号到达，被信号处理函数“消费”掉了；然后线程进入 `KVM_RUN`，在 guest 的 HLT 里睡下去，再也没有信号来叫醒它。

KVM 为此专门提供了一个机制：`kvm_run` 共享页里的 **`immediate_exit`** 字段（`KVM_CAP_IMMEDIATE_EXIT`）。它为 1 时，`KVM_RUN` 在入口处直接返回 `-EINTR`，根本不进入 guest。正确的停机顺序是：**先把目标 vCPU 的 `immediate_exit` 置 1，再给它发信号**。已经在 `KVM_RUN` 里的线程被信号踢出来，还没进去的线程被 `immediate_exit` 挡在门外，两个窗口都被覆盖了。

还有一个副作用需要注意：`immediate_exit` 生效时，KVM **不会写 `kvm_run->exit_reason`**，里面还是上一次退出时的旧值。如果 VMM 在 `-EINTR` 之后仍然去读 `exit_reason` 并分发处理，就会把上一次的 I/O 再执行一遍。

### 8.9 小结

- x86 多核启动是接力：BSP 初始化后用 INIT-SIPI-SIPI 唤醒 AP，SIPI 向量乘以 `0x1000` 就是 AP 的实模式入口，必须位于 1MB 以下。
- Linux 在低端内存放 trampoline，带 AP 从实模式爬到长模式；6.6 并行启动时 AP 读 LAPIC ID 去查固件表建出的数组，确定自己的编号。
- vCPU 是 host 线程，guest 的并行就是线程的并行，内存一致性由硬件原生保证；锁持有者抢占、IPI 开销是虚拟化特有的代价。
- KVM 用 `mp_state` 模拟 AP 的等待状态，INIT/SIPI 全部在内核态 LAPIC 里完成，VMM 只需让每个 vCPU 线程进入 `KVM_RUN`；AP 醒来时 `KVM_RUN` 返回 `-EAGAIN`，要重进而不是报错。
- 没有内核态 irqchip 时所有 vCPU 都是 RUNNABLE，无法按真实协议启动 AP。
- `KVM_GET_SUPPORTED_CPUID` 给的拓扑是 host 的，VMM 必须按 vCPU 改写。
- 三方一致：KVM 的 LAPIC ID（= vcpu_id）、固件表里的 APIC ID、CPUID 里的 APIC ID 必须相同。
- 停下所有 vCPU 要用 `immediate_exit` + 信号，缺一不可；被打断时 `exit_reason` 是旧值，不能分发。
