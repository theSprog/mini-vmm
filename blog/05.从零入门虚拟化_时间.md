中断解决了“设备怎么通知 CPU”，但《中断·原理篇》2.1 节说过，最重要的中断是时钟中断。这一篇讲时间：OS 需要哪几种时间设施，它们在虚拟机里由谁实现，为什么一个“蜂鸣器端口”会决定 Linux 能不能启动，以及 KVM 的半虚拟化时钟 kvmclock 怎样让这条脆弱的校准链整个变得多余。

## 一、OS 需要的时间设施

### 1.1 两种“时间”

操作系统对时间的需求可以分成两类，对应两种不同的硬件：

**定时器（timer / clock event）**：“请在 N 毫秒之后打断我一次”，或者“请每隔 N 毫秒打断我一次”。它产生中断，是调度器抢占、`sleep()` 超时、网络重传定时器的基础。

**时钟源（clocksource）**：“现在是什么时刻”。它不产生中断，只是一个可以随时读取的、单调递增的计数器。`gettimeofday()`、调度器的运行时间统计、日志时间戳都靠它。

两者经常配合使用：定时器负责“按时叫醒”，时钟源负责“精确计量”。Linux 的时间子系统把它们抽象成 `clock_event_device` 和 `clocksource` 两个接口，启动时给每个候选打分（`rating`），从可用的硬件里挑分最高的。

### 1.2 x86 上的候选，以及在 mini-vmm 里由谁实现

| 设施 | 角色 | 频率从哪来 | mini-vmm 里由谁实现 |
|---|---|---|---|
| 8254 PIT | 定时器（启动早期）、校准参照 | 固定 1.193182 MHz | KVM 内核（`KVM_CREATE_PIT2`） |
| LAPIC 定时器 | 每 CPU 定时器 | 未知，需要校准 | KVM 内核（in-kernel LAPIC） |
| TSC | 时钟源 | 未知，需要校准或由别人告知 | 硬件直接执行，KVM 设置 offset |
| kvmclock | 时钟源，并告知 TSC 频率 | 由 KVM 写入共享内存 | KVM 内核，VMM 只负责让 guest 发现它 |
| ACPI PM timer | 时钟源、校准参照 | 固定 3.579545 MHz | 还没有（acpi-pm-timer 里程碑） |
| HPET | 定时器、时钟源、校准参照 | 寄存器里写明 | 还没有（hpet 里程碑） |
| CMOS RTC | 墙钟（年月日时分秒） | 1 Hz 更新 | VMM 用户态，只有读时间（cmos-rtc 里程碑补中断） |

这张表里最关键的一列是“频率从哪来”。TSC 和 LAPIC 定时器又快又好，但它们每秒走多少，操作系统一开始并不知道；PIT、PM timer、HPET 的频率是规范写死的，但读起来慢。所以启动早期有一个绕不开的步骤：**拿一个频率已知的慢设备，去量频率未知的快设备。** 第二章讲这条校准链，第五章讲 kvmclock 怎样绕过它。

## 二、PIT 与 TSC 校准

### 2.1 8254 PIT：最古老也最可靠的定时器

**PIT（Programmable Interval Timer，可编程间隔定时器）** 是 1981 年 IBM PC 上的 Intel 8253（后来是 8254）。它的输入时钟频率是一个非常奇怪的数：**1.193182 MHz**。这个数字来自原始 IBM PC 的 14.31818 MHz 晶振（NTSC 电视彩色副载波频率的 4 倍，这样可以复用电视机的晶振，降低成本）除以 12。四十多年后，Linux 源码里仍然定义着 `PIT_TICK_RATE 1193182`。

PIT 有三个独立的 16 位倒计数通道，端口是 `0x40`、`0x41`、`0x42`（三个通道的计数器），外加 `0x43`（模式/命令寄存器）：

| 通道 | 历史用途 | 今天在做什么 |
|---|---|---|
| 通道 0 | 系统时钟，输出接 IRQ0 | Linux 启动早期的时钟中断来源 |
| 通道 1 | 刷新 DRAM | 已经没用了 |
| 通道 2 | 驱动 PC 喇叭发声 | **被 Linux 用来测量 TSC 频率** |

每个通道有一个 GATE 输入（门控，高电平时计数器才计数）和一个 OUT 输出。通道 0 和 1 的 GATE 永远接高电平。通道 2 的 GATE 和 OUT 比较特殊：它们通过另一个端口 **`0x61`**（历史上叫“系统控制端口 B”，属于 8255 PPI 芯片）暴露给软件：

```
   端口 0x61 的位
   bit 0  （写）PIT 通道 2 的 GATE        1 = 允许计数
   bit 1  （写）喇叭数据使能               1 = 通道 2 的输出送到喇叭
   bit 4  （读）刷新时钟翻转位             大约每 15 微秒翻转一次
   bit 5  （读）PIT 通道 2 的 OUT 输出     计数到 0 时变化
```

软件往 bit 0 写 1、bit 1 写 0，就能让通道 2 “静音计数”；读 bit 5，就能知道计数器有没有数完。这个组合被 Linux 当成了一块高精度的秒表。

### 2.2 频率校准：为什么“蜂鸣器端口”决定能否启动

TSC（Time Stamp Counter）是一个每个时钟周期加一的 64 位计数器，用 `rdtsc` 指令读取，只要几十个周期，是 x86 上最好的时钟源。它的根本问题是频率未知：TSC 的频率等于 CPU 的某个标称频率，不同型号不同。有些 Intel CPU 能通过 CPUID leaf `0x15`/`0x16` 直接报告这个频率，AMD 和海光的 CPU 不提供这个信息。

裸机 Linux 的办法是**用一个已知频率的时钟去测量 TSC**：让 PIT 通道 2 从 `0xFFFF` 开始倒数，同时读 TSC；PIT 以 1.193182 MHz 的已知频率计数，数了多少个 PIT 周期、TSC 同时走了多少，一除就得到 TSC 的频率。不知道自己在虚拟机里的 guest 内核，启动日志开头会有这两行：

```
[    0.000000] tsc: Fast TSC calibration using PIT
[    0.000000] tsc: Detected 3000.118 MHz processor
```

`quick_pit_calibrate()` 函数的第一件事就是操作端口 `0x61`：

```c
    /* Set the Gate high, disable speaker */
    outb((inb(0x61) & ~0x02) | 0x01, 0x61);

    /* Counter 2, mode 0 (one-shot), binary count */
    outb(0xb0, 0x43);

    /* Start at 0xffff */
    outb(0xff, 0x42);
    outb(0xff, 0x42);
```

快速校准失败时，`native_calibrate_tsc()` 退到 `pit_calibrate_tsc()` 的慢路径；PIT 也给不出可信结果时，再找 HPET 或 ACPI PM timer 当参照（`tsc.c` 里打印 `using HPET/PMTIMER reference calibration` 的那个分支）。三者都没有，TSC 频率就是 0，内核把 TSC 标为不稳定。5.4 节有这条路走到底的实测。

TSC 频率一旦测错或者测不出来，后面的一切都会乱：`udelay()` 的循环次数、LAPIC 定时器的校准（第三章）、时间戳、调度器时钟。轻则时间跑得快慢不对，重则某个等待循环永远等不到预期的时间，内核卡死。

**这就是“蜂鸣器端口决定能否启动”的因果链**：端口 `0x61` 的 GATE 位 → PIT 通道 2 能否计数 → TSC 频率能否测准 → 所有依赖时间的代码能否正常工作。

### 2.3 `KVM_PIT_SPEAKER_DUMMY`：名字最误导人的一个 flag

在虚拟机里，PIT 本身由 KVM 在内核里模拟（`KVM_CREATE_PIT2`），端口 `0x40`–`0x43` 由 KVM 处理。但端口 `0x61` 是另一块芯片（8255 PPI）的一部分，它**默认不归 KVM 管**，guest 对 `0x61` 的访问会以 `KVM_EXIT_IO` 回到用户态。如果用户态 VMM 不处理它，GATE 位就永远写不进 KVM 模拟的 PIT，通道 2 的 GATE 保持复位值 0（KVM 在 `kvm_pit_reset()` 里把通道 2 的 gate 初始化为 0），计数器根本不动。

KVM 为此提供了一个 flag。读 host 的 `kvm_create_pit()`（`arch/x86/kvm/i8254.c`）：

```c
    if (flags & KVM_PIT_SPEAKER_DUMMY) {
        kvm_iodevice_init(&pit->speaker_dev, &speaker_dev_ops);
        ret = kvm_io_bus_register_dev(kvm, KVM_PIO_BUS,
                                      KVM_SPEAKER_BASE_ADDRESS, 4,
                                      &pit->speaker_dev);
        ...
    }
```

只有带了这个 flag，KVM 才会在内核的 PIO 总线上为端口 `0x61` 注册处理函数，写的时候把 GATE 位转发给通道 2，读的时候返回真实的 OUT 位和刷新翻转位（`speaker_ioport_read()`）：

```c
    /* Refresh clock toggles at about 15us. We approximate as 2^14ns. */
    refresh_clock = ((unsigned int)ktime_to_ns(ktime_get()) >> 14) & 1;
    ...
    ret = ((pit_state->speaker_data_on << 1) | pit_get_gate(pit, 2) |
           (pit_get_out(pit, 2) << 5) | (refresh_clock << 4));
```

“SPEAKER_DUMMY”听起来像是“一个假的喇叭，可有可无”，实际意思是“没有真的喇叭，但端口的行为是真的”。mini-vmm 在 `irqchip_create()`（`src/devices/irqchip.c`）里创建 PIT 时带上它：`pit.flags = KVM_PIT_SPEAKER_DUMMY;`。QEMU、Firecracker、kvmtool 也都带了这个 flag。

不带它会怎样，可以按证据链复盘一遍，因为这类“名字看起来无关紧要”的 flag 在 KVM 里并不少见：

- **症状**：guest 启动**间歇性**卡住，日志停在 `skipped IO-APIC setup` 之后，时间戳停在 `0.001000` 不再前进，VMM 的 CPU 占用是 100%。有时候又能正常启动。
- **证据**：打开 VMM 的未处理端口调试日志，能看到对端口 `0x61` 的读写落到了用户态，VMM 按浮空总线约定处理：写丢弃、读返回 `0xFF`。
- **分析**：`quick_pit_calibrate()` 写 `0x61` 被丢弃，通道 2 的 GATE 一直是 0，计数器不走，快速校准失败。退到 `pit_calibrate_tsc()` 后，它读 `0x61` 的第 5 位判断计数是否结束，而 `0xFF` 让 OUT 永远是 1。校准得到的是一个没有意义的值，后续依赖时间的等待循环于是表现得时好时坏。
- **根因**：上面那段 `kvm_create_pit()`，没有 flag 就没有人处理 `0x61`。

教训是：**用 KVM 的内核态设备时，要把每个 flag 的实现读一遍，不能只看名字。**

### 2.4 PIT 在 KVM 里的实现与“补发”

KVM 用一个 host 上的高精度定时器（hrtimer）来模拟 PIT 通道 0：guest 把通道 0 编程为每隔 N 个 PIT 周期产生一次中断，KVM 就启动一个周期为 `N / 1193182` 秒的 hrtimer，每次到期时通过《中断·原理篇》4.6 节讲的路由表拉一下 GSI 0。

这里有一个虚拟化特有的问题：**guest 不一定总在运行**。vCPU 只是 host 上的一个线程，它可能被 host 调度器换下去几毫秒。在这期间 hrtimer 照样到期，但 guest 没有机会处理中断。等 vCPU 重新运行时，可能已经“欠”了好几个时钟中断。

有些操作系统（老版本的 Windows、老的 Linux）靠数时钟中断的次数来计时，丢一个中断时间就慢一个 tick。所以 KVM 的 PIT 默认工作在**补发（reinject）模式**：它记录欠了多少个中断，并注册一个 **ack notifier**，guest 每对上一次 PIT 中断写一次 EOI，KVM 就补发一个欠下的中断，直到还清为止。这是《中断·原理篇》2.6 节说的“EOI 作为被别人观察的信号”的具体用例。

现代 Linux 不靠数 tick 计时（它用 TSC 这样的时钟源），补发反而可能造成短时间内时钟中断扎堆。但 Linux 在启动早期很快就会切换到 LAPIC 定时器，PIT 只是过渡，所以这个问题在实践中影响不大。

## 三、LAPIC 定时器：每颗 CPU 自己的闹钟

PIT 只有一个，而多核系统需要每颗 CPU 都能独立地设置定时器。所以 Linux 在启动后期会把时钟事件切换到 **LAPIC 定时器**：每个 LAPIC 里都有一个 32 位倒计数器，通过 LVT Timer 寄存器（偏移 `0x320`）配置向量号和模式（单次、周期、TSC deadline）。

LAPIC 定时器的频率同样是未知的（真实硬件上它通常等于总线频率），所以也要校准。guest v6.6 的 `calibrate_APIC_clock()` 让 LAPIC 计数器从最大值往下数，等 100 个 tick（`LAPIC_CAL_LOOPS`，HZ=1000 时是 100 ms）后看它走了多少。“一个 tick 过去了”有两种判断方法，代码里写得很直接：

```c
	/*
	 * Methods to terminate the calibration loop:
	 *  1) Global clockevent if available (jiffies)
	 *  2) TSC if available and frequency is known
	 */
```

TSC 频率已知时用 TSC 计时，否则数 jiffies，也就是数 PIT 的 IRQ0。校准完还有一道验证：用刚校准的 LAPIC 定时器当时钟事件跑 100 个 tick，看 jiffies 是否落在 98–102 之间，落不进去就打印 `APIC timer disabled due to verification failure`，放弃 LAPIC 定时器，继续用 PIT 当全局时钟事件。所以 LAPIC 定时器能不能用，又绑回了第二章：TSC 频率测准了，LAPIC 跟着准。

在 KVM 里，LAPIC 定时器同样用 hrtimer 模拟：guest 写初始计数寄存器时，KVM 根据分频设置算出到期时间，启动一个 hrtimer；到期时在对应 vCPU 的虚拟 LAPIC 里挂起 LVT Timer 指定的向量，然后走《中断·原理篇》4.4 节的 kick 流程。KVM 模拟的 LAPIC 总线频率是固定的 1 GHz（host `arch/x86/kvm/lapic.h` 的 `APIC_BUS_CYCLE_NS 1`），guest 用 `apic=verbose` 启动就能看到校准结果和它对上：

```
[    0.473447] ... lapic delta = 6250291
[    0.474432] ..... host bus clock speed is 1000.0046 MHz.
[    0.589750] ... jiffies delta = 100
[    0.590432] ... jiffies result ok
```

`lapic delta` 是 100 ms 里 LAPIC 计数器走的数，Linux 默认的分频是 16，所以总线频率 = 6250291 × 16 / 0.1 s ≈ 1000 MHz。

在 TSC deadline 模式下，guest 写的是 MSR `IA32_TSC_DEADLINE`（`0x6E0`），KVM 同样把它转换成 hrtimer；CPUID 报告了 TSC deadline 时 `calibrate_APIC_clock()` 第一行就返回，根本不用校准。Intel 平台上 KVM 还可以用硬件的 VMX preemption timer 来实现 TSC deadline，省掉 hrtimer 的开销；AMD 上没有对应的硬件，只能用 hrtimer。

## 四、TSC 的虚拟化

TSC 是本篇里唯一一个**不需要陷出**就能工作的时间设施。`rdtsc` 指令默认不被拦截，guest 执行它时直接读物理 CPU 的 TSC。但直接读有两个问题需要硬件帮忙：

**问题一：偏移。** 物理 TSC 从 host 开机就开始计数，可能已经是一个很大的值。guest 期望的是“从我开机开始计数”。SVM 在 VMCB 控制区里提供了一个 **TSC_OFFSET** 字段：guest 读到的 TSC = 物理 TSC + TSC_OFFSET。KVM 为每个 vCPU 设置这个偏移，让 guest 的 TSC 从接近 0 开始。

**问题二：频率。** 热迁移时，虚拟机可能从一台 3.0 GHz 的机器迁到一台 2.5 GHz 的机器，guest 已经校准好的 TSC 频率就不对了。SVM 提供了 **TSC ratio**（host 特性列表里的 `tsc_scale`）：guest 读到的 TSC = 物理 TSC × ratio + offset，KVM 可以让 guest 看到的 TSC 频率保持不变。

**多核的额外问题：同步。** 在多核 guest 里，Linux 要求所有 CPU 的 TSC 是同步的，否则一个线程从 CPU 0 迁到 CPU 1 上读时间，可能读到一个比刚才更早的值，时间倒流了。真实硬件上，现代 CPU 的 TSC 在所有核之间是同步的，而且不随变频和深度睡眠改变速率（`/proc/cpuinfo` 里的 `constant_tsc`、`nonstop_tsc` 标志，后者对应 CPUID `0x80000007` EDX 的 invariant TSC 位）。虚拟机里，每个 vCPU 的 TSC_OFFSET 是在不同时刻设置的，如果不加处理，各 vCPU 的 TSC 就会有细微差别。KVM 在 `kvm_synchronize_tsc()` 里做了专门处理：如果多个 vCPU 在很短时间内被写入了“相同”的 TSC 值，KVM 就认为 VMM 的意图是让它们同步，给它们设置完全相同的偏移。Linux guest 在启动每个 AP 时也会检查 TSC 同步（`check_tsc_sync_source()`），发现不同步会打印 `TSC synchronization` 相关的警告并放弃使用 TSC。mini-vmm 的 smp 测试专门断言了日志中没有这类警告。

## 五、kvmclock：KVM 已经替我们做好的半虚拟化时钟

### 5.1 思路：别让 guest 去量，直接告诉它

第二章的校准链之所以脆弱，是因为 guest 在用模拟出来的慢设备去量真实的快设备，而模拟设备的时序受 host 调度影响。hypervisor 其实知道答案：它知道物理 TSC 的频率，也知道给 guest 设了多少 offset 和 ratio。**kvmclock** 就是把这些信息直接交给 guest 的半虚拟化时钟。

guest 往 MSR `MSR_KVM_SYSTEM_TIME_NEW`（`0x4b564d01`）写入一块 guest 内存的 GPA，KVM 就在这块内存里维护一个 32 字节的结构（`arch/x86/include/asm/pvclock-abi.h`）：

```c
struct pvclock_vcpu_time_info {
	u32   version;            /* 奇数表示 KVM 正在更新，偶数表示内容一致 */
	u32   pad0;
	u64   tsc_timestamp;      /* 某一时刻的 guest TSC */
	u64   system_time;        /* 同一时刻的 guest 纳秒时间 */
	u32   tsc_to_system_mul;  /* TSC 差值换算成纳秒的乘数 */
	s8    tsc_shift;
	u8    flags;              /* PVCLOCK_TSC_STABLE_BIT 等 */
	u8    pad[2];
} __attribute__((__packed__)); /* 32 bytes */
```

guest 读时间时，先读 TSC，再按 `__pvclock_read_cycles()` 换算：

```
delta = rdtsc() - tsc_timestamp
delta 按 tsc_shift 左移（负数则右移）
now   = system_time + (delta × tsc_to_system_mul) >> 32
```

前后各读一次 `version`，两次相同且为偶数才算读到了一致的快照，这是一个 seqlock。`MSR_KVM_WALL_CLOCK_NEW`（`0x4b564d00`）同理，给出 guest 启动时刻对应的墙钟。

这样 guest 拿到了三样东西：TSC 频率（由乘数和移位反推，`pvclock_tsc_khz()`）、一个随时可读的纳秒时钟、一个墙钟。第二章那条从端口 `0x61` 开始的校准链整个不需要了。

### 5.2 guest 怎么发现它：VMM 只负责一个 CPUID 位

kvmclock 在 KVM 内核里实现，VMM 不需要写一行时钟代码，只需要让 guest 知道自己运行在 KVM 上。发现过程分三步：

1. guest 看 CPUID.1:ECX[31]（hypervisor 位）。物理 CPU 上这一位恒为 0，`KVM_GET_SUPPORTED_CPUID` 也不报告它，**要 VMM 自己置上**。mini-vmm 在 `cpuid_mark_hypervisor()`（`src/arch/amd/svm.c`）里做这件事，那里的注释列出了这一位对 guest 的其他影响。
2. 置了这一位，开了 `CONFIG_KVM_GUEST` 的内核才会去读 CPUID `0x40000000`（`KVM_CPUID_SIGNATURE`），看到签名 `KVMKVMKVM` 就打印 `Hypervisor detected: KVM`。
3. 再读 `0x40000001`（`KVM_CPUID_FEATURES`），`KVM_FEATURE_CLOCKSOURCE2`（bit 3）表示支持新版 MSR，`KVM_FEATURE_CLOCKSOURCE_STABLE_BIT`（bit 24）表示 `PVCLOCK_TSC_STABLE_BIT` 可信。

第 2、3 步的两片 CPUID 叶子由 `KVM_GET_SUPPORTED_CPUID` 给出，mini-vmm 把它们原样透传给 guest。所以 VMM 侧的全部工作就是第 1 步那一个位。

### 5.3 实测：一次带 kvmclock 的启动

mini-vmm 的 e2e 测试用的 guest 内核（`tools/build_guest_kernel.sh` 构建）开了 `CONFIG_KVM_GUEST`。用 `--smp 2 --mem 512M` 启动，和时间有关的日志是这样的：

```
[    0.000000] [Firmware Bug]: TSC doesn't count with P0 frequency!
[    0.000000] Hypervisor detected: KVM
[    0.000000] kvm-clock: Using msrs 4b564d01 and 4b564d00
[    0.000001] kvm-clock: using sched offset of 458669773 cycles
[    0.001032] clocksource: kvm-clock: mask: 0xffffffffffffffff max_cycles: 0x1cd42e4dffb, max_idle_ns: 881590591483 ns
[    0.004312] tsc: Detected 3193.916 MHz processor
[    0.137643] clocksource: tsc-early: mask: 0xffffffffffffffff max_cycles: 0x2e09d6abbf7, max_idle_ns: 440795264984 ns
[    0.140424] Calibrating delay loop (skipped) preset value.. 6387.83 BogoMIPS (lpj=3193916)
[    0.539499] clocksource: Switched to clocksource kvm-clock
[    0.618787] clocksource: tsc: mask: 0xffffffffffffffff max_cycles: 0x2e09d6abbf7, max_idle_ns: 440795264984 ns
[    0.622367] clocksource: Switched to clocksource tsc
```

逐行对照 guest v6.6 的源码：

- `tsc: Detected` 前面**没有** `Fast TSC calibration using PIT`。`kvmclock_init()` 把 `x86_platform.calibrate_tsc` 换成了 `kvm_get_tsc_khz()`，频率直接从 pvclock 结构换算，PIT 一次都没被用来量 TSC。`kvm_get_tsc_khz()` 顺手置上 `X86_FEATURE_TSC_KNOWN_FREQ`，guest 的 `/proc/cpuinfo` 因此出现 `tsc_known_freq` 标志。
- `Calibrating delay loop (skipped) preset value`：`kvm_get_preset_lpj()` 用同一个频率算好了 `loops_per_jiffy`，BogoMIPS 正好是频率的两倍。
- **先切到 kvm-clock，又切到 tsc。** kvm-clock 的默认分数是 400，比 tsc 的 300 高。但 `kvmclock_init()` 末尾有一段判断：

  ```c
	if (boot_cpu_has(X86_FEATURE_CONSTANT_TSC) &&
	    boot_cpu_has(X86_FEATURE_NONSTOP_TSC) &&
	    !check_tsc_unstable())
		kvm_clock.rating = 299;
  ```

  mini-vmm 透传了 host 的 CPUID，guest 看到了 `constant_tsc` 和 `nonstop_tsc`，于是 kvm-clock 降到 299。`clocksource_done_booting()` 第一次挑选时，tsc-early 和 kvm-clock 都是 299，分数相同时排在链表前面、也就是先注册的 kvm-clock 胜出（`clocksource_enqueue()` 把新来的插在所有同分者之后）。随后 `init_tsc_clocksource()` 因为频率已知，直接以 300 分注册正式的 `tsc`，取而代之。

所以在 mini-vmm 里，kvmclock 的主要作用是**把 TSC 频率告诉 guest**，最终的时钟源是 TSC 本身。如果 guest 看不到 invariant TSC，kvm-clock 会保持 400 分，一直是时钟源。

`available_clocksource` 印证了这一点：

```
[guest ~]# cat /sys/devices/system/clocksource/clocksource0/available_clocksource
tsc kvm-clock
[guest ~]# cat /sys/devices/system/clocksource/clocksource0/current_clocksource
tsc
```

列表里没有 hpet 和 acpi_pm，因为 mini-vmm 还没有提供这两个设备。

### 5.4 对照：关掉 kvmclock 会怎样

内核参数 `no-kvmclock` 让 guest 不使用 kvmclock，回到第二章的校准链。用 `--append no-kvmclock` 在 WSL2 的嵌套 KVM 上启动，连续三次结果一致：

```
[    0.007000] tsc: Unable to calibrate against PIT
[    0.011000] tsc: No reference (HPET/PMTIMER) available
[    0.013000] tsc: Marking TSC unstable due to could not calculate TSC khz
[    0.014000] Calibrating delay loop... 33.02 BogoMIPS (lpj=16512)
[    0.439000] clocksource: Switched to clocksource refined-jiffies
```

这几行把 2.2 节描述的退路完整走了一遍：快路径和慢路径的 PIT 校准都失败（嵌套虚拟化下读一次 PIT 要经过两层 hypervisor，时序抖动超出了校准算法的容忍范围），没有 HPET 和 PM timer 当后备参照，TSC 频率为 0，TSC 被标为不稳定。`available_clocksource` 里只剩 `refined-jiffies jiffies`，时间戳精度退到毫秒级，BogoMIPS 从 6387 掉到 33，`udelay()` 等待的时间远短于要求的时长。

LAPIC 定时器也受牵连。TSC 频率未知，第三章的校准只能数 PIT 的 jiffies。加上 `apic=verbose` 跑了四次，两次验证通过，两次失败：

```
..... host bus clock speed is 976.0863 MHz.
... jiffies delta = 97
APIC timer disabled due to verification failure
```

另一次失败是 `jiffies delta = 124`。校准量出的总线频率在 976 到 1001 MHz 之间摆动，验证落不进 98–102 的窗口，guest 就放弃 LAPIC 定时器，一直用 PIT 当时钟事件。这就是 2.3 节说的“时好时坏”在另一个环节的样子。

在海光物理机上的 KVM 里（只有一层虚拟化），不用 kvmclock 的内核走 `quick_pit_calibrate()` 能成功，打印的就是 2.2 节开头那两行，《对照日志把Linux跑起来》一篇逐段解读的就是这样一次启动。`tests/lib.sh` 的 `expect_tsc_calibrated` 因此同时接受这几种结局：有 kvmclock 时只要求 `tsc: Detected`，没有时接受 PIT 校准的三种结果。

这组对照也说明了路线图里 acpi-pm-timer 和 hpet 两个里程碑的价值：它们正是 `No reference (HPET/PMTIMER) available` 这一行缺的那个后备参照。

### 5.5 日志里那句 Firmware Bug

5.3 节日志开头那句警告看起来很吓人：

```
[    0.000000] [Firmware Bug]: TSC doesn't count with P0 frequency!
```

这是 AMD/海光平台特有的检查：内核读 MSR `HWCR`（`0xC0010015`）的第 24 位，确认 TSC 以最高性能状态 P0 的频率计数。KVM 模拟的 `HWCR` 没有置这一位，用户态也改不了（KVM 的 `HWCR` 写处理只接受 bit 18，理由见 `src/arch/amd/svm.c` 里 `cpuid_mark_hypervisor()` 上方的注释）。它不影响任何功能：有 kvmclock 时 TSC 频率由 KVM 告知，没有时靠实测，都不依赖这一位。

### 5.6 VMM 还能对 kvmclock 做什么

kvmclock 本身由 KVM 维护，VMM 能控制的是它在 VM 生命周期里的连续性：`KVM_GET_CLOCK` / `KVM_SET_CLOCK` 读写 VM 级的 kvmclock 值，用于暂停、快照和迁移时让 guest 时间不倒退、不乱跳。这部分和“guest 模块直接读 pvclock 结构”“各时钟源读取成本对比”一起放在 `MILESTONES.md` 的 kvmclock 里程碑，它依赖 TSC、PM timer、HPET 和 PV 特性几个里程碑先完成，因为它的验收要在这些时钟源之间做对照。
