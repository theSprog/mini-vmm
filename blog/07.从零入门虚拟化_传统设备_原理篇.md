## 一、设备虚拟化：本文涉及的那一部分

### 1.1 三条路线

“让 guest 用上设备”这件事，业界有三条成熟的路线：

| 路线 | 做法 | guest 需要知道自己被虚拟化吗 | 性能 | 代表 |
|---|---|---|---|---|
| **全模拟**（Full Emulation） | 用软件精确模仿一块真实存在的硬件芯片的寄存器行为 | 不需要，guest 用该芯片的原生驱动 | 差：每次寄存器访问都陷出 | QEMU 的 e1000 网卡、IDE 硬盘、本文的全部设备 |
| **半虚拟化**（Paravirtualization） | 设计一种“为虚拟化而生”的虚拟设备，接口专门优化，减少陷出 | 需要，guest 要装专门的驱动 | 好：批量传输，陷出很少 | VirtIO（后续篇目的主角） |
| **直通**（Passthrough） | 把一块真实物理设备直接交给 guest，guest 的驱动直接操作硬件 | 不需要 | 接近裸机 | VFIO、SR-IOV |

本文只涉及第一条路线，而且只涉及其中最“古老”的一批设备：串口、RTC、键盘控制器、电源管理寄存器。选择它们不是因为它们重要（对一台现代服务器来说，它们几乎都没用），而是因为**Linux 启动时一定会碰它们**，不处理好就启动不起来或者启动很慢。

### 1.2 设备模拟的本质：一台寄存器状态机

从 guest 的角度看，一个设备就是一组寄存器：往某个地址写一个值，设备会“做点什么”；从某个地址读，会得到反映设备当前状态的值；设备有事情时，会拉一根中断线。

所以用软件模拟一个设备，本质上是写一个**状态机**：

```
                      ┌────────────────────────────────┐
   guest 写寄存器 ────►│                                │────► 副作用（输出一个字节、
   (KVM_EXIT_IO/MMIO) │     设备内部状态                │       开始一次传输……）
                      │  （寄存器值、FIFO、模式位……）     │
   guest 读寄存器 ◄────│                                │────► 中断线电平
                      │                                │       （KVM_IRQ_LINE）
   外部事件   ────────►│                                │
   （host 输入等）     └────────────────────────────────┘
```

状态机的三个输入是 guest 写寄存器、guest 读寄存器（注意：**读也可能改变状态**，比如读串口的数据寄存器会把 FIFO 里的字节取走）、外部事件；三个输出是读的返回值、副作用、中断线电平。

写设备模拟时，最容易犯的错误是按芯片手册“完整地”实现所有功能。一块 16550 UART 的手册有几十页，包括波特率发生器、奇偶校验、断线检测、modem 控制线……在虚拟机里，这些大部分毫无意义（没有真实的线缆，波特率设多少都一样）。

真正有用的问题是：

> **guest 的驱动实际会读写哪些寄存器？它期望读到什么值？读不到期望的值时它会怎么做？**

驱动的探测逻辑，才是设备模拟的真正规格说明书。一个设备只需要模拟到“驱动认为它工作正常”的程度。多一分是浪费，少一分是 bug。这是本文最核心的方法论，下面每一个设备都会用这个视角去看。

### 1.3 端口分发与“浮空总线”约定

回忆《一次 out 指令的完整旅程》：guest 执行 `in`/`out` 时，如果端口不归 KVM 内部的设备（PIC、PIT、以及带 `SPEAKER_DUMMY` 时的 `0x61`）管，就会以 `KVM_EXIT_IO` 回到用户态，`kvm_run->io` 里给出端口号、方向、宽度、次数。VMM 要做的第一件事是**分发**：根据端口号找到对应的设备模拟代码。

一个 VMM 通常会维护一张“地址区间 → 设备”的表，PIO 和 MMIO 各一张。MMIO 的分发逻辑完全相同，只是退出原因换成 `KVM_EXIT_MMIO`、地址换成物理地址。

那**没有任何设备认领的端口**呢？Linux 启动时会盲目地探测一大堆传统端口：第二个串口 `0x2f8`、并口 `0x378`、软驱控制器、游戏杆……如果 VMM 对未知端口报错退出，Linux 根本启动不起来。

正确的做法是模仿真实硬件的行为：在真实的 ISA 总线上，读一个没有设备响应的端口，数据线处于“浮空”状态，由上拉电阻拉成全 1，读回 `0xFF`；写一个没有设备的端口，数据就丢了。所以 VMM 对未知端口的约定是：**读返回全 1，写直接丢弃。** Linux 的很多探测代码正是依赖这个约定来判断“这里没有设备”的，比如串口驱动写一个值再读回来，读到 `0xFF` 就知道这里没有 UART。

### 1.4 16550A 串口：guest 的主要输出通道

串口是本文最重要的设备，因为它是 guest 唯一的“显示器”和“键盘”：内核日志通过它输出，shell 通过它交互。

#### 1.4.1 寄存器布局

16550A 占 8 个连续端口（COM1 是 `0x3f8`–`0x3ff`），但寄存器不止 8 个，有几个端口“一址多用”：

| 偏移 | 读 | 写 | DLAB=1 时 |
|---|---|---|---|
| 0 | RBR：接收到的字节 | THR：要发送的字节 | DLL：波特率除数低字节 |
| 1 | IER：中断使能 | IER | DLM：波特率除数高字节 |
| 2 | IIR：中断标识 | FCR：FIFO 控制 | |
| 3 | LCR：线路控制（第 7 位是 DLAB） | LCR | |
| 4 | MCR：modem 控制 | MCR | |
| 5 | LSR：线路状态 | — | |
| 6 | MSR：modem 状态 | — | |
| 7 | SCR：暂存寄存器 | SCR | |

**DLAB（Divisor Latch Access Bit）** 是 LCR 的第 7 位。它为 1 时，偏移 0 和 1 变成波特率除数寄存器。驱动设置波特率的流程是：置 DLAB → 写除数 → 清 DLAB。模拟时必须根据 DLAB 区分这两组寄存器，否则驱动设置波特率时写的除数会被当成要发送的字符打印出来——一个串口没模拟好时常见的症状，就是开头输出一个奇怪的乱码字符。

#### 1.4.2 输出：LSR 与 THRE 中断

发送一个字节的最简流程：驱动读 LSR，等第 5 位 **THRE（Transmitter Holding Register Empty，发送保持寄存器空）** 为 1，然后把字节写进 THR。

在虚拟机里，“发送”就是把字节写到 host 的标准输出，瞬间完成。所以 LSR 可以永远报告 THRE=1、TEMT=1（发送器完全空闲），驱动永远不需要等待。

但 Linux 的串口驱动在正常工作时并不轮询 LSR，而是用**中断驱动发送**：它打开 IER 的 THRI 位（“发送保持寄存器空时给我中断”），然后在中断处理程序里一次往 THR 塞一批字节。这里有一个关键的语义：**打开 THRI 的那一刻，如果 THR 已经是空的，16550 会立即产生一次中断。** Linux 的 `serial8250_start_tx()` 就是靠这个“一打开就来中断”的行为来启动发送的。如果模拟时漏掉了这个语义，驱动会一直等一个永远不来的中断，表现为 printk 在控制台注册后输出突然停止。

THRE 中断的清除也有讲究：驱动读 IIR 读到“THRE 中断”时，这个中断就被视为已应答；或者驱动再往 THR 写数据，也会清除它。

#### 1.4.3 输入：FIFO、RDA 中断与边沿触发

host 终端上敲的字符，由 VMM 的一个输入线程放进串口的接收 FIFO，同时置位 LSR 的 DR（Data Ready）位。如果 IER 打开了 RDI（接收数据中断），就拉高中断线。guest 驱动在中断处理程序里循环读 LSR 和 RBR，直到 DR 为 0。

IRQ4 是 ISA 中断，**边沿触发**。所以串口模拟每次需要产生新中断时，都必须保证中断线经历一次“低 → 高”的跳变。一种可靠的做法是：每次寄存器访问后都重新计算“当前是否有待处理的中断”，把结果和上一次的线电平比较，只在变化时调用 `KVM_IRQ_LINE`。驱动读空 FIFO 时条件变假、线被拉低；新字节到来时条件变真、线被拉高，这就形成了一个新的上升沿。

#### 1.4.4 IIR 与中断优先级

16550 同时可能有多个中断条件（有数据可读、发送保持寄存器空、线路状态错误、modem 状态变化），但 IIR 一次只报告优先级最高的一个。优先级从高到低是：线路状态 > 接收数据 > 发送保持寄存器空 > modem 状态。IIR 的低 4 位编码中断类型（`0x01` 表示无中断，`0x04` 表示接收数据，`0x02` 表示 THRE），高 2 位在 FIFO 启用时为 `11`。

#### 1.4.5 探测：Linux 怎么认出“这是一块 16550A”

Linux 的 8250 驱动在注册端口前会运行一个叫 `autoconfig()` 的探测函数。它是“驱动定义了模拟规格”的最好例子，以下三步都会碰到：

1. **IER 读写测试**：往 IER 写 0，读回来应该是 0；写 `0x0F`，读回来低 4 位应该是 `0x0F`。读不对，驱动认为这个地址上没有 UART。
2. **回环测试**：把 MCR 设成“回环模式 + OUT2 + RTS”，然后读 MSR。在回环模式下，16550 内部把 MCR 的输出线直接接到 MSR 的输入线上：RTS 接 CTS、DTR 接 DSR、OUT1 接 RI、OUT2 接 DCD。所以驱动期望读到 MSR 的高 4 位恰好是 DCD 和 CTS（`0x90`）。读不对，驱动同样判定没有 UART。
3. **FIFO 测试**：往 FCR 写“启用 FIFO”，然后读 IIR 的高 2 位：`00` 表示老式的 8250/16450，`10` 表示有缺陷的 16550，`11` 表示 16550A。

只有三步都通过，日志里才会出现这一行：

```
[    0.590811] serial8250: ttyS0 at I/O 0x3f8 (irq = 4, base_baud = 115200) is a 16550A
```

回环模式还有一个副作用需要模拟：回环时写入 THR 的字节不应该出现在 host 的输出上，而是回到自己的接收 FIFO 里，并且此时中断线不往外送。

#### 1.4.6 OUT2：PC 上的中断门控

最后一个 PC 特有的细节：在 IBM PC 的主板设计中，串口芯片的中断输出线**经过 MCR 的 OUT2 位控制的一个三态门**才连到中断控制器。OUT2 为 0 时，无论 UART 内部有没有中断，中断线都不会到达 8259A/IOAPIC。Linux 在打开串口时会置位 OUT2。模拟时要照这个规矩来：OUT2 为 0 时不拉线。这个细节会影响驱动的 IRQ 自动探测逻辑。

### 1.5 CMOS RTC：用 host 的时间回答“现在几点”

**RTC（Real-Time Clock，实时时钟）** 是一块由主板纽扣电池供电的时钟芯片（原型是 Motorola MC146818），关机后也在走，Linux 启动时从它读取当前日期时间来初始化系统时间。它还附带 64 或 128 字节的 **CMOS RAM**，BIOS 用来保存设置。

RTC 通过一对端口访问：往 `0x70` 写寄存器编号（第 7 位是历史遗留的“NMI 屏蔽”位，与寄存器选择无关），再从 `0x71` 读写数据。重要的寄存器：

| 编号 | 内容 |
|---|---|
| `0x00` / `0x02` / `0x04` | 秒 / 分 / 时 |
| `0x06` / `0x07` / `0x08` / `0x09` | 星期 / 日 / 月 / 年（两位） |
| `0x0A` | 寄存器 A，第 7 位是 **UIP（Update In Progress）** |
| `0x0B` | 寄存器 B，控制 24 小时制、BCD/二进制编码、中断使能 |
| `0x0C` | 寄存器 C，中断标志，读后清零 |
| `0x0D` | 寄存器 D，第 7 位是 VRT（电池有效） |
| `0x32` | 世纪（事实标准，由 ACPI FADT 的 `century` 字段声明） |

RTC 芯片每秒要更新一次时间寄存器，更新期间（大约 2 毫秒）读出来的值可能不一致。所以协议规定：**读时间之前，要等寄存器 A 的 UIP 位为 0**。Linux 的 `mc146818_get_time()` 就是这样做的：循环读寄存器 A，等 UIP 清零。

如果 VMM 不模拟 RTC，端口 `0x71` 按浮空总线约定读回 `0xFF`，UIP 位永远是 1，Linux 就会一直等下去——每次读寄存器 A 都是一次 `KVM_EXIT_IO`。当然 Linux 不会真的死等，它有超时，但在超时之前已经产生了大量陷出。mini-vmm 实测：不模拟 RTC 时启动过程多出约 4 万次 exit、多花约 1.4 秒，最后打印 `Unable to read current time from RTC` 放弃。

模拟 RTC 很简单：寄存器 A 返回一个 UIP=0 的固定值，寄存器 B 声明“24 小时制、BCD 编码”，读时间寄存器时现取 host 的时间转换成 BCD 返回。真实日志里的这一行说明模拟成功了：

```
[    0.617835] rtc_cmos rtc_cmos: setting system clock to 2026-09-11T06:48:34 UTC (1789109314)
```

**BCD（Binary-Coded Decimal）** 编码的意思是用 4 位表示一个十进制数字：45 秒存成 `0x45` 而不是 `0x2D`。这是 1980 年代为了让数字直接在七段数码管上显示而做的设计。忘记 BCD 转换是 RTC 模拟最常见的 bug，症状是 guest 的系统时间是一个奇怪的日期。

### 1.6 i8042 键盘控制器：为什么键盘控制器能重启机器

**i8042** 是 IBM PC/AT 上的键盘控制器，本身是一颗可编程的 8 位微控制器。它通过两个端口与 CPU 通信：

- `0x60`：数据端口。读是控制器的输出缓冲（键盘扫描码或命令应答），写是命令参数或发给键盘的字节。
- `0x64`：读是状态寄存器，写是控制器命令。

状态寄存器最重要的两位是 **OBF**（第 0 位，输出缓冲满，也就是“有数据可以从 `0x60` 读”）和 **IBF**（第 1 位，输入缓冲满，也就是“我还没处理完你上次写的东西，先别写”）。所有交互都遵循“写之前等 IBF=0，读之前等 OBF=1”的握手协议。

#### 1.6.1 A20 与 reset：键盘控制器的“副业”

i8042 除了管键盘，还有两个与键盘毫无关系的副业，都源于 IBM PC/AT 的历史：

**A20 门。** 8086 只有 20 根地址线，地址超过 1MB 会回绕到 0。有些 DOS 程序依赖这个回绕。80286 有 24 根地址线，不再回绕，为了兼容，IBM 在第 20 根地址线（A20）上加了一个“与门”，由……键盘控制器的一个空闲输出引脚控制。于是 i8042 的**输出端口**第 1 位成了 A20 开关。

**CPU 复位。** 80286 从保护模式回到实模式的唯一办法是复位 CPU。IBM 同样把 CPU 的 RESET 线接到了键盘控制器的一个输出引脚上——输出端口的第 0 位，低电平有效。于是“往 `0x64` 写命令 `0xFE`”（让控制器把输出端口第 0 位拉低一个脉冲）就成了 PC 上最经典的重启方法。

这就是为什么 Linux 的 `reboot=k` 参数（`k` 代表 keyboard）会让内核在重启时往 `0x64` 写 `0xFE`。mini-vmm 的默认 cmdline 就带了 `reboot=k`，VMM 看到这个写入就退出，这是“guest 请求重启 → VMM 退出”的通路。另一条通路是 `panic=-1`：内核 panic 后立即重启，同样走到这里。

#### 1.6.2 探测：让驱动快速通过

Linux 的 i8042 驱动探测时会发一串控制器命令：读控制器配置字节（CTR，命令 `0x20`）、控制器自检（命令 `0xAA`，期望应答 `0x55`）、键盘口测试（命令 `0xAB`，期望应答 `0x00`）、AUX（PS/2 鼠标）口测试等。每一条命令都期望在 `0x60` 上读到应答。

如果 VMM 只实现了一个空壳（比如只处理 `0xFE` 重启），驱动发出“读 CTR”后等不到 OBF，就会忙等到超时（大约 0.6 秒），然后打印 `Can't read CTR while initializing i8042`。功能上没问题，但每次启动白白浪费 0.6 秒。所以控制器命令需要逐条应答。

AUX 口的处理更有技巧：我们不想模拟鼠标，希望驱动“当场”判定 AUX 口不存在，而不是等超时。驱动判断 AUX 口是否存在的方法之一是回环测试：用命令 `0xD3` 让控制器把一个字节“假装从鼠标收到”放回输出缓冲，然后检查状态寄存器的 AUXDATA 位（第 5 位，“这个字节来自鼠标”）。真实硬件上有 AUX 口时这一位会置 1。所以模拟时**故意不置这一位**，驱动就立刻判定回环失败；接下来的 AUX 口测试命令（`0xA9`）回应 `0x01`（“时钟线卡在低电平”），驱动就放弃 AUX 口。整个过程没有一次超时。

键盘本身也要应答：atkbd 驱动会发“复位键盘”（期望 `0xFA` ACK 和 `0xAA` 自检通过）、“读 ID”（期望 `0xFA 0xAB 0x83`）等命令，而且键盘的应答要通过 **IRQ1** 送达，因为 PS/2 设备的数据路径是中断驱动的。控制器自身对命令的应答则不打中断，驱动在关中断的状态下轮询读取。真实日志里探测成功的样子：

```
[    0.606665] i8042: Probing ports directly.
[    0.610182] serio: i8042 KBD port at 0x60,0x64 irq 1
[    0.613705] input: AT Translated Set 2 keyboard as /devices/platform/i8042/serio0/input/input0
```

注意日志里只有 KBD 口没有 AUX 口，说明 AUX 口被当场判定不存在了。

一个布局上的小坑：i8042 的两个端口是 `0x60` 和 `0x64`，中间夹着 `0x61`，而 `0x61` 由 KVM 在内核里处理（《时间·原理篇》第一章的 PIT 通道 2 门控）。所以 VMM 注册 i8042 时不能占用 `[0x60, 0x65)` 整段，要分成两个单端口设备分别注册。

### 1.7 ACPI PM1 寄存器块：让 `poweroff` 真的关机

重启有键盘控制器，关机呢？在 ACPI 时代，关机的标准方式是写 ACPI 定义的**电源管理寄存器**。

ACPI 规定每台机器有一组 **PM1 寄存器块**：PM1 事件块（状态寄存器 `PM1_STS` 和使能寄存器 `PM1_EN`）和 PM1 控制块（`PM1_CNT`）。它们在哪个端口，由固件表（FADT，《固件与启动协议·原理篇》第一章讲）声明。`PM1_CNT` 的几个关键位：

```
   PM1_CNT（16 位）
   bit 0        SCI_EN    1 = 系统处于 ACPI 模式
   bit 10–12    SLP_TYP   要进入的睡眠状态类型
   bit 13       SLP_EN    写 1 = 立即进入 SLP_TYP 指定的状态
```

ACPI 定义了 S0（正常工作）到 S5（软关机）几种系统状态。`poweroff` 的最后一步是：内核从固件的 AML 代码里查出“S5 对应的 SLP_TYP 值”，然后往 `PM1_CNT` 写入 `SLP_TYP << 10 | SLP_EN`。真实硬件上电源就断了；VMM 看到这个写入就退出。

“S5 对应的 SLP_TYP 值”这个信息存放在固件的 DSDT 表里的一个叫 `_S5_` 的对象中，《固件与启动协议·原理篇》第一章会把它逐字节拆开。真实日志里关机的样子：

```
[   15.901146] ACPI: PM: Preparing to enter system sleep state S5
[   15.903697] reboot: Power down
[INFO] guest requested poweroff via ACPI S5
```

最后一行是 VMM 自己的输出：它在端口 `0x604` 上收到了 `SLP_TYP=5, SLP_EN=1` 的写入。

### 1.8 设备放在哪里：一张总表

至此，本文涉及的所有设备都出场了。按“谁来模拟”分组：

| 设备 | 端口 / 地址 | 中断 | 模拟者 | 为什么在那里 |
|---|---|---|---|---|
| 8259A PIC ×2 | `0x20-0x21`、`0xA0-0xA1` | — | KVM | 中断控制器，高频 |
| IOAPIC | `0xFEC00000` | — | KVM | 中断控制器，高频 |
| LAPIC ×N | `0xFEE00000` | — | KVM | 中断控制器，最高频 |
| 8254 PIT | `0x40-0x43` | GSI 0 | KVM | 时钟，高频 |
| 端口 B（PIT 门控） | `0x61` | — | KVM（需 `SPEAKER_DUMMY`） | 与 PIT 状态紧耦合 |
| i8042 | `0x60`、`0x64` | GSI 1 | VMM | 低频 |
| 16550A COM1 | `0x3f8-0x3ff` | GSI 4 | VMM | 与 host 终端交互，必须在用户态 |
| CMOS RTC | `0x70-0x71` | GSI 8（未实现） | VMM | 低频 |
| ACPI PM1a | `0x600-0x605` | GSI 9（SCI，未使用） | VMM | 低频，关机要通知 VMM |
| 其他所有端口 | — | — | VMM 兜底 | 读 `0xFF`，写丢弃 |

规律很清楚：**高频的、与 CPU 紧密交互的放内核；低频的、需要与 host 世界交互的放用户态。**

### 1.9 设备模型的并发

最后一个问题在单核时不存在，多核时立刻出现：**多个 vCPU 线程可能同时陷出，同时访问同一个设备。**

比如 vCPU 0 正在往串口写日志，vCPU 2 同时也在写。两个线程同时进入串口模拟代码，同时修改 FIFO 指针、同时计算中断线电平，数据结构就乱了。更隐蔽的是设备与 host 输入线程之间的竞争：输入线程往接收 FIFO 里放字节，vCPU 线程同时从里面取。

设备模型的并发保护有两种思路：每个设备自己加锁（细粒度），或者所有设备访问共用一把大锁（粗粒度）。QEMU 历史上用的是后者，这把锁叫 **BQL（Big QEMU Lock）**，vCPU 线程陷出到用户态处理设备访问时要先拿 BQL。这样设备模型的代码可以完全不考虑并发，代价是所有 vCPU 的设备访问被串行化。对于本文这些低频设备，串行化的代价完全可以接受。

mini-vmm 采用了同样的思路：一把大锁 `io_lock` 包住整个 PIO/MMIO 分发过程。串口另外有一把自己的锁，用来和 host 输入线程同步。两把锁之间有固定的加锁顺序（先大锁、后串口锁），输入线程只拿串口锁，从而避免死锁。《传统设备·实现篇》会展开。

### 1.10 小结

- 本文只涉及全模拟路线里最古老的一批设备，它们重要是因为 Linux 启动一定会碰它们。
- 设备模拟是一台寄存器状态机，模拟到什么程度由驱动的探测和使用逻辑决定。
- 未认领的端口读 `0xFF`、写丢弃，这是 Linux 探测逻辑依赖的“浮空总线”约定。
- 串口要处理 DLAB、THRE 中断的“一打开就触发”语义、回环自检、IIR 的 FIFO 位、OUT2 门控，以及边沿触发下每个事件一个新上升沿。
- RTC 要让 UIP=0，并用 BCD 返回 host 时间。
- i8042 要逐条应答控制器命令，用 AUXDATA 位和 AUX_TEST 应答让 AUX 口被当场判定为不存在；命令 `0xFE` 是重启通路。
- ACPI PM1_CNT 的 SLP_TYP/SLP_EN 写入是关机通路。
- 多 vCPU 并发访问设备，用一把大锁串行化是最简单可靠的方案。
