P1 结束时，guest 里的 e1000 驱动已经认出了网卡、读到了 MAC、报告链路 up，但这块网卡还没有接到任何地方：guest 发出的帧不知道该交给谁，host 这边也没有帧能送进来。这一 P 讲网卡的另一半，也就是 host 上帧真正进出的地方，以及两半之间怎么接。

| P | 内容 |
|---|---|
| P1 | 设备的外观：PCI 身份、寄存器窗口、EEPROM、PHY，驱动探测成功并报告链路 up |
| P2（本篇） | 前端与后端：`--netdev`/`--device`，TAP，收包为什么在 I/O 线程上，后端怎样暂停和恢复收包 |
| P3 | 中断：中断原因寄存器、INTx 电平、为什么中断数约等于 ICR 读次数 |
| P4 | 发送：描述符环、DMA、上下文描述符与校验和 offload |
| P5 | TSO：硬件替驱动切包，以及“哈希对了也可能是错的” |
| P6 | 接收：地址过滤、描述符写回的顺序、什么时候算环满，端到端验证 |

## 一、前端和后端

### 1.1 一张虚拟网卡的两半

一块真网卡一头插在 PCI 总线上，一头接着网线。虚拟网卡也有这两头，但两头完全是两回事：

- **前端**（frontend）是 guest 看得见的那一半：PCI 配置空间、寄存器、描述符环、中断。它模拟的是某一块具体的芯片，P1 讲的全是前端。
- **后端**（backend）是 guest 看不见的那一半：帧离开虚拟网卡之后去哪里、从哪里来。可以是 host 上的一个 TAP 接口，也可以是以后的 vhost-net、vhost-user，或者一个 UDP socket。

两半分开写，是因为它们的组合是乘法：

```
  不分层：每种组合写一遍                      分层：前端和后端各写一份

  e1000 + TAP          virtio-net + TAP       前端         接口          后端
  e1000 + vhost-user   virtio-net + vhost-user e1000      ─┐            ┌─ TAP
  e1000 + socket       virtio-net + socket     virtio-net ─┼─ netdev.h ─┼─ vhost-user
  ...                                                      ┘            └─ socket
  N 种网卡 × M 种后端                          N + M 份代码
```

QEMU 的命令行也是按这两半分的：`-device e1000` 是前端，`-netdev tap` 是后端，中间用 id 连起来。mini-vmm 照搬了这个写法（第二章）。

### 1.2 两半之间只有三个动作

`include/net/netdev.h` 是两半之间唯一的接口。前端不碰后端的 fd，后端不认识任何寄存器，它们之间只有三个动作：

```
        vCPU 线程                                 I/O 线程
  ┌──────────────────┐                     ┌──────────────────┐
  │ e1000（前端）      │  ① netdev_send()     │ netdev + TAP     │
  │  guest 写 TDT     │ ──────────────────▶ │  writev(tap_fd)  │──▶ host 协议栈
  │                  │                     │                  │
  │  e1000_receive() │ ◀────────────────── │  read(tap_fd)    │◀── host 协议栈
  │   返回 DONE/FULL  │  ② receive 回调       │                  │
  │                  │                     │                  │
  │  guest 写 RDT     │ ──────────────────▶ │  停读 / 恢复读      │
  │                  │  ③ netdev_rx_resume  │                  │
  └──────────────────┘                     └──────────────────┘
```

| 动作 | 谁调用 | 在哪个线程 | 含义 |
|---|---|---|---|
| ① 发送 | 前端调 `netdev_send(nd, iov, iovcnt)` | 写 TDT 的那个 vCPU 线程 | 一次一整帧，可以分成几段 iovec |
| ② 接收 | 后端调前端登记的 `receive(opaque, frame, len)` | I/O 线程 | 一次一整帧；前端没有空闲缓冲时返回 `NETDEV_RX_FULL` |
| ③ 恢复 | 前端调 `netdev_rx_resume(nd)` | 任意线程，e1000 是写 RDT 的 vCPU 线程 | guest 补充了接收缓冲，后端可以继续送帧 |

第三个动作是流控，第六章专门讲。

### 1.3 帧在边界上长什么样

接口还要约定帧的格式。mini-vmm 的约定是：两边交换的都是**不带 FCS 的普通以太网帧**，前面没有 TAP 的 packet information 头，也没有 virtio-net 的 vnet header。

这条约定决定了几件事放在前端做，而不是后端：

- **补齐短帧和 FCS。** 以太网线上的帧至少 64 字节（含 4 字节 FCS），不够的由发送方补零。TAP 交上来的帧没经过真正的线，可能比这短（一个 ARP 请求只有 42 字节），末尾也没有 FCS。可是 82540EM 只在 `RCTL.SECRC` 置位时才替驱动剥掉 FCS，Linux 的 e1000 驱动从不置这一位，而是在 `e1000_clean_rx_irq()` 里对每一帧 `pskb_trim(skb, skb->len - 4)`。如果前端原样转交 TAP 的帧，每一帧末尾都会有 4 字节真实数据被当成 FCS 剪掉。所以 `e1000_receive()` 自己把帧补到 60 字节，`SECRC` 没置位时再算一个 CRC32 接在后面。这是“线”的性质，只有模拟线的那一方知道要不要做。
- **校验和与 TSO。** e1000 的驱动把这些工作交给硬件（P4、P5），硬件的语义写在上下文描述符里。后端不认识上下文描述符，所以由 e1000 前端在设备模型里把校验和填好、把大包切开，交给后端的已经是能直接上线的帧。

不用 vnet header 是有代价的：以后 virtio-net 自己就带着一套 offload 元数据，用 vnet header 可以直接交给 host 内核去切包和算校验和，省掉一次在用户态的计算。目前的后端只服务 e1000 这样没有元数据格式的全模拟网卡，先按最简单的格式约定；virtio-net 里程碑需要时再给接口加上可选的元数据。

## 二、命令行：沿用 QEMU 的写法

### 2.1 两个选项，一个 id

```sh
./build/vmm --mode linux --mem 512M \
    --netdev tap,id=n0,ifname=tap0 \
    --device e1000,netdev=n0,mac=52:54:00:ab:cd:ef \
    --initrd build/initramfs.cpio.gz guest-kernel/vmlinux
```

`--netdev` 定义后端并给它起名 `n0`，`--device` 定义前端并用 `netdev=n0` 引用它。两个选项的写法和 QEMU 的 `-netdev`、`-device` 一致，同一台 guest 放到 QEMU 里对照时，命令行几乎可以原样搬过去。

`--netdev help` 和 `--device help` 列出可用的类型：

```text
Available --netdev types:
  tap          host TAP interface; properties: id, ifname
Available --device drivers:
  e1000        Intel 82540EM gigabit NIC (fully emulated), needs netdev=, optional mac=
  pci-test     PCI bus test device: MMIO and IO BAR over a magic/scratch register file
```

### 2.2 参数值的语法

逗号分隔的 `key=val` 列表，语法沿用 QEMU 的 QemuOpts（`util/qemu-option.c` 的 `get_opt_name_value()`），解析在 `src/opts.c`，`--device` 和 `--netdev` 共用：

- 第一个元素没有 `=` 时，它是“隐含键”的值。`--device` 的隐含键是 `driver`，`--netdev` 的是 `type`，所以 `e1000,netdev=n0` 和 `driver=e1000,netdev=n0` 是一回事。
- 值里的 `,,` 表示一个逗号：`ifname=a,,b` 的值是 `a,b`。

有三处比 QEMU 严格，目的都是让写错的参数在启动前报错，而不是静默地变成另一个意思：

| 写法 | QEMU | mini-vmm |
|---|---|---|
| `tap,id=n0,ifname=tap0,ifname=tap1` | 取最后一个，`tap1` | 报错 `property 'ifname' given twice` |
| `e1000,netdev=n0,foo` | 当成 `foo=on`（已废弃的短格式，打印警告） | 报错：第一个元素之外的元素必须带 `=` |

空元素和空键也一律报错。第一条最常见：长命令行改了一处、忘了删另一处，QEMU 下看不出生效的是哪个。

### 2.3 解析、连线、挂载、打开

一个 `--netdev` 从命令行到开始收帧，要经过四步。分成四步，是因为每一步依赖的东西不同：

| 步骤 | 时机 | 做什么 | 这一步能发现的错误（真实输出） |
|---|---|---|---|
| 解析 | 读命令行时，逐个参数 | `netdev_parse()` 检查语法、类型、属性名、id 格式和 ifname 长度，只分配对象，不打开任何 fd；`vmm_device_parse()` 对 `--device` 做同样的事，`netdev=` 只记下名字 | `--device e1000,netdev=n0,mca=...: unknown property 'mca' (valid: driver, netdev, mac)` |
| 连线 | 所有参数读完后，一次 | `netdev_link()` 把每个 `netdev=` 解析成对象，检查一一对应 | `--device e1000,netdev=n0: no --netdev with id 'n0'` |
| 挂载 | VM 和 PCI 总线建好后 | 前端 attach 到总线，顺便 `netdev_set_frontend()` 登记自己的 `receive` | — |
| 打开 | 所有前端挂载完、`evl_start()` 之前 | `netdev_open()` 打开 TAP、建唤醒用的 eventfd，两个 fd 都注册到 I/O 线程 | `netdev n0: TAP tap9: Operation not permitted; create it beforehand with 'ip tuntap add dev tap9 mode tap user $(id -un)'` |

几个顺序上的理由：

- **连线要等全部读完。** `--netdev` 可以写在引用它的 `--device` 后面，解析到 `--device` 时，它引用的后端可能还没出现。
- **打开要等挂载完。** TAP 一注册进 I/O 线程就可能有帧到达，那时必须已经有前端接着，否则帧不知道交给谁。
- **打开要在 `evl_start()` 之前。** 事件循环的回调表只允许在启动前或在 I/O 线程上修改（《线程模型与事件循环》2.3 节），主线程在 I/O 线程跑起来之后注册 fd 会和它抢同一张表。

连线这一步有两条规则：

- **一个后端只接一个前端。** 两张网卡共用一个 TAP 时，从 TAP 读到的帧该交给哪一张没有定义。报错：`netdev 'n0' is already used by --device e1000,netdev=n0`。
- **没有前端的后端是错误。** QEMU 对这种情况只打印一条 `has no peer` 警告。这里报错，是因为漏写 `--device` 时 TAP 照样被打开，host 上看起来一切正常，guest 里却根本没有网卡，排查要绕一大圈。报错：`--netdev tap,id=n0,ifname=tap0: not used by any --device (a NIC needs netdev=n0)`。

## 三、TAP：原理

### 3.1 一块网线是文件描述符的网卡

TAP 是 host 内核里的一块虚拟网卡（`drivers/net/tun.c`）。它和真网卡一样有名字（`tap0`）、MAC、IP 地址，`ip link` 能看到它，路由表能指向它。区别在于网线：真网卡的网线是一根电缆，TAP 的网线是一个文件描述符。

```
        host 协议栈                                VMM 进程
  ┌───────────────────────┐                  ┌────────────────────┐
  │ ping 10.0.2.15        │                  │                    │
  │   → 路由：走 tap0       │                  │                    │
  │   → tap0 “发出”一帧  ───┼── read(fd) ────▶ │ 交给 e1000 前端       │
  │                       │                  │ → DMA 进 guest 内存   │
  │                       │                  │                    │
  │ tap0 “收到”一帧        │                  │ e1000 前端发出一帧     │
  │   → 协议栈处理 ICMP 回复 ◀┼── write(fd) ───── │                    │
  └───────────────────────┘                  └────────────────────┘
```

方向容易搞反，用一次 ping 走一遍：

- host 上 `ping 10.0.2.15`，路由把包交给 `tap0` 发出去。对一块真网卡来说帧会上网线；对 TAP 来说，帧进了内核里的一个队列，VMM `read(fd)` 就能读到它。
- guest 回复的 ICMP 帧由 VMM `write(fd)` 写进去。在 host 协议栈看来，这是 `tap0` 从网线上**收到**的一帧，和真网卡收包走同一条路。

所以在 host 上用 `ip -s link show tap0` 看计数时，`TX` 是 host 发往 guest 的方向，`RX` 是 guest 发往 host 的方向，和 guest 里 `eth0` 的计数正好相反。

### 3.2 打开时的几个标志

打开 TAP 就是打开 `/dev/net/tun`，再用 `TUNSETIFF` ioctl 说明要接哪个接口、什么模式。mini-vmm 用两个标志：

- `IFF_TAP`：二层模式，读写的是完整以太网帧。另一种是 `IFF_TUN`，三层模式，读写的是 IP 包，没有以太网头。网卡模拟要的是以太网帧（guest 驱动要看目的 MAC、发 ARP），所以只能是 TAP。
- `IFF_NO_PI`：不要 packet information 头。不加这个标志时，每帧前面多出 4 字节（标志和协议号），前端得在每次收发时剥掉、补上。

没加的标志是 `IFF_VNET_HDR`，理由见 1.3 节。

### 3.3 新建还是接上

`TUNSETIFF` 对名字的处理有两种情况（`tun.c` 的 `tun_set_iff()`）：

| 名字 | 结果 | 权限 |
|---|---|---|
| 不存在 | 新建一个 TAP，进程退出就消失 | 需要所在 network namespace 的 `CAP_NET_ADMIN` |
| 已存在 | 接到这个接口上 | 预先用 `ip tuntap add ... user <用户名>` 建的接口，属主可以不带特权打开 |

所以普通用户的标准做法是让管理员预先建好接口：

```sh
sudo ip tuntap add dev tap0 mode tap user $(id -un)
sudo ip addr add 10.0.2.1/24 dev tap0
sudo ip link set tap0 up
```

之后 VMM 以普通用户身份运行就能打开 `tap0`。其他几种失败的 errno 都有确定的含义，`tap_open()` 把它们翻译成可操作的提示：

| errno | 原因 | 提示 |
|---|---|---|
| `EPERM` | 接口不存在，又没有权限新建 | 给出上面的 `ip tuntap add` 命令 |
| `EBUSY` | 单队列 TAP 已经被另一个 fd 接着（`tun_attach()`），比如另一个 VMM 还在跑 | `another process already has it open` |
| `EINVAL` | 同名接口存在但不是 TAP（比如 `lo`），或者多队列属性不一致 | `exists but is not a single-queue TAP` |

还有一种情况不会让打开失败：接口没 up。这时往 TAP 写会得到 `EIO`（`tun_get_user()` 检查 `IFF_UP`），guest 发出的帧全部丢失。接口可以在 VM 运行中再 up，所以 `tap_open()` 只打一条警告：`TAP tap0 is down, frames from the guest are dropped until 'ip link set tap0 up'`。

### 3.4 测试为什么不需要 root

`ip tuntap add` 要 root，但自动化测试不能要求 root。Linux 允许普通用户建一个新的 user namespace 加 network namespace（`unshare -rn`）：在里面用户映射成 root，拥有这个 namespace 的 `CAP_NET_ADMIN`，可以随便建 TAP、配地址；这些接口对外面的 host 不可见，进程退出 namespace 就消失。`/dev/kvm` 的权限检查不受 namespace 影响，VMM 照常能用 KVM。

`tests/e2e/emu-net.sh` 就是这样做的：脚本用 `unshare -rn` 把自己再执行一次，在新的 namespace 里建 `tap0`（10.0.2.1）、起对端程序，再启动 VMM（guest 是 10.0.2.15）。单元测试 `tests/unit/netdev_test.c` 也在启动任何线程之前调 `unshare()` 进入自己的 namespace。

## 四、TAP：实现

### 4.1 打开

`src/net/tap.c` 只负责拿到 fd 和给出提示，收发都在 `src/net/netdev.c`：

```c
fd = open("/dev/net/tun", O_RDWR | O_NONBLOCK | O_CLOEXEC);
...
ifr.ifr_flags = IFF_TAP | IFF_NO_PI;
memcpy(ifr.ifr_name, ifname, strlen(ifname) + 1);   /* 长度在解析阶段已经限制 */
if (ioctl(fd, TUNSETIFF, &ifr) < 0) {
    /* 按 errno 给出 3.3 节表里的提示 */
}
warn_if_down(id, ifr.ifr_name);
```

`O_NONBLOCK` 是给接收用的：I/O 线程一次回调里循环读，读空时要拿到 `EAGAIN` 返回事件循环，而不是阻塞在 `read` 里（那样 I/O 线程管的其他 fd 就都停了）。

### 4.2 发送：一次 writev 就是一帧

```c
int netdev_send(struct netdev *nd, const struct iovec *iov, int iovcnt)
{
    ...
    /* TAP 的一次 write 就是一帧（tun_get_user），不存在“写了一半再补” */
    n = writev(nd->fd, iov, iovcnt);
    if (n >= 0 && (size_t)n == want) {
        nd->stats.tx_frames++;
        ...
        return VMM_OK;
    }
    /* 第一次失败给出原因，之后只计数 */
    if (nd->stats.tx_errors++ == 0)
        vmm_warn("netdev %s: write to TAP %s failed: %s (further failures are only counted)", ...);
    return VMM_ERR_SYS;
}
```

两个设计点：

**为什么用 iovec。** 前端拼出来的帧常常不在一块连续内存里。e1000 打开了 VLAN 插入时，要在目的 MAC、源 MAC 之后塞进 4 字节 tag，再接上原来的负载；短帧还要在末尾补零。`tx_emit()` 用三四段 iovec 描述这一帧，不用先拷到一个临时缓冲里：

```c
iov[n++] = (struct iovec){ pkt, 2 * ETH_ALEN };                         /* 两个 MAC */
iov[n++] = (struct iovec){ tag, VLAN_HLEN };                            /* 插入的 tag */
iov[n++] = (struct iovec){ pkt + 2 * ETH_ALEN, len - 2 * ETH_ALEN };    /* 其余部分 */
...
iov[n++] = (struct iovec){ (void *)zeros, ETH_ZLEN - total };           /* 补齐短帧 */
netdev_send(s->net, iov, n);
```

TAP 把一次 `writev` 的所有段拼成一个 skb，当作一帧处理。

**为什么失败只警告一次。** 最常见的失败是接口没 up（`EIO`）。这时 guest 每发一帧都会失败，ARP 重试、TCP 重传每一帧都打印一行的话，日志会被刷满。以太网本来就允许丢帧，guest 的协议栈会自己重传，所以第一次说清原因，之后只在 `tx_errors` 里计数。

### 4.3 接收缓冲有多大

```c
#define NETDEV_RX_BUF     (65535 + 4)
```

一帧最长多少，取决于 TAP 能交出什么。没有 `IFF_VNET_HDR` 时，host 内核在把 GSO 大包交给 TAP 之前已经切成不超过 MTU 的帧；TAP 的 MTU 上限是 65535 减以太网头（`tun_net_init()` 的 `max_mtu`），加上以太网头和可能插回的 4 字节 VLAN tag（`tun_put_user()`），最长 65539 字节。

缓冲比帧短会怎样？`tun_put_user()` 在缓冲不够时截断拷贝，但 `read()` 仍然返回整帧的长度。所以返回值大于缓冲就说明截断了，`netdev_on_rx()` 按错误丢弃这一帧，而不是把半帧交给 guest：

```c
if ((size_t)n > sizeof(nd->rxbuf)) {
    vmm_warn("netdev %s: dropped a %zd-byte frame, longer than the %zu-byte receive buffer", ...);
    nd->stats.rx_errors++;
    continue;
}
```

### 4.4 一次回调读多少帧

```c
#define NETDEV_RX_BATCH   64
```

TAP 可读时，回调循环读帧交给前端，读空（`EAGAIN`）就返回。但如果 host 一直在灌包，TAP 可能永远读不空，I/O 线程就一直困在这一个回调里，它管的终端输入等其他 fd 都得不到处理。所以一次回调最多处理 64 帧，然后返回事件循环。剩下的帧不会丢：epoll 是水平触发，fd 还可读，下一轮 `epoll_wait` 会再报上来。

## 五、收包为什么在 I/O 线程上

### 5.1 发送由 guest 触发，接收由外界触发

两个方向的触发者不同，所以跑在不同的线程上。

**发送**由 guest 触发。guest 驱动把帧放进发送描述符环，写 TDT 寄存器告诉网卡“有新帧”。这次写 MMIO 产生一次 `KVM_EXIT_MMIO`，正在执行驱动代码的那个 vCPU 线程从 `KVM_RUN` 返回，进入 e1000 的寄存器处理，`tx_process()` 读描述符、DMA 读出帧、调 `netdev_send()` 写进 TAP，然后返回 `KVM_RUN`。整个过程在 vCPU 线程上同步完成，guest 的那颗 CPU 在这段时间里停着。

**接收**由外界触发。host 上的一帧什么时候到达 TAP，guest 不知道，vCPU 线程也不知道。guest 闲着时 vCPU 线程睡在 `KVM_RUN` 里的 `HLT` 上，根本不会醒来看 TAP。所以必须有一个线程专门等 TAP 可读，这就是《线程模型与事件循环》1.1 节说的“后端等 host”。mini-vmm 里这个线程是 I/O 线程，TAP 是继终端之后注册进去的第二种后端。

一帧从 host 到 guest 的完整路径：

```
  I/O 线程                                           vCPU 线程（可能正睡在 HLT 上）
  epoll_wait 返回：tap_fd 可读
  netdev_on_rx()
    read(tap_fd) → rxbuf
    e1000_receive()
      lock(io_lock)
      过滤、补齐、加 FCS
      rx_ring_put()：DMA 写进 guest 的接收缓冲，
                     回写描述符，移动 RDH
      raise_icr(RXT0) → pci_set_irq(1)
                     → KVM_IRQ_LINE(GSI 17, 1)  ───▶  KVM 把中断送进 IOAPIC，
      unlock(io_lock)                                唤醒 vCPU，注入中断
                                                    guest 中断处理函数读 ICR …
```

中断从一个非 vCPU 线程发出，这对 KVM 没有问题：`KVM_IRQ_LINE` 是 VM 级的 ioctl，任何线程都能调，KVM 负责把目标 vCPU 叫醒。串口的输入中断早就是这样从 I/O 线程发出的。

### 5.2 两个线程碰同一个设备

e1000 的状态现在有两个线程在改：vCPU 线程处理寄存器访问，I/O 线程处理收帧。两者都要读写 RDH、RDT、ICR 这些寄存器，必须串行。

mini-vmm 用的是已有的 `vm->io_lock`。vCPU 线程的 PIO/MMIO 分发本来就持着这把锁进入设备（《线程模型与事件循环》第四章），所以寄存器处理函数里不需要再加锁；I/O 线程上的 `e1000_receive()` 进来第一件事就是拿这把锁：

```c
static enum netdev_rx_result e1000_receive(void *opaque, const uint8_t *frame, size_t len)
{
    ...
    pthread_mutex_lock(&s->vm->io_lock);
    rctl = *reg(s, E1000_RCTL);
    if (!(rctl & E1000_RCTL_EN) || len < ETH_HLEN || !rx_filter(s, frame))
        goto out;
    ...
out:
    pthread_mutex_unlock(&s->vm->io_lock);
    return res;
}
```

锁的顺序仍然是 `io_lock` → 设备内部状态 → KVM ioctl，和串口一致：`pci_set_irq()` 里的 `KVM_IRQ_LINE` 在持锁时调用，KVM 内部不会回调用户态，所以不会反过来等这把锁。

## 六、guest 来不及收：后端的暂停与恢复

### 6.1 真网卡怎么办，虚拟网卡可以怎么办

guest 驱动预先在接收描述符环里放好一批空缓冲，网卡收到一帧就填一个。如果帧来得比 guest 补缓冲快，环会被用完。这时候真网卡和虚拟网卡的处境不一样。

**真网卡的网线不能等。** 对端发出的帧会按线速到达，网卡要么存下来，要么丢掉。82540EM 片内有一块接收 FIFO：环用完时先把帧存在 FIFO 里，同时把 RNBC（Receive No Buffers Count，手册第 13.7.33 节）加一，“只要 FIFO 还有空间，帧仍会被接收”；FIFO 也满了，帧就丢掉，MPC（Missed Packets Count，第 13.7.5 节）加一，同时置 ICR 的 RXO 位（Receiver Overrun）。

**虚拟网卡的“网线”可以等。** 帧在 TAP 的队列里，VMM 不去读，它就留在那里。所以环满时，最自然的做法是先停止读 TAP，等 guest 补了缓冲再继续。TAP 的队列就相当于那块 FIFO：它的容量是接口的 `tx_queue_len`（`tun_attach()` 按它设置环的大小，`ip link` 显示为 `qlen`），队列也满了，host 内核才丢帧（`tun_net_xmit()` 里的 `SKB_DROP_REASON_FULL_RING`），计入 `tap0` 的 TX dropped。

| | 82540EM | mini-vmm |
|---|---|---|
| 环用完时帧暂存在哪 | 片内接收 FIFO | TAP 的队列，容量是 `qlen` |
| 暂存时的计数 | RNBC | `netdev_stats.rx_pauses`（暂停的次数） |
| 暂存也满了 | 丢帧，MPC 加一，置 ICR.RXO | host 内核丢帧，`tap0` 的 TX dropped 加一 |

mini-vmm 的统计寄存器（0x4000–0x40FC）读出来都是 0，所以 guest 里看不到 RNBC 和 MPC（`/sys/class/net/eth0/statistics/rx_missed_errors` 来自 MPC，永远是 0）。要看丢帧，得看 host 上 `tap0` 的计数。

### 6.2 为什么不能只是“这次不收”

最省事的实现是：环满时 `e1000_receive()` 返回，帧丢掉，下一帧到了再试。这会把 TCP 吞吐打垮，因为丢一帧就要等重传。

稍好一点的实现是：环满时帧不丢，下次回调再试。但 epoll 是水平触发，TAP 里还有帧时 fd 一直可读，I/O 线程会立即再次回调、再次被拒、再次回调，空转占满一个 CPU，直到 guest 补了缓冲。

所以正确的做法要满足三点：帧不丢，不空转，guest 一补缓冲就立刻恢复。

### 6.3 实现

后端保存着被拒的那一帧（`pending_len > 0` 表示 `rxbuf` 里有一帧还没送出去），停止关心 TAP 的可读事件，等前端通知：

```
  I/O 线程                                        vCPU 线程
  netdev_on_rx()
    read → rxbuf
    e1000_receive() 返回 FULL
    rx_pause():
      evl_mod(tap_fd, 0)        不再关心 tap_fd 可读
      rx_blocked = true
      再试一次 → 仍然 FULL
      return                    I/O 线程回到 epoll_wait，
                                tap_fd 不会再把它叫醒
                                                 guest 驱动补充缓冲，写 RDT
                                                 → e1000 寄存器处理
                                                 → netdev_rx_resume():
                                                     rx_blocked 原来是 true，换成 false
                                                     write(wake_fd, 1)
  epoll_wait 返回：wake_fd 可读
  netdev_on_wake()
    read(wake_fd)
    把 rxbuf 里挂着的帧交给前端 → DONE
    evl_mod(tap_fd, EPOLLIN)    恢复读 TAP
```

前端这边只需要在“可能多出空闲缓冲”的地方调一次 `netdev_rx_resume()`。e1000 有两处：写 RDT（guest 补了缓冲）和写 RCTL（驱动可能先填好缓冲再打开接收使能，这时后端也许正停着）：

```c
case E1000_RCTL:
    *reg(s, E1000_RCTL) = val;
    /* 驱动可能先填好缓冲再打开 EN，这时后端也许正停着等缓冲 */
    if (s->net)
        netdev_rx_resume(s->net);
    return;
case E1000_RDT:
    *reg(s, E1000_RDT) = val & 0xFFFF;
    if (s->net)
        netdev_rx_resume(s->net);
    return;
```

guest 每收几帧就写一次 RDT，所以 `netdev_rx_resume()` 必须便宜。后端没暂停时，它只做一次原子交换就返回，不写 eventfd、不产生系统调用：

```c
void netdev_rx_resume(struct netdev *nd)
{
    uint64_t one = 1;

    if (!__atomic_exchange_n(&nd->rx_blocked, false, __ATOMIC_SEQ_CST))
        return;
    if (write(nd->wake_fd, &one, sizeof(one)) != sizeof(one))
        vmm_err(...);
}
```

唤醒用 eventfd，而不是在 vCPU 线程上直接调 `evl_mod()` 恢复读 TAP：事件循环的回调表只有 I/O 线程能改（《线程模型与事件循环》2.3 节）。vCPU 线程只负责“叫一声”，真正的恢复由 I/O 线程自己做。

### 6.4 最容易错的地方：丢失的唤醒

`rx_pause()` 里置位 `rx_blocked` 之后还要“再试一次”，看起来多余，实际上没有它，收包会永远停住。

看一个时间线。假设没有那次重试：

```
  I/O 线程                               vCPU 线程
  e1000_receive() → FULL
                                         guest 补充缓冲，写 RDT
                                         netdev_rx_resume():
                                           rx_blocked 还是 false → 直接返回，什么都不做
  rx_pause():
    evl_mod(tap_fd, 0)
    rx_blocked = true
    return
                                         （guest 等着收包，不会再写 RDT）
  永远没人写 wake_fd，TAP 永远不再被读
```

guest 补充缓冲的那一刻，后端还没来得及挂出“我停了”的牌子，那次通知就落空了。之后 guest 在等帧，后端在等通知，两边都不会动。

加上重试之后，两种先后顺序都被覆盖：

- **RDT 写发生在置位之前**（上图的情况）：缓冲已经补上，置位后的那次重试就能成功，后端恢复读 TAP，不需要任何唤醒。
- **RDT 写发生在置位之后**：`netdev_rx_resume()` 看到 `rx_blocked` 是 true，写 eventfd，I/O 线程被唤醒后重试。

为什么两种情况就是全部？因为重试（`e1000_receive()`）和 RDT 的写处理（包括其中的 `netdev_rx_resume()`）都在 `io_lock` 下执行，两段临界区必有先后。RDT 写的临界区在前，重试就能看到补上的缓冲；重试的临界区在前，那么置位发生在重试拿锁之前，也就早于 RDT 写处理里的原子交换，交换一定看到 true。不存在“前端判断到一半、缓冲才补上”的中间状态。

如果重试成功了，而 vCPU 线程恰好也抢先清零并写了 eventfd，I/O 线程之后会收到一次多余的唤醒。`netdev_on_wake()` 发现 `pending_len` 是 0，只是把 TAP 重新设为可读，无害。

### 6.5 实测：什么时候真的会暂停

在 `unshare -rn` 的 namespace 里启动 guest，`-v` 打开调试日志，暂停和恢复各打印一行。

**host → guest 下载 64 MiB（TCP，wget）**：1.68 秒传完，0 次暂停。guest 收得比 host 发得快，环从没用完。

**host 对 guest 打 20 万个 UDP 小包**（每个 18 字节负载，Python 循环 `sendto`，0.75 秒发完）：

```text
[DBG ] netdev.c:201: netdev n0: frontend has no RX buffer, pausing
[DBG ] netdev.c:258: netdev n0: frontend refilled RX buffers, resuming
[DBG ] netdev.c:201: netdev n0: frontend has no RX buffer, pausing
[DBG ] netdev.c:258: netdev n0: frontend refilled RX buffers, resuming
```

guest 里 `eth0` 的 `rx_packets` 是 200001（20 万个 UDP 加一个 ARP），`rx_dropped` 是 0；host 上 `tap0` 的 TX 是 200007 帧，dropped 也是 0。环用完了两次，两次都是暂停读 TAP、等 guest 补缓冲、再恢复，暂停期间到达的帧都在 TAP 的队列里等着，一帧没丢。

## 七、验证

### 7.1 单元测试

`tests/unit/netdev_test.c` 不启动 guest，用一个假前端直接测后端。解析和连线的用例覆盖 id 格式、未知类型、引用不存在的 id、两张网卡共用一个后端、没有网卡引用的后端、id 重复。TAP 的用例在测试自己建的 namespace 里打开一个真实 TAP，对端是绑在这个接口上的 `AF_PACKET` socket：

- 两段 iovec 发出去，对端收到的是原样的一帧；
- 对端发的帧在 I/O 线程上交给前端；
- 假前端切到“满”状态后，对端连发 A、B、C 三帧：前端恰好被调用两次（第一次 FULL，加上置位后的那次重试），之后 200 毫秒内不再被调用（证明没有空转）；主线程调 `netdev_rx_resume()` 后，A、B、C 按原顺序到达，之后的新帧 D 也照常到达（证明恢复了读 TAP）；
- 同一 TAP 第二次打开报 EBUSY，打开 `lo` 报 EINVAL，接口 down 时写入失败且只警告一次。

所有等待都有 5 秒上限，超时会报出在等哪一帧。

测试的有效性用九个错误实现检验，每个都让测试变红：暂停时不停读 fd、FULL 时丢弃挂起的帧、resume 不写 eventfd、唤醒后不恢复读 fd、只写第一段 iovec、漏掉 `IFF_NO_PI`、不检查未被引用的 netdev、每次写失败都警告、不检查 id 格式。

### 7.2 端到端

`tests/e2e/emu-net.sh` 的前五条用例检查真实的 `vmm` 程序：非 linux 模式下用 `--netdev`、没有网卡引用的后端、拼错的属性、不存在的类型，都在创建 VM 之前报错；`--netdev help` 列出类型。之后的用例在 namespace 里跑真实 guest，那部分属于 P3 到 P6 的内容，P6 统一讲。

## 八、限制

- 后端只有 TAP。vhost-net、vhost-user 各自有里程碑。
- 接口不传 offload 元数据（1.3 节），校验和与分段都在用户态的设备模型里算。
- 单队列。多队列 TAP 要配合多队列网卡，82540EM 只有一对环。
- 统计寄存器读 0，guest 里看不到 RNBC、MPC，丢帧要看 host 上 TAP 的计数（6.1 节）。
- 发送在 vCPU 线程上持着 `io_lock` 做 `writev`，这段时间 I/O 线程的收包要等锁。这是慢路径的固有代价，ioeventfd 里程碑会把“guest 写 TDT”从 vCPU 线程上拿走，届时可以对照。
