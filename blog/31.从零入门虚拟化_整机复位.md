到上一篇为止，guest 一重启，mini-vmm 就退出了：Linux 的 `reboot` 最后往 i8042 的 0x64 端口写 0xFE，VMM 收到后把它当作关机信号，整个进程结束。测试一直靠这一点收尾，`panic=-1` 也是为了让 panic 的 guest 尽快“重启”从而让 VMM 退出。可是下一个里程碑要跑完整的发行版，发行版装完软件包会重启，systemd 的 `reboot` 是日常操作；挂着 gdb 调试启动流程时，也希望 guest 重启后 gdb 还连着。这一篇让 VMM 像真机按下 reset 键那样，在同一个进程里把整台机器带回上电状态再启动一次，磁盘镜像、TAP、gdb 连接都不断。顺着实现要回答三个问题：“上电状态”到底由哪几部分组成，每一部分该由谁来恢复；为什么最常用的 `reboot -f` 测不出漏恢复了 AP 的状态；复位进行时 I/O 线程和 gdbstub 线程还在跑，怎样不让它们看到一台复位到一半的机器。

## 一、从“退出”到“复位”

### 1.1 guest 怎样请求复位

guest 的内核命令行里有 `reboot=k`，意思是重启走键盘控制器。Linux 6.6 的 `arch/x86/kernel/reboot.c` 里，`native_machine_emergency_restart()` 在 `BOOT_KBD` 分支执行 `outb(0xfe, 0x64)`：8042 的 0xFE 命令把输出端口的 bit 0 拉低一下，PC 上这根线接到 CPU 的复位输入。没有 `reboot=k` 时 x86 Linux 先试 ACPI（`reboot_type` 缺省是 `BOOT_ACPI`），按 FADT 的 `RESET_REG` 写 `RESET_VALUE`；mini-vmm 的 FADT 把这两项填成 0x64 和 0xFE（`src/boot/acpi.c`），所以 ACPI 这条路最后也落在同一个 i8042 命令上。三种常见的重启都汇到这里：

| guest 里发生了什么 | 内核路径 | 走到 0x64 时其它 CPU 在干什么 |
|---|---|---|
| `reboot -f` | `reboot(2)` → `kernel_restart` → `native_machine_restart` → `machine_shutdown`（里面 `stop_other_cpus()`）→ `__machine_emergency_restart` | 已经被 IPI 叫停，关着中断停在 `hlt` 里 |
| `echo b > /proc/sysrq-trigger` | `drivers/tty/sysrq.c` → `emergency_restart()` | 照常运行，不做任何准备 |
| panic，命令行有 `panic=-1` | `panic()` → `emergency_restart()` | 已被 panic 路径停下 |

表里最后一列在第三节会变得很重要。

VMM 这一侧，i8042 模型收到 0xFE 后调用 `vm_request_reset(vm, "i8042")`。它只做两件事：打一行 `guest requested reset via i8042`，没带 `--no-reboot` 时置 `vm->reset_requested`；然后返回 `VMM_ERR_EXIT`，让这个 vCPU 按普通的停机路径退出。普通停机路径会叫停所有 vCPU（`smp` 里程碑里的 `vm_request_stop`：置 `should_stop`、`immediate_exit`，再给每个线程发 SIGUSR1），`vm_run` 等所有线程 join 后返回。和以前唯一的区别在 `main` 里：

```c
for (;;) {
    r = vm_run(&vm);
    if (r != VMM_OK || !vm.reset_requested)
        break;
    r = vm_reset(&vm, linux_load_images, &vm);
    if (r != VMM_OK)
        break;
}
```

`vm_run` 返回时，如果是 guest 请求了复位，就调 `vm_reset` 把整机带回上电状态，再进下一轮 `vm_run`。整个过程画出来是这样：

```
 vCPU 2 线程          其它 vCPU 线程           main 线程                 I/O 线程
 ───────────          ─────────────           ─────────                 ────────
 OUT 0x64 ← 0xFE
 i8042 → vm_request_reset
   reset_requested = true
   返回 VMM_ERR_EXIT
 vm_request_stop ──SIGUSR1──▶ KVM_RUN 返回 EINTR
 线程退出                     线程退出
                                              vm_run 里 join 全部线程
                                              vm_run 返回
                                              vm_reset:
                                                lock(io_lock) ─────────▶ 收包/控制台输入
                                                恢复 irqchip、vCPU          在锁外等待
                                                设备复位回调
                                                重新装载镜像
                                                unlock(io_lock) ───────▶ 继续
                                              vm_run：重新创建 vCPU 线程
```

### 1.2 重建 VM 还是原地复位

最省事的做法是把 VM 拆了重建：关掉 vm fd，`KVM_CREATE_VM` 再来一遍，所有状态天然是新的。没这么做，原因是复位要保留的东西和要清掉的东西交织在一起：磁盘镜像的 fd 带着排他锁，TAP fd 一关，host 侧的接口和上面的地址就没了，gdb 的 TCP 连接、断点表、`--exit-stats` 的累计计数都挂在 `struct vmm_vm` 上。重建 VM 要把这些一样样摘下来再挂回去，每多一个后端就多一处要记得摘挂的地方。

原地复位是反过来的：VM、vCPU、memslot、设备对象都留着，只把“状态”改回上电时的值。真机的 reset 也是这样：RESET# 让 CPU 和芯片组回到上电状态，但不断电，内存内容还在（这正是冷启动攻击能从刚重启的机器里读出密钥的原因）。QEMU 的 `qemu_system_reset()` 走的也是这条路：逐个调用设备的 reset 回调，`kvm_apic_reset`、`kvm_ioapic_reset`、`kvm_pit_reset` 把复位状态经 `KVM_SET_*` 写回 KVM，RAM 不清零，`-kernel` 指定的内核由固件重新装载。

代价是必须说清楚“上电状态”由哪几部分组成，漏掉任何一部分，复位后的机器就带着上一次启动的残留。

## 二、上电状态由哪几部分组成

### 2.1 四个部分

| 部分 | 状态在哪 | 由谁恢复 |
|---|---|---|
| vCPU 和内核态 PIC/IOAPIC/PIT | KVM 内核里 | `vm_reset`：第一次运行前 GET 出来存好，复位时原样 SET 回去 |
| 中断线电平 | KVM 内核里，但不在上一行的结构体中 | `vm_reset`：恢复 irqchip 之前用 `KVM_IRQ_LINE` 把每根线拉低 |
| 用户态设备的寄存器 | 各设备的结构体里 | 每个设备登记的复位回调 |
| 装进内存的内核、initrd、固件表、页表、BSP 入口寄存器 | guest RAM 和 BSP 寄存器 | `main.c` 的 `linux_load_images`，第一次启动和每次复位共用 |

下面逐个说。

### 2.2 KVM 里的状态：抄下来，而不是算出来

vCPU 的复位值看起来可以照着手册填：Intel SDM 和 AMD APM 都有一张“上电和 INIT 之后的寄存器值”表。但 VMM 要恢复的不是手册里的 CPU，而是“这个 VMM 在这台 host 上启动 guest 时给它的那个状态”：BSP 的入口寄存器是 VMM 按 Linux 启动协议设的，AP 的初始状态是 KVM 创建 vCPU 时给的，CPUID 是 VMM 改写过的，MSR 的复位值和 CPU 型号、KVM 版本都有关系。自己算一份，必然和 KVM 给的不一致。

所以 `vm_power_on_save()` 在第一次 `KVM_RUN` 之前，把每个 vCPU 和 irqchip 的状态全部 GET 出来存着：

```
每个 vCPU：KVM_GET_REGS、SREGS、XSAVE（或 XSAVE2）、XCRS、LAPIC、MP_STATE、VCPU_EVENTS、DEBUGREGS，加上 MSR
整个 VM：  KVM_GET_IRQCHIP（PIC master、PIC slave、IOAPIC 三片）、KVM_GET_PIT2
```

日志里能看到存了多少：

```
[INFO] reset: saved power-on state of 4 vCPU(s), 106 MSRs each, XSAVE 4096 bytes
```

这里有三处细节。

**MSR 存哪些。** `KVM_GET_MSR_INDEX_LIST` 给出 KVM 认为需要保存的 MSR 列表，包括硬件 MSR 和 KVM 自己模拟的 PV MSR（kvmclock、steal time、async PF 等）。列表里不是每一项都能用：有的在这颗 CPU、这份 CPUID 下不存在，读不出来；有的只能读，不能由用户态写回。`KVM_SET_MSRS` 返回成功写入的条目数，遇到第一个失败的条目就停下，所以如果把整张列表存下来，复位时会停在中间，后面的 MSR 全没恢复。`msrs_save()` 逐个试读、试写（写回的是刚读出的值，vCPU 还没跑过，等于没改），两样都过的才存。这台 AMD host 上通过的是 106 个。复位时 `msrs_restore()` 再检查返回值等于条目数，不等就报出停在哪一个 MSR。

**XSAVE 区的大小。** 打开了 AMX 这类大状态时 XSAVE 区超过 `struct kvm_xsave` 的 4 KiB，必须用 `KVM_GET_XSAVE2`，大小由 `KVM_CHECK_EXTENSION(KVM_CAP_XSAVE2)` 给出（`Documentation/virt/kvm/api.rst`）。这台 host 上它返回 4096，于是用普通的 `KVM_GET_XSAVE`。

**挂起的 NMI。** `KVM_GET_VCPU_EVENTS` 返回的 `flags` 里没有 `KVM_VCPUEVENT_VALID_NMI_PENDING`，而 `KVM_SET_VCPU_EVENTS` 只有带着这个标志才会按 `nmi.pending` 设置挂起的 NMI。存下来的时候把它补上，复位时上一次启动遗留的挂起 NMI 才会被清掉。

恢复的顺序也有讲究，写在 `vcpu_restore()` 的注释里：SREGS 里带着 APIC base，要在 LAPIC 之前；MSR 在 LAPIC 之后，因为 TSC deadline 定时器的 MSR 只有 LAPIC 处在 deadline 模式时才有意义；`MP_STATE` 放在最后，AP 回到 `UNINITIALIZED`，等新内核发 INIT/SIPI。

### 2.3 中断线电平不在 IRQCHIP 结构体里

直觉上，`KVM_SET_IRQCHIP` 把 IOAPIC 恢复到上电状态，中断方面就干净了。看 host 内核 `arch/x86/kvm/ioapic.c` 的 `kvm_set_ioapic()`，它只把 `struct kvm_ioapic_state`（重定向表、IRR 等）拷进去。而每个中断源当前的线电平记在 `ioapic->irq_states[]` 里（PIC 那边是 `i8259.c` 的 `irq_states`），KVM 用它把多个中断源的电平“或”起来，只在合成后的电平变化时才算一次边沿。这个数组 `KVM_SET_IRQCHIP` 不碰。

复位前某个设备正把 GSI 拉高着，复位后 IOAPIC 状态是新的，`irq_states` 里却还记着“高”。`irqchip_restore()` 第一步对 GSI 0..23 逐根调 `KVM_IRQ_LINE` 拉低，然后才 `KVM_SET_IRQCHIP`，让 KVM 里记的电平和设备复位后的 0 一致。这一步放在 `vm_reset` 里统一做，而不是指望每个设备的复位回调都记得拉低自己的线。

不过要说清楚，这个残留在目前的 mini-vmm 里看不出效果。`__kvm_irq_line_state()`（host 内核 `arch/x86/include/asm/kvm_host.h`）按中断源的 source id 记一位，返回所有位的“或”；GSI 1..23 上只有 VMM 这一个用户态中断源（PIT 在 GSI 0 上用自己的 source id），设备复位后第一次调 `KVM_IRQ_LINE` 就把这一位改写了。IOAPIC 判断边沿看的是 `irr`（`ioapic_set_irq()` 里 `old_irr == ioapic->irr` 时不送达），而 `irr` 随 `KVM_SET_IRQCHIP` 一起恢复。残留的那一位要等一根 GSI 上有了第二个中断源才会起作用：它通过“或”让这根线一直为高，电平触发的引脚每次 EOI 之后都会被重新送达。这是读源码得出的推断，没有测试覆盖，见 3.5 节。

反过来，设备模型自己也记着线电平（例如 PCI 核心的 `intx_level`、串口的 `irq_level`），只在电平变化时才调 `KVM_IRQ_LINE`。KVM 那边已经拉低了，设备如果还以为线是高的，下一次拉高时就不会发 ioctl。所以每个设备的复位回调要把自己记着的电平也清零。

### 2.4 用户态设备：复位回调

设备在 attach 时用 `vmm_register_reset(vm, name, fn, opaque)` 登记回调，`vm_reset` 持 `io_lock` 按登记顺序调用。PCI 总线先于挂在它上面的设备登记，所以配置空间先回到上电值，设备再复位自己的寄存器。

| 设备 | 复位回调做什么 |
|---|---|
| 串口 8250 | 寄存器回到上电值，清空 RX FIFO，重新计算中断线 |
| i8042 | 控制器状态、输出缓冲区回到上电值 |
| ACPI PM | PM1 事件和控制寄存器清零 |
| PCI 总线 | 每个设备的 256 字节配置空间从注册结束时的快照 `cfg_power_on` 拷回，按恢复后的 BAR 和 COMMAND 重建地址路由，INTx 和 MSI 的跟踪状态清零 |
| e1000 | 走设备自己的 `CTRL.RST` 复位逻辑 |
| AHCI | 先清掉命令列表和 FIS 接收区的基地址，再做 HBA 复位（`GHC.HR`） |
| pci-test | scratch 寄存器清零 |

PCI 配置空间用快照而不是重新算，原因和 2.2 节一样：BAR 的地址是 VMM 在注册时像固件那样分配的，快照就是“固件刚分配完”的那一刻。

AHCI 为什么要额外清基地址：AHCI 1.3.1 第 10.4.3 节规定 `GHC.HR` 复位 HBA 的全局寄存器和端口状态时保留 PxCLB/PxFB 这几个基地址寄存器（HR 是给运行中的驱动用来恢复控制器的，基地址指向驱动已经分配好的内存）。上电时它们是 0，整机复位要回到上电，就得自己清，否则新内核的驱动设置它们之前，残留的地址还指向上一次启动的内存。

RTC 没有复位回调：CMOS RAM 由电池供电，真机复位不改变它的内容，RTC 本身也没有需要撤销的中断状态。

### 2.5 镜像：重新装载

guest 运行时会改写内存里的一切：内核把自己的 `.data`、`.bss` 写满了运行时状态，initrd 在解包后被释放、拿去另作他用，低端的 boot_params、页表、MP table、ACPI 表也可能已经被覆盖。所以复位后必须重新装载。`main.c` 把以前的 `boot_linux` 拆成两半：只做一次的 attach（建设备、开后端），和每次上电都做的 `linux_load_images`（装内核和 initrd，写 MP table、ACPI 表、boot_params、页表，设好 BSP 的入口寄存器）。后者就是 `vm_reset` 的 reload 回调。复位时日志里会再出现一遍装载的过程：

```
[    1.465371] sysrq: Resetting
[INFO] guest requested reset via i8042
[INFO] vmlinux PT_LOAD #0: GPA [0x1000000, 0x285c5f8) file 0x185c5f8 mem 0x185c5f8
...
[INFO] vCPU 0: Linux boot protocol, CS=0x10 DS=0x18 RSI=0x7000
[INFO] reset: guest reset #1 done, restarting vCPUs
[INFO] 4 vCPU thread(s) running
[    0.000000] Linux version 6.6.0 ...
```

RAM 的其余部分不清零，和真机、QEMU 一致。新内核不会假设内存是零：`.bss` 由内核自己清，其余内存经 E820 交给页分配器，用之前会被初始化。

BSP 的入口寄存器是装载时设的，而 `vcpu_restore` 也会恢复寄存器，谁覆盖谁？顺序是先恢复 vCPU、再调 reload，所以 BSP 最终是 reload 设的入口状态。两者其实一样，因为 `vm_power_on_save` 是在第一次 `linux_load_images` 之后调用的，存下来的正是入口状态。

## 三、最反直觉的地方：`reboot -f` 测不出 AP 的问题

### 3.1 一个什么都不恢复也能通过的测试

最先写的验收用例是：`--smp 4`，guest 里连续三次 `reboot -f`，每次都要回到 shell，所有 CPU 都上线。为了确认它能挡住错误，把 `vcpu_restore` 整个去掉，只保留重新装载镜像。结果测试照样通过，四个 CPU 每次都上线。

原因在 1.1 节表格的最后一列。`reboot -f` 走 `native_machine_restart`，先 `machine_shutdown()`，里面 `stop_other_cpus()` 用 IPI 让每个 AP 关中断停在 `hlt` 里，然后 BSP 才去写 0x64。复位后，BSP 从新装载的内核入口开始执行，没恢复的 AP 们还停在 `hlt` 里（MP_STATE 是 `HALTED`）。新内核启动 AP 时照例发 INIT-SIPI-SIPI，KVM 处理 INIT 时调用 `kvm_vcpu_reset(vcpu, true)`（host 内核 `arch/x86/kvm/lapic.c` 里 INIT 的处理），把 AP 复位成等 SIPI 的状态。也就是说，在这条路径上，guest 内核自己替 VMM 把 AP 复位了。

这和 kexec 很像：kexec 也是在同一台“机器”上换一个内核，靠的就是旧内核先把其它 CPU 停好，新内核再用 INIT/SIPI 把它们唤醒，全程不需要固件和硬件复位。

### 3.2 让 AP 在复位那一刻还在跑

要测出 AP 的状态有没有恢复，复位那一刻 AP 必须还在执行旧内核的代码。sysrq-b 正好是这样：`emergency_restart()` 不叫停任何 CPU，直接写 0x64。新的用例在三个后台进程里跑忙循环，占住三个 AP，然后 `echo b > /proc/sysrq-trigger`，复位后检查 `/sys/devices/system/cpu/online` 是不是 `0-3`。

去掉 `vcpu_restore` 再跑，这次挂了：

```
[ERR ] vCPU 1: SHUTDOWN (usually a triple fault)
=== vCPU 1 state ===
  rip=000000000000fff0 rflags=0000000000000002
  cr0=0000000000000010 cr2=0000000000000000 cr3=0000000000000000 cr4=0000000000000000
  cs  sel=f000 base=00000000ffff0000 limit=0000ffff type=a s=1 dpl=0 p=1 l=0 db=0 g=0
  exits=3493 (io=3492 mmio=0 hlt=0)
[ERR ] vCPU 1 stopped with error -5
```

vCPU 1 复位后带着旧内核的 RIP、页表、栈接着跑，可内存已经换成了新装载的镜像，它执行到的是另一份代码和数据，很快 triple fault，KVM 报 `KVM_EXIT_SHUTDOWN`，VMM 按 guest 错误（`VMM_ERR_GUEST`，-5）停机。寄存器 dump 里看到的是复位向量 `f000:fff0`，不是出错时的现场：AMD 上 SHUTDOWN 拦截之后 VMCB 的内容是未定义的，KVM 的 `shutdown_interception()`（`arch/x86/kvm/svm/svm.c`）会先 INIT 这个 vCPU 再把 exit 交给用户态。

只恢复 BSP、不恢复 AP 时，结果相同（vCPU 1 和 2 都 SHUTDOWN）。这个用例现在是 `system-reset` 里挡住 AP 问题的那一条。

### 3.3 BSP 收不到 INIT：PV MSR

3.1 节说 AP 收到新内核的 INIT 时，KVM 会替我们复位它。`kvm_vcpu_reset()`（host 内核 `arch/x86/kvm/x86.c`）在 INIT 和完整复位两种情况下都会清掉 async PF 的 `msr_en_val`、steal time 的 `msr_val`，并调用 `kvmclock_reset()`。但 BSP 从来收不到 INIT，没有任何机制替它清掉这些 PV MSR。

这些 MSR 里登记的是 guest 内存地址：kvmclock 的时间结构、steal time 的计数区，KVM 会持续往登记的地址写。如果不恢复 BSP 的 MSR，复位后新内核在重新登记之前，KVM 还在往旧内核登记的地址写数据，而那块内存现在属于新内核的某个数据结构。

这一项没有测试能挡住。去掉 MSR 恢复，所有用例照样通过：新内核启动很早就会在同样的地址重新登记（同一份 vmlinux，同样的内存布局，地址一样），中间那段时间 KVM 写进去的内容恰好是新内核马上要覆盖的。这里依靠的是对 KVM 行为的推导，测试结果只能说明这次没撞上。

### 3.4 不恢复 irqchip：卡在串口驱动

去掉 `irqchip_restore`（不拉低中断线，也不 `KVM_SET_IRQCHIP`）时，`reboot -f` 的用例仍然通过，sysrq 用例在第二次启动时卡住，最后一行输出是：

```
[    0.544236] Serial: 8250/16550 driver, 4 ports, IRQ sharing enabled
```

之后再没有输出，测试等了 120 秒超时。正常启动时下一行是 ttyS0 的注册信息。IOAPIC 的重定向表、PIC 的屏蔽字和 PIT 的计数状态都还是旧内核写的，新内核在这种状态上初始化中断和串口。具体卡在 8250 驱动的哪一步，没有继续追，这里只把它当作“irqchip 不恢复就会出问题，而且 sysrq 用例能看到”的证据。

### 3.5 小结

| 去掉哪一步 | `reboot -f` 用例 | sysrq-b 用例 | 设备寄存器用例 |
|---|---|---|---|
| 恢复 vCPU 状态 | 通过 | AP triple fault | 通过 |
| 只恢复 BSP | 通过 | AP triple fault | 通过 |
| 恢复 irqchip | 通过 | 卡在 8250 | 通过 |
| 设备复位回调 | 通过 | 通过 | 读回旧值 |
| 恢复 MSR | 通过 | 通过 | 通过 |
| 复位前拉低中断线 | 通过 | 通过 | 通过 |

最后两行是这套测试挡不住的。MSR 的原因见 3.3 节；拉低中断线的原因见 2.3 节：每根 GSI 只有一个用户态中断源时，残留的电平位在设备下一次 `KVM_IRQ_LINE` 时就被改写，本来就观察不到。

## 四、复位时其它线程在干什么

### 4.1 vCPU 线程都已 join，I/O 线程靠 io_lock 挡住

`vm_reset` 的调用条件是所有 vCPU 线程都已 join，所以 KVM 的 vCPU ioctl 不会和 `KVM_RUN` 并发，设备的 MMIO/PIO 回调也不会在复位中途被调用。

I/O 线程没有停。它负责 TAP 收包和串口输入，回调里会改设备状态，e1000 收包时还会 DMA 进 guest 内存。复位时如果让它继续，它可能在镜像装载到一半时往 guest 内存里写一个包，或者看到一个复位了一半的 e1000。`vm_reset` 全程持有 `io_lock`，I/O 线程上的设备回调也要先拿这把锁（`event-loop` 里程碑定下的锁顺序：io_lock → 设备锁 → KVM ioctl），于是复位期间它们在锁外等待，拿到锁时看到的已经是完整复位后的设备：e1000 复位后接收被关闭，收到的包按“接收未使能”处理。

为什么不像停 vCPU 那样停掉 I/O 线程：控制台输入要跨越复位持续可用，TAP 上的包在复位期间被设备按自己的状态丢弃就是真机的行为，停掉再重启线程只是多一处要处理的生命周期。

### 4.2 gdb 跨越复位

gdb 连着的时候，复位对它应该是透明的：连接不断，断点表保留，gdb 已经 continue 的话 guest 复位后直接接着跑，断点照样命中。这里有两个问题。

**软件断点。** 软件断点是 VMM 写进 guest 内存的 int3。重新装载镜像时，内核代码所在的页被新内容覆盖，int3 没了；但装载不一定覆盖断点所在的每一页（比如断点在 initrd 区域之外、内核镜像之外的地方），没覆盖的地方还是 int3。如果只在装载之后统一处理，看到一个 0xCC 时分不清它是我们写的 int3 还是镜像本来的字节。所以分两步：

```
gdbstub_reset_before：装载之前，把每个软件断点的原字节写回内存
reload：              装载镜像
gdbstub_reset_after： 装载之后，重新读出每个断点地址上的字节作为新的原字节，再写入 int3
```

这对 vmlinux 成立，因为 VMM 把 ELF 的各段直接装到物理地址上，装载完的内存就是内核代码。bzImage 不行：VMM 装进去的是压缩的内核和解压器，真正的内核代码由 guest 里的解压器运行时写出来，提前写好的 int3 会被解压结果覆盖。这时断在解压后内核里的位置要用 `hbreak`，硬件断点比较的是线性地址，不在内存里。

**gdbstub 线程怎样判断 VM 结束了。** 以前 gdbstub 线程看到 `vm->running` 变成 false，就给 gdb 发退出报告（`W00`）。复位时 `running` 也会短暂变 false（vCPU 线程全部退出了），如果照旧判断，gdb 会以为 guest 已经结束。现在的规则是 `running` 和 `reset_requested` 同时为 false 才算结束，而 `vm_reset` 里两者的写入顺序是先把 `running` 置回 true、再清 `reset_requested`，保证 gdbstub 线程在任何时刻读到的都不是“两个都为 false”。复位期间 vCPU 报上来的停止事件推迟到 `gdbstub_reset_after` 唤醒 gdbstub 线程之后再处理。

## 五、`--no-reboot`

测试大量依赖“guest 一重启 VMM 就退出”来收尾：`reboot -f` 结束 guest，`rdinit=/nonexistent` 让 guest panic 后重启从而退出。现在默认行为变成了复位，这些用例如果不改，`panic=-1` 会让 VMM 无限重启下去。

`--no-reboot` 恢复以前的语义：`vm_request_reset` 看到 `cfg.no_reboot` 时打一行 `--no-reboot: stopping instead of resetting`，不置 `reset_requested`，`vm_run` 返回后 `main` 直接退出。名字和 QEMU 的同名选项一致。所有靠重启结束 guest 的测试都加上了它。它只对 Linux 模式有意义，其它模式下带上它会报 `--no-reboot requires --mode linux`。

## 六、验证

`make test system-reset` 一共 7 条：

| 用例 | 判据 |
|---|---|
| 参数检查 | 非 linux 模式下 `--no-reboot` 报错退出 |
| `--smp 4` 连续 3 次 `reboot -f` | 挂着 AHCI 磁盘和 pci-test。第一次启动往盘上写 `MARK42`。每次启动打印一行：在线 CPU 列表、PCI/平台/serio 设备列表加磁盘容量加 `/proc/interrupts` 中断源名字的哈希、盘上前 6 个字节。4 行必须完全相同，CPU 列表是 `0-3`，盘上读到 `MARK42`；VMM 报 `reset: guest reset #3 done` |
| sysrq-b | 3 个 AP 在跑忙循环时复位，下一次启动 `cpus=0-3` |
| 设备寄存器 | 改 pci-test 的 scratch 寄存器为 0x12345678、配置空间 cache line size 为 0x10，复位后读回都是 0。选这两处是因为没有驱动会碰它们：Linux 启动时会重新初始化它驱动的设备，在那些地方看不出设备有没有复位 |
| bzImage | 重启后重新解压并进入 shell |
| `--no-reboot` + `reboot -f` | VMM 退出，退出码 0 |
| `--no-reboot` + panic | VMM 只退出一次，不循环 |

“每次启动探测结果一致”为什么用哈希：dmesg 里有很多和时间相关的行（kvm-clock 的偏移、RTC 时间、几条异步打印的先后），整段比较必然不同。设备列表、磁盘容量、中断源名字是设备状态没复位干净时最先变化的东西（驱动报错不绑定、中断源缺失），又和时间无关。

`make test gdbstub` 里多了一条：guest 用 `rdinit=/nonexistent` 启动、不带 `--no-reboot`，每次启动都会 panic 再复位。gdb 先 `hbreak start_kernel` 停住，删掉它，`break rest_init` 在第一次启动里停下，然后 `continue`。第一次启动走到 panic、复位，第二次启动又停在 `rest_init`，此时读 `panic_cpu.counter` 是 -1。第一次启动 panic 过，它的 `panic_cpu` 已经不是 -1，读到 -1 说明内核的数据段确实被重新装载了，停下的是新的一次启动，软件断点在新装载的内核里被重新写好。

## 七、限制

- **MSR 恢复和中断线拉低没有测试覆盖。** 见 3.3 节和 2.3 节，它们的必要性来自对 KVM 源码的推导。
- **bzImage 上的软件断点不跨越复位。** 见 4.2 节，用 `hbreak`。
- **复位只有 i8042 一个入口。** ACPI 的 `RESET_REG` 也指向它；q35 常见的 0xCF9 复位端口没有实现，它和 PCI conf1 的 0xCF8–0xCFF 窗口重叠，理由见 `src/boot/acpi.c` 里 FADT 的注释。guest 只有在 ACPI 和键盘控制器都失败后才会去试 0xCF9。
- **复位不清 guest RAM。** 和真机一致，但这意味着复位前 guest 内存里的数据对复位后的 guest 可见。
