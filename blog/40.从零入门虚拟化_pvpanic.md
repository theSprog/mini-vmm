guest 内核 panic 了，VMM 怎么知道？在这之前 mini-vmm 只能从结局倒推：默认命令行带 `panic=-1`，panic 之后内核立刻请求复位，VMM 看到的是一次和 `reboot -f` 一模一样的 i8042 复位。要分辨“崩了”和“正常重启”，只能去串口输出里搜 `Kernel panic`，这既不可靠（输出可能被截断、被别的行打断，guest 也可以关掉 console），也不是一个接口。pvpanic 给 guest 一个专门的出口：panic 时往一个 I/O 端口写一个字节，VMM 收到就知道发生了什么，并用退出码把结局告诉调用者。

这一篇讲这个设备的规范、guest 怎么发现它、panic 时 guest 内核里发生了什么，以及 mini-vmm 怎么处理三种事件。机制本身很小，原理和实现放在一章里。

## 一、规范：一个端口，三个位

pvpanic 是 QEMU 定义的半虚拟化设备，规范在 QEMU 的 `docs/specs/pvpanic.rst`，位定义在 Linux 的 `include/uapi/misc/pvpanic.h`：

| 位 | 名字 | 含义 | host 该做什么 |
|---|---|---|---|
| 0 | `PANICKED` | guest panic 了 | 由 host 处理 |
| 1 | `CRASH_LOADED` | guest panic 了，但 guest 自己会处理（装了 kdump 内核） | 只记录，不能影响 guest 继续执行 |
| 2 | `SHUTDOWN` | guest 正常关机 | 由 host 处理 |

ISA 版本只有一个端口，默认 0x505，宽 1 字节。读写语义是一个最小的能力协商：

- 读：返回设备认识的位；
- 写：设备不认识的位忽略，软件只应该写双方都认识的位。

“读返回认识的位”让新旧两边可以混用。Linux 驱动把 capability 定为“驱动自己认识的位 & 读端口的值”，以后只发 capability 里的事件。mini-vmm 的设备认识全部三个位，读端口得到 0x07；6.6 的驱动只认识前两个，capability 是 3；7.x 的驱动加上了 `SHUTDOWN`，capability 是 7。两种 guest 都在测试里跑过，结果正是这两个数。

规范还给 ACPI 定义了两个方法 `RDPT`、`WRPT`，作用和读写端口一样。Linux 驱动直接读写端口，不调用它们。

## 二、guest 怎么找到它

PCI 设备有配置空间，guest 扫一遍总线就能发现；ISA 端口上的设备没有任何可枚举的标识，guest 不会去 0x505 上碰运气。这类设备要靠固件表告诉 OS：ACPI 规范 6.1.5 说得很直接，OSPM 只枚举总线枚举器发现不了的设备，ISA 设备就是典型。

于是 DSDT 里多了一个 Device：

```text
Scope (\_SB) {
  Device (PEVT) {
    Name (_HID, "QEMU0001")
    Name (_CRS, ResourceTemplate () { IO (Decode16, 0x0505, 0x0505, 0x01, 0x01) })
  }
}
```

`_HID` 告诉 OS“这是什么设备”，`_CRS` 告诉它“设备占了哪些资源”。Linux 的 ACPI 扫描为它建一个 platform device（名字 `QEMU0001:00`），`pvpanic-mmio` 驱动的 `acpi_device_id` 表里正好有 `"QEMU0001"`，于是绑定。驱动的名字里虽然有 mmio，它同时处理 IO 端口资源：

```c
/* drivers/misc/pvpanic/pvpanic-mmio.c，pvpanic_mmio_probe() */
res = platform_get_mem_or_io(pdev, 0);
switch (resource_type(res)) {
case IORESOURCE_IO:
    base = devm_ioport_map(dev, res->start, resource_size(res));
    ...
pi->capability = PVPANIC_PANICKED | PVPANIC_CRASH_LOADED;
pi->capability &= ioread8(base);      /* 能力协商：VMM 看到一次读 */
pi->events = pi->capability;
```

### 2.1 `_HID` 只能是字符串

mini-vmm 的 DSDT 之前只有一个 `_HID`：host bridge 的 `EisaId("PNP0A03")`，编码成一个 32 位整数。`QEMU0001` 塞不进这种格式：EISA ID 是 3 个字母加 4 个十六进制数字（`AAA####`），压成 15 + 16 = 31 位；`QEMU0001` 是 ACPI ID，4 个字母或数字加 4 个十六进制数字（`NNNN####`），只能写成字符串（ACPI 6.5 6.1.5）。AML 编码器因此多了一个 `aml_string`：

```text
before（只有整数形式）                  after（字符串形式）
08 5F 48 49 44                          08 5F 48 49 44
   NameOp "_HID"                           NameOp "_HID"
0C 41 D0 0A 03                          0D 51 45 4D 55 30 30 30 31 00
   DWordPrefix 0x030AD041                  StringPrefix "QEMU0001" NUL
```

字符串以 `0x0D` 开头、以 NUL 结尾（20.2.3 `String := StringPrefix AsciiCharList NullChar`）。字符串没有长度字段，解析器靠 NUL 找到它的结尾，漏掉 NUL 时它会一直读到下一个 0 字节，把后面的 `_CRS` 也算进字符串，整个 Device 解析错位。

### 2.2 IO 端口描述符

`_CRS` 里只有一个 8 字节的小型资源描述符（6.4.2.5，Table 6.33）加结束标记：

```text
47           I/O Port Descriptor（小型，类型 0x8，长度 7）
01           _DEC = 1：译码全部 16 位地址
05 05        _MIN = 0x0505
05 05        _MAX = 0x0505（固定端口：最小基址 = 最大基址）
01           _ALN
01           _LEN = 1
79 00        End Tag
```

`_DEC` 写 0 表示设备只译码低 10 位地址，那是老 ISA 卡的做法，0x505 在 10 位译码下会和 0x105、0x905…… 混叠。

### 2.3 为什么没有 `_STA`

设备对象缺 `_STA` 时，OSPM 当它存在、启用、工作正常（6.3.7）。pvpanic 不会被拔出也不会被关闭，没有别的状态要报。实测 guest 里 `/proc/ioports` 出现 `0505-0505 : QEMU0001:00`，驱动绑定在它上面。

## 三、panic 时 guest 里发生了什么

`echo c > /proc/sysrq-trigger` 让内核解引用空指针，进入 `panic()`。Linux 6.6 的 `kernel/panic.c` 里，和这里有关的顺序是：

```text
panic("sysrq triggered crash")
  ├─ 打印 "Kernel panic - not syncing: ..." 和调用栈
  ├─ if (!crash_kexec_post_notifiers) __crash_kexec()   ← 装了 kdump 内核就从这里跳走
  ├─ panic_other_cpus_shutdown()                         其余 CPU 被 NMI 停下
  ├─ atomic_notifier_call_chain(&panic_notifier_list)
  │     └─ pvpanic_panic_notify()                         优先级 INT_MAX，第一个被调用
  │           event = kexec_crash_loaded() ? CRASH_LOADED : PANICKED
  │           iowrite8(event, base)                       ← VMM 看到 KVM_EXIT_IO，out 0x505
  ├─ if (crash_kexec_post_notifiers) __crash_kexec()
  └─ panic_timeout != 0 → emergency_restart()             panic=-1 时走到这里：复位
```

两条结局的分叉就在 notifier 那一步：挂了 pvpanic，VMM 在端口写入时就结束了，`emergency_restart()` 根本没机会执行；没挂 pvpanic，guest 走到最后一步，VMM 看到的是 i8042 复位。

有一个容易想错的地方：`CRASH_LOADED` 不是“装了 kdump 就会发”。默认情况下 `__crash_kexec()` 排在 notifier 前面，kdump 内核装着时 guest 直接跳进去，pvpanic 的 notifier 一次都不会被调用。只有 guest 加了 `crash_kexec_post_notifiers` 参数，notifier 才先跑、发出 `CRASH_LOADED`，再跳进 kdump 内核。

## 四、VMM 怎么处理三种事件

```c
/* src/devices/pvpanic.c，pvpanic_write() */
unsigned ev = v & PVPANIC_FEATURES;          /* 不认识的位忽略 */

if (!ev)                      → 记一行 "ignored write"，返回
if (ev & PVPANIC_PANICKED)    → vm->exit_code = 3; return VMM_ERR_EXIT;
if (ev & PVPANIC_SHUTDOWN)    → vm->exit_code = 0; return VMM_ERR_EXIT;
否则（只有 CRASH_LOADED）      → 记一条 warning，guest 继续
```

`VMM_ERR_EXIT` 是 run loop 里“guest 请求停机”的约定信号，和 ACPI S5、0xF4 调试端口走同一条路：所有 vCPU 停下，`main` 返回 `vm->exit_code`。

**PANICKED → 退出码 3。** 这是里程碑要的东西：退出码能区分 panic（3）和正常结束（0）。选 3 而不是 2，是因为 1 已经是“VMM 自身出错”，2 在很多命令行工具里是“用法错误”，用 3 不会和这两种混淆。`--help` 里新增了一节 `Exit status` 列出全部约定。

**CRASH_LOADED → 只记录。** 规范要求 host 不影响 guest 继续执行：guest 接下来要启动 kdump 内核把内存转存出去，VMM 这时退出就把 dump 丢了。

**SHUTDOWN → 当关机处理，退出码 0。** 规范说这个事件“由 host 处理”，但没说处理成什么。看 Linux 怎么发它就清楚了：

```c
/* 7.x drivers/misc/pvpanic/pvpanic.c */
register_sys_off_handler(SYS_OFF_MODE_POWER_OFF, SYS_OFF_PRIO_LOW, pvpanic_sys_off, NULL);
```

`SYS_OFF_PRIO_LOW`（-128）在 `include/linux/reboot.h` 里的注释是“handler of last resort”，ACPI 的关机 handler 是 `SYS_OFF_PRIO_FIRMWARE`（224）。关机时内核按优先级从高到低调用：ACPI S5 能用时 VMM 在 S5 写入时就退出了，pvpanic 的 handler 轮不到；轮到它，说明前面的关机手段都没生效，它写完端口返回，内核接着进入 halt 死循环。这时 host 如果只是记一笔，guest 就永远挂在那里，所以 VMM 把它当成关机请求。Arch guest 的测试里驱动的 capability 是 7、`SHUTDOWN` 打开着，`systemctl poweroff` 照样经 S5 退出，日志里没有 SHUTDOWN 事件，和上面的分析一致。

**同时出现时 PANICKED 优先。** Linux 驱动一次只发一个位，但端口接受任意值。PANICKED 和 SHUTDOWN 都要求 host 介入，panic 是更需要被调用者知道的结局，所以按 panic 处理；CRASH_LOADED 不阻止 host 介入，和 PANICKED 同时出现时也按 panic 处理。

设备没有状态：读永远返回 0x07，写只触发一次动作。所以它不登记复位回调。

## 五、为什么是可选设备

pvpanic 用 `--device pvpanic` 挂上，不默认存在，挂上时 VMM 置 `vm->pvpanic`，`boot/acpi.c` 据此在 DSDT 里加上 `PEVT`。

默认挂上的话，panic 就不再走 `panic=-1` 的复位路径，而复位路径本身也要能测：linux-boot、smp、system-reset 几个 suite 都用“找不到根文件系统的 VFS panic”来触发一次复位，验证 i8042 复位、`--no-reboot`、AP 重新上线。可选还带来一个好处：同一个 panic，挂和不挂设备就是现成的对照组。

DSDT 只在挂了设备时描述它，也是同样的道理反过来：DSDT 里有 `QEMU0001` 而端口上没人响应时，guest 驱动读到的是未注册端口的 0xFF，会以为设备认识全部位，panic 时往空端口写，VMM 什么也收不到。`boot_tables_test` 检查没挂设备时 DSDT 里不出现这个 ID。

`--device` 以前只挂 PCI 设备，pvpanic 是第一个 ISA 设备：它的 attach 不碰 PCI 总线，只注册一个 PIO 区间，也不占 PCI slot。

## 六、实际观察到的执行流

BusyBox guest，2 个 vCPU，挂 pvpanic，跑一条 `echo c > /proc/sysrq-trigger`：

```text
[guest ~]# echo c > /proc/sysrq-trigger
[    1.626973] sysrq: Trigger a crash
[    1.628241] Kernel panic - not syncing: sysrq triggered crash
...（调用栈和寄存器，约 40 ms）
[    1.671020]  </TASK>
[ERR ] pvpanic: guest panicked (events 0x01: PANICKED), exiting with code 3
$ echo $?
3
```

`--exit-stats` 显示从开机到退出，pvpanic 的端口上一共只有两次 exit：

```text
  device                     space         reads       writes
  pvpanic                    PIO               1            1
```

那一次读是驱动 probe 时的能力协商，那一次写是 panic 通知。平时这个设备没有任何开销。

同一条命令去掉 `--device pvpanic`、加 `--no-reboot`，panic 之后 VMM 打印的是 `--no-reboot: stopping instead of resetting`，退出码 0。

## 七、最容易弄错的地方

- **`_HID` 的类型。** ACPI ID 只能写成字符串，按 EISA ID 压缩会得到一个根本不对的整数，驱动匹配不上，guest 不报任何错误，只是没有设备。
- **DSDT 和端口要一致。** 只描述不响应，驱动会读到 0xFF 并在 panic 时写空端口；只响应不描述，驱动不绑定。两者都由 `vm->pvpanic` 一个标志控制。
- **`CRASH_LOADED` 的发出条件。** 依赖 `crash_kexec_post_notifiers`，见第三节。
- **`SHUTDOWN` 在正常 Linux 上几乎不会出现。** 它是最低优先级的关机手段，有 ACPI 时轮不到它；真轮到它时 guest 已经别无出路，host 不处理 guest 就挂死。
- **capability 是交集。** guest 里 sysfs 的 `capability` 是驱动和设备都认识的位，不是设备认识的位。直接读端口才能看到设备的 0x07。

## 八、验证

`tests/e2e/pvpanic.sh` 的用例（`make test pvpanic`）：

| 用例 | 判据 |
|---|---|
| BusyBox，`--device pvpanic --smp 2` | 驱动是 `pvpanic-mmio`，`capability`/`events` 为 3；`/dev/port` 读 0x505 得 0x07；写 0xF8 被整体忽略、guest 继续；写 0xFA 只剩 `CRASH_LOADED`、guest 继续；sysrq-c 后 VMM 打印 PANICKED、退出码 3，没有复位请求 |
| 不挂设备 | guest 里没有 `QEMU0001`；同一个 panic 走复位，`--no-reboot` 下退出码 0，日志里没有 pvpanic |
| 挂设备但 guest 把 `events` 写成 0 | 驱动不写端口，panic 走复位，退出码 0 |
| guest 写 `SHUTDOWN` | 按关机处理，退出码 0 |
| guest 写 `PANICKED|SHUTDOWN` | 按 panic 处理，退出码 3 |
| 两个 `--device pvpanic` | 启动前报错，退出码 1 |
| Arch，发行版内核 | 驱动是模块（`/proc/modules` 里有 `pvpanic_mmio`），按 ACPI modalias 自动加载，capability 7；`systemctl poweroff` 经 S5 退出，没有 SHUTDOWN 事件；sysrq-c 退出码 3 |

两个对照组排除了“VMM 从串口输出认出了 panic”这种可能：guest 里同样打印了 `Kernel panic`，只要驱动没写端口，退出码就是 0。`/dev/port` 不经过驱动，每个字节是一次 `inb`/`outb`，用来送驱动不会发出的取值。

单元测试：`boot_tables_test` 按规范逐字节写出 `_HID` 字符串和 IO 描述符，检查挂设备时 DSDT 里有、不挂时没有；tables suite 用 iasl 把挂了 pvpanic 的 DSDT 反汇编再编译，和原始字节逐字节一致。`aml_test` 检查 `aml_string` 的编码。

`tests/mutate.py pvpanic` 的 10 个源码 mutant 全部变红：DSDT 漏描述、不挂也描述、`_DEC` 写成 10 位译码、字符串漏 NUL 由单测挡住；attach 不置标志、读端口返回 0、不屏蔽未知位、panic 退出码写成 0、`CRASH_LOADED` 让 VMM 退出、`SHUTDOWN` 压过 `PANICKED`，各让 e2e 变红。

## 九、限制

- 真实的 kdump 路径没有测：`CRASH_LOADED` 只由 guest 直接写端口送出。要走真实路径，guest 得预留 crashkernel 内存、装载 kdump 内核并带上 `crash_kexec_post_notifiers`。
- 只有 ISA 版本。QEMU 还有 `pvpanic-pci`（BAR0 上一个字节的 MMIO），机制相同，没有新东西可学。
- panic 之后 VMM 直接退出，不保留现场。QEMU 可以配置成暂停 guest，留给 `dump-guest-memory` 之类的工具取内存；mini-vmm 的 monitor 目前没有内存转储命令，暂停了也取不走什么。
- monitor 里查不到 pvpanic 事件，只能看日志和退出码。
