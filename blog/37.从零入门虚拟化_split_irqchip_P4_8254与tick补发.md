## 一、平台上的接线

PIIX4 8.8 节给出了三个通道的接法：

```text
 OSC 14.31818 MHz ──÷12──▶ CLK 1.193182 MHz（周期 838 ns），三个通道共用
   counter 0：GATE0 接高   OUT0 ──▶ IRQ0（PIC IR0、IOAPIC pin 0）
   counter 1：GATE1 接高   OUT1 ──▶ refresh request（NMISC bit 4 翻转）
   counter 2：GATE2 = NMISC bit 0   OUT2 ──▶ NMISC bit 5，经 bit 1 去扬声器
```

端口 `0x61` 在 PIIX4 里叫 NMISC（NMI Status and Control），可写的是 bit 3:0（bit 0 GATE2，bit 1 扬声器数据使能，bit 3:2 是两个 NMI 源的使能），可读的另有 bit 5（OUT2）、bit 4（refresh 翻转）、bit 7:6（SERR#、IOCHK# 的 NMI 状态）。mini-vmm 没有那两个 NMI 源，bit 7:6 恒为 0；Linux 的 NMI 处理函数会读这两位找原因（`arch/x86/kernel/nmi.c`），读到 0 就知道不是它们。

kernel irqchip 下端口 `0x61` 由 KVM 的 `speaker_dev` 处理（《时间》2.3 节的 `KVM_PIT_SPEAKER_DUMMY`）；split 模式下它和 PIT 一起在用户态，由 `i8254_nmisc_read/write` 处理。

## 二、时间模型：不逐拍推进

### 2.1 为什么不能逐拍模拟

CLK 是 1.19 MHz，逐拍模拟意味着每秒唤醒一百多万次去给计数器减一。真实的芯片当然是逐拍工作的，但它的状态只有两种时刻会被外界观察到：guest 访问端口的时候，和 OUT0 跳变送出中断的时候。只要在这两种时刻能算出“此刻计数器是多少、OUT 是什么电平”，中间的每一拍就不用真的走。

所以 mini-vmm 的 8254 不存“当前计数”，只存“第几个 CLK 脉冲把什么值装进了计数元件（CE）”：

```c
struct i8254_ce {
    bool     active;
    uint32_t n;             /* 装入值，二进制 1..模数（计数 0 表示模数） */
    uint64_t start;         /* 在第 start 个 CLK 脉冲装入 */
    uint32_t phase;
    bool     stopped;       /* GATE 低，或 mode 0 只写了半个计数 */
    uint64_t stop_tick;
    int      forced_out;    /* -1 不强制；0/1 OUT 固定为该值 */
    bool     pend;          /* mode 2/3 计数中写入的新值，在 pend_tick 生效 */
    ...
};
```

时间从单调时钟换算成 CLK 脉冲号：

```c
static uint64_t ns_to_tick(uint64_t ns)
{
    return (uint64_t)((unsigned __int128)ns * I8254_OSC_HZ /
                      (I8254_OSC_DIV * NS_PER_SEC));
}
```

用 14318180 / 12 而不是 Linux 的 `PIT_TICK_RATE 1193182`：后者是前者四舍五入的结果，差 0.28 ppm，长时间运行会累积。

### 2.2 “下一个脉冲装入”

数据手册对写计数的时机说得很具体：新计数“is loaded on the next CLK pulse”，然后才开始递减。在第 T 个脉冲之后、第 T+1 个之前写入的计数，在 T+1 装入。这一拍的偏差决定了 mode 2 的周期是 N 还是 N+1，变异体 `pit-load-same-pulse`（同一拍装入）被 `test_mode2_periodic` 挡下。

### 2.3 六种模式在段内位置 d 上的公式

装入之后已经过去的脉冲数记为 d，每种模式的读数和 OUT 都是 d 的函数（第 9–13 页）：

| 模式 | 读数 | OUT |
|---|---|---|
| 0 计数到终点中断 | n − d（回绕） | d ≥ n 为高；写计数时拉低 |
| 1 可重触发单稳 | n − d（回绕） | d ≥ n 为高；GATE 上升沿触发装入 |
| 2 分频器 | n − (d mod n) | d mod n = n−1 时为低（一拍） |
| 3 方波 | 每拍减 2 | d mod n < ⌈n/2⌉ 时为高 |
| 4 软件触发选通 | n − d（回绕） | d = n 时为低（一拍） |
| 5 硬件触发选通 | n − d（回绕） | d = n 时为低；GATE 上升沿触发装入 |

于是 mode 0 的 OUT 在写计数后第 n+1 个脉冲变高，mode 2 在第 n 个脉冲变低，mode 4 在第 n+1 个脉冲选通，和第 9、11、12 页的原文逐字对得上。mode 3 的奇数计数是个容易错的地方：高半周期比低半周期多一拍（第 11–12 页），变异体 `pit-mode3-odd-symmetric` 把它写成对称的，被 `test_mode3_square` 挡下。

### 2.4 上升沿计数和 `sync()`

IRQ0 是边沿触发的，它关心的不是 OUT0 的电平，而是 OUT0 的上升沿。mode 2 的低电平只持续一个 CLK（838 ns），定时器不可能卡在这个窗口里去采样电平，所以模块对外报告的是“自上次以来 OUT 有几个上升沿”：

```c
uint64_t i8254_poll(struct i8254 *pit, int ch, int *level);     /* 取走上升沿个数 */
uint64_t i8254_next_rise_ns(struct i8254 *pit, int ch);         /* 下一个上升沿的时刻 */
```

在一段装入值不变的时间里，上升沿个数可以直接算：周期模式下 d 每到 n 的正整数倍就是一个。难点在于 guest 随时会写端口改变状态，所以每个改状态的入口都先调 `sync()` 到当前脉冲，把旧状态下 `(last_tick, now]` 里的上升沿记账，再改状态；改完比较前后的 OUT，写端口直接造成的上升沿（比如写 mode 2 的控制字把 OUT 从复位的低电平拉高）也记上。这样两次 `sync` 之间状态恒定，区间计数总是对一段恒定的状态做的。变异体 `pit-missed-periods-merged`（一次唤醒错过多个周期只记一个）和 `pit-control-word-edge-lost`（写端口造成的上升沿不记）分别被挡下。

## 三、数据手册里的细节

几条写错了 Linux 也能启动、但和芯片不一致的规则：

- **控制字的副作用**（第 14 页）：写控制字时控制逻辑立刻复位，OUT 进入该模式的初始电平，CR 和计数锁存被清掉；状态锁存不清。
- **counter latch 和 read-back**（第 7–8 页，图 10、图 13）：锁存后、读完之前再锁存被忽略（变异体 `pit-relatch-overrides`）；状态和计数都锁存时先读到状态（`pit-status-after-count`）。
- **mode 0 只写了 LSB**（第 9 页）：原文第 1) 条说写 LSB 时 OUT 立刻变低、“does not disable counting”，第 3) 条又说计数还没回绕到 FFFFh 之前写 LSB 会停住计数。两条冲突，按更具体的第 3) 条（变异体 `pit-mode0-lsb-keeps-counting`）。
- **mode 2/3 计数中写新值**：不影响当前周期，到周期末尾（mode 3 是当前半周期末尾）才换上（变异体 `pit-rewrite-immediate`）。这对 Linux 不是问题，它总是先写控制字再写计数；但 `i8254_next_rise_ns` 必须看到待生效的新值，否则定时器会按旧周期排（变异体 `pit-next-rise-ignores-pending`）。
- **GATE**（图 21）：mode 2/3 下 GATE 变低立刻把 OUT 拉高、停止计数，GATE 上升沿重新装入；mode 0/4 下 GATE 低只是暂停，恢复后接着数（变异体 `pit-gate-low-out-unforced`、`pit-gate-resume-restarts`）。只有通道 2 的 GATE 能变，它就是端口 `0x61` 的 bit 0。
- **BCD 计数**：计数 0 等于 10000 而不是 65536（变异体 `pit-bcd-ignored`）。

### 3.1 端口 0x61 的两个可读位

bit 5 就是 OUT2，读的时候先 `sync` 通道 2 再取电平。Linux 慢路校准就是靠不停地读它等 OUT2 变高（第七章），变异体 `pit-nmisc-out2-constant` 把它写成常数，被 `test_nmisc` 挡下。

bit 4 是 refresh 翻转位，PIIX4 8.8 节说 refresh request 由 counter 1 产生，所以取 OUT1 上升沿个数的奇偶。KVM 的 `speaker_ioport_read` 用的是近似：`(ktime_get() >> 14) & 1`，大约每 16 µs 翻转一次，不看 counter 1。mini-vmm 照芯片接线实现，代价是 guest 不编程 counter 1 时这一位不动。Linux 不读这一位，BIOS 才会用它做延时。

## 四、接到 IRQ0 上

主板（`split_irqchip.c`）在三个时刻处理通道 0：

```c
static void pit_service(struct split_irqchip *s)
{
    int level;
    uint64_t edges = i8254_poll(&s->pit, 0, &level);

    s->pit_ticks += edges;
    if (s->pit_reinject) {
        s->pit_backlog += edges;
        pit_reinject_kick(s);
    } else if (edges) {
        s->pit_coalesced += edges - 1;
        pit_pulse(s);
    }
    timer_arm(s, i8254_next_rise_ns(&s->pit, 0));
}
```

- timerfd 到期时（I/O 线程，`pit_timer_cb`）；
- guest 写 PIT 端口或 `0x61` 之后（vCPU 线程，`port_write`），因为写端口可能改变下一个上升沿；
- 复位时。

timerfd 用 `TFD_TIMER_ABSTIME` 设成 `i8254_next_rise_ns` 给出的绝对时刻，一次性的，每次处理完重新设。`i8254_next_rise_ns` 向上取整到那个脉冲之后，保证定时器到期时 `i8254_poll` 一定能看到这个上升沿，不会因为舍入早醒一点什么也看不到，又空转一次。

OUT0 的电平本身不接到线上，线上的形状由 `pit_pulse` 产生（先低后高，P3 8.2 节）。原因在下一章：补发积压期间 OUT0 照样上升，线如果跟着 OUT0 走，这个上升就绕过补发直接在引脚上成了一个边沿。

## 五、tick 补发

### 5.1 问题

PIT 的 tick 是按 host 的真实时间产生的，guest 处理 tick 却要 vCPU 在跑。host 过载、vCPU 线程被换下去时，tick 照样到期，guest 却没机会处理。PIC 和 IOAPIC 对同一根边沿线上还没处理的请求只记一次（PIC 的 IRR 是一位，IOAPIC 边沿引脚第二个上升沿到来时上一个消息已经发出），所以 vCPU 回来时，欠下的 N 个 tick 最多变成一个中断。

guest 如果靠数 tick 计时，就丢了 N−1 个 tick 的时间。Linux 在 PIT 承担 tick 的配置下（周期 tick，没有更好的 clocksource 时）正是这样：`tick_periodic` 每个 IRQ0 调一次 `do_timer(1)`，jiffies 加一。

KVM 内核 PIT 的默认策略是补发（reinject），由 `KVM_REINJECT_CONTROL` 开关（api.rst 4.99 节；`arch/x86/kvm/i8254.c`）：

- 欠下的 tick 记在 `pending` 里；
- 送出一个之后，等 guest 确认（ack notifier：PIC 上清掉 IRQ0 的 ISR 位，或 IOAPIC 上 pin 0 的向量收到 EOI），确认之后才送下一个；
- 积压在这些时候清零：通道 0 重新装数（`create_pit_timer`）、IRQ0 被解除屏蔽（`pit_mask_notifer`）、复位（`kvm_pit_reset`），以及运行中打开补发时（`kvm_pit_set_reinject`），都是调 `kvm_pit_reset_reinject`。解除屏蔽这一条的理由是：屏蔽期间送出的 tick 在 IOAPIC 上直接丢掉，永远等不到确认，不清的话解除屏蔽后 PIT 就哑了。

补发的代价是 vCPU 回来之后，欠下的 tick 背靠背地送进来，guest 在很短时间内处理一串时钟中断。

### 5.2 用户态实现同样的两种策略

`--pit-reinject on|off`，默认 on，两种 irqchip 模式下语义相同：kernel 模式下 mini-vmm 在 `KVM_CREATE_PIT2` 之后调 `KVM_REINJECT_CONTROL`，split 模式下由主板自己实现。

```c
/* on：上一个 tick 已确认且有积压时送下一个 */
static void pit_reinject_kick(struct split_irqchip *s)
{
    if (s->pit_backlog && s->pit_irq_ack) {
        s->pit_irq_ack = 0;
        s->pit_backlog--;
        pit_pulse(s);
    }
}
```

off 策略就是 `pit_service` 里的 else 分支：一次唤醒里攒下多个上升沿只送一个脉冲，多出的计入 `pit_coalesced`。

on 策略的难点是“确认”从哪来。KVM 在内核里，PIC 清 ISR、IOAPIC 收 EOI 时直接调 ack notifier。用户态这边：

- **PIC 路径**：IRQ0 的 ISR 位从 1 变 0 就是确认。主板在每次写 PIC 主片之后、每次 INTA 之后比较 ISR bit 0（`pit_watch`）。AEOI 模式下 ISR 根本不置位（P3 6.3 节），INTA 交出 IRQ0 本身就是确认，在 `split_irqchip_pre_run` 里单独判断。
- **IOAPIC 路径**：需要 pin 0 的 EOI。可 IRQ0 是边沿中断，P1 2.3 节讲过，KVM 只为路由里标成 level 的向量产生 `KVM_EXIT_IOAPIC_EOI`。办法是 reinject 打开时，把 pin 0 的路由标成 level：

```c
if (pin == 0 && s->pit_reinject &&
    IOAPIC_RTE_DELMOD(rte) <= IOAPIC_DELMOD_LOWEST)
    data |= 1u << 15;
```

投递仍然走 `KVM_SIGNAL_MSI` 的 edge 消息，LAPIC 的 TMR 跟消息走，guest 看到的还是边沿中断，只是它的 EOI 会退出到用户态。KVM 内核 IOAPIC 对挂了 ack notifier 的边沿引脚做的是同一件事（`ioapic.c` 的 `kvm_ioapic_scan_entry` 里的 `kvm_irq_has_notifier` 条件）。P1 4.2 节 `info irqchip` 里 280 次 EOI 退出、几乎全是 pin 0 的，来源就在这里。

- **清积压**：写通道 0 计数之前（先按旧计数把到期的 tick 交给策略再清），PIC IMR bit 0 或 RTE 0 的 mask 从 1 变 0 时，复位时。和 KVM 的前三个清零点一一对应；第四个（运行中打开补发）在这里不存在，策略在启动时就定了。

### 5.3 实验：让 vCPU 停一秒

“host 过载”不好精确复现：stress-ng 抢 CPU 的效果取决于 host 的核数和调度器，同一条命令在不同机器上欠下的 tick 数不同。实验用一个确定的替代：`kill -STOP` 整个 VMM 进程一秒再 `kill -CONT`。这一秒里 vCPU 线程和 I/O 线程都不跑，guest 的时间流逝和 host 被抢占的效果一样，而欠下的 tick 数是确定的 1000 个（HZ=1000）。

guest 用 `noapictimer nohz=off highres=off` 启动：不用 LAPIC 定时器，tick 由 PIT 的周期模式（mode 2，计数 1193）承担；关掉 NO_HZ 和高精度定时器，保证每个 tick 都来自 PIT。测量在 guest 里读 `/proc/timer_list` 的 `now at`（`ktime_get`，由 TSC clocksource 给出的真实时间）和 `jiffies`，以及 `/proc/interrupts` 里 IRQ0 的计数，在 SIGSTOP 前后各读一次，中间 guest 再 `sleep 2`：

| 模式 | 策略 | 真实时间 Δ（ms） | jiffies Δ | 漂移（ms） |
|---|---|---|---|---|
| kernel | reinject on | 3076 | 3077 | −1 |
| kernel | reinject off | 3031 | 2029 | 1002 |
| split | reinject on | 3051 | 3052 | −1 |
| split | reinject off | 3032 | 2029 | 1003 |

漂移 = 真实时间 Δ − jiffies Δ（HZ=1000，一个 jiffy 1 ms）。每次测量 IRQ0 的增量都等于 jiffies 的增量，说明 jiffies 确实是一个 IRQ0 一个 tick。

- reinject off：SIGSTOP 那一秒的 1000 个 tick 合并成 1 个，jiffies 落后真实时间约一秒，此后不再追回。两种 irqchip 模式的结果一样。
- reinject on：vCPU 恢复后，欠下的 1000 个 tick 一个确认一个地送进来，jiffies 追平真实时间。split 模式下 `info irqchip` 显示 `coalesced 0`，积压在测量时已清空。

split-irqchip 套件把这个实验做成 4 个用例（两种模式 × 两种策略），判据是 on 时 |漂移| ≤ 50 ms，off 时漂移 ≥ 500 ms，|IRQ0 增量 − jiffies 增量| ≤ 10；split 模式下 on 要求 `coalesced` 为 0、`backlog` ≤ 2，off 要求 `coalesced` ≥ 500。套件末尾的 manual guide 写了用 stress-ng 在真实过载下重复这个实验的步骤。

### 5.4 反直觉：`noapic` 下补发几乎不起作用

把 5.3 的实验原样再做一遍，只在命令行上多加一个 `noapic`，让 IRQ0 改走 8259A：

| 模式 | 策略 | 真实时间 Δ（ms） | jiffies Δ | 漂移（ms） |
|---|---|---|---|---|
| kernel | reinject on | 3012 | 2012 | 1000 |
| kernel | reinject off | 3012 | 2012 | 1000 |
| split | reinject on | 3011 | 2011 | 1000 |
| split | reinject off | 3011 | 2011 | 1000 |

补发开着，停掉的那一秒照样全丢。split 模式的 `info irqchip` 给出了去向：

```
pit: reinject on, ticks 3823, irqs 2817, coalesced 0, acks 2817, backlog 0, dropped 1006
```

`coalesced` 是 0，说明策略确实把 1000 个 tick 都放进了积压；`dropped` 是 1006，说明它们是被“清积压”这条规则扔掉的，不是被合并的。

原因在 Linux 处理 PIC 中断的方式（P3 4.1 节）。`i8259A_chip` 的流控是 `handle_level_irq`，每个 IRQ0 都按这个顺序碰一遍 PIC：

1. `mask_and_ack_8259A`：写 IMR 把 bit 0 置上（屏蔽），再写 `0x60` 对 IRQ0 发 specific EOI；
2. 跑时钟中断处理函数；
3. `cond_unmask_irq` → `unmask_8259A_irq`：写 IMR 把 bit 0 清掉（解除屏蔽）。

第 1 步的 EOI 清掉 ISR bit 0，补发策略把它当作确认，从积压里取一个 tick 拉一次线，IRR 置上，但这时 IRQ0 屏蔽着，不会马上送出。第 3 步解除屏蔽，正好命中“IMR bit 0 从 1 变 0 就清积压”这条规则，剩下的九百多个 tick 一次清空。所以 VMM 恢复后，guest 只多收到一两个 tick。

KVM 内核 PIT 的行为完全一样：PIC 的 OCW1 改了 IMR 就调 mask notifier，`pit_mask_notifer` 在解除屏蔽时调 `kvm_pit_reset_reinject`。这不是哪一边实现错了。清积压这条规则本来是防止“屏蔽期间送出的 tick 永远等不到确认”，它假设解除屏蔽是一件少见的事；Linux 的 PIC 路径每个中断都解除一次屏蔽，这个假设就不成立了。IOAPIC 路径没有这个问题：边沿引脚走 `handle_edge_irq`，不会每次中断都改 RTE 的 mask 位，所以 5.3 里补发能把积压送完。

kernel 模式的这组启动有一个与补发无关的现象：`noapic noapictimer` 下大约每五次启动有一次卡住，原因是 KVM 内核 PIC 的中断丢失，见第九节。表里的两行取自正常启动的那几次。

### 5.5 该开还是该关

现代 Linux 不靠 tick 数计时：默认配置（NO_HZ、高精度定时器）下，`timekeeping` 从 TSC 或 kvmclock 读真实时间，jiffies 由 `tick_do_update_jiffies64` 按经过的真实时间补齐，丢 tick 不丢时间。补发对它只有副作用：一串背靠背的时钟中断。而 `noapictimer nohz=off` 这种让 PIT 独自承担 tick 的配置，在正常的 Linux guest 里根本不会出现。KVM 默认开补发是为了靠数 tick 计时的老系统。mini-vmm 两种模式都默认 on，和 KVM 保持一致，这样同一个 guest 在两种模式下的行为可以直接对照。

## 六、TSC 校准的路径

### 6.1 Linux 的慢路

没有 kvmclock 时（`no-kvmclock`），guest 要用 PIT 测 TSC 频率。《时间》2.2 节讲了快路 `quick_pit_calibrate()`，嵌套虚拟化下它总是静默失败（`tests/lib.sh` 的 `expect_tsc_calibrated` 注释），于是走慢路 `pit_calibrate_tsc()`：

```c
/* arch/x86/kernel/tsc.c */
    outb((inb(0x61) & ~0x02) | 0x01, 0x61);    /* GATE2 高，扬声器关 */
    outb(0xb0, 0x43);                          /* 通道 2，mode 0 */
    outb(latch & 0xff, 0x42);                  /* CAL_LATCH：10 ms */
    outb(latch >> 8, 0x42);
    ...
    while ((inb(0x61) & 0x20) == 0) {          /* 等 OUT2 变高 */
        t2 = get_cycles();
        delta = t2 - tsc;
        tsc = t2;
        if ((unsigned long) delta < tscmin)
            tscmin = (unsigned int) delta;
        if ((unsigned long) delta > tscmax)
            tscmax = (unsigned int) delta;
        pitcnt++;
    }
    if (pitcnt < loopmin || tscmax > 10 * tscmin)
        return ULONG_MAX;                      /* 判废 */
```

每一轮在 10 ms 里不停地读端口 `0x61`，记下两次读之间 TSC 差值的最小值和最大值。两条判据都在防 SMI 之类的打断：读的次数少于 1000 次，或者最慢的一次比最快的一次慢 10 倍以上，这一轮作废。调用方 `pit_hpet_ptimer_calibrate_cpu` 跑三轮，取最小的有效结果。mini-vmm 的 FADT 不提供 PM timer、也没有 HPET，三轮都用 10 ms 的参数（有参照时钟才会在两轮失败后换成 50 ms、5000 次，见 `pit_calibrate_tsc` 调用方的 `ref1 == ref2` 分支）。三轮全部作废就是 `Unable to calibrate against PIT`，TSC 被标为不稳定，clocksource 退回 `refined-jiffies`。

### 6.2 在嵌套虚拟化下，读一次端口要多久

每读一次 `0x61` 是一次 exit：kernel 模式下在 KVM 里处理，split 模式下回到用户态。开发机是 WSL2（Hyper-V 上的嵌套 KVM），每次 exit 都要经过 L0 的 Hyper-V，代价比裸机大一个数量级。下面的数字依赖这个环境，换到裸机 KVM 上要重新测（`tools/guest/pitprobe.c` 就是为此写的）。

`pitprobe` 在 guest 用户态重放同一个循环，打印每一轮的读次数、最小/最大间隔和判废原因。它不能关中断（用户态的 `iopl` 不给 CLI 权限），guest 自己的 tick 会落进来，所以只能在同一配置下横向比较两种模式，不能当成内核校准的成功率：

| 模式 | 最快一次读 | 每轮读次数 | 判废的主要原因 |
|---|---|---|---|
| kernel | 约 16000 周期（约 5 µs） | 约 1700–1880 | 最大间隔超过最小间隔的 10 倍 |
| split | 约 28000 周期（约 8.8 µs） | 约 1070 | 读次数低于 1000 |

两种模式下，用 TSC 量出的 10 ms 窗口中位数都是约 31.92M 周期，即 3192 MHz，和 kvmclock 报的 3193.9 MHz 差 0.06%：用户态 PIT 的计时和内核 PIT 一样准，差别只在读一次端口有多贵。

这两条判据对“读得慢”的反应是相反的。split 模式每次读多走一趟用户态，最快一次读从 5 µs 变成 8.8 µs，10 倍的阈值随之放宽到 88 µs，偶发的长延迟不再触发第二条判据；可 10 ms 里只读得了一千次出头，离 1000 次的下限很近，一次稍长的打断就让次数掉到下限以下。kernel 模式读得快，次数富余，但阈值只有 50 µs，嵌套环境下偶发的一次几十微秒的延迟就足以判废。

### 6.3 启动日志里的结局

同一配置（`no-kvmclock`，1 个 vCPU，256M，host 空闲）每种模式连续启动 10 次，数 dmesg 里的结局：

| 模式 | `Fast TSC calibration using PIT` | `Using PIT calibration value` | `Unable to calibrate against PIT` |
|---|---|---|---|
| kernel | 0 | 3 | 7 |
| split | 0 | 10 | 0 |

两种模式都没有走成快路：`quick_pit_calibrate` 要求在很短的时间内读出 PIT 计数并外推到 500 ppm 的精度，嵌套环境下每次读的延迟抖动太大，它静默返回 0，交给上面的慢路。

慢路的结果和 6.2 的分析一致：kernel 模式多数时候三轮都被“最大间隔超过 10 倍”判废，TSC 被标为不稳定；split 模式三轮里总有一轮通过。这不说明用户态 PIT 更好，只说明在这个环境里它恰好落在两条判据都满足的区间里。split 模式的每轮读次数离 1000 次的下限只有百分之几的余量，host 稍忙时同样会出现 `Unable`，套件运行中见到过。所以 `tests/lib.sh` 的 `expect_tsc_calibrated` 在两种模式下都接受三种结局：它们都是 Linux 对“参照时钟不可信”的正当反应，不是 VMM 的错误。

结局不同的后果在 guest 里看得见：成功时 clocksource 用 TSC，`Calibrating delay loop (skipped)` 直接由 TSC 频率算 lpj；失败时 TSC 被标为不稳定，clocksource 是 `refined-jiffies`，`Calibrating delay loop` 现场跑出一个只有几十 BogoMIPS 的值。

## 七、最难或最反直觉的地方

**IRQ0 关心的是上升沿，不是电平。** 8254 的模型最初很自然地想做成“报告 OUT 的电平变化”，可 mode 2 的低电平只有 838 ns，任何基于定时器的采样都会错过它。改成数上升沿之后，“定时器晚到错过几个周期”也自然有了答案：一次取到多个沿，补不补发交给策略。

**确认信号从哪来。** KVM 的补发靠 ack notifier，那是内核里的函数回调。搬到用户态之后要从三个地方收集同一个信号：PIC 的 ISR、AEOI 下的 INTA、IOAPIC 的 EOI 退出。最后一个还要靠把边沿引脚的路由标成 level 才能拿到，这是在利用 KVM 的路由规则，而 KVM 自己的内核 IOAPIC 恰好也是这么做的。

**补发的“清零”规则。** 只实现“等确认再送下一个”是不够的：屏蔽期间送出的 tick 永远等不到确认，PIT 就哑了。KVM 用三个清零点解决这个问题，用户态必须一个不少地对上，而其中“解除屏蔽”这一条和 Linux 的 PIC 中断处理方式相遇时，又让补发在 `noapic` 下形同虚设。

## 八、验证

**单元测试** `tests/unit/pit_test.c`，18 个用例，用假时钟驱动，按 Linux 实际的端口序列编排：`pit_set_periodic`（mode 2）、`pit_set_oneshot` / `pit_next_event`（mode 4）、`pit_calibrate_tsc`（端口 `0x61` + mode 0）、`quick_pit_calibrate`（不锁存直接读 mode 0 的计数），以及 latch、read-back（图 13 的序列）、mode 1/3/5、GATE、BCD、宽访问和端口 `0x61` 的各个位。

**变异测试** 17 个 `pit-*` 变异体全部被预期的断言挡下（第二、三章提到的那些）。接线层的 `backlog-discarded`（积压直接丢弃）、`policy-ignored`（不看 `--pit-reinject`）、`pin0-route-edge`（pin 0 的路由不标 level，IOAPIC 路径收不到确认）、`unmask-keeps-backlog`（解除屏蔽不清积压）和 kernel 模式的 `kernel-reinject-always-on`（不调 `KVM_REINJECT_CONTROL`）由 split-irqchip 套件的补发用例挡下。

**e2e**：5.3 节的四个补发用例；两种模式下 `no-kvmclock` 启动都能确定 TSC 频率（三种合法结局之一，日志里打印走了哪条路径）；主启动用例里 `pitprobe` 测出的频率和 `tsc: Detected` 相差不超过 1%。

## 九、限制

- kernel 模式（`--kernel-irqchip on`）加 `noapic noapictimer` 启动时，大约每五次有一次卡住，原因在 KVM 的内核 PIC，不在 VMM。现象是串口输出停在 `Serial: 8250/16550 driver` 之后（guest 的时间戳其实在 `Calibrating delay loop` 之后就不再前进），KVM 的 `irq_injections` 整次启动停在个位数，`halt_exits` 每秒增长十几万。split 模式和只加 `noapic` 的 kernel 模式各跑十几次没有出现过。

  机理分三步。第一，KVM 的内核 PIC 只在 INT 输出出现上升沿时通知 vCPU，而且只通知那一刻 LVT0 能接收 ExtINT 的 vCPU（`pic_unlock()` 里用 `kvm_apic_accept_pic_intr()` 判断）。第二，Linux 的 `setup_local_APIC()` 先清 SPIV 的使能位把 APIC 软关闭，KVM 随之屏蔽所有 LVT；写完一串 APIC 寄存器之后，最后才把 LVT0 写成未屏蔽的 ExtINT。IRQ0 的 tick 正好落进这段窗口时，上升沿到来时没有 vCPU 能接收，这次通知就丢了。第三，PIC 的 INT 输出会一直保持高电平，直到 CPU 用 INTA 取走中断，所以之后不会再有新的上升沿；而 KVM 处理 LVT0 写入时（`kvm_lapic_reg_write()`）不发 `KVM_REQ_EVENT`，不会回头检查 PIC。于是这个 tick 永远注入不进去，后面的 tick 又被它堵在 PIC 里，guest 的时钟就停了。vCPU 执行 HLT 后立刻被唤醒，是因为判断“有没有事件”的 `kvm_vcpu_has_events()` 看的是 PIC 输出，输出一直为高；但真正注入的路径只在收到 `KVM_REQ_EVENT` 时才检查，两边对不上，vCPU 就在“醒来、没东西可注入、再 HLT”之间空转。“大约五次一次”就是 tick 落进那段窗口的概率。

  同类的漏洞还有一处：guest 通过 `IA32_APIC_BASE` 把 APIC 整个关掉时，LINT0 直接成为 CPU 的 INTR 引脚，锁存在 PIC 里的中断此时应该送达，KVM 的这条路径（6.6 的 `kvm_lapic_set_base()`）同样不发 `KVM_REQ_EVENT`。Linux 正常启动不走这条路径，但它和 LVT0 那条是同一个根因。

  这个问题在最新的 KVM（kvm-x86/next）上依然存在。上游已经有人提交了修 LVT0 这条路径的补丁，正在讨论中（kvm 邮件列表，Message-ID `20261008-lapic-extint-lvt0-unmask-fix-v1-1-db2bf68fba75@collabora.com`）。我们在同一线程里补充了能确定性复现的 KVM selftest、APIC 硬件关闭那条路径的修复，以及维护者提出的“只对 level 触发的 LVT 重新检查”这一改法对 Linux 无效的反例（Linux 写 LVT0 时不带 level 位）。修复进入 host 内核之前，`split-irqchip` 套件不用这个组合；套件的 `noapic` 用例不带 `noapictimer`，不受影响。复现：`build/vmm --mode linux --kernel-irqchip on --append 'noapic noapictimer nohz=off highres=off' ...` 连续启动十次，卡住时用 monitor 的 `info exit-stats` 看上面两个计数。
- refresh 翻转位跟随 counter 1，guest 不编程 counter 1 时不动（3.1 节）。
- 扬声器只有端口位，没有声音输出。
- 补发策略只有 on/off 两种。在两者之间还可以做折中，例如加快送 tick 的频率去追赶积压（slew），机制上没有新东西。
- split 模式下 IOAPIC 路径的确认依赖 pin 0 的 EOI 退出，而 AMD AVIC 对边沿中断（TMR=0）的 EOI 写由硬件直接完成、不退出。KVM 内核 PIT 遇到的是同一个问题，它的对策是补发打开时禁用 APICv（`kvm_pit_set_reinject` 里的 `APICV_INHIBIT_REASON_PIT_REINJ` 及其注释）；用户态 PIT 补发时 KVM 并不知道，不会禁用。所以在开了 AVIC 的 AMD host 上（`kvm_amd avic=1`），split 模式加 `--pit-reinject on` 时 IOAPIC 路径收不到确认，第一个 tick 之后积压只增不减。开发机的 `avic` 是关的（Linux 6.6 的默认值），这个组合没有验证过。Intel APICv 不受影响：它的 EOI-exit bitmap 就是从 `ioapic_handled_vectors` 装的。
